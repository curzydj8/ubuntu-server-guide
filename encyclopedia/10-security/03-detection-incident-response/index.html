    检测与应急响应¶

    本篇只讲防御侧：怎么发现事件、怎么止损、怎么恢复、怎么复盘。 不写规避检测的方法，不写针对真实系统的攻击步骤；示例一律用自有设备的日志。

    1. 技术原理¶

    1.1 检测与响应的位置¶

    安全工作分三层：预防（不让坏事发生）、检测（坏事发生了要知道）、响应（知道了要处置）。本篇讲后两层。预防做得再好也有漏网的时候——新漏洞、配置漂移、内部误操作都会绕过预防层；没有检测与响应，预防层的失效要等到损失扩大后才会被发现。

    检测与响应是一个闭环，不是两件独立的事：检测输出“事件”，响应输出“处置结果”，处置结果（根因、影响面）反过来改进检测（补规则、补日志、补基线）。没有复盘的响应，下次同一个问题还会以同一种方式被发现。

    1.2 检出思路：三种信号¶

    • 已知坏特征：与已知威胁特征匹配的信号——恶意文件哈希、已知恶意域名、公开漏洞的利用特征。优点是误报低，缺点是只能发现“已知的坏”。
    • 异常行为：与基线偏离的信号——平时不登录的账号深夜登录、平时不访问的目录突然被批量读取、平时稳定的服务突然大量崩溃。优点是能发现未知问题，缺点是误报多，需要基线与人工研判。
    • 关联分析：单条日志看不出问题，多条日志拼出问题——例如“新账号创建 + 权限提升 + 大量数据读取”三条先后出现。关联分析的价值在于把孤立事件连成事件链，难点在于日志要全、时间要准、字段要一致。

    三者不是三选一：已知特征负责“快”，异常行为负责“广”，关联分析负责“准”。小型团队可以先从已知特征与关键异常做起，再补关联。

    1.3 应急响应流程（NIST SP 800-61 的四阶段思想）¶

    公开的应急响应框架（NIST SP 800-61）把流程分为四个阶段，本篇按这个思想展开，只讲管理与防御动作：

    1. 准备：平时的工作——资产清单、日志留存策略、联系人清单、隔离与恢复手段、演练。事件发生时才准备，已经晚了。
    2. 检测与分析：确认“是不是事件”、定级（影响面与紧急度）、初步遏制判断。定级不清就动手，容易把小事搞大或把大事搞小。
    3. 遏制、根除与恢复：先止损（隔离受影响系统），再根除（去掉立足点、补漏洞、改口令），最后恢复（从可信备份或干净镜像重建，分批恢复并持续观察）。
    4. 事后活动：复盘（时间线、根因、处置得失）、改进（补检测规则、补流程、补演练）、归档（事件报告留存）。

    顺序不能乱：没有确认就隔离，可能误伤业务；没有根除就恢复，问题会复发；没有复盘就结项，下次还会重演。

    1.4 日志：检测的原材料¶

    日志是检测唯一可靠的原材料。关键要求有四条：

    • 全：系统日志、应用日志、认证日志、网络设备日志、云审计日志，能接的都接；缺一类，关联分析就断一环。
    • 准：时间同步（NTP）是前提——时间对不上，事件链就拼不起来。
    • 久：留存期要覆盖“发现滞后”——很多事件被发现时距离发生已有数周，留存期只有几天就等于没有日志。
    • 不可篡改：日志集中存放、限制写入权限，攻击者拿到一台机器不等于能改掉所有日志；本地日志被改是常事，集中日志被改才是事件升级的信号。

    2. 合法研究范围¶

    • 本篇讨论的检测与响应只在以下范围内合法：自有设备与自有系统的日志分析与处置、授权系统的应急处置（按授权与合同约定的职责范围）、隔离靶场上的演练。
    • 未授权测试他人系统是违法行为，本文不提供相关指导；应急响应中接触到的他人系统与数据，只在授权与法定职责范围内处理。
    • 处置中可能接触用户数据：按“最小必要”查看，查看范围记入事件记录；超出处置需要的数据不查看、不留存、不扩散。

    3. 实验环境¶

    • 环境：自有设备——自己的测试虚拟机与自己的服务器日志；演练用隔离靶场，不拿生产事件练手。
    • 软件与版本：只列防御、检测、分析类工具——日志集中工具、告警平台、基线核查工具、备份恢复工具；不列规避检测类工具。
    • 权限要求：自有设备上的日志读取权限；生产处置权限按组织内的应急职责授予，不在本篇讨论个人获取方式。
    • 一个无害的日志自查示例（环境：自有测试虚拟机，Ubuntu 24.04；输出为示例）：
    # 只查自己这台机器最近一小时的 SSH 服务日志，不对外、不碰他人系统
journalctl -u ssh --since "1 hour ago" --no-pager | head -20

    示例输出（示例，非真实日志）：

    Nov 04 00:10:01 testvm sshd[1234]: Accepted publickey for muse from 127.0.0.1 port 40000 ssh2
Nov 04 00:12:44 testvm sshd[1235]: Failed password for root from 127.0.0.1 port 40001 ssh2

    读法：第一条是本机回环地址的正常密钥登录；第二条是本机回环地址对 root 的口令失败——在靶场里这是自己演练的记录，在生产里“失败口令 + 非常用来源 + 高频出现”三者叠加才构成需要研判的信号；单条失败记录本身不是事件。

    4. 风险¶

    • 误判风险：把正常运维当成事件隔离，误伤业务。规避：隔离前先定级，定级不清时先观察与取证，不直接断网核心系统。
    • 证据破坏风险：处置动作（重启、重装、清日志）会毁掉根因分析的证据。规避：隔离前先留存关键日志与内存快照（按组织流程），能取证先取证。
    • 扩散风险：受影响系统继续联网，问题蔓延到更多资产。规避：确认影响面后先做网络隔离（断外联、保留内网取证通道），再慢慢根除。
    • 恢复复发风险：没根除就从旧备份恢复，旧备份里还带着问题。规避：恢复前确认备份时间点在事件发生之前，或从干净镜像重建并重新加固。
    • 沟通风险：事件信息在组织内扩散失控，引发误传。规避：单一事件负责人对外口径，内部按需知晓，事件报告归档不群发。

    5. 检测方式¶

    按日志来源列检测要点（防御侧）：

    • 认证日志：异地登录、非常用时间登录、短时间大量失败、特权账号异常使用；重点是“账号 + 来源 + 时间”三者的基线偏离，不是单条失败。
    • 系统日志：非预期进程、计划任务新增、服务异常崩溃、权限变更记录；与资产清单对照——清单上没有的服务与任务先研判。
    • 应用日志：异常请求模式（高频、非常用接口、参数异常）、错误率突增、后台管理接口的非预期访问；应用日志要与 WAF、网关日志对照看。
    • 网络日志：非常用端口的外联、大量数据外发、与已知恶意地址的通信（以威胁情报为准，不自行臆断地址性质）；外联行为要结合业务解释——备份、更新、监控都会外联。
    • 告警分级与误报处理：告警分三级——高（已确认影响，立即处置）、中（疑似事件，限时研判）、低（基线偏离，定期复核）；误报不直接删除规则，先记一条“为什么是误报”，再决定是调阈值、补白名单还是补业务上下文；同一误报反复出现，说明规则缺业务上下文，不是“告警太吵”。

    6. 修复与防御方法¶

    • 隔离止损：确认影响面后，按“断外联、保内网取证通道”的顺序隔离；隔离动作记入事件时间线，隔离范围事后复核（有没有漏、有没有多）。
    • 根除：去掉立足点（恶意账号、计划任务、后门文件按取证流程处置）、补漏洞（升级到修复版本）、改口令（受影响账号与相关服务口令轮换，参考秘密信息管理的做法）。
    • 恢复：优先从事件发生前的可信备份或干净镜像重建；重建后重新加固（基线复核、补丁状态复核），分批恢复并持续观察一段时间，确认无复发再全面恢复。
    • 复盘：写清时间线（发现、定级、隔离、根除、恢复各环节的时间点）、根因（技术根因 + 流程根因，两者缺一不可）、处置得失（哪些动作有效、哪些动作慢了）、改进项（每项有负责人与期限）。
    • 改进落地：复盘改进项进跟踪清单，定期复核关闭情况；下一次演练把本次事件的场景加进去，验证改进是否真的生效。
    • 平时的准备清单：资产清单、日志留存策略、联系人清单、隔离与恢复手段、备份恢复演练——这五项平时不备齐，事件发生时每一项都会现补，而现补的每一项都会拖慢处置。

    7. 历史与案例¶

    Log4Shell（CVE-2021-44228，2021 年 12 月公开）的应急侧面：该事件公开后，各组织的应急动作基本是同一套流程的实战检验——

    • 检测：先靠资产清单列出引用了受影响版本的系统，清单不全的组织只能全网排查；同时上线针对性的检测规则，关注相关服务的异常日志。
    • 遏制：不能立即升级的系统先用厂商给出的缓解措施（配置开关、访问控制收紧）顶上，争取修复时间。
    • 恢复与复盘：升级到修复版本后复测确认，事后复盘的共识是“供应链可见性”——不知道自己用了什么，就谈不上应急速度。
