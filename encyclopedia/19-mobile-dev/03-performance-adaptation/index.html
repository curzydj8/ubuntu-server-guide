    移动端性能与适配¶

    1. 本章目标¶

    读完本篇能理解：移动端性能问题从哪五个方向来（启动、帧率、内存、适配、耗电），以及每类问题应按什么思路排查。

    2. 背景与问题¶

    移动端性能问题有个特点：开发机上跑得好好的应用，到了用户手里就卡。原因不在代码变了，而在约束变了——用户的机器可能是三年前的低端机、内存只剩几百兆、网络在电梯里断断续续、系统正在省电模式下限流。性能工作不是“把代码写快一点”，而是“在约束下保证关键体验不掉链子”：启动要快、滑动不掉帧、内存不爆、所有机型都能用、耗电不被用户卸载。

    本篇讲成因与排查思路，不讲某一款性能工具的点击步骤；工具名称只作为排查方向的路标，工具用法以官方文档为准，且本文未做真机实测验证。

    3. 总体架构¶

    性能问题的五个方向与对应的系统约束：

    启动速度 ← 应用进程创建 + Application 初始化 + 首屏渲染
帧率     ← 16.7ms 一帧的预算（60Hz）或 8.3ms（120Hz）+ 主线程 + GPU
内存     ← 堆上限（按设备分档）+ GC + 系统低内存回收（LMK）
屏幕适配 ← 尺寸、密度、折叠、刘海、挖孔、手势导航、横竖屏
耗电     ← CPU 唤醒、网络射频、定位、屏幕、后台任务调度

    五者互相牵制：启动时预加载越多，首屏越快，但内存与耗电越差；动画越华丽，帧率预算越紧；后台越勤快，数据越新鲜，电量与系统限制越先找上门。性能优化是取舍，不是单项指标竞赛。

    4. 工作机制¶

    4.1 启动：三种启动与时间花在哪¶

    • 冷启动：进程不存在，系统要创建进程、加载 Application、初始化各 SDK、渲染首屏。耗时大头通常在 Application 里的同步初始化（数据库、统计、推送、配置拉取排队执行），而不是界面本身。
    • 温启动：进程在，Activity 重建。耗时在界面重建与数据恢复。
    • 热启动：Activity 已在后台，直接回到前台，最快。

    优化思路按优先级：第一，延迟初始化——首屏不需要的 SDK 移到后台线程或首次使用时再初始化；第二，缩短首屏渲染链——首屏布局层级越浅、首屏数据越少，越快；第三，基线配置文件（Baseline Profiles）让系统提前编译热点代码，改善冷启动后的第一帧表现。不要做的事：启动时同步做网络请求等首屏渲染，那是把网络延迟直接加到用户等待里。

    4.2 帧率：16.7ms 预算与掉帧的三种来源¶

    屏幕每 60Hz 刷新一次，留给应用画一帧的时间是 16.7ms（120Hz 屏是 8.3ms）。系统按 VSync 信号节拍回调，应用在主线程完成测量、布局、绘制，再交给 GPU 合成。掉帧只有三种来源：

    • 主线程被堵：网络请求、数据库读写、JSON 解析、大图编解码放在主线程，帧回调排不上队。特征是滑动时整段卡住、点击无响应。
    • 布局与绘制过重：布局层级过深、过度绘制（同一像素被反复画多次）、每帧都创建对象。特征是列表滑动时帧率波动、越滑越卡。
    • GPU 负载过高：超大图、过多阴影与圆角裁剪、每帧全屏重绘。特征是动画场景掉帧、机身发热。

    排查方向：先确认掉帧发生在主线程还是 GPU（性能分析工具按线程与 GPU 分段呈现），再按来源处理——主线程问题挪到后台线程，布局问题减层级与复用，GPU 问题减绘制量。不要做的事：凭感觉加缓存、加线程，缓存与线程本身也会吃内存与电量。

    4.3 内存：泄漏、抖动与系统回收¶

    移动端内存有硬上限，且按设备分档，低端机上限远低于开发机。三种典型问题：

    • 泄漏：本该回收的对象被长期引用。常见形态：静态变量持有 Activity、未注销的监听与回调、单例持有界面上下文、Handler 消息队列里的延迟任务持有外部类。泄漏不立即崩溃，而是越用越卡，最终被系统杀掉。
    • 抖动：短时间内反复分配又释放大量小对象，GC 频繁触发，主线程被 GC 暂停打断，表现为间歇性卡顿。常见于列表每一项都新建对象、每帧都拼接字符串。
    • 系统回收：内存紧张时，系统按优先级杀后台进程（LMK 机制），前台应用也可能被要求释放缓存。正确姿势是监听内存紧张回调、主动释放图片缓存等可重建资源，而不是假设内存一直够用。

    排查方向：先看内存曲线是“持续爬升”（泄漏嫌疑）还是“锯齿高频”（抖动嫌疑），再对嫌疑对象查引用链。图片类内存要单独算：原图尺寸远大于显示尺寸时，先下采样再加载，不要原图进内存。

    4.4 屏幕与机型适配：尺寸、密度与形态¶

    Android 机型的差异是结构性的，不是“几款主流机型”能覆盖的：

    • 尺寸与密度：用 dp（密度无关像素）描述尺寸、用 sp 描述文字，图片按密度分桶提供；直接写 px 会在高密度屏上缩成一团、在低密度屏上溢出。
    • 资源限定符：按屏幕宽度、方向、夜间模式提供不同的布局与资源，系统按当前配置自动选取；一份布局打天下的写法在平板与折叠屏上必然变形。
    • 异形与手势：刘海、挖孔、圆角、手势导航条都会吃掉可视区域，关键内容与点击区要避开系统窗口 insets（状态栏、导航栏、刘海区），而不是假设屏幕是完整矩形。
    • 折叠与大屏：折叠屏展开/折叠、平板横屏都会触发配置变更（见第一篇生命周期），界面要能重建恢复，不能假设“竖屏手机”是唯一形态。
    • 系统行为差异：厂商定制系统对后台、权限、电池优化的实现各有加严，同一功能在不同品牌机型上表现可能不同，发布前要在目标品牌机型上逐项验收，不能只测一台。

    4.5 耗电：看不见的性能指标¶

    耗电问题的特点是用户先感知、数据后证明：应用被卸载时，理由常常是“耗电”，而不是“卡”。耗电来源按量级：

    • 唤醒与后台：频繁唤醒 CPU、定时任务过密、后台定位持续开启，是耗电大头。系统对后台有 Doze（打盹）与应用待机桶机制：不常用的应用会被系统限制后台活动，对抗系统限制的写法（如常驻前台服务伪装）会被商店政策与用户双重惩罚。
    • 网络射频：移动网络射频在传输后会保持高功率一段时间（尾时），零散的小请求比批量请求更耗电。优化方向是合并请求、延迟非紧急同步、Wi-Fi 下做大宗同步。
    • 定位与传感器：持续高精度定位、常开传感器监听，耗电远高于按需单次获取。按需申请、用完即关，是基本纪律。
    • 屏幕与渲染：高亮度、持续动画、高帧率渲染，耗电与发热同步上升；动画不是免费的。

    排查方向：先看电池统计中本应用的占比与后台活动时长，再按“唤醒次数、网络请求分布、定位使用时长”三项定位来源；不要做的事：为省电而砍掉用户明确需要的功能，省电与功能取舍要摆到明面上让产品定。

    5. 关键设计取舍¶

    • 启动快慢换首屏完整度：骨架屏 + 异步加载换启动速度，代价是首屏短暂不完整；全量预加载换首屏完整，代价是启动慢、内存高。按“用户第一眼要什么”取舍。
    • 流畅换内存：图片缓存、预加载、复用池都换帧率，代价是内存；缓存必须有上限与淘汰策略，无上限的缓存就是慢泄漏。
    • 新鲜换电量：实时同步换数据新鲜，代价是唤醒与射频；非紧急同步合并与延迟，是常规解法。
    • 适配广度换开发量：覆盖折叠屏、平板、老机型的每一项都要测试量；按用户机型分布定优先级，而不是按“理论上所有机型”平均用力。

    6. 分类与变体¶

    • 按排查阶段分：开发期（布局检查、主线程检测、严格模式）、测试期（性能基线、机型矩阵、低端机专项）、线上期（启动耗时、帧率、崩溃与内存异常的聚合上报）。
    • 按机型分：旗舰机（验证上限体验）、主流机（验证达标体验）、低端机与老系统（验证底线体验：能用、不崩、不耗电异常）。底线机型定错，优化方向全错。

    7. 应用与限制¶

    • 本篇适用于原生与跨平台应用：启动、帧率、内存、耗电的成因跨框架通用，具体工具与 API 按框架而异（见第二篇选型）。
    • 不适用：把性能指标当成唯一目标——帧率满分但耗电异常、启动极快但首屏残缺，都是失败的优化。
    • 本篇所述工具用法与系统行为均为原理级描述，未经真机实测验证；厂商定制系统的行为差异以目标机型实测为准。

    8. 常见误解¶

    • “卡就是 CPU 不够。”错：多数卡顿是主线程被堵或绘制过重，不是算力不够，加配置掩盖不了设计问题。
    • “内存大就不怕泄漏。”错：泄漏是持续爬升，再大的上限也会被爬满，只是时间问题。
    • “适配就是多测几台手机。”错：适配是尺寸、密度、形态、系统行为四个维度的矩阵，测机只是最后一环，布局与资源设计才是本体。
    • “耗电优化就是少用后台。”错：耗电是唤醒、网络、定位、屏幕的总账，单砍后台可能误伤用户需要的功能。
