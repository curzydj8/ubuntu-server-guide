    文件传输与远程执行¶

    一、概述与使用场景¶

    登录服务器解决问题只是一半工作，另一半是把文件搬上搬下、在远程批量执行命令。本章覆盖三类工具：传文件用 scp / sftp / rsync，跑命令用 ssh host '命令'，长任务用 tmux 防断线。密钥与 agent 的准备工作见同目录 SSH 密钥、Agent 与轮换，本章默认你已经能密钥登录。

    三种传输工具的定位对比：

    工具 定位 增量传输 交互浏览 断点续传 典型场景
    scp 简单直传，一条命令搞定 否，每次全量 否 否 临时拷单个文件、配置文件
    sftp 交互式会话，像远程 FTP 否 是 reput / reget 手动续 不记得远程路径、边看边传
    rsync 增量同步引擎 是，只传差异部分 否 是（-P） 目录同步、站点发布、备份

    选型口诀：单个文件用 scp，路径不熟用 sftp，目录和大文件一律 rsync。rsync 也是备份体系的基础工具，与 备份与恢复 中的 rsync / restic 方案衔接；当主机数量多到逐台执行吃不消时，应转用 Ansible 做规模化分发与执行。

    Note

    示例服务器为 192.0.2.10，用户 ubuntu，SSH 端口示例用 2222 表示"非默认端口"的情形。版本口径 Ubuntu 22.04 / 24.04 LTS。

    二、环境准备与前置条件¶

    1. 已按 SSH 密钥、Agent 与轮换 完成密钥部署，能免密登录目标机；
    2. 客户端与服务端都装有 rsync（Ubuntu 默认可能未装，缺了就 sudo apt install rsync，两端都要有）；
    3. 知道目标机的 SSH 端口；不确定时先用普通 ssh 登录确认一次；
    4. 传大文件前先看一眼目标磁盘余量：ssh ubuntu@192.0.2.10 'df -h /data'，避免传到一半磁盘写满。

    三、手把手操作步骤¶

    3.1 scp：简单直传¶

    基本语法是 scp [参数] 源 目标，任意一端都可以是远程路径，远程路径写成 用户@主机:路径。

    Warning

    scp 的端口参数是大写 -P，而 ssh 是小写 -p。这是 SSH 家族里最著名的不一致：scp -p 不是端口，而是"保留文件属性"。写错不会立刻报错，而是连到默认 22 端口或行为不符预期，排查时先查这一项。

    常用参数：

    • -P 2222：指定端口（大写）；
    • -r：递归传整个目录；
    • -i ~/.ssh/id_ed25519_ops：指定私钥；
    • -p：保留原文件的修改时间、访问时间与权限；
    • -3：两台远程主机之间传文件时经本地中转（见本节末尾）。

    上传（本地 → 远程）：

    scp -P 2222./app.tar.gz ubuntu@192.0.2.10:/data/incoming/

    下载（远程 → 本地）方向反过来即可：

    scp -P 2222 ubuntu@192.0.2.10:/var/log/app/error.log./error.log

    error.log 100% 45KB 512.3KB/s 00:00

    解读：输出一行依次是文件名、进度百分比、已传大小、速率、预计剩余时间；出现 100% 且命令正常退出即完成。小文件可能一闪而过看不到进度行，以退出码与第四节校验为准。

    传目录加 -r：

    scp -r -P 2222./site ubuntu@192.0.2.10:/var/www/

    两台远程主机互传（-3）：默认情况下 scp 主机A:文件 主机B:目录 由 A 直接连 B；A、B 互不可达、只能经你本地中转时加 -3，流量走 A → 本地 → B，速度受本地带宽限制，能直连就不要用。

    3.2 sftp：交互式浏览与批处理¶

    不记得远程文件放在哪时，先连进去边看边传：

    sftp -P 2222 ubuntu@192.0.2.10

    Connected to 192.0.2.10.
sftp> ls /var/log/app
error.log access.log
sftp> get /var/log/app/error.log
Fetching /var/log/app/error.log to error.log
/var/log/app/error.log 100% 45KB 380.2KB/s 00:00
sftp> put./fix.sh /tmp/fix.sh
Uploading./fix.sh to /tmp/fix.sh
sftp> bye

    会话内常用命令分两组：不带 l 的操作远程，带 l 的操作本地——ls/cd/pwd 是远程，lls/lcd/lpwd 是本地；put 上传、get 下载，方向与 scp 一致。

    断点续传：下载中断后用 reget 文件 接着传未完的部分，上传对应 reput 文件。注意续传要求本地已有的半截文件与远程文件前半部分一致，文件被改过就不要续，老老实实重传。

    批处理模式 -b：把命令写进文件批量执行，适合固定动作脚本化：

    cat > /tmp/sftp-batch.txt <<'EOF'
cd /data/incoming
put./app.tar.gz
ls -l
EOF
sftp -b /tmp/sftp-batch.txt -P 2222 ubuntu@192.0.2.10

    解读：批处理模式下任何一条命令失败，sftp 默认会继续执行后面的命令（交互模式则停留在会话里等你处理），脚本里应自行检查最终结果。

    3.3 rsync：增量同步（重点）¶

    rsync 先对比两端文件的大小与修改时间（或校验和），只传有差异的部分，重复执行同一条命令的成本极低，这是它碾压 scp 的核心能力。

    最常用组合逐参数拆解：

    rsync -avP -e 'ssh -p 2222'./site/ ubuntu@192.0.2.10:/var/www/site/
    • -a：归档模式，一揽子包含递归、保留权限/时间/属主/软链接等，是传目录的默认选择；
    • -v：输出每个被传文件的清单，没有它你不知道到底传了什么；
    • -P：等同 --partial --progress，保留未传完的部分文件以便续传，并显示单文件进度；
    • -e 'ssh -p 2222'：指定走 SSH 通道并给出 ssh 参数（注意这里的端口是小写 -p，因为这是 ssh 的参数）。

    目录尾随斜杠语义——rsync 最容易翻车的一点：

    # 带斜杠：把 site 目录里的同步到目标目录里
rsync -av./site/ ubuntu@192.0.2.10:/var/www/
# 结果：/var/www/index.html、/var/www/css/...

# 不带斜杠：把 site 目录同步到目标目录下
rsync -av./site ubuntu@192.0.2.10:/var/www/
# 结果：/var/www/site/index.html、/var/www/site/css/...

    记法：源路径带 / 结尾 = 只同步内容；不带 = 连目录一起搬。目标路径末尾的斜杠则基本无影响。每次拿不准，先加 --dry-run 看清单：

    rsync -av --dry-run./site/ ubuntu@192.0.2.10:/var/www/

    --dry-run（或 -n）只演习、不真传，输出将要传输/删除的文件清单。任何新写的 rsync 命令、任何带 --delete 的命令，第一遍都必须先 dry-run。

    Danger

    --delete 会删除目标端存在、但源端没有的文件，让目标与源严格一致。方向写反（源和目标写颠倒）时执行 --delete，等于拿旧目录覆盖新目录并删掉新文件，可能直接抹掉线上数据。使用纪律：先 --dry-run 看删除清单 → 人工核对清单里每一项都确实该删 → 再去掉 --dry-run 执行。深夜、疲惫、赶时间时不要执行带 --delete 的同步。

    其他实用参数：

    • --bwlimit=2000：限速，单位 KB/s（2000 约 16Mbps），同步大目录时避免打满带宽影响线上业务；
    • --exclude='*.log'：排除匹配文件，可多次使用，也可用 --exclude-from=文件 从清单读取；
    • --checksum：用校验和而非时间/大小判断文件是否变化，慢但准，见 3.5 节。

    断点续传原理：-P 中的 --partial 让中断时已传的部分保留在目标端（默认正式文件名，部分场景下是隐藏的临时名），下次执行同一命令时 rsync 的增量算法会跳过已一致的数据块、只补剩余部分，所以命令不用改、直接重跑即可。

    3.4 远程执行命令¶

    单条命令直接跟在主机后面，输出回显到本地：

    ssh ubuntu@192.0.2.10 'systemctl status ssh --no-pager | head -5'

    多条命令用分号或 && 串在同一对引号里，或写成多行字符串：

    ssh ubuntu@192.0.2.10 'cd /var/www && git pull && systemctl reload nginx'

    引号陷阱：命令里的 $变量 由哪一端 shell 展开，取决于引号种类——

    # 双引号：$HOME 先被shell 展开，远程收到的是本地的家目录路径
ssh ubuntu@192.0.2.10 "echo $HOME"
# 输出：/home/你本地的用户名 ← 多半不是你想要的

# 单引号：整串原样发到远程，$HOME 由shell 展开
ssh ubuntu@192.0.2.10 'echo $HOME'
# 输出：/home/ubuntu ← 通常想要这个

    规律：远程命令默认用单引号；确实需要把本地变量的值传进远程命令时才用双引号，且要清楚每个 $ 是在哪端展开的。

    需要 sudo 时加 -t：远程命令默认不分配终端，sudo 没地方输密码会直接失败：

    ssh -t ubuntu@192.0.2.10 'sudo systemctl restart nginx'

    -t 强制分配伪终端，sudo 才能提示输密码。脚本里则应优先用免密 sudo 的受限配置或密钥化方案，而不是在脚本里塞密码。

    批量多主机：主机不多时 for 循环足够：

    for h in 192.0.2.10 192.0.2.11 192.0.2.12; do
echo "== $h =="
ssh -o ConnectTimeout=5 ubuntu@$h 'uptime' || echo "连接失败: $h"
done

    Warning

    批量执行的风险在于错误也会被批量放大：一条写错的重启/删除命令会在所有主机上依次生效。纪律：先在一台 canary 主机上单独验证 → 循环里带连接超时与失败即停的检查 → 涉及变更的命令先把 ssh... '命令' 换成 echo 打印一遍核对主机清单。主机超过十台或需要并发、重试、结果汇总时，别再堆 shell 循环，改用 Ansible。

    3.5 大文件与不稳定网络¶

    先压缩还是直接 rsync？ 权衡点是 CPU 与带宽谁更贵：日志、文本、未压缩数据先用 tar 打包并经 zstd/gzip 压缩再传，通常省一半以上流量；mp4、jpg、已压缩的安装包再压几乎不缩小，纯属浪费两端 CPU，直接 rsync。rsync 自带 -z 是传输中压缩，适合慢网络传可压缩内容，但弱 CPU 机器上可能跑不满带宽，按实测取舍。

    完整性校验：rsync 默认传输后有整体校验，但重要文件发布后应再做一次独立对照：

    # 两端分别计算，哈希一致即内容一致
sha256sum./app.tar.gz
ssh ubuntu@192.0.2.10 'sha256sum /data/incoming/app.tar.gz'

    怀疑时间戳判断漏传（文件改了但大小、时间碰巧相同）时，用 rsync -avP --checksum 强制按内容比对，代价是两端都要读全文件计算哈希，大目录会明显变慢，只在必要时用。

    3.6 断线续跑：tmux / screen / nohup¶

    网络一断，远程命令默认跟着 SSH 会话一起被终止。长任务（编译、批量处理、跨网同步）要跑在与会话解耦的环境里：

    # 在远程主机上新建一个名为 job 的会话，在里面启动长任务
ssh -t ubuntu@192.0.2.10 'tmux new -s job'
# 会话内按 Ctrl-b 再按 d 脱离（detach），任务继续跑；也可以直接关掉终端

# 之后任意时间重新连上，回到现场看进度
ssh -t ubuntu@192.0.2.10 'tmux attach -t job'

    screen 是同类老牌工具，基本用法 screen -S job 新建、screen -r job 恢复，功能够用但新系统优先 tmux。nohup 命令 >日志 2>&1 & 的定位是"让单个命令忽略挂断信号继续跑"，局限是没有交互界面、断线后看不到实时输出（只能看日志文件）、也无法重新接管，出问题时不如 tmux 灵活——适合无人值守的一次性命令，不适合需要盯着调的任务。

    四、效果验证与测试¶

    传输是否成功，不看命令的退出动画，看两端文件本身：

    # 1. 两端大小与时间对照
ls -l./app.tar.gz
ssh ubuntu@192.0.2.10 'ls -l /data/incoming/app.tar.gz'
# 2. 哈希对照（最硬的证据）
sha256sum./app.tar.gz
ssh ubuntu@192.0.2.10 'sha256sum /data/incoming/app.tar.gz'
# 3. 目录同步后做一次 dry-run，应无待传文件输出
rsync -av --dry-run./site/ ubuntu@192.0.2.10:/var/www/site/

    解读：第 2 项两串哈希完全一致，即可判定内容无损；第 3 项 dry-run 只输出目录头尾统计、没有文件清单，说明两端已同步到位。远程执行的验证同理：命令跑完后再单独查一次状态（如 systemctl is-active nginx），不要把"命令已发出"当成"已生效"。

    五、常见错误与排坑指南¶

    5.1 scp 路径含空格¶

    • 现象：传 scp "./my file.txt" ubuntu@192.0.2.10:/data/ 报 No such file or directory 或把路径拆成两段报错。
    • 原因：空格被本地 shell 分词；远程路径里的空格更麻烦，因为它还要被远程 shell 再解析一次，本地加一层引号不够。
    • 修复：本地路径照常用引号包裹；远程路径含空格时用双层转义，如 scp "./my file.txt" "ubuntu@192.0.2.10:'/data/my dir/'"，或者干脆改用 sftp / rsync 传这类路径。
    • 验证：传输成功且远程 ls -l 能看到完整带空格的文件名。养成习惯：服务器上的目录、文件名不使用空格，从源头消灭此问题。

    5.2 rsync 斜杠方向错¶

    • 现象：同步完发现目标里多套了一层同名目录（/var/www/site/site/...），或本想同步内容却连目录壳一起搬了过去。
    • 原因：源路径尾随斜杠语义记反，见 3.3 节对照示例。
    • 修复：先 rsync -av --dry-run 看清单确认层级，再决定加不加斜杠；已经传错的，先核对哪份是最新的，再删除多余层级——删除前同样先 dry-run 列清单。
    • 验证：目标路径下 ls 的层级与预期一致，且 --dry-run 复查无异常待传项。

    5.3 远程命令变量被本地展开¶

    • 现象：ssh host "echo $PATH" 输出的是本地的 PATH，或脚本里的 $1、$(...) 在远程执行结果莫名其妙。
    • 原因：双引号下本地 shell 在发送前就把变量、命令替换全部展开了，远程收到的是展开后的残串。
    • 修复：远程命令改单引号；必须混用本地变量时，把远程变量写成 \$VAR 转义、本地变量保持不转义，发送前先把整条命令 echo 出来检查一遍。
    • 验证：以 3.4 节的 $HOME 对照实验复测，单引号输出远程家目录即正确。

    5.4 Permission denied（权限不足）¶

    • 现象：传输或远程写入报 Permission denied，rsync 输出里对应文件标记失败。
    • 原因：目标目录属主不是当前登录用户（如写 /var/www 却用普通用户），或本地源文件无读权限；rsync 还会在结尾汇总 some files/attrs were not transferred。
    • 修复：先确认应该由谁写：站点目录把属主改为部署用户（sudo chown -R ubuntu:www-data /var/www/site），或用 rsync -e ssh... ubuntu@...:/目标 后在目标端以正确用户落盘；不要图省事对目录 chmod 777。文件、权限与属主的基本功见 文件与权限速查。
    • 验证：以目标用户身份 touch 目标目录能成功建文件，再重跑传输无失败汇总。

    六、生产环境最佳实践与安全建议¶

    1. 同步前先 dry-run 是生产纪律，尤其是 --delete 与写线上的路径；保留 dry-run 清单截图/日志作为变更记录的一部分。
    2. 传输通道只走密钥：脚本化的 scp/rsync 一律用密钥 + agent 或专用部署密钥，并给部署密钥在服务端用 authorized_keys 的 from= 限制来源 IP，避免一把万能钥匙满网跑。
    3. 大同步避开业务高峰：用 --bwlimit 限速并安排在低峰期；站点发布用"传到新目录 → 校验 → 切软链接"的原子切换法，而不是直接覆盖正在服务的目录。
    4. 批量远程执行留痕：循环执行的输出逐台落日志文件，出事后能回答"哪台在什么时间跑了什么"。
    5. 重要文件传输后必验哈希：发布包、备份包、数据库导出，传输完成的标准是两端 sha256 一致，不是进度条走到 100%。

    回滚方案：

    • 同步覆盖回滚：覆盖线上目录前先在目标端留一份带时间戳的备份（cp -a /var/www/site /var/www/site.bak.$(date +%F-%H%M)，大目录可用 rsync 到备份路径）；发布出问题时把软链接切回旧目录或用备份目录反向 rsync 回来，并再次 dry-run 核对清单。
    • --delete 误删回滚：没有备份就没有回滚——这正是 3.3 节要求先 dry-run 的原因。误删发生后第一时间停写目标盘，走文件系统快照（LVM/ZFS）或备份体系恢复，方案见 备份与恢复；恢复后用 sha256 与清单逐项核对再上线。
    • 批量执行误伤回滚：逐台按日志定位已执行的主机，对变更命令执行其逆操作（如 reload 回旧配置、切回旧版本目录）；无法逆操作的变更，必须在执行前就准备好整机快照或镜像回退路径，否则不要批量执行。
    • 原则：任何传输与远程执行的变更，执行前先回答"错了怎么退"，答不上来就先补回滚手段，再动手。
