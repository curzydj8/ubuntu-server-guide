    PROJ-07：论坛、电商、CMS、后台管理、SaaS 完整教程¶

    任务编号：PROJ-07（网站建设与部署实战指南 · 完整实战第 7 篇） 上一篇：PROJ-06 Docker 多容器网站平台；下一篇：PROJ-08 旗舰：一台服务器托管多网站。 本篇只讲五类系统的选型方法、部署步骤、关键配置、常见坑与验证方法。不讲具体某个框架的语法（那是 BE 篇的范围），不讲部署流水线本身（那是 DEPLOY 篇的范围），不讲一台服务器托管多网站的完整旗舰实战（那是 PROJ-08 的范围）。

    1. 本章目标¶

    读完并动手做完本篇，你能：

    • 说清论坛、电商、CMS、后台管理、SaaS 五类系统各自的核心能力与边界，不把五类混成一个“万能系统”。
    • 按选型维度给自己的需求定一个落点，而不是先选一个产品再往需求上套。
    • 照着第 10 节的部署骨架，把任意一类系统从零部署到自己的服务器上，并按验证清单逐项确认它真的能用。
    • 说清电商与 SaaS 的支付与数据安全红线：支付走正规支付渠道，不自己存卡号，不做本文不展开的合规承诺。
    • 在部署失败或上线后出问题时，按第 15、16、18 节定位、回滚、恢复，而不是把整个服务器推倒重来。

    2. 适用人群¶

    • 已经能照着 DEPLOY 篇把一个普通网站部署上线的读者：会用 Nginx、会用 Docker Compose 或 systemd 起服务、会看日志。
    • 正在给自己的业务选系统的人：想开论坛、开网店、做内容站、做内部后台、做订阅制服务，但还没定下来用哪条路线。
    • 不适合只想学某个框架语法的人：框架的具体写法请回 BE 篇（PHP、Python、Node.js、Go、Java 各一篇），本篇只讲到“选什么、怎么部署、配什么、怎么验”这一层。

    3. 适用系统和版本¶

    • 服务器系统：Ubuntu 22.04 LTS 或 24.04 LTS（二选一，本文示例按 24.04 写命令，22.04 的步骤相同）。
    • 运行环境：Docker Engine + Docker Compose v2，或 Nginx + systemd 直跑（二选一，本文第 10 节的骨架以 Docker Compose 为主，systemd 的改法在每类骨架里注明）。
    • Web 层：Nginx（反向代理与静态分流，写法见 SRV-01），数据库以 MySQL/PostgreSQL 为例、缓存以 Redis 为例。
    • 版本说明：本文不钉死某个框架或某个开源程序的补丁号。开源程序与框架的版本变化快，安装时以官网当场公布的稳定版为准；第 10 节的骨架写的是“技术栈 + 部署步骤 + 配置要点”，不是“某年某月某版本的逐字安装录像”。Ubuntu、Docker、Nginx 的版本以你服务器上实际装好的为准，命令里的路径与端口须换成你自己的真实值。

    4. 使用前提¶

    • 一台能连网的 Ubuntu 服务器，上面已有 Docker 与 Docker Compose，或已有 Nginx 与对应语言的运行环境。
    • 一个已经解析到这台服务器的域名（示例域名一律用 example.com 及其子域名，真实部署时换成你自己的域名）。
    • 域名解析与 HTTPS 的前置步骤已经走完（见 DEPLOY-03 的上线全流程；证书签发细节见 09-web-hosting/05，不在本篇重讲）。
    • 你已经读过 ARCH-03 的选型决策树，知道自己的需求落在哪个落点：本篇的五类正好对应决策树的五个落点方向（静态站之外的五类动态系统）。
    • 电商与 SaaS 的读者还须额外满足一条：已经有一个正规支付渠道的商户账号（或明确知道去哪里申请），不要在没有支付渠道的情况下先把“在线支付”写进上线清单。

    5. 所需资源¶

    • 服务器：单台 2 核 4G 内存起步可跑任意一类骨架的开发与小流量版本；电商与 SaaS 上线前按第 8 节先估算并发与数据量，内存与磁盘不够就先升配置再上线，不要先上线再救火。
    • 域名：主域名一个，子域名按需（如 bbs.example.com、shop.example.com、admin.example.com，示例域名，真实部署时换成你自己的域名）。
    • 账号：域名注册商账号、服务器 SSH 账号、支付渠道商户账号（电商与 SaaS）、邮件服务账号（注册验证、找回密码、订单通知用）。
    • 时间：任意一类骨架从零到可访问约半天到一天；五类全做不要排在同一天，每类部署完按验证清单确认后再做下一类。

    6. 技术原理¶

    五类系统共用同一套分层原理（见 ARCH-01 的十层总览），区别只在“哪一层最重”：

    • 论坛最重的是内容层与治理层：帖子、回复、版块、用户等级、内容审核、反垃圾。技术难点不在“发帖子”本身，而在“帖子多了、用户多了之后怎么管”。
    • 电商最重的是交易层：商品、库存、购物车、订单、支付、退款。技术难点不在“展示商品”，而在“钱与库存不能错”：库存不能超卖，订单状态不能丢，支付结果不能只信前端回跳。
    • CMS 最重的是内容模型层：栏目、文章、字段、发布流程、权限。技术难点不在“写文章”，而在“内容结构变了之后，旧数据与旧链接怎么办”。
    • 后台管理最重的是权限与审计层：谁能看什么、谁能改什么、改了有没有记录。技术难点不在“做个表格页”，而在“越权与无审计”。
    • SaaS 最重的是隔离与计费层：多租户数据隔离、订阅与用量、租户级别的配置。技术难点不在“多用户登录”，而在“租户 A 绝不能看到租户 B 的数据”。

    一句话：选型之前先问“这一类最重的那一层，我能不能接住”。接不住，就换一类更轻的落点，或者先把最重的那一层外包给成熟方案（如支付走正规支付渠道、邮件走成熟邮件服务），不要自己从零造。

    7. 架构说明¶

    7.1 五类系统的架构对照¶

    类别 核心实体 最重的一层 典型部署形态 绝对不能省的东西
    论坛 用户、版块、帖子、回复、举报 内容治理层 Web + 应用 + 数据库 + 缓存 + 搜索 审核、反垃圾、备份
    电商 商品、库存、购物车、订单、支付 交易层 Web + 应用 + 数据库 + 缓存 + 支付渠道 库存扣减、订单状态机、支付对账
    CMS 栏目、文章、字段、发布流程 内容模型层 Web + 应用 + 数据库 + 对象存储（可选） 发布流程、旧链接处理
    后台管理 账号、角色、权限、操作日志 权限与审计层 Web + 应用 + 数据库（内网或受限访问） RBAC、操作日志、登录保护
    SaaS 租户、用户、订阅、用量 隔离与计费层 Web + 应用 + 数据库（租户隔离）+ 缓存 租户隔离、订阅状态、数据备份

    7.2 选型维度总表¶

    五类共用同一套选型维度，打分时按维度逐项过，不要只看“功能多不多”：

    维度 要问的问题 权重建议
    需求匹配 核心能力是不是这一类系统的主业，还是硬凑出来的 最高，先过这一项
    维护成本 升级、备份、漏洞修复由谁做，多久一次 高
    数据主权 数据能不能完整导出、能不能迁走 高
    扩展能力 用户量、数据量涨 10 倍时，瓶颈在哪一层 中
    安全与合规 登录、支付、个人信息按哪条红线处理（见第 17 节） 最高，电商与 SaaS 必过
    团队能力 团队会不会这套技术栈，能不能读懂它的报错 高

    选型结论的写法：不要写“某款产品最好”。要写“按以上维度，本需求落点是某类，候选有 A、B、C，A 在某维度占优、B 在某维度占优，最终选 A 的理由是某维度得分最高”。举例不等于推荐，举例只是帮你定位到“这类东西长什么样”。

    7.3 各类架构要点¶

    • 论坛：应用层之后接搜索服务（帖子搜索不能只靠数据库模糊查询，数据量上去之后会变慢）；上传的图片与附件走对象存储或独立静态目录，不要和应用代码混在一起。
    • 电商：支付回调必须走服务端对账（支付渠道的服务端通知 + 主动查询），不要只信浏览器回跳；库存扣减必须在事务里做，见 DB-01 的事务一节。
    • CMS：内容发布要有“草稿 → 审核 → 发布 → 归档”的状态，发布不是直接改数据库；旧链接变更时要做 301，不要直接 404。
    • 后台管理：必须只能从内网或受限网络访问，公网直接暴露后台登录页是常见事故；登录必须有限流与二次验证（见 OPS-02）。
    • SaaS：租户隔离必须在数据层做（每张业务表带租户标识、每次查询带租户条件），不能只靠前端隐藏；订阅状态变更必须有对账与重试，不能只靠一次回调。

    8. 操作前检查¶

    动手部署任何一类之前，先逐项打勾，缺一项就先补，不要边部署边补：

    • [ ] 域名已解析到服务器，curl -I https://example.com/ 能拿到响应（真实部署时把域名换成你自己的）。
    • [ ] HTTPS 证书已就绪，80 已跳转到 443（见 DEPLOY-03）。
    • [ ] 服务器磁盘、内存余量已确认，数据库与上传目录的磁盘配额已留出。
    • [ ] 数据库账号、缓存、对象存储（如用）的凭据已准备好，全部只放在环境变量或凭据文件里，权限 600，不进仓库。
    • [ ] 备份策略已定：备份什么、多久一次、保留多久、恢复演练什么时候做（见 OPS-04，红线是“没演练过的备份等于没有备份”）。
    • [ ] 电商与 SaaS：支付渠道商户账号已就绪，支付回调地址已在支付渠道后台配好，测试模式已跑通过一笔测试订单。
    • [ ] 后台管理：访问来源已定（内网、VPN 或 IP 白名单），不要先公网暴露再补限制。
    • [ ] 回滚方案已定：部署失败时指回上一版的步骤写在纸上，而不是到时候现想（见第 18 节）。

    9. 逐步操作¶

    五类共用同一套部署流程，区别只在第 10 节每类骨架里的技术栈与配置要点：

    1. 定落点：按第 7.2 节的维度表打分，写出选型结论（落点是哪一类、候选有哪些、最终选谁、理由是什么）。
    2. 准备服务器：装好 Docker 与 Docker Compose（或 Nginx + 对应语言运行环境），配好域名解析与 HTTPS。
    3. 准备数据层：建数据库与账号，建缓存，配好备份（见 DB-02 与 OPS-04）。
    4. 部署应用：按第 10 节对应类别的骨架，起服务、做初始化（建管理员账号、建初始栏目或商品分类）。
    5. 配 Web 层：Nginx 反向代理与静态分流（见 SRV-01），安全响应头与限流（见 OPS-02）。
    6. 接外部服务：邮件（注册验证、通知）、支付（电商与 SaaS）、对象存储（如用），每一项单独验证，不要一次全接上再排错。
    7. 走验证清单：按第 10 节对应类别的验证清单逐项打勾，全部通过才算部署完成。
    8. 写运维记录：把部署步骤、配置文件路径、账号位置（只写位置，不写口令）、备份策略、回滚步骤记下来，存在团队能找到的地方。

    框架语法、部署流水线、服务器配置模板本身不在本篇重讲：框架写法回 BE 篇，CI 部署回 DEPLOY-01，Docker 编排回 DEPLOY-02，Nginx 模板回 SRV-01。

    10. 完整代码¶

    本节是实战核心：五类各给一个部署骨架，每类都包含技术栈、部署步骤、关键配置文件要点、验证清单四项，缺一类都不算完成。配置文件示例里的口令与密钥一律用占位符，域名一律用 example.com 及其子域名，真实部署时全部换成你自己的值。

    10.1 论坛部署骨架¶

    • 技术栈：Web（Nginx）+ 论坛应用（开源论坛程序一类，举例不等于推荐，按第 7.2 节维度自选）+ 数据库 + 缓存 + 搜索服务。
    • 部署步骤：起数据库与缓存 → 起搜索服务 → 起论坛应用 → 做初始化（建版块、建管理员账号、开审核）→ 配 Nginx 反向代理 → 开反垃圾与邮件验证。
    • 关键配置文件要点：应用的环境变量（数据库连接、缓存地址、邮件服务、站点域名）全部放凭据文件；Nginx 配置见下；上传目录单独挂卷，不要和代码混在一起。
    • 验证清单：注册 → 邮箱验证 → 发帖 → 回复 → 举报 → 管理员审核通过/驳回 → 搜索帖子 → 备份恢复演练，逐项打勾。
    server {
    listen 80;
    server_name bbs.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name bbs.example.com;

    ssl_certificate /etc/nginx/certs/bbs.example.com.crt;
    ssl_certificate_key /etc/nginx/certs/bbs.example.com.key;

    client_max_body_size 20m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /uploads/ {
        alias /opt/forum/uploads/;
    }
}
    • 常见坑：反垃圾没开就上线，半天就被垃圾帖淹没；搜索没接，帖子一多查询就变慢；上传目录没单独挂卷，换版本时附件丢了。

    10.2 电商部署骨架¶

    • 技术栈：Web（Nginx）+ 电商应用（开源电商程序一类，举例不等于推荐，按第 7.2 节维度自选）+ 数据库 + 缓存 + 支付渠道（正规支付渠道，见第 17 节红线）。
    • 部署步骤：起数据库与缓存 → 起电商应用 → 做初始化（建商品分类、建管理员账号、配运费与税率）→ 接支付渠道（先测试模式跑通一笔测试订单，再切正式模式）→ 配 Nginx → 走对账验证。
    • 关键配置文件要点：docker-compose.yml 见下；支付密钥只放凭据文件，不进仓库，不写进前端代码；订单状态机不要自己发明一套没有对账的状态。
    • 验证清单：上架商品 → 下单 → 支付（测试模式）→ 支付回调对账 → 库存扣减 → 发货 → 退款 → 对账单核对，逐项打勾。

  web:
    image: nginx:stable
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/shop.conf:/etc/nginx/conf.d/default.conf:ro
      - ./certs:/etc/nginx/certs:ro
    depends_on:
      - app
  app:
    image: shop-app:latest
    environment:
      - DATABASE_URL=请填数据库连接串
      - REDIS_URL=redis://cache:6379/0
      - PAYMENT_API_KEY=请填支付渠道密钥
    depends_on:
      - db
      - cache
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      - POSTGRES_USER=shop
      - POSTGRES_DB=shop
      - POSTGRES_PASSWORD=请填数据库口令
  cache:
    image: redis:7-alpine
    volumes:
      - redisdata:/data
volumes:
  pgdata:
  redisdata:
    • 常见坑：只信浏览器支付回跳、不做服务端对账，掉单了都不知道；库存扣减不在事务里，并发下单超卖；支付密钥写进前端代码或仓库，等于公开。

    10.3 CMS 部署骨架¶

    • 技术栈：Web（Nginx）+ CMS 应用（开源 CMS 程序一类，举例不等于推荐，按第 7.2 节维度自选）+ 数据库 + 对象存储（可选，图片多时再接）。
    • 部署步骤：起数据库 → 起 CMS 应用 → 做初始化（建栏目、建管理员账号、定发布流程）→ 导旧内容（如有）→ 配 Nginx 与缓存 → 走发布流程验证。
    • 关键配置文件要点：环境变量只放凭据文件；栏目与字段变更先在测试环境做，再上生产；旧链接变更必须配 301，不要直接 404。
    • 验证清单：建栏目 → 写草稿 → 审核 → 发布 → 前台访问 → 改栏目结构后旧链接 301 → 搜索收录检查 → 备份恢复演练，逐项打勾。
    • 常见坑：内容结构一改，旧文章链接全 404；图片全放应用目录，换版本时丢图；发布流程没设审核，一篇错别字文章直接上了首页。

    10.4 后台管理部署骨架¶

    • 技术栈：Web（Nginx，仅内网或受限访问）+ 后台应用（框架自带后台或独立后台程序一类，举例不等于推荐）+ 数据库。
    • 部署步骤：起数据库 → 起后台应用 → 建角色与权限（RBAC）→ 建管理员账号并开二次验证 → 配访问限制（内网、VPN 或 IP 白名单）→ 配操作日志 → 走越权验证。
    • 关键配置文件要点：环境变量只放凭据文件；登录接口单独限流；操作日志表只追加、不允许业务账号删除；会话有效期不要设成永不过期。
    • 验证清单：管理员登录 → 普通账号登录 → 越权访问被拒绝 → 改数据后操作日志有记录 → 登录限流生效 → 会话过期后重新登录 → 备份恢复演练，逐项打勾。
    • 常见坑：后台直接暴露在公网，登录页被暴力破解；权限只在前端隐藏、后端接口没校验，越权一测就通；操作日志能被业务账号删改，出事查不到。

    10.5 SaaS 部署骨架¶

    • 技术栈：Web（Nginx）+ SaaS 应用（多租户应用一类，举例不等于推荐）+ 数据库（租户隔离）+ 缓存 + 支付渠道（订阅计费，正规支付渠道，见第 17 节红线）。
    • 部署步骤：起数据库与缓存 → 起 SaaS 应用 → 做初始化（建租户、建订阅套餐、建管理员账号）→ 配租户域名或子域名路由 → 接支付渠道（先测试模式跑通一笔订阅测试）→ 走隔离验证。
    • 关键配置文件要点：租户隔离必须在数据层做（每张业务表带租户标识、每次查询带租户条件）；订阅状态变更必须有对账与重试；租户配置不要混进全局配置。
    • 验证清单：注册租户 A → 注册租户 B → A 登录看不到 B 的数据 → B 登录看不到 A 的数据 → 订阅开通 → 订阅到期后降级 → 支付回调对账 → 备份恢复演练，逐项打勾。
    • 常见坑：隔离只做在前端，后端接口一换租户标识就看到别家数据；订阅回调只处理成功、不处理失败与重试，掉单后用户付了钱没开通；租户数据删了没法恢复，备份里没有按租户恢复的演练。

    10.6 部署脚本示例¶

    下面是一份通用的部署后检查脚本骨架（以论坛骨架为例，其余四类把检查地址换成自己的即可），路径见第 11 节，脚本里的域名与端口真实部署时换成你自己的值：

    #!/bin/bash

SITE_URL="https://bbs.example.com"

curl -fsS -o /dev/null -w "健康端点状态码: %{http_code}\n" "${HEALTH_URL}"
echo "检查完成"

    12. 每个关键配置项的解释¶

    配置项 位置 含义与写错后果
    server_name Nginx 站点配置 本站点的域名，写错会导致请求落到默认站或 404
    proxy_pass Nginx 站点配置 反代到本机应用的地址，应用只绑回环地址，不要绑 0.0.0.0 对外暴露
    client_max_body_size Nginx 站点配置 上传大小上限，论坛附件与 CMS 图片上传时必须按需调大，默认 1m 会导致大附件上传失败
    ssl_certificate / ssl_certificate_key Nginx 站点配置 证书与私钥路径，私钥权限 600，路径写错会导致 Nginx 起不来
    DATABASE_URL 应用环境变量 数据库连接串，口令只放凭据文件，不要写进代码或仓库
    REDIS_URL 应用环境变量 缓存地址，缓存丢了可以重建，但会话与限流数据丢了会影响在线用户，要按业务定
    PAYMENT_API_KEY 应用环境变量 支付渠道密钥，只放凭据文件，绝不写进前端代码（电商与 SaaS）
    POSTGRES_PASSWORD 编排文件环境变量 数据库口令，占位符，真实值只放凭据文件
    volumes（pgdata、redisdata） 编排文件 数据卷，不挂卷的数据库容器一删数据就没了
    depends_on 编排文件 启动顺序，不等于“服务已就绪”，应用起不来时先看数据库与缓存是不是真的就绪了

健康端点状态码: 200
检查完成
    • 电商对账验证时应看到的样子：支付渠道后台一笔订单状态为“已支付”，本站订单状态为“已支付”，库存扣减 1，三个地方一致才算对账通过；任一处不一致，先停掉自动发货，查回调日志与对账接口，不要手动改订单状态。
    • SaaS 隔离验证时应看到的样子：租户 A 登录后只能看到 A 的数据，租户 B 登录后只能看到 B 的数据，交叉访问返回无权限或空结果；任一处能看到别家数据，立即停掉该接口，按第 16 节排查租户条件。
    • 失败时应看到的样子：首页状态码不是 200、健康端点连不上、数据库连不上，统一按第 16 节排查，不要先重启整个服务器。

    14. 成功验证¶

    每类部署完成之后，按对应类别的验证清单逐项打勾，全部通过才算成功；任一类验证清单没走完，不要宣布“上线了”：

    1. 论坛：注册 → 邮箱验证 → 发帖 → 回复 → 举报 → 管理员审核通过/驳回 → 搜索帖子 → 备份恢复演练。
    2. 电商：上架商品 → 下单 → 支付（测试模式先跑通，再切正式模式）→ 支付回调对账 → 库存扣减 → 发货 → 退款 → 对账单核对。
    3. CMS：建栏目 → 写草稿 → 审核 → 发布 → 前台访问 → 改栏目结构后旧链接 301 → 搜索收录检查 → 备份恢复演练。
    4. 后台管理：管理员登录 → 普通账号登录 → 越权访问被拒绝 → 改数据后操作日志有记录 → 登录限流生效 → 会话过期后重新登录 → 备份恢复演练。
    5. SaaS：注册租户 A → 注册租户 B → A 登录看不到 B 的数据 → B 登录看不到 A 的数据 → 订阅开通 → 订阅到期后降级 → 支付回调对账 → 备份恢复演练。
    6. 通用：首页与健康端点状态码 200、HTTPS 证书有效、备份文件确实存在且能恢复、回滚步骤已写下来。

    15. 常见错误¶

    错误现象 常见原因 先查什么
    首页 502 应用没起来，或 Nginx 反代地址写错 应用日志、Nginx 错误日志、反代地址与端口
    上传失败 client_max_body_size 没调大，或上传目录权限不对 Nginx 配置、上传目录属主与权限
    支付掉单 只信浏览器回跳，没做服务端对账 支付渠道回调日志、对账接口、订单状态
    库存超卖 库存扣减不在事务里 扣减代码的事务边界、并发测试
    后台越权 权限只在前端隐藏，后端接口没校验 接口的权限校验、越权测试用例
    租户串数据 查询没带租户条件 业务查询的租户条件、交叉访问测试
    换版本丢数据 数据没挂卷，或备份里没有上传文件 卷挂载、备份清单（OPS-04）
    证书过期 续期任务没配，或续期后没重载 Nginx 续期任务、证书有效期、重载记录

    16. 故障排查¶

    按“先分层、再定位”的顺序查，不要一上来就重启整个服务器：

    1. 分层：是 Web 层（Nginx）、应用层、数据层（数据库/缓存）、外部服务（支付、邮件、对象存储）哪一层出问题。首页 502 先看 Nginx 错误日志与应用日志，数据库连不上先看数据库服务与连接串，支付问题先看支付渠道回调日志。
    2. 看日志：应用日志、Nginx 访问与错误日志、数据库慢日志（见 DB-02）、系统日志，按时间对齐，不要只看最后三行。
    3. 复现：用最小步骤复现（一个账号、一个商品、一个租户），复现不了的故障先不要改配置，改了也验证不了。
    4. 隔离：把可疑的外部服务逐个断开验证（先关支付回调、再关邮件、再关搜索），定位到哪一项再修哪一项。
    5. 记录：故障现象、定位过程、修复方法、验证结果写下来，下次同类故障直接查记录，不要每次从头排。

    17. 安全注意事项¶

    • 口令与密钥：全部只放凭据文件（权限 600）或环境变量，不进仓库，不写进前端代码，不贴进聊天记录或工单；轮换流程见 OPS-02（固定顺序为先吊销再排查）。
    • 登录保护：后台与管理入口必须限流、开二次验证、限制访问来源（内网、VPN 或 IP 白名单），不要公网直接暴露后台登录页。
    • 支付红线（电商与 SaaS，必读）：支付必须走正规支付渠道；不要自己存卡号、不要自己处理卡信息；支付回调必须做服务端对账，不要只信浏览器回跳；退款与对账必须有记录；合规方面，本文只讲到技术实现这一层，具体的资质、税务、数据合规要求以主管部门与支付渠道当场公布的要求为准，本文不做合规承诺。
    • 数据安全红线（SaaS，必读）：租户隔离必须在数据层做，不能只靠前端隐藏；个人信息只收业务必需的字段，不要多收；数据导出与删除要有流程，租户注销后数据怎么处理要事先定好。
    • 内容安全红线（论坛与 CMS，必读）：用户发布的内容必须有审核与举报流程；反垃圾与敏感词处理按平台规则做，不要把审核责任推给“用户自觉”。
    • 依赖与漏洞：定期更新应用与依赖，漏洞通告出来先评估影响、再定修复窗口、测试后上线（见 OPS-02），不要看到通告就直接在生产环境升级。

    18. 回滚和恢复¶

    • 部署回滚：部署前先备份当前版本（代码、配置、数据库、上传文件），部署脚本里写好“健康检查失败自动指回上一版”的逻辑（见 DEPLOY-01 的部署脚本思路）；回滚不是“重新部署一遍”，而是“指回上一版 + 恢复上一版的数据”。
    • 数据库迁移回滚红线：删字段、改类型这类破坏性迁移不能只靠回滚镜像解决；迁移之前先备份，先在测试环境跑，再上生产；迁移失败时按迁移工具的回滚语句恢复，不要手动改表结构。
    • 支付与订单回滚红线：已经支付成功的订单不要靠“改数据库状态”回滚，按支付渠道的退款流程走；对账不一致时先停掉自动发货，查清再动。
    • 整站恢复：按 OPS-04 的整站备份清单与演练计划恢复，恢复后按第 14 节的验证清单重新走一遍，全部通过才算恢复完成；恢复演练的频率与记录表见 OPS-04。
    • 备份恢复的底线：没演练过的备份等于没有备份。部署完成后的第一周内至少做一次恢复演练，演练结果记下来。
