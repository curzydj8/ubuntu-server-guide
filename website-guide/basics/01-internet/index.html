    NET-01：互联网、HTTP/HTTPS、浏览器、DNS、域名、IP、端口完整教程¶

    任务编号：NET-01（网站建设与部署实战指南 · 网络基础第 1 篇） 上一篇：UX-01 网站设计与用户体验；下一篇：NET-02 域名购买、注册商选择、实名、备案适用范围、泛域名、多域名。 本篇只讲网络基础：互联网怎么连通、HTTP 与 HTTPS 的区别、浏览器打开一个网页的完整流程、DNS 记录、域名结构、IP 地址、端口。不讲域名购买与备案（那是 NET-02），不讲服务器部署（那是后面的服务器与部署篇），不展开证书签发细节（那是本指南 09-web-hosting 的 HTTPS 章节）。

    1. 本章目标¶

    读完并动手做完本篇，你能：

    1. 用自己的话说清“在浏览器输入一个网址、按回车后发生了什么”，顺序不出错；
    2. 分清 HTTP 与 HTTPS、域名与 IP、内网 IP 与公网 IP、端口与网址这四组概念；
    3. 读懂 DNS 的 A、AAAA、CNAME、TXT、MX 记录分别用来干什么；
    4. 用 dig、curl -v、openssl s_client 三组命令，自己走一遍“查解析、看请求响应、看 TLS 证书”的完整流程，并读懂关键输出行；
    5. 遇到“网站打不开”时，能先判断是 DNS 问题、连接问题、证书问题还是服务器返回的错误，而不是笼统地说“网坏了”。

    2. 适用人群¶

    • 零基础、第一次做网站的人：本篇是全指南的网络地基，后面讲 Nginx、HTTPS、部署时都会默认你懂这些词；
    • 会用宝塔、WordPress 建站，但没弄明白“域名解析后为什么还要等”“为什么有的网址是 http、有的是 https”的人；
    • 已经会写 HTML、CSS、JavaScript，但一遇到跨域、证书报错、端口占用就卡住的人。

    3. 适用系统和版本¶

    • 系统：本篇命令在 Linux、macOS、Windows（WSL 或 Git Bash）上都能跑，命令本身不依赖某个发行版；本篇验证用的工具版本见下表，版本不同、输出格式略有不同是正常的，关键字段不变。
    • 工具版本（2026-11-03 在本机实测，命令见第 8 节）：
    工具 本机实测版本 用途
    dig DiG 9.18.39-0ubuntu0.24.04.8-Ubuntu 查 DNS 解析结果
    curl curl 8.5.0，OpenSSL/3.0.13 看 HTTP 请求与响应、TLS 握手
    openssl OpenSSL 3.0.13 看 TLS 证书与握手
    • 适用前提：你不需要先有服务器、不需要先有域名；第 10 节全部用公开站点 example.com 做演示，这是互联网上专门用来举例的域名，不会给你造成任何影响。

    4. 使用前提¶

    • 一台能上网的电脑，会打开终端（命令行）；
    • 知道怎么复制命令、粘贴到终端、按回车；不知道也没关系，第 9 节会一步一步带你做；
    • 不需要管理员权限：本篇所有命令都不用 sudo，只有第 11 节那个“仅用于本地练习”的 hosts 示例在改系统文件时才需要 sudo，而且那一步是可选的，不做也不影响本篇学习。

    5. 所需资源¶

    • 终端一个；
    • 浏览器一个（任意现代浏览器都可以）；
    • 网络连接一个（家庭宽带、手机热点都可以）；
    • 不需要花钱、不需要注册任何账号、不需要准备服务器和域名。

    6. 技术原理¶

    6.1 互联网是一张“网络的网络”¶

    互联网不是一台电脑，也不是一家公司的机房。它是很多个网络连在一起的总称：你家的路由器是一个小网络，运营商的网络是一个大网络，机房的网络又是一个网络，这些网络之间用路由器连起来，数据就可以从一个网络走到另一个网络。

    数据在网上传输时不是整块搬过去的，而是被切成一个个小包（数据包），每个包都写着“从哪来、到哪去”，路由器按目标地址一个个转发，最后在目的地重新拼起来。就像寄快递：一个大件拆成几个包裹，每个包裹都贴着收件地址，走不同的路线，最后在收件人手里拼回原样。

    6.2 IP 地址：每台设备的门牌号¶

    要把包送到正确的设备，每台联网设备都需要一个地址，这就是 IP 地址。现在常用的有两套：

    • IPv4：形如 93.184.215.14，四组数字，每组 0 到 255，一共约 43 亿个地址，已经不够用了；
    • IPv6：形如 2606:2800:220:1:248:1893:25c8:1946，地址空间极大，是未来的方向。

    IP 地址还分公网和内网：公网 IP 是互联网上唯一的、别人能直接找到你的地址；内网 IP（如 192.168.1.x、10.x.x.x）只在你家或公司内部有效，出了路由器就不再是这个地址。家庭宽带通常只有一个公网 IP，全家人共用，家里的每台设备在内网各有一个内网 IP，路由器负责在内外之间翻译，这就是 NAT（网络地址转换）。所以“家里电脑的 IP”和“别人从互联网上看到的你的 IP”常常不是同一个数字，这不是故障，是正常设计。

    6.3 域名：给人看的名字，DNS 是查号本¶

    IP 地址难记，于是有了域名，如 example.com、crozz.me。人记域名，机器认 IP，中间靠 DNS（域名系统）翻译：浏览器问 DNS 服务器“example.com 的 IP 是多少”，DNS 服务器回答一个 IP，浏览器再拿着 IP 去连接。

    DNS 本身也是分层的：根服务器告诉你去找哪个顶级域（如 .com）的服务器，顶级域服务器告诉你去找哪个权威服务器，权威服务器最后给出答案。平时你感觉不到这几步，是因为运营商或公共 DNS（如 8.8.8.8、1.1.1.1）已经帮你跑完了全程，还把结果缓存一段时间（这就是 TTL，见第 12 节）。

    6.4 TCP：保证数据不丢、不乱序的规矩¶

    IP 只负责“把包送过去”，不管包丢没丢、顺序对不对。TCP 在 IP 之上加了一套规矩：连接前先三次握手确认双方都听得到，传输中每个包都要对方确认收到，丢了就重发，到达后按顺序拼好。网页、文件下载、登录这些“不能错一个字节”的场景都走 TCP。还有 UDP，它不握手、不确认、丢了不管，适合视频通话、游戏这种“宁可丢一点、也不能等”的场景，本篇不展开。

    6.5 HTTP：浏览器和服务器说话的格式¶

    浏览器和服务器之间用 HTTP（超文本传输协议）对话，格式很简单：浏览器发一个请求（我要什么、用什么方法、带什么信息），服务器回一个响应（状态码 + 内容）。一个请求里最关键的三样东西是：

    • 方法：GET（拿东西）、POST（交东西，如提交表单）、HEAD（只拿响应头，不要内容）、PUT、DELETE 等；
    • 网址（URL）：https://example.com/路径?查询，由协议、域名、端口（默认不写）、路径、查询串组成；
    • 状态码：服务器用三位数字告诉你结果，200 是成功，404 是你要的东西不存在，500 是服务器自己出错了（完整对照见第 12 节）。

    6.6 HTTPS：在 HTTP 外面加了一层 TLS 加密¶

    HTTP 本身是明文的：路上任何一个中间节点都能看到你发了什么、服务器回了什么。HTTPS 就是 HTTP + TLS：先做一次 TLS 握手，再在加密通道里传 HTTP。

    TLS 握手只做三件事，记住这三句就够了：

    1. 加密：协商出一套只有浏览器和服务器知道的密钥，路上的人就算截获数据也看不懂；
    2. 身份验证：服务器出示证书，证明“我真的是这个域名的主人”，证书由受信任的机构签发，浏览器会核对证书上的域名和有效期；
    3. 完整性：传输中数据被改过一个字节，接收方都能发现。

    握手过程的概念顺序是：浏览器发 ClientHello（我支持哪些加密方法）→ 服务器回 ServerHello（就用这一种）并出示证书 → 双方算出会话密钥 → 之后所有 HTTP 内容都加密传输。证书怎么申请、怎么签发、怎么续期，是 09-web-hosting 的 HTTPS 章节的事，本篇只讲到“握手在干什么”为止。

    6.7 浏览器渲染：拿到 HTML 只是第一步¶

    浏览器拿到 HTML 后还要做很多事：解析 HTML 建出页面结构，加载 CSS 算出每个元素的样式，执行 JavaScript 改动页面或再发请求拿数据，最后把结果画到屏幕上。所以“网页打开慢”不一定是网络慢，也可能是 CSS、JavaScript、图片太多；“页面是空白的”也不一定是服务器没回东西，可能是 JavaScript 出错了。定位问题时要先分清：是没拿到响应，还是拿到了但渲染出了问题。

    7. 架构说明¶

    一个网页从输入网址到显示出来，完整链路是下面这条线，每一步缺了都会在不同的地方报错：

    你输入网址
  → 浏览器查本地缓存（有没有刚查过的 DNS 结果、刚拿过的页面）
  → DNS 解析：域名 → IP 地址
  → TCP 连接：三次握手，和服务器的 80（HTTP）或 443（HTTPS）端口建立连接
  → TLS 握手（仅 HTTPS）：协商密钥、验证证书
  → HTTP 请求：浏览器发 GET 请求
  → 服务器处理：Web 服务器（如 Nginx）收到请求，静态文件直接返回，动态请求转给应用处理
  → HTTP 响应：状态码 + 页面内容返回浏览器
  → 浏览器渲染：解析 HTML、加载 CSS/JS/图片、画出页面

    对应的各方分工是：

    一方 负责什么 出问题时的典型现象
    DNS 服务器 域名翻译成 IP “找不到服务器”“DNS 解析失败”
    网络与路由器 把数据包送到服务器 超时、连接被重置
    服务器与 Web 软件 接受连接、返回内容 连接成功但状态码是 404、500、502
    浏览器 发请求、渲染页面 白屏、样式错乱、脚本报错
    证书机构与浏览器内置信任库 证明服务器身份 “证书不受信任”“证书已过期”

    12. 每个关键配置项的解释¶

    12.1 dig 输出里的每个字段¶

    以第 13 节里真实跑出来的 example.com. 15 IN A 198.18.237.248 为例：

    字段 含义
    example.com. 查询的域名，末尾的点表示“根”，是 DNS 的完整写法
    15 TTL（生存时间，单位秒）：解析结果可以被缓存 15 秒，15 秒后要重新查；改 DNS 解析后迟迟不生效，常常就是 TTL 和各级缓存还没过期
    IN 类别，固定是 IN（Internet），不用管
    A 记录类型，A 表示 IPv4 地址
    198.18.237.248 查到的 IP 地址（注意：这个值是本机验证环境的解析结果，见第 13 节的特别说明，不要把它当成 example.com 的真实公网 IP 背下来）

    12.2 DNS 记录类型对照表¶

    核对方法：记录类型的定义见 DNS 标准 RFC 1035 及后续扩展；本机核对办法是 dig 域名 类型，有回答就是该域名配了这条记录，无回答不代表这种记录类型不存在，只代表这个域名没配它。

    类型 用途 举例说明
    A 域名指向一个 IPv4 地址 example.com 指向一个 IPv4 地址
    AAAA 域名指向一个 IPv6 地址 支持 IPv6 的站点会同时配 A 和 AAAA
    CNAME 域名指向另一个域名（别名） 把 blog.example.com 指到 example.com，改目标 IP 时只改一处
    MX 这个域名的邮件由哪台服务器收 邮箱服务商会让你配 MX 记录
    TXT 一段文字，常用来做域名所有权验证、发信方验证 搜索引擎验证、AdSense、SPF 都用 TXT
    NS 这个域名的权威 DNS 服务器是谁 域名 NS 改到 Cloudflare，就是改 NS 记录
    SOA 这个域名的起始授权信息（含主服务器、序列号） 一般不用手工改，注册商和 DNS 服务商自动维护
    PTR IP 反向解析成域名 服务器反查、邮件服务器常用
    SRV 某个服务在哪个主机、哪个端口 即时通讯、部分游戏服务用
    CAA 允许哪些机构给这个域名签发证书 限制证书签发方，防止冒签

    12.3 端口对照表¶

    核对方法：本机用 grep 服务名 /etc/services 对照，权威来源是 IANA 的服务名与端口号注册表；下面这张表里的每一项都在本机 /etc/services 里核对过，确实存在（见第 13 节节选）。

    端口 协议 用途 备注
    21 TCP FTP 文件传输 明文，不建议在公网用
    22 TCP SSH 远程登录 服务器管理最常用
    25 TCP SMTP 发邮件 很多家用宽带会封 25 端口出站
    53 TCP/UDP DNS 查域名解析走的就是这个端口
    80 TCP HTTP 浏览器默认的 HTTP 端口，网址里不写就是 80
    443 TCP（UDP 是 HTTP/3） HTTPS 浏览器默认的 HTTPS 端口，网址里不写就是 443
    3306 TCP MySQL 数据库 只应内网访问，不要直接暴露到公网
    5432 TCP PostgreSQL 数据库 同上，只应内网访问
    6379 TCP Redis 同上，只应内网访问
    8080 TCP HTTP 备用端口 开发、测试、代理常用，不是标准 HTTP 端口

    记住一条规矩：端口号 0 到 1023 是系统端口，普通程序绑定需要管理员权限；1024 以上是普通端口，开发时常用 3000、8000、8080、9000 这类。网址里写 :8080 就是明确告诉浏览器“不要走默认端口，走 8080”，例如 http://服务器IP:8080/。

    12.4 HTTP 状态码对照表¶

    核对方法：状态码的定义见 HTTP 标准 RFC 9110 第 15 节；本机只实测了 200 和 404（见第 13 节），其余为标准定义，读者可以用 curl -s -o /dev/null -w "%{http_code}\n" 网址 自行验证。

    状态码 含义 常见场景
    200 成功 页面正常打开
    301 永久重定向 http 跳 https、旧网址换新网址，浏览器会记住新地址
    302 临时重定向 登录后跳回原页面、临时活动页
    400 请求有问题 参数格式错、请求体不合法
    401 需要先登录 没带登录凭证就访问了要登录的页面
    403 服务器拒绝 有登录也不让看，如权限不足、目录被禁
    404 要的东西不存在 网址拼错、文章已删、文件没传上去
    500 服务器内部出错 程序崩溃、配置错误
    502 网关拿到无效响应 Nginx 后面的应用没起来、应用崩了
    503 服务暂时不可用 服务器过载、正在维护

    12.5 curl -v 输出里的关键行¶

    关键行（节选） 含义
    CONNECT example.com:443 浏览器（这里是 curl）请代理帮忙连 example.com 的 443 端口，只在走代理时出现
    TLSv1.3 (OUT), TLS handshake, Client hello 开始 TLS 握手，浏览器先打招呼
    TLSv1.3 (IN), TLS handshake, Certificate 服务器出示了证书
    TLSv1.3 (IN), TLS handshake, CERT verify 浏览器验证证书
    SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 握手成功，本次用的 TLS 版本和加密套件
    > GET / HTTP/1.1 浏览器发出的 HTTP 请求（> 开头是发出去的）
    < HTTP/1.1 200 OK 服务器返回的 HTTP 响应状态行（< 开头是收到的）

    另外一处如实说明：本机用 curl 访问 http://example.com/ 实测返回的是 200，没有复现常见的 301 跳 https。这是因为本机处在代理环境下，代理对 http 请求的处理和直连网络不同。301 本身的定义没有错，读者在自己的直连网络上跑 curl -I http://自己的域名/ 时，很可能会看到 301 和指向 https 的 Location 头，以自己机器的结果为准。

    第三组：openssl s_client 的真实输出（节选）——本机跑不通，如实记录¶

    # echo | openssl s_client -connect example.com:443 -servername example.com（节选，真实输出）
New, (NONE), Cipher is (NONE)
Verify return code: 0 (ok)

    这几行说明：在本机验证环境里，这条命令没有完成 TLS 握手。Cipher is (NONE) 就是“没有协商出加密套件”的意思。原因是本机沙箱只允许经代理的出站连接（上面 curl 能走通正是因为它走了代理），而 openssl s_client 是直接连 example.com:443，直连被拦截，所以握手做不下去。Verify return code: 0 (ok) 在这里不要误读成“证书验证通过了”——没有握手成功，就没有证书可验证。

    替代办法（按顺序试）：第一，用上面 curl -v 的 TLS 握手行确认 TLS 本身是通的；第二，在浏览器里打开 https://example.com/，点地址栏的锁图标看证书信息；第三，到一台有公网直连的电脑或服务器上再跑一次 openssl s_client，在那里你应该能看到 subject=、issuer=、Verify return code: 0 (ok) 这三类行，那时 0 (ok) 才是真正的验证通过。

    14. 成功验证¶

    按下面清单逐项打勾，全部通过才算本篇过关。注意：IP 地址、证书信息以你自己机器上的结果为准，不要和第 13 节的本机结果逐字比对：

    1. dig example.com A 能返回一行 A 记录，你能指出哪一段是 TTL、哪一段是 IP；
    2. curl -v https://example.com/ -o example.html 能看到 TLS 握手行和 SSL connection using TLSv1.3（或你机器上的 TLS 版本），下载到的文件能在浏览器里打开并看到 Example Domain；
    3. curl -s -o /dev/null -w "%{http_code}\n" https://example.com/ 返回 200，换成一个不存在的路径返回 404；
    4. openssl s_client -connect example.com:443 -servername example.com 在你自己的直连网络上能看到 subject=、issuer= 和 Verify return code: 0 (ok)；如果你的网络也走了代理、跑不通，按第 13 节第三组的方法用 curl -v 和浏览器锁图标替代，并能说出跑不通的原因；
    5. 不看书，能按顺序说出浏览器打开网页的七步：DNS 解析 → TCP 连接 → TLS 握手（HTTPS 才有）→ HTTP 请求 → 服务器处理 → HTTP 响应 → 浏览器渲染；
    6. 不看书，能说出 A、AAAA、CNAME、TXT、MX 各自的用途，并能说出 80、443、22、53、3306 各自是谁的端口。

    15. 常见错误¶

    错误现象 常见原因 正确做法
    dig 查不到、或查到的 IP 和别人不一样 各级 DNS 缓存还没过期；解析器被代理改写；域名刚改了解析、TTL 还没到 等 TTL 过期再查；换公共 DNS 交叉核对；不要把一次查询结果当成永久答案
    浏览器报“找不到服务器” 域名没解析出来、或域名根本没注册、或本地网络断了 先 dig 看有没有 A 记录，再看本地网络通不通
    浏览器报证书错误还点了“继续访问” 证书过期、域名和证书对不上、中间人攻击 不要点继续，先核对网址拼写、证书域名和有效期，确认无误再处理
    网址里写了 https://example.com:80 却打不开 HTTPS 默认端口是 443，80 是 HTTP 的端口，协议和端口配错了 HTTPS 不写端口就是 443，HTTP 不写端口就是 80，需要非标准端口时再显式写
    把 192.168.1.10 发给别人让别人访问 内网 IP 只在自己局域网内有效，别人从互联网上找不到它 对外服务要走公网 IP 或域名，内网 IP 只用于局域网内访问
    改了 DNS 解析，立刻就说“没生效” TTL 没过期，各级缓存（运营商、浏览器、系统）还存着旧结果 等一个 TTL 周期，期间用 dig 看权威服务器的回答是不是已经变了
    以为“http 和 https 只是差一个 s” 差的是整层 TLS：加密、身份验证、完整性保护 涉及登录、支付、个人信息的页面必须用 https，明文 http 不要输密码
    把数据库端口直接暴露到公网 以为“端口通了就是能用了”，忽略了访问控制 数据库、Redis 只监听内网，需要远程管理时走 SSH 隧道，不要直接放公网端口

    16. 故障排查¶

    按“先分层、再定位”的顺序查，不要一上来就重启所有东西：

    1. 先看 DNS 通不通：跑 dig 域名 A。有 A 记录，说明 DNS 没问题，往下查；无回答或超时，换公共 DNS 再查一次（dig @8.8.8.8 域名 A），如果公共 DNS 有回答而默认 DNS 没有，就是默认解析器的问题；如果都没有，先确认域名拼写和域名是否已注册。
    2. 再看连接通不通：DNS 有回答但浏览器超时，用 curl -v https://域名/ 看停在哪一步。停在 CONNECT 或 TCP 阶段，是网络或防火墙问题；停在 TLS 握手阶段，是证书或 TLS 配置问题；走到 HTTP 响应阶段但状态码是 4xx、5xx，是服务器或应用的问题。
    3. 证书问题单独查：浏览器报证书错误时，先看证书上的域名是不是你访问的域名、有效期是不是过了、是不是自签名证书。自签名证书在浏览器里一定会报警，这是正常保护，不是“点继续就能解决的小问题”。
    4. 代理与沙箱环境特别说明：如果你和本篇验证环境一样处在代理或沙箱里，dig 结果可能被改写、openssl s_client 直连可能握手失败，这时不要反复重跑同一条命令，改用 DoH 交叉核对 DNS、用 curl -v 看 TLS、用浏览器锁图标看证书，这三样能互相印证。
    5. 缓存问题：改了解析、改了证书、改了页面内容但浏览器还是旧样子时，先分清是哪一级缓存：浏览器缓存（强制刷新或无痕模式）、系统 DNS 缓存、运营商缓存、CDN 缓存。每一级都有自己的过期时间，TTL 只是 DNS 这一级的。
    6. 端口问题：服务起不来或连不上时，先确认服务到底监听在哪个端口、哪个地址。只监听 127.0.0.1 的服务，局域网其他机器是连不上的；端口被别的程序占了，服务会直接启动失败，报错里通常会写明端口号。

    17. 安全注意事项¶

    • 证书警告不要习惯性点“继续”：浏览器报证书错误时，最可能的原因是网址拼错了（钓鱼网站就靠这个），其次是证书真的过期了，点继续等于主动放弃身份验证。
    • 不要在 http 页面输入密码、验证码、支付信息：明文传输意味着路上任何节点都能看到，https 不是“可选项”，是这类页面的底线。
    • 不要把内网服务直接暴露到公网：数据库、Redis、管理后台一旦直接放公网端口，就等于把大门钥匙挂在门上；需要远程访问时走 SSH 或内网穿透，不要图省事开端口。
    • hosts 文件不要乱改、不要从不明来源复制：hosts 会覆盖 DNS 解析，恶意 hosts 条目能把银行、邮箱的域名指向钓鱼服务器；改之前备份，改完不用就恢复，第 11 节的恢复命令就是干这个的。
    • 域名拼写要逐字核对：钓鱼域名常常只差一个字母或把字母换成数字，点链接前先看清域名全称，不要只看页面长得像不像。
    • 公开 WiFi 下不要做敏感操作：即使是 https，公开 WiFi 上的 DNS 劫持、假热点仍然可能把你引到假页面；必须操作时用手机流量或可信网络。

    18. 回滚和恢复¶

    本篇的学习操作本身不改服务器、不改域名解析，所以正常情况下没有什么可回滚的。唯一需要回滚的是第 11 节那个可选的 hosts 练习，恢复方法就是第 11 节写的那条命令，再写一遍：

    # 目录：家目录；用户：需要 sudo（仅这一步）
sudo cp /etc/hosts.bak /etc/hosts

    如果你还做了下面这些事，对应恢复方法是：

    • 下载的 example.html 用完就删：rm example.html（在下载它的那个目录下执行，普通用户即可）；
    • 改过 DNS 解析（本篇没让你改，如果你在别的练习里改过）：把记录改回原来的值，然后等一个 TTL 周期让缓存过期，不要反复改来改去；
    • 在浏览器里点过“继续访问”证书错误的站点：关掉那个标签页，清除该站点的例外（不同浏览器位置不同，一般在隐私与安全设置里），下次再遇到证书错误时重新判断，不要让一次例外变成永久信任。
