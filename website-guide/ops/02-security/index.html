    OPS-02：安全：WAF、限流、漏洞修复、安全响应头、密钥管理完整教程¶

    任务编号：OPS-02（网站建设与部署实战指南 · 生产运营第 2 篇） 上一篇：OPS-01 SEO、性能、缓存、图片优化、访问统计；下一篇：OPS-03 监控、日志、告警、压力测试、可用性检测。 本篇只讲防御性安全运营：WAF、限流、漏洞修复、安全响应头、密钥管理。不讲任何攻击手法、绕过方法、漏洞利用细节；不讲 SEO 与性能优化（那是 OPS-01），不讲监控告警（那是 OPS-03），不讲备份恢复（那是 DB-02 与 OPS-04 的范围）。

    1. 本章目标¶

    读完并动手做完本篇，你能做到下面六件事：

    • 说清 WAF、限流、安全响应头、密钥管理各自防的是哪一类问题，以及它们分别在请求链路的哪一层生效。
    • 照着第 10 节，给自己的站点配出一套完整的 Nginx 安全配置：安全响应头、限流、隐藏文件拒绝、敏感路径拒绝。
    • 上线新规则时先用“只记录不拦截”的观察模式跑一段时间，再切到拦截模式，误拦时能按第 15 节定位到具体规则并处理。
    • 给登录接口和通用接口定出不同的限流值，并说清突发（burst）与延迟（delay）参数的取舍。
    • 按第 10 节的检查清单做一次密钥轮换，并说清密钥泄漏后的应急顺序：先吊销再排查，不要先排查再吊销。
    • 按第 14 节的步骤，用 curl 验证响应头确实下发、限流确实生效，出问题时按第 16 节定位到配置层、规则层还是应用层。

    2. 适用人群¶

    • 已经按 DEPLOY 篇把站点上线的人：站点能访问了，现在要补安全这一层。
    • 负责维护一个或几个小型网站的人：没有专职安全团队，需要一套能自己落地的防御清单。
    • 读过 SRV-01（Web 服务器配置）与 API-01（接口与认证）的人：本篇直接在这些配置上加安全层，不从头讲 Nginx 与接口基础。

    不适用的人：只想做一个本地练习页、还没有对外服务的人，可以先读不做，等站点对外服务时再按第 9 节动手。

    3. 适用系统和版本¶

    • 操作系统：Ubuntu 24.04 LTS 或 Ubuntu 26.04 LTS，普通用户执行日常命令，需要改配置与重载服务时用 sudo。
    • Web 服务器：Nginx 1.24 及以上版本。SRV-01 核查时 Nginx 开源稳定版为 1.30.6（2026-10-14 发布），安装时以官网当场公布的版本为准，本篇的配置项在 1.24 及以上版本均可用。
    • WAF 形态：本篇不绑定某一家具体 WAF 产品，讲的是三层通用做法——CDN 或云厂商托管的 WAF、反向代理层的规则、应用层的输入校验。读者用哪一层，取决于自己站点的部署形态，具体产品的开关位置以该产品当场公布的文档为准。
    • 本篇不涉及任何需要购买的商业产品，示例全部用 Nginx 自带模块（limit_req、limit_conn）与标准响应头实现。

    4. 使用前提¶

    动手前请先确认下面四项，缺一项就先补齐再往下做：

    • 站点已经能正常访问，域名解析与 HTTPS 已经按 DEPLOY-03 配好。本篇是在能跑的站点上加安全层，不是在没跑起来的站点上排错。
    • 你有服务器的 sudo 权限，能改 Nginx 配置并重载服务。
    • 你知道自己站点的后端地址与管理后台路径。本篇的敏感路径拒绝规则要按真实路径改，照抄示例路径等于没配。
    • 你已经按 DB-02 的要求做过备份，至少 Nginx 配置目录有一份能恢复的备份。改安全配置前先备份，这是第 18 节回滚的前提。

    5. 所需资源¶

    • 一台已经上线的 Ubuntu 服务器，上面跑着 Nginx。
    • 一个对外服务的域名，本篇示例统一用保留域名 example.com，读者要换成自己的真实域名。
    • 一份当前 Nginx 配置的备份，存放在配置目录之外或带日期后缀的备份文件里。
    • 访问 Nginx 错误日志与访问日志的权限，用来在观察模式里看规则命中情况。

    6. 技术原理¶

    6.1 请求链路上安全措施的位置¶

    一个请求从访客到应用，一般经过四层，每层的安全措施管的事不一样：

    层 位置 本篇讲的安全措施 不管的事
    边缘层 CDN 或云厂商入口 托管 WAF、大流量清洗 应用内部的业务逻辑
    反向代理层 自己服务器上的 Nginx 安全响应头、限流、隐藏文件与敏感路径拒绝 业务数据的合法性判断
    应用层 后端程序 输入校验、登录限流、权限检查 网络层的流量清洗
    数据与密钥层 配置文件与环境变量 密钥存放、权限、轮换、泄漏应急 请求本身的放行与拦截

    各层是互补关系，不是替代关系。只配了 Nginx 限流，不等于应用层可以不做登录限流；只开了 CDN 的 WAF，也不等于源站可以不设响应头。源站直接暴露时，绕过边缘层就能直达源站，所以源站自己的安全配置不能省。

    6.2 WAF 的基本工作方式（只讲防御侧）¶

    WAF 站在应用前面，按规则检查请求的各个部分：请求路径、请求方法、请求头、请求体里的字段。规则命中时有两种处理方式：

    • 观察模式：只记录命中日志，不拦截请求。用来在新规则上线初期看它会误拦多少正常请求。
    • 拦截模式：命中后直接拒绝请求，通常返回 403。

    新规则必须先走观察模式，再切拦截模式。直接上拦截模式，误拦正常用户时往往要等用户投诉才发现，这是第 15 节要避免的典型错误。

    WAF 规则分两类：通用规则与业务规则。通用规则由规则集提供，覆盖常见的注入类、跨站脚本类、扫描类请求模式；业务规则由自己写，只针对自己站点的管理后台、上传接口、登录接口这类敏感位置。通用规则不要自己从头写，优先用成熟规则集；业务规则不要写得太宽，一条规则只管一个位置。

    6.3 限流的基本原理¶

    限流管的是“单位时间里允许多少请求”，不是“请求内容对不对”。Nginx 的 limit_req 模块用漏桶算法理解最直观：请求以固定速率漏出处理，多余的请求先排队（突发桶），桶满了就拒绝。两个参数决定行为：

    • 速率（rate）：每秒或每分钟允许的请求数，是长期平均值。
    • 突发（burst）：允许短时间超出的排队数量，是短期弹性。

    只设速率不设突发，正常用户一次点开多个页面就可能被误拦；突发设得太大，限流就等于没限。登录接口与通用接口要分开设：登录接口的速率要低得多，因为正常用户一分钟登录不了几次，而通用页面浏览的速率要高得多。限流的键（key）通常是客户端 IP，但要注意：多个用户共用一个出口 IP 时，按 IP 限流会互相影响，这一点在第 15 节有处理办法。

    6.4 安全响应头的作用¶

    安全响应头是服务器在响应里告诉浏览器的“安全策略”，浏览器按策略约束页面行为。它们不拦截请求，管的是浏览器拿到响应之后怎么做：

    • 传输安全类：告诉浏览器今后只用 HTTPS 访问本站。
    • 内容类型类：告诉浏览器不要猜测响应内容的类型，按声明的类型处理。
    • 框架类：告诉浏览器本站页面能不能被嵌进别人的页面里。
    • 引用与权限类：告诉浏览器跨站时带不带引用地址、页面能不能调用某些浏览器能力。
    • 内容安全策略（CSP）：告诉浏览器页面只允许加载哪些来源的脚本、样式、图片，是最强但也最容易配错的一项，需要按第 12 节的取舍单独对待。

    响应头配错的代价是页面功能异常，不是安全事件变多，所以 CSP 一定要在测试环境先验证再上线，这一点在第 9 节的步骤里有明确顺序。

    6.5 密钥管理的生命周期¶

    密钥从生成到作废要走完整的一圈，缺一环就会出事：

    环节 要求
    生成 用系统随机源生成足够长的随机串，不要用人能猜到的口令、不要复用别的站点的密钥
    存放 只放环境变量或权限 600 的专用文件里，绝不进代码仓库、绝不写进前端代码
    使用 程序启动时读一次，日志里绝不打印密钥与 Token，报错信息里也要脱敏
    轮换 定期轮换，泄漏时立即轮换，轮换期间新旧密钥短暂并存、确认新密钥生效后再废旧密钥
    作废 废掉的密钥立即在服务端吊销，只删本地文件不算作废

    7. 架构说明¶

    7.1 本篇的安全分层图（文字表）¶

    访客浏览器
  → 边缘层（CDN 或云厂商入口，可选）：托管 WAF、大流量清洗
  → 反向代理层（Nginx）：安全响应头、限流、隐藏文件与敏感路径拒绝
  → 应用层（后端程序）：输入校验、登录限流、权限检查
  → 数据与密钥层（配置文件与环境变量）：密钥存放、权限、轮换

    每一层只做自己那层的事，层与层之间用日志串起来：边缘层记拦截日志，反向代理层记限流与拒绝日志，应用层记登录失败与权限拒绝日志。排查时先看哪一层的日志里有这条请求，再决定改哪一层。

    7.2 三种部署形态下的取舍¶

    • 只有一台服务器、没有 CDN：反向代理层是主力，WAF 用 Nginx 规则与应用层校验承担，限流与响应头全部在 Nginx 里做。
    • 有 CDN 但源站也直接暴露：必须给源站加同样的响应头与限流，并且限制源站只接受 CDN 回源与管理 IP，否则边缘层的安全措施可以被绕过。
    • 多站点共用一台 Nginx：限流区域（zone）要按站点分开设，不要多个站点共用一个限流区域，否则一个站点的流量高峰会拖垮另一个站点。安全响应头可以共用一份 include 文件，各站点引用同一份。

    8. 操作前检查¶

    动手前按顺序做下面五项检查，全部通过再改配置：

    1. 备份当前 Nginx 配置：把站点配置文件复制一份带日期后缀的备份，例如 cp example.com.conf example.com.conf.bak-20261103，备份文件不要放在 Nginx 会自动加载的目录里，避免被当成配置加载。
    2. 确认 Nginx 配置当前能通过检查：在服务器上跑 nginx -t，看到 syntax is ok 与 test is successful 再往下做。
    3. 记录当前响应头基线：用 curl -I https://example.com/ 看一遍当前响应头，记下来，改完之后对照，确认新增的头确实下发、原有的头没有丢。
    4. 确认日志位置：知道访问日志与错误日志的路径，观察模式的命中记录要去这里看。
    5. 确认后端地址与管理后台路径：敏感路径拒绝规则里的路径必须按真实情况改，照抄示例路径等于没配。

    9. 逐步操作¶

    按下面顺序做，不要跳步，尤其是第 3 步的观察模式不要省：

    1. 备份配置（见第 8 节第 1 项），并确认 nginx -t 通过。
    2. 先加安全响应头：把第 10 节里响应头那一部分加进站点配置，重载后用 curl 验证响应头，再继续。
    3. 再加限流，但先用观察模式：限流规则先配好，配合日志观察一周或至少一个业务高峰，看正常请求会不会被限流挡住，确认误拦率可以接受再切到拦截。
    4. 再加隐藏文件与敏感路径拒绝规则：逐条加，每加一条就用 curl 验证该路径确实返回 403、正常页面不受影响。
    5. WAF 规则同样先观察后拦截：托管 WAF 或反向代理规则先开观察模式，看命中日志，确认没有正常业务被命中，再切拦截。
    6. 最后做密钥检查：按第 10 节的轮换检查清单过一遍，确认没有密钥进仓库、没有密钥出现在日志里、.env 文件权限是 600。
    7. 全部做完后跑一遍第 14 节的验证清单，逐项打勾，留档。

    10. 完整代码¶

    10.1 限流区域定义（http 上下文，存放路径：/etc/nginx/conf.d/security-limits.conf）¶

    限流区域必须定义在 http 上下文里，不能定义在 server 块里，所以单独放一个文件，由主配置文件 include。注意：这个文件里只有区域定义，没有 server 块。

    limit_req_zone $binary_remote_addr zone=general:10m rate=10r/s;
limit_req_zone $binary_remote_addr zone=login:10m rate=1r/m;
limit_conn_zone $binary_remote_addr zone=addr:10m;

    10.2 站点完整安全配置（存放路径：/etc/nginx/sites-available/example.com.conf）¶

    下面是一份完整的站点配置，含安全响应头、限流、隐藏文件拒绝、敏感路径拒绝。示例域名一律用 example.com，读者要换成自己的真实域名；后端地址用 127.0.0.1:8000，读者要换成自己的真实后端地址；管理后台路径用 /admin/ 作示例，读者要换成自己的真实管理路径。

    server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    root /var/www/example.com;
    index index.html;

    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
    add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'" always;

    location / {
        limit_req zone=general burst=20 nodelay;
        limit_conn addr 20;
        try_files $uri $uri/ =404;
    }

    location /api/ {
        limit_req zone=general burst=20 nodelay;
        limit_conn addr 20;
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/login {
        limit_req zone=login burst=3 nodelay;
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location ~ /\. {
        deny all;
        access_log off;
    }

    location ~ ^/(admin|wp-admin|phpmyadmin)/ {
        allow 203.0.113.10;
        deny all;
    }

    location = /healthz {
        access_log off;
        return 200 "ok";
    }
}

    10.3 密钥轮换检查清单（不是代码，是操作清单，逐项打勾）¶

    序号 检查项 通过标准
    1 仓库里没有密钥 在仓库根目录搜密钥文件名与常见密钥变量名，搜不到结果
    2 日志里没有密钥 搜最近一周的应用日志与 Nginx 日志，搜不到密钥与 Token 明文
    3 环境文件权限正确 .env 与凭据文件权限为 600，属主为运行应用的用户
    4 密钥没有复用 每个站点、每个用途的密钥都不一样，换一个站点不影响另一个
    5 旧密钥已吊销 轮换后旧密钥在服务端已吊销，只删本地文件不算完成
    6 轮换后服务正常 轮换后按第 14 节验证一遍，登录、接口、管理后台都正常

    10.4 一个容易抄错的点：限流区域与引用要成对出现¶

    限流分两步，缺一步都不生效：第一步在 http 上下文里用 limit_req_zone 定义区域（第 10.1 节），第二步在 location 里用 limit_req zone=区域名 引用（第 10.2 节）。只定义不引用，等于没限流；只引用不定义，nginx -t 会直接报错。改完配置一定要跑 nginx -t 再重载，不要直接重载。

    本篇涉及的完整配置文件一共三份，路径与用途如下：

    文件 存放路径 用途 权限要求

    12. 每个关键配置项的解释¶

    12.1 安全响应头逐项解释¶

    响应头 取值（示例） 作用 取舍与注意事项
    Strict-Transport-Security max-age=63072000; includeSubDomains 告诉浏览器今后只用 HTTPS 访问本站与子域名 上线初期先用短时间（例如 86400），确认 HTTPS 全站正常后再改长；一旦下发，浏览器在有效期内不会再用 HTTP 访问，改回去也要等过期
    X-Content-Type-Options nosniff 禁止浏览器猜测内容类型，按声明类型处理 几乎没有副作用，新站与老站都可以直接开
    X-Frame-Options SAMEORIGIN 只允许本站自己的页面嵌本站页面，防别人把本站嵌进自己的页面 如果本站确实需要被别的站点嵌（例如嵌入式小部件），这项要改成允许的方案并单独评估，不要直接关掉
    Referrer-Policy strict-origin-when-cross-origin 跨站时只带域名不带完整路径，同站时带完整路径 对统计与外链分析的影响最小的一档，适合大多数站点
    Permissions-Policy camera=(), microphone=(), geolocation=() 禁用页面调用摄像头、麦克风、定位 按自己站点的实际功能改：确实需要某项能力的页面再放开那一项，不要全站放开
    Content-Security-Policy default-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self' 只允许加载本站来源的脚本、样式、图片 最强但最容易配错：用了第三方统计、第三方字体、内联脚本的站点，照抄示例会直接把功能打断。必须先在测试环境验证，再上线；上线初期可以先放宽再逐步收紧

    12.2 限流配置逐项解释¶

    配置项 取值（示例） 作用 取舍
    limit_req_zone $binary_remote_addr zone=general:10m rate=10r/s 区域名 general，内存 10m，速率每秒 10 个请求 通用接口的限流区域，按客户端 IP 记数 速率按自己站点的正常峰值定，不要照抄：先看一周访问日志的峰值，再定一个高于峰值、低于攻击量级的值
    limit_req_zone $binary_remote_addr zone=login:10m rate=1r/m 区域名 login，内存 10m，速率每分钟 1 个请求 登录接口的限流区域，比通用接口严得多 正常用户一分钟登录不了几次，这个值是故意设严的；但要给“输错密码重试”留余地，burst 设 3
    limit_conn_zone $binary_remote_addr zone=addr:10m 区域名 addr，内存 10m 限制单个 IP 的并发连接数 防单个 IP 占满连接数，值按正常浏览器并发数定，示例 20
    limit_req zone=general burst=20 nodelay 引用 general 区域，突发 20，不延迟 突发请求直接处理，不排队 nodelay 让突发请求不等，体验好，但突发桶用完后超出的请求直接拒绝，适合页面浏览
    limit_req zone=login burst=3 nodelay 引用 login 区域，突发 3，不延迟 登录接口允许短时间 3 次尝试 给输错密码重试留了 3 次，第 4 次起按速率限制，防暴力尝试又不至于一次输错就锁死

    12.3 拒绝规则逐项解释¶

    规则 作用 注意事项
    location ~ /. 拒绝所有以点开头的文件与目录的访问，例如版本控制目录与隐藏配置文件 这条规则要放在所有 location 之前或确保优先级正确，否则可能被别的 location 抢先匹配
    location ~ ^/(admin wp-admin phpmyadmin)/
    location = /healthz 健康检查专用路径，不记访问日志 健康检查路径不要带敏感信息，返回内容越简单越好；不要把健康检查路径设成管理后台路径

    13.3 配置检查示例¶

    改完配置后跑 nginx -t，应看到类似下面的输出（示例输出，路径以自己机器为准）：

    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

    只有看到这两行，才能重载服务。nginx -t 只检查语法，不检查限流值合不合理、响应头对不对，这些要按第 14 节逐项验证。

    14. 成功验证¶

    全部做完后，按下面清单逐项验证，每一项都要在自己机器上亲手看到结果，不要只看配置写对了就认为生效了：

    1. nginx -t 通过，看到 syntax is ok 与 test is successful。
    2. 重载服务后，用 curl -I https://example.com/ 检查六个安全响应头全部下发。
    3. 打开首页、文章页、登录页，确认页面功能正常，没有被 CSP 打断的脚本与样式。
    4. 访问一个以点开头的文件路径，确认返回 403。
    5. 从非管理 IP 访问管理后台路径，确认返回 403；从管理 IP 访问，确认能正常打开登录页。
    6. 向登录接口连续发少量请求，确认超过突发后返回 503，并且错误日志里有限流记录。
    7. 检查应用日志，确认没有密钥与 Token 明文。
    8. 检查 .env 文件权限为 600，属主为运行应用的用户。
    9. 检查仓库，确认没有密钥文件与密钥明文被提交。
    10. 把验证结果与配置备份一起留档，下次改配置时对照。

    15. 常见错误¶

    错误 现象 正确做法
    新规则直接上拦截模式 正常用户被误拦，等投诉才发现 先观察模式跑一段时间，看命中日志，确认没有正常业务被命中再切拦截
    限流值照抄示例 正常高峰被限流，或限流等于没限 先看自己站点一周访问日志的峰值，再定高于峰值、低于攻击量级的值
    CSP 照抄示例 第三方统计、第三方字体、内联脚本被打断，页面功能异常 先在测试环境验证，再上线；上线初期先放宽再逐步收紧
    管理后台路径照抄示例 真实管理路径没被保护，示例路径被保护了个寂寞 拒绝规则里的路径必须按真实管理路径改，改完用 curl 逐条验证
    多个站点共用一个限流区域 一个站点的流量高峰拖垮另一个站点 限流区域按站点分开设，不要共用
    限流只定义不引用，或只引用不定义 前者等于没限流，后者 nginx -t 直接报错 定义与引用成对出现，改完必跑 nginx -t
    location 自己写了 add_header 导致 server 层响应头丢失 某个 location 下响应头少了几项 给这个 location 补齐需要的头，或者把头移到共用的 include 文件里统一引用
    密钥写进仓库后只删文件不处理历史 密钥还在提交历史里，任何人拉取历史都能看到 立即吊销该密钥并轮换，不要只删文件；历史里的密钥一律按已泄漏处理
    日志里打印了密钥 报错日志、调试日志里出现 Token 明文 日志输出前脱敏，密钥变量绝不直接打印；已打印的日志要清理并轮换对应密钥
    多个用户共用一个出口 IP 时按 IP 限流误伤 同一出口下的正常用户被连坐限流 评估共用 IP 的比例，必要时给登录接口加应用层的账号级限流，与 IP 限流配合使用，不要只依赖 IP

    16. 故障排查¶

    现象 先查什么 常见原因与处理
    正常页面返回 403 先看是哪个 location 拒绝的，再看错误日志 隐藏文件规则或敏感路径规则的优先级抢了正常路径：调整规则顺序或缩小拒绝范围
    登录接口频繁返回 503 看错误日志里是不是限流记录 限流值低于正常重试量：适当放宽 burst，或给登录接口加账号级限流分流
    响应头少了几项 看生效的 server 块与 location 有没有自己的 add_header location 自写 add_header 会覆盖继承：给该 location 补齐头，或统一用 include 文件
    页面样式或脚本失效 看浏览器控制台报的是不是 CSP 拦截 CSP 来源写窄了：先在测试环境放宽对应来源，确认功能恢复后再逐步收紧，不要直接关掉 CSP
    管理后台从管理 IP 也打不开 确认当前出口 IP 是不是规则里的 IP 管理 IP 变了：更新 allow 规则并重载；没有固定 IP 时改用应用层登录与权限控制
    限流没生效，请求全放行 确认限流区域定义与引用是不是成对出现 只定义不引用等于没限流：补上 location 里的引用并重载
    nginx -t 报错 看报错指向的行号与指令名 限流区域定义放进了 server 块、或引用了不存在的区域名：区域定义放回 http 上下文，区域名两边写一致
    轮换密钥后服务报错 先看新密钥是不是已生效、旧密钥是不是已被吊销 轮换顺序反了：先让新密钥生效并验证通过，再吊销旧密钥；不要先吊销再验证

    区分“被限流拒绝”与“后端挂了”的办法：看错误日志。限流拒绝会在错误日志里留下限流记录，而后端挂了通常是连接失败或超时记录，两者日志内容不一样。不要只看状态码就下结论。

    17. 安全注意事项¶

    • 防御清单不是一劳永逸：规则集、依赖、响应头策略都要定期复查，站点功能变了（例如接了新的第三方服务），CSP 与放行规则要同步评估。
    • 最小权限原则：管理后台只允许必要的 IP，应用运行用户只读自己需要的文件，备份账号只给备份需要的权限，不要图方便给宽权限。
    • 密钥绝不进仓库、绝不进前端代码、绝不出现在聊天记录、工单截图、日志里。截图排错时先把密钥打码。
    • 依赖更新要走流程：先看漏洞通告的影响范围（是不是自己用的版本、有没有对外暴露），再定修复窗口，测试通过再上线，不要一看到通告就直接在生产环境升级。
    • 不要把安全配置本身变成信息泄漏：错误页面不要暴露服务器版本与后端细节，Nginx 版本号按 SRV-01 的做法隐藏，调试信息只在测试环境开。
    • 本篇不讲攻击手法，排错时也不要在生产环境复现攻击行为。验证限流用少量正常请求就够了，不要用压测工具对生产站点做大规模请求。
    • 密钥泄漏的应急顺序固定为：先吊销泄漏的密钥，再排查泄漏范围，再轮换相关密钥并复查日志。顺序反了，泄漏窗口会越拖越长。

    18. 回滚和恢复¶

    改安全配置前的备份就是回滚的底气，回滚步骤如下：

    1. 找到改动前的备份文件，例如 example.com.conf.bak-20261103。
    2. 把当前配置再备份一份（带新日期后缀），避免回滚后想找回当前配置却没有。
    3. 把备份文件复制回原路径。
    4. 跑 nginx -t，确认语法通过。
    5. 重载服务，用第 14 节的清单快速验证一遍：首页能打开、响应头正常、管理后台按预期放行或拒绝。
    6. 如果回滚的是限流规则，还要确认错误日志里不再有误拦记录。

    密钥轮换的回滚与配置回滚不一样：密钥一旦吊销就不能“回滚”回旧密钥，轮换失败时要靠轮换期间新旧密钥短暂并存的窗口恢复，不要把旧密钥重新启用当成常规操作。轮换前务必确认新密钥已验证通过，再吊销旧密钥。

    WAF 规则的回滚：先切回观察模式，再删规则或改规则，不要直接删了拦截规则就以为没事了——观察模式的日志能告诉你这条规则到底拦了什么，删之前看一眼日志。
