    OPS-03：监控、日志、告警、压力测试、可用性检测完整教程¶

    任务编号：OPS-03（网站建设与部署实战指南 · 生产运营第 3 篇） 上一篇：OPS-02 安全：WAF、限流、漏洞修复、安全响应头、密钥管理；下一篇：OPS-04 备份、迁移、灾难恢复、RTO/RPO、恢复演练。 本篇只讲监控、日志、告警、压力测试、可用性检测。不讲 SEO 与性能优化（那是 OPS-01 的范围），不讲安全防护（那是 OPS-02 的范围），不讲备份恢复（那是 OPS-04 的范围，也不讲数据库备份本身，那是 DB-02 的范围）。

    1. 本章目标¶

    读完并动手做完本篇，你能做到下面五件事：

    • 给自己的站点搭一套最小可用的监控：首页与健康端点有人定时查，挂了能发现，而不是等访客来告诉你。
    • 把日志写成结构化的样子，查问题时能按时间、级别、请求定位，而不是在一堆杂乱的输出里翻。
    • 把告警分级，紧急的立刻处理，不紧急的白天处理，不再被半夜的重复告警吵醒。
    • 对自己的站点做一次有节制的压力测试，知道它在多少并发下开始变慢，而不是凭感觉说“应该够用”。
    • 给站点做一个可用性检测与状态页，访客能看到站点当前是否正常，你也能看到它在不同时间的可用率。

    2. 适用人群¶

    • 已经有一个跑起来的站点（参考 DEPLOY 篇部署出来的站点），想让它“有人看着”的人。
    • 一个人或几个人运维小站的人：本篇不讲大型监控平台，只讲一个人能维护得起来的做法。
    • 不需要你会写大型系统，但需要你会看命令行输出、会改配置文件、会用 cron 或 systemd 定时任务。

    3. 适用系统和版本¶

    • 服务器系统：Ubuntu 22.04 LTS 或 Ubuntu 24.04 LTS，普通用户执行日常操作，需要 sudo 的步骤会单独说明。
    • 工具版本（以本篇写作时本机实测为准）：curl 8.5.0（本机实测，见第 13 节），Python 3.12.3（只用来起本地测试服务，不是监控本身的依赖）。
    • 本机实测说明：本机没有安装 logrotate（which logrotate 无结果），所以第 11 节的日志轮转配置只做了结构核对，没有在本机跑 logrotate --debug 验证，读者要在自己的服务器上按第 14 节验证。监控脚本本身不依赖 logrotate，缺了它只影响日志轮转，不影响监控。
    • 监控脚本依赖：bash、curl、awk、date、tee，Ubuntu 默认自带，不需要额外安装。
    • 版本口径：工具的小版本号以读者当场查到的为准，本篇只钉住大方向（用系统自带的 curl 与 cron，不指定某个监控平台的版本）。

    4. 使用前提¶

    • 站点已经能通过域名或 IP 访问，首页能返回 200。
    • 你能在服务器上执行命令，并且知道站点跑在哪个用户、哪个目录下（写配置文件时要填真实值）。
    • 如果站点还没有健康端点（例如 /healthz），先按第 9 节的办法加一个：健康端点只返回“服务还活着”与依赖是否正常，不要返回敏感信息。
    • 压测前提：只对自己的站点压测（见第 17 节红线），压测前先确认当前不是业务高峰，并且已经告诉一起运维的人。

    5. 所需资源¶

    • 一台能访问站点的服务器（就是站点本身所在的服务器，或者另一台能访问它的机器，推荐后者：监控机与被监控的站点分开，站点挂了监控还能报警）。
    • 一个能收到告警的地方：最简单的就是告警日志文件加邮箱或即时通讯的 webhook，本篇先讲日志文件与 webhook 占位，具体的通知渠道按读者自己的工具接。
    • 磁盘空间：日志与监控记录每天都会增长，第 11 节的轮转配置把保留期定为 14 天，读者按自己站点的访问量调整。

    6. 技术原理¶

    6.1 监控看什么：四个信号¶

    业界常用的做法是看四个信号：延迟（请求多慢）、流量（请求多少）、错误（失败多少）、饱和度（资源用到什么程度）。对小站来说，不需要一开始就全上，先抓住两条：

    • 可用性：首页与健康端点是不是 200，挂了多久。
    • 延迟：响应时间是不是突然变长，变长往往是出问题的前兆。

    6.2 黑盒与白盒¶

    • 黑盒监控：从外面看站点，像访客一样请求首页与接口，只关心“外面看得到的结果”。本篇第 10 节的健康检查脚本就是黑盒监控。
    • 白盒监控：从里面看服务，读应用自己的指标与日志，例如数据库连接池用了多少、队列积压了多少。白盒需要应用配合输出指标，本篇讲它的位置与格式要求，不展开某个平台的接入。

    6.3 日志、指标、追踪的分工¶

    • 日志：记“发生了什么事”，一条一条的记录，查问题时用。
    • 指标：记“数值随时间的变化”，例如每分钟请求数、平均响应时间，画图与告警用。
    • 追踪：记“一个请求经过了哪些服务”，单机小站一般用不上，多服务以后再补。
    • 本篇以日志与黑盒检查为主，指标只讲最少的三个：可用率、平均响应时间、错误率。

    6.4 告警的原理：阈值加持续时间¶

    告警不是“超过阈值立刻喊”，而是“超过阈值并且持续一段时间才喊”。本篇脚本的做法是：一次失败不喊，重试 3 次都失败才喊。这样一次网络抖动不会把人吵醒，真正挂了也不会漏报。阈值与重试次数要在第 11 节的配置文件里写清楚，而不是写死在脚本里。

    7. 架构说明¶

    本篇的最小监控架构只有四层，每层负责一件事：

    层 负责什么 不负责什么
    探针层 定时请求首页与健康端点，记录状态码与响应时间 不分析业务逻辑，不读数据库
    记录层 把每次检查结果写进日志文件，把告警写进告警文件 不发通知（通知由下一层接）
    通知层 告警文件有新内容时，通过邮箱或 webhook 通知值班人 不决定告警级别（级别在配置里定）
    展示层 状态页与可用率统计，让访客与运维看到当前状态 不替代探针，状态页的数据来自探针记录

    数据流是单向的：探针定时执行 → 结果写日志 → 失败超过重试次数写告警 → 通知层把告警发出去 → 状态页读日志算可用率。任何一层坏了都不应该让其他层跟着坏：例如通知渠道断了，探针与日志还要继续记，这样恢复后还能看到故障期间的记录。

    健康端点的设计原则：健康端点只做轻量检查（进程在、能连数据库、磁盘没满），不要在健康端点里做重查询；健康端点返回 200 表示“能服务”，返回 503 表示“暂时不能服务”，不要返回 200 但实际已不可用。

    8. 操作前检查¶

    动手前先逐项确认，缺一项就先补齐再往下做：

    • 确认站点首页地址与健康端点地址，例如首页是 https://example.com/，健康端点是 https://example.com/healthz（示例域名，换成读者自己的）。
    • 确认服务器上有 curl：执行 curl --version，能看到版本号即通过。
    • 确认定时任务的运行方式：用 cron 还是 systemd timer，二选一，本篇用 cron 文件做示例。
    • 确认日志目录存在且运行用户可写：本篇示例用 /var/log/monitor/，没有就先建目录并改属主。
    • 确认备份习惯：改任何已有配置文件之前，先复制一份加 .bak 后缀的备份，恢复时直接拷回来（见第 18 节）。

    9. 逐步操作¶

    9.1 建目录与配置文件¶

    以 root 或 sudo 用户执行：

    sudo mkdir -p /opt/monitor /var/log/monitor
sudo chown -R www-data:adm /var/log/monitor
sudo chmod 755 /opt/monitor

    www-data 是示例运行用户，换成读者站点实际的运行用户。日志目录权限 755 配文件 640（见第 11 节），保证只有运行用户与同组能读。

    9.2 放健康检查脚本与配置¶

    把第 10 节的脚本存为 /opt/monitor/healthcheck.sh，把第 11 节的配置存为 /opt/monitor/monitor.conf，然后：

    sudo chmod 755 /opt/monitor/healthcheck.sh
sudo chmod 640 /opt/monitor/monitor.conf
sudo chown www-data:adm /opt/monitor/healthcheck.sh /opt/monitor/monitor.conf
bash -n /opt/monitor/healthcheck.sh

    bash -n 只检查语法，不执行，输出为空即通过。

    9.3 手动跑一次¶

    sudo -u www-data /opt/monitor/healthcheck.sh /opt/monitor/monitor.conf
echo $?
cat /var/log/monitor/healthcheck.log

    退出码 0 表示两次检查都通过，日志里应有两条 OK 记录（见第 13 节的真实输出样子）。

    9.4 接定时任务¶

    把第 11 节的 cron 文件存为 /etc/cron.d/mysite-healthcheck，每 5 分钟跑一次：

    sudo chmod 644 /etc/cron.d/mysite-healthcheck

    cron 文件改完不需要重启 cron 服务，cron 会自动读新文件。等 10 分钟后看日志，应有 2 到 3 次检查记录（每 5 分钟一次）。

    9.5 接日志轮转¶

    把第 11 节的轮转配置存为 /etc/logrotate.d/mysite，然后在自己的服务器上验证（本机未装 logrotate，这一步留给读者）：

    sudo logrotate --debug /etc/logrotate.d/mysite

    --debug 只演练不真正轮转，输出里没有 error 即通过。

    9.6 加健康端点（如果还没有）¶

    健康端点由应用提供，不是由监控脚本提供。最小的健康端点只做三件事：进程在、数据库能连通、返回 JSON 状态。不要在健康端点里返回版本号、内部地址、密钥、用户数据。健康端点的响应时间要短，超过 1 秒就要先优化它本身，否则监控测到的延迟说不清是站点慢还是健康端点慢。

    9.7 做一次压测演练¶

    压测只对自己的站点做，步骤在第 10 节之后、第 14 节之前先讲清顺序：先在低峰时段、小并发起步（例如 10 并发），看响应时间与错误率，再逐步加到 50、100 并发，每一步都记录结果；一旦错误率明显上升或响应时间成倍变长就停，不要继续加压。压测工具本篇不指定某一个，读者用自己熟悉的工具（例如 ab、wrk、hey）按同一套记录方法记结果即可。

    9.8 做一个状态页¶

    状态页可以非常简单：一个静态页面，上面写当前状态（正常/故障）、最近一次故障时间、最近 30 天可用率。可用率的算法在第 12 节讲：用探针日志里的成功次数除以总次数。状态页的数据不要手写，要从日志里算出来，否则状态页本身就会撒谎。

    10. 完整代码¶

    10.1 健康检查脚本¶

    文件存放路径：/opt/monitor/healthcheck.sh，权限 755，属主为站点运行用户。

    #!/bin/bash
# 健康检查脚本：查首页与健康端点，状态码与响应时间判断，失败重试后写告警。
# 用法：healthcheck.sh [配置文件路径]，默认 /opt/monitor/monitor.conf
set -u
CONFIG="${1:-/opt/monitor/monitor.conf}"
# shellcheck disable=SC1090
source "$CONFIG"

check_one() {
    local name="$1"
    local url="$2"
    local attempt=1
    local code=""
    local total=""
    local slow=""
    while [ "$attempt" -le "$RETRIES" ]; do
        read -r code total <<< "$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time "$TIMEOUT_SECONDS" "$url" || echo "000 0")"
        if [ "$code" = "200" ]; then
            slow="$(awk -v t="$total" -v m="$MAX_SECONDS" 'BEGIN { print (t > m) ? "yes" : "no" }')"
            echo "$(date '+%F %T') OK $name $url code=$code time=${total}s" >> "$LOG_FILE"
            if [ "$slow" = "yes" ]; then
                echo "$(date '+%F %T') WARN $name $url slow time=${total}s over ${MAX_SECONDS}s" >> "$LOG_FILE"
            fi
            return 0
        fi
        attempt=$((attempt + 1))
        sleep "$RETRY_WAIT"
    done
    echo "$(date '+%F %T') ALERT $name $url code=$code after $RETRIES attempts" | tee -a "$LOG_FILE" >> "$ALERT_FILE"
    return 1
}

fail=0
check_one "homepage" "$SITE_URL" || fail=1
check_one "health" "$HEALTH_URL" || fail=1
exit "$fail"

    脚本的设计要点：

    • 状态码只认 200，不认 301 或 302：首页如果被跳转，监控应该发现它，而不是把它当成正常。读者如果首页确实要跳转，把期望状态码改成跳转后的最终状态码，并在配置里注明。
    • 响应时间超过 MAX_SECONDS 只写 WARN，不算失败：慢是预警，挂才是告警，两者分开，告警才不会被“慢”淹没。
    • 失败重试 RETRIES 次都失败才写 ALERT：一次抖动不告警，真正挂了才告警。
    • code=000 表示 curl 根本没连上（连接被拒、DNS 失败、超时），不是服务器返回的状态码，排查时先看网络与服务在不在，再看应用日志。
    • 脚本不直接发邮件或 webhook：告警只写进告警文件，通知渠道由读者在告警文件上接（例如另一个定时任务读告警文件发通知），这样通知渠道坏了也不影响探针与日志。

    11. 完整配置文件¶

    11.1 监控配置文件¶

    文件存放路径：/opt/monitor/monitor.conf，权限 640，属主为站点运行用户。示例域名与地址换成读者自己的。

    SITE_URL="https://example.com"
HEALTH_URL="https://example.com/healthz"
TIMEOUT_SECONDS=5
MAX_SECONDS=2
RETRIES=3
RETRY_WAIT=5
LOG_FILE="/var/log/monitor/healthcheck.log"
ALERT_FILE="/var/log/monitor/alerts.log"

    11.2 定时任务文件¶

    文件存放路径：/etc/cron.d/mysite-healthcheck，权限 644。每 5 分钟以 www-data 用户跑一次，运行用户换成读者站点实际的运行用户。

    */5 * * * * www-data /opt/monitor/healthcheck.sh /opt/monitor/monitor.conf

    11.3 日志轮转配置¶

    文件存放路径：/etc/logrotate.d/mysite，权限 644。注意：脚本每次写日志都是打开文件、写一行、关闭文件，不会一直占着文件描述符，所以轮转不需要发信号重载服务，直接生成新文件即可。

    /var/log/monitor/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 www-data adm
}

    如果读者的应用是“一直占着日志文件不关闭”的写法（例如常驻进程打开文件后一直写），上面这份配置要改成 copytruncate（复制后截断原文件），代价是轮转瞬间可能丢一两行日志，两种写法只能选一种，不要同时写。

    12. 每个关键配置项的解释¶

    12.1 监控配置项¶

    配置项 含义 取值建议
    SITE_URL 首页地址，探针查的第一个点 填访客实际访问的首页地址，不要填内网地址（内网通不代表外网通）
    HEALTH_URL 健康端点地址，探针查的第二个点 应用提供的 /healthz，只做轻量检查
    TIMEOUT_SECONDS 单次请求的超时秒数 5 秒；太小会把慢请求误判为挂，太大则故障发现得慢
    MAX_SECONDS 响应时间超过多少秒算慢（只警告） 2 秒；小站首页超过 2 秒就值得看一眼
    RETRIES 失败后重试几次 3 次；1 次太敏感，5 次以上则故障发现得太慢
    RETRY_WAIT 每次重试之间等几秒 5 秒；给服务留一点恢复时间，也避免重试本身变成压测
    LOG_FILE 每次检查结果的记录文件 放在 /var/log/monitor/ 下，权限 640
    ALERT_FILE 告警记录文件，只有重试都失败才写 与日志文件分开，方便通知任务只读告警文件

    12.2 定时任务字段¶

    cron 文件的 6 列依次是：分、时、日、月、周、用户、命令。*/5 * * * * 表示每 5 分钟一次。不要把间隔设得太密：每分钟一次对小站来说已经很密，每 5 分钟是兼顾及时性与日志量的起点，故障发现延迟最多 5 分钟加重试时间，读者按自己能接受的延迟调整。

    12.3 日志轮转指令¶

    指令 含义
    daily 每天轮转一次
    rotate 14 保留最近 14 个轮转文件，超过的删除
    compress 轮转后的旧文件用 gzip 压缩
    delaycompress 最近一次轮转的文件先不压缩，下一次再压（避免正在被读的文件被压缩）
    missingok 日志文件不存在也不报错
    notifempty 空文件不轮转
    create 0640 www-data adm 生成的新文件权限 640，属主与属组按运行用户填

    12.4 可用率算法¶

    可用率 = 成功次数 ÷ 总检查次数 × 100%，按天或按 30 天算。成功指状态码 200（慢也算成功，慢单独统计）。例如一天 288 次检查（每 5 分钟一次），失败 3 次，可用率就是 285 ÷ 288 = 98.96%。状态页上写可用率时，必须同时写统计区间（例如“最近 30 天”），不写区间数字没有意义。

    12.5 告警分级¶

    级别 含义 处理要求
    P1 首页或健康端点连续失败，站点不可用 立刻处理，不分昼夜
    P2 响应时间持续超过阈值，或错误率上升但站点还能访问 当天处理，白天处理即可
    P3 单次慢、单次抖动、磁盘或证书到期提醒 排期处理，不要半夜叫人

    分级要写在值班约定里，而不是只记在某个人脑子里。P3 的告警不要走电话或强提醒渠道，走普通消息即可，否则 P3 会把人吵到对所有告警麻木，这就是告警疲劳。

    13. 执行结果示例¶

    下面是本篇写作时在本机实测的真实输出，测试方法：用 python3 -m http.server 18071 在本地起一个测试服务（目录里有 index.html 与 healthz 两个文件），健康检查脚本的测试配置把两个地址指向 http://127.0.0.1:18071 与 http://127.0.0.1:18071/healthz，重试间隔在测试配置里是 2 秒（生产配置是 5 秒，见第 11 节）。时间戳是测试当天的真实时间，读者在自己机器上跑，时间与响应时间会不同，状态与退出码应该相同。

    13.1 服务正常时的输出¶

    $ /tmp/ops03-test/healthcheck.sh /tmp/ops03-test/monitor.conf
$ echo $?
0

    日志文件内容：

    2026-11-03 15:39:14 OK homepage http://127.0.0.1:18071 code=200 time=0.005538s
2026-11-03 15:39:14 OK health http://127.0.0.1:18071/healthz code=200 time=0.001192s

    成功时没有生成告警文件（告警文件只在失败时才创建），退出码 0，日志里两条 OK 记录，响应时间分别是 0.005538 秒与 0.001192 秒，都在 2 秒阈值内，所以没有 WARN 记录。

    13.2 服务停掉后的输出¶

    停掉测试服务后再跑一次：

    $ /tmp/ops03-test/healthcheck.sh /tmp/ops03-test/monitor.conf
$ echo $?
1

    日志文件追加的内容与告警文件内容相同：

    2026-11-03 15:39:21 ALERT homepage http://127.0.0.1:18071 code=000 after 3 attempts
2026-11-03 15:39:28 ALERT health http://127.0.0.1:18071/healthz code=000 after 3 attempts

    退出码 1，code=000 表示 curl 根本没连上（服务已停，连接被拒），不是服务器返回的状态码。两条告警之间相隔 7 秒，是因为每条检查都重试 3 次、每次间隔 2 秒，读者在生产配置（间隔 5 秒）下会等得更久，这是“重试后再告警”设计本身的代价，不是故障。

    13.3 本次实测的边界¶

    • 本机实测的只是健康检查脚本本身：语法检查 bash -n 通过，成功与失败两条路径都跑通。
    • 没有实测的内容：日志轮转配置没有在本机跑 logrotate --debug（本机未装 logrotate，见第 3 节），读者要在自己的服务器上按第 14 节验证；压测没有在本机跑（压测需要读者自己的站点与低峰时段，不适合在本机对测试服务做样子）；通知渠道（邮件、webhook）没有接通，告警目前只写进告警文件，读者按自己的通知工具接。
    • 没有编造的数据：本篇没有写任何“监控到某次故障”“可用率百分之多少”的记录，所有输出都是上面两段实测日志的原文，生产环境的数字要读者自己跑出来。

    14. 成功验证¶

    按顺序做完下面每一项，才算本篇做完：

    • 手动跑一次脚本，退出码 0，日志里有两条 OK 记录。
    • 停掉测试服务或改一个错的地址再跑一次，退出码 1，日志与告警文件里都有 ALERT 记录，确认重试次数与 code=000 的含义都符合第 10 节的说明。
    • 接上 cron 后等 10 分钟，日志里出现 2 到 3 次检查记录，确认定时任务真的在跑（不要只看 cron 文件存在）。
    • 在自己的服务器上跑 logrotate --debug，输出里没有 error，确认轮转配置能被 logrotate 读懂。
    • 检查日志文件里没有敏感信息：搜一下日志里有没有出现过 token、口令、Cookie、Authorization 头，有就按第 17 节改掉日志写法。
    • 压测演练：低峰时段、小并发起步，记录响应时间与错误率，确认自己知道站点在多少并发下开始变慢。
    • 状态页：从日志里算一次可用率，写上统计区间，确认状态页的数据来自日志而不是手写。

    15. 常见错误¶

    错误现象 常见原因 解决办法
    脚本一跑就报错，提示变量未定义 配置文件路径不对，或配置文件里漏写了某个变量 检查传给脚本的配置文件路径，set -u 下任何未定义的变量都会报错，这是故意的，先补变量再跑
    日志里全是 code=000，但浏览器能打开站点 探针地址填的是内网地址或错地址，或者服务器出站被拦 先在服务器上手动 curl -v 探针地址，看看到底是 DNS、连接还是证书问题，再改配置
    告警半夜响个不停 重试次数太少，或阈值太严，或 P3 走了强提醒渠道 按第 12.5 节分级，P3 走普通消息，重试次数提到 3 次，阈值按第 12.1 节的建议值先跑一段时间再调
    日志文件几个月没轮转，磁盘满了 logrotate 配置没生效，或 cron 的 logrotate 任务没跑 先跑 logrotate --debug 看配置能不能被读懂，再看系统 logrotate 的定时任务在不在
    状态页显示正常，但访客说打不开 探针查的是内网地址，或只查了首页没查接口 探针地址改成访客实际访问的地址，健康端点之外再加一个关键接口的检查
    压测时把站点压挂了 压测并发起步太高，或在高峰时段压测 立即停压测，先恢复服务；下次低峰时段、小并发起步、逐步加压（见第 9.7 节）

    16. 故障排查¶

    按“先分层、再定位”的顺序查，不要一上来就重启服务：

    • 先看探针日志：是 code=000（连不上）还是 5xx（连上了但应用报错）还是慢（WARN 多）。code=000 查网络与进程在不在，5xx 查应用日志，慢查数据库与慢查询（见 DB-02 的慢查询方法）。
    • 再看健康端点：直接 curl 健康端点，看它返回什么。如果健康端点本身就慢或报错，先修健康端点，否则监控数据不可信。
    • 再看资源：磁盘满了会让日志写不进去、数据库写不进去，内存满了会让进程被杀，CPU 满了会让响应变慢，这三项用系统命令先看一眼再往下查。
    • 再看最近改动：故障前有没有改配置、发版、改定时任务，有就先按第 18 节回滚，再慢慢找根因。
    • 查日志时只查必要的信息：不要把整段请求体、整段响应体打进日志，日志里只留方法、路径、状态码、响应时间、错误码，敏感信息一律脱敏（见第 17 节）。

    17. 安全注意事项¶

    • 日志脱敏是红线：日志里绝不出现口令、token、密钥、Cookie、Authorization 头、身份证号、手机号。应用写日志时就要脱敏，不要事后去日志文件里删（删过的日志不可信，删不干净还会漏）。
    • 压测红线：只对自己的站点压测，不要对他人的站点压测。压测本质上是向目标发大量请求，对他人站点压测与攻击没有区别，轻则被封 IP，重则触犯法律。压测前确认目标是自己的站点、时段是低峰、并发是小步起步。
    • 健康端点不要泄露信息：健康端点只返回“正常/不正常”与必要的依赖状态，不要返回版本号、内部地址、数据库结构、环境变量。
    • 告警渠道不要带敏感信息：告警消息里只写“哪个站点、哪个检查、什么状态、什么时候”，不要把日志原文、请求体、密钥贴进告警消息。
    • 监控脚本本身的权限：脚本与配置文件只给运行用户读，告警文件与日志文件权限 640，不要把监控目录设成所有人可写，否则别人改了探针地址，监控就成了摆设。
    • 状态页不要暴露内部信息：状态页是给访客看的，只写对外状态与可用率，不要写服务器地址、内部错误详情、故障根因分析过程。

    18. 回滚和恢复¶

    回滚的意思是“把监控恢复到没做之前的状态”，不是“把站点恢复到没故障之前的状态”，两者不要混淆：

    • 停定时任务：删掉 /etc/cron.d/mysite-healthcheck 文件，cron 会自动不再跑，正在跑的一次不受影响。
    • 停日志轮转：删掉 /etc/logrotate.d/mysite 文件，已轮转的文件不受影响。
    • 停脚本：删掉 /opt/monitor/healthcheck.sh 与 /opt/monitor/monitor.conf 之前，先把它们复制一份到 /opt/monitor/ 之外的备份目录，恢复时拷回来即可。
    • 改过已有配置文件（例如改过 Nginx 配置加健康端点）：改之前先复制一份加 .bak 后缀的备份，恢复时把 .bak 文件拷回原名，再重载服务。
    • 故障恢复的顺序：先恢复服务（按应用自己的恢复步骤），再看监控记录确认服务真的恢复了（日志里重新出现 OK 记录），最后再写故障记录，不要先写记录后恢复服务。
    • 恢复演练：每季度至少做一次“停掉服务、确认告警能出来、再恢复服务、确认告警停止”的演练，没演练过的告警等于没有告警（与 DB-02 的“没演练过的备份等于没有备份”是同一条道理）。
