    ARCH-03：建站方案选型决策树完整教程¶

    任务编号：ARCH-03（网站建设与部署实战指南 · 网站架构第 3 篇） 上一篇：ARCH-02 单体、前后端分离、SSR、SSG、微服务、多站点架构对比与升级路径；下一篇：BE-01 PHP 框架：Laravel、Symfony、ThinkPHP。 本篇只讲选型：用一棵真正能走的决策树，从需求一步步走到一个明确的落点。本篇不重复讲某个框架的完整安装和组件用法，那是各框架自己的文章；不讲服务器的具体部署步骤，那是部署阶段的文章。

    1. 本章目标¶

    读完并动手做完本篇，你能：

    1. 对着六个决策问题，给自己的网站逐一作答，不靠“感觉”选方案；
    2. 从决策树的起点开始，一步步走到一个明确的落点，不走到一半没结论；
    3. 说出五个落点各自是什么、适合什么、不适合什么；
    4. 给五个典型案例各走一遍决策树，并说出为什么不是其他落点；
    5. 看懂一份 Nginx 多站点分流配置，知道每个关键配置项是干什么的。

    2. 适用人群¶

    本篇适合下面这些人：

    • 正准备建站，但不知道该选静态站、博客、后台系统、高并发接口还是多站点的人；
    • 已经有一个想法，但被“别人都用某某框架”带偏过，想先把需求想清楚的人；
    • 负责给团队或客户定方案的人，需要一套能讲清楚、能复核的选型过程；
    • 读过 HTML、CSS、JavaScript 基础篇的读者，不需要先学后端框架。

    不适合只想直接抄一份代码跑起来的人：本篇的重点是“选什么”，而不是“怎么写代码”。选定落点之后，再去读对应框架的文章。

    3. 适用系统和版本¶

    • 操作系统：本篇的决策过程与操作系统无关；第 11 节的 Nginx 配置示例以 Ubuntu/Debian 系的目录结构为准（sites-available + sites-enabled），其他发行版的 Nginx 配置目录不同，改路径即可，配置项本身不变。
    • 软件版本：决策树本身没有版本号；第 11 节示例只用到 Nginx 的通用配置项（listen、server_name、root、location、proxy_pass），不依赖某个大版本的专属写法。
    • 阅读前提：不需要装任何软件。决策树可以在纸上走完；第 11 节的配置只在读者自己的服务器上验证，不需要在本机装 Nginx。

    4. 使用前提¶

    开始走决策树之前，先确认下面四件事，缺一项就先补齐，否则走出来的落点不可靠：

    1. 网站是给谁用的：访客是谁，登录的人是谁，管理员是谁，三者不要混成“用户”一个词。
    2. 网站的核心内容是什么：是文章、是商品、是订单、是数据接口，还是几个独立的网站，先说清楚。
    3. 内容由谁更新、多久更新一次：是技术人员改文件，还是非技术人员在后台点一点就发布。
    4. 团队与预算的真实情况：会不会写代码、有没有人长期维护、服务器预算大概在哪个档位，不要按“理想情况”作答。

    5. 所需资源¶

    • 一张纸或一个文档：把六个决策问题的答案逐一写下来，不要只在脑子里过一遍。
    • 一份需求清单：网站要做的功能列成条目，越多越具体，走树时越不容易走偏。
    • 一台能访问互联网的电脑：用来查各落点对应框架的官方文档，不需要装服务器。
    • 如果走到多站点落点，还需要一台已经装好 Nginx 和 Docker 的服务器（部署细节不在本篇，配置骨架在第 11 节）。

    6. 技术原理¶

    选型决策树的原理很简单：把“建什么网站”拆成六个是非题，按固定顺序逐一回答，每个答案都把可能性缩小一圈，最后只剩一个落点。顺序本身就是原理的一部分：先问部署形态（多站点），再问核心形态（接口还是页面），再问登录与业务数据，最后问内容更新方式。顺序乱了，就容易出现“既像博客又像后台”的中间状态。

    六个决策问题如下，编号在第 9 节和第 10 节的案例里会反复用到：

    • Q1：是不是一台服务器要放多个相互独立的网站？
    • Q2：网站的核心是不是对外提供 API、或者高并发的数据接口（页面只是其中一个调用方）？
    • Q3：需不需要访客注册登录、以及登录后对业务数据做增删改查（订单、会员、库存、工单这类业务记录）？
    • Q4：业务数据的主体是不是文章、资讯、页面内容？
    • Q5：内容更新是不是频繁、且更新人是非技术人员？
    • Q6：团队能不能写代码并长期维护自定义服务，预算够不够支撑自定义服务的运维？

    决策树的走法如下，每个分支都有落点，没有“走到一半没结论”的分支：

    • Q1 是 → 落点 E：多站点（Nginx + Docker）。注意：多站点是一种部署形态，不是内容形态。走到 E 之后，站内的每个子站还要各自再走一遍 Q2 到 Q5，定下每个子站自己的类型，最后统一用 Nginx 分流、Docker 隔离。
    • Q1 否 → Q2。
    • Q2 是 → Q6。Q6 是 → 落点 D：高并发 API（Go/Java/Node.js 类）。Q6 否 → 过渡落点：先用现成系统顶一下（内容型用落点 B，业务型用落点 C 的现成后台产品），把高并发 API 目标记为二期，等有开发与运维人力后再升级到 D。这一支同样有明确落点，不是死胡同，只是落点分“现在”和“二期”两段。
    • Q2 否 → Q3。
    • Q3 是 → Q4。Q4 是 → 落点 B：博客（WordPress/Typecho 类）。Q4 否 → 落点 C：管理后台（Django/Laravel 类）。
    • Q3 否 → Q5。Q5 是 → 落点 B：博客（WordPress/Typecho 类）。Q5 否 → 落点 A：静态站。

    这里要讲清 Q3 和 Q5 里“登录”的区别，否则容易走错：Q3 问的是访客的业务登录（注册账号、下单、查自己的订单、改自己的资料）；Q5 背后的登录是编辑的发布登录（编辑登录后台发文章，访客不需要注册）。一个资讯站可以“访客不用注册、编辑需要登录发文章”，走 Q3 否、Q5 是，落到 B，这不矛盾。

    五个落点一览：

    落点 一句话 典型代表
    A：静态站 内容基本固定，改动时由技术人员改文件、重新发布 纯 HTML/CSS/JS 页面、静态站点生成器输出的页面
    B：博客 内容经常更新，更新人是非技术人员，需要发布后台 WordPress、Typecho 类
    C：管理后台 员工登录后管理业务数据，有权限、有流程 Django、Laravel 类
    D：高并发 API 核心是给 App、小程序、第三方调用的数据接口 Go、Java、Node.js 类
    E：多站点 一台服务器放多个独立网站，统一入口、各自隔离 Nginx + Docker

    7. 架构说明¶

    五个落点的架构形态各不相同，先看清形态，再谈选型：

    • 落点 A 静态站：浏览器直接向 Nginx（或任何静态服务器）要文件，服务器原样返回，没有应用服务器、没有数据库。形态最简单，出错面最小。
    • 落点 B 博客：浏览器 → Nginx → 博客程序 → 数据库。博客程序自带发布后台、评论、分类、主题，编辑在后台发文章，访客看到的是程序渲染出来的页面。
    • 落点 C 管理后台：浏览器 → Nginx → 后端框架程序 → 数据库。程序里有登录、权限、业务表单、审批流程，页面是为“办事”服务的，不是为“阅读”服务的。
    • 落点 D 高并发 API：调用方（App、小程序、第三方系统、前端页面）→ Nginx → API 服务 → 数据库/缓存。API 服务本身不负责“长得好看的页面”，它的产品就是接口。
    • 落点 E 多站点：浏览器 → Nginx（按域名分流）→ 每个子站自己的容器或程序 → 各自的数据。Nginx 只做入口分流，不替子站做业务；每个子站独立部署、独立出问题、独立回滚。

    五个落点的代价对照（只分高、中、低三档，不写没有来源的具体数字）：

    落点 开发工作量 长期维护工作量 出错面
    A：静态站 低 低 小
    B：博客 低 低到中（要及时更新程序与插件） 中（程序与插件都可能出问题）
    C：管理后台 中到高 中到高（权限与业务逻辑要持续有人管） 中到大
    D：高并发 API 高 高（接口、限流、监控、扩容都要有人管） 大
    E：多站点 中到高（取决于子站数量） 中到高（子站越多，维护量越大） 各子站独立，但入口一处出问题会影响所有子站

    每个落点不适合的场景（选型时最容易忽略的一半）：

    • A 静态站不适合：内容每天都变、更新人是非技术人员、需要访客登录后看自己的数据、需要在线交易与审批。
    • B 博客不适合：业务数据复杂（订单、库存、权限、审批流程）、访客登录后要做业务操作、核心是接口而不是页面。
    • C 管理后台不适合：只是发文章、做宣传页、没有业务流程；用后台框架做宣传页，是拿重工具做轻活。
    • D 高并发 API 不适合：访问量本来就不大、核心是页面内容、团队没有人能长期维护自定义服务；为“万一以后火了”提前做高并发，是最常见的过度设计。
    • E 多站点不适合：只有一个网站、或者几个“网站”其实是同一个网站的不同栏目；为多站点付出的隔离与维护成本，只在真的有多个独立网站时才划算。

    8. 操作前检查¶

    走决策树之前，逐项打勾，缺一项就先补齐：

    1. 需求清单有没有写下来：功能条目、访客角色、登录角色、内容更新频率，缺了就先补。
    2. 多站点问题有没有问过自己：到底是多个独立网站，还是一个网站的多个栏目，两个答案走的分支完全不同。
    3. “登录”有没有分清：访客业务登录和编辑发布登录是两回事，混了就会在 Q3 和 Q5 之间走错。
    4. 团队与预算有没有按真实情况作答：会不会写代码、有没有人长期维护、服务器预算在哪个档位，不要按“以后招到人”作答。
    5. 有没有先排除“别人都用某某框架”这种理由：流行不是需求，流行只能作为落点确定之后的参考，不能代替走树。

    9. 逐步操作¶

    按下面七步走，不要跳步：

    1. 先回答六个决策问题：把 Q1 到 Q6 的答案逐一写下来。Q6 在不是 D 候选时可以先空着，等走到 Q2 是的那一步再回答。
    2. 从 Q1 开始走：Q1 是，直接落到 E，并把每个子站单独再走一遍 Q2 到 Q5；Q1 否，进入 Q2。
    3. 走 Q2：核心是高并发 API，就进入 Q6；核心是页面，就进入 Q3。
    4. 走 Q3 和 Q4：需要访客业务登录，就看业务数据主体是不是文章内容，是则落到 B，否则落到 C。
    5. 走 Q5：不需要访客业务登录时，看内容更新频率与更新人，频繁且由非技术人员更新则落到 B，否则落到 A。
    6. 预算与维护人力复核：对照第 7 节的代价表，问自己“这个落点未来一年有没有人维护”。如果答案是否，落点要降一档：D 降为过渡落点，C 降为现成后台产品，E 的子站数量要砍到真的需要的个数。
    7. 把结果写成一句话：格式是“本站落点是 X，因为 Q1 是……、Q2 是……（按实际走过的节点逐一列出）”。写不出来这句话，说明中间有一步是猜的，回到那一步重答。

    10. 完整代码¶

    本节没有要运行的代码，给出五个完整走树案例。每个案例都从 Q1 开始，一步步走到落点，并说明为什么不是其他落点。案例里的网站名、域名都是示例，域名一律用保留域名 example.com 及其子域名，不是真实网站。

    案例一：个人作品集与公司宣传页 → 落点 A 静态站¶

    • 需求：展示个人作品或公司介绍，页面有首页、作品列表、联系方式，内容几个月才改一次，改动时由懂技术的人直接改文件。
    • 走树：Q1 是不是多站点？否，只有一个网站。Q2 核心是不是高并发 API？否，核心是给人看的页面。Q3 需不需要访客业务登录？否，访客只看不登录。Q5 内容更新频繁且由非技术人员更新吗？否，几个月改一次，改的人懂技术。落点 A。
    • 为什么不是其他落点：不是 B，因为没有频繁发布的需求，上博客程序等于多一套需要更新的程序；不是 C，因为没有业务数据与流程；不是 D，因为没有接口产品；不是 E，因为只有一个网站。

    案例二：个人博客与资讯站 → 落点 B 博客¶

    • 需求：作者每周发几篇文章，访客阅读、搜索、评论，作者本人不是技术人员，希望在后台写完点发布就能上线。
    • 走树：Q1 否，只有一个网站。Q2 否，核心是文章页面，不是接口。Q3 否，访客不需要注册登录做业务操作（作者登录后台发文章属于编辑发布登录，不是 Q3 问的访客业务登录）。Q5 内容更新频繁且由非技术人员更新吗？是。落点 B。
    • 为什么不是其他落点：不是 A，因为内容每周都变，靠改文件发布会把作者挡在门外；不是 C，因为没有订单、权限、审批这类业务流程；不是 D，因为核心是阅读不是接口；不是 E，因为只有一个网站。

    案例三：内部订单与客户管理系统 → 落点 C 管理后台¶

    • 需求：员工登录后录入订单、查客户资料、按角色看不同数据、有主管审批环节，数据每天都在变，访客（未登录的人）看不到任何业务数据。
    • 走树：Q1 否，只有一个内部系统。Q2 否，核心是员工办事的页面，不是对外接口（即使内部也调接口，接口也是为这个系统服务的，不是独立产品）。Q3 需不需要访客业务登录与业务增删改查？是，员工登录后要增删改查订单与客户。Q4 业务数据主体是不是文章内容？否，是订单与客户这类业务数据。落点 C。
    • 为什么不是其他落点：不是 B，因为博客做不了角色权限与审批流程；不是 A，因为数据每天变且必须登录；不是 D，因为访问量是内部规模，核心不是对外高并发接口；不是 E，因为只有一个系统。

    案例四：对外 API 服务 → 落点 D 高并发 API¶

    • 需求：给 App、小程序和第三方系统提供数据接口，接口是产品本身，调用量大且有波峰，团队会写 Go 或 Node.js，有人长期维护接口与运维。
    • 走树：Q1 否，只有一个服务（多实例部署不等于多站点，实例是同一个服务的副本，域名与内容相同）。Q2 核心是不是高并发 API？是。Q6 团队能不能写代码并长期维护、预算够不够支撑自定义服务运维？是。落点 D。
    • 为什么不是其他落点：不是 A，因为数据是动态接口，不是固定页面；不是 B，因为博客程序不是为高并发接口设计的；不是 C，因为管理后台的页面框架不是接口产品的核心；不是 E，因为只有一个服务，不是多个独立网站。

    案例五：一台服务器放三个独立网站 → 落点 E 多站点¶

    • 需求：一台服务器上同时放公司官网、公司博客、内部工具三个网站，域名各不相同，各自独立部署、独立出问题、入口统一。
    • 走树：Q1 是不是多站点？是。直接落点 E，不再往 Q2 走（Q2 到 Q5 是给每个子站单独走的，不是给“三个网站合起来”走的）。
    • 每个子站再走一遍：公司官网内容固定、无登录，Q1 否（单看这个子站）、Q2 否、Q3 否、Q5 否，子站落点 A；公司博客内容常更新、作者非技术人员，Q5 是，子站落点 B；内部工具员工登录管业务数据，Q3 是、Q4 否，子站落点 C。三个子站的落点不同，但部署形态统一是 E：Nginx 按域名分流，Docker 各自隔离。
    • 为什么不是其他落点：不是 A/B/C/D 中的任何一个单独落点，因为没有任何一个落点能同时装下三个域名、三种内容、三种部署节奏；多站点落点解决的正是“多个独立网站共用一台服务器”这个问题，而不是某个子站的内容问题。

    11. 完整配置文件¶

    本节选多站点落点做示例，理由是：五个落点里，多站点配置最容易抄错（域名分流写错一个地方，访问就会串站），而静态站、博客、后台的目录结构在各自框架的文章里已经讲过。下面的配置是完整的 Nginx 多站点分流骨架，无省略号，存放路径为 /etc/nginx/sites-available/multi-site.conf（Ubuntu/Debian 系），启用方法是链接到 sites-enabled，修改前先备份，改完先测试再重载，具体步骤在第 14 节。

    server {
    listen 80 default_server;
    server_name _;
    return 444;
}

server {
    listen 80;
    server_name www.example.com;
    root /var/www/site-www;
    index index.html;

    access_log /var/log/nginx/site-www.access.log;
    error_log /var/log/nginx/site-www.error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}

server {
    listen 80;
    server_name blog.example.com;
    access_log /var/log/nginx/site-blog.access.log;
    error_log /var/log/nginx/site-blog.error.log;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name tool.example.com;
    access_log /var/log/nginx/site-tool.access.log;
    error_log /var/log/nginx/site-tool.error.log;

    location / {
        allow 203.0.113.0/24;
        deny all;
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

    注意三点：第一，示例里的域名一律是保留域名 example.com 及其子域名，读者要换成自己的真实域名；第二，203.0.113.0/24 是文档示例网段，不是真实的办公网段，读者要换成自己实际允许的网段；第三，127.0.0.1:8000 与 127.0.0.1:8001 是示例里的本地后端端口，读者要换成自己后端实际监听的端口。

    12. 每个关键配置项的解释¶

    配置项 含义 写错会怎样
    listen 80 default_server 第一个 server 块是默认站点，收没有匹配域名的请求 没有默认块时，未匹配域名的请求会落到第一个 server 块，容易串站
    return 444 直接断开连接，不返回任何页面 写成 404 也可以，但 444 更适合“不想让未知域名看到任何内容”的场景
    server_name 这个 server 块负责哪个域名 域名写错或漏写，请求就会落到默认块或别的站点
    root 静态站的文件根目录 目录写错，页面会 404；目录权限不对，页面会 403
    index index.html 访问目录时默认找的文件 不写时，访问目录可能列出文件列表或 403，取决于其他配置
    try_files $uri $uri/ =404 先找文件，再找目录，都没有就返回 404 不写时，静态站的刷新与深链接容易出问题
    proxy_pass 把请求转发给本地后端程序 端口写错，后端没监听，访问会 502
    proxy_set_header Host $host 把原始域名透传给后端 不写时，后端看到的域名是 127.0.0.1，依赖域名的逻辑会出错
    proxy_set_header X-Real-IP 把访客真实 IP 透传给后端 不写时，后端日志里全是 127.0.0.1，查问题时找不到访客
    proxy_set_header X-Forwarded-For 把经过的代理链 IP 追加透传 不写时，多层代理下的真实 IP 链会丢
    proxy_set_header X-Forwarded-Proto $scheme 把原始协议（http/https）透传给后端 不写时，后端可能误判协议，登录跳转与 Cookie 容易出错
    access_log / error_log 每个站点各自的访问日志与错误日志 不分开写时，三个站点日志混在一起，出问题难定位
    allow / deny 内部工具站只允许示例网段访问，其余一律拒绝 顺序写反（先 deny all 再 allow）时，允许规则不会生效

    13. 执行结果示例¶

    第 11 节配置在读者自己的服务器上验证时，应看到的结果如下（示例输出，实际路径以本机为准，不是本机实测输出）：

    • 修改前备份：/etc/nginx/sites-available/multi-site.conf 旁边多出一个 .bak 文件，内容与修改前一致。
    • 测试配置：nginx -t 的成功提示格式为配置文件语法正确、测试成功两行，缺一不可；只要有一行不是成功提示，就不要重载。
    • 重载之后：用三个域名分别访问，应分别看到官网静态页、博客首页、内部工具登录页，三个站点的访问日志文件里应各自出现对应域名的请求，而不是全挤在一个日志文件里。
    • 串站检查：用一个没有配置过的域名访问，应直接断开连接（对应 return 444），而不是看到某个站点的页面。

    14. 成功验证¶

    按下面步骤在自己的服务器上验证，全部通过才算落点 E 的配置生效：

    1. 备份：修改前先把原配置文件复制一份 .bak，确认备份文件存在。
    2. 测试：跑 nginx -t，确认语法正确、测试成功两行都出现，否则先改配置，不要重载。
    3. 重载：测试通过后再重载 Nginx，不要直接重启整个服务器。
    4. 分域名访问：分别用三个域名访问，确认各站内容互不串位，内部工具站从示例网段之外访问时应被拒绝。
    5. 查日志：分别打开三个站点的访问日志，确认请求按域名分流到了各自的日志文件。
    6. 回滚演练：故意把新配置换回 .bak 文件，重载一次，确认网站回到修改前状态，再换回新配置。回滚演练本身就是验证的一部分，不要等到真出问题才第一次试回滚。

    15. 常见错误¶

    错误 后果 正确做法
    只看“别人都用某某框架”，不走决策树 宣传页上了博客程序，博客上了后台框架，维护成本白白变高 先走 Q1 到 Q6，再谈框架
    把“多个栏目”当成“多个网站” 为一个网站付了多站点的隔离与维护成本 栏目用路径区分，独立域名、独立部署节奏才算多站点
    把编辑发布登录和访客业务登录混为一谈 在 Q3 和 Q5 之间走错，博客被误判成后台，或反过来 按第 6 节的定义分清两种登录再作答
    为“万一以后火了”提前选高并发 API 团队没有运维能力，接口还没火就先被维护拖垮 先按当前真实需求落点，把高并发记为二期目标
    选了多站点，却把三个站点的日志写到同一个文件 出问题时分不清是哪个站点 每个 server 块写各自的 access_log 与 error_log
    内部工具站直接公开访问 内部数据暴露给全网 用 allow/deny 限制网段，或走内网与登录双重保护
    改配置前不备份、不测试就重载 一次手误让所有站点同时出问题 先备份、再 nginx -t、再重载，顺序不要反

    16. 故障排查¶

    • 访问串站（A 域名看到 B 站点内容）：先查 server_name 是否写错、漏写，再查默认 server 块是不是第一个，最后查是不是有旧的 server 块还在 sites-enabled 里没删。
    • 静态站 404：先查 root 目录对不对，再查文件在不在那个目录，最后查目录与文件权限。
    • 静态站 403：先查目录权限，再查 index 有没有写，最后查是不是目录下没有 index.html 又开了目录浏览。
    • 代理站 502：先查后端程序有没有在跑，再查 proxy_pass 的端口对不对，最后查后端日志。
    • 内部工具站从外网也能打开：先查 allow/deny 的顺序，再查示例网段有没有换成真实网段，最后查是不是还有别的 server 块也匹配了这个域名。
    • 改完配置没生效：先确认改的是 sites-available 里被 sites-enabled 链接的那一份，再确认重载过，最后确认浏览器缓存不是旧页面（换隐私模式或清缓存再看一次）。

    17. 安全注意事项¶

    • 内部工具站不要只靠“域名没人知道”来保护：域名可以被猜到、被扫描到，必须有登录与网段限制双重保护。
    • 不要把密码、密钥、数据库连接信息写进 Nginx 配置或公开的示例配置里：配置里只写域名、路径、端口这类公开信息。
    • 未知域名不要返回任何页面：默认块用 return 444 直接断开，比返回默认站点更安全。
    • 博客与后台程序要及时更新：程序与插件的旧版本是常见的入侵口，选 B、C 落点就等于接受了“要有人定期更新”这个维护责任。
    • HTTPS 不要只在入口做一半：走到生产环境时，三个站点都要配 HTTPS，只给其中一个配，等于给另外两个留了明文口子（证书申请与续期的具体步骤在 HTTPS 章节，不在本篇展开）。

    18. 回滚和恢复¶

    • 配置回滚：把第 14 节第 1 步备份的 .bak 文件复制回原路径，跑 nginx -t，通过后再重载。不要直接删新配置了事，删了就不知道回到了哪个版本。
    • 落点回滚：如果发现落点选错了（例如博客其实需要业务流程），不要在原程序上硬改：先把已发布的内容与数据导出来，再按新的落点重建，旧站保留到新站验证通过后再下线。
    • 多站点回滚：只回滚出问题的那一个子站，不要动入口与其他子站；入口配置本身出问题时，才回滚整个 multi-site.conf。
    • 恢复演练：每季度至少做一次“换回备份、重载、确认、换回来”的演练，回滚步骤只有演练过才算真的会。
