    ARCH-02：单体、前后端分离、SSR、SSG、微服务、多站点架构对比与升级路径完整教程¶

    任务编号：ARCH-02（网站建设与部署实战指南 · 网站架构第 2 篇） 前置：NET-01 的互联网与 HTTP 基础、FE-01 的 Vue 3、FE-05 的 Next.js、FE-06 的 Nuxt。本篇只讲架构模式的对比与升级路径，不重讲 Next.js 与 Nuxt 的具体用法（那是 FE-05、FE-06 的范围），不讲具体某个后端框架的写法。 上一篇：ARCH-01 网站完整架构总览；下一篇：ARCH-03 建站方案选型决策树。

    1. 本章目标¶

    读完并动手做完本篇，你能做到下面五件事：

    1. 说清六种架构模式（单体、前后端分离、SSR、SSG、微服务、多站点）各自是什么、在什么情况下用。
    2. 给同一个站点需求，分别画出单体、前后端分离、SSR 三种模式的拓扑（组件、请求流、部署方式）。
    3. 判断一个现有单体项目该不该拆、拆成什么样、按什么顺序拆。
    4. 拆错了知道怎么回退，而不是硬着头皮继续拆。
    5. 给一份前后端分离模式的 Nginx 分流配置，并能逐项解释它。

    2. 适用人群¶

    • 已经能写出一个能跑的网站，但不知道“这个网站该用什么架构”的人。
    • 正在维护一个越长越大的单体项目，想知道要不要拆、怎么拆的人。
    • 要同时管多个站点，或者准备把一个站点拆成多个服务的人。
    • 不适合只想学某一个框架具体写法的人：Vue 的写法在 FE-01，Next.js 在 FE-05，Nuxt 在 FE-06，本篇不重复。

    3. 适用系统和版本¶

    • 系统：本篇讲的是架构选型，与操作系统无关；在 Ubuntu 服务器上部署的例子沿用指南前面的约定（Nginx 做反向代理、应用跑在本地端口上）。
    • 版本：本篇不依赖某个框架的具体版本号。Nginx 配置示例按 Nginx 1.18 及以上版本的通用写法写，不用只有新版本才有的指令；安装时以你机器上 nginx -v 的实际版本和官网文档为准。
    • 前提版本说明：SSR 与 SSG 的概念引用 FE-05（Next.js）与 FE-06（Nuxt），如果你还没有读过这两篇，先读它们再回来看本篇第 7 节的 SSR/SSG 小节，理解会更顺。

    4. 使用前提¶

    开始之前，你应当已经具备：

    1. 能说清浏览器打开一个网页要经过 DNS 解析、TCP 连接、TLS 握手、HTTP 请求与响应这几步（NET-01 的内容）。
    2. 能区分“前端页面”和“后端接口”：前端负责展示与交互，后端负责数据与业务规则。
    3. 有一个可以拿来对照的真实项目，哪怕只是一个待办清单或商品列表：没有具体项目，架构对比很容易变成空话。
    4. 知道本篇的边界：本篇只做选型与升级路径的决策，不替你把代码拆完；拆代码的动手步骤在第 9 节只给顺序与检查点，具体到某一个项目的拆法要结合它的代码结构定。

    5. 所需资源¶

    资源 说明 是否必需
    一个现有项目（或本篇第 10 节的示例需求） 用来套六种模式做对照，没有项目就用第 10 节的示例需求 必需
    一台能跑 Nginx 的服务器或虚拟机 用来验证第 11 节的配置，没有服务器也可以先读配置、后验证 建议有
    纸或白板（或画图工具） 画拓扑用：组件、请求流、部署方式三样必须画出来，只在脑子里想容易漏 建议有
    FE-05、FE-06 两篇 SSR/SSG 的具体用法出处，本篇只引用结论 读过更好

    不需要额外购买云服务、不需要注册域名：本篇的示例全部用本地路径与本地端口讲，域名与备案是 NET-02 的内容。

    6. 技术原理¶

    架构模式回答的其实是三个问题，六种模式只是这三个问题的不同答案组合：

    1. 代码与部署怎么切？ 切成一份（单体）还是多份（前后端分离、微服务、多站点）？切得越碎，单块越好改，但拼起来的成本越高。
    2. 页面在哪里生成？ 在浏览器生成（纯前端渲染）、在服务器每次请求时生成（SSR）、还是提前生成好静态文件（SSG）？生成地点决定了首屏体验、服务器压力与内容更新方式。
    3. 请求怎么流转？ 浏览器是直接找后端，还是经过一层 Nginx 分流？有没有缓存挡在前面？请求流决定了出错时先查哪一层。

    理解这三个问题，就能理解本篇的全部结论：没有一种模式在三个问题上全赢，每一种都是在“好改、好跑、好维护”之间取舍。后面第 7 节的每一节，都会按“是什么、适用场景、优点、缺点、典型坑”五项讲，缺一项都不算讲完。

    一个必须先立住的规矩：架构是为业务规模服务的，不是为“显得先进”服务的。 团队只有一两个人、站点只有几个页面时，选最简单的单体往往是对的；等到单体真的改不动了，再按第 9 节的顺序拆，比一开始就拆成微服务要省得多。

    7. 架构说明¶

    本节按顺序讲六种模式。每一模式都按五项写：是什么、适用场景、优点、缺点、典型坑。读的时候注意：优点与缺点是成对出现的，凡是只讲优点不讲缺点的说法，都不要信。

    7.1 单体（Monolith）¶

    • 是什么： 前端页面、后端接口、业务逻辑、数据访问全部放在一个工程里，打包成一份部署物、跑在一个进程（或同一组相同进程）里。对外只有一个入口。
    • 适用场景： 团队人少、页面与接口数量都不多、业务还在快速变化、需要一个人从头改到尾的项目；个人站点、内部工具、早期产品。
    • 优点： 改动链路最短，改一处、部署一份就能生效；本地调试最简单，不用先把多个服务都跑起来；没有服务间调用，排错时先看一份日志。
    • 缺点： 工程越大，改动越容易互相影响；部署是整包部署，改一个小功能也要重新部署全部；不同模块对资源的需求不同（有的吃 CPU、有的吃内存）时，没法单独扩容。
    • 典型坑： 一是把单体写成“大泥球”：模块之间没有边界，改哪里都牵一发而动全身，拆的时候才发现根本分不开；二是过早拆分：明明还是单体规模，却提前按微服务切目录、切仓库，结果是“分布式单体”，既有单体的耦合，又有分布式的排错成本。

    7.2 前后端分离¶

    • 是什么： 前端与后端是两个独立的工程、两份部署物。前端只负责展示与交互，通过 HTTP 接口向后端要数据；后端只负责接口与业务规则，不直接拼 HTML。
    • 适用场景： 前后端由不同的人或小组负责；同一个后端要同时给网页端与移动端供数据；前端需要独立发版，不想等后端一起部署。
    • 优点： 前后端可以独立开发、独立部署、独立回滚；接口一旦定下来，两边可以并行；前端可以用 FE-01 至 FE-06 的任何框架，后端换语言也不影响前端。
    • 缺点： 多了一层协作成本：接口变了，前后端要一起改；联调与排错要跨两份日志；前端首屏如果是纯浏览器渲染，首屏体验与搜索引擎收录要另外处理（这正是 SSR/SSG 要解决的问题）。
    • 典型坑： 一是接口没有版本与文档意识：后端悄悄改字段，前端线上直接报错；二是跨域与鉴权没提前定好：开发时用代理绕过去，上线才发现 Cookie、跨域、登录态全是问题；三是把“分离”理解成“各写各的”，接口契约没人负责，最后两边互相等。

    7.3 SSR（服务端渲染）¶

    • 是什么： 每次浏览器请求页面时，服务器先把页面内容渲染成 HTML 再返回，浏览器拿到的是已经有内容的页面，之后再由前端接管交互。结论引用 FE-05 与 FE-06，具体框架用法不在本篇重讲。
    • 适用场景： 首屏内容重要、希望搜索引擎直接看到完整内容、页面内容随用户或随数据变化的站点，例如内容站、商品详情页、带登录态的页面。
    • 优点： 首屏能看到内容，不用等前端下载完脚本再拼页面；搜索引擎收录友好；需要登录态或个性化内容的页面也能在服务端拼好。
    • 缺点： 每次请求都要在服务端渲染，服务器压力比纯静态大；服务端与浏览器两份运行环境，写代码时要分清哪些代码只能在浏览器跑（例如直接读 window 的代码不能原样放在服务端）；排错要同时看服务端渲染日志与浏览器日志。
    • 典型坑： 一是把所有页面都做成 SSR，包括根本不需要每次渲染的页面，白白增加服务器压力；二是服务端与浏览器状态不一致：服务端渲染一份、浏览器接管后又改成另一份，页面会闪一下；三是把浏览器专属 API 写进服务端渲染路径，上线才发现服务端报错。

    7.4 SSG（静态站点生成）¶

    • 是什么： 在构建（部署前）时就把页面提前生成成静态 HTML 文件，部署后服务器只负责把文件原样返回，不再每次请求时渲染。结论引用 FE-05 与 FE-06，具体框架用法不在本篇重讲。
    • 适用场景： 内容不常变、或者可以接受“改内容后重新构建一次”的站点，例如文档站、博客、产品介绍页、指南站本身这类内容。
    • 优点： 部署后几乎没有渲染成本，服务器压力最小；静态文件最容易做缓存与分发；没有运行时渲染，出错面最小。
    • 缺点： 内容一改就要重新构建与部署，不能像 SSR 那样“请求时现算”；页面数量很大时构建时间会变长；需要登录态、个性化、实时数据的页面不适合纯 SSG，要另外用接口补数据。
    • 典型坑： 一是把需要实时数据的页面硬做成纯静态，上线后数据永远是构建那一刻的旧数据；二是构建时间失控：页面成千上万还每次全量重建，改一个错别字也要等很久；三是把 SSG 与“不用后端”画等号：评论、搜索、表单提交这类动态能力仍然需要后端或第三方服务。

    7.5 微服务¶

    • 是什么： 把后端按业务边界拆成多个独立服务，每个服务有自己的代码、部署物，服务之间通过 HTTP 接口或消息互相调用。注意：微服务是“后端拆法”，不是“前后端分离”的同义词；一个项目可以既是前后端分离、后端又是微服务。
    • 适用场景： 业务已经大到单体改不动、不同业务模块的发布节奏与资源需求差别很大、有多个小组各自负责一块业务、某一块业务需要单独扩容或单独用另一种技术栈。
    • 优点： 每个服务可以独立开发、独立部署、独立扩容、独立选技术栈；单个服务出问题，影响面可以控制在该服务内（前提是调用链与降级设计得好）。
    • 缺点： 成本是六种模式里最高的：服务发现、配置、日志、监控、链路追踪、分布式事务、接口版本，缺一不可；一次请求跨多个服务，排错要串多份日志；数据一致性从“一个数据库里的事务”变成“多个服务之间的协调”，复杂度跳了一个量级。
    • 典型坑： 一是拆得太早、拆得太碎：服务数量超过团队能管的数量，改一个功能要改五个服务；二是边界切错：两个服务天天互相调用、改一个就要改另一个，说明边界本身就是错的，应当合并不应当拆；三是没有先把单体内部的模块边界理清就直接拆，结果是把单体内部的混乱原样复制成分布式混乱。

    7.6 多站点¶

    • 是什么： 一台服务器（或一组服务器）同时托管多个站点：每个站点有自己的域名（或子域名）、自己的内容与配置，对外是多个独立的网站，对内共用同一套服务器、Nginx 与运维流程。多站点是“部署与托管方式”，不是“一种页面生成方式”：每个站点内部仍然可以是单体、前后端分离、SSR 或 SSG 中的任何一种。
    • 适用场景： 一个人或一个团队同时维护多个站点（例如指南站、工具站、演示站）；多个站点规模都不大，单独各买一台服务器不划算；多个站点要统一做 HTTPS、日志、备份与监控。
    • 优点： 服务器与运维成本分摊；Nginx、证书、日志、备份可以统一管理；新加一个站点主要是加一份配置，不用重搭整套环境。
    • 缺点： 站点之间互相影响：一个站点流量暴涨或出问题，可能拖累同机的其他站点；配置一改错，可能影响多个站点；权限与数据隔离要格外小心，一个站点的漏洞不应当能读到另一个站点的数据。
    • 典型坑： 一是共用配置不做隔离：多个站点共用同一个应用进程或同一个数据库账号，出问题一起倒；二是域名与证书管理混乱：新站点的域名解析、证书、Nginx 配置三处对不上，上线才发现打不开；三是备份只备了整机、没按站点分：恢复某一个站点时，不知道该恢复哪一份。

    7.7 六种模式对照表¶

    下表只做对照，不做排名：没有哪一行是“永远最好”的，选型要看第 9 节的判断方法。

    模式 代码与部署 页面生成 适合的规模 最怕什么
    单体 一份工程、一份部署物 前后端同工程，页面生成方式自选 小到中 工程长成大泥球、改不动
    前后端分离 前后端两份工程、两份部署物 前端渲染为主，可再叠加 SSR/SSG 中 接口契约没人管、联调扯皮
    SSR 前后端可分可合，关键在服务端渲染 每次请求时服务端渲染 中到大，首屏与收录重要 服务端压力、两端状态不一致
    SSG 构建时生成，部署后是静态文件 提前生成 内容不常变 内容要实时变、构建时间失控
    微服务 后端拆成多个独立服务 与页面生成方式无关 大，且已有清晰业务边界 拆太早、拆太碎、边界切错
    多站点 多个站点共用服务器与运维 每个站点自选 多个小到中站点 站点互相影响、配置与权限不隔离

    注意一个容易混淆的点：SSR、SSG 回答的是“页面在哪里生成”，单体、前后端分离、微服务、多站点回答的是“代码与部署怎么切”。这两个维度可以组合：例如一个前后端分离的项目，前端可以用 SSR；一个多站点部署里，甲站用 SSG、乙站用单体，互不冲突。

    8. 操作前检查¶

    在动手改架构之前，先把下面六项核对完，缺一项就先补齐，不要直接开拆：

    1. 现有规模写下来： 页面数量、接口数量、团队人数、每天大概的访问量级（不用精确数字，写“个人用”“小范围用”“公开访问”这个量级就够了）。没有规模数字的选型讨论都是空话。
    2. 痛点写下来： 现在最痛的是什么？是改不动、部署太慢、首屏太慢、收录不好，还是多站点管不过来？痛点不同，答案不同：改不动指向拆分，首屏与收录指向 SSR/SSG，多站点混乱指向隔离与配置管理。
    3. 模块边界画出来： 现有代码里哪些模块经常一起改、哪些几乎不互相碰？经常一起改的模块不应当拆到两个服务里。
    4. 接口清单拉出来： 前后端分离与微服务的前提是接口清单，没有清单就先把清单列出来，再谈拆。
    5. 回退方案想好： 拆错了怎么回去？第 9.4 节讲回退，动手前就要想好，不要等拆坏了再想。
    6. 验证方法定好： 改完之后怎么证明变好了？是部署时间、首屏表现、收录情况，还是多站点互不影响？验证方法要在动手前定，不要事后找理由。

    9. 逐步操作¶

    9.1 判断：这个项目该不该拆¶

    按下面顺序问，问到“否”就停在当前模式，不要继续往下拆：

    1. 单体是不是真的改不动了？如果只是代码写得乱，先在单体内部把模块边界理清、把大文件拆小，而不是直接上微服务。
    2. 是不是有明确的、可独立发布的一块业务？例如订单模块每周都要发版、内容模块几个月才改一次，发布节奏差得很多，才值得拆。
    3. 是不是有某一块业务需要单独扩容或单独用另一种技术？如果没有，拆分的收益还抵不上多出来的运维成本。
    4. 团队能不能管得住拆出来的服务数量？服务数量超过团队能看日志、能值班的数量，就是拆过头了。

    9.2 拆的顺序：从最不痛的地方开始¶

    推荐顺序（不要一上来就拆核心业务）：

    1. 先把单体内部的模块边界理清：目录、函数、数据访问按业务分开，互相调用只走明确的接口，而不是随手跨模块读写。
    2. 先拆“边缘且独立”的模块：例如独立的后台管理、独立的报表、独立的文件处理，这些模块与其他模块来往少，拆坏了影响面也小。
    3. 再做前后端分离（如果还没分）：把前端静态资源与后端接口分开部署，Nginx 按第 11 节分流，先让“一份变两份”跑稳。
    4. 再按需叠加 SSR 或 SSG：首屏与收录有问题的页面走 SSR，内容不常变的页面走 SSG，不要全站一刀切。
    5. 最后才考虑微服务：而且一次只拆一个服务，跑稳一个再拆下一个，不要一次性全拆。

    9.3 拆成什么样：边界怎么定¶

    • 按业务定，不按技术定：按“订单、商品、用户”这种业务边界拆，不要按“前端组、后端组、数据库组”这种技术边界拆。
    • 一个服务只负责一件事：服务名能用一句话说清它负责什么，说不清的边界就是错的。
    • 服务之间只走接口，不共享数据库表：两个服务共用同一张表，等于没拆，改表还是要两边一起改。
    • 每个服务都要有自己的日志、监控与回退办法：拆完才发现某个服务没有日志，等于拆完就失明。

    9.4 拆错了怎么回退¶

    回退不是“失败”，是升级路径的一部分，动手前就要准备好：

    1. 保留旧部署物： 拆之前先把旧单体的完整部署包与配置文件备份好，注明存放路径与恢复命令（见第 18 节），不要拆完就删旧包。
    2. 先并行、后切换： 新服务先在旁边跑起来，用一小部分流量或内部测试验证，确认没问题再把流量切过去，不要直接把旧服务停掉。
    3. 接口保持兼容： 拆的过程中旧接口不要悄悄改字段或返回值，改接口要先加新版本、再逐步迁移调用方。
    4. 回退触发条件提前写好： 例如错误率明显上升、核心流程走不通、回退窗口内修不好，就按原定步骤切回旧部署物，不要在故障现场临时想回退办法。
    5. 回退后复盘再拆： 回退不是终点，记下这次拆错的原因（边界切错、顺序不对、接口没对齐），下一次换一个更小的切口再试。

    9.5 常见错误做法（只写在表格与行内代码里，不写成带围栏的代码块）¶

    错误做法 为什么错 应当怎么做
    一上来就把单体拆成十几个微服务 团队管不住，改一个功能要改多个服务 先理清单体内部边界，一次拆一个
    把 user 表同时给两个服务读写 等于没拆，改表还是两边一起改 每个服务只读写自己的数据，跨服务走接口
    所有页面无差别做 SSR 不需要每次渲染的页面白白增加服务器压力 只有首屏与收录重要的页面走 SSR，其余按需选 SSG 或前端渲染
    内容每天都变的页面用纯 SSG 且不重建 上线后数据永远是构建那一刻的旧数据 要么改走 SSR，要么把动态部分改成接口补数据
    多站点共用同一个数据库账号与进程 一个站点出问题拖累其他站点，漏洞也可能横向扩散 按站点隔离账号、进程与数据目录
    拆完就删旧部署包 回退时无物可回 旧包与旧配置按第 18 节备份，保留到新架构跑稳

    10. 完整代码¶

    本节不用“一张对比表就结束”。先定一个示例需求，再分别写出单体、前后端分离、SSR 三种模式的完整拓扑：组件、请求流、部署方式三样都要写全。三种模式共用同一个需求，差别只在架构，这样对照才有意义。

    示例需求（三种模式共用）：一个小型“内容 + 商品”站点，功能固定不变——首页、文章列表与文章详情、商品列表与商品详情、购物车、下单、后台管理（文章与商品的增删改）。团队三个人，站点刚上线，访问量级为“小范围公开访问”。

    10.1 单体模式拓扑¶

    层 组件 说明
    入口 Nginx（80 端口） 只做一件事：把请求转发给应用进程，不做前后端分流
    应用 单体应用进程（本地 8000 端口） 首页、文章、商品、购物车、下单、后台管理全部在同一个工程里；页面由后端模板或同一工程的前端代码渲染
    数据 数据库（本地，不对外） 文章、商品、订单、用户都在同一个库里，表之间可以直接关联
    静态文件 与应用同一台机器的静态目录 图片与样式文件由 Nginx 或应用直接返回，不单独部署

    请求流（单体）：

    步骤 动作
    1 浏览器请求首页
    2 Nginx 转发给本地 8000 端口的单体应用
    3 应用读数据库，拼出首页 HTML，返回给浏览器
    4 浏览器请求商品详情，同样走 Nginx → 应用 → 数据库 → 返回 HTML
    5 下单请求同样走同一条链路，订单写入同一个库

    部署方式（单体）：一份代码、一份部署包、一次部署全部生效；回退就是换回上一份部署包（见第 18 节）。

    10.2 前后端分离模式拓扑¶

    层 组件 说明
    入口 Nginx（80 端口，按路径分流，配置见第 11 节） / 走前端静态，/api/ 走后端接口
    前端 前端静态文件（独立部署物） 首页、文章、商品、购物车、下单、后台管理页面全部由前端工程构建出静态文件，部署后只负责展示与交互
    后端 后端接口进程（本地 8000 端口） 只提供接口：文章接口、商品接口、购物车接口、订单接口、管理接口；不直接拼 HTML
    数据 数据库（本地，不对外） 与单体模式相同，文章、商品、订单、用户在同一个库里

    请求流（前后端分离）：

    步骤 动作
    1 浏览器请求首页：Nginx 返回前端静态文件，浏览器先拿到页面骨架
    2 前端脚本向 /api/articles 请求文章列表，后端读库返回 JSON，前端再把列表渲染出来
    3 浏览器请求商品详情：前端先渲染详情页骨架，再向 /api/products/某商品编号 要数据并填充
    4 下单：前端把购物车内容 POST 到 /api/orders，后端写库并返回订单号，前端显示下单成功
    5 后台管理：前端管理页同样走接口增删改文章与商品，不直接碰数据库

    部署方式（前后端分离）：前端与后端各一份部署物，可以分开发布；前端改了只重新部署静态文件，后端改了只重启接口进程；回退也是分开回退，互不牵连（但接口变了要前后端一起对齐，见第 15 节）。

    10.3 SSR 模式拓扑¶

    层 组件 说明
    入口 Nginx（80 端口） 转发给 SSR 应用进程；静态资源（图片、样式、脚本）可由 Nginx 直接返回，不必每次都走渲染
    应用 SSR 应用进程（本地 3000 端口） 每次请求时在服务端渲染页面：首页、文章详情、商品详情都在服务端拼好 HTML 再返回；浏览器拿到 HTML 后再由前端脚本接管交互（例如购物车加减、筛选）
    接口与数据 后端接口与数据库（可在同一进程内读库，也可走独立接口进程） 本示例为求简单，让 SSR 进程直接读库；规模变大后再把接口拆成独立进程，不要一开始就把两层都拆
    静态文件 与应用同一台机器的静态目录，或由 Nginx 直接返回 构建产物中的静态资源不走渲染流程

    请求流（SSR）：

    步骤 动作
    1 浏览器请求商品详情
    2 Nginx 转发给本地 3000 端口的 SSR 应用
    3 SSR 应用读数据库，拿到该商品的数据，在服务端拼出完整详情页 HTML，返回给浏览器
    4 浏览器直接看到商品内容，不用等脚本下载完再拼页面；之后前端脚本接管购物车按钮等交互
    5 下单仍走接口：前端脚本把购物车内容提交给订单接口，后端写库并返回订单号

    部署方式（SSR）：一份 SSR 应用部署物，部署后每次请求都要渲染，服务器压力比纯静态大；静态资源走 Nginx 直返，不走渲染；回退就是换回上一份 SSR 部署包。

    10.4 三种拓扑对照（在完整拓扑之上再对照，不代替拓扑）¶

    对照项 单体 前后端分离 SSR
    部署物数量 1 份 2 份（前端静态 + 后端接口） 1 份 SSR 应用（另加静态资源）
    首屏内容来源 服务端拼好或同工程渲染 浏览器拿到骨架后再向接口要数据 服务端每次请求时拼好
    改前端要不要动后端 要一起部署 不用，前端单独部署 SSR 应用一起部署
    改接口要不要动前端 同工程内改 要对齐接口契约 接口在应用内或独立进程，视实现而定
    出问题先查哪份日志 单体应用日志 前端日志 + 后端接口日志，先分清是哪一边 SSR 服务端日志 + 浏览器日志
    本示例下最适合的阶段 刚上线、团队小、功能还在快速变 前后端分工明确、前端要独立发版 首屏与收录重要、详情页内容随数据变

    读完本节应当能回答：同一个需求换一种模式，到底换了什么？答案是：换的是“部署物数量、页面生成地点、请求流经的层数”，不是换功能清单。功能清单三种模式完全相同，差别全在上面这张表里。

    11. 完整配置文件¶

    本节以前后端分离模式为例，给一份完整的 Nginx 分流配置：前端静态与后端 API 分开走。存放路径：服务器上的 /etc/nginx/sites-available/shop，启用方式是链接到 /etc/nginx/sites-enabled/ 后执行 nginx -t 检查再重载（重载命令与备份方法见第 18 节）。

    server {
    listen 80;
    listen [::]:80;
    server_name shop.example.com;

    access_log /var/log/nginx/shop.access.log;
    error_log /var/log/nginx/shop.error.log;

    location / {
        root /srv/www/shop-frontend/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 10m;
    }

    location /static/ {
        root /srv/www/shop-frontend/dist;
        expires 7d;
        add_header Cache-Control "public";
    }
}

    注意：上面配置里的域名 shop.example.com 与目录 /srv/www/shop-frontend/dist 都是示例占位，部署时要换成你自己的域名与实际的前端构建输出目录；后端地址 127.0.0.1:8000 是指与 Nginx 同一台机器上的后端接口进程，如果后端在另一台机器上，要换成那台机器的内网地址，不要写成公网地址暴露给所有人。

    12. 每个关键配置项的解释¶

    配置项 含义 写错了会怎样
    listen 80 与 listen [::]:80 监听 IPv4 与 IPv6 的 80 端口 只写其一，另一协议的用户打不开
    server_name shop.example.com 这个 server 块只接这个域名的请求 写错域名，请求会落到默认 server 块，表现就是“打不开或打开了别的站”
    location / 配 try_files $uri $uri/ /index.html 前端是单页应用时，刷新深层路由也要返回首页，再由前端路由接管 不写最后的 /index.html，刷新详情页会直接 404
    root /srv/www/shop-frontend/dist 前端静态文件的实际目录 目录写错，前端页面全部 404
    location /api/ 配 proxy_pass http://127.0.0.1:8000 以 /api/ 开头的请求转发给后端接口进程 漏写末尾的斜杠含义会变：proxy_pass 后面有没有 URI，转发时的路径拼接规则不同，改动前要对照官网文档核对，不要凭感觉改
    proxy_set_header Host $host 把原始域名透传给后端 不传，后端看到的域名是 127.0.0.1，依赖域名的逻辑会出错
    proxy_set_header X-Real-IP 与 X-Forwarded-For 把真实客户端 IP 透传给后端 不传，后端日志里全是 127.0.0.1，排错与限流都无从下手
    proxy_set_header X-Forwarded-Proto $scheme 把原始协议（http/https）透传给后端 不传，后端可能误判协议，生成错误的跳转链接
    client_max_body_size 10m 允许的请求体上限 上传图片或大表单时不设或设太小，会直接报 413
    location /static/ 配 expires 7d 静态资源让浏览器缓存 7 天 缓存时间设太长且文件名不带哈希，改了静态文件用户还看到旧的；设太短则每次都要重新下载

    13. 执行结果示例¶

    本节不贴“编出来的性能数字”。架构选型在本机无法用一次运行证明好坏，能实测的是下面三件可以真实看到的东西：

    1. Nginx 配置能通过检查： 在服务器上执行 nginx -t，应当看到测试成功的提示；如果提示配置文件有错，按提示的行号回去改，不要跳过检查直接重载。
    2. 分流能按预期走： 部署第 11 节的配置后，浏览器访问首页应当返回前端静态页面，访问 /api/ 下的一个已知接口应当返回后端接口的响应（JSON 或接口约定的格式），两者不要串位：首页返回 JSON、接口返回 HTML，都说明分流写错了。
    3. 拓扑能对应上真实部署： 把第 10 节的拓扑表拿出来，逐行对应你机器上的实际进程与端口：Nginx 在 80 端口、前端静态目录存在、后端接口进程在 8000 端口（或 SSR 应用在 3000 端口），缺一行就说明部署还没做完。

    如果上面三件都对得上，第 11 节的配置就算“执行成功”；至于“这种架构是不是比另一种更好”，那不是一次命令能证明的，要按第 14 节的方法在真实使用中观察，不要在本篇里找一个数字当答案。

    按下面五步验证，全部通过才算完成本篇的学习与动手：

    1. 六种模式能复述： 不看本篇，能说出每种模式的适用场景、优点、缺点、典型坑各至少一条；说不出的那一种，回第 7 节重读。

    3. 升级路径能判断： 给一个假设的现有单体项目，能按第 9.1 节的四个问题判断该不该拆，并按第 9.2 节的顺序写出拆的第一步是什么。
    4. Nginx 配置能通过检查： nginx -t 通过，且首页与 /api/ 分流实测没有串位（见第 13 节第 2 条）。

    15. 常见错误¶

    错误 后果 正确做法
    只看优点选模式，不看缺点 上线后才发现缺点正好打在自己的痛点上 按第 7 节每种模式的五项逐项对照，缺点也要打勾
    把 SSR 与 SSG 混为一谈 内容要实时变的页面用了纯 SSG，或不需要每次渲染的页面全用 SSR 按“内容变不变、变了要不要立刻生效”区分：要立刻生效走 SSR 或接口补数据，不常变走 SSG
    前后端分离后接口没有文档与版本 后端一改，前端线上直接报错 接口变更先写文档、先加新版本、再逐步迁移调用方
    微服务拆完没有统一日志与监控 一次请求跨多个服务，出问题不知道先看哪一份日志 拆之前先把日志、监控、链路追踪三样配好，缺一不可
    多站点共用账号与进程 一个站点出问题拖累其他站点 按站点隔离账号、进程、数据目录（见第 7.6 节）
    选型时追求“最先进”而不是“最合适” 团队管不住的架构比落后的架构更贵 按第 9.1 节的四个问题判断，规模没到就不要硬上
    拆的过程中删旧部署包 回退时无物可回 按第 18 节备份旧包与旧配置，保留到新架构跑稳

    16. 故障排查¶

    现象 先查什么 常见原因
    前端页面能打开，但接口数据出不来 先看浏览器网络请求：接口地址是不是 /api/ 开头、返回的状态码是什么；再看后端日志 Nginx 分流写错，接口请求没走到后端；或后端进程没起来
    刷新前端深层路由直接 404 看第 11 节 location / 的 try_files 有没有最后的 /index.html 单页应用的深层路由没有回退到首页
    SSR 页面偶尔空白或报错 先看 SSR 服务端日志，再看浏览器日志，分清是哪一端报错 服务端渲染路径里写了浏览器专属 API，或两端状态不一致
    SSG 页面内容一直是旧的 看最后一次构建是什么时候、有没有重新部署 内容改了但没有重新构建，或者构建产物没有同步到服务器
    微服务一次请求时好时坏 按调用链逐个服务看日志与健康状态，不要只看入口服务 某个下游服务不稳定，或接口版本不一致
    多站点其中一个打不开、其他正常 先看该站点的域名解析、证书、Nginx 配置三处是否对得上 新站点的三处配置没有同步改齐
    改完架构后核心流程走不通 按第 9.4 节的回退触发条件判断，不要在故障现场临时想办法 拆的过程中接口不兼容，或流量切换顺序错了

    排错的总原则：先分清是“哪一层”出问题（Nginx 分流、前端、后端接口、数据库、渲染），再进那一层看日志；不要一上来就全量重启所有服务，那样会把现场日志也冲掉。

    17. 安全注意事项¶

    1. 后端接口不要直接暴露给所有人： 前后端分离与微服务模式下，后端接口进程只监听内网地址或本地端口，对外只经过 Nginx；管理接口更要单独鉴权，不要靠“地址没人知道”当安全措施。
    2. 多站点之间要隔离： 不同站点的应用进程、数据库账号、文件目录分开，一个站点的漏洞不应当能读到另一个站点的数据；上传目录不要给执行权限。
    3. SSR 要注意服务端注入： 服务端渲染时会把数据拼进 HTML，用户输入的数据必须转义后再拼，不要原样拼进页面；管理页与公开页的权限要在服务端也校验一遍，不能只靠前端隐藏按钮。
    4. 接口鉴权要在后端做： 前端隐藏某个按钮不等于后端拒绝了请求，订单、支付、管理类接口必须在后端校验登录态与权限。
    5. 配置里不要写真实密钥： 第 11 节的示例配置里没有任何密钥，部署时也不要把数据库密码、接口密钥写进 Nginx 配置或前端代码里；密钥只放在服务器上权限受限的配置文件或环境变量里。
    6. 回退本身也是安全操作： 回退时不要把旧的有漏洞的版本长期留在线上，回退只是争取修复时间的手段，修好后要重新走正常的发布流程。

    18. 回滚和恢复¶

    回滚分两层：部署回滚与架构回退，不要混为一谈。

    部署回滚（改错了配置或发错了版本，几分钟内要恢复）：

    1. 部署前先备份：旧部署包保存在服务器上的固定目录并注明日期，Nginx 配置改动前先复制一份，例如把 /etc/nginx/sites-available/shop 复制为同目录下的 .bak 文件再改。
    2. 改动后先执行 nginx -t 检查，通过后再重载，不要跳过检查。
    3. 出问题时先换回旧部署包与旧配置文件，再重载，然后按第 14 节验证首页与核心流程，确认恢复后再排查原因。

    架构回退（拆错了模式，要回到上一个模式）：

    1. 保留旧模式的完整部署物与数据：拆之前旧单体的代码、配置、数据库备份都要留着，不要拆完就删。
    2. 按第 9.4 节的顺序切回：先把流量切回旧模式，再停新服务，最后复盘拆错的原因。
    3. 数据要对得上：如果拆的过程中数据格式变了，回退前要确认旧模式能读回退后的数据，读不了就先做数据迁移再回退，不要直接切。
    4. 回退后不要立刻再拆一次：先记下这次的原因（边界切错、顺序不对、接口没对齐），换一个更小的切口再试。

    无论哪一层回滚，事后都要补一条记录：改了什么、为什么回滚、下一次怎么做。这条记录就是下一次选型时最有用的资料。
