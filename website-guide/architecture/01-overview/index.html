    ARCH-01：网站完整架构总览完整教程¶

    任务编号：ARCH-01（网站建设与部署实战指南 · 架构第 1 篇） 上一篇：NET-02 域名购买、注册商选择、实名、备案适用范围、泛域名、多域名；下一篇：ARCH-02 单体、前后端分离、SSR、SSG、微服务、多站点架构对比与升级路径。 本篇只讲一个网站从用户到运维的完整分层总览：用户层、网络层、Web 层、前端层、后端层、API 层、数据层、存储层、运行层、运维层，每层讲清负责什么、不负责什么、上下层之间传什么。不讲具体某个框架的用法，不讲架构模式的选型对比（那是 ARCH-02），不讲选型决策树（那是 ARCH-03）。

    1. 本章目标¶

    读完并动手做完本篇，你能做到下面五件事：

    • 画出一个网站的十层分层图，并说出每一层的位置。
    • 说出每一层负责什么、不负责什么，以及它和上下层之间传什么。
    • 跟踪一次“打开文章列表”和一次“发表评论”的完整请求流程，说出请求经过了哪些层。
    • 照着第 11 节写出一份 Nginx 反向代理骨架和一份 Docker Compose 骨架，并说出每个关键配置项的意思。
    • 判断一个故障大概出在哪一层，而不是把所有问题都归到“服务器坏了”。

    2. 适用人群¶

    • 已经读过 HTML、CSS、JavaScript 基础，能写出一个静态页面，但还没有完整做过一个带登录、带数据库的网站的读者。
    • 想从“写页面”进到“做网站”的人：需要先建立一张整站地图，再去学后端、数据库、部署。
    • 不要求你已经会用某个后端框架。本篇不教你写业务代码，只教你认清各层的位置和关系。

    3. 适用系统和版本¶

    • 操作系统：本篇示例不依赖某个发行版，只要能装 Docker 就能跟着做；命令以 Linux 终端为准。
    • Docker Compose v2：命令用 docker compose（中间是空格），不是老版的 docker-compose。
    • 示例所用版本（写骨架时用的版本，安装时以当场查到的版本为准）：Nginx 1.28 线、PostgreSQL 16、Redis 7。版本号写进配置是为了让示例可复现，不是说只有这些版本才能用。
    • 浏览器：任意现代浏览器，用于第 14 节的验证。

    4. 使用前提¶

    • 会用终端执行基本命令，会用文本编辑器改文件。
    • 理解域名、IP、端口、HTTP 请求与响应的基本概念。如果这部分不熟，先读 NET-01。
    • 理解 HTML、CSS、JavaScript 各自是干什么的。如果这部分不熟，先读 HTML、CSS、JavaScript 的基础篇。
    • 不需要你已经有域名。本地练习用 http://127.0.0.1/ 就够，域名只在部署到公网时才需要。

    5. 所需资源¶

    • 一台能装 Docker 的电脑或服务器，本地练习即可，不需要先买服务器和域名。
    • Docker Engine 和 Docker Compose v2，第 8 节会先检查它们在不在。
    • 一个文本编辑器，用于写第 11 节的两个配置文件。
    • 一个浏览器，用于第 14 节的验证。

    6. 技术原理¶

    一个网站不是一个程序，而是一串互相传话的程序。浏览器发出的请求要经过很多道手，每道手只做自己那一部分，做完就传给下一道。分层的好处有三点：

    • 第一，每层可以单独换。换数据库不用重写前端，换前端框架不用重写数据库表。
    • 第二，每层可以单独查。文章列表打不开时，可以一层一层问：是网络没通，还是入口没分流，还是后端报错，还是数据库查不到。
    • 第三，每层可以单独扩。访问量上来时，先看是哪一层顶不住，再去加那一层的资源，而不是把整台机器一股脑换掉。

    分层也有代价：层与层之间要传话，传话就要定格式。前端和后端之间定的格式就是 API 契约，后端和数据库之间定的格式就是表结构和查询语句。本篇的重点就是把这张“谁传给谁、传什么”讲清楚。

    一个常见的误解是把“层”和“机器”画等号。层是逻辑分工，不是机器数量。十层可以全部跑在一台服务器的几个容器里，也可以拆到很多台机器上。初学阶段先在一台机器上把十层跑通，再去学拆分和扩容，那些是 ARCH-02、DEPLOY 阶段的内容。

    7. 架构说明¶

    下表是本篇的十层总览。读表时注意三列：每一层负责什么、不负责什么、它和相邻层传什么。把这张表背下来，后面的示例就好懂了。

    层 负责什么 不负责什么 向下传什么 向上返回什么
    用户层 人在浏览器里看页面、点按钮、填表单 不写代码，不存数据 点击、输入、登录信息 页面、提示、报错
    网络层 域名解析、寻址、传输、加密通道 不决定页面长什么样，不处理业务 解析后的地址、加密后的请求 解析结果、传输状态
    Web 层 入口分流、静态文件、TLS 终结、限流、缓存头 不处理登录、文章、评论的业务逻辑 分流后的请求、客户端地址 静态文件、后端响应
    前端层 在浏览器里渲染页面、处理交互、向 API 发请求 不直接连数据库，不保管别人的密码 API 请求、用户输入 渲染好的页面、交互反馈
    后端层 业务逻辑、登录鉴权、文章与评论的规则 不直接画页面，不直接操作浏览器 校验后的业务请求 业务结果、错误码
    API 层 接口契约：地址、方法、参数、返回格式、错误码 不实现业务规则本身，只定格式 按契约整理好的请求 按契约整理好的响应
    数据层 结构化数据的表、查询、事务、约束 不存图片、视频这类大文件本体 查询语句、写入语句 查询结果、写入确认
    存储层 文件、对象、缓存、备份的存放载体 不决定业务规则，不替代数据库表 存取请求、缓存键 文件内容、缓存值、备份文件
    运行层 容器、进程、操作系统、资源、健康检查 不决定业务，不保管域名 启动命令、环境变量 进程状态、日志、健康结果
    运维层 监控告警、日志收集、备份恢复、部署发布、证书续期 不写业务代码，不改接口契约 部署指令、备份任务 监控数据、告警、备份结果

    再补三点容易混淆的区分：

    • Web 层和前端层的区别：Web 层在服务器一侧，是请求的入口和分流员；前端层在浏览器一侧，是页面的渲染和交互者。一个管“请求往哪送”，一个管“页面怎么画”。
    • 后端层和 API 层的区别：后端层是“做事的人”，API 层是“约定的格式”。同一个后端逻辑可以换一种 API 格式对外提供，格式变了，业务不一定变。
    • 数据层和存储层的区别：数据层管结构化数据，典型是关系数据库里的表；存储层管“东西放哪”，典型是文件、对象存储、缓存、备份文件。文章正文放数据层，文章配图放存储层，用户登录会话可以放存储层的缓存里。

    8. 操作前检查¶

    动手之前先检查下面四项，缺哪项补哪项，不要跳过直接写配置：

    • Docker 能不能用：执行 docker --version，能看到版本号才算通过。
    • Docker Compose v2 在不在：执行 docker compose version，能看到版本号才算通过。注意命令中间是空格。
    • 80 端口有没有被占用：本地练习用 80 端口起 Nginx，如果已被占用，先停掉占用它的程序，或者把第 11 节里的端口映射改成别的端口，并同步改第 14 节的访问地址。
    • 文本编辑器能不能保存纯文本文件：配置文件必须是纯文本，不能用带格式的文档编辑器去写。

    9. 逐步操作¶

    按下面六步走，每一步做完再做下一步：

    1. 在家目录下新建一个项目目录，例如 mysite，并进入这个目录。本篇后面说的“项目根目录”就是这个目录。
    2. 在项目根目录下新建 nginx 目录，用于放 Nginx 配置。
    3. 照着第 11 节写两个文件：nginx/default.conf 和 docker-compose.yml，每个文件写完都对照第 12 节逐项检查一遍。
    4. 在项目根目录下新建一个 .env 文件，只写键名对应的值（数据库名、数据库用户、数据库口令、缓存口令），这个文件不要放进版本库，也不要发给别人。第 12 节会讲每个键是干什么的。
    5. 执行 docker compose config 检查 Compose 文件的语法，报错先修好再往下走。
    6. 按第 14 节的五步验证：先看服务状态，再用浏览器打开首页，再走一遍登录、看文章列表、发表评论，最后看日志里有没有报错。

    10. 完整示例架构¶

    本节用一个具体站点把十层串起来。示例站点叫“示例内容站”，功能只有三样：登录、文章列表、评论。不做商城，不做支付，不做实时聊天，功能越少，架构越看得清。

    10.1 每层在这个站点里是什么¶

    层 在示例内容站里是什么
    用户层 读者用浏览器打开首页、登录、看文章、写评论
    网络层 域名解析到服务器，浏览器和服务器之间走加密连接
    Web 层 Nginx：首页和静态文件直接返回，登录、文章、评论的请求转发给后端
    前端层 浏览器里跑的页面：首页、文章列表页、文章详情页、登录页、评论框
    后端层 登录校验、文章查询、评论发布规则（例如未登录不能评论、评论内容不能为空）
    API 层 登录接口、文章列表接口、文章详情接口、评论列表接口、发表评论接口，返回格式统一
    数据层 用户表、文章表、评论表，存在 PostgreSQL 里
    存储层 文章配图存在文件或对象存储里，会话存在 Redis 里，备份文件存在备份目录里
    运行层 Nginx、后端、PostgreSQL、Redis 各跑一个容器，分别有健康检查
    运维层 容器日志、服务状态检查、数据库备份任务、证书续期提醒

    10.2 打开文章列表的完整流程¶

    1. 用户在浏览器输入地址，浏览器向网络层发起域名解析，拿到服务器地址。
    2. 浏览器和服务器建立加密连接，请求发到 Web 层。
    3. Web 层判断：这是文章列表页的请求，先看有没有静态缓存，没有就转发给后端。
    4. 前端层已经在浏览器里准备好页面骨架，向 API 层发“文章列表”请求。
    5. API 层按契约检查请求参数，合格就交给后端层。
    6. 后端层按业务规则处理：不需要登录就能看列表，直接去数据层查文章表。
    7. 数据层返回文章记录，后端层整理成 API 层约定的返回格式。
    8. Web 层把响应送回浏览器，前端层渲染出文章列表。
    9. 文章配图另外走存储层：浏览器按图片地址去取，Web 层直接返回文件，不经过后端。

    10.3 发表评论的完整流程¶

    1. 用户在文章详情页写好评论，点提交，前端层先做最基本的检查：内容不能为空。
    2. 前端层向 API 层发“发表评论”请求，并带上登录凭证。
    3. API 层检查请求格式，合格就交给后端层。
    4. 后端层校验登录凭证：凭证无效就返回未登录的错误，不写数据库。
    5. 凭证有效，后端层按规则处理：文章必须存在，评论内容要符合长度要求，合格就写入数据层的评论表。
    6. 写入成功后，后端层返回成功结果，前端层把新评论显示在列表里，并清空输入框。
    7. 如果写入失败，前端层显示错误提示，不假装成功。

    10.4 部署拓扑¶

    示例站点在一台服务器上用四个容器跑起来，拓扑如下表。拓扑的意思是“谁和谁连在一起”，不是“每层一台机器”。

    容器 角色 对外暴露 只在内部网络里被访问
    nginx Web 层入口 80 端口 否，对外
    app 后端层加 API 层 不直接对外 是，只接受 nginx 的转发
    postgres 数据层 不直接对外 是，只接受 app 的连接
    redis 存储层里的会话缓存 不直接对外 是，只接受 app 的连接

    数据持久化用命名卷：数据库数据放在 pgdata 卷里，缓存数据放在 redisdata 卷里，容器删了重建，卷里的数据还在。备份任务由运维层定期把数据库导出到备份目录，不放在容器里。

    11. 完整配置文件¶

    本节给两个完整文件，没有省略。两个文件要放在同一个项目根目录下，互相配合。注意：配置文件里的域名用 example.com 作示例，动手时换成你自己的域名；数据库口令、缓存口令不要直接写进文件，统一用 ${变量名} 引用 .env 文件里的值，.env 文件不要放进版本库。

    第一个文件，存放路径：项目根目录下的 nginx/default.conf。

    server {
    listen 80;
    server_name example.com;

    client_max_body_size 10m;

    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options SAMEORIGIN;

    location / {
        proxy_pass http://app:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /static/ {
        alias /usr/share/nginx/html/static/;
        expires 7d;
        add_header Cache-Control "public";
    }
}

    第二个文件，存放路径：项目根目录下的 docker-compose.yml。

    services:
  nginx:
    image: nginx:1.28
    ports:
      - "80:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app
  app:
    image: mysite/app:1.0
    environment:
      - POSTGRES_DB=${POSTGRES_DB}
      - POSTGRES_USER=${POSTGRES_USER}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_PASSWORD=${REDIS_PASSWORD}
    depends_on:
      - postgres
      - redis
  postgres:
    image: postgres:16
    environment:
      - POSTGRES_DB=${POSTGRES_DB}
      - POSTGRES_USER=${POSTGRES_USER}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
  redis:
    image: redis:7
    command: redis-server --requirepass ${REDIS_PASSWORD} --appendonly yes
    volumes:
      - redisdata:/data
volumes:
  pgdata:
  redisdata:

    再补一份 .env 的键名表，只列键名，不写真实口令。存放路径：项目根目录下的 .env，不要放进版本库。

    键名 填什么
    POSTGRES_DB 数据库名，例如示例内容站的库名
    POSTGRES_USER 数据库用户名
    POSTGRES_PASSWORD 数据库口令，自己生成一串长的，不要用常见口令
    REDIS_PASSWORD 缓存口令，自己生成一串长的，不要和数据库口令相同

    12. 每个关键配置项的解释¶

    12.1 Nginx 配置项¶

    配置项 意思
    listen 80 监听 80 端口，浏览器用不带端口的 http 地址访问时就是走这个端口
    server_name example.com 这个配置只处理发给 example.com 的请求，动手时换成你自己的域名
    client_max_body_size 10m 单次请求体最大 10 兆，评论、配图上传超过这个值会被拒绝，数值按业务改
    add_header X-Content-Type-Options nosniff 告诉浏览器不要猜文件类型，按服务器声明的类型处理，减少类型混淆带来的风险
    add_header X-Frame-Options SAMEORIGIN 只允许本站自己的页面用框架嵌套本站页面，减少被别的站点套壳的风险
    location / 所有请求默认走这一段，除非被更具体的 location 匹配到
    proxy_pass http://app:8000 把请求转发给名叫 app 的容器里的 8000 端口，app 是 Compose 里的服务名，不是域名
    proxy_set_header Host $host 把浏览器发来的域名原样传给后端，后端按域名区分站点时要用它
    proxy_set_header X-Real-IP $remote_addr 把访问者的真实地址传给后端，后端记日志、做限流时要用它，否则看到的都是 nginx 的地址
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for 把经过的代理地址链传给后端，便于排查请求经过了哪些代理
    proxy_set_header X-Forwarded-Proto $scheme 把原始协议（http 还是 https）传给后端，后端生成链接、判断安全 Cookie 时要用它
    location /static/ 以 /static/ 开头的请求走这一段，不转发给后端
    alias /usr/share/nginx/html/static/ 静态文件在 nginx 容器里的实际目录，动手时按你自己的目录改
    expires 7d 告诉浏览器静态文件可以缓存 7 天，7 天内重复访问不用重新下载
    add_header Cache-Control "public" 告诉浏览器和中间缓存：这个响应可以被公开缓存

    12.2 Docker Compose 配置项¶

    配置项 意思
    services 下面列出的每个服务就是一个容器，服务名同时也是内部网络里的主机名
    nginx image nginx:1.28 nginx 容器用的镜像和版本，动手时以当场查到的版本为准
    ports "80:80" 左边是宿主机端口，右边是容器端口，浏览器访问宿主机 80 端口就进到容器 80 端口
    volumes ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro 把项目里的配置文件挂载进容器，ro 表示容器里只读，不能反过来改宿主机的文件
    depends_on app nginx 启动时先等 app 服务启动，但这只保证启动顺序，不保证 app 已经能处理请求
    app image mysite/app:1.0 后端容器用的镜像名，换成你自己构建并推送的镜像名，不要以为这个名字自带代码
    environment POSTGRES_DB 等 把 .env 里的值传进容器，应用代码从环境变量里读，不要把口令写死在配置文件里
    postgres image postgres:16 数据库容器用的镜像和版本
    volumes pgdata:/var/lib/postgresql/data 把数据库数据存到名叫 pgdata 的卷里，容器删了重建，数据还在
    redis command redis-server --requirepass 启动缓存时要求口令，并打开持久化，缓存重启后数据不全丢
    volumes 顶部的 pgdata 和 redisdata 声明本文件用到的两个命名卷，不声明就用不了

    13. 执行结果示例¶

    下面是按第 9 节走到第 5 步时应该看到的结果。结果分三段，每段都写明“应该看到什么”，而不是让你背数值。

    第一段，执行 docker compose config，应该看到配置检查通过，不报错，并且列出的服务名就是 nginx、app、postgres、redis 四个。如果报错，先看报错指出的行号，再对照第 12 节改。

    第二段，服务启动后执行 docker compose ps，应该看到四个服务的状态都是运行中。如果某个服务反复重启，先看它的日志，不要反复执行启动命令。

    第三段，用浏览器打开 http://127.0.0.1/，应该看到示例内容站的首页；点文章列表，应该看到文章；登录后发表一条评论，应该看到评论出现在列表里，并且刷新页面后评论还在。如果刷新后评论没了，说明评论没有真正写进数据库，先看后端日志和数据库连接，再看前端是不是只把评论存在了页面内存里。

    14. 成功验证¶

    按下面五步验证，全部通过才算跑通：

    1. 配置检查通过：docker compose config 不报错，服务名是 nginx、app、postgres、redis。
    2. 服务状态正常：docker compose ps 里四个服务都是运行中，没有反复重启。
    3. 首页能打开：浏览器打开 http://127.0.0.1/，能看到首页和文章列表。
    4. 登录、评论全流程能走通：登录成功，发表评论后刷新页面，评论还在，退出登录后不能再发表评论。
    5. 日志没有报错：分别看 nginx、app、数据库的日志，没有连接失败、口令错误、表不存在这类报错。

    如果第 4 步里“发表评论后刷新就没了”，说明评论没有落库，这是数据层的问题，不是前端样式的问题。如果第 3 步首页都打不开，先按第 16 节的顺序查：先看端口有没有被占用，再看 nginx 配置，再看后端有没有起来。

    15. 常见错误¶

    下表里的错误写法只用行内代码写，没有写成带围栏的代码块。读的时候注意：左边是错的写法，右边是错在哪里。

    错误写法 错在哪里
    proxy_pass http://localhost:8000; 写在 nginx 容器里 localhost 在容器里指的是 nginx 容器自己，不是后端容器，应该写服务名 app
    把数据库口令直接写进 docker-compose.yml 并提交到版本库 口令进了版本库就等于公开了，应该用 .env 文件传值，并且不提交 .env
    ports: - "80:80" 写了两个服务都占 80 端口 一个端口只能给一个服务，两个服务抢一个端口，后启动的起不来
    前端直接连数据库 前端代码在浏览器里运行，数据库地址和口令会暴露给所有人，应该只让后端连数据库
    评论只存在页面内存里，刷新就没了 没有经过 API 写进数据层，刷新页面数据自然就没了
    把图片文件路径直接写进数据库表里当成图片本体 表里应该存图片的地址或标识，图片本体放存储层，混在一起会让表越来越大、备份越来越慢
    备份只存在容器里 容器删了备份就跟着没了，备份要放到容器外的目录或另外的机器上

    16. 故障排查¶

    按下面顺序查，不要跳着查。每一行都是一层，先排除上面一层再往下一层走。

    现象 先查哪一层 怎么查
    浏览器打不开，提示无法连接 网络层、Web 层 先看服务器地址对不对、端口有没有被占用，再看 nginx 服务在不在
    能打开首页，但文章列表是空的 后端层、数据层 先看后端日志有没有报错，再看数据库里有没有文章数据
    登录总是失败 后端层、API 层 先看接口返回的错误码和提示，再看凭证、口令、会话有没有过期
    发表评论后刷新就没了 前端层、数据层 先看前端是不是只存在了内存里，再看评论有没有真正写进评论表
    图片打不开 Web 层、存储层 先看图片地址对不对，再看静态文件目录和权限对不对
    服务反复重启 运行层 看这个容器的日志，启动命令、环境变量、依赖服务有没有问题
    磁盘满了 运维层、存储层 看日志、备份、旧镜像是不是把磁盘占满了，先清能清的，再补备份策略

    17. 安全注意事项¶

    • 口令、密钥、Token 一律走环境变量或密钥文件，不要写进配置文件、不要提交到版本库、不要发到聊天记录里。
    • 数据库和缓存不要直接对外暴露端口。本篇的 Compose 里只有 nginx 占 80 端口，数据库和缓存只在内部网络里被访问，这是有意为之的设计，不要为了图方便把数据库端口也映射到宿主机上。
    • 前端不要保管别人的密码，不要把数据库地址、口令、管理后台的密钥写进前端代码。
    • 用户输入要经过后端校验。前端的检查只是为了体验好，真正的安全检查必须在后端做，前端检查可以被绕过。
    • 上传的文件要限制类型和大小，上传目录不要允许直接执行脚本，具体做法放在后端和部署章节讲。
    • 证书到期会让加密连接失败，运维层要安排续期提醒，不要等到用户打不开才发现。

    18. 回滚和恢复¶

    • 改 Nginx 配置之前，先把旧文件复制一份，例如复制成 default.conf.bak，改坏了就把备份文件拷回来，再执行重载或重启。
    • 改 Compose 文件之前，同样先备份旧文件。回滚时用旧文件重新启动服务，不要凭记忆重写。
    • 换后端镜像之前，记下旧镜像的版本号。回滚时把镜像名改回旧版本号再启动，不要用一个没验证过的新版本去救一个已经出问题的旧版本。
    • 数据库恢复之前，先确认备份文件是哪一天的、对应哪个版本的数据结构，再恢复到一台先验证用的环境里，确认没问题再恢复到正式环境。
    • 回滚不是“把所有东西都还原”。先定位是哪一层改坏了，只回滚那一层，别的不动，动得越多越难定位。
