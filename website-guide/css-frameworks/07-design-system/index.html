    CSS-15：完整 Design System（自建设计系统）¶

    任务编号：CSS-15（网站建设与部署实战指南 · CSS 框架阶段第 7 篇） 上一篇：CSS-14 自己编写 CSS 框架；下一篇：CSS-16 同一页面需求的多框架对照实战。 本篇只讲“从零给一个网站建一套设计系统”：设计令牌、组件规范、文档与示例页、版本管理与迭代规则。不讲某个现成框架的具体组件用法（那是 CSS-09 至 CSS-13 的框架篇），不讲 Flex/Grid 的基础属性（那是 CSS-04、CSS-05），不讲 Sass 的完整配置（概念见 CSS-08）。

    1. 本章目标¶

    读完并动手做完本篇，你能：

    1. 说清楚“设计系统”和“单个 CSS 框架”有什么区别：前者是一套规范加令牌加组件加文档，后者只是一份别人写好的样式代码；
    2. 给一个网站定一套设计令牌：颜色、字号、间距、圆角、阴影各有一张表，改一个值全站跟着变；
    3. 写出五个核心组件的规范：按钮、输入框、卡片、导航、弹窗，每个组件有哪些变体、每种状态长什么样；
    4. 做出一页设计系统文档与示例页：别人打开这一页，就能看到全部令牌和全部组件，不用翻你的源代码；
    5. 给设计系统定版本规则和迭代流程：什么时候升大版本、什么时候只改小版本，旧页面怎么不被新版本打坏。

    2. 适用人群¶

    • 已经学完 CSS-01 至 CSS-03，能写选择器、单位、颜色、盒模型、定位，并且读过 CSS-08 的文件组织和 BEM 命名的人；
    • 网站已经不止一两个页面，按钮在这一页是蓝色、那一页是绿色，字号、间距全凭感觉写的人；
    • 想和别人一起维护一个网站，需要一份“大家都按这个写”的规矩，而不是口头约定的人；
    • 还没有接触过现成设计系统（例如 Ant Design、Material Design）的人——本篇从零自建，学完再去看现成系统会更容易理解。

    3. 适用系统和版本¶

    • 操作系统：Windows、macOS、Linux 均可；浏览器：任意现代浏览器（Chrome、Edge、Firefox、Safari 的近几年版本均可）。
    • 编辑器：任意纯文本编辑器或 VS Code，不需要装任何构建工具。
    • 技术版本：原生 CSS3，设计令牌用 CSS 自定义属性（也叫 CSS 变量，写法是 --名字 加 var()），这是所有现代浏览器都支持的标准写法，不依赖 Sass、Less。
    • 本篇的示例页是纯 HTML 加内部样式，不需要服务器、不需要联网，本地双击打开或用本地服务打开都可以。

    4. 使用前提¶

    • 会写 HTML 文档结构：标题、段落、列表、链接、表单、按钮（见 HTML 基础篇）。
    • 会写 CSS 基础：选择器、单位、颜色、盒模型、定位（见 CSS-01 至 CSS-03）。
    • 理解 CSS-08 的两个概念：文件怎么组织、组件样式为什么要用 BEM 命名防撞名。
    • 有一个练手用的网站或页面，哪怕只有一个首页也行——设计系统是给真实页面服务的，没有页面就只能空谈规范。

    5. 所需资源¶

    • 一台电脑、一个编辑器、一个浏览器，就够了；不需要注册账号、不需要买域名、不需要服务器。
    • 准备一个空文件夹，例如 my-design-system/，里面只放本篇第 11 节给出的两个文件：令牌文件和示例页。
    • 建议再准备一张纸或一个空白文档，用来先手写“我的网站需要哪几种颜色、哪几档字号”，写代码之前先把这张表定下来——设计系统先定规矩、后写代码，顺序反了就等于没系统。

    6. 技术原理¶

    6.1 设计系统到底是什么¶

    设计系统不是“一套好看的样式”，而是四样东西合在一起：

    组成部分 是什么 没有它会怎样
    设计令牌 颜色、字号、间距、圆角、阴影这些最基础的值，集中写成变量 每个页面各写各的颜色，改一次主色要全站搜索替换
    组件规范 按钮、输入框、卡片、导航、弹窗这些常用部件的长相、变体和状态 同一个按钮在不同页面长得不一样，用户分不清哪个能点
    文档与示例页 一页能看全所有令牌和组件的页面 新人加入团队，只能翻旧页面去猜“这个按钮该怎么写”
    版本与迭代规则 什么时候能改、改了怎么通知、旧页面怎么办 改一个令牌，全站页面一夜之间全变样，没人敢改

    6.2 设计系统和单个 CSS 框架的区别¶

    这是本篇最关键的一句区分，记住它：

    • 单个 CSS 框架（例如 Bootstrap、Tailwind）是别人写好的样式代码：你拿来用，照着它的类名写页面，省的是“写样式的时间”。
    • 设计系统是你自己给自己的网站定的规矩：颜色叫什么、间距有几档、按钮有哪几种、文档放在哪、改了怎么升级，省的是“以后每一次改样式、加页面、多人协作的时间”。

    两者不冲突：一个网站完全可以“用 Bootstrap 做框架，同时有自己的设计系统”，也可以“不用任何框架，只用自己的设计系统”。本篇自建的设计系统不依赖任何框架，第 10 节的示例页就是证明——它只用原生 CSS 变量和普通类名。

    6.3 设计令牌为什么要用 CSS 变量¶

    CSS 自定义属性的写法是：在 :root 里定义 --颜色-主色: #e8590c;，在需要的地方写 background-color: var(--颜色-主色);。本篇用英文名，例如 --color-primary，因为英文名在代码里不会出现编码问题。

    这样做的好处只有一句：值只写在一个地方。主色从橙色改成蓝色，只改 :root 里的一行，全站所有用了这个变量的按钮、链接、导航高亮一起变；如果每个按钮都直接写死颜色值，改主色就要改几十处，漏一处就是一个 bug。

    变量还可以分层：先定义“原始值”（例如 --color-orange-500），再定义“语义值”（例如 --color-primary: var(--color-orange-500);）。换主题时只换语义值指向的原始值，不用动组件代码。暗黑模式也是这个道理：同一套组件，换一套变量值，页面就换了主题（暗黑模式的完整做法见 CSS-07）。

    6.4 组件规范为什么要写“变体”和“状态”¶

    一个按钮不是只有一种长相。变体是“同一组件的不同用途”：主要按钮、次要按钮、危险按钮、大按钮、小按钮。状态是“同一变体在不同时刻的样子”：正常、悬停、按下、禁用、获得焦点。

    规范必须把变体乘以状态都列出来，否则就会出现：设计稿上有禁用按钮，代码里没有，开发只能临时写一个灰色按钮，下次另一个人又临时写一个不一样的灰色按钮。规范的价值就在于：所有情况都有现成的写法，不用临时发明。

    6.5 文档页为什么是设计系统的一部分，不是附赠品¶

    没有文档页的设计系统，等于没有设计系统。因为使用者（包括三个月后的你自己）不会去翻令牌文件逐行读变量名，他只会打开文档页，看到“主要按钮长这样、复制这段代码就能用”。所以本篇第 10 节的示例页本身就是设计系统的一半成品：它既是验证手段，也是交付物。

    7. 架构说明¶

    一个最小可用的自建设计系统，只需要三个文件，放在一个文件夹里：

    my-design-system/
├── tokens.css            # 设计令牌：全部变量，只放变量，不放组件样式
├── components.css        # 组件样式：按钮、输入框、卡片、导航、弹窗，只引用变量，不写死颜色和尺寸
└── design-system.html    # 文档与示例页：引用上面两个文件，展示全部令牌和组件

    分工必须死守一条线：tokens.css 里只有变量定义，没有任何组件选择器；components.css 里所有颜色、间距、字号、圆角、阴影都必须写成 var(--...)，不许出现写死的数值。这条线一破，令牌就失去了“改一处全站变”的意义。

    正式项目里，tokens.css 和 components.css 还可以再拆：令牌按颜色、字号、间距拆成几个文件，再由一个入口文件汇总；组件按一个组件一个文件拆。但最小版本先按上面三个文件做，跑通了再拆——先有系统，再谈拆分。

    版本管理不放在样式文件里，放在一个单独的说明文件里，见第 11 节的 CHANGELOG.md。版本号用三段式：主版本.次版本.修订号，例如 1.0.0，规则见第 9 节第 6 步。

    8. 操作前检查¶

    动手之前，先逐项打勾，缺一项就先补齐：

    1. 能新建文件夹和文本文件，会用编辑器保存为 .css 和 .html 后缀；
    2. 知道 :root 是什么意思（文档的根元素，变量写在这里就是全局变量）；
    3. 知道 var(--color-primary) 的括号里写的是变量名，前面必须有两个连字符；
    4. 手头有一个真实页面或练手页面，能把本篇的组件换上去试一试；
    5. 已经想好自己网站的主色、文字颜色、背景颜色各是什么——哪怕先随便定一个，也比边写边想强；
    6. 备份习惯：改旧页面的样式之前，先把旧文件复制一份，名字后面加 .bak，回滚方法见第 18 节。

    9. 逐步操作¶

    第 1 步：定令牌表，先写在纸上¶

    在纸上列出五张小表，每张不超过十行：颜色（主色、危险色、文字色、次要文字色、边框色、背景色、卡片背景色）、字号（小、正常、大、标题）、间距（4 档）、圆角（小、中、大）、阴影（轻、重）。档数宁少勿多：颜色超过十种、间距超过六档，系统就没人记得住。

    第 2 步：把令牌表写成 tokens.css¶

    按第 11 节的模板，把纸上的表翻译成 :root 里的变量。命名用英文、按“类别-用途-程度”三段写，例如 --color-primary（颜色类、主色）、--space-2（间距类、第 2 档）、--radius-md（圆角类、中档）。不要用 --a、--x 这种看不懂的名字。

    第 3 步：定组件清单，只写五个¶

    本篇只做五个核心组件：按钮、输入框、卡片、导航、弹窗。每个组件先在纸上列出变体和状态：按钮有主要、次要、危险三种变体，加大、小两种尺寸，加禁用一种状态；输入框有正常、错误、禁用三种状态；卡片有普通和带阴影两种；导航有横向一种；弹窗有打开一种展示形态。清单定死了再写代码，写代码时不许临时加变体。

    第 4 步：写 components.css，全部引用变量¶

    按 BEM 命名写组件类名，例如按钮是 btn，主要变体是 btn--primary，大尺寸是 btn--lg，禁用状态直接用原生的 disabled 属性加 :disabled 样式，不用再发明一个类。每个颜色、间距、字号、圆角、阴影都写成 var(--...)，写完后全文搜索一遍：除了变量定义本身，文件里不应该再出现颜色值和尺寸值。

    第 5 步：做文档与示例页 design-system.html¶

    这一页分四段：第一段展示令牌（每个颜色画一个色块、每档间距画一条长度条）；第二段展示五个组件的全部变体；第三段写“怎么用”（引用哪两个文件、类名怎么写）；第四段写“不要怎么做”（反面做法，见第 15 节）。这一页用的样式必须全部来自 tokens.css 和 components.css，不许在页内再写一套私有样式——文档页本身就是系统的第一个用户。

    第 6 步：定版本规则，写进 CHANGELOG.md¶

    版本号三段：主版本、次版本、修订号，规则是：删掉或改名一个变量、删掉一个组件变体、改了某个组件的默认长相，就升主版本；只加新变量、只加新变体、只加新组件，就升次版本；只改文字说明、只修文档错字，就升修订号。每次改动先写进 CHANGELOG.md 再改代码，顺序不能反。

    第 7 步：把系统用到一个真实页面上¶

    挑一个旧页面，把它的按钮、输入框、卡片换成系统组件，删掉页面里原来写死的颜色和尺寸。换完之后做一个验证：把 tokens.css 里的主色临时改成另一个颜色，刷新页面，如果全站主色一起变了，系统就通了；如果有的地方没变，那个地方就是漏网的写死值，补成变量引用。验证完把主色改回去。

    类名 含义 备注

    14. 成功验证¶

    按下面五步验证，每一步都要亲手做，不要只看一遍就当通过：

    1. 打开示例页，确认第 13 节列出的七段内容都在，没有缺段、没有错位、没有空白方块；
    2. 打开浏览器的开发者工具，选中主要按钮，看它的计算样式里背景色是不是来自 --color-primary，而不是一个写死的颜色值；
    3. 把 :root 里的 --color-primary 临时改成另一个颜色（例如蓝色），刷新页面，确认导航当前项、主要按钮、色块一起变色——这一步就是设计系统存在的证明；
    4. 把主色改回原来的橙色，刷新确认恢复；
    5. 对照第 12 节的两张表，逐项核对：每个变量名、每个组件类名，在示例页里都能找到对应的展示。

    如实说明：本篇作者的验证只做到“文件能返回、解析通过”（见第 5 节汇报里的实测数字），没有用浏览器逐项看视觉效果；上面五步的视觉验证需要你自己在浏览器里做，改主色全站变色那一步尤其不能省——只有它能证明你的变量真的被所有组件引用了。

    15. 常见错误¶

    错误做法 为什么错 正确做法
    组件里直接写 background-color: #e8590c; 主色一改，这个按钮漏网，全站出现两种主色 写 background-color: var(--color-primary);
    令牌起 --a、--x、--tmp 这种名字 三个月后没人知道它是什么，没人敢改 按“类别-用途-程度”起名，例如 --color-primary
    间距档数定到十几档，例如 --space-1 一直写到 --space-12 没人记得住第 7 档和第 8 档有什么区别，最后还是凭感觉写 间距最多四到六档，不够用先想想是不是布局本身有问题
    按钮变体无限加，例如 btn--primary-blue、btn--primary-green 变体一多，系统就退化成“每个页面一套样式” 变体只按用途分：主要、次要、危险；颜色差异用令牌解决，不用新变体
    文档页里又写一套私有样式，例如 .doc-title { color: red; } 文档页和真实页面长得不一样，文档就失去了对照价值 文档页只用系统自己的变量和组件类
    令牌文件里混进组件选择器，例如在 tokens.css 里写 .btn { ... } 分工一乱，别人就不知道该去哪个文件改 令牌文件只放变量，组件文件只放组件
    改了变量不写 CHANGELOG 别人不知道这次升级会不会打坏他的页面 先写 CHANGELOG 再改代码，见第 9 节第 6 步
    把弹窗的打开关闭也写进本篇 本篇只定长相，交互逻辑需要 JavaScript，混在一起会让新手分不清哪部分是样式、哪部分是逻辑 弹窗先以打开状态展示，交互留待 JavaScript 阶段接

    16. 故障排查¶

    现象 可能原因 排查和修复方法
    按钮没有颜色，全是默认灰色 样式文件没引用成功，或者令牌文件在组件文件之后引用 检查页面头部两个文件的引用顺序：令牌在前、组件在后；再检查文件路径对不对
    改了主色变量，页面一点没变 组件样式里写的是死颜色值，没有引用变量 在组件文件里搜索颜色值，把所有死值换成对应的 var(--...)
    变量名写错，样式不生效 例如把 --color-primary 写成 --color-primay，浏览器不会报错，只会默默用默认值 对照第 12 节的表逐个核对变量名；也可以在开发者工具里看变量有没有被解析出来
    间距忽大忽小 有的地方用了变量，有的地方直接写了数值 全文搜索 px，除了变量定义本身，其他地方出现数值就是漏网处
    卡片阴影和边框同时出现，显得很脏 带阴影变体忘了去掉边框 检查 card--shadow 里有没有把边框设成透明，见第 12 节备注
    弹窗在页面里把其他内容顶走了 弹窗示例是按普通文档流写的，没有脱离文档流 本篇示例本来就是“展示长相”，真实弹窗需要定位到视口中央，这属于定位知识（见 CSS-03）和后续的交互逻辑，不要在本篇里硬凑
    团队里有人不用系统，自己写样式 系统没有文档页，或者文档页不好找 把文档页放到团队都找得到的地方，并在新人入职第一天就指给他看；系统不用就是没有系统

    17. 安全注意事项¶

    设计系统本身不处理用户数据，安全风险很低，但有三条不能大意：

    1. 令牌文件里不许放任何秘密：颜色、间距、字号都是公开的设计值，但不要顺手把接口地址、密钥、内部域名写进同一个文件——样式文件是公开给浏览器的，写进去就等于公开。
    2. 不要为了“好看”牺牲可读性：主色和背景色的对比度要够，禁用按钮不能只靠颜色区分（本篇同时用了透明度），错误状态不能只靠红色（本篇同时用了文字说明）；对比度和无障碍的完整做法见 HTML 无障碍篇。
    3. 弹窗里的按钮文案要写清楚后果：删除、付款、提交这类不可逆操作的按钮，不能只写“确定”，要写“确认删除”这种带动作和对象的话；文案是设计系统的一部分，不是开发时临时想的。

    18. 回滚和恢复¶

    改设计系统之前，先做备份，方法只有一句：改哪个文件，先把那个文件复制一份，后缀改成 .bak，例如改 tokens.css 之前先复制出 tokens.css.bak。回滚时把 .bak 文件覆盖回去、刷新页面就行，不需要任何工具。

    版本回滚的规则和第 9 节第 6 步对应：如果一次升级升了主版本（删了变量、改了默认长相），旧页面可能已经按新规范改过，回滚时要连同旧页面一起回到旧版本，不能只回滚令牌文件；如果只是升了次版本或修订号（只加了新东西、只改了文档），回滚时只覆盖令牌和组件文件就够了。

    最坏的情况：令牌文件被改乱、备份也没有，那就用第 11 节给出的完整 tokens.css 重新建一个文件——这就是“配置即代码”的好处：只要第 11 节还在，系统就能从零恢复。恢复之后，务必再跑一遍第 14 节的五步验证，尤其是改主色全站变色那一步。
