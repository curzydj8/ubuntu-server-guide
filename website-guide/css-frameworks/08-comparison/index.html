    CSS-16：同一页面需求的多框架对照实战¶

    任务编号：CSS-16（网站建设与部署实战指南 · CSS 框架第 8 篇） 上一篇按任务索引顺序：CSS-15 完整 Design System。 本篇只讲对照：同一个落地页需求，用本批介绍过的框架思路分别怎么做、各自的代价和适用场景，最后给出选型建议。本篇不重复讲某个框架的完整安装和组件用法，那是各框架自己的文章；不讲新的布局基础，那是 CSS-04、CSS-05、CSS-06 的内容。

    1. 本章目标¶

    读完并动手做完本篇，你能：

    1. 用一句话说清楚同一个落地页需求：导航、英雄区、卡片列表、页脚，四部分各要什么；
    2. 对照本批的框架思路，说出每个框架写同一个页面时类名怎么写、代码量大概是什么量级、定制改颜色改间距难不难；
    3. 说出每个框架在什么情况下不适合，不再只看优点做决定；
    4. 解释为什么不能把多个框架的 CSS 同时引进同一个页面混用，混用会出什么冲突；
    5. 给一个真实的小项目选出一个框架，并说出你放弃其他框架的理由，而不是“都好”。

    2. 适用人群¶

    • 已完成 CSS-01 至 CSS-08，能写选择器、盒模型、Flex、Grid、响应式的人；
    • 已经读过本批至少一个框架的文章，对“框架就是别人写好的类名和组件”有直观印象的人；
    • 正在给自己的第一个小网站选框架、纠结用哪个的人；
    • 不适合还没学过 CSS 基础的人：对照的前提是你能看懂类名和样式规则，否则先回 CSS-01 至 CSS-08。

    3. 适用系统和版本¶

    • 系统：Windows、macOS、Linux 都可以，本篇只用浏览器打开一个 HTML 文件，不装构建工具，不装服务器。
    • 浏览器：任何现代浏览器（Chrome、Edge、Firefox、Safari 近几年版本）都可以，示例只用 Flex、Grid、媒体查询这些基础特性。
    • 框架版本：本篇不硬编版本号。对照中提到的每个框架，其版本号以该框架文章的第 3 节为准；如果你手头没有那篇文章，安装时以各框架官网为准。版本号写错比不写更误事，所以本篇宁可不写具体号，也不猜一个号。
    • HTML 与 CSS：示例只用 HTML5 语义标签和 CSS3 基础语法，不依赖任何实验特性。

    4. 使用前提¶

    1. 能新建文件夹和 HTML 文件，会用浏览器打开本地文件；
    2. 知道 CSS-04 的 Flex、CSS-05 的 Grid、CSS-06 的响应式思路，能看懂“导航横向排列、卡片三列变一列”是怎么回事；
    3. 知道 CSS-08 的 BEM 和文件组织思路，能理解“自写框架”和“设计系统”在对照表里是什么意思；
    4. 有一个练习文件夹，例如 comparison/，本篇所有文件都放在里面，不碰线上网站。

    5. 所需资源¶

    • 一个文本编辑器（记事本、VS Code、任何能存 UTF-8 的编辑器都行）；
    • 一个现代浏览器；
    • 不需要 Node.js、不需要 npm、不需要构建工具、不需要服务器；
    • 第 11 节的 landing-spec.json 一份，它就是本篇对照的“同一需求”的书面定义，所有框架实现都对着它写；
    • 可选：网络。网络只在你想试某个框架的 CDN 链接时才需要；第 10 节的完整示例不用 CDN，离线也能打开。

    6. 技术原理¶

    对照的核心思想只有一句话：需求固定，实现可变。

    同一个落地页，内容和结构是固定的：顶部导航（站名加三个链接）、英雄区（一句标题、一句副标题、一个按钮）、卡片列表（三张卡片，每张有标题和一段话）、页脚（一行版权文字）。HTML 的语义结构在所有实现里都一样，变的是“样式从哪来、类名怎么写、改样式时改哪里”。

    按这个维度，本批的框架思路可以分成四类：

    第一类是组件框架，代表是 Bootstrap、Bulma、Foundation、UIkit、Materialize。它们给你现成的组件和栅格：导航、卡片、按钮都有现成类名，你拼起来就行，写得快，样子统一。代价是样子容易和别人撞，而且改细节要和框架的默认值较劲。

    第二类是工具类框架，代表是 Tailwind CSS。页面上几乎每个样式都由小类名拼出来，例如一个元素同时挂上内边距、文字大小、颜色的类名。好处是改样式不用离开 HTML，不用再起名字；代价是 HTML 很长，读起来像一串密码，新手第一眼会晕。

    第三类是轻量框架，代表是 Pico CSS。它的思路是“少写类名”：你按语义写 header、main、section、footer 这些标签，框架直接给这些标签上样式，页面不用堆类名就能看。好处是写得最少；代价是可定制空间最小，样子基本就是框架给的样子。

    第四类不是用别人的框架，而是自己定规矩：自写框架和设计系统。自写框架是你按 CSS-08 的 BEM 思路，给自己的小网站写一套类名；设计系统是在这之上再加一套规矩：颜色、字号、间距、组件用法全部写成文档和变量，全站统一。好处是完全贴合你的需求，没有多余代码；代价是前期要花时间定规矩，小项目可能觉得“为三张卡片定一套系统”不值得。

    还有一条必须先讲清楚的原理，也是本篇最重要的红线：不要把多个框架的 CSS 同时引进同一个页面混用。每个框架都会定义自己的 button、card、container 这类通用样式和类名，两个框架一混用，后加载的会覆盖先加载的，同一个类名在两个框架里意思不一样，页面会一半像这个框架、一半像那个框架，出了问题你根本不知道是哪一套在起作用。正确做法永远是“同一需求、不同实现、分别展示”：给每个框架各做一个独立的 HTML 文件，或者只做一个文件、每次只引一个框架，比较时切换文件看效果。本篇第 10 节只给一个完整示例页，其他框架的写法只用表格和行内代码对照，绝不把它们拼进同一个页面。这条红线在第 15 节还会再出现一次，因为它是新手最容易踩的坑。

    选型没有“最好”，只有“最适合当前项目”。一个只有三张卡片的落地页，和一个要长期维护、十几个人协作的产品站，答案本来就该不一样。对照表的作用就是把这个“不一样”摊开给你看。

    7. 架构说明¶

    本篇的对照实验由三部分组成，缺一不可：

    第一部分是需求规格，也就是第 11 节的 landing-spec.json。它写清了页面有哪几块、每块的文字是什么、卡片有几张、断点怎么变。所有框架实现都对着同一份规格写，这样比较才公平：如果 A 实现的卡片是三张、B 实现的是四张，那比的就不是框架，而是需求。

    第二部分是实现文件。每个框架一个独立文件，互不引用，例如 bootstrap.html、tailwind.html、bulma.html、pico.html、own.html，每个文件只引自己那套样式。第 10 节给出的完整示例就是其中“自写思路”的那一个文件，离线可打开；其他框架的文件不要求你全写出来，对照表里给出了每个文件关键部分的类名写法，你按表里的写法各写一个小文件，就能亲手比出来。

    第三部分是对照表。表里每一行是一个框架，每一列是一个维度：类名写法、代码量感觉、定制难度、学习成本、不适合的场景、适用场景。读表时要一行一行读，不要只看“优点”那一列：一个框架的优点往往就是另一个框架的缺点反过来说，真正做决定的信息在“不适合”那一列。

    文件组织建议如下，全部放在练习文件夹 comparison/ 里：

    • landing-spec.json：需求规格，所有实现共用；
    • comparison.html：第 10 节的完整示例，自写思路，离线可打开；
    • 其他框架的实现各一个文件，名字按框架起，互相不引用；
    • 不要有任何一个文件同时引用两个框架的 CSS，那是第 15 节的头号错误。

    8. 操作前检查¶

    动手前先确认下面五条，缺一条就先补：

    1. 练习文件夹 comparison/ 已建好，你知道它在电脑上的完整路径；
    2. 能新建 HTML 文件并用浏览器打开，页面能显示文字；
    3. 能分清 Flex 和 Grid 各自适合什么：导航横向排列用 Flex，卡片多列用 Grid，这个判断在 CSS-04、CSS-05 里讲过；
    4. 知道第 11 节的规格文件要先看一遍再写实现，不要凭印象写；
    5. 明确本篇的目标是“比出区别”，不是“做出最漂亮的页面”：比得清楚比做得花哨重要。

    9. 逐步操作¶

    按下面六步做，每一步都有明确的产出，做完再进下一步：

    第一步，读规格。打开第 11 节的 landing-spec.json，把四部分（导航、英雄区、卡片列表、页脚）和三张卡片的文字读一遍，确认你脑子里有这个页面的样子。

    第二步，写自写思路的完整示例。把第 10 节的完整代码原样存成 comparison/comparison.html，浏览器打开，确认导航在上、英雄区居中、三张卡片一排、页脚在下。这是你的基准线：所有框架实现最后都要长成这个样子，样子差太多说明实现写偏了。

    第三步，挑一个组件框架写一版。只引那一个框架的样式，按对照表里那一行的类名写法，把同一个页面的四部分拼出来，另存为一个新文件。不要改规格里的文字，不要加第四张卡片。

    第四步，再挑一个工具类框架写一版。同样只引它一个，另存为新文件。写的时候你会立刻感觉到区别：组件框架是“一个类名就是一个组件”，工具类框架是“一串小类名拼出一个效果”。

    第五步，挑一个轻量框架写一版。按语义标签写，不堆类名，另存为新文件。写完你会发现这一版代码最短，但改颜色改间距的入口最少。

    第六步，填对照表。把你三版的真实感受填进第 12 节表格的“你的实测”一栏：哪一版写得最快、哪一版改颜色最顺手、哪一版 HTML 最难读。表格里印好的内容是通用判断，你自己的感受才是选型的依据。最后按第 14 节逐项验证，验证通过才算本篇完成。

    12. 每个关键配置项的解释¶

    先解释规格文件里的每一项，再解释对照表里的每一列，这样你读表时不会被术语绊住。

    规格文件解释：page 是页面类型，这里固定是落地页；title 是浏览器标签页标题；nav.brand 是导航左边的站名，nav.links 是导航右边的三个链接；hero.heading 是英雄区大标题，hero.subheading 是副标题，hero.button 是按钮文字；cards 是卡片数组，正好三张，每张只有 title 和 text，不许加图、不许加第四张；footer 是页脚文字；layout.desktop_columns 是桌面端卡片列数 3，layout.mobile_columns 是手机端列数 1，layout.breakpoint_px 是切换列数的断点 760 像素，layout.max_width_px 是内容最大宽度 960 像素。

    对照表分两张读。第一张是“写法对照”：同一处效果，各框架的类名怎么写。导航横向排列，Bootstrap 的思路是容器加栅格类名拼，Tailwind 的思路是一串工具类名拼，Bulma 的思路是导航组件类名拼，Pico 的思路是基本不用类名、靠语义标签加少量类名，自写思路就是第 10 节里的 site-nav 这种自己起的名字。卡片三列，组件框架用栅格列类名，工具类框架用网格工具类名，轻量框架靠语义标签加框架默认样式，自写思路用自己写的 Grid 规则。三列变一列，组件框架和工具类框架都用带断点前缀的类名，轻量框架和自写思路用自己写的媒体查询。按钮，组件框架给现成按钮类名，工具类框架给一串内边距加颜色类名，轻量框架基本不用类名，自写思路用自己写的按钮规则。读这张表时记住：类名越短不代表越好，类名越长也不代表越差，关键看“改的时候改哪里”。

    第二张是“选型对照”，这是本篇真正要交付的结论：

    框架思路 代码量感觉 定制难度 学习成本 不适合的场景 适用场景
    Bootstrap 中等，HTML 里类名不少但可读 中等，改主题要动变量或覆盖样式 低，文档多、例子多 想要完全独特、不想撞衫的外观；只想要一两个组件却要引整套样式 后台、文档站、内部工具、快速上线的普通网站
    Tailwind CSS HTML 很长，样式全在类名里 低，改样式直接改类名，不用另起名字 中等，要先熟记常用工具类名 团队没人愿意读长类名串；页面要交给不懂工具类的人长期维护 长期迭代的产品站、设计稿还原要求高的页面
    Bulma 中等，类名语义比较直白 中等，改主题用变量 低，上手快 需要大量 JavaScript 交互组件（它本身不带） 静态展示站、文档站、轻量后台
    Foundation 中等偏多，功能全但概念多 中等偏高，定制要理解它的整套约定 中等偏高 只是做一个三张卡片的落地页 大型响应式站点、有专人维护的复杂项目
    UIkit 中等，组件丰富 中等 中等 团队只熟悉另一套组件命名，想快速切换 内容站、组件丰富的展示站
    Pico CSS 最少，语义标签为主 高，想改出自己的样子要覆盖默认样式 最低 对外观有明确品牌要求、要高度定制 个人小站、演示页、快速原型
    Materialize 中等，组件带 Material 风格 中等，风格很固定 低 不想要 Material Design 风格的项目 喜欢 Material 风格的展示站、原型
    自写框架 样式文件要自己写，但 HTML 很干净 低，规则全是自己的，改哪里一清二楚 低，只需要 CSS 基础 页面越来越多、组件越来越多、一个人维护不过来 只有一个或几个页面的小站、学习练手
    设计系统 前期最多，要写变量、文档和用法规矩 前期高、后期低，规矩定好后改动反而快 高，要理解整套规矩 只有一个落地页、没有后续页面 多页面、多人协作、长期维护的产品

    读这张表要特别注意三行容易误读的地方。第一，Pico 的“代码量最少”不等于“最好用”，它的代价在定制那一列：你想改出自己的品牌色和间距，要花力气覆盖它的默认值，改得越多越不划算。第二，自写框架的“定制难度低”只在小项目成立，页面一多，没有文档和变量约束的自写样式会越长越乱，这时就该升级成设计系统，而不是继续往自写框架里堆规则。第三，Foundation 和 UIkit 的“功能全”对落地页是负担不是优点：一个三张卡片的页面用不上它的大部分功能，引进来只是多了一堆用不上的样式。

    最后补一句选型建议的通用顺序，给纠结的人一个落点：先问页面以后会不会变多、变复杂。不会，就在 Pico 和自写思路里选一个；会变多但团队小，选 Bootstrap 或 Bulma；会长期迭代、设计稿要求高，选 Tailwind；已经有多人协作、多页面，值得花时间定设计系统。选完之后，把放弃其他框架的理由写一句话记下来，三个月后你回看时就知道当初为什么这样选。

    3. 对照第 12 节的表格，至少亲手写出两个不同框架的版本（各一个独立文件），打开后四部分齐全、文字一致；
    4. 检查你写的每个框架版文件：只引用了那一个框架的样式，没有同时引用两个框架的 CSS；

    如实说明两处未实测，不算通过：第 10 节的完整示例不用 CDN，所以不存在 CDN 加载问题；但如果你写了框架 CDN 版，curl 只能证明你本地的 HTML 文件能返回，不能证明 CDN 在读者浏览器里一定能加载，CDN 被墙、CDN 地址失效、网络慢都会让框架版在读者那边变样，这一点必须在读者那边用浏览器打开验证，不能用 curl 通过代替。多框架之间的视觉对照效果（例如 Bootstrap 版和 Tailwind 版并排看起来差多少）也没有用浏览器实测过，留待你按上面第 3 步亲手写、亲手打开比较，不要把本篇的表格结论当成你亲眼看到的效果。

    15. 常见错误¶

    下面是新手做对照时最常犯的错误，每一条后面都跟着正确做法。注意：反面例子只用行内代码或表格描述，不会给你一段能直接复制粘贴的错误完整页面，免得你误贴进自己的文件。

    第一，混用多个框架。错误做法是在同一个文件的头部同时写上两个框架的样式链接，例如既引 Bootstrap 又引 Bulma，或者既引 Tailwind 又引 Pico。结果是按钮、卡片、容器的样式互相覆盖，页面一半像 A、一半像 B，调试时不知道该改哪一套。正确做法是每个框架一个独立文件，每次只引一个，比较时切换文件。

    第二，拿不同需求比框架。错误做法是 Bootstrap 版写了三张卡片，Tailwind 版写了四张还加了图，然后说 Tailwind 更丰富。正确做法是先对第 11 节规格文件，文字、数量、断点全一样，再比写法和定制难度。

    第三，只比优点不比代价。错误做法是看中 Pico 代码少就选它，事后发现品牌定制改不动；或者看中 Tailwind 改起来顺手就选它，事后发现团队没人愿意读长类名串。正确做法是先看第 12 节表格里“不适合的场景”那一列，再决定。

    第四，把框架类名和自己的类名起重了。错误做法是自己写了一个 card 样式，又引了一个也有 card 类名的框架，两个规则打架，卡片样子忽好忽坏。正确做法是自写类名加前缀，例如 site-、my-，或者干脆不用自写类名、只用框架类名，二选一。

    第五，CDN 版离线打不开就以为是代码错了。错误做法是断网打开框架 CDN 版，页面没样式，就回去改 HTML。正确做法是先看网络：CDN 版本来就需要网络，第 10 节的自写示例离线能打开，框架 CDN 版离线打不开是预期行为，不是代码错误。

    第六，断点写反。错误做法是桌面三列、手机也三列，或者手机一列、桌面也一列，根源是媒体查询条件和列数对应错了。正确做法是对着规格文件核对：宽屏 3 列、窄屏 1 列、切换点 760 像素，再检查媒体查询里写的是不是这个数。

    第七，定制时直接改框架原文件。错误做法是下载框架 CSS 后直接在里面改颜色，下次升级框架就全丢了。正确做法是另外写一个自己的样式文件覆盖，或者用框架提供的变量定制，框架原文件永远不动。

    16. 故障排查¶

    按症状查，先查最可能的原因，不要一上来就重写：

    • 症状：页面一片白、只有文字没有样式。先查文件路径和样式链接是不是写对了，离线打开的是不是第 10 节的自写示例；如果是框架 CDN 版，先查网络和 CDN 地址能不能打开，再查是不是同时引了两个框架。
    • 症状：卡片没有排成三列，上下摞在一起。先查卡片容器是不是用了 Grid 或栅格规则，再查断点：是不是浏览器窗口本来就窄于 760 像素，或者媒体查询把列数改成了一列。
    • 症状：导航挤成一团、链接换行很难看。先查导航容器是不是 Flex、是不是左右分开，再查小屏幕下有没有改成纵向排列。
    • 症状：按钮颜色和想象的不一样。先查是不是两个样式规则撞了：自己写的按钮规则和框架的按钮规则，后加载的会赢；再查是不是同时引了两个框架。
    • 症状：改了颜色没变化。先查改的是不是真正起作用的规则：框架默认值、自己写的覆盖规则、浏览器缓存，三者里最常见的是缓存，强制刷新一次再看；其次是选择器优先级被框架规则压住了。
    • 症状：手机上看布局乱了。先查 viewport 那一行有没有写，再查断点是不是 760 像素，最后查固定宽度元素（例如写死的宽卡片）有没有把布局撑坏。
    • 症状：两个框架版看起来一模一样，分不出区别。先查两个文件是不是真的各引了各的样式，还是误写成同一个链接；再查是不是规格文字被改得不一样，导致你比较的其实是文字不是框架。

    如果上面都查过还是不对，把问题缩小到最小：新建一个只有导航和一张卡片的文件，只引一个框架，能复现问题就继续查这个小文件，复现不了就说明问题出在原文件的其他部分。

    17. 安全注意事项¶

    本篇没有服务器、没有登录、没有数据库，安全风险很小，但有三条仍要讲清楚：

    1. CDN 链接只用框架官网给的地址，不要从不明网站复制样式链接。不明来源的 CSS 文件里可能夹带恶意样式或脚本引用，页面一旦上线就会影响所有访客。
    2. 对照用的落地页不要放真实的用户信息、真实的联系方式、真实的后台地址。示例里的“小站”“开始了解”都是假文字，上线前必须换成真实内容并重新检查。
    3. 框架版本以官网为准，不要用搜索引擎搜到的旧教程里的旧链接直接上线。旧版本可能有已知样式问题或安全问题，升级前先在练习文件夹里试一遍，再换到正式页面。

    另外，页面里的链接目前都是占位链接，点开不会跳到真实页面，这是对照示例的正常状态，不是缺陷；正式上线前必须把占位链接换成真实地址，并检查有没有死链。

    18. 回滚和恢复¶

    本篇所有文件都在练习文件夹 comparison/ 里，没有部署、没有改线上网站，回滚非常简单：

    • 写错了：编辑器里撤销，或把第 10 节的完整代码重新复制覆盖一次；
    • 某个框架版写乱了：删掉那个框架版文件，只保留规格文件和第 10 节的自写示例，对照可以重做，规格文件不受影响；
    • 混引了两个框架：删掉其中一个样式链接，只留一个，刷新浏览器，页面就回到单一框架的样子；
    • 规格文件改乱了：把第 11 节的 JSON 重新复制一份覆盖，文字和数量就回来了；
    • 整个文件夹删错了：重新新建 comparison/，把第 10 节和第 11 节的代码再贴一遍，五分钟就能恢复；
    • 没有任何线上内容会被影响，因为本篇文件只在你的练习文件夹里，还没有部署到 crozz.me。
