# 多架构服务器：x86-64 与 ARM64

## 一、概述与使用场景

过去服务器几乎清一色 x86-64，装软件不用想架构。现在云厂商 ARM 实例凭性价比进入生产，同一套服务常要同时部署在 x86 机房机器和 ARM 云主机上。架构混杂时最先出问题的不是性能，而是名词对不上、包装不上、镜像跑不起来。

三个典型现场：把 x86 二进制拷到 ARM 上执行，报无法执行，根因是指令集完全不同；在 ARM 上拉到只发了 x86 的镜像，启动即报 exec format error；在包管理里搜不到包，其实只是同一架构在不同工具里叫法不同。本章依次讲清架构识别与名词对齐、dpkg 多架构、容器多架构镜像与模拟边界，最后给出上 ARM 前的核查清单。按架构选安装镜像见 [系统安装章](02-installation.md)，容器完整内容见 [Docker 章](../05-containers/01-docker.md)。

## 二、环境准备与前置条件

本章命令已按 Ubuntu 与 Debian 官方文档核对，适用于 Ubuntu 22.04 LTS 与 24.04 LTS，两个版本在架构命名和 dpkg 多架构机制上没有实质差异。Ubuntu 26.04 的相关行为标注为待核验。本章为文档核对级别内容，涉及改动 dpkg 架构配置的操作，请先在测试机验证再上生产机。

开始前需要具备：一台可登录的 Ubuntu 服务器和 sudo 权限；如果要练多架构装包和容器构建，还需要已安装 Docker 并会基本命令。本章所有查询命令都是只读的，可以放心在生产机执行；凡是会改系统状态的命令，都在对应小节里单独标明了风险。

改任何配置前先备份。本章会改动的状态主要是 dpkg 的架构列表和 apt 索引，动手前把当前状态留档，出问题时能对照恢复。

```bash
sudo mkdir -p /root/backup-20261021
dpkg --print-architecture > /root/backup-20261021/arch-before.txt
dpkg --print-foreign-architectures > /root/backup-20261021/foreign-arch-before.txt
sudo cp -a /etc/apt /root/backup-20261021/apt-backup
cat /root/backup-20261021/arch-before.txt
```

逐条说明：存档主架构与附加架构、备份 apt 配置目录、确认记录成功。改 /etc 下其他文件同样先备份，这是全站统一纪律。

!!! warning "加错架构比不加更麻烦"

    `dpkg --add-architecture` 一旦执行，apt 就会去拉取该架构的包索引。填错架构名、或在不需要时乱加架构，会让每次 `apt update` 变慢，还可能在后续装包时引入难以排查的依赖混乱。本章涉及该命令的小节都要求先想清楚场景再执行，不要把它当成试错工具。

## 三、手把手操作步骤

### 3.1 架构识别：先把本机架构查准

识别架构有两条命令，分工不同，都要会。

```bash
uname -m
dpkg --print-architecture
dpkg --print-foreign-architectures
```

逐条讲解：`uname -m` 是内核看到的硬件架构；`dpkg --print-architecture` 是包系统认定的本机架构，装包以它为准；`dpkg --print-foreign-architectures` 列出额外启用的附加架构，未启用时无输出。前两条指向同一架构只是叫法不同，见下一节名词表。把输出记入台账，下载包、选镜像时以此为准，不要凭型号猜。

### 3.2 名词对应表：x86_64 与 amd64、aarch64 与 arm64 是同一件事

同一个架构在内核、发行版和软件官网各有叫法，这是跨架构工作中最高频的困惑来源。下表把服务器最常见的对应关系一次对齐。

| CPU 架构 | `uname -m` 输出 | dpkg 与 apt 架构名 | 常见别名与说明 |
|----------|-----------------|--------------------|----------------|
| 64 位 x86 | x86_64 | amd64 | Intel 与 AMD 的 64 位机器都用 amd64，不要被名字误导 |
| 64 位 ARM | aarch64 | arm64 | 官网写 aarch64 的包就是给 arm64 用的 |
| 32 位 x86 | i686 或 i386 | i386 | 老旧 32 位程序和兼容库场景才会碰到 |
| 32 位 ARM | armv7l | armhf | 树莓派等 32 位系统常见，服务器较少用 |

用法：下载时把官网叫法换算成 dpkg 架构名再判断。例如官网提供 x86_64 和 aarch64，本机是 arm64 就选 aarch64；反过来 apt 只认 dpkg 名，写 aarch64 找不到包。Ubuntu 官方镜像文件名用的也是 amd64 和 arm64。

### 3.3 dpkg 多架构：给系统添加附加架构

默认情况下系统只为本机架构装包。多架构机制允许在同一台机器上额外启用一个附加架构，为它拉取索引并安装它的包。先查看现状，再按需添加。

```bash
dpkg --print-foreign-architectures
sudo dpkg --add-architecture arm64
sudo apt update
dpkg --print-foreign-architectures
```

逐条说明：第一条看现状，初始通常为空；第二条以 amd64 上添加 arm64 为例，执行时换成真正需要的架构；第三条必须紧跟，否则新架构索引不存在，装包会报找不到；最后一条确认已生效。

最经典的真实场景不是加 arm64，而是 64 位 x86 机器为了跑老旧的 32 位程序添加 i386，再安装带架构后缀的兼容库。

```bash
sudo dpkg --add-architecture i386
sudo apt update
sudo apt install -y libc6:i386
apt-cache policy libc6:i386
```

说明：`libc6:i386` 是包名加冒号加架构的写法，指定装 i386 版 C 库；最后一条确认候选版本正常。通用规则：不写后缀默认本机架构，写了后缀装指定架构，查询、安装、卸载都支持，`dpkg -l` 输出也用后缀区分同名不同架构的包。

### 3.4 跨架构装包的风险提示

多架构不是免费的，启用前认清三条边界。

- 装上附加架构的库不等于能运行该架构程序：执行 arm64 二进制还需内核或模拟层支持，见 3.6 节；最稳妥的场景是同家族兼容，如 amd64 加 i386。
- 同名包的两个架构版本必须严格一致，一个升级另一个没跟上就会触发依赖冲突，卡住后续 apt 操作。
- 附加架构会增加索引下载量和依赖计算复杂度，只启用真正需要的，需求消失后及时清理。

原则：没有具体软件明确要求，就不要启用任何附加架构。

### 3.5 容器镜像多架构：判读、报错排查与 buildx 构建

容器把跨架构问题从装包转移到了镜像。先学会判读一个镜像到底支持哪些架构，再谈构建。

```bash
docker manifest inspect nginx
docker manifest inspect example-registry.example.com/example/app:1.0
```

第二条是占位示例，执行时换成真实镜像。输出判读：多架构镜像会出现 manifests 列表，每项带 platform 字段标明 os 和 architecture，如 linux/amd64 与 linux/arm64 并存；只有一个平台说明该标签只发了单架构。拉镜像前先查清单，能提前拦截绝大多数不匹配。

在 ARM 机器上跑到只发了 x86 的镜像时，典型报错如下。

```text
standard_init_linux.go: exec user process caused: exec format error
```

根因只有一个：容器主程序是异架构二进制，CPU 执行不了。排查：先用 manifest 确认有没有 arm64 变体；有变体仍报错，检查是否被固定标签拉到了单架构版本；确认只有单架构时只有三条路：索要多架构版本、换多架构替代镜像、或按 3.6 节模拟应急，改容器参数绕不过指令集差异。

自己构建镜像时，用 buildx 一次产出多架构镜像是标准做法，最小命令示意如下，完整讲解见 [Docker 章](../05-containers/01-docker.md)。

```bash
docker buildx create --name multiarch-builder --use
docker buildx build --platform linux/amd64,linux/arm64 -t example-registry.example.com/example/app:1.0 --push .
```

说明：第一条创建多平台构建器；第二条同时构建 amd64 与 arm64 并推送，地址为占位。前提是构建不依赖特定架构的闭源二进制，Dockerfile 写死某架构下载链接是最常见的失败原因，应按目标平台参数化。

### 3.6 模拟运行：qemu-user-static 与 binfmt 的概念和边界

程序只有 x86 版又必须临时在 ARM 上跑时，最后的办法是用户态模拟：QEMU 在软件层翻译指令。组合是两个东西：qemu-user-static 提供各架构的静态模拟器，binfmt_misc 是内核按文件头自动调用解释器的机制，两者配合后执行异架构二进制会自动被模拟器接管，表面上像原生运行。

```bash
sudo apt install -y qemu-user-static
ls /proc/sys/fs/binfmt_misc/
```

注册细节以该包官方说明为准。边界必须讲清：模拟有显著性能代价，CPU 密集型程序可能慢数倍到数十倍，涉及特殊指令的程序还会直接失败。它只适合应急、验证和低负载小工具，长期生产服务不应建在模拟层上，长期解法是原生多架构版本或把服务放回匹配架构的机器。

### 3.7 选型核查：上 ARM 之前先过清单

云上 ARM 实例的吸引力很实在：以 Ampere 和 AWS Graviton 为代表的 ARM 实例通常更便宜或同价位核心更多，对无状态和横向扩展负载性价比突出。前提是软件栈真能原生运行，上之前逐项核对清单，不过关先在测试机解决。

- 业务程序：自研可重编还是闭源二进制；闭源软件查官网架构列表，只写支持 Linux 不等于支持 ARM，必须明确看到 arm64 或 aarch64。
- 驱动与内核模块：厂商驱动、加密卡、网卡专用模块只发 x86 的情况最常见，也最难绕过。
- 基础软件：数据库、中间件、监控与备份代理是否都有 arm64 版本或多架构镜像，逐个按 3.5 节核查。
- 交付链：持续集成能否产出多架构产物，回滚方案是否保留两个架构的版本。
- snap 包覆盖：同一 snap 的架构覆盖不一致，有的只发 amd64，有的 arm64 更新滞后；用 `snap info` 查清支持架构再决定。

结论用法：全部通过就用 ARM；个别边缘组件不支持就混合部署；核心闭源软件或驱动不支持，这批服务继续用 x86。

## 四、效果验证与测试

完成架构识别或多架构配置后，按以下命令做一次完整验证。

```bash
uname -m
dpkg --print-architecture
dpkg --print-foreign-architectures
sudo apt update
docker manifest inspect nginx
```

期望输出与判读：前两条指向同一架构且叫法能用 3.2 节的表对上；第三条列出的附加架构与你的规划一致，没有多余架构；`apt update` 全程无报错，说明各架构索引健康；最后一条的平台列表包含你计划部署的目标架构。任一项不符，回到对应小节修正，不要带着架构状态不明的机器继续部署。

再做一次最小闭环测试，在测试机上验证附加架构装包链路是否真正可用。

```bash
apt-cache policy libc6:i386
sudo apt install -y libc6:i386
dpkg -l libc6:i386
```

上例以 amd64 机器加 i386 场景为例，其他架构组合把后缀换成对应架构名即可。能查到候选版本、能正常安装、`dpkg -l` 状态为 ii，三点齐全才算多架构链路验证通过。

## 五、常见错误与排坑指南

### 场景一：把 x86 二进制拷到 ARM 上执行，报无法执行

现象：在 ARM 机器上运行从别处拷来的程序，系统提示无法执行二进制文件或格式错误。根因是文件本身是 x86-64 的可执行文件，ARM CPU 无法识别其指令。先用下面命令实锤文件的真实架构，不要靠文件名猜。

```bash
file ./example-program
uname -m
dpkg --print-architecture
```

`file` 的输出会明确写出文件是 x86-64 还是 ARM aarch64 的可执行文件，与本机架构对照即可定性。example-program 为占位文件名，换成你的真实文件。修复方法只有下载或构建该程序的 arm64 版本；确实没有且负载很低时，才考虑 3.6 节的模拟应急，并明确记录这是临时方案。

### 场景二：添加附加架构后 apt update 报错或装包找不到

现象：执行了添加架构命令后，`apt update` 出现某架构索引 404 或签名相关报错，或者安装带后缀的包时提示找不到。常见根因有三个：添加后忘了执行 `apt update` 就直接装包；所用镜像站没有同步该架构的目录；架构名写错，例如把 dpkg 架构名 arm64 写成了 aarch64。

```bash
dpkg --print-foreign-architectures
sudo apt update
apt-cache policy
```

修复顺序：先确认附加架构列表里的名字与 3.2 节表格的 dpkg 架构名完全一致；再完整执行一次更新并看清报错指向哪个源；若是镜像站缺该架构目录，换一个同步完整的正规镜像站，换源前按第二节的方法备份。不要用删除报错索引或强行忽略的方式蒙混过去，索引不完整时装上的包同样不完整。

### 场景三：容器在 ARM 上起不来，反复重启

现象：容器在 x86 机器上运行正常，搬到 ARM 机器后启动即退出，日志或事件中出现 exec format error。根因见 3.5 节：镜像没有当前架构的变体。不要在容器参数、环境变量和权限上兜圈子，先做架构定性。

```bash
docker manifest inspect example-registry.example.com/example/app:1.0
docker image inspect example-registry.example.com/example/app:1.0
uname -m
```

第一条看标签支持的全部平台，第二条看本地已拉取的那个镜像具体是哪种架构，示例镜像地址为占位写法。确认缺 arm64 变体后，按 3.5 节的三条路处理：换多架构镜像、用 buildx 自行构建多架构版本、或把该服务调度回 x86 节点。把架构检查写进部署前清单，以后每次上新镜像先查 manifest 再部署，这类问题就不会再进生产。

## 六、生产环境最佳实践与安全建议

第一，架构信息进台账：登记每台机器两条识别命令的真实输出，部署和下载一律读台账或实时查询，不靠型号推断。

第二，收敛架构种类：双架构时写明哪类服务跑在哪，并对两个架构同等验证，避免 ARM 侧成为没人认真测的二等公民。

第三，多架构只解决真问题：附加架构按需启用、用完清理；模拟只作应急并标注退出条件，靠模拟撑着的核心服务要推动原生化。

第四，供应链按架构核查：采购选型阶段就把 arm64 支持写进确认项并索要厂商正式说明，不要等迁移当天才发现没版本。

第五，部署前先查镜像平台：把 manifest 检查列入发布清单，目标平台不在清单里的镜像不许进生产。
