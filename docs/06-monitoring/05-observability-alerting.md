# 可观测性与告警治理

## 一、概述与使用场景

第 06 部分第 2 章已搭好 Prometheus 与 Grafana 监控栈，第 3 章已把日志集中收集，但工具齐全不等于可观测性到位。值班的真实困境通常是：仪表盘很多，出事时不知道先看哪个；告警很多，真正要动手的淹没在重复通知里；日志很全，却拼不出一次请求慢在哪一段。本章先讲清指标、日志、追踪三类信号的分工，再把告警从「装上就响」治理成「响了有人处理、处理有手册、处理完有复盘」的闭环。

三支柱分工与局限先看对照表：

| 支柱 | 回答的问题 | 典型形态 | 擅长 | 局限 |
| --- | --- | --- | --- | --- |
| 指标（Metrics） | 是否异常、有多大 | Prometheus 加 Grafana 曲线 | 长期留存、阈值告警与趋势 | 只有聚合值，无单次细节；标签失控引发高基数 |
| 日志（Logs） | 发生了什么 | Loki 等集中日志（见第 3 章） | 细节最丰富，事后溯源靠它 | 量大成本高，非结构化难聚合 |
| 追踪（Traces） | 慢在哪一段 | Jaeger、Tempo 等后端 | 还原跨服务调用链 | 需埋点，量大，通常必须采样 |

配合方式：指标先发现异常并触发告警，追踪顺着请求标识定位出问题的服务与环节，日志最后给出完整上下文。只用指标，知道 CPU 高了但不知道为什么；只用日志，发现故障往往靠用户投诉；只看追踪，单次请求清楚，却答不出整体错误率是否恶化。

两个代价要提前知道。一是高基数：指标标签放用户号、请求号这类取值近乎无限的维度，时序条数会爆炸，存储与查询一起被拖垮。二是采样：追踪为控制成本普遍只采样一部分请求，被丢掉的部分可能正藏着偶发错误，所以错误请求应优先保留，采样按信号价值定，不要一刀切。

本章定位是概念与治理层，不重复部署第 2、3 章已落地的组件。内容为「文档核对」级别，适用于 Ubuntu 22.04 LTS 与 24.04 LTS；Ubuntu 26.04 上的组件版本与默认行为标记为「待核验」。

## 二、环境准备与前置条件

- 已有监控底座：第 2 章 [Prometheus 与 Grafana 监控栈](02-prometheus-grafana.md) 已部署可用，Alertmanager 能发出通知。
- 已有日志底座：第 3 章 [集中式日志收集](03-logging-stack.md) 已部署可用；没有也能先做告警治理，但复盘缺日志证据链。
- 权限：监控机上有 sudo 账号，能改 Prometheus 规则与 Alertmanager 配置。
- 组织前提：先定值班人、通知渠道与各级响应时限（见 3.4 节），没有承接人，规则写得再细也会落空。

本章会动告警规则与 Alertmanager 配置，改任何配置前先备份：

```bash
sudo mkdir -p /root/alerting-backup
sudo cp -a /etc/prometheus/rules /root/alerting-backup/rules.bak-20260101
sudo cp -a /etc/alertmanager/alertmanager.yml /root/alerting-backup/alertmanager.yml.bak-20260101
ls -l /root/alerting-backup/
```

路径以第 2 章实际部署为准，不同按实际替换。回滚：备份复制回原路径，`promtool check rules` 与 `amtool check-config` 校验过后 reload 对应服务，不要用重启代替重载。

!!! danger "不要在故障进行时改告警规则"
    大面积告警爆发时，不要删规则或关通知，那会把真实故障的信号一起掐掉。先处置故障本体，止血只用带到期时间的静默（见 3.5 节）；规则修改等复盘时再评审落地。大量「告警失灵」事故，都是故障当晚随手改规则、事后忘了改回来造成的。

## 三、手把手操作步骤

### 3.1 OpenTelemetry 概念：信号、埋点与协议

OpenTelemetry（缩写 OTel）是厂商中立的遥测标准与工具集，统一了三件事：信号定义、埋点接口、传输协议。三类信号与第一节三支柱一一对应：

| 信号 | 内容 | 关键概念 | 说明 |
| --- | --- | --- | --- |
| Traces（追踪） | 一次请求的完整调用链 | 一条 Trace 由多个 Span 组成 | 用 Trace ID 串起跨服务请求 |
| Metrics（指标） | 随时间变化的聚合数值 | 计数器、直方图、仪表盘 | 与 Prometheus 指标可衔接 |
| Logs（日志） | 带时间戳的离散事件 | 可携带 Trace ID 与 Span ID | 能从慢 Span 跳到对应日志 |

应用侧埋点由 SDK 完成：各语言 SDK 提供统一 API 产出 Span、指标与日志；很多框架有自动埋点组件，常见库可零改代码先采，业务关键路径再手工补。数据通过 OTLP 协议传输，它是 OTel 的原生协议，支持 gRPC（默认 4317）与 HTTP（默认 4318），记住这个对应关系是看懂 Collector 配置的前提。

边界：OTel 只负责产生与传输遥测数据，不做长期存储与查询。存储与展示仍落在已有后端上（Prometheus 存指标、Loki 存日志、Tempo 存追踪），它解决的是「各应用用统一方式送出数据」，不是再引入一套新监控系统。

### 3.2 Collector：接收、处理、导出三段管道

应用多起来后，让每个应用直连后端会有两个问题：后端地址与凭证散落各处，改一次要全量发版；采样、脱敏、加标签等加工逻辑要在每个应用里重复实现。Collector 就是为此存在的中间层：独立进程，应用只把数据发给它，加工与转发收敛在这一层。管道分三段：

| 管道段 | 组件名 | 职责 | 常见例子 |
| --- | --- | --- | --- |
| 接收 | Receivers | 收数据并转成统一格式 | otlp 接收 OTLP 数据 |
| 处理 | Processors | 批处理、采样、过滤、脱敏 | batch 攒批，memory_limiter 防打爆 |
| 导出 | Exporters | 发往一个或多个后端 | 按后端选 OTLP 或专用导出器 |

下面是 Collector 最小配置的概念示意，只保留 otlp 接收、batch 处理与调试导出器，把管道结构看清：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 1000

exporters:
  debug:
    verbosity: basic

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
```

逐段讲解：

| 配置段 | 含义 | 要点 |
| --- | --- | --- |
| `receivers.otlp.protocols` | OTLP 接收器开 gRPC 与 HTTP 两入口 | 4317 与 4318 为默认约定 |
| `processors.batch` | 攒批后发送，降低开销 | 定义不等于启用，须在管道引用 |
| `exporters.debug` | 打印数据做调试 | 仅验管道，生产换真实导出器 |
| `service.pipelines` | 按信号各定义一条管道 | 三条管道可引用不同组件 |

!!! warning "这份配置只是概念示意"
    上面这份 yaml 只讲结构，不要直接当生产配置。生产选型时导出器要用实际后端的类型与地址，处理器补内存限制与采样，接收端配 TLS 与访问控制，每项按 OpenTelemetry 官方文档当前版本核验后再落地。与本站 Prometheus、Loki 体系如何对接，结合第 2、3 章部署形态评估，不要照搬网上整套示例覆盖现有可用配置。

### 3.3 Canonical Observability Stack（COS）与现有路线的分工

Canonical Observability Stack（COS）是 Canonical 基于 Juju 的整套可观测性方案：用 Charm 编排部署并关联 Prometheus、Grafana、Loki、Alertmanager 等组件（另有轻量版 COS Lite），对接由 Charm 关联自动完成，适合 Juju 与 Kubernetes 体系里新建的大规模环境。它与本站现有路线不冲突，但不要重复建设：

| 维度 | 本站现有路线（第 2、3 章） | COS |
| --- | --- | --- |
| 部署方式 | 二进制加 systemd，手工配置 | Juju Charm 编排，关联自动对接 |
| 组件 | Prometheus、Grafana、Alertmanager、Loki、Vector | 同类组件的 Charm 化版本 |
| 适合规模 | 数台到数十台主机 | 多集群、大规模、已有 Juju 体系 |
| 运维门槛 | 熟悉 Linux 服务管理即可 | 需要 Juju 与 Kubernetes 能力 |
| 本站建议 | 已部署且稳定的继续用 | 新建大型环境且有 Juju 能力时评估 |

一条硬纪律：同一指标来源只能进一套体系。已有小规模部署跑得好好的，不必迁移到 COS；评估 COS 的新环境，也不要在过渡期让同一批 Exporter 同时向两套 Prometheus 写数据，双写会让告警双响、口径打架。迁移要走变更评审，明确切换点与回滚点。

### 3.4 告警治理一：分级与升级路径

告警治理的第一步是分级，标准只有一个：收到的人需要多快、以什么方式响应。

| 级别 | 响应方式 | 时限示例 | 典型例子 | 处理要求 |
| --- | --- | --- | --- | --- |
| P1 | 电话强提醒，立即打断工作 | 15 分钟内确认 | 核心服务不可用、数据有丢失风险 | 立即处置，超时未确认自动升级 |
| P2 | 工单或值班群通知 | 4 小时内处理 | 单节点故障但有冗余、容量数小时内耗尽 | 当班内处理并留记录 |
| P3 | 仅记录到面板或日报 | 下一工作日评估 | 证书 30 天后到期、非核心指标越界 | 批量评估，转工单或删规则 |

分级要落到规则标签上：第 2 章规则中的 `severity` 标签就是分级载体，Alertmanager 按它路由到不同接收人（配置思路见第 2 章 3.3 节，本章不重复）。新增规则先定级别再写表达式，定不下级别说明还没想清楚，不要先上线再说。

升级路径（escalation）解决「没人理」：P1 在约定时限内无人确认，自动通知二线负责人；再超时，通知团队负责人。升级靠 Alertmanager 的重复通知参数配合值班表实现，值班表（谁在一线、谁是二线、如何轮换）单独维护，并保证接收人与值班表一致，换班后第一件事就是核对接收人。

### 3.5 告警治理二：分组、抑制与静默

通知风暴的根源通常不是告警太多，而是同源告警没有收敛。三个机制各管一段：

| 机制 | 解决什么 | 关键概念 | 纪律 |
| --- | --- | --- | --- |
| 分组（Grouping） | 同源告警合并成一条通知 | 按 `group_by` 聚合，回链第 2 章 3.3 节 | 按告警名与实例起步，不过细拆分 |
| 抑制（Inhibition） | 上游大故障时压住下游告警 | 源告警存在时目标告警不发送 | 只对因果确定的链路配，不滥用 |
| 静默（Silence） | 已知时段内不发某类告警 | 界面或 amtool 创建，带起止时间 | 必须带到期时间与原因 |

抑制规则示例（写入 Alertmanager 配置的 `inhibit_rules` 段）：

```yaml
inhibit_rules:
  - source_match:
      alertname: "ClusterDown"
    target_match:
      alertname: "InstanceDown"
    equal:
      - "cluster"
```

逐项讲解：`source_match` 是抑制源（集群级 ClusterDown）；`target_match` 是被抑制目标（单实例 InstanceDown）；`equal` 表示两边 cluster 标签相同才抑制，避免 A 机房故障错误压住 B 机房的独立故障。一句话：整集群已确认出事，就不要让每台实例各发一遍失联告警，但被抑制的告警仍能在界面查到，抑制的是通知，不是数据。

静默纪律三条，必须条条执行：必须带到期时间，窗口多长就静默多长，禁止无结束时间的长期静默；必须写原因，注明变更单或故障单号；创建人负责到期复查，故障当晚的止血静默第二天逐一确认已过期或手动解除。命令形态：

```bash
amtool silence add alertname="InstanceDown" instance="192.0.2.21:9100" --duration=2h --comment="维护窗口 变更单 CHG-2026-001" --alertmanager.url=http://localhost:9093
amtool silence query --alertmanager.url=http://localhost:9093
```

第一条创建两小时后自动到期的静默，第二条列出当前全部静默，交接班时当固定检查项，能当场发现「忘了摘」的静默。

### 3.6 告警治理三：告警疲劳与处理手册

告警疲劳是治理的最终敌人：通知长期大多是无需动作的噪声，值班人就会先忽略再处理，真正的 P1 混在其中被一起忽略，告警系统在组织层面失效。对策是给每条告警立三条硬标准：

- 必须有明确的第一步动作。收到的人五分钟内能说出先做什么，做不到说明还不可行动。
- 必须有处理手册链接。注解里带 runbook 链接，手册至少写清影响判断、第一步命令、止血方法与升级联系人；沿用第 2 章注解的 summary 与 description 写法，在 description 中补手册地址即可。
- 无动作的告警降级或删除。连续多次触发而每次结论都是「无需处理」的，评审后改阈值降为 P3 记录，或直接删除，留着只消耗注意力。

执行节奏：每月评审一次，过一遍触发最多与从未触发的告警清单，前者查聚合与阈值，后者查规则是否失效。结论（保留、降级、删除、改阈值）记入变更记录，不要只在会上口头过一遍。

### 3.7 故障复盘：postmortem 模板

P1 与影响较大的 P2 故障，恢复后必须写复盘。目的不是追责，而是产出能防同类故障再发生的行动项。要点：摘要一句话说清发生了什么；影响面写清受影响服务、用户与时长；时间线按分钟记录发现、确认、处置、恢复节点；根因写到技术与流程两层，只写技术根因通常防不住下一次；处置评价如实记录哪些动作有效、哪些环节被耽误（含告警是否及时、静默是否误伤）；行动项每条有负责人与期限，没有负责人的行动项等于没有。可直接复制的模板骨架：

```markdown
# 故障复盘：服务名加一句话摘要

## 摘要与影响面

- 结论：
- 受影响服务与用户：
- 故障时长：

## 时间线

- HH:MM 触发 / 确认 / 关键处置 / 恢复：

## 根因与处置评价

- 技术根因：
- 流程根因：
- 有效的动作与被耽误的环节：

## 行动项

- 行动项一：负责人 / 期限
- 行动项二：负责人 / 期限
```

复盘产出后，行动项同步进第 08 部分处置体系：涉及取证与响应流程的改进，对照 [事故响应与取证](../08-troubleshooting/07-incident-response.md)（本期同批新增）落地；涉及告警规则的改进，回到 3.4 至 3.6 节按治理流程评审，不要在复盘文档里直接改生产规则。

## 四、效果验证与测试

告警治理是否生效，不能等真故障检验，要用演练验证。本节是标准演练脚本：人为触发测试告警，走完触发、分组、抑制、通知、确认、恢复全链路，逐项核对。

第一步，确认基础服务健康：

```bash
curl http://localhost:9090/-/healthy
curl http://localhost:9093/-/healthy
amtool check-config /etc/alertmanager/alertmanager.yml
```

期望前两条返回各自的健康应答文本，第三条输出校验成功。任一项不通过先修复，不要带着坏底座演练。

第二步，发送一条带级别与实例标签的测试告警：

```bash
amtool alert add DrillAlert instance="192.0.2.21:9100" severity="warning" --alertmanager.url=http://localhost:9093 --annotation=summary="告警链路演练测试"
```

第三步，按检查表逐项观察，不预设平台输出文案，以观察点是否成立为准：

| 检查点 | 观察方法 | 通过标准 |
| --- | --- | --- |
| 触发 | 界面看告警列表 | 测试告警按时出现，标签与级别正确 |
| 分组 | 看通知条数 | 同组合并为预期条数，不刷屏 |
| 抑制 | 先触发上游再触发下游 | 下游可见但不单独发通知 |
| 通知 | 看对应级别渠道 | 到达正确接收人，含摘要与手册链接 |
| 确认与静默 | 建短时静默再等到期 | 静默期不发通知，到期自动恢复 |
| 恢复 | 停止测试告警并等待 | 能查到恢复状态，告警移出活跃列表 |

第四步，演练收尾：发现的问题（通知延迟、分组不合理、接收人错误等）逐条记入清单，按 3.6 节评审流程处理，并把演练时间、参与人与结论补进复盘归档。演练建议每月一次，值班人员或通知渠道变更后立即补做。

## 五、常见错误与排坑指南

场景一：一次机房故障，值班人收到几百条通知。根因几乎总是三缺一：没有分组，同故障下每条规则、每个实例各发一条；没有抑制，实例级告警在集群级故障时照发；重复通知间隔太短。修复不是删规则，而是按 3.5 节补齐分组与抑制、拉长重复间隔，改完用第四节脚本复测。

场景二：静默忘了摘，真实故障被压了几小时。根因是静默没设到期时间，或维护结束无人复查。先用 `amtool silence query` 盘点存量静默，该过期的手动过期；再把「静默带到期与原因」「交接班查静默清单」写进规范（见 3.5 节），并给「存在活跃静默」设一条 P3 提醒。

场景三：指标一查就超时，存储涨得飞快。典型根因是高基数：用户号、请求号、完整 URL 被当成标签，每个取值生成一条新时序。先定位基数最高的标签并停掉其产生源，已写入数据等自然过期，不要动底层存储文件。规范上加标签白名单，只允许主机、服务、环境、级别等低基数维度，与第 3 章日志侧纪律一致。

场景四：装了追踪却定位不了偶发错误。根因多在采样：采样率太低，偶发错误没被采到；或只在入口采 Span，跨服务上下文没透传，链是断的。修复：错误与高延迟请求优先保留采样；透传问题回埋点侧逐服务核查，不要指望后端拼断链。

场景五：并行上了两套指标体系。同故障两边都告警、口径还不一样。处置见 3.3 节：选定一套为权威，另一套限期下线，过渡期只认权威侧告警。发现双写先停非权威侧通知路由，再排迁移计划。

## 六、生产环境最佳实践与安全建议

第一，告警数量要做预算。值班周期内需人工动作的告警长期两位数，问题不在值班人，在告警体系本身，按 3.6 节月度评审持续做减法，把人力留给真正的 P1。

第二，分级与值班表同源维护。分级、接收人、升级路径与值班表放在同一份受控文档，任一项变更同步其余项并留记录；人员交接后先跑一遍第四节演练脚本，验过再算交接完成。

第三，监控系统自身也要被监控。Prometheus、Alertmanager、Loki 与 Collector 都会坏，用独立于主链路的外部探针检查其健康接口，主监控全挂时至少还有通道告诉你「监控挂了」。

第四，配置与手册纳入版本管理。告警规则、Alertmanager 配置、抑制规则与 runbook 统一进版本库，变更写清原因与工单；密码类配置沿用第 2 章做法走独立文件引用，不写明文。

第五，遥测数据访问收口。Grafana、Alertmanager 与追踪后端只对运维网段开放，禁止裸露公网；日志与追踪可能含用户标识与业务数据，查询权限按最小必要授予，敏感字段在采集侧脱敏（见第 3 章与 3.2 节），不要等落库后补救。

第六，复盘行动项要有闭环。每月检查历史复盘行动项完成情况，超期未完成的重新评估或升级；同类故障第二次发生时，先回看上次行动项是否真的落地。
