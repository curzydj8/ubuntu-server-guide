# 端口开放：三重门

## 一、概述与使用场景

游戏服务端进程启动成功，不等于玩家能连进来。外网的一个连接请求要依次穿过三道门：第一道是云厂商安全组（机房层面的网络防火墙），第二道是 Ubuntu 本机的 UFW 防火墙，第三道是游戏服务端自己的监听绑定地址。任意一道门关着，玩家端看到的都是同一句「连接超时」或「无法连接服务器」，这正是开服排错最容易乱成一团的原因：现象只有一个，病因却有三层。

不配好这三道门的后果很具体：服务端日志一切正常、本机回环测试也能连，唯独外网玩家进不来；更隐蔽的是协议开错——Minecraft Java 版走 TCP，而 Palworld 走 UDP，在安全组里只放行了 TCP 25565 却漏了 UDP 8211，Palworld 就会永远搜不到服务器。本章给出一套固定顺序：先开安全组、再开 UFW、最后确认绑定地址，再用同一套命令逐层验证，以后任何「连不上」都按这个顺序查，不靠猜。

适用场景包括：云服务器上首次开服、换了新游戏或新端口后补放行、从家里内网迁移到云上、以及帮朋友远程排障时需要一份可复述的定位清单。

## 二、环境准备与前置条件

- 系统：Ubuntu 22.04 LTS 或 24.04 LTS，云服务器或有公网 IP 的主机。
- 权限：拥有云厂商控制台账号（能改安全组），且本机有 `sudo` 权限。
- 已知信息：服务器公网 IP（下文示例统一写作 `198.51.100.10`）、要开放的游戏端口与协议。
- 工具：系统自带 `ss`、`ufw`，外网测试可用另一台设备或手机热点网络。

端口与协议先列清楚，后面所有操作都照这张表执行：

| 游戏 | 默认端口 | 协议 | 用途 |
| --- | --- | --- | --- |
| Minecraft Java 版 | 25565 | TCP | 游戏主连接 |
| Palworld | 8211 | UDP | 游戏主连接 |
| Palworld RCON（可选） | 25575 | TCP | 远程管理，仅限管理 IP 访问 |

!!! warning "TCP 与 UDP 不能互相代替"
    安全组和 UFW 里的协议必须与游戏实际使用的协议一致。给 UDP 游戏只放行 TCP，等于没放行；反过来也一样。拿不准时查游戏官方文档，不要两个协议一起全开来碰运气。

## 三、手把手操作步骤

### 第一步：云厂商安全组放行入站

安全组是云厂商在虚拟机之外的一层防火墙，规则默认拒绝所有入站流量，必须手动添加放行规则。阿里云与腾讯云的菜单名称不同，但要点完全一致：进入「云服务器 ECS / 轻量应用服务器」控制台 → 选中目标实例 → 找到「安全组」或「防火墙」页签 → 添加入站规则，每条规则填四要素：协议类型、目的端口、授权对象（来源）、策略为允许。

以放行 Minecraft 为例添加第一条：协议选自定义 TCP，目的端口填 `25565/25565`，授权对象填 `0.0.0.0/0`（表示任意公网来源，游戏服面向朋友开放时这样填），策略选允许，优先级取默认，备注写明 `minecraft-game` 便于日后清理。再以同样方式添加 Palworld 的规则：协议选自定义 UDP，目的端口填 `8211/8211`，授权对象 `0.0.0.0/0`，备注写 `palworld-game`。

操作要点：阿里云在安全组规则列表里点「手动添加」，方向选「入方向」；腾讯云轻量服务器在「防火墙」页签点「添加规则」，云服务器 CVM 则在安全组里点「添加规则」。保存后规则通常数秒内生效，无需重启实例。若同一实例绑了多个安全组，任一安全组拒绝都可能拦住流量，排障时逐个检查。

!!! note "RCON 等管理端口不要对全网开放"
    像 Palworld RCON 25575/TCP 这类管理端口，授权对象只填你自己的出口 IP，例如 `198.51.100.20/32`，不要填 `0.0.0.0/0`。游戏端口对玩家开放，管理端口只对自己开放，这是两条不同的安全边界。

### 第二步：UFW 放行对应端口

安全组放行后，再处理本机防火墙。先备份当前规则状态以便回退查看，然后逐条放行：

```bash
sudo ufw status verbose > /tmp/ufw-before.txt
sudo ufw allow 25565/tcp comment 'minecraft'
sudo ufw allow 8211/udp comment 'palworld'
sudo ufw allow 22/tcp comment 'ssh'
sudo ufw enable
```

注意顺序：务必先放行 22/TCP 的 SSH 再启用 UFW，否则可能把自己锁在服务器外面。已经启用过 UFW 的机器直接追加规则即可，规则即时生效。用下面的命令判读结果：

```bash
sudo ufw status verbose
```

期望看到类似输出（节选关键行）：

```text
Status: active
Default: deny (incoming), allow (outgoing), disabled (routed)

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    Anywhere    # ssh
25565/tcp                  ALLOW IN    Anywhere    # minecraft
8211/udp                   ALLOW IN    Anywhere    # palworld
```

判读方法：`Status` 必须是 `active`；每条游戏规则的 `Action` 必须是 `ALLOW IN`；协议后缀 `/tcp`、`/udp` 必须与游戏一致，只显示端口号不带协议后缀表示 TCP 与 UDP 都放行了，与计划不符时用 `sudo ufw delete allow <端口>` 删掉重加。

### 第三步：确认应用绑定 0.0.0.0

最后一道门在应用自身：服务端如果只监听 `127.0.0.1`，它只接受本机连接，安全组和 UFW 开得再全，外网也连不进来；监听 `0.0.0.0` 才表示接受所有网卡上的入站连接。

Minecraft 在服务端目录的 `server.properties` 中控制绑定：

```bash
cd /home/steam/minecraft
cp -a server.properties server.properties.bak
nano server.properties
```

关键两行这样设置（`server-ip` 留空即监听全部地址，这是最常见的正确写法）：

```ini
server-ip=
server-port=25565
```

Palworld 通过启动参数指定端口，绑定行为由服务端默认监听全部地址，启动命令中明确写出端口即可：

```bash
/home/steam/palworld/PalServer.sh -port=8211 -players=16
```

其它游戏同理：凡是配置文件或启动参数里出现 `bind`、`host`、`listen`、`server-ip` 字样的选项，都不要填 `127.0.0.1` 或 `localhost`，要么留空，要么填 `0.0.0.0`。

## 四、效果验证与测试

第一层验证看监听。在服务器上执行：

```bash
ss -tulnp | grep -E '25565|8211'
```

期望输出示例：

```text
tcp   LISTEN 0  4096   0.0.0.0:25565   0.0.0.0:*   users:(("java",pid=2143,fd=58))
udp   UNCONN 0  0      0.0.0.0:8211    0.0.0.0:*   users:(("PalServer-Linux",pid=2210,fd=27))
```

关键看本地地址列：出现 `0.0.0.0:端口` 说明第三道门已开；出现 `127.0.0.1:端口` 说明只监听本机，立即回第三步改绑定；完全没有这一行，说明服务端进程根本没起来或端口配错，先看服务端日志。普通用户看不到进程名时加 `sudo` 再查。

第二层验证从外网测连通性。TCP 端口可在任意外网设备上测试：

```bash
nc -vz 198.51.100.10 25565
```

期望输出 `Connection to 198.51.100.10 25565 port [tcp/*] succeeded!`。没有 `nc` 时可用在线端口检测工具，输入公网 IP 与端口做 TCP 检测。UDP 没有连接握手，无法用同样方法确认，最可靠的办法是让玩家用游戏客户端直连 `198.51.100.10:8211` 实测，同时在服务器上抓包确认有没有流量到达：

```bash
sudo tcpdump -ni any udp port 8211 -c 5
```

玩家尝试连接时能抓到数据包，说明前两道门已通、问题在服务端本身；一个包都抓不到，说明流量还卡在安全组或 UFW。

## 五、常见错误与排坑指南

**场景 1：本机能连，外网超时，`ss` 显示 127.0.0.1。** 报错现象是玩家端提示连接超时，服务端日志无任何连接记录。原因是服务端绑定地址被填成了 `127.0.0.1`，只监听回环。修复：改配置前先备份，再把绑定改为空或 `0.0.0.0` 并重启服务端：

```bash
cp -a server.properties server.properties.bak2
sed -i 's/^server-ip=.*/server-ip=/' server.properties
```

**场景 2：安全组只开了 TCP，Palworld 搜不到服务器。** 玩家在游戏内输入地址后长时间无响应，`tcpdump` 抓 UDP 8211 一个包都没有。原因是 Palworld 走 UDP，而安全组与 UFW 只放行了 TCP。修复是把两处都补上 UDP 规则：

```bash
sudo ufw allow 8211/udp comment 'palworld'
sudo ufw status | grep 8211
```

同时回云控制台确认存在 UDP 8211 的入站放行规则，缺失就按第一步补加。

**场景 3：UFW 规则写错协议后缀。** 执行过 `sudo ufw allow 8211` 后以为已放行，实际该写法默认只放行 TCP。`sudo ufw status` 中该行显示为 `8211 ALLOW IN` 而非 `8211/udp`。修复：删掉错误规则再按正确协议重加：

```bash
sudo ufw delete allow 8211
sudo ufw allow 8211/udp comment 'palworld'
```

逐层定位表收尾，任何连不上都按此表从上往下查：

| 层级 | 检查命令或位置 | 正常状态 | 异常时处理 |
| --- | --- | --- | --- |
| 安全组 | 云控制台入站规则 | 有对应协议与端口的允许规则 | 补加规则，核对实例绑定 |
| UFW | `sudo ufw status verbose` | active 且有 ALLOW IN | 补放行或修正协议后缀 |
| 绑定地址 | `ss -tulnp` | 本地地址为 0.0.0.0:端口 | 改配置绑定并重启服务端 |
| 进程存活 | `ss` 有监听且日志无报错 | 进程在跑、端口一致 | 先修服务端启动错误 |

### 回滚：关闭已开放的端口，恢复变更前状态

下线游戏、临时开放到期或放行错了端口时，按开门的相反顺序逐项关闭：先 UFW、再安全组、最后验证。三道门只要重新关上一道，外网就已不可达；但要恢复到变更前的干净状态，三处都要处理，只删一处会留下日后没人记得的残规则。

**第一步：删除 UFW 规则。** 先看带编号的现状，再逐条删本章加过的游戏规则（当时开了 RCON 的一并删 25575/tcp）。**22/tcp 的 SSH 规则不在回滚范围内，删它会把自己锁在服务器外面**：

```bash
sudo ufw status numbered
sudo ufw delete allow 25565/tcp
sudo ufw delete allow 8211/udp
sudo ufw delete allow 25575/tcp
```

最后一条 RCON 没开过时执行会报错说规则不存在，忽略即可。删完与第三步变更前留存的快照对照，应当完全一致：

```bash
sudo ufw status verbose > /tmp/ufw-after.txt
diff /tmp/ufw-before.txt /tmp/ufw-after.txt
```

`diff` 无输出即表示 UFW 已回到开放端口之前的状态。

**第二步：删除安全组规则。** 回云厂商控制台的安全组/防火墙页签，按备注 `minecraft-game`、`palworld-game` 逐条删除对应的入站放行规则；实例绑了多个安全组的逐个检查，不要只删当前页签看到的那个。

**第三步：验证外网已不可达。** 在外网设备上重测 TCP 端口，期望从第四节的 `succeeded!` 变为连接超时或被拒绝：

```bash
nc -vz 198.51.100.10 25565
```

同时请一位玩家再连一次 UDP 游戏，服务器上 `sudo tcpdump -ni any udp port 8211 -c 5` 应一个包都抓不到。注意此时服务器本机 `ss` 仍能看到游戏进程在监听，这是正常的——进程还在，只是三道门关了；若是整个游戏下线，再停掉游戏服务端进程本身。收尾逐项核对：

| 项目 | 回滚动作 | 确认方式 |
| --- | --- | --- |
| UFW 游戏规则 | `ufw delete allow` 逐条删除 | `ufw status` 无 25565、8211、25575 行，与 `/tmp/ufw-before.txt` 对照一致 |
| 安全组入站规则 | 控制台按备注删除 | 规则列表里查不到对应端口与协议 |
| SSH 规则 | 不动 | `ufw status` 中 22/tcp 仍为 ALLOW IN，自己仍能 SSH 登录 |
| 外网连通性 | 无需动作，被动验证 | 外网 `nc` 失败、玩家连不上、`tcpdump` 抓不到包 |

## 六、生产环境最佳实践与安全建议

只开放确有游戏在用的端口，关服或下线游戏时同步删除安全组与 UFW 里的对应规则，减少暴露面。管理类端口（RCON、面板、数据库）一律限制来源 IP 或只监听本机，再通过 SSH 隧道访问。为每条规则写清备注，注明游戏名与添加日期，半年复查一次。不要为了省事关闭 UFW 或把安全组设为全端口放行，一旦服务端程序出现漏洞，全网扫描器几分钟内就能找上门。最后，把本章的三层检查写成开服习惯：每次改完网络配置，先 `ss` 看监听、再外网测连通、最后请一位玩家实连确认，三步全过才算交付。
