# 第 13 部分：AI 工具与智能化运维

当服务器规模从一两台增长到几十台，靠人工逐台登录、逐条敲命令的运维方式很快就会遇到瓶颈：日志看不过来、配置改不一致、故障复盘全凭记忆。本部分介绍如何把 AI 工具与基础设施即代码（IaC）引入 Ubuntu Server 的日常运维——让本地大模型成为离线可用的排错助手，让云端 AI CLI 加速命令与脚本的起草，让 Ansible、Terraform 与 GitOps 把「一键构建标准生产基线」从口号变成可重复执行的流程。

## 每章一句话

- **01 本地大模型运维助手**：在服务器本地跑起 Ollama 与 Open WebUI，日志不出内网也能用 AI 帮忙读报错、理思路。
- **02 云端 AI CLI 助手辅助运维**：云端模型能力更强，但必须先立规矩——密钥只走环境变量、日志先脱敏、命令先审后跑。
- **03 IaC 与 GitOps 深化**：把基线写成 Ansible role 与 Terraform 代码，用 Git 管理变更，用巡检发现漂移，让每台新机器都长一个样。

## AI 辅助运维的总安全原则

无论使用本地模型还是云端服务，以下五条原则贯穿本部分全部章节，请先读完再动手：

1. **AI 给的是建议，不是命令。** AI 生成的任何命令、脚本、配置，都必须经过人工阅读理解后才能执行；看不懂的命令不执行，先查 `man` 手册或在测试机验证。
2. **敏感信息不进提示词。** 真实公网 IP、内网地址、主机名、API Key、密码、客户数据在粘贴给 AI（尤其是云端 AI）之前必须脱敏，方法见第 02 章的脱敏清单。
3. **密钥只走安全通道。** API Key 只通过环境变量或密钥管理工具注入，绝不写进脚本、配置文件并提交到 Git 仓库；示例中一律写作 `<api-key>` 占位。
4. **危险命令二次确认。** `rm`、`dd`、`mkfs`、`chmod 777` 等不可逆或高风险操作，即使由 AI 建议，也必须人工二次确认目标与参数，生产环境优先只读操作。
5. **变更走代码与流程。** 重要配置变更优先通过第 03 章的 IaC/GitOps 流程落地，保证可回滚、可审计，而不是在生产机上直接改完就忘。

!!! warning "先在测试机练，再上生产机"
    本部分涉及的模型服务、自动化工具都会真实修改系统状态。第一次操作请在虚拟机或测试机完成全流程，确认理解每一条命令的作用后，再应用到生产服务器。

读完本部分，你应能部署本地模型助手、规范使用云端 AI CLI，并用 IaC/GitOps 构建生产基线。
