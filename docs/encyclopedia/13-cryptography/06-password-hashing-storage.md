# 密码哈希与口令存储

> 本篇是[哈希与数字签名](02-hash-signature.md)的深挖篇，只讲防御侧：口令应该怎么存才安全。
> 本篇不讲任何口令破解的操作步骤与工具用法，不讲如何针对他人系统做口令猜测。
> 总览里的原则（口令绝不明文存、不用普通快哈希存）在这里展开为可落地的参数与做法。

## 1. 技术原理

### 1.1 口令存储要解决的问题

验证口令时，服务端其实不需要“知道”口令原文，只需要能在用户下次输入时判断“这次输入的和当初设定的是同一个”。因此正确做法是只存一个**不可逆的验证值**，而不是原文，更不是可逆加密后的原文：加密能解密，密钥一旦泄露就等于原文泄露；哈希不可逆，验证值本身不能直接当口令用。

但“哈希”不等于“安全存储”。通用哈希（SHA-256、SHA-1、MD5）是为校验完整性设计的，算得越快越好——这恰恰是口令存储最忌讳的性质：验证值一旦泄露，猜测成本就由单次计算成本决定，快哈希意味着单位时间内可以尝试更多候选。口令存储专用函数反其道而行之：**故意算得慢、故意占用内存**，把“验证一次”的成本抬到对正常登录可接受、对批量猜测不可接受的水平。这类函数叫慢哈希（slow hash）或口令哈希函数，不要把它和总览里的通用哈希混为一谈。

### 1.2 盐值：每个口令一个、随机、公开存放也无妨

盐值（salt）是一个在哈希前混入口令的随机值，规则只有三条：

- **每个口令都不一样**：同一口令在不同用户、不同系统里算出的存储值也不同。
- **随机生成**：用密码学安全的随机数生成器产生，不要用用户名、时间戳、固定字符串凑数。
- **盐值本身不是秘密**：它通常和哈希结果一起存放。它的作用不是“藏起来”，而是让“算一次、对所有用户通用”的预计算失去意义——每个口令都必须按自己的盐值单独算一遍。

没有盐值时，两个用户设了相同口令，存储值就相同，一眼就能看出来；加了盐值，相同口令也会存成不同结果。盐值不解决“口令本身太弱”的问题，它解决的是“批量”问题：把一次泄露的代价从“全库通用”降为“逐条单独算”。

### 1.3 慢哈希为什么要“慢”和“占内存”

慢哈希有两个成本维度，对应两种防御：

- **时间成本（迭代/轮数）**：一次验证要做多少轮运算。轮数越高，单次验证越慢。正常登录一天不过几次，慢 0.1–1 秒用户无感；批量猜测要乘以百万次，成本就上去了。
- **内存成本（内存硬度，memory-hard）**：一次验证要占用多少内存。只靠时间成本的函数（如 PBKDF2）可以用高度并行的专用硬件把时间成本摊薄；内存硬度要求每个猜测都占用一块内存，并行规模就被内存总量卡住。Argon2id 与 scrypt 是内存硬的，bcrypt 有一定的内存占用但不如前两者，PBKDF2 不是内存硬的——这是选型时要看清的本质差异，不只是参数数字大小。

参数永远是**下限，不是目标**：硬件每年变便宜，今天够用的参数几年后就不够。做法是定期复核官方指南、在自己的服务器上实测登录延迟，然后在“用户可接受的延迟”内取尽可能高的参数（见第 6 节的升级做法）。

### 1.4 四种主流口令哈希函数

| 函数 | 定位 | 内存硬度 | 适用场景 |
|---|---|---|---|
| Argon2id | 首选（新系统默认） | 是 | 新系统无合规限制时默认选它 |
| scrypt | 备选 | 是 | Argon2id 不可用时 |
| bcrypt | 仅限存量系统 | 有限 | 已在用 bcrypt 的老系统，参数达标可继续用 |
| PBKDF2 | 合规场景 | 否 | 需要 FIPS-140 验证实现时 |

**Argon2id**（RFC 9106，2015 年口令哈希竞赛胜出者 Argon2 的混合变体）：前半程用与数据无关的内存访问（抗侧信道），后半程用与数据相关的访问（抗时间–内存权衡），兼顾两者。三个参数：内存 m（KiB）、迭代次数 t、并行度 p。注意 p 是把内存分到几条 lane 上并行算，**增大 p 不等于增大总内存**，也不要把 p 理解成迭代次数。

**scrypt**（RFC 7914）：三个参数 N（CPU/内存成本，必须是 2 的幂）、r（分组大小）、p（并行度），内存占用约与 N × r 成正比。参数要成套看，单独调一个没有意义。

**bcrypt**：基于 Blowfish 的口令哈希，成本参数 cost 是对数制的：cost 加 1，计算量翻一倍。它的输入上限是 72 字节（多数实现），超过部分会被截断——长口令/长口令短语用 bcrypt 前必须先确认实现的行为，不要假设“越长越安全”。

**PBKDF2**（RFC 2898）：用 HMAC 反复迭代的密钥派生函数，参数就是迭代次数与内部哈希。优点是实现最广、有 FIPS 验证版本；缺点是不是内存硬的，同等时间成本下抗并行猜测的能力弱于 Argon2id/scrypt，因此只在合规要求它时才选它，不要因为“熟悉”而在新系统里默认用它。

### 1.5 参数推荐值（核查过的下限，以官方发布为准）

下面两组 Argon2id 数值来源不同、用途不同，不要混为一谈：

- **OWASP《Password Storage Cheat Sheet》给出的交互式登录下限**（本节核查时该页的现行值）：以下五组被视为同等防御水平，只是 CPU 与内存的权衡不同，任选其一作为下限，不要低于其中任何一组：

| m（内存） | t（迭代） | p（并行度） |
|---|---|---|
| 47104 KiB（46 MiB） | 1 | 1 |
| 19456 KiB（19 MiB） | 2 | 1 |
| 12288 KiB（12 MiB） | 3 | 1 |
| 9216 KiB（9 MiB） | 4 | 1 |
| 7168 KiB（7 MiB） | 5 | 1 |

其中最常被引用的一组是 m=19456 KiB、t=2、p=1。OWASP 同时强调：在自己的服务器上实测，单次验证耗时以低于 1 秒为一般原则，并根据负载调整。

- **RFC 9106 给出的通用默认选项**（不针对某个登录场景裁剪，更保守）：首选 Argon2id，t=1、p=4、m=2 GiB、盐值 128 位、输出 256 位；内存受限时的次选是 t=3、p=4、m=64 MiB、同样盐值与输出长度。这两组是“不针对硬件裁剪也安全”的默认值，交互式登录按 OWASP 下限起步、按实测往上调，与 RFC 默认并不矛盾：一个是下限，一个是通用默认。

其他函数的 OWASP 下限（同样是下限，不是推荐目标）：

| 函数 | 下限 |
|---|---|
| scrypt | N=2^17、r=8、p=1（约 128 MiB）；或 N=2^16、r=8、p=2 等同等水平组合 |
| bcrypt | 成本参数不低于 10，且口令输入不超过 72 字节 |
| PBKDF2 | HMAC-SHA-256 不低于 600,000 次迭代；HMAC-SHA-512 不低于 220,000 次迭代 |

所有参数都会随硬件与指南更新而变化：**本文的数字以 2026-11-04 核查时的官方页面为准，落地前请以 OWASP 与 RFC 的最新发布为准**（见文末未完成项）。

### 1.6 胡椒（pepper）：纵深防御，不是替代品

胡椒是一个**全库共用、不随哈希存放**的秘密值，存放在与口令数据库分离的地方（如密钥保管服务、HSM）。它的防御场景很窄：只有数据库泄露、但胡椒没有同时泄露时才起作用。OWASP 的原话精神是：胡椒可作纵深防御，但单凭它没有任何安全特性——没有它，合格的盐值加慢哈希已经成立；有了它，也不能因此调低慢哈希参数。

胡椒换起来代价很大：它一旦更换，旧胡椒保护的哈希全部失效，只能等用户下次登录时重算，或强制用户重置口令。因此上胡椒前要先想好轮换预案，不要把它当成“加了就不用管”的配置。

### 1.7 常见错误做法（只列结论，不展开攻击手法）

- 明文存储、或用可逆加密“代替”哈希。
- 用 MD5、SHA-1、SHA-256 等通用快哈希直接存口令，或只做一轮、少轮迭代。
- 全库共用一个盐值，或盐值可预测、重复使用。
- 把成本参数写死在代码里多年不复核，硬件变便宜了参数却没跟上。
- 校验时用普通字符串相等比较：要用恒定时间比较，防止时序信息泄露比对进度（各语言标准库都有现成函数，直接用，不要自己写循环比对）。

## 2. 合法研究范围

本篇只讨论**自己负责的系统**的口令存储设计：自己的应用、自己的数据库、自己的测试账号。未授权测试他人系统、尝试登录他人账号、利用泄露的口令数据库做任何事，都是违法行为，本文不提供相关指导。实验一律用自己生成的测试口令，不要用真实账号口令做演示。

## 3. 实验环境

- 环境：代理 VM 本机，Python 3.12.3 标准库（`hashlib`），OpenSSL 3.0.13；全部为自有测试数据，无真实用户、无真实口令。
- 软件与版本：Python 3.12.3（`hashlib.pbkdf2_hmac`、`hashlib.scrypt`）、OpenSSL 3.0.13。VM 上没有安装 Argon2 与 bcrypt 的库，因此 Argon2/bcrypt 的代码片段为**示例未实测**（见第 4 节说明），不要把它当成跑通过的命令。
- 权限要求：无需特殊权限；演示口令均为现场生成的测试值，实验后不留存。

## 4. 风险

- **数据库泄露后口令仍可被逐条猜测**：慢哈希只能抬高成本，不能让弱口令变强。规避：参数取高限 + 提示用户用长口令 + 对已泄露口令做筛查（见第 6 节）。
- **参数过高导致登录被拖垮**：验证太慢会在登录高峰变成拒绝服务。规避：实测单次耗时与并发下的内存占用（Argon2id 的内存参数乘以并发数就是峰值内存），设上限与超时。
- **胡椒与盐值混淆**：把胡椒当盐值存进数据库，或把盐值当秘密藏起来。规避：盐值随哈希存、每口令不同；胡椒全库共用、与数据库分离存放。
- **实现细节出错**：截断（bcrypt 72 字节）、空字节、编码不一致（口令先转什么编码再哈希）都会让“存进去的”和“验证时算的”对不上，或悄悄削弱口令。规避：用成熟库的整套生成/验证函数，不要自己拼接盐值与哈希格式。

## 5. 检测方式

只讲服务端自查，不讲针对他人的探测：

- **存储格式自查**：抽查数据库里的口令字段——应为慢哈希函数的标准编码格式（含算法标识、参数、盐值、哈希值），出现明文、可逆加密密文、裸 MD5/SHA-256 十六进制串即为不合格。
- **参数自查**：解析存储值里的参数，与第 1.5 节的下限逐项比对；低于下限的记为待升级（不要等用户登录才发现，全库扫描一次就有清单）。
- **盐值自查**：同一口令在不同用户下应存成不同值；全库出现重复盐值，或盐值为空/固定值，即为缺陷。
- **日志与告警**：登录验证失败率突增、验证耗时异常升高，都应告警——前者可能是异常登录尝试，后者可能是参数或并发配置出了问题。

## 6. 修复与防御方法

### 6.1 新系统：默认 Argon2id，按实测调参

1. 选 Argon2id，用成熟库自带的生成/验证函数（库会自动生成盐值、编码参数，不要自己拼格式）。
2. 起步不低于 OWASP 下限（如 m=19456 KiB、t=2、p=1），在目标服务器上实测单次验证耗时与并发内存，往“低于 1 秒且内存可承受”的方向调高。
3. 校验用库提供的恒定时间验证函数，不要自己写相等比较。

### 6.2 存量系统：不要等用户登录才升级

- 参数偏低但算法本身合格（如 bcrypt 成本为 10 以下、PBKDF2 迭代不足）：用户下次成功登录时，用新参数重算并替换存储值；长期不登录的账号，评估后强制重置，不要让低参数哈希无限期留在库里。
- 算法本身不合格（如通用快哈希、无盐值）：不能“在旧哈希外面再包一层新哈希”就当作修好了——要按迁移方案处理：用户下次登录时用旧方式验证通过后，立即按新方式重存；无法验证的旧值到期清理。迁移细节以官方指南为准（待核实，见未完成项）。

### 6.3 配套防御（口令存储之外的必选项）

- 登录限流与失败锁定策略、异常登录告警（属于应用层防护，不在本篇展开）。
- 泄露口令筛查：新口令设定时，比对公开泄露口令库，命中则要求换一个（只比对“是否在泄露库里”，不要记录用户口令原文）。
- 多因素认证：口令只是第一因素，重要系统必须叠加第二因素——口令存储做得再好，也防不住用户在别处复用同一口令。

### 6.4 实测过的示例（Python 标准库，演示参数非生产参数）

下面是本机真实运行过的代码，环境见第 3 节。注意：演示为了跑得快把 PBKDF2 迭代次数降到了 1000，**生产必须用第 1.5 节的 600,000 次（HMAC-SHA-256）**，演示数字绝不能照抄到生产。

```python
import hashlib, hmac, os

pw = b"demo-password-not-a-real-account"  # 测试值，非真实口令
salt = os.urandom(16)                      # 每次随机生成，生产由库自动生成
dk = hashlib.pbkdf2_hmac("sha256", pw, salt, 1000, dklen=32)  # 演示用 1000 次
print(len(dk), len(salt))                  # 实测输出：32 16
print(hmac.compare_digest(dk, hashlib.pbkdf2_hmac("sha256", pw, salt, 1000, dklen=32)))    # 实测：True
print(hmac.compare_digest(dk, hashlib.pbkdf2_hmac("sha256", b"wrong", salt, 1000, dklen=32)))  # 实测：False
dk2 = hashlib.scrypt(pw, salt=salt, n=16384, r=8, p=1, dklen=32)
print(len(dk2))                            # 实测输出：32
```

实测结果：PBKDF2 输出 32 字节、盐值 16 字节，正确口令验证通过、错误口令验证不通过，scrypt 输出 32 字节。Argon2 与 bcrypt 因 VM 未装对应库未实测，下列为**示例未实测**，仅示意参数位置，落地前须在目标环境跑通并以库文档为准：
