# TLS 与证书体系原理

> 本篇只讲原理。服务器上怎么申请、安装、续期证书，是操作层面的内容，归 10 域后续展开，不在本篇写步骤；应用层面的证书管理见[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)。

## 1. 本章目标

读完本篇，能说清一次 HTTPS 连接建立时发生了什么、浏览器凭什么相信“这个网站就是它自称的那个网站”，以及证书透明机制是在防谁。

## 2. 背景与问题

HTTP 本身是明文协议：请求与响应在网络上裸奔，路上任何一个节点都能看、能改。TLS（传输层安全协议，前身 SSL）就是给 HTTP 加的一层“密封 + 身份验证”：内容加密防偷看，证书认证防冒充，完整性校验防篡改。三个目标缺一不可——只加密不认证，中间人可以冒充服务器和你谈一次加密会话，你的数据照样被看光。

TLS 要同时解决三个子问题：双方怎么在公开信道上协商出会话密钥？服务器怎么证明自己的身份？协商好的密钥怎么保证“这次会话专用、日后泄露也不连累旧会话”？

## 3. 总体架构

一次 TLS 连接涉及四方（前三方在握手里出现，第四方在事后审计里出现）：

```
客户端 ──握手──▶ 服务器（出示证书）
   │                │
   │         证书链：叶证书 → 中间 CA → 根 CA（信任锚）
   │                │
   └──── 会话密钥 ──┘（对称加密后续全部数据）
证书透明日志（公开账本，事后可审计 CA 的每一次签发）
```

- **记录层**：握手完成后，全部应用数据经对称密码（AEAD）加密传输。
- **握手层**：协商版本与算法、认证服务器身份、协商会话密钥。
- **证书体系（PKI）**：CA 负责签发证书，信任锚是预装在操作系统与浏览器里的根证书；证书透明（CT）日志是公开账本，记录每一次公开信任证书的签发。

## 4. 工作机制

### 4.1 TLS 1.3 握手思想（RFC 8446，2018 年）

TLS 1.3 把握手压缩到 1 个往返（1-RTT），步骤的思想是：

1. **ClientHello**：客户端发来支持的版本、算法列表、一个临时的密钥协商参数（(EC)DHE 公开值），以及一个随机数。
2. **ServerHello + 证书 + 完成**：服务器选定版本与算法，发回自己的密钥协商参数、证书（证明“这个公钥属于这个域名”）、以及用协商出的密钥算出的 Finished 验证值。
3. **客户端验证**：验证证书链（见 4.3 节），验证 Finished，确认双方算出的会话密钥一致；随后发回自己的 Finished，握手完成。

之后的数据全部用会话密钥对称加密。TLS 1.2 的握手是 2 个往返且算法协商更复杂；新部署应优先 TLS 1.3，TLS 1.2 只作为兼容保留。TLS 1.3 还删掉了一批不安全的老算法与静态 RSA 密钥协商——这是“少给选择就少出错”的设计取舍。

### 4.2 前向保密：为什么每次会话的密钥都不同

握手里的密钥协商用 (EC)DHE：双方各生成一次性的临时参数，协商出会话密钥后立即丢弃临时参数。这意味着：

- 会话密钥只属于这次会话，不重复使用。
- 即使服务器的长期私钥（证书私钥）日后泄露，攻击者也无法由私钥反推过去会话的密钥——因为会话密钥从来不是由长期私钥算出来的，长期私钥只在握手里用来**签名认证**，不用来加密会话密钥。

这就是前向保密（Forward Secrecy）。没有它的旧做法（静态 RSA 密钥协商：客户端用服务器公钥加密会话密钥发过去）一旦私钥泄露，历史流量可批量解密——TLS 1.3 删掉静态 RSA，正是为此。

### 4.3 证书链验证：从叶证书走到信任锚

浏览器收到服务器证书后，按链逐级验证：

1. **叶证书**：主体是域名，内含服务器公钥与有效期，由中间 CA 签名。
2. **中间 CA 证书**：由根 CA 签名，证明这个中间 CA 有权签发证书。
3. **根 CA 证书**：自签名，预装在操作系统与浏览器的信任库里，这就是**信任锚**——链条在这里停下，不再需要上一级证明。

验证内容包括：每级签名是否正确、主体名称是否匹配、有效期是否在内、证书用途字段是否允许作服务器认证、以及是否被吊销。任何一环失败，浏览器就拒绝连接并告警。注意信任锚本身不是被“证明”出来的，而是你（通过操作系统与浏览器厂商）**选择信任**的起点；信任库里的根 CA 被攻破或作恶，整条链的根基就动摇了——这正是下一节要防的事。

### 4.4 证书透明：给 CA 的签发行为记公开账

证书体系的软肋是：任何一家受信任的 CA 都可以给任何域名签发证书。如果某家 CA 被攻破或误发一张假证书，攻击者就能冒充任意网站，而受害者毫无察觉。证书透明（CT，RFC 6962）用一本公开账本来堵这个洞：

- CA 每签发一张公开信任证书，必须把它记入公开的 CT 日志（只追加、不可篡改、可公开审计）。
- 浏览器要求服务器出示“证书已记入日志”的证明（SCT），否则拒绝或告警。
- 域名所有者可以监视日志，一旦发现有人给自己的域名签了未授权的证书，立刻能发现并要求吊销。

CT 不阻止误发，它让误发**无法悄悄发生**。信任从“相信 CA 不会犯错”变成了“CA 犯错会被所有人看见”。

## 5. 关键设计取舍

- **1-RTT 与安全的平衡**：TLS 1.3 允许 0-RTT 恢复会话（用上次的密钥直接发数据，省一次往返），但 0-RTT 数据可能被重放攻击——重放一段“转账请求”会造成重复执行。因此 0-RTT 只适合幂等请求（例如普通 GET），不适合任何会改变状态的操作。
- **证书有效期持续缩短**：公开信任证书的有效期近年来在持续缩短，趋势是逼着持有人自动化续期——有效期越短，私钥泄露或误发证书的危害窗口越小，代价是运维必须自动化（手动续期会频繁断档）。
- **集中信任 vs 去中心化**：根 CA 体系把信任集中在几十家机构上，管理简单但单点风险大；CT、证书固定（HPKP 已废弃）、多视角验证等机制，都是在不推翻体系的前提下给集中信任加制衡。

## 6. 分类与变体

| 类别 | 一句话特征 |
|---|---|
| TLS 1.3（RFC 8446） | 当前主流，1-RTT、前向保密、删掉不安全老算法 |
| TLS 1.2（RFC 5246） | 上一代，2-RTT，兼容保留，新部署不优先 |
| 单向 TLS（常见 HTTPS） | 只认证服务器，客户端匿名 |
| 双向 TLS（mTLS） | 双方都出示证书互认证，用于服务间调用、设备接入 |
| 公开信任证书 | 由信任库内 CA 签发，浏览器默认接受 |
| 自签名证书 | 自己给自己签名，不在公开信任库内，浏览器会告警，只适合内网与测试 |

## 7. 应用与限制

- **HTTPS**：Web 的默认传输保护；浏览器地址栏的小锁只表示“连接加密且证书链验证通过”，不表示网站内容可信——钓鱼网站同样可以拿到有效证书。
- **非 Web 场景**：邮件传输、数据库连接、API 调用、物联网设备联网，同样用 TLS（或 mTLS）保护传输。
- **限制**：TLS 只保护传输途中，不保护端点——服务器本身被攻破、用户设备中了恶意软件，TLS 帮不上忙；TLS 不审查内容真假；私钥保管、证书续期、吊销检查是应用层必须做对的事，做错任何一个都会让握手本身的正确性打折扣。
- **本篇边界重申**：证书申请、安装、续期的具体操作步骤不在本篇，归 10 域后续；应用层面的生命周期管理见[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)。

## 8. 常见误解

- **误解：有小锁就是可信网站**：小锁只证明连接加密且证书属于该域名，不证明域名背后的人可信。`https://` 开头的钓鱼站同样有小锁。
- **误解：TLS 加密了就万事大吉**：端点安全、应用漏洞、钓鱼、恶意软件都不在 TLS 的保护范围里。
- **误解：证书越贵越安全**：公开信任证书的安全性来自同一套链验证机制，价格差异主要在验证流程与保险条款，不在密码强度上。
