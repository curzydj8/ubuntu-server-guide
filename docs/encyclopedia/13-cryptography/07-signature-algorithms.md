# 数字签名算法详解

> 本篇是[哈希与数字签名](02-hash-signature.md)的深挖篇。总览讲了“先哈希、再签名”的流程与三者的分工，
> 本篇展开三者各自是怎么签、参数怎么选、用错会在哪里出事。不重复总览的证书链与信任传递内容，
> 证书怎么用这些签名，见[TLS 与证书体系原理](03-tls-pki.md)。

## 1. 本章目标

读完本篇，能说清 RSA-PSS、ECDSA、EdDSA 各自的签名与验证在算什么、各自的关键参数是什么、
以及选型与实现时最容易踩的坑（随机数、填充、编码、哈希匹配）。

## 2. 背景与问题

总览的签名流程只有两步：哈希、再用私钥对摘要做签名运算。但“签名运算”本身有三种主流做法，
安全性来源完全不同：RSA 靠大整数分解困难，ECDSA 靠椭圆曲线离散对数困难，EdDSA 靠 Edwards 曲线上的
Schnorr 型构造。把三者混为一谈、或只看“密钥长度”选型，都会选错：256 位 ECDSA 私钥与 256 位 RSA 私钥
的安全强度天差地别（见[对称与非对称密码](01-symmetric-asymmetric.md)第 3.5 节的强度对照表）。

三种算法在 FIPS 186-5《数字签名标准》（2023 年）里都是批准的签名算法：RSA、ECDSA 与 EdDSA；
同一标准把 DSA 降为仅可验证旧签名，不再用于新签名生成。新系统选型只在这三者里选，
不要再用 DSA、不要用无填充的“裸 RSA 签名”。

## 3. 总体架构

三种算法共用总览的流程，区别只在“私钥运算”那一步：

```
原始数据 ──哈希──▶ 摘要
摘要 ──私钥签名运算──▶ 签名值
签名值 + 原始数据 + 公钥 ──验证运算──▶ 通过 / 不通过

RSA-PSS：  摘要 + 随机盐 ──填充编码──▶ 私钥幂运算
ECDSA：    摘要 + 每签一次的秘密随机数 k ──椭圆曲线点运算──▶ (r, s)
EdDSA：    私钥确定性派生随机数 ──Edwards 曲线点运算──▶ (R, S)
```

共性提醒：签名不保密、不证明内容为真、不自带时间效力（总览第 4.4 节）；私钥泄露后，
攻击者就能以你的名义签任意内容，吊销与轮换见[密钥生命周期管理](10-key-lifecycle-management.md)。

## 4. 工作机制

### 4.1 RSA-PSS：给 RSA 签名加随机盐与填充

RSA 的私钥运算本身是“对一个数做私钥指数幂”。如果直接对摘要做这个运算（教科书式 RSA），
攻击者可以利用 RSA 的乘法同态性拼凑出新签名——这就是为什么**裸 RSA 签名绝不能用**，
必须先经过填充编码。现代标准填充是 PSS（Probabilistic Signature Scheme，RFC 8017《PKCS #1》第 9.1 节）。

PSS 的签名流程（思想层面，不展开全部编码字节）：

1. 对消息算哈希，得到摘要。
2. 生成一段随机盐（salt），把“8 个零字节 + 摘要 + 盐”再哈希一次。
3. 用掩码生成函数 MGF1 把上一步的哈希扩展成掩码，与盐拼接、填充，得到编码消息。
4. 对编码消息做私钥幂运算，得到签名值。

验证时反向操作：用公钥恢复编码消息、重算掩码与哈希，比对盐与摘要是否一致。
关键点有三：

- **每次签名盐都不同**：同一消息签两次，签名值也不同。这是故意的——随机化让签名不可预测，
  也是 PSS 与确定性签名的根本区别。不要因为“同一消息两次签名不一样”就怀疑实现坏了。
- **参数必须成套约定**：哈希函数、MGF1 用的哈希、盐长度、 trailer 字段。常见组合是
  “SHA-256 + MGF1-SHA-256 + 盐长等于哈希长度（32 字节）”。签发方与验证方参数不一致，
  验证就会失败——这不是算法坏了，是参数没对齐。OpenSSL 默认的 PSS 盐长行为以所用版本与
  命令参数为准，跨实现互通前必须先对齐参数（见第 7 节实测命令里显式写出的参数）。
- **不要再用 PKCS#1 v1.5 做新设计**：v1.5 是确定性填充，结构固定，历史上出过多次实现解析问题；
  FIPS 186-5 与现代指南都把 PSS 作为新应用的首选。存量系统里 v1.5 签名仍需验证时，
  验证要严格按规范解析，不要自己写宽松解析。

密钥长度按强度成套选：RSA-2048 约 112 比特强度、RSA-3072 约 128 比特强度（NIST SP 800-57 对照，
见 01 篇）。新系统直接按 128 比特选型，即 RSA-3072 起步；只在兼容性确实要求时才用 RSA-2048，
并记下它在 2030 年后的强度窗口问题（见未完成项）。

### 4.2 ECDSA：椭圆曲线版签名，随机数是命脉

ECDSA 是 DSA 在椭圆曲线上的版本（FIPS 186-5，另见 ANSI X9.62）。私钥是一个整数 d，
公钥是曲线上的点 Q = d·G（G 为基点）。签名流程（P-256 + SHA-256 为例）：

1. 对消息算哈希，取与曲线阶 n 位数相当的前缀作整数 z（P-256 配 SHA-256 时就是整个摘要）。
2. 选一个秘密随机数 k（1 ≤ k < n），算点 k·G，取其横坐标模 n 得 r。
3. 算 s = k⁻¹(z + r·d) mod n。签名值就是 (r, s) 这一对数。
4. 验证时用公钥 Q 与 (r, s) 重算一个点，比对横坐标是否等于 r——验证者不需要知道 d 与 k。

**k 是 ECDSA 全部安全性的命脉**，规则只有两条，但违反任何一条都是灾难：

- **每次签名 k 都必须不同**：同一 k 签两条不同消息，两组 (r, s) 联立就能直接解出私钥 d。
  历史上真实发生过：固定 k、随机数生成器故障导致 k 重复，都造成过私钥泄露。
  本文只讲这个结论与防御，不展开由签名值反推私钥的计算步骤。
- **k 必须均匀、不可预测**：k 即使不重复，但有偏差或部分比特可预测，积累足够多签名后
  同样可能泄露私钥（隐数问题）。不要用弱随机源、不要用时间戳或计数器凑 k。

防御做法就是 RFC 6979《确定性 DSA/ECDSA》：k 不再靠运行时的随机数生成器，
而是由私钥与消息哈希经 HMAC-DRBG 确定性派生。同一消息同一私钥永远得到同一签名，
不同消息自动得到不同 k，从根上消除了“随机数生成器出故障导致 k 重复”这一整类事故。
RFC 6979 生成的签名与普通 ECDSA 签名格式完全兼容，验证方不需要知道 k 是怎么来的。
现代库默认走确定性路线或高质量随机源时，不要自己再包一层随机数逻辑。

编码注意：ECDSA 签名在不同场合有两种编码——原始 (r, s) 各定长拼接（如 P-256 各 32 字节，
共 64 字节），与 ASN.1 DER 编码（两个整数的 SEQUENCE，P-256 通常 70–72 字节，长度随整数
前导零变化）。两者只是同一对数的不同装箱，互通前必须确认对方要哪一种；把 DER 签名
当成原始拼接去验证（或反过来）是最常见的“算法没错、验证总失败”原因。

曲线与哈希要成套：P-256 配 SHA-256、P-384 配 SHA-384、P-521 配 SHA-512。
哈希强度低于曲线强度时，整体强度由哈希决定；不要用 SHA-1 配任何新签名（SHA-1 已淘汰，
见总览第 4.1 节）。

### 4.3 EdDSA：确定性、快速、误用空间最小

EdDSA（RFC 8032）是 Edwards 曲线上的 Schnorr 型签名，两个标准化实例：

| 实例 | 曲线与内部哈希 | 公钥 | 签名 | 约略强度 |
|---|---|---|---|---|
| Ed25519 | Edwards25519，内部 SHA-512 | 32 字节 | 64 字节（R‖S） | 约 128 比特 |
| Ed448 | Edwards448，内部 SHAKE256 前 114 字节 | 57 字节 | 114 字节（R‖S） | 约 224 比特 |

签名流程（Ed25519 为例，思想层面）：

1. 私钥是 32 字节随机种子，对它算 SHA-512，前半部分经“钳制”（clamping，清除/固定若干比特）
   得到标量 a，后半部分作前缀（prefix）。
2. 公钥 A = a·B（B 为基点），编码为 32 字节。
3. 签名时随机数 r 由 prefix 与消息确定性派生（r = SHA-512(prefix‖消息)），算 R = r·B；
   再算 S = (r + SHA-512(R‖A‖消息)·a) mod ℓ（ℓ 为基点阶）。
4. 签名值就是 R 与 S 的拼接。验证时重算点并比对，不需要、也不应该知道私钥与 r。

EdDSA 相对 ECDSA 的三点优势，全部来自“确定性 + 结构简单”：

- **没有 ECDSA 的 k 事故**：随机数由私钥与消息确定性派生，不依赖运行时的随机数生成器质量，
  同一消息签名永远相同，但这不削弱安全性——签名本来就不需要保密。
- **验证规则可严格化**：RFC 8032 要求验证时拒绝 S ≥ ℓ 等非法值；实现必须做这些检查，
  宽松验证会让“看似通过”的签名在不同实现间行为不一致。
- **速度与体积**：Ed25519 签名与验证都快，公钥与签名都短（32/64 字节），适合证书、软件签名、
  SSH（OpenSSH 的 ssh-ed25519）等高频验证场景。

变体注意：RFC 8032 还定义了预哈希变体 Ed25519ph/Ed448ph（先对消息哈希再签，适合大消息流式处理）
与带上下文字符串的变体。**纯变体（PureEdDSA，无预哈希、无上下文）是默认与互通最广的选择**；
除非协议明确要求预哈希或上下文，否则不要混用变体——验证方按纯变体验证预哈希签名一定会失败，
反之亦然。上下文字符串为空与非空也是协议的一部分，必须两边一致。

### 4.4 三者对照

| 维度 | RSA-PSS | ECDSA | EdDSA |
|---|---|---|---|
| 安全基础 | 大整数分解 | 椭圆曲线离散对数 | Edwards 曲线离散对数（Schnorr 型） |
| 签名随机性 | 随机盐，每次不同 | k 必须每次不同（或 RFC 6979 确定性派生） | 确定性派生，无需运行时随机源 |
| 128 比特强度选型 | RSA-3072 | P-256 + SHA-256 | Ed25519 |
| 签名体积 | 与密钥同长（RSA-3072：384 字节） | P-256：DER 约 70–72 字节 | Ed25519：64 字节 |
| 签名速度 | 慢（私钥幂运算） | 中 | 快 |
| 验证速度 | 快 | 中 | 快 |
| 最易踩的坑 | 参数没对齐、误用 v1.5 | k 重复/偏差、DER 与原始编码混淆 | 变体（纯/预哈希/上下文）混用、验证不严格 |
| 典型场景 | 证书、兼容性要求高的旧系统 | TLS 证书、WebAuthn、区块链（secp256k1 非 NIST 曲线，见注） | SSH、现代证书与软件签名、TLS 1.3 可选 |

注：secp256k1 是 ECDSA 在比特币等系统里用的曲线，不在 FIPS 186-5 的 NIST 曲线（P-256/P-384/P-521）
之列；本文的曲线参数只覆盖 NIST 曲线与 RFC 8032 实例，secp256k1 的部署细节不在本篇范围内。

## 5. 关键设计取舍

- **随机化 vs 确定性**：RSA-PSS 故意随机化，同一消息签名不同；EdDSA 与 RFC 6979 ECDSA 故意确定性，
  同一消息签名相同。两者都安全，安全来自不同的地方：随机化靠盐不可预测，确定性靠派生过程
  不泄露私钥。不要用“两次签名是否相同”判断签名对错，要用验证是否通过判断。
- **密钥短 vs 生态广**：EdDSA 密钥最短、速度最快，但老旧硬件、HSM 与合规流程对 ECDSA/RSA 的支持
  更广。选型先看验证方支持什么，再看性能——签发方选了验证方不支持的算法，等于没签。
- **哈希与曲线/密钥成套**：强度由最短板决定。P-256 配 SHA-512 不会比配 SHA-256 更安全，
  RSA-3072 配 SHA-1 反而会把强度拉低到哈希的水平。选型表要整行看，不要单项拉满。
- **不要自造签名算法**：三种标准算法任选其一、按标准参数用，就是全部选项。把哈希换成自家函数、
  把填充改一改、把曲线参数换一组，都会立刻失去标准的安全论证，且验证方无法互通。

## 6. 分类与变体

- RSA 签名：RSASSA-PSS（新设计首选，RFC 8017）、RSASSA-PKCS1-v1_5（仅验证存量，见 4.1 节）。
- ECDSA：按曲线分 P-256、P-384、P-521（FIPS 186-5）；按 k 来源分随机 k 与 RFC 6979 确定性 k
  （签名格式相同，验证方无感知）。
- EdDSA：Ed25519（纯变体默认）、Ed448（更高强度）；预哈希变体 Ed25519ph/Ed448ph 与上下文变体
  只在协议明确要求时用。
- 不在本篇范围：后量子签名 ML-DSA（FIPS 204）、SLH-DSA（FIPS 205）——迁移是进行中的工程工作，
  见前沿域后续展开，不要把经典签名与后量子签名混为同一选型表。

## 7. 应用与限制

- **证书与 TLS**：服务器证书的签名算法就是三者之一；TLS 1.3 握手里服务器用证书私钥签名，
  客户端用证书公钥验证（见 03 篇）。证书选型错误（例如签发方与客户端支持的算法无交集）
  会直接导致握手失败。
- **软件与固件签名**：发布方私钥签名、用户公钥验证，Ed25519 因体积小、验证快而常用；
  RSA-PSS 因兼容性广而仍大量存在。
- **SSH 与 API 认证**：OpenSSH 支持 ssh-ed25519 与 ECDSA/RSA 密钥；API 请求签名多用 Ed25519
  或 ECDSA，验证方只认协议约定的那一种编码。
- **限制**：签名不保密、不证明内容为真、不自带时间效力；私钥保管、轮换、吊销是应用层必须补的课
  （见[密钥生命周期管理](10-key-lifecycle-management.md)）；量子计算在理论上威胁 RSA 与 ECC
  （Shor 算法），但需要大规模容错量子计算机，目前不存在，迁移按标准推进，不必恐慌。

### 7.1 实测过的 OpenSSL 示例（代理 VM，OpenSSL 3.0.13）

以下三组命令均在本机真实运行通过：生成密钥、签名、验证通过，且篡改消息后 RSA-PSS 验证失败。
密钥为现场生成的测试密钥，实验后已删除；命令里的消息文件为测试文本，无真实数据。

```bash
# RSA-PSS：显式写出全部参数，避免默认行为随版本变化
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out rsa_priv.pem
openssl pkey -in rsa_priv.pem -pubout -out rsa_pub.pem
openssl dgst -sha256 -sign rsa_priv.pem \
  -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:32 \
  -sigopt rsa_mgf1_md:sha256 -out msg.rsa-pss.sig msg.txt
openssl dgst -sha256 -verify rsa_pub.pem -signature msg.rsa-pss.sig \
  -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:32 \
  -sigopt rsa_mgf1_md:sha256 msg.txt
# 实测：签名生成成功，验证输出 Verified OK；签名 256 字节（RSA-2048）
# 实测：把消息换成篡改后的文本再验证，输出 Verification failure，退出码非零

# ECDSA P-256：签名为 DER 编码
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ecdsa_priv.pem
openssl pkey -in ecdsa_priv.pem -pubout -out ecdsa_pub.pem
openssl dgst -sha256 -sign ecdsa_priv.pem -out msg.ecdsa.sig msg.txt
openssl dgst -sha256 -verify ecdsa_pub.pem -signature msg.ecdsa.sig msg.txt
# 实测：签名生成成功，验证输出 Verified OK；本次签名 71 字节（DER 长度随整数变化，P-256 通常 70–72 字节）

# Ed25519：签名为 R‖S 拼接，不经过 dgst 预哈希
openssl genpkey -algorithm ED25519 -out ed_priv.pem
openssl pkey -in ed_priv.pem -pubout -out ed_pub.pem
openssl pkeyutl -sign -inkey ed_priv.pem -rawin -in msg.txt -out msg.ed.sig
openssl pkeyutl -verify -pubin -inkey ed_pub.pem -rawin -in msg.txt -sigfile msg.ed.sig
# 实测：签名生成成功，验证输出 Signature Verified Successfully；签名 64 字节
```

注意三处易错点，均已在命令里显式处理：RSA-PSS 的盐长与 MGF1 哈希必须签发与验证两边一致；
ECDSA 的 `dgst -sign` 输出是 DER 编码，不要当成 64 字节原始拼接；Ed25519 必须用 `-rawin`
（算法内部自己做哈希），不要先用 `dgst -sha256` 预哈希一遍再签——那会签成另一个东西。

## 8. 常见误解

- **误解：签名两次结果不同就是坏了**：RSA-PSS 故意随机化，不同是正常的；EdDSA/确定性 ECDSA
  两次相同也是正常的。用验证结果判断，不要用“两次是否相同”判断。
- **误解：密钥越长越安全**：跨体制比位数没有意义（01 篇第 3.5 节）；同体制内超过需求加长
  只会拖慢速度，且错误使用（参数不对齐、k 重复）会让长密钥也白搭。
- **误解：验证通过就说明内容可信**：验证只说明“确实是持有该私钥的人签的、且内容未被改动”，
  不说明签名者可信、内容为真（总览第 8 节）。
- **误解：Ed25519 和 ECDSA P-256 可以互换验证**：两者曲线、签名结构、编码完全不同，
  密钥与签名互不兼容，协议约定哪种就只能用哪种。

  IETF RFC 8017《PKCS #1：RSA 密码学规范》（RSASSA-PSS、MGF1）；IETF RFC 8032《EdDSA》
  （Ed25519/Ed448 参数与签名格式）；IETF RFC 6979《确定性 DSA/ECDSA》；NIST SP 800-57 Part 1 Rev. 5
  （密钥长度与安全强度对照）；OpenSSL 3.0.13 命令行文档（第 7.1 节命令以实测为准）。
- 适用版本：FIPS 186-5（2023）；RFC 8017、RFC 8032、RFC 6979 现行版；实测环境 OpenSSL 3.0.13。
- 核实日期：2026-11-04
- 成熟度：成熟应用
- 难度：L4
- 前置知识：[哈希与数字签名](02-hash-signature.md)（总览，先哈希再签名的流程）、[对称与非对称密码](01-symmetric-asymmetric.md)（密钥长度与安全强度对照）
- 相关主题：[TLS 与证书体系原理](03-tls-pki.md)（证书签名在握手里的位置）、[密钥生命周期管理](10-key-lifecycle-management.md)（本批新篇，私钥轮换与吊销）、[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)（证书管理的应用做法）
- 未完成项：RSA-2048 在 2030 年后的强度窗口与迁移时点待以 NIST 最新指南为准补充；secp256k1 等非 NIST 曲线的部署细节不在本篇范围内；Ed448 的 OpenSSL 实测未做（本机只实测了 Ed25519，Ed448 参数以 RFC 8032 为准）；后量子签名（ML-DSA/SLH-DSA）的选型与迁移归前沿域后续展开。
