# 椭圆曲线与现代密钥交换

> 本篇是[对称与非对称密码](01-symmetric-asymmetric.md)总览的深挖：总览讲了“Diffie-Hellman 让双方在公开信道上协商出共享秘密、TLS 1.3 由此获得前向保密”这个结论，本篇讲椭圆曲线版（ECDH）是怎么算的、X25519 与 NIST 曲线各是什么、以及“前向保密”到底保什么、不保什么。本篇只讲原理与正确用法，不讲任何私钥推导、密钥提取或绕过认证的操作步骤。

## 1. 本章目标

读完本篇，能说清 ECDH 的协商思想、X25519 与 P-256 的参数与取舍、为什么协商出的共享秘密不能直接当密钥用，以及为什么“每次会话换一对临时密钥”就是前向保密。

## 2. 背景与问题

总览留下的难题是：对称加密需要共享密钥，但密钥本身怎么安全地交给对方？Diffie-Hellman（1976 年）的回答是：**不传送密钥**——双方各自生成一对密钥，只交换公开的那一半，各自用“自己的私钥 + 对方的公钥”算出同一个共享秘密，偷听者即使看到全部公开消息也算不出来。

经典 DH 在有限域（大整数模运算）里做这件事，密钥与公开值都很长。椭圆曲线版 ECDH 把同样的思想搬到椭圆曲线点运算上：达到相同安全强度所需的密钥短得多（总览对照表：128 比特强度约需 ECC 256 位、RSA 3072 位），握手更小、计算更快。这就是 TLS、SSH、即时通讯里默认用 ECDH 而不是经典 DH 的原因。

但 ECDH 本身只解决“协商”，不解决“认证”：它不告诉你对方是谁。没有认证的 ECDH 会被中间人冒充两边各谈一次——这个警告总览已经讲过，本篇再强调一次：**实际系统里 ECDH 必须配合身份认证（例如证书、长期身份密钥）使用，裸用 ECDH 是不安全的**。

## 3. 总体架构

```
Alice：私钥 a ──▶ 公钥 A = a·G ──┐
                                  ├─公开信道交换 A、B（任何人可见）
Bob：  私钥 b ──▶ 公钥 B = b·G ──┘

Alice 算：a·B = a·(b·G) = ab·G
Bob 算：  b·A = b·(a·G) = ab·G
          ──▶ 双方得到同一个点 ab·G ──▶ 取其坐标作共享秘密
                ──▶ 经密钥派生函数 KDF ──▶ 会话密钥（再经 AEAD 加密数据）
```

图中 G 是约定的基点（生成元），“·”是椭圆曲线上的标量乘法（把一个点连加多次）。关键性质是**乘法可交换**：先乘 a 再乘 b，与先乘 b 再乘 a，结果是同一个点。偷听者只看到 A、B 与 G，要从 A 反推 a（或从 B 反推 b），就是椭圆曲线离散对数问题——在选定的曲线上，这个问题被认为是难解的，整个体制的安全性就建立在这个难度上。

注意架构里的最后一层：**共享秘密不是会话密钥**。共享秘密是一个点的坐标，它的分布不均匀、长度与曲线绑定，不能直接喂给 AES。正确做法是把它连同会话上下文（例如双方公开值、协议标识）一起送进 KDF（如 HKDF，RFC 5869），派生出定长的会话密钥。跳过 KDF、直接把原始共享秘密当密钥用，是实现层面的常见错误。

## 4. 工作机制

### 4.1 椭圆曲线上的“一把钥匙”是什么意思

椭圆曲线密码的私钥是一个整数（标量），公钥是“标量乘以基点”得到的一个曲线点。私钥保密、公钥公开；从公钥反推私钥就是离散对数问题。曲线本身由一组公开参数定义：素数域、曲线方程系数、基点、阶。参数选错（例如阶有小因子、曲线有弱结构）会让离散对数变容易——因此**实践中只用标准曲线，绝不自选参数、自造曲线**。标准曲线分两大家族，见 4.2 与 4.3 节。

### 4.2 X25519：只用 x 坐标的 Montgomery 曲线

X25519（IETF RFC 7748）是 ECDH 在 Curve25519 上的具体函数，名字要分清：Curve25519 是曲线，X25519 是在这条曲线上做 DH 的函数。

核查过的参数：

- 曲线方程：Montgomery 型，y² = x³ + 486662x² + x，定义在素数域 p = 2²⁵⁵ − 19 上。
- 密钥与公开值：私钥、公钥、共享秘密均为 32 字节；安全强度约 128 比特。
- 只用 x 坐标：公开值只传点的 x 坐标（在 RFC 7748 里记为 u），不需要传 y 的符号位，计算用 Montgomery ladder（一种固定步数的标量乘法），天然适合写成恒定时间实现。
- 标量钳制（clamping）：实现内部会对私钥标量做固定处理（清掉低三位、固定某一位），目的是让计算总落在主子群、且步数固定——这是实现细节，调用方不需要、也不应该自己干预，交给成熟的密码库即可。

X25519 的正确用法检查点（防御侧，调用方与协议设计者要确认的）：

1. **拒绝全零共享秘密**：如果对方给了一个导致共享秘密全为零的公开值，协商必须中止。TLS 1.3 与多数协议都要求这一检查，库没做、协议没要求时要补上。
2. **私钥来自密码学安全的随机数源**，不要用口令、时间戳、自增序号派生私钥。
3. **不要把 X25519 当签名用**：X25519 只做密钥交换；同一条曲线上的签名是 Ed25519（RFC 8032），那是另一套函数，见[哈希与数字签名](02-hash-signature.md)中 EdDSA 的辨析。

X25519 的适用面：TLS 1.3、SSH、WireGuard、Signal 等现代协议的默认密钥交换之一，速度快、实现简单、公开值只有 32 字节。

### 4.3 NIST 曲线：P-256、P-384、P-521

NIST 曲线（FIPS 186-4 / SP 800-186 定义，TLS 里记为 secp256r1、secp384r1、secp521r1，对应 P-256、P-384、P-521）是另一大家族：短 Weierstrass 型曲线，公开值传完整的点（未压缩格式为 0x04 + X + Y，例如 P-256 公开值 65 字节）。

核查过的对应关系（与总览对照表一致）：

| 曲线 | 密钥规模 | 约略安全强度 |
|---|---|---|
| P-256（secp256r1） | 256 位 | 128 比特 |
| P-384（secp384r1） | 384 位 | 192 比特 |
| P-521（secp521r1） | 521 位 | 256 比特 |

NIST 曲线的正确用法检查点与 X25519 有一处不同：P 曲线**需要验证对方公开值确实是曲线上的合法点**（点验证），否则可能接受非法点。X25519 的 x-only 设计与曲线选择让非法点问题大幅弱化，但 P 曲线没有这层天然保护——同样是“交给成熟库”，但协议审计时要确认库确实做了点验证，而不是假设它做了。

取舍：P-256 是 TLS 1.3 要求实现必须支持的曲线（RFC 8446 的 mandatory-to-implement），合规与互通场景下优先它；X25519 在速度与实现简洁性上占优，是现代协议的常用默认。两者在 128 比特强度这一档是等价选择，不是高低之分；P-384/P-521 是为更高强度档准备的，代价是更大的公开值与更慢的运算。

### 4.4 临时密钥与前向保密：保的是“过去”，不是“现在”

前向保密（Forward Secrecy，TLS 语境里常写作 Perfect Forward Secrecy, PFS）的机制在[TLS 与证书体系原理](03-tls-pki.md)里已经讲过思想，本篇把它落到 ECDH 上：

```
长期身份密钥（证书私钥）：只用来签名认证，不用来算会话密钥
临时 ECDH 密钥对：每次会话新生成，会话结束即丢弃
会话密钥 = KDF(临时 ECDH 共享秘密, 会话上下文)
```

- **保什么**：长期私钥日后泄露（或被法院、被攻击者拿到），也推不出过去会话的密钥——因为过去会话的密钥是由早已丢弃的临时私钥算出来的，长期私钥从来没有参与过会话密钥的计算。TLS 1.3 只允许临时 (EC)DHE 密钥交换、删掉了静态 RSA 与静态 (EC)DH，正是把这个性质写进了协议：任何 TLS 1.3 连接（除纯 PSK 不带 DHE 的恢复模式外）都默认有前向保密。
- **不保什么**：前向保密不防正在进行的中间人（没有认证时，临时密钥照样能被冒充）、不防端点本身被攻破（会话密钥就在端点内存里）、不防会话密钥本身泄露（会话密钥一丢，该会话就是明文的）。它只针对“长期密钥日后泄露”这一种威胁模型。

实现层面的两个硬要求：临时私钥必须**每次会话真随机生成**（复用“临时”密钥就是静态密钥，前向保密随即失效）；会话结束后必须**真正丢弃**（从内存中清除，而不是留在日志、崩溃转储、备份里）。前向保密是“生成—使用—丢弃”整条链的性质，任何一环不断链都不算数。

### 4.5 从协商到可用密钥：KDF 与会话上下文绑定

完整的派生链是：ECDH 共享秘密 → KDF（提取 + 扩展，例如 HKDF，RFC 5869）→ 会话密钥。KDF 的输入除了共享秘密，还应绑定会话上下文：双方公开值、协商的算法标识、协议版本号等。绑定的意义是：即使两个会话碰巧协商出同一个共享秘密（正常情况下不会，但防御要按最坏情况设计），上下文不同也会派生出不同密钥，且会话密钥不能被拿到另一个协议里重用。TLS 1.3 的密钥调度（key schedule）就是这条链的完整实现，本篇不展开其全部步骤，只保留这个原则。

### 4.6 经典 DH 的位置：还在，但不是默认

有限域 DH（ffdhe2048/3072/4096 等，RFC 7919 定义的标准群）仍在 TLS 1.3 的群列表里，作为 ECDH 之外的备选。它的公开值大（2048 位群的公开值 256 字节）、运算慢，现代部署里通常只是兼容保留。新系统默认选 ECDH（X25519 或 P-256），不要为了“经典”而选有限域 DH；自选 DH 参数（自己挑素数 p 与生成元 g）是明确的错误做法，只用 RFC 7919 的标准群。

## 5. 分类与变体

| 类别 | 代表 | 公开值大小 | 一句话特征 |
|---|---|---|---|
| 椭圆曲线 ECDH | X25519（RFC 7748） | 32 字节 | x-only、速度快、实现简洁，须拒绝全零秘密 |
| 椭圆曲线 ECDH | P-256 / P-384 / P-521 | 65 / 97 / 133 字节（未压缩点） | NIST 曲线，P-256 为 TLS 1.3 必备，须做点验证 |
| 有限域 DH | ffdhe2048/3072（RFC 7919） | 与群规模同长 | 兼容保留，公开值大、运算慢，新系统不优先 |
| 临时（Ephemeral） | ECDHE / DHE | — | 每次会话新密钥对，前向保密的来源 |
| 静态（Static） | 静态 ECDH | — | 长期密钥对参与协商，无前向保密，TLS 1.3 已删除 |

注：上表 P-384/P-521 公开值字节数由“未压缩点 = 1 字节前缀 + 两倍坐标长度”算出（P-384 坐标 48 字节 → 97 字节；P-521 坐标 66 字节 → 133 字节），其余参数见 4.2–4.3 节。X448（Curve448 上的 ECDH）同样在 TLS 1.3 群列表里，提供更高强度档，其部署细节以官方发布为准（待核实），见文末未完成项。

## 6. 典型应用

- **TLS 1.3 握手**：ClientHello 与 ServerHello 各带一个临时 key_share，协商出会话密钥后全部记录层数据走 AEAD；证书只做签名认证，不加密会话密钥。详见[TLS 与证书体系原理](03-tls-pki.md)。
- **SSH 会话建立**：双方用 ECDH（常见 X25519）协商会话密钥，再用该密钥加密后续全部传输；主机密钥只做身份认证。
- **即时通讯与 VPN**：Signal、WireGuard 等协议每会话（乃至每条消息）做 ECDH，用临时密钥链实现前向保密与后向保密（后向保密指当前密钥泄露不连累未来消息，机制超出本篇范围，见未完成项）。
- **密钥信封与密钥管理**：ECDH 协商出的共享秘密经 KDF 派生数据密钥，是“密钥不落地传输”的标准做法之一；密钥的存储、轮换与吊销见[密钥生命周期管理](10-key-lifecycle-management.md)。

## 7. 本机实测：双方算出的共享秘密确实一致

以下演示用 OpenSSL 命令行做 ECDH 密钥交换演示（合法操作示例，演示双方协商过程，不涉及任何私钥推导）。环境：代理 VM，OpenSSL 3.0.13。

### 7.1 P-256（NIST 曲线）演示（实测通过）

```bash
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
$ openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out alice_priv.pem
$ openssl pkey -in alice_priv.pem -pubout -out alice_pub.pem
$ openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out bob_priv.pem
$ openssl pkey -in bob_priv.pem -pubout -out bob_pub.pem
$ openssl pkeyutl -derive -inkey alice_priv.pem -peerkey bob_pub.pem -out alice_secret.bin
$ openssl pkeyutl -derive -inkey bob_priv.pem -peerkey alice_pub.pem -out bob_secret.bin
$ cmp alice_secret.bin bob_secret.bin && echo SECRETS_MATCH
SECRETS_MATCH
```

实测结果：双方共享秘密均为 32 字节，逐字节一致（`cmp` 无差异输出）。注意演示里 Alice 与 Bob 的密钥对是各自本地生成的，交换的只是公开值文件——这正是 ECDH 的架构：私钥文件从未离开各自一方。

### 7.2 X25519 演示（实测通过）

```bash
$ openssl genpkey -algorithm X25519 -out x_alice.pem
$ openssl pkey -in x_alice.pem -pubout -out x_alice_pub.pem
$ openssl genpkey -algorithm X25519 -out x_bob.pem
$ openssl pkey -in x_bob.pem -pubout -out x_bob_pub.pem
$ openssl pkeyutl -derive -inkey x_alice.pem -peerkey x_bob_pub.pem -out x_alice_secret.bin
$ openssl pkeyutl -derive -inkey x_bob.pem -peerkey x_alice_pub.pem -out x_bob_secret.bin
$ cmp x_alice_secret.bin x_bob_secret.bin && echo X25519_MATCH
X25519_MATCH
```

实测结果：双方共享秘密同样为 32 字节且一致，与 4.2 节参数（32 字节）吻合。演示只验证“双方算出同一秘密”，不验证认证——演示环境里双方身份是人为指定的，生产环境必须叠加证书或长期身份密钥认证（见第 2 节警告）。

> 提醒：演示生成的私钥是临时演示密钥，演示结束后应删除，不要用于任何真实系统；生产密钥的生成、存储与轮换见[密钥生命周期管理](10-key-lifecycle-management.md)。

## 8. 关键设计取舍

- **短密钥 vs 数学假设**：ECC 用更短的密钥达到相同强度，代价是安全性完全押在椭圆曲线离散对数这一个假设上；RSA 的假设是大整数分解。两者都是“未被证明难、但久经考验”的假设，选型时看生态与合规，不看“谁的数学更漂亮”。
- **x-only vs 完整点**：X25519 只要 x 坐标，实现简单、验证负担小；P 曲线传完整点，验证负担大但兼容性与合规覆盖广。没有免费午餐，只有场景适配。
- **临时 vs 静态**：临时密钥换来前向保密，代价是每次握手都要生成密钥对、做一次标量乘法；静态密钥省计算，但丢掉前向保密。现代硬件上这点代价不值一提，TLS 1.3 直接替所有人做了决定：只用临时。
- **协商 vs 封装**：ECDH 是“双方各出一半”的协商；后量子方向的 ML-KEM（FIPS 203）是“一方封装、一方解封”的密钥封装机制（KEM），两者接口不同。未来迁移可能是“ECDH + KEM 混合”的形态，但混合方案的具体标准与部署状态以官方发布为准（待核实），不在本篇下结论。

## 9. 限制与常见误解

- **误解：ECDH 加密了数据**：ECDH 只协商出共享秘密，数据加密是之后 AEAD（见[分组密码模式与认证加密](04-block-cipher-modes-aead.md)）的事。把“做了 ECDH”说成“数据已加密”是错的。
- **误解：前向保密 = 万无一失**：前向保密只针对长期密钥日后泄露；它不防中间人（无认证时）、不防端点攻破、不防会话密钥本身泄露。见 4.4 节。
- **误解：共享秘密可以直接当 AES 密钥**：共享秘密分布不均匀、长度与曲线绑定，必须经 KDF 派生。见 4.5 节。
- **误解：密钥越短越好**：X25519 的 32 字节是“曲线参数定死的 32 字节”，不是“可以任意缩短的 32 字节”。缩短私钥、截断公开值都会破坏安全假设。
- **限制：量子计算的影响**：Shor 算法在理论上能解椭圆曲线离散对数，因此 ECDH 与 RSA、ECDSA 一样面临长期威胁；总览已指出 NIST 后量子标准 ML-KEM（FIPS 203，2024 年）是进行中的迁移工作，本篇不展开迁移步骤。
- **限制**：本篇不讲曲线点运算的具体数学推导、不讲标量乘法的恒定时间实现细节——那是密码库实现者的课题，调用方做到“用标准曲线、用成熟库、做 4.2–4.3 节的检查点”就够了。

## 10. 小结

ECDH 是“各出一半公开值、各自算出同一秘密”的协商；X25519 32 字节、x-only、快而简洁，P-256 是 TLS 必备的合规选择，两者都是 128 比特档；共享秘密必须经 KDF 才成会话密钥；每次会话换临时密钥对、会话结束即丢弃，就是前向保密——保过去，不保现在与端点。
