# 零知识证明入门

## 1. 本章目标

读完本篇，能说清零知识证明在证明什么、它必须同时满足哪三条性质，以及为什么同一思想会分化出 zk-SNARKs 与 zk-STARKs 这样取舍不同的工程路线。

## 2. 背景与问题

很多验证场景都有一个两难：验证方需要确认一件事是真的，证明方却不想把背后的秘密交出来。例如：证明“我年满 18 岁”不需要交出出生日期与身份证号；证明“我知道这把私钥对应的口令”不需要把口令本身发过去；证明“一批交易按规则执行了”不需要公开每笔交易的细节。传统的办法是“把证据全交出来再核查”，隐私就这样在验证过程中漏掉了。

零知识证明（Zero-Knowledge Proof，ZKP）就是为这个两难而生的密码学工具：证明方（Prover）说服验证方（Verifier）相信某个断言为真，而验证方除“断言为真”这一事实之外，学不到任何其他信息。

这个概念由 Shafi Goldwasser、Silvio Micali 与 Charles Rackoff 在 1985 年的论文《The Knowledge Complexity of Interactive Proof-Systems》中形式化。他们的工作首先是一个**定义**：什么叫“什么都没泄露”，必须能被精确地说出来，否则任何“好像没泄露”的协议都不可信。

> 本篇只讲原理与正确应用，不讲任何伪造证明、窃取秘密或绕过验证的方法。证明系统的安全性恰恰建立在“不知道秘密就通不过验证”这一点上。

## 3. 总体架构

一个零知识证明系统涉及两方与一个断言：

```
证明方（知道秘密证据 witness）
   │  证明：断言为真，但不交出 witness
   ▼
验证方（只持有公开断言）
   │  输出：接受 / 拒绝
   ▼
验证方学到的全部内容 = “断言为真”这一事实本身
```

举一个贯穿全篇的例子：证明方声称“我知道一个数 x，使得公开值 y 等于 g 的 x 次方”（即知道离散对数）。验证方只知道 g 和 y。证明成功后，验证方确信证明方确实知道 x，但对 x 本身仍然一无所知——既算不出 x，也无法把“知道 x”这件事转授给第三方去冒充。

## 4. 工作机制

### 4.1 三条性质，缺一不可

一个合格的零知识证明必须同时满足：

1. **完备性（Completeness）**：断言为真、证明方诚实，就一定能通过验证。诚实的人不应该被自己的证明系统冤枉。
2. **可靠性（Soundness）**：断言为假、证明方不知道秘密，就几乎不可能通过验证。“几乎”是因为很多协议允许一个极小的作弊成功概率（例如猜中一次挑战），这个概率必须小到可以忽略，并且可以通过重复协议把它压得更低。
3. **零知识性（Zero-Knowledge）**：验证方在验证过程中学不到断言真实性之外的任何信息。形式化的说法是：验证方看到的全部交互记录，都可以由验证方自己在“不知道秘密”的前提下模拟出来——既然能自己模拟出来，交互本身就没有带来新信息。

三条性质互相制衡：只满足前两条，那是普通证明，不是零知识证明；只满足第一、三条而不要第二条，骗子也能过关，证明就没有意义。

### 4.2 交互式证明：承诺—挑战—回应

最经典的形态是三步交互，以 Schnorr 身份识别协议的思想为例（本篇只讲思想，不展开具体群运算参数）：

1. **承诺**：证明方先用随机数算出一个承诺值发给验证方，并在这个承诺里把自己“锁定”——之后不能再改。
2. **挑战**：验证方发回一个随机挑战。关键在顺序：挑战必须在承诺之后才产生，证明方事先猜不到它。
3. **回应**：证明方结合秘密与挑战算出回应值发回。验证方用公开值检验回应是否自洽。

为什么这个顺序重要？因为回应必须同时对得上“承诺”和“挑战”。不知道秘密的人，只有事先猜中挑战才可能蒙混过关；而挑战是承诺之后才随机产生的，猜中的概率极小。重复多轮之后，作弊概率呈指数下降。

这个例子也说明了零知识性的直觉：验证方看到的承诺与回应，都是掺了随机数的“盲化”结果，无法反推出秘密本身。

### 4.3 非交互式证明：用哈希代替验证方

交互式证明要求验证方在线、来回发消息，很多场景做不到（例如把证明贴在链上、供任何人事后验证）。Fiat 与 Shamir 在 1986 年提出的做法是：**让证明方自己用哈希函数算出挑战**——挑战 = 哈希（承诺与公开信息）。因为哈希输出在选定承诺之前无法预测，这就复现了“挑战在承诺之后随机产生”的关键顺序，而不再需要验证方实时参与。

这样得到的非交互式证明（NIZK）可以只发一次、由任何人离线验证。代价是安全性分析要放在“随机预言机模型”里：即假设哈希函数的行为像一个理想随机函数。真实哈希函数只是对这个理想的近似，这是使用非交互证明时必须知道的前提，不是实现细节。

### 4.4 从“能证明”到“能实用”：电路化

现代零知识证明系统通常把“要证明的计算”先翻译成一种统一的约束形式（例如算术电路或执行轨迹），再对这个约束形式生成证明。证明方的工作量、证明大小与验证时间，都取决于这一步的翻译与所选的证明系统。不同系统在这一层的选择不同，这正是下一节取舍的来源。

## 5. 关键设计取舍

- **证明大小 vs 可信设置**：证明越小、验证越快，往往越依赖特殊的公共参数生成方式；而“参数里有没有藏秘密”本身就成了一个信任问题。
- **通用性 vs 专用性**：通用系统什么计算都能证明，但为通用付出的代价是证明方计算量大；专用系统（如区间证明）只解决一类断言，但在这类断言上更轻量。
- **交互 vs 非交互**：交互省去了对哈希理想模型的依赖，但要求双方同时在线；非交互便于发布与复验，但要接受随机预言机模型的假设。
- **安全性假设 vs 量子前景**：基于椭圆曲线配对的系统与基于哈希的系统，在“未来量子计算面前是否还成立”这一点上并不相同（见 6 节与相关主题中的量子分支篇目）。

## 6. 分类与变体

| 类别 | 全称要点 | 一句话特征 |
|---|---|---|
| 交互式证明 | 多轮消息往来 | 经典形态，需验证方在线 |
| 非交互式证明（NIZK） | 一次发送、离线可验 | 经 Fiat-Shamir 变换得到，依赖哈希的随机预言机假设 |
| zk-SNARKs | 简洁（Succinct）的非交互式知识论证 | 证明极小（约数百字节量级）、验证快；多数构造需要可信设置 |
| zk-STARKs | 可扩展、透明（Transparent）的知识论证 | 不需要可信设置，参数公开可验证；证明较大（数十 KB 量级），基于哈希函数 |
| Bulletproofs | 基于内积论证的非交互证明 | 不需要可信设置，特别适合区间证明（证明一个秘密数落在某个范围内而不透露它）；验证时间随规模增长 |

展开说明两点取舍：

- **可信设置（Trusted Setup）**：zk-SNARKs 的常见构造需要先生成一组公共参数，生成过程用到的秘密随机数必须在使用后销毁——残留的秘密（俗称“有毒废料”）若被保留，持有者就可能伪造出能通过验证的证明。多方仪式把秘密拆给多方参与者，只要其中一方确实销毁了自己的那份，整体就是安全的；但“仪式是否被正确执行”本身仍是一个需要审计的信任点。zk-STARKs 与 Bulletproofs 不需要这一步，参数只来自公开可验证的随机性，这就是 STARK 名字中“透明（Transparent）”的含义。
- **量子前景**：zk-STARKs 的安全性建立在哈希函数的抗碰撞性上，目前没有已知的高效量子攻击；基于椭圆曲线配对的 zk-SNARKs 则与 RSA、ECC 一样，面临 Shor 算法在理论上的威胁。本篇不展开后量子密码，相关讨论见[量子计算](../24-frontier/01-quantum-computing.md)（量子分支）。

## 7. 应用与限制

**成熟度分层说明**：本篇整体成熟度标为“实验研究中”，指的是零知识证明作为一类通用技术仍在快速演进；但其中一部分已经落地的工程路线要另算：

- **工程发展中**：zk-SNARKs 已在实际系统中部署，例如 Zcash 的隐私交易（源自 2014 年的 Zerocash 协议）与以太坊上的 zk-Rollup 类扩容方案（把一批交易在链下执行、只把简洁证明发上链验证）；zk-STARKs 亦已用于以太坊扩容网络。部署不等于“开箱即用”：电路编写、参数仪式、可信设置审计与证明方性能，仍是工程落地的真实成本。
- **实验研究中**：通用电路的证明效率、递归证明、后量子安全的简洁证明、以及面向普通开发者的工具链，仍是活跃的研究方向；不要把研究原型当成可直接上线的产品。

典型应用（每个场景里，零知识证明只解决“证明而不泄露”这一环，不解决场景的全部问题）：

- **选择性披露的身份证明**：证明“年满 18 岁”“持有有效凭证”而不交出完整证件信息；凭证本身的签发与吊销仍需另外的身份体系支撑。
- **隐私交易与扩容**：在不公开交易细节的前提下证明交易合法，或在链下执行后用一纸证明代替全部重算。
- **合规而不泄密的审计**：向监管或审计方证明“账目符合某条规则”，而不必公开全部账目。

限制与常见误解：

- **误解：零知识等于匿名**：零知识证明只保证“验证过程不泄露额外信息”，不保证证明方身份不被其他渠道（网络层、金额模式、时间关联）暴露。匿名需要整套系统配合，单靠证明不够。
- **误解：证明通过就说明结论可信**：证明只保证“计算过程符合电路所编码的规则”；如果电路本身把规则编错了（例如漏掉一个检查），证明会一本正经地证明一个错误的规则。电路审计与规则本身的正确性不在证明的保证范围内。
- **误解：可信设置做一次就一劳永逸**：仪式的安全性依赖于参与者确实销毁秘密与仪式过程可审计；仪式被质疑或实现被发现漏洞时，依赖它的证明都要重新评估。
- **限制**：证明方计算开销通常远大于直接执行原计算；不适合“证明成本比计算本身还贵、且没有隐私或扩容收益”的场景。

## 8. 小结

零知识证明 = 完备性 + 可靠性 + 零知识性三条性质同时成立的证明：诚实者总能通过，作弊者几乎总被抓住，验证者除“断言为真”外什么也学不到。交互式是原形，Fiat-Shamir 变换把它变成可发布、可复验的非交互证明；工程上在“证明大小、可信设置、量子前景”之间取舍，才有了 SNARKs、STARKs 与 Bulletproofs 的分化。
