# KMS 与 HSM 入门

> 本篇只讲 KMS 与 HSM 的形态、原理与选型思路，不讲任何密钥提取、绕过保护机制或从内存、设备中取回密钥的方法。各云厂商 KMS 的具体功能、规格与价格一律以官方文档为准，本篇不写、不比价。

## 1. 一句话定义

KMS（Key Management Service，密钥管理服务）是集中生成、保管并提供密钥运算的服务；HSM（Hardware Security Module，硬件安全模块）是专门做密钥生成、保管与运算的防篡改硬件设备。两者解决的是同一个问题：**让密钥材料不必落到应用服务器上，也能被安全地使用**。

## 2. 为什么需要它

[密钥生命周期管理](10-key-lifecycle-management.md)要求密钥与数据分开、调用者“只见运算、不见材料”、操作全量审计。如果每个应用各自在本地文件里存一把密钥，这些要求一条都落不了地：密钥散落在各处，轮换要逐台改，泄露了都不知道哪台漏的，审计更是无从谈起。

KMS 与 HSM 就是把“保管密钥”这件事从应用里抽出来，集中到一个专门的服务或设备上：应用不再持有密钥材料，只持有“调用某把密钥的权限”；密钥的生成、轮换、停用、销毁、审计，都在这个集中点上统一做。

## 3. 核心含义

### 3.1 KMS：密钥的集中服务台

一个典型的 KMS 提供以下能力（具体能力以各厂商官方文档为准）：

- **生成与保管**：在服务侧生成密钥材料并保管，应用不直接接触材料。
- **运算接口**：应用通过 API 发起“用密钥 X 加密/解密/签名/验证”的请求，KMS 在服务边界内完成运算，只返回结果。
- **策略与审计**：每把密钥配访问策略（谁能用、能做什么操作），每次调用记审计日志（谁、何时、对哪把密钥、做了什么）。
- **生命周期操作**：启用、停用、轮换、计划删除等状态变更，都在服务侧统一执行并留痕，与[密钥生命周期管理](10-key-lifecycle-management.md)的状态机对应。
- **与存储、数据库等服务的集成**：数据服务加密静态数据时，一般不直接把数据发给 KMS 逐条加密，而是走包封加密（见 3.3 节），KMS 只负责保护数据密钥。

关键辨析：**KMS 保护的是密钥，不是数据本身**。数据加密仍由应用或数据服务用数据密钥完成；KMS 的价值在于数据密钥本身是被妥善保管的，并且每一次对数据密钥的操作都有策略与审计。

### 3.2 HSM：把密钥关进防篡改的硬件里

HSM 是一台专用硬件设备（物理设备、机架卡或云上的独占硬件形态），它的设计目标是：密钥材料在设备内部生成、存储与使用，**以明文形式不出设备边界**；设备检测到物理篡改时，会主动清除内部密钥材料（清零，zeroization），而不是让人有机会把芯片拆下来慢慢研究。

HSM 与普通服务器上跑的软件密钥库的区别，不在于算法（两者都可能跑 AES、RSA、ECC），而在于**边界**：软件密钥库的边界是操作系统与进程，拿到主机权限就可能拿到密钥；HSM 的边界是硬件外壳与固件，攻击面被压缩到设备接口与物理防护上。HSM 不是“更快的加密卡”，它是“更难被连锅端的保管箱”。

### 3.3 包封加密（envelope encryption）：KMS/HSM 与大数据量的折中

直接用 KMS 的主密钥逐条加密全部业务数据，既慢又会让主密钥的调用量失控。标准做法是分两层：

```
数据 ──数据加密密钥 DEK 加密──▶ 密文数据
DEK ──密钥加密密钥 KEK 加密──▶ 已加密的 DEK（可与密文数据一起存放）
KEK 只存放在 KMS / HSM 内，永不出边界
```

解密时反向操作：先请 KMS/HSM 用 KEK 解开 DEK，再用 DEK 解密数据。这一层结构的好处：

- **主密钥调用量小**：KEK 只接触 DEK，不接触业务数据，调用频率低、审计清晰。
- **轮换成本分层**：轮换 DEK 只需重加密该 DEK 保护的数据；轮换 KEK 只需重包装 DEK，不必重加密全部业务数据。
- **粒度灵活**：可以按租户、按数据分区、按数据分级各配一把 DEK，一把 DEK 泄露只影响它保护的那部分数据。

包封加密不是某个厂商的专利做法，而是 KMS/HSM 场景下的通用模式；具体 API 名称与调用限制以各厂商官方文档为准。

### 3.4 FIPS 140-3：怎么判断一个密码模块靠不靠谱

FIPS 140-3 是 NIST 发布的密码模块安全要求标准，现行版本；它定义了密码模块（实现密码运算与密钥管理的硬件、软件或固件组合）在设计、测试与验证上必须满足的要求。验证由 CMVP（密码模块验证计划，NIST 与加拿大网络安全中心的联合计划）执行：经认可的实验室测试、CMVP 发证，证书编号可在 CMVP 已验证模块清单中公开查到。

FIPS 140-3 定义了四个递增的安全等级（等级越高，物理与操作防护越严）：

| 等级 | 一句话特征 |
|---|---|
| Level 1 | 基线：正确实现经批准的算法，无专门的物理安全要求；软件密码模块常见于此级 |
| Level 2 | 增加防篡改证据（封条、涂层等，能看出是否被动过）与基于角色的身份认证 |
| Level 3 | 防篡改从“能看出”升级为“能抵抗”，基于身份的身份认证，防护被突破时清除关键安全参数；HSM 的常见目标等级 |
| Level 4 | 最强的物理防护：完整的防入侵 envelope，检测并响应物理入侵与环境异常（如电压、温度异常） |

选型时要注意三点：第一，**验证对象是模块与版本，不是整个产品**——“用了 AES”不等于“FIPS 已验证”，“某产品通过验证”也不等于它里面所有组件都通过验证，要核对具体的模块名称、版本与证书编号。第二，等级不是越高越好，而是与数据敏感度与物理风险匹配——机房外的软件服务与银行金库里的支付 HSM，合理等级本来就不同。第三，旧版 FIPS 140-2 证书的过渡安排以 CMVP 最新公告为准，采购时查清单现状，不要只看厂商资料页上的旧标注。

### 3.5 谁持有密钥：云厂商管理、BYOK、HYOK

在云上用 KMS 时，“谁持有密钥”有三种常见形态，控制权与运维成本依次递增：

| 形态 | 密钥材料在哪 | 一句话特征 |
|---|---|---|
| 云厂商管理密钥 | 云厂商 KMS 内，由厂商生成与管理 | 最省事；密钥控制权主要在厂商侧的策略与审计里体现 |
| BYOK（Bring Your Own Key，自带密钥） | 你在自有受控环境（通常是自有 HSM）生成密钥材料，再导入云厂商 KMS | 你掌握密钥来源与原始材料，导入后由厂商 KMS 代为保管与运算 |
| HYOK（Hold Your Own Key，自持密钥） | 密钥材料始终留在你自己的 HSM 或外部密钥管理方，永不进入云厂商 KMS | 云厂商只持有密文；每次加解密需经你方 HSM 批准，断开即不可解密 |

辨析要点：BYOK 解决的是“密钥从哪来”的问题，不等于“密钥现在谁能用”——导入后密钥的运算仍由厂商 KMS 执行，访问策略仍须管好。HYOK 解决的是“密钥现在在哪”的问题，代价是每次运算多一次到你方 HSM 的往返、你方 HSM 一旦不可用云上解密也随之停摆。选哪种形态，先看合规与数据主权要求，再看运维能力，不要只看宣传口径。

### 3.6 互操作：KMIP

不同厂商的密钥服务之间要互通，需要一套公共协议。KMIP（Key Management Interoperability Protocol，密钥管理互操作协议）是 OASIS 制定的标准，让存储、数据库、虚拟化平台等客户端能向中心密钥服务器请求创建、获取、轮换、吊销与销毁密钥；其对象状态（预激活、激活、停用、泄露、已销毁等）与 NIST SP 800-57 的状态框架对应。具体版本与实现支持情况，以 OASIS 官方发布为准（待核实项见文末）。

## 4. KMS 与 HSM 怎么选

| 场景 | 更适合的起点 | 原因 |
|---|---|---|
| 普通应用、数据量中等、团队无专职密码运维 | 托管 KMS | 轮换、审计、备份由服务方承担，团队专注访问策略与调用审计 |
| 受监管场景、密钥必须由客户方生成或审计方要求密钥来源证明 | BYOK + 托管 KMS | 保留密钥来源控制权，同时不自建全套运维 |
| 数据主权要求高、云厂商必须被排除在解密路径之外 | HYOK / 自有 HSM | 密钥材料永不进入云厂商边界，代价是自建高可用与运维 |
| 支付、发卡、密钥托管等高保障场景，或法规明确要求硬件保护 | 自有或独占 HSM | 硬件边界 + FIPS 140-3 高等级验证 + 专属管控 |
| 密钥量极大、调用极频繁 | 包封加密 + 分层密钥 | KMS/HSM 只保护 KEK，业务数据走本地 DEK，避免调用瓶颈 |

选型时先回答五个问题，再谈厂商：密钥丢了谁负责恢复？密钥泄露了多久能发现、多久能轮换完？审计日志谁能看、保存多久？密钥服务不可用时业务降级成什么样？退出时密钥与数据怎么交接？这五个问题答不上来，选哪个厂商都会在同一个地方出事。

## 5. 风险与常见误解

- **风险：把 KMS 当成“加密了就安全”**：KMS 只管密钥，不管应用漏洞、端点安全与访问策略。应用服务器被攻破后，攻击者可能直接调用应用已有的 KMS 权限——密钥没泄露，数据照样被解密。规避：按最小权限配调用策略，密钥调用与应用身份绑定，异常调用告警。
- **风险：单点依赖**：密钥服务一停，所有依赖它的解密都停。规避：评估服务可用性与区域容灾，关键路径做降级预案并演练；HYOK 场景更要把自有 HSM 的高可用当作一等大事。
- **风险：删除即失去数据**：计划删除密钥后，依赖它的全部数据将无法解密。规避：删除前设等待期（服务侧一般提供可配置的等待窗口，具体以官方文档为准）、核对依赖清单、演练恢复路径；生产删除操作须双人复核。
- **误解：HSM 里密钥就“绝对安全”**：HSM 抬高的是提取与篡改的门槛，不是消除全部风险——接口权限配错、运维流程失控、备份保管不当，同样会出事。硬件边界要配上正确的策略与审计才完整。
- **误解：FIPS 等级越高，应用就越安全**：等级验证的是密码模块，不是你的应用架构。Level 3 的 HSM 配上硬编码的调用凭证，整体安全性仍由最短板决定。
- **误解：BYOK 后云厂商就看不到数据了**：BYOK 导入后，密钥运算仍在厂商 KMS 内执行；要让厂商在任何情况下都无法解密，需要的是 HYOK（密钥材料永不进入厂商边界），而不是 BYOK。
- **误解：KMS 可以替代密钥生命周期管理**：KMS 是执行生命周期操作的工具，密码周期、轮换演练、泄露应对、销毁清单这些管理决策仍须由使用方制定（见[密钥生命周期管理](10-key-lifecycle-management.md)）。

## 7. 小结

KMS 是把密钥保管集中成服务的办法，HSM 是把保管边界收进防篡改硬件的办法，包封加密是两者与大数据量共存的办法。选型不看宣传看五问：恢复、发现、审计、降级、退出。工具再好，密码周期与轮换演练仍是使用方自己的功课。
