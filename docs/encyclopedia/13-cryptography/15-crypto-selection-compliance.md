# 密码算法选型与合规要点

> 本篇只讲选型原则与合规要求。**不讲绕过合规检查、降低安全配置、关闭校验、伪造合规证明的方法；“降级兼容”不是修复手段，不在本篇推荐。** 凡是会变动的清单（证书状态、标准现行版本、具体适用范围），一律以官方发布为准，本文不替官方背书。
>
> 一句话结论：选型不是挑“最强的算法”，而是挑“一套互相匹配、现行标准认可、能轮换、能审计”的组合——强度看最短板，合规看模块与配置，迁移看时间表。

## 1. 技术原理：选型先看什么

选型之前先定三件事，顺序不能乱：

1. **任务是什么**：保密（加密）、完整性（哈希 / 认证）、身份（签名）、密钥协商、口令存储——任务不同，算法不同。拿哈希当加密、拿加密当签名，都是选型错误，见[对称与非对称密码](01-symmetric-asymmetric.md)与[哈希与数字签名](02-hash-signature.md)。
2. **安全强度是多少**：用比特数衡量，系统整体强度由最短板决定。AES-256 配 RSA-2048，整体仍是 112 比特那一档——成套看，不要只看其中一个数字。对照表见[对称与非对称密码](01-symmetric-asymmetric.md)第 3.5 节；新系统默认按 128 比特强度起步（AES-128、RSA-3072、ECC P-256 这一档）。
3. **生命周期有多长**：数据要保密多久、证书有效期多长、算法退役时间表是什么。保密期长的历史数据，要为“未来算法退役、未来计算能力变化”留出迁移余量；短期会话数据与长期归档数据的选型可以不同，但都要写进迁移计划。

### 1.1 四条选型原则

- **用标准算法，不自造算法**：算法公开、经受检验是前提；自造与魔改实现不在选型表里，无论它“看起来多快”。
- **默认 AEAD，不裸加密**：新系统的数据加密默认选带认证的模式（AES-GCM、ChaCha20-Poly1305），只加密不校验的方案需要额外论证，见[分组密码模式与 AEAD](04-block-cipher-modes-aead.md)。
- **密钥与算法分开选**：算法选对了，密钥长度、生成方式、保管方式、轮换周期还要单独过关，见[密钥生命周期管理](10-key-lifecycle-management.md)。
- **密码敏捷性**：算法与密钥长度写成可配置项；标准一变、算法一退役，能走配置与迁移流程切换，而不是全库翻代码。

## 2. 适用范围与合规边界

- **本文的适用范围**：为新系统选型、为旧系统制定迁移计划、为合规审计准备算法清单。具体的采购、投标、审计结论，以合同、监管要求与官方清单为准，本文不代替合规结论。
- **合规边界**：合规要求来自标准与监管两个方向——算法是否现行标准认可、模块是否经过验证、配置是否落在认可模式内。三者缺一不可：算法正确不等于模块已验证，模块已验证不等于配置正确。
- **不覆盖的内容**：具体产品的合规认证申请流程、某个机构的内部审批流程、跨境数据传输的法律判断——这些以官方发布与专业法律意见为准，本文不展开，见未完成项。

## 3. 实验环境

- 环境：自有设备（代理 VM，隔离演示目录，演示数据为临时测试串，不含真实密钥与真实用户数据）。
- 软件与版本：OpenSSL 3.0.13（见第 8 节实测记录）。本机查询显示默认提供方列出了 SM4 与 SM2 实现——这只是“本机库支持查询”的结果，**不等于合规认证**，合规认证看的是模块证书与配置，见第 6 节。
- 权限要求：演示只需普通用户权限；合规审计需要只读的算法清单与配置读取权限，不需要生产密钥。

## 4. 风险

- **退役算法风险**：继续在新签名、新加密路径上使用已退役算法，等于把已知弱点写进新系统；历史数据的校验需求要单独处理，不能因此把退役算法留在新路径上。
- **短板风险**：混用不同强度（长对称密钥配短非对称密钥、强算法配弱随机源），整体强度被最短板拖低。
- **“算法合规、模块不合规”风险**：用了 AES、SHA-256 这类认可算法的系统，如果跑在未经验证的模块里、或运行在非认可模式下，合规审计仍可能不通过——审计查的是模块证书编号与运行模式，不是算法名字。
- **宣传数字风险**：厂商宣传的“速度提升倍数”“等效强度”一律不采信；选型依据只认标准文本、公开清单与可复现的实测。
- **量子 horizon 风险**：RSA 与 ECC 在理论上受 Shor 算法影响，但这需要大规模容错量子计算机，目前不存在；后量子迁移是进行中的工程工作（见第 7 节），不是今天就要恐慌、也不是可以无限期拖延的事——长期保密数据要先做清查与迁移排序。

## 5. 检测方式

合规审计的检测，本质是给系统做一份**密码算法清单**，再逐项对照现行标准。只写检测侧，不写规避检测的方法。

1. **拉清单**：从代码、配置、依赖里列出全部算法名、模式、密钥长度、协议版本（TLS 版本、证书签名算法），包括间接依赖带进来的算法。
2. **对照退役表**：清单里的每一项，对照第 6 节选型表与现行标准文本：退役项列入迁移清单，存疑项标注“以官方发布为准（待核实）”，不要凭印象放行。
3. **查模块证书**：声称“已验证”的模块，核对证书编号、证书状态（现行 / 历史）、模块版本与安全策略里的认可模式，再核对实际部署的版本与模式是否一致——产品名被验证过，不等于你部署的这个版本被验证过。
4. **查配置**：TLS 版本与算法套件、证书校验开关、密钥长度下限、口令哈希参数，是否落在认可范围内；测试环境的宽松配置有没有隔离、有没有带进生产。
5. **查生命周期**：密钥与证书的生成时间、轮换记录、吊销记录是否可查；长期未轮换项先列入清单，再按业务影响排期，见[密钥生命周期管理](10-key-lifecycle-management.md)。

## 6. 修复与防御方法：选型表与迁移路径

### 6.1 新系统默认选型表

| 任务 | 默认选型 | 不选（新系统） | 依据与说明 |
|---|---|---|---|
| 对称加密 | AES-GCM（AES-128 / 256）或 ChaCha20-Poly1305 | DES、3DES、RC4、ECB 模式 | FIPS 197（AES）；AEAD 一次完成加密与认证 |
| 哈希（完整性 / 签名摘要） | SHA-256 / 384 / 512 或 SHA-3 | MD5、SHA-1（新签名路径） | FIPS 180-4（SHA-2）、FIPS 202（SHA-3）；SHA-1 仅遗留校验场景，以官方过渡安排为准 |
| 非对称加密 / 密钥协商 | RSA-3072（128 比特档）或 ECC P-256 / X25519、ECDH | RSA-2048 以下（新系统）、静态 RSA 密钥协商 | NIST SP 800-57 Part 1 Rev. 5 强度对照；TLS 1.3 已删静态 RSA 协商 |
| 数字签名 | RSA-PSS、ECDSA（确定性随机数，RFC 6979）、Ed25519 | 随机数实现不可审计的 ECDSA、SHA-1 签名 | 见[哈希与数字签名](02-hash-signature.md)；签名随机数问题见[密码学误用案例分析](14-crypto-misuse-cases.md) |
| 口令存储 | 独立随机盐 + 慢哈希（Argon2、bcrypt 一类） | 明文、普通快哈希、无盐哈希 | 详见[口令哈希与存储](06-password-hashing-storage.md)，本篇只定原则 |
| 传输保护 | TLS 1.3 优先，TLS 1.2 仅作兼容保留 | TLS 1.0 / 1.1、关闭证书校验 | RFC 8446（TLS 1.3）；握手与证书链见 [TLS 与证书体系原理](03-tls-pki.md) |
| 密钥派生 | 标准 KDF（HKDF、PBKDF2 一类，按场景选） | 直接把口令、时间戳当密钥用 | 派生参数（盐、迭代次数）按现行指南取，口令派生见[口令哈希与存储](06-password-hashing-storage.md) |

### 6.2 迁移路径：旧系统怎么退场

1. **先清查，再排期**：按第 5 节拉出清单，按“新签名路径 > 新加密路径 > 历史数据校验”排优先级；历史数据只校验、不产生新签名的场景，可以单独设过渡期，但过渡期与责任人要写下来。
2. **双轨过渡**：新数据走新算法，旧数据在受控流程里解密重加密或重签名；过渡期内新旧并存是正常的，但“并存”要有截止日期，没有截止日期的并存就是永久保留退役算法。
3. **密钥同步轮换**：算法迁移时顺带轮换受影响密钥；只换算法不换密钥，等于给旧密钥续命——密钥若已可疑，轮换优先于算法迁移。
4. **回归验证**：迁移后跑第 5 节的检测清单复查，确认退役算法调用已清零（或仅剩有书面过渡期的历史校验点），并把清单留档备审计。

### 6.3 国密 SM 系列概述

国密（商用密码）算法是中国自主的密码算法体系，与国际主流算法形成对应关系：SM2 对应椭圆曲线公钥体制，SM3 对应 256 位哈希，SM4 对应 128 位分组密码，SM9 为基于标识的密码体制。下表只列经核查的标准编号与名称对应关系，具体适用场景与现行版本以官方发布为准。

| 算法 | 类型与功能 | 标准编号（核查结果） | 对应关系（功能层面） |
|---|---|---|---|
| SM2 | 椭圆曲线公钥密码：数字签名、密钥交换、公钥加密 | GB/T 32918 系列（行业标准 GM/T 0003 系列） | 功能对应 RSA / ECDSA / ECDH 一类体制 |
| SM3 | 密码杂凑算法，256 位输出 | GB/T 32905—2016（行业标准 GM/T 0004—2012） | 功能对应 SHA-256 |
| SM4 | 分组密码，128 位分组、128 位密钥 | GB/T 32907—2016（行业标准 GM/T 0002—2012） | 功能对应 AES-128 |
| SM9 | 标识密码算法：基于标识的签名、加密、密钥交换 | GB/T 38635 系列（行业标准 GM/T 0044 系列） | 无直接一一对应的国际体制；以标识本身作公钥，无需事先分发证书 |

选型注意事项（只讲原则，不代替合规结论）：

- **“支持国密算法”不等于“合规产品”**：库支持某个算法，只是功能层面的事实；合规层面还要看产品与模块是否通过相应检测认证、部署模式是否符合要求——这三层要分开核查，见第 5 节第 3、4 步。
- **国密与国际算法并存是常态**：同一系统里国密与国际算法可能按场景分工（例如境内合规场景与跨境互通场景），并存方案要写清“哪个场景走哪套、切换条件是什么”，不要在同一条链路上无规则混用。
- **SM4 的模式问题与 AES 相同**：SM4 是分组密码，同样需要正确的工作模式；只加密不校验、ECB 模式的问题在 SM4 上一样存在，修复方向见[密码学误用案例分析](14-crypto-misuse-cases.md)与[分组密码模式与 AEAD](04-block-cipher-modes-aead.md)。
- **涉及中国境内商用密码应用的场景**，具体适用范围、产品与服务管理要求，以《密码法》及国家密码管理部门现行发布为准（待核实，见未完成项）；本文不给出“某场景必须用国密”的断言。

### 6.4 模块验证：FIPS 140-3 看什么

- **验证对象是模块，不是算法**：FIPS 140-3 验证的是具体实现（某个库、固件、硬件的某个版本），验证结果由 NIST 与加拿大 CCCS 联合运行的密码模块验证计划（CMVP）以证书形式发布；查证时认证书编号与状态，不认产品宣传语。
- **查证三要素**：证书是否现行有效、部署的模块版本是否与证书一致、运行模式是否为证书安全策略里的认可模式。三者有一项对不上，合规结论就要存疑。
- **历史证书问题**：已转入历史清单的证书不代表算法突然变弱，但代表它不再作为现行验证依据——新采购、新部署以现行证书为准，具体清单状态以 CMVP 公开清单为准（待核实，见未完成项）。

### 6.5 常见误解

- **误解：密钥越长越安全**：超过需求加长只拖慢速度，不提升整体强度（短板原则）；且错误用法会让长密钥也白搭。
- **误解：有国密 / 有 FIPS 字样就合规**：合规看的是标准编号、模块证书、运行模式三层，不是宣传页上的字样。
- **误解：后量子算法一到就全量切换**：后量子迁移要按数据保密期排序，先清查、再试点、再分批切；没有清单的“全面切换”口号，执行时必然遗漏。
- **误解：合规就是安全**：合规是底线，不是上限；通过合规清单的系统，仍要按[密码学误用案例分析](14-crypto-misuse-cases.md)做误用审计。

## 7. 历史与案例

- **算法退役是常态，不是例外**：MD5（2004 年实际碰撞公开）、SHA-1（2017 年 SHAttered 首次实际碰撞公开）先后从安全场景退役；3DES 按 NIST SP 800-131A Rev. 2 的过渡安排不再用于新加密。教训：选型表要定期对照现行标准复核，写进清单的算法不是一劳永逸的。
- **后量子标准落地（2024 年 8 月）**：NIST 发布首批后量子标准 FIPS 203（ML-KEM，密钥封装）、FIPS 204（ML-DSA，数字签名）、FIPS 205（SLH-DSA，基于哈希的签名）。教训：长期保密数据的迁移排序现在就该开始做清查；具体部署细节与时间表以 NIST 现行迁移指南为准（待核实，见未完成项）。
- **TLS 版本退役**：TLS 1.0 / 1.1 已被 IETF RFC 8996 废弃，新部署不选；TLS 1.3（RFC 8446）删掉了静态 RSA 密钥协商与一批不安全老算法——“少给选择就少出错”本身就是一种选型设计。

## 8. 实测对照：正确用法长什么样

以下命令均在代理 VM 上真实运行过，环境：OpenSSL 3.0.13；演示数据为临时测试串 `hello-crozz-demo`（无换行），演示密钥为临时生成、用后删除，不含任何真实密钥。

```bash
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)

$ printf 'hello-crozz-demo' | openssl dgst -sha256
SHA2-256(stdin)= 8e71c394f4a43fb542c69ab01a2f49ac37d58ba02ff7e694c39767d7aa38a381

$ printf 'hello-crozz-demo' | openssl dgst -sm3
SM3(stdin)= 1f9d54ddc6b2420ea2b6781c99e459312f2f99c6567569a78a4f2e73c63011ec

$ openssl genpkey -algorithm ED25519 -out edkey.pem
$ openssl pkeyutl -sign -inkey edkey.pem -rawin -in plain.txt -out sig.bin
$ openssl pkeyutl -verify -pubin -inkey edpub.pem -rawin -in plain.txt -sigfile sig.bin
Signature Verified Successfully
```

实测结论（只写跑过的结果）：

1. **摘要对照**：SHA-256 与 SM3 对同一输入各自输出固定摘要——选型时“哈希输出长度相同”不等于“算法可互换”，互通场景要按标准与协议约定选，不能凭输出长度混用。
2. **签名闭环**：Ed25519 临时密钥签名后公钥验证通过，这是签名选型的最小正确闭环；生产选型还要补密钥保管、轮换与证书链，见[密钥生命周期管理](10-key-lifecycle-management.md)。
3. **本机支持查询不等于合规**：本机 OpenSSL 默认提供方列出 SM4 与 SM2 实现，且 `openssl enc -aes-256-gcm` 实测返回 `AEAD ciphers not supported`——前者只说明本机库支持，后者提醒 AEAD 不要走 `openssl enc`（见[密码学误用案例分析](14-crypto-misuse-cases.md)第 8 节）。AEAD 的库接口示例未在本机以 OpenSSL 实测，暂不写成 OpenSSL 实测示例。
