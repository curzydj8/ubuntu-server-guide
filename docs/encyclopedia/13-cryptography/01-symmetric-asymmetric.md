# 对称与非对称密码

## 1. 一句话定义

对称密码是收发双方用**同一个密钥**加解密的密码；非对称密码是每方持有一对密钥，**公钥公开、加密用公钥，私钥保密、解密用私钥**（签名时方向反过来，见[哈希与数字签名](02-hash-signature.md)）。

## 2. 为什么需要它

两个人要在公开信道上说悄悄话，最原始的办法是事先约好一套暗语。但暗语本身怎么安全地交给对方？如果每次通信都要先见面交换暗语，互联网就没法用了。对称密码解决了“怎么把明文变成看不懂的密文”，非对称密码进一步解决了“密钥本身怎么分发”——公钥可以贴在墙上，私钥永远不用出门。两者合起来，才有了今天 HTTPS、加密聊天、软件签名的基础。

## 3. 核心含义

### 3.1 对称密码：同一把钥匙开锁和锁门

加密与解密用同一个密钥。发送方用密钥把明文变成密文，接收方用同一密钥还原。流程极简：

```
明文 ──密钥 K 加密──▶ 密文 ──密钥 K 解密──▶ 明文
```

优点是速度快，适合加密大量数据；缺点是密钥分发难——密钥必须事先安全地交到双方手里，一旦泄露，之前用它加密的全部内容都可能被还原（除非每次更换密钥）。所以对称密码的真正难题往往不是算法，而是**密钥怎么来、怎么换、怎么管**，这部分应用实践见[秘密信息管理](../../02-security/09-secrets-management.md)。

### 3.2 分组密码与流密码

对称密码按一次处理多少数据分两类：

- **分组密码（block cipher）**：把明文切成固定大小的块（例如 AES 每块 128 位），一块一块加密。代表算法：AES（NIST FIPS 197，2001 年发布），密钥长度 128 / 192 / 256 位。
- **流密码（stream cipher）**：把密钥扩展成一串密钥流，逐字节（或逐位）与明文异或。代表算法：ChaCha20（RFC 8439）。流密码没有“块”的概念，适合长度不定的数据流。

分组密码还需要一个**工作模式**来规定“块与块之间怎么衔接”。其中一个必须知道的反面例子是 ECB 模式：每个块独立加密，相同明文块永远产生相同密文块，密文会泄露明文的结构（例如一张图片加密后轮廓仍可见）。现代实践用带认证的模式，例如 AES-GCM（GCM 同时提供加密与完整性校验，属于认证加密 AEAD），不要在新系统里用 ECB。

### 3.3 非对称密码：两把钥匙，各管一头

非对称密码每方有一对密钥：公钥可以公开，私钥必须保密。两个方向各做一件事：

- **加密方向**：任何人用接收方的**公钥**加密，只有接收方用**私钥**能解密。解决密钥分发问题。
- **签名方向**：发送方用自己的**私钥**签名，任何人用发送方的**公钥**验证。解决“这话真是你说的、且没被改过”问题（详见[哈希与数字签名](02-hash-signature.md)）。

代表体制：

- **RSA**（1977 年，Rivest、Shamir、Adleman）：安全性建立在大整数分解的困难性上。公钥是一对大数，私钥与之对应；加密与签名的数学细节不需要在这里展开，记住“公钥能做的事，私钥能反向做”就够了。
- **椭圆曲线密码 ECC**：在椭圆曲线点运算上建立的体制，达到相同安全强度所需的密钥短得多（例如 256 位 ECC 约相当于 3072 位 RSA，见 3.5 节）。手机、物联网、TLS 1.3 的密钥协商里大量使用 ECC。

### 3.4 密钥交换的思想：不传送密钥，也能共享秘密

Diffie-Hellman（1976 年）解决了一个看似不可能的问题：双方只在公开信道上交换几条公开消息，最后却各自算出同一个秘密，而偷听者算不出来。这个秘密随后可以当作对称密钥使用。现代变体是 ECDH（椭圆曲线版），TLS 1.3 的握手就用 (EC)DHE 做密钥协商，并由此获得**前向保密**（见 [TLS 与证书体系原理](03-tls-pki.md)）：即使服务器私钥日后泄露，之前会话的密钥也推不出来，因为每次会话的协商参数都是一次性的。

注意：原始 Diffie-Hellman 本身不认证对方身份，中间人可以冒充两边各谈一次。因此实际系统里密钥交换必须配合身份认证（例如证书），裸用 DH 是不安全的。

### 3.5 密钥长度与安全强度：位数不是直接比大小

“安全强度”用比特数衡量：强度为 n 比特，意味着攻击者大约要做 2^n 次尝试。不同体制达到同一强度所需的密钥长度差别很大（NIST SP 800-57 第 1 部分修订版 5 的近似对应关系）：

| 安全强度 | 对称密钥 | RSA 密钥 | ECC 密钥 |
|---|---|---|---|
| 112 比特 | 112 位 | 2048 位 | 224 位 |
| 128 比特 | 128 位 | 3072 位 | 256 位 |
| 192 比特 | 192 位 | 7680 位 | 384 位 |
| 256 比特 | 256 位 | 15360 位 | 521 位 |

三点结论：

1. **跨体制比位数没有意义**：256 位 ECC 不等于 256 位 RSA，前者约等于 128 比特强度，后者远超 256 比特强度。比的是安全强度那一列。
2. **112 比特是下限**：NIST 建议 112 比特强度可用至 2030 年，之后应迁移到 128 比特及以上；新系统直接按 128 比特选型（AES-128、RSA-3072、ECC P-256）。
3. **强度由最短板决定**：系统里混用 AES-256 与 RSA-2048，整体强度仍是 112 比特。选型要成套看，不要只看其中一个数字。

## 4. 分类

| 类别 | 代表 | 一句话特征 |
|---|---|---|
| 对称分组密码 | AES | 定长分块加密，需工作模式 |
| 对称流密码 | ChaCha20 | 密钥流逐字节异或，适合流数据 |
| 认证加密（AEAD） | AES-GCM、ChaCha20-Poly1305 | 加密 + 完整性校验一次完成，现代默认选择 |
| 非对称加密 | RSA 加密、ECIES | 公钥加密、私钥解密，解决密钥分发 |
| 密钥交换 | DH、ECDH | 公开信道协商共享秘密，需配合认证 |
| 数字签名 | RSA 签名、ECDSA、EdDSA | 私钥签名、公钥验证（详见下一篇） |

## 5. 典型应用

- **HTTPS 的传输加密**：握手阶段用非对称/密钥交换协商出会话密钥，之后的数据用对称密码（AES-GCM 或 ChaCha20-Poly1305）加密，兼顾安全与速度。握手全过程见 [TLS 与证书体系原理](03-tls-pki.md)。
- **磁盘与文件加密**：LUKS 磁盘加密用对称密码加密数据，密钥本身再由口令或密钥文件保护（应用做法见[LUKS 磁盘加密](../../02-security/10-luks-disk-encryption.md)）。
- **端到端加密聊天**：双方用非对称密码交换密钥、用对称密码加密消息，服务器只转发密文。
- **软件与固件签名**：发布方私钥签名、用户公钥验证，保证下载的东西确实来自发布方且未被篡改（机制见下一篇）。

## 6. 限制与常见误解

- **加密不等于认证**：只加密不校验完整性，攻击者可以篡改密文而不被发现（某些模式下甚至能推测明文）。现代系统默认用 AEAD，不要只做“裸加密”。
- **算法公开不是弱点**：现代密码的安全性建立在“密钥保密、算法公开”上（柯克霍夫原则）。靠算法保密的安全叫“隐匿式安全”，一旦算法泄露就全塌。不要自造算法、不要魔改标准算法。
- **密钥管理比算法选择更重要**：真实事故里，密钥硬编码进代码、随仓库泄露、长期不轮换，比算法本身被攻破常见得多。算法选对只是及格线。
- **误解：密钥越长越安全**：超过需求一味加长只会拖慢速度，不提升系统整体强度（见 3.5 节短板原则）；且错误使用（例如 ECB、IV 重复）会让长密钥也白搭。
- **误解：非对称可以加密一切**：非对称运算慢、密文长度受限，实际只用来加密小数据（会话密钥、哈希摘要），大数据一律走对称。
- **前瞻：量子计算的影响**：Shor 算法在理论上能破解 RSA 与 ECC，但需要大规模容错量子计算机，目前不存在。NIST 已发布后量子标准（ML-KEM，FIPS 203，2024 年），迁移是进行中的工程工作，不是今天就要恐慌的事；本篇不展开，后续前沿域再讲。

## 7. 小结

对称密码一把钥匙、速度快，难在密钥分发；非对称密码两把钥匙，公钥公开、私钥保密，解决了分发与签名问题；实际系统永远是两者混合：非对称协商密钥，对称加密数据。选型看安全强度那一列，不要跨体制比位数。
