# 密钥生命周期管理

> 本篇只讲密钥的管理流程与正确做法，不讲任何密钥提取、绕过保护机制或从内存、设备中取回密钥的方法。文中示例均为作者自有演示材料，所用密钥在演示后已销毁，生产密钥绝不能照搬演示里的存放方式。

## 1. 一句话定义

密钥生命周期管理，是从一把密钥生成开始，到它停止使用并被彻底销毁为止，对其生成、存储、分发、使用、轮换、停用、归档与销毁全过程加以记录、设限与审计的管理工作。

## 2. 为什么需要它

[对称与非对称密码](01-symmetric-asymmetric.md)里已经说过：真实事故里，密钥硬编码进代码、随仓库泄露、长期不轮换，比算法本身被攻破常见得多。算法选对只是及格线，密钥管不好，加密就等于没加密。

更具体地说，密钥管理要回答四个日常问题：这把密钥是谁生成的、在哪台机器上、谁能用？它还能用多久，什么时候必须换？它泄露了怎么办，旧数据还能不能解开？它退役之后，残留的副本是不是真的没了？没有生命周期管理，这四个问题在出事时一个都答不上来。

## 3. 核心含义：状态、阶段与密码周期

### 3.1 NIST SP 800-57 的阶段与状态

本篇的状态划分遵循 NIST SP 800-57 Part 1 Rev. 5《密钥管理建议》的框架。该标准把密钥的一生分成四个阶段，阶段之内再分状态：

| 阶段 | 包含的状态 | 一句话含义 |
|---|---|---|
| 使用前（pre-operational） | 预激活（pre-activation） | 已生成，尚未投入正常使用 |
| 使用中（operational） | 激活（active）、暂停（suspended） | 激活态可保护与处理数据；暂停态一般只可处理已受保护的数据，不再保护新数据 |
| 使用后（post-operational） | 停用（deactivated）、泄露（compromised） | 不再用于正常业务；停用态仍可解密旧数据，泄露态则不可再信任 |
| 已销毁（destroyed） | 已销毁（destroyed）、已销毁且曾泄露（destroyed-compromised） | 密钥材料已不可用；元数据（如名称、类型、密码周期记录）可以保留，事后发现泄露仍须记入审计 |

两条状态规则必须刻在流程里：

1. **停用不等于销毁**。停用的密钥材料还在，只是“不再给新数据加密”。删掉使用权限、停掉自动续期，都不等于删掉了密钥本身。
2. **泄露态不可复活**。一旦确认或高度怀疑泄露，该密钥就不能再被重新激活回正常使用，只能走泄露应对流程（见 6.3 节）。事后才发现“销毁前其实已经泄露”，也要补记为已销毁且曾泄露，而不是悄悄改成普通销毁。

### 3.2 密码周期（cryptoperiod）：一把密钥能用多久

密码周期是指一把密钥被授权使用的时间跨度。SP 800-57 把它拆成两段：

- **产生方使用期（originator-usage period）**：密钥可以用来保护新数据的时间，例如用它加密新文件、签署新文档。
- **接收方使用期（recipient-usage period）**：密钥可以用来处理已受保护数据的时间，例如解密旧文件、验证旧签名。这一段通常比产生方使用期长。

SP 800-57 表 1 给出的建议起点（不是硬性上限，具体期限须按风险评估定）包括：

- 对称数据加密密钥、密钥包装密钥：低流量场景下产生方使用期一般不超过 2 年，接收方使用期一般不超过产生方使用期再加 3 年；大流量或链路加密场景下，产生方使用期可能短到约一天或一周。
- 私钥签名密钥：产生方使用期一般为 1 至 3 年；与之对应的公钥验证期可以更长，因为旧签名可能需要在多年后仍能验证。

密码周期的意义有三点：限制一把密钥保护的数据量，从而限制一次泄露的 blast 半径；限制密码分析可用的密文样本量；逼着组织定期演练轮换，而不是等到出事才第一次换密钥。期限本身不是目的——“到期就换、换完能验证、旧数据仍可读”这个闭环才是目的。

### 3.3 生成：随机性是第一道关

密钥的安全性首先取决于生成时的随机性。SP 800-57 要求使用经批准的随机数发生器生成密钥材料。实践要点：

- 用操作系统或密码模块提供的密码学安全随机源生成，不要用普通伪随机数、时间戳、进程号或自编算法“凑”密钥。
- 生成环境本身要可信：高保障场景在硬件安全模块内生成（见 [KMS 与 HSM 入门](11-kms-hsm-intro.md)）；普通场景至少要在受控主机上生成，生成过程不留屏显、不进聊天记录、不贴进工单。
- 生成即登记：密钥标识、用途、算法与长度、生成时间、产生方使用期截止时间、保管位置、负责人，生成那一刻就记下来。事后补记的台账永远补不齐。
- 一密钥一用途：加密密钥、签名密钥、包装密钥不要混用。用途写进密钥元数据与访问策略，而不是只写在某个人的记忆里。

### 3.4 存储与分发：密钥与数据分开，密钥与密钥分开

存储与分发的总原则只有一条：**密钥不能和它保护的数据放在同一个篮子里，也不能和访问它的口令放在同一个地方**。

- **分层保护**：用密钥加密密钥（KEK 包装 DEK），是标准做法。数据加密密钥（DEK）负责加密大量数据，密钥加密密钥（KEK）只负责包装 DEK，本身极少直接接触数据。分层之后，轮换 KEK 不必重加密全部数据，轮换 DEK 也不必惊动 KEK 的保管流程。包封加密（envelope encryption）的完整形态见 [KMS 与 HSM 入门](11-kms-hsm-intro.md)。
- **权限最小化**：能用密钥加密的人，不一定需要能解密；能调用密钥的人，不一定需要能看到密钥材料本身。理想形态是“调用运算、不见材料”：应用只向密钥服务发起“请用这把密钥加密/解密”的请求，密钥材料不出服务边界。
- **传输保护**：密钥分发必须走已认证、已加密的通道，接收方要验证来源与完整性。把密钥贴进代码仓库、聊天工具、工单附件、未加密邮件，都是分发事故，不是因为“有人偷看”才算事故，发出那一刻就已经算。
- **备份与恢复是同一枚硬币的两面**：密钥丢了，数据就等于丢了；备份做得太随意，密钥就等于泄露了。备份必须与生产密钥同等保护、异地存放、定期演练恢复，并且备份清单本身也要进台账——销毁时要销毁的正是“生产 + 备份 + 归档”全部副本（见 6.4 节）。

### 3.5 使用：只在授权用途与授权期限内

使用阶段的管理，核心是“让正确的使用顺畅，让错误的使用立刻可见”：

- **用途绑定**：签名密钥不用来加密，加密密钥不用来签名，测试密钥不进生产。用途越界的调用应当被策略拒绝并记入审计，而不是靠使用者的自觉。
- **用量也要设限**：密码周期不只看日历，还要看用量。例如 AES-GCM 在随机 96 位初始向量（IV）下，NIST SP 800-38D 建议同一密钥的加密次数上限为 2^32 次——高频系统可能在日历到期之前就先触到用量上限。日历与用量，哪个先到就按哪个轮换。
- **审计不可关**：每次关键操作（生成、启用、轮换、停用、销毁、访问失败）都要留下“谁、何时、对哪把密钥、做了什么、结果如何”的记录。审计日志本身要防篡改、定期复核；没有审计的密钥管理，出事后无法定性是“泄露”还是“误操作”，也就无法决定旧数据还能不能信。

## 4. 合法研究与实验范围

本篇讨论的管理操作只适用于以下范围：你自己的设备、你有权管理的系统、隔离的演示环境。在他人系统上测试密钥管理流程、尝试访问他人密钥，均不在本篇讨论内，且可能违法。

文中实验环境为代理 VM（Ubuntu，OpenSSL 3.0.13），全部材料均为演示生成、用后销毁，不含任何真实生产密钥。

## 5. 实验：生成、权限与轮换演示（实测通过）

以下命令均在代理 VM 上真实运行过，环境：Ubuntu（Linux 内核 7.0.0-39-generic，x86_64），OpenSSL 3.0.13。演示只证明流程本身可行，**不是生产配置**：生产环境应使用 KMS/HSM（见下一篇），而不是把口令文件与密文放在同一目录。

### 5.1 生成并收紧权限

```bash
# 生成 32 字节（256 位）对称密钥材料与一对 Ed25519 演示密钥
openssl rand -out sym-v1.bin 32
openssl genpkey -algorithm ED25519 -out ed-v1.pem
openssl pkey -in ed-v1.pem -pubout -out ed-v1.pub
chmod 600 sym-v1.bin ed-v1.pem
stat -c '%a %s %n' sym-v1.bin ed-v1.pem
```

实测输出（节选，不含任何密钥材料本身）：

```text
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
600 32 sym-v1.bin
600 119 ed-v1.pem
```

实测中值得注意的一个细节：刚生成的 `sym-v1.bin` 初始权限是 `660`（受当前 umask 影响），执行 `chmod 600` 后才变为仅所有者可读写。**生成后不检查权限，就等于没做权限管理**——把 `stat` 或 `ls -l` 检查写进生成脚本，而不是靠事后想起来。

### 5.2 轮换演示：新密钥加密新数据，旧密钥只解旧数据

轮换的正确语义不是“旧密钥立刻作废”，而是“旧密钥不再保护新数据，但仍能处理旧数据，直到旧数据全部迁移或到达接收方使用期终点”。演示用两份口令文件代表两代密钥，对同一份演示明文做“v1 加密 → v1 解密 → v2 加密 → v2 解密”的完整闭环：

```bash
openssl rand -hex 32 > hex-v1.txt
openssl rand -hex 32 > hex-v2.txt
# v1 加密
openssl enc -aes-256-cbc -salt -pbkdf2 -in plain.txt -out cipher-v1.bin -pass file:hex-v1.txt
# v1 解密验证，再用 v2 重新加密
openssl enc -aes-256-cbc -salt -pbkdf2 -d -in cipher-v1.bin -out plain-v1.txt -pass file:hex-v1.txt
openssl enc -aes-256-cbc -salt -pbkdf2 -in plain-v1.txt -out cipher-v2.bin -pass file:hex-v2.txt
openssl enc -aes-256-cbc -salt -pbkdf2 -d -in cipher-v2.bin -out plain-v2.txt -pass file:hex-v2.txt
diff plain.txt plain-v2.txt && echo ROTATION_OK
```

实测结果：`ROTATION_OK`。另测过渡期语义：旧密钥仍能解密旧密文（`OLD_STILL_DECRYPTS`），而新密钥解密旧密文失败，退出码为 1 并报 `bad decrypt`。这正是轮换期间应有的状态——**新旧密钥各管各的数据，互不串台**。

轮换清单（每次轮换都应照单执行）：生成新密钥并登记 → 新数据改用新密钥 → 旧数据按计划重加密或保留旧密钥的解密能力至接收方使用期终点 → 更新所有调用方配置 → 验证新密钥路径与旧数据读取路径各跑通一次 → 旧密钥转停用，记入台账。跳过验证直接停用旧密钥，是轮换事故最常见的起因。

### 5.3 销毁演示：删文件不等于销毁，要覆盖全部副本

演示中对一份旧密钥副本执行 `shred -u` 后，目录中已找不到该文件：

```text
ls: cannot access 'old-copy-to-destroy.txt': No such file or directory
```

但这只是演示层面的“文件已删”，**不能当作生产销毁的证明**：固态硬盘的磨损均衡、写时复制文件系统、快照与备份，都可能让“已删”文件仍有残留。生产销毁必须覆盖生产、备份、归档、密钥加载器上的全部副本，并按介质清理标准（如 NIST SP 800-88 Rev. 1 的介质清理指南）执行与记录；演示结束后，本文全部演示材料均已用 `shred -u` 删除，演示目录已清空。

## 6. 风险、检测与防御

### 6.1 主要风险

| 风险 | 规避做法 |
|---|---|
| 密钥硬编码进代码、随仓库泄露 | 密钥只进密钥服务或受控保管位置；仓库做密钥扫描，检出即按泄露流程处理，而不是只删代码 |
| 密钥与数据同处一地 | 分层保护（KEK/DEK），密钥服务与数据存储分离部署、分离权限 |
| 长期不轮换、无人记得密码周期 | 台账 + 到期告警 + 定期轮换演练；密码周期写进策略，不是写进备忘录 |
| 轮换时旧数据读不出来 | 先验证新旧两条路径再停用旧密钥；保留接收方使用期内的解密能力 |
| 销毁不彻底（备份、快照残留） | 销毁清单覆盖全部副本位置；销毁操作留审计记录 |
| 审计缺失，出事无法定性 | 关键操作全量审计，日志防篡改、定期复核 |

### 6.2 检测方式

- **台账对账**：定期拿密钥台账与实际调用记录对账——台账上有、调用记录里没有的密钥可能是僵尸密钥；调用记录里有、台账上没有的密钥是失控密钥，两者都要查。
- **到期与用量告警**：对每把密钥设产生方使用期截止告警与用量阈值告警，提前一个轮换窗口报警，而不是到期当天才报警。
- **异常调用告警**：非工作时间、非预期来源、用途越界、连续解密失败，都应触发告警并留待复核。
- **泄露扫描**：对代码仓库、镜像、日志、工单附件做密钥材料扫描；检出后先冻结相关密钥的使用权限，再按 6.3 节处理。

### 6.3 泄露应对：先止血，再定性，最后轮换

1. **止血**：立即停用受影响密钥的“保护新数据”能力，冻结相关访问权限，保全审计日志与调用记录。
2. **定性**：确认泄露范围——哪些数据曾被该密钥保护、泄露发生在何时、是否波及备份与归档。定性不清时，按“已泄露”从严处理。
3. **轮换**：生成新密钥，新数据改用新密钥；旧数据按风险决定重加密或隔离；受影响的证书与签名按证书生命周期流程吊销与重发（见[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)）。
4. **复盘**：把泄露路径写进台账与整改项——是硬编码、权限过大、还是分发通道问题？只换密钥不改流程，下一次还会在同一个地方漏。

### 6.4 销毁：什么时候销毁，销毁什么

销毁的触发条件有三类：密码周期走完且旧数据已迁移或已过保存期；密钥被替换且接收方使用期已终结；业务下线，密钥不再有任何合法用途。销毁的对象是**全部副本**：生产存储、备份、归档、密钥加载器、历史快照中残留的副本都要覆盖；只删生产库、不清备份的“销毁”是假销毁。销毁后保留元数据与审计记录（密钥曾存在过、何时销毁、由谁执行），以备事后审计，但元数据里不得残留密钥材料本身。

## 7. 常见误解

- **误解：密钥长度够长就不用轮换**：长度防的是暴力破解，轮换防的是泄露扩散与长期暴露。两者解决的问题不同，不能互相替代。
- **误解：轮换就是把旧密钥删掉**：删旧密钥之前，旧数据必须已有出路（重加密完成，或旧密钥保留解密能力至接收方使用期终点）。先删后想，是数据丢失事故的标准写法。
- **误解：删文件就是销毁**：文件系统删除只是去掉索引，备份、快照、介质残留都还在。销毁要按介质清理标准走完整流程并留记录。
- **误解：密钥管理就是“找个地方存密钥”**：存储只是生命周期的一环；生成、期限、轮换、泄露应对、销毁缺了任何一环，存储做得再好也只是“安全地保管着一个迟早出事的密钥”。
- **误解：小系统不需要生命周期管理**：小系统更需要——因为小系统往往只有一个人记得密钥在哪、什么时候换的，这个人一离职，台账就是零。

## 8. 小结

密钥管理管的不是一把密钥，而是它的一生：生成时随机可信，存储时分层隔离，使用时用途与期限双约束，到期时轮换验证双路径，泄露时止血定性再轮换，退役时全部副本销毁并留审计。算法见[对称与非对称密码](01-symmetric-asymmetric.md)，证书侧的吊销与续期见[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)，保管的工程形态见下一篇 [KMS 与 HSM 入门](11-kms-hsm-intro.md)。
