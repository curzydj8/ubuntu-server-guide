# 分组密码模式与认证加密

> 本篇是[对称与非对称密码](01-symmetric-asymmetric.md)总览的深挖：总览讲了“分组密码需要工作模式、现代实践用 AEAD”这个结论，本篇讲每种模式到底怎么衔接分组、AEAD 的契约是什么、以及哪些用法错误会让正确的算法也失效。本篇只讲原理与正确用法，不讲任何破解、降级或绕过验证的操作步骤。

## 1. 本章目标

读完本篇，能说清 ECB、CBC、GCM、CCM 各自解决了什么、各自还缺什么，以及为什么新系统应当默认选 AEAD 而不是“裸加密 + 自拼校验”。

## 2. 背景与问题

AES 本身一次只处理一个 128 位分组（FIPS 197，密钥长度 128 / 192 / 256 位）。真实数据很少正好是一个分组：文件、消息、网络记录都是任意长度。于是需要一个**工作模式**回答三个问题：多分组之间怎么衔接？长度不足一个分组时怎么办？以及——最关键的一点——接收方怎么知道密文在路上没被改过？

前两个问题是“怎么加密”，第三个问题是“怎么验真”。只回答前两个的模式叫**普通模式**；把加密与验真一次做完的叫**认证加密**。总览已经给过结论：只加密不校验，攻击者可以篡改密文而不被发现。本篇把这个结论展开成可执行的选型规则。

## 3. 总体架构

```
明文 ──分组──▶ [工作模式 + 密钥 + nonce/IV] ──▶ 密文
                                                    │
普通模式：解密方只能还原明文，无法判断密文是否被改过
                                                    │
AEAD：   密文 + 认证标签 + 附加数据(AAD) ──验证──▶ 通过才给明文 / 失败则拒绝
```

AEAD 的标准接口（IETF RFC 5116）是四个输入、一个成败输出：

- 输入：密钥 K、nonce N（只用一次的数）、附加数据 A（Associated Data）、明文 P。
- 输出：密文 C 与认证标签 T。
- 解密：只有当标签对“密钥 + nonce + AAD + 密文”全部验证通过时才返回明文；任何一位对不上，解密就失败，且**不得返回明文**（fail closed，失败即关闭）。

附加数据 AAD 是 AEAD 最容易被低估的部分：它**不加密、但要验真**。典型用法是把“必须明文传输、但不许被改”的头部放进 AAD，例如记录序号、版本号、租户标识。接收方先读头部、再用它验标签，头部被改同样会导致验证失败。

## 4. 工作机制

### 4.1 ECB：每块独立加密，只当反面教材

ECB（Electronic Codebook）把每个分组用同一密钥独立加密：相同明文块永远产生相同密文块。总览已经指出后果——密文会泄露明文的结构。ECB 连“分组之间衔接”这个问题都没有真正回答，它只是把分组密码重复使用。

选型规则只有一条：**新系统不要用 ECB**。它在本文中出现，只是因为读旧代码、旧文档时还会遇到它，需要认得出、换得掉。ECB 没有 nonce、没有链式关系、没有标签，三个问题一个都没解决。

### 4.2 CBC：链式衔接，但仍然没有验真

CBC（Cipher Block Chaining）把前一个密文块混入下一个明文块再加密，并用一个初始向量 IV 启动第一块：

```
C[i] = Enc(K, P[i] XOR C[i-1])，其中 C[0] = IV
```

CBC 解决了 ECB 的结构泄露问题：相同明文块在不同位置、不同 IV 下会产生不同密文。但它仍有两个缺口：

1. **没有完整性**：CBC 本身不产生标签。只用 CBC 加密而不另外校验，接收方无法发现密文被改过。历史上“加密 + 自拼 MAC 拼错顺序”出过不少事故，正确做法是直接用 AEAD，而不是自己发明“加密后加校验”的组合方式。
2. **IV 要求严格**：CBC 的 IV 必须对每个消息都不可预测（实践中用密码学安全的随机数生成，每条消息换一个），且长度为一个分组（AES 是 128 位）。IV 本身不需要保密，可以随密文一起传输，但**绝不能固定、不能重复使用同一 IV 加密不同消息**。此外明文需填充到分组长度的倍数，填充本身的处理也有讲究——这些细节都应交给成熟的密码库，而不是手写。

CBC 今天的合理位置是：维护必须兼容的老系统、且已在外层补了正确校验的场景。新系统不优先选它。

### 4.3 CTR：把分组密码变成流

CTR（Counter）模式用“nonce + 计数器”作为输入块加密，得到一串密钥流，再与明文异或。它的优点是：不需要填充（密文与明文等长）、各块可以并行处理、解密与加密是对称操作。

CTR 的硬规则与 CBC 类似但更严格：**同一密钥下，nonce + 计数器的组合绝不能重复**。重复意味着同一段密钥流被用了两次，这在原理上等同于“一密一钥”被打破。CTR 本身同样没有标签，裸用 CTR 与裸用 CBC 犯的是同一个错误：只加密、不验真。

### 4.4 GCM：CTR 加密 + GHASH 认证，现代默认选择之一

GCM（Galois/Counter Mode，NIST SP 800-38D）是本篇的主角之一：加密部分就是 CTR，认证部分是 GHASH（在 GF(2^128) 上的多项式哈希），两者共用一个密钥，一次调用同时产出密文与标签。

核查过的参数（以标准为准，见文末来源）：

- 底层：AES，密钥 128 / 192 / 256 位。
- nonce：推荐 96 位（12 字节）；标准允许其他长度，但会多一次哈希处理，实践中统一用 96 位最省事、最不容易出错。
- 标签：常用 128 位（16 字节）；标准允许更短的标签，但缩短标签会降低伪造难度，没有充分理由不要缩短。
- 用量上限：同一密钥下认证加密的调用总次数不得超过 2^32 次（SP 800-38D 第 8 节），且单条消息也有长度上限——密钥不是无限用的，用量大了就轮换，轮换做法见[密钥生命周期管理](10-key-lifecycle-management.md)。

GCM 的硬规则只有一条，但必须刻进实现里：**同一密钥下 nonce 绝不能重复**。重复不仅泄露两条明文之间的关系，还会危及该密钥下全部消息的认证能力。正确做法是：随机生成 96 位 nonce（随机碰撞概率在合理用量下可忽略），或用不会重复的计数器构造 nonce，并在密钥轮换时把计数器一并重置——两者选一，不要混用，更不要把“时间戳”“自增 ID”这类可能回绕、可能重置的值直接当 nonce 用而不做唯一性论证。

GCM 的适用面最广：TLS 1.3 的两个 AES 密码套件（TLS_AES_128_GCM_SHA256、TLS_AES_256_GCM_SHA384）用的就是它，磁盘、数据库、云 KMS 信封加密里也常见。它的代价是：实现必须保证 nonce 唯一性，且在没有硬件加速的平台上不如 ChaCha20-Poly1305 快——选型时按平台定，不要按偏好定。

### 4.5 CCM：CTR 加密 + CBC-MAC 认证，约束环境的 AEAD

CCM（Counter with CBC-MAC，NIST SP 800-38C）是另一条 AEAD 路线：认证用 CBC-MAC、加密用 CTR，两遍处理同一份数据，只需要 AES 的加密方向（解密方向也不需要 AES 解密运算）。

核查过的参数：

- nonce 长度 7–13 字节，nonce 越长、单条消息允许的最大长度越小（例如 13 字节 nonce 时消息上限较小），两者是此消彼长的关系，选型时按消息规模定。
- 标签长度可配，常见 16 字节；约束环境里缩短标签前，同样要先论证伪造难度是否可接受。
- 同样要求：同一密钥下 nonce 不重复；标签验证失败时不得返回明文。

CCM 比 GCM 多一遍处理、不能并行认证，因此吞吐不如 GCM；它的优势是实现只需要 AES 加密原语、结构简单，适合资源受限的设备与已有 CBC-MAC 基础的协议（例如一些物联网与无线协议）。新系统在通用服务器与浏览器场景下优先 GCM，约束设备场景再评估 CCM——两者都是 AEAD，选哪个是工程取舍，不是安全等级的高低之分。

### 4.6 ChaCha20-Poly1305：非 AES 路线的 AEAD

ChaCha20-Poly1305（IETF RFC 8439）不是分组密码模式，而是“流密码 + 认证器”的 AEAD 组合：ChaCha20 负责加密、Poly1305 负责认证，同样一次调用产出密文与标签，同样支持 AAD。

核查过的参数：密钥 256 位（32 字节）、nonce 96 位、标签 128 位。它是 TLS 1.3 的第三个密码套件（TLS_CHACHA20_POLY1305_SHA256），在没有 AES 硬件加速的设备（许多手机、嵌入式芯片）上速度优势明显。它的 nonce 规则与 GCM 完全相同：同一密钥下绝不重复。

### 4.7 解密失败时该做什么：什么都不给

AEAD 解密失败只有一种正确行为：返回错误，不返回明文、不返回“部分明文”、不在错误信息里区分“标签错”与“格式错”到足以被利用的程度（具体错误信息粒度以所用库与协议规范为准）。调用方收到失败后应当：丢弃该记录、记一条可审计的日志（只记“某记录验签失败”，不要把密文、密钥、nonce 记进日志）、按协议决定是断开连接还是拒绝该条消息——而不是“先用着明文看看”。

## 5. 分类与变体

| 类别 | 代表 | 加密 | 验真 | 一句话特征 |
|---|---|---|---|---|
| 反面教材 | ECB | 有 | 无 | 每块独立，泄露明文结构，新系统禁用 |
| 普通模式 | CBC | 有 | 无 | 链式衔接，需随机 IV 与填充，仍需外层校验 |
| 普通模式 | CTR | 有 | 无 | 密钥流异或，无填充可并行，nonce 绝不重复 |
| AEAD | AES-GCM（SP 800-38D） | 有 | 有 | CTR + GHASH，现代默认选择之一 |
| AEAD | AES-CCM（SP 800-38C） | 有 | 有 | CTR + CBC-MAC，两遍处理，适合约束设备 |
| AEAD | ChaCha20-Poly1305（RFC 8439） | 有 | 有 | 流密码 + 认证器，无 AES 加速时更快 |

辨析：GMAC 是 GCM 只认证、不加密的变体（AAD 照常验真、明文为空），适用于“内容本来就要公开、但不许被改”的场景，不要把它与 GCM 混淆——需要保密时必须用完整 GCM。

## 6. 典型应用

- **TLS 记录层**：握手完成后，全部应用数据经 AEAD（AES-GCM 或 ChaCha20-Poly1305）加密传输，记录头信息可作 AAD 的一部分。握手本身见[TLS 与证书体系原理](03-tls-pki.md)。
- **磁盘与数据库加密**：每条记录、每个扇区用独立 nonce 做 AEAD，篡改任一记录都会在读取时验证失败，而不是静默返回被改过的数据。
- **消息与文件封装**：把“发送方、序号、版本号”放进 AAD，把正文加密——转发者可以读头部路由，但改头部就会验签失败。
- **密钥信封（Envelope）**：数据密钥加密数据、主密钥加密数据密钥时，内层同样用 AEAD，避免“密钥被换过却没人发现”。

## 7. 本机实测：AEAD 的“验真”是可以亲手验证的行为

以下两段是本机真实跑过的命令与输出，不是示意。环境：代理 VM，OpenSSL 3.0.13（CBC 部分）与 Go 标准库（GCM 部分，Go 由 `~/workspace/devtools/` 提供）。

### 7.1 对照：OpenSSL CBC 加解密往返（实测通过）

```bash
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
$ openssl enc -aes-256-cbc -K <64 位十六进制密钥> -iv <32 位十六进制 IV> \
    -in plain.txt -out cbc.bin
$ openssl enc -d -aes-256-cbc -K <同一密钥> -iv <同一 IV> \
    -in cbc.bin -out cbc_back.txt
$ cmp plain.txt cbc_back.txt && echo CBC_ROUNDTRIP_OK
CBC_ROUNDTRIP_OK
```

实测说明：CBC 往返本身只能证明“加解密配对正确”，**不能**证明“没被篡改”——本段只是对照组，验真能力来自下一段的 AEAD，而不是 CBC。

### 7.2 主实验：Go 标准库 AES-256-GCM（实测通过）

用 Go 标准库 `crypto/aes` + `crypto/cipher` 的 GCM 接口，对明文 `hello-aead-demo`（15 字节）做一次密封，再做三次开启：

```
nonce=12 tag-included ct=31 pt=hello-aead-demo open_err=<nil>
tampered_open_err_nonempty=true
wrong_aad_open_err_nonempty=true
```

读法：nonce 12 字节；含标签的密文 31 字节 = 15 字节明文 + 16 字节标签（标签长度与上文一致）；正常开启成功并还原明文；把密文改一位后开启失败；把 AAD 换成另一个头部后开启失败。两次失败都只返回错误、没有返回明文——这正是 4.7 节要求的 fail closed 行为。密钥与 nonce 均由程序内随机生成，每次运行结果不同，上面只记录结构与成败，不记录密钥值。

> 提醒：演示代码的密钥是临时随机生成的，只用于验证 AEAD 行为。生产代码的密钥来源、存储与轮换见[密钥生命周期管理](10-key-lifecycle-management.md)，不要把演示里的临时密钥用法搬进生产。

## 8. 关键设计取舍

- **一次做完 vs 两次拼起来**：AEAD 把“加密 + 校验”做成一个原语，调用方没有机会拼错顺序（先加密后校验、先校验后加密、校验哪几部分，都是事故高发区）。代价是：调用方必须理解 nonce 与 AAD 这两个新参数，不能再像用 CBC 那样只传密钥与 IV。
- **随机 nonce vs 计数 nonce**：随机 nonce 实现简单，但依赖随机数质量与用量上限；计数 nonce 绝不重复是确定性的，但依赖计数器持久化与密钥轮换时同步重置。两种都正确，混用或论证不清才是错。
- **标签长度 vs 伪造难度**：128 位标签是默认选择；缩短标签省下的几个字节，换来的是伪造成功率的指数级上升。约束环境里缩短前必须先算账，而不是先省字节。

## 9. 限制与常见误解

- **误解：AES-256 一定比 AES-128 安全**：在模式用错（ECB、nonce 重复、只加密不验真）面前，密钥长度救不了任何东西。先把模式与 nonce 规则做对，再谈密钥长度；总览的安全强度对照表见[对称与非对称密码](01-symmetric-asymmetric.md)。
- **误解：IV/nonce 可以保密代替唯一**：IV/nonce 的安全要求是“不重复”（CBC 的 IV 还要求不可预测），不是“保密”。把它藏起来而不保证唯一，是本末倒置。
- **误解：密文长度不变就是没问题**：CTR 与 GCM 的密文与明文等长（不计标签），长度本身会泄露明文长度信息。对长度敏感的场景（例如定长口令、已知格式的消息），需要在应用层补长度填充——这是 AEAD 之外的另一层设计，不在本篇展开。
- **限制**：AEAD 只保证“这条记录来自持有密钥的一方、且没被改过”，不保证发送方身份（那是签名与证书的事，见[哈希与数字签名](02-hash-signature.md)）、不保证密钥本身没泄露（那是密钥管理的事）、不保证端点没被攻破。
- **限制**：GCM/CCM 的用量上限、nonce 唯一性、标签长度，都是“同一密钥下”的约束。密钥一轮换，计数归零重算；轮换周期与触发条件归密钥管理，不归本篇。

## 10. 小结

分组密码本身只会加密一个块；模式决定多块怎么衔接，AEAD 再补上“验真”这一半。ECB 是反面教材，CBC/CTR 只有加密没有验真，GCM、CCM、ChaCha20-Poly1305 一次完成加密与验真——新系统默认选 AEAD，并把“同一密钥下 nonce 绝不重复、验证失败不给明文”两条刻进实现。
