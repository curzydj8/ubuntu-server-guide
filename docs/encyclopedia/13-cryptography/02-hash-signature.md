# 哈希与数字签名

## 1. 本章目标

读完本篇，能说清哈希函数为什么能当“指纹”用、数字签名为什么能证明“谁说的、没改过”，以及证书签名是怎么把信任从 CA 传递到一张证书上的。

## 2. 背景与问题

加密解决的是“别偷看”，但还有两个问题它不管：第一，对方发来的东西有没有在路上被改过？第二，说话的人到底是不是他自称的那个人？把整份文件加密一遍既慢又没必要——验证完整性与身份不需要藏起内容，只需要一个办法，让任何改动都无所遁形、让冒名者无法假冒。这就是哈希与签名的分工：哈希负责“有没有被改”，签名负责“谁签的”。

## 3. 总体架构

三者是层层递进的关系：

```
原始数据 ──哈希──▶ 固定长度摘要（指纹）
摘要 ──私钥签名──▶ 签名值（可公开验证）
签名值 + 原始数据 + 签名者公钥 ──公钥验证──▶ 通过 / 不通过
```

证书签名是同一机制的再上一层：证书机构（CA）用自己的私钥，给“主体身份 + 主体公钥 + 有效期”这组信息签名，签出来的就是证书。验证证书，本质上就是验证 CA 的签名（详见 [TLS 与证书体系原理](03-tls-pki.md)）。

## 4. 工作机制

### 4.1 哈希函数：三条性质，缺一不可

哈希函数把任意长度的输入变成固定长度的输出（摘要）。SHA-256 的输出永远是 256 位，无论输入是一个字还是一部电影。一个合格的密码学哈希函数必须同时满足：

1. **抗原像性（单向）**：给定摘要，算不出原来的输入。摘要不是压缩包，不能解压还原。
2. **抗第二原像性**：给定一个输入，找不到另一个不同输入算出同一摘要。否则攻击者可以偷换文件而不改变指纹。
3. **抗碰撞性**：找不到任意两个不同输入算出同一摘要。这是最强的一条，也是最难保证的一条——MD5 与 SHA-1 正是因为碰撞攻击变得实际，才被淘汰出安全用途。

此外还有一个实用性质：**雪崩效应**——输入改一个比特，输出大约一半比特都会变。指纹因此对任何改动都敏感。

### 4.2 数字签名流程：先哈希，再签名

签名不是对全文直接做私钥运算（全文可能很大，私钥运算又慢），标准流程是两步：

1. **哈希**：对原始数据算摘要。
2. **签名**：用签名者的私钥对摘要做签名运算，得到签名值。

验证时反向操作：验证者用同一哈希函数对收到的数据重算摘要，再用签名者的公钥对签名值做验证运算，两边对得上才算通过。任何一处对不上——数据被改过、签名值被改过、用错了公钥——验证都会失败。注意这个流程同时说明了两件事：签名**不保密**（数据本身是明文传输的，想保密要另外加密），签名**只认证来源与完整性**，不保证内容本身是对的。

### 4.3 证书签名的思想：信任是可以传递的

证书签名的结构与普通签名完全相同，只是被签名的内容换成了“身份绑定声明”：

- 被签名内容：主体名称（如域名）+ 主体公钥 + 有效期 + 发行者名称。
- 签名者：CA 的私钥。
- 验证者：任何持有 CA 公钥（即信任锚）的人。

验证通过意味着：CA 曾经确认过“这个公钥确实属于这个主体”，且证书内容自签发后未被改动。信任就这样从“你信任 CA”传递到了“你信任这张证书上的公钥”。链条再往上走（中间 CA、根 CA），就是证书链，见下一篇。

### 4.4 时间维度：签名本身不管“什么时候”

哈希与签名回答“谁签的、有没有改”，不回答“现在还能不能信”。一张证书过期了，签名在数学上依然能验证通过，但系统必须拒绝它——这就是有效期、吊销（CRL、OCSP）要解决的问题。签名机制本身没有时钟，信任的有效期是靠证书字段与吊销机制另外叠加的。

## 5. 关键设计取舍

- **为什么先哈希再签名**：私钥运算慢且对输入长度有限制，先哈希把任意长度压成定长摘要，既快又通用。代价是签名的安全性同时依赖哈希的抗碰撞性——哈希一破，签名跟着受牵连（这正是 SHA-1 淘汰连带影响旧签名的原因）。
- **确定性签名 vs 随机化签名**：ECDSA 签名需要一个随机数，随机数一旦重复或可预测，私钥就会泄露（历史上真实发生过此类事故）；EdDSA 改为从私钥确定性派生随机数，消除了这一整类失误。取舍是：确定性更稳，但同一消息的签名永远相同（这本身不是问题，签名本来就不需要保密）。
- **签名不是时间戳**：需要证明“某文件在某时刻之前已经存在”时，要另外引入可信时间戳服务，签名 alone 做不到。

## 6. 分类与变体

| 类别 | 代表 | 一句话特征 |
|---|---|---|
| 哈希函数 | SHA-256（FIPS 180-4）、SHA-3（FIPS 202） | 定长摘要，满足三条抗性 |
| 已淘汰哈希 | MD5、SHA-1 | 碰撞攻击已实际可行，不再用于安全场景 |
| RSA 签名 | RSASSA-PSS | 大整数体制，应用最广 |
| 椭圆曲线签名 | ECDSA、EdDSA | 密钥短；EdDSA 确定性派生随机数 |
| 消息认证码 MAC | HMAC | 对称版的“签名”，双方共享密钥，无公钥验证 |
| 慢哈希（口令存储专用） | bcrypt、Argon2 | 故意算得慢，加盐防批量猜测；不是通用哈希 |

辨析：MAC 与数字签名常被混淆。MAC 用共享密钥，验证方也能伪造，因此只能证明“持有密钥的某一方”发过，不能证明具体是哪一方，也不能给第三方看；数字签名用私钥签名、公钥验证，任何第三方都能验证，且签名者无法否认（不可否认性）。

## 7. 应用与限制

- **文件与软件完整性校验**：发布方公布哈希值，用户下载后重算比对。比对不上就说明文件被改过或下错了版本。下面是本机实测的哈希命令（环境：代理 VM，OpenSSL 3.0.13）：

```bash
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)
$ echo -n "hello" | openssl dgst -sha256
SHA2-256(stdin)= 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

上面是实际跑过的输出：同样输入在任何机器上都应得到同一个摘要，这正是哈希可作指纹的原因。`echo` 不加 `-n` 会多一个换行，摘要会完全不同——雪崩效应的直观例子。

- **口令存储**：口令绝不能明文存，也不能只用一次普通哈希存——普通哈希算得太快，攻击者可以批量猜测。正确做法是加盐（每个口令一个随机盐值）再用慢哈希（bcrypt、Argon2）存储。本篇只讲这个原则，不展开攻击手法；服务端的口令保管实践见[秘密信息管理](../../02-security/09-secrets-management.md)。
- **软件签名与证书**：操作系统、应用商店、浏览器用签名验证软件与网站身份；证书签名是其核心一环（见下一篇）。
- **限制**：哈希不能加密、不能还原；签名不能保密、不能证明内容为真、不能自带时间效力；私钥一旦泄露，攻击者就能以你的名义签名——吊销与轮换是应用层必须补的课（见[证书与密钥生命周期](../../02-security/08-certificate-lifecycle.md)）。

## 8. 常见误解

- **误解：哈希就是加密**：加密可逆（有密钥就能还原），哈希不可逆。把“哈希后存储”说成“加密存储”是错的，两者的安全承诺完全不同。
- **误解：签名能保证对方是好人**：签名只保证“确实是持有该私钥的人签的”，不保证这个人可信。信任来自你是否信任这个身份本身（证书体系就是干这个的）。
- **误解：摘要相同就是同一个文件**：理论上碰撞存在，实践中合格哈希的碰撞概率可以忽略不计，但“忽略不计”建立在算法未被攻破的前提上——MD5、SHA-1 就是前车之鉴。
