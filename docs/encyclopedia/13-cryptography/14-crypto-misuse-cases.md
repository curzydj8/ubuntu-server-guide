# 密码学误用案例分析：识别与修复

> 本篇只讲防御侧：误用的表现、检测方法、修复方法。**不写利用代码、不写攻击步骤、不写可直接复制的攻击载荷与工具命令。** 文中提到的历史案例均以公开披露为准，只讲公开结论与修复教训，不复述未公开的利用细节。
>
> 一句话结论：真实系统里出问题最多的往往不是算法本身被攻破，而是**算法用错了地方、用错了方式**——模式选错、随机数重复、密钥写进代码、只加密不校验。算法选对只是及格线，用对才是分水岭。

## 1. 技术原理：误用为什么比算法被破更常见

密码算法的安全承诺都是有条件的。AES 的承诺建立在“密钥保密、模式正确、随机数不重复”之上；ECDSA 的承诺建立在“每次签名的随机数新鲜且保密”之上；哈希的承诺建立在“算法本身未被攻破”之上。条件一破，承诺即失效，而失效的样子往往不是“密文被瞬间解开”，而是悄悄地：密文泄露结构、两个签名之间泄露密钥、旧密钥在补丁之后仍然有效。

因此识别误用的思路不是“猜算法有没有漏洞”，而是**对照承诺条件逐项核查**：这个算法在这里承担什么任务（保密？完整性？身份？）、它需要哪些前提（密钥从哪来、随机数从哪来、校验做没做）、这些前提有没有被代码或配置破坏。下一节的分类表就是按这个思路组织的。

### 1.1 误用分类总览

| 类别 | 误用的样子（识别特征） | 破坏的前提 | 修复方向（见第 6 节） |
|---|---|---|---|
| 模式误用 | 分组密码用了 ECB，或只加密不做完整性校验 | 密文不能泄露结构、不能被无声篡改 | 改用 AEAD（AES-GCM、ChaCha20-Poly1305），见[分组密码模式与 AEAD](04-block-cipher-modes-aead.md) |
| 随机数误用 | IV、nonce、签名随机数重复、固定或可预测 | 每次加密 / 签名的一次性值必须新鲜且不可预测 | 用密码学安全的随机源生成，签名优先用确定性随机数或 EdDSA |
| 密钥误用 | 密钥硬编码、随仓库泄露、长期不轮换、多用途共用一把密钥 | 密钥必须保密、专用途、可轮换 | 密钥进密钥库 / 保险库，轮换与吊销流程见[密钥生命周期管理](10-key-lifecycle-management.md) |
| 算法误用 | 安全场景仍用 MD5、SHA-1、DES、3DES、RC4 | 算法本身必须未被攻破、未被退役 | 按现行标准迁移到 SHA-256 / SHA-3、AES，见[密码算法选型与合规要点](15-crypto-selection-compliance.md) |
| 口令误用 | 口令用普通哈希（甚至明文）存储、无盐、快哈希 | 口令存储必须加盐且故意算得慢 | 加盐 + 慢哈希，见[口令哈希与存储](06-password-hashing-storage.md) |
| 随机源误用 | 用普通伪随机数、时间戳、进程号生成密钥或随机数 | 密钥材料必须来自密码学安全的随机源 | 只用操作系统 / 密码库提供的密码学安全随机源 |
| 协议误用 | 允许老旧 TLS 版本、关闭证书校验、静态密钥协商 | 传输保护必须认证身份且会话密钥一次一密 | TLS 1.3 优先、校验不关闭、前向保密，见 [TLS 与证书体系原理](03-tls-pki.md) |
| 实现误用 | 自造算法、魔改标准算法、错误处理泄露信息 | 算法公开、实现经受检验；失败时不泄露区分信息 | 用标准库与验证过的模块，不自造算法 |

## 2. 合法研究范围

本篇的研究只在以下范围内合法：自有设备、自有代码、自有系统，或已获得书面授权的系统，以及公开披露资料的案头研究。超出范围的行为不在本文讨论内。

**未授权测试他人系统是违法行为，本文不提供相关指导。** 审计他人系统、做渗透测试、验证某个公开案例的可复现性，都必须先拿到授权；拿到授权后也只在授权范围内、用防御性方法核查（读代码、读配置、读自有日志），不写、不跑针对他人系统的利用步骤。

## 3. 实验环境

- 环境：自有设备（代理 VM，隔离的演示目录 `/tmp/crypto-demo`，演示数据均为临时测试串，不含真实密钥与真实用户数据）。
- 软件与版本：OpenSSL 3.0.13（见第 8 节实测记录）、Node.js 24.22.1（仅用于 AEAD 篡改被拒的对照演示，因本机 Python 未安装 `cryptography` 库，见第 8 节）。
- 工具性质：本节只列防御、检测类用法——摘要计算、签名验签、配置与代码审计；不列攻击载荷生成类工具的操作用法。
- 权限要求：演示只需普通用户权限；审计生产系统需要只读的代码与配置读取权限，不需要也不应索取生产密钥。

## 4. 风险

- **数据泄露风险**：误用导致密文可被推断、签名密钥可被推导、口令可被批量猜测。规避：按第 5 节做上线前审计，把误用当作发布门禁项，而不是事后补丁项。
- **密钥失陷后无法“只打补丁”**：密钥一旦可被推导或已经泄露，修复补丁本身救不回这把密钥，必须轮换密钥、吊销旧证书、重新签发（Debian 案例的教训，见第 7 节）。规避：密钥失陷预案里写明“轮换 + 吊销”，不要只写“升级版本”。
- **合规与信任风险**：继续使用已退役算法、关闭证书校验，可能同时违反合规要求并破坏用户信任。规避：选型以现行标准为准，见[密码算法选型与合规要点](15-crypto-selection-compliance.md)。
- **误报与过度修复风险**：把“算法名字出现在代码里”直接当成漏洞（例如仅用于非安全场景的校验和、历史数据解密）会浪费修复资源。规避：先定性用途——这个调用点承担安全任务吗？承担才按安全标准修；不承担的，标注用途、隔离使用，不混用。

## 5. 检测方式

检测分三层：代码审计、配置审计、运行审计。只写检测侧，不写规避检测的方法。

### 5.1 代码审计：按名字与模式查

- **搜算法名**：在自有代码库里搜索 `ECB`、`MD5`、`SHA1`、`DES`、`RC4`、`3DES` 这类标识，逐个确认用途。出现在安全路径（签名、口令、令牌、加密）里的，列入修复清单；出现在非安全路径的，标注用途并确保不与安全路径混用。
- **搜密钥踪迹**：搜索硬编码的密钥、口令、令牌字面量，以及提交历史里是否曾经提交过密钥。密钥扫描工具的告警要当作“可能已泄露”处理，而不仅是“删掉这行代码”。
- **搜随机数来源**：确认生成密钥、IV、nonce、盐值、令牌的代码走的是密码学安全随机源，而不是普通伪随机数、时间、进程号、计数器。凡是“我自己拼了一个随机数”的实现，一律重点审查。
- **搜校验缺失**：加密调用点有没有配套的完整性校验（AEAD 的认证标签、HMAC、签名验证），解密 / 验证失败时有没有明确拒绝。只加密不校验的调用点，就是第 1.1 节“模式误用”行的候选。

### 5.2 配置审计：按清单查

- TLS 配置是否仍允许 TLS 1.0 / 1.1、是否允许静态 RSA 密钥协商、证书校验是否被关闭（测试环境关掉校验后有没有带回生产）。
- 密钥与证书的有效期、轮换周期、吊销状态是否可查；长期（例如数年）未轮换的密钥先列入清单，再按业务影响排期。
- 依赖的密码库版本是否在厂商支持期内；密码库升级后，旧算法调用有没有随之清理（升级库版本不等于清理旧调用）。

### 5.3 运行审计：看日志与重复

- 在自有日志里检查同一 nonce / IV 是否在同一密钥下出现重复（日志本身不得记录密钥与明文，只记录标识与计数）。
- 检查签名验证失败、解密认证失败的告警是否有人跟进：认证失败率突然上升，可能是配置错误，也可能是篡改尝试——两种情况都要先按“配置错误”排查、按“疑似攻击”留存证据。
- 检查证书透明日志（CT）里有没有未授权的自家域名证书，见 [TLS 与证书体系原理](03-tls-pki.md)第 4.4 节。

## 6. 修复与防御方法

修复按“先止血、再根治、最后防复发”排序；同一误用不要只修一处调用，要全库清查同类调用。

| 误用 | 修复方法 |
|---|---|
| ECB / 裸加密 | 改用 AEAD：AES-GCM 或 ChaCha20-Poly1305；历史 ECB 密文按数据敏感度决定重加密或隔离，解密旧数据时只在受控迁移流程里进行 |
| IV / nonce 重复 | 每次加密生成新鲜随机 IV / nonce；同一密钥下绝不重复使用；能用库自动生成随机数的，优先用库的默认行为，不要手写 |
| 签名随机数问题 | 优先选用 EdDSA（如 Ed25519）或 RFC 6979 确定性 ECDSA 实现；ECDSA 随机数必须来自密码学安全随机源且每次不同 |
| 密钥硬编码 / 泄露 | 立即吊销并轮换受影响密钥与证书，清理提交历史中的密钥（清理历史不等于密钥恢复安全——轮换才是关键），密钥改走密钥库 / 保险库，见[密钥生命周期管理](10-key-lifecycle-management.md)与[秘密信息管理](../../02-security/09-secrets-management.md) |
| 退役算法 | 按现行标准迁移：SHA-256 / SHA-3 替代 MD5 / SHA-1，AES 替代 DES / 3DES / RC4；迁移期对历史数据的校验需求单独处理，不把退役算法留在新签名路径上 |
| 口令存储 | 每个口令独立随机盐 + 慢哈希，见[口令哈希与存储](06-password-hashing-storage.md)；已用快哈希存储的口令库要制定迁移方案（例如下次登录时重哈希），不要等泄露才动手 |
| 弱随机源 | 密钥、随机数、盐值、令牌一律走密码学安全随机源；虚拟机快照恢复、容器启动早期熵不足的场景，要确认随机源已就绪再生成密钥 |
| TLS 配置 | 新部署优先 TLS 1.3，不关闭证书校验，不用静态 RSA 密钥协商；证书校验失败就是拒绝连接，不做“告警但放行”的折中 |
| 自造算法 | 停用自造与魔改实现，改用标准库与验证过的模块；“算法保密”不是安全措施，见[对称与非对称密码](01-symmetric-asymmetric.md)第 6 节 |

### 6.1 纵深防御：让一次失误不成灾

- **密钥分层**：主密钥只用来保护数据密钥，不直接加密业务数据；数据密钥定期轮换，单把密钥的危害窗口有限。
- **用途隔离**：加密、签名、认证各用不同的密钥；一把密钥不跨用途、不跨系统复用。
- **最小暴露**：日志、错误信息、调试输出不含密钥、明文与完整密文材料；解密与验证失败只返回“失败”，不区分失败原因给调用方以外的信息。
- **密码敏捷性**：把算法与密钥长度写成可配置项，而不是散落在各处的硬编码常量；下一次算法退役时，改配置与走迁移流程，而不是全库翻代码。

### 6.2 常见误解

- **误解：算法名字够新就安全**：AES-GCM 用错 nonce、Ed25519 的私钥保管不当，照样出事。安全的是“算法 + 正确用法 + 密钥管理”这一整套。
- **误解：打了补丁就等于修好了**：补丁修的是产生弱密钥的代码，已经生成的弱密钥、已经泄露的密钥必须另外轮换与吊销。
- **误解：测试环境关掉校验没关系**：测试配置最容易原样带进生产。校验开关必须按环境隔离，且生产环境的“关闭校验”应被配置审计直接判为失败项。
- **误解：加密了就不需要校验**：加密防偷看，校验防篡改；只加密的系统，篡改可以不被发现。现代默认是 AEAD，两者一次完成。

## 7. 历史与案例

本节案例均来自公开披露，只讲公开结论与修复教训，不复述利用细节。

- **MD5 碰撞公开（2004 年）**：王小云团队公开了 MD5 的实际碰撞结果；此后 MD5 不再适合用作安全场景的完整性或签名哈希。教训：哈希算法一旦出现实际碰撞，就应启动退役迁移，而不是等到“有人用它伪造证书”才动手（2008 年确有研究者用 MD5 碰撞思路演示伪造 CA 证书的公开研究，本文不展开其构造方法）。
- **SHAttered：SHA-1 首次实际碰撞（2017 年 2 月 23 日）**：Google 与荷兰 CWI 研究机构公开宣布，首次以实际计算得到两个内容不同、SHA-1 摘要相同的 PDF 文件，并呼吁迁移到 SHA-256 等更安全的哈希。教训：SHA-1 的退役不是“理论风险”，而是已有公开演示；新签名、新证书路径上不应再出现 SHA-1。
- **Debian OpenSSL 可预测随机数（CVE-2008-0166，Debian 安全公告 DSA-1571-1，2008 年 5 月 13 日）**：Debian 的 OpenSSL 打包改动误删了随机数生成的熵输入，导致在受影响版本上生成的密钥材料可被猜测；公告明确要求把受影响期间生成的所有密钥材料从头重新生成，而不只是升级软件包。教训：随机源出问题时，“升级 + 轮换”缺一不可；这也是今天高价值密钥强调在可验证熵源的模块里生成的原因之一。
- **Sony PlayStation 3 签名随机数问题（2010 年，第 27 届混沌通信大会，fail0verflow 公开演示）**：演示指出 Sony 的 ECDSA 代码签名实现对每次签名使用了固定不变的随机数，导致签名私钥可从公开签名中被推导出来，已泄露的根签名密钥无法靠软件更新恢复保密性。教训：签名随机数与私钥同等重要；确定性签名（RFC 6979）与 EdDSA 正是为消除“每次都要掷出好随机数”这一整类失误而存在的。本篇不给出推导公式与复现步骤。

## 8. 实测对照：正确用法长什么样

以下命令均在代理 VM 上真实运行过，环境：OpenSSL 3.0.13、Node.js 24.22.1；演示数据为临时测试串 `hello-crozz-demo`（无换行），演示密钥为临时生成、用后删除，不含任何真实密钥。

```bash
$ openssl version
OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024)

$ printf 'hello-crozz-demo' | openssl dgst -sha256
SHA2-256(stdin)= 8e71c394f4a43fb542c69ab01a2f49ac37d58ba02ff7e694c39767d7aa38a381

$ printf 'hello-crozz-demo' | openssl dgst -sm3
SM3(stdin)= 1f9d54ddc6b2420ea2b6781c99e459312f2f99c6567569a78a4f2e73c63011ec

$ openssl genpkey -algorithm ED25519 -out edkey.pem
$ openssl pkeyutl -sign -inkey edkey.pem -rawin -in plain.txt -out sig.bin
$ openssl pkeyutl -verify -pubin -inkey edpub.pem -rawin -in plain.txt -sigfile sig.bin
Signature Verified Successfully
```

三点实测结论（只写跑过的结果）：

1. **摘要可复现**：同一输入在任何机器上都应得到同一摘要，这正是哈希可作指纹的原因；输入差一个换行，摘要完全不同。
2. **签名验签闭环**：Ed25519 临时密钥签名后，用对应公钥验证通过——这是“私钥签名、公钥验证”的最小正确闭环，见[哈希与数字签名](02-hash-signature.md)。
3. **两个反直觉的实测提醒**：第一，`openssl enc -aes-256-gcm` 在本机实测返回 `AEAD ciphers not supported`——`openssl enc` 不支持 AEAD，不要用它冒充 AEAD 加密，AEAD 请走支持 AEAD 的库接口；第二，用 Node.js 的 AES-256-GCM 接口实测，篡改后的密文解密时被拒绝（`Unable to authenticate data`），这正是 AEAD“篡改必被发现”的正确表现——本条为 Node.js 24.22.1 实测，不是 OpenSSL 实测，特此区分。
