# TLS 1.3 握手与会话恢复

> 本篇是[TLS 与证书体系原理](03-tls-pki.md)的深挖篇。总览已讲清“1-RTT、前向保密、证书链”的思想，本篇不再重复，只展开总览没写细的部分：握手消息一支一支是怎么走的、会话密钥是怎么一层层派生出来的、恢复会话时 PSK 到底代替了什么、0-RTT 为什么只能用于幂等请求。服务器部署与证书申请、续期的操作步骤不在本篇，归 10 域后续与[证书与密钥生命周期](10-key-lifecycle-management.md)。

## 1. 本章目标

读完本篇，能按消息顺序说清一次 TLS 1.3 完整握手、能说清 PSK 恢复与完整握手在“省了什么、没省什么”上的区别、能说清 0-RTT 数据为什么在协议层没有重放保护。

## 2. 背景与问题

总览把 TLS 1.3 握手概括为“客户端发 ClientHello，服务器回证书与 Finished，客户端验证后握手完成”。这个概括对理解思想够了，但对判断配置与排查问题不够，因为它没回答：

- 客户端凭什么敢在第一条消息里就把密钥协商参数发出去？猜错了怎么办？
- 服务器证书之后的那几条加密消息各证明了什么？少了哪一条会怎样？
- “恢复会话”到底恢复了什么——是跳过了证书验证，还是跳过了密钥协商，还是两者都跳过？
- 0-RTT 把数据塞进第一条消息，省掉的往返是用什么换来的？

本篇按 RFC 8446（TLS 1.3，2018 年）的消息顺序回答这些问题。TLS 1.2 的握手是另一套流程（2-RTT，消息更多），本篇只在对照处提及，不展开。

## 3. 总体架构

一次完整握手的消息飞行（flight）分三段。注意：从 ServerHello 之后，服务器发出的握手消息全部已加密——这是 TLS 1.3 与 TLS 1.2 的一个重要区别，证书内容不再明文出现在握手里。

```
客户端                                                      服务器
   │  ClientHello（版本、算法、key_share、随机数）               │
   │ ──────────────────────────────────────────────────────────▶ │
   │                                                             │
   │  ServerHello（选定版本、算法、key_share）                     │
   │  EncryptedExtensions（其余协商参数，已加密）                  │
   │  [CertificateRequest]（仅要求客户端认证时出现）               │
   │  Certificate（服务器证书链）                                 │
   │  CertificateVerify（对握手 transcript 的签名）               │
   │  Finished（密钥确认的 MAC）                                  │
   │ ◀────────────────────────────────────────────────────────── │
   │                                                             │
   │  [Certificate]（仅客户端认证时出现）                          │
   │  [CertificateVerify]                                         │
   │  Finished                                                    │
   │ ──────────────────────────────────────────────────────────▶ │
   │                                                             │
   │ ◀── 应用数据（会话密钥加密）──▶                              │
   │                                                             │
   │  [NewSessionTicket]（握手完成后，服务器发给客户端的恢复票据） │
   │ ◀────────────────────────────────────────────────────────── │
```

括号 `[]` 表示可选消息。`Finished` 双方都要发，不可省略。

## 4. 工作机制

### 4.1 完整握手：每条消息证明了什么

**第一段：ClientHello。** 客户端发来：支持的最高版本（通过 supported_versions 扩展声明 TLS 1.3）、愿意接受的密码套件列表、签名算法列表、支持的密钥协商组，以及——关键的一步——它**猜测**服务器会选的组对应的密钥协商公开值（key_share 扩展），外加一个随机数。TLS 1.3 敢让客户端先猜，是因为可选的组很少，猜中的概率很高；猜错的处理见 4.2 节。

**第二段：服务器的回答。** 服务器选定版本、密码套件与组，发回自己的 key_share。此时双方都已算出共享秘密，于是从 EncryptedExtensions 起的所有服务器握手消息都已加密：

- **EncryptedExtensions**：放那些不需要在明文阶段协商、但需要加密保护的扩展，例如协商的应用层协议（ALPN）。
- **CertificateRequest**（可选）：服务器要求客户端也出示证书时才出现，即双向 TLS（mTLS）的情形；普通 HTTPS 没有这一条。
- **Certificate**：服务器证书链。链本身的验证规则（签名、名称、有效期、吊销）见总览与下一篇[证书透明化与吊销机制](09-certificate-transparency-revocation.md)，本篇不重复。
- **CertificateVerify**：服务器用证书私钥对截至 Certificate 为止的握手 transcript（全部已发握手消息的哈希）做签名。这一条证明的是“持有该证书私钥的一方确实参与了这次握手”，而不是“证书是真的”——证书真假由链验证负责，两者分工不同，缺一不可。
- **Finished**：用握手密钥算出的 MAC，覆盖截至 CertificateVerify 为止的 transcript。它做两件事：密钥确认（双方确实算出了同一套密钥）与握手完整性确认（中间没有任何一条握手消息被改过）。

**第三段：客户端的回答。** 客户端验证证书链、验证 CertificateVerify 签名、验证服务器 Finished，全部通过后发回自己的 Finished（若被要求客户端认证，则先发自己的 Certificate 与 CertificateVerify，再发 Finished）。此后双方切换到应用数据密钥，开始传输应用数据。

一个容易错的点：客户端在收到服务器 Finished 之前不能发应用数据（0-RTT 例外，见 4.6 节）；服务器在收到客户端 Finished 之前就可以发应用数据（图中第二段之后标注的 `[Application Data*]`）：服务器发应用数据不依赖客户端 Finished，但连接在客户端 Finished 校验通过之前不算完全建立。

### 4.2 猜错了怎么办：HelloRetryRequest

如果客户端 key_share 里没有服务器想要的组，服务器不直接失败，而是回一条 HelloRetryRequest：它在形式上像一条 ServerHello，指明服务器要的组，客户端再发一次携带正确组 key_share 的 ClientHello。这次重发多花一个往返，握手变成 2-RTT，但这只是“猜错”的代价，不是常态。实现上应让客户端在首条 ClientHello 里带上最常见的组（例如 X25519），把猜错变成小概率事件。

### 4.3 密钥编排：HKDF 一层层派生

TLS 1.3 的全部密钥派生都用 HKDF（RFC 5869，提取 + 扩展两步），密钥编排分三个阶段，输入逐阶段增加：

1. **早期秘密（Early Secret）**：输入是 PSK（完整握手时 PSK 为空，即用全零代替）。由此派生早期流量密钥——只有 0-RTT 恢复时才真正用它加密 early data。
2. **握手秘密（Handshake Secret）**：输入是 (EC)DHE 共享秘密。由此派生握手流量密钥，加密 EncryptedExtensions 之后、Finished 之前的全部握手消息。
3. **主秘密（Master Secret）**：握手完成后，由此派生应用数据流量密钥，以及**恢复主秘密（resumption master secret）**——会话恢复的 PSK 正是从它派生的，而不是直接复用旧会话密钥。

这个分层设计的意义是“密钥隔离”：握手密钥、应用数据密钥、恢复密钥各不相同，一处泄露不直接等于处处泄露；同时每一阶段的密钥都绑定了截至当时的 transcript，改动任何一条握手消息都会导致后续密钥对不上、Finished 校验失败。

### 4.4 密码套件为什么只有 5 个

TLS 1.2 的密码套件名把“密钥交换 + 认证 + 对称加密 + 哈希”四件事写进一个名字，组合爆炸。TLS 1.3 把套件名缩减为只写“AEAD 算法 + 哈希”，密钥交换（supported_groups 扩展）与签名算法（signature_algorithms 扩展）各自独立协商。RFC 8446 定义的 5 个套件全部是 AEAD（加密与完整性一次完成）：

| 密码套件 | AEAD | 哈希 |
|---|---|---|
| TLS_AES_128_GCM_SHA256 | AES-128-GCM | SHA-256 |
| TLS_AES_256_GCM_SHA384 | AES-256-GCM | SHA-384 |
| TLS_CHACHA20_POLY1305_SHA256 | ChaCha20-Poly1305 | SHA-256 |
| TLS_AES_128_CCM_SHA256 | AES-128-CCM | SHA-256 |
| TLS_AES_128_CCM_8_SHA256 | AES-128-CCM（8 字节认证标签） | SHA-256 |

“少给选择就少出错”在这里是字面意义：没有 CBC、没有静态 RSA 密钥交换、没有压缩与重协商，协商出错的空间被协议本身砍掉了。日常部署最常见的是前三个套件；CCM 两个主要面向受限设备。

### 4.5 会话恢复：PSK 代替了什么、没代替什么

完整握手完成后，服务器可以发一张或多张 **NewSessionTicket**。票据里包着恢复用 PSK（由恢复主秘密派生），票据本身经服务器的票据加密密钥加密后发给客户端——客户端只负责保管票据，不需要、也不应该能解密它；服务器收到票据时解密，恢复出 PSK。票据带有效期，过期即失效；票据有效期的上限数值以 RFC 8446 第 4.6.1 节原文为准（见文末未完成项）。

下一次连接时，客户端在 ClientHello 里带上 pre_shared_key 扩展（出示票据）与一个 PSK 绑定值（binder，用 PSK 对本次 ClientHello 算出的 MAC，证明出示者确实持有该 PSK）。恢复握手的两种模式：

| 模式 | 客户端发什么 | 前向保密 | 省了什么 |
|---|---|---|---|
| psk_ke（纯 PSK） | 只有 PSK，不做新的 (EC)DHE | 依赖 PSK 本身不泄露；没有新增的一次性密钥交换 | 证书传输与证书签名验证 |
| psk_dhe_ke（PSK + (EC)DHE） | PSK + 新的 key_share | 有：新鲜 (EC)DHE 保证即使 PSK 日后泄露，新会话密钥也不会被反推 | 证书传输与证书签名验证 |

关键辨析：**恢复握手省的是“证书”这一段，不是“密钥协商”这一段**。即使在恢复模式下，服务器也不再发证书、客户端也不再验证证书链——信任来自“这个 PSK 是上次完整握手时由已验证过的服务器发给我的”这一链条。因此恢复的安全性完全系于 PSK 的保管与票据加密密钥的轮换：票据加密密钥长期不轮换，等于给了攻击者一张长期有效的“免证书通行证”素材；这部分运维要求见[证书与密钥生命周期](10-key-lifecycle-management.md)，本篇只讲机制。

恢复握手的往返仍是 1-RTT：客户端发 ClientHello（含 PSK），服务器回 ServerHello（接受 PSK）+ EncryptedExtensions + Finished，客户端回 Finished，随后传应用数据。比完整握手省的是证书往返的字节与一次签名验证的计算，不是往返次数——往返次数要降到 0，靠的是下一节的 0-RTT。

### 4.6 0-RTT：省掉往返的代价是重放

如果客户端持有有效的 PSK，且服务器允许，它可以在第一条 ClientHello 里就附带 **early data**（0-RTT 数据），用早期密钥加密，随 ClientHello 一起发出。服务器若接受，在 ServerHello 里用 early_data 扩展确认；若不接受，客户端必须把数据在完整握手后重发一次（1-RTT 路径）。

0-RTT 的代价必须讲清楚，因为它决定了“什么数据能走 0-RTT”：

- **协议层没有重放保护**。early data 是在服务器发来任何新鲜随机数之前发出的，攻击者把截获的 0-RTT 包原样重发一次，服务器在协议层无法区分“重发”与“原件”——密文本身是合法的，重发不需要破解密文。这与“篡改”是两回事：重放不改内容，只重复执行。
- **因此 0-RTT 只适合幂等请求**：重复执行一次也不会造成不良后果的操作，例如普通的 GET。任何会改变状态的操作（下单、转账、写库）都不应走 0-RTT；服务器侧的正确做法是对非幂等请求拒绝 early data、要求客户端走 1-RTT 重发。
- **前向保密也打折**：early data 的加密密钥来自上次会话的 PSK，而不是本次新鲜的 (EC)DHE；一旦该 PSK 泄露，early data 就可能被解密，而后续应用数据的密钥在握手完成后已切换为新鲜密钥，不受影响。0-RTT 的保密窗口只覆盖“第一段数据”。
- **服务器侧的缓解是应用层责任**：例如只对安全方法放行 early data、给下游标明“这是 early data”（以便应用层自己做幂等校验）、限制 early data 的大小与票据的单次使用。协议本身不替应用做这些判断。

一句话：0-RTT 是“用可重放性换延迟”的交易，交易成立的前提是应用能承受重复执行。拿不准时，关掉 0-RTT、只用 1-RTT 恢复，是正确的默认选择。

### 4.7 握手之后：密钥更新与握手后认证

连接建立后还有两个机制值得知道名字，不必深究细节：

- **KeyUpdate**：任一方可以在连接中途发起密钥更新，切换到下一代应用数据密钥。长期连接（例如大文件传输、长会话）借此限制“同一密钥加密的数据量”，降低密钥长期使用的风险。
- **握手后客户端认证（post-handshake authentication）**：服务器可以在握手完成后、连接进行中再发 CertificateRequest，要求客户端出示证书。注意：纯 PSK 恢复的主握手里服务器不能发 CertificateRequest，握手后认证是它的例外通道。

### 4.8 降级保护：为什么“谈成低版本”会被发现

TLS 1.3 的降级保护只讲原理，不讲绕过方法。机制有两层：

- **supported_versions 扩展**：客户端在扩展里声明自己支持的最高版本，服务器按扩展选择，而不是按 ClientHello 外层那个为兼容而保留的旧版本号字段选择。
- **降级哨兵**：当服务器因为客户端只支持旧版本而不得不协商 TLS 1.2 或更低版本时，它会在 ServerHello 随机数的尾部放入一个固定的哨兵值。支持 TLS 1.3 的客户端如果在谈成的低版本握手里看到这个哨兵，就知道“对方其实支持 1.3，这次降级不正常”，从而中止连接。哨兵的意义是：攻击者无法在不被发现的情况下把双方从 1.3 压到 1.2，因为哨兵本身是服务器签名的握手 transcript 的一部分，改动它会导致 Finished 校验失败。

## 5. 关键设计取舍

- **客户端先猜 vs 服务器先选**：先猜省一个往返，代价是猜错时多花一个往返（HelloRetryRequest）。因为可选组很少，这个赌注的期望收益是正的。
- **加密更多的握手内容 vs 兼容中间设备**：TLS 1.3 从 ServerHello 之后就加密握手，证书不再明文传输，隐私更好；代价是某些依赖明文握手做检测的中间设备需要升级。这是“端到端加密优先于中间设备可观测性”的取舍。
- **PSK 恢复 vs 每次都完整握手**：恢复省证书传输与签名验证，代价是信任链从“每次验证证书”变成了“信任上次握手发来的 PSK 与票据加密密钥的保管”。票据加密密钥的轮换周期，就是这条信任链的有效期。
- **0-RTT vs 1-RTT 恢复**：0-RTT 再省一个往返，代价是可重放与前向保密打折，且判断“能不能重放”只能由应用层做，协议帮不上忙。

## 6. 分类与变体

| 握手类型 | 往返 | 证书 | 适用场景 |
|---|---|---|---|
| 完整握手（(EC)DHE + 证书） | 1-RTT（猜错组时 2-RTT） | 每次都发、每次都验证 | 首次连接、PSK 过期或被拒之后 |
| PSK 恢复（psk_dhe_ke） | 1-RTT | 不发、不验证，信任来自 PSK | 常规重连，推荐的默认恢复方式 |
| PSK 恢复（psk_ke） | 1-RTT | 不发、不验证 | 不需要前向保密或设备算力极受限时；一般不优先选 |
| 0-RTT 恢复（early data） | 0-RTT | 不发、不验证 | 仅幂等请求，且应用层能承受重放 |
| 客户端认证（mTLS） | 同上 | 双方都发证书 | 服务间调用、设备接入等需要认证客户端的场景 |
| TLS 1.2 握手（对照） | 2-RTT | 每次都发 | 仅兼容旧客户端，新部署不优先 |

## 7. 应用与限制

- **Web 与 API**：浏览器与服务器的常规 HTTPS 握手就是完整握手 + PSK 恢复的组合；短连接多的场景下恢复的收益最大。
- **移动与弱网**：往返次数对弱网延迟的影响比带宽更大，1-RTT 与 0-RTT 的价值在这里最明显；但 0-RTT 的重放边界在移动端同样适用，不能因为“快”就放宽。
- **限制**：TLS 1.3 不解决端点安全、不审查内容真假（见总览）；恢复机制不解决“服务器私钥泄露后，已发出的票据是否还可信”的问题——票据加密密钥泄露后，已发票据应视为不可信并轮换，这是运维动作，不是协议动作。
- **合法演示范围**：本节所有命令均在自有虚拟机上对本地回环地址运行，不涉及任何他人系统。

### 7.1 本地实测：自签证书 + TLS 1.3 握手（实测通过）

环境：代理 VM，OpenSSL 3.0.13（`openssl version` 输出：OpenSSL 3.0.13 30 Jan 2024）。先用自签证书起一个仅监听本地回环的测试服务，再用客户端连它——自签证书不在系统信任库内，客户端必然报自签告警，这正是演示要验证的现象（“不在信任库内的证书会被告警”，与总览的信任锚概念一致）：

```bash
# 1. 生成仅用于本地演示的自签证书（有效期 1 天，CN=localhost）
$ openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem \
    -days 1 -nodes -subj "/CN=localhost"
$ openssl x509 -in cert.pem -noout -subject -issuer -dates
subject=CN = localhost
issuer=CN = localhost
notBefore=Nov  4 09:47:01 2026 GMT
notAfter=Nov  5 09:47:01 2026 GMT

# 2. 本地起 TLS 1.3 测试服务（只绑回环端口），客户端以 TLS 1.3 连接
$ openssl s_server -accept 18444 -cert cert.pem -key key.pem -tls1_3 -www
$ printf "GET / HTTP/1.0\r\n\r\n" | \
    openssl s_client -connect 127.0.0.1:18444 -tls1_3
```

实际跑过的关键输出（演示用证书与端口，演示后已清理）：

```
Server Temp Key: X25519, 253 bits
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 18 (self-signed certificate)
```

三点与本篇机制对得上：协议确实是 TLSv1.3；协商出的套件是 4.4 节表中的 TLS_AES_256_GCM_SHA384；临时密钥是 X25519 的 (EC)DHE，符合“每次会话新鲜密钥协商”的描述；`Verify return code: 18` 表示自签证书不在信任库内——演示环境故意如此，生产环境绝不能用自签证书冒充公开信任证书。

### 7.2 未实测的部分（诚实标注）

- **PSK 票据保存与恢复握手演示，未实测**：同一环境下用 `openssl s_client -sess_out` 两次尝试保存 TLS 1.3 会话，均未生成会话文件，因此未能演示“第二次连接复用票据”的完整过程。本篇 4.5 节的恢复机制只以 RFC 8446 为准描述，不以本地演示背书；该演示列入文末未完成项，待换一种会话保存方式后补测。

## 8. 常见误解

- **误解：恢复会话就是“跳过握手”**：恢复仍要走一次完整的 ClientHello/ServerHello/Finished 交换（1-RTT），省的只是证书传输与签名验证，不是整个握手。
- **误解：0-RTT 只是“更快的 1-RTT”**：0-RTT 在安全属性上降了一档（可重放、前向保密打折），不是单纯的加速版；把它当作普通加速开启，是配置错误。
- **误解：TLS 1.3 握手全程加密**：ClientHello 与 ServerHello 本身是明文的（不然双方无法协商出密钥），加密是从 ServerHello 之后才开始的。明文部分仍会暴露“双方在谈 TLS、用的哪些组”等元信息。
- **误解：密码套件越多越灵活越好**：TLS 1.3 恰恰反其道而行之——5 个 AEAD 套件、密钥交换与签名各自独立协商，灵活性来自正交的扩展，而不是套件数量。
