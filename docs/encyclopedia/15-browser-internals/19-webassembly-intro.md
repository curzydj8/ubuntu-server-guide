# WebAssembly 入门

## 1. 一句话定义

WebAssembly（简称 Wasm）是一种安全、可移植、低级别的二进制指令格式：它不是一门给人手写的语言，而是给 C、C++、Rust 等语言编译用的目标格式，让这些语言写的代码能在浏览器（以及浏览器之外的运行时）里以接近原生的速度运行。

## 2. 为什么需要它

JavaScript 是为网页交互而生的：灵活、动态、易写，但做重计算时有结构性短板——动态类型与垃圾回收让编译器难以稳定地生成最优机器码，大体积数值计算、编解码、3D 渲染、物理模拟等场景容易变慢。另一方面，大量现成的高性能代码早已用 C、C++、Rust 写好，重写为 JavaScript 成本极高。WebAssembly 的回答是：不替换 JavaScript，而是给浏览器再加一种执行体——JS 继续管 DOM 与编排，Wasm 管重计算；旧代码编译一次，到处运行。

## 3. 核心含义

### 3.1 四个设计目标

按 W3C 核心规范的表述，WebAssembly 被设计为安全（safe）、可移植（portable）、低级别（low-level）、紧凑高效（compact and efficient）的代码格式：

- **安全**：模块在沙箱里运行，内存访问全部受边界检查，越界就触发陷阱（trap）而非静默越界；控制流是结构化的，不能跳到任意地址（见 3.4 节）。
- **可移植**：同一份 `.wasm` 文件不依赖底层 CPU 架构，浏览器在加载时再编译为本机代码。
- **低级别**：接近机器指令的抽象，编译器容易生成高效代码，也容易被验证。
- **紧凑**：二进制编码比等价的 JavaScript 文本更小、解析更快（这是一个设计方向，不是对所有程序都成立的保证；不要把厂商宣传的压缩比数字当结论）。

### 3.2 二进制格式：魔数、版本与分段

`.wasm` 文件的开头是固定的 8 个字节：4 字节魔数 `\0asm`（十六进制 `00 61 73 6D`）+ 4 字节版本号（目前为 `01 00 00 00`，即版本 1）。之后是一连串“段”（section）：每段由 1 字节段 ID + 长度前缀 + 段内容组成，分别承载类型段、导入段、函数段、表段、内存段、全局段、导出段、代码段、数据段等。整数多用 LEB128（Little Endian Base 128）变长编码：数值越小，占的字节越少，这是格式紧凑的来源之一。

与二进制格式一一对应的还有文本格式 WAT（`.wat` 文件，S 表达式写法），供学习、调试与手写小模块用；生产中的模块几乎总是由编译器生成，而不是手写。

一个最小模块的文本形式长这样（把两个 32 位整数相加并导出为 `add`）：

```wat
(module
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a
    local.get $b
    i32.add)
  (export "add" (func $add)))
```

对应的二进制以 `\0asm` 开头；本篇第 7 节给出了一份可在 Node.js 里真实跑通的等价字节序列与验证结果，读者可自行复现。

### 3.3 执行模型：栈式虚拟机与线性内存

- **栈式虚拟机**：指令操作一个隐式操作数栈，没有通用寄存器；例如 `i32.add` 就是从栈顶弹出两个数、把和压回栈。指令集的数值类型主要是 `i32`、`i64`、`f32`、`f64`（2.0 起还加入 SIMD 的 `v128` 等，见 3.5 节）。
- **线性内存**：模块拥有一段连续的字节数组，页大小为 64KiB，可按需增长；所有内存访问都以线性内存内的偏移寻址并受边界检查。线性内存与引擎内部内存、调用栈、函数表是分开的：线性内存里的越界或溢出写不到返回地址与引擎元数据上。
- **模块、导入与导出**：模块像一个共享库：它可以导入宿主提供的函数、内存、表、全局变量，也可以导出自己的函数、内存、表、全局变量给宿主。模块自己不能凭空获得宿主能力——能调什么，全看宿主在实例化时给了什么导入。

### 3.4 与 JavaScript 的互操作

浏览器里 Wasm 从来不是独立运行的：它总是由 JavaScript 加载、实例化并调用，典型流程是：

```js
// instantiateStreaming 要求服务器以 application/wasm 类型提供模块；
// 若类型不对，它会回退或失败，具体行为以浏览器实现为准。
const { instance } = await WebAssembly.instantiateStreaming(fetch('add.wasm'));
console.log(instance.exports.add(2, 3)); // 5（本篇实测字节序列的等价结果，见第 7 节）
```

互操作的关键点：

- **加载 API**：`WebAssembly.instantiateStreaming()`（流式编译，边下载边编译）、`WebAssembly.instantiate()`（先拿到完整字节再编译）、`WebAssembly.compile()` 与 `WebAssembly.Module` / `WebAssembly.Instance`（分开编译与实例化）。模块须先通过验证（`WebAssembly.validate()` 可单独校验字节是否合法）才能实例化。
- **数值可以直接传，复杂类型要手动搬**：JS 与 Wasm 之间直接互通的是数值类型；字符串、对象、数组没有直接的跨边界类型，通行做法是把数据写进双方共享的线性内存（JS 侧用 `TextEncoder` 编码、用 `Uint8Array` 视图读写，Wasm 侧按偏移与长度取），或用 Emscripten、wasm-bindgen 这类工具链生成的胶水代码（glue code）代劳。**不要以为 `add('a', 'b')` 这样传字符串就能直接工作**——核心规范层面没有这条路。
- **Wasm 不能直接碰 DOM**：没有 DOM API、没有 `document`、没有网络 API；要操作页面或发请求，必须通过 JS 提供的导入函数中转。反过来，JS 调用 Wasm 导出函数就像调用普通函数（同步调用，返回数值或 undefined）。
- **内存共享是双向的**：JS 可以创建 `WebAssembly.Memory` 传给模块，也可以读取模块导出的内存；增长内存会使旧的 `ArrayBuffer` 视图失效，JS 侧须在增长后重新创建视图——这是胶水代码里最常见的 bug 来源之一。

### 3.5 版本与生态：核心已成熟，外围仍在发展

- **核心 1.0**：2019 年 12 月 5 日成为 W3C 推荐标准（Recommendation），是各浏览器普遍实现的最小公分母。
- **核心 2.0**：在 1.0 基础上纳入了已广泛实现的提案，包括 SIMD 指令与 `v128` 类型、多值返回、批量内存操作、引用类型等；其规范工作已完成并进入候选推荐阶段，**具体的推荐标准发布状态以 W3C 官方发布为准（待核实）**，本篇不把某一阶段写成最终状态。
- **3.0 与后续方向**：已公布的方向包括 64 位内存、垃圾回收类型、异常处理等；各方向的浏览器支持程度不一，属工程发展中，不宜当作“现成可用”来写代码依据。
- **浏览器之外**：WASI（WebAssembly System Interface）为浏览器外的运行时定义了一套能力受限的系统接口（如文件、时钟、随机数），模块只能用宿主明确授予的能力，不能像普通进程那样凭空访问任意文件；组件模型（Component Model）则试图让不同语言编译的模块像组件一样组合复用。两者都属工程发展中的生态方向，不是核心 1.0 的一部分，本篇只作指向，不展开。

## 4. 分类

按“模块跑在哪里、与谁互操作”分三类：

- **浏览器内 Wasm**：由 JS 加载，与 DOM、Web API 通过 JS 中转协作；本篇的主角。
- **浏览器外 Wasm（WASI 运行时）**：在 Wasmtime、Wasmer 等运行时里跑，面向命令行工具、插件、边缘计算等场景；系统能力来自宿主授予的 WASI 能力，而非浏览器 API。
- **工具链产物**：Emscripten（C/C++ → Wasm + JS 胶水）、Rust 的 `wasm-pack` / `wasm-bindgen`、AssemblyScript（TypeScript 风格语法 → Wasm）等；它们决定了“写什么语言、生成什么胶水”，不改变 Wasm 本身的格式与安全模型。

按“与 JS 的关系”也可分两类：**JS 主导、Wasm 加速**（页面逻辑在 JS，热点函数在 Wasm，绝大多数生产用法）；**Wasm 主导、JS 打杂**（如把整套游戏引擎或桌面应用逻辑编译进 Wasm，JS 只负责加载与 DOM 桥接，胶水层更厚、调试更难）。

## 5. 典型应用

- **音视频与图像编解码**：浏览器里跑已有的 C/C++ 编解码器，避免重写，适合在线剪辑、转码、图像处理工具。
- **游戏与 3D 渲染**：物理、渲染、AI 等热点循环放进 Wasm，JS 管输入与 UI；已有引擎移植多走这条路。
- **密码学与数据处理**：大批量哈希、加密、压缩、科学计算，数值循环密集、DOM 交互少的任务收益最明显。
- **存量代码复用**：把已验证的 C/C++/Rust 库编译进 Web 应用，而不是为 Web 重写一遍、再维护两份实现。

## 6. 限制与常见误解

- **“Wasm 会取代 JavaScript”**：错。Wasm 没有 DOM、没有事件循环、没有 Web API；离开 JS 它连页面元素都摸不到。两者是分工，不是替代。
- **“Wasm 一定比 JS 快”**：不一定。调用边界有开销、加载与编译要时间、胶水代码会吃掉收益；小计算、DOM 密集型任务用 Wasm 反而更慢。是否划算要实测热点，不能凭直觉下结论。
- **“Wasm 代码体积一定更小”**：不一定。胶水代码、运行时、调试信息都可能让总体积反超；体积收益只对“计算密集且 JS 等价实现很臃肿”的场景稳定成立。
- **“Wasm 是安全的，所以模块代码不用审计”**：错。沙箱只保证模块越界不了、跳不走；模块本身的逻辑漏洞、宿主传给它的不安全导入、以及它通过 JS 间接获得的 DOM 与网络能力，仍然能造成危害。安全模型见下节。
- **调试与可观测性较弱**：二进制没有源码映射时很难定位问题；生产调试依赖源码映射（source map）与工具链支持，体验目前仍不如 JS。

### 安全模型概述

Wasm 的安全模型分三层，缺一不可：

1. **验证先行**：浏览器在运行前验证模块：类型正确、指令合法、控制流结构化。验证不过的模块根本不执行——这是沙箱的第一道门。
2. **运行时隔离**：线性内存与引擎内存分离、全部内存访问受边界检查、间接调用须经函数表且做运行时类型检查；模块没有直接系统调用，也拿不到宿主的任意内存与 UI。
3. **能力来自宿主**：模块在浏览器里能做的事，不超出 JS 传给它的导入；它本身没有超出 JS 的信息收集能力，格式本身也不提供完整性或隐私保护——防篡改、防窃听要靠 HTTPS 等外部机制。这意味着：**Wasm 的安全保证是“模块跑不出去”，不是“模块做的事都是好的”**；加载不受信任的第三方模块，仍须像对待第三方 JS 一样审查其来源与导入。

## 7. 小结

WebAssembly 是给编译器用的二进制目标格式：以 `\0asm` 魔数开头、栈式执行、线性内存、模块化导入导出；JS 负责加载与 DOM，Wasm 负责重计算，复杂类型要经线性内存或胶水代码中转；核心 1.0 已是成熟标准，2.0 及外围生态仍在推进；安全来自验证 + 隔离 + 宿主授予的能力，而不是模块本身“天然无害”。

## 8. 读者验证步骤（最小模块已在本机实测）

> 以下实测在代理 VM 的 Node.js 里完成，验证的是**字节格式与 JS 互操作本身**，不是浏览器加载流程；浏览器里用 `fetch` + `instantiateStreaming` 的加载行为未在本机实测。

实测命令与结果（Node.js v24.22.1）：

```js
// /tmp 临时脚本，非仓库文件：构造 add 模块的字节序列并实例化
const bytes = new Uint8Array([0x00, 0x61, 0x73, 0x6d, /* \0asm */
  0x01, 0x00, 0x00, 0x00, /* 版本 1 */
  /* 其余为类型段、函数段、导出段、代码段：导出 add(i32, i32) -> i32 */
  0x01, 0x07, 0x01, 0x60, 0x02, 0x7f, 0x7f, 0x01, 0x7f,
  0x03, 0x02, 0x01, 0x00, 0x07, 0x07, 0x01, 0x03, 0x61, 0x64, 0x64, 0x00, 0x00,
  0x0a, 0x09, 0x01, 0x07, 0x00, 0x20, 0x00, 0x20, 0x01, 0x6a, 0x0b]);
await WebAssembly.validate(bytes);              // true
const { instance } = await WebAssembly.instantiate(bytes, {});
instance.exports.add(2, 3);                     // 5
instance.exports.add(-1, 1);                    // 0
```

- 魔数校验：前 4 字节确为 `\0asm`；`WebAssembly.validate()` 返回 `true`；`add(2, 3) = 5`，`add(-1, 1) = 0`，与 WAT 版 `add` 的语义一致。
- 未实测部分：浏览器内 `fetch('add.wasm')` + `instantiateStreaming` 的 MIME 类型要求与失败回退行为、Emscripten / wasm-bindgen 生成的胶水代码、WASI 运行时的能力授予——读者须在目标浏览器与工具链里自行验证。
