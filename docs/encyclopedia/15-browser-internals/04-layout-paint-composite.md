# 布局、绘制与合成

> 本篇是总览篇的深挖篇。总览只给管线顺序，本篇只讲布局、绘制、合成这三段内部是怎么算、怎么画、怎么拼的。
> 总览：[渲染引擎与渲染流程](01-rendering-pipeline.md)。
> 本篇不含任何本机实测：所有浏览器内行为、帧时间与内存数字均为原理说明与估算示意，**示例未实测**，不得当作实测结论引用。

## 1. 本章目标

读完本篇，能说清一次样式变化到底走到哪一步就停了：什么时候只算布局、什么时候只重画、什么时候只合成；以及为什么“改同一个属性”在不同元素、不同上下文里代价可以完全不同。

## 2. 背景与问题

总览篇已经给出管线：解析 → 树 → 布局 → 绘制 → 合成。但这条线只回答“顺序”，不回答“代价”。真实页面里的问题从来不是“管线存不存在”，而是：

- 一个改动为什么会牵连整页重算，而另一个改动只动一个图层？
- 绘制记录和像素是什么关系——为什么“改了样式”不一定立刻产生像素？
- 合成层为什么能让动画变流畅，又为什么建得太多反而变慢？

本篇回答这三个问题。页面写法（怎么写 CSS、怎么写动画）属 03 域，本篇只讲机制与取舍，代码片段只作机制示意。

## 3. 总体架构

把布局、绘制、合成三段摊开，数据是这样流动的：

```
渲染树（可见节点 + 计算后样式）
        │
        ▼
布局树：每个盒的位置与尺寸（盒模型计算结果）
        │
        ▼
绘制记录：每层的绘制指令清单（Display List，尚未生成像素）
        │
        ▼
分层 / 合成层树：哪些内容各自成层、按什么顺序叠
        │
        ▼
光栅化：指令 → 位图（分块进行，可走 CPU 或 GPU）
        │
        ▼
合成：各层位图按顺序、位置、透明度拼成最终画面 → 屏幕
```

三段的分工可以用一句话区分：**布局算“在哪、多大”，绘制记“画什么”，合成定“怎么拼”**。三段跑在不同的执行位置上：样式计算与布局一般在主线程（与 JavaScript 同一线程），合成与滚动类动画可以走合成器线程；光栅化可由 CPU 或 GPU 承担，具体分工因引擎与硬件而异。正是“主线程忙不一定卡住合成”这一点，让合成层动画有可能在主线程繁忙时仍继续。

## 4. 工作机制

### 4.1 布局树与盒模型计算

布局的输入是渲染树节点及其计算后样式，输出是每个盒的精确位置与尺寸。布局树不是另一份 DOM，而是“渲染树节点 + 几何结果”的对应关系：一个渲染节点对应一个或多个盒（例如一行文本断成多行时，一个元素可能产生多个行盒），`display: none` 的节点既不进渲染树，也就没有盒。

#### 盒模型：四层，从里到外

每个盒由四层组成，从里到外依次是：

- **内容（content）**：文本、图片或子盒实际占据的区域。
- **内边距（padding）**：内容与边框之间的空间，背景会延伸到这一层。
- **边框（border）**：包围内边距与内容的可见边缘，自身有宽度。
- **外边距（margin）**：边框之外的透明间距，用来把盒与邻居推开。

`width` 与 `height` 到底量的是哪一层，由 `box-sizing` 决定，这是最容易算错账的地方：

- `content-box`（默认值）：`width` 只量内容。`width: 350px` 加 `10px` 边框，渲染出来的盒宽是 `370px`（两边边框各加 `10px`）。
- `border-box`：`width` 把内容、内边距、边框都包进来。同样的 `width: 350px` 加 `10px` 边框，盒宽仍是 `350px`，内容区被压缩到 `330px`。
- 两种模式下外边距都不计入 `width` / `height` 本身；外边距影响的是盒在布局中占据的位置与间距，不是盒的声明尺寸。

#### 布局计算为什么会“牵一发而动全身”

布局是依赖传播的计算，约束从外向内、尺寸从内向外来回传递：

1. **自上而下传约束**：父容器先告诉子节点“你最多能占多宽”（可用宽度、定位上下文、书写方向等）。
2. **自下而上回尺寸**：子节点根据内容与约束算出自身尺寸，再回传给父容器，父容器据此定自己的高度（例如高度由内容撑开的块）。
3. **兄弟与祖先再受影响**：一个节点变宽、变高或换行，可能推动后续兄弟换行、父容器变高，进而推动整页后续内容下移。

所以布局代价不能只看“改了一个元素”：改动越靠上、越靠近根，影响面越大；改动只落在叶子节点、且不改变其外尺寸时，影响面最小。同一属性在不同位置的代价不同，正是这个传播机制造成的。

几个布局计算中常见的连锁点（机制层面，不展开写法）：

- **内容驱动尺寸**：文本换行、图片加载后获得真实尺寸、字体替换后字形宽度变化，都会让“内容尺寸”变了，进而让布局重算。图片未预留尺寸、字体替换后度量不一致，是布局抖动的两类典型来源。
- **外边距合并**：普通流中相邻块级盒的垂直外边距可能合并为一个（取较大者而非相加）。这不是 bug，而是盒模型规范的行为；Flex 与 Grid 容器内不发生这种合并。算间距时先确认元素处于哪种布局上下文，再数外边距。
- **格式化上下文**：块级格式化、Flex、Grid、表格等是不同的布局模式，各自的尺寸分配与对齐规则不同。同一份盒模型输入，在不同模式下会算出不同的位置结果；查布局问题时，先确认盒处于哪种上下文，再套用该模式的规则。

### 4.2 样式失效与布局失效：改动不是立刻重算

浏览器不会在每次样式写入时立刻重算一切。常见做法是把改动记为“脏”：样式脏了记一笔，布局脏了记一笔，等到真正需要时（下一帧渲染前，或脚本主动索要最新几何值时）再批量重算一次。批量处理是性能的关键：一次写十处样式，正常情况下只触发一次布局，而不是十次。

这个批量机制有一个例外，就是**强制同步布局**：脚本在样式或布局已脏的情况下，立刻读取一个依赖最新几何值的属性，浏览器无法用旧值回答，只能当场把布局算完再返回。会触发这类读取的属性包括 `offsetWidth`、`offsetHeight`、`getBoundingClientRect()`、`scrollTop` 等几何类读取，以及在某些情况下索要计算样式（`getComputedStyle()`）后又依赖几何的读取。单次读取本身并不贵——如果布局本来就是最新的，读取只是取值；贵的是“写后立刻读”这个顺序：每写一次就读一次，批量就被打碎成多次同步布局。

```
<!-- 机制示意：示例未实测 -->
<!-- 反模式：写 → 读 → 写 → 读，循环内每次读都可能强制同步布局 -->
<!-- 正模式：先把所有读集中做完，再把所有写集中做完，只留一次布局 -->
```

把“读”与“写”分阶段（先集中读、再集中写），或把写推迟到下一帧的渲染回调里，是同一条原理的两种落地方式。滚动、尺寸监听这类高频回调里尤其要避免“读—写”交错：回调本身跑得频繁，再叠加同步布局，帧预算很容易被吃光。

### 4.3 绘制记录与分层：先记指令，后出像素

布局算完后，浏览器并不立刻画像素，而是先为每一层生成**绘制记录**（Display List）：一串“画什么、按什么顺序画”的指令，例如画背景矩形、画边框、画文字、画图片。绘制记录有两点值得注意：

- **记录不是像素**：改动只影响绘制记录时（例如只改颜色），代价是重做记录与重画受影响区域，布局结果可以复用；但只有光栅化之后才真正有位图。
- **绘制有顺序**：层内按绘制顺序（背景、边框、内容、后代、浮动、定位元素等规则）记录，顺序错了画面就错了。分层不能打乱这个顺序，合成时必须按正确的层叠顺序拼回去。

**分层**是把绘制记录划分为若干绘制层与合成层的过程。普通内容通常共用一层；满足特定条件的元素会被提升为独立的**合成层**，由合成器单独处理。常见的提升条件包括（具体条件因引擎与版本而异，以各引擎文档为准）：

- 元素应用了 3D 变换或正在做变换、透明度动画；
- 元素声明了 `will-change: transform` / `will-change: opacity` 等提示；
- 元素是视频、canvas 等需要独立更新的内容；
- 元素与已有合成层重叠、需要独立绘制以避免互相污染时（例如合成层上方的普通内容也可能被一并提升）。

分层发生在布局与绘制之间、也与绘制结果相关：布局变了，分层可能要重算；绘制记录变了，层的内容要重画；但层本身的结构（有几层、谁在谁上面）不变时，改动可以只落在某一层内部。

### 4.4 合成器与 GPU 光栅化

光栅化是把绘制记录真正画成位图的过程。为了控制内存与响应速度，浏览器通常把层切成**小块（tile）**再光栅化：先光栅化视口附近的块，远离视口的块可以晚做或先不做；滚动时再补画新进入视口的块。块的大小、缓存策略与是否走 GPU 光栅化，因引擎、设备与硬件加速状态而异，本篇不给具体数值——任何“某引擎块固定为多大”的说法都应以官方发布为准（待核实），见文末未完成项。

合成器拿到各层的位图后，按层叠顺序、位置、透明度与变换拼成最终画面。合成这一步的特点是：

- **它操作的是已画好的位图**，而不是重新算布局、重新记绘制指令。只改合成层属性时，前面几步可以跳过。
- **它可以不在主线程上跑**：滚动与合成层动画因此有可能在主线程被 JavaScript 占住时仍继续，这是合成动画流畅的机制基础——但前提是动画确实只走了合成路径，且所需位图已经光栅化好；位图还没画好时，合成器也只能等。
- **它受层数与内存制约**：每层位图都要占内存（见 5.2 的估算），层越多、层越大，内存与管理开销越大，合成器反而可能被拖慢。

### 4.5 重排、重绘、合成：触发条件与代价区分

用一张表把三类变化的路径与代价区分开。注意：下表是机制层面的分类，**具体属性在具体引擎、具体上下文里的触发结果以 MDN 每属性文档与各引擎文档为准**，例如某些属性在某些条件下会走合成、某些条件下仍需绘制；不要把下表当作放之四海的查询表。

| 变化类型 | 走过的阶段 | 典型触发（示意） | 相对代价 |
| --- | --- | --- | --- |
| 重排（回流，Layout） | 样式 → 布局 → 绘制 → 合成 | 改 `width`、`height`、`top`、`left`、`margin`、`padding`、`font-size`，增删节点，图片或字体导致内容尺寸变化 | 最高：可能牵连整棵子树乃至后续内容 |
| 重绘（Paint） | 样式 → 绘制 → 合成 | 改 `color`、`background-color`（见下注）、`box-shadow`、`border-radius`，且不改变几何 | 中等：重做绘制记录与受影响区域的光栅化，布局可复用 |
| 仅合成（Composite） | 样式 → 合成 | 在已提升为合成层的元素上改 `transform`、`opacity` | 最低：只移动、混合已有位图，不重算布局、不重画 |

表下有三处必须说明的限定：

1. **“仅合成”是有前提的**：元素必须已经在自己的合成层上，且改动确实只影响合成属性。同样是改 `transform`，元素没有独立层时，浏览器仍要先处理分层与绘制；动画过程中才建层，第一帧就可能付出建层代价。`will-change` 的作用正是把建层提前（见 5.2），而不是凭空免掉建层。
2. **`background-color` 一行要打补丁**：在较新的 Chromium 实现里，某些 `background-color` 变化可以走合成路径；但这不是跨引擎的通用保证，不能据此认定“改背景色永远只合成”。跨引擎稳妥的合成属性仍是 `transform` 与 `opacity`，其余属性一律按“可能需要绘制”来评估，确切行为以各引擎当前文档为准（待核实）。
3. **代价是相对的，不是绝对的**：一次小范围重排（叶子节点、不影响兄弟）可能比一次大面积重绘（全屏阴影、复杂背景）便宜；一次只合成但层极大、位图需重新光栅化的动画，也可能比小范围重绘贵。查问题时先看“影响范围”（多少节点、多少像素、多少层），再看“走了哪几步”，两者相乘才是真实代价。

## 5. 关键设计取舍

### 5.1 批量失效换帧率，同步读取换正确性

浏览器把样式与布局改动先记脏、后批量算，是用“结果晚一点”换“算得少一点”。强制同步布局则是反方向的取舍：脚本索要最新几何值时，浏览器宁可当场算完，也不给旧值——正确性优先于批量收益。两者并存时，性能责任落在调用顺序上：读—写交错就是在反复选择“正确性优先”那条昂贵的路。

### 5.2 合成层：用内存换流畅，层泛滥时反噬

合成层的取舍是本篇最核心的一条：

- **收益**：动画只走合成时，跳过布局与绘制，主线程压力小，动画更可能赶上帧节奏。
- **代价**：每层位图都要占内存。估算示意（非实测，忽略分块、压缩与设备差异）：一层位图大致为 `宽 × 高 × 每像素字节数`，按每像素 4 字节（RGBA）计，一个 `800 × 600` 的层约 `1.9 MB`；设备像素比为 2 时，同一逻辑尺寸的位图约变为 4 倍。层数一多、层一大，内存与上传开销就会反过来拖慢合成与滚动。
- **误用**：`will-change` 是“最后手段”的渲染提示，不是性能开关。MDN 的表述是：只在处理已存在的性能问题时作为最后手段使用，不要用来预判尚未出现的问题；对过多元素使用会消耗过多内存、让渲染更复杂。正确用法是动画开始前加上、动画结束后去掉（例如脚本在交互前设置、动画结束事件后恢复为 `auto`），而不是在样式表里给大批元素常驻声明。`translateZ(0)` 等“强行提层”的写法同理：它确实可能建层，但建层本身就是代价，滥用等于提前把所有代价都付了，还可能挤占真正需要层的元素。
- **取舍结论**：提层只给“确实要动、且只动合成属性”的元素；不动的元素不提层；动画结束就把层还回去。层数没有放之四海的“安全上限”数字——以 DevTools 的 Layers 面板实测为准，本篇不给阈值（待核实）。

### 5.3 分块光栅化：用局部重画换内存与首屏

整层一次画完最简单，但大页面整层位图会非常大；切块后只画视口附近，是用“管理复杂度”换“内存与首屏”。代价是滚动到未光栅化区域时可能出现补画延迟（俗称“棋盘格”或空白闪现，表现因引擎而异），以及块边界处的额外管理。分块策略因此是引擎与设备相关的实现细节，不宜写成固定数值。

## 6. 分类与变体

- **按触发范围**：全量布局（影响整棵树或大片后续内容）与局部布局（只影响子树内部）；全量绘制（整层重画）与局部绘制（只重画脏区域）。优化的第一步永远是先缩小范围，再谈换路径。
- **按执行位置**：主线程路径（样式、布局、绘制记录）与合成器路径（合成、部分光栅化）。动画与滚动优先走合成器路径，是“把工作搬离主线程”的变体，而不是“把工作变没了”。
- **按引擎**：Blink、WebKit、Gecko 的分层条件、光栅化策略与合成器实现各不相同；本篇以 Chromium/Blink 的常见结构为例讲机制，WebKit 与 Gecko 的对应行为以各自文档为准（待核实）。
- **按内容类型**：普通文档流内容走完整管线；canvas、WebGL 与视频内容大量工作直接落在合成层与 GPU，布局阶段参与较少，优化手段也不同（例如 canvas 内容变化通常意味着重画该层位图，而不是重排）。

## 7. 应用与限制

- **应用（机制推论，不展开写法）**：
  - 动画优先用 `transform` 与 `opacity`，且只给真正动画的元素提层；动画结束移除 `will-change`。
  - 高频回调（滚动、尺寸变化）里先集中读几何值、再集中写样式，避免读—写交错。
  - 布局抖动先查“内容尺寸变化源”：图片是否预留尺寸、字体替换后度量是否对齐（字体策略见下一篇）。
  - 长页面、大列表先考虑缩小每帧工作量（局部布局、局部绘制、跳过屏外内容，见下一篇的 `content-visibility`），而不是先加层。
- **限制**：
  - 本篇不展开样式计算本身（选择器匹配、级联、继承的算法细节），只讲“样式脏了之后发生什么”。
  - 本篇不展开 GPU 驱动、合成器线程调度与各引擎内部数据结构；这些是实现细节，因版本而异。
  - 本篇不给任何“提速倍数”“安全层数”“块尺寸”等数值承诺：厂商宣传倍数一律不采信，确切数值以读者自己在目标浏览器里的实测为准。
- **读者验证步骤（未在本机实测）**：
  1. 在自己浏览器里打开任意页面，按 F12 → Performance 面板 → 录制一次刷新与一次动画。
  2. 在时间线里区分 Layout（布局）、Paint（绘制）、Composite Layers（合成）三类事件，对照 4.5 的表判断一次改动走了几步。
  3. 用 Layers 面板查看当前页的合成层数量与提层原因，对照 5.2 判断是否有常驻 `will-change` 或无动画元素被提层。

## 8. 常见误解

- **“改样式就一定回流”**：错。只改颜色类属性一般只重绘；只改合成层属性可以只合成；改尺寸位置才回流。先看属性，再看上下文。
- **“`transform` 动画永远免费”**：错。免费的前提是元素已在合成层、位图已就绪、改动只影响合成。建层、首次光栅化、大位图上传都是要付的代价，只是付的时机不同。
- **“层越多越流畅”**：错。层是内存与管理开销，泛滥时合成器与内存反而成为瓶颈。流畅来自“关键动画走合成”，不是“所有元素都成层”。
- **“读几何属性只是取值，没有代价”**：错。布局已是最新时确实只是取值；但在写后立刻读时，读会强制同步布局，代价在“顺序”而不在“读取”本身。
