# 内存管理与垃圾回收

## 1. 本章目标

读完本篇，能说清 V8 的堆为什么分代、年轻代与老年代各用什么算法回收、增量/并行/并发三个词的区别，以及“内存一直涨”时如何区分真泄漏与正常增长并定位到持有链。

## 2. 背景与问题

JavaScript 程序员不手动 `malloc`/`free`：对象用完之后由垃圾回收器（GC）自动收回。这带来方便，也带来一个问题：如果回收器在错误的时间做很重的工作，主线程会被长时间暂停，页面就会掉帧、输入无响应；如果回收器漏收了本该释放的对象，内存会一路上涨，最终导致标签页或进程崩溃。

V8 的解法建立在一个经验规律上：**分代假设**——大多数对象死得很快，活下来的对象往往会活很久。堆按这个规律分区，对不同分区用不同的回收策略：死得快的区域收得勤、收得便宜；活得久的区域收得少、收得仔细。再辅以增量、并行、并发三种手段，把主线程的暂停时间压下来。

本篇讲 V8 的 GC（代号 Orinoco）。JavaScript 语言本身的写法属 website-guide 的 JavaScript 系列，本篇只讲引擎内部视角；引擎如何执行代码见 [10 篇](10-js-engine-principles.md)，GC 暂停与渲染帧的关系见 [01 篇](01-rendering-pipeline.md)。

## 3. 总体架构

V8 堆的分代布局（大意）：

```
新对象 ──▶ 年轻代（Young Generation）
              ├─  nursery：刚分配的对象
              └─  intermediate：活过一次回收的对象
                        │ 再活过一次回收
                        ▼
              老年代（Old Generation）：长期存活的对象
                        │
              回收器：年轻代用 Minor GC（Scavenger）
                      老年代用 Major GC（Mark-Compact）
```

- **根（root）**：GC 判定存活的起点，包括执行栈、全局对象等。从根出发、沿引用能到达的对象就是“活的”，到不了的就是垃圾。
- **可达性即存活**：GC 不判断对象“有没有用”，只判断“能不能从根到达”。一个再也不会被读取、但仍被某个长寿命对象引用的数组，在 GC 眼里是活的——这正是第 7 节多数泄漏的本质。

## 4. 工作机制

### 4.1 年轻代：Scavenger（Minor GC，复制式回收）

年轻代用半区（semi-space）复制算法：年轻代空间被分成 From-Space 与 To-Space，每次回收时：

1. 从根与“老年代指向年轻代的引用”（见 4.4 节）出发，找出年轻代里的存活对象；
2. 把存活对象**复制**到另一块空闲区域（To-Space），并更新指向它们的指针（原地留一个转发地址）；
3. 复制完后交换两个半区的角色，旧 From-Space 里的全部内容（包括所有死对象）被整体丢弃——死对象不需要逐个标记和释放。

这个算法的成本与**存活对象数量**成正比，而不是与分配总量成正比。按分代假设，年轻代里绝大多数对象在回收时已经死了，所以复制量很小，回收很便宜——这就是年轻代可以收得很勤的原因。

晋升规则（V8 官方博客《Trash talk》）：对象先进 nursery；活过一次回收后成为 intermediate，仍留在年轻代；再活过一次回收后被**晋升（promote）到老年代**。年轻代空间因此不会被长寿对象慢慢占满。

### 4.2 老年代：Mark-Compact（Major GC，标记—清除—整理）

老年代对象多、活得久，复制整个老年代的代价太大，所以用标记—清除—整理，分三个阶段：

1. **标记（Mark）**：从根出发遍历整个对象图，给所有可达对象打上“活着”的标记。
2. **清除（Sweep）**：把未标记对象占用的内存块挂到按大小分档的空闲链表（free-list）上，供后续分配复用；清除本身不移动存活对象。
3. **整理（Compact）**：按碎片化程度挑选部分页面，把存活对象复制到一起，腾出连续空间。整理要移动对象并更新全部指针，代价最高，所以 V8 只对碎片严重的页面做整理、其余页面只清除，不会每次 Major GC 都全量整理。

Major GC 的触发与堆的动态上限有关：堆接近动态计算的上限时启动标记等工作；具体上限算法随版本与可用内存变化，不宜抄一个固定数值。

### 4.3 增量、并行、并发：三个词不要混用

Orinoco 的目标是把主线程暂停时间压下来，三个手段分工不同（V8 官方博客《Trash talk》的定义）：

- **并行（parallel）**：主线程与辅助线程**同时**做同一件 GC 工作，仍然是 stop-the-world（JavaScript 暂停），但暂停时间被多个线程分摊。用于并行 Scavenge、并行整理与指针更新。
- **增量（incremental）**：把一次 GC 切成许多小片，穿插在 JavaScript 执行之间做。**它不减少主线程上 GC 的总耗时（通常还略增），只是把暂停摊薄**，让页面能在两次小片之间响应输入和推进动画。用于 Major GC 的标记等阶段。
- **并发（concurrent）**：辅助线程在**主线程继续执行 JavaScript 的同时**在后台做 GC 工作，主线程基本不被占用，但要处理对象图随时变化带来的竞态，是三者中最难的。用于并发标记与并发清除。

一句话区分：并行是“多人同时停下手头活一起干”，增量是“一次干一点、干干停停”，并发是“后台线程趁主线程干活时自己干”。现代 V8 是三者的组合：并发标记先行、主线程做一次短暂的标记收尾、再并行整理与更新指针、并发清除随后进行。

### 4.4 写屏障与记忆集：年轻代回收为什么不必扫全堆

年轻代回收只关心“哪些年轻代对象还活着”，但老年代对象也可能引用年轻代对象。如果每次 Minor GC 都扫描整个老年代找这些引用，就失去了分代的意义。V8 用**写屏障（write barrier）**解决：程序在老年代对象上写入一个指向年轻代对象的引用时，屏障会把这条引用记录到**记忆集（remembered set，老→新引用表）**里。Minor GC 时只需把栈、全局对象与记忆集作为根，就能找全年轻代的存活对象，而不必遍历老年代。

同理，并发标记期间 JavaScript 还在运行、还在新建引用，写屏障也会把这些新引用记录下来，保证标记结果不因“标记时新建的引用”而漏标活对象。

### 4.5 空闲时间回收与堆增长的边界

浏览器在帧与帧之间的空闲时间里可以主动推进 GC 工作（idle-time GC）：例如动画一帧提前做完了，剩余的帧预算可用来做本来迟早要做的回收。这不是“提前释放程序员忘了的东西”，而是把回收工作挪到不影响交互的时间点。

另外两条边界要先说清，避免误诊：

- **堆增长不等于泄漏**：堆在动态上限内随负载增长、随后在 GC 后回落，是正常行为；只有“反复执行同一操作后，GC 后的基线持续抬高”才指向泄漏。
- **程序不能直接命令 GC**：GC 时机是实现定义的。Node.js 的 `--expose-gc`（暴露 `global.gc()`）只用于诊断（见第 8 节），不能写进生产代码当“手动释放”用；浏览器里的页面脚本没有等价手段。

## 5. 关键设计取舍

- **复制换便宜**：年轻代复制算法用“一半空间永远空闲”换取“死对象零成本丢弃”；空间换时间，且只在存活率低时划算。
- **整理换连续**：整理消除碎片、腾出连续空间，但要移动对象与更新指针，所以只挑碎片严重的页面做，不做全量整理。
- **摊薄换延迟**：增量与并发把暂停切小、挪到后台，换来的是实现复杂度（写屏障、竞态处理）与略增的总 GC 耗时——延迟优先于吞吐。
- **可达性换精确**：GC 只认“能否到达”，不认“是否还有用”。它永远无法回收“仍被引用但不再被读”的对象——这部分只能靠程序员的引用管理解决。

## 6. 分类与变体

- **按代**：Minor GC（Scavenger，年轻代，复制式）与 Major GC（Mark-Compact，老年代，标记—清除—整理）。两者不是二选一，是分工。
- **按执行方式**：stop-the-world（并行仍属此类）与增量/并发。区分标准是“主线程是否在执行 JavaScript”，不是“用了几个线程”。
- **按引擎**：本文讲 V8 的 Orinoco。SpiderMonkey（Firefox）与 JavaScriptCore（Safari）也是分代 GC，但代划分、算法名与触发策略不同，本篇不展开；Blink 渲染器另有自己的 C++ 对象回收器 Oilpan，与 V8 堆协作，具体协作机制待核实（见未完成项）。
- **相关但不同的机制**：`WeakRef` 与 `FinalizationRegistry` 让程序持有“不阻止回收”的弱引用。弱引用不保证回收时机、更不能替代清理逻辑；把它当“自动释放”用是误解，具体语义以语言规范与 MDN 为准，本篇不展开。

## 7. 应用与限制

### 7.1 内存泄漏常见模式

以下模式的共同点都是“对象仍可达，所以 GC 不能收”：

1. **无界增长的长寿命容器**：全局数组、Map、缓存只加不删。每次操作都往里追加，堆基线随操作次数线性抬高。
2. **未清理的订阅**：定时器、事件监听、消息订阅、观察者在组件/页面销毁后仍注册着，且回调闭包捕获了本该释放的大对象。
3. **闭包捕获过大作用域**：一个长期存活的回调捕获了整个外层作用域，作用域里的大对象因此一直可达，即使回调只用到其中一小部分。
4. **无淘汰策略的缓存**：缓存没有容量上限、过期或 LRU 淘汰，等于模式 1 的另一种写法。
5. **浏览器里的分离 DOM（detached DOM）**：节点已从文档中移除，但仍被 JavaScript 变量或闭包引用，节点及其子树都无法回收。排查时在堆快照里搜 detached 节点并看持有链。
6. **误把“堆涨了”当泄漏**：页面刚加载、堆在爬升、尚未触发 Major GC 时的快照不能定罪；要以“重复操作 + GC 后基线”作为判断标准。

### 7.2 排查思路（通用流程）

1. **复现与基线**：记录操作前的堆基线；重复执行可疑操作若干次（如打开/关闭同一面板 10 次）。
2. **看基线，不看峰值**：每次操作后等待回收（浏览器里可借助开发者工具的回收触发；Node 诊断里可用 `--expose-gc`），比较“操作后稳定下来”的堆大小是否持续抬高。
3. **对比堆快照**：拍操作前后的两份堆快照，做差量对比，找“数量与 retained 大小同时增长”的构造函数或对象类型。
4. **沿持有链（retainers）追到根**：从增长的对象沿引用链向上走，找到是哪条长寿命引用把它钉住的——修持有链，而不是修 GC。
5. **定点验证**：去掉可疑持有后重复步骤 1–2，确认基线不再抬高。只改代码不复测，等于没定位。
6. **先查持有，再谈调参**：调大 `--max-old-space-size` 之类上限只能推迟崩溃，不能修复泄漏；它是容量手段，不是修复手段。

## 8. 实测记录（代理 VM 上真实运行）

> 环境：代理 VM，Node.js v24.22.1，V8 13.6.233.17-node.58，linux-x64。以下输出均真实跑过；地址、耗时、兆字节数每次运行都会变化，数值仅作本机示例，不作性能承诺。

1. 年轻代回收（Scavenge）：

   ```bash
   node --trace-gc -e 'for(let i=0;i<100000;i++){({a:i,b:i*2})} console.log("ok")'
   ```

   实测通过：输出多行 `Scavenge 5.8 (6.3) -> 5.3 (7.3) MB, ... allocation failure`，即年轻代满后触发 Minor GC、堆占用回落。

2. 老年代回收（Mark-Compact）与“释放后回落”：

   ```bash
   node --expose-gc --trace-gc -e 'global.gc(); let keep=[]; for(let i=0;i<500000;i++) keep.push({v:i}); console.log("before", Math.round(process.memoryUsage().heapUsed/1048576)+"MB"); keep=[]; global.gc(); console.log("after", Math.round(process.memoryUsage().heapUsed/1048576)+"MB");'
   ```

   实测通过：输出含 `Mark-Compact 7.6 (11.6) -> 6.7 (11.8) MB ... GC in old space requested`；本机一次运行的 `before 31MB` 在解除引用并手动 GC 后变为 `after 7MB`。这验证了 4.2 节与 7.2 节的两点：解除引用后对象才可回收；堆回落要以 GC 后的值为准。

3. 泄漏与非泄漏的对照（同一脚本，只差是否解除引用）：

   ```bash
   node --expose-gc -e 'function used(){return Math.round(process.memoryUsage().heapUsed/1048576);} let cache=[]; global.gc(); let a=used(); for(let i=0;i<200000;i++) cache.push({i}); global.gc(); let b=used(); cache=[]; global.gc(); let c=used(); console.log("baseline",a,"MB retained",b,"MB freed",c,"MB");'
   ```

   实测通过：本机输出 `baseline 7 MB retained 15 MB freed 7 MB`——数组被 `cache` 持有时 GC 后仍占 15MB，解除引用并 GC 后回到 7MB。这就是 7.1 节模式 1 的最小复现：GC 无法回收仍可达的对象。

> 注意：以上 `--expose-gc` 用法仅用于诊断演示。生产代码里不要依赖 `global.gc()`；浏览器页面脚本也没有这个手段。

## 9. 常见误解

- “内存涨了就是泄漏”：错。先看 GC 后的基线是否持续抬高（见 4.5 节与 7.2 节）。
- “GC 会回收所有没用的对象”：错。GC 只回收不可达对象；仍被引用但不再被读的对象，它无权回收。
- “调大堆上限能修泄漏”：错。只能推迟内存耗尽，不能消除持续增长的持有链。
- “增量 GC 让 GC 变快了”：不准确。增量主要是把暂停摊薄，总耗时通常略增；它优化的是延迟，不是吞吐（见 4.3 节）。
- “手动 GC 能解决内存问题”：错。`global.gc()` 只是诊断时强制触发一次回收；真正的修复是断开不必要的引用。
