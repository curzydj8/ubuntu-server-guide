# 开发者工具使用详解

> 阅读提示：本篇以 Chrome 内置的 DevTools 为例。Edge、Brave 等 Chromium 系浏览器面板大体相同，Firefox、Safari 有功能相近但名称与细节不同的自带工具，以各自文档为准。
>
> 环境说明：本地没有可交互验证 DevTools 面板的浏览器环境，本篇所有面板操作描述均以 Chrome 官方文档为准，演示一律为**示例未实测**，不许理解为“实测通过”；请在自己的 Chrome 里按每节验证步骤跑一遍。

## 1. 工具定位

Chrome DevTools 是直接内置在 Chrome 里的一套网页开发工具：改页面、查样式、看请求、测性能、断点调试，都不用另装软件。它解决的核心问题是“页面在浏览器里到底发生了什么”——源代码写的是意图，DevTools 看到的是浏览器真实执行的结果：真实的 DOM、真实的请求时序、真实的主线程耗时。查线上问题时，先问 DevTools，再猜代码。

本篇只讲最常用的三个面板：Elements（看结构与样式）、Network（看请求）、Performance（看耗时）。Console、Sources、Application、Lighthouse 等面板各有专长，不在本篇展开，需要时以官方文档为准。

打开方式（以官方文档为准）：在页面上右键 → **检查**，直接跳到 Elements 面板并定位到所点元素；或按 `Ctrl+Shift+C`（Windows / Linux / ChromeOS）或 `Cmd+Option+C`（Mac）进入元素检查模式；`F12` 或 `Ctrl+Shift+I`（`Cmd+Option+I`）打开上次使用的面板。面板名、快捷键若随版本变化，以当前浏览器内显示为准。

## 2. 适用环境

- 系统 / 版本：Chrome 浏览器内置，无需安装；本篇事实以 Chrome 官方文档为准（Network 教程 2024-10-14 更新、Performance 运行时分析教程 2024-10-23 更新，个别面板细节可能随版本演进，以当前浏览器内显示为准）。
- 安装方式：不适用（浏览器内置）。
- 权限要求：不适用（调试自己打开的页面不需要管理员权限；调试他人线上页面只能看到浏览器收到并渲染的内容，看不到对方服务器源码与数据库）。

## 3. 基本用法

### 3.1 先定排查路线：三个面板各管什么

| 现象 | 先开哪个面板 | 看什么 |
| --- | --- | --- |
| 样子不对、布局乱了、样式没生效 | Elements | 真实 DOM 与最终生效的 CSS |
| 数据没回来、接口报错、页面一直转圈 | Network | 请求列表、状态码、响应体、耗时分解 |
| 页面卡、动画掉帧、操作反应慢 | Performance | 帧率、主线程火焰图、长任务与强制布局警告 |
| 不知道慢在哪 | Performance 先录一段，再由结果决定是看 Network 还是看代码 | 官方文档也提醒：不要一上来就只盯 Network，加载慢不一定是网络问题 |

一个通用前提：**Network 只记录 DevTools 打开之后发生的请求**。查加载问题要先开 DevTools 再刷新页面，否则关键请求已经错过了；同理，Performance 只记录录制时间段内的活动。

### 3.2 Elements 面板：看真实 DOM，不是看源文件

Elements 面板左侧是 DOM 树，右侧是选中节点的样式等信息。关键认知：这里显示的是浏览器当前持有的 DOM——JavaScript 运行后增删改过的结构，而不是服务器最初发来的 HTML 源文件。两者对不上时，以 DOM 树为准。

核心用法（均以官方 DOM 教程为准，示例未实测）：

- **定位节点**：页面上右键 → 检查；或在 Elements 面板点“选择元素”图标，再点页面上的元素；已选中节点可用方向键在 DOM 树里上下移动、左右折叠 / 展开。
- **找节点**：在 Elements 面板按 `Ctrl+F`（`Cmd+F`）打开搜索条，可按文本、CSS 选择器、XPath 搜索；面板会选中第一个匹配结果并滚动到可见位置。
- **临时改内容与属性**：双击节点文本改文字，双击属性名或属性值改属性，双击标签名可改节点类型，右键节点可选“以 HTML 格式编辑”整段改写；拖动节点可调整顺序。所有改动只影响当前页面、刷新即失效——它是验证想法的草稿纸，不是改源码的编辑器。
- **看样式**：右侧 Styles 栏显示作用于该节点的全部规则，划线表示被覆盖的声明；Computed 栏显示最终算出的值。样式没生效时先看这里：是规则没命中、被更高优先级覆盖，还是写错了属性名。
- **强制状态**：右键节点 → Force State，可强制 `:hover`、`:focus`、`:active` 等状态常驻，方便调那些“鼠标一移开就消失”的悬停样式。
- **隐藏 / 删除 / 复制**：选中节点按 `H` 隐藏、再按一次恢复；按 `Delete` 删除（`Ctrl+Z` 可撤销）；右键可复制节点、复制其 JS 路径（`document.querySelector(...)` 表达式，方便在 Console 或测试里复用）。
- **在 Console 里引用选中节点**：选中节点旁边标有 `== $0`，表示在 Console 里输入 `$0` 就是这个节点；需要反复引用时右键“存储为全局变量”，会生成 `temp1` 这类变量。

常见排查流程（示例未实测）：元素没显示 → 在 DOM 树里确认节点是否存在 → 若存在，看 Computed 里的 `display` / `visibility` / 尺寸与溢出 → 若不存在，问题在生成它的脚本或数据，不在样式。

### 3.3 Network 面板：看每一次请求

打开 Network 面板后刷新页面，面板逐行记录所有网络活动：默认列是**状态码（Status）、类型（Type）、发起方（Initiator）、传输大小（Size）、耗时（Time）**，行按时间顺序排列，第一行通常是主 HTML 文档。点某一行，右侧可看该请求的详情：

- **Headers**：请求与响应头、状态码，先看这里确认“请求发到哪、服务器回了什么”。
- **Preview**：对响应体的友好渲染（如把 HTML 渲染出来、把 JSON 结构化展示），适合快速看内容对不对。
- **Response**：响应体原文，适合复制、比对、确认编码与格式。
- **Initiator**：发起链——是谁触发了这次请求，点进去可跳到触发它的源码位置，适合追“这个请求到底是谁发的”。
- **Timing**：一次请求的耗时分解（排队、DNS、连接、等待响应、下载各占多久），适合区分“服务器慢”还是“传输慢”还是“前面被别的请求挡住了”。

常用操作（均以官方 Network 教程为准，示例未实测）：

- **过滤**：顶部过滤栏按类型按钮（JS、CSS、Img 等）只看某类资源；过滤框支持字符串、正则与属性过滤（如 `domain:example.com` 只看某域名，按 `-main.css` 排除某文件），多类型可按住 `Ctrl` / `Cmd` 多选。
- **搜索全部请求**：按 `Ctrl+F`（`Cmd+F`）打开搜索，可在所有请求的头与响应体里搜字符串或正则（如搜 `Cache-Control` 检查各资源的缓存策略）。
- **模拟慢网络**：节流下拉框默认“无节流”，可选 3G 等预设，再用“清空缓存并硬性重新加载”重跑，观察首访用户视角下的加载顺序与阻塞情况。
- **看加载过程截图**：在 Network 设置里开启 Screenshots，刷新后可按时间点看页面长什么样、当时正在传什么资源。
- **屏蔽请求做对照实验**：用命令菜单打开 Request Blocking，加一条匹配（如 `main.css`），刷新后看页面在该资源缺失时是“降级可用”还是“直接不可用”；被屏蔽的请求行会以红色显示。做完记得取消屏蔽。

常见排查流程（示例未实测）：

1. 接口没数据 → 先看该请求行是红色失败、还是状态码非 200、还是 200 但响应体是错误页。
2. 状态码 4xx / 5xx → 看 Headers 确认请求地址与参数有没有拼错，再看 Response 确认服务端返回的错误信息（不要只看状态码就下结论）。
3. 请求根本没出现 → 检查是不是 DevTools 打开晚了、是不是被过滤条件藏起来了、是不是发起它的脚本根本没执行（再去 Console / Sources 查）。
4. 加载慢 → 先看 Timing 分解：等待响应时间长是服务端或上游问题，下载时间长看 Size 是否过大、是否可压缩或分包；再结合 Performance 判断是不是主线程也在抢时间。

### 3.4 Performance 面板：看时间花在哪

Performance 面板录一段页面运行过程，再回放分析：它回答的不是“慢不慢”，而是“时间具体花在哪一步、哪行代码”。官方运行时分析教程的工作流是：

1. **准备干净环境**：官方建议用无痕窗口录制，避免已装扩展的干扰；同时开启 CPU 节流（如 4 倍减速）模拟性能较弱的设备——在高性能开发机上不卡的问题，在低端机上可能很卡。
2. **录制**：点 Record，执行那个“感觉慢”的操作（滚动、点击、加载），再点 Stop；也可以用“开始分析并重新加载页面”直接录一次完整加载。
3. **先看概览**：顶部 FPS 图表出现红色条，说明帧率掉到可能影响体验的程度；CPU 图表长时间满格，说明主线程一直在干活，是“做太多事”的信号；把鼠标在概览图上左右移动可逐帧回放当时页面截图。
4. **再看 Main 火焰图**：展开 Main 区，横轴是时间、纵轴是调用栈，条越宽表示该事件耗时越长；点一个事件，下方 Summary 栏会说明它是什么、由谁发起，并给出跳到相关源码的链接。
5. **认警告标志**：事件右上角的红色三角是警告；Task 上的红三角表示长任务，Layout 事件上的警告常指向强制同步布局（forced reflow，即在读布局信息后又立刻改布局，逼浏览器反复算布局）。官方示例里正是沿着“Summary → 强制布局警告 → 源码链接”这条线找到肇事代码的。

常见排查流程（示例未实测）：

- **动画掉帧**：录一段动画 → 看 FPS 图红条出现的位置 → 在 Main 火焰图里找对应时间段最宽的事件 → 看它是脚本、样式计算、布局还是绘制 → 只改布局属性的动画（如宽度）要一路重做布局与绘制，优先改成只走合成的属性（如位移、透明度），原理见本组第一篇。
- **点击后反应慢**：录“点击 → 界面更新”全过程 → 找点击事件后最宽的长任务 → 沿 Summary 的源码链接定位 → 看是同步计算太重、还是强制布局、还是在主线程做了本可推迟的工作。
- **加载慢但 Network 看不出问题**：录一次加载 → 看 Main 火焰图里加载阶段的脚本执行与样式、布局占比；若主线程被长任务占满，瓶颈在执行不在传输，优化方向是拆任务、减计算，而不是加带宽。

## 4. 常用选项与场景

- **样式调不通**：Elements 的 Styles + Computed，先确认规则是否命中、是否被覆盖，再怀疑选择器写法。
- **接口联调**：Network 的 Headers + Response，先确认地址、参数、状态码、响应体四项，再讨论业务逻辑。
- **弱网体验**：Network 节流 + 清空缓存硬刷新，模拟首访与慢网用户；不要只在开发机千兆网络下验收。
- **卡顿定位**：Performance 录制 + CPU 节流，先看 FPS 与 CPU 概览定性，再钻 Main 火焰图定量到事件与源码。
- **回归对照**：同一操作改动前后各录一段 Performance、Network 各截一次关键请求耗时，只凭感觉说“变快了”不算数。

## 5. 风险与注意事项

- **DevTools 的改动不保存**：Elements 里改的 DOM 与样式、Network 里屏蔽的请求，刷新页面即失效；确认有效的改法要回源码里正式改，不要把“DevTools 里调好了”当成“修好了”。
- **不要在 DevTools 里对生产页面做写操作验证**：改 DOM 只是改自己浏览器里的呈现，不会改服务器数据；但 Console 里执行写请求、改存储的操作是真实生效的，生产环境慎用。
- **录制数据会带隐私**：Performance 与 Network 的录制里可能含请求体、Cookie、页面内容，截图与导出文件发给他人前先检查、脱敏。
- **扩展会污染测量**：日常装的扩展会在页面里注入脚本、发请求，性能录制与 Network 记录都会带上它们的噪声；做正式测量前用无痕窗口或干净配置。
- **节流是模拟，不是真实设备**：CPU 节流与网络节流能放大问题、不能等同真机；关键结论要在目标设备或真实网络下复核。
- **面板细节随版本演进**：本篇写的按钮位置与预设（如节流档位）以写作时官方文档为准，当前浏览器内显示不一致时以浏览器内显示为准，不要硬按本文点。

## 6. 读者验证步骤（示例未实测）

> 以下是在自己 Chrome 里的验证方法，不是本文已跑过的测试。

1. 打开任意页面，右键 → 检查，确认 Elements 面板定位到所点元素；改一次该元素的文字与一个样式属性，确认页面即时变化、刷新后恢复原样。
2. 保持 DevTools 打开，刷新页面，在 Network 里找到主文档请求，依次打开 Headers、Preview、Response、Timing，确认四项内容与本篇 3.3 的描述一致；再试一次过滤与 `Ctrl+F` 搜索。
3. 打开 Performance 面板，设 CPU 为 4 倍减速，录一段滚动或点击操作，确认能看到 FPS、CPU 概览与 Main 火焰图，并能点开一个事件看到 Summary。
4. 在一个已知较重的动画页面上重复第 3 步，对比“改位移”与“改宽度”两种动画在火焰图里的布局事件数量，验证本组第一篇“合成属性更省”的结论。

## 7. 常见问题

- **Network 里是空的，是页面没发请求吗？** 多半是 DevTools 打开晚了：Network 只记录打开之后的请求，先开面板再刷新页面。
- **Elements 里看到的结构和“查看网页源代码”不一样，哪个对？** 都对，但说的是不同东西：源代码是服务器发来的初始 HTML，Elements 显示的是脚本运行后的真实 DOM；查渲染问题以 DOM 为准。
- **Performance 录出来全是数据，从哪下手？** 按官方教程的顺序：先看 FPS 红条定有没有问题，再看 CPU 图定是不是主线程满载，最后钻 Main 火焰图里最宽的事件，不要从第一行逐条读。
- **页面在开发机上不卡，还要测吗？** 要。开发机性能远高于普通用户设备，官方教程明确建议录制时开 CPU 节流模拟弱设备；上线前至少做一次节流下的对照录制。
