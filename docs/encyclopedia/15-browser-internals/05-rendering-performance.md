# 关键渲染路径与渲染性能优化

> 本篇是总览篇的深挖篇。总览只讲“首屏要经过哪几步”，本篇只讲“每一步被什么卡住、以及每种优化手段到底在换什么”。
> 总览：[渲染引擎与渲染流程](01-rendering-pipeline.md)；代价区分（重排/重绘/合成）见上一篇：[布局、绘制与合成](04-layout-paint-composite.md)。
> 本篇不含任何本机实测：所有浏览器内行为、耗时与收益数字均为原理说明，**示例未实测**，不得当作实测结论引用；厂商宣传的提速倍数一律不采信。

## 1. 本章目标

读完本篇，能把“页面慢”定位到关键渲染路径（CRP）上的具体关卡——是 HTML 还没到、CSS 还在挡渲染、脚本还在挡解析、字体或图片还在等发现——再判断手头的优化手段到底是在缩短路径、提前发现，还是在把代价挪到首屏之后。

## 2. 背景与问题

关键渲染路径是指：浏览器从拿到 HTML 起，到首次把内容画出来为止，必须走完的步骤序列。路径越长、关卡越多，首屏越晚；路径上的每一步都可能成为瓶颈，但瓶颈各不相同，解法也各不相同：

- CSS 挡的是“渲染”，脚本挡的是“解析”，两者不能混为一谈；
- 字体与图片挡的不是同一类东西：字体挡的是“文字能不能按最终字形画”，图片挡的是“最大内容何时能画、版式会不会抖”；
- 很多优化不是“让某一步变快”，而是“让某一步不在首屏路径上”——代价没有消失，只是被挪到了首屏之后或用户交互时。

本篇按“关卡 → 手段 → 代价”的结构讲，不讲页面写法本身（写法属 03 域），代码片段只作机制示意。

## 3. 总体架构

CRP 的主线与关卡可以画成一张图。注意：这张图只画首屏路径，首屏之后的交互、动画与滚动优化见第 4 节后半与上一篇。

```
HTML 到达 ──解析──▶ DOM（增量构建）
   │  脚本关卡：普通 <script> 阻塞解析；脚本执行前还可能等 CSSOM
   ▼
CSS 到达 ──解析──▶ CSSOM（须完整才可用）
   │  渲染关卡：CSSOM 没建好，浏览器宁可不画首屏
   ▼
DOM + CSSOM ──▶ 渲染树 ──▶ 布局 ──▶ 绘制 ──▶ 合成 ──▶ 首屏
   │  字体关卡：文字按哪套字形画、等不等字体到
   │  图片关卡：最大内容元素何时被发现、尺寸是否已定
   ▼
首屏之后：非关键脚本执行、非关键样式应用、屏外内容渲染
```

优化手段在这张图上的位置只有三类：**缩短路径**（关键资源更少、更小）、**提前发现**（关键资源更早被下载）、**移出路径**（非关键工作挪到首屏之后）。判断一种手段时，先问它属于哪一类、挪走的代价由谁在何时付——这是整篇的判断框架。

## 4. 工作机制

### 4.1 CRP 各阶段的阻塞点

#### CSS：渲染阻塞

CSS 默认是渲染阻塞资源。浏览器看到样式表（内联 `<style>` 或外链 `<link rel="stylesheet">`）后，会避免在 CSSOM 建好之前渲染更多内容，理由在总览篇已讲：后出现的规则可能覆盖前面的，先画再改会闪变。阻塞的后果取决于样式表的位置与大小：

- 样式表在 `<head>` 靠前、体积小，阻塞时间短；
- 样式表在文档靠后、体积大或链式依赖多（样式表里再 import 别的样式表），阻塞时间就长；
- 媒体查询不匹配当前视口的样式表（如 `media="print"`）不阻塞当前渲染——这是“把非关键 CSS 移出路径”的机制基础，见 4.3。

关键点：CSS 阻塞的是“渲染”，不是“解析”。浏览器在等 CSS 时仍可继续解析 HTML（解析与渲染是两条线），但画不出来。把“解析慢”与“渲染慢”分开，是定位 CRP 问题的第一步。

#### JavaScript：解析阻塞，且可能等 CSSOM

普通 `<script>`（无 `async`/`defer`）是解析阻塞资源：解析器遇到它就停下来，先下载、解析、执行脚本，再继续解析后面的 HTML。原因也是机制性的：脚本可能修改正在构建的 DOM，解析器无法在不知道脚本干了什么的情况下继续。

脚本阻塞还有第二层：脚本执行前可能要等尚未完成的 CSSOM。因为脚本可能读取计算样式，浏览器必须先把 CSSOM 建好，才能让脚本读到正确结果。于是出现一种连锁阻塞：**脚本在等 CSS，解析在等脚本，渲染在等解析**——首屏被一条链拖住时，先找链上最靠前的环节。

浏览器有一个缓解机制：**预加载扫描器**。主解析器被脚本挡住时，扫描器会提前扫一遍原始 HTML，把后面出现的图片、样式、脚本先发起下载。扫描器只能发现“写在 HTML 里的资源”：由 JavaScript 动态拼出来的内容、CSS 背景图这类“要执行/解析后才知道”的资源，扫描器发现不了，发现时间就晚。这是“首屏大图不要只用 JS 注入、不要只放 CSS 背景里”的机制原因。

#### 字体：文字画不画、按哪套画

字体是 CRP 上最容易被误判的关卡。浏览器要画文字，必须知道字形；自定义字体文件到达之前，浏览器面临两难：先画 fallback 文字、等字体到了再换（会出现字体替换闪烁，FOUT），还是先不画文字、等字体到了再画（会出现文字不可见，FOIT）。`font-display` 就是让作者显式选这条取舍的描述符，写在每条 `@font-face` 规则里。按 web.dev 对浏览器行为模型的总结（具体实现细节以官方发布为准）：

| `font-display` 取值 | 阻塞期（文字不可见） | 替换期（fallback 先显示、后替换） | 适用取舍 |
| --- | --- | --- | --- |
| `block` | 较长（约 2–3 秒量级） | 无限（字体到了就换） | 宁可文字晚出现，也要最终字形；正文一般不选 |
| `swap` | 极短 | 无限（字体到了就换） | 正文常用：先保证文字可见，字体到了再换 |
| `fallback` | 约 100 毫秒 | 约 3 秒（过期后不再换） | 折中：迟到的字体不再引起 late 替换 |
| `optional` | 约 100 毫秒 | 无（过期后不再换） | 性能与版式稳定优先：慢网络下可能永远用 fallback |

上表的时间是行为模型值，不是各浏览器的实测承诺；不同引擎、不同网络条件下的实际表现以官方文档为准（待核实）。除 `font-display` 外，字体还有两个连锁代价：

- **发现晚**：浏览器必须先下载 CSS、构建页面，才知道需要哪些字体；字体下载启动得比 CSS、图片都晚。预加载（见 4.3）就是把这个发现时间提前。
- **替换抖动**：fallback 字体与自定义字体的字形宽度、行高不同，替换时会让文本换行位置变化，进而触发布局重算（见上一篇 4.1 的“内容驱动尺寸”）。用 `size-adjust` 等度量覆盖描述符调整 fallback 字体的度量去贴近自定义字体，可以缩小替换时的版式位移，但“贴近”不等于“相等”，残余位移仍需实测确认。

#### 图片：发现晚、尺寸未定、最大内容

图片在 CRP 上的关卡有三层：

1. **发现**：写在 HTML 里的 `<img>` 可被预加载扫描器发现；CSS 背景图、JS 注入的图片发现得晚。首屏最大内容（LCP）元素若是图片，发现晚就直接拖后 LCP。
2. **尺寸**：图片在加载完成前若无预留尺寸，加载后获得真实宽高时会撑开布局，引发后续内容位移（布局偏移，CLS 的来源之一）。给 `<img>` 写明 `width` 与 `height`（或用 `aspect-ratio` 预留比例），是让布局在图片到达前就把位置定下来的机制手段。
3. **体积与格式**：图片本身的下载时间取决于体积与网络；响应式图片（按视口与设备像素比选不同尺寸）与现代压缩格式是“缩短下载时间”那一类手段，具体格式支持状态因浏览器版本而异，以官方发布为准（待核实）。本篇不推荐具体格式，只讲“体积与尺寸匹配”的原则：给手机送桌面大图，是路径上纯粹的浪费。

#### 其他关卡：长任务、第三方与服务端

- **长任务**：主线程上一次执行过久的脚本会挡住样式、布局与交互响应；首屏路径上的长任务直接拖后首次渲染，首屏后的长任务则表现为交互卡顿。拆分任务、把非关键脚本移出首屏，是同一条“移出路径”原理。
- **第三方资源**：第三方脚本、字体、统计代码若放在首屏路径上，会与关键资源争带宽、争主线程；其阻塞方式与自有资源相同（CSS 挡渲染、脚本挡解析），只是作者更难控制其体积与到达时间。处理原则是：先确认它是否必须在首屏路径上，不必须的就挪后或按需加载。
- **服务端与网络**：HTML 首字节到达得晚（TTFB 高），后面一切都晚；这一步属网络与服务端域（见 02 篇），本篇只把它记为 CRP 的起点关卡，不展开服务端优化。

### 4.2 优化手段总览：先定性，再定量

判断手段前，先把它放进第 3 节的三类里：

| 手段 | 属于哪类 | 首屏收益的机制 | 付出的代价 / 风险 |
| --- | --- | --- | --- |
| 关键 CSS 内联 + 非关键 CSS 异步 | 缩短路径 + 移出路径 | 首屏样式无需再等一次样式表往返 | 内联 CSS 增大 HTML 体积、不可缓存；异步样式到达前可能出现无样式闪烁（需兜底） |
| `defer` / `async` 脚本 | 移出路径 | 解析不再被脚本挡住 | 见 4.3：执行时机与顺序变化，依赖关系错了会出错 |
| 预加载、预连接、优先级提示 | 提前发现 | 关键资源更早开始下载 | 见 4.3：预加载错资源等于抢关键资源带宽 |
| `font-display` + 字体预加载 | 提前发现 + 显式取舍 | 文字更早可见、字体更早到达 | `swap` 有替换抖动；`optional` 可能放弃自定义字体；预加载字体须配 `crossorigin` |
| 图片预留尺寸、懒加载屏外图片 | 缩短路径 + 移出路径 | 首屏布局先定、屏外图片不争首屏带宽 | 懒加载误用于首屏图片会拖后 LCP；预留尺寸写错仍会抖动 |
| 合成层提升（`will-change` 等） | 换路径（动画走合成） | 动画跳过布局与绘制 | 见 4.4：内存代价，滥用反噬 |
| `content-visibility: auto` | 移出路径（渲染层面） | 屏外内容跳过布局与绘制 | 见 4.4：须配尺寸占位，否则滚动条抖动 |

没有“只赚不赔”的手段：每一行“代价”列都是必须在自己的页面上验证的项。本篇不给任何手段的“平均提速”数字——页面结构、网络、设备不同，收益不同，厂商宣传倍数一律不采信。

### 4.3 缩短与提前：关键 CSS、脚本加载、预加载

#### 关键 CSS：内联首屏样式，异步加载其余

关键 CSS 是指“首屏视口内内容真正用到的样式”。做法是把这部分样式直接内联进 `<head>` 的 `<style>` 里，首屏渲染不再等外链样式表；其余样式改走非阻塞方式加载，例如用 `media="print"` 配合加载后切回 `media="all"` 的技巧，或用 `<link rel="preload" as="style">` 在加载完成后再切换为样式表。两点代价必须同时讲：

- 内联的 CSS 随每个 HTML 响应重复传输、不能像外链文件那样被浏览器缓存；内联量越大，HTML 越大，首字节后的解析负担也越大。内联只给“真正关键”的一小部分，不是把整份样式表塞进 HTML。
- 异步加载的非关键样式在到达前是不生效的：首屏之后滚动到的内容可能先按关键样式画、后按完整样式重画，出现样式闪变。是否可接受，取决于页面结构与内容类型，不是“异步就一定好”。

#### 脚本加载：`defer`、`async` 与模块脚本

三者的区别只在“下载是否挡解析”与“执行时机、顺序”：

| 写法 | 下载 | 执行时机 | 顺序保证 | 适合场景（机制层面） |
| --- | --- | --- | --- | --- |
| 普通 `<script>` | 阻塞解析 | 下载完立刻执行 | 按文档顺序 | 必须在解析中途就运行、且后续解析依赖其结果的脚本；首屏路径上应尽量避免 |
| `async` | 并行下载 | 下载完立刻执行 | 不保证 | 彼此独立、不依赖 DOM 完成状态的脚本，如统计、广告类 |
| `defer` | 并行下载 | 文档解析完成后、`DOMContentLoaded` 之前 | 按文档顺序 | 依赖完整 DOM、彼此有依赖顺序的首屏后脚本；是首屏路径上最常用的移出方式 |
| `type="module"` | 并行下载 | 默认按 `defer` 行为 | 按模块依赖图 | 模块化脚本；默认 deferred，不必再写 `defer` |

选错的代价是功能性的，不是性能性的：`async` 脚本若依赖另一脚本先执行，顺序错了就会出错；`defer` 脚本若必须在解析中途改写 DOM，挪后就错过了时机。优化前先确认脚本的依赖关系与执行时机要求，再选属性——“全部加 `defer`”不是通用答案。

#### 预加载、预连接与优先级提示

- **`<link rel="preload">`**：告诉浏览器“这个资源马上就要用，现在就开始下载”，用于纠正“发现晚”的资源（首屏字体、首屏大图、关键样式）。预加载只提前下载，不改变资源是否阻塞：预加载的样式表在切换为 stylesheet 之前不阻塞渲染，预加载的字体仍需 `font-display` 决定文字行为。
- **预加载的两个常见坑**：一是预加载了首屏并不用的资源，等于用关键带宽去抢关键资源；二是字体预加载漏了 `crossorigin`——字体一律按 CORS 模式取，缺了该属性，预加载的请求与实际字体请求无法复用，可能导致字体被取两次。预加载只给“确定在首屏用、且发现确实晚”的 1–2 个资源。
- **`<link rel="preconnect">`**：提前与第三方源完成 DNS、TCP、TLS 握手，省掉后续请求建立连接的时间；用于“确定会用、但还没发请求”的第三方源。只预连接真正会用的源，多余的预连接是纯开销；字体源的预连接同样需要 `crossorigin`。
- **`fetchpriority`**：给资源标高/低优先级提示（如首屏大图标高、屏外图片标低），让浏览器在带宽竞争时先保关键资源。它是“提示”而非“命令”，最终调度仍由浏览器决定；且它不能把一个发现晚的资源变早——发现问题仍需预加载解决。
- **早期提示（103 Early Hints）**：服务端在正式响应完成前，先告诉浏览器可以预加载哪些关键资源；这是把“提前发现”再往前推一步的服务端手段，是否可用取决于服务端与 CDN 是否支持（待核实，本篇不展开配置）。

### 4.4 移出与换路径：屏外内容、合成层提升的取舍

#### `content-visibility: auto`：跳过屏外渲染

对长页面、长列表的屏外区块，`content-visibility: auto` 让浏览器在区块与用户无关时跳过其布局与绘制，等区块接近视口、获得焦点或被查找时再渲染；与 `display: none` 不同，跳过的内容仍留在 DOM 与无障碍树中，可被查找与聚焦。这是“渲染层面移出路径”的手段，收益取决于屏外内容占首屏渲染工作的比例——屏外内容本来就少时，收益也小。

必须配对使用的另一半是 `contain-intrinsic-size`：被跳过的区块在布局时没有真实尺寸，若不给占位尺寸，滚动条会在区块陆续渲染时反复跳动、滚动位置漂移。常见写法是 `content-visibility: auto; contain-intrinsic-size: auto 500px;`——其中 `500px` 只是占位示意值，不是推荐值；`auto` 关键字让浏览器在区块渲染过一次后记住其真实尺寸，后续跳过时用记住的尺寸占位。不要把 `content-visibility: auto` 用于首屏内容：首屏内容被跳过等于首屏被主动推迟。

与之相关的另一属性是 `contain`（如 `contain: layout paint`）：它告诉浏览器某元素的内部布局与绘制与外部隔离，内部变化不必牵连外部重算。`content-visibility: auto` 内部已隐含布局、样式与绘制 containment；`contain` 是更细粒度的手动版本，用于“内部确实独立”的组件。注意 `contain: paint` 会裁剪溢出内容：靠溢出实现的下拉、提示类元素不能用 paint containment，否则会被裁掉。

#### 合成层提升：取舍与内存代价（本篇只讲优化视角，机制见上一篇）

把元素提升为合成层，是把动画从“布局—绘制—合成”换成“只合成”的手段，收益只在动画确实只改合成属性时成立。优化视角的取舍表：

| 做法 | 收益 | 代价 |
| --- | --- | --- |
| 动画用 `transform` / `opacity` | 走合成路径，跳过布局与绘制 | 需元素已在合成层；位图未就绪时仍需等待光栅化 |
| 动画前加 `will-change`，动画后移除 | 建层时机提前，动画首帧不被建层拖住 | 建层即占内存；常驻等于常付代价；对大批元素用会显著增加内存 |
| 样式表里常驻 `will-change` 或到处写 `translateZ(0)` | 看似“一劳永逸” | MDN 定性为最后手段、反对预判式使用；层泛滥时内存与合成管理开销反噬，低端设备更明显 |
| 动画改 `width` / `top` / `left` | 直观、易理解 | 每帧都走布局甚至全量绘制，代价最大；优先改写为等效的 `transform` 表达 |

内存估算示意（非实测，忽略分块、压缩与设备差异，算法见上一篇 5.2）：一层位图大致为 `宽 × 高 × 4 字节`，`800 × 600` 的层约 `1.9 MB`，设备像素比为 2 时约 4 倍。估算的意义是建立量级感——“几十个大层”与“几个小层”不是一个量级——而不是给出可引用的实测内存数。层数与每层内存以 DevTools 的 Layers 面板在目标设备上的实测为准，本篇不给安全阈值。

## 5. 关键设计取舍

- **阻塞换正确**：CSS 挡渲染、脚本挡解析，都是“宁可晚画、不能画错/算错”的取舍。优化不是取消阻塞，而是把“必须挡”的东西减到最少、把“不必挡”的东西挪出路径。
- **提前换带宽**：预加载、预连接、内联关键 CSS 都是把未来的工作提前到现在；提前的代价是现在的带宽与 HTML 体积。提前错对象，等于把关键资源的带宽让给了非关键资源。
- **可见换稳定**：`font-display: swap` 用“先看见 fallback、后替换”换文字可见性，代价是替换抖动；`optional` 用“可能放弃自定义字体”换版式稳定。没有同时“立刻可见、最终字形、绝不抖动”的选项，选哪条取决于文字是品牌关键还是正文阅读。
- **流畅换内存**：合成层用内存换动画流畅；层泛滥时内存与管理开销会把收益吃掉。流畅的正确单位是“关键动画走合成”，不是“层多”。
- **首屏换后续**：几乎所有 CRP 优化都是把代价从首屏挪到首屏后；挪走不等于消除。首屏后集中爆发的非关键脚本、样式与屏外渲染，仍可能在用户刚开始交互时造成卡顿，需要同样按“移出—分批—按需”处理。

## 6. 分类与变体

- **按优化目标**：首屏优化（CRP：缩短、提前、移出）与交互优化（帧内工作量：批量读写、合成动画、跳过屏外渲染）。两者手段有重叠（合成层、屏外跳过），但衡量标准不同：前者看首次渲染时间，后者看帧时间与交互响应。
- **按衡量指标**：首次内容绘制（FCP：首个内容画出）、最大内容绘制（LCP：最大内容画出）、布局偏移（CLS：版式位移量）、交互响应（INP：交互到下一次绘制的延迟）。web.dev 给出的常用参考阈值（以官方发布为准，见未完成项）为 LCP 良好线约 2.5 秒、INP 良好线约 200 毫秒、CLS 良好线约 0.1；阈值是“真实用户数据 75 分位”的参考线，不是实验室单次测量的承诺值。定位时先看哪个指标差，再回 CRP 图上找对应关卡：LCP 差先查发现与阻塞，CLS 差先查尺寸与字体替换，INP 差先查长任务与帧内工作。
- **按渲染分工**：客户端渲染（CSR：首屏内容依赖脚本拼出，CRP 上多了一段脚本执行）、服务端渲染（SSR：服务器先拼好 HTML，首屏快、后续再由脚本接管）。分工不改变 CRP 的关卡结构，只改变“谁、在哪一步、付出多少”——CSR 的首屏瓶颈更可能落在脚本，SSR 的首屏瓶颈更可能落在服务端与 HTML 到达。
- **按引擎**：各引擎的预加载扫描、字体行为模型、合成层提升条件与优先级调度实现各异；本篇讲的是共通机制，具体行为与默认值以各引擎当前文档为准（待核实）。

## 7. 应用与限制

- **应用（机制推论，不展开写法）**：
  - 首屏慢时按 CRP 图逐段排查：HTML 到达 → CSS 阻塞 → 脚本阻塞 → 字体/图片发现 → 布局绘制合成，先定位关卡再选手段，不要先堆手段。
  - 动画卡顿时先查“走了几步”（见上一篇 4.5）：走布局的改写为 `transform` 表达，走绘制的缩小重绘范围，走合成的检查层是否已建、动画后是否及时还层。
  - 长页面首屏慢时，先算屏外内容占比：占比大再考虑 `content-visibility: auto`，占比小则优先处理阻塞与关键资源。
  - 每次优化后只改一个变量、再测一次：多手段齐上时，无法判断哪一个起了作用、哪一个引入了闪变或抖动。
- **限制**：
  - 本篇不展开服务端优化（缓存、CDN、服务端渲染实现）、图片格式选型、打包与代码分割实现；这些属网络、服务端与 03 域，CRP 视角只指出它们在路径上的位置。
  - 本篇不给任何“提速百分比”“安全层数”“内联 CSS 字节上限”等数值承诺；所谓“关键 CSS 不超过某 KB”一类说法在本篇只作“内联量宜小”的定性提醒，具体上限以自己页面的实测为准。
  - 本篇不展开 Core Web Vitals 的完整定义与采集方法，只用其指标名作定位线索；指标口径以 web.dev 官方文档为准。
- **读者验证步骤（未在本机实测）**：
  1. 在自己浏览器里打开目标页面，按 F12 → Performance 面板 → 录制一次刷新，找出最长的渲染阻塞段与解析阻塞段，对照 4.1 判断是 CSS、脚本还是字体/图片。
  2. 在 Network 面板里按“发现时间”看首屏大图与字体是何时开始下载的：若明显晚于 HTML 与 CSS，说明存在“发现晚”问题，再考虑预加载或改为 HTML 内可发现的写法。
  3. 改动后只改一个变量再录一次：比较同一指标（如 LCP 或帧时间）的前后变化，不要同时改多处再归因。

## 8. 常见误解

- **“`defer` 和 `async` 可以随便换”**：错。`async` 不保证顺序、`defer` 保证顺序且在解析后执行；依赖关系与执行时机要求决定了选哪个，选错是功能错误，不是性能差异。
- **“预加载越多越快”**：错。预加载是抢带宽：预加载非关键资源会拖慢关键资源；字体预加载漏 `crossorigin` 还可能导致重复下载。
- **“`font-display: swap` 就没有代价”**：错。`swap` 换来的是文字立刻可见，代价是字体到达后的替换与可能的版式位移；需要度量对齐来缩小位移，且位移无法仅靠声明消除。
- **“首屏快了就是优化完了”**：错。CRP 优化多是把代价挪到首屏后；首屏后集中执行的脚本、样式与屏外渲染仍可能在用户交互时造成卡顿，需要同样处理。
- **“层越多动画越流畅”**：错。见上一篇 5.2：层是内存，泛滥反噬；流畅来自关键动画走合成，不是层多。
