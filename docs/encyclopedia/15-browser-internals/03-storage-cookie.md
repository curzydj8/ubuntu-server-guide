# 存储与 Cookie 模型

## 1. 本章目标

读完本篇，能说清浏览器里几种存储各用来装什么、活多久、谁能读写，以及“清掉 Cookie”为什么不等于“清掉所有数据”。

## 2. 背景与问题

HTTP 本身是无状态的：服务器默认认不出“上一次请求和这一次请求是不是同一个人”。要维持登录态、记住偏好、离线存数据，就得在浏览器里留点东西。但不同东西的需求完全不同：登录凭证要小、要自动跟请求走；用户偏好要大一点、但没必要每次请求都发；离线数据要能装很多、能查询。于是浏览器不是只有一种存储，而是一组各有分工的存储。

本篇讲存储的机制与边界：具体怎么写代码属 03 域；怎么防窃取、防伪造属 10 域。

## 3. 总体架构

```
浏览器存储（按作用域隔离：同源策略）
├── Cookie ───────────── 随请求自动发送，服务器也可读写
├── localStorage ─────── 同源持久键值，标签页共享
├── sessionStorage ───── 同源会话键值，标签页隔离
├── IndexedDB ────────── 同源事务型数据库，大容量、异步
└── Cache Storage ────── 请求/响应缓存（机制见网络篇，脚本可控）
```

分界线只有一条：**同源**（协议 + 域名 + 端口都相同）才能互相读写对方的存储。跨源默认互不可见，这是整套模型的安全地基。

## 4. 工作机制

### 4.1 Cookie：跟着请求走的小纸条

- **来源**：服务器通过响应头 `Set-Cookie` 发，或页面脚本写（脚本写不出 `HttpOnly` 的）。
- **发送规则**：浏览器按 `Domain`（作用域）与 `Path`（路径）匹配，匹配上的请求自动带上；与页面同源与否无关，只看 Cookie 自己的作用域。
- **生命周期**：没写过期时间的是会话 Cookie，浏览器关闭即失；写了 `Expires` 或 `Max-Age` 的是持久 Cookie，到期才失。
- **安全属性**：
  - `Secure`：只在 HTTPS 下发送。
  - `HttpOnly`：脚本读不到，只能由浏览器在请求里带——防脚本窃取，但防不住网络层与服务器侧问题。
  - `SameSite`：控制跨站请求带不带。`Lax`（默认）：顶级导航的 GET 会带，跨站 POST、图片、iframe 不带；`Strict`：跨站一律不带；`None`：跨站也带，但必须配 `Secure`。
- **第三方 Cookie**：由页面内嵌的第三方资源种下的 Cookie；现代浏览器正在逐步限制它（默认分区或拦截），因为它能跨站追踪用户。限制节奏各浏览器不同，属工程发展中的变化，写死某家浏览器的具体时间表都会过期——本篇只讲机制方向。
- **分区 Cookie（CHIPS）**：允许第三方 Cookie 按“顶级站点”分区存放，A 站内嵌的第三方 Cookie 与 B 站内嵌的同名 Cookie 互不可见，是“既要功能、又要隔离”的折中。

### 4.2 Web Storage：不跟请求走的键值

- **localStorage**：同源持久，字符串键值；容量通常约 5MB（各实现有差异，以实现为准）；API 是同步的——读写会占主线程，存大对象会卡页面。
- **sessionStorage**：同源、但按标签页隔离；标签页关闭即失；同源新标签页不共享。
- 两者**都不随请求自动发送**：服务器想知道，得由脚本主动发。这是与 Cookie 最根本的区别：Cookie 是“请求的一部分”，Web Storage 是“页面自己的抽屉”。

### 4.3 IndexedDB：浏览器里的数据库

- 异步、事务型、面向对象：存的不是字符串，而是对象；按对象仓库与索引组织，支持范围查询与游标遍历。
- 容量远大于 Web Storage（一般按磁盘配额动态给，以实现为准），适合离线应用、缓存结构化数据。
- 有版本概念：数据库结构升级要走版本变更流程，旧版本客户端打开新结构库时会触发升级——这是 IndexedDB 最容易出 bug 的地方，也是它“像数据库”的证明。
- 与 Cache Storage 的分工：Cache Storage 存“请求换回来的响应”，IndexedDB 存“应用自己算出来的结构化数据”。

### 4.4 边界总表

| | Cookie | localStorage | sessionStorage | IndexedDB |
|---|---|---|---|---|
| 随请求自动发送 | 是 | 否 | 否 | 否 |
| 容量量级 | 约 4KB/个 | 约 5MB | 约 5MB | 磁盘配额级 |
| 生命周期 | 会话或到期 | 持久（可被清除） | 标签页关闭即失 | 持久（可被清除） |
| 作用域 | Domain/Path | 同源 | 同源 + 标签页 | 同源 |
| API 风格 | 头部/文档属性 | 同步 | 同步 | 异步事务 |
| 典型用途 | 会话、登录态 | 偏好、轻量缓存 | 表单临时状态 | 离线数据、结构化缓存 |

容量数字以实现为准，跨浏览器、跨版本有差异；拿“5MB”当硬上限写判断逻辑会出错。

## 5. 关键设计取舍

- **自动发送换带宽与隐私**：Cookie 自动跟请求走，省了脚本每次手动带，但每个请求都多带字节，且跨站发送能力带来了追踪面——`SameSite` 与分区就是给这项取舍打的补丁。
- **同步简单换主线程**：localStorage 同步 API 写起来简单，但大读写会卡页面；IndexedDB 异步复杂，但不阻塞渲染。
- **持久换清理责任**：持久存储不清理就一直在；浏览器提供“清除站点数据”入口，但用户不点它就不会自动消失——应用自己要负责过期与清理策略。
- **同源隔离换便利**：同源是硬边界，子域想共享要靠 `Domain` 放宽（且放宽方向有限制）；便利与隔离的取舍点就在这里。

## 6. 分类与变体

- 按发送行为：随请求走（Cookie）与不随请求走（其余）。
- 按生命周期：会话级（会话 Cookie、sessionStorage）、持久级（持久 Cookie、localStorage、IndexedDB）。
- 按数据模型：键值（Cookie、Web Storage）、对象数据库（IndexedDB）、响应缓存（Cache Storage）。
- 按控制方：服务器可写（Cookie）、脚本可写（全部）、脚本可控缓存（Cache Storage）。

## 7. 应用与限制

- 应用：登录态与会话（Cookie，配 `HttpOnly` + `Secure` + `SameSite`）；主题、偏好、轻量缓存（localStorage）；多步表单临时状态（sessionStorage）；离线文章、结构化缓存（IndexedDB）。
- 限制：Cookie 单个约 4KB，塞大对象既超限又拖慢每个请求；localStorage 同步 API 不宜存大对象与高频读写；IndexedDB API 繁琐，出错处理与版本升级要认真写；存储不是安全边界——非 `HttpOnly` 的内容脚本可读，跨站脚本拿到就能用，真正的防线在 10 域。
- 常见误解：
  - “清掉 Cookie 就干净了”：错。localStorage、IndexedDB、Cache Storage 各有各的清理项，浏览器“清除 Cookie”默认不一定全清。
  - “localStorage 是永久的”：不全面。用户清站点数据、磁盘配额、浏览器策略都可能清掉它；重要数据要当“可能丢失”来设计。
  - “sessionStorage 关浏览器才丢”：不精确。标签页关闭即丢；浏览器恢复标签页的行为因实现而异，不能依赖。

## 8. 读者验证步骤（未在本机实测）

> 本机无浏览器实测环境，以下是读者在自己浏览器里的验证方法，不是本文已跑过的测试。

1. 打开任意网站，按 F12 → Application（或“应用”）面板 → 左侧 Storage 一栏。
2. 对照查看 Cookies、Local Storage、Session Storage、IndexedDB、Cache Storage 五项：同一站点下它们各自存了什么、容量显示是多少。
3. 在 Console 里执行 `document.cookie`，观察只能看到非 `HttpOnly` 的 Cookie；再对比 Application 面板里标 `HttpOnly` 的项——脚本看不到、请求里会带。
