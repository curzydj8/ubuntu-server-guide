# HTTP 缓存策略详解

> 本篇是总览 [网络栈与缓存](02-network-cache.md) 的深挖篇。总览只讲了“两道门”的结论，本篇讲每道门里每条规则是怎么判定的、有哪些例外、以及选错策略会付出什么代价。总览已讲过的内容（DNS、TCP、TLS、HTTP 版本演进）本篇不再重复。

## 1. 本章目标

读完本篇，能根据一个响应头逐条推断浏览器会不会存、存多久、过期后会不会先问服务器，以及“用户说页面没更新”时应该先查哪条指令。

## 2. 背景与问题

缓存的根本矛盾在总览里已经点明：存得越久越快，更新就越晚被看到。但只靠“设个 `max-age`”解决不了全部问题，现实中至少有四类麻烦：

- **不知道该存多久**：服务器没给任何过期信息，浏览器是直接不存，还是自己猜一个有效期？
- **存了但不敢直接用**：登录后的页面、带个人信息的接口，存下来给别人用就是泄漏。
- **同一个 URL、不同内容**：按语言、按压缩格式返回不同正文时，只按 URL 查缓存会串味。
- **过期了但源站挂了**：是宁可给用户看旧内容，还是宁可报错？

`Cache-Control` 指令表就是为这四类麻烦准备的答案。下面先给判定流程，再逐条讲指令。

## 3. 总体架构

浏览器收到响应后，缓存层按以下顺序做决定（RFC 9111 的核心流程，简化后）：

```
响应到达
   │ ① 能存吗？── no-store → 不存；带 Authorization 且无 public/s-maxage/must-revalidate → 默认不存
   │ ② 新鲜吗？── 算新鲜有效期：s-maxage（共享缓存）/ max-age / Expires / 启发式
   │    新鲜 → 直接用，不发请求（强缓存）
   │    过期 → 进第 ③ 步
   │ ③ 能问吗？── 有 ETag → If-None-Match；只有 Last-Modified → If-Modified-Since
   │    服务器回 304 → 用缓存里的正文；回 200 → 用新正文并更新缓存
   │    问不到（断网、源站 5xx）→ 按 must-revalidate / stale-if-error 决定给旧内容还是报错
   ▼
下一次请求：先按缓存键查（URL + Vary 参与的请求头 + 分区键，见第 7 节）
```

关键一点：**“存”与“用”是两个独立的决定**。`no-cache` 管的是“用之前必须先问”，`no-store` 管的是“根本不许存”，两者不可互换（见第 8 节）。

## 4. 工作机制

### 4.1 第一步：新鲜有效期的计算顺序

新鲜有效期（freshness lifetime）决定强缓存能持续多久。计算有严格的优先级，浏览器不会“取个平均值”：

1. **共享缓存看 `s-maxage`**：只对共享缓存（代理、CDN）有效，且会覆盖 `max-age`；浏览器作为私有缓存不受它约束。
2. **再看 `max-age=N`**：从响应生成时刻起 N 秒内新鲜。`Age` 头（响应在共享缓存里已经待了多久）会计入已消耗时间，所以经手多层缓存的响应，浏览器手里的剩余新鲜期可能比 `max-age` 短。
3. **再看 `Expires`**：老式绝对过期时间。`Cache-Control` 一旦出现，`Expires` 即被忽略；两者都给时以 `Cache-Control` 为准。`Expires` 的值依赖服务器与浏览器时钟是否对齐，时钟 skew 会直接导致“还没过期却已过期”或反之，这是它被 `max-age` 取代的原因之一。
4. **都没有，才轮到启发式缓存**（见 4.5 节）。

`Date` 头是这套算术的起点：`max-age` 从响应生成时间算起，而不是从浏览器收到时间算起；没有 `Date` 时的回退行为以实现为准，本文不展开。

### 4.2 第二步：协商缓存——验证器怎么比对

过期只是“不能直接用”，不是“缓存作废”。浏览器拿验证器去问服务器，服务器只回“没变”或“变了”：

- **强验证器 `ETag`**：资源内容的指纹。浏览器下次带 `If-None-Match: <ETag>`；指纹一致，服务器回 `304 Not Modified`，正文不传输，浏览器用缓存里的正文，并按新响应的头更新缓存元数据。`ETag` 分强弱两种：弱验证器（`W/` 前缀）只保证语义等价，适合内容轻微变化仍可接受的场景；强验证器要求字节级一致。哪种适合哪个资源，由服务器决定，浏览器只负责原样回传。
- **弱验证器 `Last-Modified`**：资源最后修改时间。浏览器带 `If-Modified-Since` 去问。精度只有秒级：一秒内改两次、或内容改了但修改时间没变，都会误判“没变”。所以 `ETag` 优先于 `Last-Modified`；两者都给时，浏览器按规范同时带上，服务器按 `If-None-Match` 优先判定。
- **304 不是错误**：它是协商缓存成功的正常响应，意思是“你手里的那份还能用”。收到 304 后浏览器不会清空缓存，而是刷新缓存条目的新鲜期（按 304 响应里的新头重新算）。
- **只有 `GET`/`HEAD` 语义的响应才走这套流程**：提交类请求（`POST` 等）的响应默认不在浏览器 HTTP 缓存的复用路径上，本文不展开其例外。

### 4.3 Cache-Control 指令全解

下表按“管什么”分组。响应指令是服务器写给缓存的；请求指令是浏览器（或页面脚本通过请求头）写给缓存的，服务器看到请求指令时不负责执行它，执行者是沿途的缓存。

**响应指令：管“能不能存、存给谁”**

| 指令 | 含义 |
| --- | --- |
| `public` | 任何缓存（浏览器、共享缓存）都可以存。即使响应本不该被共享缓存存（如带 `Authorization` 的请求），`public` 也明确放行。 |
| `private` | 只能由私有缓存（浏览器）存，共享缓存不许存。适合带个人信息的页面；但注意 `private` 不等于“不许存”，浏览器照样存。 |
| `no-store` | 任何缓存都不许存，也不许把响应写进任何非易失存储。登录态、支付结果、敏感接口用它。注意：它约束的是存储行为，浏览器仍可能把响应放在内存里用于当前页面渲染，区别在“下一次请求能不能复用”。 |
| `s-maxage=N` | 共享缓存的新鲜有效期，覆盖 `max-age`；浏览器忽略它。只给 CDN/代理，不给浏览器不同策略时用。 |

**响应指令：管“过期后怎么办”**

| 指令 | 含义 |
| --- | --- |
| `max-age=N` | 新鲜 N 秒，见 4.1 节。 |
| `no-cache` | 可以存，但每次用之前必须先向源站验证。没有它字面上的“不缓存”意思。常与 `must-revalidate` 连用，见下。 |
| `must-revalidate` | 过期后不许“将就着用旧内容”：验证失败（源站不可达、返回 5xx）时必须报错，不能擅自给旧内容。 |
| `proxy-revalidate` | 与 `must-revalidate` 相同，但只约束共享缓存，不约束浏览器。 |
| `no-transform` | 中间缓存/代理不许改动响应正文（如转码、压缩格式转换）。 |

**响应指令：扩展指令（不在 RFC 9111 核心内，浏览器支持程度以各自实现为准）**

| 指令 | 出处与含义 |
| --- | --- |
| `immutable` | RFC 8246：响应在新鲜期内绝不会变，浏览器连普通刷新时的条件请求都可以省掉；只有强制刷新才会重新请求。只适用于内容永不改变的 URL（文件名带哈希的静态资源），用在会变的 URL 上等于把更新锁死一个 `max-age` 周期。 |
| `stale-while-revalidate=N` | RFC 5861：过期后 N 秒内，缓存可以先给用户旧内容，同时在后台重新验证；下次访问就能拿到新的。这是用“短暂过期内容”换“零等待”，N 不是新鲜期的延长。 |
| `stale-if-error=N` | RFC 5861：过期后验证时源站出错（5xx 或不可达），N 秒内仍可给旧内容而不是报错。可用性兜底，不是新鲜保证。 |

**请求指令：浏览器发给缓存的要求**

| 指令 | 含义 |
| --- | --- |
| `no-cache`（请求） | 即使缓存里有新鲜副本，也要先向源站验证。 |
| `no-store`（请求） | 不读缓存也不写缓存。 |
| `max-age=N`（请求） | 只接受“年龄”不超过 N 秒的缓存副本；`max-age=0` 等价于要求重新验证。 |
| `min-fresh=N`（请求） | 只接受剩余新鲜期不少于 N 秒的副本。 |
| `max-stale=N`（请求） | 愿意接受过期不超过 N 秒的副本；不带 N 时表示接受任意过期副本。 |
| `only-if-cached`（请求） | 只用缓存，缓存没有就失败（返回 504 语义），不发网络请求。离线场景的显式表达。 |

不认识的指令按规范应被忽略，而不是报错——这是扩展指令能安全部署的前提；但“被忽略”也意味着：不要指望一个新指令在所有浏览器里都生效，关键策略必须用核心指令表达。

### 4.4 Vary：同一个 URL 不止一份缓存

缓存键不只是 URL。`Vary` 头列出的请求头也会参与缓存键：服务器回 `Vary: Accept-Encoding`，表示“压缩格式不同，正文不同”，浏览器要按“URL + 该请求实际带的 `Accept-Encoding`”分别存取；回 `Vary: Accept-Language` 同理。`Vary: *` 表示“每次都必须重新验证”，等于关掉了按 URL 的复用。

`Vary` 用错有两个典型后果：一是漏写——服务器按请求头返回不同内容却没声明 `Vary`，缓存会把 A 用户的内容给 B 用户看；二是滥写——`Vary` 列了一堆无关请求头，缓存被切成大量几乎不复用的碎片，命中率骤降。判断标准只有一条：**凡是影响响应正文的请求头，都应出现在 `Vary` 里；不影响的，一个都不要加**。

### 4.5 启发式缓存：没有任何过期信息时

响应既没有 `Cache-Control`，也没有 `Expires`，但状态码属于“可启发式缓存”的一类（如 200），浏览器**可以**自己估一个新鲜期，而不是默认不存。RFC 9111 建议的典型算法是：取 `Date` 与 `Last-Modified` 之差的 10% 作为新鲜期。例如文件 100 天前修改过，估出的新鲜期约 10 天。

这条规则的危险正在于“可以”二字：10% 只是建议值，不是强制值，不同实现可以取不同比例；而且一旦服务器后续补上 `Cache-Control`，启发式结果立即作废。所以启发式缓存的正确态度是：**把它当作“服务器没表态时的兜底”，而不是策略**。任何希望被稳定缓存的资源都应显式给 `Cache-Control`；任何不希望被缓存的资源更应显式给 `no-store`——“什么都不写”是最不可预测的一种写法。

### 4.6 浏览器里的缓存分层

HTTP 缓存不是一块存储，而是按速度与生命周期分层（与总览 4.5 的“放哪”衔接，本节讲分工与淘汰）：

- **内存缓存**：当前会话内最快的一层，页面内的重复资源、返回上一页时优先命中；标签页关闭、进程退出即失。
- **磁盘缓存**：跨会话持久化，容量大、速度次之；按策略淘汰（最近最少用等，具体算法以实现为准），磁盘满时旧条目先被逐出。
- **Service Worker 的 Cache Storage**：由页面脚本显式控制的另一套缓存，键与策略都由脚本定，不走 HTTP 缓存的头判定；属应用层机制，写法属 03 域，本篇只作区分：HTTP 缓存是“服务器说了算”，Cache Storage 是“脚本说了算”。
- **CDN/代理共享缓存**：在浏览器之外，浏览器只能从它回的响应头（`Age`、`Cache-Control`、`s-maxage`）中间接感知它的存在，不能直接控制它。

同一份资源可能同时存在于内存与磁盘：浏览器先查快的，再查慢的；查到新鲜副本就停，不会为了“更新鲜”继续向下查。

## 5. 关键设计取舍

- **新鲜期换更新延迟**：`max-age` 越长，重复访问越快、源站压力越小，但内容更新被看到的时间也越晚。标准解不是“折中取个中等值”，而是“分层”：HTML 入口给 `no-cache`（每次验证，便宜，因为 304 不传正文），文件名带哈希的静态资源给一年 `max-age + immutable`（内容一变文件名就变，旧缓存自然失效）。两层各取所长，而不是一层迁就另一层。
- **验证换带宽**：协商缓存省正文、不省请求。304 的往返时延还在，弱网下的首字节照样慢；它省的是字节数，不是往返数。真正“零请求”只有强缓存能做到。
- **共享换隐私**：共享缓存省源站带宽，但 `private` 与否的判断一旦出错就是跨用户泄漏。默认策略应是“拿不准就 `private` 或 `no-store`”，而不是“先共享再说”。
- **过期内容换可用性**：`stale-while-revalidate` 与 `stale-if-error` 是在“正确性”与“可用性”之间向可用性倾斜：用户看到稍旧的内容，好过看到错误页；但对价格、库存、权限这类“旧了会误事”的内容，这两个指令一律不该用。

## 6. 分类与变体

- 按判定阶段：强缓存（不发请求）→ 协商缓存（发请求、不传正文）→ 过期兜底（`stale-*`、报错）。
- 按缓存归属：私有缓存（浏览器）与共享缓存（代理/CDN），`private`/`public`/`s-maxage` 就是这条分界线的写法。
- 按策略意图：长期不变（哈希静态资源）、每次验证（HTML 入口）、绝不存储（敏感接口）、过期可用（弱网兜底）。一张表对应四种意图，见第 7 节。
- 按控制方：HTTP 缓存（服务器头说了算）与 Cache Storage（脚本说了算），两者并存、互不替代。

## 7. 应用与限制

**四种意图的推荐写法（服务器视角，浏览器行为按本篇规则推断）**：

| 资源类型 | 推荐写法 | 浏览器行为 |
| --- | --- | --- |
| 文件名带哈希的静态资源（JS/CSS/图片） | `Cache-Control: public, max-age=31536000, immutable` | 一年内不发请求；内容更新靠新文件名 |
| HTML 入口页 | `Cache-Control: no-cache`（可加 `must-revalidate`） | 每次先问服务器，没变回 304 |
| 登录态页面、私人接口 | `Cache-Control: private, no-cache` 或 `no-store` | 共享缓存不存；敏感内容直接不存 |
| 弱网下可接受稍旧的内容 | `max-age=N, stale-while-revalidate=M` | 过期 M 秒内先给旧内容、后台更新 |

**限制与边界**：

- 本篇只讲浏览器 HTTP 缓存的判定；服务器与 CDN 的具体配置（Nginx、CDN 规则）属 06/09 域，不在本篇展开。
- 缓存解决不了的问题：DNS 慢、连接建不起、证书错误、源站本身返回错误内容——缓存只能复用“曾经正确的响应”，不能修正“现在错误的源站”。
- 强制刷新（浏览器提供的“清空缓存并硬性重新加载”）会绕过强缓存与 `immutable`，但它只影响当前浏览器，不影响其他用户与共享缓存；“用户清缓存就好了”不是修复策略，只是排障手段。
- 缓存中毒（攻击者让缓存存下错误内容再分发给他人）属于缓存安全议题，防御核心在源站侧的输入校验与 `Vary` 正确性，本篇只点名，不展开攻击手法。

## 8. 常见误解

- **“`no-cache` 就是不缓存”**：错。`no-cache` 是“存了也得先问”，`no-store` 才是“不许存”；`max-age=0` 是“存了但立刻过期”，效果接近 `no-cache`，但语义上仍是“可存”。三者查表见 4.3 节。
- **“设了 `max-age` 就万事大吉”**：错。`max-age` 只管新鲜期，不管“同一个 URL 返回不同内容”（那是 `Vary` 的事）、不管“共享缓存能不能存”（那是 `private`/`public` 的事）、也不管“过期后源站挂了怎么办”（那是 `must-revalidate`/`stale-if-error` 的事）。
- **“304 是服务器出错”**：错。304 是协商缓存成功的正常响应，见 4.2 节。
- **“不写缓存头就是不缓存”**：错。不写头时浏览器可能按启发式缓存（4.5 节），结果不可预测；不想被缓存必须显式写 `no-store`。

## 9. 可核验示例：本地服务 + curl 看缓存头与 304

> 环境：代理 VM，Python 3.12.3 自带 `http.server` 改写的最小演示服务（仅用于演示响应头与条件请求语义，见下文声明），curl 8.5.0，2026-11-04 实际运行。**声明：curl 本身不做浏览器式缓存**，本节证明的是“服务器回了什么头、条件请求是否回 304”，而不是“浏览器下次会不会发请求”；浏览器内的缓存命中行为未在本机实测，见未完成项。

演示服务在 `127.0.0.1:18199` 上提供四个端点（脚本为一次性演示，未入仓）：

```bash
curl -si http://127.0.0.1:18199/fresh.css
curl -si http://127.0.0.1:18199/app.js
curl -si -H 'If-None-Match: "v1-7e5c6567"' http://127.0.0.1:18199/app.js
curl -si http://127.0.0.1:18199/api.json
curl -si http://127.0.0.1:18199/plain.txt
```

实际输出（节选，`Date` 为运行时刻）：

```
# /fresh.css：一年强缓存 + 不可变
HTTP/1.0 200 OK
Cache-Control: public, max-age=31536000, immutable
ETag: "v1-7e5c6567"
Content-Length: 22

body { color: #333; }

# /app.js 首次：可存、每次必问
HTTP/1.0 200 OK
Cache-Control: no-cache, must-revalidate
ETag: "v1-7e5c6567"
Content-Length: 22

# /app.js 带匹配的 If-None-Match：协商成功，无正文
HTTP/1.0 304 Not Modified
ETag: "v1-7e5c6567"
Cache-Control: no-cache, must-revalidate

# /app.js 带不匹配的 If-None-Match：对照组，仍回 200 全文（输出头略）
HTTP/1.0 200 OK
Cache-Control: no-cache, must-revalidate
ETag: "v1-7e5c6567"

# /api.json：不许存
HTTP/1.0 200 OK
Cache-Control: no-store

# /plain.txt：只有 Last-Modified，没有 Cache-Control/Expires
HTTP/1.0 200 OK
Last-Modified: Wed, 01 Oct 2025 00:00:00 GMT
```

怎么读：`fresh.css` 是第 7 节第一行的真实样子——浏览器在 `max-age` 内不会为它发请求；`app.js` 的两组对照证明协商缓存的判定只认验证器是否匹配，与 URL 无关；`api.json` 的 `no-store` 是敏感接口的写法；`plain.txt` 正是启发式缓存的触发条件——浏览器可能按 4.5 节估一个新鲜期，也可能不存，具体以实现为准，这正是“不写头不可预测”的实证。
