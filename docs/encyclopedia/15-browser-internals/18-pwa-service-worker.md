# PWA 与 Service Worker 入门

## 1. 一句话定义

PWA（Progressive Web App，渐进式 Web 应用）是达到可安装条件的普通网站：用 Web 应用清单（Web App Manifest）告诉浏览器“这是一个应用”，并（通常）用 Service Worker 提供离线与缓存能力；Service Worker 则是浏览器在独立线程里运行的、可以拦截并处理页面网络请求的脚本。

## 2. 为什么需要它

普通网站有两个短板：一是断网或弱网就打不开、打不开就等于不存在；二是只能活在浏览器标签页里，没有“装到桌面、从启动器打开”的应用形态。原生应用能解决这两点，但要走应用商店、按平台各写一套。PWA 的思路是渐进增强：先保证它在任何浏览器里都是一个能正常打开的网站，再在支持的浏览器里叠加安装、离线、后台能力——不支持的浏览器也不会因此打不开网站。

Service Worker 是这套能力里最关键的一块：它让网站第一次有机会在“页面与网络之间”放一段自己写的、可编程的代理逻辑，而不是只能被动依赖浏览器内置的 HTTP 缓存。

## 3. 核心含义

### 3.1 三个组成部分，各管一摊

- **网站本身**：仍是 HTML、CSS、JavaScript，仍按普通网站打开。这是底线：PWA 首先是一个网站，其次才是一个应用。
- **Web 应用清单（manifest）**：一个 JSON 文件，写明应用名、图标、启动地址（`start_url`）、显示方式（`display`，如 `standalone` 表示去掉浏览器地址栏、以独立窗口打开）等。页面用 `<link rel="manifest">` 引用它。浏览器靠它决定“这能不能装、装完叫什么、用什么图标、从哪里启动”。
- **Service Worker**：一个独立的 JavaScript 文件，由页面注册。注册后它运行在自己的线程里，**没有 DOM 访问权限**，不能直接读写页面元素；它通过事件（`install`、`activate`、`fetch` 等）工作，浏览器可以在事件处理完后随时终止它。因此不要把需要持久的状态放在它的全局变量里，持久状态应放 Cache Storage 或 IndexedDB。

### 3.2 Service Worker 生命周期：一次只活一个版本

生命周期是 Service Worker 最容易踩坑的地方，核心规则只有两条：**同一作用域在同一时间只有一个激活版本**；**新版本默认要等旧版本的所有受控页面都关闭后才接管**。

```
注册 → 下载 → 安装（install）→ 等待（waiting）→ 激活（activate）→ 已激活（activated，可处理 fetch）
                                              ↑                       ↓
                                         新版本默认停在这里        被更新版本取代后变为 redundant（废弃）
```

按顺序讲清每一步：

1. **注册（register）**：页面调用 `navigator.serviceWorker.register('/sw.js')`。脚本所在路径决定它的默认作用域：放在站根的 `sw.js` 默认管整个站，放在子目录里的脚本默认只管该子目录。页面首次访问时注册的 Worker **不控制当前页面**，当前页面要刷新后才受控，除非 Worker 在 `activate` 里调用 `clients.claim()` 主动接管已打开的页面。
2. **安装（install）**：每个版本只触发一次，是预缓存的时机：把应用外壳（App Shell，即骨架 HTML、CSS、主 JS）等关键资源写进 Cache Storage。`install` 处理函数里常用 `event.waitUntil(...)` 延长安装，等缓存写完再算安装完成；如果延长中的 Promise 失败，安装失败，该版本被废弃。
3. **等待（waiting）**：新版本安装完成、但旧版本还在控制页面时，新版本停在这里。这是有意的设计：避免同一会话里两个版本的页面与 Worker 混用、行为不一致。
4. **激活（activate）**：旧版本页面全部关闭（或新版本调用 `skipWaiting()` 主动跳过等待）后，新版本激活。**清理旧缓存的标准位置就在这里**：删掉不属于当前版本的旧缓存名，否则旧文件会一直占着存储。
5. **已激活**：开始接收 `fetch` 事件，拦截作用域内的请求并决定怎么响应。此后浏览器会按需启动、终止它；事件驱动，不是常驻进程。

更新机制也由此而来：浏览器会定期重新下载 Worker 脚本（字节有变化才算新版本），走一遍“安装 → 等待 → 激活”。所以“改了代码、刷新却没生效”通常不是缓存没清，而是新版本还在等待旧页面关闭——这是最常见的误判，见第 6 节。

### 3.3 安全上下文与注册前提

Service Worker 只能在**安全上下文**里注册：生产环境须用 HTTPS；开发时 `localhost` / `127.0.0.1` 被视为安全源，可用 HTTP 调试。局域网 IP（如 `http://192.168.1.x`）一般不算安全源，不能直接注册——这也是本机实测时要先确认的点，见第 7 节。

### 3.4 安装条件：清单是必需，Service Worker 不是“装”的必需

按 MDN 对 Chromium 系浏览器的安装条件归纳，可安装一般要求：通过 HTTPS（或本地开发例外）提供；清单含应用名（`name` 或 `short_name`）、192×192 与 512×512 图标、`start_url`、`display` 或 `display_override`，且 `prefer_related_applications` 为 `false` 或不存在。需要注意的演变是：**Service Worker 曾被列为安装条件，但后来不再是菜单安装的硬性条件**——没有 Service Worker 的网站仍可安装，只是没有离线能力；自动安装提示与各浏览器的具体条件仍各不相同，且会随版本变化。**因此不要把“装了 Service Worker”写成“可安装”的充分条件，也不要照抄某一家浏览器的条件当通用标准**；上线前以各浏览器当前文档为准（见文末未完成项）。

安装方式也因平台而异：桌面 Chromium 系浏览器多在地址栏提供安装入口；移动端多为浏览器菜单或系统分享菜单里的“添加到主屏幕 / 安装”；桌面 Firefox 不提供基于清单的 PWA 安装。各平台的安装提示、图标与卸载行为都不一样，属工程实现差异，不属本篇原理。

## 4. 分类：三种缓存策略（按请求类型各选一种）

一个应用通常不会只用一种策略，而是**按资源类型分别定策略**：带哈希文件名的 CSS/JS/字体用一种，HTML 导航用一种，图片用一种。三种主流策略（命名来自 web.dev《Offline Cookbook》的通行叫法）：

| 策略 | 做法 | 新鲜度 | 离线可用 | 典型用途 |
|---|---|---|---|---|
| Cache First（缓存优先） | 先查缓存，命中直接返回；未命中才走网络，拿到后顺手写进缓存 | 直到文件名或缓存名变化才更新，可能偏旧 | 是（已缓存后） | 带内容哈希的 CSS、JS、字体、图标 |
| Network First（网络优先） | 先走网络，成功返回最新；失败（断网）才返回缓存里的旧副本 | 在线时最新，离线时退回旧版 | 是（有旧副本时） | HTML 导航页、API 数据（可接受旧数据时） |
| Stale-While-Revalidate（过期再验证） | 立刻返回缓存副本，同时在后台走网络刷新缓存 | 返回的副本比最新落后一次访问 | 是（已缓存后） | 头像、商品图等“旧一点也能接受”的内容 |

另有两种边界策略，作补充而不作主力：Cache Only（只读缓存，从不联网，适合安装时已预缓存的离线页）；Network Only（只走网络，适合绝不能用旧数据的请求，如支付、提交表单）。

两个实现细节必须写对，否则示例跑起来就错：

- **请求与响应流只能读一次**：要“既返回给页面、又写进缓存”，须先 `clone()` 一份再存，否则读过的流第二次读会失败。
- **缓存键是请求**：Cache Storage 存的是“请求 → 响应”对，匹配时看 URL 与请求头，不是按文件名模糊匹配；查询参数不同就是不同条目，版本化缓存名（如 `app-v2`）是区分新旧版本最稳妥的办法。

Cache Storage 本身的存储模型、容量与清理规则不属本篇展开范围，见[Web 存储详解](09-web-storage-apis.md)；存储与 Cookie 的分工见[存储与 Cookie 模型](03-storage-cookie.md)。

## 5. 典型应用

- **离线可读的阅读类应用**：安装时预缓存外壳与文章，断网后仍能打开已读内容；导航请求失败时返回专门的离线页，而不是浏览器默认断网页。
- **弱网下的管理后台与工具站**：外壳走 Cache First 秒开，数据走 Network First，在线最新、离线显示上次数据并提示“当前为离线数据”。
- **可安装的轻量应用**：不走应用商店，以独立窗口形态提供给用户，适合内部工具、活动页、文档站等分发成本敏感的场景。
- **后台能力（需另行申请权限与单独实现）**：推送通知、后台同步等都以 Service Worker 为载体，但它们各自有权限模型与平台限制，不是有了 Service Worker 就自动获得——本篇只讲缓存与离线，推送与同步不在此展开。

## 6. 限制与常见误解

- **“离线”不等于“所有功能离线”**：只有预缓存或运行时缓存过的内容才能离线用；没缓存过的页面、没缓存过的 API 数据，断网后依然拿不到。离线能力是设计出来的，不是装了 Worker 就自动有的。
- **“刷新没生效 = 缓存没清”**：多数情况下是新版本 Worker 还在 waiting。验证时应先看浏览器开发者工具 Application 面板里的 Worker 状态，而不是反复清缓存。
- **Service Worker 不是万能代理**：它只能拦截同作用域、同源的请求（跨源请求受 CORS 等规则约束）；不能拦截浏览器自身行为，也不能绕过 HTTPS 与同源策略。
- **缓存不是永久存储**：浏览器可在存储压力下清理缓存；关键业务数据应放 IndexedDB（见[存储与 Cookie 模型](03-storage-cookie.md)），并把缓存当“可丢失、可重建”来设计。
- **首次访问不受控**：注册页本身第一次加载时还没有 Worker 接管，离线与缓存效果要从第二次访问（或 `clients.claim()` 接管后）才看得到；拿首次访问测离线会得出错误结论。

## 7. 小结

PWA 是“网站 + 清单 +（通常）Service Worker”的渐进增强：清单决定能不能装、装成什么样；Service Worker 在独立线程里按“安装 → 等待 → 激活”的生命周期接管请求，用 Cache First、Network First、Stale-While-Revalidate 三种策略分资源管理缓存；离线能力只覆盖被缓存过的东西，安装条件因浏览器而异、须以官方文档为准。

## 8. 读者验证步骤（本机部分实测，浏览器行为未实测）

> 以下示例代码的语法与本地服务已在本机跑过，但**浏览器内注册、接管与断网缓存行为未在本机实测**（本机无浏览器实测环境），读者须在自己浏览器里走完第 3–5 步再采信离线效果。

1. 在本地目录放 `index.html`（含 `navigator.serviceWorker.register('/sw.js')`）、`sw.js`（`install` 预缓存 `/`、`/index.html`、`/offline.html`；`activate` 清旧缓存；`fetch` 对导航请求失败时返回 `/offline.html`，其余请求走缓存优先）、`offline.html`。
2. 本机实测已通过的部分：`node --check sw.js` 语法通过；`python3 -m http.server` 在 `127.0.0.1:8765` 上提供服务，`curl` 验证 `/index.html` 与 `/sw.js` 均返回 200（`sw.js` 的 Content-Type 为 `text/javascript`）。这只证明“文件能被 HTTP 服务正常送出”，**不证明**浏览器能注册成功。
3. 在自己浏览器里打开 `http://localhost:8765/`，看开发者工具 Application → Service Workers 一栏：状态应为 activated and is running；Cache Storage 里应出现预缓存的缓存名与条目。
4. 刷新一次页面（让 Worker 接管），再在开发者工具里切断网络（或直接停掉本地服务），刷新：应看到缓存的页面或离线页，而不是浏览器断网错误页。
5. 改动 `sw.js` 后刷新：观察新版本是否停在 waiting；关闭所有受控标签页再重开，或调用 `skipWaiting()`，确认新版本接管。
