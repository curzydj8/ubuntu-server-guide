# 浏览器网络栈与连接管理

> 本篇是总览 [网络栈与缓存](02-network-cache.md) 的深挖篇。总览讲了“从地址栏到响应要过哪几道关”，本篇讲每一关在浏览器里是谁在管、连接是怎么被复用与排队的、以及浏览器为省时间提前做了什么。**分工声明**：DNS、TCP、TLS、QUIC 各协议的原理本身属 07 域（与 13 密码学域），本篇只讲浏览器视角的流程与取舍，原理细节一律链接过去，不重复展开。

## 1. 本章目标

读完本篇，能说清浏览器发一个请求之前要经过哪几层准备、连接池在什么情况下会复用、什么情况下会排队，以及“页面资源多就慢”到底慢在哪一层。

## 2. 背景与问题

浏览器每发一个请求，表面上只是一次“取数据”，底下却是四件成本不同的事：域名解析（可能要问出去）、连接建立（至少一个往返）、加密协商（至少一个往返）、数据传输（受拥塞与丢包影响）。更关键的是：这些成本不是每个请求都付一遍——连接可以复用、解析结果可以缓存、协商结果可以恢复。浏览器网络栈的全部工作，就是**把“每个请求都付全价”变成“多数请求只付传输价”**，同时在隐私与公平之间划线：连接不能无限制地开，缓存不能跨站共享（见 06 篇第 7 节的分区）。

## 3. 总体架构

以 Chromium 为例，浏览器侧的网络工作集中在网络服务（Network Service）里，渲染进程不直接碰套接字，只提需求、收数据：

```
渲染进程：“我要 https://example.com/app.js”
   │
   ▼
网络服务
   │ ① 主机解析：浏览器 DNS 缓存 → 系统解析 → 递归解析（见 4.1）
   │ ② 连接池：按“源 + 网络分区键”找空闲连接，找不到就新建（见 4.4）
   │ ③ 加密层：TCP 之上做 TLS 协商；QUIC 则把传输与加密合成一次握手（见 4.3）
   │ ④ 协议层：按协商结果走 HTTP/1.1、HTTP/2 或 HTTP/3（见 4.5）
   │ ⑤ 缓存层：响应回来先过 06 篇的缓存判定，再交给渲染进程
   ▼
渲染进程：收数据、解析、渲染（见 01 篇）
```

“源”（origin）是连接池的第一把钥匙：协议 + 域名 + 端口三者任一不同，就是不同的源，原则上不共用连接（符合条件的 HTTP/2 连接合并为例外，见 4.4 节）。“网络分区键”是第二把钥匙：同一资源在不同顶级站点下看到的连接池与缓存也是隔离的，这是分区隐私设计在连接层的延伸，具体隔离范围以各浏览器当前实现为准。

## 4. 工作机制

### 4.1 DNS：浏览器视角只关心三件事

DNS 的解析流程、记录类型与服务器搭建属 07 域（[DNS 服务器搭建](../../04-network/01-dns.md) 与 07 域网络文章），浏览器视角只关心：

1. **查哪几级**：浏览器自身 DNS 缓存 → 操作系统缓存 → 配置的递归解析器。每一级都有生存时间（TTL），过期重查；“刚换了服务器 IP 但浏览器还打不开旧地址”时，排障要先分清卡在哪一级缓存，而不是直接怀疑源站。
2. **解析结果影响连接**：一个域名可能对应多个 IP，浏览器选哪一个、失败后是否换下一个，属于解析与连接策略的交界，具体行为以实现为准，本文不写成固定规则。
3. **加密 DNS 的位置**：DNS over HTTPS（DoH）是把解析查询本身放进 HTTPS 通道，解决的是“查询内容被旁路看到”的问题，不改变“域名 → IP”这个映射关系。各浏览器是否默认开启、默认用哪家解析器，策略不同且会变动，**以官方发布为准（待核实）**，见未完成项。

DNS 慢的代价是前置的：连接还没建，时间已经花出去了；而且 DNS 结果会被后续所有同源请求复用，所以一次解析失败拖住的往往不是一个请求，而是一整批。

### 4.2 TCP：连接是“建好就留着”的资产

TCP 的握手、重传、拥塞控制原理属 07 域，本篇只讲浏览器怎么用它：

- **三次握手至少一个往返**：客户端发 SYN、服务器回 SYN-ACK、客户端回 ACK，三个包走完才能发数据。往返时延（RTT）越大，这一步越贵；跨洋链路上握手本身就可能占首字节时间的大头。
- **持久连接是默认项**：HTTP/1.1 起连接默认不随响应关闭（除非显式声明关闭），用完放回连接池，下一个同源请求直接复用，握手只付一次。这就是总览里“复用值钱”的来源。
- **空闲连接会过期**：连接池里的空闲连接不会无限保留，服务器与浏览器各自有空闲超时，超时后关闭；下一次请求到来时重新握手。超时时长以实现与服务器配置为准，本文不写具体秒数——排障时“偶尔第一个请求慢”往往就是空闲连接刚好过期。
- **连接失败不等于“网站挂了”**：握手超时、连接被中间设备重置、TLS 协商失败，在浏览器里都表现为打不开，但根因分属不同层；开发者工具 Network 面板里“排队（Queued）”与“连接（Connecting）”是区分“在等连接池”还是“在建连接”的第一线索（面板字段名以浏览器当前版本为准）。

### 4.3 TLS：浏览器视角的协商与恢复

TLS 的握手细节、证书链验证与密码套件属 13 密码学域（见相关主题的 13 域文章；证书体系本身不在本篇展开），浏览器视角只讲四点：

- **版本决定往返数**：TLS 1.2 协商需要两个往返，TLS 1.3 压缩到一个往返；这是版本升级在浏览器侧最直接的收益。协商版本由双方在握手时商定，浏览器会按自身支持的最高版本尝试，服务器不支持时回落——回落底线（是否允许 TLS 1.0/1.1）以各浏览器当前策略为准。
- **ALPN 决定 HTTP 版本**：握手时双方通过应用层协议协商（ALPN）商量好用 HTTP/1.1、HTTP/2 还是 HTTP/3，协商结果决定后续走哪条协议路径（见 4.5 节）。HTTP/3 的发现走另一条路：服务器通过 `Alt-Svc` 响应头或 HTTPS DNS 记录宣告支持，浏览器下次才尝试，见 4.5 节。
- **会话恢复省往返**：曾经协商过的会话，凭票据（session ticket / PSK）可以缩短甚至省去完整协商；TLS 1.3 的 0-RTT 恢复能让请求随第一个包发出，但 0-RTT 数据存在重放风险——服务器只能用它承载可重放也无害的请求，浏览器侧不决定这条策略，只负责按协商结果发送。
- **证书失败时浏览器拦截**：证书过期、域名不匹配、链不完整时，浏览器会先拦截并警告，而不是“先连上再说”；用户点“继续前往”绕过警告，等于放弃了这一层身份验证，风险自担。

### 4.4 连接复用与并行限制：池子有多大、什么时候排队

这是本篇的核心，也是“资源多就慢”最常见的根因。

**HTTP/1.1：每源约 6 条连接**

HTTP/1.1 的一条连接一次只能传一个响应（队头阻塞在应用层），浏览器用“多开连接”缓解。主流浏览器对同一源的 HTTP/1.1 并发连接数常见实现约为 **6 条**（多来源一致的常见值，具体数字以各浏览器当前实现为准，见未完成项）；超过 6 个的同源请求只能在连接池外排队，等前面请求的连接空出来。注意两点：一是这个限制**按浏览器、按源统计，跨标签页共享**——六个标签页各占一条长连接时，第七个请求照样排队；二是“源”按域名算，`static.example.com` 与 `api.example.com` 是不同的源，各自有自己的池子——这就是“域名分片”曾经有效的原因，也是它后来被 HTTP/2 取代的原因。

**HTTP/2：一条连接、多路复用**

HTTP/2 在同一连接内把请求与响应拆成帧交错传输（多路复用），一条连接就能并行多个请求，HTTP/1.1 的“6 条”限制不再是瓶颈；新的上限是**并发流数**，由服务器通过 `SETTINGS_MAX_CONCURRENT_STREAMS` 宣告，常见值为 100 左右（以服务器宣告为准）。代价是队头阻塞从 HTTP 层移到了 TCP 层：TCP 丢一个包，整条连接上的所有流都得等重传补齐（见总览 4.4 节）。

**连接合并（coalescing）的例外**：符合条件时（同一 IP、证书覆盖多个域名等），浏览器可把发往不同源的 HTTP/2 请求合并到同一连接上。这是“原则上按源隔离”的例外而非默认，具体判定条件以实现为准，排障时不要假设它一定发生。

**连接池的排队信号**：页面同时请求几十个同源资源时，开发者工具里会出现“排队等待空闲连接”的请求——这不是服务器慢，而是浏览器侧的池子满了。解法在架构层（升级 HTTP/2、减少同源关键资源数、域名分片只在 HTTP/1.1 下有意义），不在“多刷新几次”。

### 4.5 QUIC 与 HTTP/3 入门：只讲浏览器能感知到的三处变化

QUIC 与 HTTP/3 的完整原理属 07 域（[QUIC 与 HTTP/3 原理](../07-network-comms/02-quic-http3.md)），浏览器视角只讲三处可感知变化：

1. **握手合一**：QUIC 把传输握手与 TLS 1.3 协商合成一次，首个请求在一个往返后就能发出；恢复连接时可 0-RTT 发出（重放风险见 4.3 节）。TCP+TLS 1.3 需要两个往返，省下的就是这一个往返。
2. **流级隔离**：QUIC 的流各自独立排序与重传，单流丢包不拖住其他流——HTTP/2 在 TCP 上的队头阻塞在这里被解开。代价是底层换成 UDP：某些网络会限流或拦截 UDP，浏览器必须能回退到 HTTP/2（见第 3 点）。
3. **连接迁移**：QUIC 连接用连接 ID 而非“源 IP + 端口”标识，设备从 Wi-Fi 切到移动网络、IP 变了，同一逻辑连接可以继续，不必重新握手；TCP 连接在这种切换下必然断开重连。迁移仍需路径验证，具体机制属 07 域。

**发现与回退**：浏览器第一次访问某源时并不知道它支持 HTTP/3，仍走 TCP+TLS；只有服务器通过 `Alt-Svc: h3=":443"` 或 HTTPS DNS 记录宣告后，浏览器后续访问才会尝试 QUIC；UDP 被拦截或握手失败时回退 TCP——回退是正常路径，不是故障。HTTP/3 的全网部署比例、浏览器默认开启情况会变动，**以官方发布为准（待核实）**，见未完成项。

### 4.6 预连接：把准备工作提前到用户点击之前

浏览器可以在用户真正需要之前，提前做 4.1–4.3 节里的准备工作，代价是“用户根本不点的链接也会消耗资源”：

- **DNS 预解析**：提前把链接域名的解析结果备好，省一次解析往返；页面可用提示声明，浏览器也可自行推断。
- **预连接**：在 DNS 预解析之上再提前建好 TCP 连接、甚至完成 TLS 协商，用户点击时直接发请求。收益最大，浪费也最大——预连接建好后长期不用，空闲超时一到又被关闭，等于白建。
- **预取与预渲染**：比预连接更进一步（提前取数据、提前渲染），收益与浪费、隐私代价都更大，且涉及渲染与存储，不属本篇连接管理的范围，本文只点名。

取舍原则只有一条：**对用户大概率要点的下一步（如搜索结果首位、登录后必访页）值得预连接；对页面上所有链接无差别预连接，是在用用户的带宽与服务器连接数换不确定的收益**。

## 5. 关键设计取舍

- **复用换队头阻塞**：HTTP/2 一条连接复用到底，省了握手与连接数，但 TCP 丢包拖住全连接；HTTP/3 用 QUIC 解开这一层，代价是 UDP 可达性与实现成本。
- **并行换公平**：HTTP/1.1 的每源连接上限既是性能约束，也是公平约束——没有上限，单个页面可以瞬间占满服务器连接；上限的存在让“排队”成为可预期的反压信号，而不是无限制的资源争夺。
- **预连接换浪费**：提前准备省的是用户点击后的等待，付的是提前消耗的连接与带宽；预判越准，性价比越高。
- **分区换复用**：连接池与缓存按顶级站点隔离后，跨站共享连接与缓存的收益下降（见 06 篇），换来的是跨站探测能力的削弱；隐私优先时，这笔交易是值得的。

## 6. 分类与变体

- 按传输层：TCP + TLS（HTTP/1.1、HTTP/2）与 QUIC（HTTP/3，内置 TLS 1.3）。
- 按连接状态：新建连接、复用连接、恢复会话（TLS 会话恢复 / QUIC 0-RTT）、预连接。
- 按并行模型：HTTP/1.1 多连接并行、HTTP/2 单连接多路复用、HTTP/3 单连接逐流独立。
- 按连接归属：按源划分的连接池，再叠加按顶级站点的网络分区（范围以实现为准）。

## 7. 应用与限制

- **排障分层法**：打不开时先分清卡在哪一层——DNS（域名解析失败）、TCP（连接超时/被重置）、TLS（证书警告/协商失败）、HTTP（状态码与响应头）、缓存（06 篇的两道门）。层与层之间的报错长得很像，分层是唯一不跑偏的办法。
- **性能优化的层归属**：首字节慢先查 DNS 与握手往返（本篇），正文慢先查传输与缓存（06 篇），渲染慢属 01 篇；把渲染优化手段用在连接问题上不会见效，反之亦然。
- **本篇不讲的**：TCP 拥塞控制算法细节、QUIC 的丢包恢复与流量控制、TLS 密码套件选型、DNS 服务器搭建与记录管理——分别属 07 域与 13 域，见相关主题。
- **示例未实测声明**：浏览器内的连接池状态、并发流数、QUIC 回退行为均需在浏览器开发者工具（Network 面板、内部网络状态页）中观察，**本篇写作时未在本机浏览器内实测**（代理 VM 无浏览器实测环境），读者验证方法见未完成项；本文不虚构任何浏览器内部截图与计数。

## 8. 常见误解

- **“HTTP/2/3 让连接数限制消失了”**：不准确。消失的是 HTTP/1.1 的“每源约 6 条连接”瓶颈，取而代之的是服务器宣告的并发流数上限与单连接的拥塞控制；限制换了个形式，没有消失。
- **“连接复用就是省流量”**：不准确。复用省的是握手往返与连接建立成本，正文该传多少字节还是多少字节；省字节是缓存与压缩的事（见 06 篇）。
- **“QUIC 不走 TCP 所以不受防火墙影响”**：错。QUIC 走 UDP，恰恰是更容易被拦截的那一个；回退到 TCP 是它的正常设计，不是故障。
- **“预连接越多越快”**：错。预连接建好不用等于白付握手成本，还会占用连接池名额；只对高概率的下一步做预连接。
