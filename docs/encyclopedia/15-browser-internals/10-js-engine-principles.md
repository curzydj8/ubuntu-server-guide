# JavaScript 引擎原理

## 1. 本章目标

读完本篇，能说清一段 JavaScript 从源码到机器码在 V8 里走过哪几层、每一层为什么存在，以及“隐藏类”和“内联缓存”这两个概念为什么能让动态类型语言跑得快。

## 2. 背景与问题

JavaScript 是动态类型语言：变量没有固定类型，对象可以随时增删属性，同一个函数这一次传数字、下一次可能传字符串。引擎在写代码时无法像静态语言那样提前知道类型，只能在运行时一边执行、一边学习程序的实际行为，再据此生成更快的代码。

这带来一对矛盾：

- **启动要快**：页面打开、脚本第一次执行不能等很久的编译；
- **执行要快**：反复运行的热点代码值得花成本做深度优化。

单一策略顾此失彼：只解释执行，热点代码永远慢；一上来就深度优化，启动慢、内存占用大。现代引擎的答案是**分层执行**：先用便宜的方式跑起来，边跑边收集反馈，越热的代码越往高层编译。

本篇以 V8 为例（Chrome、Edge、Node.js、Deno 所用的引擎）。JavaScript 语言本身的写法属 website-guide 的 JavaScript 系列，本篇只讲引擎内部视角，不重复语言教程。渲染流程中脚本在何处执行，见 [01 篇](01-rendering-pipeline.md)。

## 3. 总体架构

V8 的执行管线（大意，层与层之间可以跳级，具体策略随版本调整）：

```
JavaScript 源码
      │ 解析（Parser）
      ▼
抽象语法树（AST）──▶ 字节码（Ignition 生成）
      │                    │
      │              Ignition 解释执行（收集类型与形状反馈）
      │                    │ 反馈稳定、代码变热
      │                    ▼
      │              Sparkplug：基线编译（不做深度优化）
      │                    │
      │                    ▼
      │              Maglev：中层优化编译（SSA 中间表示）
      │                    │
      │                    ▼
      │              TurboFan：顶层优化编译（推测性优化）
      │                    │
      └────── 反优化（Deoptimization）：假设被推翻时回到 Ignition ──┘
```

- **解析器**：把源码变成抽象语法树，再由 Ignition 的字节码生成器变成字节码。
- **Ignition**：基于寄存器的字节码解释器，启动快、字节码紧凑，同时收集运行反馈。
- **Sparkplug**：基线编译器，把字节码快速翻译成机器码，不做深度优化，消除解释器的取指与分派开销。
- **Maglev**：中层优化编译器（Chrome 117 引入），用静态单赋值（SSA）中间表示做“够好又够快”的优化。
- **TurboFan**：顶层优化编译器，面向最热的代码做推测性优化；假设被推翻时触发反优化，回到解释执行。

各层不是“低层被高层取代”，而是共存：冷代码停在解释或基线层，热代码才付得起高层编译的成本。

## 4. 工作机制

### 4.1 解析：从源码到字节码

解析分两步：先做词法与语法分析，生成抽象语法树（AST）；再由 Ignition 把 AST 编译成字节码。字节码是比机器码更紧凑的中间形式：一份源码只生成一次字节码，各编译层都以它为出发点，而不是每次都重新解析源码。

解析失败（语法错误）在这里就暴露出来：引擎在执行前就知道这段代码写得不合法。解析本身不执行代码，所以“解析通过”不等于“运行正确”——类型错误、空引用这类问题要到执行时才出现。

### 4.2 Ignition：解释执行并收集反馈

Ignition 是基于寄存器的字节码解释器：它逐条读取字节码，调用对应的处理例程（handler）执行。解释执行的好处是**启动代价最小**——字节码生成快、体积小，适合只执行一次或几次的代码。

解释执行还有一个关键副产品：**反馈**。执行过程中，Ignition 记录每个操作点的实际行为，例如：

- 某个属性访问见到的对象是什么形状（见 4.5 节隐藏类）；
- 某个二元运算见到的操作数是整数还是浮点数；
- 某个函数被调用了多少次、分支往哪边走。

这些反馈存在反馈向量（feedback vector）里，是高层编译器做推测的依据。没有反馈的优化等于盲猜，所以高层编译不能跳过“先跑一阵子”这一步。

### 4.3 Sparkplug：基线编译，去掉解释开销

Sparkplug 是不做优化的基线编译器：它沿字节码做一次线性扫描，直接生成对应的机器码，复杂语义大多委托给与解释器共用的内建例程（builtin）。它不建中间表示（IR），因此编译极快，可以铺得很广。

它的收益来自去掉解释器固有的开销：每条字节码的取指、解码和分派。按 V8 官方博客的说法，Sparkplug 本质上是把“解释器执行”序列化成了机器码，让代码从“跑在模拟器里”变成“直接跑在 CPU 上”。基线代码不做类型特化，所以它不会因为类型变化而反优化——稳定，但上限不高。

### 4.4 Maglev 与 TurboFan：两档优化编译

**Maglev**（Chrome 117 引入，见来源）是介于 Sparkplug 与 TurboFan 之间的优化编译器。它用 SSA 中间表示加控制流图，在图构建时就结合反馈做特化：例如反馈说 `o.x` 处的对象总是同一种形状，它就生成“先检查形状、再按偏移直接取字段”的代码。它的设计目标是“够好又够快”：优化幅度明显大于基线编译，编译成本又远低于顶层优化。

**TurboFan** 是顶层优化编译器，面向真正最热的代码。它做的事包括：基于反馈的**推测性优化**（假设今后见到的类型与过去一致，生成高度特化的机器码）、函数内联、以及对数字的拆箱（把整数、浮点数从堆对象表示还原成机器寄存器里的原始数值，避免反复装箱）。

推测就有可能错，所以 TurboFan 代码必须能**反优化**：一旦运行时检查发现假设被推翻（例如一个一直传整数的函数突然传了字符串），引擎丢弃优化代码，把执行状态映射回解释器状态，从字节码断点处继续执行，之后再根据新的反馈重新学习。这不是错误，而是设计的一部分：宁可偶尔回退，也不为“永远正确”放弃对常见情况的优化。

> 版本说明：V8 官方博客 2025 年 3 月《Land ahoy: leaving the Sea of Nodes》指出，TurboFan 后端已从 Sea of Nodes 中间表示迁移到 Turboshaft（一种更传统的控制流图中间表示），顶层编译器在 Node.js 的 `--trace-opt` 输出里仍标注为 TURBOFAN_JS（见第 9 节实测）。本文按“TurboFan = 顶层优化编译器”这一层级概念来讲，不展开 Turboshaft 内部的遍（pass）细节；该迁移在当前版本中的确切范围列入未完成项。

### 4.5 隐藏类：给动态对象一个“形状”

JavaScript 对象从语言层面看像字典：任意键、任意值、随时增删。如果每次属性访问都要做字典查找，代价很高。V8 的办法是给每个对象关联一个**隐藏类（Hidden Class，内部称 Map）**：它描述对象的形状——有哪些属性、每个属性的值存在哪个偏移位置。对象本身只存值，形状信息由隐藏类共享。

关键规则（V8 官方博客《Fast properties in V8》）：

- **相同结构共享隐藏类**：属性相同、添加顺序相同的对象共享同一个隐藏类。`{x: 1, y: 2}` 和 `{y: 2, x: 1}` 形状不同，隐藏类也不同。
- **添加属性会切换隐藏类**：从空对象开始，每加一个命名属性就沿一条转移链走到新的隐藏类；按相同顺序加相同属性，一定走到同一个隐藏类。
- **整数索引属性不走隐藏类**：数组下标类属性存在独立的元素存储里，不创建新的隐藏类。
- **快慢两种属性存储**：常规属性按偏移快速访问；属性被频繁增删到维护描述符的代价过大时，对象可能退到字典式（慢属性）存储，访问变慢但增删便宜。

对写代码的启示是机制性的，不是风格口号：构造函数或字面量里**按固定顺序初始化全部属性**，能让一批对象共享形状；事后零散地给不同对象补不同属性，会制造出许多互不相同的形状。

### 4.6 内联缓存：把“上次怎么查到的”记在访问点上

隐藏类让“按偏移访问”成为可能，**内联缓存（Inline Cache，IC）**则让引擎不必每次都重新推导偏移。每个属性访问点都带一个小缓存：第一次访问时做完整查找，并记下“这个形状的对象，这个属性在偏移 N”；下次执行到同一访问点时，先比对对象隐藏类，命中就直接按偏移取值，跳过查找。

按见过的形状数量，访问点有几种状态（概念划分，具体阈值与实现细节随版本变化，以官方发布为准）：

- **单态（monomorphic）**：只见过一种形状——一次比对、直接访问，最快；
- **多态（polymorphic）**：见过少量几种形状——逐个比对，仍比完整查找快；
- **超多态（megamorphic）**：形状太多，本地缓存放弃，退回通用慢速查找。

内联缓存的反馈也会喂给优化编译器：Maglev、TurboFan 在编译时读到的“这个访问点总是同一种形状”，正是来自这里的记录。反过来，形状不稳定的热点访问点会让优化编译器无从特化，或者反复反优化。

### 4.7 数字表示：小整数与拆箱

按语言规范，JavaScript 数字是 64 位浮点数，但引擎不必总是这样存。V8 会把小整数编码为带标签的小整数（Smi），省内存且整数运算更快；优化编译器在确认类型后还会把数值**拆箱**，直接用机器寄存器里的原始整数或浮点数运算，只在必要时才重新装箱成堆对象。数组也有对应的区分：纯整数数组、纯浮点数组与通用数组的内部存储不同，混入不同类型会改变数组的内部表示（具体种类划分以官方发布为准）。

## 5. 关键设计取舍

- **启动换峰值**：分层越多，冷启动越快，但每上一层都要付编译成本；只有热到“省下的执行时间超过编译时间”的代码才值得上顶层。
- **推测换回退**：推测性优化赌的是“未来像过去”；赌赢了快很多，赌输了付一次反优化的代价。反馈越稳定，赌赢的概率越高。
- **紧凑换速度**：字节码体积小、生成快，适合内存受限与冷代码；机器码体积大、生成慢，只给值得的代码。
- **形状稳定换访问速度**：隐藏类与内联缓存把动态语言的查找变成了固定偏移访问，代价是程序员（或框架生成的代码）需要保持对象形状稳定，否则优化基础就不存在。

## 6. 分类与变体

- **按引擎**：V8（Chrome、Edge、Node.js、Deno）用本文的 Ignition→Sparkplug→Maglev→TurboFan 管线；SpiderMonkey（Firefox）与 JavaScriptCore（Safari）也有各自的分层即时编译设计，但层名、反馈机制与优化策略不同，本篇不展开——跨引擎比较时以各引擎官方文档为准。
- **按执行模式**：即时编译（JIT，本文讲的）与纯解释执行。V8 在某些受限环境（如需要降低可写可执行内存风险的场景）可以关闭 JIT，只保留解释器；那是安全与性能的取舍，不是“引擎坏了”。
- **按代码温度**：冷代码（解释/基线）、温代码（Maglev）、热代码（TurboFan）。温度由调用次数、循环次数与反馈稳定性共同决定，没有一个放之四海而皆准的固定阈值可抄。

## 7. 应用与限制

- 应用（机制层面的推论，不展开写法）：
  - 热点函数保持输入类型与对象形状稳定，是让优化编译器敢于特化的前提；
  - 性能问题先定位热点再动手：冷代码的优化空间不在编译层，而在算法与调用次数上；
  - 反优化本身不是故障信号，但“同一函数反复反优化”说明反馈不稳定，值得检查调用点是否混入了不同类型。
- 限制：本篇不讲事件循环与任务调度（属 15 域后续主题）；不讲具体字节码指令集（随版本变化，调试时以所用版本的 `--print-bytecode` 输出为准）；不给任何“某写法一定快 X 倍”的承诺——不同版本、不同设备、不同 workload 下结果都不同。
- 常见误解：
  - “JavaScript 是解释型语言，所以没有编译”：错。现代引擎对同一份代码会编译多次，只是编译发生在运行时。
  - “JIT 让所有代码都变快”：错。冷代码可能一生都停在解释或基线层；JIT 的收益集中在热点上。
  - “隐藏类就是 JavaScript 的 class”：错。`class` 是语言层面的语法；隐藏类是引擎内部为任意对象（包括字面量）建立的形状描述，两者不在同一层。
  - “反优化是引擎 bug”：错。反优化是推测性优化的安全网；没有它，引擎就不敢做任何基于反馈的假设。

## 8. 读者验证步骤

> 以下步骤除第 9 节外均为读者在自己机器上的验证方法，不是本文已跑过的测试。

1. 在 Node.js 里对一个小函数加 `--print-bytecode`，观察函数对应的字节码长度与寄存器数。
2. 对热点循环加 `--trace-opt`，观察函数被标记为优化到哪一层。
3. 让热点函数先只接受整数、再突然传入字符串，配合 `--trace-deopt` 观察反优化记录。

## 9. 实测记录（代理 VM 上真实运行）

> 环境：代理 VM，Node.js v24.22.1，V8 13.6.233.17-node.58，linux-x64。以下输出均真实跑过；地址、耗时每次运行都会变化，数值仅作本机示例，不作性能承诺。

1. 字节码生成：

   ```bash
   node --print-bytecode -e 'function add(a,b){return a+b;} console.log(add(1,2));'
   ```

   实测通过：输出 `[generated bytecode for function: ...]`，顶层脚本与 `add` 各有一段字节码，含寄存器数与帧大小等信息。

2. 分层优化：

   ```bash
   node --trace-opt -e 'function add(a,b){return a+b;} for(let i=0;i<200000;i++) add(1,2); console.log(add(3,4));'
   ```

   实测通过：输出先出现 `for optimization to MAGLEV` 与 `completed compiling ... (target MAGLEV)`，随后出现 `(target TURBOFAN_JS) OSR`；最终输出 `7`。这与第 3 节的管线一致：热点函数先上 Maglev，再上顶层优化。

3. 反优化：

   ```bash
   node --trace-deopt -e 'function add(a,b){return a+b;} for(let i=0;i<100000;i++) add(1,2); console.log(add(1,"x"));'
   ```

   实测通过：输出含 `[bailout (kind: deopt-eager, reason: not a Smi) ... deoptimizing ... <JSFunction add> ...]`——整数特化的代码在遇到字符串时反优化，与 4.4 节的机制一致。
