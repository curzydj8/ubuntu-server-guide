# 同源策略详解

## 1. 本章目标

读完本篇，能说清“源”由哪三部分决定、同源策略到底拦什么、不拦什么，以及为什么“请求发出去了”不等于“同源策略失效了”。

## 2. 背景与问题

浏览器里同时跑着许多互不信任的页面：用户在 A 标签页登着邮箱，在 B 标签页打开了一个陌生网站。如果 B 页的脚本能直接读 A 页的 DOM、读 A 站接口返回的登录后数据，登录态就形同虚设。同源策略就是浏览器的第一道默认隔离线：**默认不许一个源的脚本去读另一个源的数据**，除非对方明确放行（放行的机制见下一篇跨域通信方案）。

它要解决的不是“不许联网”，而是“不许偷看”：网络请求本身可以发出，读回来的内容能不能交给脚本，是另一回事。分清“发”与“读”，是理解整篇的关键。

## 3. 总体架构

```
源（origin）= 协议（scheme）+ 主机（host）+ 端口（port）
                三项全相同 → 同源；任一项不同 → 跨源

同源策略的默认姿态：拒绝跨源读取
├── 读 ── 跨源 DOM、接口响应体、存储内容：脚本默认读不到
├── 写 ── 脚本对跨源 DOM / 存储的写入：同样被隔离（不是想写就能写）
└── 执行 ─ 跨源脚本被引入后，在“引入页的源”里执行，而非在它自己源里执行
```

还要区分两个易混概念：

- **源（origin）**：协议 + 主机 + 端口，三项全相同才算同源。`https://app.example.com` 与 `https://api.example.com` 是不同源，哪怕它们同属一个域名。
- **站点（site）**：协议 + 可注册域名（例如 `https://example.com`）。同站不同源的页面仍受同源策略隔离；“同站”只在 Cookie 的 `SameSite`、存储分区等机制里才有单独意义，细节见存储篇与本批 Cookie 跨站篇。

## 4. 工作机制

### 4.1 源的定义与判定

两个 URL 同源，当且仅当协议、主机、端口三项都相同。默认端口不写出来也算数：`http` 默认 80，`https` 默认 443，显式写默认端口与不写视为相同；写了非默认端口就是不同源。路径、查询串、片段（`#` 后）不参与判定：只改路径的两个 URL 永远同源。

| 与 `http://store.company.com/dir/page.html` 比较 | 是否同源 | 原因 |
|---|---|---|
| `http://store.company.com/dir2/other.html` | 是 | 只改了路径 |
| `https://store.company.com/page.html` | 否 | 协议不同 |
| `http://store.company.com:81/dir/page.html` | 否 | 端口不同（`http` 默认 80） |
| `http://news.company.com/dir/page.html` | 否 | 主机不同（子域也算不同主机） |

特殊情形只讲机制方向，不展开实现细节：

- `about:blank`、`javascript:` 这类 URL 本身不含源信息，其文档继承包含它的文档的源。
- 被沙箱化的 iframe、`file:` 协议加载的文件等，现代浏览器通常给予**不透明源（opaque origin）**：它与任何源都不相同，包括它自己的 URL 字面源。各浏览器对 `file:` 的处理有差异，以官方发布为准（待核实），见文末未完成项。
- `data:` 等 URL 的源处理同样属不透明源一类，具体行为以规范与各实现为准，不宜凭记忆写死。

### 4.2 读隔离：被拦住的是什么

同源策略拦的是**脚本读取跨源数据**，典型包括：

- **跨源 DOM**：父页面读不到跨源 iframe 里的文档内容，跨源 iframe 也读不到父页面的 DOM。互相“看得见框、看不见里面”是正常表现。
- **跨源网络响应**：脚本用 `fetch` / `XMLHttpRequest` 请求跨源接口，响应能不能交给脚本，取决于对方是否按 CORS 明确放行（见下一篇）。没放行时，浏览器会阻止脚本读取响应——注意是浏览器在读取环节拦截，不是服务器拒绝了请求。
- **跨源存储与 Cookie**：一个源的脚本读不到另一个源的 `localStorage`、IndexedDB，也读不到另一个源的 Cookie（Cookie 的发送规则另有一套作用域逻辑，见存储篇；“发不发”与“脚本读不读得到”是两回事）。

一句话：同源策略保护的是“数据进了浏览器之后，能不能被别源的脚本拿走”。

### 4.3 写与执行：隔离的另一面

- **写**：脚本不能直接改跨源页面的 DOM，也不能直接写另一个源的存储。想让两个源协作，要走双方都认可的通信机制（下一篇的 `postMessage`、CORS），而不是直接跨过去写。
- **执行**：跨源脚本一旦被页面引入，就在**引入页的源**里执行，能访问引入页的 DOM 与存储。这正是“引入谁的脚本，就等于信任谁”的原因：脚本的“出身源”不决定它的执行权限，决定权限的是“它被哪个页面的源加载”。
- **发送不等于写成功**：脚本或表单可以把跨源请求发出去，请求到达服务器后可能产生副作用（如下单、改状态）。同源策略不拦“发”，所以服务器不能把“浏览器拦了读取”当成“请求不会到来”：鉴权、防伪造仍是服务器自己的责任，机制细节不属本篇。

### 4.4 例外：不拦的跨源行为

以下跨源行为默认是允许的，它们是同源策略有意留下的口子，也是“为什么网页能正常用第三方资源”的原因：

- **表单提交**：`<form>` 可以向任何源提交，提交后浏览器会导航到响应页面；但提交页的脚本读不到跨源响应的内容。
- **脚本引入**：`<script src="跨源地址">` 可以加载并执行，脚本在引入页的源里执行（见 4.3）。能执行不等于能读：引入页的脚本仍然读不到该脚本源站的其他数据。
- **资源嵌入**：`<img>`、`<link rel="stylesheet">`、`<video>`、`<audio>` 等可以嵌入跨源资源并展示/播放；但脚本读不到跨源图片的像素、跨源样式表的规则细节等原始数据（读像素、读规则属“读”，仍受限）。
- **顶级导航与链接**：点击链接跳到跨源页面、地址栏输入跨源地址，都是正常导航，不受同源策略限制——同源策略管的是“页内脚本跨源读数据”，不是“用户能不能去别的站”。
- **iframe 嵌入显示**：跨源页面可以被嵌进 iframe 里显示出来；显示不等于可读，父页脚本仍读不到框内文档。

例外清单的要点是统一的：**能发、能嵌、能显示，不代表能读**。凡是“把跨源数据交到脚本手里”的动作，默认都要对方明确放行。

### 4.5 历史演变

- **成型**：源的概念在 RFC 6454《The Web Origin Concept》（2011 年）中形式化：源即协议、主机、端口三元组。此后各浏览器与 WHATWG HTML 标准、Fetch 标准沿用同一模型，核心定义至今稳定。
- **放宽机制的退场**：历史上，同一可注册域名下的两个子域曾可通过设置 `document.domain` 为共同父域来放宽限制、互访 DOM。这一做法已被 MDN 标记为已弃用：它会抹掉源中的端口分量，扩大可互访的范围，并给跨源隔离带来安全与互操作问题。Chrome 方面已宣布自 Chrome 115 起使 `document.domain` 不可修改，并建议改用 `postMessage` 或 Channel Messaging；其他浏览器的跟进节奏以各自官方发布为准（待核实），新代码不应再依赖它。
- **从“源”到“站”的分层**：随着第三方 Cookie 限制、存储分区等机制出现，浏览器在“源”之外又引入了“站”这一层概念，用于描述跨站追踪与分区存放。但这没有改变同源策略本身：读隔离的判定单位仍然是源，不是站。Cookie 跨站行为的完整机制见[Cookie 属性与安全](08-cookie-attributes-security.md)，存储分区的机制见存储篇。

## 5. 关键设计取舍

- **默认拒绝换安全**：默认什么跨源读取都不许，再由资源方逐项放行。开发时多一步配置，换来的是“陌生页面默认偷不到数据”。
- **拦读不拦发送换兼容**：Web 从一开始就允许跨源表单与资源嵌入；如果连发送都拦，图片、脚本、表单这些基础能力全会断。代价是服务器必须自己防“请求被冒名发出”的问题，同源策略不替它背。
- **执行归属引入页换简单**：脚本在引入页的源里执行，规则简单明确；代价是引入第三方脚本就是完全信任它——脚本一旦被篡改或本身不可信，引入页的数据就暴露在它面前。选脚本源时要按“可信代码”来选，不按“能不能加载”来选。
- **源粒度换精确**：端口也算进源，粒度很细，本地开发时 `localhost:3000` 与 `localhost:8000` 就是跨源，会多出配置成本；换来的是“同机不同服务互不可读”的精确隔离。

## 6. 分类与变体

- **按源的种类**：三元组源（正常 Web 页面）；不透明源（沙箱 iframe 等特殊上下文，与任何源都不等同）。不透明源没有“放宽成同源”的路径，只能走 `postMessage` 这类显式通信。
- **按隔离对象**：DOM 隔离、网络响应隔离、存储隔离——三者共用“源”这把尺子，但放行机制各不相同（DOM 靠 `postMessage`，网络响应靠 CORS，存储原则上不跨源共享）。
- **按关系**：同源（全放行）、同站跨源（仍隔离，Cookie 与分区机制另有规则）、跨站（隔离，且跨站请求还受 Cookie `SameSite` 等规则约束）。

## 7. 应用与限制

- 应用：登录态隔离（邮箱页脚本读不到陌生页、陌生页脚本读不到邮箱页）；多租户与内嵌组件隔离（iframe 里的第三方内容默认读不到宿主数据）；本地开发多端口服务的前后端分离（靠 CORS 显式放行，而非关掉策略）。
- 限制：同源策略只管浏览器内的脚本读取，不管非浏览器客户端——`curl` 能拿到响应不代表浏览器脚本能读；它也不管服务器收到的请求是不是用户本意；它更不是访问控制：服务器仍须对每个请求做鉴权。
- 常见误解：
  - “请求发出去就是绕过了同源策略”：错。发与读是两步，浏览器拦的是读；服务器日志里看到请求到来，不能反推“策略失效”。
  - “同站就是同源”：错。子域不同就是不同源，`app.example.com` 与 `api.example.com` 互访要走跨域机制。
  - “CORS 是关掉同源策略”：错。CORS 是资源方对特定源的逐项放行，放行范围之外的源仍然被拦；下一篇讲放行的正确写法。
  - “改端口不算跨源”：错。端口是源的第三项，`localhost:3000` 与 `localhost:8000` 是跨源，本地联调最常在这里绊倒。

## 8. 读者验证步骤（未在本机浏览器实测）

> 以下是在读者自己浏览器里的验证方法，不是本文已跑过的测试。本地服务器响应头的实测见下一篇第 8 节。

1. 在浏览器打开任意两个不同源的页面（例如两个不同端口的本地服务），在其中一个页面的控制台尝试读取另一个源 iframe 的 `contentDocument`，观察到跨源访问被拒绝的报错。
2. 在同一页面控制台用 `fetch` 请求一个未配置 CORS 的跨源地址，观察网络面板里响应实际到达、但脚本侧报跨源读取失败——对照理解“发”与“读”的分界。
3. 打开一个引入了第三方脚本的页面，确认该脚本能访问引入页的 DOM：验证“脚本在引入页的源里执行”这一条。
