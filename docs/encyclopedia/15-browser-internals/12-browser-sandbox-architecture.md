# 浏览器沙箱与进程架构

## 1. 本章目标

读完本篇，能说清浏览器为什么要把网页放进低权限进程里跑、站点隔离把隔离边界从“标签页”收紧到“站点”改变了什么，以及渲染进程与浏览器进程之间只能通过什么通道说话。

## 2. 背景与问题

网页代码是不可信代码：浏览器每天都要执行来自任意站点的 HTML、JavaScript、图片解码、字体解析。早期浏览器是单进程的——一个页面崩溃拖垮整个浏览器，一个页面里的漏洞就可能直接触及文件系统与网络。解决办法不是“让网页代码更可信”，而是“假设它终会被攻破，然后把它的破坏范围关进笼子”。这个笼子就是沙箱，而装笼子的架子就是多进程架构。

本篇只讲浏览器视角的隔离机制。漏洞的分类与研究方法、授权测试流程属 10 域，见文末相关主题，不在此重复。

## 3. 总体架构

以 Chromium 为例（Blink 引擎），各引擎分工名称不同，但“特权进程管资源、非特权进程跑网页内容”的分层是共通的：

```
┌─────────────────────────────────────────────────────────┐
│ 浏览器进程（Browser Process）                              │
│  不进沙箱，权限最高：管标签页、地址栏、网络、存储、权限      │
│  唯一被信任“替别人办事”的进程；所有 IPC 输入都视为不可信    │
└──────────────┬──────────────────────┬───────────────────┘
               │ Mojo IPC（消息 + 句柄传递）│
       ┌───────┴────────┐  ┌──────────┴───────┐  ┌──────────────┐
       │ 渲染进程        │  │ GPU 进程         │  │ 网络 / 工具进程│
       │ 最强沙箱、权限最低│  │ 较弱沙箱         │  │ 各有不同强度沙箱│
       │ 跑网页代码      │  │ 光栅化与合成     │  │ 联网、解码等   │
       └────────────────┘  └──────────────────┘  └──────────────┘
```

- **浏览器进程**：唯一不进沙箱的进程。它持有用户数据、文件与网络的直接访问权，因此也是攻击者最想到达的位置——沙箱设计的全部目标，就是不让渲染进程直接到达这里。
- **渲染进程**：运行 Blink 与 JavaScript 引擎，执行网页代码。沙箱最强：默认没有直接的文件系统访问、没有原始网络访问，只能通过浏览器进程代劳。
- **GPU 进程**：承接光栅化与合成的加速部分，沙箱弱于渲染进程（它必须直接与图形驱动打交道）。
- **网络进程与工具进程**：分别处理网络请求与解码、解析等不可信数据，沙箱强度按各自需要而定，均弱于渲染进程但仍受限。

Firefox（Gecko）与 Safari（WebKit）也有各自的多进程与沙箱实现：Firefox 的桌面站点隔离工程名为 Fission，Safari 在苹果平台上依赖系统沙箱机制。实现细节与默认开启范围各不相同，以各厂商官方文档为准（见未完成项）。

## 4. 工作机制

### 4.1 沙箱是怎么“关笼子”的

沙箱不是浏览器自己发明的一层魔法，而是借用操作系统提供的隔离原语组合而成：

- **降权运行**：渲染进程以低权限身份运行，能调用的系统调用（syscall）被白名单收紧；文件、网络、窗口等资源默认不可直接访问。
- **中介（Broker）模式**：渲染进程想做的特权事（例如读一个文件、发一个网络请求），不能自己做，只能向浏览器进程发 IPC 请求，由浏览器进程按策略决定做不做、做多少。浏览器进程就是那个“中介”。
- **隔离桌面 / 隔离 UID**：在不同平台上，渲染进程还会被进一步隔开，例如与用户可见桌面分离，或以独立的受限用户身份运行，使它难以向用户界面注入输入或窥探其他进程。

关键理解：沙箱防的是“已经拿到渲染进程执行权的代码继续向外走”，而不是“阻止网页代码运行”。网页代码在笼子里可以任意折腾——折腾的范围出不了笼子，才算沙箱起作用。

### 4.2 进程间通信（IPC）边界

进程之间不共享内存，说话只能走 IPC。Chromium 的 IPC 系统名为 Mojo：

- **消息传递**：调用方把请求序列化成消息发过去，接收方反序列化后再处理。序列化边界本身就是一道检查点：畸形、超大、越权的消息可以在这里被拒绝。
- **句柄传递**：Mojo 还可以传递文件句柄等对象，但这同样受浏览器进程的策略管控，不是渲染进程想拿就能拿。
- **默认不信任**：浏览器进程必须把所有来自渲染进程的 IPC 输入当作不可信输入来校验。任何“渲染进程说是什么就是什么”的接口，都是架构上的缺口——这条规则在 Chromium 安全文档中被反复强调。

因此 IPC 接口的数量与严格程度直接决定沙箱的实际强度：接口越少、校验越严，逃出笼子的路就越窄。

### 4.3 站点隔离：从“每标签页一进程”到“每站点一进程”

多进程的早期形态是“一个标签页一个进程”：A 标签页崩溃不影响 B 标签页。但同一个标签页里可以嵌着多个站点的 iframe——如果它们共享一个渲染进程，进程内就还存在跨站点的数据边界，只靠逻辑隔离（同源策略）守着。2018 年初公开的 Spectre 类推测执行侧信道问题让这一点变得尖锐：进程内的逻辑边界拦不住跨站点的数据读取。

站点隔离（Site Isolation）把边界收紧了一档：

- **锁定渲染进程**：一个渲染进程只装载来自同一个站点（scheme + eTLD+1，即 schemeful same-site）的文档与 Worker，即使是 iframe 里的跨站点文档，也要分到各自站点的进程里。
- **浏览器侧强制**：浏览器进程监视锁定进程的 IPC，拒绝它索取其他站点的数据、冒用其他站点的权限。
- **网络响应过滤**：浏览器进程确保锁定进程只能收到本站点的敏感响应（如 HTML、XML、JSON），跨源子资源（如图片、媒体）仍可按兼容性需要加载——这部分由跨源读取阻断（CORB）及其后继的不透明响应阻断（ORB）机制实现。

经联网核查的关键时间线（以 Chromium 官方站点隔离页面为准）：Chrome 67（2018 年，桌面 Windows / Mac / Linux / Chrome OS）默认对所有站点启用站点隔离；Chrome 77 起，站点隔离在桌面端同时用于防御已被完全攻破的渲染进程；Chrome 92 起扩展到隔离各个扩展；Chrome 110 起支持 `<webview>` 标签。Firefox 桌面版的 Fission 自 2021 年起逐步默认启用；移动端各浏览器的站点隔离开启范围变动较频繁，以官方发布为准（待核实），见文末未完成项。

### 4.4 同源策略与站点隔离是什么关系

两者是互补的两层边界，不要混为一谈：

- **同源策略**是逻辑边界：协议、域名、端口三者都相同的源才能互相读写对方的数据。它由浏览器内的检查逻辑执行，细节见[同源策略](14-same-origin-policy.md)。
- **站点隔离**是物理边界：把不同站点放进不同的操作系统进程，即使逻辑检查被绕过或出现侧信道读取，攻击者能读到的也只限于本站点进程内的数据。

一句话：同源策略决定“按规矩不许看”，站点隔离决定“即使不守规矩也看不到别人的”。

### 4.5 关键设计取舍

- **进程越多，内存越多**：站点隔离把一个页面拆成多个进程，内存占用上升。浏览器用“站点”而非“源”作为锁定粒度（同一站点的不同子域可共享进程），就是在隔离强度与内存开销之间取的折中。
- **特权集中换接口风险**：浏览器进程不进沙箱、权力最大，于是它收到的每一条 IPC 都成了攻击面。架构上用“最小接口 + 严格校验”来还这笔账。
- **兼容换安全**：跨源子资源、跨站点 iframe 通信（如 postMessage）必须继续工作，隔离不能一刀切断所有跨站点协作；于是才需要 CORB / ORB 这类“按响应类型过滤”的精细机制，而不是简单地禁掉跨源加载。

## 5. 合法研究范围

本篇的研究只在自有设备、授权系统或隔离靶场内讨论架构与防御。未授权测试他人系统是违法行为，本文不提供相关指导。沙箱与站点隔离的讨论止于“机制如何工作、如何检测它是否生效、如何加固”，不涉及逃出沙箱或绕过站点隔离的操作步骤。

## 6. 实验环境（示例未实测）

> 本地没有可跑浏览器沙箱实验的环境：以下均为读者在自己设备上的观察方法示例，未在本机实测，不许理解为“实测通过”。

- 环境：自有设备上的日常浏览器，不改动任何安全开关。
- 观察方法（只读、不改配置）：
  1. 打开一个含跨站点 iframe 的页面，再打开浏览器自带的任务管理器（Chrome 系：菜单 → 更多工具 → 任务管理器），对照标签页与进程的对应关系，观察跨站点 iframe 是否落在不同进程。
  2. 在地址栏输入浏览器的内部进程查看页（如 Chrome 系的任务管理器），只看进程归属与内存占用，不关闭、不结束任何进程。
- 权限要求：不需要管理员权限；不要以 `--no-sandbox` 或同类开关启动浏览器——那等于亲手拆掉笼子，不属于任何合法实验。

## 7. 风险

- **误以为“多进程 = 绝对安全”**：沙箱与站点隔离缩小破坏范围，不等于消灭漏洞。浏览器进程本身、IPC 校验、操作系统原语仍可能出问题。规避做法：保持浏览器自动更新，不把“有沙箱”当作不更新的理由。
- **为排障而关沙箱**：网上排障帖偶尔建议加禁用沙箱的启动参数。规避做法：日常浏览绝不使用此类参数；排障应在隔离环境、且事后立即恢复默认启动方式的前提下进行。
- **扩展与插件越过隔离**：扩展的权限模型与网页不同，个别扩展拥有跨站点能力。规避做法：只装必需的扩展，定期清理不再用的扩展（扩展权限管理的通用流程属 10 域授权与检测主题，不在此展开）。

## 8. 检测方式

以下均为防御侧的“隔离是否生效”检查，不含规避检测的方法：

- **进程归属检查**：用浏览器任务管理器确认不同站点是否落在不同渲染进程；同一站点反复出现、跨站点混进同一进程时，先确认是否为同站点的子域共享（属正常折中），再怀疑配置异常。
- **崩溃隔离检查**：单个标签页崩溃（例如页面无响应）时，其他标签页是否继续正常工作——这是多进程架构最直观的生效信号。
- **版本与策略检查**：在受管设备上，通过企业策略或浏览器版本信息确认站点隔离未被策略关闭；个人设备上不建议手动改动相关开关，默认开启即为预期状态。
- **日志与告警**：企业环境可结合浏览器与终端的崩溃、沙箱违规日志做集中告警；具体日志字段与告警规则属 10 域检测主题，见相关主题链接。

## 9. 修复与防御方法

- **对普通用户**：保持浏览器自动更新开启；不使用禁用沙箱的启动参数；不安装来源不明的扩展；站点隔离是默认开启的，不需要、也不建议手动开关。
- **对网站开发者**：用 `Cross-Origin-Opener-Policy` 与 `Cross-Origin-Embedder-Policy` 等响应头声明跨源隔离需求（这是让浏览器把你的页面放进更严格隔离环境的声明方式，具体取值以 MDN 文档为准）；其余防御头（CSP 等）见下一篇。
- **对企业管理员**：通过受管策略统一浏览器版本与站点隔离策略，集中收集崩溃与沙箱日志；不要为兼容个别老旧内网应用而全局关闭站点隔离，确需例外时只对单个站点放行并记录原因与到期复核时间。

## 10. 历史与案例

只引用公开来源，不展开任何利用细节：

- **2018 年 Spectre / Meltdown 公开**：推测执行侧信道问题公开后，进程内逻辑边界的不足被摆上台面，Chrome 67 随即在桌面端默认启用全站点隔离（见 4.3 时间线）。这是站点隔离从“长期工程”变成“默认配置”的直接推动力。
- **Chrome 77 起的防御升级**：据 Chromium 官方站点隔离页面，站点隔离自 Chrome 77 起在桌面端同时用于防御已被完全攻破的渲染进程，而不只限于侧信道场景。
