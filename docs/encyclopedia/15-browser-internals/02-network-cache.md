# 网络栈与缓存

## 1. 本章目标

读完本篇，能说清浏览器从拿到一个网址到拿到响应字节要经过哪几层、每一步在等什么，以及浏览器缓存“什么时候直接用、什么时候先问服务器”。

## 2. 背景与问题

渲染进程要画页面，先得有数据。数据在另一台机器上，中间隔着域名解析、连接建立、加密协商、协议传输四道关；每一道都要花时间，而且任何一道出问题都会表现为“打不开”或“很慢”。更麻烦的是：每次都从头走一遍既慢又浪费——于是有了缓存：在正确性允许的前提下，能不发请求就不发，能少传字节就少传。

本篇讲浏览器侧的机制：服务器怎么配置缓存属 06/09 域，本篇只讲浏览器拿到响应头之后的行为。

## 3. 总体架构

```
地址栏 URL
   │ ① DNS：域名 → IP（浏览器缓存 → 系统缓存 → 递归解析）
   │ ② TCP：三次握手建连接（或复用已有连接）
   │ ③ TLS：加密协商（HTTPS 才有）
   │ ④ HTTP：发请求、收响应（版本决定复用与压缩方式）
   │ ⑤ 缓存：响应按策略进内存/磁盘缓存，供下次复用
   ▼
渲染进程（见上一篇）
```

浏览器内部这条链路由网络服务负责：连接池管复用，缓存层管存储，渲染进程只管“要数据”与“收数据”。

## 4. 工作机制

### 4.1 DNS：先查缓存，再问出去

浏览器按顺序查：自身 DNS 缓存 → 操作系统缓存 → 配置的递归解析器 → 权威服务器。查到就停，查不到才向下一级问。域名解析结果本身也有生存时间（TTL），过期重查。**DNS 慢，首字节就慢**——连接还没建，时间已经花出去了。

### 4.2 TCP：三次握手

客户端发 SYN，服务器回 SYN-ACK，客户端回 ACK——三个包走完，连接才算建立，数据才能发。握手本身至少一个往返时延（RTT）；离服务器越远、RTT 越大，握手代价越高。这就是连接复用（keep-alive）值钱的原因：一次建好，多次请求共用，握手只付一次。

### 4.3 TLS：加密协商

HTTPS 在 TCP 之上再加一层协商：双方确认协议版本、交换密钥材料、验证服务器证书。TLS 1.2 需要两个往返，TLS 1.3 压缩到一个往返——版本升级省下的就是这一次往返。协商完成后，HTTP 报文才在加密通道里传输；证书验证失败时浏览器会拦截并警告（证书体系本身属 13 密码学域）。

### 4.4 HTTP：版本演进是一部“去排队史”

- **HTTP/1.1**：一连接一次只能传一个响应，后面的请求排队等（队头阻塞）；缓解办法是开多连接，但连接数一多，握手与拥塞成本又上去了。
- **HTTP/2**：同一连接内多路复用——多个请求与响应拆成帧交错传输，互不排队；头部用 HPACK 压缩，重复头部不再反复传。代价是：TCP 层丢一个包，整条连接上的所有流都得等（TCP 队头阻塞还在，只是从 HTTP 层移到了 TCP 层）。
- **HTTP/3**：底层换成 QUIC（基于 UDP）：连接建立与 TLS 协商合并，单流丢包不影响其他流，连接还可以在网络切换（如 Wi-Fi 切移动网络）后存活。代价是：UDP 在某些网络会被限流或拦截，协议实现与运维成熟度仍在追赶。

版本协商本身由 TLS 的 ALPN 机制完成：握手时双方就商量好用 HTTP/1.1、HTTP/2 还是 HTTP/3，浏览器与服务器按协商结果走。

### 4.5 响应之后：浏览器缓存的两道门

浏览器拿到响应后，先看响应头决定“能不能存、能存多久”：

**第一道门：强缓存（不发请求）**

- `Cache-Control: max-age=N`：N 秒内直接用缓存，一次请求都不发。
- `Cache-Control: no-store`：不许存，每次都重新请求。
- `Expires`：老式绝对过期时间，`Cache-Control` 存在时优先用后者。
- 强缓存过期后，才轮到第二道门。

**第二道门：协商缓存（发请求、可能不传正文）**

- 服务器给过 `ETag`（资源指纹）时，浏览器下次带 `If-None-Match` 去问；指纹没变，服务器回 `304 Not Modified`，正文不传，浏览器用缓存。
- 只有 `Last-Modified` 时，带 `If-Modified-Since` 去问，语义相同、精度较粗（秒级）。
- `Cache-Control: no-cache` 的意思是“可以存，但每次用之前必须先问服务器”——不是“不缓存”。

**缓存放哪**：内存缓存（当前会话，速度快、关页面即失）与磁盘缓存（跨会话，按策略淘汰）；Service Worker 的 Cache Storage 是另一套由脚本控制的缓存，属应用层机制，本篇只点名，不展开写法。

**缓存分区**：现代浏览器按“顶级站点”隔离缓存——A 站存过的资源，B 站内嵌同一个 URL 时不能直接复用。这是隐私设计：否则第三方能通过“缓存命中与否”探测用户去过哪些站。分区会让跨站共享缓存的收益下降，是隐私换性能的取舍。

## 5. 关键设计取舍

- **缓存时长换新鲜度**：`max-age` 越长，重复访问越快，但内容更新越晚被看到；文件名带哈希的静态资源敢设一年，就是因为内容一变、文件名就变，旧缓存自然失效。
- **复用换队头阻塞**：HTTP/2 多路复用省了连接数，但 TCP 丢包会拖住整条连接；HTTP/3 用 QUIC 解了这一层，代价是 UDP 的可达性与实现成本。
- **TLS 往返换安全**：加密协商的往返省不掉，只能压缩（TLS 1.3）或复用（会话恢复）；明文省时间，但内容与身份全暴露。
- **预连接换资源**：浏览器可提前做 DNS 预解析、TCP 预连接，代价是用户根本不点的链接也会消耗连接与带宽。

## 6. 分类与变体

- 按缓存位置：内存缓存、磁盘缓存、Service Worker 缓存、CDN 边缘缓存（最后一项在浏览器之外，浏览器只看到它回的响应头）。
- 按缓存策略：强缓存、协商缓存、不缓存。
- 按协议：HTTP/1.1、HTTP/2、HTTP/3（见 4.4）。
- 按连接：新建连接、复用连接、预连接。

## 7. 应用与限制

- 应用（机制层面的推论）：页面“刷新一下就好了”往往是因为强缓存过期或协商后更新；“换了浏览器就好了”往往是因为缓存分区或缓存状态不同；静态资源一年缓存 + 文件名哈希，是缓存时长与新鲜度取舍的标准解。
- 限制：本篇不讲服务器缓存配置（Nginx、CDN 配置属 06/09 域）；不讲 DNS 服务器搭建（属 07 域）；不展开 Service Worker 编程（属 03 域）。
- 常见误解：
  - “`no-cache` 就是不缓存”：错。它是“存了也得先问”，`no-store` 才是“不许存”。
  - “304 是错误”：错。304 是“没变，用你缓存里的”，是协商缓存成功的正常响应。
  - “清缓存就能解决一切加载问题”：不全面。清缓存只解决缓存陈旧，DNS、连接、证书、服务器问题都不在缓存里。

## 8. 可核验示例：用 curl 看本站真实响应头

> 环境：代理 VM，curl 直连，2026-11-04 实际运行结果。注意第一行 `HTTP/1.1 200 Connection Established` 是本地代理隧道的 CONNECT 回显，不是目标站点的响应；真正的状态行在第二行。

```bash
curl -sI --max-time 30 https://crozz.me/assets/images/favicon.png
curl -sI --max-time 30 https://crozz.me/website-guide/html/01-basics/
```

实际输出（节选）：

```
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
cf-cache-status: MISS
```

```
HTTP/1.1 200 OK
last-modified: Tue, 03 Nov 2026 16:00:14 GMT
Server: cloudflare
cf-cache-status: DYNAMIC
```

怎么读：站内 `/assets/` 下的静态资源带 `public, max-age=31536000, immutable`——一年强缓存且声明内容不可变，浏览器一年内不会为它再发请求（文件名带哈希，内容变则文件名变）；而文章 HTML 页没有 `Cache-Control`，且 `cf-cache-status: DYNAMIC`——这类页面不走强缓存，每次访问都会向源站确认。这正是 4.5 两道门在本站的真实对照。
