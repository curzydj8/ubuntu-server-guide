# 渲染引擎与渲染流程

## 1. 本章目标

读完本篇，能说清浏览器把一份 HTML 文档变成屏幕像素要经过哪几步、哪一步会被什么阻塞，以及“回流”“重绘”“合成”三个词到底指什么。

## 2. 背景与问题

浏览器拿到的只是一堆文本：HTML、CSS、JavaScript。屏幕要的却是像素。中间必须有人把文本翻译成“哪个元素在什么位置、长什么样”，并且在内容变化时只重做必要的部分——全量重画每一帧既慢又耗电。渲染引擎就是干这个的：它把文档变成像素，并尽量让每一帧都赶在下一次屏幕刷新之前完成。

本篇讲“为什么这样工作”，不讲“怎么写页面”：写 HTML、CSS、JavaScript 的方法属 03 前端开发域，本篇只在需要时引用它。

## 3. 总体架构

以 Chromium 为例（Blink 引擎），一次页面呈现涉及多个进程分工，但渲染管线本身各引擎大同小异：

```
HTML 文本 ──解析──▶ DOM 树
CSS 文本 ──解析──▶ CSSOM 树
                         │
              DOM + CSSOM ──▶ 渲染树（只含可见内容）
                         │
                    布局 ──▶ 每个节点的位置与尺寸
                         │
                    分层 ──▶ 划分为绘制层与合成层
                         │
                    绘制 ──▶ 生成绘制指令（Display List）
                         │
              光栅化 + 合成 ──▶ 像素上屏
```

- **浏览器进程**：管标签页、地址栏、网络与存储的协调。
- **渲染进程**：跑渲染引擎与 JavaScript 引擎，是本篇的主角。
- **GPU 进程**：接管光栅化与合成的加速部分。
- 其他引擎（WebKit、Gecko）的进程划分不同，但“解析 → 树 → 布局 → 绘制 → 合成”这条管线是共通的。

## 4. 工作机制

### 4.1 解析：边读边建树

HTML 解析是**增量**的：浏览器不必等整个文档下载完才开始，读到哪、解析到哪、渲染到哪。解析器按规范做容错处理——标签没闭合、嵌套写错，浏览器会按规则修复而不是报错，这就是“同一份写坏的 HTML 在各浏览器看起来差不多”的原因。

CSS 解析生成 CSSOM（CSS 对象模型）：选择器、声明、级联与继承都在这一步算出“每个元素最终穿什么衣服”。**CSSOM 没建好之前，渲染会被阻塞**：浏览器不知道元素长什么样，宁可晚点画，也不能先画错再闪变。

JavaScript 对解析的影响是机制性的：

- 普通 `<script>` 会**阻塞 HTML 解析**：因为脚本可能修改正在建的 DOM，解析器必须停下来先执行它。
- `defer` 的脚本等文档解析完、触发 DOMContentLoaded 之前按顺序执行；`async` 的脚本下载完就执行，不保证顺序。两者都是“让解析少被挡住”的机制，具体写法属 03 域。

### 4.2 渲染树：不是 DOM 的复制品

渲染树 = DOM + CSSOM 的交集，但**只含需要画出来的东西**：

- `display: none` 的节点不进渲染树（它不占位置也不画）。
- `visibility: hidden` 的节点进渲染树（占位置，只是不画出来）。
- 伪元素、文本节点按规则参与布局。

DOM 是文档结构，渲染树是“待绘制清单”——两者一字之差，查问题时先分清查的是哪棵树。

### 4.3 布局：算位置与尺寸

布局（Layout，又称回流）遍历渲染树，算出每个节点的精确位置与尺寸，依据是盒模型：内容、内边距、边框、外边距。布局是**自上而下、依赖传播**的：父容器尺寸变了，子节点往往要跟着重算；改动越靠上、影响面越大，这就是“尽量少动布局、改动往叶子节点放”这条经验的根源。

### 4.4 分层、绘制与合成

- **分层**：渲染树再按规则划分为若干层。普通内容共用一层；特定条件下（如 3D 变换、视频、canvas）会提升为独立的**合成层**，由 GPU 单独处理。
- **绘制**：每层生成绘制指令清单（画矩形、画文字、画图片……），但这时还没产生像素。
- **光栅化**：把指令真正画成位图（可由 CPU 或 GPU 做）。
- **合成**：把各层的位图按正确顺序与位置拼成最终画面，交给屏幕。

动画只改合成层属性（如位移、透明度）时，可以跳过布局与绘制，只重做合成——这是“某些动画特别流畅”的机制原因；反过来，动画改了布局属性，就得从布局一路重做到合成，代价最大。

### 4.5 帧节奏

屏幕一般每秒刷新 60 次，留给一帧的时间约 16.6 毫秒。JavaScript 执行、样式计算、布局、绘制、合成都要挤进这个预算；某一帧超了，就表现为掉帧或卡顿。渲染管线存在的意义，就是把每帧要做的事压到最少。

## 5. 关键设计取舍

- **容错解析换兼容**：HTML 解析器按规范修复错误写法，代价是解析规则复杂；好处是绝大多数页面都能画出来，而不是一错就白屏。
- **CSS 阻塞渲染换正确**：CSS 没就绪就不画首屏，换来的是不闪变；代价是样式表一大，首屏就晚。
- **合成层换流畅**：层越多，动画越能走合成快车道；但每层都要占内存、都要单独光栅化，层泛滥反而更慢。`will-change` 这类提示的本质就是“提前建层”，用内存换未来某次动画的流畅——滥用等于提前把代价全付了。
- **增量解析换首屏**：边读边画让首屏更快，但解析器必须随时能处理“文档还没读完”的状态，复杂度由引擎承担。

## 6. 分类与变体

- **按引擎**：Blink（Chromium 系）、WebKit（Safari）、Gecko（Firefox）。管线阶段相同，实现细节与进程模型不同；本篇以 Blink 为例，结论可迁移，数值与行为细节以各引擎文档为准。
- **按渲染地点**：客户端渲染（CSR）——浏览器拿到空壳再取数据拼页面，首屏依赖脚本；服务端渲染（SSR）——服务器先拼好 HTML 再发给浏览器，首屏快、后续再由脚本接管交互。两者只是“拼页面的活谁干、在哪干”的分工不同，浏览器内的渲染管线不变。
- **按内容类型**：普通文档流、canvas 2D/WebGL、视频——后两者大量工作在合成层与 GPU，布局阶段参与较少。

## 7. 应用与限制

- 应用（机制层面的推论，不展开写法）：关键渲染路径越短，首屏越快——阻塞解析的脚本、阻塞渲染的样式表、庞大的 DOM，都是路径上的关卡；动画优先走合成属性，是管线结构直接给出的结论。
- 限制：本篇不展开 JavaScript 引擎的执行机制（解析、编译、事件循环属 15 域的另一主题，待写）；不展开网络传输细节（见下一篇）；不教页面写法（属 03 域）。
- 常见误解：
  - “DOM 就是渲染树”：错。`display: none` 的节点在 DOM 里、在渲染树外。
  - “改样式就一定回流”：错。只改颜色类属性一般只重绘；改尺寸位置才回流；改合成层属性可只合成。
  - “CSS 放在哪里都一样”：错。样式表在文档靠后位置会拖后 CSSOM，进而拖后首次渲染；机制上样式表越早可达，阻塞越短。

## 8. 读者验证步骤（未在本机实测）

> 本机无浏览器实测环境，以下是读者在自己浏览器里的验证方法，不是本文已跑过的测试。

1. 打开任意页面，按 F12 打开开发者工具 → Performance 面板 → 录制一次刷新。
2. 在时间线里找到 Parse HTML、Recalculate Style、Layout、Paint、Composite Layers 几个阶段，对照本篇 4.1–4.4 的顺序。
3. 找一个长动画页面，对比“改位移属性”与“改宽度属性”两种动画的帧时间：前者一般只触发合成，后者会触发布局。
