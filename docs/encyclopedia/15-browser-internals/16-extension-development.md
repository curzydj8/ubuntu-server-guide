# 浏览器扩展开发入门

> 阅读提示：本篇以 Chrome 为例讲扩展的通用结构与开发流程。Firefox、Safari 的扩展模型与 Chrome 不完全相同，细节以各自官方文档为准。
>
> 环境说明：本地没有可交互验证扩展加载与调试的浏览器环境，本篇所有代码与操作步骤均为**示例未实测**，请在自己的 Chrome 里按文末验证步骤跑一遍再用于正式项目。

## 1. 工具定位

浏览器扩展是运行在浏览器里的小程序：它可以在工具栏上放一个按钮、在指定网页里注入脚本改写页面、监听浏览器事件做后台处理，或者拦截、改写网络请求。它的价值在于“浏览器原生能力 + 网页能力”的结合——既能像网页脚本一样读写页面 DOM，又能调用浏览器才提供的 API（如标签页、存储、闹钟）。

Manifest V3（简称 MV3）是 Chrome 当前的扩展平台版本。它相对上一代 Manifest V2 最核心的变化是三点：后台由常驻页面改为事件驱动的 Service Worker；网络请求改动由阻塞式拦截改为声明式规则；API 权限与网站访问权限分开声明。理解这三点，就理解了 MV3 开发的大半约束。

## 2. 适用环境

- 系统 / 版本：Chrome 浏览器（本篇事实以 Chrome 官方文档为准；各 API 的最低 Chrome 版本以官方 API 参考为准，本文不逐条列出版本号）。
- 安装方式（开发调试）：在 Chrome 地址栏打开 `chrome://extensions`，开启右上角的**开发者模式**，用**加载已解压的扩展程序**选择扩展文件夹即可本地加载；正式分发走 Chrome 应用商店，见第 6 节。
- 权限要求：开发本地加载不需要管理员权限；发布需要一个 Chrome 应用商店开发者账号，注册流程与费用以注册时仪表盘显示为准（待核实，见文末未完成项）。

## 3. 基本用法

### 3.1 一个扩展由哪些部分组成

```
my-extension/
├── manifest.json      # 清单：扩展的“身份证 + 权限申报单”
├── background.js      # Service Worker：后台逻辑
├── content.js         # 内容脚本：注入网页，读写 DOM
└── popup.html         # 可选：点工具栏图标弹出的小页面
```

清单文件 `manifest.json` 是浏览器最先读的文件：名字、版本、权限、后台脚本路径、内容脚本匹配网址都在这里声明。清单写错，扩展就加载失败——排错先看 `chrome://extensions` 里该扩展卡片下的报错信息。

最小可读示例（示例未实测，仅示意结构，不保证逐字段可直接加载）：

```json
{
  "manifest_version": 3,
  "name": "示例扩展",
  "version": "0.1.0",
  "description": "最小 MV3 结构示例",
  "permissions": ["storage", "activeTab"],
  "host_permissions": ["https://example.com/*"],
  "background": {
    "service_worker": "background.js"
  },
  "content_scripts": [
    {
      "matches": ["https://example.com/*"],
      "js": ["content.js"]
    }
  ],
  "action": {
    "default_title": "示例扩展"
  }
}
```

要点：`manifest_version` 必须写 `3`；后台只声明一个 `service_worker` 文件路径，不再有常驻后台页面；`permissions` 声明的是浏览器 API 权限，`host_permissions` 声明的是可访问的网站，两者在 MV3 里是分开的字段，不要混写。

### 3.2 Service Worker 后台：事件驱动，用完即走

MV3 的后台是一个 Service Worker，而不是一直运行的页面。它的工作方式是：

- 浏览器在需要时加载它（如扩展安装、收到消息、闹钟触发、标签页事件），事件处理完、空闲一段时间后，浏览器会把它回收；下次事件到来时再重新加载。
- 它**没有 DOM、没有 `window`**，不能直接操作页面元素；需要 DOM 能力的后台任务（如解析页面、播放媒体），官方给出的路线是交给短时存在的离屏文档（Offscreen document）处理，细节以官方文档为准（待核实）。
- 正因为会被回收，**不要把重要状态只放在全局变量里**：下次唤醒时全局变量会回到初始值。持久状态应存到 `chrome.storage`（或 IndexedDB 等受支持的持久层），每次唤醒时先从存储里恢复。
- 监听器要在顶层同步注册，不要包在异步回调里再注册，否则唤醒时可能错过事件。
- 定时任务不要依赖 `setTimeout` / `setInterval` 长期准时触发（Worker 睡着时它们不可靠），应使用 `chrome.alarms` 这类由浏览器唤醒的机制；闹钟的最短间隔等数值以官方发布为准（待核实）。

示例（示例未实测）：

```js
// background.js：顶层同步注册监听，状态走 chrome.storage
chrome.runtime.onInstalled.addListener(() => {
  chrome.storage.local.set({ enabled: true });
});

chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type === "ping") {
    sendResponse({ type: "pong" });
  }
});
```

### 3.3 内容脚本：在网页里跑，但与页面脚本隔离

内容脚本是注入到匹配网页里运行的脚本，可以读写该页的 DOM、改样式、监听页面事件。它的两个关键边界是：

- **隔离世界（isolated world）**：默认情况下，内容脚本与页面自己的 JavaScript 共享 DOM，但**不共享 JavaScript 变量与函数**。页面脚本读不到内容脚本的变量，内容脚本也读不到页面脚本定义的变量。这是隔离带来的安全收益；如果确实需要触碰页面自己的 JavaScript 对象，需要用 `world: "MAIN"` 声明，但这会放弃隔离保护，只在确有必要时使用。
- **API 受限**：内容脚本只能用一小部分 `chrome.*` API（主要是消息与存储类），标签页、后台类能力要通过消息发给 Service Worker 代办。两边的通信用 `chrome.runtime.sendMessage` / `onMessage`，或 `chrome.runtime.connect` 建立长连接。

注入方式有两种：

- **声明式**：在 `manifest.json` 的 `content_scripts` 里写 `matches`（网址匹配模式）与 `js` / `css`，匹配的页面打开时自动注入；注入时机可配置（文档开始、文档结束、空闲时），默认值与各取值的确切语义以官方参考为准（待核实）。
- **编程式**：由用户操作（如点工具栏图标）触发，用 `chrome.scripting` API 向当前标签页注入脚本或样式，适合“只在用户需要时才动手”的场景。

示例（示例未实测）：

```js
// content.js：只读写 DOM，需要浏览器能力时发消息给后台
const headings = document.querySelectorAll("h1");
chrome.runtime.sendMessage({ type: "headings-found", count: headings.length });
```

### 3.4 网络请求：声明式规则取代阻塞式拦截

MV2 时代扩展可以用阻塞式 `webRequest` 在请求中途拦下来改内容；MV3 里常规扩展不再走这条路，改为 `declarativeNetRequest`：扩展事先声明一批规则（如“屏蔽某类脚本请求”“给某域名请求加响应头”），由浏览器在请求时按规则执行，扩展代码不逐条拦截、也不因此看到请求体内容。官方说明这一设计的好处是更省跨进程通信开销、隐私暴露更少；需要动态复杂拦截的企业 / 教育场景仍有受限的支持，细节以官方文档为准（待核实）。

另外一条 MV3 红线：**不允许执行任意远程托管的代码**。扩展的可执行代码必须打包在提交审核的扩展包里，不能运行时从网上拉一段脚本来执行；远程下发的只能是数据 / 配置，且执行路径须事先确定。动态代码的合法例外（如用户脚本、沙箱 iframe 内的远程代码）以官方文档为准（待核实）。

## 4. 常用选项与场景

- **只要“用户点一下、对当前页做点事”**：优先用 `activeTab` 权限 + 编程式注入，不要一上来就申请全站访问。`activeTab` 是用户手势触发的、针对当前标签页的临时访问，安装时不产生宽泛警告，用户接受度更高。
- **必须常驻在特定网站上**：用声明式内容脚本 + 窄 `host_permissions`（如只写 `https://example.com/*`），并在商店列表里写清为什么需要这个站。
- **权限可以晚点再要**：把非核心权限声明为可选权限（`optional_permissions` / `optional_host_permissions`），在用户真正用到某功能时用 `chrome.permissions.request()` 现场申请；用户拒绝也不应让扩展整体不可用。
- **后台需要“过一会儿提醒我”**：用 `chrome.alarms`，不要用全局计时器；需要“每天 / 每小时”这类周期任务时同样走闹钟。
- **扩展页面不要写内联脚本**：MV3 的内容安全策略禁止扩展页面里的内联 `<script>`，所有脚本一律放独立 `.js` 文件并引用。

## 5. 风险与注意事项

- **权限过大是最常见的上架被拒原因**：每申请一个权限，都要能在商店的权限说明里用一句话讲清用途；讲不清的权限先删掉，宁可功能上线后再申请。
- **宽泛主机权限会触发更严审查**：`<all_urls>`、全站通配这类声明会让用户看到醒目的安装警告、让审核更久，能窄则窄。
- **不要把密钥、口令写进扩展包**：扩展包是发给用户机器的东西，里面任何字符串都可被拆开看到；需要服务端能力的走自己的后端接口，密钥放服务端。
- **不要收集超出功能所需的页面数据**：内容脚本能读到整页 DOM 就意味着能读到用户在页上看到的隐私内容；只取功能必需的字段，传输与存储都要在隐私说明里讲清。
- **远程代码红线**：不要用“先上架一个壳、运行时拉脚本”的方式绕过审核，一旦被发现会被下架；配置数据与可执行代码的界限以官方政策为准。
- **Service Worker 睡眠导致的“偶发丢失”**：开发时在 `chrome://extensions` 里一直开着 Service Worker 的检查器，Worker 不会按真实空闲节奏休眠，睡眠类 bug 在开发机上复现不出来；验证时要关掉检查器、按真实使用节奏测。

## 6. 发布流程概述

发布只是“打包 → 填表 → 送审 → 等结果”四步，但每一步都有人工成本，时间预期不要写死：

1. **打包**：整理一个只含运行必需文件的发布文件夹（不要把源码草稿、测试文件打进去），先用“加载已解压的扩展程序”在干净的浏览器配置里完整测一遍，再压缩成 zip（`manifest.json` 须在 zip 根目录）。
2. **注册开发者账号**：用长期持有的 Google 账号登录 Chrome 应用商店开发者仪表盘，按提示接受开发者协议、完成注册；注册费用、身份核验要求以注册时仪表盘显示为准（待核实）。
3. **建项目、填表**：上传 zip 后填写商店列表（名称、描述、截图、图标）、隐私做法（单用途说明、每项权限的用途说明、数据收集声明）与分发设置（公开 / 不公开链接 / 限定测试人群等，可选项以仪表盘为准）。需要登录或特殊步骤才能体验的功能，要在送审说明里给审核员一条能走通的测试路径。
4. **送审并跟踪**：点“提交审核”后在仪表盘跟踪状态、查收邮件通知；审核时长会因权限范围、代码复杂度而有很大波动，官方口径为数天到数周不等，**不要向用户承诺具体上架日期**；被拒时按邮件里指出的政策条款改，改完重新送审；每次更新（哪怕只改一行）都要重新走一遍审核。
5. **更新**：已发布扩展的更新同样先在本地干净环境测过再上传新 zip；更新文案里写清改了什么，权限有新增时要同步更新权限说明。

## 7. 读者验证步骤（示例未实测）

> 以下是在自己 Chrome 里的验证方法，不是本文已跑过的测试。

1. 新建文件夹，按 3.1 的示例写 `manifest.json`、`background.js`、`content.js`，在 `chrome://extensions` 开启开发者模式后加载已解压的扩展程序，确认扩展卡片无报错。
2. 打开一个匹配 `matches` 的页面，确认内容脚本生效（如在控制台看到消息往来）；再打开一个不匹配的页面，确认内容脚本未注入。
3. 关掉 Service Worker 检查器、静置一段时间后再触发一次消息，观察后台是否重新唤醒、存储里的状态是否还在（验证“状态不能只放全局变量”）。
4. 把 `host_permissions` 改窄 / 改宽各测一次，对比安装时警告文案的变化，体会最小权限的意义。

## 8. 常见问题

- **扩展装上没反应，第一步查什么？** 先看 `chrome://extensions` 里该扩展卡片的错误信息，再看 Service Worker 检查器里的控制台报错；多数加载失败是 `manifest.json` 写错字段或 `service_worker` 路径不对。
- **后台变量“偶尔丢了”是怎么回事？** 大概率是 Service Worker 休眠后重建，全局变量被重置。把状态迁到 `chrome.storage`，唤醒时先恢复再处理事件。
- **内容脚本读不到页面脚本定义的变量，是 bug 吗？** 不是，这是隔离世界的默认设计；共享的是 DOM，不是 JavaScript 运行环境。确需互通时用消息中转，或谨慎使用 `world: "MAIN"` 并接受失去隔离保护的代价。
- **MV2 的老扩展还能直接改个版本号就用吗？** 不能。后台、权限声明、网络拦截、远程代码四处都要按 MV3 重做，属于迁移不是改版本号；迁移清单以官方迁移指南为准。
