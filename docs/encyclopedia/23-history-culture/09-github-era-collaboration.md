# GitHub 时代的协作文化

## 1. 一句话定义

GitHub 时代的协作文化是指：
以分布式版本控制 Git 为底座、以 GitHub 的 fork 与 pull request（拉取请求）为入口，让任何人都能复制一份代码、改完再把改动公开送回评审，从而把开源协作从少数维护者之间的邮件往来，变成大规模、公开、可追溯的社会化协作。

## 2. 为什么需要它

开源的理念在 1990 年代就已经讲清楚了，但理念不等于参与。

在 GitHub 出现之前，想给一个开源项目做贡献，往往要先加入邮件列表、读懂不成文的规矩、学会用补丁格式发邮件，再等维护者有空处理。
技术门槛只是一部分，**真正的门槛是“不知道从哪儿下手、改了也不知道会不会有人看”**。

GitHub 时代的意义就在于把这道门槛拆掉了：贡献的入口从“写一封格式正确的邮件”变成“点一下 fork，再发一个 pull request”。

理解这段历史，才能理解今天的开源为什么长成这样：
为什么一个学生的第一次提交可能出现在全世界都在用的项目里，为什么“在 GitHub 上有个主页”会成为程序员的简历，为什么企业会愿意把核心代码放在一家商业公司的平台上。

## 3. 核心含义：时间线与转折

### 3.1 邮件补丁时代：协作靠人，不靠平台

- **1990 年代的典型流程是“补丁 + 邮件列表”**：想改代码，先从服务器上拉一份源码，在本地改好，生成一份补丁文件，再发到项目的邮件列表里。
  维护者收到邮件、看补丁、手动合入，有问题再回邮件讨论。Linux 内核在很长一段时间里就是这样协作的。
- 这种方式能工作，但处处依赖人：补丁发丢了没人知道，讨论散落在几百封邮件里，新人不知道补丁该发给谁、格式对不对。
  **协作的知识只存在于老手的脑子里**，没有写成任何人都能照着走的流程。
- **集中式版本控制是当时的主流工具**：CVS、Subversion 这类系统把“唯一的正确版本”放在中央服务器上，开发者先从服务器取代码，改完再提交回去。
  好处是秩序清楚，代价是离线没法工作、分支很贵、实验性改动不敢轻易动手——每一次分支都像在中央仓库里动手术。
- 更深的问题是**权限即门槛**：没有提交权限的人，连“先改着试试”都要经过批准。贡献于是天然分成两级：圈内人直接改代码，圈外人只能在邮件列表里提建议。
  很多有能力的人，就卡在了这一步。
- 与此同时，托管平台已经出现：SourceForge 等网站提供代码托管、下载与议题管理，让项目不必自己搭服务器。
  但它们本质上还是“放代码的地方”，协作流程本身并没有变——补丁照样靠邮件，评审照样靠人。

### 3.2 2005 年 Git：先有分布式的工具，才有分布式的协作

- **导火索是 2005 年的 BitKeeper 风波**：
  Linux 内核此前用商业工具 BitKeeper 管理源代码，免费授权被收回后，内核社区一下子没了趁手的工具。托瓦兹决定自己写一个，前后只用了几周，Git 就此诞生。
- Git 的设计直接针对集中式工具的痛点：**每个人手里的都是一份完整的仓库**，包含全部历史；分支只是换个指针，创建与合并的成本极低；
  离线也能提交、查历史、做实验，联网只是为了同步。
- 转折在于协作关系的改变：以前是“中央仓库说了算，谁能提交由权限决定”；Git 之后，**任何人都可以先在本地完整地改、完整地试，不需要任何人批准**。
  批准只发生在“要不要把改动合进主线”那一步，而不是“能不能开始改”那一步。
- 但 Git 本身只是命令行工具，学习曲线陡峭。它解决了“怎么改”，没有解决“改完给谁看、谁来评、怎么讨论”。
  分布式协作的工具齐了，**一个让人愿意用的协作场所还没出现**。这个空缺，由三年后上线的 GitHub 补上。
- 同期还有另一条线：2005 年前后出现的 Mercurial 等分布式工具说明，分布式版本控制是行业的共同方向，不是 Git 一家的偶然；
  Git 最终胜出，更多是因为 Linux 内核与 GitHub 的选择，而不是它在技术上处处最优。

### 3.3 2008 年 GitHub 上线：协作第一次有了“社交层”

- **2008 年 2 月 8 日，GitHub 公司成立；同年 4 月 10 日，网站正式上线**：
  四位创始人——汤姆·普雷斯顿-沃纳（Tom Preston-Werner）、克里斯·万斯特拉斯（Chris Wanstrath）、P. J. 海特（P. J. Hyett）、斯科特·查孔（Scott Chacon）——此前都在旧金山 Ruby 社区里活动，他们想解决的是一个切身问题：
  用 Git 协作太麻烦了。
- GitHub 做的事可以概括为一句话：**把 Git 放在网上，再给它加一层社交界面**。
  公开仓库免费托管，私人仓库收费——这个定价让它一开始就能靠自己活下去，不必先找风投再想商业模式。
- **fork（复刻）+ pull request（拉取请求）是核心发明**：任何人点一下 fork，就能得到一份属于自己的完整副本；
  改完之后发一个 pull request，等于公开说“我改好了，请拉过去看看”。维护者在网页上就能看到改了哪些行、通没通过检查、有哪些讨论，点一下就能合并或打回。
- 这一模式的转折有三层：
  第一，**贡献不需要事先获得信任**：以前要先证明自己值得给权限，现在可以先做出改动，再凭改动赢得信任。顺序反过来了。
  第二，**评审过程本身变成公开内容**：讨论、修改意见、拒绝理由都留在 pull request 里，任何人都能围观学习。
    - 新人不再靠“问老手”入门，而是靠“看别人是怎么被评审的”入门。
  第三，**贡献变成可见的履历**：公开的提交记录、个人主页、star 与关注，把“为开源做过什么”变成可以展示的东西。
    - 找工作时亮出 GitHub 主页，逐渐成为程序员群体的通行做法。
- GitHub 还顺手把周边工具收进同一个页面：议题（issue）跟踪缺陷与需求、Wiki 写文档、Pages 托管静态网站。
  **一个项目从代码、讨论到发布的全部痕迹，第一次集中在一个地方**，外人不用翻遍邮件列表就能看懂项目在干什么。
- 需要分清的是：pull request 是 GitHub 的平台功能，不是 Git 自带的概念；
  Git 只有分支与合并，pull request 是 GitHub 给“请把我的分支合进去”这件事做的网页包装。
  后来 GitLab 等平台沿用了同一模式，它才成为行业通用语言。

### 3.4 治理的演变：从“一个人说了算”到“写下来的规则”

- **早期的治理大多是“仁慈的独裁者”模式**：项目由创始人说了算，托瓦兹之于 Linux 内核是最著名的例子。
  这种模式效率高、方向稳，但完全依赖个人的判断与精力，也埋下了“创始人一旦离开或犯错，项目怎么办”的隐患。
- **基金会托管是第二种答案**：
  Apache 软件基金会（1999 年成立）确立了“精英治理”（meritocracy）——按持续贡献授予表决权，重大决策投票决定，项目归基金会所有而不属于任何一家公司。
  Linux 基金会（2007 年由开放源代码开发实验室与自由标准组织合并而成）则走了另一条路：以企业会员费支撑内核及周边项目的长期维护。
- **公司主导是第三种形态**：由一家企业发起并主导的项目，决策权在公司手里，社区更多是贡献者而非决策者。这种形态资源充足，但社区始终要问一个问题：
  公司战略变了，项目会不会跟着变？
- **2010 年代，治理开始补上“人的规则”**：代码评审管的是代码质量，管不了讨论区里的人身攻击与排挤。
  2014 年，科拉琳·阿达·埃姆克（Coraline Ada Ehmke）起草《贡献者公约》（Contributor Covenant），给出第一份被广泛采用的开源行为准则模板：
  承诺营造不受骚扰的参与环境，并写明违规的执行方式。
- 行为准则的推广并不平坦：有人认为它与“只看代码”的传统冲突，也有人认为没有执行细则的准则只是一纸空文。但趋势是明确的：
  **越来越多的大项目把它写进仓库**，GitHub 也在新建仓库时提供行为准则模板。
  到 2018 年，Linux 内核项目也采纳了《贡献者公约》，托瓦兹同时公开为自己过去的沟通方式道歉——这件事的象征意义在于，连最坚持“只看代码”的项目，也承认协作文化需要明文规则。
- 今天的治理更像一张光谱，而不是三选一：同一个项目里，日常合并由维护者决定，方向性决策由技术委员会或指导委员会讨论，行为纠纷按行为准则处理。
  **规则越写越细，恰恰是因为参与的人越来越多、越来越不一样**。

### 3.5 企业参与的历史转变：从对手到房东

- **本世纪初，大企业与开源的关系还是对抗**：微软时任首席执行官史蒂夫·鲍尔默曾公开把 Linux 称为“癌症”，这句话成了那个时代的标志。
  企业眼里的开源，是威胁现有商业模式的东西。
- 转变是渐进的：企业先发现开源软件好用、省钱，开始在内部大量使用；接着发现只用不回馈有风险——上游项目一旦停更，自己的产品也要跟着出问题；
  于是开始派员工参与上游项目、赞助基金会、把自己的项目开源。
- **2018 年 6 月 4 日，微软宣布以 75 亿美元收购 GitHub，同年 10 月 26 日交易完成**：
  这件事的象征意义超过商业意义——二十年前把开源称为“癌症”的公司，如今买下了开源世界最大的协作广场。
  收购当时引发过出走潮与质疑，但 GitHub 此后继续独立运营，平台地位并未动摇。
- 同期的另一面是**收购与赞助成为常态**：IBM 收购 Red Hat、谷歌把 Kubernetes 开源后交给云原生计算基金会托管、企业纷纷成为各大基金会的白金会员。
  开源项目的“东家”越来越多是上市公司，维护者越来越多是领薪水的全职员工。
- 这种转变带来一对新的张力：
  一方面，**全职维护者让项目更可持续**：以前靠业余时间维护的关键项目，如今有人全职负责，响应更快、发布更稳。
  另一方面，**平台与资本的集中也带来新的依赖**：全世界最活跃的开源协作几乎都发生在一个商业平台上；一家公司的战略、一个基金会的资金，都可能影响项目的走向。
    - Git 的分布式设计本意是“谁也关不掉协作”，但协作的场所却比以往更集中了。
- 还有一种更安静的变化：**企业参与改变了贡献的动机结构**。早年贡献多出于兴趣与声誉，今天大量贡献是工作的一部分——员工上班时间写开源代码，绩效里算这一笔。
  志愿者与受雇者混在一起，成了开源社区的新常态。

### 3.6 从边缘到主流：开源如何变成默认选项

- **2008 年，Android 随第一款手机上市**：它以 Linux 内核为底座，把开源系统装进了数以亿计的口袋。普通人不需要知道什么是开源，就已经每天在用开源软件。
- **2010 年代，云计算把开源推上基础设施**：服务器、容器、编排工具的主流选择大多是开源项目；
  一家公司从零搭建服务，第一反应是去 GitHub 找现成的开源组件，而不是从头写。
- **协作方式本身也溢出了软件**：
  GitHub 的议题、pull request 与评审流程，被拿去写书、做法规草案、做数据分析——“公开提议、公开讨论、公开合并”成了一种通用的协作方法，而不只是程序员的工具。
- 主流化也有代价：**参与人数暴涨，但维护者没有同比例增长**。
  热门项目的维护者每天面对成百上千个 pull request 与议题，倦怠与“无人维护”成为 2010 年代后期反复出现的话题。
  开源从“缺参与者”变成了“缺维护者”，问题的重心转移了。
- 还有一个常被忽略的变化：**开源的地理版图变了**。早期的开源社区以欧美为主；
  GitHub 时代之后，来自世界各地的贡献者成为常态，时区、语言与文化差异第一次成为社区治理必须面对的日常问题，而不只是会议上的话题。

## 4. 分类

- 按治理形态分：
  个人主导：创始人或核心维护者说了算，效率高、依赖个人。
  基金会托管：Apache、Linux 基金会等模式，项目归基金会，决策按章程走。
  公司主导：企业发起并掌握方向，社区以贡献者身份参与。
  三种形态没有唯一正确的答案，同一个项目也可能随时间从一种形态过渡到另一种。
- 按参与角色分：
  使用者：用软件、提问题、报缺陷，是社区最大的人群。
  贡献者：交代码、写文档、修缺陷，贡献靠 pull request 进入项目。
  维护者：评审合并、定方向、处理纠纷，权限靠持续贡献赢得。
  同一人在不同项目里可以同时是这三种角色。
- 按协作入口分：
  议题驱动：从一个 issue 出发，讨论清楚再动手。
  pull request 驱动：先做出改动，再请人评审。
  两种入口没有高下，成熟的项目往往两者并用。

- 代码评审的礼仪与检查清单：
  评审不是“挑错”，而是“一起把改动变好”，见 [代码评审与质量实践](../16-software-engineering/03-code-review-quality.md)。
- 自动化检查接管了部分评审工作：pull request 合并前跑测试与构建的做法，见 [CI/CD 流水线设计：阶段、制品、环境晋升与回滚](../09-cloud-devops/03-cicd-pipeline-design.md)。

## 6. 限制与常见误解

- **“GitHub 就是 Git”是误解**：
  Git 是托瓦兹 2005 年写的分布式版本控制工具，GitHub 是 2008 年上线、建立在 Git 之上的商业协作平台；
  Git 可以完全离线使用，GitHub 不能。
- **“发了 pull request 就等于贡献被接受了”是误解**：pull request 只是“请评审”的提议，维护者可以合并、要求修改，也可以拒绝；
  被拒绝的改动只能留在自己的 fork 里。
- **“开源项目人人平等”是误解**：人人都能 fork、人人都能提 pull request，但合并权、发布权、方向决定权集中在维护者与治理机构手里；
  平等的是参与入口，不是决策权。
- **“行为准则只是摆设”是误解，也是部分事实**：没有执行细则的准则确实近乎摆设；但写明执行方式、并真的执行过的准则，是社区能留住不同背景参与者的关键条件。
- **“企业参与就是收编开源”是简化**：企业带来资金与全职维护者，也带来战略依赖；判断的标准不是“有没有企业参与”，而是许可证承诺有没有被遵守、治理规则有没有被架空。
- **“GitHub 时代解决了开源的可持续问题”是误解**：它解决了“怎么参与”，没有解决“谁来长期维护”；
  热门项目维护者倦怠、冷门项目无人接手，仍是今天开源世界最现实的问题。
- **本文不是操作教程**：Git 命令、GitHub 界面操作、分支策略的具体做法，见本站 02 域的版本控制文章；本文只讲这些做法背后的历史与文化。

## 7. 小结

GitHub 时代的协作文化走过四步：
邮件补丁时代靠人协作，Git 让每人手里都有完整仓库，GitHub 用 fork 与 pull request 把参与门槛降到“点一下”，治理与企业参与随后把这套协作制度化。
它没有发明开源，却让开源从少数人的手艺变成了所有人的日常——而“谁来长期维护”，是它留给下一个时代的问题。
