# 量子软件栈、模拟器与开发工具

> 本篇是 [量子计算基础](01-quantum-computing.md) 的三级展开：总览只点了 Qiskit、Cirq 等工具名，本篇把“写量子程序”这件事本身讲透——从线路描述、编译、模拟到上机提交的分层。线路语言见 [63 篇](63-qubits-gates-circuits.md)，混合工作流见 [70 篇](70-hybrid-quantum-classical.md)。本地开发工具链的一般背景（本地部署、环境管理）只链接 18 域，不复制：[本地模型部署](../18-local-ai/01-local-model-deployment.md)。

## 1. 研究问题

量子软件要解决的问题常被低估：硬件各不相同（超导、离子阱、光子、中性原子的原生门、连通图、噪声模型全不一样），而用户只想写一次程序。软件栈必须回答三个问题：第一，用什么语言描述量子程序，才能既表达算法又不绑定某台硬件；第二，如何把逻辑线路编译到某台具体硬件上（门分解、比特映射、SWAP 插入、深度优化），且编译结果的质量可度量；第三，在没有硬件（或排队太久）时，如何用经典计算机模拟量子程序，且模拟的规模边界在哪里。

这三个问题的答案构成今天的量子软件栈：SDK（写程序）→ 中间表示（OpenQASM 等）→ 编译器（ transpiler）→ 模拟器或硬件后端。理解这一分层，是“会调 SDK”与“理解量子软件”的分界。

## 2. 基础理论

- **量子线路中间表示**：量子程序的本质是“门序列 + 测量 + 经典控制流”；中间表示（如 OpenQASM）把这三者标准化，使同一程序可在不同 SDK 与硬件间交换。OpenQASM 2.0 只支持基础线路，OpenQASM 3 增加了经典控制流、脉冲级描述等能力。
- **编译（transpilation）**：把逻辑线路翻译成硬件原生门集的过程，含门分解（把任意旋转拆成原生旋转）、比特映射（逻辑比特 → 物理比特）、路由（插入 SWAP 解决连通性）、优化（门合并、约简）。编译质量直接决定物理线路深度，进而决定在含噪硬件上的成功率（见 63 篇）。
- **态矢模拟**：在经典内存里存 2ⁿ 个复振幅、按门序列更新；精确但内存指数增长——约 30 个量子比特的态矢模拟需约 16 GB 内存（2³⁰ 个复数，双精度），50 比特则需约 16 PB，实际不可行。态矢模拟是教学与小规模验证的主力，不是大规模验证的出路。
- **张量网络模拟**：把线路表示为张量网络，按一定顺序缩并；对浅层、低纠缠线路，张量网络模拟可远超态矢模拟的比特数（百比特量级的浅线路已有演示），但对深层、高纠缠线路同样指数爆炸。模拟方法的选择取决于线路结构，没有通用的“模拟任意线路”的方法。
- **噪声模拟**：在理想模拟中加入噪声模型（退极化噪声、振幅阻尼、读出误差等），预测硬件上的结果分布；噪声模拟的价值在“预估”，不在“替代硬件”——噪声模型本身来自硬件校准数据，模型不准则预估无意义。
- **误差缓解的软件侧**：零噪声外推、概率误差消除、读出误差校准等方法以 SDK 库的形式提供（见 67 篇）；它们是软件栈的一部分，但采样开销随深度指数增长，不能替代纠错。

## 3. 技术路线：软件栈的分层

### 3.1 SDK 层：写程序的入口

- **Qiskit（IBM）**：开源 Python SDK，用于写量子线路、做模拟、在 IBM 云硬件上提交任务；是今天最常见的量子编程入口之一。核心概念：QuantumCircuit（线路）、transpile（编译）、Sampler/Estimator（V2 原语，分别用于采样与期望值估计）。版本号变化快，本篇锁定的核查点见第 7 节与未完成项。
- **Cirq（Google）**：开源量子编程框架，面向含噪中规模（NISQ）电路的设计与模拟；特点是对比特布局与门时序的精细控制，适合针对特定处理器做研究。
- **PennyLane（Xanadu）**：可微分编程框架，支持 PQC 与经典神经网络的混合训练；强项在量子机器学习与变分算法（见 67 篇），且支持多硬件后端。
- **Q# 与 Azure Quantum 开发包（微软）**：Q# 是微软设计的量子编程语言，配有资源估算器（可估算算法在容错硬件上的逻辑资源）；资源估算是 Q# 的独特价值——它回答“这个算法离容错还有多远”的量化问题。
- **Braket SDK（亚马逊）**：AWS Braket 的开发包，特点是多厂商硬件聚合（超导、离子阱、中性原子等多家后端经同一接口提交）；选型逻辑是“硬件无关的提交层”，不是“某家硬件的专属工具”。
- **选型原则**：选 SDK 首先看“要用的硬件”，其次看“要做的任务”（教学选 Qiskit、硬件研究选 Cirq、变分与机器学习选 PennyLane、资源估算选 Q#）；按“哪个宣传声量大”选，是本末倒置。

### 3.2 中间表示与编译器层

- **OpenQASM**：量子汇编语言标准；OpenQASM 3 是当前版本线（以官方发布为准，见未完成项），支持经典控制流与脉冲级描述。中间表示的意义在互通：同一线路可在不同 SDK 间交换、在不同编译器上优化。
- **编译器（transpiler）**：Qiskit 的 transpiler、Cirq 的 transformer、tket（Quantinuum 的开源编译器）等；编译策略（优化级别、布局算法、路由算法）对物理深度的影响可达数倍，是软件栈里最容易被低估的一环。评估编译器时应看“同一逻辑线路在同一硬件上的编译后深度与双比特门数”，不是“支持多少种门”。
- **脉冲级控制**：Qiskit Pulse 等脉冲层接口允许用户直接定义微波脉冲形状与时序；这是硬件研究的深水区，普通算法开发不需要触及，但理解“门是脉冲的抽象”有助于理解保真度与串扰的来源。

### 3.3 模拟器层

- **态矢模拟器**：Qiskit Aer、Cirq 模拟器等；适用规模约 30 比特以内（取决于内存与并行能力），是教学与小规模验证的主力。
- **张量网络与 Clifford 模拟器**：张量网络模拟器适用于浅层线路；Clifford 模拟器（Stim 等）可高效模拟纯 Clifford 线路（见 63 篇 Gottesman–Knill 定理），是纠错研究的主力工具——表面码的校验子采样就是用 Stim 做的。
- **噪声模拟器**：Aer 等支持噪声模型注入；噪声模型需来自硬件校准，脱离校准数据的噪声模拟只是“换个参数的理想模拟”。
- **模拟器的边界**：任何经典模拟器都不能替代硬件验证——模拟器验证的是“线路逻辑正确”，硬件验证的是“线路在噪声下仍正确”；两者缺一不可，混为一谈是常见误读。

### 3.4 云接入与任务管理层

- **云硬件队列**：IBM Quantum Platform、Google Quantum AI、AWS Braket、Azure Quantum 等提供云上硬件接入；任务提交后排队、执行、返回样本，整个过程是异步的（见 70 篇混合工作流）。
- **成本与配额**：云硬件按任务、按 shots、按机型计价或配额；免费层与研究配额的范围以官方发布为准（待核实），本篇不写具体价格（价格会变动，写了即过期）。
- **本地部署对照**：量子 SDK 的本地安装与环境管理（Python 版本、依赖、虚拟环境）与经典本地部署的通用做法一致，见 18 域 [本地模型部署](../18-local-ai/01-local-model-deployment.md)，本篇不复制安装步骤，只说明“量子 SDK 的本地部分只是经典 Python 环境，真正的量子资源在云端或模拟器里”。

## 4. 系统架构：从代码到结果的完整链路

```
用户代码（Qiskit/Cirq/PennyLane/Q#）
        ↓  线路构造
中间表示（OpenQASM 3 等）
        ↓  编译（门分解、映射、路由、优化）
后端选择：模拟器（态矢/张量网络/Clifford/噪声）
        或：云硬件（超导/离子阱/中性原子/光子）
        ↓  执行（shots 次采样）
结果：比特串样本 / 期望值估计
        ↓  经典后处理（误差缓解、统计、可视化）
```

这个链路解释了三个常见困惑：为什么同一代码在不同后端结果不同（编译与噪声不同）；为什么模拟器上完美的代码上机就垮（模拟器无真实噪声）；为什么“跑通一次”不等于“算法有效”（一次采样只是分布的一个点，需要统计显著性）。

## 5. 代表性实现与开源项目

- **Qiskit（IBM，Apache 2.0）**：最广泛使用的量子 SDK；含 Aer 模拟器、transpiler 编译器、V2 原语。
- **Cirq（Google，Apache 2.0）**：硬件导向的量子编程框架；含模拟器与针对 Google 处理器的工具。
- **PennyLane（Xanadu，Apache 2.0）**：可微分量子编程框架；强项在变分算法与量子机器学习。
- **tket（Quantinuum，Apache 2.0）**：硬件无关的量子编译器；强项在编译优化，可与多家 SDK 配合。
- **Stim、PyMatching**：纠错模拟与解码工具（见 65 篇）。
- **Qualtran（Google）**：容错算法的资源估算与构件库（Cirq 的容错扩展演进而来）；面向“算法在容错硬件上要多少资源”的量化分析。
- **OpenQASM 3**：中间表示标准，非某个厂商的 SDK；版本以官方发布为准。

## 6. 关键论文与标准

- OpenQASM 3 规范（Qiskit 组织维护的开源规范，版本以官方发布为准）——量子程序中间表示的标准。
- Andrew W. Cross 等《Open quantum assembly language》（2017，https://arxiv.org/abs/1707.03429）——OpenQASM 2.0 的原始论文。
- Craig Gidney《Stim: a fast stabilizer circuit simulator》，Quantum 5, 497（2021，https://doi.org/10.22331/q-2021-07-06-497）。
- 暂无公开标准：SDK 接口、编译器基准、模拟器精度报告尚无统一标准，跨工具比较需先对齐测试线路与指标。

## 8. 技术瓶颈

- **编译质量不透明**：编译器是软件栈里最影响结果的一环，却最难评估；同一逻辑线路在不同编译策略下的物理深度可差数倍，而论文与新闻很少报告编译策略。
- **噪声模型失真**：噪声模拟的价值取决于噪声模型的准确性；真实硬件的噪声有关联性、时变性、串扰，简单噪声模型（独立退极化）会系统性低估真实误差。
- **SDK  churn**：量子 SDK 的 API 变动快（Qiskit 从 1.x 到 2.x 的 breaking change 即是一例）；教程代码过期是常态，读者应以官方文档的当前版本为准，不应照抄旧教程。
- **硬件异构的抽象泄漏**：SDK 试图屏蔽硬件差异，但连通图、原生门、噪声、排队延迟总会“泄漏”到用户层；完全硬件无关的量子编程目前不存在，用户仍需了解目标硬件的基本特性。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：SDK、编译器、模拟器已是可日常使用的工程工具（教学、小规模研究、云上提交均已常态化），但编译质量评估、噪声模型准确性、跨硬件互通标准仍在发展中；软件栈的“可用”不等于其上运行的算法“有优势”——两者要分开判断。

## 10. 未来研究问题

- **已有研究在做**：噪声感知的编译（以实时校准数据为输入的布局与路由）；编译器基准的统一（同一组标准线路在不同编译器上的深度与保真度对比）；容错资源估算的标准化（Q# 资源估算器一类工具的方法论统一）。
- **已有研究在做**：经典—量子混合编程模型的语言级支持（把“量子子程序”作为经典程序的一等公民，而非字符串拼接的线路）。
- **本文推测**：未来量子软件栈的竞争焦点可能从“SDK 功能多少”转向“编译质量与资源估算精度”——因为硬件差异收敛后，决定用户体验的是“同一算法在谁家跑得更深、更准、更省”；检验标准是：编译器与资源估算器是否成为硬件方公开竞争的指标。
