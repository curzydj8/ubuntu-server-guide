# 编译器正确性

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章。总览讲“形式化方法整体”；本篇讲它最容易被忽略的一环——编译器。源码验证得再严密，如果编译器把程序编错了，运行的二进制与被验证的源码就不是同一个程序。编译器正确性要回答的是：编译过程是否保持程序语义？即源程序的每个可观测行为，在目标程序中都对应地出现（或在源程序本身出错的前提下被合理改善）。

## 1. 研究问题

现代编译器做几十种优化：常量传播、死代码消除、寄存器分配、指令调度、循环变换。每一种变换都可能引入 bug，而且这类 bug 极难调试——开发者看到的是源码，跑的是二进制，中间隔着编译器。更棘手的是，编译器 bug 具有“传染性”：同一个编译器编出的所有程序都可能带上同一个错。形式化验证的源码结论要延伸到可执行产物，必须补上编译这一环；否则验证链在最后一公里断开。编译器验证的难点在于规模：要为源语言、每种中间语言、目标语言各自建立形式语义，再为每个编译遍证明语义保持。

## 2. 基础理论

- **形式语义**：操作语义给“程序执行一步是什么意思”下定义；编译器验证需要源语言、中间语言、目标语言各自的形式语义，否则“语义保持”无从陈述。
- **模拟关系（simulation）**：源程序的一步执行对应目标程序的若干步执行（前向模拟），或反之（后向模拟）；CompCert 的正确性定理以“目标行为是源行为的改善”为核心表述——对有定义行为的程序，行为精确保持；对会出错的源程序，编译结果可以“改善”它（如把出错执行替换为更长的执行前缀），但不能凭空产生源程序没有的行为。
- **语义保持与行为改善**：编译器正确性的标准表述不是“目标代码与源代码逐行对应”，而是“目标程序的可观测行为集合被源程序的可观测行为集合所约束”；可观测行为通常指输入输出、终止与发散，不含执行时间等非语义属性。
- **翻译验证（translation validation）**：不证明“编译器对所有输入都对”，而是对每一次具体编译结果，用一个已验证的检查器验证“这次输出确实对应这次输入”；启发式部分可以不被信任，检查器必须被信任。这是用“验证检查器”替代“验证编译器”的务实路线。

## 3. 技术路线

- **全编译器验证路线**：在证明助手中从头实现编译器并证明每个遍的语义保持，CompCert 是标杆；结论最强，工作量最大。
- **翻译验证路线**：编译器本身不被信任，每次编译产物由已验证的检查器逐一验证；寄存器分配等启发式强的遍尤其适合此路线——启发式可以猜，检查器负责验。
- **中间语言验证路线**：只验证某一段编译链（如从验证语言到 C 中间语言），与前后段组合成完整链；CertiCoq（Coq 程序到 CompCert 的 Clight 语言）即属此路线，与 CompCert 组合可形成从规约到汇编的长链。
- **特定遍验证路线**：只验证最容易错、最关键的遍（如寄存器分配、指令选择），其余遍靠测试；是资源有限时的务实取舍，但结论必须写明“哪些遍已验证、哪些遍未验证”。

## 4. 系统架构

一个已验证编译器通常由以下部分组成：

- **前端**：源语言解析与语义建模，把源码翻译成第一种中间表示；源语言语义的忠实度决定整个证明的起点是否可信。
- **中间语言链**：一系列中间表示，每种有自己的形式语义；遍与遍之间用模拟关系连接，模拟关系可传递，最终拼成端到端的语义保持定理。
- **后端**：目标体系结构相关的遍（指令选择、寄存器分配、汇编生成）与汇编语义模型；不同目标架构需要各自的后端证明，结论不自动跨架构。
- **可信基**：证明助手内核、形式语义定义、汇编器与链接器（通常不在证明内）、硬件语义假设；报告“已验证编译器”时必须同时报告可信基，否则是夸大。

## 5. 代表性实现与开源项目

- **CompCert**：用 Coq/Rocq 实现的、经形式验证的 C 编译器，编译 C 语言的一个大子集到 PowerPC、ARM、RISC-V、x86 等目标；其正确性定理为机器检查的语义保持证明，证明规模约十万行 Coq 代码量级（量级表述，精确行数以官方发布为准，待核实）。CompCert 于 2021 年获 ACM 软件系统奖（以官方发布为准，待核实）。
- **CertiCoq**：经验证的、从 Coq 语言到 CompCert 的 Clight 语言的编译器，与 CompCert 组合可形成从 Coq 程序到汇编的验证链。
- **CakeML**：经验证的 ML 语言编译器，在 HOL 中实现并证明，目标包括 x86-64 与 ARM 等；具体目标清单以官方发布为准（待核实）。
- **Jasmin、Vélus**：分别面向密码学实现与同步数据流语言（Lustre 风格）的经验证编译器方向，具体覆盖范围以官方发布为准（待核实）。
- **LLVM 的验证研究**：对工业编译器做部分验证或翻译验证的研究工作仍在进行中；LLVM 本身不是已验证编译器，不能把“研究进展”写成“LLVM 已验证”。

## 6. 关键论文与标准

- Leroy，《Formal Verification of a Realistic Compiler》，Communications of the ACM——CompCert 的系统性论述。
- Leroy，《Formal Verification of a Realistic Compiler》之外的 CompCert 技术报告与手册，具体版本以官方发布为准（待核实）。
- 暂无统一标准：编译器正确性没有行业标准定义其证明义务；功能安全标准对编译器工具鉴定的要求见[安全关键软件](131-safety-critical-software.md)，那是“工具鉴定”而非“编译器语义证明”。

## 7. 当前实验结果

本节不转载“比 GCC 快多少、慢多少”的性能数字：编译器性能对比高度依赖基准测试集、优化级别与目标架构，脱离条件不可比较。只写经核查的定性结论：CompCert 的公开论述称其生成的代码性能与优化编译器具有可比性（具体基准与条件以论文原文为准，待核实）；它已被用于对正确性要求极高的场景（如航空领域的部分软件编译，具体项目细节以官方发布为准，待核实）。“已验证”不等于“最快”，也不等于“支持全部 C 语言特性”——CompCert 支持的是 C 的一个大子集，不支持的特性（如某些未定义行为依赖、部分语言扩展）需要开发者注意。

## 8. 技术瓶颈

- **语义建模成本**：为 C 这样充满未定义行为与实现定义行为的语言建立忠实的形式语义，本身就是一项大工程；语义与语言标准文本之间的偏差是潜在的信任缺口。
- **优化遍的证明负担**：每个优化遍都要证明模拟关系，激进优化的证明尤其困难；这就是为什么已验证编译器的优化激进程度通常低于工业编译器。
- **目标架构扩展成本**：每个新目标架构需要新的后端语义与证明，架构越多，维护成本越高。
- **语言子集限制**：已验证编译器通常只支持源语言的子集；真实项目若用了子集外的特性，要么改代码，要么放弃验证结论，迁移成本真实存在。
- **可信基残留**：汇编器、链接器、硬件语义、证明助手内核本身仍在可信基内；编译器验证缩小了信任缺口，没有消灭它。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：CompCert 等已验证编译器已有真实部署与可复查证明，但语言子集、优化激进程度与目标架构覆盖仍限制它替代工业编译器的范围。

## 10. 未来研究问题

- **已有研究在做**：把验证扩展到更多语言特性与目标架构、把翻译验证接入 LLVM 等工业编译器的工作流。
- **已有研究在做**：验证编译器与验证工具链的组合——源码验证（VST、Frama-C）+ 已验证编译（CompCert）+ 已验证运行时的端到端链。
- **本文推测**：已验证编译最可能先以“关键模块专用编译”的形态普及（安全关键代码用 CompCert 编，普通代码用工业编译器编），而不是全量替代；检验标准是安全关键项目的构建流程中是否出现“关键目标用已验证编译器”的分流配置。
