# GPU 运行时和异构资源调度

## 1. 研究问题

CPU 的调度问题操作系统已经研究了几十年：抢占、优先级、公平性、隔离，都有成熟答案。GPU 不一样：它最初是图形加速器，后来变成 AI 计算的主力，但调度语义长期停留在“一个进程独占整卡、跑完再换下一个”的粗粒度水平。现实需求却相反：一张卡很贵，多数推理任务用不满整卡；多租户要共享，共享要隔离；训练要抢占，推理要延迟保证。GPU 运行时与异构资源调度要回答的问题是：能不能像调度 CPU 一样调度 GPU——共享、隔离、抢占、公平，四者兼得？以及当 NPU、FPGA、DPU 等加速器都加入时，调度器能不能统一看待它们？

## 2. 基础理论

- **GPU 执行模型**：核函数（kernel）在流式多处理器（SM）上以线程块为单位执行；显存、SM、带宽是三类主要资源，瓶颈常在显存而非算力。
- **共享的三档隔离**：时间分片（轮流用整卡，无显存隔离）、进程级并发（MPS，多进程核函数真正并行，显存共享）、硬件分区（MIG，硅片级切分，显存与算力均隔离）；隔离越强，利用率弹性越差。
- **运行时与驱动的分工**：CUDA、ROCm 等运行时提供编程模型与库，驱动负责设备管理与调度；Kubernetes 设备插件把 GPU 暴露为可调度资源，但默认是整卡分配。
- **异构统一调度的难点**：不同加速器的编程模型、内存模型与性能特征不同，统一抽象要么太粗（只按“卡”计数）、要么太细（暴露每种硬件细节，调度器无法通用）。

## 3. 技术路线

- **硬件分区路线（NVIDIA MIG）**：Ampere 架构起引入，A100、H100 等数据中心卡可切为最多 7 个硬件隔离实例，每实例有固定显存、缓存与 SM 分区，对操作系统呈现为独立 CUDA 设备；重配需销毁重建实例，会中断运行中负载；支持型号以官方发布为准。
- **进程并发路线（NVIDIA MPS）**：多进程服务让多个 CUDA 进程的核函数真正并行执行，共享同一 GPU 上下文；地址空间隔离，但致命故障的 containment 有限，不适合强隔离的多租户场景。
- **时间分片路线**：驱动或设备插件让多任务轮流独占整卡，任何 GPU 都可用；无显存隔离，上下文切换有开销，适合开发测试与低流量场景。
- **虚拟化路线（vGPU、SR-IOV）**：把 GPU 切分给多个虚拟机，兼顾隔离与共享；许可、驱动与硬件支持条件以官方发布为准（待核实）。
- **Kubernetes 调度路线**：NVIDIA 设备插件、GPU Operator、动态资源分配（DRA）等，把 GPU 从“整卡计数”推向“分片、拓扑感知、按需分配”；调度策略（装箱、打散、拓扑亲和）直接影响训练任务的通信效率。
- **异构统一路线**：oneAPI、ROCm、OpenCL、Triton 等跨硬件编程模型，以及调度器对 CPU/GPU/NPU 的统一资源视图；与本站异构计算文章（[异构计算](77-heterogeneous-computing.md)）交叉，统一调度仍在演进中。

## 4. 系统架构

典型 GPU 调度栈的组成部分：

- **应用与框架层**：PyTorch、TensorFlow、vLLM 等框架发出核函数与显存申请；框架的显存缓存策略直接影响共享效果。
- **运行时层**：CUDA/ROCm 运行时、驱动、MPS 服务、MIG 配置工具；负责核函数发射、显存管理与设备分区。
- **容器与设备插件层**：容器运行时注入 GPU 设备，Kubernetes 设备插件/DRA 把 GPU 资源广告给调度器，调度器按资源请求做放置。
- **调度器层**：集群调度器（Kubernetes Scheduler、Slurm、Volcano 等）做节点与设备选择，考虑拓扑（NVLink、PCIe、机架）与亲和性；训练任务的放置错误可能让通信走慢速链路，抵消算力收益。
- **可观测层**：DCGM 等工具采集利用率、显存、功耗与故障；没有可观测性，共享策略就是盲调。

## 5. 代表性实现与开源项目

- **NVIDIA CUDA 运行时与驱动**：GPU 计算的事实标准运行时，MIG、MPS、时间分片均出自该生态（支持型号与版本以官方发布为准）。
- **AMD ROCm**：AMD 的 GPU 计算平台，HIP 编程模型，面向 Instinct 系列加速器；生态覆盖以官方发布为准（待核实）。
- **NVIDIA Kubernetes 设备插件与 GPU Operator**：把 GPU 暴露为 Kubernetes 可调度资源，管理驱动、MIG 配置与设备发现。
- **Kubernetes DRA（动态资源分配）**：新一代资源调度 API，支持结构化参数与更细粒度的设备声明；成熟度与版本以官方发布为准（待核实）。
- **Volcano、KAI Scheduler 等**：面向 AI 与批处理的 Kubernetes 调度增强，支持 gang 调度、队列与公平共享；选型以官方发布为准（待核实）。
- **Slurm**：高性能计算集群的作业调度器，GPU 感知调度在 HPC 场景的长期实践。

## 6. 关键论文与标准

- CUDA、ROCm、MIG、MPS 的编程与配置文档见 NVIDIA、AMD 官方文档（版本以官方发布为准）。
- Kubernetes 设备插件与 DRA 见 Kubernetes 官方文档（版本以官方发布为准）。
- 暂无统一的异构调度标准：各厂商的分区、共享与调度接口互不兼容，跨厂商统一调度仍是研究与社区演进中的问题。

## 7. 当前实验结果

本节不写吞吐与利用率数字：GPU 共享的收益高度依赖模型、批量、并发数与硬件型号，脱离条件的数字不可比；厂商与第三方测评的“提升多少倍”本篇一律不采信。只写定性结论：MIG 在多租户推理场景的隔离价值已确立；MPS 在同租户并发推理场景的利用率价值已确立；Kubernetes 整卡分配仍是默认，但分片与 DRA 正在改变默认；跨厂商异构统一调度尚未成熟，生产系统大多仍按厂商分治。

## 8. 技术瓶颈

- **抢占缺失**：GPU 核函数一旦发射，抢占粒度粗、代价高；长任务阻塞短任务是推理延迟抖动的主要来源。
- **显存隔离与超分**：时间分片与 MPS 下显存共享，一个任务的显存膨胀会影响邻居；显存超分与回收机制不如 CPU 内存成熟。
- **故障 containment**：MPS 与时间分片下，一个进程的致命故障可能波及同卡其他进程；强隔离只能靠 MIG 或虚拟化，代价是弹性。
- **拓扑感知**：多卡、多节点训练的通信拓扑（NVLink、InfiniBand、机架）对性能影响大，调度器必须懂拓扑，否则放置错误代价高。
- **异构抽象**：CPU、GPU、NPU 的资源单位、性能模型与故障语义不同，统一调度器容易退化成“按厂商分开调度”的拼盘。

## 9. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：CUDA/ROCm 运行时、MIG/MPS/时间分片、Kubernetes GPU 调度均已在生产 AI 集群中大规模使用，GPU 调度作为工程实践已经成熟；未成熟的是细粒度抢占与跨厂商统一调度，不是 GPU 调度本身。

## 10. 未来研究问题

- **已有研究在做**：GPU 抢占（核函数级、线程块级）、推理延迟保证的调度算法、显存超分与压缩、DRA 的成熟化。
- **已有研究在做**：异构统一调度（CPU/GPU/NPU 的统一资源模型）、能效感知的调度（功耗封顶下的性能分配）。
- **本文推测**：GPU 调度可能从“集群调度器管卡”走向“运行时管核函数”（框架与运行时协同做细粒度共享）；检验标准是框架侧共享机制是否进入生产默认配置。
- **本文推测**：机密计算与 GPU 共享的结合（多租户 + 显存加密隔离）可能成为下一代云 GPU 的卖点；检验标准是云厂商机密 GPU 实例的普及程度。
