# 内存池化与 CXL

本篇是[新型存储与互连总览](09-new-storage-interconnect.md)中 CXL 方向的展开与讲透篇：总览只讲 CXL 的结构定位（扩展容量、不替代 HBM 带宽），本篇只讲内存池化与 CXL 这一条三级主题——CXL.mem、扩展、池化、共享、分层管理与延迟代价。总览与后续文章如需提及 CXL，只链接本篇，不重复本篇细节。

## 1. 研究问题

服务器内存面临一个结构性浪费：内存是按“单台服务器峰值需求”采购、按“单台服务器”锁死的——A 服务器内存闲置时，B 服务器可能正因内存不足而拒绝任务或把数据换出到闪存。云厂商的公开分析中，内存闲置（stranded capacity）被反复提及为成本问题：算力有空闲，只因内存先耗尽。

内存池化要回答的问题是：能不能把内存从“每台服务器的固定资产”变成“机架/集群级的可调配资源”——需要时分给需要的服务器，不需要时收回？而 CXL 要回答的配套问题是：用什么互连才能让“远端内存”仍可用普通 load/store 指令访问，而不是退化成“网络存储”？

CXL 的答案与 RDMA 的区别正在于此：RDMA 是“显式消息/远程访问”，应用或中间件要感知远端；CXL.mem 是“内存语义”，主机把远端内存映射进自己的物理地址空间，用普通 load/store 访问。这是“一层语义”的区别，决定了软件改造成本与延迟量级都不同。

## 2. 基础理论

- **CXL（Compute Express Link）**：建立在 PCIe 物理层上的开放互连标准，三种子协议——CXL.io（类似 PCIe 的 I/O，用于发现、配置、DMA）、CXL.cache（设备可缓存主机内存）、CXL.mem（主机可访问设备上的内存）；内存池化主要用 CXL.mem。
- **Type 3 设备**：CXL 内存扩展设备，只提供 CXL.mem（与 CXL.io），本身没有计算单元；主机像访问本地内存一样访问它上面的 DDR 内存，代价是更高的延迟与更低的带宽。
- **内存扩展（expansion）**：一台主机接一块 CXL 内存扩展卡，获得超出本机内存插槽的容量；这是最简单的形态，无池化、无共享，延迟代价最小。
- **内存池化（pooling，CXL 2.0）**：多台主机从一个共享的物理内存池中动态分配容量；关键机制是多逻辑设备（Multi-Logical Device，MLD）——一块物理内存设备切分为多个逻辑设备（公开资料常述为可达 16 个分区，另有 Fabric Manager 占用的逻辑设备），每个逻辑设备在同一时刻只属于一台主机，由 Fabric Manager（FM，结构管理器）分配与回收。2.0 的池化是“分区式”而非“共享式”：容量可调配，但同一块内存同一时刻只被一台主机独占，不存在多主机同时读写同一地址的相干性冲突。
- **内存共享（sharing，CXL 3.x）**：多台主机同时读写同一块内存区域，硬件维护缓存一致性；代表机制是全局结构附加内存（Global Fabric Attached Memory，GFAM）与基于端口的路由（Port-Based Routing，PBR）。共享比池化难一个量级：需要目录/监听过滤式一致性、宿主代理（home agent）裁决冲突，Fabric Manager 的角色也从“分配容量”扩展为“管理共享访问”。
- **分层内存（tiered memory）**：本地 DRAM、 CXL 内存、闪存按速度分层；操作系统把热页放快层、冷页放慢层。分层的收益是容量与利用率，代价是页迁移开销与“放错层”的延迟惩罚。
- **NUMA 视角**：CXL 内存常以“无 CPU 的 NUMA 节点”形式暴露给操作系统；应用与调度器若不感知 NUMA，会把热数据误放到慢节点上，分层收益会被抵消。

## 3. 技术路线

按 CXL 规范演进（版本与功能以 CXL 联盟官方发布为准，总览已列 1.0/2.0/3.0/4.0 的发布时间，本篇补 3.x 的细分）：

- **CXL 1.x 直接扩展路线（2019 年）**：单台主机直连 Type 3 设备，做内存扩展；解决“单机容量不够”，不解决“跨机调配”。
- **CXL 2.0 池化路线（2020 年）**：引入 CXL 交换机与 MLD 池化，Fabric Manager 分配逻辑设备；解决“容量跨机调配”，但仍是分区独占，不是真共享。公开报道中，2.0 池化是目前部署描述中最完整的形态。
- **CXL 3.0/3.1/3.2 结构与共享路线（2022 年 8 月 / 2023 年 11 月 / 2024 年 12 月）**：3.0 基于 PCIe 6.0、速率翻倍至 64 GT/s（公开表述为“速率翻倍、延迟不高于 2.0”），引入多级交换、结构（fabric）与内存共享；3.1 加入全局集成内存（GIM）概念下的主机间通信与 Fabric Manager API；3.2 侧重设备可管理性、可靠性、可观测性与热页监控（如热页监控单元，Hotness Monitoring Unit / CXL Hotness 相关机制）。规范发布不等于产品齐全：多级 PBR 结构、真共享的量产部署进度以厂商与云厂商官方发布为准（待核实）。
- **CXL 4.0 路线（2025 年 11 月）**：规范层面速率再翻倍（公开表述为 128 GT/s）、捆绑端口等；处于规范与 IP 阶段，产品落地时间以官方发布为准（待核实），本篇不写量产时间表。
- **软件分层路线（与硬件版本平行）**：操作系统与运行时感知分层——热页识别（硬件计数、采样、控制器内遥测）、页迁移策略、NUMA 感知调度；这是池化收益兑现的另一半，硬件不解决软件问题。

## 4. 系统架构

一个 CXL 内存池化系统由五部分组成：

- **主机与根端口**：CPU 的 CXL 根端口发出 CXL.mem 请求；根复合体（Root Complex）常是带宽瓶颈之一，公开的 CXL 到 GPU 传输分析中曾指出根复合体限制了聚合带宽——具体数值依赖平台，不宜跨平台引用。
- **CXL 交换机**：连接多台主机与多台内存设备；交换机不是免费的——公开实测综述中，交换机本身贡献的延迟量级在数百纳秒讨论中被单独列出（见第 7 节），多级交换的延迟更高。
- **Type 3 / MLD 内存设备**：设备上的控制器 + DDR 内存；控制器实现（硬化 ASIC vs FPGA 软核）直接影响延迟与带宽，是“同规范、不同性能”的主要来源。
- **Fabric Manager（控制面）**：分配/回收逻辑设备、管理共享访问、编程交换机路由；控制面故障与数据面故障是两类不同的故障域，FM 本身的高可用设计是池化系统必须回答的问题。
- **分层管理软件**：操作系统 NUMA 节点管理、热页监控、页迁移策略；公开实践中常见做法是把 CXL 节点设为可移动区（ZONE_MOVABLE），使页表、slab 等不可移动内核结构不落入慢层——这是“慢层只放可迁移数据”的工程护栏，不是规范强制。

## 7. 当前实验结果

本节的数字全部来自公开实测综述的转述，不是本篇的实测（本地无硬件可测）；数字高度依赖设备实现、拓扑、负载与带宽利用率，脱离条件没有可比性，只读“量级与结构”：

- **延迟量级（P50 负载到可用延迟，64 字节随机读，公开综述转述的 Octopus 类实测口径）**：本地 DDR5 约 115 纳秒量级；直连 CXL 扩展设备约 230–270 纳秒；多端口 CXL 设备约 260–300 纳秒；经 CXL 交换机约 490–600 纳秒（其中交换机本身被归因至少 220 纳秒）；经 RDMA 到另一台服务器约 3,550 纳秒。结构结论是：CXL 远近于本地 DRAM、远优于 RDMA 与闪存（企业级 SSD 随机读中位数约 80 微秒量级），但交换机与多级结构会显著抬高延迟——“池化”不是“免费容量”，交换是明码标价的延迟。
- **另一组口径（Meta 生产部署的公开转述）**：本地 DDR5 空闲延迟约 130 纳秒、CXL 约 250 纳秒；60% 带宽利用率下本地约 234 纳秒、CXL 约 372 纳秒（延迟惩罚约 60%）。两组口径的绝对值不同（平台、设备、负载不同），但结构一致：CXL 延迟约为本地的 1.5–2 倍量级，且随负载加重而拉大。
- **设备实现差异（MICRO 2023 类表征的公开转述）**：同规范的三款设备，相对远端 DDR5 的负载延迟分别为约 +35%（硬化 ASIC + DDR5）、约 2 倍（硬化 ASIC + DDR4）、约 3 倍（FPGA 软核 + DDR4）；带宽相对本地 DRAM 的比例在公开表征中从不足 10% 到约 80% 都有报道。结论是：不能用“CXL 延迟”一个数字概括所有产品，控制器实现是第一变量。
- **带宽瓶颈**：公开表征中 CXL 带宽在少量线程（4–8 线程量级）即饱和，而本地/远端 DRAM 可扩展到 20–28 线程量级；CXL 链路带宽远低于封装内 HBM 带宽（见总览），这是 CXL 不适合带宽敏感热数据层的结构原因。
- **适用负载边界（按负载的结论，不是通用结论）**：公开分析中常见的分界是——热足迹（hot footprint）占比低、大量页面长期闲置（如公开转述中 75% 以上页面闲置超 4 秒、中位闲置达数十分钟量级的缓存与广告类负载）时，CXL 分层收益明显；热足迹占比高、延迟敏感的负载（如高频交易、延迟敏感的数据库热集）不适合把热数据放 CXL 层。混合部署（本地 DRAM 占 60–80%、CXL 占 20–40%）被公开讨论为常见的折中比例，但这仍是“讨论中的经验值”，不是规范或基准结论，须以自身负载实测为准。

## 8. 技术瓶颈

- **延迟瓶颈**：CXL 内存延迟高于本地 DRAM，且经交换机、多级结构、负载加重后进一步拉大；对延迟敏感的负载，CXL 只能做容量层，不能做热数据层——这是适用边界的第一条。
- **带宽瓶颈**：单链路带宽与根复合体瓶颈限制了 CXL 层的聚合带宽；带宽敏感负载（AI 推理的热权重、HPC 的热数据）不适合 CXL 层。
- **分层软件瓶颈**：热页识别、页迁移、NUMA 感知调度仍在演进；放错层的代价（迁移流量吃掉本地带宽、延迟抖动）可能抵消容量收益；控制器内热页遥测（如 3.2 的热页监控方向）是被寄望的降低管理开销的路径，但效果以实测为准。
- **共享一致性瓶颈**：3.x 的真共享需要硬件一致性裁决，复杂度与验证成本远高于 2.0 的分区池化；共享的量产成熟度低于池化，不能把 3.x 规范的存在等同于共享已可用。
- **故障域与隔离瓶颈**：池化后一台内存设备故障影响多台主机，Fabric Manager 故障影响分配能力；多租户共享下的隔离（容量、带宽、故障）与安全（CXL IDE 等机密计算方向）仍是待完善点。
- **标准与产品时差瓶颈**：CXL 4.0 等新规范发布后，控制器、交换机、设备与主机支持的齐全需要时间；规范版本不等于可采购的产品版本，采购决策须按“主机 + 交换机 + 设备 + FM 软件”四件套齐全与否判断。
- **成本**：控制器、交换机、FM 软件与运维成本都会传导到系统总价；“省下的内存采购”须减去“新增的互连与管理成本”才是净收益，公开讨论中对池化净收益的质疑（HotNets 2023 的反方观点）正是从这一账算起的。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：CXL 内存扩展已有标准、产品与生产级部署分析，2.0 池化已有部署描述，但延迟、带宽、分层软件与 3.x 真共享的成熟度仍在解决中，尚未达到“内存可像计算一样自由池化且无感知代价”的成熟度。

## 10. 未来研究问题

- **已有研究在做**：更低延迟的控制器与交换机实现、分层内存管理的自动化（热页遥测、迁移策略）、多主机共享的一致性协议与隔离、Fabric Manager 的高可用与标准化 API。
- **已有研究在做**：CXL 在 AI 场景的定位——KV 缓存等容量敏感、延迟容忍度相对较高的负载，是否比通用内存池化更先兑现价值；公开的 CXL KV 缓存研究（如 Beluga 类工作）属于这一方向，其加速倍数以论文原文为准（待核实）。
- **本文推测**：CXL 的价值可能先在“容量弹性”（按需扩容、跨主机调配、避免内存闲置）而非“性能”上兑现，与总览的推测一致；检验标准是云厂商是否先把 CXL 用于容量弹性场景而非性能敏感场景。
- **本文推测**：分层管理的胜负手可能不在操作系统，而在控制器内遥测 + 硬件辅助迁移；检验标准是未来分层方案是否普遍把热页跟踪从软件采样转向控制器内硬件遥测。
