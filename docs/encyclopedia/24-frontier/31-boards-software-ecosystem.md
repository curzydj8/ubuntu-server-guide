# 开发板、软件生态与发行版支持

> 本篇是 [RISC-V 生态](04-riscv-ecosystem.md) 的三级专题，只讲开发板、软件生态与发行版支持这一分支：有哪些真实存在的开发板、它们各用什么 SoC、启动与内核支持是怎样的、以及各发行版对 RISC-V 的支持范围。生态总貌与标准组织归总览篇，开源核与 EDA 工具链归 [30 篇](30-open-chip-eda.md)，本篇不重复；本篇不做选购推荐——消费级选购方法归 01 域硬件选型文章。

## 1. 研究问题

一颗 RISC-V 芯片“能用”与一块开发板“能用”是两回事。开发板要回答的问题是：拿到一块板子之后，能不能装上一个通用发行版、连上网络、跑起常用软件、并在出问题时找到可升级的内核与文档？这个问题的答案在 RISC-V 世界里因板而异：同一发行版的名字，装在不同板子上的实际体验可能完全不同，差别往往不在发行版本身，而在板子的启动链、设备树与内核支持是否进了上游。

这个问题之所以要单列一篇，是因为 RISC-V 开发板正处在“厂商镜像”向“通用发行版”过渡的阶段。早期的大多数板子只能跑厂商定制的镜像（BSP 内核、旧内核版本、定制 U-Boot）；通用发行版的支持范围扩大，意味着用户不再被绑在某一家厂商的镜像更新节奏上。判断一块板子“生态好不好”，看的正是它离通用发行版还有多远，而不是它的纸面参数。

## 2. 基础理论

- **开发板与单板机（SBC）**：把 SoC、内存、存储接口与外设接口做在一块板上的开发平台。SoC 决定指令集子集与性能上限，板子决定接口与散热；谈“板子支持”时必须同时说清 SoC 与板名，只说板名或只说 SoC 都会丢信息。
- **启动链**：典型 RISC-V Linux 板子的启动顺序是：片上 ROM → SPL/一阶段引导 → U-Boot → OpenSBI（RISC-V 的 Supervisor Binary Interface 实现，提供 S 态与 M 态之间的标准接口）→ Linux 内核 → 发行版用户空间。链上任何一环缺了板级支持，通用发行版就装不上。
- **设备树（Device Tree）**：描述板上硬件（CPU、外设地址、中断、时钟）的数据结构，内核靠它认硬件。设备树是否进了上游内核，是“通用发行版能不能直接支持这块板”的硬指标。
- **厂商内核（BSP 内核）与上游内核**：厂商基于某一旧内核版本打补丁、加板级支持后发布的内核叫 BSP 内核；上游内核是 kernel.org 主线。BSP 内核往往功能全但版本旧、升级慢；上游内核版本新但可能缺某块板的驱动或外设支持。用户在两者之间选，实际是在“功能全”与“可长期升级”之间选。
- **Profile（兼容性基线）**：见总览篇。开发板语境下的关键分界是 RVA20 与 RVA23：较老的板子多为 RVA20 级实现，较新的 SoC（如 SpacemiT K3）面向 RVA23；发行版提高最低基线时，老板子会被留在旧版本发行版上（见第 5 节），这是本篇最重要的结构性事实。
- **发行版支持的三种形态**：官方正式架构支持（进正式版本、有安全更新）、移植（ports）支持（有包但未进正式版本或支持程度有限）、社区/第三方镜像（厂商或爱好者自建）。三者不可混为一谈，本篇逐项区分。

## 3. 技术路线

让一块 RISC-V 板子跑起 Linux，有三条路线，做法与代价不同：

- **厂商镜像路线**：用厂商提供的预装镜像（通常是定制 Debian、Yocto 或厂商发行版），开箱功能最全，GPU、NPU、多媒体等外设支持往往只在这条路上有。但代价是内核版本与软件源被厂商锁定，安全更新与升级节奏取决于厂商。
- **通用发行版路线**：直接装 Debian、Ubuntu、Fedora 等通用发行版的 riscv64 镜像。代价是板级支持必须已进上游（设备树、驱动、U-Boot），且发行版的最低 profile 必须与板子匹配；收益是与 x86/ARM 相同的包管理与安全更新机制。
- **模拟与交叉路线**：在 x86/ARM 机器上用 QEMU 模拟 RISC-V 系统，或用交叉工具链编译 RISC-V 程序而不上板。这条线适合“先学软件、后上硬件”，不依赖任何一块板子；但模拟不能验证板级外设、功耗与真实性能，QEMU 的 CPU profile 参数也必须与目标发行版的最低基线匹配。

三条路线不是对立关系：多数开发者的实际路径是“先用厂商镜像确认板子能工作，再尝试通用发行版，最后把长期运行的系统落在通用发行版上”。本篇的发行版表格（第 5 节）讲的是第二条路线的现状，第一条路线的镜像细节以各厂商发布为准（待核实）。

## 4. 系统架构

一块 RISC-V 开发板跑起通用发行版，需要以下各层都就位，缺一层就表现为“装不上”或“装上缺功能”：

- **硬件层**：SoC（含 CPU 核、GPU、视频编解码、NPU 等）、内存、存储（microSD、eMMC、NVMe）、网络与 USB 等接口；GPU 与 NPU 的驱动是否开源、是否进上游，决定了桌面与 AI 功能的可用程度。
- **固件与引导层**：片上 ROM、SPL、U-Boot、OpenSBI。U-Boot 的板级支持是否进上游，是通用发行版安装镜像能否直接引导的关键。
- **内核层**：上游内核的板级支持（设备树、时钟、电源、网络、存储驱动）与发行版内核的配置。内核缺驱动时，现象往往是“系统能进 shell，但网口、USB 或显示不工作”。
- **发行版层**：riscv64 的软件包仓库、安装镜像、启动镜像与安全更新。发行版层只负责“软件包能不能装”；板级硬件问题不在这一层解决。
- **应用层**：桌面环境、浏览器、开发工具、容器等。应用层的问题常被误读为“板子不行”，实际可能是“该应用尚未针对 RISC-V 优化”或“依赖的库尚未移植”，需要分层定位。

这套分层的工程含义是：排障时先定位在哪一层——进不了引导是固件层，进系统缺外设是内核层，装不上软件包是发行版层；混在一起笼统说“不支持”会误导后续动作。

### 5.2 软件生态：工具链、操作系统与应用

- **工具链**：GCC 与 LLVM 均已支持 RISC-V，是写 RISC-V 软件最常用的两条编译路线；交叉编译（在 x86/ARM 上编 RISC-V 程序）与原生编译（在 RISC-V 板子上直接编译）都存在，具体扩展支持以各工具链发布说明为准。
- **操作系统内核**：Linux 内核主线支持 RISC-V 64 位；FreeBSD 与 OpenBSD 亦有 RISC-V 移植，支持程度与 tier 划分以各自官方发布为准。QEMU 提供 RISC-V 系统模拟，Spike 是 RISC-V 官方参考模拟器。
- **嵌入式系统**：Zephyr、FreeRTOS 等实时系统支持部分 RISC-V 微控制器；与通用发行版是两条线，不可混用“支持”一词。
- **语言与运行时**：Go、Python、Rust、Node.js 等主流语言运行时已有 riscv64 相关支持，但具体版本与预编译包的覆盖程度因发行版而异；缺预编译包时往往需要从源码编译，这是 RISC-V 开发的常见额外成本。
- **容器与虚拟化**：Docker 等容器工具在 RISC-V 上的可用性取决于发行版的包与内核配置；虚拟化（KVM）支持取决于 SoC 是否实现虚拟化扩展与内核支持，不能默认所有板子都可用。

### 5.3 发行版支持范围

下表只写经核查的定性范围，逐板、逐版本的镜像清单以各发行版官方发布为准（待核实）：

- **Debian**：Debian 13 “Trixie”是首个正式支持 64 位 riscv64 架构的稳定版本；其硬件基线为 RV64GC、lp64d ABI，覆盖面比以 RVA23 为基线的发行版更宽，老板子（如 JH7110 板）仍在覆盖讨论内。具体支持的板子清单与安装镜像见 Debian RISC-V 官方文档。
- **Ubuntu**：Ubuntu 24.04 LTS 支持 RVA20 级板子（包括 VisionFive 2、Milk-V Mars CM、Star64 等，见 Canonical 的板级支持说明）；自 Ubuntu 25.10 起，最低基线提高到 RVA23，非 RVA23 硬件留在 24.04 LTS 通道；Ubuntu 26.04 LTS 定位为首个以 RVA23 为统一基线的长期支持版本。板子与版本的对应关系必须逐项查 Canonical 的 RISC-V 镜像目录，不可凭“装过 Ubuntu”推断新版本也能装。
- **Fedora**：Fedora 维护 RISC-V 移植，Fedora 42 前后已有面向支持板子、QEMU 与容器的 RISC-V 镜像；其板级支持列表（包括 BPI-F3、Lichee Pi 4A、Milk-V Mars、Milk-V Jupiter 等）由 Fedora RISC-V 特别兴趣小组维护，具体版本与镜像类别（Server、Container、Cloud 等）以 Fedora 官方发布为准（待核实）。Fedora 是否跟进 RVA23 基线，截至本篇核实日期以其官方说明为准（待核实）。
- **其他发行版**：openSUSE、Gentoo、Arch Linux RISC-V（社区移植）等均有不同程度的 RISC-V 相关支持；其中 Arch 的 RISC-V 支持为社区移植性质，不等同于 Arch 官方正式架构；各发行版的正式程度、镜像形态与更新策略差异很大，须逐项查官方发布，不可一概而论（待核实）。
- **厂商发行版与社区镜像**：各板厂商提供的定制镜像、Armbian 等社区镜像是通用发行版之外的补充；它们的内核版本、更新周期与支持期限由各自维护方决定，不等同于上游发行版的支持承诺。

## 6. 关键论文与标准

- RISC-V 指令集规范与 RVA23 等 profile 规范：见 RISC-V International 官网的批准规范文本；RVA23 于 2024 年前后获批，是 Ubuntu 25.10 起提高基线的依据。
- Debian 13 “Trixie”发布说明：首个正式支持 riscv64 的 Debian 稳定版本，基线 RV64GC、lp64d ABI。
- Canonical 关于 Ubuntu RISC-V 的公开回顾：Ubuntu 25.10 起以 RVA23 为最低基线，RVA20 用户留在 24.04 LTS 通道；Ubuntu 26.04 LTS 以 RVA23 为统一长期支持基线。
- 暂无单一论文可作为本篇的理论来源：开发板与发行版支持是标准、内核上游化与发行版工程协作的结果，不是某一篇论文的产物；本篇事实主张以各发行版与厂商的官方发布为准。

## 7. 当前实验结果

本节不写性能数字：开发板横向性能数字高度依赖测试集、编译选项、散热、内核版本与 GPU/NPU 驱动状态，第三方博客的跑分表往往缺其中几项，不具备可比性。只写经核查的定性事实：

- 通用发行版对 RISC-V 的支持已从“移植实验”进入“正式版本”阶段：Debian 13 正式收录 riscv64，Ubuntu 24.04/25.10 的基线划分已公开，Fedora 亦有面向板子与容器的 RISC-V 构建。
- 但“正式支持”不等于“所有板子同等可用”：同一发行版在不同板子上的外设完整度（GPU、视频编解码、Wi-Fi、PCIe）差异很大，须按板查文档。
- 厂商宣传的“某板性能达到某 ARM 板水平”“某 NPU 算力达到多少 TOPS”等说法，测试条件与驱动状态往往未公开，本篇不采信、不转载，以厂商与发行版的官方发布为准。

## 8. 技术瓶颈

- **Profile 分叉**：RVA20 板子与 RVA23 板子并存，发行版提高基线后，老板子被留在旧 LTS 通道；用户升级发行版前必须先确认板子的 profile，否则会出现“新版装不上”的断层。
- **上游化滞后**：板级设备树、驱动与 U-Boot 支持进上游需要时间；用户拿到新板时，能用的往往是厂商镜像而非通用发行版，通用发行版支持到来时板子可能已换代。
- **GPU 与 NPU 驱动**：GPU 的图形栈（Mesa 驱动、Vulkan 支持）与 NPU 的推理栈成熟度因 SoC 而异；桌面与 AI 功能的可用程度不能只看 SoC 参数表，要看驱动是否进上游。
- **固件与启动链的闭源部分**：部分 SoC 的启动固件、电源管理或外设固件仍不开放，通用发行版无法完全替代厂商固件；这是“开源指令集”不等于“全开源板子”的具体表现。
- **供货与换代快**：开发板型号、内存版本与供货状态变化快，同一板名可能有多个硬件版本；文档与镜像须按板子的具体版本核对，不能只按板名购买与安装。
- **排障资料稀缺**：相比 x86 与 ARM 板，RISC-V 板的排障问答、已知问题清单与商业支持覆盖面仍较窄；串口日志是定位启动问题的主要手段，但这要求用户会接串口、会读引导日志，门槛高于“插卡开机”。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：Debian 13 正式收录 riscv64、Ubuntu 的 RVA23 基线划分已公开、主流板子均可跑起 Linux，说明软件生态已越过“能不能用”的门槛；但板级支持仍大量依赖厂商镜像、GPU/NPU 驱动与 profile 分叉尚未收敛，尚未达到与 x86/ARM 开发板相当的“装上通用发行版就能全功能使用”的成熟度。

## 10. 未来研究问题

- **已有研究在做**：RVA23 级 SoC 与板子的量产与上游化、发行版对 RISC-V 的正式支持范围扩大、GPU 与 NPU 驱动进上游。
- **已有研究在做**：统一内核与通用安装镜像——同一份发行版镜像能否覆盖多块板子，而不必每块板子单独做镜像。
- **本文推测**：开发板生态的下一道门槛不是“有没有更多板子”，而是“新板子上市多久能进通用发行版”；检验标准是主流发行版从板子发布到提供官方镜像的平均滞后时间是否缩短到与 ARM 板相当的水平。
- **本文推测**：RVA20 板子可能长期停留在 24.04 LTS 这类旧通道上，形成“老板子跑旧发行版、新板子跑新发行版”的长期分层；检验标准是旧通道的安全更新是否确实覆盖到旧板子的整个承诺周期，而不是只覆盖到发行版的通用支持期。
- **本文推测**：决定一块板子长期价值的可能不是首发参数，而是上游化速度——设备树与驱动进主线越快的板子，在厂商停止维护镜像后仍能靠通用发行版续命；检验标准是厂商镜像停更后，该板子的通用发行版支持是否仍在更新。
