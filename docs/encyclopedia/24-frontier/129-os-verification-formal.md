# 操作系统验证（形式化方法视角）

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章，也是与操作系统方向文章配套的方法篇：OS 产品、架构演进与部署背景见[操作系统验证](100-os-formal-verification.md)（由操作系统方向写手并行编写，落盘后链接即通），本篇只讲形式化方法视角——验证一个内核要证什么、规约怎么写、证明怎么组织、信任假设有哪些，不重复 100 篇的产品与架构内容。

## 1. 研究问题

内核是系统中最难验证、又最值得验证的部分：它运行在最高特权级，一个 bug 就可能破坏所有进程的隔离；它又与硬件、并发、中断、内存管理纠缠在一起，状态空间巨大。操作系统验证要回答的问题是：能不能对内核给出机器检查的正确性证明，使“隔离确实成立”“系统调用确实按规约行事”不再依赖测试抽样？回答这个问题的难点不在“写证明”，而在“证明什么”——内核的规约本身就是一个完整的操作系统抽象模型，写规约的工作量与写内核相当，且规约错了，证明就失去了意义。

## 2. 基础理论

- **精化（refinement）**：内核验证的核心定理形式——C 实现的行为是抽象规约行为的子集。精化具有传递性：抽象规约 → 可执行规约 → C 代码，两段精化拼成端到端结论；高层性质（如隔离性）在抽象规约上证明后，经精化保持传到实现。
- **信息流与非干涉（noninterference）**：隔离性的形式化表述——一个进程的可观测行为不受其他进程秘密数据的影响；seL4 的机密性、完整性、可用性论证建立在精化与信息流性质之上。
- **并发推理**：多核内核需要推理细粒度锁、中断、内存模型；并发分离逻辑与精化理论是处理这部分的工具，但多核完整验证仍是开放难题。
- **最坏情况执行时间（WCET）**：seL4 方向曾做过完整的 WCET 分析工作（以官方发布为准，待核实）；实时性证明与功能正确性证明是两条不同的证明线，不能互相冒充。

## 3. 技术路线

- **微内核优先路线**：先验证小内核（seL4 约数千行 C 代码量级），再在其上构建验证过的系统服务；小是验证可行的前提，宏内核的规模至今无人完整验证。
- **分层精化路线**：抽象模型、可执行模型、C 实现三层递进，每层只解决一层的问题；抽象层讲“系统调用应该做什么”，可执行层讲“数据结构怎么组织”，C 层讲“代码确实这样做”。
- **并发内核路线**：CertiKOS 用 Coq 验证支持细粒度锁与中断的并发内核，证明组织围绕并发精化展开；与 seL4 的单核主线形成对照——并发验证的证明复杂度显著更高。
- **全系统验证路线**：Ironclad/IronFleet 用 Dafny、Boogie 与 Z3 从应用层一路验证到内核汇编层，目标是“整条链都有证明”，代价是系统规模与性能取舍（Ironclad 依赖的垃圾回收与停表设计是其简化假设之一，以官方发布为准，待核实）。
- **Rust 验证内核路线（研究中）**：用 Verus 等 Rust 验证器写内核并证明功能正确性，试图把 Rust 的所有权类型优势转化为更低的证明成本；Atmosphere 等研究原型属此方向，具体覆盖范围以官方发布为准（待核实）。

## 4. 系统架构

一套内核验证工作通常由以下部分组成：

- **抽象规约**：用高阶逻辑或依赖类型写的操作系统模型，定义系统调用、能力（capability）、地址空间、调度的抽象行为。
- **可执行规约**：接近实现的中间模型，数据结构已具体化，但仍是逻辑语言而非 C 代码；它是抽象与实现之间的桥梁。
- **C 语义接入**：用证明助手内的 C 语义（如 Isabelle 的 C 解析器）把 C 代码翻译成逻辑表示，再证明它精化可执行规约。
- **二进制层（部分覆盖）**：部分工作把证明延伸到编译产物（翻译验证式证明链），但二进制验证并非覆盖所有平台与配置，具体覆盖矩阵以 seL4 官方文档为准（待核实）。
- **假设清单**：编译器正确、汇编代码正确、硬件正确、启动代码正确、底层 TLB/缓存操作正确使用——这些是证明成立的前提，不是证明的结论，必须在报告中明示。

## 5. 代表性实现与开源项目

- **seL4**：首个通用操作系统内核的机器检查功能正确性证明，2009 年由 Klein 等报告，证明在 Isabelle/HOL 中完成，从抽象规约到 C 实现；内核 C 代码约数千行量级，证明脚本约数十万行量级（量级表述，精确数字因版本与统计口径而异，以官方发布为准，待核实）。初始证明针对单处理器 ARM 版本，后续扩展到其他架构与性质，具体覆盖以官方文档的验证矩阵为准。
- **CertiKOS**：耶鲁大学方向用 Coq 验证的并发操作系统内核，支持细粒度锁，证明围绕并发精化组织；与已验证 C 编译器工具链方向有协同。
- **Ironclad / IronFleet**：微软研究院方向用 Dafny 验证的应用与分布式系统，Ironclad 把验证从应用层延伸到内核汇编层，IronFleet 验证分布式系统协议与实现。
- **Verve**：早期用类型与内存安全验证简单内核的工作，后被 Ironclad 扩展；其验证目标是安全性质而非完整功能正确性，这一点在引用时不可夸大。
- **FSCQ**：用 Coq 验证的文件系统，证明崩溃一致性等性质；属于“内核部件验证”而非“整个内核验证”，引用时须区分。

## 6. 关键论文与标准

- Klein 等，《seL4: Formal Verification of an OS Kernel》，SOSP 2009——内核验证的标杆论文，2019 年入选 ACM SIGOPS Hall of Fame（以官方发布为准，待核实）。
- CertiKOS、Ironclad、IronFleet 的相关论文，具体篇名与发表细节以官方发布为准（待核实）。
- 暂无统一标准：内核验证没有“验证过”的行业标准定义；功能安全与适航标准对证据的要求见[安全关键软件](131-safety-critical-software.md)，那是证据链要求，不是内核证明本身的标准。

## 7. 当前实验结果

本节不写“证明花了多少人年、性能快了多少”的精确数字：人年数随团队、统计口径（是否含规约、工具、后续维护）而异，公开梳理中 seL4 的工作量有“约 20 人年”与“证明代码比实现高一个数量级以上”等不同口径的表述，本篇不采信单一数字。只写经核查的定性结论：seL4 验证发现了设计与实现中的数百个 bug 量级的问题（公开论述称验证过程揭示约数百个 bug，具体数字以论文原文为准，待核实）；验证后的内核在隔离性论证上达到了测试无法达到的强度；但验证覆盖随架构与配置而异，不存在“一证永逸、覆盖所有平台”的版本。

## 8. 技术瓶颈

- **证明成本**：证明代码量远超实现代码量，改动内核常需重做大量证明，迭代速度受限；这是内核验证至今只覆盖微内核的根本原因。
- **并发与多核**：细粒度锁、中断、弱内存模型使精化证明复杂度陡增；多核完整验证仍是研究前沿，不是工程常规。
- **硬件与驱动缺口**：设备驱动、固件、硬件行为大多不在证明内；“内核已验证”不等于“整机已验证”，驱动 bug 仍可破坏隔离。
- **规约可信度**：抽象规约由人写，规约本身的错误不受证明保护；规约评审、规约与需求文档的对照，是验证项目中与证明同等重要的一环。
- **演进与维护**：内核要演进（新架构、新特性），证明要同步演进；证明库的长期维护成本是立项时最容易低估的一项。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：seL4、CertiKOS、Ironclad 等已有可复查的完整证明与真实部署探索，但证明成本、并发覆盖与驱动缺口使内核验证仍未成为操作系统开发的常规环节。

## 10. 未来研究问题

- **已有研究在做**：Rust 验证内核（Verus 方向）降低证明成本、多核内核验证、驱动与固件的形式化建模。
- **已有研究在做**：证明的模块化与复用——内核改动时只重做受影响部分的证明，而非全量重做。
- **本文推测**：内核验证最可能先以“安全关键场景的微内核 + 未验证部分严格沙箱化”的混合架构落地，而不是以“整个宏内核验证”落地；检验标准是量产安全关键系统中已验证微内核的部署案例是否从个位数增长。
