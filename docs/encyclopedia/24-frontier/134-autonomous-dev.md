# 自主软件开发

自主软件开发是指：以 Agent 为主体完成软件开发任务的工作流——Agent 阅读需求与代码库、制定修改计划、编辑代码、运行测试、根据失败反馈迭代，最后提交可供审查的变更（例如合并请求），人保留审查、验收与合并的决定权。它与“代码补全”的区别在于任务粒度：补全是“人写、机器续写一行或一段”；自主开发是“机器主导一整项任务，人验收结果”。本篇讲开发流程侧；代码补全与日常维护归 [135 篇](135-ai-programming.md)，测试与修复的专有技术归 [136 篇](136-auto-testing-repair.md)。

本篇属于本方向总览 [133 篇](133-autonomous-systems.md)下的三级主题之一。

## 1. 研究问题

软件开发的瓶颈正在从“写代码的速度”转向“理解与验证的速度”：代码库越来越大，需求、历史提交、测试、文档散落在各处，人要先花大量时间读懂上下文才能动手改一处。自主开发要回答的问题是：Agent 能否在不把全部上下文塞给人的前提下，自己完成“理解—修改—验证”的闭环，并把结果以人可审查的形式交出来？

关键子问题：Agent 如何在大型代码库中定位相关代码而不迷路？如何保证修改不破坏已有行为（回归）？如何让一次失败的尝试成为下一次的有效信息，而不是重复试错？以及：当任务描述本身含糊或自相矛盾时，Agent 是该追问、该按最合理理解推进，还是该停下？

## 2. 基础理论

- **Agent—计算机接口（agent-computer interface, ACI）**：Yang 等 2024 年提出的核心思想——语言模型是新型终端用户，需要为其专门设计的工具接口（如面向模型的查看、搜索、编辑命令与反馈格式），而不是直接复用人用的 shell；接口设计显著影响 Agent 的任务成功率。
- **工具调用与 ReAct 式循环**：推理—行动—观测的迭代循环，是编码 Agent 执行多步任务的基本工作模式。
- **测试作为验证标准**：以项目自带测试（通过/失败）作为补丁正确性的可机验证据；这是 SWE-bench 类基准成立的前提，也是自主开发区别于“只生成代码”的关键。
- **检索与上下文管理**：在有限上下文内定位相关文件与历史，是大型仓库任务成败的分水岭；长上下文缓解了问题，但没有消除定位与取舍问题。

## 3. 技术路线

- **单 Agent 端到端路线**：一个 Agent 独立完成从需求理解到提交的全过程；优点是简单、责任清晰，缺点是长任务中容易偏离与累积错误。
- **多 Agent 分工路线**：规划、编码、测试、审查由不同 Agent 担任，互相校验；优点是分工与制衡，缺点是协调成本与通信开销，系统视角见 [142 篇](142-multi-agent-workflows.md)。
- **人机协同路线**：Agent 在关键节点停下请人确认（方案、接口变更、危险操作），其余环节自主推进；这是当前最接近量产的路线，治理框架见 [143 篇](143-human-machine-collaboration.md)。
- **沙箱执行路线**：一切代码执行都在隔离沙箱中进行，Agent 只有受限的文件与网络权限；这是安全底线，不是可选项。
- **规格驱动路线**：先由人或 Agent 写出可验证的规格（测试、契约、类型约束），Agent 的修改必须通过规格检验；规格越完整，自主越可信。

## 4. 系统架构

一个典型的自主开发系统由以下部分组成：

- **任务输入层**：需求描述、问题单（issue）、失败测试或重构目标；输入质量直接决定输出质量，含糊输入是首要失败源。
- **上下文引擎**：代码搜索、符号索引、历史提交与相关文档的检索；负责把“需要的那部分仓库”交给模型。
- **Agent 核心**：规划、工具调用、迭代执行的推理主体；维护任务状态与已尝试路径，避免重复试错。
- **执行沙箱**：隔离的运行环境，负责运行测试、构建与静态检查；一切外部副作用（发包、删数据、调外部服务）默认禁止。
- **验证与审查层**：测试结果、差异（diff）摘要、风险标注（如改动了公共接口、迁移了数据）；输出必须以人可快速审查的形式呈现，否则“自主”只是把审查负担转嫁给人。

## 5. 代表性实现与开源项目

只列真实存在的研究与工程载体，不写未核实的采用数字：

- **SWE-agent**：Yang 等 2024 年提出的开源研究 Agent，以 ACI 为核心设计；是本方向方法论的代表性工作，不是某个商业产品的代称。
- **OpenHands（原 OpenDevin）**：开源的通用 Agent 执行框架，可在沙箱中完成编码类任务；其具体版本与基准表现以官方发布为准（待核实）。
- **商业编码 Agent 产品**：以“Agent 模式”提供多文件自主修改的编辑器与平台类产品；各产品的定价、模型与基准分数变动快，本篇不转载，以官方发布为准（待核实）。
- **尚无“无人验收的端到端交付”量产形态**：按“Agent 独立交付生产变更、无需人工审查”的定义，今天不存在可信的量产形态；现有落地形态均为“Agent 起草、人审查合并”。

## 6. 关键论文与标准

- Yang, J.、Jimenez, C. E.、Wettig, A.、Lieret, K.、Yao, S.、Narasimhan, K. 与 Press, O.（2024）《SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering》，NeurIPS 2024，arXiv:2405.15793——ACI 思想与原始评测的来源。
- Jimenez, C. E. 等（2024）《SWE-bench: Can Language Models Resolve Real-World GitHub Issues?》，ICLR 2024，arXiv:2310.06770——真实 GitHub 问题单与项目测试作为评测标准的来源。
- 暂无统一标准：自主开发没有类似“Agent 提交质量”的行业标准；评测基准、沙箱规范与审查流程均处于各家自定阶段。

## 7. 当前实验结果

只写经核查的原始论文数字，不写各源不一致的当前榜单分数：

- SWE-agent 原始论文报告：以 GPT-4 Turbo 为底座，在 SWE-bench 全部 2294 项任务上 pass@1 为 12.47%，在 HumanEvalFix 上为 87.7%（Yang 等，NeurIPS 2024）。这是 2024 年的方法论起点，不是今天的水平。
- SWE-bench 本身的构成经核查：原始测试集 2294 项真实 GitHub 问题单，Verified 子集为经人工筛选的 500 项；评测以项目自带测试的通过/失败为准。
- 今天的 SWE-bench Verified 榜单数字在不同来源（官方榜、独立复跑、厂商自报）之间存在显著差异且口径不同（执行框架、尝试次数、模型版本均不同），本篇不采信任何一个当前分数，以 SWE-bench 官方发布为准（待核实）。
- 定性结论：单任务修复的基准表现已有可复现的长足进展；但基准任务不等于生产任务——生产任务常涉及跨服务变更、数据迁移、灰度与回滚，这些在基准中基本不出现。

## 8. 技术瓶颈

- **上下文定位**：仓库越大，Agent 越难一次找全相关代码；找不全就改错地方，找太多又淹没关键信息。
- **验证不完备**：测试通过不等于行为正确；测试覆盖不足的区域，Agent 的“修复”可能是未被发现的回归。
- **长任务漂移**：步骤越多，早期小偏差累积成后期大偏离；缺乏中间检查点的长任务尤其脆弱。
- **含糊需求**：任务描述含糊时，Agent 倾向于“按最合理理解推进”而不是追问，结果可能是精致地实现了错误的东西。
- **审查负担转移**：Agent 一次提交几千行 diff 时，人的审查成本可能超过自己写的成本；“自主”若不附带可审查的输出，就是负担转移。
- **安全与权限**：Agent 在沙箱外的任何写操作（发布、删库、调外部 API）都必须有显式授权与审计；默认放行等于把生产钥匙交给模型。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：单任务、测试可验证的修复已有可复现的研究进展与“Agent 起草、人审查”的工程落地，但无人验收的端到端交付、跨服务与数据迁移类任务仍不可信。

## 10. 未来研究问题

- **已有研究在做**：面向 Agent 的代码库索引与上下文管理——如何让 Agent 在百万行仓库中稳定定位。
- **已有研究在做**：补丁的语义验证——超越“测试通过”的验证手段（契约、属性测试、形式化规约）。
- **已有研究在做**：可审查的 Agent 输出——diff 摘要、风险标注、测试覆盖说明的标准格式。
- **本文推测**：自主开发的量产形态将长期是“分级放权”：从文档与测试类任务开始放权，核心逻辑与数据迁移最后放权；检验标准是各任务类型是否有公开的放权条件与事故复盘。
- **本文推测**：规格（测试、契约）可能成为人机分工的新界面——人写规格、Agent 填实现；检验标准是规格驱动流程是否在真实项目中降低了返工率。
