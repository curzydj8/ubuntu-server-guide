# 自动程序修复

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章。总览讲“形式化方法整体”；本篇讲它的镜像问题：如果说验证是“证明程序对不对”，自动程序修复（automated program repair, APR）就是“程序被证明（或被测试）错了之后，能不能自动把它改对”。这是一个诱人的承诺，也是一个布满陷阱的领域：生成一个“让测试通过”的补丁很容易，生成一个“真正正确”的补丁很难，两者的差距就是 APR 全部的研究史。

## 1. 研究问题

调试占开发者大量时间，且高度依赖经验：定位故障、理解意图、写出不破坏其他功能的补丁。APR 要回答的是：给定一段有 bug 的程序与一组失败测试（或规约、或崩溃报告），机器能不能自动生成补丁，使失败测试通过且不破坏已有正确行为？关键限定词是后半句——只让失败测试通过的补丁可能是“过拟合测试”的补丁：它恰好满足测试用例的字面条件，却违背程序的真实意图。APR 的核心难题不是“生成补丁”，而是“如何知道补丁是对的”——而这正是形式化验证要解决的问题。于是 APR 与验证天然互补：验证提供“对”的标准，修复提供“改”的手段。

## 2. 基础理论

- **故障定位（fault localization）**：用测试覆盖谱（哪些测试经过哪些语句、哪些失败）给语句打可疑度排序，把搜索空间从全程序缩小到少数可疑区域；定位不准则后续搜索全是无用功。
- **生成—验证（generate-and-validate）**：APR 的经典范式——生成候选补丁，用测试套件验证，保留通过全部测试的候选；验证标准就是测试套件本身，这既是它的力量（可自动化），也是它的阿喀琉斯之踵（测试即规约的近似）。
- **语义修复与约束求解**：把“补丁应满足的条件”编码成约束，用 SMT 求解器求解补丁参数（如 SemFix、Nopol 方向）；比纯搜索更精确，但约束建模本身需要规约或测试oracle。
- **补丁过拟合（patch overfitting）**：补丁通过已有测试、但在未见输入上错误；这是 APR 文献中最核心的评估问题，缓解手段包括扩充测试（模糊测试、变异测试）、用规约或形式验证复核补丁、人工评审。
- **补丁正确性 vs 合理性**：文献区分“测试通过的补丁”（plausible patch）与“与开发者真实修复等价的补丁”（correct patch）；报告修复率时不区分两者，就是数字造假。任何 APR 成果报告都必须写明用的是哪种口径。

## 3. 技术路线

- **搜索式修复路线**：用遗传编程、变异、模板在补丁空间中搜索，GenProg 是开创者——2009 年 ICSE 论文（Weimer、Nguyen、Le Goues、Forrest）首次在规模上证明：对数十万行量级的真实程序，遗传编程可以自动演化出通过测试套件的补丁；2012 年的 TSE 扩展进一步讨论了补丁质量问题。
- **语义与约束式修复路线**：从失败测试推导补丁应满足的约束，用求解器合成补丁；适合条件、算术、空指针等局部 bug，补丁更精确，但适用范围受约束建模能力限制。
- **模板与模式修复路线**：从历史修复中挖掘常见补丁模式（如空检查、边界修正、API 误用修正），按模式生成候选；TBar 等工作系统梳理了修复模板的效果边界，具体结论以论文原文为准（待核实）。
- **学习式与大语言模型修复路线**：用神经机器翻译式模型或大语言模型直接生成补丁，再用测试与验证复核；2022 年以来的 LLM 修复（如对话式修复 ChatRepair 方向）显著提高了候选生成能力，但“生成”与“验证”的分离仍是可信前提——模型可以猜，测试与证明负责验。
- **运行时修复与缓解路线**：不改源码，而是在运行时绕过、重启、降级（如 ClearView、Jolt 方向的运行时修复思想）；适合可用性优先、正确性可事后补的场景，不等于源码修复。

## 4. 系统架构

一套 APR 系统通常由以下部分组成：

- **故障定位器**：输入失败测试与覆盖信息，输出可疑语句排序。
- **补丁生成器**：搜索、约束求解、模板或语言模型，输出候选补丁。
- **验证器**：用原测试套件验证候选，过滤掉破坏回归的候选；高阶系统还会用扩充测试、模糊测试或形式验证复核。
- **排序与呈现层**：按可信度排序候选，呈现补丁差异与验证证据，供开发者评审；APR 的交付物是“建议补丁 + 证据”，不是“静默改代码”——静默合并不经评审的自动补丁是工程事故的配方。

## 5. 代表性实现与开源项目

- **GenProg**：自动程序修复的开创性系统，遗传编程路线，2009 年 ICSE 论文与 2012 年 TSE 扩展是领域奠基文献；后续研究围绕其补丁质量展开。
- **Prophet、Nopol、SemFix**：搜索式与约束式修复的代表性研究系统，具体适用范围与评估口径以论文原文为准（待核实）。
- **TBar、SequenceR、CoCoNuT**：模板与学习式修复的代表性研究工作，具体结论以论文原文为准（待核实）。
- **ChatRepair、RepairAgent**：大语言模型对话式修复的研究方向，模型生成、测试反馈、迭代修正的闭环；具体成功率数字因基准与评估口径而异，本篇不转载。
- **工业界修复框架**：Meta 等厂商公开提及受 GenProg 思想启发的生产级自动修复框架方向，具体部署细节以官方发布为准（待核实）；本篇不把“研究原型”写成“工业默认流程”。

## 6. 关键论文与标准

- Weimer、Nguyen、Le Goues、Forrest，《Automatically Finding Patches Using Genetic Programming》，ICSE 2009——GenProg 的原始论文。
- Le Goues、Nguyen、Forrest、Weimer，《GenProg: A Generic Method for Automatic Software Repair》，IEEE Transactions on Software Engineering，2012——GenProg 的扩展与补丁质量讨论；另有 2025 年的演进综述（IEEE TSE，DOI 10.1109/TSE.2025.3533309，以官方发布为准，待核实）。
- 暂无统一标准：APR 没有行业标准定义“修复成功”的口径；基准测试集（如 Defects4J 等）的评估方法以各自官方文档为准，具体基准名称与版本以官方发布为准（待核实）。

## 7. 当前实验结果

本节不转载任何“修复率百分之几”的数字：修复率随基准、测试套件强度、“合理补丁”与“正确补丁”的口径、是否允许人工评审而剧烈波动，脱离口径的数字没有比较意义。只写经核查的定性结论：搜索式修复在真实程序上可行已被 GenProg 以来大量工作证实；学习式与 LLM 修复提高了候选生成能力，但过拟合问题没有消失；工业界对 APR 的采纳形态是“建议 + 人工评审”，不是“自动合并”。

## 8. 技术瓶颈

- **过拟合是结构性问题**：测试套件永远是规约的不完备近似，以测试为唯一验证标准的 APR 必然产生过拟合补丁；缓解需要更强的验证标准（规约、形式验证、扩充测试），而这又把成本推回验证本身。
- **故障定位天花板**：定位错了，生成再强也无用；多故障、并发故障、非确定性故障的定位仍是难题。
- **补丁空间爆炸**：搜索空间随程序规模与补丁复杂度指数增长；模板与学习模型缩小了空间，但也引入了“模板外 bug 修不了”的盲区。
- **语义理解缺口**：LLM 生成补丁时并不真正理解程序意图，复杂逻辑 bug、跨模块 bug、需求误解类 bug 超出其可靠范围。
- **评估口径混乱**：不同论文用不同基准、不同口径报告修复率，横向比较困难；领域需要统一的“正确补丁”判定与报告规范，至今未成。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：APR 在研究基准与受控场景中已证明可行、工业界有建议式部署探索，但过拟合、定位天花板与评估口径问题使它尚未成为“自动修 bug”的通用工程环节。

## 10. 未来研究问题

- **已有研究在做**：用形式规约复核补丁（修复 + 验证闭环）、用模糊测试扩充验证标准、用人工评审数据训练补丁排序。
- **已有研究在做**：APR 与大语言模型的结合——模型负责生成与解释，测试与验证负责把关，分工越清晰，可信度越高。
- **本文推测**：APR 最可能先以“IDE 内补丁建议 + 一键评审合并”的形态普及，而不是以“CI 自动合并补丁”的形态普及；检验标准是开发者对 APR 建议的接受率与评审后返工率，而非论文中的修复率数字。
