# 云原生和边缘操作系统

## 1. 研究问题

云上节点与边缘节点的共同点是“多、散、难管”：成千上万台机器，每台的任务只是跑容器；传统发行版是为“人登录上去折腾”设计的：包管理器、Shell、长期原地升级——这些在无人值守的节点上全是负担：配置漂移、升级一半卡住、攻击面大。云原生与边缘操作系统要回答的问题是：节点 OS 能不能退化成“只跑容器的运行时”——不可变、原子更新、可回滚、API 管理、无人登录？边缘再加一层难：节点可能离线、算力小、网络差、位置分散，系统要在断网时自治、联网时同步。

## 2. 基础理论

- **不可变基础设施**：系统文件运行时只读，变更靠发布新镜像、替换整机实现，不靠原地修补；漂移从机制上被消除。
- **原子更新与 A/B 分区**：新系统写进备用分区，验证通过后切换启动项，失败回滚到旧分区；更新没有“进行到一半”的中间态。
- **节点 OS 与编排的分工**：节点 OS 只负责内核、容器运行时与更新；调度、服务发现、存储编排归 Kubernetes 等编排层（见 [96-distributed-os.md](96-distributed-os.md) 的云原生演变路线）。
- **边缘自治**：边缘节点在断网时要能继续跑本地负载、缓存决策、本地存储；联网后与中心同步状态与配置，而不是停下来等中心指令。

## 3. 技术路线

- **云厂商节点 OS 路线（Bottlerocket）**：AWS 的容器专用 OS，根文件系统 dm-verity 只读、A/B 原子更新、默认无 Shell（管理靠 admin 容器）、SELinux 强制模式；深度绑定 EKS/ECS，版本与 Kubernetes 版本对应发布；云外使用以官方发布为准（待核实）。
- **API 管理路线（Talos Linux）**：Sidero Labs 的 Kubernetes 专用 OS，无 SSH、无 Shell、无包管理器，用户空间极小，全部管理走 gRPC API（`talosctl`）；系统以 SquashFS 镜像在内存中运行，磁盘留给 Kubernetes；是最彻底的“节点 OS 即 API”实践。
- **社区延续路线（Flatcar Container Linux）**：CoreOS Container Linux 的社区延续，CNCF 孵化项目，`/usr` 只读、双分区更新、Omaha 协议更新引擎；适合多云与裸机场景。
- **通用发行版容器化路线（Fedora CoreOS、openSUSE MicroOS）**：在通用发行版上做不可变变体，rpm-ostree 或事务更新 + 容器运行时；兼顾不可变性与通用发行版的生态。
- **边缘发行版路线（Ubuntu Core、BalenaOS、Azure Sphere OS 等）**：面向物联网与边缘设备：事务更新、应用沙箱（snap、容器）、离线自治、设备管理；各发行版的设备覆盖与更新策略以官方发布为准（待核实）。边缘 OS 常与 [92-rtos.md](92-rtos.md) 的实时系统共存：实时控制归 RTOS，联网与 AI 推理归边缘 OS。

## 4. 系统架构

典型云边节点 OS 的组成部分：

- **只读根与 A/B 分区**：系统镜像整体签名、只读挂载、双分区切换。
- **容器运行时**：containerd 等运行时为一等组件，随系统镜像一起发布与回滚。
- **更新引擎**：拉取新镜像、验证签名、写备用分区、切换启动、失败回滚；更新策略（自动、窗口、手动）由编排层或管理 API 控制。
- **管理面**：API（Talos 的 gRPC）、本地 API（Bottlerocket 的 settings API）或设备管理服务；没有 SSH 意味着排障要靠日志、指标与远程 API，不是登录上去看。
- **边缘扩展**：本地镜像缓存、离线队列、边缘存储与网络自治模块；断网时的行为（继续跑、降级、缓存写操作）需显式设计。

## 5. 代表性实现与开源项目

- **Bottlerocket**：AWS 开源容器 OS，Apache 2.0/MIT，EKS/ECS 变体，dm-verity + A/B 更新（版本以官方发布为准）。
- **Talos Linux**：Sidero Labs 开源 Kubernetes OS，MPL-2.0，无 Shell/SSH、API 管理，SquashFS 内存运行（版本以官方发布为准）。
- **Flatcar Container Linux**：社区开源容器 OS，CNCF 孵化，`/usr` 只读、双分区更新。
- **Fedora CoreOS**：Fedora 的不可变容器 OS，rpm-ostree + 自动更新，适合通用云与裸机。
- **Ubuntu Core**：Canonical 的事务更新边缘 OS，snap 应用沙箱，面向物联网与边缘设备。
- **BalenaOS**：Balena 的容器边缘 OS，面向舰队化物联网设备管理；版本与功能以官方发布为准（待核实）。

## 6. 关键论文与标准

- 不可变基础设施与容器编排的实践文献见云原生社区公开资料（完整引用以原文为准，待核实）。
- OCI 镜像与运行时规范是容器层事实标准，节点 OS 的镜像格式则各项目自定，暂无统一的节点 OS 标准。
- 暂无统一的边缘 OS 标准：各厂商的设备管理、更新与应用沙箱接口互不兼容。

## 7. 当前实验结果

本节不写性能与规模数字：各项目的部署规模、启动时间与更新耗时口径不一，脱离条件的数字不可比。只写定性结论：Bottlerocket、Talos、Flatcar、Fedora CoreOS 均已在生产 Kubernetes 集群中使用，不可变节点 OS 从理念变为常规选项；边缘 OS 在物联网舰队管理中已有规模部署，但断网自治、异构硬件适配与长期维护仍是各项目公开讨论的难点。

## 8. 技术瓶颈

- **排障习惯的改变**：无 Shell、无 SSH 意味着传统“登录上去看”的排障失效；日志、指标、远程 API 与可观测性工具链必须先行，否则运维会抵制。
- **驱动与硬件覆盖**：节点 OS 镜像要覆盖云实例类型与边缘硬件，驱动缺失就无法用；通用发行版的驱动广度仍是优势。
- **更新策略的组织成本**：自动更新省事但有风险，手动更新安全但拖延；大规模舰队的更新窗口、灰度与回滚需要组织流程配合，不是纯技术问题。
- **边缘异构与离线**：边缘硬件千差万别，网络时断时续；统一镜像与统一管理在边缘的难度远高于同构云节点。
- **生态锁定**：Bottlerocket 绑定 AWS、Talos 绑定 Kubernetes，选择节点 OS 常等于选择云与编排，迁移成本高。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：云侧不可变节点 OS 已有生产应用，但边缘侧的异构适配、离线自治与统一管理仍在演进，云边作为整体仍处工程发展中而非全面成熟。

## 10. 未来研究问题

- **已有研究在做**：节点 OS 与机密计算的结合（可验证启动、可信执行环境中的节点）、GPU 节点的不可变 OS 变体（见 [98-gpu-runtime.md](98-gpu-runtime.md)）。
- **已有研究在做**：边缘 AI 负载的 OS 支持（模型热更新、推理资源预留、断网推理）。
- **本文推测**：节点 OS 可能进一步“消失”——被云厂商的托管节点池与边缘设备的出厂镜像吸收，用户不再直接选型节点 OS；检验标准是托管节点服务是否成为默认选项。
- **本文推测**：边缘 OS 与 RTOS 的分工可能从“两台设备”走向“一台设备的两个域”（实时域 + 边缘域共存）；检验标准是异构芯片上双域系统的出现。
