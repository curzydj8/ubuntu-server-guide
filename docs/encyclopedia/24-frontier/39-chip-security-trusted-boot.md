# 芯片安全与可信启动

> 本篇是 [先进芯片与 Chiplet](05-advanced-chips-chiplet.md) 所在 24 域先进芯片分支的下级专题，只讲芯片层面的安全原理与可信启动机制，不重复总览的封装与互连内容。本篇是防御侧文章：只讲威胁模型、防御机制与验证方法，不写可直接用于攻击、绕过启动链、提取密钥或破解验证的操作步骤。HBM 与 CXL 的细节归新型存储与互连分支，见 [新型存储与互连：HBM 与 CXL](09-new-storage-interconnect.md)、[CXL 内存池化](24-memory-pooling-cxl.md) 与 [HBM 各代](25-hbm-generations.md)，本篇只链接、不展开；RISC-V 安全相关的生态内容归 RISC-V 生态分支，见 [RISC-V 生态总览](04-riscv-ecosystem.md)，本篇只链接、不展开；开源信任根设计本身见 [开源芯片设计与 EDA](30-open-chip-eda.md) 中的 OpenTitan 一节，本篇讲其安全原理而不重复其设计流程。

## 1. 研究问题

操作系统与应用的安全都建立在一个前提上：启动时最先运行的代码是可信的。如果启动链的第一环就被替换，之后运行的任何安全软件都可能运行在一个已被控制的平台上，而自身毫无察觉。芯片安全与可信启动要回答的问题是：从上电那一刻起，系统如何确认“最先运行的代码确实是它应该运行的代码”，并把这种确认一环一环传递下去，直到操作系统接管？

这个问题的难点在于“信任从哪里来”。软件无法自己证明自己可信——验证者本身也需要被信任。因此信任必须锚定在硬件上：一段不可修改的代码、一组烧录后不可更改的密钥、一个独立的安全子系统。整个可信启动体系，都是围绕“如何锚定第一环信任、又如何不让它在后续环节中断”展开的。

## 2. 基础理论

- **信任根（Root of Trust，RoT）**：系统中最先被信任的硬件或代码，通常是片上不可修改的只读存储（ROM）中的启动代码，或独立的安全子系统；信任根本身不被验证——它就是验证的起点，因此必须尽可能小、尽可能难改。
- **信任链（Chain of Trust）**：每一级在把控制权交给下一级之前，先验证（或度量）下一级；信任由此从信任根逐级传递。链中任何一环断裂，后续环节的信任都无从谈起。
- **验证启动（Verified Boot / Secure Boot）**：启动前用数字签名验证下一级代码，签名不符则拒绝执行（或转入恢复流程）；它回答的问题是“这段代码允不允许运行”。
- **度量启动（Measured Boot）**：启动时计算下一级代码的哈希值并记录到可信平台模块（TPM）等安全存储中，本身不阻止执行；它回答的问题是“实际运行的是什么”，供事后或远端核查。
- **远程证明（Remote Attestation）**：设备用 TPM 等安全硬件对度量值签名后发给远端验证方，验证方据此判断该设备是否处于预期状态，再决定是否放行（如是否允许接入集群、是否发放密钥）；证明的前提是度量链完整且验证方持有正确的预期值。
- **DICE（Device Identifier Composition Engine）**：可信计算组织（TCG）提出的设备身份派生机制，每一级启动代码用上一级的度量值派生本级身份；设备身份由此与“实际运行了什么固件”绑定，固件变了，派生出的身份也随之变化。
- **固件韧性三支柱**：按 NIST SP 800-193（2018 年发布）的框架，平台固件韧性由保护（防止未授权修改）、检测（发现未授权修改）与恢复（从受信备份恢复到正确状态）三部分组成；只做到“验证”而不做到“恢复”的系统，在固件损坏时只能停机，不能自愈。

## 3. 技术路线

主流防御路线按“信任锚定在哪里、验证做到哪一步”分四条：

- **硬件信任根 + 验证启动**：信任根验证第一级可变固件的签名，签名通过才放行，逐级验证到引导加载程序与操作系统内核；这是 UEFI Secure Boot 与各类芯片厂商安全启动机制的共同思路，区别主要在信任根的实现形态（片上 ROM、独立安全芯片或安全处理器）与密钥由谁掌控。
- **度量启动 + 远程证明**：每一级把下一级的哈希度量值写入 TPM 的平台配置寄存器（PCR），启动完成后由 TPM 对度量值签名，供本地策略（如密钥解封条件）或远端验证方核查；这条路线不直接阻止可疑代码运行，而是让“运行了什么”变得可审计、可问责。
- **固件韧性与自愈**：在验证与度量之外，另备一份受信的固件备份与独立的恢复信任根；检测到主固件损坏时，由恢复信任根把备份写回，实现保护—检测—恢复的闭环；这是 NIST SP 800-193 所要求的“可恢复平台”与“韧性平台”的核心能力。
- **开放信任根**：把信任根的设计本身开源（RTL、固件与验证工具均可审计），让信任不依赖“厂商说它安全”，而依赖“任何人都可以检查它”；OpenTitan 与 Caliptra 属于这一类，其成熟度与量产覆盖仍在发展中，见第 5 节与第 9 节。

四条路线不是互斥的：同一平台上可能同时存在验证启动（决定能否运行）、度量启动（记录运行了什么）与恢复机制（损坏时如何自愈），三者各司其职。

## 4. 系统架构

一个典型的可信启动系统由以下部分组成：

- **不可变启动代码**：固化在 ROM 中的第一级代码，上电后最先运行；它的任务是验证或度量下一级，并把控制权交出。ROM 不可修改是整条链的物理前提。
- **信任根安全子系统**：独立于主处理器运行的安全核或安全芯片，负责密钥存储、签名验证与度量记录；它与主处理器的隔离程度，决定了主处理器被攻陷后安全子系统是否还能独立作证。
- **密钥与熔丝**：验证用的公钥哈希、设备身份密钥等关键材料烧录在一次性可编程熔丝（OTP/eFuse）或安全存储中；密钥一旦烧录即不可更改，这是“验证”有意义的前提，也是密钥管理一旦出错难以挽回的原因。
- **启动链各阶段**：信任根 → 第一级固件 → 引导加载程序 → 操作系统内核 → 早期用户态组件；每一级在交出控制权前验证或度量下一级，度量值沿链累积进 TPM PCR 或等效存储。
- **恢复与更新通道**：受信的固件备份、带签名的安全更新机制与防回滚计数器；更新必须验证签名且版本号不得回退到已知有漏洞的旧版本，否则“更新”本身就成为降级攻击的入口。
- **证明与策略层**：TPM 签发的度量报告（Quote）供本地密钥解封策略或远端验证方使用；策略层决定“度量值与预期不符时，是拒绝解封密钥、拒绝接入网络，还是仅告警”，这一决策属于部署策略，不属于芯片本身。

## 5. 代表性实现与开源项目

只列真实存在的机制与项目，具体型号与版本细节以官方发布为准：

- **UEFI Secure Boot**：UEFI 规范中的验证启动机制，固件用密钥数据库（平台密钥 PK、密钥交换密钥 KEK、签名数据库 db 与吊销数据库 dbx）验证待执行的 UEFI 程序签名；签名不在信任库中或已被吊销的程序不被执行。它验证的是 UEFI 阶段，UEFI 之前的信任根需由芯片厂商的机制（如下面一项）提供。
- **芯片厂商的硬件启动验证**：英特尔 Boot Guard、AMD 安全处理器机制、Arm 架构下的信任启动实现等，均属“芯片级信任根验证第一级固件”的思路；各厂商的具体模式（验证模式、度量模式或两者结合）、密钥烧录方式与可配置性以各厂商官方发布为准（待核实），本篇不做横向排名。
- **TPM 2.0（可信平台模块）**：TCG 规范定义的安全芯片或固件 TPM，提供度量存储（PCR）、密钥密封/解封、签名与证明能力；它是度量启动与远程证明的常见载体，但 TPM 本身不验证启动链——验证与度量的分工见第 2 节。
- **OpenTitan**：lowRISC 牵头的开源硅片信任根项目，以 Ibex RISC-V 核为安全核，覆盖安全启动、密钥管理与证明；lowRISC 方面称基于 OpenTitan 的分立信任根器件已于 2024 年达到商业可用（以官方发布为准，待核实），本篇不转载其后续具体出货数字。
- **Caliptra**：源自开放计算项目（OCP）、现由 CHIPS Alliance 托管的开源信任根 IP，面向数据中心 CPU、GPU 与加速器芯片内部集成，提供基于 DICE 的身份、度量启动与证明能力；其后续版本的后量子密码等功能演进以项目官方发布为准（待核实）。
- **尚无“一种机制包打天下”的形态**：UEFI Secure Boot、TPM、芯片厂商信任根与开放信任根解决的是链上不同环节的问题；把其中任何一项单独称为“可信启动的完整方案”都是对架构的误读。

## 6. 关键论文与标准

- NIST SP 800-193《平台固件韧性指南》（2018 年发布）：平台固件保护、检测与恢复的权威框架，本篇第 2 节的三支柱即出自该指南；它取代了范围较窄的早期 BIOS 保护与度量指南。
- TCG TPM 2.0 规范与 DICE 相关规范：TPM 的度量、密封与证明能力，以及设备身份派生的权威来源；具体规范版本以 TCG 官方发布为准。
- UEFI 规范中的 Secure Boot 章节：UEFI 验证启动的密钥数据库结构与验证流程的权威来源；具体规范版本以 UEFI Forum 官方发布为准。
- OCP 与 CHIPS Alliance 关于 Caliptra 的公开规范与文档，以及 lowRISC 关于 OpenTitan 的公开文档：开放信任根的架构与接口来源；具体版本以各项目官方发布为准。
- 暂无单一论文可作为本篇的理论来源：可信启动是信任根、密码学与平台架构的工程综合，其理论分散于上述标准与各厂商、项目的公开文档中。

## 7. 当前实验结果

本节不写性能数字：可信启动的价值不在速度，而在“能否在攻击与故障面前维持信任链”，这无法用单一基准分数衡量。只写经核查的定性事实：

- 验证启动与度量启动已是主流平台的量产机制：UEFI Secure Boot 与 TPM 2.0 在 PC 与服务器平台上广泛部署，移动与嵌入式平台也有各自的验证启动实现；“广泛部署”不等于“普遍正确配置”——密钥管理、吊销更新与恢复策略的落地质量因厂商与部署而异。
- 开放信任根已从原型走向早期商用：OpenTitan 与 Caliptra 均有公开的 RTL、固件与验证工具，lowRISC 方面报告了分立信任根器件的商业可用；但开放信任根在主流芯片中的覆盖广度，截至本篇核实日期仍在发展中，不宜写成“已成主流”。
- 固件韧性的“恢复”一环落地最晚：保护与检测相对容易验证，恢复则需要备份固件、独立恢复信任根与故障演练三者齐备；缺少演练的恢复机制，在真实故障时是否可用是未经证实的，本篇不把“有备份”写成“可自愈”。

## 8. 技术瓶颈

以下只讲威胁类别与防御难点，不含任何可操作步骤：

- **密钥管理与吊销**：信任根密钥烧录后难以更改；一旦某级签名密钥泄露或某版本固件被发现漏洞，吊销与轮换的流程必须在所有已出货设备上可靠执行，否则吊销数据库更新不到的设备仍信任旧签名。
- **恢复与“变砖”的权衡**：验证失败时是停机、回退还是恢复，每种选择都有代价——停机影响可用性，回退可能回到有漏洞的版本，恢复依赖备份本身未被破坏；策略选择属于部署方的安全决策，没有通用最优解。
- **供应链信任**：芯片从设计、制造、封装到集成，任何环节的替换或篡改都可能动摇信任根；芯片级证明与供应链审计是防御方向，但其覆盖深度与成本仍在权衡中。
- **物理攻击面**：信任根与密钥存储面临的威胁类别包括侧信道分析与故障注入等物理手段；防御方向是硬件层面的隔离、屏蔽与检测，具体防护设计属于芯片厂商的机密实现，本篇不展开。
- **Chiplet 时代的信任边界**：当系统由多个厂商的 chiplet 拼成时（见 [先进芯片与 Chiplet](05-advanced-chips-chiplet.md)），“谁是信任根、每个 chiplet 的固件由谁验证、证明覆盖哪些裸片”成为新的架构问题；截至本篇核实日期，跨厂商 chiplet 的统一信任根方案仍在探索中，以官方发布为准（待核实）。
- **后量子迁移**：启动链的签名算法若需迁移到后量子密码，信任根中烧录的旧算法公钥、签名体积与验证时延都会受影响；迁移节奏与兼容策略以各标准组织与厂商的官方发布为准（待核实），本篇不预测时间表。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：UEFI Secure Boot 与 TPM 度量启动等核心机制已是量产多年的成熟应用，但开放信任根的规模化覆盖、跨厂商 chiplet 的统一信任方案、固件自愈的实战验证与后量子迁移仍在建设中，整体尚未达到“所有环节均已成熟定型”的程度。

## 10. 未来研究问题

- **已有研究在做**：开放信任根的规模化集成、Chiplet 系统的信任根架构、以及后量子签名算法进入启动链的兼容方案。
- **已有研究在做**：固件韧性的实战验证方法——如何用故障演练证明恢复机制在真实损坏场景下可用，而不只是在文档中存在。
- **本文推测**：可信启动的下一道门槛不是“验证算法更强”，而是“信任的可审计性”——即验证方能否独立核查信任根的设计与实现，而不只依赖厂商声明；检验标准是开放信任根设计是否被主流芯片厂商实际采纳为信任根，而非仅停留在参考设计。
- **本文推测**：远程证明可能从“单机自证”走向“集群准入”——即设备在接入集群前先出示证明，未通过者被隔离；检验标准是数据中心与边缘集群的准入流程是否普遍把证明结果作为硬性门禁，而非仅作日志记录。
