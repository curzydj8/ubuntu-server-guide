# 异构计算与 CPU/GPU/NPU/TPU 协同

> 本篇是新型计算架构分支中“换并行组织”方向的三级展开，归属见 [后冯·诺依曼架构](72-post-von-neumann.md) 的路线四与 [新型计算架构：光子与存算一体](08-new-computing-arch.md) 总览的边界说明。它讲单机/单节点内多种处理器的协同，不讲多节点集群（集群侧归 [GPU 集群与异构集群](11-gpu-hetero-clusters.md)），不讲某一款芯片的细节（芯片侧归 [GPU、NPU 与 AI 专用芯片](34-gpu-npu-chips.md) 与 [先进芯片与 Chiplet](05-advanced-chips-chiplet.md)），不讲互连物理细节（归 [缓存、互联与内存控制器](36-cache-interconnect.md) 与 [新型存储与互连：HBM 与 CXL](09-new-storage-interconnect.md)）。

## 1. 研究问题

没有一种处理器在所有任务上都最优：CPU 擅长控制流与串行逻辑，GPU 擅长大规模数据并行，NPU/TPU 擅长低精度矩阵运算，FPGA 擅长定制流水线（见 [可重构计算与 FPGA](78-reconfigurable-fpga.md)）。异构计算要回答的问题是：**如何把一个应用切分到多种处理器上，让每种处理器只做它最擅长的事，并且切分、搬运与同步的开销不超过协同带来的收益？**

这个问题的难点不在“有多种处理器”，而在“协同”二字：数据在不同处理器的内存之间搬运要花时间，任务在不同处理器之间同步要花时间，程序员为每种处理器写一遍代码要花人力。异构计算史，就是不断降低这三项开销的历史——统一内存降搬运、异步任务图降同步、统一编程模型降人力，但三项开销至今没有一项被彻底消除。

## 2. 基础理论

- **处理器分工原理**：控制密集（分支多、依赖链长）归 CPU，数据并行（规则、大规模、无复杂分支）归 GPU，矩阵密集（低精度、可量化）归 NPU/TPU，定制流水线归 FPGA；分工的依据是任务的并行模式与精度需求，不是厂商宣传。
- ** roofline 模型（Williams 等，2009 年）**：用计算强度（每字节访存的运算数）判断任务是计算受限还是访存受限；异构切分的第一个判断就是：这个算子在目标处理器上是算受限还是访存受限——访存受限的算子换更快的处理器收益有限，先解决带宽问题。
- **统一内存与异构内存架构（HSA）**：CPU 与加速器共享同一虚拟地址空间，指针可跨处理器传递，省掉显式拷贝；代价是缓存一致性与页面迁移的硬件/驱动复杂度。
- **任务图与依赖调度**：把应用表示为任务有向无环图，运行时按依赖关系把任务分发到不同处理器并重叠通信与计算；这是异构运行时（如 CUDA Graph、SYCL 任务图、OpenCL 命令队列）的共同思想。
- **精度与量化理论**：NPU/TPU 的能效优势很大程度上来自低精度（INT8、FP16、BF16）与量化；精度换能效的代价是模型准确率，需要逐任务验证，不能默认“量化无损”。

## 3. 技术路线

按“编程模型与内存模型”划分：

- **厂商原生路线（CUDA / ROCm / Metal 等）**：为某一厂商硬件深度优化，性能与工具链最成熟；代价是锁定——代码换厂商要重写。CUDA（NVIDIA, 2007 年）是这条路线的标杆，也是异构编程事实上的参照系。
- **跨厂商可移植路线（OpenCL、SYCL、HIP）**：一次编写、多厂商运行。OpenCL 是最早的跨厂商标准，抽象层较薄、样板代码多；SYCL 是基于标准 C++ 的单源编程模型（Khronos 标准，Intel oneAPI 的 DPC++ 是其实现之一），用 buffer/accessor 或统一共享内存（USM）表达数据移动；HIP 是 AMD 的可移植层，设计上贴近 CUDA 语法以降低迁移成本。可移植性的代价是：性能可移植性不等于代码可移植性——同一份代码在不同硬件上的性能可能差很多，仍需针对性调优。
- **框架托管路线（PyTorch、TensorFlow、JAX 等）**：程序员写框架代码，框架的后端负责切分到 CPU/GPU/TPU 并做算子融合与内存管理。这是今天 AI 异构计算的主流使用方式；代价是框架抽象层之下仍有硬件差异，性能问题定位要穿透框架。
- **统一内存与 Chiplet 集成路线**：把 CPU、GPU、NPU 做到同一封装内（Chiplet、3D 集成），用片内互连代替板级总线，搬运代价大幅下降；封装细节归 [Chiplet、先进封装与 3D IC](37-chiplet-packaging-3d.md)，本篇只讲它对异构协同的意义：搬运便宜了，切分就可以更细，协同的粒度可以从“算子级”下探到“子算子级”。
- **存算与光子加速平面路线**：把存算阵列、光子张量核作为新的异构单元加入协同（见 [存算一体与近存计算](75-compute-in-memory.md) 与 [光子计算](73-photonic-computing.md)）；它们的加入不改变异构协同的基本问题（切分、搬运、同步），只是把“处理器种类”从四种变成六种，把问题放大。

## 4. 系统架构

一个典型的异构节点由以下部分组成：

- **宿主 CPU**：操作系统、控制流、任务调度与异常处理；异构系统的“大脑”，但不是算力主力。
- **数据并行处理器（GPU）**：大规模线程并行，配高带宽显存（HBM，见 [HBM 各代](25-hbm-generations.md)）；适合训练与大规模推理。
- **矩阵加速器（NPU/TPU）**：脉动阵列或专用矩阵单元，低精度、高吞吐；适合量化后的推理，训练场景受限于精度与编程灵活性。
- **可重构单元（FPGA/CGRA）**：定制流水线，适合固定算法的低延迟场景；细节归 [可重构计算与 FPGA](78-reconfigurable-fpga.md)。
- **统一内存与互连**：CPU 与加速器之间的共享内存、缓存一致性协议与高速互连（NVLink、CXL、Infinity Fabric 等，物理细节归 [新型存储与互连：HBM 与 CXL](09-new-storage-interconnect.md)）；互连带宽决定协同粒度的下限——互连越慢，切分必须越粗。
- **运行时与调度器**：任务图执行、内存池管理、算子融合、负载均衡；运行时质量常比硬件峰值更决定实际性能。
- **编程模型层**：CUDA、HIP、SYCL、oneAPI、OpenCL 等；选型时要同时评估性能、人力成本与锁定风险，三者不可兼得。

## 5. 代表性实现与开源项目

只列真实存在的项目，不写未核实的性能数字：

- **NVIDIA CUDA 生态**：CUDA 语言、cuBLAS/cuDNN 等库、NCCL 集合通信库；异构编程的参照系，锁定风险最高。
- **AMD ROCm 与 HIP**：ROCm 是 AMD 的开放异构平台，HIP 提供 CUDA 风格的可移植编程层。
- **Intel oneAPI 与 DPC++**：oneAPI 是 Intel 的统一编程模型，DPC++ 是其 SYCL 实现，覆盖 CPU、GPU、FPGA。
- **Khronos SYCL 与 OpenCL**：跨厂商标准；SYCL 是单源 C++ 模型，OpenCL 是显式 API 模型。
- **PyTorch / TensorFlow / JAX**：框架托管路线的主流实现；后端覆盖 CPU、GPU、TPU，细节以各框架官方文档为准。
- **Apache TVM、MLIR**：编译器基础设施路线——把算子编译到多种硬件后端，目标是“一次描述、多硬件高性能”；仍在演进中，性能可移植性是开放问题。

## 6. 关键论文与标准

- Williams, S. 等，《Roofline: An Insightful Visual Performance Model for Multicore Architectures》, Communications of the ACM, 2009 年。
- Khronos SYCL 规范与 OpenCL 规范——跨厂商异构编程的标准文本。
- CUDA 编程指南（NVIDIA 官方文档）——厂商原生路线的参照文档。
- 暂无统一的跨厂商性能可移植性标准：代码可移植与性能可移植是两回事，目前没有标准能保证前者自动带来后者。

## 7. 当前实验结果

本节不写性能倍数：异构系统的加速比高度依赖任务切分、数据规模、互连与驱动版本，脱离测试条件的数字无法比较，本篇一律不采信。只写经核查的定性结论：

- CPU+GPU 协同已是工程现实：训练、推理、科学计算的生产系统每天都在用，编程模型与运行时均已成熟。
- CPU+GPU+NPU 协同在手机与 PC 上已是产品现实（SoC 内集成），但协同粒度仍较粗（应用级或算子级），细粒度协同仍受互连与调度开销限制。
- TPU 协同以框架托管为主（TensorFlow/JAX 生态），云端训练场景成熟，端侧与跨框架场景受限。
- 可移植编程模型的代码可移植性已实现，性能可移植性仍是开放问题——同一份 SYCL/OpenCL 代码在不同硬件上的性能差距需要针对性调优来弥合。

## 8. 技术瓶颈

- **搬运瓶颈**：处理器间的数据搬运（显存与内存之间、加速器之间）常先于计算成为瓶颈；统一内存缓解但不消除它（页面迁移本身有代价）。
- **同步与调度开销**：任务切得越细，调度与同步开销占比越大；协同粒度的最优值取决于互连速度，是动态变化的，不是一次调优能定死的。
- **编程模型分裂**：原生路线性能好但锁定，可移植路线通用但性能调优难，框架路线易用但穿透难；三者取舍没有银弹。
- **负载均衡**：不同处理器的速度差几个数量级，静态切分易导致快者等慢者；动态负载均衡需要运行时支持，且本身有开销。
- **精度与量化**：NPU/TPU 的低精度优势需要量化支撑；量化带来的准确率损失逐任务不同，需要验证流程，不能默认无损。
- **可观测性**：异构系统的性能问题定位要穿透框架、运行时、驱动与硬件四层，工具链仍不完善。
- **功耗与散热**：多处理器同时满载时，功耗墙与散热墙会先于算力墙到来；异构协同的调度必须考虑功耗预算（见 [液冷、能效与绿色超算](17-green-hpc-cooling.md) 的系统级背景）。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：CPU+GPU 协同已大规模生产运行，CPU+GPU+NPU 协同已在 SoC 产品中落地，但可移植性能、细粒度协同调度与存算/光子新单元的加入仍在演进中；异构计算是“已落地、未完成”的状态。

## 10. 未来研究问题

- **已有研究在做**：性能可移植的编译技术——让同一份代码在不同硬件上都接近原生性能（MLIR、TVM 等编译器基础设施是主战场）。
- **已有研究在做**：细粒度异构调度——在 Chiplet 集成、互连提速的背景下，把协同粒度从算子级下探，并动态适应负载与功耗。
- **已有研究在做**：存算、光子新单元的异构接入——新单元的编程模型与调度如何与现有异构运行时统一。
- **本文推测**：异构协同的下一个瓶颈可能不在硬件，而在“调度智能”——运行时能否根据任务、数据与功耗实时决定最优切分与放置；检验标准是运行时能否在不改应用代码的情况下持续给出接近手工调优的性能。
