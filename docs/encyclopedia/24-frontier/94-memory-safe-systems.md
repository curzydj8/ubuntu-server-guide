# 内存安全系统软件

## 1. 研究问题

系统软件的缺陷有一个顽固的统计特征：内存安全问题（越界读写、释放后使用、双重释放、整数溢出导致的越界）长期占据操作系统与浏览器等底层软件高危漏洞的大头。C 语言不检查这些错误，靠程序员自律；代码规模一大，自律就失效。内存安全系统软件要回答的问题是：能不能让“写出内存不安全代码”在系统层面变得困难或不可能，而不是靠事后测试与补丁追赶？本篇讲防线本身（语言、硬件、验证、迁移），Rust 的具体实践见 [95-rust-systems.md](95-rust-systems.md)。

## 2. 基础理论

- **空间安全**：每次内存访问都在对象边界内；越界读写是空间不安全的典型。
- **时间安全**：不访问已释放或未初始化的对象；释放后使用（use-after-free）是时间不安全的典型。
- **三类防线**：语言防线（编译期检查或运行时检查）、硬件防线（标签、能力、边界检查）、验证防线（证明代码无某类缺陷）；三者成本与保证强度不同。
- **安全与性能的取舍**：运行时检查（边界检查、垃圾回收）有开销；编译期检查（如 Rust 的借用检查）把代价移到编译时；硬件防线把代价移到芯片。

## 3. 技术路线

- **内存安全语言路线**：Rust（编译期所有权与借用检查，无垃圾回收）、Go、Swift、Ada/SPARK 等；Rust 是目前系统软件领域最受关注的一条，因其兼顾无垃圾回收与编译期安全。
- **硬件辅助路线**：ARM 的内存标记扩展（MTE，给内存贴标签、指针带标签， mismatch 即报错）、CHERI 能力架构（指针变为带边界与权限的能力，越界即陷阱）、Intel 的控制流强制技术（CET，防返回导向编程）；硬件防线可保护遗留 C 代码，但需要新芯片与工具链支持。
- **形式化验证路线**：证明代码无某类内存缺陷，或证明整个内核正确（seL4，见 [100-os-formal-verification.md](100-os-formal-verification.md)）；保证最强，成本最高。
- **沙箱与隔离路线**：即使部件不安全，也把它关进沙箱（见 [99-lightweight-sandbox.md](99-lightweight-sandbox.md)），让缺陷的影响局部化；这是“防不住就关住”的务实路线。
- **渐进迁移路线**：不重写整个系统，而是新驱动、新子系统用安全语言写，旧 C 代码逐步替换或加沙箱；Linux 内核的 Rust 集成是这条路线的代表。

## 4. 系统架构

内存安全系统软件没有单一架构，典型组合是分层防线：

- **语言层**：新代码用安全语言写，`unsafe` 或等价逃逸口集中在小范围并重点审查。
- **接口层**：安全语言与 C 代码之间的 FFI 边界是高危区：类型、生命周期与所有权在边界处最容易错位，需要显式契约与封装。
- **硬件层**：MTE、CHERI 等硬件机制为遗留代码与语言逃逸口提供运行时兜底。
- **验证层**：对安全关键部件（调度器、内存分配器、加密原语）做验证或高强度测试，作为最后一道证据。
- **部署层**：不可变 OS 镜像、签名更新、回滚机制，保证“安全的代码”确实是跑在机器上的代码。

## 5. 代表性实现与开源项目

- **Rust for Linux**：Linux 内核的 Rust 支持，初始支持随 Linux 6.1 于 2022 年 12 月合入；新驱动可用安全 Rust 编写，详见 95 篇。
- **Redox OS、Asterinas**：以 Rust 为主的整系统实现，见 95 篇。
- **CHERI**：剑桥大学等推动的能力硬件架构，有 FPGA 原型与 CheriBSD 等系统实现；商用芯片覆盖范围以官方发布为准（待核实）。
- **ARM MTE**：ARMv8.5-A 起的内存标记扩展，已在部分芯片与 Android 系统中用于堆内存错误检测；覆盖范围以官方发布为准（待核实）。
- **Microsoft 的安全语言实践**：Windows、Azure 等产品线逐步引入 Rust，公开资料表明内存安全问题在其漏洞统计中占重要比例，具体比例数字以官方发布为准（待核实），本篇不转载。
- **seL4**：以验证而非语言保证内存安全，见 100 篇。

- Rust 语言的所有权与借用检查机制见 Rust 官方文档与《The Rust Programming Language》；系统软件视角的论述见 95 篇来源。
- CHERI 架构见剑桥大学等机构的技术报告（完整引用以原文为准，待核实）。

- 暂无统一的“内存安全系统软件”标准：各语言、硬件与验证路线的保证口径不同，选型时需逐项核对保证范围。

## 7. 当前实验结果

本节不写漏洞比例数字：各厂商的漏洞统计口径（是否含内部发现、是否按年份归因）不同，脱离口径的数字不可比。只写定性结论：内存安全语言在新驱动与新系统中的采用已从倡议变为工程实践；硬件标记与能力架构已有原型与部分商用部署，但生态覆盖仍有限；形式化验证仍只覆盖小规模关键部件。三条防线目前是互补关系，没有一条单独宣称“解决了内存安全”。

## 8. 技术瓶颈

- **遗留代码规模**：Linux、Windows 等系统有数千万行 C 代码，重写不现实；迁移只能是渐进的，FFI 边界长期存在。
- **Unsafe 逃逸口**：Rust 等语言的安全保证在 `unsafe` 块内失效；驱动、硬件交互、FFI 处不可避免地要用 `unsafe`，审查质量决定实际安全。
- **硬件普及**：MTE、CHERI 需要新芯片、新编译器与新操作系统支持三方齐全，普及周期以硬件换代周期计。
- **性能与可预测性**：运行时检查与垃圾回收在实时与高性能场景有代价；编译期检查的代价是学习曲线与开发效率。
- **保证口径不清**：厂商与项目对“内存安全”的宣称口径不一（是“无某类缺陷”还是“某部件无缺陷”），选型时容易误读。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：内存安全语言已进入主流内核与产品，硬件防线已有部署，但遗留代码迁移、硬件普及与验证规模化均未完成，内存安全作为系统级目标仍在工程推进中。

## 10. 未来研究问题

- **已有研究在做**：C 代码的自动迁移与安全封装、FFI 边界的契约检查、MTE/CHERI 的编译器与操作系统支持。
- **已有研究在做**：安全语言在实时、驱动与固件场景的覆盖（中断处理、DMA、裸机启动等边界情况）。
- **本文推测**：未来系统更可能是“安全语言为主 + 硬件兜底 + 关键部件验证”的组合，而不是单一防线；检验标准是主流系统中三类防线的同时出现率。
- **本文推测**：内存安全的下一战场是“逻辑安全”（竞态、协议状态机错误），语言与验证的关注点可能从内存扩展到并发与状态；检验标准是相关工具与语言特性的出现。
