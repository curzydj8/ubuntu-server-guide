# 空间计算和三维界面

## 1. 研究问题

平面界面用了几十年，已经把“窗口、图标、菜单、指针”这套语言打磨得很成熟。空间计算把界面从平面搬进房间，立刻冒出一堆平面时代没有的问题：窗口应该放在哪儿——贴在墙上，还是悬在空中？人一转头，窗口是跟着人走，还是留在原地？虚拟物体被真实桌子挡住时，该显示还是该隐藏？手伸过去“点”一个悬空按钮时，系统怎么知道点中了没有？

本篇的研究问题就是：三维空间里的界面，应该遵循什么组织原则？答案不是“把平面界面立起来”——平面界面的很多假设（固定尺寸、固定朝向、鼠标精确点击）在空间里都不成立。三维界面需要自己的布局、交互与反馈语言。

## 2. 基础理论

- **空间锚点（spatial anchor）**：把虚拟内容绑定到真实世界某个位置的坐标记录；锚点稳，虚拟物才“钉得住”，不漂移、不抖动。
- **深度线索**：遮挡、大小、视差、阴影、运动视差共同告诉大脑“谁在前、谁在后”；三维界面必须同时满足这些线索，否则虚拟物看起来像“贴纸”而不是“物体”。
- **注视点渲染（foveated rendering）**：人眼中央视力高、周边低；只把注视点附近渲染到最高分辨率、周边降低分辨率，可以省算力。固定注视点渲染不需要眼动追踪，眼动注视点渲染需要眼动追踪（见 [手势、眼动和语音交互](116-gesture-eye-voice.md)）。
- **Fitts 定律的空间版**：目标越大、距离越近，指向越快越准；在空间里，“距离”是三维的、带深度的，手臂够不着的目标再大也难操作。
- **身体图式与本体感觉**：人对自己手臂、头部位置有天然感知；界面设计可以借用这种感知（比如把常用控制放在手边），而不是要求人盯着菜单找。

## 3. 技术路线

- **窗口悬浮路线**：把平面应用窗口悬在空间里，可移动、可缩放；visionOS 的做法接近这条路——熟悉、易迁移，但没有充分发挥三维优势。
- **体积应用路线**：应用本身就是三维的（立体模型、空间数据、虚拟场景），界面围绕体积内容组织；适合设计、医疗、教育类应用，开发成本最高。
- **环境融合路线**：界面元素附着在真实物体上（墙上的面板、桌上的工具盘）；最自然，但依赖可靠的空间建图与语义理解。
- **语音 + 注视主导路线**：用“看 + 说”代替“点 + 拖”，菜单变少、对话变多；适合双手被占用的场景，依赖语言模型与意图理解（见 [自然语言操作系统](121-natural-language-os.md)）。
- **标准优先路线**：用 OpenXR 等开放标准写应用，换设备不用重写；适合跨厂商部署，代价是各厂商特色能力暴露得较慢。

## 4. 系统架构

一个空间计算操作系统通常包含以下层次：

- **感知与追踪层**：SLAM 定位、手部与眼动追踪、平面与物体检测，输出持续更新的空间模型。
- **空间服务层**：锚点管理、空间网格、遮挡处理、共享空间（多人同场时各自看到一致的虚拟物位置）。
- **渲染层**：立体渲染、注视点渲染、空间音频、透视合成（视频透视下把虚拟与真实画面合成为一帧）。
- **界面框架层**：三维窗口管理、手势与注视事件、体积布局、系统级手势与语音入口。
- **应用层**：沉浸式应用、平面应用的空间化版本、系统应用（浏览器、设置、文件管理）。

系统架构的关键取舍在“延迟分配”：追踪与渲染的延迟预算只有十几毫秒量级，任何一层拖后腿都会表现为漂移、抖动或眩晕。

## 5. 代表性实现与开源项目

- **Apple visionOS**：Vision Pro 的操作系统，以眼动注视 + 手指捏合为主要交互，窗口悬浮于空间；visionOS 的空间小组件等后续更新以官方发布为准（待核实）。
- **Android XR**：谷歌、三星、高通联合开发的头显与眼镜平台，首款设备三星 Galaxy XR 于 2025 年 10 月发售；内置 Gemini 助手，说明语言模型已成为空间系统的标配入口。
- **Meta Horizon OS**：Quest 系列的操作系统，支持手部追踪、彩色透视与空间应用；其系统级手势与空间锚点能力以官方发布为准（待核实）。
- **OpenXR（Khronos Group）**：跨平台 XR 标准，1.0 版 2019 年、1.1 版 2024 年；Unity、Unreal、Godot、Blender 等引擎与工具均支持 OpenXR，是空间应用跨设备的事实接口。
- **WebXR Device API（W3C）**：浏览器里的 XR 接口，让网页可以直接启动头显会话；浏览器支持情况以官方发布为准（待核实）。
- **Godot / StereoKit**：开源引擎与开源 XR 框架，前者是通用开源游戏引擎（支持 OpenXR），后者是面向混合现实的轻量开源库；两者都适合学习三维界面原型——原型示例未实测，照文档搭建时以官方文档为准。
- **尚无代表性商用系统**：按“跨厂商空间锚点互通、三维界面设计语言统一”的定义，今天不存在通用的空间界面标准实现；各厂商的窗口、手势与锚点行为仍不互通。

## 6. 关键论文与标准

- OpenXR 1.0（Khronos Group，2019 年）与 OpenXR 1.1（2024 年）：XR 应用的开放 API 标准，是本篇第 5 节的主要依据。
- WebXR Device API（W3C）：浏览器 XR 的标准接口。
- 暂无统一标准：三维界面的布局规范、手势语义、空间锚点共享格式、眼动数据的隐私格式，均没有被广泛采纳的统一标准。

## 7. 当前实验结果

本节不写脱离测试条件的数字，只写经核查的定性结论与一个带条件的数字：

- **注视点渲染的收益是有条件的**：Meta 在 Quest Pro 开发者分享中报告，在其性能测试应用里，眼动注视点渲染相对不做注视点渲染约有 2 倍以内的提升，且相对固定注视点渲染的增益很小；该结论的测试条件是 Meta 自家的测试应用与默认分辨率，不可推广为通用结论。
- **眼动已成为量产输入**：Vision Pro、Quest Pro、PS VR2 等量产机型均已集成眼动追踪，眼动从研究配置变为系统级输入（见 116 篇）。
- **空间锚点仍不跨厂商**：同一房间的锚点在不同厂商设备间共享，仍需各自的云服务与格式转换；“一次建图、处处可用”尚未实现。

## 8. 技术瓶颈

- **锚点漂移与重定位**：光线变化、家具移动、长时间使用都会让锚点漂移；系统重定位失败时，虚拟物会“跳”到错误位置。
- **遮挡处理**：虚拟物被真实物体正确遮挡，需要实时的深度图；深度不准时，遮挡边缘会出现撕裂与闪烁。
- **深度布局的可用性**：东西放远了看不清、放近了挡视线、放多了找不着；三维空间没有平面界面的“滚动条”与“文件夹”这类成熟收纳手段。
- **输入精度**：空中手势没有物理支点，手会抖、会累；精细操作（选小目标、拖动滑块）仍不如鼠标可靠。
- **多用户一致性**：多人同场时，每个人看到的虚拟物位置、朝向必须一致；网络延迟与各自建图误差都会破坏一致性。
- **可访问性**：眼动与手势为主的界面对视力、肢体条件不同的用户并不友好；空间界面的无障碍设计仍在起步阶段。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：visionOS、Android XR、Horizon OS 等空间操作系统与 OpenXR 标准已经落地，但跨厂商锚点互通、三维界面设计语言与无障碍方案均未成熟，空间界面仍处工程化阶段。

## 10. 未来研究问题

- **已有研究在做**：更稳的锚点与重定位算法、实时深度遮挡、多人共享空间的一致性协议。
- **已有研究在做**：三维界面的设计语言与可用性度量——怎样才算“好用”的空间界面，目前连度量方法都没有共识。
- **本文推测**：空间界面的杀手级交互可能不是新手势，而是“语言 + 注视 + 手势”的组合：语言定意图、注视定目标、手势做确认；检验标准是组合交互在真实任务中是否比单一通道更快、更少误操作。
- **本文推测**：空间锚点可能先以厂商内闭环成熟（同一品牌设备间共享），再谈跨厂商互通；检验标准是同一厂商的多设备共享是否先于跨厂商标准落地。
