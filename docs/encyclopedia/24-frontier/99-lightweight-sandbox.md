# 轻量级沙箱和隔离机制

## 1. 研究问题

多租户云、函数计算、AI 智能体执行不可信代码，都面临同一个问题：怎么让一段不可信代码跑起来，又不让它碰到宿主与其他租户？传统虚拟机隔离强、启动慢、开销大；容器启动快、开销小，但共享宿主内核——宿主内核的一个漏洞就可能成为逃逸通道。轻量级沙箱要回答的问题是：能不能在“接近容器的启动速度与开销”与“接近虚拟机的隔离强度”之间找到可用的中间点？答案不是一种技术，而是一条光谱：不同位置对应不同的隔离强度、启动速度与兼容性。

## 2. 基础理论

- **隔离边界的位置**：边界可以画在系统调用处（拦截 syscall）、进程处（命名空间与 cgroup）、虚拟机处（硬件虚拟化）、语言运行时处（Wasm 沙箱）；边界越靠硬件，越强、越贵。
- **可信计算基（TCB）**：沙箱的安全依赖于边界内代码的正确性；TCB 越小，越容易审计与验证，但功能也越受限。
- **攻击面**：沙箱暴露给不可信代码的接口数量与复杂度；系统调用表越大，逃逸机会越多；gVisor 的思路正是缩小暴露给宿主内核的 syscall 子集。
- **纵深防御**：沙箱常与 seccomp、AppArmor/SELinux、只读文件系统、网络策略叠加；单层失效不等于整体失效。

## 3. 技术路线

- **容器加固路线（runc + 命名空间/cgroup + seccomp）**：Linux 命名空间隔离进程、网络、文件系统视图，cgroup 限资源，seccomp 过滤系统调用；启动接近进程速度，兼容性最好，隔离最弱——适合可信或半可信负载，不适合直接跑敌对代码。
- **用户态内核路线（gVisor）**：Google 的开源沙箱，Go 编写的用户态内核 Sentry 拦截并处理应用的系统调用，只把安全的子集转发给宿主内核；另有 KVM 平台模式借硬件虚拟化加速地址空间切换，但仍不是带 guest 内核的虚拟机；兼容性上部分 syscall 与 ioctl 未实现，依赖它们的原生库可能无法运行。
- **微虚拟机路线（Firecracker、Cloud Hypervisor）**：AWS 为 Lambda 与 Fargate 开发的 Firecracker 是 Rust 编写的虚拟机监视器，设备模型极简（virtio-net、virtio-block、virtio-vsock、串口等），无 BIOS、无 PCI/USB 仿真；每实例一个独立 guest 内核，隔离由硬件虚拟化保证，启动约百毫秒量级、每实例内存开销约数 MB（数字为项目公开资料，测试条件以官方发布为准，待核实）。
- **容器即虚拟机路线（Kata Containers）**：保持 OCI 容器接口（containerd/CRI-O、Kubernetes RuntimeClass），底层每个 Pod/容器跑在轻量 guest 虚拟机里；VMM 可选 QEMU、Cloud Hypervisor 或 Firecracker；用户侧仍是容器体验，隔离侧是硬件边界。
- **语言级沙箱路线（WebAssembly/WASI）**：Wasm 模块在受限的线性内存与能力化接口（WASI）内运行，无直接系统调用、无任意文件与网络访问；启动快、跨平台，适合函数与插件场景；限制是应用需编译为 Wasm 目标，现有原生应用迁移成本高。
- **机密沙箱路线（机密容器）**：Kata 的机密容器变体结合 Intel TDX、AMD SEV-SNP 等硬件内存加密，给沙箱再加一层“宿主也看不见”的保证；硬件与驱动支持条件以官方发布为准（待核实）。

## 4. 系统架构

典型轻量沙箱栈的组成部分：

- **运行时选择层**：按负载风险选运行时——可信负载用 runc，多租户 SaaS 用 gVisor，敌对代码用 Kata/Firecracker，函数与插件用 Wasm；选型是策略，不是品味。
- **边界实现**：Sentry（gVisor）、VMM + guest 内核（Firecracker/Kata）、Wasm 运行时（wasmtime 等）——三者边界位置不同，见第 3 节。
- **镜像与启动**：OCI 镜像复用是 Kata/gVisor 的优势；Firecracker 直接启动需要内核与根文件系统镜像；Wasm 需要 Wasm 模块；快照恢复（Firecracker snapshot）可把启动压到更低，但快照的熵与状态一致性需处理。
- **网络与存储接入**：virtio-net、virtiofs、vsock 等是沙箱内外的数据通道；通道本身也是攻击面，需最小化与审计。
- **可观测与排障**：沙箱内的日志、指标与追踪要能透出到宿主运维面，又不破坏隔离；无 Shell 的沙箱排障靠宿主侧工具（与 97 篇的节点 OS 排障问题同源）。

## 5. 代表性实现与开源项目

- **gVisor（runsc）**：Google 开源用户态内核沙箱，Go 实现，Sentry 拦截 syscall；GKE Sandbox 等产品用它做多租户隔离（版本以官方发布为准）。
- **Firecracker**：AWS 开源 Rust 微虚拟机监视器，KVM 之上，Lambda/Fargate 的底座（版本以官方发布为准）。
- **Kata Containers**：CNCF 项目，OCI 兼容的虚拟机化容器运行时，支持 QEMU、Cloud Hypervisor、Firecracker 多 VMM（版本以官方发布为准）。
- **Cloud Hypervisor**：Intel 主导的 Rust 微虚拟机监视器，面向云负载（版本以官方发布为准）。
- **WebAssembly 运行时（wasmtime、WasmEdge 等）**：WASI 沙箱的运行时实现，函数与插件场景的主力。
- **seccomp、AppArmor、SELinux**：Linux 内核与发行版的强制访问控制与 syscall 过滤机制，常与上述沙箱叠加使用。

## 6. 关键论文与标准

- gVisor、Firecracker、Kata Containers 的架构文档见各项目官方文档（版本以官方发布为准）。
- OCI 运行时与镜像规范是容器侧事实标准；WASI 规范见 Bytecode Alliance 公开资料（版本以官方发布为准）。
- 暂无统一的沙箱安全标准：各沙箱的威胁模型、保证范围与测试方法互不相同，选型时需逐项核对威胁模型，不可只看“隔离强”一词。

## 7. 当前实验结果

本节不写启动时间与开销的对比表：各沙箱的启动时间、内存开销高度依赖配置（guest 内核大小、快照与否、VMM 选择），脱离条件的数字不可比；第三方测评的毫秒数本篇一律不采信。只写定性结论：gVisor、Firecracker、Kata 均已在云厂商生产环境大规模使用，轻量沙箱从研究变为常规选项；Wasm 沙箱在函数与插件场景落地，但通用应用迁移仍有限；“容器即虚拟机”正在成为多租户 Kubernetes 的默认加强选项之一。

## 8. 技术瓶颈

- **兼容性**：gVisor 未实现的 syscall、Wasm 的目标编译要求、微虚拟机的设备模型限制，都会让部分应用无法直接运行；兼容性测试是选型必做项。
- **性能**：syscall 拦截、虚拟化进出、virtio 数据面都有开销；I/O 密集与 syscall 密集负载的开销最明显，需按负载实测（示例未实测）。
- **启动与密度**：微虚拟机每实例一个内核，密度与启动速度仍低于纯容器；快照恢复缓解启动问题，但引入状态管理复杂性。
- **可观测性**：沙箱越强，宿主越难“看进去”；调试、 profiling 与故障定位工具链仍在补齐。
- **威胁模型误读**：把 gVisor 当虚拟机、把容器当沙箱、把 Wasm 当万能隔离，都是常见误读；选型错误比技术缺陷更危险。

## 9. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：gVisor、Firecracker、Kata Containers、Wasm 运行时均已在云厂商与生产系统大规模使用，轻量沙箱作为一类技术已经成熟；未成熟的是机密沙箱、快照安全与统一选型标准，不是沙箱本身。

## 10. 未来研究问题

- **已有研究在做**：沙箱与机密计算的结合、快照恢复的安全性、Wasm 组件模型（Component Model）与 WASI 的演进。
- **已有研究在做**：AI 智能体代码执行沙箱（不可信代码 + 工具调用 + 网络访问的组合隔离），与 [06-frontier-ai-agents.md](06-frontier-ai-agents.md) 的智能体场景交叉。
- **本文推测**：运行时选择可能从“人工选型”走向“按风险自动选型”（调度器按负载风险等级自动挑 runc/gVisor/Kata）；检验标准是编排器是否出现风险感知的 RuntimeClass 选择机制。
- **本文推测**：Unikernel 与微虚拟机的合流可能继续（见 [93-unikernel.md](93-unikernel.md)）：guest 内核被裁剪到只剩应用所需功能时，两者在实践上趋同。
