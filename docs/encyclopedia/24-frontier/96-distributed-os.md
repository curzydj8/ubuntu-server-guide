# 分布式操作系统

## 1. 研究问题

集群、数据中心与边缘网络里，应用常常要同时用多台机器：进程在 A 机上跑，数据在 B 机上，GPU 在 C 机上。程序员不得不显式处理机器边界：哪台机器、怎么通信、对方挂了怎么办。分布式操作系统要回答的问题是：能不能把多台机器抽象成“一台计算机”——进程、文件、内存看起来是全局的，机器边界对应用透明？这个理想叫单系统映像（single system image, SSI）。它诱人，也昂贵：透明性的代价是跨机器的延迟、一致性与故障处理，全部要由系统扛下来。

## 2. 基础理论

- **单系统映像**：用户与应用看到一个统一的进程空间、文件命名空间与资源视图，任务可在机器间迁移而不改代码。
- **透明性维度**：位置透明（资源在哪不重要）、迁移透明（进程可移动）、复制透明（副本多少不重要）、故障透明（部分机器故障不影响应用）——透明性越强，系统付出的代价越大。
- **分布式共享内存（DSM）**：把多台机器的内存抽象成共享地址空间，页缺失时跨网络取页；一致性协议（写更新、写失效、释放一致性等）决定性能与正确性。
- **故障模型**：单机假设“要么全活、要么全挂”失效后，系统要面对部分故障、网络分区、消息丢失与重复；CAP 一类取舍（一致性、可用性、分区容忍）从数据库领域延伸到系统设计。

## 3. 技术路线

- **经典分布式 OS 路线**：Amoeba、Plan 9、Sprite 等研究系统：Amoeba 以微内核 + 分布式服务做透明计算，Plan 9 把“一切皆文件”扩展到网络（9P 协议让远程资源像本地文件一样访问），Sprite 探索进程迁移与分布式文件系统。这些系统证明了 SSI 在研究规模可行，但未成为主流。
- **多核即分布式路线（Barrelfish）**：把“多核机器本身就是分布式系统”作为出发点：每个核跑自己的内核实例，核间只用显式消息通信，不共享内存状态；系统状态以消息复制而非共享内存维护。Barrelfish 是苏黎世联邦理工学院与微软研究院的合作研究项目，面向异构多核与未来众核架构。
- **集群 SSI 路线**：MOSIX、Kerrighed 等：让 Linux 集群呈现单系统映像，进程可在节点间迁移、负载均衡；适用于批处理与高性能计算，云时代后热度下降。
- **云原生演变路线**：Kubernetes 等编排系统放弃了“单机幻觉”，改以声明式 API 与控制器做跨机器调度：应用显式声明“我要多少副本、什么资源”，系统保证实际状态趋近声明状态。透明性从“系统假装是一台机”退为“系统提供统一的调度与服务发现接口”——这是分布式 OS 思想在云时代的实际继承者，详见 [97-cloud-edge-os.md](97-cloud-edge-os.md)。
- **边缘与去中心化路线**：边缘节点、物联网网关之间的协同操作系统，节点时断时续、资源受限，SSI 的强假设不再成立，系统转向最终一致、离线可用与本地自治。

## 4. 系统架构

典型分布式 OS 的组成部分：

- **全局命名与定位**：文件、进程、设备的全局名字如何解析到具体机器；名字服务本身的可用性与一致性是关键。
- **进程迁移机制**：进程状态（地址空间、打开文件、网络连接）的捕获、传输与恢复；迁移时正在进行的网络连接与文件锁是最难处理的部分。
- **分布式一致性层**：DSM 的一致性协议、分布式锁、分布式文件系统的缓存一致性；协议选择决定延迟与可扩展性。
- **故障检测与恢复**：心跳、租约、多数派选举、检查点与重放；分区时系统要决定“继续服务可能不一致的部分”还是“停下来保一致”。
- **云原生变体**：API 服务器、控制器、调度器、服务发现、存储编排——把 SSI 的“透明”换成“显式声明 + 最终一致”。

## 5. 代表性实现与开源项目

- **Plan 9**：贝尔实验室的操作系统，9P 协议与“一切皆文件”的网络扩展影响了后来的许多系统；现为研究与教学系统，生产部署以官方发布为准（待核实）。
- **Barrelfish**：ETH Zürich 与微软研究院的多核分布式 OS 研究项目，核间消息传递架构；研究性质，未作为通用产品发布。
- **MOSIX / Kerrighed**：Linux 集群的单系统映像扩展，进程迁移与负载均衡；维护状态以官方发布为准（待核实）。
- **Kubernetes**：云原生编排系统，不是传统意义上的分布式 OS，但继承了其调度与资源抽象问题；详见 97 篇。
- **Amoeba、Sprite**：历史研究系统，已停止维护；本篇列为思想来源，不作为选型依据。

## 7. 当前实验结果

本节不写性能数字：DSM 与进程迁移的性能高度依赖网络延迟、应用访存模式与集群规模，脱离条件的数字不可比。只写定性结论：SSI 在中小规模、同构集群与批处理负载上可行；规模一大、网络一慢、负载一杂，透明性的代价就超过收益——这是云原生放弃强 SSI、转向声明式编排的根本原因。Barrelfish 一类“多核即分布式”的思想仍在影响异构多核与 Chiplet 时代的系统设计，但尚未成为主流内核架构。

## 8. 技术瓶颈

- **延迟**：跨机器操作比本地操作慢几个数量级；把本地假设（页缺失、系统调用、锁）透明地搬到网络上，延迟会被放大。
- **一致性代价**：强一致需要跨机器协调，协调的延迟与消息量随节点数增长；弱一致则把复杂性推给应用。
- **部分故障**：网络分区时“谁说了算”没有廉价答案；多数派、租约与人工干预各有代价。
- **异构性**：节点架构、算力、网络能力不同，统一抽象要么迁就最弱节点、要么暴露差异——两种选择都破坏透明性。
- **调试与可观测性**：跨机器的故障现场分散在多台机器的日志里，因果追踪需要分布式追踪工具链，不是单机调试器的简单扩展。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：经典 SSI 系统停留在研究与小众部署，云原生编排继承了其问题但放弃了其“单机幻觉”目标，严格意义上的分布式操作系统至今没有主流生产形态。

## 10. 未来研究问题

- **已有研究在做**：异构多核与 Chiplet 架构下的核间通信模型、CXL 内存池化对 DSM 的影响（见本站新型存储与互连相关文章）。
- **已有研究在做**：边缘节点的去中心化协同、离线可用与最终一致的系统模型。
- **本文推测**：分布式 OS 的下一形态可能不是“更透明的单机”，而是“更诚实的分布式原语”——系统显式暴露位置、延迟与故障语义，让应用按需选择；检验标准是新系统是否停止追求完全透明。
- **本文推测**：内存池化与高速互连可能让 DSM 在机架尺度上复活（延迟足够低时透明性代价可接受）；检验标准是机架内 DSM 原型是否出现可用的性能数据。
