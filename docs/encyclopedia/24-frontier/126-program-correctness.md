# 程序正确性证明

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章。总览讲“形式化方法整体”；本篇讲它最落地的形态——对一段具体程序证明正确性。模型检测查的是抽象模型，定理证明器提供的是通用引擎，而程序正确性证明回答的是工程师真正关心的问题：这段代码，在这些输入假设下，是不是一定产生符合规约的输出、一定不越界、不泄漏、不死锁？

## 1. 研究问题

测试只能证明“这些输入下没出问题”。程序正确性证明要把“这些输入”换成“所有满足前置条件的输入”，把“没出问题”换成“满足后置条件”。为此需要三样东西：程序的数学语义、规约的精确写法、从代码到逻辑命题的可靠翻译。缺任何一样，证明都是空中楼阁。历史上，图灵在 1949 年就勾勒过程序正确性论证的思路；Floyd 与 Hoare 在 1960 年代末建立了公理化传统，使“证明程序”从哲学讨论变成可操作的演算。

## 2. 基础理论

- **Hoare 逻辑**：Hoare 在 1969 年《An Axiomatic Basis for Computer Programming》中提出的三元组 {P} S {Q}——若 P 在 S 执行前成立，则 S 执行后 Q 成立。顺序、条件、循环各有推理规则，循环规则的核心是循环不变式：一个在每次迭代前后都保持的断言。
- **部分正确性与完全正确性**：部分正确性只保证“若程序停机，则结果满足后置条件”；完全正确性还要保证“程序一定停机”。终止性证明通常需要一个随迭代严格递减的良基度量（如自然数），这是容易被忽略的第二半。
- **最弱前置条件（weakest precondition）**：Dijkstra 的谓词变换器 wp(S, Q)——使 S 执行后 Q 成立的最弱前提。验证工具把“程序满足规约”翻译成“前置条件蕴含最弱前置条件”，再交给求解器；Frama-C 的 WP 插件即按此思路实现。
- **分离逻辑（separation logic）**：在 Hoare 逻辑上加入“堆的分离合取”，让关于指针与堆的推理可以局部化——推理一块内存时不必同时谈论整个堆；这是验证带指针程序的关键扩展。
- **精化（refinement）**：实现行为是规约行为的子集，即实现精化规约；seL4 与 CompCert 的正确性定理本质上都是精化陈述，详见[操作系统验证](129-os-verification-formal.md)与[编译器正确性](128-compiler-correctness.md)。

## 3. 技术路线

- **契约式演绎验证路线**：在代码中写 requires（前置条件）、ensures（后置条件）、invariant（循环不变式），工具生成验证条件、用 SMT 求解器 discharging；Dafny、Frama-C、SPARK、Verus、Creusot 属此路线，是目前工程化程度最高的程序验证形态。
- **交互式证明路线**：在 Coq/Rocq、Isabelle/HOL 中对程序做深度证明，适合规约复杂、自动化求解器搞不定的部分；代价是人力，见[自动定理证明](124-automated-theorem-proving.md)。
- **分离逻辑与堆推理路线**：针对指针、并发数据结构，用分离逻辑与并发分离逻辑做局部推理；VeriFast、Iris（Coq 上的并发分离逻辑框架）是代表。
- **轻量契约与运行时检查路线**：把契约降级为运行时断言或类型系统的一部分（如 Rust 的所有权检查），不求完整证明，但以极低成本排除一整类错误；这是“证明”向“工程实践”让渡的一步，详见[类型系统和依赖类型](127-type-systems.md)。

## 4. 系统架构

一套契约式验证工作流通常由以下部分组成：

- **契约标注层**：源码中的规约注释或语言内置的契约语法，写前置条件、后置条件、不变量与辅助断言。
- **验证条件生成器**：按最弱前置条件或类似演算，把“代码 + 契约”翻译成逻辑公式（验证条件）；中间验证语言如 Boogie、Why3、Viper 让多个前端共享同一生成器与求解器接口。
- **求解与交互层**：SMT 求解器（如 Z3）自动 discharging 大部分验证条件；剩余条件交给人工交互证明或提示用户补不变式。
- **反例与定位层**：求解器给出反例模型时，工具把它还原成“哪条契约、在哪次调用、取什么输入会违反”，否则开发者无法行动。

## 5. 代表性实现与开源项目

- **Dafny**：微软研究院的验证语言，契约写进语言语法，验证条件交给 Z3，可编译到 C#、Java、JavaScript、Go、Python；2009 年前后由 Rustan Leino 推出。
- **Frama-C**：面向 C 程序的验证平台，其 WP 插件实现最弱前置条件演算，ACSL 为其契约标注语言。
- **SPARK**：Ada 的可验证子集，1980 年代末成型，在航空、国防、铁路领域有长期工业部署；以契约与信息流分析见长。
- **Verus**：面向 Rust 的验证器，用契约式规约加 SMT 求解，相关论文发表于 OOPSLA 2023（以官方发布为准，待核实）。
- **VeriFast**：面向 C 与 Java 的分离逻辑验证器，适合指针密集型程序。
- **VST（Verified Software Toolchain）**：在 Coq 中用分离逻辑验证 C 程序的工具链，与 CompCert 的语义衔接。

## 6. 关键论文与标准

- Hoare，《An Axiomatic Basis for Computer Programming》，Communications of the ACM，1969。
- Floyd 关于程序正确性论证的早期工作（1960 年代末），具体篇名以官方发布为准（待核实）。
- Dijkstra 关于最弱前置条件的论述，具体出处以官方发布为准（待核实）。
- 暂无统一标准：契约语言（ACSL、Dafny 规约、SPARK 契约）各工具自成体系；功能安全标准对验证活动的要求见[安全关键软件](131-safety-critical-software.md)。

## 8. 技术瓶颈

- **不变式难**：循环不变式与辅助断言是契约验证中最需要人工智慧的部分；机器擅长检查不变式是否成立，不擅长发明它。
- **规约与代码的双重维护**：代码改了，契约常常要同步改；契约漂移后，证明通过的结论对应的是旧规约。
- **堆与并发的推理成本**：指针别名、并发交错使验证条件迅速复杂化；分离逻辑缓解了局部性问题，但并发分离逻辑的学习与使用门槛仍然很高。
- **求解器边界**：非线性算术、复杂数据结构、量化公式常超出 SMT 求解器的舒适区，验证条件卡住时开发者得到的往往只是一句“无法证明”，而不是可行动的线索。
- **“证了什么”的审计**：契约本身可能过弱——证明了“函数不崩溃”，不等于证明了“函数算对了”；规约强度评审是验证项目中不可外包的一环。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：Dafny、Frama-C、SPARK 在真实工业项目中有部署与可复查证据，但不变式发明、堆与并发推理、求解器边界仍使全量应用受限。

## 10. 未来研究问题

- **已有研究在做**：用大语言模型辅助生成循环不变式与契约，再由求解器或证明助手严格检查——生成可猜，检查不可含糊。
- **已有研究在做**：把契约验证接入 Rust、Go 等主流语言工具链（Verus、Creusot 方向），降低“换语言才能验证”的门槛。
- **本文推测**：契约验证最可能先以“关键函数契约化”的粒度普及（排序、加密、解析、状态机核心），而不是“全代码库契约化”；检验标准是关键模块的契约覆盖率是否成为代码评审的常规项。
