# 自然语言操作系统

## 1. 研究问题

操作系统几十年来的接口是窗口、菜单、图标与命令行：人要先学会系统的语言，系统才听得懂人。自然语言操作系统要回答的问题反过来：系统能不能先学会人的语言，让人直接说“把上周的会议纪要整理出来发给小李”，系统自己去完成？

这个问题之所以现在才被认真提出来，是因为语言模型补上了最后一块拼图：此前的语音助手只能执行预设的固定命令（“定个闹钟”“放首歌”），语言模型则能理解开放表述、拆解多步任务、调用工具完成操作。但“能理解”不等于“能安全地操作系统”——删文件、发消息、花钱、改配置，这些操作一旦做错就无法挽回。自然语言越方便，系统越需要“确认、回滚与留痕”。

本篇讲两种形态与四道关；语言模型本身的原理归 AI Agent 相关篇目（见 [AI Agent 前沿：多智能体与自主研究](06-frontier-ai-agents.md)），本篇只讲它作为操作系统接口时的系统问题。

## 2. 基础理论

- **意图理解与槽位填充**：把一句话解析成“想干什么”（意图）与“关键参数”（槽位，如时间、对象、收件人）；这是传统对话系统的基本框架，语言模型把它从固定模板扩展到了开放表述。
- **工具调用（function calling）**：语言模型输出结构化的工具调用请求，系统执行对应的 API（发邮件、查日历、改文件）；工具调用是语言模型从“会说”走向“会做”的关键机制。
- **Agent 编排**：多步任务需要规划、执行、检查、纠错的循环；语言模型既做规划者、又做执行者时，错误会在循环里放大。
- **权限模型**：操作系统用用户、组、能力（capability）限制程序能做什么；自然语言系统必须把“这句话授权了什么”映射到同一套权限模型上，否则一句话就能越权。
- **可审计性**：系统必须记录“谁在什么时候、用什么话、授权了什么操作、实际执行了什么”；没有审计日志的自然语言操作，出了问题无法追责、无法复现。

## 3. 技术路线

- **助手路线**：语言模型作为应用内的助手，帮人写、帮人查、帮人总结，但不直接操作系统级能力；人在每一步确认结果。优点是安全、易落地，缺点是人仍是执行者，省力有限。这是今天主流产品的形态。
- **编排者路线**：语言模型作为系统级编排者，直接调用系统能力完成多步任务（整理文件、发消息、订行程）；优点是省力最多，缺点是误操作风险最大，需要确认、回滚与审计三件套。
- **空间助手路线**：语言模型作为空间计算系统的入口，与注视、手势组合使用（见 [多模态人机交互](120-multimodal-interaction.md)）；语言定意图、注视定目标、手势做确认，三者分工降低误操作。
- **端侧小模型路线**：把语言理解放在设备端，敏感操作不经过云端；优点是隐私与延迟，缺点是模型能力受限，复杂任务仍需云端大模型。
- **形式化护栏路线**：用规则、类型系统或验证器约束语言模型的输出——工具调用必须符合事先声明的权限与参数范围，不符合的直接拒绝；这是“让语言模型安全地操作系统”最被看好的工程方向，但护栏本身的设计仍在探索中。

## 4. 系统架构

一个自然语言操作系统通常包含以下层次：

- **语言理解层**：语音转文字（可选）、意图理解、任务拆解，输出结构化的执行计划。
- **权限与确认层**：把执行计划映射到权限模型；高风险操作（删除、发送、支付、改配置）触发确认，确认时必须向用户展示“将要做什么、影响什么、能否撤销”。
- **工具与执行层**：应用 API、系统 API、文件操作、网络请求的统一调用入口；所有调用都经过权限检查，不存在绕过检查的直通路径。
- **检查与回滚层**：执行后检查结果是否符合预期；可撤销的操作提供回滚，不可撤销的操作在执行前必须明确告知。
- **审计层**：完整记录原始表述、执行计划、每次工具调用与结果；日志本身需要防篡改，至少要做到用户可查。

这个架构的关键取舍在“确认的粒度”：每步都确认，人会烦到关掉助手；从不确认，错一次就失去信任。好的系统按风险分级确认——低风险自动执行、高风险逐项确认、不可撤销的操作必须二次确认。

## 5. 代表性实现与开源项目

只列真实存在的产品与方向，能力描述以官方发布为准（待核实）：

- **系统级助手入口**：Android XR 内置 Gemini、visionOS 内置 Siri、Windows 与 macOS 的系统级 AI 助手入口，均属于“助手路线”的量产形态；它们能帮人查、帮人写、帮人总结，但系统级自动执行能力以各厂商官方发布为准。
- **Agent 式操作系统探索**：多家厂商与研究机构在探索“语言模型直接操作系统”的原型（桌面任务自动化、手机任务自动化）；这些多为研究演示或限定场景产品，不是面向普通用户的通用操作系统，演示与量产严格区分。
- **开源 Agent 框架**：面向桌面与浏览器的开源 Agent 框架（如 OSWorld 等研究基准与配套工具）属于研究工具，用于度量 Agent 完成操作系统任务的能力；基准分数的测试条件以论文与官方发布为准，不可直接等同于日常可用性。
- **尚无代表性商用系统**：按“用户只用自然语言、系统全自动完成日常操作系统任务、且误操作率可接受”的定义，今天不存在商用的自然语言操作系统；现有产品或是助手、或是限定场景的 Agent 原型。

## 6. 关键论文与标准

- 工具调用与 Agent 任务完成的相关公开研究：语言模型调用外部工具、多步任务规划的基准与方法，见公开文献（具体篇目以论文原文为准，本文不转载未核对的引用）。
- OSWorld 等操作系统任务基准：度量 Agent 在真实操作系统环境里完成任务的能力，是“Agent 能不能操作系统”相对可比的度量之一；基准分数的测试条件以论文原文为准。
- 暂无统一标准：自然语言操作的权限模型、确认规范、审计日志格式、误操作率的度量方法，均没有被广泛采纳的标准；不同产品的“Agent 能力”宣传不可直接比较。

## 7. 当前实验结果

本节只写定性结论，不写脱离测试条件的数字：

- **助手路线已经量产**：系统级 AI 助手入口已进入主流操作系统与空间计算系统；写、查、总结类任务是其最可靠的场景。
- **编排者路线的可靠性仍有限**：多步任务的成功率随步骤数快速下降；一步错、步步错的连锁失败是公开报告的现象，具体数字因基准与任务而异，本篇不转载单一数字。
- **确认机制是有效的护栏**：高风险操作前展示执行计划并请用户确认，能拦截大部分误操作；但确认本身也会带来疲劳，确认疲劳后的“无脑点确认”会抵消护栏效果。
- **不写进本节的数字**：各厂商宣传的“Agent 任务成功率百分之几”“效率提升百分之几”——因基准、任务集、允许的人工干预不同，本篇不采信、不转载。

## 8. 技术瓶颈

- **误操作风险**：语言天然有歧义——“删掉旧文件”里的“旧”是什么意思？系统猜错一次，损失可能无法挽回。
- **不可复现性**：同一句话在不同时间、不同上下文可能得到不同的执行计划；不可复现的操作难以测试、难以审计、难以追责。
- **幻觉与工具误用**：语言模型可能编造不存在的文件、联系人或参数，并据此调用工具；工具层必须校验每个参数的真实性，不能信任模型的输出。
- **权限映射难题**：自然语言的授权边界是模糊的（“帮我整理一下”授权了删除吗？），操作系统的权限模型是精确的；两者之间的映射没有现成答案。
- **提示注入**：网页、邮件、文件里的恶意文本可能被语言模型当成指令执行；系统必须区分“用户的话”与“环境里的话”，这是自然语言操作系统特有的安全难题。
- **确认疲劳**：确认太多，人会关掉确认；确认太少，误操作会漏网；确认策略本身需要按风险与用户习惯动态调整。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：助手路线的产品已经量产，但“语言模型作为系统级编排者、全自动完成日常操作系统任务”的形态仍处研究与限定场景阶段，权限、误操作、不可复现性与可审计性四道关均未解决。

## 10. 未来研究问题

- **已有研究在做**：形式化护栏（约束工具调用的权限与参数范围）、提示注入的防御、Agent 任务基准的完善、确认策略的动态调整。
- **已有研究在做**：端侧小模型与云端大模型的分工——敏感操作本地化、复杂推理云端化。
- **本文推测**：自然语言操作系统最可能先在“只读 + 低风险操作”场景成熟（查、总结、整理草稿），再逐步放开“写操作”；检验标准是低风险场景的误操作率是否长期保持在可接受水平。
- **本文推测**：审计日志可能先于技术突破成为监管要求——系统必须能回答“这句话导致了什么操作”；检验标准是主流平台是否出台自然语言操作的审计规范。
