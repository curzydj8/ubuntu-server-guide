# AI 模型和 Agent 安全

## 1. 研究问题

传统应用的安全边界是“谁能调用哪个接口”；Agent 系统多了一层“模型能替用户做什么”。一个 Agent 可能读取邮箱、查询数据库、调用外部 API、执行脚本、代表用户发消息——它的能力越大，一次错误判断或一次被污染的输入造成的后果也越大。本篇的研究问题是：如何给模型与 Agent 划出可执行的权限边界，并让越权行为在发生前被拦住、发生后可追溯？

合法研究范围声明：本篇只面向自有系统、授权系统或隔离靶场上的防御研究；未授权测试他人系统是违法行为，本文不提供相关指导。

## 2. 基础理论

- **最小权限原则**：每个组件只拥有完成其任务所必需的最小权限；这是传统安全原则在 Agent 系统中的直接延伸，也是 OWASP 2025 版“过度授权（Excessive Agency）”风险的对应防御。
- **威胁建模**：用 NIST AI RMF 的映射（Map）功能与 MITRE ATLAS 的战术结构，列出“攻击者能接触系统的哪些点、能造成哪些影响”，再据此排防御优先级。
- **纵深防御**：不依赖模型“自己判断对错”这一单点；权限、网关、校验、确认、审计多层叠加。
- **可审计性**：Agent 的每一次工具调用都应留下“谁授权、调了什么、参数是什么、结果如何”的记录，否则事后无法定责与复盘。

## 3. 技术路线

- **身份与权限路线**：Agent 以独立身份运行，而不是复用用户的全部权限；按任务颁发短期、有范围限制的凭证；敏感操作（如转账、删除、对外发送）必须经过二次确认或人工审批。
- **工具网关路线**：所有工具调用都经过一个网关：网关做参数校验、允许清单（allowlist）检查、速率限制与敏感操作拦截；模型不能直接接触底层凭证与原始接口。
- **上下文隔离路线**：区分可信指令（系统指令、开发者指令、用户本人指令）与不可信数据（检索到的网页、邮件、文件、工具返回结果）；不可信数据默认只作“参考信息”，不直接获得指令地位。具体隔离机制见 [提示注入和工具调用风险](103-prompt-injection-risks.md)。
- **运行时监控路线**：监控 Agent 的调用序列是否偏离任务基线（如正常任务只读 3 个接口，某次却枚举了全部接口），偏离即告警或熔断。

## 4. 系统架构

一个防御较完整的 Agent 系统通常包括：

- **Agent 运行时**：模型服务与任务编排；不直接持有长期高权限凭证。
- **工具网关**：统一的工具调用入口，负责鉴权、参数校验、允许清单、审计日志。
- **权限服务**：按任务签发短期令牌，支持按工具、按资源、按金额或数量设限。
- **确认与审批层**：敏感操作在执行前暂停并呈现“将要做什么、影响什么”，等用户或审批人确认后才放行。
- **审计与回滚**：完整的调用日志与可撤销的操作设计（如先写草稿、后正式提交；删除类操作先入回收站）。

## 5. 代表性实现与开源项目

只列防御与治理侧的真实项目与框架：

- **MITRE ATLAS**：AI 威胁建模知识库，可用于梳理 Agent 系统的攻击面。
- **OWASP GenAI Security Project**：LLM 与 Agentic 应用风险指南，用于风险优先级排序。
- **NIST AI RMF Playbook**：NIST 风险管理框架的配套实践建议，可按组织规模裁剪使用。
- 尚无“开箱即用的通用 Agent 安全网关标准产品”这一统一说法：各厂商与开源项目的网关、确认与审计能力差异较大，选型以官方文档为准（待核实）。

## 6. 关键论文与标准

- NIST AI 100-1（AI RMF 1.0，2023 年 1 月）：四项功能 Govern / Map / Measure / Manage。
- NIST AI 100-2e2025（2025 年 3 月）：对抗机器学习分类，含生成式 AI 的滥用与注入类别。
- OWASP Top 10 for LLM Applications 2025 版：LLM06 过度授权、LLM01 提示注入等类别。
- 暂无统一的 Agent 安全强制标准：Agent 权限、确认与审计的具体要求以各平台官方文档与组织内部制度为准（待核实）。

## 7. 当前实验结果

本节不写脱离测试条件的拦截率数字。只写定性结论：公开披露的 EchoLeak（CVE-2025-32711，见总览）说明，即使是成熟厂商的助手产品，外部数据进入上下文后也可能驱动助手访问超出用户当次意图的数据；微软已在服务端修复并称无实际利用证据。这一案例的防御启示是架构性的：仅靠模型自身“识别恶意指令”不够，必须靠权限隔离与输出通道控制兜底。其他厂商的同类公开案例未系统核对，未写入正文。

## 8. 技术瓶颈

- **权限粒度与任务灵活性的冲突**：Agent 任务千变万化，事前把权限划得太细会频繁打断用户，划得太粗则失去保护意义。
- **确认疲劳**：确认弹窗太多，用户会习惯性点“同意”，确认机制随之失效；需要按风险分级，只对真正敏感的操作弹确认。
- **多 Agent 协作的责任边界**：一个 Agent 的输出成为另一个 Agent 的输入时，权限与信任如何传递，目前缺乏成熟的通用做法。
- **日志与隐私的平衡**：审计越完整，日志本身就越敏感；日志的访问控制与保留期限需要单独设计。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：权限最小化、工具网关、人工确认等手段在传统安全中成熟，但在 Agent 语境下的默认集成、跨平台标准与效果度量仍在发展中。

## 10. 未来研究问题

- **已有研究在做**：Agent 权限的声明式策略语言——能否像写防火墙规则一样写“这个 Agent 能读什么、不能动什么”。
- **已有研究在做**：基于任务基线的异常检测——从历史调用序列中学习正常模式，偏离即告警。
- **本文推测**：Agent 安全可能先以“平台默认能力”（网关、确认、审计三件套默认开启）的形态普及，而不是以独立安全产品的形态普及；检验标准是主流 Agent 框架是否把这些能力设为默认而非可选。
