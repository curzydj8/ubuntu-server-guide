# 提示注入和工具调用风险

## 1. 研究问题

大语言模型把所有输入文本放在同一个上下文里处理：系统指令、用户问题、检索到的网页、邮件正文、工具返回结果，在模型看来都是“文本”。传统程序用语法与类型严格区分“代码”与“数据”，模型没有这道硬墙。于是，来自不可信渠道的文本就有可能影响模型后续的行为选择——这就是提示注入。直接注入指通过用户输入渠道进入的干扰；间接注入指通过外部数据（网页、文件、邮件、工具返回）进入的干扰，后者在 Agent 系统中尤其值得警惕，因为用户本人可能根本没见过那段文本。

本篇只讲原理、风险、检测、防御与评估。本篇不写可直接用于注入的操作步骤与可用载荷，不给可复制的攻击提示词；凡是拿不准是否越界的写法，一律不写。

合法研究范围声明：防御研究只在自有系统、授权系统或隔离靶场上进行；未授权测试他人系统是违法行为，本文不提供相关指导。

## 2. 基础理论

- **指令与数据不分**：模型没有内置的指令/数据分隔机制；英国国家网络安全中心（NCSC）2025 年 12 月的公开提示也指出，不应把提示注入简单类比为 SQL 注入，因为后者有参数化查询这样的结构性解法，而前者缺乏对应的硬边界。这一判断的原文表述以 NCSC 官方发布为准（待核实）。
- **OWASP 分类**：OWASP Top 10 for LLM Applications 2025 版把提示注入列为 LLM01 首位风险，并区分直接注入、间接注入与多模态注入（指令藏在图像或音频等伴随内容中）。
- **NIST 分类**：NIST AI 100-2e2025 把直接提示注入编为 NISTAML.018、间接提示注入编为 NISTAML.015，并明确指出现有缓解措施不能对所有对抗技术提供完全保护。
- **工具调用放大效应**：没有工具的模型最多“说错话”；接上工具的 Agent 可能“做错事”——读文件、发消息、改数据。注入风险因此从“输出风险”升级为“操作风险”，防御重心必须从“管住嘴”转向“管住手”（见 102 篇的权限与网关设计）。

## 3. 技术路线

防御沿四条路线展开，没有一条能单独解决问题：

- **架构隔离路线**：给每段上下文标注来源与可信等级；不可信内容默认只能作为“被讨论的对象”，不能直接成为“要执行的指令”；工具网关只接受来自可信决策路径的调用请求。
- **权限收紧路线**：Agent 的工具权限按任务最小化；敏感操作（对外发送、删除、修改、支付类）必须经过人工确认；输出通道（如渲染链接、图片、引用）不默认携带敏感数据。
- **检测路线**：在输入侧与输出侧做检测——输入侧识别“文本试图改变任务目标”的语义信号，输出侧检查“将要执行的操作是否超出本次任务范围”；检测结果用于告警与阻断，而非仅记日志。
- **评估与回归路线**：用授权范围内的红队评估（见 111 篇）持续检验注入防御，把新发现的失效模式沉淀为回归测试用例。

## 4. 系统架构

一个针对注入风险的防御架构通常包括：

- **来源标注层**：检索、邮件、文件、工具返回等外部内容进入上下文时携带来源标签；系统在呈现与决策时保留这层标签，不让它在处理中丢失。
- **输入处理层**：对不可信内容做结构化处理（如只抽取事实字段、剥离指令性表述的执行地位），而不是原样拼进指令位置。
- **决策与网关层**：模型输出的工具调用请求先经过网关校验——调用是否在允许清单内、参数是否在任务范围内、是否需要人工确认。
- **输出审查层**：对外输出在发送前检查是否夹带敏感数据或超出任务范围的引用与链接；高风险输出先拦截、后人工复核。
- **审计层**：记录“哪段外部内容进入了上下文、模型据此做了哪些调用”，便于事后还原注入链路。

## 5. 代表性实现与开源项目

只列防御与评估侧的真实项目，不写攻击探针的具体用法：

- **OWASP GenAI Security Project**：LLM01 提示注入的公开风险说明与缓解建议。
- **Microsoft PyRIT 与 NVIDIA garak**：在授权范围内对自有系统做注入相关评估的开源框架（评估方法见 111 篇；本篇不写其探针内容）。
- **各厂商的注入分类器与护栏服务**：微软等厂商公开表示在其助手产品中部署了跨提示注入分类器等防护；具体模型、阈值与覆盖范围以厂商官方说明为准（待核实）。
- 尚无“能彻底防住注入”的通用产品或标准：NIST 与 NCSC 的公开判断均指向“缓解而非根除”，选型时应以此为前提。

## 6. 关键论文与标准

- OWASP Top 10 for LLM Applications 2025 版，LLM01 提示注入。
- NIST AI 100-2e2025（2025 年 3 月）：NISTAML.015 间接提示注入、NISTAML.018 直接提示注入，及“现有缓解不能提供完全保护”的结论。
- Greshake 等《Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection》（arXiv:2302.12173，2023 年）：间接提示注入概念的早期公开研究；本篇只引用其概念与结论，不复述其实验细节。
- 暂无统一的提示注入防御强制标准：相关缓解建议散见于 OWASP、NIST 与各厂商文档，以官方发布为准（待核实）。

## 7. 当前实验结果

本节不写任何可复现的注入成功率数字（不同评估集与模型下的数字不可比，且易被误读为操作指南）。只写经公开披露核查的定性结论：

- EchoLeak（CVE-2025-32711）：微软 2025 年 6 月公开披露的 Microsoft 365 Copilot 漏洞，由 Aim Security（Aim Labs）负责任披露；微软称已在 2025 年 5 月服务端修复、无需用户操作、无证据表明已被实际利用；微软自评 CVSS 9.3（严重），NVD 后续 enrich 给出 7.5 分，两者评分口径不同，均以官方记录为准。本篇只复述上述披露口径，不写漏洞链路的技术细节。
- 该案例的防御启示是：即使不点击任何内容，外部邮件进入检索上下文后也可能影响助手行为；因此“用户是否点击”不能作为安全边界，边界必须设在权限、输出通道与人工确认上。

## 8. 技术瓶颈

- **无结构性解法**：不像 SQL 注入有参数化查询，提示注入缺乏“把指令与数据彻底分开”的通用机制；现有防御多为缓解与纵深叠加。
- **检测的误报与漏报权衡**：把检测调得太严会误伤正常任务（如用户正当引用外部文档），调得太松则漏掉隐蔽干扰；阈值需要按场景实测调校。
- **多模态与多轮稀释**：指令可能藏在图像、音频、长文档或多轮对话中逐步成型，单轮、单模态的检测难以覆盖。
- **Agent 链路放大**：一次注入可能经由多 Agent 传递、经由工具返回再次进入上下文，单点检测看不到完整链路，需要全链路审计。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：检测、来源标注、网关与确认等缓解手段已进入产品，但 NIST 与 NCSC 的公开判断均承认尚无完全防御，注入防御仍是“持续对抗、持续评估”的工程问题。

## 10. 未来研究问题

- **已有研究在做**：结构化上下文表示——能否用显式的来源标签与权限标签替代“纯文本拼接”，让模型与网关都能区分指令与数据。
- **已有研究在做**：注入检测的基准与度量——统一评估集与评分口径，使不同防御方案可比。
- **已有研究在做**：Agent 全链路审计——把“哪段外部内容导致了哪次调用”可视化、可回放。
- **本文推测**：注入防御的突破口可能不在模型本身，而在“默认最小权限 + 敏感操作人工确认”成为 Agent 平台默认配置；检验标准是主流平台是否默认开启而非默认关闭这些能力。
