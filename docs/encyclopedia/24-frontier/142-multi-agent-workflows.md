# 多 Agent 工作流：编排、调度、容错与可观测性

本篇讲多 Agent 工作流的系统视角：当多个 Agent 共同完成一项任务时，系统层要解决的问题——谁先谁后（编排）、谁跑哪里与跑多少（调度）、一个 Agent 失败时怎么办（容错）、整个流程如何被看见与审计（可观测性）。Agent 个体如何分工、如何通信、如何协商的研究本身归 [49 篇](49-multi-agent-collaboration.md)，本篇不重复其内容，只在需要时链接过去。本篇属于本方向总览 [133 篇](133-autonomous-systems.md)下的三级主题之一。

## 1. 研究问题

单个 Agent 的能力边界是：上下文有限、长任务易漂移、单点失败即全失败。多 Agent 的动机是分工：规划、检索、编码、测试、审查各由专长 Agent 担任，互相校验。但分工引入了系统问题：Agent 之间的依赖如何表达？中间结果以什么格式传递？一个 Agent 的错误如何不污染下游？整个流程的成本与延迟如何可控？本篇要回答：多 Agent 系统如何从“一组能干的 Agent”变成“一个可靠的系统”？判据不是单个 Agent 的基准分，而是端到端任务成功率、成本、延迟与可审计性。

## 2. 基础理论

- **工作流与有向无环图（DAG）**：把任务分解为带依赖的步骤图，是编排的经典表达；DAG 表达了“谁依赖谁”，但表达不了“条件分支与循环”之外的动态结构。
- **状态机与图编排**：以节点（Agent 或工具）与边（转移条件）表达工作流，支持条件分支、循环与人工介入点；是当前多 Agent 编排框架的主流表达。
- **消息传递与共享状态**：Agent 之间通过消息或共享状态（如黑板、共享记忆）交换中间结果；传递格式不统一会导致“上游输出、下游读不懂”的集成失败。
- **容错理论**：超时、重试、熔断、补偿（Saga）等分布式系统容错手段在 Agent 工作流中的实例化；Agent 的“失败”还包括“成功返回了错误答案”，这是传统容错不覆盖的语义失败。
- **可观测性**：追踪（trace）是多 Agent 系统的第一性证据：哪个 Agent、在哪一步、用了什么输入、产生了什么输出、花了多少成本；没有追踪，多 Agent 系统不可调试、不可审计。

## 3. 技术路线

- **顺序流水线路线**：Agent 按固定顺序依次处理（规划→编码→测试→审查）；简单、可预测，缺点是上游错误会原样传给下游，且无法回跳。
- **图编排路线**：以状态机或图表达条件分支、循环与并行；灵活，缺点是图规模变大后难以理解与验证。
- **主管—工人（supervisor-worker）路线**：主管 Agent 分解任务、派发子任务、汇总结果；分工清晰，缺点是主管成为单点瓶颈与单点失败源。
- **议会与投票路线**：多个 Agent 独立给出方案再投票或辩论取优；可提高关键决策的可靠性，代价是成本成倍增长。
- **事件驱动路线**：Agent 由事件触发、异步协作；适合长周期、跨系统的任务，缺点是流程状态分散、难以全局追踪。

## 4. 系统架构

一个典型的多 Agent 工作流系统由以下部分组成：

- **编排层**：工作流定义（图、状态机或声明式配置）、执行引擎；负责按依赖与条件推进步骤，支持暂停、恢复与人工介入点。
- **调度层**：决定 Agent 任务跑在哪里、并发度多少、优先级如何；与 [141 篇](141-auto-resource-scheduling.md)的资源调度相通，但调度对象是 Agent 任务而非容器。
- **状态与记忆层**：工作流状态、中间结果、共享记忆的存储；状态格式不统一是多 Agent 集成的首要失败源。
- **容错层**：超时、重试上限、熔断、降级（回退到单 Agent 或人工）、补偿动作；语义失败（错误答案）需要“验证 Agent”或“审查步骤”兜底，而非仅重试。
- **可观测与成本层**：全链路追踪、每步的输入输出快照、token 与调用成本统计、审计日志；成本护栏（预算上限、步数上限）在此层强制执行。

## 5. 代表性实现与开源项目

只列真实存在的框架类别，不写未核实的性能数字：

- **图编排框架**：以 LangGraph 为代表的基于图与状态机的多 Agent 编排框架；其版本与 API 变动快，以官方发布为准（待核实）。
- **Agent 框架与运行时**：以 AutoGen、CrewAI 等为代表的多 Agent 框架，提供角色、对话与任务派发原语；各框架的适用场景与版本以官方发布为准（待核实）。
- **工作流引擎类**：通用的 DAG 与工作流引擎（如 Airflow、Temporal 等）可用于编排 Agent 任务，但它们本身不是 Agent 框架；用通用引擎编排 Agent 时，语义失败的容错仍需上层补齐。
- **尚无“系统级可靠”的量产标准形态**：按“端到端成功率、成本、延迟均可预测、可审计”的定义，今天不存在公认的量产标准；现有落地均为特定任务的定制编排。

- 暂无统一标准：多 Agent 工作流没有统一的编排语言、状态格式、追踪格式或成本度量标准；框架间互操作性有限。

## 7. 当前实验结果

本节不写任何框架宣传的“多 Agent 比单 Agent 提升 X%”数字：这类数字的任务集、基线（单 Agent 配置）、成本口径各不相同，达不到三件套标准的，一律不采信。只写经核查的定性结论：

- 图编排已成为多 Agent 系统的主流表达：状态机与图结构在主流框架中被广泛采用，是行业公开可见的趋同方向。
- 成本是多 Agent 落地的首要显性约束：Agent 数量与步骤数乘上每步的模型调用成本后，总成本随规模快速增长；没有成本护栏的多 Agent 系统在生产中难以为继。
- 语义失败是多 Agent 容错的新维度：传统容错处理“超时、崩溃”，不处理“Agent 自信地返回错误答案”；验证步骤与审查 Agent 是公开讨论的应对手段，但其本身的可靠性仍需验证。
- 可观测性是多 Agent 系统落地的共识前提：没有全链路追踪，失败归因与成本归因均无从谈起。

## 8. 技术瓶颈

- **错误传播**：上游 Agent 的错误答案被下游当作事实使用，错误在流程中放大而非收敛；中间结果缺乏验证是主因。
- **状态格式不统一**：各 Agent 输出格式、记忆格式不一致，集成成本高；格式漂移会导致流程静默失败。
- **成本与延迟失控**：并行、投票、辩论等机制成倍增加调用量；成本护栏与预算机制尚未标准化。
- **死锁与活锁**：Agent 之间互相等待、反复修正、循环争论而不收敛；需要步数上限、超时与人工接管。
- **调试困难**：长链路、多 Agent 的失败难以复现与归因；追踪不完整时，调试只能靠猜。
- **评估缺失**：多 Agent 系统缺乏端到端的评估标准——单 Agent 基准分不能代表系统表现，系统级评估方法仍在发展中。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：编排框架与分工模式已有大量实践，但系统级的可靠性（错误不放大）、成本可控性与可审计性尚未达到量产标准，仍处实验与定制化阶段。

## 10. 未来研究问题

- **已有研究在做**：中间结果的验证机制——验证 Agent、契约检查、交叉校验的有效性。
- **已有研究在做**：多 Agent 系统的成本建模与预算控制——成本护栏的标准化表达。
- **已有研究在做**：系统级评估基准——端到端任务成功率、成本、延迟的联合度量。
- **本文推测**：多 Agent 工作流可能先以“固定图 + 验证步骤”的保守形态量产，而非“动态自组织”的开放形态；检验标准是固定图形态是否在真实任务中证明了成本与可靠性。
- **本文推测**：追踪与审计格式可能先于编排语言标准化——因为“看见系统”比“统一系统”更迫切；检验标准是跨框架的追踪格式是否出现。
