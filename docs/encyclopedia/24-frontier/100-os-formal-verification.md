# 操作系统形式化验证

## 1. 研究问题

测试能发现缺陷，不能证明缺陷不存在：测试用例没覆盖的路径，缺陷就还在。操作系统是正确性要求最高的软件之一——内核缺陷影响整机，而传统测试对“所有输入、所有交错、所有状态”的覆盖在原理上做不到。形式化验证要回答的问题是：能不能用数学证明，给出“内核实现符合其规范”的机器检查证据？seL4 给出了第一个肯定答案，但答案有严格的边界：证明的是什么、假设了什么、不覆盖什么，必须讲清楚，否则“已验证”会被误读成“无缺陷”。

形式化方法本身（定理证明器、模型检验、抽象解释等方法论的深度论述）归本站形式化方向的 [129-os-verification-formal.md](129-os-verification-formal.md)，本篇只讲 OS 验证的方法选择与案例，不重复其方法论内容。

## 2. 基础理论

- **规范与精化**：先写抽象规范（内核“应该”做什么的数学描述），再证明实现是规范的精化（实现的每个行为都在规范允许的行为集合内）；精化链越长，信任传递的环节越多。
- **功能正确性**：实现严格遵循抽象规范；这是 seL4 2009 年证明的核心结论。
- **安全性质**：完整性（无权限不改数据）、机密性（无权限不读数据）是比功能正确性更强的性质；seL4 后续证明了规范蕴含这些性质。
- **证明假设**：任何证明都有假设——硬件正确、汇编与启动代码正确、证明器本身正确等；假设不在证明内，假设失效则结论失效。

## 3. 技术路线

- **定理证明路线（seL4）**：用 Isabelle/HOL 交互式定理证明器，从抽象规范经可执行规范到 C 实现，逐层精化证明；2009 年完成的功能正确性证明是世界上第一个通用 OS 内核在代码级的形式化验证，证明脚本当时约 20 万行；后续扩展到二进制正确性（编译器不再需要被信任）、完整性（2011 年）、机密性（2013 年）与最坏执行时间分析（2011 年，seL4 团队公开资料）。2022 年，seL4 获得 ACM 软件系统奖。
- **模型检验路线**：对协议、调度器、并发算法等小规模状态机做穷尽状态探索；适合找并发与协议缺陷，不适合整个内核。
- **抽象解释与静态分析路线**：用抽象域自动证明某类性质（如无空指针、无越界、无死锁）；自动化程度高，保证范围窄于定理证明。
- **验证编译器路线（CompCert）**：证明编译器本身的正确性，消除“源码正确、二进制未必正确”的缺口；与 seL4 的二进制验证互补。
- **验证扩展路线**：把验证从微内核扩展到驱动、文件系统、网络栈等更大部件；代表工作包括验证文件系统（如 FSCQ，完整引用以原文为准，待核实）与验证驱动子集；扩展的代价是证明工作量随代码规模快速增长。

## 4. 系统架构

seL4 验证的证明链（自顶向下）：

- **抽象规范**：用高阶逻辑写的内核行为数学描述，是“应该做什么”的权威定义。
- **可执行规范**：抽象规范的可执行版本，用于测试与原型验证，缩小规范与实现的语义距离。
- **C 实现**：约 8700 行 C 代码加约 600 行汇编（2009 年论文数据）；规模刻意保持小，是验证可行的前提。
- **二进制验证**：自动工具链验证编译产物与 C 实现一致，消除对编译器的信任假设（中等优化级别条件下，见 seL4 团队公开资料）。
- **性质层**：在规范层证明完整性、机密性等安全性质，再经精化链传递到实现；时序信道（timing channel）不在机密性证明覆盖内，需经验方法处理。

## 5. 代表性实现与开源项目

- **seL4**：L4 家族微内核，Isabelle/HOL 验证，2014 年开源，seL4 基金会维护；是 OS 形式化验证的标杆案例，详见 [91-microkernel.md](91-microkernel.md) 的结构侧论述。
- **CertiKOS**：耶鲁大学等的验证 OS 内核项目，分层验证方法的研究代表；成熟度与维护状态以官方发布为准（待核实）。
- **FSCQ**：验证文件系统，证明崩溃一致性等性质；完整引用以原文为准（待核实）。
- **CompCert**：验证 C 编译器，消除编译环节的信任假设；与 OS 验证互补，不直接验证 OS。
- **Ironclad Apps、Komodo 等**：验证应用与验证隔离机制的研究项目；成熟度以官方发布为准（待核实）。

## 6. 关键论文与标准

- Klein 等《seL4: Formal verification of an OS kernel》，SOSP 2009：功能正确性证明的原始论文。
- Klein 等《Comprehensive formal verification of an OS microkernel》，ACM Transactions on Computer Systems 2014 年：扩展的长文版本。
- seL4 基金会《The seL4 Microkernel: An Introduction》白皮书（2020 年 6 月修订版）：验证故事的系统介绍。
- 形式化方法的方法论深度论述见 [129-os-verification-formal.md](129-os-verification-formal.md)，本篇不重复。
- 暂无统一的 OS 验证标准：验证的规范、性质与假设各项目自定，认证标准（如 Common Criteria）对形式化证据的要求按等级而异，具体以标准文本为准。

## 7. 当前实验结果

本节不写“缺陷减少多少”一类数字：验证的收益是“某类缺陷被证明不存在”，不是可计数的缺陷减少量；把证明规模（脚本行数）当成绩数字也是误读——行数反映工作量，不反映保证强度。只写定性结论：seL4 证明了工业强度微内核的形式化验证可行且不牺牲性能；验证已从内核扩展到文件系统、驱动子集等部件，但通用大内核的完整验证仍不可行；验证的成本（人年、证明维护）仍是推广的主要障碍。

## 8. 技术瓶颈

- **证明工作量**：证明脚本常数倍于被验证代码；内核一改，证明要跟着改，维护成本高。
- **规范本身的正确性**：证明只保证“实现符合规范”，不保证“规范就是用户想要的”；规范写错，证明照样通过。
- **假设边界**：硬件、汇编、启动代码、证明器、底层工具链都在假设内；侧信道（时序、功耗、缓存）大多不在模型内。
- **并发与多核**：多核并发的精化证明复杂度远高于单核；弱内存模型下的验证仍是研究难题。
- **生态缺口**：验证人才少、工具链学习曲线陡、与主流开发流程（快速迭代、持续集成）有摩擦。

## 9. 成熟度判断

- **成熟度：实验研究中。** 判断依据一句话：seL4 等案例证明了验证的可行性并有真实部署，但验证作为 OS 开发的常规方法仍未普及，通用大内核的验证仍不可行，故整体定为实验研究中而非工程发展中。

## 10. 未来研究问题

- **已有研究在做**：验证向驱动、文件系统、网络栈的扩展，验证与 Rust 类型系统的结合（类型检查分担部分证明负担），证明自动化（SMT 求解器、证明助手自动化策略）。
- **已有研究在做**：多核与弱内存模型下的验证、时序信道的建模与验证。
- **本文推测**：验证可能先在“小而关键”的部件普及（加密原语、调度器、内存分配器），再向整系统扩展；检验标准是主流内核中带验证证据的关键部件数量。
- **本文推测**：AI 辅助证明（证明脚本生成、引理推荐）可能降低验证成本，但生成的证明仍需机器检查才算证据；检验标准是 AI 生成证明的通过率与人工审查成本变化。
