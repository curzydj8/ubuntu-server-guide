# 自动测试、调试和修复

自动测试、调试和修复是指：机器自动完成软件质量保障闭环中的三个环节——生成测试用例、定位缺陷根因、生成并验证修复补丁。它与 [134 篇](134-autonomous-dev.md)的关系是：134 篇讲“Agent 主导一整项开发任务”，本篇讲其中“测试—调试—修复”这一段的专有技术；与 [135 篇](135-ai-programming.md)的关系是：135 篇的验证层（编译、测试、检查）是本篇的输入与判据。本篇属于本方向总览 [133 篇](133-autonomous-systems.md)下的三级主题之一。

## 1. 研究问题

测试、调试、修复是开发中最耗时且最依赖经验的环节：写测试要覆盖边界，定位缺陷要在海量日志与代码中找根因，修复要改对地方且不引入回归。本篇要回答：机器能否在“测试即规格”的前提下，把“发现缺陷—定位—修复—验证”做成可重复的闭环？核心难点不在生成，而在判定：生成的测试是否测到了真问题？定位是否找对了根因而非症状？补丁是否修了问题而没有悄悄改变其他行为？

## 2. 基础理论

- **测试即规格**：以可执行的测试（通过/失败）作为行为规格；这是 SWE-bench 类基准与自动修复评测共同的前提。
- **基于搜索的测试生成**：以覆盖率为目标，用搜索、符号执行或模糊测试（fuzzing）系统地探索输入空间，寻找触发缺陷的输入。
- **缺陷定位（fault localization）**：基于频谱（spectrum-based）等方法，用“通过测试与失败测试执行过的代码行”差异给可疑代码排序；排序靠前不等于根因，仍需验证。
- **补丁生成与验证**：从模板、搜索或模型生成候选补丁，再以失败测试转通过、已有测试不回归为验证条件；验证条件越完整，补丁可信度越高。
- **回归（regression）**：修复引入新缺陷的风险；“失败测试通过”只是必要条件，“全部已有测试通过”才是回归检查的底线。

## 3. 技术路线

- **模糊测试路线**：以随机与变异输入持续探索程序，在崩溃、超时、断言失败处发现缺陷；发现能力强，但“发现”之后仍需人工或工具做定位与修复。
- **符号执行与约束求解路线**：以符号表示输入、沿路径收集约束、用求解器生成触发特定路径的输入；路径爆炸是其规模瓶颈。
- **模板与搜索式修复路线**：在预定义的修复模式（如空指针 guard、边界条件修正）内搜索候选补丁；可解释、可审计，但覆盖的问题类型有限。
- **模型生成式修复路线**：由语言模型直接生成候选补丁，再以测试验证；覆盖面广，但补丁正确性完全依赖验证环节，验证不足时风险高。
- **Agent 式调试路线**：Agent 结合日志、复现、测试与代码阅读做多步调试；是 [134 篇](134-autonomous-dev.md)中调试环节的实例化，长链路漂移是其主要风险。

## 4. 系统架构

一个典型的自动测试—调试—修复系统由以下部分组成：

- **复现层**：把缺陷报告、失败日志或崩溃输入还原为可稳定复现的失败测试；复现不了的缺陷无法进入自动闭环。
- **测试生成层**：生成新的测试用例（单元、属性、模糊种子）；新测试的价值在于“能区分正确行为与缺陷行为”，而非数量。
- **定位层**：输出可疑代码排序与证据（执行轨迹、日志片段、相关测试）；定位结果必须附带证据，否则审查者无法判断。
- **修复层**：生成候选补丁（单候选或多候选排序）；补丁应尽量小——小补丁易审查、易回滚，大补丁的回归风险难以评估。
- **验证层**：失败测试转通过、已有测试全部通过、静态检查通过；验证层是自动修复的信任锚，验证不足的修复不应合入。
- **合入层**：以合并请求提交补丁与新增测试，附带定位证据与验证报告；人审查后合入。

## 5. 代表性实现与开源项目

只列真实存在的类别与项目，不写未核实的检出数字：

- **模糊测试工具**：以 AFL++、libFuzzer 为代表的覆盖率引导模糊测试器；是“自动发现缺陷”最成熟的工程实践之一。
- **自动修复研究原型**：以 GenProg（基于遗传编程的自动修复早期工作）为代表的模板与搜索式修复研究；其原始结论限定于特定类型缺陷与特定基准，不可泛化为“自动修复已解决”。
- **SWE-bench 类评测**：以真实 GitHub 问题单与项目测试为评测标准的研究基准（Jimenez 等，2024）；是模型生成式修复进展的可比口径，但基准分数不等于生产修复能力。
- **CI 中的测试自动化**：持续集成中的自动测试执行、覆盖率报告与失败通知；是测试环节最广泛的量产形态。
- **尚无“通用自动修复”量产形态**：按“任意类型缺陷、任意代码库、补丁无需人工审查直接合入”的定义，今天不存在；现有落地均为“小范围、可验证补丁 + 人审查”。

## 6. 关键论文与标准

- Jimenez, C. E. 等（2024）《SWE-bench: Can Language Models Resolve Real-World GitHub Issues?》，ICLR 2024，arXiv:2310.06770——真实问题单评测的来源。
- Yang, J. 等（2024）《SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering》，NeurIPS 2024，arXiv:2405.15793——Agent 式修复的代表性工作。
- GenProg 自动修复的早期工作（Le Goues 等）：基于遗传编程的补丁搜索路线来源；具体论文年份与基准数字未逐项核对，记入未完成项，不展开引用数字。
- 暂无统一标准：自动修复没有“补丁正确性”的行业标准；各评测的测试完备性不同，分数不可直接比较。

## 7. 当前实验结果

只写经核查的数字，不写厂商宣传的检出率：

- SWE-agent 原始论文报告：以 GPT-4 Turbo 为底座，在 SWE-bench 全部 2294 项任务上 pass@1 为 12.47%（Yang 等，NeurIPS 2024）。这是 2024 年的起点数字，不是今天的水平；当前榜单分数各源口径不一致，以 SWE-bench 官方发布为准（待核实）。
- 定性结论：模糊测试在解析器、编解码器等输入驱动型组件上发现缺陷的能力已被长期工程实践验证；但“发现缺陷”与“修复缺陷”是两段能力，前者成熟、后者仍受限。
- 定性结论：自动修复的可信度随补丁规模与验证完备性急剧变化——单行、单函数、可测试验证的补丁最可信；跨模块、涉及时序与并发的补丁最不可信。
- 本节不写任何“自动修复率提升 X%”的厂商数字：这类数字的评测集、验证标准与人工介入程度各不相同，达不到三件套标准，一律不采信。

## 8. 技术瓶颈

- **测试完备性**：验证只能覆盖“已有的测试”；测试本身有盲区时，补丁的“通过”可能是假通过。
- **定位歧义**：症状与根因常常分离（崩溃点不是错误点）；定位排序靠前不等于根因，错误定位会导致“修症状、留根因”。
- **补丁过拟合**：补丁只针对失败测试“特化”（如硬编码期望输出），而不修复一般性问题；防止过拟合需要新增测试与语义检查，不只是原测试通过。
- **规模瓶颈**：符号执行的路径爆炸、模糊测试的长尾覆盖、模型修复的长链路漂移，各自限制了规模。
- **并发与时序缺陷**：竞态、死锁、时序依赖的缺陷难以稳定复现，复现不了就进不了自动闭环。
- **审查成本**：机器生成的补丁与测试同样需要人审查；补丁越大、证据越少，审查成本越高。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：测试生成与执行、模糊测试已是量产实践，但自动修复仍以小范围、可验证补丁为主，通用、无人审查的修复尚未成熟。

## 10. 未来研究问题

- **已有研究在做**：补丁的语义验证——超越测试通过的等价性与属性检查。
- **已有研究在做**：缺陷定位的证据化——定位结果附带可审查的执行证据，而非仅排序分数。
- **已有研究在做**：防过拟合的测试生成——为候选补丁自动生成区分性测试。
- **本文推测**：自动修复的放权将按“补丁规模与验证完备性”分级：小补丁+全量测试通过先放权，大补丁与并发类缺陷长期保留人工审查；检验标准是各级别是否有公开的放权条件与回归记录。
- **本文推测**：复现技术（稳定复现偶发缺陷）可能比修复生成更先成为瓶颈突破点；检验标准是偶发缺陷的自动复现率是否公开可比。
