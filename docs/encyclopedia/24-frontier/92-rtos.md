# 实时操作系统

## 1. 研究问题

通用操作系统优化的是平均性能与吞吐：一个任务晚几毫秒完成，通常只是“慢了一点”。实时系统不一样：刹车、电机控制、起搏器、工业机器人这类任务，错过截止期就是错误——哪怕平均延迟很低，一次超时也可能造成事故。实时操作系统（RTOS）要解决的是可预测性问题：在最坏情况下，任务能不能保证在截止期前完成？这个保证需要调度算法、同步原语与系统分析共同支撑，而不是靠“机器够快”来碰运气。

## 2. 基础理论

- **硬实时与软实时**：硬实时错过截止期即系统失效；软实时错过只降低服务质量；两者对调度与验证的要求完全不同。
- **周期任务模型**：任务以固定周期释放、有最坏执行时间（WCET）与截止期；可调度性分析（如速率单调调度、最早截止期优先）判断一组任务在最坏情况下是否都可按时完成。
- **优先级反转**：低优先级任务持有高优先级任务需要的锁，导致高优先级任务被中优先级任务“插队”；优先级继承与优先级天花板协议是标准解法。
- **确定性来源**：可抢占的固定优先级调度、有界的中断关闭时间、可分析的同步原语；动态内存分配、页面调度与不可预测的缓存行为都会破坏确定性。

## 3. 技术路线

- **小型静态 RTOS 路线**：FreeRTOS、ThreadX 一类内核：任务、队列、信号量、软件定时器，静态配置为主， footprint 小，适合单片机；FreeRTOS 为 MIT 许可、由 Amazon 维护，广泛用于物联网设备（部署规模数字以官方发布为准，待核实）。
- **可扩展开源 RTOS 路线**：Zephyr（Linux 基金会托管，Apache 2.0）：Kconfig 与设备树配置、驱动模型、网络与蓝牙协议栈、电源管理，覆盖从小单片机到较复杂物联网节点的范围；是近年增长最快的开源 RTOS 之一。
- **商用安全认证 RTOS 路线**：VxWorks、QNX Neutrino：面向汽车、航空、医疗与工业控制，配套功能安全认证（如 ISO 26262、IEC 61508 相关认证等级以官方发布为准，待核实）与长期支持；认证成本高，但进入门槛本身就是卖点。
- **通用系统实时化路线**：Linux + PREEMPT_RT 补丁、Xenomai 等：让通用 Linux 获得可预测的实时能力，适合“既要实时控制、又要跑复杂应用”的场景；实时性保证弱于专用 RTOS，换取生态与开发效率。
- **微内核实时路线**：QNX、seL4 等微内核天然带故障隔离，实时性来自可分析的 IPC 与调度；与 [91-microkernel.md](91-microkernel.md) 交叉。

## 4. 系统架构

典型 RTOS 的组成部分：

- **内核**：可抢占调度器（固定优先级或 EDF）、任务控制块、队列与信号量、软件定时器、中断管理。
- **同步与防反转机制**：互斥量带优先级继承、优先级天花板、关中断临界区（要求有界）。
- **驱动与中间件**：按板级支持包（BSP）组织的外设驱动、文件系统、网络栈；Zephyr 用设备树描述硬件，FreeRTOS 靠移植层适配芯片。
- **时间分析工具**：WCET 分析、调度仿真、最坏情况测试；没有分析工具链的 RTOS 只能算“快”，不能算“实时保证”。

## 5. 代表性实现与开源项目

- **FreeRTOS**：MIT 许可的开源 RTOS，任务、队列、信号量与软件定时器齐全，移植面广；Amazon 维护，配套 AWS IoT 连接库（版本以官方发布为准）。
- **Zephyr**：Linux 基金会开源 RTOS，Apache 2.0，支持 ARM、x86、RISC-V、ARC 等架构，Kconfig + 设备树配置，内置网络、蓝牙与文件系统。
- **VxWorks**：Wind River 商用 RTOS，航空、国防与工业领域的长期部署案例，认证与长期支持是其主要卖点。
- **QNX Neutrino**：BlackBerry 商用实时微内核，汽车与医疗领域部署，详见 91 篇。
- **ThreadX（Azure RTOS，现 Eclipse ThreadX）**：微软曾主导的商用 RTOS，现已开源；许可与维护状态以官方发布为准（待核实）。
- **PREEMPT_RT**：Linux 内核的实时抢占补丁集，已逐步合入主线；不是独立 RTOS，而是通用系统的实时化路线。

## 6. 关键论文与标准

- Liu 与 Layland 1973 年的速率单调调度论文是实时调度理论的起点（完整引用以原文为准，待核实）。
- 优先级继承协议（Sha、Rajkumar、Lehoczky，1990）是解决优先级反转的经典工作（完整引用以原文为准，待核实）。
- 功能安全标准：ISO 26262（汽车）、IEC 61508（工业）、DO-178C（航空）对 RTOS 的认证提出流程与证据要求；具体认证等级按产品与官方发布为准，不在本篇逐项列出。
- 暂无统一的 RTOS 接口标准：POSIX 的实时扩展（POSIX.1b）是部分共识，但各 RTOS 的 API 仍不统一。

## 7. 当前实验结果

本节不写延迟数字：中断延迟、任务切换时间高度依赖芯片、编译选项与测试方法，脱离条件的数字不可比。只写定性结论：FreeRTOS 与 Zephyr 在单片机与物联网领域的部署已成规模；VxWorks 与 QNX 在安全关键领域的认证与部署是其成熟度的证据；PREEMPT_RT 让 Linux 在“软实时 + 复杂应用”场景成为可行选项，但硬实时保证仍需专用 RTOS 与分析工具链支撑。

## 8. 技术瓶颈

- **WCET 分析难**：现代芯片的缓存、分支预测与多核干扰让最坏执行时间难以精确估计；分析保守则资源浪费，分析乐观则保证失效。
- **多核实时**：多核共享缓存、内存带宽与中断路由带来任务间干扰；多核可调度性分析远比单核复杂。
- **安全与实时的冲突**：加密、认证与安全启动都会引入不可预测的延迟；安全关键系统要在两者之间做显式取舍。
- **生态碎片**：各 RTOS 的驱动、中间件与工具链不互通，换 RTOS 常等于重写板级与驱动层。
- **认证成本**：功能安全认证的流程与证据成本高，小团队难以承担，限制了新 RTOS 进入安全关键市场。

## 9. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：FreeRTOS、Zephyr、VxWorks、QNX 均有大规模商用部署与长期维护，RTOS 作为一类系统软件已经完全成熟；未成熟的是多核实时分析、异构加速器实时调度等新问题，不是 RTOS 本身。

## 10. 未来研究问题

- **已有研究在做**：多核干扰分析、混合关键性调度（同一芯片上安全关键任务与非关键任务共存）、时间敏感网络（TSN）与 RTOS 的协同。
- **已有研究在做**：Rust 编写的 RTOS 内核与驱动（见 [94-memory-safe-systems.md](94-memory-safe-systems.md)），把内存安全带入实时领域。
- **本文推测**：边缘 AI 推理的实时化（推理延迟有界）可能成为 RTOS 的新负载；检验标准是 RTOS 是否出现面向加速器推理的调度原语。
- **本文推测**：形式化验证可能从内核向 RTOS 的调度器与同步原语扩展；检验标准是是否有 RTOS 的调度正确性证明进入产品认证证据。
