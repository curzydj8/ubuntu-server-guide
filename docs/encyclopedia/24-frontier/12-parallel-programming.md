# MPI、OpenMP、CUDA、HIP、SYCL：并行编程模型与接口

## 1. 研究问题

[超算与高性能计算入门](03-hpc-supercomputing.md)讲了集群由什么组成、本篇要回答下一个问题：程序员用什么接口让成千上万个处理器协同工作？问题拆成三层：

- **跨节点**：不同机器上的进程没有共享内存，怎么交换数据、怎么同步？
- **节点内**：同一台机器的几十上百个核共享内存，怎么分工又不互相踩数据？
- **加速器**：主机与 GPU 的内存是分开的，计算怎么卸载过去、结果怎么拿回来，还要不要为每家厂商各写一套？

五种接口正好各管一层或一层的一部分：MPI 管跨节点消息传递，OpenMP 管节点内共享内存并行，CUDA 与 HIP 管 GPU 计算（各绑定一家硬件生态），SYCL 想用一套标准 C++ 代码覆盖多家加速器。本篇讲五者的定位、内存模型与选用方法，不讲集群调度（归总览第 6 节）与具体算法（归本域 13 篇）。

一个常见的入门误解要先纠正：Open MPI 是一个 MPI 实现，OpenMP 是一套独立的接口标准，两者名字相近、机制完全不同；CUDA 与 HIP 的 API 高度相似，但那是 HIP 有意对齐 CUDA 的结果，不是同一个接口。

## 2. 基础理论

- **分布式内存与共享内存**：分布式内存模型里每个进程有独立地址空间，数据共享必须显式通信；共享内存模型里多个线程看同一地址空间，数据共享是默认的，正确性靠同步与数据竞争控制来保证。两种模型没有优劣，只有适用范围：跨节点只能用分布式内存（或其上的抽象），节点内两种都可用。
- **SPMD（单程序多数据）**：所有进程运行同一份程序、处理不同数据，是 MPI 程序最常见的组织方式；进程靠自己的“秩”（rank）区分分工。
- **Fork-join 与任务并行**：OpenMP 的经典模式是主线程在并行区“分叉”出线程队、区末“汇合”；任务（task）模式则把工作拆成有依赖的任务，由运行时调度，适合不规则、非循环的并行结构。
- **SIMT（单指令多线程）**：GPU 的执行模型——大量线程以“线程束/波前”（warp/wavefront）为单位执行同一条指令、处理不同数据；分支发散（同一束内线程走不同分支）会让执行串行化，是 GPU 性能分析的第一检查项。
- **Amdahl 定律与扩展性**：见总览第 2 节；此处只补一句：接口选型影响的是“并行部分能做多大、同步与通信开销有多大”，串行部分的天花板任何接口都绕不过去。
- **内存模型与数据竞争**：共享内存并行里，两个线程无同步地读写同一地址、其中至少一次是写，就是数据竞争，结果未定义；加速器 offload 里，主机与设备各有一份内存，任何一方修改后另一方看到的可能是旧值，直到显式同步或统一内存机制介入。

## 3. 技术路线

五条路线按“管哪一层”划分，每条一句话讲清做法：

- **MPI：消息传递路线**。进程间显式收发消息（点对点发送/接收、广播、规约、全交换等集合操作），另有单边通信（RMA，远程内存访问）与并行 I/O；做法最通用，能跨节点扩展到全系统，是超算应用的主力模型，代价是程序员要自己管数据划分与通信。
- **OpenMP：共享内存制导路线**。用编译制导（C/C++ 的 `#pragma omp`、Fortran 的 `!$omp`）把循环、代码段、任务标记为并行，编译器与运行时负责线程创建与调度；做法最简单、增量并行化成本最低（串行代码加制导逐步变并行），但默认跨不了节点，近年也扩展了设备 offload 制导（`target` 指令把计算卸载到加速器）。
- **CUDA：厂商原生 GPU 路线**。NVIDIA 的并行计算平台与编程模型：程序员写核函数（kernel），按线程块（block）与网格（grid）组织线程，用 `cudaMalloc`/`cudaMemcpy` 管设备内存；做法最成熟、生态（cuBLAS、cuFFT、NCCL 等库）最完整，代价是绑定 NVIDIA 硬件。
- **HIP：对齐 CUDA 的可移植 GPU 路线**。AMD ROCm 平台上的 GPU 编程接口，API 有意与 CUDA 高度对齐（`hipMalloc` 对 `cudaMalloc`、`hipMemcpy` 对 `cudaMemcpy`），并提供 HIPIFY 工具把 CUDA 源码机械转换为 HIP 源码；做法是“一份近 CUDA 的代码、两家硬件可跑”，代价是对齐本身会随 CUDA 演进而需要持续跟进，且 HIP 的原生后端是 AMD GPU（经由 HIP 的 CUDA 后端也可面向 NVIDIA GPU，具体支持以官方发布为准）。
- **SYCL：标准 C++ 单源路线**。Khronos 的单源异构编程标准：主机代码与设备核函数写在同一个 C++ 源文件里，运行时按队列（queue）把核函数提交到选定的设备（CPU、GPU 或其他加速器）；做法是“标准在上、后端在下”，可移植性来自标准而非某家厂商，代价是实现成熟度与性能表现因后端而异，调试链路比厂商原生路线长。
- **混合路线（不是第六种接口，而是组合用法）**：节点间 MPI + 节点内 OpenMP + 加速器 CUDA/HIP/SYCL，是大型应用最常见的实际组织方式；总览第 3 节已讲其取舍，本篇不重复，只补一句选型原则：接口层数越多，性能调优的自由度越大，编程与调试复杂度也越高。

## 4. 系统架构

五种接口在程序里的分工位置不同，画成一层栈最清楚：

1. **应用层**：科学计算代码（求解器、模拟、数据分析），调用下层接口，不直接碰硬件。
2. **MPI 层（进程间）**：负责跨进程的数据交换与同步；实现（如 Open MPI、MPICH、Cray MPICH、Intel MPI）内部再对接底层互连（InfiniBand、Slingshot、以太网等），程序员通常不直接写互连代码。
3. **OpenMP 层（线程间）**：负责节点内线程的创建、调度与同步；运行时与编译器（GCC、LLVM/Clang、Intel 编译器等）配合实现。
4. **加速器层（主机—设备）**：CUDA 运行时/驱动、ROCm 运行时、或 SYCL 运行时负责核函数启动、设备内存管理与主机—设备同步；其下是各厂商的驱动与硬件。
5. **库层（常被误认为接口）**：cuBLAS、rocBLAS、oneMKL、NCCL、RCCL 等数值与集合通信库建在上述接口之上；用库不等于用接口，调库解决的是“算子怎么写得快”，接口解决的是“并行结构怎么组织”。

一个程序可以同时穿过这几层：MPI 进程内再开 OpenMP 线程、线程内再启动 GPU 核函数；层与层之间靠“谁拥有哪份数据”划分：MPI 管进程间的数据副本，OpenMP 管线程间的数据共享，加速器层管主机与设备间的数据搬运。

## 5. 代表性实现与开源项目

只列真实存在的标准与实现，具体版本号以官方发布为准（待核实）：

- **MPI 标准（MPI Forum）**：消息传递接口标准；MPI 5.0 于 2025 年 6 月 5 日批准，主要新增是标准应用二进制接口（ABI），让不同 MPI 实现的二进制可以互操作；MPI 4.1 于 2023 年 11 月批准。注意区分标准与实现：标准批准不等于各实现已全部支持，部署时以所用实现的文档为准。
- **MPI 实现**：Open MPI、MPICH（及其衍生，如 Intel MPI、Cray MPICH 均源于 MPICH 系谱）、MVAPICH；各实现对互连、加速器感知通信（如 CUDA-aware MPI，即 MPI 调用可直接传设备指针、由实现处理设备间搬运）的支持程度不同，以实现文档为准。
- **OpenMP 规范（OpenMP Architecture Review Board）**：共享内存并行编程接口标准；OpenMP 6.0 于 2024 年 11 月发布，是截至本篇核实日期的最新正式规范，重点在异构计算与设备支持；编译器对新规范的支持通常滞后于规范发布，以编译器文档为准。
- **CUDA（NVIDIA）**：并行计算平台与工具包；CUDA Toolkit 1.0 于 2007 年发布，CUDA 13 系列于 2025 年 8 月起发布（13.0），其后小版本以 NVIDIA 官方存档为准（待核实）。生态库包括 cuBLAS（稠密线性代数）、cuFFT、cuSOLVER、NCCL（多 GPU 集合通信）。
- **HIP 与 ROCm（AMD）**：ROCm 是 AMD 的开源 GPU 计算平台，HIP 是其上的 C++ 运行时 API；ROCm 7.0 对 HIP API 做了向 CUDA 进一步对齐的改动（部分改动与旧版本不兼容，需重新编译，见 AMD 官方 HIP 7.0 改动说明），ROCm 7.1.0 于 2025 年 10 月 30 日发布；HIPIFY 是 CUDA 到 HIP 的源码转换工具。ROCm 7 系列其后小版本以官方发布为准（待核实）。
- **SYCL（Khronos Group）**：单源 C++ 异构编程标准；SYCL 2020 最终规范于 2021 年 2 月 9 日发布，基于 C++17；代表性实现有 Intel oneAPI DPC++（DPC++ 编译器）与 AdaptiveCpp（前身 hipSYCL），后者可面向 ROCm、CUDA、Level Zero 与 CPU 后端。SYCL 2020 的修订号仍在演进，以 Khronos 官方注册表为准（待核实）。
- **OpenACC（对照，不展开）**：与 OpenMP 制导风格相近的加速器 offload 标准，由 OpenACC 组织维护；本篇只提一句：它与 OpenMP 的 `target` 制导在定位上重叠，选型时二选一即可，不要混用两套制导。

## 6. 关键论文与标准

- **MPI 标准**：MPI Forum，《MPI: A Message-Passing Interface Standard》5.0 版（2025 年 6 月 5 日批准），官方文档见 https://www.mpi-forum.org/docs/ ；4.1 版（2023 年 11 月 2 日）为此前版本。MPI 1.0 最早于 1994 年发布。
- **OpenMP 规范**：OpenMP Architecture Review Board，《OpenMP Application Programming Interface》6.0 版（2024 年 11 月发布）；OpenMP for Fortran 1.0 最早于 1997 年 10 月发布。
- **SYCL 规范**：Khronos Group，《SYCL 2020 Specification》（2021 年 2 月 9 日发布最终版），官方注册表见 Khronos SYCL 页面（以官方发布为准）。
- **CUDA 与 HIP**：两者为厂商平台文档而非独立标准组织发布的标准，版本与 API 以 NVIDIA CUDA 文档与 AMD ROCm 文档为准（待核实）；本篇不把厂商文档写成“标准”。
- **经典算法文献（与本域 13 篇共用，接口篇只列与接口机制直接相关的）**：MPI 的集合通信算法、OpenMP 的任务调度机制均属实现与编译器文献，接口规范本身即是最权威的引用；并行矩阵算法的原始文献见 13 篇第 6 节。

## 7. 当前实验结果

本节不写任何实测性能数字——理由按模板硬规则：性能数字必须同时有来源与测试条件；跨接口的性能对比高度依赖硬件、问题规模、实现版本与编译选项，转载二手“谁比谁快百分之几”必然缺测试条件。本节只写可核查的“存在性事实”：

- MPI、OpenMP、CUDA、HIP、SYCL 均有生产级实现并在超算中心实际运行（见第 5 节的标准与实现清单）；“能用”与“跑得快”是两回事，后者须在目标硬件上用自己的程序实测。
- 总览第 7 节的 TOP500 数字（HPL 实测）是系统级基准，不是接口对比：同一台系统上不同接口的程序性能差异，HPL 榜单不回答。
- 读者自测的正确姿势：固定硬件、固定问题规模、固定实现版本，分别报告强扩展与弱扩展曲线（定义见总览第 2 节），并注明编译器、MPI 实现、GPU 驱动版本；缺其中任何一项的对比都不具备可复现性。

## 8. 技术瓶颈

- **可移植性与性能可移植性是两回事**：代码能在多家硬件上编译运行（可移植），不等于在每家硬件上都跑得快（性能可移植）；SYCL 与 HIP 解决的是前者，后者仍需针对每家硬件调优（线程块大小、内存布局、占用率），这是异构编程至今未彻底解决的矛盾。
- **混合编程的复杂度**：MPI + OpenMP + 加速器三层叠加后，数据有三份归属（进程、线程、设备），同步点、数据竞争、死锁的排查面成倍扩大；性能分析工具（各厂商 profiler、MPI 性能分析接口）是必需品，不是可选项。
- **通信与同步开销**：MPI 集合操作的延迟随规模增长、GPU 核函数启动与主机—设备数据搬运有固定开销；小规模问题、细粒度任务在这些开销面前可能“并行反而更慢”，这是接口选型时必须算的一笔账。
- **标准与实现的滞后**：MPI 5.0、OpenMP 6.0 的新特性从规范发布到编译器与库实现全面支持需要时间；写新特性前先查所用编译器与实现的支持表，不要以规范为准假设部署环境已支持。
- **厂商生态锁定**：CUDA 的库生态最完整，但绑定单一厂商；HIP 与 SYCL 降低锁定，但要付出对齐滞后与调试链路更长的代价；选型是“生态完整度”与“硬件选择权”之间的权衡，没有免费答案。

## 9. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：MPI（1994 年起）、OpenMP（1997 年起）、CUDA（2007 年起）均有数十年生产验证，HIP 已在超算中心的生产系统上运行并支撑真实应用（总览的 Frontier、El Capitan 级系统即运行此类混合并行程序）；SYCL 已有生产部署案例，具体覆盖以实现方发布为准，五者都不是实验性接口；“成熟”指的是接口本身，个别新版本特性（如 MPI 5.0 的 ABI）的实现覆盖度仍在推进中，见第 8 节。

## 10. 未来研究问题

- **已有研究在做**：MPI 5.0 的 ABI 落地——不同 MPI 实现的二进制互操作能否让容器化、模块化部署真正摆脱“实现绑定”；检验标准是主流实现是否普遍提供 ABI 兼容构建。
- **已有研究在做**：标准 C++ 并行（`std::execution`、并行算法）与 SYCL、OpenMP 的关系——语言层并行能否逐步吸收一部分今天靠制导与库实现的异构 offload；检验标准是编译器对标准并行特性的设备 offload 支持是否可用。
- **已有研究在做**：通信与计算重叠、GPU 感知 MPI、集合通信算法的拓扑感知优化——在互连成为瓶颈的规模下，接口层如何帮程序把通信藏到计算背后。
- **本文推测**：未来并行编程的主流形态可能不是“一种接口统治一切”，而是“分层组合 + 更高层抽象”（如任务图、领域库）继续分工：接口层保持稳定，真正的易用性提升来自其上的库与编译器自动并行；检验标准是新一代科学应用是否普遍不再手写 MPI 集合操作而改调领域库。

## 附：最小示例（示例未实测）

以下两段是接口写法的示意，**示例未实测**（代理 VM 上无 MPI、GPU 环境，读者须在目标环境编译运行）：

```c
/* MPI：每个进程打印自己的秩与进程总数（示例未实测） */
#include <mpi.h>
#include <stdio.h>
int main(int argc, char **argv) {
    MPI_Init(&argc, &argv);
    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);
    printf("rank %d of %d\n", rank, size);
    MPI_Finalize();
    return 0;
}
```

```c
/* OpenMP：用制导把循环并行化（示例未实测） */
#include <omp.h>
#include <stdio.h>
int main(void) {
    #pragma omp parallel for
    for (int i = 0; i < 8; i++)
        printf("thread %d handles i=%d\n", omp_get_thread_num(), i);
    return 0;
}
```
