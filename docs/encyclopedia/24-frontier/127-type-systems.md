# 类型系统和依赖类型

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章。总览讲“形式化方法整体”；本篇讲其中最日常、最无感的一支——类型系统。每个程序员每天都在和类型系统打交道：编译器报错“类型不匹配”，就是类型系统在编译时排除了一整类错误。依赖类型把这条路推到极致：类型可以依赖于值，规约可以直接写进类型，类型检查就变成了证明检查。

## 1. 研究问题

动态语言与弱类型语言的错误常常在运行时才暴露：空指针、类型混淆、越界、数据竞争。测试能覆盖一部分，类型系统想回答的是：能不能在程序运行之前，就用一套机械规则排除某一类错误，而且这套规则要足够轻、足够快，让开发者愿意每天用它？类型系统的设计史，就是“排除的错误类越来越广”与“开发者要写的标注越来越多”之间的拉锯。依赖类型把拉锯推到顶点：排除的类可以任意广（原则上任何可形式化的性质都能编码进类型），但标注与证明的负担也随之涨到交互式证明的量级。

## 2. 基础理论

- **简单类型与 λ 演算**：λ 演算的类型化版本是类型理论的起点；类型即“值的集合与使用规则”，类型检查即“按规则判定程序是否合乎用法”。
- **Curry-Howard 对应**：命题对应类型、证明对应程序，见[计算理论和数学逻辑](123-computing-theory-logic.md)；在依赖类型论中，这一对应从命题逻辑扩展到谓词逻辑——“对所有 n，P(n) 成立”可以写成一个类型，而它的证明就是一个程序。
- **依赖类型（dependent types）**：类型可以依赖于项的值，如“长度为 n 的向量”Vec(n)——n 是值，不是类型参数的占位符。于是“两个向量长度相等才能相加”可以写进类型签名，长度不匹配在编译时就被拒绝。
- **所有权与线性类型**：线性逻辑启发的类型规则——值只能被使用一次、或只能有一个可变所有者；Rust 的所有权与借用检查是这套思想最成功的工业落地，在无垃圾回收的前提下用编译时规则排除内存安全类错误。
- **渐进类型与效应系统**：渐进类型允许类型化与非类型化代码共存、边界处动态检查；效应系统把“函数会做什么副作用”也写进类型（如是否抛异常、是否做 IO），是类型系统向规约方向的又一步。

## 3. 技术路线

- **静态类型主流路线**：Java、C#、Go、TypeScript 等语言的类型系统，以“防低级错误、给 IDE 与重构撑腰”为目标，不求证明任意性质；这是类型系统最普及的形态。
- **所有权类型路线**：Rust 的所有权、借用、生命周期，用类型规则在编译时保证内存安全与无数据竞争（安全 Rust 子集内）；这是“类型系统替代一整类运行时检查与测试”的标杆。
- **依赖类型路线**：Coq/Rocq、Lean、Agda、Idris 的类型系统，类型即规约、程序即证明；表达力最强，但类型检查常需要证明辅助，开发体验接近交互式证明，见[自动定理证明](124-automated-theorem-proving.md)。
- **精化类型与契约类型路线**：在普通类型上加谓词精化，如“大于 0 的整数”“非空字符串”，由 SMT 求解器在编译时或验证时检查；Liquid Haskell、F* 的精化类型属此路线，介于普通类型与完全依赖类型之间。

## 4. 系统架构

一个带依赖类型的语言系统通常由以下部分组成：

- **核心类型检查器**：小而可信的内核，判定“给定项是否属于给定类型”；与证明助手的小核心同源，是信任根。
- **elaborator 与隐式参数推断**：把用户写的省略形式展开成核心项，推断隐式参数与实例；这一层可以复杂，但错了只会导致“检查失败”，不会导致“错的结论被接受”。
- **求解器后端（精化类型）**：把精化谓词交给 SMT 求解器判定，超出求解器能力的部分回落为人工证明或运行时检查。
- **擦除与编译层**：证明与类型层面的信息在编译时擦除，只留可执行代码；依赖类型语言能否生成高效代码，取决于擦除设计是否干净。

## 5. 代表性实现与开源项目

- **Rust**：所有权与借用检查的工业标杆；安全 Rust 的内存安全保证来自类型系统，不是运行时检查。
- **Coq/Rocq、Lean、Agda**：依赖类型论的证明助手与语言，Lean 与 Rocq 均基于构造演算变体（Lean 用非累积宇宙层级，Rocq 用累积层级，属技术细节差异）。
- **Idris**：以依赖类型为核心设计的通用编程语言，尝试把依赖类型带出证明助手、带进日常编程。
- **F\***：带精化类型与效应的验证语言，规约用 SMT 求解器（Z3）检查，可抽取为可执行代码。
- **Liquid Haskell**：为 Haskell 加精化类型的系统，用 SMT 求解器检查谓词精化。
- **TypeScript、Python 类型标注（mypy/pyright）**：渐进类型的普及形态——不强制全量类型化，但类型化部分带来检查与工具收益。

## 6. 关键论文与标准

- Curry 与 Howard 关于“命题—类型对应”的早期工作，具体篇名以官方发布为准（待核实）。
- Martin-Löf 关于直觉主义类型论的论述，依赖类型论的源头之一，具体出处以官方发布为准（待核实）。
- 暂无统一标准：各语言的类型系统是语言定义的一部分，没有跨语言的类型标准；Rust、TypeScript 等的类型规则以各自官方参考手册为准。

## 8. 技术瓶颈

- **标注负担与可读性**：依赖类型签名本身就是规约，写对签名常常比写实现更难；类型错误信息随之变得晦涩，调试体验差是普及的最大障碍之一。
- **类型检查的可判定性与性能**：依赖类型检查可能需要归约与证明搜索，检查时间不可预测；工程上必须在表达力与检查性能之间划线。
- **与现有生态的互操作**：依赖类型语言与主流库、框架、构建工具的互操作成本高，团队引入它往往意味着生态重起。
- **“证了什么”的边界**：类型正确的程序仍可能逻辑错误——类型系统只排除它“声称”排除的类；把规约写进类型时，规约本身仍可能写错（见总览 122 篇的规约难问题）。
- **学习曲线**：从“类型是标签”到“类型是命题”的思维转变需要数理逻辑训练，这不是靠工具文档能一夜补齐的。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：静态类型与所有权类型已是工业默认配置，但依赖类型仍主要停留在证明助手与研究语言中，尚未成为通用开发的常规手段。

## 10. 未来研究问题

- **已有研究在做**：更友好的依赖类型错误信息、更强的隐式推断、把精化类型接入主流语言工具链。
- **已有研究在做**：Rust 形式化子集的验证（Verus、Creusot 方向）——在所有权类型之上再叠加契约验证，见[程序正确性证明](126-program-correctness.md)。
- **本文推测**：依赖类型最可能先以“精化类型 + 求解器”的折中形态进入主流语言，而不是以“全依赖类型”形态进入；检验标准是主流语言是否默认提供可用的精化类型检查。
