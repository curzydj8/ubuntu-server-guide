# 形式化验证和模型检测

本篇是总览[计算机形式化与可信软件](122-formal-methods.md)的分支文章。总览讲“形式化方法整体”；本篇讲其中最自动化的一支——形式化验证与模型检测。它的口号是“让机器替人把状态空间走完”：给定系统模型与待验证性质，模型检测器穷尽所有可达状态，要么证明性质成立，要么给出一条通向违反的具体执行路径（反例）。反例是模型检测最宝贵的产出：它不是“可能有问题”，而是“按这个模型，问题确实能这样发生”。

## 1. 研究问题

并发系统、分布式协议、硬件控制逻辑的 bug 往往不在单条执行路径上，而在“两个事件恰好以某种顺序交错”时。测试很难恰好撞上那个交错，复现也困难。模型检测要解决的问题是：把“所有可能的交错”从测试抽样变成穷尽检查。代价是状态空间：n 个并发部件的状态组合数随 n 指数增长，这就是状态爆炸。模型检测的全部技术史，基本就是一部“如何在爆炸面前保住穷尽性”的历史——约简、抽象、符号化、有界化，每种技术都在“保真”与“可算”之间做交易。

## 2. 基础理论

- **时序逻辑**：LTL（线性时序逻辑）描述“沿每条执行路径都成立”的性质（如“请求最终总会得到响应”）；CTL（计算树逻辑）描述“在分支结构上成立”的性质（如“从每个状态都存在一条通向恢复的路径”）。性质写错，检查结果就没有意义。
- **状态机与可达性**：系统被建模为状态与迁移的集合，验证即判定“坏状态是否可达”；安全性质（坏事永不发生）归结为可达性，活性性质（好事最终发生）需要更复杂的公平性与不动点推理。
- **模型检测的奠基**：模型检测由 Clarke 与 Emerson、Queille 与 Sifakis 在 20 世纪 80 年代初独立提出，两组工作后来共同获得 2007 年图灵奖；这是本节唯一写年份的理论史断言，依据为公开的时间线梳理，具体获奖引文以官方发布为准（待核实）。
- **有界模型检测（BMC）**：只检查长度不超过 k 的执行；k 步内没发现反例，不等于 k 步之外没有反例——BMC 是找 bug 的利器，不是无 bug 的证明，除非配上归纳或完备性阈值论证。
- **抽象解释与 CEGAR**：用抽象域过近似真实状态，抽象中发现的反例若是虚假的，就据此精化抽象再查；反例引导的抽象精化（CEGAR）是把“抽象”与“穷尽”结合起来的经典框架。

## 3. 技术路线

- **显式模型检测路线**：逐个枚举状态并存储已访问集合，代表为 SPIN；直观、反例具体，但状态数一上来就存不下。
- **符号模型检测路线**：用 BDD 或 SAT/SMT 公式表示状态集合，一次操作一整批状态，代表为 SMV 家族；能处理的状态数远超显式方法，但对变量顺序与公式结构敏感。
- **有界与 SMT 路线**：把“k 步内是否存在违反”编码成 SAT/SMT 问题交给求解器，代表为 CBMC（针对 C/C++ 程序）与 Kani（针对 Rust，基于 CBMC）；适合在真实代码上找内存安全与断言违反，结论天然带“有界”限定。
- **规约先行路线**：在写代码之前先用 TLA+ 写规约、跑 TLC 检查设计，设计 bug 在编码前暴露；亚马逊公开报告过 TLA+ 在 S3、DynamoDB 等系统中发现了测试遗漏的 bug，具体案例细节以官方发布为准（待核实）。
- **运行时与静态混合路线**：模型检测查设计，抽象解释与符号执行查实现，测试查集成；三者结论的范围不同，不能互相冒充。

## 4. 系统架构

一套模型检测工作流通常由以下部分组成：

- **建模层**：用 Promela（SPIN）、TLA+、SMV 语言或直接从代码抽取，写出系统模型；模型与真实系统的差距（建模假设、环境假设）是结论可信度的第一上限。
- **性质层**：用时序逻辑公式、断言、不变量写待验证性质；性质通常比模型更难写对，工业实践中性质评审与模型评审同等重要。
- **检查引擎**：显式枚举器、BDD 引擎、SAT/SMT 求解器，负责可达性判定与反例生成。
- **反例与诊断层**：把反例路径还原成可读的执行轨迹，定位到模型中的具体迁移；没有可读反例，模型检测就只剩“通过/不通过”两个字，调试价值大减。

## 5. 代表性实现与开源项目

- **TLA+ 与 TLC**：Leslie Lamport 的规约语言与模型检查器，面向并发与分布式系统设计；Apalache 是面向 TLA+ 与 Quint 的符号模型检查器。
- **SPIN**：贝尔实验室 Gerard Holzmann 团队开发的模型检测器，用 Promela 建模并发软件与协议，1991 年起自由提供，2002 年获 ACM 系统软件奖（年份与奖项以官方发布为准，待核实）。
- **CBMC**：针对 C/C++ 的有界模型检查器，可检查内存安全、断言、算术溢出等性质；JBMC 为其 Java 字节码版本，Kani 为基于 CBMC 的 Rust 检查器。
- **NuSMV / nuXmv**：SMV 家族的符号模型检查器，面向硬件与有限状态控制逻辑。
- **UPPAAL**：面向实时系统的模型检查器，用时间自动机建模，性质含时间约束。
- **Alloy**：轻量级建模与分析工具，用关系逻辑写规约并在有界范围内自动找实例与反例，适合设计早期探索。

## 6. 关键论文与标准

- Clarke、Emerson、Sifakis 等关于模型检测的奠基性论文（1980 年代初），具体篇名以官方发布为准（待核实）。
- Lamport 的 TLA 相关论述：TLA 于 1990 年代提出，TLA+ 随后成型（时间线梳理称 TLA+ 在 1999 年前后出现，具体以官方发布为准，待核实）。
- 暂无统一标准：模型检测的语言与性质表示各工具自成体系，互操作性有限；行业标准（如 131 篇所列功能安全标准）引用的是“验证活动”要求，不指定具体模型检测工具。

## 7. 当前实验结果

本节不写“查了多少状态、快了多少倍”一类的数字：状态数、耗时高度依赖模型规模、抽象粒度与硬件配置，脱离条件不可比较。只写经核查的定性结论：

- 模型检测在协议设计、硬件验证、云基础设施设计评审中已有可复查的工业用例，反例定位设计 bug 的能力是其立身之本。
- 有界检查在真实代码上找内存安全与断言违反方面已进入持续集成可用的程度，但结论必须带“有界”限定。
- 状态爆炸仍是规模上限：并发度、数据域大小一上来，显式与符号方法都会触顶，抽象与组合推理是唯一出路，而非更快的枚举。

## 8. 技术瓶颈

- **状态爆炸**：并发部件数、数据取值范围、时间维度，每一项都可能让状态空间指数膨胀；偏序约简、对称约简、抽象是缓解手段，不是根治。
- **建模鸿沟**：模型不是系统本身；环境假设、时序假设、故障模型写得不完整，检查通过也可能漏掉真实 bug。
- **性质表达难**：活性、公平性、实时性写成时序公式需要训练；性质写错比模型写错更隐蔽，因为检查器会一本正经地证明一个错的性质。
- **有界结论的误读风险**：BMC“k 步内无反例”被误读为“系统无 bug”，是工业落地中最常见的概念事故；报告必须写明界。
- **与实现脱节**：查模型不等于查代码；从模型结论到代码结论之间需要精化、代码抽取或运行时监控补链，否则是两张皮。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：模型检测工具在协议、硬件、云设计等领域已有真实工业部署，但状态爆炸与建模成本使它仍是关键设计环节的专项工具，不是通用开发流程的默认步骤。

## 10. 未来研究问题

- **已有研究在做**：符号化与 SMT 技术的组合、组合式模型检测（分而治之再组合结论）、模型检测与测试生成的结合。
- **已有研究在做**：从代码自动抽取模型、从模型自动生成测试用例，缩小模型与实现的鸿沟。
- **本文推测**：模型检测最可能先以“设计评审的默认环节”（如分布式协议上线前必须跑 TLC）普及，而不是以“全代码验证”普及；检验标准是头部云厂商与硬件厂商的设计评审流程中模型检查是否成为门禁而非可选项。
