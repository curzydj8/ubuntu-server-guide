# 小型语言模型与端侧模型

本篇是 [AI Agent 前沿总览](06-frontier-ai-agents.md) 的分支文章，只讲小型语言模型（SLM）与端侧模型的研究侧问题：小模型为什么在某些任务上能接近大模型、端侧部署的约束如何改变模型设计、以及“小”与“弱”之间的界限在哪。本地部署与量化的操作步骤见本站 18 域[本地模型部署](../18-local-ai/01-local-model-deployment.md)与[量化与推理](../18-local-ai/02-quantization-inference.md)，本篇只链接、不复制；压缩方法的前沿视角见[模型压缩、量化、蒸馏与推理加速](51-model-compression.md)。

## 1. 研究问题

小型语言模型通常指参数量在数亿到数十亿量级、能在手机、个人电脑、边缘设备上本地运行的语言模型；端侧模型则强调部署位置（设备端而非云端）带来的约束。研究问题是：在算力、内存、功耗、延迟都受限的设备上，模型能做到什么、做不到什么？以及，小模型的“小”是否必然意味着“弱”？

现有方法解决不了这个问题的两个原因。第一，**能力与规模的关系不是线性的**：在某些任务上，小模型加高质量数据与针对性微调可以接近大模型；在另一些任务（尤其是开放推理、长程规划）上，规模差距难以靠技巧弥补；哪类任务属于哪一边，目前没有可靠的事先判定方法，只能逐任务实测。第二，**端侧约束是多维的**：内存、算力、功耗、散热、存储、网络、隐私要求同时起作用，优化其中一维可能恶化另一维；只谈“参数量小”而不谈内存占用、首 token 延迟、持续生成速度与功耗，端侧评估就是不完整的。

## 2. 基础理论

- **缩放规律与数据质量**：Chinchilla 研究（Hoffmann 等人，2022）指出，模型规模与训练数据量应按比例增长；小模型研究的补充观点是，在固定参数量下提高数据质量（去重、筛选、合成高质量教材式数据）可以带来不成比例的收益。Phi 系列的研究正是这一观点的代表：用精心筛选与合成的“教材式”数据训练小模型，在特定任务上取得超出其规模的预期表现。
- **知识蒸馏**：Hinton 等人（2015）提出，用大模型的软标签（概率分布而非硬答案）训练小模型，使小模型学到大模型的泛化结构而非仅答案；蒸馏是小模型获得能力的重要途径，但蒸馏也会把大模型的偏见与错误一并传给小模型。
- **稀疏与高效架构**：注意力变体（如分组查询注意力 GQA、滑动窗口注意力）、混合专家（MoE）的稀疏激活、状态空间模型等，都旨在降低单位能力的计算成本；架构改进的收益需在同等任务与硬件条件下验证，不能只看参数量。
- **量化理论**：降低权重与激活的数值精度以减小体积、加速推理；量化方法的细节与前沿问题见[模型压缩、量化、蒸馏与推理加速](51-model-compression.md)，实操见 18 域量化文章。

## 3. 技术路线

- **高质量数据路线**：用筛选、合成、教材式数据提升小模型的数据效率；代表是 Phi 系列的思路。优点是不改架构也能见效；缺点是数据筛选标准本身难以公开复现，且“高质量”的定义随任务而变。
- **蒸馏与专用化路线**：针对特定任务或领域，用大模型生成训练数据或软标签，训练专用小模型。优点是在目标任务上性价比极高；缺点是专用小模型超出目标任务后能力下降快，通用性与专用性需要权衡。
- **架构高效化路线**：用更省算力的架构、更小的词表、更短的上下文、更高效的注意力实现来降低端侧成本。优点是收益可迁移；缺点是架构改动需要重新训练验证，试错成本高。
- **系统协同路线**：模型与硬件、推理引擎、操作系统协同优化（如 NPU 加速、KV 缓存管理、投机解码）；优点是端到端延迟与功耗收益明显；缺点是优化与特定硬件绑定，跨设备迁移时收益可能消失。
- **混合部署路线**：端侧小模型处理常见、隐私敏感、低延迟任务，复杂任务回退到云端大模型；或端侧模型做初筛、云端做复核。优点是兼顾隐私、延迟与能力；缺点是“何时回退”的判定规则本身就是研究问题，判错时要么浪费云端资源，要么把难题留给了最弱的模型。

## 4. 系统架构

一个端侧小模型系统通常包含：

- **模型本体**：经量化、剪枝或蒸馏后的小模型，体积与精度需按设备内存与算力选型。
- **推理引擎**：负责 KV 缓存、批处理、投机解码、硬件加速调度；引擎选型对端侧延迟的影响常大于模型本身的微小差异。
- **任务路由层**：决定任务在端侧、云端还是混合处理；路由错误是混合部署最常见的失效模式。
- **隐私与数据层**：端侧数据的留存、同步与删除规则；端侧运行不等于隐私自动安全，模型输出、日志与缓存仍可能泄露信息。
- **更新层**：模型版本的分发、回滚与灰度；端侧模型更新失败时的回退机制常被忽视。

尚无代表性商用系统可以按“端侧通用智能”来介绍：现有端侧产品多针对特定功能（输入法、语音助手、文档摘要、代码补全等），通用端侧 Agent 仍是研究目标。

## 5. 代表性实现与开源项目

只列真实存在的项目类别，不写性能排名：

- **Phi 系列（微软研究院）**：Phi-2 约 2.7B 参数、Phi-3-mini 约 3.8B 参数，是“数据质量替代规模”思路的公开代表；其论文与技术报告讨论了教材式数据的作用，但训练数据的完整细节未完全公开，复现结论应以论文原文为准。
- **Gemma、Qwen、Llama 等开源小模型系列**：各厂商均发布了数十亿参数量级的开源模型，适用于端侧研究；各系列的许可、数据披露与基准口径不同，选型时应先看许可与官方说明，而非只看基准分数。
- **SmolLM 等学术界小模型系列**：Hugging Face 等机构发布的、面向端侧研究的小模型，附带训练数据与评估细节，适合作为复现起点。
- **端侧推理引擎**：llama.cpp、MLC LLM、MediaPipe 等，提供跨设备的推理实现；引擎的硬件支持范围以其官方发布为准（待核实）。
- **系统性研究**：ACL 2025《Demystifying Small Language Models for Edge Deployment》收集了 68 个 100M–5B 参数的解码器小模型并做了系统性基准，结论之一是小模型能力正在接近 7B–8B 级模型系列，但具体差距因任务与评估条件而异；该研究的范围限定为 100M–5B 解码器模型，结论不宜外推到所有架构。

## 6. 关键论文与标准

- Hinton 等人《Distilling the Knowledge in a Neural Network》（2015，arXiv:1503.02531）。
- Hoffmann 等人《Training Compute-Optimal Large Language Models》（Chinchilla，2022，arXiv:2203.15556）。
- 微软研究院 Phi 系列技术报告（Phi-2，2023；Phi-3，2024），以官方发布为准。
- 《Demystifying Small Language Models for Edge Deployment》（ACL 2025）：68 个小模型的系统性端侧基准研究。
- 暂无公开标准：小模型的端侧评估标准（内存、延迟、功耗、离线能力）无公认统一标准，各厂商的“可在手机运行”说法口径不一。

## 7. 当前实验结果

本节不写模型排行榜，只写经公开研究确认的定性结论与带条件的数字：

- ACL 2025 的系统性研究（68 个 100M–5B 模型）发现：小模型能力正在快速演进、与 7B–8B 级模型系列的差距在缩小；同时发现小模型普遍存在“过度训练”（训练 token 数远超 Chinchilla 建议比例）的现象，且数据质量对结果的影响显著。以上结论限于该研究的模型范围与评估设置。
- EASE 2025 关于小模型函数调用的研究（评估了 DeepSeek-Coder-1.3B、Phi-3-mini、Phi-2、StarCoder2-3B、Stable-Code-3B 等模型）表明：小模型在函数调用任务上有可用表现，但对提示扰动的脆弱性仍是公开问题——微小扰动可导致性能下降；该结论限于该研究的任务与设置。
- 端侧实测的共识是：同一模型在不同设备、不同引擎、不同量化格式下的延迟与内存占用差异显著；只报参数量而不报设备、引擎、量化格式与测试任务的端侧性能说法，没有可比性。
- 隐私方面的定性结论：端侧运行减少了数据上传云端的需求，但不等于隐私问题已解决；模型记忆训练数据、日志留存、云端回退时的数据传输仍是需要单独处理的问题。

所有示例均为文献复述，不是本站实测；本地没有端侧实验环境，任何设备实测均属示例未实测。

## 8. 技术瓶颈

- **能力天花板瓶颈**：开放推理、长程规划、多步工具任务上，小模型与大模型的差距仍明显，且差距随任务开放程度扩大。
- **数据瓶颈**：高质量教材式数据的筛选与合成方法难以公开复现；数据质量的度量本身就是开放问题。
- **评估瓶颈**：缺乏统一的端侧评估标准（设备、引擎、量化格式、功耗、延迟口径不一），厂商说法不可直接比较。
- **更新与维护瓶颈**：端侧模型版本碎片化、更新分发与回滚机制不成熟；旧版本模型的已知缺陷可能长期留在设备上。
- **安全瓶颈**：小模型的安全对齐资源通常少于大模型，提示注入、越狱等攻击在小模型上可能更容易成功；具体表现因模型与对齐方法而异，以独立评测为准（待核实）。
- **混合路由瓶颈**：“何时回退云端”的判定规则不可靠时，混合部署的收益会被误判消耗。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：小型语言模型已有可用的开源实现与端侧产品，能在受限功能上交付价值，但开放任务的能力天花板、统一端侧评估标准与混合路由三大问题未解决，尚不能按“端侧通用智能”来交付。

## 10. 未来研究问题

- **已有研究在做**：更省 token 与算力的架构、数据质量的度量方法、端侧评估标准的统一、混合路由的可靠判定。
- **已有研究在做**：小模型的安全对齐方法、端侧模型的隐私保护（记忆、日志、回退传输）。
- **本文推测**：小模型最可能先在“专用化 + 混合部署”形态上大规模落地（端侧做高频专用任务，云端做开放难题），而非以单一通用端侧模型形态落地；检验标准是混合系统的端到端任务成功率与成本是否在公开任务上优于纯云端或纯端侧方案。
