# Rust 系统编程

## 1. 研究问题

本篇不讲 Rust 语言入门（变量、语法、标准库用法不在此），只讲一个系统软件问题：操作系统、驱动与固件长期用 C 编写，内存安全缺陷随之长期存在；能不能换一种语言，在不引入垃圾回收、不牺牲底层控制的前提下，让编译器在编译期排除整类内存错误？Rust 的回答是所有权模型：每个值有唯一所有者，借用规则在编译期检查，数据竞争在类型层面受限。问题随之变为：这套模型在内核、驱动与固件这些“必须直接操作硬件、必须与 C 互操作”的场景里，到底能走多远、卡在哪里？

## 2. 基础理论

- **所有权与借用**：值的所有权唯一，借用分可变（独占）与不可变（共享）两种，编译器在编译期检查借用规则；违反规则的代码编译不通过，而不是运行时崩溃。
- **生命周期**：引用不能比它指向的值活得长；生命周期标注让编译器能检查跨函数、跨结构的引用有效性。
- **无垃圾回收的安全**：安全来自编译期检查而非运行时回收，适合无标准库（`no_std`）、无堆分配的裸机与内核场景；代价是某些 C 惯用写法（如复杂共享可变状态、循环数据结构）需要重构。
- **Unsafe 逃逸口**：裸指针解引用、调用 C 函数、操作硬件寄存器等必须写在 `unsafe` 块内；`unsafe` 不关闭检查，而是把责任从编译器转移给程序员，并把高危代码圈定在可审计的范围。

## 3. 技术路线

- **内核内 Rust 路线（Rust for Linux）**：Linux 内核初始 Rust 支持随 6.1 于 2022 年 12 月合入，起初只有基础设施与示例驱动；随后逐步扩展到驱动抽象（平台设备、PCI、块设备、网络 PHY 等，具体覆盖范围以官方发布为准，待核实）。Rust 驱动与 C 内核通过绑定层互操作，C 侧的缺陷不会因 Rust 侧安全而消失——保证范围是“Rust 代码自身无某类内存错误”，不是“整个内核无缺陷”。
- **整系统 Rust 路线（Redox OS）**：从微内核到驱动、文件系统、显示服务全部用 Rust 写，用户态服务化（见 [91-microkernel.md](91-microkernel.md)）；证明 Rust 可以支撑完整系统，代价是生态与硬件覆盖远小于 Linux。
- **Framekernel 路线（Asterinas）**：内核跑在单一地址空间（性能接近单体内核），但用 Rust 的所有权把内核源码划分为可写 `unsafe` 的小框架（OSTD）与必须纯安全 Rust 的服务层；隔离边界是语言而非 MMU。这是微内核安全与单体内核性能之间的新折中，生产就绪程度以官方发布为准（待核实）。
- **固件与嵌入式路线**：Rust 用于引导加载、嵌入式固件与驱动，`no_std` + 裸机运行时；与 [92-rtos.md](92-rtos.md) 的实时场景交叉，实时性保证仍需调度与分析工具链支撑。
- **驱动先行策略**：新驱动优先用 Rust，旧驱动不动；这是各大厂商与内核社区的实际策略——迁移按驱动边界推进，不按“重写内核”的口号推进。

## 4. 系统架构

Rust 系统软件的典型分层：

- **安全服务层**：驱动逻辑、协议处理、文件系统逻辑用安全 Rust 写，享受编译期检查。
- **框架/绑定层**：小范围的 `unsafe` 代码封装硬件寄存器访问、DMA 描述符、C 内核 API 调用；对外暴露安全接口，把不安全操作“关进笼子”。
- **C 互操作层**：绑定生成器把 C 头文件与内核 API 翻译成 Rust 可调用的形式；绑定本身的正确性（类型、生命周期、并发假设）是高危区，需人工审查。
- **构建与测试层**：内核 Rust 需要特定工具链配置（如 `no_std`、内核日志宏替代标准库输出）；测试覆盖单元测试、内核自测试与真实硬件测试，缺一不可。

## 5. 代表性实现与开源项目

- **Rust for Linux**：Linux 内核的 Rust 支持项目，初始合入 6.1（2022 年 12 月）；后续驱动与抽象的合入进度以内核官方发布为准。
- **Redox OS**：Rust 微内核整系统，驱动与服务用户态化，带自有桌面与包管理；仍处 1.0 之前，硬件覆盖以官方发布为准（待核实）。
- **Asterinas**：Rust 的 framekernel，Linux ABI 兼容目标，x86-64 为主要支持平台，ARM64 与 RISC-V 支持层级以官方发布为准（待核实）；明确声明未达到生产就绪。
- **Theseus、DragonOS 等**：Rust 内核研究与教学项目，成熟度各异，以官方发布为准（待核实）；本篇不将其与上述三者并列为同等成熟度。
- **Rust 驱动实践**：Android 等产品线已有 Rust 编写的系统组件落地，具体组件与版本以官方发布为准（待核实）。

- Rust 语言机制见 Rust 官方文档与《The Rust Programming Language》；内核集成见 Rust for Linux 项目文档与内核文档中的 Rust 章节（版本以官方发布为准）。

## 7. 当前实验结果

本节不写缺陷减少比例数字：Rust 驱动与 C 驱动的缺陷对比需要同口径的统计（代码规模、运行时间、发现渠道），脱离口径的数字不可比。只写定性结论：Rust 已从“能否进内核”的争论阶段进入“能写哪些驱动”的工程阶段；整系统 Rust 项目证明了语言可支撑完整系统，但生态与硬件覆盖仍是主要差距；`unsafe` 的存在意味着 Rust 系统软件的安全是“可审计的局部不安全”，不是“全局无不安全代码”。

## 8. 技术瓶颈

- **FFI 边界**：Rust 与 C 内核的接口处，所有权、生命周期与并发假设最容易错位；绑定错误可能把 C 的缺陷引入 Rust 侧。
- **Unsafe 审查**：驱动必须操作硬件，`unsafe` 不可避免；审查质量参差不齐时，安全保证随之打折。
- **异步与中断模型**：Rust 的异步模型与内核的中断、锁、睡眠/非睡眠上下文规则需要显式适配；写错上下文规则会导致死锁或睡眠中调用非法操作。
- **学习与重构成本**：借用检查要求重构 C 惯用写法；存量驱动的 Rust 重写不是机械翻译，需要重新设计数据结构。
- **工具链与架构覆盖**：内核 Rust 对架构、编译器版本与配置有要求，覆盖面以官方发布为准；不是所有架构与配置都同等支持。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：Rust 已合入 Linux 内核并有真实驱动落地，但覆盖面仍在扩展、整系统项目未达生产就绪，Rust 系统编程作为工程实践正在发展，尚未成为系统软件的默认选项。

## 10. 未来研究问题

- **已有研究在做**：驱动抽象的扩展（更多总线与子系统）、FFI 绑定的自动生成与契约检查、`unsafe` 代码的审查工具。
- **已有研究在做**：Rust 在实时、固件与机密计算场景的应用，形式化验证与 Rust 类型系统的结合（见 [100-os-formal-verification.md](100-os-formal-verification.md)）。
- **本文推测**：内核 Rust 的覆盖面可能按“新驱动先行、旧驱动不动”的节奏扩大，十年内仍是 C 为主、Rust 为辅的混合内核；检验标准是主线内核中 Rust 代码的行数占比与子系统覆盖数。
- **本文推测**：Framekernel 一类“语言即边界”的架构可能比纯微内核更快进入实用，因为它不要求重写驱动生态；检验标准是 Asterinas 等项目是否出现生产部署案例。
