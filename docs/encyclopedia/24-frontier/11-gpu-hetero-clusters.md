# GPU 集群与异构集群

> 本篇是[超算与高性能计算入门](03-hpc-supercomputing.md)（总览）下的一篇三级文章。总览讲 HPC 的组织方式：四条并行模型、集群五部分、调度与互连、TOP500 的正确读法。本篇不重复总览的内容，只讲总览里留给本篇的三级主题：以 GPU 为主力的集群在节点内、节点间、软件栈三个层次上是怎么组织起来的，以及“异构”这个词在集群层面到底难在哪里。

## 1. 研究问题

GPU 集群要解决的问题是：单块 GPU 再强，也装不下也算不动最大的科学问题与 AI 训练任务——模型参数、网格规模、粒子数一旦超过单卡内存与算力，就必须把成百上千块 GPU 组织成一个能协同算的系统，并且让“协同”的开销不要吃掉“并行”的收益。

异构集群把问题再推进一步：一个集群里同时有 CPU、GPU，有时还有专用 AI 加速器、FPGA、未来量子设备——它们的速度、内存模型、编程接口全都不一样。异构集群要解决的问题是：让一个应用在“不一样的硬件”上跑起来、跑得有效率，而不用为每种硬件重写一遍程序。这后半句至今没有完美答案，是本篇的核心张力。

本篇的边界：GPU 编程接口（CUDA、HIP、SYCL）的语法细节属于本分支后续三级主题“MPI、OpenMP、CUDA、HIP、SYCL”，本篇只讲它们在集群组织中的位置，不展开语法；单卡架构细节属于[先进芯片与 Chiplet](05-advanced-chips-chiplet.md)，本篇只讲“卡与卡之间”与“节点与节点之间”。

## 2. 基础理论

- **数据并行与模型并行**：数据并行是把数据分片、每块 GPU 跑同一份程序（适合“数据大、模型能装进单卡”的任务）；模型并行是把模型本身切开、分到多块 GPU 上（适合“模型装不进单卡”的任务）。大规模训练常是两者的混合，外加流水线并行；切分策略本身就是集群组织的一部分。
- **集合通信（collective communication）**：多 GPU 协同的四种基本操作——广播（broadcast）、规约（all-reduce）、收集（all-gather）、全交换（all-to-all）。AI 训练里的梯度同步就是 all-reduce；HPC 里的全局规约、全交换同样是集合通信。集合通信的算法与实现方式（环、树、分层）直接决定集群的扩展效率。
- **带宽阶梯**：从 GPU 自身内存，到节点内 GPU 间互连，到节点间网络，再到并行存储，每向外走一层，带宽通常下降、延迟通常上升。集群设计的第一原则就是：让最频繁、最大量的通信发生在最内层。
- **强扩展与弱扩展**：见总览第 2 节。报告 GPU 集群扩展效率时必须说明是哪一种扩展、通信占比多大的任务，否则“线性扩展”的说法没有意义。
- **异构的两种含义**：节点内异构（同一节点里 CPU + GPU/加速器）与系统级异构（同一集群里多种节点类型、多种加速器）。前者是今天的主流，后者是正在工程化的方向；混淆两者会误判难度。

## 3. 技术路线

按“协同发生在哪个层次”分四条路线，每条一句话讲清做法：

- **节点内 GPU 直连（NVLink/NVSwitch 路线）**：同一节点内的多块 GPU 不经过 PCIe 与主机内存中转，而是通过专用的 GPU 间互连直连；做法是节点内通信带宽与延迟都比走 PCIe 好一个档次，是 8 卡节点成为标准 building block 的原因。NVLink 与 NVSwitch 是 NVIDIA 的实现；AMD 的 Infinity Fabric 与 Intel 的 Xe Link 是同类思路的不同实现，名字与带宽口径各不相同，不可直接对标（具体带宽数字以各厂商官方发布为准，待核实）。
- **节点间 RDMA 网络（InfiniBand / 高速以太网路线）**：节点间通信走 RDMA（远程直接内存访问），GPU 内存可以不经过主机 CPU 中转、直接由网卡读写（GPUDirect RDMA）；做法是把节点间延迟压到最低、把 CPU 从数据搬运路径上摘掉。InfiniBand 与支持 RoCE 的高速以太网是两条竞争路线，选型涉及成本、生态与已有运维经验，没有 universal 的正确答案。
- **集合通信库（NCCL / RCCL / MPI 路线）**：应用不直接写裸网络代码，而是调用针对 GPU 优化的集合通信库——NVIDIA 的 NCCL、AMD 的 RCCL（同类实现）、以及支持 GPU 感知的 MPI 实现；做法是把“环/树算法选型、拓扑感知、分层规约”这些脏活交给库，应用只表达“要同步什么”。
- **可移植编程模型（Kokkos / RAJA / SYCL 路线）**：用一层抽象把“计算核函数”与“硬件后端”分开，同一份源码经不同后端编译到 NVIDIA、AMD、Intel 加速器上；做法是牺牲少量峰值性能换取跨厂商可移植，是 ECP 软件栈（见[Exascale 与 Post-Exascale](10-exascale-post.md)第 3 节）验证过的工程方向。注意：可移植不等于性能可移植——“能跑”与“跑得有效率”之间仍隔着针对每种硬件的调优。

还有一条常被并列提及、但层次不同的东西：**超节点/机柜级互连（rack-scale 域）**。新一代设计把 NVLink 域从“8 卡节点”扩大到“整机柜几十块 GPU”（如 GB200 NVL72 形态的机柜级设计），机柜成为新的“节点”。本篇把它记为正在工程化的方向，其具体带宽与规模数字以厂商官方发布为准（待核实），不写进正文。

## 4. 系统架构

一个 GPU 集群由五层组成，由内向外，通信成本逐层上升：

1. **GPU 与节点内互连层**：标准 building block 是 8 卡节点（DGX、HGX 等形态均为 8 卡节点，OEM 厂商基于同一基板出货）；卡间通过 NVSwitch/NVLink 类互连全互连，节点内任意两卡通信为一跳。节点内另有主机 CPU（常为双路）、主机内存与 PCIe 通道，负责控制、数据预处理与不规则任务。
2. **节点间计算网络层**：叶脊（leaf-spine）胖树拓扑是主流组织方式；关键组织技巧是**轨道对齐（rail-optimized）布线**——每台服务器的第 i 块网卡（第 i 条“轨道”）都接到同一台叶交换机上，使得集合通信时同一轨道的流量不互相抢同一条上行链路。这是 GPU 集群布线区别于普通数据中心布线的要点之一。
3. **网络平面分离**：参考架构通常把网络分成计算网（节点间 GPU 通信）、存储网（并行文件系统与共享存储）、管理网（带内管理与带外管理）三个平面；分开的目的是让存储流量与检查点流量不挤占计算网的带宽。
4. **存储层**：计算节点共享并行文件系统（如 Lustre、BeeGFS、GPFS/Spectrum Scale 等，总览第 4 节已列），另加节点本地 NVMe 作为缓存与临时存储；写检查点时先问“存储能接住吗”，再问“算得快吗”（总览第 6.4 节的结论在这里同样适用）。
5. **调度与资源管理层**：Slurm 等调度器把 GPU 作为可分配资源（Slurm 里以 GRES，即通用资源的方式申请，如 `--gres=gpu:8` 的写法，见第 6 节示例）；作业按节点、GPU 数、内存、时间申请资源。异构集群的调度比同构集群多一层难题：调度器要知道“这块 GPU 是哪家、什么型号、与哪个 CPU 配对”，并把作业放到匹配的节点上；节点类型越多，调度策略越复杂。

异构集群的系统架构补充：除了“GPU 集群”这种以一种加速器为主的形态，真正的系统级异构集群还会出现 CPU-only 节点、GPU 节点、专用 AI 加速器节点共存的分区（partition）划分——不同分区跑不同作业，调度器按作业需求把作业路由到对应分区。分区划分是运维策略，不是硬件属性；同一套硬件换一套分区策略，就是另一套集群行为。

## 5. 代表性实现与开源项目

只列真实存在的项目与系统，数字只写已核查的项：

- **NVIDIA DGX SuperPOD 参考架构**：NVIDIA 发布的 GPU 集群参考架构，以 DGX 系统为 building block、可扩展单元（SU）为部署单位；以 DGX H200 版本为例，一个 SU 含 32 台 DGX H200 系统，计算网采用 NDR（400 Gbps）InfiniBand，软件栈含 Base Command、AI Enterprise、CUDA、Magnum IO（来源：NVIDIA DGX SuperPOD 参考架构文档，2025 年 4 月 14 日版）。SuperPOD 是“参考架构 + 部署蓝图”，不是单一型号的机器；不同代际（H100/H200/Blackwell）的 SU 规模与网络配置以对应版本的官方文档为准（待核实）。
- **TOP500 中的 GPU 集群**：已验证的四台 exascale 系统全部是 GPU/加速器集群——El Capitan（AMD MI300A APU）、Frontier（AMD MI250X）、Aurora（Intel Data Center GPU Max）、JUPITER Booster（NVIDIA GH200），见[Exascale 与 Post-Exascale](10-exascale-post.md)第 7 节的表；GPU 集群不是 AI 专用的新事物，它就是今天超算的主流形态。
- **NCCL（NVIDIA Collective Communications Library）**：NVIDIA 的 GPU 集合通信库，针对 NVLink 与 InfiniBand 拓扑优化，是 GPU 集群上 all-reduce 等操作的事实标准实现之一。
- **RCCL（ROCm Communication Collectives Library）**：AMD ROCm 生态中的同类集合通信库，与 NCCL 接口思路相近、后端针对 AMD 加速器优化；跨厂商可移植代码常以“NCCL/RCCL + MPI”组合或 Kokkos/RAJA 抽象层来覆盖两者。
- **Slurm Workload Manager**：开源作业调度器（总览第 5 节已列），在 GPU 集群上以 GRES 机制分配 GPU 资源；本篇第 6 节的命令以 Slurm 为例，其他调度器（PBS、LSF、Flux 等）概念相通、命令不同。
- **Kokkos 与 RAJA**：美国国家实验室主导的可移植并行编程抽象库，同一份源码可编译到不同厂商的加速器后端；是 ECP 软件栈中“性能可移植”方向的代表实现（来源：ECP 官网软件生态描述与 IEEE exascale 技术导航页）。
- **尚无代表性商用系统**：这句话不适用于 GPU 集群——DGX SuperPOD 参考架构、TOP500 前列系统、云厂商的 GPU 集群均已是商用与生产系统；本篇的“尚无”节按模板要求删除，不硬填。

## 6. 关键论文与标准

- **MPI 标准（MPI Forum）**：节点间消息传递的标准，GPU 感知 MPI 实现允许 MPI 缓冲区直接指向 GPU 内存；版本号未写入正文，以官方发布为准（待核实）。
- **InfiniBand 规范（InfiniBand Trade Association）与 RoCE 规范**：节点间 RDMA 网络的事实标准与以太网承载方案；具体规范版本号未核对，未写入正文（待核实）。
- **代表性论文**：本篇不列具体论文篇目——集合通信算法（环、树、分层规约）与 GPU 集群拓扑的奠基性工作分散在多个方向，逐篇核对标题、作者与年份的工作尚未完成，宁缺毋滥（待核实）。

## 7. 当前实验结果

本节坚持“数字 + 来源 + 测试条件三件套，缺一件就不写”的规则，因此可写的硬数字很少——这本身就是结论的一部分：GPU 集群的公开可核对数字高度依赖具体系统与具体任务，没有“GPU 集群的速度”这种通用数字。

- **TOP500 口径的硬数字**：见[Exascale 与 Post-Exascale](10-exascale-post.md)第 7 节的表（HPL Rmax、HPCG、榜单申报功耗，TOP500 第 66 届榜单，2025 年 11 月）。本篇不重复贴表，只强调读法：HPL 名次高不等于你的应用在该集群上跑得快，拿自己的应用实测弱扩展与强扩展曲线才是验收标准。
- **参考架构口径的组织数字**：DGX SuperPOD（H200 版）一个可扩展单元含 32 台 DGX H200 系统、计算网为 NDR（400 Gbps）InfiniBand（来源：NVIDIA 参考架构文档，2025 年 4 月 14 日版）。这是“组织规模”的数字，不是“性能”的数字；不同代际的 SU 规模以对应版本文档为准。
- **不写进本节的数字**：各厂商宣传的单卡混合精度峰值算力、NVLink/NVSwitch 的逐代带宽数字、集合通信库在某规模下的实测带宽——它们要么口径不一（峰值 vs sustained、理论 vs 实测），要么缺可核对的测试条件，本篇一律不转载；以官方发布为准（待核实）。

## 8. Slurm GPU 作业示例（示例未实测）

以下脚本是通用写法，**示例未实测**（代理 VM 上无 Slurm、无 GPU、无 MPI 环境；读者须以目标集群的文档为准调整分区名、模块名与 GPU 型号）：

```bash
#!/bin/bash
#SBATCH --job-name=hello-gpu
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=2
#SBATCH --gres=gpu:2
#SBATCH --cpus-per-task=4
#SBATCH --time=00:30:00
#SBATCH --partition=gpu

module load cuda mpi  # 模块名以目标集群为准
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK
srun ./hello_gpu
```

读法：`--gres=gpu:2` 是每节点申请 2 块 GPU（Slurm 的通用资源机制）；`--ntasks-per-node` 是每节点 MPI 进程数；GPU 任务常按“每进程一块 GPU”的方式配比，`--cpus-per-task` 保证每进程有足够 CPU 核做数据预处理与通信；`srun` 在分配的资源上启动作业步。常见踩坑：申请了 GPU 却忘了申请配套的 CPU 核与内存，导致数据预处理成为瓶颈；或者多进程抢同一块 GPU，导致互相干扰——作业脚本里 GPU 与进程的配比必须显式写清。

## 9. 技术瓶颈

- **通信墙**：节点内 GPU 间带宽与节点间网络带宽之间仍有量级差距，集合通信（尤其是 all-to-all）在规模上去后最容易成为瓶颈；轨道对齐布线、SHARP 类网内规约（把规约算子卸载到交换机芯片上）是缓解手段，不是根治手段。
- **内存墙**：单卡 HBM 容量装不下最大模型与最大网格时，必须切分——切分策略（数据并行、模型并行、流水线并行）本身带来通信与负载均衡成本；统一内存与更大 HBM 是硬件侧的缓解，算法侧的切分仍是人工活。
- **可移植性墙**：CUDA、HIP、SYCL、Kokkos、RAJA 各有后端覆盖与性能调优成本；“一份源码处处跑”已接近实现，“一份源码处处跑得快”仍是工程难题；换代加速器时，调优工作常常要重做一遍。
- **调度与分区复杂性**：异构集群的节点类型越多，调度策略、配额、优先级、故障隔离的复杂度越高；“把作业放到对的节点上”本身成为运维成本。
- **故障与容错**：节点数、GPU 数上万后，单点故障不再是小概率事件；检查点/重启动、弹性训练（故障后自动恢复）成为必备能力，细节见本分支后续三级主题“集群调度、容错与资源管理”。
- **功耗与散热**：GPU 集群的功率密度高于 CPU 集群，液冷与供电已成为部署的前置约束，细节见本分支后续三级主题“液冷、能效与绿色超算”。

## 10. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：GPU 集群已是 TOP500 前列系统与云厂商 AI 基础设施的主流形态（四台已验证 exascale 系统全部是 GPU/加速器集群，DGX SuperPOD 参考架构已出到多代并有生产部署），调度、集合通信、RDMA 网络均有数年生产验证；跨厂商性能可移植仍是工程难题，但这不改变“GPU 集群”这个系统类别本身已成熟的判断。

## 11. 未来研究问题

- **已有研究在做**：机柜级互连域（NVLink 域从 8 卡节点扩大到整机柜）能否成为新的标准 building block；网内计算（交换机内规约）能覆盖多少集合通信模式；光互连能否进入节点间网络。
- **已有研究在做**：可移植编程模型的性能可移植——让同一份源码在不同厂商加速器上都接近手写优化的性能，而不只是“能跑”。
- **本文推测**：异构集群的调度可能会从“按节点类型分区”走向“按任务特征动态组合”——即同一作业的不同阶段用不同的加速器；检验标准是主流调度器是否普遍支持阶段感知的异构资源申请。
- **本文推测**：AI 训练与传统 HPC 仿真共用同一 GPU 集群的“融合集群”可能成为常态，但前提是调度器能同时满足“训练任务的弹性”与“仿真任务的独占批处理”两种模型；检验标准是主流超算中心是否普遍提供融合调度接口。
