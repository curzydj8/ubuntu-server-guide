# 下一代操作系统与系统软件

## 1. 研究问题

操作系统是硬件与应用之间的中介。过去几十年，主流通用操作系统大多是单体内核加 C 语言实现：性能好、生态大，但一个驱动或文件系统的缺陷就可能拖垮整个内核；同时，云、边缘、实时控制、异构加速器与多租户沙箱这些新负载，对操作系统提出了旧架构不太擅长的要求：更小的可信基、更可预测的时延、按工作负载裁剪的形态、以及对 GPU 等异构资源的第一等调度。

下一代操作系统方向要回答的问题是：能不能在不放弃性能与兼容性的前提下，让系统软件更安全、更可裁剪、更可验证？本方向的 10 个三级主题从不同角度回答这个问题：有的改内核结构（微内核、Unikernel），有的改时间保证（实时系统），有的改实现语言（内存安全、Rust），有的改部署形态（分布式、云边），有的改资源对象（GPU 运行时、沙箱），最后用形式化验证给正确性以数学证据。本篇是总览：每个主题各介绍一小段，不展开三级细节，细节见各三级篇。

## 2. 基础理论

- **内核结构**：单体内核把服务都放进特权态，微内核只留最小机制在特权态、其余服务放用户态；结构决定了故障隔离边界与通信代价。
- **实时性**：硬实时要求任务在截止期前完成是正确性的一部分，而非“越快越好”；可预测性优先于平均性能。
- **内存安全**：空间安全（不越界、不悬空）与时间安全（不重用已释放对象）是系统软件缺陷的主要来源；语言、硬件与验证是三条防线。
- **分布式与异构**：单机假设失效后，命名、一致性、故障模型与资源调度都要重新设计；加速器不再是外设，而是与 CPU 平行的计算资源。

## 3. 技术路线

本方向的十条路线各有主攻点，彼此交叉而非互斥：

- **改结构**：微内核与混合内核、Unikernel 与 Library OS。
- **改保证**：实时操作系统、操作系统形式化验证。
- **改语言**：内存安全系统软件、Rust 系统编程。
- **改形态**：分布式操作系统、云原生与边缘操作系统。
- **改资源边界**：GPU 运行时与异构资源调度、轻量级沙箱与隔离机制。

一条常见的组合是：微内核结构 + 内存安全语言实现 + 形式化验证关键部分 + 沙箱隔离不可信负载——四条防线叠加，而不是只押注一条。

## 4. 系统架构

下一代系统软件没有统一的参考架构，但有共同的演变趋势：特权态代码做减法（只留调度、内存管理与通信机制），策略与服务上移到用户态或编译期；系统以镜像、组件或服务单元为单位发布与更新，而不是以“装好后再改”的方式长期原地修补；加速器、网络与存储的调度从“事后外挂”变为内核与运行时的一等公民。本篇不规定一种架构，各三级篇分别讲自己的架构取舍。

## 5. 代表性实现与开源项目

总览只点名，不展开——细节与链接见各三级篇：微内核侧有 seL4、QNX 与 Fuchsia 的 Zircon；实时侧有 FreeRTOS、Zephyr 与 VxWorks；Unikernel 侧有 MirageOS 与 Unikraft；Rust 侧有 Linux 内核 Rust 支持、Redox OS 与 Asterinas；云边侧有 Bottlerocket、Talos Linux 与 Flatcar；沙箱侧有 gVisor、Firecracker 与 Kata Containers；GPU 侧有 CUDA 运行时、ROCm 与 Kubernetes 设备插件生态。版本号与发布状态以官方发布为准（待核实），本篇不转载厂商宣传数字。

## 6. 关键论文与标准

- Klein 等人 2009 年的 seL4 形式化验证工作（见 [100-os-formal-verification.md](100-os-formal-verification.md)）是本方向“验证可达”的关键证据。
- Madhavapeddy 等人的 Unikernel 论文是 Library OS 路线的经典论述，具体标题与年份见 [93-unikernel.md](93-unikernel.md) 的未完成项核对说明。
- POSIX、AUTOSAR 等接口与行业标准在实时与车载场景仍有约束力，但本方向没有统一的“下一代 OS”标准，暂无可列的统一标准编号。

## 7. 当前实验结果

本节不写性能倍数：各路线在不同硬件、不同负载下的数字不可直接比较，脱离测试条件的宣传数字本篇一律不采信。只写定性结论：微内核与实时系统已有商用部署；Rust 已进入 Linux 内核（初始支持随 Linux 6.1 于 2022 年 12 月合入，见 [95-rust-systems.md](95-rust-systems.md)）；云边不可变 OS 与微虚拟机沙箱已在云厂商生产环境使用；Unikernel 与通用 OS 形式化验证仍主要停留在研究与小众部署。

## 8. 技术瓶颈

- **兼容性**：新内核与新语言要跑现有应用，接口兼容与生态迁移是最大的非技术成本。
- **性能**：用户态服务化、跨域通信与沙箱拦截都会带来开销；开销是否可接受取决于负载，不是普适结论。
- **验证成本**：形式化验证的证明工作量随代码规模增长，通用大内核的完整验证仍不可行。
- **异构调度**：GPU、NPU 等加速器的共享、隔离与抢占语义远不如 CPU 成熟，调度器仍在演进。
- **碎片化**：云、边、端、实时各走各的系统，统一工具链与可移植性不足。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：本方向的个别分支（实时系统、云边不可变 OS、GPU 运行时、沙箱）已有生产应用，但作为整体的“下一代操作系统”并无统一形态，Unikernel 与形式化验证仍处研究阶段，故整体定为工程发展中而非成熟应用。

## 10. 未来研究问题

- **已有研究在做**：微内核的通信开销优化、Rust 在内核中的覆盖面扩大、GPU 的细粒度共享与抢占、沙箱与机密计算的结合。
- **已有研究在做**：形式化验证从微内核向驱动、文件系统等更大部件扩展。
- **本文推测**：下一代 OS 更可能以“混合形态”落地——单体内核吸收微内核与内存安全技术的部分成果，而不是被某一种新内核整体取代；检验标准是主流内核中内存安全语言代码与用户态服务化的占比变化。
- **本文推测**：云边 OS 与沙箱的边界可能继续模糊：节点 OS 越来越像“只跑容器的运行时”，而沙箱越来越像“轻量虚拟机”；检验标准是两者在接口与部署形态上的趋同程度。
