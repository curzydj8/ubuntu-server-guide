# 分布式对象存储

本篇是[新型存储与互连总览](09-new-storage-interconnect.md)所列存储路线中“分布式与互连”方向的展开：总览讲存储分层与互连结构，本篇只讲分布式对象存储这一条三级主题——对象语义、数据放置、冗余、一致性与元数据，不重复总览的 HBM 与 CXL 内容，也不重复 05 域的基础选型内容。

## 1. 研究问题

对象存储要解决的问题是：数据规模从“一个机房能装下”增长到“必须跨大量节点、跨站点、且持续增长”时，传统的“目录树 + 集中式元数据表 + 固定卷”模式会在哪里先撑不住？答案通常是三个地方同时吃紧：元数据查询成为瓶颈、单点故障的 blast radius（影响面）变大、扩容与故障恢复需要人工干预。

分布式对象存储的回答是：放弃 POSIX 文件语义的全部承诺（没有目录改名原子性、没有原地修改的字节流），换取三个能力——用扁平命名空间与确定性放置摆脱集中式元数据瓶颈、用冗余编码在节点故障时自动恢复、用 API 语义（不可变对象、版本化）简化一致性问题。这是一种“用语义换规模”的 trade-off（权衡），不是“文件系统升级版”。

## 2. 基础理论

- **对象语义**：存储单元是“对象”——一段不可变字节 + 元数据（键、大小、版本、自定义标签）+ 唯一标识；对象没有目录层级，所谓“前缀”只是键的命名约定，列举（list）是按前缀过滤，不是遍历目录树。对象一般不支持原地改写，更新即写入新版本或新对象。
- **确定性放置（以 Ceph 的 CRUSH 为例）**：客户端与存储节点用同一算法（Controlled Replication Under Scalable Hashing，受控复制的可扩展哈希）从对象名与集群映射算出数据应落在哪组节点上，而不需要每次查询中央元数据表；这消除了集中式查找瓶颈，是规模化的关键一环。放置组（Placement Group，PG）是复制与纠删的单位，对象先归属 PG，PG 再映射到一组存储节点（OSD）。
- **复制（replication）**：保存若干份完整副本；优点是恢复简单、读可并行，代价是容量开销随副本数线性增长。Ceph 文档中的配置示例是：3 副本池存 1 TB 有效数据用 3 TB 容量——这是配置示例，不是通用比率。
- **纠删码（erasure coding）**：把数据切为 K 个数据块、算出 M 个校验块，K+M 块分散存放，丢失任意 M 块以内仍可重建；优点是容量开销低于多副本，代价是重建要读多块并计算、写路径与小对象场景的开销较大。Ceph 文档中的默认纠删码配置示例是：存 1 TB 有效数据用 2 TB 容量、可容忍两块 OSD 的重叠丢失——同样只是配置示例，不同 K/M 组合的开销与容忍度不同，不能跨配置引用。
- **一致性边界**：一致性必须对“哪个服务、哪种操作、哪个边界”讲才有意义；“对象存储是强一致的”与“对象存储是最终一致的”作为通用断言都太宽泛。Ceph 的 RADOS Gateway（RGW）文档表述为对象操作的读后写一致：写成功返回后，后续读应看到该写或更新的写/删除，其实现方式是对象头（head）最后写入作为原子可见步骤——这是 RGW 的实现表述，不是所有对象存储的通用保证。跨站点复制的一致性是另一个边界：本地写成功不等于远端站点已同步。
- **元数据与数据分离**：对象数据与索引、桶（bucket）信息是两类不同的状态；对象字节本身只占工作量的一部分，系统还必须维护“对象在哪、桶里有什么、版本关系”这些信息，否则数据存进去了也列不出来、找不回来。

## 3. 技术路线

- **统一存储路线（以 Ceph 为代表）**：同一分布式对象层（RADOS）之上同时提供对象（RGW 的 S3/Swift 兼容接口）、块（RBD）、文件（CephFS）三种访问；优点是同一集群、同一冗余机制服务多种负载，代价是系统复杂度高，调优需要理解 PG、CRUSH、池策略等多层概念。
- **云原生对象服务路线（以 S3 兼容 API 为代表）**：以 HTTP + S3 语义为事实标准接口，应用按桶/键访问，不关心后端节点拓扑；优点是生态与工具链最广，代价是一致性、版本、生命周期等语义以各服务商的具体实现与文档为准，不能把一家服务的保证平移到另一家。
- **纠删码优先的冷数据路线**：对大对象、写少读少、容量敏感的负载用纠删码换容量效率；对小对象、高频写、延迟敏感的负载仍倾向复制——这是按负载选冗余策略，不是“纠删码全面优于复制”。
- **元数据分离与可扩展索引路线**：对象索引（桶索引、全局命名空间）独立扩展，常见做法是把索引本身也分布式存放、按桶分片；索引的扩展性与一致性往往比数据面更先成为瓶颈。
- **多站点与分层路线**：跨站点复制、生命周期分层（热对象留本地、冷对象迁往低成本层）是规模化后的常见演进；分层策略与一致性边界必须一起讲，否则“数据在两个地方”会变成“不知道哪个是真的”。

## 4. 系统架构

以 Ceph 为例（它是公开文档最完整的开源实现，不代表所有对象存储都长这样）：

- **RADOS（可靠、自主、分布式对象存储层）**：集群的核心，负责对象存放、I/O 服务、数据保护（复制或纠删码）、故障重平衡与完整性校验（scrubbing / deep-scrubbing）。
- **MON（监视器）**：维护集群映射与配置，通过仲裁（quorum）保证集群状态一致；客户端与 OSD 用集群映射做 CRUSH 放置计算。
- **OSD（对象存储守护进程）**：真正存放数据的节点，处理读写、复制/纠删、恢复；是数据面的工作主体。
- **MGR（管理器）**：集群管理与监控信息的汇聚点，不直接服务数据 I/O。
- **MDS（元数据服务器）**：只在配置了 CephFS 文件系统时部署，管理目录层级与文件元数据（归属、时间戳、模式等）；对象路径（RGW）不经过 MDS——把 MDS 当成对象存储的元数据瓶颈是常见误解。
- **RGW（RADOS Gateway）**：对象访问的 HTTP 网关，提供 S3 与 Swift 兼容接口；RGW 实现中一个 API 对象可由头对象与尾对象组成，桶索引条目另行存放——这说明“对象”在实现上不只是一段字节。
- **尚无代表性商用系统之外的统一架构**：各云厂商的对象服务后端架构不公开，不能把 Ceph 的结构套用到所有 S3 兼容服务上；讲架构时须区分“开源实现的公开结构”与“云服务的黑盒实现”。

## 5. 代表性实现与开源项目

只列真实存在的项目与接口方向，不写未核实的规模与份额数字：

- **Ceph（RADOS / RGW / RBD / CephFS）**：开源软件定义存储，统一对象、块、文件三种访问；创建者 Sage Weil 在加州大学圣克鲁兹分校的博士研究期间起步。部署规模、性能数字以各部署的实测为准，本篇不转载“可扩展到 EB 量级”之外的横向性能结论。
- **MinIO**：开源的 S3 兼容对象存储实现，面向“自建 S3 兼容服务”的场景；其纠删码、版本、生命周期等语义以项目文档为准（待核实），本篇不逐项转载其配置参数。
- **S3 兼容 API 生态**：S3 接口已成为对象存储的事实标准接口，大量工具（备份、数据湖、AI 数据加载）按 S3 语义编写；“兼容 S3”不等于“语义完全相同”，一致性、版本、加密、生命周期细节须按各实现文档核对。
- **云厂商对象服务**：各大云的对象存储服务是分布式对象存储最成熟的部署形态，但其后端架构、冗余实现与一致性保证属于服务商文档范畴，本篇不推测其内部结构。

## 6. 关键论文与标准

- **S3 API（Amazon Simple Storage Service 接口）**：对象存储的事实标准接口，桶/键/版本/生命周期等概念的来源；具体语义以各实现的 API 文档为准，不存在一份覆盖所有实现的单一标准文本可逐条引用。
- **Ceph 相关公开文档**：RADOS、CRUSH、RGW 一致性等概念的来源是 Ceph 官方文档与 Red Hat 的 Ceph 架构介绍；本篇的 CRUSH、PG、MON/OSD/MDS/MGR、RGW 结构表述以这些公开文档为准。
- **暂无单一论文可作为本篇的理论来源**：分布式对象存储是工程系统演进的结果，纠删码本身来自编码理论、一致性来自分布式系统理论，但“对象存储架构”没有一篇奠基论文可概括；需要引用时应直读各项目的官方文档再补。
- **不编造引用**：本篇不列出未经核查的论文标题与链接。

## 7. 当前实验结果

本节不写横向性能数字：对象存储的吞吐与延迟高度依赖对象大小分布、冗余策略、网络、节点数与客户端并发，脱离条件没有可比性。只写经核查的定性结论：

- 复制与纠删码的取舍是容量效率 vs 恢复与写开销的取舍，不是单向优劣；小对象与高频写场景下纠删码的优势会被分块与计算开销抵消。
- 确定性放置（CRUSH 类算法）消除了集中式元数据查找瓶颈，但代价是集群映射变更（扩容、故障）需要全集群收敛到同一映射版本，收敛期间的放置行为须按实现文档理解。
- 对象语义的不可变性简化了一致性：没有原地改写，就没有“读到一半新一半旧”的字节流问题；但版本、删除、列举的语义仍需按实现文档核对，不能想当然。
- 跨站点场景下，本地一致性保证不等于全局一致性；“写成功”与“远端可见”是两个事件，应用须按服务商的复制语义设计重试与冲突处理。

## 8. 技术瓶颈

- **元数据与索引瓶颈**：对象数量增长时，桶索引、列举、版本管理的扩展性往往先于数据面成为瓶颈；索引分片与缓存策略是持续演进点。
- **纠删码的小对象与写放大瓶颈**：小对象分块后校验开销占比高、写路径需多节点协调；纠删码不是所有负载的默认最优解。
- **故障恢复的带宽瓶颈**：节点故障后重建数据要跨网络读多块并计算，重建流量与正常业务流量争带宽；重建速度与业务影响的平衡是运维关键。
- **一致性理解的瓶颈**：开发者常把某一服务的保证误读为通用保证（尤其跨站点、跨版本场景），导致应用在故障时行为异常；这更多是语义理解问题，不是某一产品的缺陷。
- **运维复杂度瓶颈**：统一存储（Ceph 类）的概念层数多（池、PG、CRUSH 规则、网关、元数据服务），调参与故障定位门槛高；这是“统一”的代价。
- **成本**：冗余本身就是成本——复制的容量开销、纠删码的计算与重建开销、跨站点复制的带宽开销都会传导到总价；“对象存储便宜”只在与具体冗余策略与访问模式一起讲时才成立。

## 9. 成熟度判断

- **成熟度：成熟应用。** 判断依据一句话：分布式对象存储（Ceph、S3 兼容生态、云对象服务）已是备份、数据湖、AI 数据加载等场景的量产基础设施，但其前沿问题（索引扩展、纠删码调优、跨站点一致性）仍在演进中，成熟的是“对象存储作为基础设施”，不是“所有场景都有最优解”。

## 10. 未来研究问题

- **已有研究在做**：更高效的纠删码布局（降低重建带宽与写开销）、可扩展的对象索引与元数据服务、跨站点一致性与冲突处理的更清晰语义。
- **已有研究在做**：对象存储与 AI 数据加载的结合——按训练访问模式做预取、分层与缓存，减少对象接口在小文件随机读场景下的开销。
- **本文推测**：对象存储的下一道门槛可能不是“容量”，而是“元数据与索引的规模”——对象数增长快于单对象大小增长时，索引先撑不住；检验标准是未来对象存储的性能讨论是否从“吞吐”转向“列举与索引延迟”。
- **本文推测**：S3 语义可能继续作为事实标准，但各实现的语义差异（版本、生命周期、一致性边界）会迫使应用层出现“可移植性适配层”；检验标准是备份与数据湖工具是否开始显式标注“在哪些 S3 实现上验证过哪些语义”。
