# 计算架构仿真与基准测试

> 本篇是新型计算架构分支的方法论篇，归属见 [后冯·诺依曼架构](72-post-von-neumann.md) 的评估层与 [新型计算架构：光子与存算一体](08-new-computing-arch.md) 总览的边界说明：本分支所有文章“数字必须带来源与测试条件”的纪律，方法论就在本篇。它不讲任何一种架构的器件（器件归各三级主题篇），只讲“如何证明一个架构主张是真的”——仿真怎么搭、基准怎么选、数字怎么读、作弊怎么识。

## 1. 研究问题

新架构的论文与产品宣传里充满数字：“快多少倍”“能效高多少倍”“延迟低多少”。但这些数字常常不可比较：精度不同、模型不同、批量不同、是否含转换开销不同、是否含编译时间不同、基线不同。计算架构仿真与基准测试要回答的问题是：**如何用可复现、可比较、可证伪的方法，评估一个计算架构的真实水平，并识别出那些经不起推敲的数字？**

这个问题分两半：仿真解决“硬件还没造出来，怎么评估”的问题；基准测试解决“硬件造出来了，怎么公平比较”的问题。两半都做不好，新架构领域就会陷入“各说各话、无法证伪”的状态——而这正是本分支写作规范要求“缺来源或测试条件就不写入正文”的原因。

## 2. 基础理论

- **仿真分层**：功能仿真（算对不对）与时序仿真（算多快）分离；功能仿真验证正确性，时序仿真评估性能。两者精度与速度成反比：越精确的时序模型越慢，这是仿真领域的根本 trade-off。
- **采样仿真**：对长程序只仿真有代表性的片段（如 SimPoint 选取的程序相位），再外推整体性能；采样引入统计误差，误差必须报告，不能只报点值。
- **基准代表性**：基准套件的价值取决于它多大程度上代表真实负载；代表性不足的基准会误导架构设计（为基准优化、而非为真实负载优化），这是基准领域的经典问题。
- **性能指标的口径**：吞吐（ops/s）、延迟、能效（ops/W）、每美元性能、每瓦性能是不同维度的指标；单看任何一个都会误导，系统评估必须多维度并列。
- **统计方法**：性能测量有噪声（频率调节、系统抖动、编译差异），必须多次运行、报告均值与方差、做显著性判断；单次运行的数字没有统计意义。
- **验证（validation）**：仿真器本身需要验证——仿真结果与真实硬件的误差范围必须量化并报告；未经验证的仿真器给出的数字不可采信。

## 3. 技术路线

按“仿真粒度与基准类型”划分：

- **功能仿真路线**：QEMU、Spike（RISC-V）等；只验证功能正确性，不评估时序。适合软件开发与早期正确性验证，速度快但无性能信息。
- **时序仿真路线**：gem5、SST、Sniper、ZSim 等；建模流水线、缓存、内存系统，给出周期级或近似时序。gem5 是学术界最广泛使用的开源时序仿真器，支持多种 CPU 模型（顺序、乱序）与多种指令集；SST 面向大规模系统级仿真；Sniper/ZSim 用解析模型换速度，适合多核快速评估。
- **RTL 仿真与 FPGA 原型路线**：Verilator 等 RTL 仿真、FPGA 原型验证；精度最高（接近真实硬件），但速度最慢、搭建成本最高。适合架构定型前的最后验证，不适合早期探索。
- **解析模型路线**：Roofline 模型等；用少量参数快速估算性能上限，适合早期筛选与瓶颈定位，但无法给出精确数字。
- **通用基准路线**：SPEC CPU（通用 CPU 性能的事实标准）、LINPACK（超算排名 HPL 的基础，见 [超算与高性能计算入门](03-hpc-supercomputing.md)）；适合跨代、跨厂商的通用比较，但与 AI 负载的代表性有限。
- **AI 基准路线**：MLPerf（训练与推理的行业基准，含系统级规则与提交审核）；适合 AI 加速器比较，但规则复杂、提交成本高，小团队难以完整参与。
- **系统与云基准路线**：数据中心负载基准（如 DCPerf 一类）、存储与网络基准；适合系统级评估，但口径更复杂。
- **新兴架构专用评估路线**：存算、光子、模拟架构尚无统一基准；目前的做法是“借用”通用基准的部分负载 + 自定测试条件——这正是本分支要求“测试条件必须写清”的原因：自定条件本身不是问题，不写清才是问题。

## 4. 系统架构

一个典型的架构评估流水线由以下部分组成：

- **负载层**：基准程序与真实应用负载；负载选择决定评估结论的适用范围，负载本身必须公开、可获取。
- **仿真/硬件层**：仿真器或真实硬件；仿真器配置（CPU 模型、缓存参数、内存时序）必须完整记录，否则结果不可复现。
- **测量层**：性能计数器、功耗测量、计时方法；测量方法（硬件计数器、软件计时、仿真统计）必须说明，不同方法的系统误差不同。
- **统计与报告层**：多次运行、均值与方差、置信区间、基线说明；报告必须含：硬件/仿真配置、软件版本、编译选项、数据规模、精度、批量、是否含转换与存储开销。
- **验证层**：仿真结果与真实硬件的对照（若有硬件）、基准结果与官方提交的对照；验证失败时，仿真结论必须降级为“未验证”，不可按已验证引用。

## 5. 代表性实现与开源项目

只列真实存在的项目，不写未核实的性能数字：

- **gem5**：开源架构仿真器，功能与时序仿真、多种 CPU 模型与指令集，是学术界的标准工具之一。
- **SST（Structural Simulation Toolkit）**：Sandia 国家实验室的系统级仿真框架，面向大规模并行系统。
- **QEMU**：开源功能仿真器与虚拟化工具，速度快、无时序信息。
- **Verilator**：开源 RTL 仿真器，把 Verilog 编译成 C++ 仿真，速度高于传统事件驱动仿真。
- **SPEC CPU2017**：SPEC 组织的通用 CPU 基准套件，含整数与浮点子集，是通用 CPU 比较的事实标准。
- **MLPerf**：MLCommons 组织的 AI 基准，含训练与推理套件，有严格的提交与审核规则。
- **LINPACK / HPL**：线性方程组求解基准，TOP500 排名的基础；代表性有限（稠密线性代数），不能代表全部 HPC 负载。

## 6. 关键论文与标准

- gem5 论文：Binkert 等，《The gem5 Simulator》, ACM SIGARCH Computer Architecture News, 2011 年。
- SPEC CPU2017 规范文档（SPEC 官方）——通用 CPU 基准的规则文本。
- MLPerf 规则文档（MLCommons 官方）——AI 基准的提交与审核规则。
- Roofline 模型：Williams 等，2009 年（见 [异构计算与 CPU/GPU/NPU/TPU 协同](77-heterogeneous-computing.md)）。
- 暂无统一标准：新兴架构（存算、光子、模拟）尚无统一基准与精度度量标准；评估时必须自报测试条件，不可默认与他人可比。

## 7. 当前实验结果

本节不写任何“某架构快多少倍”的数字——那正是本篇要教会读者警惕的东西。只写方法论层面的、经核查的结论：

- 仿真器验证是必要的：未经验证的仿真器误差可达数倍，直接引用其数字会误导结论；已发表的仿真验证研究普遍报告误差范围而非点值。
- 基准作弊是真实存在的历史现象：针对基准特征优化（而非真实负载）、选择性报告、基线选择偏袒、编译选项特殊化，都是文献与行业中记录过的手法；识别方法是要求完整报告（配置、版本、选项、多次运行统计）。
- MLPerf 的审核规则（提交代码、系统描述、多次运行）是行业为解决“数字不可比”而做的制度努力；但规则本身复杂，小团队完整参与的成本高，这是制度的代价。

## 8. 技术瓶颈

- **仿真速度与精度的 trade-off**：周期级仿真慢到无法跑完整真实负载，采样与解析模型快但有误差；没有两全的仿真方法。
- **新兴架构的建模缺失**：存算、光子、模拟器件的仿真模型不成熟（噪声、失配、漂移难以建模），仿真结果的可信度低于数字电路仿真。
- **基准代表性滞后**：基准套件更新慢于负载演进；AI 负载几年一变，基准套件的代表性窗口有限。
- **功耗与能效测量难**：功耗测量需要硬件支持或精确模型；仿真功耗模型的误差常大于性能模型，且常被忽略不报。
- **复现成本高**：完整复现一个架构评估需要硬件、工具链、负载、配置四者齐全；缺一不可复现，而论文常只公开部分。
- **数字的误读**：峰值性能（peak）与持续性能（sustained）、器件级与系统级、含转换与不含转换，是三组最常见的误读；读任何数字前先确认它属于哪一组。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：通用仿真器与基准套件（gem5、SPEC、MLPerf）已是工程现实并大规模使用，但新兴架构的建模、基准代表性、功耗测量与复现机制仍在演进中；方法论本身成熟，方法论在新架构上的应用未成熟。

## 10. 未来研究问题

- **已有研究在做**：新兴架构的仿真模型——存算、光子、模拟器件的噪声、失配与漂移建模。
- **已有研究在做**：面向 AI 与异构系统的新基准——代表性更强、更新更快的基准套件与审核机制。
- **已有研究在做**：仿真与机器学习的结合——用学习模型加速仿真（以少量精度换大量速度），但学习模型本身需要验证。
- **本文推测**：架构评估的下一个进步可能不在工具，而在制度——强制完整报告（配置、版本、选项、统计、验证误差）会比新工具更有效地减少不可比数字；检验标准是顶级会议与厂商发布是否普遍采纳完整报告规范。
