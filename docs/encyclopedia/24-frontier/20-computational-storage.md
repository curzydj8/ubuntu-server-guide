# 计算型存储：把算力放到数据所在的地方

本篇是[新型存储与互连总览](09-new-storage-interconnect.md)分支下的三级主题，只讲计算型存储这一条路线：不换存储介质，而是把算力放到存储设备里或存储设备旁边，让数据少搬运。换存储器件的路线归[MRAM、ReRAM 与 PCM](18-mram-reram-pcm.md)与[新型非易失性存储](19-novel-nvm.md)，HBM 与 CXL 的结构归总览篇，本篇如需提及只链接、不展开；全闪存与消费级 SSD 的结构与选购归 01 域文章，本篇不写。

## 1. 研究问题

数据密集型任务有一个结构性浪费：数据存在 SSD 里，算力在主机 CPU/GPU 上，任务的第一步总是把全部原始数据沿着总线搬到主机，哪怕最后只要其中极小一部分（例如一次查询只返回几行、一次扫描只命中少量记录）。搬运本身耗带宽、耗时间、耗功耗，而且主机算力常常在等数据。

计算型存储要回答的问题是：如果把第一步的过滤、聚合、压缩、加密等处理放到存储设备里做，只把结果送回主机，能省多少搬运？以及为此要付出什么代价——设备里的算力从哪来、编程模型怎么统一、安全边界怎么划？

## 2. 基础理论

- **近数据处理（Near-Data Processing）**：把计算放到离数据最近的地方做，而不是把数据搬到计算所在的地方做。这是一个架构思想，不是某一种产品；计算型存储是它在存储层的一个实例，存算一体（归[新型计算架构：光子与存算一体](08-new-computing-arch.md)）是它在器件层的另一个实例，两者不要混为一谈。
- **数据缩减率决定收益**：计算型存储的收益取决于“输入数据量 / 输出结果量”之比。过滤、扫描、聚合类任务缩减率高，收益大；已经高度压缩或本身就要全量返回的任务缩减率低，收益小甚至为负（设备算力弱于主机，算得更慢）。没有缩减率的任务谈计算型存储收益，是没有前提的讨论。
- **设备内带宽高于主机总线带宽**：SSD 内部多通道并行读出的带宽总量通常高于它对外接口的带宽，这是“在设备里算”能成立的物理前提；但设备内算力（FPGA、嵌入式 CPU、固定功能加速器）的绝对算力通常弱于主机，所以它只适合做“第一步的、数据密集的、算力要求不高的”处理，不适合替代主机做重计算。
- **SNIA 的术语框架**：SNIA（存储网络工业协会）的《计算型存储架构与编程模型》把生态中的角色标准化：CSD（计算型存储盘，存储与计算一体）、CSP（计算型存储处理器，只算不存）、CSA（计算型存储阵列，多设备组合），以及在设备上运行的计算单元 CSF（计算型存储函数）。术语统一是互操作的前提，不是性能保证。
- **NVMe 的计算型存储特性**：NVM Express 组织在 NVMe 2.0 规范体系中引入了计算型存储特性，提供连接应用与计算型存储设备的厂商中立框架，包括计算程序命令集（管理设备上计算程序的加载、激活、执行）与子系统本地命令集等方向；具体命令与版本以 NVMe 官方发布为准（待核实）。

## 3. 技术路线

按设备里放什么算力，分三条路线，各自的灵活与代价不同：

- **FPGA 路线：可重构逻辑**。在 SSD 里或 SSD 旁放一块 FPGA，用可重构电路实现扫描、过滤、转码等加速逻辑。代表方向是三星 SmartSSD（SSD + FPGA 的组合）。长处是灵活：同一块硬件可换逻辑做不同任务；代价是 FPGA 成本高、开发门槛高（要写硬件逻辑或用高层次综合工具），且功耗与散热要在盘内有限空间里解决。
- **嵌入式 CPU 路线：盘里跑通用程序**。在存储设备里放 ARM 等嵌入式 CPU 核，盘里跑一个小型通用环境（如 Linux），执行普通程序。代表方向是 NGD Systems 的 Newport 等平台。长处是编程门槛低（普通软件可直接跑）；代价是嵌入式 CPU 的绝对算力弱，只适合轻量处理，且盘内操作系统的维护、安全更新成为新负担。
- **固定功能 ASIC 路线：只做几件确定的事**。在盘里放固定功能加速器，只做压缩/解压、加密、校验、去重等预先定义好的操作。代表方向是 ScaleFlux 的透明压缩盘等产品。长处是效率高、成本低、接口简单（应用不用改代码就能受益，例如写入自动压缩）；代价是不灵活：只能做厂商预设的操作，做不了用户自定义的查询逻辑。Kioxia 向 SNIA 提出的固定功能计算（FFC）框架，正是想把这类预设操作标准化成通用接口，目前仍处在早期设计阶段，以 SNIA 官方进展为准（待核实）。

## 4. 系统架构

一个计算型存储系统的组成部分与关系：

- **主机侧**：应用发出“计算型存储请求”，而不是“读全部数据请求”；主机运行时负责把请求下发到设备、管理设备上的计算函数、接收结果。没有主机侧运行时支持，设备里的算力应用用不上。
- **设备侧**：存储介质（通常是 NAND 闪存）+ 计算引擎（FPGA、嵌入式 CPU 或固定功能加速器）+ 设备内存（供计算函数使用的函数数据内存 FDM）。数据从介质读出后先进入设备内存、经计算引擎处理，结果再返回主机；原始数据不出设备。
- **互连侧**：主机与设备之间仍走 NVMe/PCIe 等标准接口；设备内介质与计算引擎之间有私有数据通路（如 SmartSSD 中 FPGA 与 NAND 之间的数据通路），这条通路不经过主机总线，是收益的来源之一。
- **一个示例流程（示例未实测）**：概念上的数据库扫描下推流程——主机下发“扫描某表、过滤出满足条件的行”的请求（示例未实测）；设备在内部读出数据、过滤、只把命中行返回主机（示例未实测）；主机不再收到全表数据。本示例只讲流程结构，不含可执行命令，也未经任何硬件实测，不得当作部署指南。
- **与 CXL 的关系**：CXL 计算型存储是较新的交叉方向（把计算型存储做到 CXL SSD 上，使设备内存对主机可见），属于研究与早期产品方向，具体形态以厂商与论文发布为准（待核实）；CXL 本身的结构见[新型存储与互连总览](09-new-storage-interconnect.md)，本篇不展开。

## 5. 代表性实现与开源项目

只列真实存在的产品与标准方向，不写未核实的性能倍数与市场份额：

- **三星 SmartSSD**：SSD 与 FPGA 组合的计算型存储盘方向；早期产品形态为 U.2 NVMe 盘 + FPGA，具体容量、FPGA 型号与代际以三星官方发布为准（待核实）。厂商宣传中的查询加速倍数高度依赖测试负载，本篇不转载。
- **ScaleFlux**：固定功能路线的代表方向，产品以透明压缩等预设加速见长；具体型号与压缩收益以官方发布为准（待核实），且压缩收益高度依赖数据类型，不可推广为通用结论。
- **NGD Systems Newport/Catalina**：嵌入式 CPU 路线的代表方向，盘内集成 ARM 核与可编程逻辑；具体配置以官方发布为准（待核实）。
- **标准方向**：SNIA《计算型存储架构与编程模型》v1.0（2022 年批准）与《计算型存储 API》v1.1（2025 年 5 月 31 日发布）；NVMe 计算型存储特性（NVMe 2.0 规范体系内）。标准存在不等于产品互通——各厂商的编程模型与工具链仍有差异，跨厂商移植仍需验证。
- **尚无统一结论**：计算型存储在真实业务负载下的横向收益（省多少带宽、省多少主机 CPU、代价是多少功耗与开发成本）尚无跨厂商的公开横向基准，本篇不做“值不值得上计算型存储”的通用结论。

## 7. 当前实验结果

本节不写横向性能数字：计算型存储的收益高度依赖任务缩减率、设备算力、主机配置与测试负载，脱离条件没有可比性。只写经核查的定性结论：

- 计算型存储的收益只在“缩减率高 + 设备算力够用”的任务上成立；缩减率低的任务用它可能更慢，这是结构性结论，不是某一产品的缺陷。
- 固定功能路线（压缩、加密、校验）的收益最容易兑现，因为应用不用改代码；可编程路线（FPGA、嵌入式 CPU）的收益取决于应用是否愿意为特定设备改代码与维护设备侧逻辑。
- 标准（SNIA 架构与 API、NVMe 计算特性）已经发布，但各厂商工具链仍有差异；“符合标准”不等于“代码跨厂商可移植”，移植成本仍需实测验证（待核实）。
- 厂商宣传中的加速倍数（如某些数据库查询场景的倍数）均为厂商测试负载下的结果，本篇不转载，读者应以自己的负载实测为准。

## 8. 技术瓶颈

- **算力放哪里**：设备里的算力弱于主机是结构性约束——盘内空间、功耗、散热都有限。放重了，盘变贵变热；放轻了，能做的任务有限。放多少算力、放什么算力，是每款产品都要重新权衡的，没有通用答案。
- **省了什么**：省的是主机总线带宽与主机 CPU 占用，不是存储介质本身的读写量——数据还是要从介质读出来，只是不再全量送上主机。对介质寿命没有直接收益，不要把“省带宽”读成“省介质磨损”。
- **代价是什么**：一是开发代价（可编程路线要为设备写逻辑、维护设备侧软件栈）；二是运维代价（盘里多了一个要更新、要监控、要隔离的计算环境）；三是安全代价（设备侧代码能接触原始数据，隔离与权限模型必须重新设计，见下一点）。
- **安全边界瓶颈**：设备侧计算函数运行在存储设备里，能接触到未经主机过滤的原始数据；多租户共享设备时，函数之间的数据隔离、函数代码的来源认证、函数对数据的越权访问，都是尚未完全标准化的风险面。固定功能路线（不允许主机向盘里下载可执行代码改写数据）的安全面小于可编程路线，这是 FFC 提案被提出的原因之一。
- **编程模型与生态瓶颈**：应用要改代码才能用可编程计算存储，而每家工具链不同；没有“写一次、各家盘上都能跑”的成熟生态，应用厂商的投入意愿就低；投入意愿低，生态就更难成熟——这是典型的冷启动问题。
- **热与功耗瓶颈**：盘内计算会增加盘内功耗与发热，在持续高负载下可能触发降频甚至关断保护；设备侧算力的持续性能与峰值性能差距较大，选型时要以持续负载为准（待核实）。

## 9. 成熟度判断

- **成熟度：工程发展中。** 判断依据一句话：已有真实产品与已发布的标准（SNIA 架构与 API、NVMe 计算特性），但可编程路线的生态未统一、横向收益基准未建立、计算型存储尚未成为数据中心存储的默认配置，仍在工程发展中。
- **分路线判**：固定功能路线最接近成熟应用（压缩、加密等预设操作已可透明受益）；FPGA 与嵌入式 CPU 的可编程路线处于工程发展中（产品存在、生态未统一）；CXL 计算型存储属于实验研究中（原型与早期产品方向）。

## 10. 未来研究问题

- **已有研究在做**：固定功能计算接口的标准化（Kioxia 向 SNIA 提出的 FFC 框架方向）、跨厂商可移植的编程模型（如 WebAssembly 等可迁移计算单元在存储设备上的应用研究）、CXL 计算型存储的内存一致性模型。
- **已有研究在做**：设备侧计算的安全隔离模型（多租户下函数间隔离、代码认证、数据访问审计）。
- **本文推测**：计算型存储的下一道门槛可能不是“设备算力更强”，而是“应用不用改代码就能受益的操作集合有多大”——即固定功能操作的标准化覆盖面；检验标准是未来 SNIA/NVMe 标准中固定功能操作的数量与厂商采纳率。
- **本文推测**：如果 AI 推理的数据预处理（过滤、解压、格式转换）成为主流负载，计算型存储可能先在“数据预处理下推”而非“通用查询加速”上规模化；检验标准是数据平台厂商是否把预处理下推作为默认配置而非可选特性。
