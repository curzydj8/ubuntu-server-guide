# 授权测试流程

> 本篇只讲流程与管理：授权怎么确认、范围怎么划、计划怎么写、报告怎么交、复测怎么验。
> 不写针对真实系统的攻击步骤、利用代码、绕过方法；测试执行一律限定在书面授权范围内的系统。

## 1. 技术原理

### 1.1 授权测试是什么

授权测试（Authorized Testing）是指在**被测方书面授权**的前提下，对约定范围内的系统做安全评估。它的合法性来自授权本身，而不是测试方法——同一种检查动作，有授权是评估，没有授权就是未授权访问。授权测试的产出不是“攻破了几个系统”，而是一份能让被测方**复现问题、修复问题、验证修复**的报告。

与之区分的三个概念：

- **漏洞扫描（防御侧资产核查）**：对自有资产做版本与配置比对，通常不涉及主动交互，风险低，但只能发现“已知问题”。
- **渗透测试**：授权测试的一种执行形式，模拟攻击者思路验证防御纵深；方法可以深入，但范围、时间、禁测项必须事先书面约定。
- **红队演练**：以组织为单位的对抗演练，带目标、有时限、有复盘；不在本篇展开，只说明它同样以授权为前提。

### 1.2 为什么流程比技术重要

授权测试出问题，十有八九不是技术失误，而是流程缺口：测了范围外的资产、动了禁测的生产接口、报告里写了无法复现的结论、修复后没人复测。流程的作用就是把这些缺口逐个堵上：

- **授权边界**回答“能不能测”；
- **范围确认**回答“测什么、不测什么”；
- **测试计划**回答“怎么测、测到什么程度、出了事找谁”；
- **报告与复测**回答“问题修好了没有、谁来证明”。

没有这四样，测试做得越“深入”，风险越大。

### 1.3 测试类型的思想（只讲概念，不讲操作）

- **黑盒**：测试者事先不掌握系统内部信息，从外部视角评估暴露面；贴近外部攻击者视角，但覆盖面依赖暴露面本身。
- **白盒**：测试者掌握架构、代码、配置等内部资料，做系统性检查；覆盖面广，但需要被测方提供资料并约定保密。
- **灰盒**：介于两者之间，例如提供普通用户账号但不提供源码；常用于业务逻辑类评估。

选哪种取决于评估目标与被测方能提供的配合程度，选型结果应当写进测试计划，而不是执行中途临时改。

## 2. 合法研究范围

- 本篇讨论的测试只在**书面授权**范围内合法：授权方、被测资产、时间窗口、测试方法类别、禁测项、数据处理方式，六项缺一不可，且应当落在纸面（邮件、合同附件、授权函均可，口头授权不算）。
- **超出授权范围的行为不在本文讨论内**：授权外的资产、授权外的时间、授权外的方法类别，一律不做；测试中偶然发现授权外的问题，先停下并报告授权方，不自行扩大范围验证。
- **未授权测试他人系统是违法行为**，本文不提供相关指导。授权测试的“授权”必须是被测资产所有者或合法管理者给出的，平台方、客户方、合作方的转述授权需要核实到资产所有者一级。
- 测试中接触到的业务数据按“最小必要”处理：能用测试账号与假数据就不用真实数据；必须接触真实数据的，事先约定脱敏、留存期限与销毁方式。

## 3. 实验环境

- 环境：**授权系统**（按授权函约定的测试环境，优先用测试/预发布环境；必须测生产时，时间窗口与禁测项要单独书面确认）或**隔离靶场**（自建靶机，用于演练流程本身）。
- 软件与版本：只列流程与管理类工具——资产清单表、测试计划模板、报告模板、问题跟踪工具；执行类工具只按“类别”写进计划（例如“版本与配置核查类工具”），不写具体攻击工具的操作用法。
- 权限要求：测试账号由被测方发放，权限按“完成评估所需的最小权限”申请；管理员权限不是默认项，需要单独说明理由并写入授权。
- 一个无害的流程自查示例（环境：自有测试虚拟机，Ubuntu 24.04；输出为示例）：

```bash
# 核对“计划里写的时间窗口”与“当前时间”是否一致——流程检查，不碰任何被测系统
date -u
```

示例输出（示例）：

```text
2026-11-04 00:00 UTC
```

读法：执行前先核对时间窗口，窗口外的时间即使“只差几分钟”也不开工；时间核对是流程动作，不产生任何测试流量。

## 4. 风险

- **越界风险**：测到授权外资产（例如云上关联资产、第三方服务）。规避：开工前逐项核对资产清单，清单外的目标一律不碰；发现疑似关联资产先报告。
- **业务中断风险**：测试流量打垮生产接口、锁死账号、写脏业务数据。规避：禁测项（支付、下单、批量写操作）写进计划；高峰时段不测；生产测试前备好回滚与应急联系人。
- **数据风险**：测试中看到真实用户数据。规避：测试账号与假数据优先；真实数据接触即上报、按约定销毁，不留存到个人设备。
- **结论失真风险**：报告写了无法复现的问题，被测方修无可修。规避：每个发现写清触发条件（到“什么配置下会出问题”为止）、影响版本、修复建议，不写无法验证的结论。
- **法律与合同风险**：授权过期、授权方变更、口头授权。规避：授权文件随测试全程可查，授权变更即停工再确认。

## 5. 检测方式

本节从防御视角写：被测方怎么识别“这是授权测试流量，不是真实攻击”。

- **测试窗口报备**：测试开始与结束时通知被测方的安全值班，值班侧把窗口内的告警先标记为“已知测试活动”，窗口结束后再恢复正常研判。
- **流量标识约定**：事先约定可识别的测试标识（例如专用测试账号、约定来源地址段、请求头中的测试标记），防御侧据此过滤与归档，不影响真实告警的研判。
- **日志对照**：测试执行记录（时间、目标、方法类别）与被测方日志逐项对照——能对上的是测试活动，对不上的是待研判事件；对不上的事件按真实事件流程处置，不先入为主当作测试。
- **禁测项触发告警**：一旦触发禁测项（例如生产支付接口出现测试流量），防御侧按事件流程处置，测试侧立即停工并上报；禁测项告警不因为“是测试”而降级。
- **事后复盘对照**：测试结束后，双方用测试记录与防御日志做一次完整对照，确认没有遗留测试账号、测试数据、未关闭的临时放行规则。

## 6. 修复与防御方法

- **报告结构**：每个发现固定五项——问题描述（类别与影响）、影响范围（资产与版本）、触发条件（到配置级别为止，不写利用步骤）、风险评级（结合 CVSS 与自家资产重要性）、修复建议（升级版本、配置收紧、代码修正方向三选一或组合）。
- **修复优先级**：暴露面大 × 资产重要 × 已有公开信息的排前面；不能立即修复的，先上缓解措施（访问控制收紧、临时规则、监控加强）并记下到期时间。
- **复测流程**：被测方修复后，测试方在约定窗口内复测“问题是否真的消失”，复测只验证该问题本身，不扩大范围；复测通过的标准是“原触发条件不再成立”，并留一条复测记录。
- **结项归档**：测试报告、复测记录、临时放行规则的关闭确认、测试账号的回收确认，四项齐了才算结项；结项后测试方删除测试过程中留存的被测方数据（按授权约定的期限与方式）。
- **流程复盘**：每次测试结束复盘一次流程缺口（范围是否划清、禁测项是否合理、沟通是否及时），复盘结论写进下一次测试计划的模板，而不是只留在某个人脑子里。
