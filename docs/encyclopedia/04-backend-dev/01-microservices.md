# 微服务架构入门

## 1. 本章目标

读完本篇，能说清微服务与单体的根本区别、按什么原则拆分服务、服务之间有哪些通信方式，以及微服务多出来的那几类成本——从而判断一个项目现在该不该拆，而不是跟风拆。

## 2. 背景与问题

一个应用刚起步时，所有功能写在一个进程、连同一个数据库，是最自然的做法：调用就是函数调用，改动一次部署，事务由数据库保证。但应用长大后，单体也会长出对应的毛病：

- **改动互相牵连**：改一个小功能也要重新部署整个应用，测试范围越来越大，上线越来越不敢动。
- **扩展只能整体扩展**：只有一个模块压力大，也得把整个应用多复制几份，浪费资源。
- **技术选型被锁死**：全站一种语言、一个框架、一套依赖升级节奏，新技术很难只在一个角落试点。
- **团队互相等待**：所有人改同一份代码、排同一个发布窗口，沟通成本随人数上升。

微服务就是针对“大到一个人、一支小团队已经 hold 不住的单体”给出的答案：把应用拆成一组小服务，每个服务独立运行、独立部署。但要注意前提——它解决的是**规模带来的组织与部署问题**，不是让代码本身变简单。拆开之后，原来一次函数调用能解决的事，要变成一次网络调用，而网络会失败、会超时、会乱序。

## 3. 总体架构

```
单体架构
┌─────────────────────────────────────┐
│  一个进程：界面 + 订单 + 支付 + 库存  │
│  一个数据库：所有表共享              │
└─────────────────────────────────────┘
        改动 → 整体重新部署

微服务架构
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 订单服务 │  │ 支付服务 │  │ 库存服务 │
│ 自己的库 │  │ 自己的库 │  │ 自己的库 │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     └────── 网络调用 / 消息 ──────┘
        改动 → 只部署改动的服务
```

微服务这个词没有一个精确到数学定义的定义。James Lewis 与 Martin Fowler 在 2014 年的文章里给出的经典表述是：把单个应用开发成**一组小服务，每个服务运行在自己的进程中，用轻量机制通信，通常是 HTTP 资源 API；服务围绕业务能力构建，可由全自动部署工具独立部署；集中管理做到最少；服务可以用不同语言、不同存储技术**。原文同时列出了九个常见特征：按服务做组件化、围绕业务能力组织、以产品而非项目的方式运营、端点智能而管道简单（smart endpoints and dumb pipes）、去中心化治理、去中心化数据管理、基础设施自动化、为失败而设计、演进式设计。记住这九条，比记住“服务要多小”更有用——“微”没有统一的行数标准。

## 4. 工作机制

### 4.1 拆分原则：按业务能力，不按技术层次

最常见的拆错法是按技术分层拆：前端服务、后端服务、数据库服务。那只是把单体切成了几块互相依赖的碎片，改一个功能仍要动所有服务、一起发布，成本全付了，好处一点没拿到。

正确的切分单位是**业务能力**：订单、支付、库存、用户、商品，每块对应一块相对完整的业务职责，内部包含它自己的界面逻辑、业务规则和数据。判断拆分是否合理的经验法则：

- **改动是否收敛**：一个业务需求下来，理想情况下只改一个服务；如果每次需求都要同时改三四个服务，边界就划错了。
- **数据是否归属清晰**：每个数据项有且只有一个服务是“主人”，其他服务要用就通过接口问主人拿，而不是直接读主人的表（见 4.3）。
- **团队是否能独立发布**：一个服务能不能不经其他团队同意就上线？不能的话，拆分在组织上就是失败的。

这背后是康威定律（Conway's Law）：Melvin Conway 在 1968 年发表于《Datamation》的《How Do Committees Invent?》中指出，**设计系统的组织，其产出设计的组织结构会复制该组织的沟通结构**。也就是说，服务边界最终会长成团队沟通边界的样子。反过来用就是“逆康威策略”：先按期望的架构调整团队与沟通方式，再让架构自然跟上。拆分服务之前先想想团队怎么分工，往往比画架构图更管用。服务拆分与领域建模的关系，见本域第三篇 [领域驱动设计入门](03-domain-driven-design.md)（限界上下文是划服务边界最常用的思考工具）。

### 4.2 从单体演进：先模块化，再拆服务

不要一上来就拆成十几个服务。实践中更稳妥的路径是：

1. **先在单体里把模块边界划清楚**：按业务能力分包、分模块，模块之间只通过明确的接口调用，不偷偷共享数据库表、不跨模块直接读写对方的内部状态。
2. **等到某个模块真的成为瓶颈**（发布互相拖累、扩展需求差异大、团队规模大到需要分工），再把它抽成独立服务。
3. **一次只抽一个**，抽完验证独立部署、监控、回滚都正常，再抽下一个。

模块化单体不是“没拆干净的失败品”，很多应用停留在这个阶段就是最优解。拆服务是有固定成本的：部署、监控、链路追踪、服务发现、容错，每一项都要有人维护。

### 4.3 服务间通信：同步与异步

服务之间不能再直接调函数，必须走网络。两种基本方式：

**同步调用（请求–响应）**：A 直接调 B 的 API，等 B 回应再继续。常用形态是 HTTP API 与 RPC。优点是直观、调用链清晰；缺点是依赖会传染——B 慢，A 就慢；B 挂，A 也跟着受影响。同步链越长，系统整体可用性越低：三个可用性 99.9% 的服务串联，整体可用性是三者相乘，低于任何一个。

**异步通信（消息与事件）**：A 把“订单已创建”这样的事件发到消息通道就继续做自己的事，感兴趣的服务自己来消费。优点是解耦、削峰：生产者不用等消费者；缺点是**最终一致**——事件发出后，各服务的数据不会立刻全部同步，读到的数据可能短暂滞后；还要处理重复投递（消费者必须能幂等处理同一条消息两次）和消息顺序问题。

选型原则：需要立刻拿到结果才能继续的（如下单时校验库存是否足够），用同步；只是通知对方“某事发生了”，对方慢慢处理也行的（如下单后发短信、记账、更新推荐），用异步。真实系统往往是两者混用：核心链路同步保证正确性，周边链路异步保证扩展性。

### 4.4 数据管理：各服务管自己的数据

这是微服务最容易被违背、也最重要的一条：**每个服务拥有自己的数据库，其他服务不得直接访问**。一旦两个服务共享一张表，它们就不再是独立的服务——改表结构要两边一起改、一起上线，拆分的好处立刻消失。

随之而来的问题是：原来一个数据库事务能保证的“订单创建与库存扣减要么都成功、要么都失败”，现在跨了两个服务，数据库保证不了了。业界的常规做法有两类思路（这里只讲思路，不展开实现）：

- **Saga（长事务拆解）**：把跨服务操作拆成一系列本地事务，每步成功后发事件触发下一步；某步失败时，执行前面各步的补偿操作（如已扣的库存加回去）。补偿逻辑要自己写，没有数据库替你回滚。
- **事件驱动 + 最终一致**：接受数据短暂不一致，靠事件把各服务的数据最终推向一致，并给用户明确的中间状态（如“处理中”），而不是假装一切瞬间完成。

哪种都不免费。凡是听到“微服务 + 强一致 + 零成本”的说法，都可以先怀疑一下。

### 4.5 必须补齐的基础设施

拆成服务后，原来单体里免费的东西都要重新建设，缺一不可：

- **服务发现与负载均衡**：服务实例会增减、会换地址，调用方要能找到活着的实例。
- **集中日志与链路追踪**：一次请求经过五个服务，出问题时没有跨服务的请求编号（trace id），根本定位不到是哪一环慢了、错了。
- **熔断与超时**：下游变慢时上游要快速失败而不是无限等下去，否则一个慢服务拖垮整条链路；超时时间、重试次数必须显式定好，且写操作重试要考虑幂等。
- **独立部署流水线与监控告警**：每个服务自己的构建、测试、发布、回滚、指标与告警。没有这些，所谓“独立部署”只是“独立出故障”。

下面这段示例演示的是 4.3 与 4.4 的核心思想——订单与支付各自持有自己的数据，支付服务只能通过订单服务暴露的只读方式拿到金额，不能直接改订单的数据。它不是真实的网络调用，只用来把“边界”这个概念落到代码上：

```python
orders, payments = {}, {}

def create_order(oid, amount):
    orders[oid] = {"amount": amount, "status": "created"}
    return orders[oid]

def charge(oid):
    # 支付服务只能通过订单服务暴露的只读接口拿金额，不能直接改 orders
    amount = orders[oid]["amount"]
    payments[oid] = {"amount": amount, "status": "paid"}
    return payments[oid]

create_order("O1", 99)
print("order:", orders["O1"], "payment:", charge("O1"))
```

实测输出（Python 3.12.3，本地运行）：

```
order: {'amount': 99, 'status': 'created'} payment: {'amount': 99, 'status': 'paid'}
```

## 5. 关键设计取舍

- **独立换复杂**：换来独立部署、独立扩展、技术选型自由；换走的是原来免费的函数调用、事务与调试便利。团队小、业务简单时，这笔账通常是亏的。
- **同步换简单，异步换解耦**：同步直观但故障会传染；异步解耦但要接受最终一致、重复投递、排查困难。不要为了“解耦”把必须同步的链路也异步化。
- **自治换一致性**：各服务管自己的数据换来自治，代价是跨服务一致性要自己用 Saga 或事件来保证，没有免费午餐。
- **演进换前期投入**：微服务支持长期演进，但要求自动化部署、监控、追踪先行；没有这些基建就拆，是先付成本、后补能力。

## 6. 分类与变体

- **单体（Monolith）**：一个进程、一个代码库、通常一个数据库。适合起步期与小团队。
- **模块化单体（Modular Monolith）**：仍是一个部署单元，但内部按业务能力严格分模块、模块间接口清晰。很多应用的最优终点，不是过渡形态。
- **微服务（Microservices）**：每个业务能力独立进程、独立部署、独立数据。适合业务复杂、团队规模大、扩展需求差异明显的系统。
- **服务化单体 / 分布式单体（Distributed Monolith）**：名义上拆了服务，实际上改动、发布、数据处处耦合——这是最差的结果：同时付了单体与微服务两份成本，只拿到两边的缺点。拆分后如果每次上线仍要所有服务一起发，就是这个症状。

## 7. 应用与限制

适合微服务的信号：业务已经复杂到单体改动成本明显上升；不同模块的流量、扩展需求差异很大；团队大到需要按业务分工、独立发布；有专人维护部署、监控、追踪等基建。

不适合的信号：团队只有几个人；业务还在快速试错、边界天天变；没有自动化部署与监控基建；只是听说“大厂都用微服务”。Martin Fowler 本人在 2014 年之后也多次提醒：微服务有明确的前提条件（快速部署、自动化测试、监控等），不满足前提就拆，成本会先于收益到来。

## 8. 常见误解

- **“服务越小越好”**：错。没有统一的“微”标准；拆得过细会导致调用链更长、故障面更大。边界按业务能力划，不按代码行数划。
- **“微服务能解决代码写得烂的问题”**：错。模块边界不清的单体拆成服务，只会变成边界不清的分布式单体，问题还更难查。
- **“拆了服务就自动高可用”**：错。网络会失败，服务会挂；高可用来自超时、熔断、重试、限流、监控这些显式设计，不是来自“拆”这个动作本身。
- **“微服务与单体只能二选一”**：错。模块化单体、按需抽取个别服务、混合部署都是正常形态；架构是随业务规模演进的，不是入教仪式。
