# API 治理与版本管理

## 1. 本章目标

读完本篇，能给一组 API 定出可执行的规矩：版本号怎么编、什么改动算破坏性、文档与网关管什么、旧版本怎么体面下线——让调用方升级时不再靠猜。

## 2. 背景与问题

API 一旦被别人调用，就不再是你一个人的代码。调用方可能在你不知道的地方、你不知道的数量级上依赖着它。没有治理的 API 会长成这个样子：

- **改动靠口头通知**：字段删了、类型变了，调用方上线后才发现，故障先到用户那里。
- **版本靠感觉编号**：v2 改了什么没人说得清，调用方不知道升不升级、升了会不会坏。
- **文档与实现两张皮**：文档写的是旧字段，线上跑的是新字段，联调全靠试错。
- **旧版本永远不敢下线**：不知道还有谁在用，只能一直维护，最后维护成本超过新功能开发。

治理要解决的不是“怎么写一个接口”，而是“接口作为公共契约，怎么长期演进而不伤害调用方”。接口本身的设计（REST 资源命名、分页、错误体、认证方式）见本站 [API 与系统集成](../../website-guide/api/01-integration.md)，本篇不重复，只讲接口之上的治理层。

## 3. 总体架构

```
API 治理的四层
┌──────────────────────────────────────────────────┐
│ 契约层：OpenAPI 文档是唯一事实来源，代码与文档互验 │
├──────────────────────────────────────────────────┤
│ 版本层：版本号规则 + 兼容性清单，什么能改、什么不能 │
├──────────────────────────────────────────────────┤
│ 运行层：网关统一做认证、限流、路由、观测与灰度     │
├──────────────────────────────────────────────────┤
│ 生命周期层：发布 → 维护 → 弃用 → 下线，全程有日期   │
└──────────────────────────────────────────────────┘
```

四层缺一不可：只有文档没有版本规则，文档会越写越乱；只有版本规则没有网关，规则落不了地；只有网关没有生命周期，旧版本会无限增殖。

## 4. 工作机制

### 4.1 版本策略：先选一种，并写下来

常见的版本放置方式有四种，没有放之四海而皆准的一种，关键是**全站统一、写进文档、长期不变**：

| 方式 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| URL 路径版本 | `/v1/orders`、`/v2/orders` | 直观、易调试、缓存友好 | URL 里带版本，资源定位不纯粹 |
| 请求头版本 | `Accept: application/vnd.example.v2+json` | URL 干净 | 调试、缓存、网关路由都麻烦 |
| 查询参数版本 | `/orders?version=2` | 实现简单 | 容易被忽略、缓存易串 |
| 不显式版本（持续演进） | 始终一个版本，只做兼容改动 | 最简单 | 一旦要做破坏性改动就无路可退 |

多数团队从 URL 路径版本起步，因为它在排障、网关路由、日志分析上都最省事。选定后要同时定两条配套规则：**默认版本**（调用方不带版本时走哪个版本，生产环境建议明确拒绝或指向最新稳定版，并在文档里写死，不要悄悄变）和**多版本并行期**（同时维护几个版本，超过上限就必须先下线旧的再发新的）。

### 4.2 兼容性：什么算破坏性改动

版本策略只有配上兼容性定义才有意义。语义化版本（Semantic Versioning，SemVer）2.0.0 规范对此有明确定义：版本号形如 `MAJOR.MINOR.PATCH`，主版本号变表示做了不兼容的 API 改动，次版本号变表示向后兼容地新增功能，补丁号变表示向后兼容的缺陷修复；主版本号为 0（0.y.z）时表示初期开发，API 尚不稳定，任何改动都可能不兼容。SemVer 原本面向软件包的公开 API，但它的“改动分级”思想同样适用于 HTTP API 的版本沟通——前提是团队真的按规则编号，而不是把版本号当装饰。

落到 HTTP API 上，常见的**破坏性改动**清单（出现任何一条就必须升主版本或开新版本）：

- 删除接口、删除请求或响应字段；
- 把可选字段改成必填；
- 改字段类型或取值含义（如把字符串 `"10"` 改成数字 `10`，或把状态码的含义换掉）；
- 改认证方式、改错误码的含义；
- 收紧校验（以前接受的输入现在拒绝）。

常见的**兼容改动**（可以不升主版本）：

- 新增接口、新增可选字段、新增枚举值（调用方要按“未知枚举值可能出现”来写代码，否则新增枚举也会 breaking 掉写死 switch 的客户端）；
- 放宽校验、新增可选的查询参数；
- 修复缺陷但不改变约定的语义。

判断标准只有一条：**已按旧文档正确编写的调用方，在新版本下是否还能正常工作**。不能，就叫破坏性。拿不准时，按破坏性处理——误判的代价是调用方半夜被叫醒。

下面这段示例把这条判断写成可跑的规则演示（只演示 SemVer 三段号的比较逻辑，不是生产校验器）：

```python
def parse(v):
    major, minor, patch = (int(x) for x in v.split("."))
    return major, minor, patch

def compatible(old, new):
    o, n = parse(old), parse(new)
    if n[0] != o[0]:
        return "不兼容：主版本号变了"
    if n[1] > o[1]:
        return "兼容：新增功能"
    return "兼容：补丁修复"

print("1.2.3 -> 2.0.0:", compatible("1.2.3", "2.0.0"))
print("1.2.3 -> 1.3.0:", compatible("1.2.3", "1.3.0"))
print("1.2.3 -> 1.2.4:", compatible("1.2.3", "1.2.4"))
```

实测输出（Python 3.12.3，本地运行）：

```
1.2.3 -> 2.0.0: 不兼容：主版本号变了
1.2.3 -> 1.3.0: 兼容：新增功能
1.2.3 -> 1.2.4: 兼容：补丁修复
```

### 4.3 文档治理：让文档成为契约，而不是事后说明

OpenAPI Specification（原 Swagger）是描述 HTTP API 的开放规范：用一份机器可读的文档写清路径、参数、请求与响应结构、认证方式。截至核实日，官方规范站列出的版本线含 3.2.x（其中 3.2.0 发布于 2025 年 9 月，3.1.0 发布于 2021 年 2 月并对齐 JSON Schema）；新项目以官方规范站当前发布为准，不要凭记忆写旧版字段。文档治理的关键做法：

- **文档即契约**：发布前用工具校验文档与实现是否一致（契约测试），不一致就不发布；不要让文档沦为“上线后有空再补”的附属品。
- **变更要评审**：接口契约的改动走评审流程，评审问题清单就是 4.2 的兼容性清单；破坏性改动必须附带迁移方案才能合入。
- **示例必须是真的**：文档里的请求与响应示例要能跑通、与真实返回一致；假示例比没示例更误导人。
- **错误体统一**：错误码、错误信息、问题定位字段全站一套格式（具体格式见 [API 与系统集成](../../website-guide/api/01-integration.md)），治理层负责检查各服务是否遵守，而不是各服务自定。

### 4.4 网关治理：把横切能力收敛到一处

当服务多起来（见本域第一篇 [微服务架构入门](01-microservices.md)），每个服务各自做认证、限流、日志，就会各自为政。API 网关是所有外部流量的统一入口，适合收敛的职责：

- **路由与版本分发**：按路径或请求头把流量分到对应版本、对应服务；新版本灰度发布时，网关按比例切流，出问题一键回切。
- **认证与授权**：统一校验调用方身份（认证机制本身如 OAuth 2.0、JWT 见 [API 与系统集成](../../website-guide/api/01-integration.md)），各服务不再各自实现一套。
- **限流与配额**：按调用方、按接口设速率上限，防止某个调用方刷垮服务；超限时返回明确的限流响应与重试提示，而不是直接拖垮。
- **观测**：统一记录每个接口的调用量、延迟、错误率、调用方分布——这组数据同时是容量规划的依据，也是 4.5 下线决策的证据（“还有谁在用 v1”要靠数据回答，不能靠猜）。

网关不管业务逻辑：业务校验、领域规则仍在各服务内部。网关一旦开始写业务逻辑，就会变成新的单体。

### 4.5 弃用流程：从标记到下线，每一步都有日期

弃用（deprecation）不是“某天突然关掉”，而是一段有明确日期的流程：

1. **宣布**：在文档中把接口或版本标为已弃用，写明替代方案与迁移指南，同时通过响应头机器可读地告知调用方。标准做法是 `Sunset` 头（RFC 8594）给出预计停止响应的 HTTP 日期，`Deprecation` 头（RFC 9745，2025 年 3 月发布）给出弃用时间（值为 `@` 加 Unix 时间戳，如 `Deprecation: @1717200000`），再配 `Link` 头指向迁移文档（`rel="deprecation"`）或替代版本（`rel="successor-version"`）。`Sunset` 日期不得早于 `Deprecation` 日期。注意：旧资料可能仍把 `Deprecation` 称为草案，以 RFC 9745 正式发布为准。
2. **观测迁移**：网关统计旧版本的剩余调用量与调用方清单，主动通知仍在用的调用方；迁移率不达标时，先延长窗口、再沟通，不要直接跳到下一步。
3. **冻结**：弃用版本只修严重缺陷，不再加功能；新需求一律引导到新版本。
4. **下线**：到达 `Sunset` 日期后移除旧版本；下线后的请求应返回明确的 `410 Gone`（表示资源已永久移除），而不是含糊的 `404`，并在响应或文档中指向替代版本。
5. **复盘**：下线后确认监控、文档、网关路由、示例代码里没有残留的旧版本引用。

示例响应头（示意，未实测——只是头部文本，不依赖任何服务运行）：

```http
HTTP/1.1 200 OK
Deprecation: @1717200000
Sunset: Tue, 30 Jun 2026 23:59:59 GMT
Link: <https://api.example.com/docs/migrating-to-v2>; rel="successor-version"
```

## 5. 关键设计取舍

- **严格换自由**：统一的版本规则、文档校验、网关策略会拖慢单个服务的“随手改接口”，换来的是所有调用方的安全感。接口的消费者越多，这笔账越划算。
- **多版本并行换维护成本**：并行版本越多，调用方越从容，维护方越辛苦。并行版本数要设上限，靠生命周期而不是靠善意来收敛。
- **网关集中换单点风险**：网关集中了认证、限流、路由，自身就必须高可用、可观测；网关挂了，所有服务对外都挂。集中能力的同时也要给网关配足冗余与演练。
- **显式日期换灵活性**：`Sunset` 日期一旦公布就很难收回，但没有日期的弃用等于没有弃用。宁可把窗口定得长一点，也不要不定。

## 6. 分类与变体

按治理强度，API 治理有三档，团队按接口的外部化程度选档，不必一开始就上满：

| 档位 | 适用 | 做法 |
|---|---|---|
| 内部接口 | 只供自己团队调用 | 统一文档 + 兼容性清单即可，版本可宽松 |
| 跨团队接口 | 供公司内多个团队调用 | 加网关路由与观测、版本策略写进文档、弃用有日期 |
| 对外开放接口 | 供外部开发者、客户调用 | 全套：契约测试、网关认证限流、配额计费、多版本并行与正式弃用流程 |

## 7. 应用与限制

典型应用：多服务系统对外统一出口（配合 [微服务架构入门](01-microservices.md) 的网关一节）；对外开放平台、合作伙伴接入；接口数量多到靠人记不住、必须靠文档与网关管起来的团队。

限制：

- 治理管的是契约与流量，不是业务正确性；网关测不出领域规则错没错。
- SemVer 是沟通约定，不是强制力——编号标错的项目到处都是，调用方升级前仍要看变更说明与契约测试结果。
- `Deprecation`/`Sunset` 头只有调用方或中间件去读才有意义；只发头、不发公告、不做迁移通知，等于没治理。
- 对外接口的版本承诺一旦写进合同或服务条款，技术上的“想下线”要服从法务与商务约束，治理流程要提前和这些约束对齐。

## 8. 常见误解

- **“加个 v2 就叫版本管理”**：错。版本号只是入口，兼容性规则、文档校验、下线流程缺一个，版本管理就是空壳。
- **“兼容改动永远安全”**：错。新增枚举值会打破写死枚举的客户端，放宽校验可能让下游收到以前见不到的数据；兼容性要按调用方的实际写法判断，不按自己的想象判断。
- **“文档可以上线后再补”**：错。接口发布那一刻，调用方就开始按文档写代码；事后补的文档纠正不了已经写错的调用。
- **“弃用就是发个公告”**：错。没有 `Sunset` 日期、没有调用量观测、没有迁移通知的弃用，旧版本会永远活着。
