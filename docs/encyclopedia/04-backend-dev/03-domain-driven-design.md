# 领域驱动设计入门

## 1. 一句话定义

领域驱动设计（Domain-Driven Design，DDD）是一种以业务领域模型为核心的软件设计方法：让代码的结构贴合业务本身的语言与规则，而不是贴合数据库表或技术框架。

## 2. 为什么需要它

很多系统的问题不在技术，而在“业务讲不清”。同一句话，业务人员、产品经理、开发人员各自理解不同：

- 销售说的“订单”与财务说的“订单”是不是同一个东西？财务关心应收与开票，销售关心下单与履约，同一个词背后是两套不同的规则与生命周期。
- “用户”在登录场景与在计费场景里，属性与行为一样吗？登录关心凭证与会话，计费关心套餐与账单，硬塞进一个“万能用户类”，最后谁也改不动。
- 需求一变，代码处处要改，因为业务规则散落在各处，没有一个地方能说清“这个业务到底是什么”。

DDD 的回答是：先把业务讲清楚，再写代码。业务专家与开发人员共用一套语言（统一语言）描述领域，用模型把这套语言落到代码里；模型有明确的边界（限界上下文），边界内保持一致，边界外允许同一个词有不同含义。这样，需求变化时，改动能收敛到对应的模型里，而不是全系统扩散。

DDD 由 Eric Evans 在 2003 年出版的《Domain-Driven Design: Tackling Complexity in the Heart of Software》（常称“蓝皮书”）中系统提出。它不是框架、不是某种语言的库、更不是“必须全套照搬”的教条——它的价值在于一套建模的思考方式，团队可以按需取用。

## 3. 核心含义

### 3.1 领域、子域与统一语言

- **领域（Domain）**：软件要解决的业务范围，如电商、银行信贷、医院挂号。
- **子域（Subdomain）**：领域内的一块相对独立的业务，如电商里的商品目录、订单履约、支付结算。Evans 建议区分三类子域：**核心域**（最能体现业务竞争力的部分，值得投入最好的设计）、**支撑子域**（业务必需但不构成竞争力，如常规的报表、通知）与**通用子域**（很多行业都有的通用能力，如身份认证、权限）。投入要分轻重：核心域精雕细琢，通用子域能买就买、能用现成就用现成。
- **统一语言（Ubiquitous Language）**：业务专家与开发人员共同使用的、贯穿需求文档、对话与代码的同一套词汇。代码里的类名、方法名、字段名就用这套语言里的词，不要一套业务词、一套代码词来回翻译。语言不一致的地方，往往就是模型边界所在的地方——同一个词在不同场景含义不同时，不要强行统一，先承认它们是两个概念。

### 3.2 限界上下文：模型生效的边界

**限界上下文（Bounded Context）**是 DDD 最核心的战略概念：一个模型在其中保持一致、无歧义的显式边界。边界内，一个词只有一个含义、一套规则；出了边界，同一个词可以有别的含义、别的规则，由上下文之间的映射关系（上下文映射，Context Map）来翻译与协调。

举例：电商里的“订单”在销售上下文中是从下单到履约的流程对象，在财务上下文中是应收与开票的凭证对象。强行用一个“订单模型”同时满足两边，结果是两边都难受：销售改个字段怕影响财务，财务加个规则怕影响销售。正确做法是两个上下文各有自己的订单模型，之间通过明确的映射（如销售订单完成后向财务发布“订单已确认”事件，财务据此生成自己的应收记录）协作。

上下文之间的常见关系（只列最常用的几种，完整清单见 Evans 原书）：

- **共享内核（Shared Kernel）**：两个上下文共享一小部分模型，改动要双方协商；共享面越小越好，共享大了就等于边界没划清。
- **客户方–供应方（Customer/Supplier）**：上游上下文为下游提供服务，下游提需求、上游排期实现；双方是协作关系。
- **遵奉者（Conformist）**：下游完全接受上游的模型，不做翻译；适用于上游强势、下游没有议价能力的场景（如对接外部系统）。
- **防腐层（Anticorruption Layer）**：下游建一层翻译与隔离，把上游模型转换成自己的模型，防止上游的概念污染自己的模型；对接遗留系统、外部系统时最常用。
- **各自独立（Separate Ways）**：两个上下文没有集成需求，干脆不集成，不要为了“统一”硬造依赖。

### 3.3 战术 building blocks：实体、值对象与聚合

限界上下文划清了“模型在哪生效”，上下文内部则用一组战术模式把模型落到代码：

- **实体（Entity）**：有唯一标识、生命周期内标识不变的对象。两个人同名同姓仍是两个人——区分靠标识，不是靠属性。典型例子：订单（订单号不变，哪怕收货地址改了，仍是同一个订单）、用户账号。
- **值对象（Value Object）**：没有唯一标识、只由属性值定义的对象。两个金额数值相等就是同一个值，不用区分“这是哪一个金额”。值对象通常设计为不可变：改了就是换一个新值，而不是原地修改。典型例子：金额（数值 + 币种）、地址、日期范围。
- **聚合（Aggregate）**：一组相关对象作为一个整体来处理数据变化的单元。聚合内有一组需要共同保证的业务规则（不变式），如“订单总金额等于各明细金额之和”“已提交的订单不能再加商品”。
- **聚合根（Aggregate Root）**：聚合对外的唯一入口。外部只能通过聚合根访问、修改聚合内部的对象，不能绕过聚合根直接改内部对象——这样不变式才有地方统一把关。聚合根通常就是那个实体，如订单聚合的根是订单，订单明细只能通过订单来增删。
- **领域服务（Domain Service）**：不适合归属某个实体或值对象的业务操作，如涉及多个聚合的计算、跨聚合的规则判断。注意区分：能放进聚合根的规则优先放聚合根，不要什么都往服务里堆。
- **资源库（Repository）**：按聚合根存取的抽象，屏蔽底层存储细节。调用方说“按订单号取出订单聚合”，不用关心它是存在关系库、文档库还是缓存里；资源库以聚合为单位存取，不以单张表为单位。

实体与值对象的区分标准不在“复杂还是简单”，而在“有没有跨越时间的同一性”：需要追踪“这是哪一个、它经历了什么”的，用实体；只关心“值是多少”的，用值对象。分错的常见症状：把金额做成实体后到处要给金额编标识；把用户账号做成值对象后，改个手机号就“变成另一个人”。

### 3.4 聚合的设计要点

聚合是 DDD 里最容易设计错、也最影响性能与并发的部分：

- **聚合宜小**：聚合越大，一次改动锁定的范围越大、并发冲突越多、加载成本越高。经验法则是：一个聚合只含“必须一起改、必须一起保证规则”的对象；能拆的就拆，跨聚合的一致性用事件与最终一致来处理，不要靠大聚合硬保证。
- **聚合之间只通过标识引用**：聚合 A 持有聚合 B 的标识（如订单持有用户标识），而不是直接持有 B 的对象。这样聚合才能独立加载、独立修改、独立演进。
- **一次事务只改一个聚合**：这是聚合边界带来的硬约束——跨聚合的“原子操作”不再由数据库事务免费提供，要用领域事件与 Saga 之类的机制在业务层协调（思路见本域第一篇 [微服务架构入门](01-microservices.md) 的数据管理一节）。

下面这段示例演示聚合根如何把关不变式——“已提交的订单不能再加商品”这条规则只写在聚合根的方法里，外部绕不开：

```python
class Order:
    def __init__(self):
        self.items, self.submitted = [], False

    def add_item(self, name):
        if self.submitted:
            raise ValueError("订单已提交，不能再加商品")
        self.items.append(name)

    def submit(self):
        if not self.items:
            raise ValueError("空订单不能提交")
        self.submitted = True

o = Order()
o.add_item("书")
o.submit()
try:
    o.add_item("笔")
except ValueError as e:
    print("聚合根拦截：", e)
print("items:", o.items, "submitted:", o.submitted)
```

实测输出（Python 3.12.3，本地运行）：

```
聚合根拦截： 订单已提交，不能再加商品
items: ['书'] submitted: True
```

## 4. 分类

按 Evans 原书的划分，DDD 的内容分两层：

| 层次 | 内容 | 回答的问题 |
|---|---|---|
| 战略设计 | 领域、子域、统一语言、限界上下文、上下文映射、核心域提炼 | 模型划在哪、边界在哪、投入放在哪 |
| 战术设计 | 实体、值对象、聚合、聚合根、领域服务、资源库、工厂、模块 | 模型在代码里怎么写、规则由谁把关 |

新手最容易犯的错误是只学战术、不做战略：实体、值对象分得头头是道，却从来没跟业务人员对过统一语言、没划过限界上下文。结果是代码“DDD 味”很浓，业务边界仍是一团糟。顺序应该是：先战略（语言与边界），再战术（对象与规则）。

## 5. 典型应用

- **复杂业务系统建模**：保险核保、银行信贷、电商履约这类规则多、概念易混淆的系统，DDD 的语言与边界能显著降低沟通与改动成本。
- **微服务拆分依据**：限界上下文是划分服务边界最常用的思考工具——一个限界上下文通常对应一个或一组服务（详见第 6 节）。
- **遗留系统治理**：用防腐层把新模型与遗留系统隔离开，新功能按新模型写，老系统逐步被替换，而不是在老模型上继续打补丁。
- **多团队协作**：上下文映射把团队之间的集成关系显式化（谁是上游、谁做翻译、共享什么），减少“我以为你会那样理解”的扯皮。

## 6. 与微服务拆分的关系

DDD 与微服务是互补关系，不是同一件事：DDD 回答“业务边界划在哪”，微服务回答“运行与部署单元怎么切”。两者结合的常见做法：

- **限界上下文 → 服务边界**：一个限界上下文内的模型一致、改动收敛，天然适合做成一个服务（或一组紧密协作的服务）；跨上下文的调用走 4.2 节的映射关系，而不是共享数据库。这是 [微服务架构入门](01-microservices.md) 中“按业务能力拆分”在建模层面的具体化。
- **但不是一一对应**：一个限界上下文可以对应多个服务（如上下文内部按扩展需求再分），一个服务也可以承载多个小上下文（小团队没必要为每个小上下文都起一个服务）。硬把“一个上下文 = 一个服务”当教条，会拆出过细的服务。
- **先有边界，再谈拆分**：没有限界上下文思考的微服务拆分，往往按技术层次或按数据表拆，最后得到的是分布式单体。反过来，没有微服务需求的单体系统，同样可以用 DDD 做模块化——DDD 不要求你上微服务。

## 7. 限制与常见误解

DDD 不能做什么：

- **不能替代业务理解**：DDD 只是把业务理解落到模型的方法；业务本身讲不清、专家不参与，再好的模式也建不出好模型。统一语言需要业务专家持续参与，不是一次访谈就能定稿的。
- **不适合简单场景**：增删改查为主、业务规则很少的系统，用 DDD 全套是过度设计；这时用简单的事务脚本、清晰的分层就够了。
- **不保证性能**：聚合过大、跨聚合查询过多都会带来性能问题；建模时要同时考虑读写场景，必要时读写模型可以分离（该做法属进阶内容，本文不展开）。

常见误解：

- **“DDD 就是分层架构 / 就是实体类加一堆注解”**：错。分层是技术组织方式，注解是框架手段；DDD 的核心是统一语言与限界上下文，没有这两样，剩下的只是换了名字的旧写法。
- **“上了 DDD 就必须上微服务 / 事件溯源 / CQRS”**：错。这些是可选的配套技术，不是 DDD 的组成部分；按需取用，不要打包全上。
- **“一个词全系统只能有一个含义”**：错。这正是限界上下文要纠正的误解——同一个词在不同上下文含义不同是正常的，正确做法是承认边界、用映射翻译，而不是强行统一。
- **“聚合越大越能保证一致性”**：错。聚合越大，并发冲突与加载成本越高；一致性要求只覆盖“必须一起变”的范围，其余用事件与最终一致处理。

## 8. 小结

DDD 是以业务领域模型为核心的设计方法：用统一语言讲清业务，用限界上下文划清模型边界，用实体、值对象与聚合把规则落到代码。它的边界是：只解决“业务复杂”带来的建模问题，不解决技术选型、性能调优本身；与微服务的关系是互补——DDD 给拆分提供边界依据，微服务给边界提供部署形态。
