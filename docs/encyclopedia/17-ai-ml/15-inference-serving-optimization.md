# 推理服务与性能优化：从模型到在线服务

## 1. 一句话定义

推理服务是把训练好的模型包成持续在线的服务、接收请求并返回推理结果的一整套做法；推理性能优化是在不（明显）牺牲结果质量的前提下，让这个服务单位时间处理更多请求、单条请求返回更快、资源用得更满的手段。

## 2. 为什么需要它

模型训好只是第一步：用户不会直接跑你的训练脚本，他们要的是“发一句话，拿到回答”。把模型从“一个文件”变成“一个服务”，中间差着一整层工程：请求从哪进来、并发来了怎么排队、显存不够怎么办、回答是一次性给还是边生成边给、服务挂了谁知道、新模型上线怎么不惊动用户。没有这一层，模型再好也只能在研究人员的电脑上跑。

性能优化的动机更直接：推理的成本账是按请求算的。大模型推理里，权重读取、注意力计算、KV 缓存都吃资源；请求一多，延迟上去、吞吐下来、成本跟着上去。优化的目标不是把某一个数字刷到极致，而是让延迟、吞吐、成本三者在业务能接受的范围内同时成立。精度、速度与显存之间的取舍本身，见[量化与推理优化：精度、速度与显存的取舍](../18-local-ai/02-quantization-inference.md)；本篇讲取舍定下来之后，服务形态与优化手段怎么搭。

## 3. 核心含义

### 3.1 推理的两个阶段：预填充与解码

理解推理服务，先分清一次生成里的两个阶段：

- **预填充（Prefill）**：把用户输入的全部 token 一次算完，生成第一个输出 token。这一阶段是并行算的，算力密集，输入越长越耗时；首 token 延迟（TTFT，Time To First Token）主要由它决定。
- **解码（Decode）**：一个 token 一个 token 地往外生成，每步只算一个新 token，但要读一遍全部权重与 KV 缓存。这一阶段是内存带宽密集，生成速度（每秒输出 token 数，TPOT，Time Per Output Token）主要由它决定。

两个阶段的瓶颈不同，优化手段也不同：预填充怕输入太长、算力不够；解码怕权重与 KV 反复读写、带宽不够。把两者混成一个“推理速度”来谈，是算不清账的。

### 3.2 服务形态：从一次请求到持续在线

推理服务按调用方式分三种形态，选型先看业务要哪种：

- **离线批量推理**：请求攒一批再算，不追求单条延迟，追求单位时间总产出。典型场景是批量打标、离线生成、数据处理。
- **在线实时推理**：请求来了立即算，追求单条延迟低。典型场景是聊天、搜索、推荐。
- **流式推理**：生成一个 token 就返回一个 token（常走 SSE 长连接），用户边等边看。典型场景是聊天对话、代码补全。流式不减少总耗时，但用户感知到的等待大幅缩短；代价是连接要一直占着，服务端要管理大量长连接。

三种形态不是递进关系，是按延迟要求分流：能离线的别走在线，能流式返回的别让用户等全文。

### 3.3 性能指标：先定口径，再谈优化

优化之前先把指标口径定下来，否则“变快了”没法验证：

- **首 token 延迟（TTFT）**：从请求发出到第一个 token 返回的时间，决定用户“有没有在等”的感受。
- **每输出 token 时间（TPOT）**：生成阶段平均每个 token 的耗时，决定流式输出“卡不卡”。
- **端到端延迟**：从请求发出到最后一个 token 返回的时间，流式场景下用户感知的是 TTFT + 生成过程，在意全文时才看端到端。
- **吞吐**：单位时间服务完成的总 token 数（或请求数），决定成本与容量。
- **并发与排队**：同时在算的请求数、排队等候的请求数与排队时间；延迟恶化时先看是不是排队引起的，再看是不是单请求变慢了。
- **资源利用率**：GPU 利用率、显存占用、KV 缓存占用率；利用率长期很低说明批没攒起来或调度有问题，利用率长期顶满说明容量要扩了。

报告指标时要同时报告分位数（p50/p90/p99），只报平均值会掩盖长尾：平均延迟好看、p99 很难看的服务，用户体感照样差。

## 4. 分类/关键方法

### 4.1 批处理：把请求攒起来一起算

批处理是一次性喂多条请求、共享权重读取开销（机制与取舍见[量化与推理优化](../18-local-ai/02-quantization-inference.md)第 4.5 节）。服务侧的进阶形态是：

- **静态批处理**：等一批请求凑齐再一起算，简单但延迟受“等齐”拖累，某条请求可能要等别的请求。
- **连续批处理（Continuous Batching）**：某条请求生成完毕就立刻补一条新的进来，不用等整批结束。服务器向框架（如 vLLM）的常用做法，兼顾吞吐与延迟。
- **分块预填充（Chunked Prefill）**：把长输入的预填充切成小块，与解码步骤交错执行，避免一次长预填充堵住后面所有解码请求。长输入场景下对延迟的改善明显。

批大小的取舍点：批越大吞吐越高、单条延迟越长、峰值内存越高；在线场景的批要跟着并发与延迟目标调，不是越大越好。

### 4.2 并发与调度：请求来了怎么排

并发控制是推理服务的第一道防线：

- **最大并发数**：同时在算的请求数要设上限，超过就排队或拒绝；没有上限的服务会在流量高峰时把显存与 KV 缓存挤爆，全部请求一起变慢甚至失败。
- **排队与超时**：排队要有上限与超时，排队过久的请求直接返回可预期的错误，比让用户无限等、最后拿到一个超时要好。
- **优先级**：交互式请求与离线批量请求要分开排队或分不同实例，避免批量任务挤占实时请求的资源。
- **限流与熔断**：按调用方限流，超限返回明确错误；下游依赖（如向量库、工具调用）出问题时熔断，避免雪崩。

### 4.3 缓存：别重复算已经算过的东西

推理服务里有三层缓存，作用不同：

- **前缀缓存（Prefix Caching）**：多条请求共享同一段输入前缀（如相同的系统提示词、相同的文档上下文）时，预填充算过的 KV 缓存可以复用，不用每条请求重算一遍。多轮对话、检索增强生成（RAG）里同一文档被反复问的场景收益明显。
- **KV 缓存管理**：KV 缓存随上下文线性增长（见[量化与推理优化](../18-local-ai/02-quantization-inference.md)第 4.4 节），服务要设上限、定淘汰策略（先淘汰不活跃的、短的），避免缓存把显存放满。KV 缓存也可以量化，代价是长上下文质量可能下降，是否开启以引擎与模型支持情况为准。
- **语义缓存**：问题语义相近就直接返回之前的结果，连推理都省了。收益最大，但风险也最大：语义“相近”不等于答案相同，缓存命中策略定得松会返回错误答案；只适用于答案稳定、容错空间大的场景，且要标明缓存来源、设过期时间。

### 4.4 流式输出与长连接管理

流式输出（SSE）的工程要点：

- **边生成边返回**：每生成一个 token 就推给客户端，用户不用等全文；服务端要按 token  flush，不能攒一批再发。
- **长连接成本**：每个流式请求占一个连接，连接数上去后要看网关与框架的连接上限；客户端断开时服务端要及时取消对应的生成任务，不取消就是白白烧算力。
- **超时与断线续接**：生成时间长、网络抖动时，要有心跳与超时策略；断线后是重算还是续接，要在产品层面定下来，不能留给用户猜。

### 4.5 性能优化手段总览

| 手段 | 针对的瓶颈 | 要点 |
|---|---|---|
| 连续批处理 | 解码阶段权重反复读 | 请求结束即补新请求，吞吐与延迟兼顾 |
| 前缀缓存 / KV 复用 | 重复的预填充计算 | 共享前缀只算一次，适合多轮对话与 RAG |
| 分块预填充 | 长输入堵住解码 | 长预填充切块，与解码交错执行 |
| 推测解码（Speculative Decoding） | 解码一次一个 token 太慢 | 小模型先猜一批 token，大模型一次验证一批；猜对得多才赚，猜错多反而亏，属于进阶手段 |
| 量化（FP16/INT8） | 权重体积与内存带宽 | 方法细节见[模型量化与 ONNX](14-model-quantization-onnx.md)，不是本篇重点 |
| 图优化与算子融合 | 算子调用开销 | 把多个小算子融成一个，减少 kernel 启动与中间读写；以引擎实现为准 |
| 并行策略 | 单卡算力/显存不够 | 张量并行、流水线并行把模型拆到多卡上；多卡之间的通信开销要算进账里 |

选优化手段的顺序：先看指标定位瓶颈在预填充还是解码、是算力还是带宽，再选对应的手段；不要按流行程度选。

### 4.6 部署形态：框架选型定位

服务器向推理框架各有定位，选型先看场景（框架名单与版本以官方发布为准，待核实）：

- **vLLM**：面向 GPU 服务器的高并发在线推理，连续批处理与前缀缓存是其代表性能力。
- **TensorRT-LLM**：面向 NVIDIA GPU 的高性能推理，优化深度与硬件绑定程度都高。
- **Triton Inference Server**：面向多模型、多框架统一服务的推理服务器，模型管理与多后端是其定位。
- **ONNX Runtime 服务化**：ONNX 模型走 ONNX Runtime 推理服务，跨硬件通用性是其定位（格式细节见[模型量化与 ONNX](14-model-quantization-onnx.md)）。
- **一体工具（Ollama、llama.cpp 的 llama-server）**：个人与低配本地场景，定位见[本地模型部署](../18-local-ai/01-local-model-deployment.md)，不在本篇展开。

一句话：高并发 GPU 服务看 vLLM / TensorRT-LLM / Triton，跨硬件通用看 ONNX Runtime，个人本地看一体工具；按场景选，不按名气选。

### 4.7 监控与灰度：上线之后的事

监控分三层，缺一层都是盲人摸象：

- **指标（Metrics）**：TTFT、TPOT、吞吐、并发、排队时间、错误率、缓存命中率、GPU 利用率与显存占用；按分位数与时间窗口看，不要只看瞬时值。
- **日志（Logs）**：请求 ID、模型版本、输入长度、输出长度、错误码；排障时靠日志把一条慢请求从头到尾串起来。
- **链路（Tracing）**：一次请求经过网关、推理服务、检索、工具调用的耗时分布；慢在哪一段，看链路才知道。

灰度（金丝雀发布）的标准流程：新模型先接 1%–5% 流量，对照旧模型的 TTFT、TPOT、错误率与业务指标（如回答采纳率），无异常再逐步扩大到 10%、50%、100%；任何一步指标异常，立即切回旧模型。模型版本要可回滚：旧模型文件与配置在灰度期间不要删，回滚是切流量，不是重新部署。灰度比例与观察窗口的具体数值按业务定，本篇不给统一数字。

## 5. 典型应用

- **聊天对话服务**：流式输出 + 连续批处理 + 前缀缓存（多轮对话共享历史前缀），TTFT 与 TPOT 是主指标。
- **检索增强生成（RAG）**：同一批文档被反复检索、反复问，前缀缓存复用文档部分的 KV，省掉大量重复预填充。
- **离线批量处理**：批量打标、批量摘要、批量翻译，用离线批量推理攒大批跑满吞吐，不占用在线实例。
- **代码补全与 Agent 工具调用**：请求短、频次高、延迟敏感，批处理与缓存的收益直接体现在交互卡顿上。

## 6. 限制与常见误解

- **“吞吐上去了，延迟就好了”**：错。吞吐与单条延迟经常是反向关系（批越大吞吐越高、单条越慢）；两个指标要分开报、分开定目标。
- **“缓存越多越好”**：错。KV 缓存与前缀缓存都占显存，缓存满了会反过来挤占正在算的请求的空间；缓存要有上限与淘汰策略，不是无上限攒。
- **“流式输出等于变快了”**：错。流式只改善用户感知到的等待，总耗时没变；端到端延迟的账还是要单独算。
- **“换个框架就快几倍”**：错。框架的收益来自它解决的那个瓶颈（连续批处理、前缀缓存、算子融合）；瓶颈不在那里的服务，换框架收益有限。先定位瓶颈，再换框架。
- **“监控就是看 GPU 利用率”**：不够。GPU 利用率只反映算力，TTFT/TPOT、排队时间、错误率、缓存命中率才是用户体感的指标；监控要覆盖指标、日志与链路三层（见第 4.7 节）。
- **“灰度只是换个版本号”**：错。灰度是“先让一小部分流量走新模型、观察指标、没问题再扩大”的完整流程，包括流量切分、指标对照、回滚预案；没有回滚预案的灰度等于直接全量。

## 7. 小结

推理服务是把模型变成持续在线能力的一层工程：预填充与解码的瓶颈不同，批处理、并发、缓存、流式输出各管一段；优化先定位瓶颈再选手段，监控要覆盖指标、日志与链路，灰度要有流量切分、指标对照与回滚预案。服务跑起来不等于服务跑得好，跑得好要靠指标说话。
