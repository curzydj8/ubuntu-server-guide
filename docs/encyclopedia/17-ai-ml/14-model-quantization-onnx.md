# 模型量化与 ONNX：格式、转换与低精度推理

## 1. 一句话定义

ONNX 是一种开放的模型交换格式，用一张计算图加一组标准算子描述训练好的模型；模型量化是把模型里的权重与激活从高精度数值改存为低精度数值、从而让模型更小、推理更省资源的一组方法。

## 2. 为什么需要它

训练与推理常常不在同一个地方做：模型可能在 PyTorch 里训出来，却要在另一个框架、另一种硬件、另一台机器上跑。没有统一格式，每换一次环境就要重写一遍模型定义、重接一遍权重，框架之间互相读不懂对方的文件。ONNX 就是为了解决这个“最后一公里”而存在的：训练框架把模型导出成 ONNX，推理侧只认 ONNX，不用关心模型原来是用哪个框架训的。

量化解决的是另一个问题：一个用 FP32（32 位浮点）存权重的模型体积大、占内存多、从内存读权重也慢。把权重改成 FP16 或 INT8，文件立刻变小，内存占用与带宽压力跟着降——在显存、内存或网络带宽有限的部署环境里，这往往是模型能不能落地的分界线。格式解决“到处能跑”，量化解决“跑得起”；两者经常一起出现：先导出 ONNX，再对 ONNX 模型做量化。

需要先说清分工：精度、速度与显存之间的取舍概览、以及本地场景下的量化级别选择，见[量化与推理优化：精度、速度与显存的取舍](../18-local-ai/02-quantization-inference.md)。本篇不重复那份取舍表，只讲 ONNX 格式与生态本身，以及量化方法在技术上是怎么做的。

## 3. 核心含义

### 3.1 ONNX 是什么：图、算子与版本

ONNX（Open Neural Network Exchange，开放神经网络交换格式）的核心思想是：**模型就是一张计算图**。一个 `.onnx` 文件里装着三样东西：

- **计算图（Graph）**：节点是算子（如卷积、矩阵乘、激活函数），边是张量（算子之间流动的数据）。图从输入一路算到输出，执行顺序由依赖关系决定。
- **算子集（Operator Set，简称 opset）**：ONNX 规定了一套标准算子，每个算子有明确的语义（输入几个张量、输出什么形状、参数怎么算）。同一个算子在不同 opset 版本里语义可能演进，因此模型文件里会写明它用的是哪个 opset 版本；推理引擎按这个版本号决定怎么执行。
- **元数据与权重**：模型的初始权重（张量数据）、输入输出的形状与类型信息，以及生产者、模型版本等元数据。权重以 Protobuf 格式序列化在文件里。

版本要分清三层，不要混为一谈：**IR 版本**（ONNX 中间表示本身的版本）、**opset 版本**（算子集的版本）、**Runtime 版本**（推理引擎的版本）。三者之间有兼容关系：新版 Runtime 通常能读旧版模型，但旧版 Runtime 未必能读新版 opset 的模型。导出与部署时，先对齐这三个版本号，再谈其他问题。具体的版本对应关系以官方发布为准（待核实），见文末未完成项。

### 3.2 ONNX Runtime：执行 ONNX 的引擎

ONNX 只是格式，不负责计算。真正跑模型的是 **ONNX Runtime**（简称 ORT），一个跨平台的推理引擎。它的关键设计是**执行提供方（Execution Provider，简称 EP）**：同一张 ONNX 图，可以交给不同的后端去算——CPU、CUDA（NVIDIA GPU）、TensorRT、OpenVINO、DirectML、CoreML 等（具体可用的 EP 与版本支持情况以官方文档为准）。换 EP 不用改模型，只改 Runtime 的配置；同一份模型文件可以在服务器 GPU、笔记本 CPU、手机端分别跑起来，区别在 EP 的选择。

这个设计的好处是解耦：模型作者只管导出正确的 ONNX，硬件厂商只管给自己的硬件写 EP，应用开发者只管选 EP。坏处是“能跑”不等于“跑得好”：某个算子在 CPU EP 上有优化实现，在另一个 EP 上可能没有，就会回退到 CPU 执行，或者干脆不支持——导出后要在目标 EP 上实际验证算子覆盖情况，不能只在导出机上测一遍就认为到处都能跑。

### 3.3 与 PyTorch、TensorFlow 的关系

ONNX 不是训练框架，它站在训练框架的下游：

- **PyTorch → ONNX**：PyTorch 提供导出工具（`torch.onnx.export`，新版也有基于 Dynamo 的导出路径），把动态图追踪或捕获成静态的 ONNX 计算图。导出时要注意：PyTorch 的动态特性（如依赖输入值做分支的控制流）在导出成静态图时可能丢失或被固化，导出后必须对照原模型做输出比对。
- **TensorFlow / Keras → ONNX**：通过转换工具（如 tf2onnx）把 SavedModel 或 Keras 模型转成 ONNX。转换工具的算子覆盖范围以其官方文档为准，不是所有 TensorFlow 算子都有对应的 ONNX 算子。
- **scikit-learn 等传统模型 → ONNX**：通过 skl2onnx 等工具转换，适用于线性模型、树模型等；是否覆盖某个具体模型类型以工具文档为准。

一句话定位：PyTorch、TensorFlow 负责“训”，ONNX 负责“搬”，ONNX Runtime 负责“跑”。三者是流水线关系，不是替代关系。训练框架选哪个，看训练生态；部署格式选 ONNX，看的是跨框架、跨硬件的通用性。

### 3.4 转换流程：导出、检查、验证

一个稳妥的 ONNX 转换流程分四步，缺了最后一步等于没做完：

1. **导出**：用训练框架的导出工具生成 `.onnx` 文件，指定 opset 版本与输入形状（动态维度还是固定维度要想清楚：动态维度灵活但对某些 EP 不友好，固定维度高效但换输入形状要重新导出）。
2. **检查**：用 ONNX 自带的检查工具验证图结构合法、算子存在、类型与形状一致。检查通过只说明“格式没错”，不说明“算得对”。
3. **输出比对**：同一组输入，分别跑原框架模型与 ONNX Runtime 模型，对比输出张量。数值允许有微小误差（浮点计算顺序不同），但误差要落在可接受的范围内；误差过大说明导出丢了语义，要回头查算子映射。
4. **目标环境验证**：在真正部署的硬件与 EP 上再跑一遍，确认算子都被目标 EP 支持、没有静默回退到慢速路径，延迟与内存符合预期。

## 4. 分类/关键方法

### 4.1 量化方法总览：按“要不要重训”分

量化方法先按一刀切：

| 方法 | 做法 | 代价 | 适用 |
|---|---|---|---|
| 训练后量化（PTQ） | 拿训好的模型直接量化，不改权重训练过程 | 不需要重训，只需要少量校准数据 | 快速落地、大多数场景的默认起点 |
| 量化感知训练（QAT） | 在训练（或微调）时模拟量化效果，让模型适应低精度 | 需要训练数据与训练时间，流程重 | PTQ 精度掉得太多、低比特场景 |

PTQ 是“事后补救”，QAT 是“事前适应”。PTQ 够用就别上 QAT；QAT 是 PTQ 效果不够时的升级手段，不是默认选项。

### 4.2 PTQ 的两种做法：动态量化与静态量化

- **动态量化（Dynamic Quantization）**：权重事先量化好，激活在推理时现场量化。优点是不需要校准数据、流程简单；缺点是激活量化是临时的，精度与速度收益都不如静态量化。常见于权重占大头、激活相对次要的场景。
- **静态量化（Static Quantization）**：权重与激活都事先量化好，激活的量化参数（缩放系数、零点）来自一轮**校准（Calibration）**：拿一小批有代表性的样本跑一遍模型，统计每层激活的数值范围，再定量化参数。优点是推理时没有现场量化的开销，精度通常更好；缺点是校准数据的代表性决定成败——校准数据与真实输入分布差得远，量化后的模型在真实输入上就可能掉精度。

校准数据的选择是静态量化里最容易被忽视的一环：它不是“随便拿几条数据跑一下”，而是“拿和线上真实输入同分布的数据跑一下”。

### 4.3 精度格式：FP16 与 INT8（以及它们的区别）

- **FP16（半精度浮点）**：每个数值 16 位，约占 FP32 一半体积。做法简单——把权重从 FP32 转成 FP16，基本不需要校准，精度损失通常很小；现代 GPU 对 FP16 有硬件加速，推理常能直接受益。缺点是体积只减半，压缩幅度不如 INT8。
- **INT8（8 位整数）**：每个数值 8 位，体积约为 FP32 的四分之一。INT8 不是浮点，需要**缩放系数（scale）与零点（zero point）**把整数映射回近似的浮点值：`真实值 ≈ (整数值 - 零点) × 缩放系数`。缩放系数按张量或按通道定：按通道（per-channel）比按张量（per-tensor）更精细，精度更好，但实现更复杂。INT8 的精度损失比 FP16 大，需要校准（静态量化）或一定的容忍度，收益是体积与带宽压力降得更多。

还有更低的精度（如 INT4）与更新的浮点格式（如 FP8、MXFP4），属于较新的发展，工具与硬件支持情况以官方发布为准（待核实），本篇只列出名称，不展开。

### 4.4 ONNX Runtime 的量化工具

ONNX Runtime 自带量化工具（`onnxruntime.quantization`），对 ONNX 模型做 PTQ。两种输出形式要分清：

- **QDQ 格式**：在图里插入 QuantizeLinear / DequantizeLinear 节点，显式表达“哪里量化、哪里反量化”。优点是格式通用、多数 EP 都能读；缺点是图里多了节点。
- **QOperator 格式**：把量化直接融进算子内部（如量化的卷积、量化的矩阵乘）。优点是执行效率更高；缺点是对 EP 的支持有要求。

选哪种格式，看目标 EP 支持哪种——导出前先查目标 EP 的文档，而不是先量化再发现跑不起来。ONNX Runtime 量化工具的具体参数与版本支持以官方文档为准（待核实）。

### 4.5 量化之外的补充：剪枝与蒸馏（只定位，不展开）

量化不是唯一的模型压缩手段。**剪枝**是删掉不重要的权重或通道，**知识蒸馏**是用大模型（教师）带出一个小模型（学生）。三者可以组合使用，但本篇只讲量化；剪枝与蒸馏的细节是后续深入篇的范围。

## 5. 典型应用

- **跨框架部署**：PyTorch 训好的模型导出 ONNX，交给只支持 ONNX 的推理服务或边缘设备运行，训练侧与部署侧解耦。
- **云端推理降本**：把 FP32 模型量化为 FP16 或 INT8 后部署，单卡能服务的并发量上升、显存占用下降；具体收益要以自己的任务实测为准，不要照搬通用数字。
- **边缘与端侧部署**：手机、嵌入式设备上跑模型时，INT8 量化后的模型体积与内存占用更容易塞进设备预算；硬件是否支持 INT8 加速以设备与 EP 文档为准。
- **多硬件适配**：同一份 ONNX 模型，在服务器上走 CUDA EP、在笔记本上走 CPU EP、在 Windows 设备上走 DirectML EP，模型文件不用为每种硬件各存一份。

## 6. 限制与常见误解

- **ONNX 不是万能胶**：不是所有算子都有 ONNX 对应物，自定义算子、动态控制流、某些新结构可能导不出或导出后语义有变。导出后必须做输出比对，不能假设“导出来就是对的”。
- **“量化只影响体积，不影响质量”**：错。体积收益是确定的，质量损失是按任务逐步显现的（取舍的完整讨论见[量化与推理优化](../18-local-ai/02-quantization-inference.md)）。对数值敏感的任务（如长代码生成、精确计算）先掉质量，选型前要用自己的任务测。
- **“FP16/INT8 一定更快”**：不一定。速度收益取决于硬件有没有对应的加速路径、算子有没有量化实现、以及内存带宽是不是瓶颈。没有硬件加速的 INT8 可能比 FP16 还慢；先看目标硬件与 EP 的支持，再谈速度。
- **“校准数据随便拿点就行”**：错。静态量化的校准数据必须与真实输入同分布，否则量化参数定错，线上精度会系统性地差。
- **“导出一次，到处能跑”**：错。opset 版本、EP 算子覆盖、动态维度的支持情况都要在目标环境上逐一验证；换个 EP 或换个 Runtime 版本，都值得重测一遍。

## 7. 小结

ONNX 用计算图加标准算子集让模型跨框架、跨硬件流通，ONNX Runtime 用执行提供方把同一份模型跑在不同后端上；量化分 PTQ 与 QAT，FP16 简单稳妥、INT8 压缩更深但需要校准与验证。格式解决“到处能跑”，量化解决“跑得起”，但两者都要在目标环境上实测验证，不能只凭导出成功就认为部署成功。
