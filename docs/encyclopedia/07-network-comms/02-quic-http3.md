# QUIC 与 HTTP/3 原理

## 1. 本章目标

读完本篇，能说清 QUIC 相对 TCP+TLS 改了哪几处关键设计、每一处改动换来了什么、又付出了什么代价，以及 HTTP/3 在此之上长什么样、部署时要先确认什么。

## 2. 背景与问题

Web 的传输层几十年没换过底座：HTTP/1.1 与 HTTP/2 都跑在 TCP 之上，再叠一层 TLS 做加密。这套组合能用，但在三个地方越用越别扭：

**第一，握手次数多。** 新连接要先 TCP 三次握手（1 个往返），再 TLS 协商（TLS 1.3 需要 1 个往返），数据才能发。往返时延（RTT）越大，这两个往返越贵；移动网络与跨洋链路上，首字节时间里握手占了大头。

**第二，TCP 的队头阻塞从 HTTP 层移到了传输层。** HTTP/2 已经在一条连接里多路复用多个请求，但 TCP 只认“一个有序字节流”：中间丢一个包，后面所有已到达的数据都得等它重传补齐，哪怕它们属于互不相干的请求。HTTP/2 解决了应用层的排队，却解不开传输层的排队。

**第三，TCP 改不动。** TCP 活在操作系统内核与无数中间设备里，改动要等内核升级、要过中间设备的“只认老行为”检查，演进周期以年计。一个想快速迭代的传输协议，不能把自己绑在内核发布节奏上。

QUIC 的回答是：不在 TCP 上修修补补，另起一个跑在 UDP 之上的传输协议，把“可靠传输、拥塞控制、加密”三件事按现代需求重做一遍；HTTP/3 就是跑在 QUIC 之上的 HTTP。注意分工：QUIC 是传输协议（RFC 9000），HTTP/3 是应用协议（RFC 9114），两者不是同一个东西——QUIC 也可以承载 HTTP 之外的应用。

## 3. 总体架构

```
HTTP/3（RFC 9114：HTTP 语义映射到 QUIC 流）
   │  方法、状态码、头部字段与 HTTP/1.1、HTTP/2 相同，线上传输格式不同
   ▼
QUIC（RFC 9000 传输 + RFC 9001 TLS 集成 + RFC 9002 丢失检测与拥塞控制）
   │  流多路复用、逐流流量控制、连接迁移、内置 TLS 1.3 加密
   ▼
UDP（通常为 443 端口）
   │  只负责把数据报送到对端，不保证可靠与顺序——可靠与顺序由 QUIC 自己实现
   ▼
IP
```

关键点：UDP 在这里只是“能穿过现有网络的信封”。几乎所有网络都放行 UDP（DNS 就跑在 UDP 上），于是新协议不必等中间设备升级就能部署；可靠性、顺序、拥塞控制这些 TCP 原来做的事，QUIC 在用户态自己重做一遍。用户态是刻意选择：协议演进不再依赖操作系统内核升级，应用与库更新就能升级协议。

标准时间线（均已核查）：QUIC 核心四件套 2021 年 5 月发布——RFC 8999（版本无关属性）、RFC 9000（传输）、RFC 9001（QUIC 上的 TLS）、RFC 9002（丢失检测与拥塞控制）；HTTP/3（RFC 9114）与头部压缩 QPACK（RFC 9204）于 2022 年 6 月发布；QUIC 第 2 版 RFC 9369 于 2023 年 5 月发布。HTTP 语义本身（方法、状态码、头部字段）由 RFC 9110 统一定义，三个 HTTP 大版本共用同一套语义。

## 4. 工作机制

### 4.1 合并握手：一次往返，恢复时零往返

QUIC 把传输握手与 TLS 1.3 握手合成一次：客户端的第一个包里同时带上连接建立信息与 TLS ClientHello，服务器回包里同时带上连接确认与 TLS ServerHello。结果是：

- **全新连接**：1 个往返即可发送加密的应用数据（TCP+TLS 1.3 需要 2 个往返）。
- **恢复连接**：客户端已访问过该服务器时，可用 0-RTT：在第一个包里就带上应用数据，服务器凭上次会话的密钥材料解密——往返省到零。

0-RTT 不是免费午餐，见 5.2。

### 4.2 流：多路复用，但丢包只拖住自己的流

QUIC 连接内有多个相互独立的流（stream）：每个请求—响应对占一条双向流，每个流有自己的字节序号、自己的流量控制、自己的可靠交付。HTTP/3 把每个请求映射到一条 QUIC 流上。

丢包时的影响面就此收窄：某个包丢了，只有承载它的流等重传，其他流的数据照常交付应用。TCP 的“全连接等一个包”在这里不存在。代价是实现复杂度：发送方要为每条流维护状态，接收方要处理乱序到达的流数据，拥塞控制也要在“连接级”与“流级”两层同时算账（RFC 9002）。

### 4.3 连接迁移：连接认 ID，不认 IP 地址

TCP 连接由四元组标识（源 IP、源端口、目的 IP、目的端口），任一元素一变，连接即死。手机从 Wi-Fi 切到移动网络时 IP 变了，TCP 连接必须重建，握手与 TLS 协商全部重来。

QUIC 连接由连接 ID 标识：每个包都带连接 ID，服务器凭 ID 查连接状态，不凭四元组。客户端地址变了之后，只要在新路径上完成一次路径验证（证明自己确实能收到发往新地址的包，防止地址欺骗），同一连接就能继续用，传输状态、TLS 会话、进行中的流都不用重建。对移动场景这是质变：切网不再等于断线重连。

连接 ID 还会轮换：同一连接在不同网络上使用不同的 ID，旧网络上的观察者与新网络上的观察者不容易把两次出现关联成同一次会话，这是协议内置的一点隐私考量。反过来对运维也有代价：按四元组做哈希的负载均衡器会在迁移后把包送错后端，QUIC 感知的负载均衡必须按连接 ID 路由（RFC 9312 为此定义了一种在连接 ID 中编码路由信息的办法）。

### 4.4 加密是默认项，不是可选项

QUIC 没有明文模式：TLS 1.3 不是“叠在外面的一层”，而是编织进握手与包格式里的。1-RTT 包的包头之外部分全部加密，连“这是什么类型的包”之外的传输元数据都尽量不暴露。好处是中间设备无法再像改写 TCP 那样“帮”协议做优化或审查——协议演进不再被中间设备的假设卡住；代价同样是中间设备：传统基于明文特征的流量识别、调试抓包、部分防火墙策略在 QUIC 面前失效，运维要换成基于连接 ID、端口与行为特征的新工具链。

### 4.5 HTTP/3 的关键机制：QPACK 与发现方式

**QPACK（RFC 9204）**：HTTP/2 的 HPACK 依赖 TCP 的按序交付来保持压缩表同步；QUIC 的流是乱序到达的，HPACK 照搬过来会重新引入跨流阻塞。QPACK 把动态表更新放到独立的单向编码流里，解码确认走另一条单向流，头部字段的编码只引用表状态、不修改表状态——压缩状态的变化不再卡住请求流。代价是压缩效率略低于 HPACK，以及实现上多出两条控制流要维护。

**服务器推送**：HTTP/3 保留了服务器推送的帧（PUSH_PROMISE 等），但实践中与 HTTP/2 的推送一样很少被真正使用；不要把推送当作 HTTP/3 的卖点，现代做法是用 103 Early Hints 之类的轻量机制提前提示浏览器。

**发现与回退**：浏览器不会一上来就试 QUIC。首次访问仍走 TCP+TLS，服务器通过 `Alt-Svc` 响应头（RFC 7838，例如 `alt-svc: h3=":443"; ma=86400`，表示“本源在 UDP 443 上提供 HTTP/3，该宣告 86400 秒内有效”）或 HTTPS DNS 记录宣告 HTTP/3 能力，浏览器下次再来时才尝试 QUIC；QUIC 不通则自动回落到 HTTP/2 或 HTTP/1.1，用户无感知。这意味着：部署 HTTP/3 是低风险的增量操作——UDP 被拦的网络只会悄悄用回老协议，不会断网；但也意味着：只看“服务器开了 HTTP/3”不等于“用户真的走了 HTTP/3”，验证要看协议分布统计，而不是配置项。

## 5. 关键设计取舍

### 5.1 用户态换演进速度，付 CPU 与实现成本

QUIC 在用户态实现加密、可靠传输与拥塞控制，升级不依赖内核，代价是：同样吞吐下用户态加解密与包处理通常比高度优化的内核 TCP 更吃 CPU；实现一个正确的 QUIC 栈（丢失检测、拥塞控制、流控、迁移、0-RTT 安全）比“调 TCP 参数”复杂一个量级。选 QUIC 时要同时评估服务器 CPU 余量与所用实现的成熟度，而不是只看协议优点。

### 5.2 0-RTT 换延迟，付重放风险

0-RTT 数据在握手完成前就被服务器处理，而这段数据在协议层面没有重放保护：攻击者截获首包并原样重发，服务器可能把同一请求执行两次。正确做法是：0-RTT 只接受安全、无副作用的请求（如 GET），有副作用的请求一律拒绝并让客户端在握手完成后重试（HTTP 语义里对应 425 Too Early 的处理思路，见 RFC 8470）。实现与网关若做不到这条区分，宁可关掉 0-RTT，只保留 1-RTT——1-RTT 已经是相对 TCP+TLS 的主要收益。

### 5.3 加密一切换演进自由，付可观测性

QUIC 加密了绝大多数传输元数据，中间设备无法再“看懂”流量来做优化、排障与策略。换来的是协议不再被中间设备行为冻结；付出的是运维工具链要重建：抓包排障要靠端点日志而非中间抓包，流量工程要靠连接 ID 而非五元组，安全设备要从“解析内容”转向“行为分析”。这是架构级取舍，不是配置项能调和的。

## 6. 与 TCP+TLS 的对比

| 维度 | TCP + TLS 1.3（HTTP/1.1、HTTP/2） | QUIC（HTTP/3） |
| --- | --- | --- |
| 承载 | TCP（内核实现） | UDP（用户态实现传输） |
| 新连接握手 | 2 个往返（TCP 1 + TLS 1） | 1 个往返 |
| 恢复连接 | 1 个往返（会话恢复） | 0-RTT 可选，但有重放风险 |
| 丢包影响面 | 整条连接等重传（传输层队头阻塞） | 只影响丢包所在的流 |
| 连接标识 | 四元组，IP 一变即断 | 连接 ID，支持迁移 |
| 加密 | TLS 叠加层，可配置但可被剥离讨论 | 内置，无明文模式 |
| 头部压缩 | HPACK（依赖按序交付） | QPACK（乱序友好） |
| 演进方式 | 依赖内核与中间设备 | 库与应用升级即可 |
| 中间设备友好度 | 高（行为可观测、可干预） | 低（多数元数据加密、UDP 可能被拦） |

## 7. 应用与限制

- **适合优先上 HTTP/3 的场景**：高延迟链路（握手节省的往返占比大）、移动用户占比高（连接迁移收益大）、丢包率较高的网络（流级隔离收益大）、面向全球用户的边缘服务（CDN 边缘天然适合先行）。
- **收益有限的场景**：低延迟稳定内网（握手本来就不贵）、纯内网服务（迁移与丢包收益都不明显）、CPU 已吃紧的源站（用户态加解密成本要先算账）。
- **部署现状**：标准已定（2021–2022 年核心 RFC 全部发布），主流浏览器与大型 CDN 均已支持；但“支持”不等于“全量”——企业内网拦截 UDP 443、老旧中间设备不识别 QUIC 的情况仍然存在，回落机制是部署设计的一部分，不是事后补丁。具体的各家支持比例与流量占比变化较快，以官方发布为准（待核实），本文不写会被迅速过期的数字。
- **部署前确认清单**：放行 UDP 443（出站与入站方向都要核对）；负载均衡器是否按连接 ID 路由（否则迁移会丢包）；0-RTT 策略是否只放行安全请求；监控是否区分 HTTP 版本统计（否则无法验证 HTTP/3 是否真的被用上）。

> 本机观察（实测）：2026-11-04 在代理 VM 上运行 `curl --version`，curl 8.5.0 的 Protocols 列表中没有 `http3`（只有 `nghttp2` 对应的 HTTP/2 支持）。结论：不要用这台机器上的 curl 去验证 HTTP/3，要么换带 HTTP/3 支持的构建，要么用浏览器开发者工具看协议列。先查工具能力再下结论，是验证 HTTP/3 时最容易省掉的一步。

```bash
# 查看本机 curl 是否支持 HTTP/3（只读命令）
# 示例未实测：HTTP/3 请求示例未在本机跑通，仅作命令示例
curl --version
curl --http3 -I https://example.com
```

## 8. 常见误解

- “QUIC 就是更快的 TCP”：不准确。QUIC 是另一套传输协议；它在握手、丢包隔离、迁移三处有结构性优势，但在稳定低延迟网络上未必比调优过的 TCP 快，CPU 成本还可能更高。
- “HTTP/3 只是 HTTP/2 换个名字”：错。HTTP 语义相同，传输底座、头部压缩、连接模型全换了；部署 HTTP/3 是换传输层，不是改配置项。
- “开了 HTTP/3 就不用管 TCP 了”：错。首次发现仍走 TCP+TLS，UDP 被拦时回落 TCP，TCP 监听必须一直保留。
- “0-RTT 是纯收益”：错。见 5.2，重放风险是协议设计时就承认的代价，必须用“只接受安全请求”的策略对冲。
- “UDP 不可靠，所以 QUIC 不可靠”：错。UDP 只负责送数据报，可靠性由 QUIC 自己实现；“跑在 UDP 上”与“不可靠”之间没有等号。
