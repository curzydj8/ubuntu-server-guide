# SDN 原理入门

## 1. 本章目标

读完本篇，能说清 SDN 到底分离了什么、控制器在中间起什么作用、南向与北向接口各管什么，以及集中控制在哪些场景是收益、在哪些场景是负担。

## 2. 背景与问题

传统网络设备是“全能单机”：一台交换机或路由器内部同时装着两套逻辑——决定报文往哪走的控制逻辑（跑 OSPF、BGP、生成转发表），与真正搬运报文的转发逻辑（按转发表把报文从入端口送到出端口）。每台设备各自独立决策，靠协议互相通告拓扑与路由，最终收敛成一致的转发行为。

这种架构跑了几十年，可靠，但有三个结构性不便：

- **改策略要逐台改**：想全网换一套流量策略（比如“视频流量走低延迟链路”），要逐台设备改配置，改动速度与一致性都受限于人工与设备差异；
- **新功能要等设备**：想上一种新的转发行为，得等厂商在设备软件里实现，网络的演进速度被设备发布节奏卡住；
- **全局视角不存在**：每台设备只看到邻居通告的局部信息，没有任何一个地方能直接回答“全网流量现在长什么样、瓶颈在哪”。

SDN 的思路不是发明一种新路由协议，而是换组织方式：把“做决策”的部分从设备里抽出来，集中到软件控制器里；设备退化成只负责按规则转发报文的执行者。决策集中了，策略就能一次下发全网；设备简单了，新功能就能以软件速度迭代。

## 3. 总体架构

SDN 的经典分层（术语与分层架构见 IRTF 的 RFC 7426，2015 年 1 月发布，信息性文档——它提供术语参考，不制定强制标准）：

```
应用层（Application Plane）
   │ 业务应用：流量工程、负载均衡、防火墙策略、租户隔离……
   │ ▲ 北向接口：应用向控制器提需求（常见为 REST / gRPC，模型常用 YANG）
   ▼
控制层（Control Plane）：SDN 控制器
   │ 拓扑发现、路径计算、策略翻译；持有全网视图
   │ ▼ 南向接口：控制器向转发设备下发规则
转发层（Forwarding / Data Plane）：交换机、路由器、虚拟交换机
   │ 只做一件事：按流表 / 转发表转发报文
   │
管理层（Management Plane）与运行层（Operational Plane）
   │ 设备的配置、监控、状态维护；与控制层并行、各司其职
```

RFC 7426 还定义了两层抽象：网络服务抽象层（NSAL）位于应用与控制之间，设备与资源抽象层（DAL）位于控制与设备之间。抽象层的作用是：上层应用不必关心底层是哪个厂商的设备，下层设备不必理解上层的业务语言——控制器在中间做翻译。这是 SDN“可编程”三个字的真正含义：可编程的不是某一台设备，而是整个网络的行为。

一个常见的简化说法是“三层两接口”：应用层、控制层、基础设施层；北向接口连应用与控制器，南向接口连控制器与设备。管理层与运行层在简化图里常被省略，但生产部署中它们真实存在——设备的软件升级、端口状态监控、配置备份都走管理面，不走控制面；把两者混为一谈是排障时常见的概念错误。

## 4. 工作机制

### 4.1 转发设备：从“自己算”到“按表办事”

SDN 转发设备的核心数据结构是流表（flow table）：每条流表项由“匹配条件 + 动作”组成。匹配条件可以是入端口、源/目的 MAC、源/目的 IP、协议、端口号等字段的组合；动作包括转发到指定端口、丢弃、修改某个头部字段、送控制器处理、统计计数等。报文到达时，设备按优先级查表：命中则执行动作，未命中则按缺省策略处理（常见是丢弃，或送控制器问一句“这包怎么处理”）。

与传统转发表相比，流表的关键区别不在“查表转发”这个动作，而在“表项是谁写的”：传统设备由本机控制进程算出表项，SDN 设备由远端控制器下发表项。设备不再需要跑全套路由协议，软件可以大幅简化；但设备也因此失去了“控制器不在时自己算路”的能力——控制器与设备之间的通道，就是 SDN 的生命线。

### 4.2 控制器：全网视图 + 策略翻译机

控制器做三件事：

1. **发现拓扑**：通过南向接口收集设备与链路信息，拼出全网拓扑图；链路断了、设备上线了，控制器要先于业务应用知道。
2. **算路与决策**：收到应用的需求（“A 租户的流量与 B 租户隔离”“这条链路拥塞时绕行”），结合拓扑算出每台设备该装什么流表项。
3. **下发与维护**：把流表项推到各设备，处理设备上报的事件（未知报文、端口状态变化、统计计数），并在拓扑变化时重新算路、更新流表。

控制器本身是软件，可以跑在普通服务器或虚拟机上，也可以集群部署。开源控制器中较有代表性的是 ONOS（面向运营商级、分布式集群设计）与 OpenDaylight（模块化、支持多种南向协议）；选型时看重的不是名气，而是“它支持的南向协议是否覆盖你的设备”与“集群高可用是否经过验证”——这两点在 7.2 会再展开。

### 4.3 南向接口：控制器与设备之间的语言

南向接口是 SDN 架构里最关键、也最体现“开放程度”的一环。主流选择有三类：

- **OpenFlow**：最早、最具代表性的 SDN 南向协议，由斯坦福研究（2008 年论文）起步，后由开放网络基金会（ONF）标准化。控制器通过 OpenFlow 下发流表项、查询统计，设备通过它上报未命中报文（PACKET_IN）与端口事件。公开的稳定规范是 OpenFlow 交换机规范 1.5.1（ONF TS-025，2015 年 3 月，协议版本 0x06）。OpenFlow 的匹配—动作模型是“固定字段”的：能匹配哪些字段、能做哪些动作由规范定义，超出规范的新协议字段需要等规范扩展——这正是 P4 要解决的问题。
- **NETCONF / YANG（RFC 6241 等）**：IETF 的网络配置协议，配合同为 IETF 的 YANG 数据建模语言。NETCONF 更偏向“设备配置管理”（接口地址、路由配置、系统参数）而非逐包流表下发；在很多部署里，OpenFlow 管转发规则、NETCONF 管设备配置，两者分工配合。RFC 7426 同样把 NETCONF/YANG 列为 SDN 使能技术之一。
- **P4Runtime**：配合 P4 可编程数据面使用。P4 语言让运维者自己定义数据面的解析器、匹配字段与处理流水线（而不是只能用规范给定的字段集），P4Runtime 则是控制器向这种自定义流水线下发转发表项的接口。P4 把“可编程”从控制面推进到了数据面本身：转发行为不再受固定字段集限制，但代价是需要可编程芯片或软件目标（如 BMv2 参考实现）支撑，硬件门槛高于普通 OpenFlow 交换机。

三者不是互斥关系：同一控制器常常同时说几种南向语言，对不同设备用不同接口；“SDN = OpenFlow”是早期常见的简化说法，放在今天的部署里已经不准确。

### 4.4 北向接口：应用与控制器之间的语言

北向接口没有像南向那样统一的标准协议，常见形态是 REST API、gRPC 接口，或基于 YANG 模型的 RESTCONF。应用通过北向接口向控制器表达“意图”而非“命令”：例如“保障这条视频流的带宽”而不是“在交换机 3 的表 0 第 5 项写这条规则”。意图与规则之间的翻译由控制器（或其上的应用层）完成。

北向不统一是 SDN 生态的长期现实：换控制器常常意味着重写上层应用。评估 SDN 方案时，北向接口的开放程度与文档质量，应当与南向支持放在同一权重上考察，而不是只看控制器名气。

### 4.5 一次转发决策的完整链路

以“新流量第一次到达”为例，走一遍全过程：

```
1. 主机 A 发包 → 交换机 S1：查流表，未命中
2. S1 按缺省策略把报文（或报文头）上报控制器（OpenFlow 的 PACKET_IN）
3. 控制器查拓扑与策略：该流量允许，路径为 S1 → S2 → S3
4. 控制器向 S1、S2、S3 下发对应流表项（沿途设备各装一条）
5. S1 按新表项转发该报文；后续同类报文直接命中流表，不再上报
6. 链路故障时：设备上报端口事件 → 控制器重算路径 → 更新受影响设备的流表项
```

注意第 5 步的含义：控制面只介入“第一次”与“变化时”，稳态流量完全由数据面硬件速度转发。SDN 没有让每个包都去问控制器——那样既慢又脆弱；控制器是“装表的人”，不是“搬包的人”。

## 5. 关键设计取舍

### 5.1 集中换全局最优，付单点与规模代价

集中控制器能看到全网拓扑，算出的路径可以是全局最优（负载均衡、拥塞绕行、租户隔离一次成型），而分布式协议只能各自局部最优、慢慢收敛。付出的代价有三：控制器故障影响面大（必须集群高可用）；控制器与设备的通道延迟与带宽成为控制面瓶颈（大规模网络要分区分层控制器）；全网策略集中后，一次错误策略下发的影响面也是全网的（策略变更需要灰度与回滚机制，与软件发布同等对待）。

### 5.2 通用设备换灵活性，付专用能力

SDN 设备越通用、越依赖控制器，单机自主能力越弱：控制器失联时，新流量无法获得规则（已装好的流表项仍可继续转发存量，这是“失效时保持转发”的常见设计，但新业务与故障切换会停滞）。传统设备反过来：单机全能，控制器死了各设备还能靠本地协议继续跑。选型时要问清楚“控制器失联时数据面行为”这一条，并把它写进验收标准，而不是留到故障时才发现。

### 5.3 开放接口换厂商中立，付集成成本

南向标准化让不同厂商设备能被同一控制器管理，摆脱单厂商绑定；但“都支持 OpenFlow”不等于“行为完全一致”——各厂商对规范的可选部分、流表规模、动作集的实现存在差异，多厂商组网仍需逐项互通测试。开放降低了锁定成本，没有消除集成成本。

## 6. 分类与变体

- **按控制器部署形态**：单控制器（小规模、实验）、集群控制器（生产高可用）、分层/分域控制器（超大规模：域内集中、域间协同，避免单集群规模爆炸）。
- **按数据面可编程程度**：固定流水线（OpenFlow 交换机：字段与动作由规范定）、可编程流水线（P4 目标：字段与流水线由用户定义）、软件数据面（虚拟交换机如 Open vSwitch、eBPF/XDP 程序：跑在通用服务器上，灵活性最高、转发性能看实现）。
- **按与传统网络的关系**：纯 SDN（全网控制器管理）、混合模式（SDN 域与传统路由域并存、边界互通）——现实中混合模式远多于纯 SDN，存量设备不可能一夜替换。
- **相近概念辨析**：SDN ≠ NFV（网络功能虚拟化）。NFV 是把防火墙、负载均衡等网络功能从专用硬件搬到虚拟机/容器里跑，解决“功能载体”问题；SDN 解决“转发决策归谁管”问题。两者经常一起出现（虚拟化功能由 SDN 控制器统一调度流量），但解决的问题不同，不要混用。

## 7. 应用与限制

### 7.1 适用场景

- **数据中心与云网络**：租户多、变更频、需要自动化开通与隔离；控制器一次下发胜过逐台登录设备，虚拟交换机与 SDN 控制器是云网络的常规组合。
- **广域流量工程**：运营商与大型企业用全局视图做跨链路负载均衡与拥塞绕行，传统分布式协议难以一次算出全局最优路径。
- **园区与分支的集中管理**：分支设备简化为转发执行者，策略总部统一下发；分支上线从“派人上门配置”变成“设备上线自动纳管”。
- **研究与教学**：控制器 + 虚拟交换机的组合可以在普通服务器上搭出可编程网络实验环境，验证新协议、新策略而不动生产设备。

### 7.2 不适用或需谨慎的场景

- **规模小、变更少的网络**：几台交换机的办公室网络，SDN 的控制器、集群、策略系统全套成本远超“逐台配置”的成本，收益为负。
- **控制器高可用未验证的部署**：单控制器、无集群、无失联预案的生产网，等于把全网命运押在一台服务器上——这是架构降级，不是升级。
- **对单包延迟极端敏感且控制面在远端的数据面**：首包上报控制器的往返会引入额外延迟；解决办法是预装常用流表项、缩短控制通道延迟，而不是“让每个包都问控制器”。
- **多厂商互通未经测试的组合**：规范一致不等于行为一致，上线前必须做互通测试，重点是流表规模上限、动作集差异、失联行为三项。

### 7.3 局限小结

SDN 解决的是“决策组织方式”，不解决带宽、延迟、单机转发性能这些物理问题；控制器集中化带来全局最优，也带来单点风险与规模瓶颈；开放接口降低厂商锁定，但不消除集成测试成本。评估 SDN 时，先问“我的网络痛点是不是决策分散与变更太慢”——如果痛点是带宽不足或单机性能，SDN 不是答案。

## 8. 常见误解

- “SDN 就是 OpenFlow”：错。OpenFlow 只是最早的南向协议之一；SDN 是架构思想，南向还可以是 NETCONF、P4Runtime 等，见 4.3。
- “上了 SDN 就不用路由器协议了”：不全面。域内转发可由控制器接管，但域间互联、与传统网络边界互通仍常常用 BGP 等协议；混合模式是常态。
- “控制器集中了，网络就变简单了”：片面。设备变简单了，复杂性转移到了控制器、策略系统与高可用设计上；总复杂度没有消失，只是换了地方。
- “SDN 让网络自动变聪明”：错。控制器只执行策略与算法；策略本身（隔离规则、路径偏好、故障切换条件）仍需人定义与验证，错误的策略会被 SDN 以全网速度不折不扣地执行。
