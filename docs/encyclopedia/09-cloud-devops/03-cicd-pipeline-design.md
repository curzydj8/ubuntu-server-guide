# CI/CD 流水线设计：阶段、制品、环境晋升与回滚

## 1. 一句话定义

CI/CD 流水线是一条自动化的交付链：代码一提交，就自动经过构建、测试、扫描、打包、部署、验证这些阶段，把“能跑的代码”变成“已上线的服务”，并且每一步都可追溯、可重做、可回滚。

## 2. 为什么需要它

没有流水线，部署靠人手工操作，问题是系统性的：

- **不一致**：这次部署的人、这次用的命令、这次的环境，和上次不一样，出问题不知道差在哪。
- **不可重复**：同一份代码，换个人、换台机器就部署不出同样的结果。
- **无审计**：谁在什么时候把哪个版本推上生产，事后查不到；出事故先花时间还原现场。
- **回滚靠记忆**：回滚步骤在某个人脑子里，他不在就没人敢动。

流水线解决的不是“部署快一点”，而是“部署这件事本身变得可重复、可追溯、可回滚”。速度是副产品，确定性才是目的。

## 3. 核心含义

### 3.1 CI 与 CD 是两件事

- **持续集成（CI）**：代码频繁合并到主干，每次合并自动构建与测试。目标是“早发现集成问题”，不是“自动上线”。
- **持续交付（CD，Delivery）**：CI 通过后，制品自动准备到“随时可发布”的状态，但发布到生产仍需人工确认。
- **持续部署（CD，Deployment）**：连发布确认也自动化，通过全部关卡就自动上生产。

三者的分水岭在“生产发布要不要人工确认”。新手最容易把三者混成一个词，结果在“要不要自动上生产”上吵不出结论：先定你要的是交付还是部署，再设计流水线。

### 3.2 流水线阶段：每阶段只做一件事

一条典型流水线按顺序是：

```text
检出 → 构建 → 单元与集成测试 → 安全扫描 → 打包制品 → 部署到测试环境 → 验收测试 → 部署到生产 → 生产验证
```

每阶段的职责与产物要分清：

- **检出**：取固定版本的代码（某次提交，不是“最新主干”这个浮动概念）。
- **构建**：把代码编成可运行物。构建环境要固定，否则“在我机器上能跑”会重演。
- **测试**：单元测试、集成测试按层跑；测试失败就停在这一阶段，不准带着失败往下走。
- **安全扫描**：依赖漏洞、镜像漏洞、密钥泄露检查。扫描是关卡，不是事后报告。
- **打包制品**：产出不可变制品（见 3.3），并打上版本。
- **部署**：把同一份制品推向各环境，不是在各环境各构建一次。
- **验证**：部署后跑健康检查与验收用例，失败就触发回滚（见 3.5）。

### 3.3 制品与版本：同一份制品走完全程

制品规则只有一条：**一次构建，处处部署**。开发环境测过的那份制品，原样晋升到测试、再到生产；每个环境重新构建，等于每个环境测的都是不同的东西，测试结果就作废了。

版本规则配套三条：

- **不可变**：同一版本号绝不指向两份不同的制品。发现制品有问题，发新版本，不覆盖旧版本。
- **语义化版本**：主版本（不兼容变更）、次版本（向下兼容的功能）、修订号（问题修复），三段各有含义，升级方一看就知道风险等级。
- **镜像标签策略**：容器镜像不用 latest 做生产标签。latest 是浮动指针，今天拉到的和昨天拉到的可能不是同一份；生产部署必须用固定版本标签或摘要（digest）。

### 3.4 环境晋升：同一制品，逐级放行

环境晋升是“制品逐级通过关卡”的过程，不是“每个环境各搞一套”：

```text
开发环境（快，容忍失败）→ 测试环境（跑完整测试）→ 预发布/灰度（接近生产，小流量验证）→ 生产（全量）
```

每一级都有自己的放行条件：测试环境要求测试全过，预发布要求验收通过，生产要求人工确认或自动关卡通过。制品在任何一级失败，都停在该级，不准跳级。跳级部署是生产事故的经典前奏。

### 3.5 回滚策略：先定好，再上线

回滚不是出事故时现想的，要和部署方案一起定。两种基本策略：

- **回滚到旧版本（Rollback）**：把上一份已知良好的制品重新部署上去。优点是快、动作小；前提是旧版本与当前数据兼容。
- **前滚修复（Roll Forward）**：不退回旧版，而是发一个修复版顶上去。优点是能同时修问题、保住新功能；缺点是慢，要走完整流水线。

选哪种，看数据兼容性：只改代码，两种都行；改了数据格式，优先评估前滚，因为回滚代码救不了已迁移的数据（与第 2 篇的结论一致）。无论选哪种，回滚本身也要能走流水线、也要能验证，不能靠手工敲命令救火。

### 3.6 与 IaC 的分工：流水线管应用，IaC 管环境

基础设施即代码（IaC）与 CI/CD 是互补的，不是竞争关系：

- **IaC 管“环境长什么样”**：服务器、网络、集群、数据库实例这些基础设施的形态，用代码描述、版本管理、评审后应用。
- **流水线管“应用怎么交付”**：代码从提交到上线的过程，制品、测试、部署、验证。

分工不清的典型症状：流水线里嵌着建服务器的步骤，改个应用版本要动基础设施代码；或者 IaC 里塞着应用部署逻辑，环境一变应用就跟着变。判断标准：**换应用版本不该动 IaC，换环境形态不该动应用流水线**。

GitOps 是这种分工的一种落地形态：把“期望状态”也写进 Git 仓库，由集群内的控制器持续对齐；流水线只负责把新制品版本写进仓库，部署由控制器完成。本篇只讲分工思想，GitOps 的完整机制属后续内容。

## 4. 分类

- **按触发方式**：提交触发（每次推送都跑）、定时触发（夜间全量回归）、手动触发（生产发布、回滚演练）。
- **按部署策略**：滚动（逐步替换，见第 2 篇）、蓝绿（新旧两套环境整体切换，出问题切回旧环境）、金丝雀（先放小比例流量验证，再逐步放大）。
- **按运行位置**：自建 Runner（自己管执行机，控制力强、维护成本高）、托管服务（厂商管执行机，开箱即用、定制受限）。选型看团队规模与合规要求，不存在 universally 正确的答案。

## 5. 典型应用

- **网站发布**：本站 website-guide 的部署教程（Git、GitHub Actions 自动部署）就是一条简化版流水线：提交 → 构建 → 部署到静态托管；本篇讲的是它背后的通用设计，工具细节见那篇教程。
- **多服务发布**：多个服务共享一条流水线框架、各服务自带阶段配置；框架统一（制品、晋升、回滚规则），配置各异。
- **回滚演练**：定期在测试环境演练回滚，确认回滚路径本身是通的；没演练过的回滚路径，出事故时大概率不通。

## 6. 限制与常见误解

- 流水线不等于自动化全部：测试写得差，流水线只是更快地把错误推上线；评审、数据迁移、发布沟通仍需人工。
- 持续部署不等于每次提交都上生产：关卡（测试、扫描、验收、灰度）没过，提交再多也不会上生产；“自动”指的是“按规则自动”，不是“无条件自动”。
- 回滚不解决数据迁移：数据格式变了，回滚代码、甚至回滚制品，都救不了数据；数据变更要单独的迁移与回滚方案。
- 密钥进流水线要用专门的 Secret 管理：密钥写进流水线配置文件、写进镜像、写进日志，都是泄露；密钥的存放与轮换见 02-security 的秘密信息管理篇。
- 误解：“上了 CI/CD 就不用测试环境了”：错。测试环境是晋升链上的一级，流水线再自动也替代不了分级验证。

## 7. 小结

CI/CD 流水线 = 一次构建的不可变制品，走逐级放行的环境晋升链，每一级有放行条件，每次发布都带可演练的回滚方案；流水线管应用交付，IaC 管环境形态，两者分工不混。
