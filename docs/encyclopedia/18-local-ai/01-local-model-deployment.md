# 本地模型部署：工具与推理引擎的定位

## 1. 本章目标

读完本篇，能说清在自己机器上跑模型要经过哪几层、Ollama 与 llama.cpp 各自处在哪一层、模型文件是什么格式、服务以什么方式暴露、以及“本地”在隐私与离线上的真实边界。

## 2. 背景与问题

大模型最初是云端服务：你在网页或 API 里发提示词，算力与权重都在别人机房。这种方式开箱即用，但有三处代价：第一，提示词与数据要出本机；第二，断网就不可用；第三，用量、价格、模型版本都不由你控制。本地部署就是把“模型与推理”搬回自己机器：权重文件下载到本地磁盘，推理进程跑在本地 CPU 或 GPU 上，应用通过本地接口调用它。代价也随之转移：你要自己管硬件、内存、模型文件与服务进程。

本篇只讲部署这一层怎么做。模型结构本身（注意力、训练方法）是 17 域的内容，本篇不重复，只在需要时引用。

## 3. 总体架构

本地部署自上而下分五层，每层只解决自己的问题：

```text
应用（聊天界面、脚本、Agent 程序）
  ↓ HTTP 调用（本地回环地址）
服务层（Ollama、llama-server 等：模型管理、并发、接口）
  ↓ 加载权重、执行推理
推理引擎（llama.cpp 等：把权重算成 token）
  ↓ 读取
模型文件（GGUF 等：权重 + 分词器 + 元数据）
  ↓ 占用
硬件（CPU / GPU、内存 / 显存、磁盘）
```

关键点：服务层与推理引擎是两层，不是一回事。Ollama 是“服务层 + 引擎打包”的一体工具；llama.cpp 是引擎本身，也可以单独跑出服务。选型先定你要哪一层，再定工具。

## 4. 工作机制

### 4.1 Ollama 路线：一体工具

Ollama 把“下载模型、管理模型、跑推理、暴露接口”包成一条命令链：

- `ollama pull <模型名>`：从模型库下载模型到本地。
- `ollama run <模型名>`：加载模型并进入交互对话。
- `ollama serve`：以后台服务方式运行，默认只监听本地回环地址 `127.0.0.1` 的 `11434` 端口。
- `Modelfile`：用类似配置文件的写法定义一个定制模型（基础模型、系统提示词、参数），再用 `ollama create` 生成。

程序调用不走命令行，走本地 HTTP 接口。Ollama 的 API 文档列出的主要接口包括：

- `GET /api/tags`：列出本地已有模型（不需要请求体，适合先验证服务是否在跑）。
- `POST /api/generate`：单次文本补全。
- `POST /api/chat`：多轮对话，请求体里带 `messages` 数组（角色为 system、user、assistant、tool），工具调用也走这个接口。
- `/v1` 路径：OpenAI 兼容接口，已有用 OpenAI 客户端写成的代码改个 base URL 就能指向本地。

两个必须知道的默认行为：第一，本地接口默认不需要鉴权，因为它只绑回环地址，本机进程才能访问；第二，`/api/chat` 本身不在服务器端保存对话状态，每次请求都要把完整历史发过去，“记忆”要由调用方自己维护（见本系列 Agent 篇）。

### 4.2 llama.cpp 路线：引擎本身

llama.cpp 是 C/C++ 写的推理引擎，Ollama、LM Studio 等工具的底层多半是它或与它同源的实现。直接用它，意味着你自己拼服务：

- `llama-cli`：命令行交互推理。
- `llama-server`：把引擎跑成 HTTP 服务，同样提供 OpenAI 兼容接口。
- `llama-quantize`：把模型转成目标量化格式（见本系列量化篇）。
- `convert_hf_to_gguf.py`：把 Hugging Face 发布的权重转成 GGUF。

这条路线的自由度最高：模型文件、量化级别、GPU 卸载层数、上下文长度都由你定；代价是每一步都要你自己确认，出了问题也由你自己定位。适合需要精细控制、或要把推理嵌进已有服务的场景。

### 4.3 模型文件格式：GGUF 与 safetensors

模型文件首先是“权重 + 分词器 + 元数据”的容器，格式决定了谁能直接读它：

- **GGUF**：llama.cpp 的单文件格式，一个文件里同时装权重、分词器与元数据（架构、层数、注意力头数、上下文长度、聊天模板等）。Ollama、llama.cpp、LM Studio 等本地工具直接读 GGUF；模型发布页上常见的 `Q4_K_M`、`Q8_0` 后缀就是 GGUF 的量化版本（见量化篇）。
- **safetensors**：训练与发布侧更常见的格式，多个权重文件加配置。本地推理前通常要先转成 GGUF（上面那条 `convert_hf_to_gguf.py` 就是干这个的）。

选模型时先看发布页的格式与量化标签，再看许可：权重许可决定了你能不能商用、能不能再分发、要不要署名，许可不在本篇展开，下载前以发布页为准。

### 4.4 服务化方式：三种暴露范围

| 方式 | 做法 | 适用 | 风险 |
|---|---|---|---|
| 本机回环 | 默认监听 127.0.0.1，只本机能访问 | 个人使用、开发调试 | 最低；不要误以为“本机”等于“局域网可达” |
| 局域网 | 改监听地址为局域网地址（如 Ollama 的 `OLLAMA_HOST`） | 家里多台设备共用一个推理服务 | 同网段设备都能访问，且本地接口默认无鉴权，必须另加反代鉴权或防火墙限制 |
| 对外服务 | 经反向代理暴露到公网 | 给他人提供服务 | 必须做鉴权、限流、TLS 与日志；裸奔的推理接口会被扫描器迅速发现 |

一句话原则：暴露范围每扩大一级，就要补一级访问控制；不要把“本地能跑”直接等同于“可以对外提供”。

### 4.5 资源估算：先算内存，再谈速度

在没有 GPU 的机器上，内存是第一瓶颈。估算分三笔账（估算口径，见本节末尾说明）：

1. **权重内存** ≈ 参数量 × 每参数字节数。F16 约 2 字节/参数，Q8 约 1 字节/参数，Q4_K_M 约 0.5 字节/参数（精确到小数点后一位的数值因张量混合精度而异，以模型发布页标注的文件大小为准）。例如 7B 模型：F16 约 13 GB，Q8_0 约 7.2 GB，Q4_K_M 约 4.1 GB。
2. **KV 缓存**：随上下文长度线性增长（见量化篇的示例演算），长对话、大上下文要单独留预算。
3. **系统余量**：操作系统与其他进程的内存不能全占，至少留出系统正常运转的部分。

按这个口径可以给选型定个粗框（估算口径，非实测承诺）：

| 场景 | 建议起点 | 说明 |
|---|---|---|
| 1–4B 小模型 | 8 GB 内存的个人电脑可尝试 | 对话、摘要、简单抽取；复杂推理能力有限 |
| 7–9B 通用模型 | 16 GB 内存是更稳的起点 | 日常问答、写作辅助、代码补全的主力区间 |
| 13B 及以上 | 需要更大内存或 GPU 显存 | 在 2 核 7.7 GB 这类低配机器上不推荐硬上 |

低配机器立场（本篇明确表态）：不要在低配机器上跑大模型，也不要写“包跑得动”的承诺。模型跑起来与跑得可用是两回事：能加载不等于速度可接受，长上下文、大批量下内存与速度都会先于质量出问题。

## 5. 关键设计取舍

- **易用换可控**：Ollama 省事，但参数与行为多由工具默认；llama.cpp 可控，但每一步都要自己确认。
- **一体换组合**：一体工具出问题时排查面小；自己拼服务时每一层都可换，但排障要分层定位。
- **单机换联网**：单机保隐私与离线，但算力上限就是本机；联网用云端模型能突破上限，但数据要出本机。两者不是对立，是按任务分流：敏感、离线任务走本地；重任务走云端。

## 6. 分类与变体

按封装程度分三类：

- **一体工具**：Ollama、LM Studio 类。装好就能跑，适合个人与快速验证。
- **推理引擎**：llama.cpp 类。给需要精细控制或二次开发的人。
- **服务器向框架**：vLLM、TensorRT-LLM 类。面向 GPU 服务器的高并发场景，不属于本篇低配本地场景，只列出来避免选型时张冠李戴。

## 7. 应用与限制

典型应用：离线问答与写作辅助、个人文档摘要、运维助手（见 17 域本地大模型运维助手篇）、Agent 程序的本地模型后端（见本系列 Agent 篇）。

限制：本地模型的能力上限由权重本身决定，部署方式不能弥补模型能力的短板；工具默认配置不等于生产配置，对外提供服务前要补鉴权与限流；模型文件体积大，下载与磁盘占用要提前规划。

## 8. 常见误解

- 误解一：“本地 = 绝对隐私”：错。权重与提示词不出本机只是隐私的一半；工具的联网行为（如遥测、模型库请求）、日志留存、以及你主动接上的联网工具，都会影响隐私边界，上线前要按官方文档逐项核查。
- 误解二：“下载下来就能跑”：错。还要过内存、量化格式、上下文长度三关，缺一关就会加载失败或慢到不可用。
- 误解三：“参数越大越好”：错。参数只在同代同类比较时有意义；任务、量化级别、上下文需求与硬件共同决定体验。

## 9. 隐私与离线边界（小结）

本地部署的隐私收益是真实的：推理过程与提示词可以不出本机，断网也能用。但边界也要说清：第一，模型本身可能记住了训练数据中的片段，输出不等于“你的数据没出去”；第二，任何联网的周边能力（联网搜索工具、云端回退、遥测）都会打开新的出口；第三，日志与对话历史存在哪、保留多久，是部署者要自己定的策略，不是工具默认给你的答案。
