# Agent 与工作流自动化：工具调用、规划执行与人工接管

## 1. 本章目标

读完本篇，能说清 Agent 与一次问答的区别在哪、工具调用是怎么实现的、规划与执行循环如何运转、记忆与检索各解决什么问题、工作流怎么编排、以及失败时人工从哪里接管。

## 2. 背景与问题

一次问答的边界很清楚：你发一段提示词，模型回一段文字。但很多真实任务不是一段文字能解决的：查数据、跑命令、读写文件、汇总结果、按条件分支处理——这些都要模型“动手”，而且不止动一次。Agent 就是把“模型”放进一个能循环执行的系统里：模型负责判断下一步做什么，宿主程序负责真正执行，并把执行结果送回模型，让它再判断下一步。模型本身不直接碰你的文件与命令，碰的是宿主程序给它的工具。

本篇讲的是工作流层面的机制，不重复 17 域的模型原理；模型为什么能“判断下一步”，属于模型能力问题，本篇只把它当成一个可用的输入。

## 3. 总体架构

一个最小 Agent 系统分六个部件：

```text
用户目标
  ↓
规划器（模型：判断下一步做什么）
  ↓ 选工具、填参数
执行器（宿主程序：真正调用工具）
  ↓
工具层（文件读写、命令执行、联网查询、数据库、其他程序接口）
  ↓ 执行结果（成功输出 / 报错）
观察反馈（结果回填给模型）
  ↓
循环：规划器再判断 → 直到完成、失败或人工接管
  ↓
记忆与检索（对话历史、持久记录、外部知识，随每轮供给模型）
```

关键分工：模型只做“判断”，宿主做“执行”。这个分工是后面所有安全与失败处理的基础——因为执行权在宿主手里，宿主才能设审批、设上限、记日志。

## 4. 工作机制

### 4.1 工具调用：模型输出请求，宿主负责执行

工具调用的标准流程（以 Ollama 的 `/api/chat` 接口为例，机制见来源）：

1. 调用方在请求里声明工具清单：每个工具的名字、用途说明、参数结构。
2. 模型判断需要用工具时，不直接输出正文，而是输出一个结构化调用请求（工具名 + 参数）。
3. 宿主程序按请求真正执行工具（读文件、跑命令、查接口），拿到结果。
4. 宿主把结果以 `tool` 角色的消息发回模型，模型再决定下一步：继续调用、换工具、或输出最终答案。

三个必须知道的点：第一，工具支持取决于模型，不是所有模型都能稳定输出结构化调用；第二，模型填的参数可能错（例如把文件名写错、把条件理解反），宿主不能盲目信任参数；第三，模型本身没有“执行”能力——它说“我删了文件”时，真正删没删，要看宿主有没有执行。

### 4.2 规划与执行循环：思考—行动—观察

常见模式是“思考—行动—观察”循环：

1. **思考**：模型根据目标与当前信息，判断下一步做什么。
2. **行动**：宿主执行选定的工具。
3. **观察**：把工具结果送回模型，更新它对任务状态的认知。
4. 循环直到模型判断任务完成，或触发终止条件。

这个循环的脆弱点在“误差累积”：第一步的参数错了，后面每一步都建立在错的结果上；长链路任务尤其明显。缓解办法不在模型侧，而在宿主侧：每步校验结果格式、关键步骤设检查点、整条链路设上限（见 4.5）。

### 4.3 记忆：对话历史、持久记录与检索是三回事

- **对话历史**：本轮对话的消息序列。注意 Ollama 的 `/api/chat` 不在服务器端保存状态，每次请求都要把完整历史发过去；历史越长，请求体越大、KV 预算越高（见量化篇）。历史管理（截断、摘要）是调用方的责任。
- **持久记录**：跨对话保留的东西，例如用户偏好、任务进度、已确认的事实。存在哪（文件、数据库）、保留多久、谁能改，都是部署者要定的策略，不是模型自带的。
- **检索（RAG 式）**：模型不知道或记不准时，去外部知识里查：把问题转成检索请求，从文档库找出相关片段，拼进提示词再让模型回答。检索解决的是“知识不在模型里”的问题，不解决“模型判断错了”的问题；检索到的片段质量，决定了回答质量的上限。

三者不要混为一谈：“模型记住了”通常只是对话历史还在请求体里，不等于它形成了持久记忆。

### 4.4 工作流编排：固定流程与自主规划的取舍

| 编排方式 | 做法 | 适用 | 代价 |
|---|---|---|---|
| 固定流程 | 步骤与分支事先画好，模型只在每步内做判断 | 巡检、报表、数据整理等重复任务 | 灵活差，遇到流程外情况要人工改流程 |
| 自主规划 | 只给定目标，步骤由模型每轮自己定 | 探索性任务、需求说不清的任务 | 不可预测，失败模式多，必须配上限与审批 |
| 混合 | 主干固定、关键节点让模型判断 | 多数生产场景 | 设计成本最高，但最可控 |

多 Agent（多个 Agent 分工协作）是编排的扩展，不是本篇重点：它把“一个 Agent 的循环”变成“多个 Agent 的分工与汇总”，复杂度与排障难度同步上升；单 Agent 没跑稳之前，不建议直接上多 Agent。

### 4.5 失败与人工接管：上线前必须有的五件套

1. **循环上限**：设最大步数与最长耗时，到上限就停，防止死循环烧掉算力与时间。
2. **有限重试**：工具失败先按错误类型分流——参数错不重试（重试也没用）、临时故障可退避重试（例如间隔几秒重发）、重试次数封顶。
3. **审批点**：写操作（改文件、改配置）、外发操作（发消息、调外部接口）、不可逆操作（删除）执行前停下来，等人工确认。审批点是宿主实现的，不是模型“自觉”的。
4. **审计日志**：每一步记下“调了什么工具、参数是什么、结果是什么、谁确认的”，出问题靠日志复盘，不靠模型回忆。
5. **降级与回滚**：写操作尽量可重放（幂等）或可撤销；失败时先停在安全状态，再由人工决定继续、重做还是放弃，不要让 Agent 自己“抢救”一个它已经搞砸的现场。

## 5. 关键设计取舍

- **自主换可控**：自主规划灵活，但不可预测；固定流程可预测，但覆盖不了流程外情况。生产场景先从混合编排起步。
- **能力换权限**：工具给得越多，Agent 能做的事越多，出事的面也越大。工具权限按最小够用给，命令执行类工具尤其要收紧（沙箱、 allowlist、禁高危命令）。
- **自动化换人工**：不是所有步骤都值得自动化。判断成本低、出错代价低的步骤先自动化；出错代价高的步骤留审批点，人工接管不是失败，是设计的一部分。

## 6. 分类与变体

按自主程度分三档：

- **助手档**：模型只建议、宿主只展示，人做执行。适合高风险操作的学习期。
- **半自动档**：模型可执行读操作与低风险写操作，高风险操作走审批。多数生产场景的起点。
- **全自动档**：模型在限定范围内自主执行，人工只看日志与异常。只适用于流程稳定、失败代价低、回滚容易的任务。

## 7. 应用与限制

典型应用：运维助手（巡检、日志初筛、报告草稿，见 17 域本地大模型运维助手篇）、个人文档问答（检索 + 摘要）、定时数据整理、跨工具搬运（例如把 A 系统的数据按规则写进 B 系统）。

限制：模型幻觉会直接变成错误工具参数；长链路误差会累积；延迟与成本随步数线性增长；Agent 不能用于无监督的高风险操作（改生产配置、删数据、对外付款），这些场景必须留人工。

## 8. 常见误解

- 误解一：“Agent 就是模型本身”：错。Agent 是“模型 + 宿主 + 工具 + 记忆 + 规则”的系统，模型只是其中判断的那一块。
- 误解二：“模型调用工具 = 模型在执行代码”：错。模型只输出调用请求，真正执行的是宿主程序；执行权在宿主，安全控制点也在宿主。
- 误解三：“多轮对话久了，模型就记住了”：错。对话历史只是每次请求带上的文本，持久记忆要靠宿主的记录与检索机制。
