# React Native 与原生桥接

## 1. 一句话定义

React Native 是用 JavaScript/TypeScript（React 写法）描述界面、由原生控件真正渲染的跨平台框架：界面是系统自己的控件，逻辑跑在 JS 运行时，两者之间靠桥接层通信。

## 2. 为什么需要它

[跨平台框架选型](02-cross-platform.md)已经讲过选型层面的取舍：React Native 属于“桥接原生控件”路线。本篇讲这条路线内部是怎么工作的。理解 React Native 的关键是分清三条线：JS 线程跑业务逻辑与 React 树、原生线程跑真正的系统控件、两者之间的通信层决定性能天花板。老架构与新架构的区别，本质上就是这条通信层换了实现——不知道新旧之分，就会在旧资料里找到已经不存在的桥、或在新架构上沿用旧架构的优化经验。

## 3. 核心含义

### 3.1 JS 运行时：代码跑在哪

React Native 的 JS 代码跑在一个独立的 JS 引擎里，当前默认是 **Hermes**（Meta 自研的轻量 JS 引擎，为移动端优化：启动快、内存占用小、支持字节码预编译）。JS 运行时与原生代码不在同一线程，互相调用必须经过跨线程通信——这是整个框架性能模型的前提。

React 的写法沿用 Web 端的 React：组件、状态（`useState`）、副作用（`useEffect`）、JSX 描述界面。会 React 的 Web 开发者上手成本低，但“写法一样”不等于“行为一样”：样式是 Yoga 布局引擎的子集（Flexbox 思想，无 CSS 层叠与选择器）、没有 DOM、事件与手势是原生事件，两者差异见 6 节。

### 3.2 老架构 Bridge：异步 JSON 消息

老架构（0.82 之前可切换、0.82 起已移除，见 3.3 节）的通信核心是一条 **Bridge**：

- JS 侧把“要调用的原生方法、参数”序列化成 JSON，通过消息队列发给原生侧；原生侧把事件与回调同样序列化发回。
- 通信是**异步批量**的：消息攒一批再发，单次调用不阻塞 JS 线程，但往返有延迟；连续高频调用（如每帧传手势坐标）会排队积压。
- 三个线程分工：JS 线程（跑 React 与业务逻辑）、原生 UI 线程（跑系统控件）、原生模块线程（跑原生模块方法）。界面更新的链路是 JS 线程算出变化 → Bridge 传消息 → 原生 UI 线程更新控件。

老架构的代价集中在两点：序列化与跨线程排队是固定开销，复杂动画与高频交互先撞上它；原生模块在启动时全部加载，启动成本随模块数增长。

### 3.3 新架构：JSI + Fabric + TurboModule

新架构分三步落地：0.76（2024 年 10 月）成为默认，0.82（2025 年 10 月）成为唯一架构、旧 Bridge 不可再启用。当前版本只有新架构，没有“开不开新架构”的选项。三个部件各解决老架构的一个问题：

| 部件 | 解决的问题 | 机制 |
|---|---|---|
| JSI（JavaScript Interface） | 序列化与异步排队的开销 | JS 与 C++ 之间直接互相持有对象引用、同步调用，不再经过 JSON 序列化与消息队列 |
| Fabric（渲染器） | 渲染管线与 React 18 并发能力脱节 | 新的渲染器：JS 侧算出的界面树以 C++ 共享对象（Shadow Tree）形式存在，原生侧直接读取；支持并发渲染，渲染优先级可调度 |
| TurboModule（原生模块） | 启动时全量加载原生模块 | 原生模块按需懒加载，第一次调用时才初始化；接口由 Codegen 从 TypeScript 类型定义自动生成原生侧的绑定代码，减少手写胶水代码 |

一句话区分：老架构是“两边写信（JSON 消息）”，新架构是“两边直接打电话（JSI 同步调用）”。新架构没有消灭跨线程通信——JS 线程与原生 UI 线程依然存在，同步调用也可能跨线程——它消灭的是序列化与无差别排队这两层固定税。重动画场景仍要实测（见 6 节）。

### 3.4 原生模块与原生组件的编写方式

系统能力或现有原生代码要接进 React Native，有两条路，写法由 Codegen 统一：

**原生模块（Native Module）——给 JS 提供“能力”**：如调用原生 SDK、读写系统服务、执行耗时计算。标准流程是：先写一份 TypeScript 接口定义（Spec），声明方法名、参数与返回值类型；Codegen 据此生成各平台的原生接口骨架；再在 Android（Java/Kotlin）与 iOS（Objective-C/Swift）分别实现该接口。JS 侧像调普通异步函数一样调用它，返回值经 JSI 直接传递。0.88 起，Java 端 TurboModule 可直接收发 JS 的 `ArrayBuffer`，二进制数据不再需要先转字符串或数字数组。

**原生组件（Native Component / Fabric Component）——给 JS 提供“控件”**：如把原生地图、视频播放器、自定义图表嵌进 React 树。同样先写 TypeScript 的 Props 与事件定义，Codegen 生成原生侧骨架，再在原生侧实现控件并把属性映射到原生视图的属性、把原生事件映射为 JS 事件。Fabric 下的原生组件参与同一棵 Shadow Tree，布局与手势与内置组件走同一管线——这是它与老架构下“原生组件是外挂”的根本区别。

两条路的共同点：接口先行（TypeScript Spec 是唯一事实来源）、双平台各实现一次、Codegen 负责生成胶水代码。常见错误是跳过 Spec 直接手写原生绑定：能跑，但升级时最先坏的就是手写部分。

### 3.5 与 Flutter 的对照

两条路线在“界面是谁画的”上已经由 [跨平台框架选型](02-cross-platform.md)定性，本篇补一张实现层对照表：

| 维度 | Flutter | React Native（新架构） |
|---|---|---|
| 界面归属 | 框架自绘（Impeller 直接画） | 系统原生控件（Fabric 驱动） |
| 语言 | Dart | JavaScript/TypeScript |
| 逻辑与界面通信 | 同一进程内 Dart 代码，无桥接层 | JS 运行时与原生侧经 JSI 通信 |
| 系统能力接入 | 插件 + MethodChannel | TurboModule + Codegen |
| 外观一致性 | 双端几乎完全一致 | 各平台保留系统控件外观与行为 |
| 热更新 | 热重载（开发期）；发布后热更新需第三方方案 | Fast Refresh（开发期）；发布后热更新需第三方方案（CodePush 类服务） |
| 团队背景 | Dart/原生背景上手顺 | Web/React 背景上手顺 |

对照的结论不是“谁更好”，而是“代价付在哪”：Flutter 的代价在系统行为差异与插件覆盖度（见 [Flutter 入门与 Widget 体系](08-flutter-widgets.md)）；React Native 的代价在 JS 与原生之间的通信成本与双端原生知识（原生模块要同时懂 Android 与 iOS）。选型结论本身见 02 篇，本篇不重复。

## 4. 分类

按“代码跑在哪”把 React Native 应用的构成要素分四类：

- **JS 层**：React 组件、业务逻辑、状态管理（React 自带 Hooks、Redux、Zustand 等，按规模选）；与 Web React 的写法相通，运行环境不同。
- **桥接层（新架构）**：JSI、Fabric、TurboModule、Codegen；应用代码不直接操作它们，但性能问题多半出在这里。
- **原生层**：Android（Java/Kotlin）与 iOS（Objective-C/Swift）实现，原生模块与原生组件的落地点；原生知识在这里是刚需，不是可选项。
- **工具层**：Metro 打包器（把 JS 打包成 bundle）、Hermes 引擎、调试工具；新项目脚手架由官方 CLI 或 Expo 提供，两者分工与取舍以官方文档为准（待核实，见未完成项）。

## 5. 典型应用

- **已有 Web/React 团队要做双端应用**：组件思想、状态管理、工具链可复用，学习成本集中在原生侧与移动端特有问题上。
- **界面要像原生、行为要跟系统走的产品**：系统控件的默认外观、无障碍、输入法、手势都直接继承，逐项验收的工作量小于自绘路线。
- **已有原生应用内嵌 React Native 页面**：个别页面用 React Native 写、其余保留原生；适合渐进迁移， Brownfield 集成细节以官方文档为准。

## 6. 限制与常见误解

常见性能坑（按出现频率排序，排查思路见 [移动端性能与适配](03-performance-adaptation.md)）：

1. **JS 线程被堵**：大数据 JSON 解析、复杂计算、同步存储读写放在 JS 线程，界面直接卡住——JS 是单线程，堵住它等于堵住一切。解法是拆分计算、放原生侧或后台线程、避免首屏同步重活。
2. **高频跨线程通信**：手势、滚动、动画每帧都向 JS 线程发事件再等回执，往返延迟直接吃掉帧预算。新架构下优先用原生侧驱动的动画（如 Reanimated 类方案）或手势库，让动画在原生线程闭环，不经过 JS 线程。
3. **列表渲染失控**：长列表不用 `FlatList` 的虚拟化、每项都重新创建组件、图片不做尺寸与缓存控制，内存与帧率一起崩。列表是大头，先治列表。
4. **不必要的重渲染**：父组件状态一变整树重渲染，大列表、深树最先遭殃。解法是拆小组件、`React.memo`、状态下放——与 Web React 的优化思想相同。
5. **启动时全量初始化**：JS bundle 越大、启动时初始化的模块越多，冷启动越慢。TurboModule 已解决原生模块侧的懒加载，JS 侧仍要自己做懒加载与分包。

常见误解：

- “React Native 就是套壳网页。”错：新架构下界面是真正的原生控件，不是 WebView；但 JS 线程与原生线程的通信成本仍在，重动画场景要实测。
- “新架构上线就自动变快。”错：新架构去掉的是固定税，不是应用自己的性能债；JS 线程被堵、列表失控、动画走 JS 线程这些问题换架构也一样存在。
- “会 React 就等于会 React Native。”错：样式子集、无 DOM、原生模块、双端原生知识、移动端性能模型，都是 Web React 没有的部分。
- “老架构的优化经验可以直接用。”错：0.82 起老 Bridge 已不存在，围绕 Bridge 的优化（如批量消息、桥接层缓存）已失效；遇到 0.82 之前的旧资料要先核对版本。

## 7. 小结

React Native = JS/React 写界面描述 + Hermes 跑逻辑 + Fabric 驱动真正的原生控件 + TurboModule 按需提供系统能力。新架构（JSI/Fabric/TurboModule）自 0.82 起是唯一架构，消灭了老 Bridge 的序列化税，但 JS 线程被堵、高频通信、列表失控这三类性能坑仍在。它的优势是原生体验与 Web 团队复用，代价是双端原生知识与通信成本。
