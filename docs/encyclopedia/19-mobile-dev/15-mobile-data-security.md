# 数据存储与传输安全

## 1. 技术原理

移动应用的数据安全问题可以归结为一句话：**数据离开应用的那一刻起，就不再由应用控制**。数据会经过三种状态：存在设备上（静态）、在网络上传输（传输中）、在内存里被使用（使用中）。本篇讲前两种：静态存储与传输。核心原则只有两条：第一，分级——不是所有数据都值得同等保护，保护强度要与数据敏感程度匹配；第二，密钥与数据分离——加密本身不难，难的是密钥放在哪里才安全。

与第 14 篇的关系：加固解决“代码难读、篡改可发现”，本篇解决“数据即使被拿到也难用、传输即使被看到也难懂”。两者是同一纵深防御的不同层。

## 2. 合法研究范围

本篇只讨论应用开发者为保护自有应用及其用户数据而采取的防御措施。研究与测试只应在自有应用、自有设备、授权系统或隔离靶场内进行。未授权访问、截取或解密他人的数据与通信是违法行为，本文不提供相关指导；任何针对他人应用的数据提取、通信解密或绕过行为均不在本文讨论范围内。

## 3. 实验环境

- 环境：自有应用在自有设备或隔离测试环境中运行；服务端为自有或授权的测试服务。
- 软件与版本：Android Keystore、Jetpack Security、iOS Keychain、网络安全配置（Network Security Config）与证书锁定库的具体版本以官方发布为准（待核实）。
- 权限要求：无需特殊权限；存储与传输验证在自有设备上完成，不涉及他人数据。

## 4. 风险

- **明文存敏感数据**：口令、令牌、身份证号、支付信息以明文写进本地文件，一旦设备丢失或备份泄露即直接可用。规避：按第 5 节分级存储，敏感数据加密后存、密钥进系统密钥库。
- **密钥与数据放一起**：加密用的密钥硬编码在代码里或与密文存在同一个文件里，等于把锁和钥匙挂在一起。规避：密钥进 Keystore/Keychain，永不进代码与仓库。
- **传输被窃听或篡改**：HTTP 明文传输、HTTPS 配置不当、证书校验被弱化，都会让中间人看到或改掉传输内容。规避：全站 HTTPS + 证书锁定 + 服务端校验（见第 6 节）。
- **日志与备份泄露**：敏感数据写进日志、崩溃上报、系统备份或应用间共享文件，等于从侧门把数据送出去。规避：日志脱敏、备份策略收紧（见第 7 节）。
- **旧数据残留**：卸载重装、版本升级后旧的明文数据仍留在设备上。规避：升级时做数据迁移与清理，敏感数据有明确的生命周期与过期删除。

## 5. 本地存储分级

本地存储不是“一个数据库装所有东西”，而是按敏感程度分层：

| 级别 | 数据举例 | 存放方式 |
|---|---|---|
| 公开 | 界面偏好、主题、语言设置 | 普通 SharedPreferences / DataStore（明文可接受） |
| 内部 | 缓存、非敏感业务数据 | 应用私有目录、Room 数据库；随应用卸载清除 |
| 敏感 | 登录令牌、刷新令牌、支付相关信息 | 加密存储，密钥进系统密钥库 |
| 高敏感 | 支付口令、生物识别相关、加密主密钥 | 尽量不存本地；必须存时进系统密钥库 + 硬件支持（如设备支持则用硬件-backed 密钥） |

### 5.1 SharedPreferences 与 DataStore：放配置，不放秘密

SharedPreferences（键值存储）与 DataStore（其继任者，支持协程与类型安全）适合存“应用的配置与偏好”，不适合存秘密。两者的默认存储是应用私有目录下的明文文件：系统沙箱能挡住其他普通应用，但挡不住拿到设备文件访问权的人。把登录令牌以明文写进 SharedPreferences，是最常见的移动端数据泄露形态之一。

规则很简单：**SharedPreferences / DataStore 只放“泄露了也无所谓”的东西**。凡是“泄露了能冒充用户、能花用户的钱、能看到用户隐私”的数据，都不属于这一层。

### 5.2 Keystore（Android）与 Keychain（iOS）：密钥的家

Android Keystore 与 iOS Keychain 是系统提供的密钥保管服务，设计思想是：**密钥材料不离开系统保管区，应用只能“请系统用这把钥匙加密/解密”，而拿不到钥匙本身**。支持的设备上，密钥还可以由硬件安全模块（如 StrongBox、Secure Enclave）背书，密钥材料连操作系统内核都接触不到。

使用要点：

- 密钥在 Keystore/Keychain 内生成，不从外部导入明文密钥；需要跨设备恢复的场景，密钥的备份与恢复要走专门的加密备份通道，而不是把密钥明文写进备份。
- 给密钥设定使用条件：例如要求设备已设锁屏、要求每次使用时用户认证（指纹/面容），密钥被盗用的窗口随之缩小。
- 密钥要能轮换与吊销：用户改密、设备丢失、令牌泄露时，旧密钥应能失效，而不是“一把钥匙用终身”。
- iOS 与 Android 的密钥库 API 不同，但思想一致：跨平台框架（见第 2 篇选型）通常要通过平台通道或专用库分别接入，不能假设“一套代码自动获得同等保护”。

### 5.3 敏感数据加密存储

敏感数据的正确存放姿势是两层结构：**数据用随机生成的数据密钥加密，数据密钥再用 Keystore/Keychain 里的主密钥加密**（信封加密）。这样即使加密后的数据文件被拿到，没有主密钥也解不开；而主密钥不出密钥库，攻击者要同时攻破两处才能拿到明文。

实践要点：

- 优先使用平台官方的加密存储封装（如 Jetpack Security 提供的加密文件与加密偏好存储），而不是自己拼加密算法；自己拼容易在填充、随机数、完整性校验上出错。Jetpack Security 各组件的最新状态与推荐用法以官方发布为准（待核实）。
- 加密要同时保证机密性与完整性（带认证的加密模式，如 AES-GCM），只加密不校验完整性，篡改后的密文可能在解密时造成非预期的行为。
- 敏感数据在内存里也尽量短命：用完即清，不长期缓存在静态变量里；内存中的敏感字符串在部分语言里难以主动擦除，要靠“少留、短留”控制风险。
- 数据库文件（Room/SQLite）整体加密是另一层选择，适用于“整库都敏感”的场景；与字段级加密的取舍按数据分布定，不必全库加密只为保护两三个字段。

## 6. 传输安全：HTTPS 与证书锁定

### 6.1 HTTPS：默认，不可降级

所有网络请求默认走 HTTPS，不留 HTTP 例外。HTTPS 在传输层做两件事：加密（中间人看不到明文）与身份认证（客户端确认自己连的是真正的服务器，而不是冒充者）。明文 HTTP 的请求在公共 Wi-Fi、运营商网络等环境下可被直接读取与篡改，没有“只是个公开接口所以无所谓”的例外——即使是公开数据，篡改后的内容也可能诱导用户做出错误操作。

配置要点：

- 服务端启用 HSTS（严格传输安全），告诉客户端“今后只用 HTTPS 连我”，防止首次连接被降级到 HTTP。
- 客户端不接受自签名证书、不关闭证书校验、不写“信任所有证书”的调试代码并带到 release 构建。Android 的网络安全配置（Network Security Config）可以集中声明“只允许 HTTPS、只信任系统证书”，是比散落在代码里的校验更可靠的落点。
- TLS 版本与密码套件跟随系统与服务端默认，不手动降级到旧版本；具体版本以官方发布为准（待核实）。

### 6.2 证书锁定（Certificate Pinning）：多一道身份确认

HTTPS 的身份认证依赖证书颁发机构（CA）体系：如果某个 CA 被攻破或误发证书，攻击者就能拿到一张“看起来合法”的证书。证书锁定是在客户端额外固定“这台服务器应该用哪一张证书（或哪一个公钥）”，连接时只认锁定的证书，即使证书链本身合法、但与锁定值不符，也拒绝连接。

证书锁定的原理与取舍：

- **锁公钥，不锁整张证书**：证书会过期换发，公钥在续期时通常保持不变；锁公钥比锁整张证书更耐换证，误伤更少。
- **留备用锁定值**：至少准备两个锁定值（当前公钥 + 备用公钥），防止主密钥轮换时所有旧版本应用同时断连。
- **锁定失效要有预案**：证书轮换、应急换发时，旧版本应用的锁定值会过期；预案包括应用内配置更新通道、服务端配合的灰度轮换、以及锁定失败时的明确上报而非静默放行。
- **锁定不是万能**：它防的是“证书体系被滥用”，不防“服务器本身被攻破”与“客户端被篡改”。锁定的校验逻辑同样在客户端，同样受第 14 篇所述的客户端限度约束。

实现上，证书锁定可以通过网络安全配置声明，也可以通过 HTTP 客户端库（如 OkHttp 的 CertificatePinner）配置；两种方式的适用版本与具体写法以官方文档为准，本文不锁定小版本（示例未实测）。

### 6.3 传输层的其他防线

- **令牌与会话**：登录令牌只通过 HTTPS 传输、只存加密存储（见第 5 节）、设有效期、支持服务端吊销；令牌泄露时的止血能力比“令牌永不泄露”的假设更重要。
- **敏感操作二次确认**：支付、改密、换绑等操作在服务端做二次校验（如短信/应用内确认），不只依赖“请求里带了令牌”。
- **服务端不信任客户端**：服务端对每个请求重新做身份与权限校验，不因为“请求来自官方应用”就放行——第 14 篇已讲过，客户端的任何声明都不可信。

## 7. 日志与备份泄露的防范

日志与备份是最容易被忽视的泄露通道，因为它们“不是正式的数据存储”，却常常装着正式数据：

- **日志脱敏**：日志里不写口令、令牌、完整身份证号、银行卡号、会话密钥。需要定位问题时，记脱敏后的标识（如令牌前几位、用户 ID 的哈希）而不是原文。release 构建的日志级别要收紧，调试用的详细日志只留在 debug 构建。
- **崩溃上报脱敏**：崩溃堆栈与上报附件同样要过脱敏，堆栈里可能夹带请求参数与界面状态；上报前检查上报内容包含哪些字段，是发布流程的一环。
- **备份策略**：Android 的自动备份与 iOS 的 iCloud 备份会把应用数据复制到云端；敏感数据应声明不参与备份（Android 的备份规则、iOS 的 Keychain 与文件保护属性按平台配置），或只备份加密后的形态。备份文件一旦泄露，等于数据换了个地方继续存在。
- **应用间共享**：通过系统分享、文件提供者（FileProvider）或剪贴板传出的数据，接收方不受本应用控制；敏感内容不走分享通道，必须走时要设有效期与最小范围，剪贴板里的敏感内容用完即清。
- **截图与录屏**：敏感页面（如支付、证件展示）应禁止截图与录屏（Android 的 FLAG_SECURE），防止用户无意中把敏感信息留在相册或投屏里。

## 8. 常见误解

- “数据在应用私有目录里就是安全的。”错：私有目录防的是其他普通应用，不防拿到设备文件访问权的人；敏感数据仍要加密。
- “用了 HTTPS 就不用管证书锁定。”错：HTTPS 防窃听，证书锁定防“合法证书被滥用”；两者是不同层的防线。
- “密钥放代码里，混淆后就看不到了。”错：混淆只改名字不加密内容，硬编码密钥在混淆后依然可被找到；密钥只能进 Keystore/Keychain（见第 14 篇的限度讨论）。
- “日志只在开发机上看得到。”错：release 构建的日志可能被读取、崩溃上报会上传、用户也可能主动导出日志发给别人；日志从写下的那一刻起就可能离开设备。
- “备份是系统的事，与应用无关。”错：备份范围由应用的备份规则决定，不声明排除，敏感数据就会跟着备份走。
