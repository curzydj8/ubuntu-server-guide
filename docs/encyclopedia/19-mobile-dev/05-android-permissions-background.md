# Android 权限与后台机制

## 1. 本章目标

读完本篇能理解：运行时权限的申请流程与一次性权限意味着什么、Android 对后台执行的限制是如何一步步收紧的（Doze、应用待机、后台服务限制）、可延迟任务与必须立即执行的任务各应走哪条路（WorkManager 与前台服务）、通知权限与精确闹钟这两项常用能力各受什么规则约束。

## 2. 背景与问题

第一篇讲过权限分普通、危险、特殊三档，第三篇讲过系统用 Doze 与应用待机桶限制后台活动。本篇把这两条线讲深：权限与后台是同一枚硬币的两面——系统把“能不能读用户数据、能不能在用户看不见时干活”的决定权，从应用手里收回到用户与系统手里。开发者要适应的不是某一个 API 的改名，而是一条演进方向：凡是用户看不见的敏感操作，都要经过用户明确同意、都要接受系统调度、都要有“被拒绝、被推迟、被收回”时的降级路径。

本篇讲机制与演进，不讲某一权限的逐项申请代码（申请代码的函数签名以官方文档为准）；权限三档的划分见第一篇，耗电与后台任务的排查思路见第三篇。

## 3. 总体架构

权限与后台约束按“谁决定”分三层（文字结构图）：

```
用户决定（运行时权限）
├── 危险权限：位置、相机、麦克风、通讯录、媒体文件等，运行时申请
├── 一次性权限：只给这一次，用完即收回
└── 特殊权限：悬浮窗、修改系统设置等，引导用户到设置页
系统决定（后台执行限制）
├── Doze（打盹）：设备静止不用时，批量推迟后台任务与网络
├── 应用待机（App Standby）与待机桶：不常用的应用，后台越受限
└── 后台服务限制：后台应用不能随意起后台服务
应用选择（合规的后台工作方式）
├── 可延迟任务 → WorkManager（系统调度，可设约束条件）
├── 用户正在感知的持续任务 → 前台服务（必须挂常驻通知）
└── 定时提醒 → 闹钟（精确闹钟需专门权限）
```

一个贯穿全篇的原则：凡是“用户看不见”的能力，系统都默认不给，应用要逐项说明理由、逐项申请、逐项接受约束。

## 4. 工作机制

### 4.1 运行时权限模型：申请、拒绝与降级

危险权限的申请流程分四步：

1. **清单声明**：先在 `AndroidManifest.xml` 里声明权限。没声明的权限申请了也不会被授予；声明了不等于授予，只是获得了“可以申请”的资格。
2. **检查是否已有**：调用前先检查是否已授予，未授予才申请；不要假设上次授予了这次还在——用户可以随时在设置里收回。
3. **运行时申请**：调用系统申请接口弹出标准对话框，由用户决定。申请前应用可以用自己的界面先说明“为什么需要这个权限”（用途说明），这一步不是系统强制的，但对通过率影响最大；用户在不理解用途时拒绝，是合理行为。
4. **处理结果与降级**：用户可能同意、拒绝、或只同意一次（见 4.2）。被拒绝后应用应降级功能或引导用户去设置页手动开启，而不是反复弹窗——反复弹窗会被系统视为骚扰，且用户在设置里勾选“不再询问”后，系统将不再弹出申请框。

还有两个机制容易被忽视：

- **权限组**：同一组的权限（如位置组内的精确位置与大致位置）有关联行为，申请其中一项可能影响另一项的授予状态，处理结果时要按单个权限逐项检查，不要按组假设。
- **权限自动重置**：长期不用的应用，其运行时权限会被系统自动收回，下次启动要重新申请。设计上不能假设“用户以前同意过，以后就一直有”；每次使用敏感能力前重新检查，是正确写法。

### 4.2 一次性权限与更细粒度的授权

Android 11 引入的一次性权限（One-time permissions）把“同意”拆成了三档：用户可以在“使用时允许”“仅本次允许”“拒绝”之间选择。选“仅本次”，权限在应用退到后台一段时间后会被系统收回，下次使用要重新申请。对开发者的直接影响是：权限检查必须放在每次使用前，不能只在应用启动时检查一次；把权限状态缓存成一个“启动时为真、以后永远为真”的布尔值，是错误写法。

同一演进方向上的其他收紧（按版本要点，细节以官方文档为准）：

- **位置精度分档**：用户可以选择只给大致位置而不给精确位置。只需要城市级位置的功能（如天气、本地资讯）应只申请大致位置；只有导航、运动轨迹这类确实需要精确位置的功能才申请精确位置。
- **媒体访问分档**：读取照片与视频从“全部媒体”收紧为可只选部分照片与视频；新项目应优先使用系统照片选择器（Photo Picker），让用户一次选出要分享的图片，而不是申请整个媒体库的读取权限。
- **后台位置单独申请**：在后台持续获取位置属于更高敏感的操作，需要单独说明理由并走单独的申请流程，不能随前台位置权限一并默认获得；后台位置的申请时机与说明要求以官方文档为准。

这些收紧的共同点是：授权粒度从“全有或全无”走向“按需、按次、按精度”，应用的功能设计也要跟着从“有权限时全功能、无权限时不可用”走向“按实际获得的授权逐级提供功能”。

### 4.3 后台执行限制的演进：系统为什么越管越严

后台限制的演进是一条单向收紧的线，每一步都是为了解决前一步留下的耗电与滥用问题：

- **Doze（打盹，Android 6.0）**：设备静止、灭屏、未充电一段时间后进入 Doze 模式，系统批量推迟后台任务、网络访问与闹钟，只在维护窗口期集中放行。应用不能假设“后台任务会按设定时间准时跑”；需要及时送达的消息应走推送通道，而不是靠后台轮询。
- **应用待机（App Standby，Android 6.0）与待机桶（App Standby Buckets）**：用户一段时间不用的应用会被系统判定为待机，限制其后台网络与任务；待机桶按使用频率把应用分档（活跃、工作集、常用、极少、受限），越不常用的档位限制越严。应用的后台配额不是固定的，而是随用户使用频率浮动的。
- **后台服务限制（Android 8.0）**：应用在后台时不能随意启动后台服务；后台服务会在系统判定下被停止。第一篇提到的“周期性任务应交给 WorkManager，而不是常驻 Service”，就是这条限制的直接结论。
- **后台启动 Activity 限制与电池优化**：后台应用原则上不能突然把界面弹到用户面前；用户可在设置里对单个应用开启或关闭电池优化，被列入“不受电池优化限制”的应用才不受 Doze 等限制——但这需要用户手动操作，应用只能引导，不能自行设置。

演进的结论只有一个：后台工作必须从“我随时能跑”改成“系统允许时才跑”，任务设计要以“可推迟、可合并、可取消”为前提（见 4.4）。

### 4.4 WorkManager 与前台服务：两条合规的后台工作路线

后台工作按“用户是否正在感知、任务是否可延迟”分两条路线，选错路线是后台类 Bug 与商店政策问题的常见来源。

**路线一：可延迟、可重试的任务 → WorkManager**

WorkManager 是官方推荐的延迟后台任务调度器，适用场景是“不要求立即执行、但要求最终执行”的任务：日志上报、数据同步、图片压缩上传、数据库清理。用法要点：

- **约束条件**：任务可声明执行条件（充电时、Wi-Fi 下、电量不低时），系统在条件满足时才执行；条件不满足时任务等待，不消耗电量硬跑。
- **重试与退避**：任务失败可按退避策略自动重试，开发者不用自己写定时重试循环。
- **一次性与周期性**：一次性任务用 `OneTimeWorkRequest`，周期性任务用 `PeriodicWorkRequest`；周期性任务的最短间隔以官方文档为准，系统不保证“每分钟准时跑一次”——要求准时性的任务不属于 WorkManager 的适用范围。

```kotlin
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .build()
    )
    .build()
WorkManager.getInstance(context).enqueue(request)
```

**路线二：用户正在感知的持续任务 → 前台服务**

前台服务适用于“用户明确知道正在进行、且需要持续运行”的任务：音乐播放、导航、运动记录、文件下载。规则是：

- **必须挂常驻通知**：启动前台服务必须同时显示一条不可清除的通知，告诉用户“这个任务正在运行”，用户可通过通知随时了解与停止它。没有通知的前台服务会被系统拒绝启动。
- **必须声明服务类型**：应用需在清单中声明前台服务的类型（如媒体播放、定位、数据同步），并申请对应的前台服务权限；类型与实际行为不符会被系统与商店政策拦截，细节以官方文档为准。
- **不是绕过限制的工具**：把本可延迟的任务包装成前台服务以求“一直跑”，属于滥用：耗电异常会被用户卸载，类型不符会被商店下架。判断标准是“用户是否正在等这个任务的结果”——在等的走前台服务，不在等的走 WorkManager。

两条路线之外的补充：需要准时提醒的用闹钟（见 4.5），需要及时送达的消息用推送；后台轮询是最后的选择，而不是默认选择。

### 4.5 通知权限与精确闹钟：两项常用能力的专门规则

**通知权限（Android 13 起为运行时权限）**：Android 13 之前，应用安装后默认可以发通知；Android 13 起，发送通知需要 `POST_NOTIFICATIONS` 运行时权限，用户拒绝后应用无法发通知。新应用应在“用户能理解通知价值的时机”申请（例如用户开启提醒功能时），而不是在首次启动时与一堆权限一起申请；被拒绝后的降级是“应用内用界面内提示代替通知”，而不是反复申请。

**精确闹钟（Exact Alarm）**：普通闹钟会被 Doze 批量推迟，适用于“大概这个时间提醒就行”的场景；精确闹钟能准时触发，但耗电代价高，因此受专门权限约束：

- Android 12 起，设置精确闹钟需要 `SCHEDULE_EXACT_ALARM` 权限，用户可在系统设置里授予或撤销。
- 只有确实需要准时触发的功能（闹钟、日历提醒）才应申请精确闹钟；“定时同步数据”“定时清理缓存”这类可延迟的任务应走 WorkManager 或普通闹钟，滥用精确闹钟会被系统与商店政策限制。
- 精确闹钟权限的授予状态可能被用户事后撤销，设置闹钟前要检查权限，权限被撤销时应降级为普通闹钟并告知用户提醒可能延迟。

通知与闹钟的共同教训：凡是“打扰用户”的能力，系统都要求单独申请、允许随时收回；产品设计要把“用户拒绝通知 / 撤销精确闹钟”当作正常分支写进流程，而不是异常分支。

## 5. 关键设计取舍

- **用户控制换隐私，代价是降级路径必须写**：每一次授权都可能被拒绝、只给一次、事后收回；功能设计要从“按实际授权逐级提供”出发，见第一篇。
- **系统调度换电量，代价是及时性不可保证**：WorkManager 与 Doze 换来的是省电，代价是任务执行时间由系统决定；要求准时性的需求要换路线（前台服务、精确闹钟、推送），而不是对抗调度。
- **前台服务换持续运行，代价是必须让用户看见**：常驻通知是前台服务的对价；看不见的持续运行在现代 Android 上没有合规路线。
- **细粒度授权换信任，代价是申请流程变长**：大致位置、部分照片、一次性授权让用户更愿意给权限，但应用要为每种授权组合写分支；“全要”式的一次性申请通过率最低。

## 6. 分类与变体

- **按决定者分**：用户决定（运行时权限、一次性权限、通知权限）、系统决定（Doze、待机桶、后台服务限制）、应用选择（WorkManager、前台服务、闹钟、推送）。
- **按任务时效分**：可延迟最终执行（WorkManager）、用户正在等待的持续任务（前台服务）、准时提醒（精确闹钟）、及时送达（推送）。
- **按权限敏感度分**：普通权限（安装时授予）、危险权限（运行时申请）、特殊权限（引导用户到设置页）、前台服务类型与精确闹钟等专项权限（单独声明与申请）。

## 7. 应用与限制

- 适用：任何需要读取用户数据或在后台工作的 Android 应用；本篇的两条路线（WorkManager / 前台服务）是后台任务设计的默认分法。
- 不适用：把后台限制当作“可以绕过的障碍”——对抗系统限制的写法（如常驻前台服务伪装、反复申请权限、引导用户关闭电池优化）会被商店政策与用户双重惩罚；厂商定制系统对后台、权限、电池优化的实现各有加严，见第三篇，同一功能在不同品牌机型上表现可能不同，发布前要在目标品牌机型上逐项验收。
- 本篇所述版本演进与 API 用法均为机制级描述，未经真机实测验证；具体权限名称、申请流程与版本行为以官方文档为准，本文不锁定未经核实的小版本细节。

## 8. 常见误解

- “用户同意过一次，权限就永远有了。”错：一次性权限会过期、长期不用会被自动重置、用户可随时收回，每次使用前都要重新检查。
- “后台服务可以一直在后台跑。”错：Android 8.0 起后台服务受严格限制，周期任务应走 WorkManager，见第一篇与第三篇。
- “用前台服务就能绕过后台限制。”错：前台服务必须挂通知、声明类型、与用户正在感知的任务对应，滥用会被商店政策拦截。
- “通知权限申请一次就行，拒绝了再弹几次用户就会同意。”错：反复弹窗会被系统视为骚扰，用户勾选“不再询问”后系统不再弹框；正确做法是降级功能或引导去设置页。
- “精确闹钟和普通闹钟只是精度不同。”错：精确闹钟是需要专门权限的高耗电能力，只有准时提醒类功能才应申请，可延迟的任务应走 WorkManager。
