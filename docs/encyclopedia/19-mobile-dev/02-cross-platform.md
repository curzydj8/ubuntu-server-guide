# 跨平台框架选型

## 1. 一句话定义

跨平台框架选型，就是在“一份代码跑多个平台”与“每个平台体验做到最好”之间，按产品需求、团队能力与长期维护成本，选出最合适的那条路线的方法。

## 2. 为什么需要它

一个产品通常要同时上 Android 与 iOS。原生双写意味着两套代码、两套 UI、两次修 Bug、两个发布流程，成本接近翻倍。跨平台框架承诺“一套代码、双端运行”，但这份“节省”不是免费的：它在渲染方式、系统能力、升级节奏上各有代价。选型选错，后期要么被框架的天花板卡住，要么为了一处平台特性写大量桥接代码，省下的成本又吐回去。选型不是“哪个框架最火”，而是“哪个代价你的产品付得起”。

## 3. 核心含义

先分清三条路线在“界面是谁画的”这个根本问题上的区别：

- **原生**：界面由系统自己的 UI 框架画（Android 的 View/Compose、iOS 的 UIKit/SwiftUI），语言也是系统首选语言（Kotlin、Swift）。系统能力零损耗，代价是双写。
- **自绘引擎型**：以 Flutter 为代表。界面不借用系统控件，由自带渲染引擎（Impeller）直接画到画布上，语言是 Dart。优点是双端长得完全一致、不受系统控件差异影响；代价是包体积较大、对系统最新控件风格的跟进要等框架适配、无障碍与输入法等系统集成细节偶有差异。
- **桥接原生控件型**：以 React Native 为代表。用 JavaScript/TypeScript（React 写法）描述界面，运行时把描述翻译成真正的系统原生控件，语言是 JavaScript/TypeScript。优点是界面就是原生控件、Web 团队上手快；代价是 JS 与原生之间的桥接层有通信与性能成本，复杂动画与手势要格外小心。
- **共享逻辑型**：以 Kotlin Multiplatform（KMP）为代表。不共享界面，只共享业务逻辑、网络、数据层，界面仍各写各的原生。优点是核心逻辑一份代码、界面体验零损耗；代价是“跨平台”只省了逻辑层，界面工作量一点没省，适合已有原生团队、想复用逻辑而不想牺牲体验的产品。

一句话区分：Flutter 省界面，React Native 省界面且借原生控件，KMP 只省逻辑，原生什么都不省但什么都不丢。

## 4. 分类

按共享程度分四档：

| 路线 | 共享内容 | 界面归属 | 典型代表 |
|---|---|---|---|
| 原生双写 | 无 | 各平台原生 | Kotlin + Swift |
| 自绘引擎 | 界面 + 逻辑 | 框架自绘 | Flutter |
| 桥接原生控件 | 界面描述 + 逻辑 | 系统原生控件 | React Native |
| 共享逻辑 | 仅逻辑层 | 各平台原生 | Kotlin Multiplatform |

另有一类“一次编写、编译到多端”的补充路线（如基于 Web 技术的混合壳、PWA 思路），本质是把网页装进应用壳：适合内容展示类产品，不适合重交互、重动画、重系统能力的产品，本篇不把它与上面四档并列，只在选型方法中作为“先问是不是必须做应用”的前置问题。

## 5. 典型应用

- **内容与工具类、双端快速上线**：Flutter、React Native 都是合理选择；团队有 Web 背景选 React Native，有 Dart 或新团队选 Flutter。
- **已有原生应用、想复用核心逻辑**：KMP。已有 Android 团队想把逻辑复用到 iOS，又不愿重写界面时最合适。
- **重系统能力（后台、传感器、系统级集成）或极致性能（大型游戏、专业音视频）**：原生。游戏本身另有引擎路线（见 21 域），不在本篇讨论。
- **原型验证、内部工具**：选团队最熟的路线，不必为“未来可能的需求”提前支付跨平台的学习成本。

## 6. 限制与常见误解

- “跨平台等于一套代码零平台代码。”错：所有跨平台路线都有平台相关代码——权限申请、推送、内购、深层链接、原生模块接入都要按平台写，占比通常在 5%–20% 之间，取决于产品对系统能力的依赖程度。
- “Flutter 画的界面和原生一模一样。”错：视觉上可以接近，但系统级行为（无障碍读屏顺序、输入法联动、系统手势、最新设计风格跟进）仍有差异，需要逐项验收，不能只看截图。
- “React Native 就是套壳网页。”错：新架构（Fabric 渲染器 + TurboModule）下界面是真正的原生控件，不是 WebView；但 JS 线程与原生线程的通信成本仍在，重动画场景要实测。
- “KMP 是 Flutter 的替代品。”错：两者解决的问题不同——KMP 不解决“界面写一次”，Flutter 不解决“已有原生代码复用逻辑”。拿它们直接对比“哪个好”是问题本身错了。
- “选型定一次就不用改。”错：框架升级节奏很快（React Native 约每两个月一个小版本，且只维护最近 3 个小版本系列），选型时要把“每年几次升级”的人力算进去；长期不升级的跨平台项目，升级成本会一次性爆发。

## 7. 选型方法（按顺序问五个问题）

1. **是不是必须做应用？** 纯内容展示先考虑响应式网站（见 03 域），不要为了“有个 App”而做 App。
2. **系统能力依赖有多深？** 后台、传感器、系统集成越深，越偏向原生；越浅，跨平台越划算。
3. **团队现有什么？** Web 团队偏 React Native，Android 团队偏 KMP 或 Flutter，有双端原生团队则原生本身就是选项。
4. **体验天花板在哪？** 动画、帧率、无障碍、平台最新设计风格，哪一项是产品的核心卖点，就按那一项的最高要求选。
5. **维护节奏付得起吗？** 查框架的发布与支持政策（例如 React Native 只维护最近 3 个小版本），把升级人力写进计划，而不是留给“以后再说”。

走完五问仍拿不准时，做最小验证：用候选框架各做一个“最难的界面 + 最难的系统能力调用”，在目标机型上实测帧率与行为，再定——不要只看官方演示。

## 8. 小结

跨平台没有银弹：Flutter 省界面、React Native 借原生控件、KMP 只省逻辑、原生什么都不丢。选型按产品需求、团队能力、维护成本五问判定；定不下来时，用最难的界面与系统能力做最小验证再定。
