# iOS 应用生命周期与沙盒

## 1. 本章目标

读完本篇能理解：iOS 应用从启动到退出的状态机是怎样的、Scene 是什么、沙盒把每个应用的数据隔在哪些目录里、后台能做什么与不能做什么、权限与隐私清单管住了什么。

## 2. 背景与问题

手机上的应用随时会被打断：来电话、切去回消息、系统内存紧张、用户锁屏。iOS 的整套设计就是围绕这几个现实展开的：用生命周期状态机管理“前台、后台、被挂起、被终止”；用沙盒把每个应用的数据隔开，一个应用默认读不到另一个应用的文件；用后台模式与任务调度管住后台耗电；用权限与隐私清单管住敏感数据。理解这些边界，比记住某个 API 更重要——越界的写法不是“跑不起来”，而是“审核不过”或“系统悄悄杀掉”。

本篇讲 iOS 原生应用的生命周期与沙盒概念，语言与界面见本域上一篇；Android 的对应概念见本域第一篇，性能与后台的关系见本域第三篇。

## 3. 总体架构

iOS 应用的运行结构（文字结构图）：

```
应用进程（每个应用独立进程）
├── App（应用级入口，@main 标记，持有应用级状态）
├── Scene（界面级会话：一个应用可有多个 Scene，如 iPad 分屏多窗口）
│   ├── Window（窗口，承载视图层级）
│   └── View 层级（SwiftUI 的 View / UIKit 的 UIViewController）
├── 沙盒（每个应用独立的文件系统区域）
│   ├── Bundle（应用包，只读：代码与资源）
│   ├── Documents（用户数据，可备份）
│   ├── Library（应用支持文件：Caches、Preferences 等）
│   └── tmp（临时文件，系统可随时清理）
└── 系统服务（通过受控接口访问：推送、定位、相机、相册、健康等）
    └── 每次访问敏感能力都要过权限检查与隐私清单声明
```

两个要点决定了后面的一切：第一，生命周期是状态机，状态变化由系统回调通知，应用不能假设自己一直在前台；第二，沙盒隔离是操作系统层面的，应用间共享数据要走系统提供的标准通道，不是直接读对方文件。

## 4. 工作机制

### 4.1 App 生命周期与 Scene：状态机，不是流程图

iOS 应用在任何时刻只处于一个执行状态，状态变化由系统回调通知。应用级状态（以 SwiftUI 的 `ScenePhase` 与 UIKit 的 `UIApplicationDelegate` 回调描述）大致是：

```
未运行（Not Running）：进程不存在
启动 → 前台活跃（Active）：正在运行，可接收触摸与事件
切走（仍可见，如来电横幅、控制中心）：前台非活跃（Inactive，过渡态）
切后台：后台运行（Background，短暂执行收尾工作）
挂起（Suspended）：进程在内存中，但不执行代码，不耗电
终止（Terminated）：进程被系统回收或用户上滑关闭
```

关键理解有三点：

- **进入后台后应用只有很短的收尾时间**。切到后台时，系统给应用一段有限时间完成保存状态、停止任务等收尾工作，超时会被强制挂起。重要状态不能等“退出时再保存”，要在进入后台的回调里及时持久化。
- **挂起不等于终止，终止不等于崩溃**。挂起的应用占内存但不执行代码，系统内存紧张时会先杀挂起的应用；被杀时不保证再给回调，所以“退出时保存”不是可靠写法。认为“进程被杀是异常”的写法，在 iOS 上同样是错误写法。
- **Scene 是界面会话，不是应用本身**。iPad 上一个应用可以同时开多个窗口（多 Scene），每个 Scene 有自己的生命周期（`ScenePhase`：active / inactive / background）。应用级状态放 App 层，界面级状态放 Scene 层；把多窗口共用的状态误放到单个 Scene 里，分屏时就会出现数据错乱。iPhone 上通常只有一个 Scene，但代码仍应按 Scene 模型写，不要假设“一个应用就是一个窗口”。

SwiftUI 中观察 Scene 阶段的写法（示例未实测）：

```swift
@main
struct MyApp: App {
    @Environment(\.scenePhase) private var scenePhase

    var body: some Scene {
        WindowGroup {
            ContentView()
        }
        .onChange(of: scenePhase) { _, newPhase in
            if newPhase == .background {
                // 进入后台：保存未持久化的状态
            }
        }
    }
}
```

### 4.2 沙盒目录结构与数据隔离

每个 iOS 应用只能访问自己的沙盒目录，系统按用途划分了几个标准位置：

- **Bundle（应用包）**：应用本身的代码与资源，只读。不要尝试往 Bundle 里写文件——运行时写不进去，正确做法是把可变数据放到下面的目录。
- **Documents（`Documents/`）**：存放用户生成的数据与用户能感知的文件（如用户创建的文档、导出的文件）。该目录默认参与 iCloud/设备备份；用户通过“文件”应用可以看到这里的内容（需在配置中声明支持）。
- **Library（`Library/`）**：存放应用的支持文件。常用子目录：`Caches/`（缓存，可重建的数据，系统在空间紧张时可清理，不参与备份）、`Application Support/`（应用运行需要但用户不直接操作的数据）、`Preferences/`（偏好设置，通常由 `UserDefaults` 管理，开发者一般不直接读写该目录下的文件）。
- **tmp（`tmp/`）**：临时文件目录，存放用完即弃的中间文件，系统可能在应用不运行时清理，不要把需要长期保存的数据放这里。

数据隔离的要点：

- **应用之间默认互不可见**。一个应用读不到另一个应用的沙盒目录；共享数据要走系统通道：App Groups（同一开发者的多个应用/扩展共享一块容器）、系统分享（Share Extension、文件选择器）、粘贴板、URL Scheme/通用链接唤起、iCloud 容器。
- **扩展（Extension）有自己的沙盒**。小组件、分享扩展等与主应用进程不同，数据共享要走 App Groups 共享容器，而不是假设能直接读主应用的目录。
- **备份与恢复要按目录语义放数据**。能重建的缓存放 `Caches`、不要进备份；用户数据放 `Documents`；放错位置的后果是备份体积膨胀、恢复后缓存过期、审核时被指出不符合数据存储规范。

### 4.3 后台模式与 Background Tasks：能做什么由系统定

iOS 对后台执行有明确限制：应用切到后台后默认很快被挂起，继续执行需要声明后台模式，且每种模式的执行条件与时长都由系统决定：

- **后台模式（Background Modes）**：在应用配置（Capabilities/Info.plist）中声明，如音频播放、定位更新、VoIP、后台获取（Background Fetch）、远程通知、蓝牙等。声明了模式不等于“可以一直跑”——系统按模式给的权限仍然有限度，例如后台定位要持续有意义地使用，滥用会被系统限流与用户投诉。
- **Background Tasks 框架**：用于“稍后在后台执行一次有限任务”，分两类：应用刷新任务（`BGAppRefreshTask`，如定时拉取新内容）与处理任务（`BGProcessingTask`，如数据库维护、备份，需要设备充电且空闲等条件）。任务由系统按电量、网络、使用习惯调度执行，应用不能保证“每小时准时跑一次”；任务执行有时长上限，超时会被系统终止。
- **推送唤醒**：静默推送（Silent Push）可以唤醒应用在后台处理数据，但频率受系统节流，短时间内大量静默推送会被延迟或丢弃；不要把静默推送当成可靠的定时器。
- **前台服务式的常驻后台不存在**：与 Android 的前台服务不同，iOS 没有“挂个通知就能一直跑”的通用机制；需要持续后台能力（如导航、音乐播放）要走对应的后台模式，且必须有真实的用户场景支撑，伪装场景会被审核拒绝。

后台设计的经验是：先问“这件事能不能等用户下次打开再做”，能等就不要放后台；必须放后台的，用系统提供的任务框架申报，让系统调度，而不是自己想办法常驻。

### 4.4 权限模型与隐私清单要点

iOS 的权限模型是“按能力逐项申请、用户逐项决定”：

- **敏感能力逐项申请**：相机、麦克风、相册、定位、通讯录、日历、健康、蓝牙、本地网络、语音识别等，每项都要在首次使用前向系统申请，系统弹出标准弹窗，用户可以允许、拒绝或选择限定范围（如相册“选中的照片”、定位“使用时允许/仅一次/永不”）。
- **申请前要说明用途**：每个权限都要在配置里写用途说明（Usage Description），弹窗会把这段话展示给用户；说明不清、与实际用途不符，会被审核打回。申请时机也有讲究：在用户真正需要该功能时再申请，而不是启动时一次性全弹出来；被拒绝后不应反复弹窗，而应降级功能或引导用户去设置页手动开启。
- **权限可以被事后收回**：用户可以在设置里随时改权限，长期不用的应用权限也可能被系统提示收回。功能设计要从“有权限时增强、无权限时可用”出发，不能假设权限一旦给了就一直在。
- **隐私清单（Privacy Manifest）与营养标签**：Apple 要求应用提供隐私清单，声明收集的数据类型、用途与是否用于追踪；用到特定系统 API（如读取文件时间戳、系统启动时间等“指纹”相关 API）时还需在清单中声明使用理由。隐私清单与 App Store 的隐私标签要一致，不一致会被审核指出。第三方 SDK 的数据收集行为也要纳入清单，不能只写自己的部分。
- **App Tracking Transparency（ATT）**：跨应用/跨网站追踪用户（如广告标识符 IDFA）必须先弹 ATT 授权框，用户拒绝后不得用其他手段变相追踪；未声明追踪又实际追踪，是审核高风险项。

## 5. 关键设计取舍

- **沙箱换安全，代价是共享要走标准通道**：应用间不能直接读对方文件，分享数据要走 App Groups、系统分享或 iCloud；绕过沙箱的写法在正常分发渠道不可行。
- **后台限制换电量与体验，代价是后台任务要重构**：从“常驻后台”转向系统调度的任务与推送，任务的及时性由系统决定，应用不能保证准时执行。
- **逐项权限换隐私，代价是降级路径必须写**：没有“用户一定同意”的假设，功能设计要从“有权限时增强、无权限时可用”出发。
- **多 Scene 换多窗口能力，代价是状态分层要清晰**：应用级与界面级状态混放，单窗口时看不出问题，多窗口时立刻错乱。

## 6. 分类与变体

- **按生命周期回调分**：SwiftUI 路线用 `ScenePhase` 与 `.onChange` 观察状态；UIKit 路线用 `UIApplicationDelegate`/`UISceneDelegate` 回调；两种路线描述的是同一套状态机，只是入口不同。
- **按后台任务分**：即时收尾（进入后台的短暂执行）、定时刷新（`BGAppRefreshTask`）、耗时处理（`BGProcessingTask`，需充电空闲条件）、持续能力（音频、定位等后台模式）。
- **按数据存放分**：用户数据（Documents，可备份）、可重建缓存（Caches，不备份）、应用支持文件（Application Support）、临时文件（tmp，随时可清理）。

## 7. 应用与限制

- 适用：需要完整 iOS 系统能力（后台任务、推送、系统分享、扩展）的产品；对隐私合规、审核通过率有要求的产品。
- 不适用：把 iOS 后台当成服务器常驻进程用——系统不会允许；把沙盒当成可自由读写的文件系统用——跨应用读取与写入 Bundle 都会失败。
- 本篇只讲生命周期、沙盒与权限的原理与要点；具体 API 调用与审核细则以 Apple 官方文档与 App Store 审核指南为准；性能与后台的关系见本域第三篇。

## 8. 常见误解

- “应用退到后台还会继续跑代码。”错：默认很快被挂起，不执行代码；继续执行需要声明后台模式或提交 Background Tasks，且执行条件与时长由系统决定。
- “把文件写到应用目录里，别的 App 就能读到。”错：沙盒隔离是系统级的，跨应用共享要走 App Groups、系统分享等标准通道。
- “缓存放 Documents 也没关系。”错：Documents 参与备份，缓存进备份会膨胀备份体积、拖慢恢复；可重建的数据应放 Caches。
- “权限申请一次就永久有效。”错：用户可以随时收回，系统也可能提示收回长期不用的权限，降级路径是必写项。
- “隐私清单只是走个形式。”错：清单与隐私标签、第三方 SDK 行为、ATT 授权要一致，不一致会被审核打回。
