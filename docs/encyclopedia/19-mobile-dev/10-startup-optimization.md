# 启动优化与卡顿排查

## 1. 一句话定义

启动优化是把应用从用户点击图标到首屏可交互的时间压短；卡顿排查是找出主线程被堵、绘制过重或 GC 打断帧节奏的原因，并按证据逐项消除。

## 2. 为什么需要它

启动与卡顿是用户最先感知、也最容易放弃的体验：启动多等一秒，流失就多一分；滑动一卡，用户立刻觉得“这应用不行”。更麻烦的是，这两类问题在开发机上往往看不见——开发机是新机、刚装的应用、没有真实数据，只有在低端机、冷启动、真实账号数据下才会暴露。没有拆解与排查方法，优化只能靠“感觉上快了一点”。

本篇是 [移动端性能与适配](03-performance-adaptation.md)（本组第三篇，总论）的纵深：总论讲了启动分三种、掉帧分三种来源，本篇讲冷启动的时间具体花在哪、优化手段怎么做取舍、卡顿如何用工具定位到证据。

## 3. 冷启动流程与耗时拆解

冷启动是进程不存在时从零开始的完整链路，大致分五段（各段占比因应用而异，以下是拆解思路，不是固定比例）：

```
点击图标
  → ① 进程创建与运行时启动：系统 fork 进程、加载 ART/Dalvik 运行时、加载应用代码
  → ② Application 初始化：Application.onCreate() 中各 SDK 与组件的初始化
  → ③ 首屏 Activity 创建：onCreate/onStart/onResume、布局加载（inflate）
  → ④ 首屏数据准备：读本地数据、发起网络请求、解析结果
  → ⑤ 首屏渲染与可交互：测量、布局、绘制上屏，响应用户操作
```

耗时拆解的第一步是**分段计时**：只看“总启动耗时”一个数是没法优化的——不知道慢在第几段，就不知道该动哪一段。Android 上可以用系统启动时间戳（如进程启动时刻）与各关键点打点相减，iOS 上有类似的启动阶段划分（进程启动到 main 入口、再到首屏渲染），具体计时接口以官方文档为准。

五段各自的典型耗时来源：

- **① 进程与运行时**：代码量与类数量越大，类加载与验证越慢；多 dex、首屏就加载大量类，都会拖慢这一段。这一段应用能做的主要是减量——首屏不需要的类不要在启动路径上加载。
- **② Application 初始化**：最常见的耗时大头。各 SDK（统计、推送、崩溃上报、配置、数据库）如果在 `Application.onCreate()` 里排队同步初始化，时间直接叠加。判断标准很简单：首屏渲染不需要它，现在就不要初始化它。
- **③ 首屏 Activity 创建**：布局层级越深、inflate 越慢；首屏布局里套了多层容器、又嵌了用不到的视图，都是纯成本。首屏布局应只放首屏真正要显示的东西。
- **④ 首屏数据准备**：同步网络请求、主线程读数据库、大 JSON 解析放在启动路径上，会把等待时间原样加进启动耗时。首屏数据能用本地缓存先顶上，就不要等网络回来再画界面。
- **⑤ 首屏渲染**：测量、布局、绘制本身的开销。首屏图片过大、首屏就做复杂动画，都会让“已画出来”晚于“已准备好”。

## 4. 启动优化手段

### 4.1 懒加载：首屏不需要的，延后

懒加载是启动优化的第一手段：把初始化从“启动时全做”改成“首次使用时再做”。

- **SDK 懒初始化**：统计、推送、分享、支付等 SDK，首屏用不上的移到后台线程或首次调用时初始化。注意区分“初始化”与“注册”——有些 SDK 要求尽早注册回调（如推送 token 回调），可以先注册轻量回调、重初始化延后。
- **界面懒加载**：首屏不可见的页面、弹窗、次级功能模块，不要在启动时创建；用占位或按需加载代替。
- **数据懒加载**：非首屏数据、配置、字典表，按需拉取，不要在启动时全量拉取。

懒加载的代价是“首次使用时多等一下”。取舍原则：首屏路径上的等待最贵，移到用户操作后的等待相对便宜；但不要把懒加载做成“每次打开都重新初始化”，首次初始化的结果要缓存复用。

### 4.2 预加载：把等待提前到用户看不见的时候

预加载与懒加载方向相反：把确定要用的东西提前准备好，让用户操作时直接命中。

- **启动期预加载**：在启动流程的空闲间隙（如首屏已显示、用户还在看第一眼内容时），后台预加载下一屏大概率要用的数据与图片。
- **基线配置文件（Baseline Profiles）**：把启动与常用路径的热点代码提前编译，改善冷启动后第一帧的表现。这是系统层面的预编译手段，是否生效、收益多大要按官方文档与实测数据判断，本文未实测。
- **启动页（Splash）与骨架屏**：严格说它们不是“变快”，而是“让等待可接受”——启动页缩短用户对白屏的感知，骨架屏让首屏先有结构、数据到了再填。它们的取舍见总论第 5 节：换启动速度的是首屏完整度。

预加载的红线是不要在启动关键路径上预加载：启动时后台线程抢 CPU、抢网络，反而会拖慢首屏；预加载要有上限，内存与流量成本见总论第 4.3、4.5 节。

### 4.3 启动器框架思想：把初始化排成任务图

应用变大后，初始化任务之间会出现依赖（A 初始化完才能初始化 B）与可并行性（C 与 D 互不依赖）。启动器框架的核心思想是把“排队同步初始化”改成“任务图调度”：

- **任务化**：每个初始化拆成一个任务，声明它依赖哪些任务、能不能在后台线程跑、超时怎么办。
- **拓扑排序 + 并行**：无依赖的任务并行执行，有依赖的按顺序执行，关键路径（决定首屏的最长依赖链）优先跑。
- **分阶段**：分“首屏必需”“首屏后必需”“空闲时再做”三档，首屏必需的才堵启动流程，其余两档异步跑。

这个思想在 Android 上有现成的 App Startup 库、在各大厂有自研启动器、在 Flutter/React Native 里也有对应的初始化编排写法——框架名与 API 以官方文档为准，本文讲的是通用思想：启动优化的终点不是“少做几件事”，而是“把事情按依赖与优先级排好，只让首屏必需的堵在启动路上”。

## 5. 卡顿成因与排查

总论第 4.2 节把掉帧归为三类来源，本篇把每一类展开成“特征 → 证据 → 处理”。

### 5.1 主线程阻塞：最常见，也最容易定位

主线程是唯一能碰界面的线程，帧回调也要排队等它。主线程被堵时，特征是整段卡住、点击无响应、滑动停住。

常见阻塞源：主线程做网络请求、读数据库、大 JSON 解析、大图编解码、遍历大集合、同步文件读写、锁等待。处理方向只有一个：挪出主线程——网络与数据库走后台线程或协程、图片编解码走后台、耗时计算分片或异步。判断“挪出去够不够”要看帧率是否恢复，而不是看代码“看起来异步了”。

### 5.2 过度绘制与布局过重：列表越滑越卡

过度绘制指同一像素在一帧内被反复画多次（如多层不透明背景叠加、每项都带全屏背景）。布局过重指层级过深、每项测量次数过多、每帧都创建对象。特征是列表滑动时帧率波动、越滑越卡、但静止时不卡。

处理方向：减层级（扁平布局、约束布局替代多层嵌套）、去冗余背景、列表项复用（不要每项新建视图与对象）、图片按显示尺寸下采样。Android 上有“调试 GPU 过度绘制”开关可直观看到过度绘制区域，具体入口以官方文档为准（示例未实测）。

### 5.3 GC 抖动：间歇性卡顿

短时间内反复分配又释放大量小对象，GC 频繁触发，主线程被 GC 暂停打断，表现为间歇性卡顿——平时流畅、隔几秒卡一下。常见于列表每一项都新建对象、每帧拼接字符串、动画里反复创建临时对象。

处理方向：复用对象（对象池、StringBuilder 复用）、减少每帧分配、图片与大对象复用缓存。排查时先看内存曲线是不是“锯齿高频”（见总论第 4.3 节），再定位到分配热点。

## 6. 排查工具与思路

工具只负责给出证据，结论要人下。排查按“先定位段、再定位点”的顺序：

### 6.1 Android：Systrace / Perfetto

Systrace 与 Perfetto 是 Android 官方的系统级 trace 工具，思路是**按时间轴看各线程在干什么**：

- **看帧**：一帧的测量、布局、绘制各花了多久，哪一帧超时、超时在哪一段。
- **看线程**：主线程在超时那一刻正在执行什么（网络？数据库？锁等待？GC？），后台线程有没有抢主线程的 CPU。
- **看系统**：CPU 频率、内存压力、Binder 调用是否在关键路径上。

使用方法是录制一段卡顿复现过程，打开 trace，按帧超时点反查主线程调用栈。具体命令与界面操作以官方文档为准，本文未做真机实测，命令不逐条罗列。

### 6.2 iOS：Xcode Instruments 思路

iOS 的对应工具是 Xcode Instruments，思路与 Perfetto 相通、落点不同：

- **Time Profiler**：看各线程 CPU 时间花在哪，找到主线程的耗时函数。
- **Allocations / Leaks**：看内存分配曲线与泄漏对象，对应 GC 抖动与内存泄漏排查。
- **Core Animation**：看帧率与离屏渲染、图层混合等绘制开销。

以上为工具定位思路，iOS 相关内容均为示例未实测——本机无 macOS/iOS 环境，Instruments 的具体操作以 Apple 官方文档为准。

### 6.3 通用排查流程

1. **复现并量化**：在目标机型（优先低端机）上复现，记录启动耗时或帧率基线；没有基线，优化无法验收。
2. **分段定位**：启动按第 3 节五段拆、卡顿按第 5 节三类分，先定段、再定点。
3. **单变量改动**：一次只改一处，改完重新测；同时改三处，无法归因。
4. **回归验证**：在同一机型、同一数据、同一网络下复测，确认指标改善且没有把问题推到别的段（如启动快了、内存涨了）。

## 7. 限制与常见误解

- “启动优化就是加启动页。”错：启动页只改感知，不改耗时；真正的优化在第 3 节的五段里。
- “卡顿就加线程。”错：线程能挪走阻塞，但线程本身抢 CPU、占内存；布局与绘制问题加线程没用。
- “高端机不卡就不用优化。”错：用户的主力机型不是开发机，低端机与老系统才是底线（见总论第 6 节）。
- “一次优化管一辈子。”错：新功能、新 SDK、新系统版本都会把耗时加回来，启动与帧率要有基线回归，不是做一次就完事。

## 8. 小结

冷启动按五段拆、逐段算账；优化靠懒加载移走首屏不需要的、预加载提前准备确定要用的、任务图排好依赖与优先级。卡顿分主线程阻塞、绘制过重、GC 抖动三类，先用 Systrace/Perfetto 或 Instruments 定位到证据，再单变量改动、回归验证。
