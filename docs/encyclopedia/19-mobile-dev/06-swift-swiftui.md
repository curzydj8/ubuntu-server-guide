# Swift 语言与 SwiftUI 入门

## 1. 本章目标

读完本篇能理解：Swift 语言为什么这样设计（类型安全、可选值、协议）、SwiftUI 如何用“声明界面 + 状态驱动”代替“命令式改界面”、SwiftUI 与 UIKit 是什么关系、常用视图与布局如何组合出一个页面。

## 2. 背景与问题

iOS 原生开发长期用 Objective-C：动态、灵活，但类型错误常在运行时才暴露，空指针崩溃是常见故障。2014 年 Apple 推出 Swift，目标是在保留开发效率的同时，把尽可能多的错误提前到编译期发现。2019 年 Apple 又推出 SwiftUI，目标是改变写界面的方式：不再一步步命令视图“改这个、改那个”，而是描述“界面应该长什么样”，状态变了界面自动跟着变。

本篇讲语言与 UI 框架的入门概念，不讲 App 打包上架（见本域后续文章）；Android 的对应概念见本域第一篇，跨平台选型对照见本域第二篇。

## 3. 总体架构

Swift 与 SwiftUI 的分工（文字结构图）：

```
Swift 语言层
├── 类型安全：静态类型 + 类型推断，类型错在编译期暴露
├── 可选值（Optional）：显式表达“可能没有值”，空值处理是语法的一部分
├── 协议（Protocol）与扩展：面向协议编程，能力按协议组合而非继承层级
├── 值类型优先：结构体（struct）与枚举（enum）默认按值传递，减少共享可变状态
└── 内存管理：ARC 自动引用计数，编译器插入 retain/release，闭包需注意循环引用
SwiftUI 框架层（基于 Swift 语言特性：结果构造器、属性包装器）
├── 声明式视图：View 协议 + body 描述界面，视图是值类型
├── 状态驱动：@State / @Binding / @ObservedObject / @EnvironmentObject 等
│   持有状态，状态变化触发视图重新计算
├── 布局系统：容器视图（VStack / HStack / ZStack / List）+ 修饰符链
└── 与 UIKit 互操作：UIViewRepresentable / UIViewControllerRepresentable 桥接
运行环境
├── Xcode + Swift 编译器（swiftc），SwiftUI 需要较新的 Xcode 与 iOS 版本
└── 应用仍以 App / Scene 结构运行（生命周期见本域下一篇）
```

两个要点决定了后面的一切：第一，Swift 把“值可能不存在”变成类型系统的一部分，而不是运行时的偶然；第二，SwiftUI 的界面不是被“改出来”的，而是由状态“算出来”的，理解了状态就理解了界面。

## 4. 工作机制

### 4.1 Swift 语言特点：把错误提前到编译期

- **类型安全与类型推断**：变量声明时类型确定，写 `let count = 0` 时编译器推断出 `Int`，之后再把字符串赋给它会在编译期报错。类型安全不等于啰嗦——推断让代码保持简洁，安全由编译器兜底。
- **可选值（Optional）**：一个值“可能没有”时，类型写作 `String?`，即 `Optional<String>`。没有值的状态是 `.none`（字面量 `nil`），有值是 `.some(值)`。使用前必须解包：`if let` 安全解包、`guard let` 提前退出、空合运算符 `??` 给默认值、强制解包 `!` 只在能保证有值时用。强制解包遇到 `nil` 会在运行时崩溃——新手最常见的崩溃来源。
- **协议（Protocol）与面向协议编程**：协议定义“一组能力”（方法与属性的要求），类型通过遵守协议获得能力。协议可以被扩展（extension）提供默认实现，多个协议可以组合。与继承的区别：继承是“是一个”（is-a）的层级关系，协议是“能做什么”（can-do）的能力组合；Swift 标准库大量用协议组织能力（如 `Equatable`、`Hashable`、`Identifiable`）。
- **值类型优先**：结构体与枚举是值类型，赋值与传参时复制；类是引用类型，共享同一份实例。SwiftUI 的视图本身就是结构体：界面描述可以安全复制与比较，状态变化时重新生成描述而不是原地修改旧视图。这与“视图是值、状态是源”的 SwiftUI 模型是一致的。
- **错误处理**：可能失败的操作用 `throws` 声明，调用方用 `do-try-catch` 或 `try?`/`try!` 处理。错误是值，不是异常抛出后到处飞——调用链上必须显式面对它。
- **内存管理（ARC）**：编译器自动插入引用计数操作，开发者一般不用手动管理内存。但闭包捕获 `self` 时容易形成强引用循环，需要用捕获列表 `[weak self]` 或 `[unowned self]` 打破。`weak` 在对象释放后自动变 `nil`（因此只用于可选值），`unowned` 假定对象不会先释放，判断错了会崩溃。

### 4.2 SwiftUI 声明式 UI：描述“应该是什么样”

传统 UIKit 是命令式的：创建 `UILabel`，再一行行命令它改文字、改颜色、改位置。SwiftUI 是声明式的：写一个符合 `View` 协议的结构体，在 `body` 里描述界面应该长什么样（示例未实测）：

```swift
struct ContentView: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("点击了 \(count) 次")
            Button("点我") {
                count += 1
            }
        }
    }
}
```

关键理解有三点：

- **视图是值，不是对象**：`Text`、`VStack`、`Button` 都是结构体，`body` 返回的是对界面的描述，不是屏幕上真实存在的对象。框架拿描述与上一次比较，只更新真正变化的部分。
- **状态是界面的唯一来源**：`@State` 标注的状态属于这个视图，状态一变，框架重新计算 `body`，界面自动更新。开发者不手动“把新数字写进 Label”，只改状态。界面与状态不一致的问题，在这个模型里从结构上就难以出现——前提是状态确实是唯一来源，绕过状态直接改底层视图会破坏这一保证。
- **修饰符返回新视图**：`.padding()`、`.font()`、`.foregroundStyle()` 这类调用不修改原视图，而是返回一个包了一层的新视图。修饰符的顺序有意义：先改字体再加内边距，与先加内边距再改字体，效果可能不同。

### 4.3 状态驱动：四种常用状态包装器

- **@State**：视图私有的本地状态，如上面例子里的 `count`。生命周期与视图绑定，视图销毁状态随之消失。
- **@Binding**：子视图对父视图状态的引用。父视图用 `$count` 把状态的绑定传给子视图，子视图改绑定就是改父视图的状态——父子之间不靠回调传值，靠共享同一份状态。
- **@ObservedObject / @StateObject**：引用类型的数据模型（遵守 `ObservableObject` 协议，用 `@Published` 标注会变化的属性）。数据模型变化时，所有观察它的视图刷新。`@StateObject` 负责创建并持有模型，`@ObservedObject` 只负责观察别人创建的模型——用错会导致模型被反复重建、状态丢失。
- **@EnvironmentObject / @Environment**：跨越多层视图共享的数据与系统环境值（如深色模式、尺寸类别）。不用一层层传参，但依赖关系变得隐式：视图用到了环境里的某个对象，调用方必须在上层注入，否则运行时会崩溃。

状态选型的经验是：状态归谁管，就看谁需要改它、谁需要读它——只一个视图用就用 `@State`，父子共享就用 `@Binding`，跨页面共享的业务数据放 `ObservableObject`，全应用共享的放环境对象。状态放错层，表现就是“改了没反应”或“切个页面数据丢了”。

### 4.4 与 UIKit 的关系与互操作

SwiftUI 不是 UIKit 的简单封装替代，而是并行的新框架，两者关系如下：

- **SwiftUI 出现之前**，iOS 界面用 UIKit（`UIView`、`UIViewController`）写，至今仍是大量存量代码与系统能力的基础；SwiftUI 底层在许多地方仍依赖 UIKit/AppKit 的实现。
- **新项目**可以直接用 SwiftUI 起步，纯 SwiftUI 已能覆盖多数常规应用；**老项目**按页面逐步迁移，SwiftUI 页面可以嵌进 UIKit（`UIHostingController`），UIKit 视图也可以嵌进 SwiftUI。
- **互操作桥接**：SwiftUI 里用 UIKit 视图时，实现 `UIViewRepresentable` 协议（创建与更新 `UIView`）；用 UIKit 控制器时，实现 `UIViewControllerRepresentable` 协议；反过来在 UIKit 里托管 SwiftUI 视图用 `UIHostingController`。桥接的代价是状态同步要手动处理：UIKit 侧的变化要通过 Coordinator 或回调传回 SwiftUI 的状态，否则两边各说各话。
- **系统能力缺口**：个别 UIKit 才有的能力（某些系统控制器、精细的手势与滚动控制）在 SwiftUI 里要么没有等价 API，要么需要桥接。选型时先列出产品依赖的系统能力清单，逐项确认 SwiftUI 是否覆盖，不要假设“新框架什么都有”。

### 4.5 常用视图与布局

- **文本与图片**：`Text`（文字，支持多语言本地化与动态字体）、`Image`（系统图标用 `Image(systemName:)`，资源图片用 `Image("name")`）、`Label`（图标加文字的组合）。
- **容器布局**：`VStack`（垂直排列）、`HStack`（水平排列）、`ZStack`（层叠，后写的在上面）、`List`（列表，支持分组、滑动删除、滚动）、`ScrollView`（可滚动容器）、`LazyVStack`/`LazyHStack`（按需加载，长列表用懒加载避免一次性创建全部行）、`Grid`（网格布局）。
- **控件**：`Button`、`Toggle`（开关）、`TextField`（输入框）、`Slider`（滑杆）、`Picker`（选择器）、`DatePicker`（日期选择）、`NavigationStack`（导航栈，配合 `NavigationLink` 做页面跳转）、`TabView`（底部标签页）、`Sheet`/`alert`（模态弹出与提示）。
- **布局规则**：父容器向子视图提议一个尺寸，子视图按自身内容与修饰符决定实际尺寸，再把结果报回父容器；`Spacer` 撑开剩余空间、`.frame()` 限定尺寸、`.padding()` 留白、`.layoutPriority()` 决定空间不足时谁先被压缩。布局出问题时，先问“是谁在决定尺寸——父容器、子视图，还是修饰符”，而不是反复调数值。

## 5. 关键设计取舍

- **编译期安全换灵活性**：Swift 的类型系统与可选值把大量运行时崩溃变成编译错误，代价是写代码时要显式处理“没有值”“可能失败”这些情况，不能像动态语言那样先跑起来再说。
- **声明式换控制力**：SwiftUI 让界面与状态自动同步，代价是精细控制（如逐帧动画、复杂手势、自定义滚动行为）不如 UIKit 直接；遇到天花板时要桥接 UIKit，而不是硬写 SwiftUI 的变通写法。
- **值类型视图换直观性**：视图是可复制的描述，状态变化重新计算，代价是新手要转变思维——“找到那个 Label 改掉它”的命令式直觉在这里不适用，改状态才是正路。
- **协议组合换继承层级**：能力按协议拼装，避免深继承树的脆弱性，代价是协议之间的组合关系需要设计，滥用协议扩展同样会让代码难追踪。

## 6. 分类与变体

- **语言路线**：Swift 是 iOS/macOS 原生开发的首选语言；Objective-C 仍可维护老项目，与 Swift 可以在同一工程里混编（通过桥接头文件），新项目无特殊原因应选 Swift。
- **界面路线**：SwiftUI（声明式、新方向）与 UIKit（命令式、存量基础）并存；跨平台路线（Flutter、React Native、KMP）见本域第二篇。
- **架构模式**：常见做法是 MVVM：视图（View）只管展示，视图模型（`ObservableObject`）持有状态与业务逻辑，数据层（网络、数据库）只管来源；视图直接调网络或数据库，是后期最难维护的写法。

## 7. 应用与限制

- 适用：需要完整 iOS 系统能力（推送、内购、系统分享、传感器、快捷指令集成）的产品；对启动速度、动画帧率、系统最新设计风格敏感的产品。
- 不适用：只做内容展示且需同时覆盖 Android 的产品（见本域第二篇选型）；团队无 Apple 生态经验又要求双端快速上线时，原生双写成本最高。
- 本篇只讲语言与 UI 框架的入门概念；应用生命周期、沙盒与权限见本域下一篇；打包、分发与商店审核不在本篇范围。

## 8. 常见误解

- “可选值就是可以为空的变量，没什么特别。”错：可选值是独立的类型，`String` 与 `String?` 是两种类型，混用会在编译期报错；`nil` 不是“空字符串”，而是“没有值”这个状态本身。
- “SwiftUI 里改界面就是改状态，所以不用管视图层级。”错：状态驱动的是“界面算什么样”，视图层级、修饰符顺序、布局规则仍然决定最终效果，状态放错层或修饰符顺序错了，界面一样会错。
- “SwiftUI 出来了，UIKit 就不用学了。”错：存量代码、系统能力缺口与桥接场景都离不开 UIKit，完全不懂 UIKit 会在迁移与调试时处处受限。
- “强制解包 `!` 只是少写几行代码。”错：强制解包是把“一定有值”的保证从编译器手里接过来自己背，判断错了就是运行时崩溃；能用 `if let`/`guard let`/`??` 的地方不要用 `!`。
