# Google Play 上架流程

## 1. 本章目标

读完本篇能理解：一个 Android 应用从“写好代码”到“用户能在 Google Play 上下载”要经过哪些步骤、每个步骤在管什么、审核为什么会驳回，以及 App Store 的上架流程在哪些地方与之不同。

## 2. 背景与问题

写好应用只是第一步。用户不会从源码里安装应用，他们从商店里下载。商店是应用与用户之间的守门人：它要确认“这个应用是谁做的”（身份）、“这个应用能不能安全运行在目标机型上”（格式与版本）、“这个应用有没有违反规则”（政策审核）。Google Play 的上架流程，就是把这三件事按顺序办完的流程：先建开发者账号与应用档案，再上传安装包、走测试轨道，最后过审核、正式发布。跳过任何一步，应用都上不了架；每一步填错信息，都会在审核环节被打回来。

本篇讲流程与概念，不讲 Play Console 里每个按钮的点击步骤（控制台界面会改，操作以官方文档为准）；应用打包成什么格式、签名是谁的，见本组下一篇。

## 3. 总体架构

上架流程按顺序分五步：

```
1. 开发者账号 ── 注册 Google Play 开发者账号，完成身份验证
2. 应用创建 ── 在 Play Console 创建应用，填商店信息、定价与分发范围
3. 上传安装包 ── 上传 AAB，填版本号，生成可安装的 APK
4. 发布轨道 ── 内部测试 → 封闭测试 → 开放测试 → 正式版，逐步放量
5. 审核与发布 ── 商店审核通过后，版本对用户可见；后续更新走同一流程
```

两个要点决定了后面的细节：第一，**账号、应用、安装包是三层不同的身份**——账号是“谁”，应用是“哪一个产品”（由应用 ID 区分），安装包是“哪一个版本”（由版本号区分）；第二，**测试轨道不是可选项的摆设**，它是商店给开发者的正式放量机制，先小范围验证、再全量发布，是正规做法，不是一次性把未经验证的版本推给所有用户。

## 4. 工作机制

### 4.1 开发者账号与应用创建

- **开发者账号**：在 Google Play 上发布应用，需要一个 Play 开发者账号。注册时要完成身份验证（个人或组织），并接受开发者分发协议。账号的注册费用、验证方式与所需材料以官方发布为准（待核实），本文不写未经核实的具体数字。
- **应用创建**：在 Play Console 里创建一个应用，得到一个应用条目。创建时要确定应用的默认语言、应用类型（应用还是游戏）、免费还是付费——付费与免费的切换有规则限制，定价策略要提前想好，不能事后随意改。
- **应用 ID（applicationId）**：每个应用有一个全局唯一的应用 ID（例如 `com.example.myapp`），见本组第一篇。它是应用的终身身份：同一个 ID 代表同一个应用，改了 ID 就等于换了一个新应用，老用户收不到更新。创建应用时就要定好，之后不能改。
- **商店信息**：应用名称、简介、图标、截图、分类、内容分级问卷、隐私政策链接。这些不是“装饰”，而是审核材料的一部分：截图与描述必须与应用实际功能一致，夸大或误导会被驳回；涉及用户数据的应用必须提供隐私政策，否则无法发布。

### 4.2 AAB 上传与版本管理

- **AAB 是上架格式**：新应用须以 Android App Bundle（AAB）格式提交，由 Play 按设备生成优化后的 APK 下发；直接上传 APK 上架新应用的做法已不被接受，以官方发布为准（待核实）。AAB 与 APK 的区别见本组第一篇：AAB 是“原材料包”，APK 是“装到设备上的成品”。
- **版本号**：每次上传都要有新的版本号（`versionCode` 递增，`versionName` 是给用户看的版本名）。`versionCode` 不递增，商店会拒绝该上传；已发布版本的版本号不能重复使用。版本号管理是发布流程的硬规则，不是约定俗成。
- **目标 API 要求**：Google Play 自 2026 年 8 月 31 日起要求新应用与更新 target Android 16（API 36）或更高，见本组第一篇。上传的应用不满足目标 API 要求，会被商店拦截。目标 API 要求会随 Android 大版本推进而提高，上架前要以官方发布为准核对当前要求。
- **版本管理**：一个应用在 Play Console 里同时存在多个版本——已发布的正式版、正在测试的测试版、已废弃的旧版。发布新版本不是“覆盖旧文件”，而是“新版本进入轨道、旧版本按规则下线”。出现严重问题时，可以通过发布修复版本或暂停发布来止血，而不是直接删除已发布版本（已发布版本没有“撤回”按钮，只有“停止分发”的等效操作）。

### 4.3 发布轨道：逐步放量

Play 提供四条发布轨道，从内到外逐步扩大用户范围：

- **内部测试**：只给团队内部（最多约一百人规模，以官方发布为准）使用。用于开发自测与持续集成出包后的第一道验证：装得上、打得开、核心流程能走通。
- **封闭测试**：给指定的测试者群体（如内测用户名单、测试群组）。用于功能验证与反馈收集：真实用户在真实机型上试用，报 Bug、提意见，版本还不公开。
- **开放测试**：任何人都能在商店页面加入测试，版本公开可见但标明“测试版”。用于大规模兼容性验证：在更多机型与系统版本上暴露问题，同时收集评分与反馈。
- **正式版**：对所有目标用户可见，可在商店搜索与下载。这是唯一面向公众的轨道。

轨道的正确用法是“由内而外、逐级放量”：内部测试没跑通不要进封闭测试，封闭测试反馈的严重问题没修不要进开放测试。直接把未经测试的版本推正式版，等于把全体用户当测试员，出问题时影响面最大、止血成本最高。分阶段发布（staged rollout）是正式版轨道内的进一步放量手段：先给一小部分用户，再逐步扩大到全部，发现问题可暂停放量。

### 4.4 审核政策要点与常见驳回原因

- **审核是什么**：应用提交后，Google Play 会做政策审核与技术检查，审核时效以官方发布为准，本文不写未经核实的具体天数。审核不通过，版本无法发布；审核通过，版本按轨道设置对用户可见。
- **政策要点**：审核覆盖的范围包括：应用功能是否真实可用（不能是空壳、不能主要功能不可用）；用户数据与隐私（权限申请是否与功能匹配、是否按要求披露数据收集与共享、是否有隐私政策）；内容合规（不得含有违规内容、不得误导用户）；付费与订阅（内购与订阅的说明、价格、取消方式必须清晰）；以及目标 API、64 位架构等技术要求。政策细节以 Google Play 开发者政策中心为准，政策会更新，上架前要按最新版自查。
- **常见驳回原因**：按高频程度，开发者最常遇到的是这几类——目标 API 级别不达标；隐私政策缺失或与实际数据收集不符；权限申请超出功能需要（如一个记事本应用要通讯录权限）；应用描述、截图与实际功能不符；应用在审核设备上崩溃或主要功能不可用；订阅说明不清（价格、周期、自动续订、取消方式缺一项都可能被驳回）。驳回通知会说明原因与依据的政策条款，按通知逐项修复后可重新提交；反复提交同一未修复版本不会通过。
- **审核不是一次性考试**：已上架的应用也会被复查，政策更新后旧版本可能被要求整改；用户举报、评分异常、崩溃率超标都可能触发复审。把“过审”当成终点是误解，上架只是合规的起点。

### 4.5 App Store 上架流程对照要点

iOS 应用上架走 Apple 的 App Store Connect，流程骨架与 Google Play 相同（账号 → 应用 → 安装包 → 测试 → 审核 → 发布），但关键点不同：

- **账号与年费**：发布到 App Store 需要加入 Apple Developer Program（个人或组织），年费与验证方式以 Apple 官方发布为准（待核实），本文不写未经核实的具体数字。
- **安装包格式**：iOS 上传的是 Xcode 归档产物（.ipa），通过 App Store Connect 提交；应用签名用 Apple 的证书与描述文件，见本组下一篇。
- **测试**：TestFlight 是 Apple 的官方测试分发渠道，对应 Play 的测试轨道；内部测试与外部测试的规则、人数上限与审核要求以官方发布为准（待核实）。
- **审核差异**：App Store 审核以人工审核为主、标准偏严，对应用功能完整性、界面规范、内购规则（必须使用 App 内购买机制处理数字商品与服务）的审查更细；审核时效以官方发布为准，本文不写未经核实的具体天数。同一款应用在两家商店可能一家通过、一家驳回，这是常态，不是“某一家的审核出错了”——两家政策本就不同，要按各自的政策分别准备材料。

## 5. 关键设计取舍

- **逐步放量换速度，代价是流程变长**：走完四条轨道比直接发正式版慢几天，但换来的是问题在小范围暴露；赶时间跳过测试轨道，省的是几天，赌的是全体用户。
- **AAB 换包体积与适配，代价是构建链路要适配**：AAB 让商店按设备生成最小 APK，用户下载更小、适配更全，但构建与签名流程必须按 AAB 来，不能沿用“打一个通用 APK 分发”的老习惯。
- **商店审核换分发便利，代价是合规成本**：商店带来流量、支付、更新与信任背书，代价是政策合规、隐私披露、目标 API 跟进都要持续投入；不走商店的直分发省了审核，但丢了这些便利，见本组下一篇。

## 6. 分类与变体

- **按发布范围分**：内部测试、封闭测试、开放测试、正式版（见 4.3 节）。
- **按更新方式分**：全新发布（新应用第一次上架）、版本更新（已上架应用的迭代）、分阶段发布（正式版内逐步放量）。
- **按商店分**：Google Play（Android）、App Store（iOS），流程骨架相同、政策与工具不同（见 4.5 节）。

## 7. 应用与限制

- 适用：准备把 Android 应用交给公众用户的产品；需要商店的支付、更新与信任背书的产品。
- 不适用：只在内部使用的工具（可走内部测试轨道或企业分发，见本组下一篇）；只做内容展示且不需商店能力的产品（先考虑响应式网站，见本域第二篇选型方法的第一问）。
- 本站的 Linux Server Toolkit 应用即通过站内直分发提供 APK（见本组下一篇），不上 Google Play；本文的上架流程是通用知识，不描述该应用的实际发布记录。

## 8. 常见误解

- “应用写好了，上传就能上架。”错：账号、商店信息、隐私政策、目标 API、审核，任何一环不合格都会卡住，上架是流程，不是上传。
- “测试轨道是给大厂用的，小应用直接发正式版就行。”错：越是小团队、测试资源越少，越需要封闭测试帮你在真实机型上发现问题；跳过测试省的是流程，付的是用户流失。
- “审核通过就万事大吉。”错：政策会更新、已上架应用会被复查，合规是持续工作。
- “Google Play 过了，App Store 肯定过。”错：两家政策与审核标准不同，要按各自的政策分别准备。
