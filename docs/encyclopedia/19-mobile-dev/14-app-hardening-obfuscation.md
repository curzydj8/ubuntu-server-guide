# 应用加固与代码混淆

## 1. 技术原理

移动应用发布后，安装包会到达用户设备上。设备在用户手里，意味着应用代码与资源原则上可以被读取和分析：一个普通的 APK 文件解包后能看到编译后的字节码、资源文件与清单声明。加固要解决的问题就是：在“代码必然发到别人设备上”这个前提下，提高他人理解与篡改应用的成本，同时检测运行环境是否可信。

理解加固要先分清三件事：**混淆**、**完整性校验**、**环境检测**。混淆让代码难读，完整性校验让篡改可被发现，环境检测让应用在不可信环境里降级或拒绝运行。三者都是“提高成本、争取时间”，没有一项能让客户端变成绝对安全。

### 1.1 代码混淆（R8 / ProGuard）：把名字换掉、把没用的删掉

Android 构建的混淆由 R8 完成（R8 是 Android Gradle Plugin 内置的默认代码压缩与混淆器，ProGuard 是它之前的同类工具，两者的规则语法兼容，历史上许多项目仍沿用 ProGuard 规则文件命名）。R8 在 release 构建中做三件事：

- **压缩（Shrinking）**：删除没有被引用到的类、方法与字段。包体积变小，攻击面随之缩小。
- **混淆（Obfuscation）**：把类名、方法名、字段名改成无意义的短名字（如 `a`、`b`、`c`）。代码逻辑不变，但阅读者失去“这个类叫 LoginManager、那个方法叫 verifyPassword”这类语义线索。
- **优化（Optimization）**：内联、合并等变换，进一步改变代码形态。

混淆不加密代码，也不改变程序行为。经过混淆的字节码仍然是合法的字节码，仍然可以被反编译；它只是把“读代码”从“读一本有目录的书”变成“读一本目录页被撕掉的书”。同时，混淆会让崩溃堆栈也变成短名字，因此发布时要保留映射文件（mapping file），用于把线上崩溃堆栈还原成原始符号；映射文件是敏感材料，只应保存在内部，不应随安装包发布。

R8 的配置要点（防御侧，配置示例见第 6 节）：

- 只在 release 构建开启混淆，debug 构建保持可读，方便调试。
- 反射、序列化、跨进程接口用到的类与成员必须显式保留（`-keep` 规则），否则运行时找不到符号会崩溃。被保留的入口越多，混淆效果越弱，这是取舍，不是配置错误。
- 第三方库通常自带混淆规则（随 AAR 内的 consumer rules 下发），升级库后要复查规则是否仍然适用。
- 混淆规则要进版本控制，随代码评审一起改；“为修一个崩溃临时加一条宽泛 keep”是最常见的混淆退化来源。

### 1.2 资源混淆与签名校验：让资源难找、让篡改可发现

- **资源混淆**：把 `res/` 下的资源文件名与字符串资源也做重命名或压缩，使资源与代码的对应关系更难建立。它与代码混淆配合使用，单独使用收益有限。需要注意：资源混淆不能替代敏感信息的管理——密钥、口令、内部接口地址不应该出现在资源或代码里（见第 15 篇数据存储）。
- **签名校验思想**：Android 应用安装包自带开发者签名。应用可以在运行时读取自身的签名信息，并与预期值比对；签名不一致，说明安装包被重新打包或篡改过。这一校验只能作为“发现篡改后降级或告警”的一环：校验逻辑本身也在客户端代码里，同样可以被分析与改动，因此它不能作为唯一的信任依据。正确的心态是把它看作纵深防御的一层，而不是一道门锁。
- **安装来源与调试状态**：防御侧还可以检查应用是否来自可信分发渠道、是否处于可调试状态（`debuggable` 标志只应出现在 debug 构建）、是否被附加调试器。这些检查同样是“提高成本”的信号层，单独一项都不构成安全保证。

### 1.3 Root / 越狱检测与完整性校验：检测信号，不是判决

Root（Android）与越狱（iOS）意味着设备获得了超出系统设计的权限：系统分区可写、沙箱可被绕过、其他应用的数据可能被读取。在这样的环境里，客户端代码看到的系统状态本身就不可信，因此检测的目标不是“证明设备干净”，而是“发现高风险信号后做风险决策”。

常见的防御侧检测信号（只列“检测什么”，不写如何绕过）：

- 系统分区是否以可写方式挂载、是否存在常见的提权管理应用与可疑文件。
- 应用运行环境是否被注入或挂接了调试、Hook 框架（例如调试器附加、异常的动态库加载）。
- 应用完整性校验：签名、关键文件哈希、代码段校验，与预期值比对。
- 服务端辅助的完整性证明：由系统或厂商提供的完整性判定服务（如 Google Play Integrity API）在服务端返回设备与应用完整性 verdict，客户端只做展示与降级，信任决策放在服务端做。

检测到高风险信号后，合理的响应是**分级降级**，而不是一律闪退：对普通功能（如浏览公开内容）可以继续提供；对敏感操作（如支付、查看敏感数据、修改安全设置）应拒绝或要求额外的服务端验证。分级响应的原因是检测本身存在误报可能（例如开发者设备、企业定制设备、某些厂商 ROM 会触发部分信号），一律拒绝会把正常用户挡在门外。

## 2. 合法研究范围

本篇只讨论应用开发者为保护自有应用而采取的防御措施。研究与测试只应在自有应用、自有设备、授权系统或隔离靶场内进行。未授权测试他人系统是违法行为，本文不提供相关指导；任何针对他人应用的分析、修改或绕过行为均不在本文讨论范围内。

## 3. 实验环境

- 环境：自有应用的 release 构建产物，在自有设备或隔离测试环境中验证。
- 软件与版本：Android Gradle Plugin 与 R8 的版本以官方发布为准（待核实）；完整性判定服务的可用版本与接入方式以官方文档为准（待核实）。
- 权限要求：无需特殊权限；混淆与签名校验的验证在构建机与测试机上完成，不涉及他人设备。

## 4. 风险

- **误报导致正常用户被拒**：环境检测信号在部分合法设备上也会出现，过度拦截会损害可用性。规避：分级响应 + 服务端复核，敏感操作才收紧，普通功能保持可用。
- **映射文件泄露**：混淆映射文件一旦公开，混淆的阅读成本优势大幅下降。规避：映射文件只存内部构建产物库，不进安装包、不进公开仓库。
- **把加固当作安全本身**：加固之后仍把密钥、口令写进客户端，或仍信任客户端传来的任何数据，等于没做加固。规避：敏感逻辑与校验放服务端，客户端只做展示与初步检查（见第 15 篇）。
- **过度加固拖垮开发效率**：每条宽泛 keep 规则、每次发布前的人工加固流程都会增加维护成本。规避：规则进版本控制、构建流程自动化、定期复查规则有效性。

## 5. 检测方式

从防御侧看，加固是否生效，用以下方式验证：

- **构建产物检查**：解包自有应用的 release 产物（自有应用、自有设备），确认类名与方法名已被混淆、未引用的代码已被删除、调试标志未开启、映射文件未随包发布。
- **篡改模拟**：在隔离环境中对自有应用的副本做改动后重打包安装，确认完整性校验能发现签名或内容变化并按预期降级（只针对自有应用做此验证）。
- **环境信号回归**：在已 Root/越狱的测试设备（自有设备）与正常设备上分别运行，确认检测信号与分级响应符合预期，且正常设备不被误拦。
- **线上监控**：统计完整性校验失败与高风险环境信号的上报比例，异常突增时先排查误报（如某厂商系统更新导致信号变化），再排查攻击。

## 6. 修复与防御方法

### 6.1 推荐的 release 构建配置（示例未实测）

以下为模块级 `build.gradle.kts` 的防御侧配置示例，展示“开启混淆 + 收缩资源”的意图，实际规则以官方文档为准，发布前应在自有构建环境验证：

```kotlin
android {
    buildTypes {
        release {
            isMinifyEnabled = true      // 开启 R8 压缩与混淆
            isShrinkResources = true    // 收缩未使用的资源
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"     // 项目自有 keep 规则
            )
        }
    }
}
```

### 6.2 纵深防御清单

1. **构建层**：release 构建默认开启 R8 混淆与资源收缩；映射文件存档到内部，不随包发布。
2. **代码层**：敏感信息与密钥不进客户端；反射与序列化入口的 keep 规则写得尽量窄，并定期复查。
3. **完整性层**：签名与关键内容校验 + 服务端完整性判定结合使用，客户端校验只做初步信号。
4. **环境层**：Root/越狱与调试检测只做风险信号，响应分级，敏感操作收紧、普通功能放行。
5. **服务端层**：所有关键校验与授权在服务端重做一次，客户端传来的任何数据都视为不可信。
6. **流程层**：加固配置进版本控制，随代码评审；每次发版前做一次构建产物检查；线上监控完整性失败率。

## 7. 加固的限度：没有绝对安全的客户端

这是本篇最重要的一节，值得单独讲透：

- **客户端代码必然可被读取**。应用要运行，就要把代码发到设备上；只要代码在设备上，就存在被分析的可能。混淆、加壳、完整性校验能提高分析成本、拖延时间，但不能把成本提高到无限大。把“客户端不可破解”当作安全假设的设计，从第一天起就是错的。
- **检测逻辑本身也在客户端**。任何“检测到异常就退出”的代码，都与被检测的对象运行在同一个不可信环境里。防御的价值在于让攻击者多花时间、多走步骤，同时让服务端有机会发现异常、让正常用户不受影响，而不是指望某一次检测“挡住所有人”。
- **真正的安全边界在服务端**。口令校验、权限判断、交易确认、敏感数据访问——这些决策必须在服务端完成，客户端只负责把用户意图传上去、把服务端结果展示出来。客户端的任何校验都只是“提前拦截、改善体验”的优化，不是安全边界。
- **加固的投入要与资产价值匹配**。一个展示公开资讯的应用与一个处理支付的应用，对加固深度的需求完全不同。过度加固会拖慢发布节奏、增加误报与维护成本；加固不足则会在关键资产上留口子。按“最坏情况下被攻破会损失什么”来定投入，而不是按“市面上有没有更强的加固方案”来定。

一句话总结：加固是给客户端穿防弹衣，不是把客户端变成保险库；保险库只能建在服务端。
