# 需求与项目管理入门

## 1. 一句话定义

需求与项目管理是把“想要什么”变成“先做什么、做到什么算完成、什么时候交付”的一套工作方法：需求定方向，拆分与估算定工作量，迭代节奏定反馈速度。

## 2. 为什么需要它

大多数项目失败不是因为技术做不出来，而是因为方向错了或节奏乱了。典型症状有四种：做了一半才发现用户要的不是这个；需求一直在变，永远做不完；估算说两周，实际做了两个月；团队每天都很忙，但到交付日拿不出可用的东西。这四种症状对应四个缺失：需求没有被确认、拆分没有边界、估算没有依据、迭代没有可交付的检查点。本篇按这个顺序讲，不讲具体项目管理工具的安装与操作。

## 3. 核心含义

### 3.1 需求的三种层次

需求不是一句话，而是一个从模糊到具体的收敛过程：

- **目标**：要解决谁的什么问题，例如“让小商家不用记账本也能对上账”。目标错了，后面做得越快错得越远。
- **用户故事**：从使用者角度写的一条需求，常用格式是“作为……，我想要……，以便……”。例如“作为店主，我想要按月查看收支汇总，以便月底对账”。故事讲的是“谁、要什么、为什么”，不规定实现细节。
- **验收标准**：判断这条故事做完没有的具体条件，例如“选择任意月份后，汇总金额与逐笔记录之和一致；没有任何记录的月份显示为空状态而非报错”。没有验收标准，故事就没有完成线。

三层缺一不可：只有目标没有故事，开发不知道做什么；只有故事没有验收标准，开发与用户对“做完”的理解会不一致；只有验收标准没有目标，团队会把功能做对、方向做错。

### 3.2 好故事的检查清单：INVEST

Bill Wake 在 2003 年提出的 INVEST 是检查用户故事质量的常用清单，六项分别是：独立（Independent）、可协商（Negotiable）、有价值（Valuable）、可估算（Estimable）、小（Small）、可测试（Testable）。逐项自问：

| 字母 | 自问 |
|---|---|
| I 独立 | 能不能不依赖其他故事单独开发、单独交付？总是成对出现的故事，考虑合并或换一种拆法。 |
| N 可协商 | 是不是只定了目标、留出了实现方式的讨论空间？把界面与数据库都定死的需求是规格说明书，不是故事。 |
| V 有价值 | 用户或业务能不能感知到它？“搭建数据库”单独成故事时，用户感知不到价值，说明拆法不对。 |
| E 可估算 | 团队能不能大致估出规模？估不出来通常是因为理解不够，先做一次短时限的调研（spike），而不是硬估一个数。 |
| S 小 | 能不能在一个迭代内完成，最好是几天的工作量？跨多个迭代的故事一定要拆。 |
| T 可测试 | 能不能写出明确通过/失败的验收标准？“页面应该很快”不可测试，“中端手机 4G 下页面加载在 2 秒内”才可测试。 |

INVEST 是检查清单，不是打分表：某一项不通过时，处理方法是改故事（拆分、补讨论、补验收标准），不是给故事打个低分就照常开工。

### 3.3 需求收集：先问问题，再写方案

需求收集最容易犯的错误是“用户说要什么，就直接做什么”。用户描述的常常是方案（“加一个导出按钮”），而不是问题（“月底要把数据交给会计”）。收集时多问三类问题：

1. **场景**：谁在什么情况下用？频率多高？现在是怎么解决的？
2. **约束**：有没有不能碰的边界，例如数据不能离线、必须兼容旧版本、必须符合某项合规要求？
3. **优先级**：如果只能做一半，哪一半最先有价值？这个问题能区分“想要”和“必须”。

收集到的需求要落成文字并与提出方确认一次：口头共识在一周后会变成各说各话，文字记录是唯一的共同依据。确认时重点对齐目标与验收标准，而不是逐字复述方案。

## 4. 拆分：把大需求切成可交付的小块

拆不好的需求有两个极端：太大（一个故事做一个月，进度不可见），太碎（十个故事拼起来才有价值，单独交付没有意义）。常用的拆分角度，按优先级排序：

1. **按工作流步骤拆**：先做“提交”，再做“审批”，最后做“通知”——每一步单独可用。
2. **按数据与规则拆**：先做主流程，再做边界与异常（空状态、权限不足、重复提交）。
3. **按用户群拆**：先做最核心的一类用户，再扩展到其他用户。
4. **按性能与体验拆**：先做功能正确，再做速度与体验优化——不要把优化和功能绑在同一个故事里。

拆分后的检验标准回到 INVEST：每一块都能独立交付、有验收标准、一个迭代内做完。拆出来的第一块应当是“能走通主流程的最小版本”，而不是“把基础设施全部搭好”——基础设施先行的做法，会让第一个可交付成果来得太晚。

## 5. 估算：估相对规模，不猜绝对工期

### 5.1 为什么绝对工期估不准

“这个需求要几天”是很难直接回答的：它受实现者熟练度、中断次数、需求理解偏差、未知技术点的影响。更可靠的做法是估**相对规模**：以一个团队都熟悉的故事为参照（例如“这个故事和上周那个登录表单差不多大”），其他故事按“更大/更小、大多少”来排。相对规模不受个人速度影响，适合团队共识；绝对工期则由团队的历史交付速度反推，而不是由估算会议拍脑袋定。

### 5.2 估算的规矩

- **团队一起估**：估算不是一个人说了算；理解最浅的人往往估得最乐观，多听不同人的理由，估算本身就是一次需求澄清。
- **估不出来就先调研**：给未知部分定一个短时限（例如半天到两天）的调研任务，调研结束后再估，而不是在完全不了解时给一个精确数字。
- **估算要留缓冲，但缓冲要透明**：把不确定性写出来（“依赖第三方接口文档，文档未到”），而不是偷偷把数字翻倍——偷偷翻倍的估算既无法复盘，也无法在风险解除时收回。
- **估算不是承诺**：估算变了要及时说，藏着掖着只会让偏差在交付日一次性爆发。

### 5.3 一个常见的自欺：把估算当成考核

一旦估算被用来考核个人（“你估两周为什么做了三周”），团队就会开始虚报估算、隐瞒风险，估算数据随之失真。估算的用途是排计划与早发现风险，不是考核工具。复盘时应当复盘“为什么理解有偏差”，而不是“为什么人不够快”。

## 6. 迭代节奏：用固定节奏换可见进度

### 6.1 迭代与 Scrum 的基本形态

迭代开发的基本思想是：把工作切成固定长度的周期，每个周期结束都拿出一个可运行、可检查的增量，而不是到最后才一次性交付。Scrum 是其中最常见的一种框架：其 2020 年版指南（Ken Schwaber 与 Jeff Sutherland）规定，Sprint（迭代）固定长度、不超过一个月，新 Sprint 在上一个结束后立即开始；Sprint 内的正式事件包括 Sprint 计划会、每日站会、Sprint 评审会、Sprint 回顾会。其中每日站会为 15 分钟，面向一个月的 Sprint 时，计划会最多 8 小时、评审会最多 4 小时、回顾会最多 3 小时。

本篇不复述 Scrum 指南全文，只强调节奏成立的三个条件：周期固定（不为了“做完”而延长迭代）、每个周期有可检查的增量（评审会上看运行的东西，不是看幻灯片）、每个周期有一次过程回顾（只复盘“工作方式”，不变成追责会）。三个条件缺一个，迭代就会退化成“把瀑布切成几段”。

### 6.2 迭代节奏的常见选择

迭代长度没有唯一正确答案，常见取舍是：周期越短，反馈越快，但会议与交付开销占比越高；周期越长，单次交付内容越多，但方向跑偏后纠正越晚。对新手团队，一个实用的起点是固定两周：短到足以早发现问题，长到足以做出可见增量。长度定下来后就不要频繁改——节奏的价值一半来自“固定”本身，改来改去等于没有节奏。

### 6.3 每日同步的正确用法

每日站会的目的是让团队针对 Sprint 目标重新规划当天工作，不是向管理者汇报进度。把它开成“昨天做了什么、今天做什么、有没有困难”的逐人汇报，且汇报对象是管理者时，站会就会变成负担。判断标准很简单：开完会，团队是否更清楚今天该先做什么、谁需要帮助；如果答案是否定的，这个会的形式就错了。

## 7. 常见失败模式

| 失败模式 | 症状 | 对策 |
|---|---|---|
| 需求蔓延 | 迭代中不断加需求，永远做不完 | 新需求进下一个迭代；本迭代的需求冻结，紧急变更走明确的替换流程（加一个、移出一个） |
| 镀金 | 做用户没要的功能，觉得“反正顺手” | 回到验收标准：标准之外的功能单独立项，不搭便车 |
| 估算乐观 | 每个迭代都完不成承诺 | 用相对规模 + 历史速度反推；把未知部分先调研再估 |
| 评审会变演示会 | 评审会上只放幻灯片，没有可运行的东西 | 评审会只评审增量本身；没有增量的迭代，评审会就应当如实承认 |
| 回顾会不开 | 同样的问题每个迭代重复 | 回顾会是固定事件，不是“有空再开”；每次只定一到两项可执行的改进 |
| 单点依赖 | 只有一个人懂关键模块 | 关键知识至少两人掌握；评审与结对是分摊知识的日常手段，不是一次性交接 |

## 8. 限制

需求与项目管理解决的是“方向与节奏”，不解决“技术能不能做出来”：一个技术上不可行的需求，管理方法再好也只能早发现、早止损，不能变可行。同样，方法不能替代判断：INVEST、迭代、估算都是工具，团队在真实约束下的取舍（例如合规 deadline 压倒一切时，迭代节奏可以临时让路，但要明说代价）才是管理本身。

## 9. 小结

需求管理 = 目标、故事、验收标准三层对齐；项目管理 = 拆成可交付小块、用相对规模估算、以固定节奏交付增量并回顾。方向对了，速度才有意义；节奏稳了，问题才暴露得早。
