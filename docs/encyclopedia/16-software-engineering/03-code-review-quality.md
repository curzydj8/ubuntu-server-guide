# 代码评审与质量实践

## 1. 一句话定义

代码评审是作者之外的人在代码合并前检查一次变更，目的不是挑错，而是保证这次变更确实让系统整体变好、且未来的人能读懂和维护它；质量门禁则是把一部分检查交给机器自动执行，让人工评审集中在机器看不懂的地方。

## 2. 为什么需要它

代码一旦合并，就变成了团队的共同负担：作者离职、半年后重构、线上出问题时，读代码的人都要为当初的写法付账。评审的价值分四层：第一层是当时拦下错误（逻辑错、边界漏、异常没处理）；第二层是传播知识（评审者了解了这块代码，作者得到了另一种思路）；第三层是统一标准（风格、命名、结构在评审中逐渐收敛）；第四层是建立集体所有权——代码是团队的，不是某个人的，任何人都能接手改。

没有评审的团队，问题不会消失，只会推迟：推迟到测试阶段、推迟到上线后、推迟到接手的人读不懂时再付，代价一次比一次高。

## 3. 从正式检查到轻量评审

代码评审不是新发明。Michael Fagan 在 IBM 于 1976 年发表的《Design and code inspections to reduce errors in program development》（《IBM Systems Journal》第 15 卷第 3 期）提出了正式的软件检查流程：计划、讲解、准备、检查会、返工、跟进，角色分工明确、节奏有要求。这是评审的源头，但它很重：需要专门开会、逐行朗读、控制速度。

今天主流的做法是轻量评审：作者提交一个自包含的变更（在 Git 语境里通常是一个合并请求），评审者在线上逐行看、逐条评论、通过或要求修改，机器检查（见第 6 节）先行通过后再进入人工环节。轻量评审保留了正式检查的核心——“作者之外的人看过”与“问题有记录、有跟进”——去掉了开会朗读的形式成本。需要正式检查的场景仍然存在：关键安全模块、核心算法、涉及资金计算的变更，可以回到更严格的形式（例如指定两名评审者、要求逐行确认），而不是对所有变更一视同仁地加重流程。

## 4. 评审清单：查什么

Google 公开的《工程实践文档》（Engineering Practices）把评审标准概括为一句话：评审者应当在变更“确实改善了所涉系统的整体代码健康”时倾向于批准，哪怕它不完美；同时绝不接受让系统明确变差的变更（真正的紧急情况除外，且事后要补清理）。围绕这个标准，评审者按以下清单检查，顺序大致是从大到小：

### 4.1 设计：这次变更放在这里对吗

- 变更是不是在正确的层次、正确的模块？一个本该放在服务层的方法被写进界面层，是设计问题，不是风格问题。
- 有没有引入不必要的复杂度？能用简单结构讲清的逻辑，不要用复杂结构。
- 与系统已有模式是否一致？新写法与旧模式冲突时，要么按旧模式改，要么在评审中说明为什么旧模式不适用。

### 4.2 功能：做的是不是作者想做的

- 代码是不是真的实现了变更说明里写的事？先读说明，再读代码，对不上先问。
- 边界与异常处理了没有：空值、零值、权限不足、外部服务失败、超时——这些是评审最容易发现问题的地方。
- 有没有副作用：改了一个函数，是否影响了其他调用者？公共接口、数据格式、配置含义变了没有，变了有没有同步更新调用方与文档。

### 4.3 测试：新行为有没有测试

- 变更逻辑的测试有没有一起提交？Google 的作者指南要求变更包含相关测试代码，纯重构也应当已有测试覆盖。
- 测试断言是不是具体的（见本批第一篇的标准），而不是“跑通了就行”。
- 测试本身是不是可读的：测试名是否说明了它在验证什么行为。

### 4.4 可读性与风格：未来的人能不能读懂

- 命名是否表达意图：函数名、变量名能不能让没写过这段代码的人猜出用途。
- 注释是否解释“为什么”，而不是复述“做了什么”：代码本身已经说了做了什么，注释要补的是动机与约束。
- 风格是否符合团队已有的风格指南：风格问题上，风格指南是权威，个人偏好不是。没有指南的细节，不要在评审中发明新规则。

### 4.5 文档与配套：变更之外的东西跟上了吗

- 改变了构建、测试、交互或发布方式的变更，相关文档（README、接口文档、配置说明）有没有同步更新？
- 删除或废弃代码时，相关文档是不是也该删？文档与代码不一致，比没有文档更容易误导人。

清单的使用原则：清单是提醒，不是逐项打分的考卷。评审者应当先看设计与功能，再看细节；把全部时间花在格式与命名上、放过了设计问题，是评审最常见的失职。

## 5. 评审文化：怎么给意见、怎么接意见

评审的质量一半在技术，一半在文化。以下做法来自 Google 工程实践文档的评审者与作者指南，是经过验证的通用做法，不是某个团队的内部规定：

### 5.1 作者的责任：让评审者容易评审

- **变更要小、要自包含**：一次变更只做一件事。Google 的作者指南指出，合适的大小通常是“一个自包含的变更”，并给出经验参考：100 行左右通常是合理的大小，1000 行通常太大了；重构应当与功能变更、bug 修复分开提交，小的局部清理可以留在同一个变更里。变更过大时，评审者有权直接要求拆分。
- **写清楚变更说明**：改了什么、为什么改、怎么验证的（跑了哪些测试、结果如何）。评审者不应当靠猜来理解变更。
- **先自审一遍**：提交前自己逐行读一遍 diff，修掉明显的笔误与调试残留。自审能拦下的问题，不应当占用评审者的时间。
- **对意见先理解再回应**：不同意时说明理由与依据，而不是直接关闭评论；确实有道理的意见，改完后明确回复“已改”，让评审者不用重新猜。

### 5.2 评审者的责任：快、准、对事不对人

- **响应要快**：Google 的评审速度指南要求，在不被手头专注任务打断的情况下，收到评审请求后应当尽快响应，一个工作日是响应上限。慢评审的代价是作者的工作被阻塞、上下文冷却后重新预热。
- **先肯定，再提问题**：好的做法值得明确指出——评审不是只找缺点，指出优点能让团队知道什么做法值得推广。
- **区分“必须改”与“建议”**：非关键的建议用明确的标记（例如以 “Nit:” 开头）表示作者可以自行决定，不必为此再跑一轮评审。把所有意见都写成“必须改”，会让评审变成无止境的拉锯。
- **评论针对代码，不针对人**：写“这个函数在空输入时会抛异常”，不要写“你怎么又忘了空输入”。评审评论是会被后人阅读的记录，语气本身就是团队文化的一部分。
- **有分歧时用数据与指南说话**：风格问题看风格指南，设计问题看已有模式与实际约束，争不出结果时升级到共同认可的决策人，而不是在评论区僵持。

### 5.3 评审不是批改作业

评审者不是“上级检查下级”：评审关系应当是对等的——资深者评审新人是传授，新人评审资深者是提问与学习，两种方向都有价值。一个健康的信号是：团队里任何人都可以对任何人的变更提意见，且意见是按内容而不是按资历被采纳的。

## 6. 静态检查与质量门禁：让机器先做一遍

人工评审不应当浪费在机器能发现的问题上。质量门禁是一组自动检查，任何一项不通过，变更就不进入人工评审或不允许合并。常见门禁按引入顺序排列：

| 门禁 | 检查什么 | 说明 |
|---|---|---|
| 格式化与风格检查 | 缩进、命名规范、导入顺序等 | 机器可判定的风格问题全部交给机器，不在评审中讨论 |
| 静态分析 | 未使用变量、可能的空指针、可疑的类型使用等 | 静态分析是在不运行代码的情况下检查代码的手段；它发现的是“可疑模式”，不是确定的 bug，误报需要人工判断 |
| 单元与集成测试 | 提交的测试是否全部通过 | 见本批第一篇：合并前测试失败应当阻塞，而不是只发警告 |
| 安全扫描 | 已知漏洞的依赖、硬编码密钥、可疑的敏感数据处理 | 安全问题见 10 域；门禁的意义是“不要把已知问题合并进去”，而不是“扫过了就安全” |

门禁的设计原则有三条：第一，**快**：门禁跑得越慢，作者绕过它的动机越强，慢的检查应当放在合并后的环节，而不是阻塞提交。第二，**稳定**：门禁本身不稳定（时过时不过）时，团队会学会忽略所有门禁结果——与不稳定测试的处理相同，先隔离修复。第三，**门禁不是目标**：覆盖率、扫描告警数这些数字是指标，不是成绩；把门禁数字当考核，会换来虚假的数字与真实的绕过。

本篇只讲门禁的选型与分工，不写具体工具的安装与配置步骤——不同语言与平台的工具差异很大，具体工具以其官方文档为准。

## 7. 评审流程的一个完整示例（未实测，仅为流程示例）

以下是一个小变更从提交到合并的正常流程，文中人名与时间均为示例，不是真实记录：

1. 作者把“登录失败时返回统一错误信息”的变更拆成一个自包含请求，附带变更说明与新增测试，提交前自审一遍 diff。
2. 格式化检查与静态分析自动运行通过，单元测试全部通过，门禁放行，进入人工评审。
3. 评审者在 4 小时内响应：指出空输入分支缺少测试（必须改），另提一处命名建议（标记为 “Nit:”，作者自定）。
4. 作者补上空输入测试，回复“已改”，并说明命名建议未采纳的理由（与模块内已有命名一致）。
5. 评审者确认修改，批准合并；合并后流水线再跑一次完整测试（见 [CI/CD 流水线设计](../09-cloud-devops/03-cicd-pipeline-design.md)）。

这个流程里，机器负责格式与回归，人工负责设计、边界与可读性——这正是第 6 节分工的落地样子。

## 8. 常见误解与失败模式

- **“评审 = 找 bug”**：错。评审同时是知识传播、标准统一与集体所有权的建立；只盯着 bug 的评审，会错过设计问题，也会让作者把评审当成考试。
- **“评审越严越好”**：错。标准是“确实改善代码健康”，不是“完美”。以完美为标准，变更会长期滞留在评审中，团队速度与士气都会受损。
- **“小变更不用评审”**：错。小变更同样可能改错关键逻辑；评审的成本与变更大小成正比，小变更的评审本来就快，跳过它省不了多少时间，却丢掉了集体所有权。
- **“评审者越多越好”**：错。评审者过多会导致责任分散（都以为别人会仔细看）。通常一名熟悉该模块的评审者加自动门禁就够了，关键变更再加一名。
- **“评审通过 = 没问题”**：错。评审与测试一样，只能提高信心，不能证明没有 bug；上线后的问题复盘，仍然要回到代码与测试本身。

## 9. 小结

好的评审 = 小而自包含的变更 + 机器先过的门禁 + 按清单从大到小看的评审者 + 对事不对人的评论。它的产出不只是一次合并，而是一个“任何人都能接手”的代码库。
