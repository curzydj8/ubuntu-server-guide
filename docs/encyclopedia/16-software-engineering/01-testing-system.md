# 测试体系入门

## 1. 一句话定义

测试体系是一套事先定好的分工与规则：什么风险由哪一层测试来拦、测试跑在什么环节、失败了怎么办，而不是“上线前突击补几个测试”。

## 2. 为什么需要它

只靠人工点一点、上线前测一遍的团队，会在三个地方反复付账。第一，回归成本：每次改动都要重新验证旧功能，改动越大，人工验证越不敢做，最后就不敢改了。第二，定位成本：一个端到端测试失败，只告诉你“流程断了”，不告诉你断在哪个模块。第三，信心成本：没有可重复的检查，发布前只能凭感觉说“应该没问题”。

测试体系要解决的正是这三笔账：把便宜的检查放在前面，把昂贵的检查留给真正值得的地方，让每一次改动都有一个可重复、可定位的验证结果。本篇讲的是体系与策略的制定；单元、集成、端到端各自怎么写、测试替身怎么用，见本站已有文章，只做链接，不重复展开。

## 3. 核心含义

### 3.1 测试金字塔：分工，不是配额

测试金字塔的比喻来自 Mike Cohn 2009 年的《Succeeding with Agile》：底层是单元测试，中间是服务测试（今天多称为集成测试），顶层是界面测试（今天多称为端到端测试）。形状的含义是经济账：底层测试数量多、速度快、定位准；顶层测试数量少、速度慢、维护贵、失败时定位难。

要注意两点。第一，金字塔是启发式，不是法律：它告诉你“便宜的多做、昂贵的少做”，不规定 70/20/10 这样的精确比例——任何声称“标准比例”的数字，本文都不采信，因为不同产品的风险结构不同。第二，金字塔不是全部：金字塔之外还有回归、冒烟、契约、性能、安全等测试类型，它们按目的划分，与金字塔按层划分是两个维度，可以交叉使用（见第 5 节）。

本站已有文章对三层分工已有完整说明，包括金字塔图示与“冰淇淋筒”反模式：[调试与测试方法](../02-programming-basics/03-debugging-testing.md)。本篇不再重画金字塔，只讲如何基于它制定策略。

### 3.2 一个测试应该回答什么

无论哪一层，一个好测试都应该同时满足三条：

- **断言具体**：断言“等于 80.0”，不要断言“大概对”或“没有抛异常”。没有具体断言的测试，失败时也提供不了信息。
- **可重复**：同样的代码、同样的输入，每次结果都一样。不依赖当前时间、随机数、外部网络或测试执行顺序。
- **失败可定位**：测试名与失败信息要能让人一眼看出“哪个行为、哪个条件”出了问题。测试名写成 `test_正常折扣` 不如写成 `test_折扣率为零时原价返回`（见下例的命名思路）。

下面的 Python 单元测试示例在本地实测通过（Python 3.12.3），它同时示范了正常值、边界值、非法输入三类断言：

```python
import unittest
from discount import discount

class TestDiscount(unittest.TestCase):
    def test_normal(self):
        self.assertEqual(discount(100, 0.2), 80.0)
    def test_boundary_zero_rate(self):
        self.assertEqual(discount(100, 0), 100.0)
    def test_invalid_rate(self):
        with self.assertRaises(ValueError):
            discount(100, 1.5)
```

实测输出：

```
test_boundary_zero_rate (test_discount.TestDiscount.test_boundary_zero_rate) ... ok
test_invalid_rate (test_discount.TestDiscount.test_invalid_rate) ... ok
test_normal (test_discount.TestDiscount.test_normal) ... ok

----------------------------------------------------------------------
Ran 3 tests in 0.000s

OK
```

其中 `discount` 在价格为负或折扣率超出 0 到 1 时主动抛出 `ValueError`，而不是返回一个含糊的结果——非法输入的行为本身就是应当写进测试的契约。

### 3.3 风险驱动：先排风险，再排测试

制定策略的第一步不是“写多少测试”，而是“列出最怕什么”。按风险排测试，常见的问题清单是：

1. **钱与数据**：支付、计费、余额、数据写入——错了无法挽回或难以挽回，优先覆盖，且至少一部分用真实依赖验证。
2. **权限与安全**：越权访问、敏感数据泄露——见 10 域相关文章，本篇只定策略：安全测试不能只靠“功能测通了”。
3. **主干流程**：登录、下单、支付、核心工作流——端到端测试只覆盖这些，不覆盖全部细节。
4. **边界与异常**：空值、零值、超大值、超时、第三方失败——单元与集成层最容易覆盖的地方。
5. **契约**：模块之间、服务之间约定的参数格式与返回结构——集成与契约测试的领地。

风险清单确定后，再反推每一层要补什么：如果“支付金额算错”排第一，单元测试里就要有金额计算的边界用例，而不是先去写十个界面点击测试。

## 4. 测试策略制定：从现状到可执行规则

### 4.1 四步制定法

1. **盘点现状**：现有测试分几层、跑一次多久、最近一个月最常失败的是哪一类、失败后平均多久能定位。没有这组数字，策略就是空话。
2. **定分层目标**：给每一层写一句话目标，例如“单元层：所有金额计算与规则分支有测试；集成层：所有对外接口契约有测试；端到端层：五条主干流程有测试”。目标写具体行为，不写“提高覆盖率”。
3. **定执行环节**：哪些测试在提交前跑、哪些在合并前跑、哪些在发布前跑。原则是越便宜的越早跑：单元测试提交前就跑，端到端测试可以放在合并或发布环节。流水线设计本身见 [CI/CD 流水线设计](../09-cloud-devops/03-cicd-pipeline-design.md)，本篇只定“测试放在哪一环”的原则，不展开流水线配置。
4. **定失败规则**：测试失败时怎么办，是阻塞合并还是只发警告？默认建议是：提交前与合并前的测试失败应当阻塞——否则测试会迅速变成“没人看的报告”。例外要明文写出（例如已知的不稳定测试先隔离修复，而不是直接放行）。

### 4.2 覆盖率的正确用法

覆盖率（跑测试时实际执行到的代码比例）是参考指标，不是目标。它的合理用法有三种：发现完全没测到的模块、对比两次改动的覆盖变化、为新代码设定一个下限参考。它的误用只有一种，却很常见：把“覆盖率达到某个百分比”当成绩单。100% 覆盖但断言空洞的测试等于没有测试；反过来，核心金额计算 100% 覆盖、界面文案 0% 覆盖，可能是完全合理的分配。

### 4.3 不稳定测试（flaky test）的处理

时过时不过的测试比没有测试更糟：它会让人对测试结果麻木，最后没人看测试报告。处理流程应当是固定的：先隔离（标记并移出阻塞环节，避免阻塞所有人），再定位根因（最常见的是时间依赖、测试间共享状态、外部服务不稳定），修好后再放回阻塞环节。禁止的做法是“重试几次直到通过”——重试掩盖了不确定性，没有消除它。

### 4.4 回归测试与冒烟测试的位置

- **回归测试**：改动后确认旧功能没坏的测试集合。它不是一种独立的测试层，而是从各层测试里挑出来的“改动相关 + 历史上出过问题的用例”的组合。每修一个 bug，至少补一个能复现该 bug 的回归用例，否则同一个 bug 会反复出现。
- **冒烟测试**：主干流程的快速过一遍，部署后先跑它，再跑完整套件。它的价值是“快速发现部署本身坏了”，而不是“验证全部功能”。

## 5. 金字塔之外的测试类型

按目的划分的测试类型，按需引入，不必一开始全上：

| 类型 | 回答的问题 | 典型位置 |
|---|---|---|
| 契约测试 | 服务之间的接口约定有没有被悄悄改坏 | 集成层，服务边界 |
| 性能测试 | 负载下的响应与资源占用是否可接受 | 发布前，独立环境 |
| 安全测试 | 是否存在越权、注入、敏感信息泄露 | 见 10 域，独立于功能测试 |
| 手工探索测试 | 自动化没想到的路径有没有问题 | 发布前，针对新功能 |

手工测试不是“落后”的代名词：自动化擅长重复验证已知行为，手工探索擅长发现未知行为。两者分工，不是替代关系。

## 6. 限制与常见误解

- **测试通过不能证明没有 bug**：测试只能证明“测过的场景是对的”，没测的场景仍然未知。这是测试体系的根本边界，不是执行不到位。
- **金字塔倒过来（端到端最多）是反模式**：跑得慢、坏了定位难、维护成本高。出现这种形状时，通常是中间层（服务/集成）被跳过了。
- **“先写功能、以后再补测试”**：以后往往没有以后。至少做到：修 bug 时先补复现测试再修，新功能的核心分支随功能一起提交测试。
- **“测试是测试人员的事”**：开发写单元与集成测试、测试人员做探索与端到端设计，是更常见的分工；但“谁写”可以分工，“有没有测试”不能推给某一方。

## 7. 小结

测试体系 = 按风险排优先级 + 按金字塔分层 + 按环节定执行规则 + 失败必阻塞。它不追求测试数量最多，而追求“最怕出错的地方一定有可重复的检查”。
