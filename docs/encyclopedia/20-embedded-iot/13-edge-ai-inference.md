# 边缘 AI 推理部署

## 1. 本章目标

读完本篇能理解：为什么模型训练放云端、推理放边缘；量化与剪枝在概念上做了什么；NPU、GPU、专用加速卡等推理硬件形态各有什么特点；以及延迟、功耗、隐私三方面的权衡如何影响选型。

## 2. 背景与问题

机器学习模型要落地到现场设备，会遇到一组云端不存在的约束：现场网络可能中断、往返云端的延迟可能超过业务容忍、原始数据（例如摄像头画面、产线图像）传上云既占带宽又有隐私顾虑。把所有推理都放云端，等于把现场的实时性与可用性交给了网络。

边缘 AI 推理的思路是把分工拆开：在云端做重活（训练），在边缘做轻活（推理）。训练需要海量数据与大算力、可以离线慢慢跑；推理只需要一个已训练好的模型与一次前向计算，可以在现场毫秒级完成。拆开之后，现场设备在断网时仍能识别、分类、告警，原始数据不必离场，只有推理结果与少量样本需要上报。本篇讲部署的分工与取舍；模型本身怎么训练与评估，见 17 域相关文章。

## 3. 总体架构

云训边推的完整链条（文字结构图）：

```
云端（训练侧）
 ├── 数据汇聚（各边缘节点上报的样本与标注）
 ├── 模型训练（大算力、长时间、离线完成）
 └── 模型轻量化（量化、剪枝，见 4.2）
        ↓ 模型下发（版本化、可回滚）
边缘侧（推理侧）
 ├── 边缘网关 / 边缘设备（见本域《边缘网关架构》）
 ├── 推理运行时（加载模型、做前向计算）
 ├── 推理硬件（NPU / GPU / 专用加速卡 / CPU，见 4.3）
 └── 本地动作（规则引擎联动、告警、执行器控制）
        ↓ 结果与样本上报（可选、按需）
云端（运营侧）
 ├── 效果监控（推理结果分布、异常样本回收）
 └── 模型迭代（用新样本再训练 → 下发新版本）
```

这条链是一个闭环，不是一次性下发：边缘的推理效果要回流到云端，模型才能持续改进；模型版本要可管理，出了问题能回滚到上一版。只讲“把模型拷到设备上”而不讲版本与回滚，是部署设计里最常见的缺口。

## 4. 工作机制

### 4.1 云端训练、边缘推理的分工

分工的依据是两种计算的性质不同：

- **训练**：要反复遍历数据集、算梯度、调参数，算力与内存需求大，对延迟不敏感，可以集中到云端的大算力集群上离线完成；训练过程还需要数据科学家介入调参与评估，集中做更方便。
- **推理**：对一个已训练好的模型做一次前向计算，输入一张图、一段音频或一组传感器读数，输出一个分类、检测或预测结果。单次计算量远小于训练，对延迟敏感，且常常要在断网时也能工作，因此适合放在边缘。

分工不是绝对的：小模型可以在边缘做增量学习或微调，大模型也可以在云端做推理；具体划在哪条线，取决于模型大小、现场算力、延迟要求与数据隐私要求四项（见第 5 节）。新手容易犯的错误是把训练代码原样搬到边缘——训练用的框架、优化器、数据管线在推理侧大多是多余的负担，推理侧只需要“加载模型 + 前向计算”这一条最小链路。

### 4.2 模型轻量化：量化与剪枝的概念

云端训出的模型往往太大、太慢，直接放到边缘设备上跑不动。轻量化是部署前的必经步骤，两个最常用的概念：

- **量化（quantization）**：把模型参数与中间计算从高精度浮点数（例如 32 位）换成低精度表示（例如 8 位整数）。直观理解是“用更粗的刻度去量同一个东西”：存储占用与计算量随之下降，推理速度上升，代价是精度会有损失。损失多大取决于模型与任务——有的任务量化后几乎不受影响，有的则明显下降，因此量化后必须重新评估精度，不能只看速度提升。量化更完整的原理与精度取舍见 18 域《量化与推理优化》。
- **剪枝（pruning）**：去掉模型中对结果贡献很小的连接或整个通道（例如某些神经元的权重长期接近零），让模型变小、变稀疏。剪枝后通常要再训练一轮（微调）把精度恢复一部分，再部署。剪枝与量化可以叠加使用，但叠加后的精度损失也要重新评估，不能假设两者互不影响。

除此之外还有知识蒸馏（用大模型教小模型）与结构设计（直接设计轻量网络）等路线，本篇只点出概念，不展开方法。轻量化的总原则是：**精度、体积、速度三者不可兼得**，任何轻量化方案都要在具体任务上实测精度损失，不能只凭概念判断“够不够用”。

### 4.3 推理硬件形态

边缘推理的硬件有四种常见形态，区别主要在“为谁优化”：

- **CPU 推理**：用设备已有的通用处理器跑推理，不加额外硬件。优点是零新增成本、部署最简单；限制是算力与能效比低，只适合小模型与低频推理（例如每秒几次的传感器分类）。
- **GPU 推理**：用图形处理器的并行计算能力跑推理。优点是通用性好、生态成熟、大小模型都能跑；代价是功耗与成本较高、体积较大，适合对算力要求高、供电与散热有保障的边缘节点（例如带 GPU 的边缘服务器、工控机）。
- **NPU（神经网络处理单元）**：为神经网络计算专门设计的加速单元，常见于手机 SoC 与边缘 AI 芯片中。优点是能效比高（单位功耗的推理能力强）、适合持续运行的端侧推理；限制是只加速特定算子与模型结构，模型要按 NPU 支持的算子集做适配，不支持的算子会回落到 CPU 上跑，实际速度以实测为准。
- **专用加速卡 / 模组**：以 PCIe 加速卡、USB 加速棒、AI 模组等形式外挂的专用推理硬件。优点是不用换整机、按需叠加算力；限制是与主机之间的数据搬运可能成为瓶颈，且不同加速卡的软件栈与模型格式各不相同，存在锁定风险。

四种形态的算力、功耗、价格等具体数值因型号与测试条件而异，以官方发布为准（待核实）；本篇不做任何算力排名，不声称某类硬件“最强”。

### 4.4 部署流水线：模型上下发的最小闭环

一次可用的边缘推理部署至少包括四步：**模型转换**（把训练框架的模型转成推理侧的格式，转换后要核对精度是否一致）、**打包**（模型文件 + 推理运行时 + 配置打成一个可部署的包）、**下发**（按设备分组灰度推送，先小批量验证再全量）、**回滚**（新版本出问题时能快速回到上一版）。四步缺一不可：没有灰度与回滚的下发，等于把全网设备当成试验场。部署流水线的具体工具与命令因平台而异，本篇不写操作步骤。

## 5. 关键设计取舍

- **延迟**：本地推理省掉一次网络往返，是实时场景（例如产线缺陷检测、跌倒告警）选边缘的首要理由。但“本地”不等于“实时”——模型太大、硬件太弱时，本地推理本身也可能比业务 deadline 还慢，延迟要按端到端实测，不能只算网络那一段。
- **功耗**：边缘设备常靠电池或受限供电，推理的功耗预算直接决定硬件选型与模型大小。NPU 与专用加速卡的价值正在于能效比而非峰值算力；但能效比的具体数值以官方发布为准（待核实），不同测试条件下的数字不可直接比较。
- **隐私**：原始数据不出场是边缘推理最强的隐私论据——摄像头画面、产线图像、语音只在本地处理，只把脱敏后的结果上报。但隐私不是“放边缘就自动合规”：推理结果本身也可能含敏感信息（例如识别出某个人），上报什么、留存多久、谁能访问，仍要按合规要求设计；边缘设备丢失或被拆出模型也是真实风险，模型文件与设备访问控制要一起考虑。

三者常常互相牵制：要更低的延迟就要更大的算力，更大的算力就要更高的功耗；要更强的隐私就要数据不出场，不出场就难做云端的大模型迭代。没有三者全优的方案，选型就是在具体业务约束下排优先级。

## 6. 分类与变体

### 6.1 按推理位置分

- **端侧推理**：模型跑在终端设备本身（摄像头、传感器节点、手机），延迟最低、隐私最好，但算力与功耗约束最严。
- **网关推理**：模型跑在边缘网关上，汇聚多台终端的数据做推理，算力比单台终端强，适合一对多的场景（例如一个网关管多路摄像头）。
- **边缘服务器推理**：模型跑在现场的边缘服务器上，算力最强，可跑较大模型，适合园区、工厂等有固定机房的场景。

### 6.2 选型维度

选硬件与模型时按六个维度打分，而不是只看算力：延迟要求（业务 deadline 是多少）、功耗预算（电池还是市电）、模型大小与算子支持（目标硬件能不能跑这个模型）、成本（硬件 + 开发 + 维护）、隐私与合规（数据能不能出场）、可维护性（模型更新、回滚、监控怎么做）。任何只谈算力的选型结论都是不完整的。

## 7. 应用与限制

典型应用：工业质检（产线图像缺陷检测）、安防与周界监控（本地识别、只上报事件）、智慧农业（病虫害图像识别）、零售（客流统计、货架识别）、语音唤醒与本地语音指令。限制有四条：边缘算力有硬上限，大模型与高分辨率实时视频推理仍需云端或边缘服务器；模型在边缘的表现可能与云端评估不一致（现场光照、角度、噪声不同），上线前要在现场数据上验证；模型更新与监控是长期负担，不是“一部署就完事”；最后，边缘推理不解决数据质量问题——传感器脏数据喂给再好的模型，输出也是脏结果。

## 8. 常见误解

- “边缘推理就是把云端模型拷到设备上”：错。拷过去之前要经过轻量化、格式转换、精度复评，拷过去之后还要有版本管理、灰度与回滚。
- “量化只会让模型变快，不会变差”：错。量化一定有精度损失，只是有的任务损失小到可接受；不经评估就量化，等于在不知道代价的情况下做交易。
- “算力越高推理越快”：错。推理速度还取决于模型与硬件算子的匹配、内存带宽、数据搬运开销；不支持的算子回落到 CPU 上跑时，峰值算力再高也没用。具体数值以官方发布为准（待核实），不做排名。
- “数据放边缘就自动合规”：错。边缘只是让原始数据不必离场，推理结果的采集、留存与访问仍要符合隐私与合规要求。
