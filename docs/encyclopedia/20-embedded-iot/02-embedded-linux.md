# 嵌入式 Linux：启动流程、设备树与交叉编译

## 1. 本章目标

读完本篇能理解：一台跑 Linux 的嵌入式设备从上电到应用启动经历了哪些阶段，设备树为什么存在，根文件系统里有什么，以及交叉编译中宿主机、目标机、工具链各自的分工。

## 2. 背景与问题

上一篇的 MCU 能胜任控制任务，但遇到三类需求就会吃力：要跑网络协议栈和文件系统、要处理多媒体、应用逻辑复杂到需要进程隔离和动态加载。这时就需要一个真正的通用操作系统，而 Linux 是嵌入式领域最常见的选择：内核成熟、驱动生态丰富、不要授权费。

但桌面 Linux 不能直接装到嵌入式板子上。板子的存储只有几十到几百 MB、内存有限、外设五花八门、启动时间有要求。嵌入式 Linux 的全部工作，就是围绕“裁剪”和“适配”：把 Linux 裁到刚好够用，把板子特有的硬件信息以一种不改内核代码的方式交给内核。后者就是设备树的由来。

## 3. 总体架构

一台嵌入式 Linux 设备的启动链条（文字结构图）：

```
上电
 └─ 片上 BootROM（固化在芯片里，第一段代码，不可改）
     └─ Bootloader（通常是 U-Boot：初始化内存、加载内核）
         └─ Linux 内核（解压、初始化、挂载根文件系统）
             ├─ 设备树（DTB：描述板子硬件的二进制数据，内核据此找驱动）
             └─ 根文件系统（init 程序、库、工具、配置文件）
                 └─ init 进程（启动系统服务）
                     └─ 应用程序（业务逻辑）
```

这条链每一环只做一件事，出了问题也按这个顺序排查：起不来先看 Bootloader 输出，再看内核日志，最后看根文件系统。

## 4. 工作机制

### 4.1 启动流程：每一阶段的职责

- **BootROM**：芯片上电后唯一能执行的代码。它初始化最基本的时钟和内存，寻找可启动介质（SD 卡、eMMC、Flash、网络），把下一段程序搬进来。BootROM 是芯片厂商固化的，改不了，出问题只能换启动介质或启动模式引脚。
- **Bootloader（以 U-Boot 为例）**：初始化 DRAM、串口、存储控制器；提供命令行，可以读写 Flash、设置启动参数、通过网络下载内核调试；最后把内核镜像和设备树 blob（DTB）加载到内存，把执行权交给内核，并传一个关键参数：DTB 的地址。
- **内核启动**：解压自身，初始化调度器、内存管理、中断子系统；解析 DTB，按描述去匹配驱动（例如“这个地址有一块 I2C 控制器”）；挂载根文件系统；启动第一个用户态进程 init。内核日志（dmesg）是排查启动问题的主要依据：驱动没匹配上、根文件系统挂载失败，都会在这里留下记录。
- **init 与用户态**：嵌入式系统常用 BusyBox 提供精简版 init 和常用命令（sh、mount、ifconfig 等），或用 systemd（功能全、体积大）。init 按配置启动网络、挂载分区、拉起业务应用。至此，设备才算“起来了”。

### 4.2 设备树：硬件描述与内核代码解耦

在设备树出现之前，每块板子的硬件信息是写进内核代码里的：板子一多，内核里就堆满了各家板子的“特例代码”。设备树的思路是把“板子长什么样”抽出来，用一种树形数据（DTS 源文件，编译成 DTB）单独描述：

- 节点表示一个硬件：CPU、内存、串口控制器、I2C 控制器、挂在 I2C 上的传感器。
- 属性描述关键信息：寄存器地址、中断号、时钟来源、引脚复用。
- 内核启动时读 DTB，按“兼容字符串”（compatible）匹配驱动：驱动只认“我能驱动这类硬件”，不认具体板子。

这样做的好处：同一份内核可以跑在多块板子上，换板子只要换 DTB，不用重新编译内核。两个常见误解需要纠正：第一，设备树不是驱动，驱动还是内核代码，设备树只是告诉内核“硬件在哪”；第二，写错设备树不会报语法错，只会表现为“驱动没加载”或“外设不工作”，排查时要对照芯片手册核对地址和引脚。

### 4.3 根文件系统：不只是“放文件的地方”

根文件系统是内核挂载的第一个文件系统，里面至少要有：init 程序、动态链接库、设备节点、基本配置文件（fstab、网络配置）、常用工具。嵌入式根文件系统有两个设计要点：

- **BusyBox 一体化**：一个二进制提供几百个精简命令，大幅省体积，是资源受限设备的常规选择。
- **分区策略**：系统分区常设为只读（掉电不怕写坏），数据分区单独可写；要求可靠升级的设备会做 A/B 双分区，升级失败回滚到旧分区。这部分与 09 域的部署和 06 域的备份恢复思想相通，本篇只讲嵌入式侧的形态。

### 4.4 交叉编译：宿主机、目标机、工具链的分工

目标板算力弱、存储小，在板子上直接编译大工程既慢又占地方。交叉编译的做法是：在性能强的宿主机（通常是 x86 电脑）上，用一套“运行在宿主机、生成目标机代码”的工具链编译，再把产物传到板子上跑。

- **宿主机（host）**：编译发生的机器。
- **目标机（target）**：程序最终运行的板子，架构常与宿主机不同（例如 ARM）。
- **工具链三元组**：形如 `arm-linux-gnueabihf` 的名字本身就是信息——目标架构（arm）、操作系统（linux）、C 库与浮点 ABI（gnueabihf 表示硬浮点）。三元组对不上，编出来的程序在板子上跑不起来，这是交叉编译最常见的报错来源。
- **sysroot**：目标机的头文件和库文件在宿主机上的一份副本，编译时链接的是它，不是宿主机的库。链接了宿主机库是另一类典型错误。
- **构建系统分工**：Buildroot（配置简单、出包快，适合单一产品）与 Yocto（分层灵活、可复现性强，适合产品线）是两种主流选择；概念上都是“描述要什么 → 自动编出内核、根文件系统、工具链”，选型看产品复杂度，不展开操作步骤。

## 5. 关键设计取舍

- **裁剪换体积与启动速度**：内核功能、驱动、用户态工具都要按需取舍，裁得多启动快、体积小，但后续加功能要重新出包；裁得少灵活，但体积和启动时间上去。取舍标准是产品需求，不是“越小越好”。
- **实时性换通用性**：标准 Linux 内核不保证硬实时；需要硬实时时用 PREEMPT_RT 实时补丁或把实时部分放到 MCU/协处理器上（异构分工），而不是指望通用内核“尽量快”。
- **可维护性换定制深度**：直接改内核源码定制最快见效，但后续跟进上游内核升级最痛苦；能用设备树、内核模块、用户态解决的，优先不改内核。

## 6. 分类与变体

- **按启动介质**：SD 卡启动（开发调试方便）、eMMC/Flash 启动（量产可靠）、网络启动（批量烧录与无盘场景）。
- **按根文件系统形态**：initramfs（打包进内核，适合恢复与安装场景）、独立根分区（常规产品）、只读系统 + 可写数据分区（高可靠产品）。
- **按构建系统**：Buildroot、Yocto，以及直接用发行版裁剪（例如 Debian 的嵌入式变体，适合对软件生态要求高的场景）。

## 7. 应用与限制

典型应用：路由器、工控机、车机、网络摄像头、智能家居中控。限制有四条：启动时间通常以秒计，做不到 MCU 的毫秒级上电即工作；存储和内存仍有限，大型应用要评估；功耗高于 MCU 方案，电池设备要算账；长期维护负担真实存在——内核与开源组件的安全更新要跟进，不能“一版固件用终身”。边缘计算（把一部分计算放在设备本地而不是全送云端）是嵌入式 Linux 设备的常见角色，但边缘计算的体系与调度属于 18 域，本篇只提一句，不展开。

## 8. 常见误解

- “嵌入式 Linux 就是把桌面 Linux 装到小板上”：错。桌面发行版的包体积、启动流程、功耗假设都不适合嵌入式板子，裁剪和适配是本体工作。
- “设备树就是驱动”：错。设备树是硬件描述，驱动是内核代码；设备树错了表现为驱动不加载，不是驱动本身有问题。
- “交叉编译只是换个 gcc”：错。工具链三元组、sysroot、目标机 C 库都要对齐，任何一环错位都会在链接或运行时暴露。
- “板子上编不过就换更大的板子”：错。先分清是资源不够、工具链不对还是代码本身的问题，换板子掩盖不了工具链错误。
