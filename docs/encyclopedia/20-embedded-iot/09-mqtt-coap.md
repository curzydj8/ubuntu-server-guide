# MQTT/CoAP 协议与选型

## 1. 对比背景

设备把数据采集到本地之后，下一个问题是：怎么把消息送出去、送给谁。板内总线（I2C/SPI/UART，见上一篇）只解决板子内部的传输，出了设备、经过网络，问题就变了：网络不可靠、设备会掉线、接收方可能有多个、设备资源极其有限。

MQTT 与 CoAP 是这个层面最常见的两种协议，解决的是同一个问题——**资源受限设备如何与服务端交换消息**——但走的是两条不同的路：MQTT 是基于 TCP 的发布/订阅消息分发，CoAP 是基于 UDP 的轻量 REST 风格请求/响应。选错的代价真实存在：拿 MQTT 做毫秒级控制回路会死于延迟，拿 CoAP 做一对多广播会死于逐个请求。读完本篇能按场景选出合适的协议。

本篇是[传感器与通信协议](03-sensors-protocols.md)的深入篇：03 篇讲 MQTT 的定位与三个关键机制，本篇展开 MQTT 的完整模型并补上 CoAP 的全貌，两篇不重复抄写。

## 2. MQTT：发布/订阅的消息分发

### 2.1 模型：发布者、订阅者与 Broker

MQTT（Message Queuing Telemetry Transport）是 OASIS 标准的消息协议，基于**发布/订阅模型**，不直接点对点：

```
设备 A（发布者）──┐
                   ▼
              Broker（中转服务器）
                   ▼
设备 B / 云端应用（订阅者）
```

设备（客户端）连接到 Broker（中转服务器），发布者把消息发到一个**主题**（topic，例如 `home/livingroom/temperature`），订阅了该主题的接收者从 Broker 收到消息。发布者和订阅者互不知道对方存在，只通过主题解耦：发布者不用知道谁在听，订阅者不用知道谁在发；一方掉线不影响另一方继续工作（只要 Broker 还在）。

这种解耦是 MQTT 的全部价值所在：设备数量、接收方数量可以独立增长，系统拓扑变化时不用改设备固件，只改订阅关系。

### 2.2 主题与通配符

主题是层级结构，用 `/` 分隔（例如 `home/livingroom/temperature`）。订阅时可用两个通配符做批量订阅：

- `+`：匹配**一层**，例如 `home/+/temperature` 订阅所有房间的温度。
- `#`：匹配**多层**（必须在末尾），例如 `home/#` 订阅 home 下的一切。

主题设计是系统设计的一部分，不是事后命名：层级太扁，订阅方收不到想要的分组；层级太深、通配符滥用，Broker 的匹配开销与误发风险上升。设备上线前就要定好主题命名规范，并把它写进系统文档。

### 2.3 QoS 三档：丢、重复、恰好一次

QoS（服务质量）是 MQTT 最核心的取舍点，三档的保证与代价各不相同：

| 等级 | 保证 | 机制 | 代价 |
|---|---|---|---|
| QoS 0 | 最多送一次（可能丢） | 发了就不管，无确认 | 最小开销、最低延迟；网络丢包即丢消息 |
| QoS 1 | 至少送一次（可能重复） | 发布 → 确认（PUBACK），无确认则重发 | 接收方可能收到重复消息，要自己去重 |
| QoS 2 | 恰好送一次 | 四步握手（发布 → 收到 → 释放 → 完成），去重在协议层 | 握手最多、开销最大 |

选哪档看业务对“丢”和“重复”哪个更不能忍，不是越高越好：温度定时上报丢一两条无所谓，用 QoS 0；门锁状态、告警这类“丢了会出事”的消息，用 QoS 1 并在接收方做幂等去重；计费、指令这类“重复执行会出事”的消息，才考虑 QoS 2。QoS 2 保证的是“恰好送达”，不是“实时送达”——延迟敏感的控制回路不要走 MQTT，见 6.2 节。

### 2.4 保留消息与遗嘱

**保留消息（Retained Message）**：发布时打上保留标志，Broker 会存下该主题最新的一条保留消息。新订阅者一订阅就立刻收到这条消息，不用等下一次发布。典型用途是设备状态：订阅 `home/livingroom/light/status` 立刻知道灯当前是开是关，而不是等灯下次变状态才知道。每个主题只有一条保留消息，新保留消息会覆盖旧的；发一条空载荷的保留消息可清除它。

**遗嘱消息（Last Will and Testament）**：设备连接时预先把一条“遗言”存在 Broker 处，约定“如果我异常断线，就替我发这条消息”。正常断开（主动发断开包）不触发遗嘱，只有异常掉线（网络中断、断电、崩溃）才触发。订阅方据此知道“它掉了”，而不是永远等一个再也不会来的上报。遗嘱是 MQTT 里最被低估的机制：没有它，系统分不清“设备没数据”和“设备已死”。

### 2.5 会话、Keep Alive 与连接

- **会话（Session）**：客户端连接时声明是否使用持久会话。持久会话下，Broker 记住该客户端的订阅关系与未送达的 QoS 1/2 消息，重连后补发离线期间的消息；非持久会话则重连后一切重来。是否持久，看业务能不能接受“离线消息补发”与“Broker 侧的状态开销”。
- **Keep Alive**：客户端与 Broker 约定一个心跳间隔，超过间隔无任何报文，任一方可判定连接已死并断开。心跳太短费电费流量，太长则“设备已死”发现得太晚；电池设备的取值要结合功耗预算。
- **默认端口**：明文 MQTT 默认 1883，TLS 加密的 MQTT 默认 8883。生产环境必须走 TLS 并做客户端认证，只做“能连上”而不做认证与加密的 Broker 等于把设备控制权敞开，见 5.3 节。
- **版本**：当前主流是 OASIS MQTT 5.0（在 3.1.1 基础上增加了原因码、共享订阅、主题别名、消息过期、用户属性等；3.1.1 设备与 5.0 Broker 之间以协商后的版本工作，具体以 OASIS 规范为准）。新项目优先用 5.0，老设备沿用 3.1.1 时注意两者在会话与错误码上的差异。

## 3. CoAP：UDP 上的轻量 REST

### 3.1 定位：给极低功耗设备的“精简版 HTTP”

CoAP（Constrained Application Protocol）由 IETF CoRE 工作组制定（RFC 7252，2014 年），是为**受限节点与受限网络**（内存以 KB 计、链路低速易丢包，例如 6LoWPAN）设计的应用层协议。它的思路是：保留 HTTP 的 REST 模型（对资源做 GET、POST、PUT、DELETE，用 URI 定位资源，用响应码表示结果），但把传输层换成 UDP、把报文压到最小。

一个 CoAP 请求长这样（概念示意，示例未实测）：

```
GET coap://[设备地址]/sensors/temperature
→ 2.05 Content（响应码，含义类比 HTTP 200）
→ 载荷：23.5
```

会用 HTTP 的人几乎不用学新概念就能用 CoAP——这是它相对 MQTT 的学习成本优势。但 CoAP 不是“跑在 UDP 上的 HTTP”：它在消息层自己补了可靠性与异步订阅，见下两节。

### 3.2 报文结构与四种消息类型

CoAP 报文头固定只有 **4 字节**（版本、消息类型、Token 长度、方法/响应码、16 位消息 ID），之后是 0–8 字节的 Token、选项与可选载荷。4 字节头是 CoAP“轻量”的直接体现：HTTP 的文本头在低速链路上本身就是负担。

四种消息类型（RFC 7252）：

| 类型 | 含义 | 用途 |
|---|---|---|
| CON（Confirmable） | 需要确认 | 要求对方回 ACK；无 ACK 则按退避策略重发 |
| NON（Non-confirmable） | 不需要确认 | 发了不管，类比 QoS 0；用于周期性上报等可丢场景 |
| ACK（Acknowledgement） | 对 CON 的确认 | 可捎带响应内容（ piggybacked response） |
| RST（Reset） | 拒绝/重置 | 对方表示“收到了但无法处理”，例如重启后不认识该消息 ID |

**消息 ID**用于去重与匹配确认，**Token**用于把响应与请求对应起来（一个客户端可并发多个请求，靠 Token 区分）。可靠性是可选的、按消息选的：重要请求用 CON，不重要的用 NON——与 MQTT 的 QoS 分档思路相通，只是粒度在每条消息而不在订阅关系。

### 3.3 观察模式：不用轮询的订阅

CoAP 的基础模型是请求/响应（客户端问、服务端答），但物联网需要“值变了就通知我”。轮询（客户端隔几秒问一次）既费电又延迟大，CoAP 用**观察模式（Observe，RFC 7641）**解决：

客户端在 GET 请求里附带 Observe 选项，服务端登记一次“观察关系”，之后资源值每次变化就主动向客户端推送通知，客户端不用再问。观察关系可由客户端取消、由服务端在资源删除时终止；通知本身可以是 CON 或 NON，丢失的通知由下一次通知自然覆盖——观察的是“最新值”，不是“每一次变化”，丢一条通知不会造成永久偏差。

观察模式与 MQTT 订阅的对比：MQTT 的订阅是 Broker 中转的一对多广播，订阅方与发布方完全解耦；CoAP 的观察是客户端与资源所在设备之间的直接关系，是一对一（或一对有限多）的直连。需要跨设备、跨网络的广播分发时，MQTT 更合适；设备之间直接对话时，CoAP 更轻。

### 3.4 资源发现与块传输

- **资源发现**：CoAP 设备在 `/.well-known/core` 路径上提供资源列表，客户端先问“你有什么资源”，再按需访问。这是 REST 风格的自然延伸，也是设备自描述的基础。
- **块传输（Block-wise Transfer，RFC 7959）**：固件升级、大配置下发这类超过单报文承载能力的载荷，用分块传输拆成多块逐块发、逐块确认。需要大载荷时不必因此换协议，但要确认两端实现都支持该扩展。
- **其他传输**：CoAP 默认走 UDP，也可走 TCP、TLS 与 WebSocket（RFC 8323），安全传输用 DTLS（CoAPS，默认端口 5684；明文默认端口 5683）。UDP 仍是 CoAP 的主场景，TCP 形态用于 UDP 受限的网络环境。

## 4. 资源占用与可靠性对比

| 维度 | MQTT | CoAP |
|---|---|---|
| 传输层 | TCP（长连接） | UDP（无连接，默认） |
| 交互模型 | 发布/订阅，Broker 中转 | 请求/响应 + 观察，直连 |
| 默认端口 | 1883（明文）/ 8883（TLS） | 5683（明文）/ 5684（DTLS） |
| 报文开销 | 固定头 2 字节起，主题字符串占大头 | 固定头 4 字节，二进制编码 |
| 可靠性机制 | QoS 0/1/2（订阅级） | CON/NON（消息级）+ 消息 ID 去重 |
| 订阅/推送 | 原生：主题订阅，Broker 广播 | Observe 选项，服务端直推 |
| 保留/离线 | 保留消息、持久会话补发离线消息 | 无 Broker、无保留；观察丢通知由下次通知覆盖 |
| 设备资源占用 | 需维持 TCP 长连接与 Broker 会话，内存与功耗较高 | 无连接、报文小，极低功耗设备友好 |
| 一对多分发 | 原生强项 | 需逐个请求/观察，不擅长广播 |
| 安全 | TLS + 用户名/密码或证书 | DTLS（CoAPS）或 OSCORE（以规范为准） |
| 适用网络 | 网络相对稳定、能维持长连接 | 低速、易丢包、间歇连接的受限网络 |

### 关键差异展开

**差异一：有没有中间人。** MQTT 的 Broker 是架构的一部分：它带来解耦与广播能力，也带来单点依赖——Broker 挂了全网消息就断，生产要做高可用；同时所有消息都经过 Broker，延迟与 Broker 性能挂钩。CoAP 没有中间人，设备之间直连，少了单点故障，但也少了“一个发布、多方接收”的天然能力。选型时先问：系统里有没有“一个消息要发给多个接收方”的需求？有，MQTT 优先；没有，CoAP 的轻量才有意义。

**差异二：可靠性的粒度。** MQTT 的 QoS 是订阅关系的属性：订阅时定 QoS，之后该订阅的所有消息都按此保证。CoAP 的 CON/NON 是每条消息的属性：重要请求用 CON、周期上报用 NON，同一连接内可混合。MQTT 的 QoS 2 提供“恰好一次”的协议级保证，CoAP 的 CON 只保证“至少一次送达 + 消息 ID 去重”，语义上弱一档。计费、指令下发这类“重复执行会出事”的场景，MQTT QoS 2 更合适；传感器读数这类“丢一条无所谓、重复一条也无所谓”的场景，两者都够用。

**差异三：资源占用的量级。** CoAP 为“KB 级内存、电池供电数年”的设备而生：无连接、4 字节头、按需收发。MQTT 的 TCP 长连接要维持会话状态、处理心跳、缓存离线消息，内存与功耗都高一档。设备资源紧张到“跑不起 TCP 长连接”时，CoAP 是更现实的选择；反之，设备资源够用、且系统需要广播与离线补发时，MQTT 的能力值得这份开销。

## 5. 选型建议

- **设备上报状态、多端订阅同一数据（智能家居、车队监控）**：优先 MQTT。发布一次、多方收到是 MQTT 的主场；保留消息让新订阅者立刻拿到当前状态，遗嘱让系统知道设备掉线。
- **极低功耗、间歇连接的传感器（电池供电数年、低速易丢包链路）**：优先 CoAP。UDP 无连接、报文小、按需收发，功耗账算得过来。
- **设备之间直接对话（局域网内设备互控、网关与终端直连）**：优先 CoAP。REST 风格直观，Observe 覆盖“值变了通知我”，不需要为直连场景搭一个 Broker。
- **消息不能丢、不能重复（计费、控制指令）**：优先 MQTT QoS 1（接收方幂等去重）或 QoS 2，并接受握手开销；CoAP 的 CON 只到“至少一次”，不要指望它做恰好一次。
- **控制回路（闭环控制、实时响应）**：两者都不合适。MQTT 的 Broker 中转与 QoS 握手、CoAP 的 UDP 重传都不保证延迟，控制回路应走本地直连或实时总线（见上一篇的板内总线与 03 篇的误配提醒）。
- **混合架构是常态**：网关侧用 CoAP 汇聚低功耗终端、用 MQTT 上云分发，是常见的分层做法——受限段用轻协议，广域段用强分发，不必二选一。

### 5.3 安全：上线前必须有的三件套

协议本身不提供安全，安全是部署配置，两边一样不能省：

- **传输加密**：MQTT 走 TLS（8883），CoAP 走 DTLS（5684）；明文端口只留在隔离的测试环境。
- **认证**：MQTT 用用户名/密码或客户端证书，CoAP 用预共享密钥、裸公钥或证书（RFC 7252 定义四种安全模式，以规范为准）；匿名可连的 Broker/服务端等于把设备控制权敞开。
- **授权**：发布与订阅权限要按主题/资源收紧，设备只能发布自己的主题、订阅自己需要的主题；默认“全通”的配置是真实的安全事故来源。

## 6. 常见误解

- “MQTT QoS 2 就等于实时”：错。QoS 保证送达语义，不保证延迟；实时控制不要走消息队列。
- “CoAP 是跑在 UDP 上的 HTTP”：错。REST 风格相同，但 CoAP 有自己的消息层可靠性、观察模式与二进制编码，不是 HTTP 的简单移植。
- “QoS 越高越好”：错。QoS 2 的四步握手在弱网下反而放大延迟与流量；按“丢”与“重复”哪个更不能忍来选。
- “用了 MQTT 就不需要考虑 Broker 高可用”：错。Broker 是单点依赖，生产环境要做高可用与备份，否则一次 Broker 故障等于全网失联。
- “CoAP 不可靠，因为它走 UDP”：错。UDP 不可靠，但 CoAP 的 CON、重传、消息 ID 去重在消息层补了可靠性；“不可靠”的是裸 UDP，不是 CoAP。
- “保留消息会一直存着”：错。每个主题只有最新一条保留消息，且新保留消息覆盖旧的；不需要时要主动发空载荷清除。
