# 物联网云平台对比

## 1. 对比背景

设备连上 MQTT Broker 只是物联网系统的起点：数据上报之后要存到哪、异常要不要告警、固件要不要升级、几千台设备怎么分组管理，这些工作不可能每台设备自己做。物联网云平台就是把这些共性能力集中提供的服务端：设备接入、数据流转、设备管理集中在一处，应用开发者只写业务逻辑。

需要选型的读者通常站在同一个路口：用主流云厂商的物联网平台、用开源物联网平台自建，还是两者结合。它们解决的是同一个问题——设备上云后的集中管理与数据处理，但成本结构、锁定程度与合规边界差别很大。本篇先讲平台共性能力，再按选型维度对比，不做厂商排名。

## 2. 对比维度

本篇按以下维度对比，维度超过选型所需的已删减，只留读者真正要决策的项：

- **设备接入**：设备如何连上平台，用什么协议与认证方式。
- **设备影子 / 孪生**：平台如何表示一台设备的当前状态。
- **规则引擎**：数据到达后如何按规则路由与处理。
- **数据流转**：数据如何进入存储、分析与业务系统。
- **OTA 管理**：固件如何批量升级与回滚。
- **成本**：付费方式与主要成本项。
- **锁定程度**：换平台的代价。
- **合规与数据位置**：数据存放在哪、受哪些合规约束。
- **规模与运维**：支撑的设备量级与运维负担。

价格、配额、服务等级等具体数值一律以官方发布为准（待核实），本篇不写任何厂商的具体价格与配额数字。

## 3. 平台共性能力

主流云厂商物联网平台与开源物联网平台在能力清单上高度重合，差别主要在实现方式与运维归属。下面是选型时要逐项核对的共性能力：

### 3.1 设备接入

平台提供设备注册与身份管理：每台设备有唯一身份（设备 ID 与凭证），接入时做认证，支持的协议以 MQTT 为主，部分平台同时支持 HTTP、CoAP 等。接入层通常包含前一篇讲的 Broker 能力（主题路由、QoS、遗嘱、会话保持），只是由平台托管。选型时核对：认证方式是否满足安全要求、设备量上去后接入层如何扩容、断网重连与离线缓存策略由谁负责。

### 3.2 设备影子 / 孪生

设备影子（Shadow）或数字孪生（Twin）是平台上为每台设备维护的一份状态副本：设备上报的最新状态（例如当前温度、开关状态）保存在影子里，应用读影子就能知道设备状态，不必直接问设备；应用想改设备状态时先改影子里的“期望状态”，设备上线后从影子取走期望值并执行，再把执行结果回写为“报告状态”。

影子的核心价值是解耦在线与离线：设备离线时应用照样能读最后已知状态、照样能下发期望，设备恢复在线后自动同步。选型时核对：影子支持哪些数据类型与更新频率、期望状态与报告状态不一致时如何处理冲突、影子数据保留多久。

### 3.3 规则引擎

规则引擎是“数据到达后按条件触发动作”的机制：例如“温度超过 40℃ 时把消息转存到数据库并推送告警”“某类设备的上报数据转发到另一个主题”。规则通常由“触发条件 + 动作”组成，动作包括写入数据库、调用函数、转发消息、发送通知等。

规则引擎是平台之间差异较大的部分：规则表达式的语法、支持的动作种类、规则执行的延迟与配额，各平台不同。选型时核对：常用动作是否覆盖业务需求、规则数量与执行频率有无配额（配额以官方发布为准，待核实）、规则出错时如何排障。

### 3.4 数据流转

数据流转指设备数据从接入层进入存储、分析与业务系统的整条链路：上报 → 规则引擎 → 存储（时序数据库、对象存储或关系数据库）→ 展示（仪表盘）或分析（流处理、离线分析）→ 触发业务动作。平台通常提供与自家存储与计算服务的内置衔接，自建开源平台则需要自己接存储与分析组件。

选型时核对：数据能否方便地导出到自己的系统（避免数据被锁在平台内）、存储成本如何计费（以官方发布为准，待核实）、历史数据保留策略能否配置。

### 3.5 OTA 管理

OTA（空中升级）指通过网络批量升级设备固件：上传新固件包、按设备分组分批下发、设备下载后校验与安装、升级失败回滚到旧版本。OTA 是设备量上去后最刚需的能力之一，手工逐台升级在几十台设备时就已不可行。

选型时核对：是否支持分批灰度与回滚、固件包签名校验怎么做、升级过程断电或断网后设备能否恢复、OTA 流量与存储如何计费（以官方发布为准，待核实）。

### 3.6 设备管理与监控

除上述能力外，平台通常还提供：设备分组与批量操作、设备在线状态与日志查询、告警与监控指标、权限管理（谁能操作哪些设备）。这些能力决定了日常运维的工作量，选型时应实际走一遍控制台流程再做判断——本篇未做实测，见文末未完成项。

## 4. 对比表

表中“主流云厂商平台”指各大云厂商提供的物联网平台服务（例如 AWS IoT、Azure IoT、阿里云物联网平台、华为云 IoT、腾讯云物联网平台等，仅作举例，不做排名）；“开源平台”指可自行部署的开源物联网平台（例如 ThingsBoard，仅作举例，不做排名）。具体功能、价格与配额以各厂商与项目的官方发布为准（待核实）。

| 维度 | 主流云厂商物联网平台 | 开源物联网平台（自建） |
|---|---|---|
| 设备接入 | 托管接入层，MQTT 为主，认证与扩容由厂商负责 | 自己部署接入层（常基于开源 Broker），认证与扩容自己负责 |
| 设备影子 / 孪生 | 内置影子或孪生服务，与规则引擎衔接 | 多数开源平台提供影子或等价的状态管理，需核对具体实现 |
| 规则引擎 | 内置，与自家存储、函数计算衔接 | 内置规则链或需外接流处理组件，能力随项目而异 |
| 数据流转 | 与自家存储、分析服务内置打通 | 自己接存储与分析组件，灵活但工作量大 |
| OTA 管理 | 内置固件升级与分批、回滚能力 | 部分开源平台内置 OTA，需核对版本与实现完整度 |
| 成本 | 按连接数、消息量、存储等计费，价格以官方发布为准（待核实） | 软件本身免费，成本在服务器、存储与人力运维 |
| 锁定程度 | 较高：规则、影子、存储多与厂商服务绑定，迁移需重写适配层 | 较低：部署在自己的基础设施上，数据与配置可控 |
| 合规与数据位置 | 数据存放在厂商云上，合规资质以厂商公开说明为准（待核实） | 数据位置自己决定，便于满足内网与数据不出境要求 |
| 规模与运维 | 弹性伸缩，运维由厂商负责 | 规模靠自己做集群与扩容，运维负担真实存在 |
| 适用场景 | 快速上线、规模波动大、需要云端分析能力 | 数据敏感、内网部署、已有运维团队、长期成本可控优先 |

## 5. 关键差异展开

### 5.1 成本：按量付费 vs 自担运维

云厂商平台的成本随连接数、消息量、存储量增长而增长，小规模时门槛低，大规模时账单需要专门测算；开源自建的成本集中在服务器与人力上，设备量增长时边际成本相对平缓，但前期投入与运维人力不能省。两种成本结构没有绝对优劣，关键是按自己的设备量级与增长预期测算——具体价格以官方发布为准（待核实），本篇不给算账示例。

### 5.2 锁定：迁移代价是选型时最容易低估的一项

用云厂商平台时，规则引擎语法、影子数据结构、存储衔接方式都与厂商绑定；将来换平台，设备端接入层、规则、数据导出都要重做。开源自建的锁定程度低，但代价是所有能力都要自己保障。降低锁定的通用做法：设备端只依赖标准 MQTT（不依赖厂商私有 SDK 的独占能力）、数据定期导出到自己的存储、规则逻辑尽量放在自己可控的服务里而不是全写在平台规则引擎中。

### 5.3 合规：数据位置先于功能清单

数据合规要求明确的场景（例如数据不出内网、特定行业合规），选型顺序应是“先定数据能放哪，再看功能清单”。开源自建在数据位置上最灵活；云厂商平台则要核对厂商的合规资质与数据区域选项，以厂商公开说明为准（待核实），不要凭印象判断。

## 6. 选型建议

- **如果要快速验证想法、设备量不大**：优先考虑云厂商物联网平台，免运维、上线快；同时把设备端做标准 MQTT 化，为将来迁移留余地。
- **如果数据合规要求明确、数据必须留在内网**：优先考虑开源平台自建，或云厂商的专有云/边缘部署形态（具体形态与价格以官方发布为准，待核实）。
- **如果设备量大且长期运行、已有运维团队**：认真测算两种路线的长期总成本（云厂商按量计费 vs 自建服务器与人力），不要只看上线第一个月的账单。
- **如果已有大量设备在用某云厂商的其他服务**：同厂商物联网平台在数据流转上有衔接优势，但仍要评估锁定代价，不要只因为“顺手”就选。
- **没有把握的场景**：涉及具体厂商的价格、配额、服务等级、合规资质的决策，本篇不给建议，以官方发布为准（待核实），见文末未完成项。

## 7. 常见误解

- “云平台贵，开源免费”：错。开源软件本身免费，但服务器、存储、运维人力都是成本；云平台按量计费，小规模时反而可能更便宜。两种路线都要算总账。
- “上了云平台就不用管设备了”：错。设备分组、固件升级策略、告警规则、权限管理都是持续的运营工作，平台只提供工具。
- “影子就是数据库”：错。影子是设备当前状态的副本，用于在线/离线解耦；历史数据查询与分析要走存储与数据流转，不是读影子。
- “选了平台就等于选了架构”：错。平台是物联网系统的一部分，设备端协议、数据模型、业务系统同样决定架构；平台选型不应替代整体架构设计。
