# 驱动开发与设备树实战

## 1. 本章目标

读完本篇能理解：Linux 驱动模型里设备、驱动与总线三者如何配合，字符设备与平台设备各自解决什么问题，设备树用什么语法描述硬件，驱动如何靠 compatible 字符串与设备树节点绑定，以及驱动不工作时沿 sysfs 与 debugfs 排查的思路。本篇讲清概念与流程，不贴未经核实的完整驱动代码。

## 2. 背景与问题

02 篇已经讲过设备树的基本思想：把“板子长什么样”从内核代码里抽出来，用一份树形数据单独描述；还讲过启动链条里内核按 DTB 找驱动。本篇是那篇的纵深：02 篇只说“内核按 compatible 匹配驱动”，本篇讲匹配发生在哪里、驱动长什么样、匹配失败时从哪里查。

驱动开发的实际问题是：**一块外设要能用，需要三样东西同时对上**——硬件确实在那个地址上（设备树说对了）、内核里有能驱动这类硬件的代码（驱动写对了）、驱动与硬件被正确地配对（绑定流程走对了）。三样缺一不可，而新手排查时最容易只盯着其中一样：反复改驱动代码，却不知道问题出在设备树地址写错；或者反复改设备树，却不知道驱动根本没编进内核。理解绑定流程，就是为了在出问题时知道该查哪一环。

还需要先讲清两个边界：第一，本篇讲的是概念与流程，不是“照抄代码就能用的驱动教程”——完整驱动代码涉及具体芯片的寄存器细节，未经板上实测贴出来只会误导人；第二，本篇不讲具体芯片的寄存器手册，那是各厂商文档的事，本篇只讲“拿到手册后，驱动与设备树分别该往哪放”。

## 3. 总体架构

Linux 驱动模型在概念上的三方关系（文字结构图）：

```
总线（bus：如 platform 总线、I2C 总线、SPI 总线）
├── 设备（device：一个硬件实例，来自设备树节点或总线枚举）
│       └── 描述：寄存器地址、中断号、时钟、引脚（见第 5 节）
└── 驱动（driver：一段内核代码，声明“我能驱动哪类硬件”）
        └── 声明：compatible 匹配表、probe/remove 回调、操作接口

绑定流程：总线发现设备 → 按 compatible 找驱动 → 调用驱动的 probe →
          驱动初始化硬件、注册设备接口 → 用户态经设备文件或 sysfs 访问

用户态访问路径
├── 字符设备文件（如 /dev/xxx）：read/write/ioctl 走文件操作接口
├── sysfs（/sys）：设备属性与驱动状态的文本化视图
└── debugfs（/sys/kernel/debug）：调试用的临时信息，不进正式接口
```

这个模型的关键是**设备与驱动分离**：驱动代码不写死“某块板子的某个地址”，只声明“我能驱动 compatible 为某某的硬件”；设备信息（地址、中断、引脚）由设备树或总线枚举提供。同一份驱动因此能用在多块板子上，换板子改设备树即可——这是设备树存在的根本理由，也是 02 篇 4.2 节的结论，本篇把它落实到绑定流程上。

## 4. 工作机制

### 4.1 Linux 驱动模型：设备、驱动与总线

驱动模型的核心是三个对象的分工：

- **设备（struct device 一类对象）**：代表一个硬件实例。它不包含“怎么操作硬件”的逻辑，只携带“硬件在哪、有什么资源”的信息：寄存器基地址、中断号、时钟源、引脚复用。设备可以来自设备树节点，也可以来自总线枚举（例如 PCI 枚举、USB 热插拔发现）。
- **驱动（struct driver 一类对象）**：代表一段能操作某类硬件的内核代码。它声明自己能驱动哪些设备（匹配表），并提供两个关键回调：probe（设备与驱动配对成功时调用，做初始化）与 remove（设备拔掉或驱动卸载时调用，做清理）。驱动不主动找设备，等总线来配对。
- **总线（struct bus_type）**：负责把设备与驱动配对。它维护两张表——已注册的设备表与已注册的驱动表；每当有新设备或新驱动注册，就按匹配规则（对平台设备主要是 compatible 字符串比对）尝试配对，配对成功就调驱动的 probe。

这个模型的好处是**配对逻辑集中在总线**：驱动作者只写“我能驱动什么 + 配对后做什么”，不用自己写扫描硬件、遍历设备的代码；板子换了，只要设备信息来源（设备树）改对，配对逻辑不用动。

### 4.2 字符设备：用户态与驱动的接口

字符设备是驱动提供给用户态的最常见接口形态，理解它要抓住三层：

- **设备号**：每个字符设备由主设备号（标识驱动）与次设备号（标识该驱动下的第几个设备）共同定位。内核用设备号把“用户态打开的设备文件”路由到对应的驱动。
- **设备文件**：用户态看到的 `/dev/xxx` 只是一个入口，真正的逻辑在驱动里。打开设备文件，就是告诉内核“把后续的读写交给这个驱动处理”。
- **文件操作接口**：驱动向内核注册一组操作（打开、关闭、读、写、定位、控制命令等），用户态的每一次系统调用都会落到其中一个操作上。驱动的读操作负责“把硬件数据交给用户态”，写操作负责“把用户态数据送到硬件”，控制操作负责“配置硬件参数”。应用层不需要知道硬件寄存器长什么样，只需要会用这组文件操作。

字符设备与块设备的区别要分清：字符设备按字节流读写（串口、传感器、GPIO 字符设备都属此类），块设备按固定大小的块读写并带缓存（存储设备）。选错类型，接口语义就全错了——传感器数据走字符设备，Flash 存储走块设备或 MTD 抽象，不要混用。

驱动的生命周期也值得单独说明：驱动以内核模块的形式存在时，加载模块执行初始化（注册驱动、申请设备号、创建设备文件），卸载模块执行清理（注销设备、释放资源）；编进内核的驱动则在启动时由总线配对触发 probe。无论哪种形态，**probe 里只做“让硬件进入可用状态”的事**，把重活留给后续的文件操作，而不是在 probe 里做耗时初始化拖慢启动。

### 4.3 平台设备：没有可枚举总线的硬件怎么办

不是所有硬件都能被总线“发现”：SoC 内部的串口控制器、I2C 控制器、GPIO 控制器没有像 PCI、USB 那样的枚举机制，内核上电时并不知道它们在哪个地址。平台设备（platform device）就是为这类硬件准备的抽象：

- **平台设备的设备信息来自设备树**：设备树节点描述“这个地址上有一个什么控制器”，内核解析设备树后为每个节点创建一个平台设备，挂到 platform 总线上。
- **平台驱动（platform driver）**：声明 compatible 匹配表的驱动，注册到 platform 总线上；总线把设备树里的节点与平台驱动配对，配对成功调 probe。
- **资源传递**：probe 被调用时，驱动从设备对象里取资源——寄存器地址范围、中断号、时钟、引脚——再按这些资源去初始化硬件。驱动代码里不写死地址，地址来自设备树节点，这是平台设备模型与设备树配合的关键点。

一句话总结：**平台设备是“设备树节点在内核里的化身”**。理解了这一点，就理解了为什么改设备树能影响驱动行为——设备树改的是平台设备的资源描述，驱动读到的资源跟着变。

### 4.4 驱动与设备树的绑定流程

把 4.1–4.3 节串起来，绑定流程按顺序是：

1. **内核解析设备树**：启动时内核读 DTB，为每个带 compatible 属性的节点创建对应的设备对象（平台设备），挂到相应的总线上。
2. **驱动注册**：驱动向内核注册，提交自己的匹配表（of_match_table，里面是一组 compatible 字符串）与 probe/remove 回调。
3. **总线配对**：总线拿设备的 compatible 字符串去匹配驱动的匹配表，字符串一致即配对成功；不一致则设备停留在“未绑定驱动”状态，硬件不可用，但内核不会报错——这是设备树问题最难查的原因之一，见第 7 节。
4. **probe 初始化**：总线调用驱动的 probe，驱动从设备对象取寄存器地址、中断号等资源，映射寄存器、申请中断、注册字符设备（创建 /dev 入口）或注册到相应子系统（如 I2C、SPI 子系统下的从设备驱动走各自总线，流程同理）。
5. **用户态访问**：应用打开 /dev 设备文件或读写 sysfs 属性，调用落到驱动的文件操作上，驱动操作硬件寄存器完成读写。

绑定失败的排查顺序就是沿这条链倒着查：先确认设备节点存在（设备树编进 DTB 了吗）、再确认 compatible 字符串拼写一致（驱动的匹配表与设备树节点是否一字不差）、再确认驱动编进内核或模块加载了（驱动注册了吗）、最后确认 probe 是否成功执行（dmesg 里有没有 probe 的报错）。跳过前面的环节直接改驱动代码，是最常见的弯路。

## 5. 设备树：作用与基本语法

### 5.1 设备树的作用

设备树的作用在 02 篇 4.2 节已有概述，这里补三点纵深：

- **它是硬件的“唯一可信描述”**：内核不读芯片手册、不猜硬件在哪，只信设备树。设备树写错一个地址，驱动读到的就是错的硬件，表现是“驱动加载了但外设不工作”，而不是“设备树语法错了”。
- **它分两层**：SoC 级设备树（描述芯片内部有哪些控制器，常用芯片厂商提供，改动少）与板级设备树（描述板子上外接了什么、引脚怎么复用、哪个控制器接了哪个外设，由板厂或产品方维护，改动多）。板级文件包含 SoC 级文件，再覆盖或追加板子特有的节点——分层复用是设备树的常规写法。
- **它是启动时数据，不是运行时配置**：DTB 在启动时传给内核，内核解析后就不再回读源文件；改了设备树源文件要重新编译 DTB 并重新烧录、重启才生效。运行时想改硬件配置，走 sysfs、debugfs 或应用层配置，不要指望改设备树源文件能立即生效。

### 5.2 基本语法：节点、属性与 compatible

设备树源文件（DTS）是一棵树：每个节点代表一个硬件或一组硬件，节点里用“属性”描述它的信息。语法要点如下（以下为通用语法示意，非某块板子的真实配置，示例未实测）：

```
 / {
    /* 根节点：整块板子 */
    compatible = "vendor,board-name";   /* 板子标识，以实际厂商命名为准 */
    model = "Board Name";               /* 板子型号字符串，以实际为准 */

    serial0: serial@10000000 {         /* 节点名：类型@地址；serial0 是标号 */
        compatible = "vendor,uart";    /* 关键属性：驱动靠它匹配 */
        reg = <0x10000000 0x1000>;     /* 寄存器地址与大小，以芯片手册为准 */
        interrupts = <...>;            /* 中断号，以芯片手册为准 */
        status = "okay";               /* okay 启用，disabled 停用该节点 */
    };
 };
```

- **节点**：`名称@地址` 的形式，节点可以嵌套（例如 I2C 控制器节点下面挂传感器节点，表示“传感器接在这个控制器上”）。节点名里的地址是寄存器基地址的提示，不是驱动匹配的依据。
- **属性**：`名 = 值` 的键值对。值可以是字符串、数值数组、布尔标记（只有属性名、没有值表示“开启某特性”）。属性名有约定俗成的含义，见下表。
- **compatible**：最重要的属性，字符串（或字符串列表），是驱动匹配的依据。写法一般是 `"厂商,型号"`，例如 `"vendor,uart"`。驱动的匹配表里必须有与之一致的字符串，配对才能成功；字符串拼写差一个字符，配对就失败，且内核不报错。
- **reg**：寄存器地址与大小，驱动据此映射硬件寄存器；地址与大小以芯片手册为准，写错会导致驱动访问到错误的地址。
- **interrupts**：中断号与触发方式，驱动据此申请中断；中断号的编码方式与中断控制器有关，以芯片手册与 SoC 设备树为准。
- **status**：`"okay"` 表示启用该节点，`"disabled"` 表示停用。板级设备树常用它来开关 SoC 级节点里默认禁用的外设。
- **标号（label）与引用**：`serial0:` 这样的标号让板级文件可以在别处引用并追加属性（例如在 SoC 节点上追加引脚配置），是板级覆盖 SoC 级的常用手法。
- **phandle 引用**：属性值可以引用另一个节点（例如时钟属性指向时钟控制器节点、引脚属性指向引脚控制器节点），表示“这个硬件依赖那个硬件提供的资源”；引用用 `&标号` 的形式写。

常见属性速查（含义为通用约定，具体取值以芯片手册为准）：

| 属性 | 含义 |
|---|---|
| compatible | 驱动匹配字符串，绑定流程的依据 |
| reg | 寄存器地址与大小 |
| interrupts | 中断号与触发方式 |
| clocks / clock-names | 时钟来源 |
| pinctrl-0 | 引脚复用配置的引用 |
| status | okay 启用 / disabled 停用 |
| model | 板子型号字符串（根节点） |

### 5.3 设备树叠加（overlay）：改动不动主树

有些场景需要在不改主设备树的前提下追加或修改硬件描述，例如给一块板子加一块扩展板、或在开发阶段临时启用某个外设。设备树叠加（device tree overlay）就是为这个场景准备的机制：一份独立的片段描述“在主树的某个节点上追加这些属性”，启动时或运行时由 Bootloader 或内核把它合并进主树。叠加的优点是改动隔离：扩展板的描述跟着扩展板走，主树保持干净；缺点是合并出错时排查更难——要同时看主树与叠加片段。叠加是否可用、由谁加载，以所用 Bootloader 与内核的配置为准（待核实）。

## 6. 关键设计取舍

- **驱动进内核还是做模块**：编进内核的驱动随启动加载，启动时即可用，但内核体积大、改驱动要重编内核；做模块的驱动可单独加载卸载，调试灵活，但模块与内核版本要严格对应，版本对不上加载会失败。开发阶段用模块、量产阶段把必需驱动编进内核，是常见的两阶段做法。
- **设备树描述换内核代码**：能用设备树描述的硬件信息（地址、中断、引脚），不要写进驱动代码；驱动代码只写“这类硬件怎么操作”。这样换板子只改设备树，驱动不用动；反过来把地址写死在驱动里，换一块板子就要改驱动，是设备树出现之前最常见的维护痛点。
- **sysfs 暴露换驱动内聚**：驱动可以通过 sysfs 把可调参数暴露给用户态（例如采样周期、阈值），方便调试与应用层调参；但暴露得越多，驱动与用户态的约定就越多，后续改驱动要顾及兼容性。调试用的临时暴露走 debugfs，正式接口走 sysfs 或字符设备，不要混用。
- **通用驱动换专用驱动**：能用内核已有的通用驱动（例如通用 GPIO、通用 I2C 从设备驱动框架）就不要重写专用驱动；通用驱动经过长期验证，专用驱动只在硬件行为确实特殊时才写。重写驱动的代价不只是代码量，还有后续跟进内核升级的维护量。

## 7. 应用与限制

典型应用：为板上新接的传感器写平台驱动并配设备树节点（传感器接线见 03 篇，协议细节以传感器手册为准）；为 SoC 内部控制器启用设备树节点并确认驱动绑定；用 sysfs 调试外设状态、用 debugfs 看驱动内部信息。

限制有五条：第一，驱动开发必须对照芯片与传感器手册，寄存器地址、位定义、中断号离开手册寸步难行，本篇不提供任何具体芯片的寄存器细节；第二，驱动跑在内核态，指针错误会拖垮整个系统（不像应用层崩了只崩一个进程），调试要格外小心；第三，设备树问题不报错、只表现为“驱动不加载”或“外设不工作”，排查要按 4.4 节的绑定链逐环核对；第四，内核版本升级可能改动驱动接口，驱动要跟进内核演进，不能“一版驱动用终身”；第五，本篇所有流程均未在真实开发板上实测，见文末未完成项。

## 8. 常见误解与调试思路

### 8.1 常见误解

- “设备树就是驱动”：错。设备树是硬件描述，驱动是内核代码；设备树错了表现为驱动不加载，不是驱动本身有问题（02 篇已有此结论，本篇在 4.4 节讲清了它在绑定链上的位置）。
- “compatible 写个大概就行”：错。匹配是字符串精确比对，差一个字符就配不上，且内核不报错。
- “驱动编进内核就一定会加载”：错。编进内核只是“驱动已注册”，还要设备树里有 compatible 一致的节点，总线才会调 probe；节点缺失或 status 为 disabled，驱动注册了也不会工作。
- “dmesg 没报错就是驱动正常”：错。绑定失败时内核常常一声不吭；没报错只能说明“没发现错误”，不能说明“配对成功了”，要到 sysfs 里看设备到底绑定了哪个驱动。

### 8.2 sysfs 调试思路

sysfs（挂载在 `/sys`）是内核把设备与驱动状态以文件形式暴露出来的视图，排查驱动问题时沿这条路走：

1. **看设备在不在**：在 `/sys/bus/platform/devices/`（平台设备）或相应总线的 devices 目录下找设备节点——设备名通常来自设备树节点名；找不到，说明内核解析设备树时就没创建这个设备，问题在设备树（节点缺失、status 为 disabled、DTB 没更新）。
2. **看驱动绑没绑**：设备目录下的 `driver` 符号链接指向绑定的驱动；没有这个链接，说明设备存在但没配上驱动，问题在 compatible 字符串不一致或驱动没注册。
3. **看设备属性**：设备目录下的属性文件（如 modalias、of_node）能确认设备树信息是否如预期；modalias 里的 compatible 字符串是驱动匹配的实际输入，拿它与驱动的匹配表逐字比对。
4. **读写驱动暴露的属性**：驱动通过 sysfs 暴露的可调属性（例如使能开关、采样配置）可以直接读写验证；写进去没反应，先确认写的是正确的属性文件、再看 dmesg 有无报错。

### 8.3 debugfs 与内核日志调试思路

- **dmesg**：内核日志是第一排查入口。驱动的 probe 里通常会打印关键步骤的成败；启动日志里搜驱动名与设备名，能定位 probe 走到哪一步失败。注意：驱动没加载时 dmesg 里可能完全没有它的痕迹，这时回到 8.2 节的 sysfs 排查，而不是反复看日志。
- **debugfs**（挂载在 `/sys/kernel/debug`）：驱动可以把内部状态、寄存器快照、统计计数放在这里，供开发调试；它是调试用的临时接口，不保证稳定、不进正式用户态接口，量产镜像可以不挂载。查某个驱动的 debugfs 入口，先看该驱动的文档说明它暴露了什么（以官方文档为准，待核实）。
- **/proc 与设备文件验证**：`/proc/devices` 能确认字符设备的主设备号是否注册；`/dev` 下的设备文件存在与否能确认驱动是否完成了设备注册；设备文件存在但读写失败，问题在驱动的文件操作实现或硬件本身，而不是绑定流程。
- **分层定位口诀**：设备不在 sysfs → 查设备树；设备在但没绑驱动 → 查 compatible 与驱动注册；绑了驱动但 probe 失败 → 看 dmesg；probe 成功但读写失败 → 查驱动实现与硬件接线。按这个顺序走，比同时改设备树和驱动代码省得多。
