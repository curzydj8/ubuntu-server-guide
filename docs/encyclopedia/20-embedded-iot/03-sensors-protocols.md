# 传感器与通信协议

## 1. 本章目标

读完本篇能理解：传感器数据是怎样进入系统的，UART、I2C、SPI、MQTT 四种协议各自解决什么问题、帧结构的关键点是什么，以及选型时按什么取舍。

## 2. 背景与问题

传感器是嵌入式系统的“感官”：温度、湿度、加速度、气压、光照，最终都要变成数字信号交给芯片处理。但传感器和芯片之间隔着一个实际问题：数据怎么传？传多快？一根总线上挂多个传感器怎么办？设备要把数据发到云端，中间经过不可靠的网络又怎么办？

这四个协议分工不同：UART、I2C、SPI 解决的是板子内部或近距离的芯片间通信；MQTT 解决的是设备到服务端的消息分发。把它们混为一谈（例如拿 MQTT 和 SPI 比“谁更快”）是选型时最常见的类别错误。

## 3. 总体架构

典型的数据链路（文字结构图）：

```
物理世界
 └─ 传感器（温度 / 湿度 / 加速度 / 气压 …）
     └─ 板内总线（二选一：I2C 或 SPI，调试常用 UART）
         └─ MCU / SoC（采集、滤波、打包）
             └─ 网络链路（Wi-Fi / 以太网 / 蜂窝）
                 └─ MQTT Broker（消息中转）
                     ├─ 云端应用（存储、展示、告警）
                     └─ 其他设备（订阅同一主题）
```

板内段讲“可靠地把数读进来”，网段讲“不可靠网络下把消息送出去”，两段的取舍标准完全不同。

## 4. 工作机制

### 4.1 UART：最简单的异步串行

UART 是点对点的异步串行通信：发送和接收各用一根线（TX、RX 交叉相连），不需要共享时钟，双方事先约定好波特率（每秒传多少位）。一帧的要点：起始位（1 位低电平，告诉对方“要开始了”）+ 数据位（通常 8 位）+ 可选校验位 + 停止位（1 位或更多，回到空闲电平）。

UART 的优点是简单、几乎所有芯片都有、调试直观（串口打印是嵌入式调试的第一手段）。限制也同样直接：点对点，不能一主多从；没有硬件流控时高速下容易丢数据；传输距离短（板级，几十厘米量级），上不了长线。波特率不是越高越好：超过芯片和线路能力，误码率会先于速度收益恶化。

### 4.2 I2C：两根线挂一串低速设备

I2C 是飞利浦（现 NXP）制定的多主多从两线总线：SDA（数据）和 SCL（时钟），外加两根上拉电阻。总线平时被上拉电阻拉高，任何设备都只能主动拉低——这种“开漏 + 上拉”结构是 I2C 能多设备共线的根本原因。

一帧的要点：起始条件（SCL 高时 SDA 拉低）→ 7 位从机地址 + 1 位读写方向 → 从机应答（ACK，把 SDA 拉低一拍）→ 数据字节（每字节后跟一个 ACK/NACK）→ 停止条件。速率档是标准：标准模式 100kHz、快速模式 400kHz、高速模式 3.4MHz，实际能跑多快取决于总线电容和上拉电阻，不是标称值说了算。

I2C 的适用面：板内低速传感器（温湿度、气压、EEPROM、实时时钟），引脚省、接线少。限制：速率低、总线电容限制了线长和挂载数量、地址冲突真实存在（两个同型号传感器默认地址相同，挂同一总线前要查地址可配性或用多路复用器）。

### 4.3 SPI：四根线换速度

SPI 是四线全双工同步总线：SCLK（时钟）、MOSI（主出从入）、MISO（主入从出），外加每从机一根片选（CS）。主机拉低某一路 CS 就选中该从机，时钟驱动下主从同时收发——全双工是 SPI 相对 I2C 的结构性优势。

一帧的要点：片选有效 → 时钟边沿采样数据；时钟极性（CPOL，空闲时高还是低）与时钟相位（CPHA，第几个边沿采样）四种组合必须主从一致，否则读回来的全是错位数据；没有寻址、没有应答机制，主机要自己知道从机在不在、数据对不对。速率通常可达数 MHz 到数十 MHz（以从机手册为准），远高于 I2C。

SPI 的代价是引脚：每多一个从机多一根 CS，引脚多的板子布线压力大。适用面：高速传感器（IMU、高速 ADC）、Flash、显示屏。限制：无标准寻址与纠错、线长同样受限、多从机时 CS 管理是设计工作的一部分。

### 4.4 MQTT：不可靠网络上的消息分发

MQTT 是 OASIS 标准的消息协议，基于发布/订阅模型，不直接点对点：设备（客户端）连到 Broker（中转服务器），发布者把消息发到一个主题（topic，例如 `home/livingroom/temperature`），订阅了该主题的接收者从 Broker 收到消息。发布者和订阅者互不知道对方存在，只通过主题解耦。

三个机制决定了 MQTT 的适用面：

- **主题与通配符**：订阅可用 `+` 匹配一层、`#` 匹配多层，做批量订阅；主题设计是系统设计的一部分，不是事后命名。
- **QoS（服务质量）三档**：QoS 0 最多送一次（可能丢）、QoS 1 至少送一次（可能重复，接收方要去重）、QoS 2 恰好送一次（握手多、开销大）。选哪档看业务对“丢”和“重复”哪个更不能忍，不是越高越好。
- **遗嘱与会话**：设备异常断线时 Broker 可代发遗嘱消息，让订阅方知道“它掉了”；会话保持与否决定重连后是否补发离线消息。

MQTT 的限制：依赖 Broker，Broker 挂了全网消息就断（生产要做高可用）；QoS 2 保证的是“恰好送达”，不是“实时送达”，延迟敏感的控制回路不要走 MQTT；载荷格式（JSON、Protobuf 等）协议不管，收发双方要另外约定。

## 5. 关键设计取舍

| 维度 | UART | I2C | SPI | MQTT |
|---|---|---|---|---|
| 距离 | 板级 | 板级 | 板级 | 跨网络 |
| 速率 | 低–中 | 低（≤3.4MHz 档） | 高 | 取决于网络 |
| 引脚/成本 | 2 根 | 2 根 + 上拉 | 4 根 + 每从机 1 根 CS | 不占 GPIO，走网络栈 |
| 多设备 | 否（点对点） | 是（地址寻址） | 是（片选） | 是（主题订阅） |
| 可靠性机制 | 校验位（可选） | ACK/NACK | 无（靠上层） | QoS、遗嘱、会话 |
| 典型用途 | 调试、模组通信 | 低速传感器 | 高速传感器、Flash | 设备上云、消息分发 |

选型口诀：板内低速传感器先看 I2C；要速度或全双工看 SPI；调试和接模组用 UART；数据要出设备、经过网络、发给多个接收方，用 MQTT。常见误配：拿 I2C 去推高速 IMU 数据（速率不够）、拿 SPI 挂一堆低速传感器（CS 引脚爆炸）、控制回路走 MQTT（延迟不可控）。

## 6. 分类与变体

- **板内总线**：UART、I2C、SPI，以及本篇不展开的 CAN（汽车与工业现场，带仲裁与纠错，适合长线多节点，属 20 域后续可补的主题）。
- **应用层消息协议**：MQTT，以及本篇不展开的 CoAP（基于 UDP 的轻量 REST 风格，适合极低功耗场景）、HTTP（通用但开销大，适合配置与非实时上报）。
- **传感器接口类型**：数字接口（I2C/SPI/UART 输出已量化的数据，本文重点）、模拟接口（输出电压，经 ADC 采样，精度受参考电压与噪声影响）、脉冲/频率接口（编码器、流量计，靠定时器输入捕获计数）。

## 7. 应用与限制

典型应用：温湿度与气压监测（I2C 数字传感器）、运动姿态（SPI IMU）、GPS 与蜂窝模组（UART AT 指令）、智能家居状态上报与远程控制（MQTT）。限制有三条：第一，协议只解决“传”，不解决“准”——传感器精度、校准、温漂是另一层问题，读数好看不等于测量准确；第二，板内总线的线长和干扰是硬约束，长线要换差分或现场总线方案；第三，MQTT 侧的主题、QoS、遗嘱、安全（TLS、认证）是系统设计，缺了任何一块，上线后都会以故障形式补回来。

## 8. 常见误解

- “I2C 地址不会冲突”：错。同型号传感器默认地址常相同，挂同一总线前必须核对地址配置位或加多路复用器。
- “SPI 不需要片选也能工作”：错。没有 CS，多个从机同时驱动 MISO 会冲突；单从机场景下 CS 也常用于帧同步。
- “MQTT QoS 2 就等于实时”：错。QoS 保证送达语义，不保证延迟；实时控制不要走消息队列。
- “波特率/总线速率越高越好”：错。速率受总线电容、线长、从机能力三重限制，超了先丢数据后丢通信。
