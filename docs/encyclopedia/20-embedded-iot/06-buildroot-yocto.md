# Buildroot/Yocto 构建系统

## 1. 本章目标

读完本篇能理解：为什么嵌入式 Linux 需要一个构建系统而不是手工拼装，Buildroot 与 Yocto 各自用什么机制把内核、根文件系统、引导程序和工具链组装成一个可烧录的系统镜像，以及两者在复杂度、定制性和维护成本上的取舍；并理解交叉编译工具链在构建系统里的位置。

## 2. 背景与问题

02 篇已经讲过嵌入式 Linux 的启动链条：Bootloader、内核、设备树、根文件系统、init 与应用，每一环都要对上板子的架构与配置。手工拼装这条链条会遇到四个现实问题：

- **来源太多**：内核、Bootloader、BusyBox、C 库、几十个用户态软件包各有自己的源码、版本与编译选项，逐个手工编译既慢又容易配错。
- **依赖会漂移**：今天在宿主机上编出来能跑的组合，下个月换一台宿主机、换一个库版本就可能编不出相同的产物；量产固件要求“同一份输入编出同一份输出”，手工拼装保证不了这一点。
- **目标不是宿主**：编译在 x86 宿主机上进行，产物要在 ARM 等目标板上运行，工具链、头文件、库文件都要对齐目标机（见 4.5），手工维护这套对齐关系很容易在链接阶段才暴露错误。
- **板子不止一块**：同一份应用要出多个板型、多个配置（开发版与量产版、带屏与不带屏），每出一版都手工改一遍配置，迟早会改漏。

构建系统的回答是：**用一份可版本控制的“配方”描述系统要什么，再由构建系统按配方自动完成下载、配置、编译、打包**。配方是输入，系统镜像是输出；中间过程可复现、可审查、可回滚。Buildroot 与 Yocto 是这个思路下的两种主流实现，分工不同，见第 5 节。

需要先划清边界：构建系统负责“编出系统”，不负责“设计系统该长什么样”——板子的硬件描述在设备树里，驱动逻辑在内核与驱动代码里，应用逻辑在应用代码里。构建系统把这些已有的部分组装起来，它本身不替你写驱动、也不替你定产品功能。设备树与驱动的深入内容见本域第七篇。

## 3. 总体架构

一个嵌入式 Linux 构建系统在概念上的输入与输出（文字结构图）：

```
构建输入（全部可进版本控制）
├── 配置：要编什么、编哪个版本、目标板是哪一块
├── 配方/包描述：每个软件包从哪来、怎么编、装到镜像的哪
├── 工具链描述：交叉编译器、C 库、目标架构与 ABI
└── 板级支持：Bootloader 配置、内核配置、设备树源文件

        ▼  构建系统执行：下载 → 打包 → 编译 → 安装 → 打包镜像

构建输出
├── 内核镜像（如 zImage / Image，以板子约定为准）
├── 设备树 blob（DTB）
├── 根文件系统镜像（如 ext4 / squashfs，以配置为准）
├── Bootloader 镜像
└── 交叉工具链（供后续单独编译应用或内核模块使用）
```

两条通用原则适用于两个系统：第一，**构建过程与宿主机环境尽量隔离**，工具链与 sysroot 由构建系统自己生成或明确指定，而不是随手用宿主机自带的编译器；第二，**输出是“板上能直接用的整套产物”**，而不仅是一个根文件系统——内核、DTB、根文件系统与 Bootloader 的版本要成套对应，混用不同批次的产物是启动失败的常见来源。

## 4. 工作机制

### 4.1 Buildroot：配置驱动的“一键出包”

Buildroot 的核心模型是**一套 Kconfig 配置 + 一组 Makefile 配方**。使用者在一个统一的配置界面（通常是 `make menuconfig` 的菜单形式）里选定目标架构、工具链、C 库、要进镜像的软件包与文件系统格式，Buildroot 据此生成一份配置，再按配置依次构建工具链、Bootloader、内核与根文件系统。

- **配置（.config / defconfig）**：一份配置就是一份“系统要什么”的完整清单。`defconfig` 是某块板子的默认配置起点，在它的基础上改动并保存，就得到该产品的配置；配置进版本库后，任何人在任何一台宿主机上用同一份配置都能复现同一套构建输入。
- **包机制**：每个软件包对应一份配方，写明源码从哪里下载、用什么版本、依赖哪些包、编译安装时执行哪些步骤。选一个包，构建系统自动把它的依赖也拉进来；取消一个包，镜像里就不含它。包的粒度是“软件包”，不是“单个文件”，这是它与手工 `make install` 的本质区别。
- **构建顺序**：先工具链，后 Bootloader 与内核，最后根文件系统与镜像打包。这个顺序不是随意定的：没有交叉工具链，后面所有目标代码都编不出来；根文件系统打包时要往里装已编好的库与工具，只能排在最后。
- **输出形态**：构建完成后在输出目录里得到成套产物（内核镜像、DTB、根文件系统镜像等），按板子的烧录方式写到存储介质上即可启动。Buildroot 的强项是“快”：配置少、概念少，从零到出第一个可启动镜像的路径最短。

Buildroot 的取舍在第 5 节展开；这里先记住它的定位：**面向单一产品、配置相对固定、出包要快**的场景。

### 4.2 Yocto：层、配方与镜像的分层模型

Yocto Project 的核心模型比 Buildroot 多一层抽象：**层（layer）、配方（recipe）与镜像（image）**。它由两部分组成：Poky（参考发行版，含构建工具 BitBake 与一组基础层）与 Yocto Project 的工具与规范；实际产品通常在 Poky 之上叠加自己的层。

- **层（layer）**：一组配方与配置的集合，按来源与归属分层。典型的分层是：基础层（提供核心工具链与基础包）、芯片厂商层（BSP，板级支持：内核、Bootloader、设备树）、产品层（自家应用与定制配置）。层与层之间是“叠加覆盖”关系：上层可以追加或改写下层的配方与配置，而不用改动下层文件本身——这正是 Yocto 适合产品线的关键：换一块板子，换一层 BSP；加一个产品变种，加一层产品配置；共用的部分留在下层不动。
- **配方（recipe，后缀常为 .bb）**：描述“一个软件包怎么来”：源码地址与版本、依赖、编译步骤、安装到镜像的哪些文件、打包成哪些子包。一个配方只管一个包；镜像由很多配方共同产出。
- **镜像配方（image recipe）**：也是一份配方，但它的产物不是单个软件包，而是一整套根文件系统：它列出镜像要包含哪些包、文件系统格式、镜像里要执行的收尾步骤。换一份镜像配方，就能从同一批包里拼出“开发镜像”（带调试工具）与“量产镜像”（精简只读）两种产物。
- **BitBake 与任务**：BitBake 是 Yocto 的构建引擎，它把每个配方拆成一系列任务（取源码、打补丁、配置、编译、安装、打包），按依赖关系排好顺序、并行执行，并把中间结果缓存起来。缓存机制（共享状态缓存，sstate）让“只改了一个包”时不必重编整个系统，这是 Yocto 在大型产品线上可用的前提；但缓存失效时的排查也相应更复杂。
- **机器（machine）与发行版（distro）**：Yocto 用这两个配置维度区分“跑在哪块板上”与“系统是什么风味”（C 库选择、init 系统、包管理格式等）。同一套配方，换一个 machine 配置就面向另一块板子；换一个 distro 配置就换一套系统策略。分层的代价是概念多：新手第一次接触要同时理解层、配方、镜像、machine、distro 五个概念，学习曲线明显陡于 Buildroot。

### 4.3 两者的构建流程对照

把两个系统放在同一张流程里看，差异不在“做什么”，而在“怎么组织”：

```
Buildroot：  一份配置 → 按配置顺序构建全部 → 输出成套镜像
Yocto：     多层配方 → BitBake 按依赖排任务、并行构建、缓存复用 → 输出镜像
```

Buildroot 是“配置即系统”：配置变了，系统就变了，简单直接。Yocto 是“配方拼系统”：系统由很多小配方拼出来，灵活但需要理解拼装规则。两者都会做下载、校验、打补丁、交叉编译、安装、打包这些步骤；区别是 Yocto 把每一步拆得更细、缓存得更彻底，并为多板型、多变种留出了分层扩展的空间。

### 4.4 选型之前先问的三个问题

在看第 5 节的对比表之前，先问自己三个问题，答案会直接指向选型：

1. **产品有几个板型、几个变种？** 只有一个板型、配置几年不变，简单方案够用；多个板型共用一套应用、每个板型有自己的 BSP，值得为分层付出学习成本。
2. **团队有没有人长期维护构建？** 构建系统不是“一劳永逸”的配置，它要跟进上游安全更新、内核升级与工具链演进；没有专人维护时，越简单的系统越不容易烂尾。
3. **对“可复现”要求有多高？** 量产、合规审计、多人协作都要求“同一份输入编出同一份输出”；要求越高，越需要构建系统自带的缓存、校验与版本锁定机制，而不是靠人工记住每一步。

### 4.5 交叉编译工具链：构建系统里的位置

02 篇已经讲过交叉编译的分工（宿主机、目标机、三元组、sysroot），这里讲它在构建系统里的具体位置——这是本篇相对 02 篇的纵深部分，02 篇只讲了概念分工。

- **工具链是构建系统的第一产物**：无论 Buildroot 还是 Yocto，构建的第一步通常都是先得到一套交叉工具链（编译器、汇编器、链接器、C 库与头文件），后面的内核、Bootloader 与所有用户态软件都用它来编。工具链不对，后面全错，所以构建系统把它当作受控产物，而不是复用宿主机上随手装的编译器。
- **内部工具链与外部工具链**：构建系统可以自己从源码编一套工具链（内部工具链：版本完全受控，构建时间长），也可以用一份现成的、由芯片厂商或第三方提供的工具链（外部工具链：上手快，但版本与 C 库由提供方决定，出了兼容问题要找提供方）。两种选择没有绝对优劣，取舍标准是“谁对工具链的版本负责”。
- **C 库的选择影响整套系统**：glibc 功能全、体积大；musl、uClibc-ng 轻量、适合资源受限的板子。C 库一旦选定，整套系统的动态链接库、工具链与应用都要与它一致，中途换 C 库等于重编整个系统——所以 C 库是立项时就要定的决策，不是构建中途能顺手改的选项。
- **sysroot 是“目标机的替身”**：编译时链接的不是宿主机的库，而是目标机库文件在宿主机上的一份副本（sysroot）。构建系统负责维护这份副本与目标机的一致性；手工交叉编译最常见的错误（链接了宿主机库、头文件版本对不上），在构建系统里因为 sysroot 由构建流程统一生成而不容易发生。
- **工具链也要给应用开发留一份**：系统编完后，应用开发还需要在宿主机上单独编译应用与内核模块，构建系统一般会输出一份与系统配套的 SDK（工具链 + sysroot + 头文件），应用开发用这份 SDK 编，编出来的东西与板上系统保证一致。用宿主机自带编译器编应用再拷到板上，是绕开这套保障的常见错误做法。

## 5. 关键设计取舍

### 5.1 Buildroot 与 Yocto 选型对比

| 维度 | Buildroot | Yocto |
|---|---|---|
| 上手难度 | 低：一份配置、少量概念 | 高：层、配方、镜像、machine、distro 多概念并行 |
| 定制粒度 | 以软件包为单位开关，够用但不够细 | 以配方与层为单位，可精确改写单个包的构建细节 |
| 多板型 / 多变种 | 靠多份配置硬分叉，共用部分靠人工同步 | 靠分层叠加，共用部分留在下层，上层只写差异 |
| 可复现性 | 配置锁定版本，复现性好 | 配方 + 锁定 + 缓存，复现性强，但缓存失效时排查难 |
| 构建速度（首次） | 快：步骤少、依赖浅 | 慢：首次构建常以小时计，缓存起来后增量构建快 |
| 长期维护成本 | 低：配置直观，升级时改动集中 | 高：要跟进层与配方的上游变更，升级常需调配方 |
| 典型适用 | 单一产品、配置固定、团队小、出包要快 | 产品线、多板型、长期演进、有专人维护构建 |

选型口诀：**一个产品、一块板子、想快点出可启动的系统，选 Buildroot；一串产品、多个板型、打算长期演进，选 Yocto**。两种系统都能编出可用的嵌入式 Linux，选错的代价不在“编不出来”，而在“维护到第二年才发现改不动”——单产品用 Yocto 是前期多付学习成本，多板型用 Buildroot 是后期多付同步成本。

### 5.2 其他取舍

- **从源码构建换构建时间**：构建系统默认从源码编译几乎所有东西，换来的是版本可控与可复现；代价是首次构建慢、宿主机磁盘占用大。预编译包能省时间，但版本控制权就交出去了。
- **精简换可维护性**：镜像裁得越狠，体积越小、启动越快，但后续加一个调试工具都要重新出包；开发阶段留调试余地、量产阶段再精简，是常见的两阶段做法，而不是“一开始就裁到最狠”。
- **跟进上游换稳定性**：内核、工具链与开源组件的安全更新要跟进；构建系统让“升级一个包”变成“改一行版本号再重编”，但升级本身仍可能引入行为变化，量产固件的升级要经过回归测试，不能只看“编过了”。

## 6. 分类与变体

- **按构建系统**：Buildroot、Yocto，以及直接用发行版裁剪（例如 Debian 的嵌入式变体，适合对软件生态要求高的场景；见 02 篇 6 节）。
- **按工具链来源**：内部工具链（构建系统自编，版本受控）与外部工具链（厂商或第三方提供，上手快）。
- **按 C 库**：glibc（功能全、体积大）、musl / uClibc-ng（轻量，适合资源受限的板子），以官方发布为准（待核实各版本的具体支持情况）。
- **按根文件系统格式**：可写的文件系统（如 ext4）与只读压缩格式（如 squashfs，配合可写数据分区），后者是高可靠产品的常见形态，见 02 篇 4.3 节。

## 7. 应用与限制

典型应用：用 Buildroot 快速给一块新板子出第一个可启动的验证系统；用 Yocto 维护一条多板型的产品线，共用应用层、每板一套 BSP；用构建系统输出的 SDK 做应用开发与内核模块编译，保证应用与板上系统一致。

限制有四条：第一，构建系统解决“编出系统”，不解决“系统该有什么功能”——产品定义、驱动与应用仍要另外做；第二，首次构建与宿主机环境有关（磁盘空间、网络、宿主机发行版），构建失败先看构建日志与宿主机依赖是否齐全，而不是先怀疑板子；第三，Yocto 的缓存能省时间，也会在缓存失效、配方改写冲突时给出难定位的错误，排查要理解任务依赖；第四，量产固件的安全更新是长期负担，构建系统只让更新“可执行”，不替你决定“什么时候升、升到哪个版本”。

## 8. 常见误解

- “构建系统就是换个方式编内核”：错。内核只是产物之一，构建系统管的是从工具链到根文件系统、从 Bootloader 到镜像打包的整套流程。
- “Yocto 一定比 Buildroot 高级”：错。两者是不同复杂度下的不同工具；单产品用 Yocto 是多付学习与维护成本，多板型用 Buildroot 是多付同步成本。
- “配置改一行就能换板子”：错。换板子要换 BSP（内核配置、设备树、Bootloader 配置），只改目标架构的配置行远远不够。
- “编过了就等于板上能跑”：错。构建成功只说明宿主机上编出来了，板上启动还要过 Bootloader、DTB 与根文件系统成套对应的那一关，见 02 篇的启动链条。
- “交叉编译只是换个 gcc”：错。工具链三元组、sysroot、C 库与 ABI 都要对齐，见 4.5 节。
