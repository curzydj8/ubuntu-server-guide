# RTOS 任务调度入门

## 1. 本章目标

读完本篇能理解：RTOS 里的任务是什么、内核按什么规则在任务之间切换、任务之间如何安全地交换数据与共享资源，以及优先级反转是怎么发生的、又如何用优先级继承缓解。

## 2. 背景与问题

01 篇已经划过裸机与 RTOS 的分界：任务超过 3–4 个、周期与 deadline 各不相同、需要协议栈或文件系统这类中间件时，超级循环就撑不住了。本篇讲分界另一边的东西：RTOS 到底提供了什么，任务调度是怎么工作的。

新手对 RTOS 最常见的误解是把它当成“小 Linux”：以为有了 RTOS 就有了进程、文件、内存保护。事实正好相反：典型 MCU 上的 RTOS（如 FreeRTOS）没有进程、没有内存管理单元（MMU）、没有虚拟内存，它只解决一件事——在有限资源上，让多个任务按确定的规则分时使用 CPU，并在任务之间安全地传递数据与共享资源。理解这一点，就理解了 RTOS 的全部定位。

本篇以 FreeRTOS 为主要例子，因为它是 MCU 领域最常见的开源 RTOS，概念（任务、队列、信号量、互斥量）也是各家 RTOS 的通用词汇。具体 API 的签名与配置项以 FreeRTOS 官方文档为准，本篇不逐条罗列函数原型。

## 3. 总体架构

一个 RTOS 系统的组成（文字结构图）：

```
应用层
├── 任务 A：周期采样（如每 10ms 读一次传感器）
├── 任务 B：数据处理（如滤波、打包）
├── 任务 C：通信（如经 UART / MQTT 上报）
└── 空闲任务（内核自带：无任务可跑时运行，常用来进低功耗）
        │ 任务间通信：队列、信号量、互斥量、事件组
        ▼
内核层
├── 调度器：按优先级 + 时间片决定下一个跑谁
├── 任务控制块（TCB）：每个任务的状态、优先级、栈指针
├── 系统节拍（Tick）：周期性定时中断，驱动调度与延时
└── 内存管理：静态分配或堆分配任务栈与内核对象
        │
        ▼
硬件层
├── 定时器：产生 Tick 中断（见 04 篇）
├── 中断：外设事件唤醒任务（ISR 发信号，任务干活）
└── CPU 核：上下文切换靠保存/恢复寄存器现场
```

这张图里最重要的一条线是“中断与任务的分工”：ISR 只做“标记 + 发信号”，任务做真正的处理。这与 04 篇的 ISR 纪律是同一条规则在 RTOS 下的形态。

## 4. 工作机制

### 4.1 任务与线程模型：任务就是“有自己栈的函数”

RTOS 里的任务，本质上是一个永不返回的函数，加上一块属于自己的栈。内核为每个任务维护一个任务控制块（TCB），记录任务的状态、优先级、栈顶指针等信息。任务有几种状态：

- **运行态（Running）**：正在占用 CPU 的任务，同一时刻只有一个（单核）。
- **就绪态（Ready）**：能跑、但在等 CPU 的任务，按优先级排队。
- **阻塞态（Blocked）**：在等某件事的任务——等延时到期、等队列里有数据、等信号量被释放。阻塞的任务不占 CPU，调度器根本不会考虑它。
- **挂起态（Suspended）**：被显式挂起的任务，除非有人恢复它，否则永远不跑。挂起是调试与特殊流程用的手段，正常业务逻辑里很少用。

任务与通用操作系统里“线程”的关系：概念上几乎等同——都是独立的执行流、都有自己的栈。区别在隔离性：没有 MMU 的 MCU 上，所有任务共享同一地址空间，一个任务的指针错误可以踩坏另一个任务的栈或全局变量，整个系统一起崩溃。RTOS 不提供进程那样的隔离保护，这是它与 Linux 最本质的区别之一（见 02 篇）。

创建任务要定三件事：入口函数、栈大小、优先级。栈大小是最容易配错的一项：栈太小会溢出（踩坏相邻内存，故障表现千奇百怪），栈太大浪费 RAM（MCU 的 RAM 只有几十到几百 KB）。栈深度的估算要看调用链与局部变量，FreeRTOS 提供栈使用水位检测（以官方文档为准），上线前应用它核对每个任务的实际用量，而不是凭感觉分配。

### 4.2 优先级抢占调度：高优先级来了，立刻让位

FreeRTOS 的默认调度策略是**基于优先级的抢占式调度**：

- 每个任务有一个优先级，数值越大优先级越高（FreeRTOS 的约定，具体范围以官方文档为准）。
- 调度器永远运行就绪任务中优先级最高的那个。
- 正在运行的任务如果有更高优先级的任务变为就绪（例如它等的信号量被释放了），内核会立即切换过去，这就是“抢占”。被抢占的任务回到就绪态，等高优先级任务阻塞或完成后再继续。

抢占带来两个直接后果：第一，高优先级任务的响应延迟有了上限——只要它变为就绪，最多等一次上下文切换就能跑，这是 RTOS “实时性”的来源；第二，低优先级任务可能长期抢不到 CPU（饿死），优先级设计必须保证每个任务在最坏情况下仍能得到执行机会，关键任务不能被无关的高优先级任务持续压住。

与之相对的是**合作式调度**：任务只有主动让出 CPU（阻塞或调用让出接口）时才切换。合作式调度没有抢占带来的不确定性，但一个任务忘了让出，整个系统就卡死。FreeRTOS 支持两种模式（以官方文档的配置项为准），默认是抢占式；合作式只在极简单的场景下使用，本篇不推荐新手用它。

### 4.3 时间片：同优先级的任务轮流跑

优先级解决了“谁先跑”，时间片解决“同优先级谁跑多久”。当多个同优先级任务同时就绪时，调度器按时间片轮转：每个任务跑满一个时间片（通常等于一个或几个系统节拍 Tick），就被切到队尾，下一个同优先级任务接着跑。

时间片的两个要点：

- **时间片长度由 Tick 决定**：Tick 是内核的周期性定时中断（见 4.4 节），时间片通常是 Tick 的整数倍。Tick 越快，切换越频繁、响应越均匀，但上下文切换的开销占比也越高；Tick 太慢，同优先级任务之间会感觉“卡顿”。
- **时间片只在同优先级之间轮转**：高优先级任务就绪时，时间片轮转立刻中断——优先级永远优先于时间片。不要以为“时间片轮转”等于“大家平均分 CPU”，它只在同一优先级内平均。

是否启用时间片轮转是可配置的（FreeRTOS 以官方文档的配置项为准）。关掉时间片后，同优先级任务之间不再自动轮换，先跑的任务会一直跑到自己阻塞为止，后面的任务可能饿死——除非业务逻辑上保证每个任务都会主动阻塞，否则不要关。

### 4.4 系统节拍（Tick）与延时：内核的时间基准

Tick 是 RTOS 的心跳：一个周期性定时中断（通常 1ms 一次，具体频率以工程配置与官方文档为准），每次中断内核做两件事：更新系统时间、检查有没有任务的延时到期了、该从阻塞态回到就绪态。

任务延时（例如“睡 10ms”）就是靠 Tick 实现的：任务调用延时接口后进入阻塞态，内核把它挂到延时链表上，Tick 中断每次检查，到期就唤醒。这里有两个实务要点：

- **延时精度是 Tick 级的**：Tick 周期 1ms 时，延时 10ms 的实际唤醒时刻有最多 1 个 Tick 的抖动；对时序精度要求到微秒级的场合，不能用任务延时，要用定时器硬件（见 04 篇）。
- **相对延时与绝对延时**：相对延时是“从现在起睡 X”，多次循环会累积每次的调度抖动，周期越跑越偏；绝对延时是“睡到下一个 X 的整数倍时刻”，每次按固定节拍唤醒，长期周期稳定。周期性采样任务应该用绝对延时，这是 FreeRTOS 官方文档明确推荐的做法。

### 4.5 任务间通信之一：队列——任务之间传数据的正道

队列（Queue）是 FreeRTOS 里任务间传数据的标准方式：一个先进先出的缓冲区，发送任务把数据拷贝进队列，接收任务从队列里取出来。队列的要点：

- **按值拷贝**：队列里存的是数据的副本，不是引用。发送大结构体进队列会拷贝一份，耗时与内存开销都要算进去；传大块数据时，队列里传指针、数据本身放共享缓冲区是常见做法，但指针指向的内存生命周期要由双方约定好。
- **阻塞式收发**：队列满时发送任务可以阻塞等空位，队列空时接收任务可以阻塞等数据，超时时间由调用者指定。阻塞式收发让任务在“没事干”时不占 CPU，这是 RTOS 任务“等事件”而不是“轮询”的关键。
- **ISR 也能用队列**：中断服务程序里不能阻塞，但可以用队列的 ISR 版本接口发数据——ISR 把采样结果丢进队列就返回，任务收到数据再处理。这是“ISR 标记、任务干活”在 RTOS 下的标准形态，与 04 篇的纪律完全一致。

队列是任务间通信的首选：它既传数据，又自带同步（空了等、满了等），多数场景下不需要再加别的同步原语。

### 4.6 任务间通信之二：信号量与互斥量——管“事件”与管“资源”

信号量（Semaphore）与互斥量（Mutex）长得很像，但用途不同，分不清是 RTOS 新手最常见的概念错误：

- **二值信号量**：只有 0 和 1 两种状态，用来做“事件通知”——例如 ISR 释放信号量，任务获取信号量后开始处理。它回答的问题是“事情发生了没有”，不回答“谁先谁后”。
- **计数信号量**：计数值可以大于 1，用来管理“有 N 个名额的资源”，例如有 3 个缓冲区，信号量初值 3，拿一个减一、还一个加一。计数到 0 时再想拿就阻塞。
- **互斥量（Mutex）**：专门用来保护“同一时刻只能一个人用的共享资源”，例如串口、全局配置结构。任务进入临界区前获取互斥量、用完释放，别的任务想用就阻塞等。互斥量与二值信号量的关键区别：互斥量有“所有权”——只有获取它的任务才能释放它；而且互斥量支持优先级继承（见 4.7 节），二值信号量不支持。

选型口诀：通知事件用信号量，保护共享资源用互斥量。拿二值信号量当互斥量用，优先级反转来了没有任何缓解手段；拿互斥量当事件通知用，所有权语义会让 ISR 无法释放它（ISR 不能获取互斥量），代码写出来就是错的。

### 4.7 优先级反转与优先级继承：低优先级任务拖住高优先级任务

优先级反转是 RTOS 里最经典的故障模式，发生过程分三步：

1. 低优先级任务 L 获取了互斥量，正在用共享资源。
2. 高优先级任务 H 就绪，想获取同一个互斥量，阻塞等待。
3. 中优先级任务 M 就绪（不碰这个互斥量），按优先级抢占了 L——L 迟迟跑不完、迟迟不释放互斥量，H 就一直等着。

结果是：H 的实际等待时间取决于 M 跑多久，而 M 与 H 之间没有任何资源关系——优先级体系被“绕过去了”。1997 年火星探路者号（Mars Pathfinder）的故障就是优先级反转的著名实例（以公开报道为准，细节待核实），系统反复复位，最终靠远程补丁缓解。

缓解办法是**优先级继承**：L 持有互斥量、H 在等它时，内核临时把 L 的优先级提升到与 H 相同，让 L 尽快跑完、释放互斥量，然后 L 的优先级恢复原值。FreeRTOS 的互斥量默认支持优先级继承（以官方文档为准），这是用互斥量而不用二值信号量保护共享资源的核心理由之一。

但优先级继承不是万能药：它只缓解“一层”反转，多重嵌套的互斥量、链式等待仍可能出问题；而且它治标不治本——真正的根治是缩短临界区（持有互斥量的时间越短，反转窗口越小）、减少共享资源、让高优先级任务尽量不依赖低优先级任务持有的资源。设计时先想“能不能不共享”，再想“怎么共享才安全”。

### 4.8 事件组与任务通知：轻量同步的补充

除了队列与信号量，FreeRTOS 还提供两种轻量机制：

- **事件组（Event Group）**：一组标志位，任务可以等“其中某一位”或“全部几位”被置位。适合“等多个条件都满足再继续”的场景，例如等 Wi-Fi 连上且传感器就绪。事件组的代价是标志位本身不携带数据，数据还要另传。
- **任务通知（Task Notification）**：直接给某个任务发一个 32 位值或一个“有通知了”的标记，比队列与信号量更快、开销更小。适合一对一的简单通知，例如 ISR 唤醒某个固定任务。缺点是只能发给指定任务，不适合一对多，语义也不如队列直观。

选型原则：先用队列与信号量把逻辑写清楚，确认性能瓶颈真的在同步原语上，再考虑任务通知这类轻量机制。过早优化同步原语，是 RTOS 代码可读性变差的常见起点。

## 5. 关键设计取舍

- **任务数量 vs 调度开销**：任务越多，结构越清晰，但每个任务都要占一份栈与 TCB，上下文切换也越频繁。任务划分按“周期与 deadline 不同”来分，而不是按“功能模块”机械地分——周期相同的几个小功能可以合在一个任务里。
- **优先级数量 vs 设计复杂度**：FreeRTOS 的优先级档位数可配置（以官方文档为准）。档位越多，调度越精细，但优先级设计越容易出错；常规做法是只用少数几档（高/中/低），并给每个任务的优先级写明理由，而不是随手填数字。
- **阻塞等待 vs 轮询**：任务等事件时用阻塞式接口（等队列、等信号量），不要用“while 循环里反复查标志位”的轮询——轮询的任务一直在占 CPU，阻塞的任务在等的时候零开销。这是 RTOS 与裸机超级循环在写法上最大的不同。
- **动态创建 vs 静态分配**：FreeRTOS 支持运行时动态创建任务与队列，也支持静态分配（编译时定好内存）。动态创建灵活，但堆碎片与创建失败是真实风险；静态分配可预测性强，是量产产品的常规选择。选哪种以产品可靠性要求为准。

## 6. 分类与变体

- **按调度策略**：抢占式调度（默认，高优先级可打断低优先级）与合作式调度（任务主动让出才切换），见 4.2 节。
- **按内核形态**：FreeRTOS 这类“微内核 + 可选组件”（任务、队列、信号量是核心，协议栈、文件系统是外挂组件）与包含完整中间件的商用 RTOS（如包含图形、网络、安全认证的成套方案）。概念相通，取舍在生态与授权模式，不展开厂商对比。
- **按实时性保证**：硬实时 RTOS（有可证明的响应时间上限，调度延迟可分析）与通用分时系统（平均响应快，但最坏情况无保证）。MCU 上的 FreeRTOS 属于前者，但“硬实时”只在优先级设计合理、临界区够短、中断延迟可控的前提下成立，配错了同样不实时。
- **与裸机、嵌入式 Linux 的关系**：裸机（超级循环 + 中断，见 01 篇 5.1 节）适合任务少、逻辑简单的场合；RTOS 适合多任务、有明确 deadline 的控制场景；嵌入式 Linux（见 02 篇）适合需要进程隔离、文件系统、网络协议栈全套的复杂设备。三者是按复杂度递进的工具，不是互相替代的版本。

## 7. 应用与限制

典型应用：多传感器周期采样与上报、带通信协议栈的联网设备、电机控制与人机界面并存的设备、需要明确 deadline 的工业控制。限制有五条：第一，没有 MMU 的芯片上任务之间没有内存隔离，一个任务的错误会拖垮全系统；第二，栈溢出、死锁、优先级反转是 RTOS 特有的故障模式，调试时要理解任务切换，裸机的调试经验不能直接照搬；第三，内核本身占 Flash 与 RAM，资源极紧张的 8 位小芯片上 RTOS 未必划算；第四，实时性是设计出来的——优先级、临界区长度、中断延迟都要算最坏情况，只写“能跑起来”的代码不等于满足了 deadline；第五，本篇的概念以 FreeRTOS 为例，具体 API 与配置项以 FreeRTOS 官方文档为准，其他 RTOS 的接口名称与语义可能不同。

## 8. 常见误解

- “RTOS 就是小 Linux”：错。典型 MCU RTOS 没有进程、没有 MMU、没有虚拟内存，它只解决多任务调度与任务间通信。
- “任务越多越能体现 RTOS 的优势”：错。任务划分按周期与 deadline 分，机械地按功能模块拆任务只会增加调度开销与栈占用。
- “优先级越高，任务跑得越快”：错。优先级决定“谁先跑”，不决定“跑多快”；高优先级任务里写死循环，低优先级任务照样饿死。
- “二值信号量和互斥量可以互换”：错。互斥量有所有权与优先级继承，信号量没有；保护共享资源必须用互斥量。
- “用了 RTOS 就自动满足实时性”：错。实时性来自优先级设计、临界区长度与中断延迟的最坏情况分析，RTOS 只是提供了实现它的机制。
