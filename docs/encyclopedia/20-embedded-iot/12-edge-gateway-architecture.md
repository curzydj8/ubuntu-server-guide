# 边缘网关架构

## 1. 本章目标

读完本篇能理解：边缘网关在设备与云之间处在什么位置，协议转换、本地缓存与断网续传、边缘规则引擎各自解决什么问题，以及工控机、单板机、虚拟化三种部署形态的取舍。

## 2. 背景与问题

本域前三篇讲的是设备自身：单片机做控制、嵌入式 Linux 跑系统服务、传感器经 UART/I2C/SPI 把数据读进来、再由 MQTT 发向云端。但现实中的现场很少是“一台设备直连云”：

- 现场设备说的“语言”各不相同——老设备可能只有串口或 Modbus，传感器走 I2C/SPI，新设备走 MQTT，彼此互不相通；
- 现场网络不可靠，断网时数据不能丢，控制动作不能等云端回话；
- 原始数据量太大，全部上云既贵又慢，很多判断在现场做完、只把结果上报就够了。

边缘网关就是为这三个问题而存在的中间层：它站在设备与云之间，向上收敛现场的异构设备，向下屏蔽网络的不稳定，在本地完成一部分计算与决策。它不是另一台“更强的传感器”，也不是云的缩小版，而是一个专门做“接入、转换、缓存、就地决策”的汇聚节点。

## 3. 总体架构

一台边缘网关在系统里的位置（文字结构图）：

```
现场设备层
 ├── 传感器 / 执行器（经 I2C、SPI、UART 接入，见本域第三篇）
 ├── 旧式工业设备（串口、Modbus 等现场总线）
 └── 新式联网设备（MQTT、CoAP、HTTP）
        ↓ 南向接入
边缘网关
 ├── 协议适配层（协议转换：把各路协议统一成内部数据模型）
 ├── 数据处理层（过滤、聚合、本地缓存）
 ├── 规则引擎（本地判断：阈值告警、联动控制）
 └── 北向通信层（经 MQTT/HTTPS 与云端同步，断网时缓存待传）
        ↓ 北向接入
云端
 ├── 设备管理、数据存储与可视化
 └── 模型训练、策略下发（见本篇姊妹篇《边缘 AI 推理部署》）
```

理解这张图的关键是数据的两条路径：**控制路径尽量短**（传感器超阈值 → 网关规则引擎 → 执行器动作，不经过云），**管理路径可以长**（配置下发、固件升级、历史数据分析走云端）。两条路径分开，是边缘架构最核心的设计思想。

## 4. 工作机制

### 4.1 南向接入：把异构设备收敛进来

网关的南向接口负责“听懂”现场设备。常见形态有三类：板内总线（I2C/SPI/UART，适合网关直连的传感器）、现场总线与工业协议（串口、Modbus、CAN 等，适合已部署的旧设备）、IP 协议（MQTT、CoAP、HTTP，适合新式联网设备）。南向接入的设计要点是隔离：某一台设备出故障（例如某路串口卡死、某传感器不断重连）不应拖垮整台网关对其他设备的采集，常见做法是每路接入独立进程或线程、独立超时与重连策略。

### 4.2 协议转换：统一数据模型，而不是逐个翻译

协议转换不是把“协议 A 的报文逐字翻译成协议 B 的报文”，而是先定义一套与协议无关的内部数据模型——通常是“设备 + 测点 + 时间戳 + 数值 + 质量位”的结构化记录——南向把各路协议解析进这个模型，北向再从这个模型编码成云端要的格式。这样做的好处是：新增一种现场协议时，只需写一个南向适配器，不用改动北向与规则引擎；反过来，云端换一套上报格式时，也只需改北向编码器。

协议转换中容易出错的两个细节：第一是**时间语义**，现场设备的时间可能不准或没有时钟，上报时要区分“设备时间”“网关收到时间”“云端收到时间”，三者混用会导致时序分析全错；第二是**单位与量程**，不同设备对同一物理量的单位、量程可能不同，转换层要做归一化，不能只做透传。

### 4.3 本地缓存与断网续传：网络不可靠是常态，不是异常

网关与云之间的网络在现场环境里随时可能中断——断线、弱信号、云端维护。本地缓存与断网续传的机制是：

- **写入即缓存**：数据先写入网关本地存储（通常是磁盘上的持久化队列或时序数据库），再异步上报云端，而不是“先上报、失败再补”。本地落盘在先，断电也不丢已采集的数据。
- **断网续传**：网络中断期间数据继续在本地累积，恢复后按时间顺序补传；补传要带去重标识，避免重传造成云端重复记录。
- **缓存有界**：本地存储不是无限的。缓存策略要事先定好：存满后是丢最旧的数据、丢优先级最低的数据，还是停采并告警？不同业务答案不同，但“无限缓存”不是答案——一台长期断网的网关迟早会把磁盘写满。
- **断网期间的本地能力不降级**：缓存只是数据侧；规则引擎、本地告警、本地控制在断网时仍要正常工作（见 4.4）。一台断网就“变砖”的网关，等于把现场可靠性交给了最不可靠的一环。

缓存容量的具体数值（如某款网关能缓存多少天的数据）取决于存储大小、采样频率与数据格式，以官方发布为准（待核实），本篇不给具体数字。

### 4.4 边缘规则引擎：把判断留在现场

规则引擎是网关上跑的一组“如果……就……”判断：温度超过阈值就告警、连续三次超标就停机、A 传感器与 B 传感器同时异常就触发联动。它与云端规则的区别不在语法，而在位置与时延：本地规则不需要等一次网络往返，适合对延迟敏感的控制与告警；云端规则适合需要全局数据、复杂计算的判断（例如跨多个网关的关联分析）。

规则引擎的设计要点有三条：规则要可热更新（改规则不重启网关、不中断采集）；规则执行要有明确的优先级与冲突处理（两条规则同时触发、动作矛盾时听谁的）；规则触发的动作要可审计——什么时间、哪条规则、执行了什么动作，都要留日志，否则现场出问题后无法复盘。

## 5. 关键设计取舍

- **本地算多少 vs 上云算多少**：本地算得越多，响应越快、对网络依赖越小，但网关硬件成本、功耗与维护复杂度越高；全送云端则网关可以很便宜，但断网即停摆、延迟不可控。取舍标准是业务对延迟与断网的容忍度，不是“越边缘越好”。
- **通用网关 vs 专用网关**：通用网关（跑 Linux、可装多种适配器与规则）灵活、复用性好，但体积、功耗与成本高于只做一件事的专用网关；专用网关（例如只做某一种工业协议转换的盒子）便宜可靠，但换个场景就要换硬件。
- **数据全量上云 vs 边缘聚合后上报**：全量上云保留了原始数据、方便事后分析，但带宽与存储成本高；边缘先聚合（例如每分钟只上报平均值与极值）省带宽，但丢掉了原始细节，事后无法追问“那一分钟里到底发生了什么”。两者可以并存：聚合值实时上报、原始数据本地留存一段时间备查。

## 6. 分类与变体

### 6.1 按部署形态分

- **工控机形态**：工业级 x86 或 ARM 整机，带宽温、抗震、防尘设计与多串口、多网口，常装在配电柜、机房机柜里。优点是性能与扩展性强、接口丰富、长期运行可靠；代价是体积大、功耗与成本高于单板机。适合工厂、楼宇、能源站等固定场所。
- **单板机形态**：以单板计算机（如树莓派类板卡）或嵌入式模组为核心的小型网关，体积小、功耗低、成本低。优点是部署灵活、适合原型与小规模场景；限制是接口较少、工业环境适应性（温度、电磁干扰、长期供电）要另外评估，量产前要核对板卡的工业级指标。适合家居、农业、零售、试点项目。
- **虚拟化形态**：网关以虚拟机或容器的形式跑在现场已有的服务器或边缘计算节点上，不再是一台独立硬件。优点是复用现有算力、易于集中管理与备份；前提是现场已有可用的宿主机，且宿主机的宕机不会同时带走网关。适合已有 IT 基础设施的园区、门店、分支机构。

三种形态不是档次高低，而是场景不同；同一套网关软件可能同时提供三种部署包，选型时先看现场条件（有没有机柜、有没有服务器、环境多恶劣），再看软件需求。

### 6.2 按网络位置分

- **现场网关**：装在设备旁边，管一个车间、一栋楼、一个站点，是最常见的形态。
- **汇聚网关**：管多个现场网关，做二次汇聚与区域级决策，适合多站点连锁场景。汇聚层越多，单点故障的影响面越大，设计时要考虑冗余。

## 7. 应用与限制

典型应用：工厂设备联网与产线数据采集、楼宇自控（空调、照明、能耗）、智慧农业（大棚温湿度与灌溉联动）、零售门店设备管理、充电桩与能源站监控。限制有四条：网关本身是单点汇聚，网关宕机的影响面比单台设备大，关键场景要考虑冗余或降级方案；网关的安全面比单台设备大——它既连现场总线又连互联网，口令、证书、固件更新缺一不可，这部分与 10 域安全内容交叉；网关的算力与存储有上限，不适合把云端的大模型训练、全局关联分析搬下来；最后，网关的价值取决于现场协议的适配质量，冷门协议的适配器可能不存在或质量参差，选型前要核对协议支持清单。

## 8. 常见误解

- “网关就是一台小服务器”：错。服务器追求通用算力，网关追求接入、转换与断网下的本地自治，两者的设计重心不同。
- “上了网关就不用云了”：错。网关做的是就地决策与接入收敛，设备管理、全局分析、模型训练仍在云端；网关与云是分工，不是替代。
- “断网续传等于数据不丢”：错。续传只能保证网络恢复后补传本地已缓存的数据；缓存写满、网关断电损坏、本地存储故障时，数据照样会丢。缓存策略与存储可靠性要一起设计。
- “协议转换就是透传报文”：错。只透传不建统一数据模型，每新增一种协议或一个云端格式就要改全链路，维护成本会随设备种类线性增长。
