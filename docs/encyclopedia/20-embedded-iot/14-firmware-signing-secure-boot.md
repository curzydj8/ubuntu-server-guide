# 固件签名与安全启动

## 1. 技术原理

### 1.1 信任链：从不可改的起点逐级传递信任

安全启动要回答一个基本问题：设备上电后执行的第一行代码，以及之后加载的每一段固件，凭什么被相信没有被改过？答案是信任链（Chain of Trust）：信任从一个不可改的起点开始，逐级传递，每一级在把执行权交给下一级之前，先校验下一级的完整性与来源，校验通过才放行，失败则停在安全状态。

信任链的起点通常是固化在芯片里的代码（BootROM）与不可改的信任根（Root of Trust）。信任根里保存的不是固件本身，而是校验固件所用的公钥或公钥摘要——公钥本身不保密，保密的是与之对应的私钥，私钥只掌握在固件发布方手里。信任链逐级展开的形态，与[嵌入式 Linux 的启动流程](02-embedded-linux.md)中 BootROM → Bootloader → 内核 → 根文件系统的链条一一对应：安全启动就是给这条链的每一级加上“先校验、再交权”的规则。

信任链成立依赖三个前提，缺一不可：第一，起点不可改（固化代码与信任根存储不可被普通写操作覆盖）；第二，校验用的公钥不可被悄悄替换（否则攻击者可以用自己的密钥给篡改过的固件“背书”）；第三，每一级的校验逻辑本身没有被绕过（校验失败必须真正阻止启动，而不是只记一条日志就继续跑）。工程上常把信任根公钥的摘要烧写进一次性可编程存储（OTP）或熔丝里，正是因为熔丝烧断后不可恢复，起到了“公钥不可替换”的作用。

### 1.2 固件签名与验签流程

固件签名的原理来自数字签名：发布方用私钥对固件（或固件的摘要）签名，设备用对应的公钥验签。签名与加密是两回事——签名不保证固件内容保密，它保证的是来源真实与内容完整：验签通过，说明这份固件确实由持有私钥的一方发布，且发布后没有被改过一个字节。签名的数学原理见[哈希与数字签名](../13-cryptography/02-hash-signature.md)与[数字签名算法详解](../13-cryptography/07-signature-algorithms.md)，本篇只讲它在固件流程里的位置。

一条完整的签名与验签流程分发布侧与设备侧：

- **发布侧（构建与签名）**：固件构建完成后，计算固件的摘要（哈希值），用发布私钥对摘要签名，把“固件 + 签名 + 证书（可选）”打包成发布件。签名操作应在受控的签名环境里进行，私钥不随构建机日常使用，不进代码仓库。
- **设备侧（验签与放行）**：设备启动到某一阶段时，先计算待加载固件的摘要，再用信任根中的公钥验证签名。两者都对上才把执行权交给该固件；任何一步对不上，都按预设的失败策略处理。

验签有两处容易被误解：第一，验签只校验“固件是不是发布方签发的、发布后有没有被改”，不校验“固件本身有没有漏洞”——一份签过名的旧版本固件可能带着已知漏洞，因此还需要版本号防回滚机制（见 6.2）；第二，签名校验发生在加载之前，固件只有通过校验才会被执行，未通过校验的固件不应被执行，哪怕它“看起来能跑”。

### 1.3 安全启动的启动阶段校验

安全启动不是一个开关，而是一条链上每一级的校验动作。以[嵌入式 Linux 启动链](02-embedded-linux.md)为例，各阶段的校验分工大致如下：

- **BootROM 校验 Bootloader**：BootROM 是固化代码，它用信任根公钥校验 Bootloader 的签名，通过后才跳转执行。这是整条链的锚点——BootROM 本身不可改，它的校验逻辑也不可改。
- **Bootloader 校验内核**：Bootloader 被信任后，由它校验内核镜像与设备树（DTB）的签名。设备树同样要校验，因为设备树描述硬件，改掉设备树同样能改变设备行为。
- **内核与用户态的延续校验**：内核启动后，对根文件系统与关键应用的校验可由内核的完整性机制延续（例如只读挂载、完整性校验机制，具体机制以所用系统与芯片方案的官方文档为准）。本篇不展开具体机制的配置步骤，只强调原则：信任链不应在内核启动后就断掉，越是关键的启动后组件，越应纳入校验范围。

每一级校验失败的默认策略应是“停在安全状态”：拒绝启动、停留在 Bootloader 的恢复模式等待合法固件，或回滚到上一个已验证的版本。失败时设备应记录可供排查的校验失败信息（哪一级、哪种失败原因），但不应把私钥、密钥材料或绕过校验的方法输出到日志里。

## 4. 风险

- **私钥泄露风险**：发布私钥一旦泄露，持有者就能给任意固件签名，整条信任链随之失效。规避做法：私钥只存放在受控的签名环境或硬件安全模块中，不进代码仓库、不随构建产物分发，访问权限最小化并留审计记录。
- **信任根被替换风险**：校验用的公钥若能被替换，验签就失去意义。规避做法：公钥或其摘要烧写进 OTP/熔丝等不可改存储，量产前核对烧写值与发布值一致。
- **旧版本固件被重放风险**：已签名的旧固件本身能通过验签，但可能含有已知漏洞。规避做法：引入单调递增的版本号或安全版本号，设备拒绝低于当前安全版本的固件（见 6.2）。
- **校验失败处理不当风险**：失败后继续启动等于没有安全启动；失败后变砖则影响可维护性。规避做法：失败默认停在安全状态，同时保留合法的恢复路径（恢复模式或回滚分区），恢复路径本身也要经过验签。
- **供应链与量产环节风险**：密钥在量产烧录、代工、物流环节可能被复制或错烧。规避做法：见 6.3 的量产密钥管理原则，密钥注入与烧录过程应可审计、可追溯。

## 5. 检测方式

防御者可从以下信号发现安全启动相关的问题，均属检测侧，不涉及规避检测的方法：

- **启动日志中的验签失败记录**：哪一级校验失败、失败原因是签名不对、摘要不对还是版本过低，应有明确区分的日志，便于定位是固件损坏、版本错误还是密钥不匹配。
- **版本号与安全版本号异常**：设备上报的固件版本低于已发布的安全版本，或版本号出现回退，是旧版本固件被重放的信号，应触发告警并按策略处理。
- **启动次数与恢复模式进入频率异常**：同一设备反复进入恢复模式或反复校验失败，可能意味着固件损坏、烧录错误或存储介质故障，应先按硬件与烧录流程排查。
- **签名环境审计**：签名操作的次数、操作者、签名对象应有审计记录；出现未在发布计划内的签名记录时，应立即核查签名环境是否被越权使用。
- **量产抽检**：量产线上抽检设备的信任根烧写值、固件签名与版本号，与发布记录逐项核对，发现错烧、漏烧及时隔离该批次。

## 6. 修复与防御方法

### 6.1 信任链设计的检查清单

- 信任根不可改：公钥摘要进 OTP/熔丝，量产前核对。
- 每一级都校验下一级，不留“信任但不校验”的缺口。
- 校验失败默认拒绝启动，失败原因可记录、可区分。
- 恢复路径（恢复模式、回滚分区）本身也要验签，不能成为绕过校验的后门。
- 信任链的每一级都应有明确的责任方：谁签 Bootloader、谁签内核、谁负责吊销，出问题时找得到人。

### 6.2 密钥吊销与轮换

密钥不是“一把用终身”的东西。吊销与轮换的原理是：当一把密钥不再可信（泄露、到期、算法不再安全）时，用一套可信的机制让设备不再接受它，并平滑过渡到新密钥。密钥的通用生命周期见[密钥生命周期管理](../13-cryptography/10-key-lifecycle-management.md)，设备侧的具体做法如下：

- **吊销**：设备端维护一份可信的吊销信息（例如吊销的密钥标识或证书列表，随合法固件更新下发）。验签时除验证签名本身，还要查该密钥是否已被吊销；已被吊销的密钥签发的固件即使签名数学上成立，也应拒绝。吊销信息本身必须经过签名与验签下发，不能接受未经校验的吊销指令。
- **轮换**：新密钥应提前部署——先把新公钥（或新证书）随一次合法固件更新下发到设备并存入可信存储，确认设备已接受新密钥后，再用新私钥签发后续固件。切忌“先停用旧密钥、再下发新密钥”的顺序，那样会造成设备无密钥可用。轮换期间新旧密钥可并存一段时间，过渡完成后再吊销旧密钥。
- **防回滚**：版本号或安全版本号应单调递增并由设备持久记录；设备拒绝版本号低于已记录安全版本的固件，即使该固件的签名有效。版本号的更新本身也应纳入签名保护，防止版本号被单独篡改。
- **应急吊销预案**：私钥泄露时的应急流程应事先写好并演练：谁有权发起吊销、吊销信息如何签名下发、已部署设备如何分批过渡、过渡失败的设备如何恢复。应急时再现想流程，是最常见的处置失败原因。

### 6.3 量产烧录时的密钥管理原则

量产是密钥最容易出问题的环节，原则只有几条，但每条都不可打折：

- **一设备一密钥材料**：信任根公钥摘要、设备身份密钥等关键材料应按设备唯一烧写，不可全线共用同一份私钥材料；共用一份意味着一台设备泄露等于全线泄露。
- **私钥不出受控环境**：发布私钥不出签名服务器或硬件安全模块；量产线上只烧写公钥、公钥摘要与设备自身的身份材料，不在产线存放发布私钥。
- **烧录可核对、可追溯**：每台设备的烧写值（公钥摘要、版本号）应有记录并可与发布值核对；抽检不合格的批次隔离复查，不流入市场。
- **最小权限与审计**：产线烧录工位只给烧录所需的最小权限，烧录操作留审计记录；调试接口在量产出厂前关闭或按产品安全策略锁定，锁定状态列入出厂检验项。
- **密钥材料与固件分离管理**：密钥的生成、分发、吊销由密钥管理流程负责，不随固件构建脚本随意存放；固件仓库里不应出现任何私钥材料。

## 7. 常见误解

- “签了名就等于没有漏洞”：错。签名只保证来源与完整，不保证固件本身没有漏洞；旧版本固件的漏洞要靠防回滚与及时更新解决。
- “安全启动开了就万事大吉”：错。安全启动只覆盖启动链，运行时的漏洞、通信安全、密钥管理同样需要防御，缺一块都会以故障形式补回来。
- “验签失败记条日志继续启动也行”：错。失败后继续启动等于没有校验，默认策略必须是停在安全状态或回滚。
- “一把密钥全产品线共用更方便”：错。共用意味着单点泄露等于全线失守，设备身份材料应一设备一份。
- “吊销就是把旧密钥删掉”：错。吊销需要设备能可信地收到吊销信息并拒绝旧密钥，删服务器上的密钥不等于设备不再信任它。
