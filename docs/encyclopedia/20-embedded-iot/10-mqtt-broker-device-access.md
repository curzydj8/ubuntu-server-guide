# MQTT Broker 与设备接入

## 1. 一句话定义

MQTT Broker 是物联网系统中负责接收、路由和分发 MQTT 消息的中间服务器：设备不直接互发消息，而是把消息发给 Broker，由 Broker 按主题转发给订阅方。

## 2. 为什么需要 Broker

上一篇讲过，MQTT 采用发布/订阅模型，发布者和订阅者互不知道对方存在，只通过主题解耦。这个模型成立的前提，是中间必须有一个双方都连得上的中转点——这就是 Broker。没有 Broker，设备之间只能回到点对点直连：每新增一个接收方就要多维护一条连接，设备上线下线、网络抖动、消息重发都要每个设备自己处理，系统很快变得不可维护。

Broker 把这些共性工作集中起来：维护设备连接、按主题路由消息、处理离线与重发、管理认证与权限。一台温湿度传感器只需要做一件事——连上 Broker、往主题发数据，至于数据要被几个应用消费、某个消费方当时在不在线，都不是传感器要操心的事。

## 3. Broker 的核心作用

### 3.1 连接管理

Broker 维护所有在线客户端的连接状态：谁连着、用的什么客户端 ID、会话是否持久。设备断线时 Broker 能感知到（TCP 断开或心跳超时），并据此触发遗嘱消息（见第 6 节）。

### 3.2 主题路由

Broker 按主题把消息从发布者转发给订阅者，支持通配符订阅（`+` 匹配一层、`#` 匹配多层）。路由只认主题字符串，不解析消息载荷——载荷是 JSON、Protobuf 还是二进制，Broker 不关心，收发双方自行约定。

### 3.3 QoS 语义的落地

QoS 0/1/2 的送达语义（最多一次、至少一次、恰好一次）由 Broker 与客户端配合实现，概念见本域第三篇。需要注意：QoS 保证的是“送达”，不是“实时”；延迟敏感的控制回路不应走 MQTT，这一点在第三篇已有说明，本篇不再展开。

### 3.4 安全边界

认证（谁能连）、授权（谁能发/订哪些主题）、传输加密（TLS）都以 Broker 为 enforcement 点。设备不直接暴露给消费方，消费方也不直接接触设备，Broker 是唯一的交汇面，也是安全策略最集中的地方。

## 4. Broker 选型：开源自建 vs 云端托管

选型首先要分清两种部署形态：自己部署开源 Broker，还是用云厂商提供的托管 MQTT 服务（托管服务通常是物联网云平台的一部分，见下一篇）。

### 4.1 开源自建

开源 Broker 的选型示例（仅作举例，不做性能排名，未实测对比）：Eclipse Mosquitto（轻量、单机场景常用）、EMQX（面向集群与大规模连接场景设计）。两者都是开源项目，具体版本特性与部署方式以各自官方文档为准。

自建的优点：数据不出自己的网络、部署形态可控、无按量计费、便于与本地系统集成。代价：高可用、备份、扩容、证书管理、版本升级全部自己负责；Broker 是单点——它挂了，全网消息就断，生产环境要做集群或主备，运维成本真实存在。

### 4.2 云端托管

云厂商的托管 MQTT 服务把 Broker 的运维（高可用、扩容、证书轮换）交给云厂商，设备直接接入云端。优点是免运维、弹性伸缩、与云端存储、规则引擎、数据分析天然衔接；代价是按连接数与消息量计费（价格与配额以官方发布为准，待核实）、数据要出内网、与厂商的绑定程度较高。托管服务的具体计费与配额本篇不展开，见下一篇的选型维度。

### 4.3 选型取舍

| 维度 | 开源自建 | 云端托管 |
|---|---|---|
| 运维负担 | 自己负责高可用、备份、升级 | 云厂商负责 |
| 数据位置 | 可留在内网 | 经过云端 |
| 成本结构 | 服务器与人力成本为主 | 按连接数与消息量计费，价格与配额以官方发布为准（待核实） |
| 扩展性 | 靠自己做集群与扩容 | 弹性伸缩 |
| 厂商绑定 | 低 | 较高 |
| 适用场景 | 内网系统、数据敏感、连接规模可预期 | 快速上线、规模波动大、需要云端能力 |

选型口诀：原型与内网小规模先看开源自建；要快速上线、规模不确定、需要云端存储与规则引擎，评估托管服务；数据合规要求明确的场景，先定合规边界再选形态。

## 5. 主题设计与命名规范

主题设计是系统设计的一部分，不是事后命名。主题一旦上线就很难改——设备固件、订阅方、规则引擎都按主题字符串硬编码，改名等于全系统联动升级。设计时遵循以下规范：

- **层级清晰**：按“场景 / 位置 / 设备 / 属性”分层，例如 `home/livingroom/sensor-01/temperature`。层级不宜过深，三到五层为宜，过深则通配符订阅难以管理。
- **只用确定的分隔与字符**：层级间用 `/` 分隔；避免空格、中文与特殊字符（不同客户端与规则引擎对特殊字符的处理可能不一致）；大小写敏感，`Temperature` 与 `temperature` 是两个主题。
- **方向分开**：上报（设备 → 云端）与下发（云端 → 设备）用不同主题，例如上报用 `.../telemetry`、下发用 `.../command`，避免订阅方误收控制消息，也便于按方向做权限控制。
- **不把敏感信息放进主题**：主题会出现在 Broker 日志、监控与订阅列表里，口令、密钥、个人身份信息不要出现在主题中。
- **预留通配符订阅位**：设计时就想好运维方要怎么批量订阅，例如用 `home/+/sensor-01/temperature` 一次订阅所有房间的同一设备，便于监控与排障。
- **版本化**：消息格式演进时，用主题中的版本段（如 `.../v1/...`）或载荷内的版本字段区分新旧格式，不要静默改变已有主题的载荷含义。

## 6. 设备接入流程

一台设备从上电到正常上报，典型要走以下步骤（概念流程，示例未实测）：

### 6.1 连接与认证

设备以 MQTT 客户端身份向 Broker 发起连接，提供客户端 ID、用户名与口令（或证书）。客户端 ID 在同一 Broker 下必须唯一——两个设备用同一个 ID 连接，后连的会把先连的顶掉，这是排障时要先查的一项。

认证方式常见的有用户名/口令与客户端证书（TLS 双向认证）。口令不要硬编码在固件里明文存放，量产设备的口令分发与轮换是部署设计的一部分。传输层建议启用 TLS，尤其是在公网链路上；内网场景是否启用 TLS，按安全要求决定。

### 6.2 遗嘱（Last Will）

设备在连接时可以向 Broker 登记一条遗嘱消息：指定一个主题与一条消息内容。设备异常断线（非正常断开）时，Broker 代发这条遗嘱，让订阅方知道“它掉了”。正常断开（设备主动发 DISCONNECT）时遗嘱不触发。

遗嘱的典型用法：设备上线时发一条 `online` 状态，遗嘱内容为 `offline`，订阅方据此维护设备在线状态表。遗嘱不是心跳——它只在断线那一刻触发一次，不能替代周期性状态上报。

### 6.3 会话保持

连接时客户端可指定是否建立持久会话（clean session / clean start，MQTT 5.0 中为 clean start 与会话过期时间）。持久会话下，Broker 会记住该客户端的订阅关系，并在客户端离线期间按 QoS 保留待投递消息，待其重连后补发；非持久会话则重连后订阅关系丢失，需重新订阅。

会话保持的取舍：需要“离线期间不丢下行消息”的场景用持久会话，但 Broker 要为每个离线客户端保留状态，规模大了是存储与内存负担；只上报、不接收下行命令的传感器类设备，通常不需要持久会话。

### 6.4 订阅与上报

连接成功后，设备订阅自己需要的下行主题（如控制命令、配置下发），再开始按业务周期上报数据。上报频率、QoS 等级、离线缓存策略（网络断开时数据是丢弃、暂存本地还是等恢复后补发）都要在设备端设计好——网络不可靠是常态，不是异常。

### 6.5 接入排障清单

设备连不上 Broker 时，按这个顺序排查：网络通不通（先 ping Broker 地址或看网关）；端口与 TLS 配置对不对（端口、证书、SNI）；认证信息对不对（用户名、口令、证书有效期）；客户端 ID 是否冲突（被别的设备顶掉）；Broker 侧是否有限流或连接数上限（配额以官方发布为准，待核实）。

## 7. 消息持久化与桥接

### 7.1 消息持久化

Broker 收到消息后默认只做转发，不长期保存。需要保留消息的场景有两种做法：

- **保留消息（Retained）**：发布时标记为保留，Broker 会保存该主题的最后一条消息；新订阅者一订阅就能立即收到这条消息，而不必等下一次发布。典型用法是设备状态主题（如 `.../status`），新上线的监控端立刻知道设备当前状态。保留消息只保留每主题最新一条，不是历史记录。
- **落盘与外部存储**：需要历史数据、审计或离线分析时，Broker 通过规则引擎或桥接把消息写入数据库、消息队列或对象存储（见下一篇数据流转）。持久化策略（存多久、存哪些主题、磁盘满了怎么办）是部署设计的一部分，不是默认配置。

### 7.2 桥接（Bridge）

桥接指两个 Broker 之间建立连接、互相转发消息。典型场景：边缘侧部署一个本地 Broker（内网设备先连它，断网时本地联动不中断），再桥接到云端 Broker 做集中管理与分析；或者两个系统之间只开放部分主题互通，而不合并成一个 Broker。

桥接设计要点：转发哪些主题要显式配置（双向桥接配错了会形成消息环路）；断线重连与消息去重要考虑；桥接链路本身的认证与 TLS 与设备接入同等重要。

## 8. 限制与常见误解

- “Broker 选个最强的就万事大吉”：错。Broker 的高可用、备份、证书、主题权限都是部署工作，选型只是开始；单机 Broker 不做高可用就是单点。
- “QoS 2 就等于消息实时到”：错。QoS 保证送达语义，不保证延迟；实时控制不要走 MQTT。
- “保留消息就是历史数据库”：错。保留消息每主题只存最新一条，要历史记录必须接外部存储。
- “遗嘱能当心跳用”：错。遗嘱只在断线瞬间触发一次，设备在线状态要靠周期性上报与超时判断共同维护。
- “主题随便起，后面再改”：错。主题是全系统的契约，改名等于全系统联动升级，上线前定好命名规范。

## 9. 小结

MQTT Broker 是发布/订阅模型的中转点，负责连接管理、主题路由、QoS 落地与安全边界。选型在开源自建与云端托管之间取舍，核心变量是运维负担、数据位置与成本结构。主题设计、接入流程、持久化与桥接是上线前就要定好的系统设计，不是部署后再补的细节。
