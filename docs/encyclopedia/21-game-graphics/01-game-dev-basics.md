# 游戏开发基础

## 1. 一句话定义

游戏开发是用可交互的实时程序把玩法规则、美术资源与音频组织成一款可玩产品的工程活动。

## 2. 为什么需要它

游戏不是一段播完就结束的视频，也不是一张点一下就出结果的表单。它必须**每秒几十次地读取输入、更新世界状态、画出画面**，并且在玩家做出意外操作时也不崩溃、不穿帮、不丢进度。游戏循环、场景管理与资源管理就是为这个“实时交互”约束而存在的三块基石；没有它们，玩法想法再好也落不了地。

## 3. 核心含义

### 3.1 游戏循环：游戏的心跳

游戏运行时本质上是一个无限循环，伪代码如下（伪代码，示例未实测）：

```
初始化（加载配置、创建窗口、载入首场景）
while 游戏未退出:
    处理输入（键盘、手柄、触屏）
    更新世界（按时间步长推进逻辑：移动、碰撞、AI、计时）
    渲染画面（把当前世界状态画到屏幕）
清理并退出
```

三个要点：

- **帧率是预算，不是分数**。60 帧每秒意味着每圈循环约 16.7 毫秒，30 帧每秒约 33.3 毫秒。输入、更新、渲染三步共享这份预算，任何一步超支都会掉帧。
- **逻辑更新与渲染帧率要解耦**。渲染帧率随硬件波动，但玩法逻辑不能因此时快时慢。常见做法是**固定时间步长**：逻辑每 1/60 秒推进一次，与渲染帧率无关；渲染时按最新逻辑状态插值显示。这样同一操作在 30 帧设备与 144 帧设备上的游戏结果一致，不会出现“高帧率等于跑得更快”的作弊式差异。
- **可核验示例（实测）**：下面这段 Python 程序模拟固定步长累加器——每帧约 5 毫秒工作，逻辑步长固定为 1/60 秒。代理 VM（Ubuntu 24.04，Python 3.12）实际运行结果：

```python
import time
accumulator = 0.0
DT = 1.0 / 60.0
logic_steps = 0
start = time.perf_counter()
frame = 0
while frame < 120:
    frame_start = time.perf_counter()
    time.sleep(0.005)  # 模拟一帧工作约 5ms
    frame_time = time.perf_counter() - frame_start
    accumulator += frame_time
    while accumulator >= DT:
        logic_steps += 1  # 一次固定步长逻辑更新
        accumulator -= DT
    frame += 1
print(f"frames={frame} logic_steps={logic_steps} elapsed={time.perf_counter()-start:.3f}s")
```

```
frames=120 logic_steps=36 elapsed=0.609s
```

解读：120 次渲染帧只对应 36 次逻辑步（0.609 秒 × 60 步/秒 ≈ 36.5），帧数与逻辑步数并不相等——这正是解耦的意义：**帧率管画面流畅度，步长管玩法正确性**，两者各算各的账。注意本示例是循环逻辑的演示，不是真实游戏引擎的运行结果。

### 3.2 场景：世界的基本组织单位

场景（scene）是某一时刻游戏世界的容器：一张地图、一间房间、一个菜单界面都可以是一个场景。场景里装的是**实体**（entity）——玩家角色、敌人、道具、灯光、摄像机——每个实体由若干**组件**（component）拼成：位置组件、渲染组件、碰撞组件、脚本组件等。这种“实体 + 组件”的组织方式（ECS 的雏形思想）让功能可以组合复用：给箱子加一个可推动组件，它就有了物理行为；拿掉渲染组件，它就变成隐形的触发器。

场景管理要解决的实际问题：

- **切换**：从主菜单进关卡、从关卡回结算界面时，旧场景资源何时卸载、新场景何时载入，中间要不要加载画面。切换时卡顿，多半是加载策略问题，不是玩法问题。
- **层级与归属**：实体常按父子层级组织（角色手持武器，武器跟随手部），父物体移动时子物体自动跟随。层级理不清，动画与碰撞会各说各话。
- **状态隔离**：暂停菜单、战斗结算这类“场景之上的状态”，通常用状态机或叠加场景实现，而不是把所有逻辑塞进一个场景。

### 3.3 资源管理：内存与加载的账本

游戏资源包括纹理、模型、音频、动画、配置表与本地化文本。资源管理的核心矛盾是：**资源总量远大于内存**，必须分批进出。

- **加载策略**：首场景只载必需资源，其余按需异步加载；大世界用流式加载（走到哪载到哪），避免一次性载入整个地图导致的长时间黑屏。
- **引用与释放**：资源被谁引用、引用计数何时归零，决定它何时能从内存卸载。切换场景后内存不降，第一怀疑对象就是仍被某处引用的旧资源。
- **打包与热更新**：发布时资源常打成包（asset bundle / pak），上线后可单独更新资源包而不重装整个程序。包划分的粒度影响更新体积：改一张贴图就重下一整个大包，是打包策略失误。
- **显存与内存是两本账**：纹理、网格既占内存又占显存，预算要分开算。移动端尤其如此，显存超了不会优雅降级，只会闪退或严重掉帧。

## 4. 分类

按开发方式，游戏开发大体分三类（不是优劣排序）：

- **引擎开发**：用 Unity、Unreal Engine、Godot 等通用引擎开发（选型见本域第三篇）。绝大多数商业项目在此列。
- **自研引擎开发**：团队自己写渲染器、物理与编辑器。自由度最高，成本也最高，只在有特殊技术需求或长期技术积累的团队出现。
- **框架与脚本开发**：用轻量框架（如 2D 框架、网页游戏框架）或在现有平台（如 Roblox Studio）内开发。适合小品、原型与教学项目。

按玩法载体还有 2D、3D、XR 等分法，那是渲染与交互维度的划分，不改变游戏循环本身的结构。

## 5. 开发流程与分工

一款游戏从想法到上线的常见流程：

1. **概念与原型**：用最糙的美术验证核心玩法是否好玩。原型阶段的唯一标准是“玩法成立吗”，画面可以全是方块。
2. **预生产**：定美术风格、技术路线、工期与预算；做垂直切片（vertical slice）——一小段达到最终品质的完整玩法，证明团队真能做出目标品质。
3. **生产**：按关卡、系统分工并行开发；美术、程序、策划、音频同步推进，定期合成为可玩版本。
4. **测试与打磨**：功能测试、性能测试、兼容性测试、本地化；修掉帧、穿模、存档丢失这类破坏体验的问题。
5. **上线与运营**：发布、热更新、活动与版本迭代。上线不是结束，留存与口碑在上线后才见分晓。

分工上，策划定规则与数值，程序实现系统与工具，美术生产视觉资源，音频负责音乐与音效，测试负责破坏与验证，制作人负责排期与取舍。跨工种最常见的摩擦点是“资源交付格式”——模型面数、贴图尺寸、音频采样率这些约束要先行约定，而不是美术交完才发现程序用不了。

## 6. 与服务端部署的衔接

单机游戏做到第 5 步就可以交付；联网游戏还要多一块：**服务端部署**。服务器选型、端口开放、性能调优与内网穿透属于运维侧工作，本篇不复制、不抄写这些步骤，统一指向本站已有内容：

- [游戏服务器部署与端口映射](../../10-game-servers/index.md)（含端口开放、服务端实战、性能调优与守护、内网穿透与公网映射）

开发侧与运维侧的分界线是：开发保证“客户端与服务端按协议说话”，运维保证“服务端在公网可达且稳定运行”。联调时先分清问题在哪一侧，再动手。

## 7. 限制与常见误解

- **“游戏开发就是写代码”**：错。代码只是其中一环；玩法设计、美术生产、音频、测试与运营同样决定成败，纯程序视角会低估一半工作量。
- **“帧率高就是优化好了”**：错。帧率高但逻辑帧不稳定、加载卡顿、发热严重，都不算优化到位；要看帧时间分布、内存曲线与发热，不只看平均帧率。
- **“先做画面再补玩法”**：顺序反了。玩法不成立时，画面越精美，返工成本越高；原型阶段就该验证玩法。
- **“资源越大越好”**：错。资源规格要按目标设备的内存、显存与带宽定；超规格资源只会拖垮加载与帧率。

## 8. 小结

游戏开发 = 游戏循环（每帧输入—更新—渲染）+ 场景（世界的组织单位）+ 资源管理（内存与加载的账本），再按概念、原型、生产、测试、上线的流程由策划、程序、美术、音频、测试分工完成。联网部分另有服务端部署，本篇只做衔接，不展开。
