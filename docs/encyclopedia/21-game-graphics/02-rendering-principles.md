# 图形渲染原理入门

## 1. 本章目标

读完本篇能理解：一张游戏画面从三维场景数据变成屏幕像素要经过哪些步骤、光栅化与着色分别解决什么问题，以及实时渲染为什么要在画质与帧率之间做取舍。

## 2. 背景与问题

游戏世界存在于数据里：顶点坐标、三角形网格、材质参数、光源位置、摄像机姿态。屏幕却只认像素：一块每秒刷新几十次的二维点阵。渲染（rendering）就是把前者变成后者的全部工作。

实时渲染多了一个硬约束：**每一帧的预算有限**。60 帧每秒意味着每帧只有约 16.7 毫秒，30 帧每秒约 33.3 毫秒。超出预算，画面就卡顿；预算花错地方，画面看起来也不好。理解渲染管线，就是理解这 16.7 毫秒花在了哪里。

## 3. 总体架构：渲染管线

现代实时渲染通常画成这样一条管线（不同引擎与 API 的叫法略有差异，阶段划分大同小异）：

```
场景数据（网格、材质、光源、摄像机）
  → 应用阶段（CPU：剔除、排序、提交绘制命令）
  → 几何阶段（GPU：顶点处理、曲面细分、几何处理）
  → 光栅化（GPU：三角形 → 像素覆盖）
  → 片元/像素阶段（GPU：着色、纹理、光照）
  → 输出合并（GPU：深度测试、混合、写入帧缓冲）
  → 屏幕
```

两个要点：

- **CPU 与 GPU 分工**：CPU 决定“画什么、按什么顺序画”，发绘制命令；GPU 执行这些命令，做真正逐像素的繁重计算。CPU 提交跟不上，GPU 再强也空转；反之亦然。性能分析时先分清瓶颈在哪一侧，再谈优化。
- **管线是流水线，不是单线程串行**：上一帧的像素着色与下一帧的 CPU 提交可以重叠。帧率看的是整条流水线的吞吐，而不是某一阶段的单次耗时。

## 4. 工作机制

### 4.1 应用阶段：CPU 先做减法

GPU 每秒能画的三角形有限，所以第一步是少画：

- **视锥剔除**：摄像机看不到的物体不提交。看不见的山、背后的房间，画了也是浪费。
- **遮挡剔除**：被别的物体完全挡住的物体不提交。室内场景里隔壁房间的家具就是典型例子。
- **排序**：不透明物体通常按从前到后画，让深度测试尽早拒绝被遮挡的像素；透明物体按从后到前画，因为透明混合的结果依赖顺序，画反了会出错。

### 4.2 几何阶段：从顶点到屏幕坐标

顶点着色器对每个顶点做变换：模型空间 → 世界空间 → 摄像机空间 → 裁剪空间，最后做透视除法得到屏幕上的二维位置。这一阶段还处理骨骼动画的顶点蒙皮、以及按需的曲面细分（把粗糙网格临时细化）。

这里有一个贯穿全文的概念：**变换是坐标系之间的换算，不是“移动物体”本身**。同一个顶点，在世界里位置不变，换个摄像机位置，它在屏幕上的位置就变了。调试渲染问题时，先问“哪个空间的坐标错了”，比盯着最终画面猜要快得多。

### 4.3 光栅化：三角形如何变成像素

光栅化回答一个看似简单的问题：这个三角形覆盖了屏幕上的哪些像素？对每个像素，管线还要插值出该点的各种属性：纹理坐标、法线、颜色、深度。插值必须是透视正确的——直接在屏幕空间线性插值，纹理会在倾斜表面上变形，这是新手渲染器最常见的视觉错误之一。

光栅化之后，每个候选像素叫一个**片元（fragment）**。片元还不是最终像素：它要经过深度测试（是不是被更近的物体挡住了）、模板测试、混合，才能写入帧缓冲。

### 4.4 着色：像素最终是什么颜色

片元着色器（像素着色器）决定每个片元的颜色，输入包括插值属性、纹理、材质参数和光照信息。现代游戏常用的光照模型是**基于物理的渲染（PBR）**：材质用几个物理含义明确的参数描述——金属度、粗糙度、基础反射率——光照计算遵循能量守恒（反射出去的能量不超过入射能量）。PBR 的好处不是“更真实”这个口号，而是**同一套材质在不同光照下表现一致**，美术不用为每个场景单独调一套参数。

纹理在这里的角色要说清：纹理不是“贴图”这个动作，而是**存在显存里的、按坐标采样的数据表**。颜色纹理给表面上色，法线纹理伪造表面细节，粗糙度纹理控制反光锐利程度。纹理分辨率与显存、带宽直接挂钩，4K 纹理贴在远处只占几个像素的物体上，纯属浪费。

### 4.5 输出合并：深度、混合与帧缓冲

最后一步把通过测试的片元写进帧缓冲：

- **深度测试**：只保留离摄像机最近的片元，挡住的丢弃。这是“近处物体遮住远处物体”最廉价的实现。
- **混合**：透明物体不直接覆盖，而是按透明度与已有颜色混合。这就是透明物体必须排序的原因。
- **帧缓冲**：画面先画到离屏缓冲，做完后期处理再送上屏幕。抗锯齿、泛光、色调映射、暗角这些“后期”效果都在这里发生。

## 5. 关键设计取舍

- **前向渲染与延迟渲染**：前向渲染每个物体画一次、光照一次，简单直接，透明物体好处理，但光源一多，每个像素的光照计算量直线上升。延迟渲染先把几何信息（位置、法线、材质）写进一组缓冲（G-buffer），再按像素统一算光照，光源数量不再与物体数量相乘，但显存占用大、透明物体要另走一路、多重采样抗锯齿难做。没有 universally 更好的一方，选哪个看场景的光源密度与透明物体占比。
- **烘焙与实时**：静态光照可以提前算好存成光照贴图（烘焙），运行时几乎零成本，但光源一动就失效；动态光照每帧重算，灵活但吃预算。常见做法是混合：静态环境烘焙，动态角色与关键光源实时算。
- **分辨率与帧率**：渲染分辨率是最直接的性能杠杆。内部渲染分辨率降一档，像素着色工作量按面积比例下降；配合后文的超分辨率技术，可以在观感损失有限的前提下换回帧率。
- **阴影质量与数量**：阴影贴图的分辨率、级联层数、每帧更新哪些光源的阴影，都是可调的预算项。阴影糊一点玩家往往注意不到，阴影闪烁或缺失却一眼可见——取舍要按“玩家会不会注意到”排优先级。

## 6. 图形 API 一览

渲染管线要通过图形 API 交给 GPU 执行。主流 API 的定位（2026-11-04 核查）：

| API | 归属与平台 | 抽象层次与特点 |
|---|---|---|
| Vulkan | Khronos Group 的开放标准；Windows、Linux、Android 为主 | 显式低层 API：队列、命令缓冲、同步都由应用显式管理，控制力强、代码量大；macOS / iOS 需经 MoltenVK 一类转译层，非原生支持 |
| DirectX 12（Direct3D 12） | 微软；Windows 与 Xbox | 与 Vulkan 同为显式低层路线，命令列表、队列、资源屏障显式管理；平台限定在微软生态内 |
| Metal | 苹果；macOS、iOS、iPadOS | 苹果平台的原生低层 API，命令缓冲与编码器模型，能力以 GPU 家族与系统版本为准 |
| OpenGL / OpenGL ES | Khronos Group 的开放标准；跨平台，移动端为 OpenGL ES | 驱动管理状态较多的高层模型，上手相对容易；新项目的主流地位已被显式 API 取代，存量项目与教学仍大量使用 |
| WebGPU | W3C 标准方向；浏览器与原生实现（如 dawn、wgpu） | 中等抽象，面向网页与可移植场景，着色语言为 WGSL；光线追踪等能力仍在演进中 |

要点：API 不决定画质上限，决定的是**控制粒度与平台覆盖**。用引擎开发时，引擎已经替你选了后端 API；只有自研渲染器才需要直接选型。

## 7. 实时渲染关键技术

### 7.1 光线追踪：从“近似”到“模拟”

传统光栅化用各种近似模拟光的行为；光线追踪反过来，从摄像机（或光源）发射光线，与场景求交，算出真实的反射、折射与阴影。效果上限高，但每像素多条光线的代价极大，所以实时游戏里通常是**混合渲染**：光栅化画主体， ray tracing 只补反射、阴影、全局光照里最难近似的那一部分，且常配合降噪与低分辨率追踪。

是否上光线追踪，先看两点：目标硬件有没有光线追踪加速单元，以及这项效果在你的场景里是不是玩家看得见的差异。看不见的真实感不值得帧率。

### 7.2 全局光照：光不只照一次

直接光照是光源直射到表面的部分；全局光照还包括光在表面间反弹的间接光。没有间接光，阴影里会死黑一片。实时方案按成本从低到高大致是：烘焙光照贴图 → 光照探针（空间中采样点存间接光，动态物体插值取用）→ 屏幕空间近似 → 全动态全局光照系统（如 Unreal 的 Lumen，见下文）。成本越高，对动态场景的适应性越好。

### 7.3 超分辨率与帧生成：用时间换像素

DLSS（NVIDIA）、FSR（AMD）、XeSS（Intel）一类技术的共同思路是：**以较低分辨率渲染，再用算法重建到目标分辨率**。时间型超分辨率还会用前几帧的信息与运动矢量补细节，重建质量明显高于单帧放大。帧生成则更进一步，在两帧之间插值出一帧，显示帧率翻倍，但输入延迟不降反升——竞技类游戏要慎用。

取舍口诀：超分辨率省的是像素着色成本，换回帧率；它不修复几何错误、阴影错误或 CPU 瓶颈。瓶颈在 CPU 提交时，开超分辨率没用。

### 7.4 Nanite 与 Lumen：两个常被误读的例子

Unreal Engine 5 的两项代表技术，适合用来检验上面所有概念是否理解：

- **Nanite（虚拟化几何）**：把超高面数模型切成小簇，按屏幕占比动态选细节，省去手工做多级 LOD 的工作。本质仍是“只画看得见的细节”这个老原则，只是自动化程度到了新高度；它不改变光栅化本身。
- **Lumen（动态全局光照与反射）**：每帧计算间接光与反射，光源或几何一动，光照即时跟上，不用烘焙光照贴图。软件光线追踪版本对场景做距离场近似，硬件光线追踪版本直接对三角形求交、精度更高。代价是持续的每帧预算，低端硬件上有专门的轻量模式（如 UE 5.8 的 Lumen Lite，Beta）。

## 8. 常见误解

- **“光线追踪开了画质就一定更好”**：错。追踪分辨率、采样数、降噪质量都会影响结果；低采样无降噪的光追可能比精心调过的光栅化近似更难看，还更慢。
- **“显卡越强帧率一定越高”**：错。瓶颈可能在 CPU 提交、内存带宽、显存容量或某一阶段的着色器上。先定位瓶颈，再谈硬件。
- **“纹理分辨率越高越好”**：错。纹理只在它占的屏幕像素足够多时才显出细节；远处物体用 4K 纹理只浪费显存与带宽。
- **“实时渲染就是光栅化”**：不全对。现代实时渲染是光栅化为主、光线追踪为辅、超分辨率收尾的混合体；只盯一种技术会误判成本。

## 9. 小结

渲染是把三维场景数据变成屏幕像素的流水线：CPU 做剔除与排序、GPU 做几何变换与光栅化、片元着色器定颜色、输出合并定遮挡与透明。实时渲染的全部艺术，是在每帧 16.7 毫秒里决定哪些近似值得花、哪些可以省。
