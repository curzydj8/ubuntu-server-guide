# 组策略排错与 Resultant Set of Policy

## 1. 本章目标

读完本篇，能用 gpresult 与 Resultant Set of Policy（RSoP）说清“一台设备、一位用户最终实际生效的策略是哪几条、来自哪个 GPO、哪几条被拒绝了以及为什么”，并能按固定流程定位策略不生效的原因。

## 2. 背景与问题

组策略的生效链条很长：管理员在域控制器上配好 GPO、链接到容器，客户端定期刷新、按顺序处理、把设置写到注册表或系统配置里。链条上任何一环出问题，结果都一样——“策略没生效”。但“没生效”本身不是原因，它只是症状；真正的原因可能在链接位置、继承、安全筛选、复制、客户端处理等十几个环节中的任何一个。

新手排障最常见的两个错误是：**一是上来就反复 `gpupdate /force`**，以为多刷几遍策略就会下来；**二是凭印象改注册表**，把“策略没下来”误诊成“值不对”。正确的做法恰恰相反：先看结果（到底生效了什么、拒绝了什么），再顺着结果找原因。本篇讲的就是这套“先看结果、再找原因”的排错方法。

基础概念（GPO、LSDOU 处理顺序、强制与阻止继承、环回处理、刷新周期）见[注册表与组策略](02-registry-group-policy.md)第 3–4 节，本篇不再重复讲原理，只讲“结果怎么看、原因怎么找、流程怎么走”。

> **实测说明**：本文作者在 Linux 虚拟机上工作，Windows 专属命令与操作无法在当前环境实测。文中所有 Windows 命令与操作示例一律标“示例未实测”，请在实际 Windows 设备上按官方文档核对后再执行。

## 3. 先看结果：gpresult 与 Resultant Set of Policy

“结果集”（Resultant Set of Policy，RSoP）就是“把所有适用的 GPO 按 LSDOU 顺序处理完之后，最终实际生效的那套策略”。排障的第一步永远是先拿到结果集，再谈原因。

### 3.1 gpresult：命令行看结果集

`gpresult` 是排障时最常用的工具，输出分摘要与完整报告两种（示例未实测）：

```cmd
gpresult /r
gpresult /h %Temp%\GPResult.html
gpresult /r /scope:user
gpresult /r /scope:computer
```

- `gpresult /r`：输出摘要，包括计算机配置与用户配置各自“已应用的 GPO”与“被拒绝的 GPO”。
- `gpresult /h <路径>`：生成完整的 HTML 报告，可在浏览器里展开查看每条设置的来源 GPO 与最终值；需要把报告发给别人协查时，用这个。
- `/scope:user` 与 `/scope:computer`：只看用户配置或只看计算机配置的结果，分不清问题在哪一类时先分开看。

读摘要时**先看“被拒绝的 GPO”一栏**：gpresult 通常会直接写明拒绝原因，例如“安全筛选”“空 GPO”“GPO 被禁用”“WMI 筛选不匹配”。拒绝原因是最直接的线索，比从头猜原因快得多。再看“已应用的 GPO”一栏：目标 GPO 在不在里面？如果目标 GPO 根本不在“已应用”里，也不在“被拒绝”里，说明它连“被评估”这一步都没走到——问题在链接、OU 位置或复制环节（见第 4 节）。

注意权限：查看计算机配置的完整结果通常需要管理员权限；普通用户运行 `gpresult /r` 可能只能看到自己的用户配置部分。排障时以管理员身份运行命令提示符再查，避免“查不到”被误判成“没生效”。

### 3.2 rsop.msc：图形界面看结果集

Resultant Set of Policy 管理单元（`rsop.msc`）以组策略编辑器相似的树形界面展示最终生效的策略：

- 打开方式：运行 `rsop.msc`（示例未实测），按向导选择要查询的计算机与用户，生成结果集后按“计算机配置 / 用户配置”树形浏览。
- 适用场景：想逐条浏览“某条设置最终值是什么、来自哪个 GPO”，或向不熟悉命令行的同事展示结果时。
- 与 gpresult 的分工：gpresult 适合快速看“哪些 GPO 应用了、哪些被拒绝了”；rsop.msc 适合逐条看“某条设置的值与来源”。两者看的是同一份结果集，选顺手的用。
- 局限：rsop.msc 展示的是策略处理结果的快照，某些类型的设置（例如首选项的部分类型、较新的策略扩展）可能不在其展示范围内；拿不准时以 `gpresult /h` 的完整报告为准（具体覆盖范围以官方发布为准（待核实））。

### 3.3 核对注册表最终值：区分“策略没下来”与“应用没读它”

策略引擎落盘后，基于注册表的设置会写到注册表对应位置。排障的最后一步核对是：到注册表对应分支看最终值（方法见[注册表备份恢复与常见键值](06-registry-backup-recovery.md)），区分两种问题：

- **策略没下来**：注册表里没有策略应有的值 → 问题在组策略链条上，继续按第 4 节排查。
- **策略下来了但没起作用**：注册表值是对的，但应用或功能行为没变 → 问题不在组策略，在应用本身（应用没读该值、应用版本不支持该设置、需要重启应用或系统）。

这一步能避免大量无用功：很多人卡在“策略没生效”上反复刷 gpupdate，其实策略早已下来，是应用侧的问题。

## 4. 策略不生效的常见原因

按排查时“从常见到少见、从上层到下层”的顺序排列。

### 4.1 对象不在正确的 OU 里

计算机或用户根本不在 GPO 链接的那个 OU 里，是最常见的低级原因。域里移动过设备、重命名过 OU、按部门调整过组织结构后，最容易出现这种情况。核查方法：在 Active Directory 用户和计算机里确认对象的实际 OU，再对照 GPO 的链接位置。注意：**对象在子 OU 里时，父 OU 上链接的 GPO 会按继承应用**，但反过来不行——把 GPO 链接到子 OU，不会影响父 OU 里的对象。

### 4.2 继承被阻止，或被强制的 GPO 覆盖

OU 上启用了**阻止继承（Block Inheritance）**后，上级容器（站点、域、父 OU）链接的 GPO 不再应用到该 OU，除非那些 GPO 被设为**强制（Enforced）**。与之对应的另一面是：目标 GPO 明明应用了，但最终值却是另一个 GPO 的——因为后应用的 GPO（LSDOU 顺序中更靠后的，或被强制的）覆盖了它。

核查方法：看 `gpresult /h` 报告里该设置的“来源 GPO”到底是哪个，再对照组策略管理控制台里的链接顺序与强制标记。启用阻止继承或强制前，应在文档里写清原因；排障时先查这两处，能解释一大半“明明配了却不是这个值”的问题。

### 4.3 安全筛选与 WMI 筛选把对象排除在外

- **安全筛选**：GPO 默认只对有“读取 + 应用组策略”权限的安全主体生效。如果筛选改成了只对某个组生效，而目标计算机或用户不在该组里，策略会静默地不应用；更隐蔽的是**计算机账户没有读取权限**——域环境里“策略死活不下来”的经典原因，gpresult 的拒绝原因栏通常会写明。
- **WMI 筛选**：按 WMI 查询结果决定 GPO 是否适用（例如只对某版本系统生效）。筛选条件写错，策略会对所有设备静默失效，且 gpresult 里只会看到“被拒绝：WMI 筛选”，不会告诉你查询语句哪里写错了——需要回组策略管理控制台逐字核对筛选语句。

### 4.4 环回处理改变了用户配置的来源

正常情况下用户配置按“用户所在 OU”决定；启用**环回处理（Loopback Processing）**后，用户配置改按“计算机所在 OU”决定（替换模式只用计算机 OU 的用户配置，合并模式先应用用户 OU 的再用计算机 OU 的覆盖）。环回只应在展台机、教室机、终端服务器这类“谁登录都该用同一套用户环境”的设备上启用。

排障要点：某台设备上用户配置“总是不对”，而同一用户在别的设备上正常，先查这台计算机 OU 有没有启用环回的 GPO；环回的两种模式细节见[注册表与组策略](02-registry-group-policy.md)第 4.2 节。

### 4.5 复制延迟：GPO 还没到客户端用的域控制器

多域控制器、多站点的环境里，GPO 改动要先复制到各域控制器，客户端登录或刷新时连接的域控制器不一定已有最新版本。刚改完 GPO 立刻去客户端验证，看到的可能是旧版本——这不是故障，是复制还没完成。

核查方法：确认 GPO 的版本号在各域控制器上是否一致（组策略管理控制台可查看状态），或等待一个复制周期后复查。跨站点复制的延迟以域的站点拓扑与复制计划为准（具体时间以官方发布为准（待核实））；排障时先确认“改动是不是真的已经复制到了客户端连接的那台域控制器”，再怀疑别的环节。

### 4.6 客户端处理失败：连通、权限与客户端扩展

客户端侧的常见故障点：

- **无法访问 SYSVOL**：客户端要从域控制器的 SYSVOL 共享拉取策略文件；DNS 解析失败、网络不通、SYSVOL 共享不可达都会导致处理失败。先确认客户端能解析域名、能访问域控制器。
- **计算机账户密码或信任关系问题**：计算机与域的信任关系损坏时，策略处理会失败，常伴随登录异常；此类问题需按域信任修复流程处理（具体步骤以官方文档为准（待核实））。
- **客户端扩展（CSE）失败**：每类设置由对应的客户端扩展处理（如注册表类、安全类、脚本类），某个扩展出错只会影响该类设置，其他类可能正常。`gpresult /h` 报告与组策略 operational 日志会记录各扩展的处理结果，按扩展逐个排查。
- **需要注销或重启的设置**：软件安装、文件夹重定向、部分安全策略等需要注销或重启才生效；`gpupdate` 刷新完不代表它们已经落地。排障前先确认该设置是否属于“需注销/重启”类型。

### 4.7 gpupdate /force 不是万能药

`gpupdate /force`（示例未实测）只会重新处理“适用”的策略：

```cmd
gpupdate /force
gpupdate /target:computer /force
gpupdate /target:user /force
```

它**绕不过**安全筛选、WMI 筛选、链接位置错误、OU 位置错误、复制未完成这些根本原因。反复执行 `gpupdate /force` 却不见效，恰恰说明问题不在“刷新没触发”，而在上面 4.1–4.6 节的某一环。此时应停下来看 gpresult，而不是继续刷。

## 5. 排错流程：按这个顺序走

把第 3–4 节串成一个固定流程，每一步都在排除一类原因，走到哪一步卡住，问题就在哪一类：

1. **确认设置本身存在**：在组策略管理控制台里确认该设置确实配在了某个 GPO 里，且该 GPO 已链接到正确的容器；确认 GPO 本身没有被禁用（GPO 可整体禁用，也可只禁用计算机配置或只禁用用户配置）。
2. **确认对象位置**：计算机或用户是不是真的在那个 OU 里（见 4.1 节）。
3. **看 gpresult**：先 `gpresult /r` 看摘要，目标 GPO 在“已应用”还是“被拒绝”？被拒绝的原因是什么？必要时生成 `gpresult /h` 完整报告。
4. **查继承与覆盖**：该 OU 是否阻止了继承？上级有没有强制的 GPO？最终值的来源 GPO 是不是你以为的那个（见 4.2 节）？
5. **查筛选**：安全筛选是否把对象排除在外？WMI 筛选语句是否写错（见 4.3 节）？
6. **查环回**：计算机 OU 是否启用了环回处理（见 4.4 节）？
7. **查复制与连通**：GPO 改动是否已复制到客户端连接的域控制器？客户端能否访问 SYSVOL、能否解析域名（见 4.5、4.6 节）？
8. **手动刷新一次并复查**：执行 `gpupdate /force`（示例未实测），再跑 `gpresult /r` 对照；需要注销或重启的设置，刷新后按要求注销或重启再验证。
9. **核对注册表最终值**：区分“策略没下来”与“策略下来了但应用没读它”（见 3.3 节）。
10. **查事件日志**：组策略 operational 日志（事件查看器 → 应用程序和服务日志 → Microsoft → Windows → GroupPolicy → Operational）会记录每次处理的警告与错误，是最后的证据链；把日志里的时间点、事件 ID 与前面的步骤对照，定位到具体环节。

流程的意义在于顺序：跳过前面的步骤直接改注册表或反复刷 gpupdate，往往是把“策略没下来”误诊成“值不对”，改完下次刷新又被刷回，白忙一场。

## 6. 组策略排错的事件日志与证据

排障要留证据，而不是凭口头说“配过了”：

- **gpresult HTML 报告**：`gpresult /h` 生成的报告是“当时到底生效了什么”的快照，协查与审计时直接发报告，不转述。
- **组策略 operational 日志**：记录每次策略处理的过程、警告与错误；出现处理失败时，先按时间点找到对应事件，再读事件详情里的错误代码与描述。
- **GPO 备份**：改动 GPO 之前先在组策略管理控制台里备份 GPO，并记录改了什么、为什么改；排障时能对照“改动前后的 GPO 是不是同一个版本”。
- **变更记录**：谁、在什么时间、改了哪个 GPO 的哪条设置、链接到了哪个 OU，四项缺一不可；没有记录的改动，排障时等于没改过。

## 7. 常见误解

- **“gpupdate /force 能解决一切”**：错。它只重新处理适用的策略，绕不过筛选、链接、复制这些根本原因；先 gpresult，再 gpupdate。
- **“策略配完就该立即生效”**：错。客户端是后台定期刷新（域环境默认约 90 分钟一轮，另有随机偏移；开机与登录时处理一次），且部分设置需注销或重启；刚配完就去验证，看到旧结果是正常的。
- **“rsop.msc 里没看到就是没配”**：不一定。rsop.msc 展示的是结果集快照，某些设置类型可能不在其展示范围内；以 `gpresult /h` 完整报告为准。
- **“删掉 GPO，设置就全没了”**：不完全对。管理模板策略值会恢复，但首选项的值会残留（俗称“纹身”）；删 GPO 前要分清两类（详见[注册表与组策略](02-registry-group-policy.md)第 5 节）。
- **“本地改注册表能顶替组策略”**：不能。域环境下手工改的值下次刷新即被策略值覆盖；要改就去改 GPO，不要在客户端硬扛。
