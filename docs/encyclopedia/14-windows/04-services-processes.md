# 服务与进程管理实务

> 实测说明：本文作者环境为 Linux 虚拟机，Windows 专属命令与图形操作无法在当前环境实测。文中所有 Windows 命令与操作示例一律标注“示例未实测”，请以实际系统行为与微软官方文档为准。

## 1. 本章目标

读完本篇，能说清服务与进程、线程分别是什么、启动类型与依赖关系如何决定一台机器“开机后谁先跑、谁跟着谁跑”，能用任务管理器与资源监视器定位“卡、慢、占满”的进程，并按固定顺序处理“服务起不来”的常见故障。

本文是[Windows 系统管理](01-system-management.md)中服务一节的展开：那篇讲了“服务是什么、启动类型分哪几种、不要乱禁服务”的结论，本篇讲“怎么看、怎么改、坏了怎么查”。服务账户的基础概念与 UAC 提权机制见 01 篇，不再重复。

## 2. 为什么需要它

一台 Windows 机器开机后，桌面出现之前已有几十个服务在后台跑：网络、打印、更新、杀毒、数据库、业务软件。用户感知到的“能上网”“能打印”“业务系统能打开”，背后都是某个服务在正常运行。服务一出问题，表现往往不是明确的报错，而是“功能突然没了”——打印队列卡住、共享文件夹打不开、业务程序连不上本机数据库。

进程则是另一面：服务最终要落实为一个或多个进程在跑，进程里再分线程干活。机器“卡”的时候，问题可能在服务层（某个服务死锁），也可能在进程层（某个进程把 CPU 或内存占满）。只会看服务、不会看进程，或者反过来，排障都会只看到一半。

## 3. 核心含义

### 3.1 服务：由服务控制管理器统一管理的后台程序

Windows 服务是由**服务控制管理器（Service Control Manager，SCM）**统一管理的后台进程：没有界面，随系统启动或按需运行。SCM 负责服务的启动、停止、暂停、恢复，以及按依赖顺序拉起服务。一个服务对应注册表 `HKLM\System\CurrentControlSet\Services` 下的一个子项（配置细节见[注册表与组策略](02-registry-group-policy.md)），服务控制台与命令行工具读写的就是这些配置。

管理服务有三个常用入口，分工不同：

| 入口 | 适合场景 |
|---|---|
| `services.msc`（服务控制台） | 图形界面：查看状态、改启动类型、看依赖关系、改登录身份与恢复策略；适合单机逐项操作 |
| `sc.exe`（Service Control 命令行） | 查询、创建、删除、配置服务；适合脚本与远程批量操作 |
| PowerShell 的 `Get-Service` / `Set-Service` / `Start-Service` / `Stop-Service` | 对象化输出，可过滤、可导出；详见[PowerShell 自动化](03-powershell-automation.md) |

三者改的是同一份服务配置，选哪个只看场景：单机点几下用控制台，批量巡检与基线核对用命令行或 PowerShell。

### 3.2 进程与线程：程序运行时的两层结构

**进程（Process）**是操作系统分配资源的基本单位：一个正在运行的程序就是一个进程，每个进程有自己独立的内存空间、句柄表与安全上下文。两个同名进程（例如两个 `notepad.exe`）互不干扰，因为它们是两个独立的进程。

**线程（Thread）**是进程内部的执行单位：一个进程可以包含多个线程，线程共享进程的内存空间，各自执行不同的任务。浏览器一个标签页卡住不等于整个浏览器卡死、杀毒软件能一边扫描一边响应界面，背后都是多线程在工作。

两者的排障意义不同：

- **进程级问题**：某个进程 CPU 或内存占用异常、进程崩溃退出、进程数异常增多——看任务管理器与资源监视器。
- **线程级问题**：某个进程 CPU 占满但界面还能点、某个服务“卡住不动但进程还在”——往往是内部某个线程死锁或死循环。线程级定位一般需要借助性能分析工具，已超出日常系统管理的范围，本文只讲到“如何判断问题在进程内、需要升级处理”这一步。

进程之间是父子关系：服务宿主进程 `svchost.exe` 一个进程里可能承载多个服务（服务分组共享宿主进程以节省资源），所以“结束 svchost.exe”从来不是正确的操作——它会连带杀掉一组服务。结束进程前先确认它是谁的进程、承载了什么服务（见 6.3 节）。

### 3.3 任务管理器与资源监视器：两个工具，分工不同

**任务管理器（Task Manager，Ctrl + Shift + Esc）**是日常第一入口：

- **进程选项卡**：看各进程的 CPU、内存、磁盘、网络占用，按列排序即可找到“谁在吃资源”；右键可结束任务、查看详细信息。
- **性能选项卡**：看 CPU、内存、磁盘、网络、GPU 的整体使用率与趋势，判断瓶颈在哪个资源上。
- **启动选项卡**：看开机自启程序的影响程度，禁用不必要的自启项（只影响登录后的自启程序，不影响服务）。
- **服务选项卡**：快速查看服务状态、启动与停止服务，是服务控制台的简化版。
- **用户选项卡**：看各登录用户的进程占用，多用户机器上定位“谁占的资源”。

**资源监视器（Resource Monitor，`resmon.exe`）**是任务管理器的深入版，适合“任务管理器只看到占用高、但看不出是谁在读写什么”的情况：

- **CPU**：按服务分组显示进程与线程的 CPU 占用，可看到某个 `svchost.exe` 内部是哪个服务在耗 CPU。
- **内存**：看提交、硬错误/秒、工作集，区分“内存真的不够”与“某个进程泄漏式增长”。
- **磁盘**：按进程列出读写速率与正在访问的文件，定位“磁盘 100% 是谁在写”。
- **网络**：按进程列出连接与收发速率，定位“带宽被谁占了”。

使用顺序建议：先任务管理器看“哪个资源满、哪个进程占得多”，需要深入再开资源监视器看“它在对哪个文件、哪个连接动手”。直接上手资源监视器容易被细节淹没。

## 4. 服务启动类型与依赖关系

### 4.1 启动类型：四种，含义要分清

| 启动类型 | 含义 |
|---|---|
| 自动（Automatic） | 系统启动时由 SCM 自动启动 |
| 自动（延迟启动，Automatic Delayed Start） | 系统启动后延后一段时间再启动，用于缓解开机时大量服务同时争抢资源 |
| 手动（Manual） | 不随系统启动；需要时由系统（其他服务或应用触发）、用户或触发器启动 |
| 禁用（Disabled） | 不能启动；SCM 会拒绝启动请求 |

两个容易混淆的点：

1. **“手动”不等于“不会启动”**。很多服务平时是手动，但被依赖它的服务或应用触发时会自动拉起。看到一个手动服务在运行，不代表有人手工启动了它。
2. **“自动（延迟启动）”不是“慢一拍的自动”**。延迟启动的服务在开机关键路径之外加载，适合“需要随开机跑、但不急于第一秒就绪”的服务（例如更新、索引类服务）。把关键业务服务设成延迟启动，可能导致开机后一段时间内业务不可用。

启动类型的改动用服务控制台的服务属性页，或用 `sc.exe`（示例未实测）：

```cmd
sc.exe config Spooler start= delayed-auto
```

上面命令把打印后台处理程序（Spooler）改成自动延迟启动。注意 `start=` 后面必须有一个空格，这是 `sc.exe` 的固定语法要求。

### 4.2 依赖关系：服务不是孤立启动的

服务之间有**依赖关系**：A 服务依赖 B 服务时，SCM 启动 A 之前必须先启动 B；停止 B 时，依赖 B 的服务也会被一并停止。服务控制台的服务属性页有“依存关系”选项卡，分两栏显示：

- **此服务依赖以下服务**：它启动前必须先起来的服务。
- **以下服务依赖此服务**：它停掉时会连带停掉的服务。

依赖关系有两层含义：

1. **启动顺序**：开机时 SCM 按依赖拓扑排序拉起服务，依赖链越深，启动越晚；依赖链上任何一环起不来，下游服务都会跟着起不来。
2. **排障线索**：“X 服务无法启动”时，先查它的依赖服务是否在运行——很多时候问题不在 X 本身，而在它依赖的某个底层服务上（例如网络相关服务依赖的底层网络服务未启动）。

用 `sc.exe` 查看依赖（示例未实测）：

```cmd
sc.exe qc Spooler
```

输出中的 `DEPENDENCIES` 一栏列出该服务的依赖服务名。PowerShell 的等价做法见[PowerShell 自动化](03-powershell-automation.md)。

### 4.3 恢复策略：服务崩溃后怎么办

服务属性页的“恢复”选项卡定义服务异常退出后的动作：第一次失败、第二次失败、后续失败分别执行什么操作——不执行操作、重新启动服务、运行程序、重新启动计算机，并可设置失败后等待多少分钟再执行、失败计数在多少天后重置。

实用建议：

- **关键业务服务**：第一次与第二次失败设为“重新启动服务”，后续失败设为“运行程序”（例如发告警脚本），而不是无限重启——无限重启的服务会在日志里刷屏，还可能掩盖真正的故障原因。
- **不要把恢复策略当成故障修复**：服务反复崩溃重启，说明有未解决的根本原因（配置错、依赖缺失、文件损坏等），恢复策略只是争取时间的缓冲，根因仍需按第 5 节定位。

## 5. 常见服务故障处理思路

按以下顺序查，每一步排除一类原因，不要跳步：

### 5.1 第一步：确认现象与范围

- 是单个服务起不来，还是一批服务都起不来？一批都起不来，优先怀疑依赖链上游或系统级原因（例如启动类型被批量改动、系统文件损坏）。
- 是开机后就没起来，还是运行中途停掉的？前者看启动类型与依赖，后者看崩溃与恢复策略。
- 该服务对应的功能是否真的受影响？有些服务停了也不影响当前使用，优先级可以放后。

### 5.2 第二步：看状态、启动类型与依赖

在服务控制台里核对三项：

1. **状态**：服务当前是“正在运行”“已停止”还是“正在启动”（卡在启动中本身就是一种故障形态）。
2. **启动类型**：是不是被改成了“禁用”或“手动”？被改的原因要先找到（组策略下发、人为误改、软件安装改动），否则改回去还会被刷回——域环境下组策略会定期覆盖本地改动（见[注册表与组策略](02-registry-group-policy.md)）。
3. **依赖服务**：依赖链上的服务是否都在运行？从最底层依赖开始逐个核对。

### 5.3 第三步：查事件日志

服务启动失败时，SCM 会把错误写进事件查看器的**系统日志**（来源多为 Service Control Manager，事件 ID 常见 7000、7001、7009、7034 等；具体 ID 含义以事件查看器内的描述与微软官方文档为准）。查日志时按时间过滤到故障发生前后，看同一时间段有没有相关的底层错误（例如依赖服务报错、驱动加载失败）。

事件查看器的完整用法见[任务计划与事件查看器](05-task-scheduler-event-viewer.md)。

### 5.4 第四步：手动启动，看原样报错

在服务控制台里右键选择“启动”，观察弹出的具体错误信息（例如“错误 1053：服务没有及时响应启动或控制请求”“错误 1068：依赖服务或组无法启动”）。错误代码是下一步搜索与定位的关键词，比“服务起不来”这句描述有用得多。记录下错误代码与完整文本再去查资料，不要只凭记忆转述。

### 5.5 第五步：核对服务账户与可执行路径

如果手动启动也失败，且错误指向权限或找不到文件，核对两项：

- **登录身份**：服务属性页“登录”选项卡，看服务以哪个账户运行；账户密码被改、账户被禁用、账户权限被收回，都会导致服务无法启动。内置服务账户（LocalSystem、NetworkService、LocalService）的含义见[Windows 系统管理](01-system-management.md)。
- **可执行文件路径**：服务属性页“常规”选项卡的“可执行文件的路径”，确认该文件确实存在、未被误删或被杀毒软件隔离。路径指向不存在的文件时，服务一定起不来。

### 5.6 不要做的事

- **不要批量禁用“看着没用”的服务**：网上流传的“优化清单”常把有依赖关系的服务列进去，禁掉一个可能连带停掉一串功能；01 篇已强调过这一点。
- **不要反复点“启动”刷屏**：每次失败启动都会写日志；连续失败十几次后，日志里就分不清哪一次是第一次故障。
- **不要直接删注册表里的服务子项来“卸载”服务**：正确做法是用 `sc.exe delete <服务名>`（示例未实测）或软件自带的卸载程序；删注册表残留配置可能导致 SCM 报错。

## 6. 进程排障：机器卡、慢、占满时怎么看

### 6.1 先定性：瓶颈在哪个资源

打开任务管理器“性能”选项卡，先看四个资源的整体使用率：

| 现象 | 优先怀疑方向 |
|---|---|
| CPU 长期 90% 以上 | 某个进程死循环、后台扫描/索引、驱动问题 |
| 内存占用接近上限 | 某个进程内存泄漏式增长、同时开的应用太多 |
| 磁盘长期 100% | 系统更新、索引重建、杀毒扫描、磁盘本身老化 |
| 网络持续跑满 | 云同步、更新下载、备份上传 |

定性错了方向，后面的排查全是无用功：内存满的时候去结束 CPU 占用的进程，解决不了任何问题。

### 6.2 再定位：哪个进程在吃资源

在任务管理器“进程”选项卡按占用列排序，找到占用最高的进程后，先问三个问题再动手：

1. **它是谁的进程**：系统进程、已装软件的进程、还是来历不明的进程？不认识的进程名先查清楚再动，不要凭名字猜。
2. **占用是持续的还是瞬时的**：更新、扫描、索引类任务占用高是正常的阶段性行为，等它跑完就下来；只有“持续高位不回落”才值得处理。
3. **它承载了什么**：如果是 `svchost.exe`，先在资源监视器的 CPU 选项卡按服务分组看清是哪个服务在耗资源，再决定处理哪个服务。

### 6.3 结束进程的纪律

- **结束前先确认归属**：用“详细信息”选项卡看进程的用户名与命令行，确认它确实是你想结束的那个。
- **优先用应用自己的退出方式**：能正常关闭的程序不要用“结束任务”强杀；强杀可能丢未保存数据、留残留锁文件。
- **不要结束系统关键进程**：`csrss.exe`、`winlogon.exe`、`System` 等系统进程被结束会导致蓝屏或强制注销。任务管理器对部分关键进程有保护，但不要去试探边界。
- **结束进程解决不了服务问题**：服务被结束后 SCM 可能按恢复策略把它重新拉起来；服务层面的问题按第 5 节处理，不要反复杀进程。

### 6.4 进程数异常增多

进程列表里同名进程突然变多（例如几十个同名浏览器子进程），先看是不是正常的多进程架构（现代浏览器每个标签页、每个扩展都可能是一个进程），再看是不是某个程序在反复崩溃重启（结合事件查看器的应用日志看同一时间段的崩溃记录）。反复崩溃重启的进程要处理崩溃原因，而不是逐个结束。

## 7. 常见误解

- **“服务占内存，禁掉能提速”**：空闲服务的内存占用通常很小，禁掉它省不下可感知的资源，反而可能断掉依赖链。真正占资源的是正在干活的进程，不是静止的服务。
- **“任务管理器里 CPU 占用高就是中毒了”**：不一定。更新、索引、扫描、编译都会让 CPU 短时跑满；先看进程归属与持续时间，再下结论。
- **“svchost.exe 占用高就是病毒”**：`svchost.exe` 是多个服务的共享宿主，占用高说明它承载的某个服务在干活，先在资源监视器里按服务分组定位，不要直接结束它。
- **“把服务改成手动就等于关掉了”**：手动服务仍会被依赖它的服务或应用触发启动；想让它彻底不跑，要设成禁用——但禁用前必须先查依赖。
- **“结束任务能解决一切卡顿”**：结束任务只解决“某个进程占资源”的问题；服务起不来、驱动故障、磁盘满、内存泄漏，结束任务都解决不了。

## 8. 小结

服务是“开机就运行的后台程序”，归 SCM 统一管；进程是“正在运行的程序”，内部再分线程干活。排障时先定性瓶颈在哪个资源，再定位到具体服务或进程：服务起不来按“状态 → 启动类型 → 依赖 → 事件日志 → 手动启动看报错 → 账户与路径”的顺序查；进程占资源先确认归属与持续性再动手。禁服务、杀进程之前，先查依赖与归属。
