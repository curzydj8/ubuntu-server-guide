# 性能瓶颈定位：计数器、资源监视器与定位流程

## 1. 本章目标

读完本篇，能说清“卡”是哪种资源先耗尽的：能用任务管理器快速判断瓶颈在 CPU、内存、磁盘还是网络，能用性能监视器读关键计数器做持续观察，能用资源监视器定位到具体进程与文件，并按一套固定流程记录证据、验证结论。

> **实测声明**：本文作者环境为 Linux 虚拟机，Windows 专属命令与操作无法在当前环境实测。文中所有 Windows 命令、操作步骤与示例数值一律标“示例未实测”，请以微软官方文档为准，在测试机上复核后再用于生产环境。

## 2. 背景与问题

“电脑变卡了”是最常见的报修描述，也是最没信息量的一句。卡可能来自 CPU 跑满、内存不够、磁盘读写排队、网络延迟，也可能来自某个进程死循环、某个服务泄漏内存、某块机械硬盘坏道拖慢读写。不先分清是哪种资源瓶颈就动手——加内存、换 SSD、重装系统——很可能钱花了，卡还在。

性能定位的核心思想只有一句话：**先看数据，再下结论**。Windows 自带的三件套——任务管理器、资源监视器、性能监视器——分别对应“快速扫一眼”“定位到进程与文件”“长期持续记录”三个层次，配合使用，多数瓶颈都能在不装第三方工具的情况下定位。

本文只讲故障排查：如何观察、如何定位、如何记录。**不涉及任何入侵、提权、绕过检测的操作步骤**。系统管理基础见[Windows 系统管理](01-system-management.md)，命令行工具的使用见[PowerShell 自动化](03-powershell-automation.md)，启动与蓝屏类故障见[启动故障与蓝屏分析](14-boot-failure-bsod.md)。

## 3. 任务管理器：先扫一眼，定性不等式

任务管理器（Ctrl+Shift+Esc）是第一现场工具，目标不是精确测量，而是**快速定性**：四个资源里谁先顶满。

### 3.1 “进程”选项卡：谁在吃资源

按 CPU、内存、磁盘、网络任一列排序，立刻能看到吃资源最多的进程。看的时候注意三点：

- **先看“总盘子”再看单个进程**：CPU 总占用 95% 与某个进程占 95% 是两回事；前者可能是多进程合力跑满，后者是单个进程的问题。
- **注意“后台进程”分组**：很多资源消耗藏在后台进程与服务里，折叠的分组要展开看，不要只看前台应用。
- **磁盘列的单位是速度，不是占用率**：进程的磁盘读写以 MB/s 显示，数值大不等于磁盘瓶颈——要结合“性能”选项卡的磁盘活动时间判断（见 3.2 节）。

### 3.2 “性能”选项卡：四个资源的实时仪表盘

“性能”选项卡给出 CPU、内存、磁盘、网络的实时曲线与关键数值，是定性判断的主战场：

| 资源 | 先看什么 | 瓶颈信号（示例数值，未实测） |
|---|---|---|
| CPU | 总利用率、逻辑处理器数、基本速度 | 利用率长期 90% 以上，且伴随操作卡顿；单核满载时总利用率可能只有 12.5%（8 核机器），要看每核曲线 |
| 内存 | 已用 / 可用、已提交、缓存 | 可用内存长期接近 0、已提交远超物理内存、频繁出现高硬盘读写（疑似分页） |
| 磁盘 | 活动时间、读写速度、响应时间 | 活动时间长期 100%、平均响应时间数百毫秒以上（机械硬盘尤甚） |
| 网络 | 发送/接收速度、适配器 | 某网卡持续跑满带宽，或发送/接收长时间为 0 但应用报网络超时（可能是网络不通而非带宽瓶颈） |

两个容易误读的点：

1. **CPU 利用率 100% 不一定是瓶颈**：视频渲染、编译、压缩本就该跑满 CPU，跑满是“在干活”不是“出故障”；只有当它跑满且用户操作无响应时，才是瓶颈。
2. **内存“已用”高不一定是瓶颈**：Windows 会主动用空闲内存做文件缓存，已用高但可用内存充足时不必紧张；真正的信号是**可用内存长期见底 + 磁盘频繁分页**。

### 3.3 “启动”与“用户”选项卡：开机慢与多用户场景

- **“启动”选项卡**：列出开机自启程序及其启动影响（高/中/低）。开机慢时先看这里：自启程序越多、影响越大，开机越慢；禁用前先确认该程序是不是业务必需（例如安全软件、同步工具），不要批量全禁。
- **“用户”选项卡**：多用户登录的机器上，看每个用户会话占用的资源；某个用户会话异常耗资源时，可先定位到人再定位到进程。

## 4. 性能监视器：关键计数器与持续观察

任务管理器只能看“现在”，性能监视器（`perfmon`，示例未实测）能看“一段时间的变化趋势”，并能把数据存成日志供事后分析。它是定位间歇性卡顿（例如每天 10 点准时卡、每周备份时卡）的关键工具。

### 4.1 关键计数器：每种资源看哪几个数

计数器的写法是“对象\计数器\实例”，例如 `\Processor(_Total)\% Processor Time`。下表是排障时最常用的计数器组合（计数器名称以系统实际提供为准）：

| 资源 | 关键计数器（示例未实测） | 读法 |
|---|---|---|
| CPU | `\Processor(_Total)\% Processor Time` | 总利用率；持续 > 85% 且伴随卡顿为瓶颈信号 |
| CPU | `\Processor(*)\% Processor Time` | 每个逻辑处理器的利用率；用于发现单核满载 |
| CPU | `\System\Processor Queue Length` | 就绪队列长度；持续 > 逻辑处理器数，说明 CPU 供不应求 |
| 内存 | `\Memory\Available MBytes` | 可用内存兆字节数；长期接近 0 为内存不足信号 |
| 内存 | `\Memory\Pages/sec` | 每秒换页次数；持续高位说明物理内存不足、频繁用磁盘做后备 |
| 内存 | `\Memory\% Committed Bytes In Use` | 已提交内存占比；长期 > 80% 需警惕 |
| 内存 | `\Process(*)\Working Set` | 各进程的工作集（实际占用的物理内存）；用于定位内存泄漏的嫌疑进程 |
| 磁盘 | `\PhysicalDisk(*)\% Disk Time` | 磁盘忙碌时间占比；持续接近 100% 为磁盘饱和信号 |
| 磁盘 | `\PhysicalDisk(*)\Avg. Disk sec/Read`、`\Avg. Disk sec/Write` | 平均读写延迟；机械硬盘数十毫秒以上、SSD 明显高于平常值时需警惕 |
| 磁盘 | `\PhysicalDisk(*)\Current Disk Queue Length` | 当前磁盘队列长度；持续 > 2 说明读写排队严重 |
| 网络 | `\Network Interface(*)\Bytes Total/sec` | 网卡总流量；与带宽上限对照判断是否跑满 |
| 网络 | `\Network Interface(*)\Output Queue Length` | 输出队列长度；持续 > 2 说明网卡发送排队 |

读计数器的一条铁律：**单个计数器高不等于瓶颈，要看组合**。CPU 利用率高 + 处理器队列长，才是 CPU 瓶颈；磁盘活动时间 100% + 队列长 + 延迟高，才是磁盘瓶颈。只看一个数下结论，和只凭“电脑卡”下结论一样不可靠。

### 4.2 数据收集器集：把卡顿录下来

间歇性问题靠“正好在卡的时候看一眼”是抓不住的，要用数据收集器集（Data Collector Set）做持续记录：

1. 新建一个数据收集器集，把 4.1 节的关键计数器加进去，采样间隔按需设定（排障常用 5–15 秒，示例未实测）。
2. 让它在后台跑，覆盖“卡”的时间段（例如一个工作日、一次备份窗口）。
3. 事后用性能监视器打开日志文件，对照卡顿发生的时间点，看哪个计数器先异常——先异常的资源最可能是瓶颈，跟着异常的资源往往是被拖累的。

记录时顺手记下：机器配置（CPU 型号与核数、内存大小、磁盘类型是 SSD 还是 HDD）、卡顿发生的起止时间、当时在做什么操作。没有这三条上下文，日志文件换个人就看不懂。

## 5. 资源监视器：定位到进程与文件

资源监视器（任务管理器 → “性能” → “打开资源监视器”，或运行 `resmon`，示例未实测）是任务管理器与性能监视器之间的桥梁：它按 CPU、内存、磁盘、网络四个选项卡组织，每个选项卡都能**定位到具体进程、并进一步定位到该进程正在读写的文件或连接的地址**。

### 5.1 磁盘选项卡：谁在读写哪个文件

磁盘选项卡分上下两部分：上半部分是正在读写磁盘的进程（读写速度、I/O 次数），下半部分是这些进程正在操作的**具体文件路径**。这是定位“磁盘 100%”的利器：

- 某个进程持续高速读写 → 先看它在读写哪个文件：是系统更新在写补丁、杀毒软件在全盘扫描、备份软件在打包，还是某个应用在疯狂写日志。
- 读写集中在某个文件上 → 看文件归属：日志文件无限膨胀、数据库文件碎片化、页面文件（`pagefile.sys`）频繁读写，都各有不同的处理方向。
- 读写速度不高但磁盘活动时间 100% → 多为小文件随机读写或磁盘本身响应慢（机械硬盘、坏道盘常见），要看响应时间而不是只看速度。

### 5.2 CPU 与内存选项卡：进程级细节

- **CPU 选项卡**：除利用率外，还能看到每个进程的线程数与平均 CPU；线程数异常暴涨的进程值得怀疑（例如死循环创建线程）。
- **内存选项卡**：能看到每个进程的工作集、提交大小与硬错误（Hard Faults/sec）。硬错误是“要的数据不在内存、得去磁盘上找”的次数，**硬错误持续高位 + 可用内存见底**，就是内存不足的实锤。
- **网络选项卡**：能看到每个进程的网络活动与远程地址；某个进程持续向陌生地址发包时，先按安全流程处理（断网、报安全团队），不要只当性能问题看。

### 5.3 三件套的分工

| 工具 | 适合场景 | 定位粒度 |
|---|---|---|
| 任务管理器 | 快速定性：现在卡在哪种资源 | 进程级、实时 |
| 资源监视器 | 定位到进程与文件：谁在读写什么 | 进程 + 文件/连接、实时 |
| 性能监视器 | 间歇性问题：卡顿何时发生、如何演变 | 计数器、可记录、可回放 |

顺序建议：先任务管理器定性 → 再资源监视器定位进程与文件 → 抓不住的间歇性问题上性能监视器做持续记录。跳过前两步直接上性能监视器，容易在几十个计数器里迷路。

## 6. 常见瓶颈特征：认得出，才定位得快

### 6.1 内存泄漏：越用越慢，重启就好

内存泄漏是指程序申请了内存却不释放，占用量随运行时间单调增长。特征：

- 机器刚开机流畅，用几小时或几天后越来越卡，重启后恢复，过一段时间又卡。
- 任务管理器里某个进程的工作集持续增长，从不回落；性能监视器里 `\Process(该进程)\Working Set` 呈上升趋势，`\Memory\Available MBytes` 呈下降趋势。
- 可用内存见底后，系统频繁换页，磁盘活动时间随之升高——这时磁盘 100% 是内存不足的**后果**，不是原因；加 SSD 缓解不了，修泄漏或加内存才是方向。

处理方向：先确认是哪个进程泄漏（看工作集趋势），再更新、回滚或替换该程序；临时缓解可用重启该进程或定时重启服务，但这只是止痛，不是根治。泄漏的根因在程序代码里，用户侧能做的有限，不要指望改注册表或清内存能修好泄漏。

### 6.2 磁盘 IO 饱和：活动时间 100%，响应时间飙升

磁盘 IO 饱和是指磁盘读写请求排队过长，特征：

- 磁盘活动时间长期 100%，平均响应时间数百毫秒，打开文件、启动程序明显变慢，但 CPU 利用率并不高。
- 资源监视器里能看到具体是哪个进程在读写；常见元凶：全盘杀毒扫描、系统更新、备份任务、索引重建、日志暴涨。
- 机械硬盘（HDD）比固态硬盘（SSD）更容易出现：随机小读写多时，HDD 的寻道时间会成为瓶颈；SSD 则要看是否接近写满（SSD 写满后性能下降，原理见[SSD 存储原理](../01-computer-basics/04-ssd-storage.md)）。

处理方向：先分清是“某个任务在集中读写”（错峰、限速、改计划）还是“磁盘本身老化或损坏”（查 S.M.A.R.T. 状态、有异响或坏道时先备份再换盘）。不要一上来就碎片整理：SSD 不需要整理，HDD 整理对随机读写为主的瓶颈帮助有限。

### 6.3 CPU 单核满载：总利用率不高，操作照样卡

多核机器上，某个单线程程序跑满一个核时，总利用率可能只有 12.5%（8 核）或 25%（4 核），但界面照样卡死。特征：

- 任务管理器“性能”选项卡里，某个逻辑处理器的曲线长期贴顶，其他核空闲。
- 涉事进程多为单线程的老程序、死循环的脚本、或某个插件卡死主线程。
- 性能监视器里 `\Processor(*)\% Processor Time` 能逐核确认。

处理方向：先确认是哪个进程、哪个线程；能换多线程版本就换，不能换就接受“这个程序只能用一个核”的现实，把期望放在减少它的负载上，而不是指望加核数解决问题。单核性能不足时，升级 CPU 要看单核性能，不只看核数。

### 6.4 其他常见瓶颈速查

| 瓶颈 | 典型信号 | 先查什么 |
|---|---|---|
| 网络带宽跑满 | 网卡流量持续接近带宽上限，下载慢、视频卡 | 哪个进程在传数据、是否在同步或备份 |
| 网络延迟高 | 带宽有余量，但应用报超时、远程桌面卡顿 | 延迟与丢包、DNS、网关与链路质量 |
| 显卡满载 | 游戏或渲染卡顿，GPU 利用率 100% | 显卡利用率与显存占用、驱动版本 |
| 启动项过多 | 开机慢，登录后长时间无响应 | 任务管理器“启动”选项卡的影响分级 |
| 系统更新/扫描占用 | 特定时间段规律性卡顿 | 更新、杀毒扫描、备份任务的计划时间 |

## 7. 定位流程与记录方法

推荐的通用流程（与[启动故障与蓝屏分析](14-boot-failure-bsod.md)的排障流程思路一致，先定位、再动手）：

1. **复现并描述**：卡顿在什么操作下出现？每次都出现还是偶发？持续多久？有没有规律的时间段？
2. **任务管理器定性**：四个资源谁先顶满？是单个进程还是多个进程合力？
3. **资源监视器定位**：顶满的资源对应哪个进程、哪个文件、哪个连接？
4. **性能监视器取证**：间歇性问题用数据收集器集录下卡顿时间段，事后对照时间点分析。
5. **一次只改一处，改完验证一次**：禁用一个自启项、更新一个驱动、错开一个计划任务，改完观察同样操作是否还卡；同时改五处，好了也不知道是哪一处起的作用。
6. **记录成文**：按 7.1 节的模板记下来，同一台机器下次再卡、或别人接手时不用从头查。

### 7.1 记录模板

```
日期时间：____（卡顿发生的起止时间）
机器配置：CPU ____ / 内存 ____ GB / 磁盘 ____（SSD/HDD）/ 网络 ____
现象描述：____（什么操作、怎么卡、持续多久、是否可复现）
任务管理器：CPU __% / 内存可用 __ / 磁盘活动 __% / 网络 __
嫌疑进程：____（进程名、占用数值）
资源监视器：该进程在读写 ____ 文件 / 连接 ____ 地址
性能监视器：异常计数器 ____，异常时间段 ____
已采取措施：____（一次一条）
验证结果：____（同样操作是否还卡）
结论：瓶颈是 ____，原因是 ____，下一步 ____
```

记录的意义在于：性能问题很少一次根治，多数是“缓解—复发—再定位”的循环；有记录，下一次定位就从上一次的结论开始，而不是从“电脑卡”重新开始。

## 8. 限制与常见误解

- **“CPU 100% 就是要换 CPU”**：错。先看是哪个进程、是不是单核满载、是不是某个任务在集中跑；渲染与编译跑满 CPU 是正常工作状态。
- **“内存占用高就是内存泄漏”**：错。缓存占用高是正常现象；泄漏的特征是某进程工作集随时间单调增长、且重启后恢复。
- **“磁盘 100% 就是硬盘坏了”**：错。多数磁盘 100% 是某个进程在集中读写（更新、扫描、备份）；先看资源监视器，再怀疑硬件。
- **“清内存、关特效能解决性能问题”**：多数情况下只是心理安慰；瓶颈在磁盘或单核时，清内存没有帮助。
- **“加内存能解决一切卡顿”**：错。CPU 单核满载、磁盘 IO 饱和、网络延迟，加内存都解决不了；先定位再花钱。
- **本文不展开的内容**：服务器性能调优（NUMA、存储阵列、虚拟化宿主机）、数据库与应用的性能分析、网络抓包的深入分析——这些各有专门的工具与篇目，超出本篇范围。

## 9. 小结

性能定位 = 先定性（任务管理器看哪种资源顶满）→ 再定位（资源监视器看哪个进程、哪个文件）→ 间歇性问题取证（性能监视器录下卡顿）→ 一次改一处、改完验证、记录成文。认得住内存泄漏、磁盘 IO 饱和、CPU 单核满载这三种典型特征，多数“电脑卡”都能在半小时内定性；定性错了，后面花的钱和时间都是白花。
