# 任务计划与事件查看器

> 实测说明：本文作者环境为 Linux 虚拟机，Windows 专属命令与图形操作无法在当前环境实测。文中所有 Windows 命令与操作示例一律标注“示例未实测”，请以实际系统行为与微软官方文档为准。

## 1. 本章目标

读完本篇，能说清任务计划程序的触发器、操作、条件、设置四部分如何组成一个计划任务，能按权限与运行身份的要求正确配置任务的执行身份，能在事件查看器里按日志分类与事件 ID 定位故障，并把“日志里出现某事件”变成“自动执行某个任务”的联动。

本文是[Windows 系统管理](01-system-management.md)中任务计划一节的展开：那篇讲了“任务计划是定时任务机制、触发器比 cron 丰富”的结论，本篇讲“怎么建、用什么身份跑、跑失败了去哪查、怎么让日志触发任务”。服务管理与进程排障见[服务与进程管理实务](04-services-processes.md)，PowerShell 的任务相关命令见[PowerShell 自动化](03-powershell-automation.md)。

## 2. 为什么需要它

很多维护工作不需要人盯着：凌晨备份、定期清理临时文件、每周导出报表、磁盘空间不足时发告警。这些工作如果靠人记、靠手工跑，迟早会漏。任务计划程序就是 Windows 里“让维护工作自己发生”的机制。

而事件查看器是另一半：系统与应用出问题时，第一手证据不在用户的描述里，而在日志里。“昨天凌晨备份失败了”是用户描述；“事件 ID 某某、在几点几分、哪个任务、什么错误代码”才是可以定位的事实。会看日志，排障就有了起点；会把日志与任务联动，排障就从“事后翻日志”升级成“出问题自动响应”。

## 3. 任务计划程序：一个任务由四部分组成

任务计划程序（Task Scheduler，`taskschd.msc`）里的每个任务由四部分组成，建任务时按这个顺序想清楚，比建完再返工快得多：

### 3.1 触发器（Trigger）：什么时候跑

触发器决定任务在什么条件下启动。常用类型：

| 触发器 | 说明 |
|---|---|
| 按计划（时间） | 一次、每天、每周、每月，在指定时间运行；可设重复间隔（例如每 30 分钟重复一次，持续 8 小时） |
| 计算机启动时 | 开机后运行；适合“开机后要做的初始化工作” |
| 用户登录时 | 指定用户（或任何用户）登录时运行 |
| 空闲时 | 计算机空闲达到指定时间后运行；适合磁盘整理、索引这类“别打扰人”的工作 |
| 事件触发 | 指定日志里出现符合条件的事件时运行；详见第 6 节 |
| 任务创建/修改时、会话状态变化时 | 较少用的触发条件，适合特定管理场景 |

一个任务可以挂多个触发器（例如“每天凌晨 2 点跑，计算机空闲时也跑”）。触发器之间是“或”的关系：任一触发器满足就启动任务。

### 3.2 操作（Action）：跑什么

操作决定触发后执行什么。现代任务计划程序里实际可用的操作主要是：

- **启动程序**：运行一个程序或脚本（例如 `powershell.exe -File C:\Scripts\backup.ps1`）。这是最常用的操作，备份、清理、报表等任务都是这一种。
- **发送电子邮件与显示消息**：旧版本提供的操作，在现代 Windows 中已被弃用，不应再用于新任务；需要通知时，改为在脚本里调用发信或写日志的方式实现。

操作里要填的三个字段容易填错：

- **程序/脚本**：填可执行文件路径（例如 `powershell.exe`），不要把参数也写进这一栏。
- **添加参数**：填传给程序的参数（例如 `-File C:\Scripts\backup.ps1`）。
- **起始于**：填脚本或程序的工作目录；脚本里用相对路径时，工作目录决定它相对谁而言，填错会导致“手工跑能成功、计划跑找不到文件”。

### 3.3 条件（Condition）：满足什么前提才跑

条件是对触发器的补充限制，触发器满足后还要过条件这一关才真正执行：

- **电源**：仅在交流电源下运行（笔记本拔掉电源时不跑备份）、唤醒计算机以运行任务（需要时把睡眠中的机器唤醒）。
- **空闲**：仅在计算机空闲时运行，并可指定空闲多久算空闲、停止空闲后是否停止任务。
- **网络**：仅在指定网络可用时运行（例如仅在连上公司内网时跑同步任务）。

条件与触发器的区别：触发器回答“什么时候启动”，条件回答“启动时还要满足什么才真跑”。一个“每天凌晨 2 点跑”的任务加上“仅交流电源”条件，笔记本拔电过夜时就不会在电池上跑备份。

### 3.4 设置（Settings）：跑起来之后怎么管

设置管任务执行过程的行为：

- **失败重试**：任务失败后隔多久重试、最多重试几次。
- **超时停止**：任务运行超过指定时间后强制停止，防止脚本死循环一直占着资源。
- **并发策略**：上一次还没跑完、触发器又到了时怎么办——不启动新实例、并行运行、排队等待、停止现有实例。
- **手动运行与历史记录**：允许按需手动运行、是否记录任务历史（历史记录默认可能关闭，需要在任务计划程序右侧操作栏开启“启用所有任务历史记录”才能看到每次运行的详细记录）。

## 4. 计划任务的权限与运行身份

计划任务最常见的失败原因不是脚本写错，而是**身份与权限配错**。这一节的每一条都对应一类真实故障。

### 4.1 运行身份：任务以谁的身份执行

创建任务时要指定“运行身份”——任务执行时用的账户。常见选择：

- **指定用户账户**：任务以该用户的身份运行，能访问该用户能访问的资源。适合“要读写某用户目录、要用某用户凭据访问网络资源”的任务。
- **SYSTEM（LocalSystem）**：以本机最高权限运行，适合纯本机维护任务（清理、备份本机文件）。SYSTEM 没有网络凭据，访问网络共享时用的是计算机账户身份，跨机器访问要按计算机账户授权。
- **组托管服务账户（gMSA）等服务账户**：域环境下为无人值守任务设计的账户类型，无需人工维护密码；是否可用取决于域环境配置，以官方发布为准（待核实）。

### 4.2 “不管用户是否登录都要运行”与“只在用户登录时运行”

这是新建任务时最关键、也最容易选错的一项：

| 选项 | 含义 | 适用场景 |
|---|---|---|
| 只在用户登录时运行 | 用户注销后任务不跑；任务运行时可见（可与桌面交互） | 需要用户在场、需要桌面交互的任务 |
| 不管用户是否登录都要运行 | 用户注销后任务照常跑；任务在后台无界面运行 | 夜间备份、定时清理等无人值守任务 |

选了“不管用户是否登录都要运行”，创建时会要求提供该账户的密码（用于把凭据存进任务，供注销后使用）。密码改了之后要同步更新任务里存的凭据，否则任务会因“登录失败”而无法启动——这是无人值守任务最常见的静默失败原因。

### 4.3 “使用最高权限运行”

勾选后任务以管理员令牌运行（相当于绕过 UAC 的提权提示）。需要写系统目录、改服务配置、访问受保护资源的任务要勾选；不需要管理员权限的任务不要勾选——权限最小化原则在计划任务里同样适用。

### 4.4 任务失败的权限类定位顺序

任务没有按预期运行（“上次运行结果”不是 0x0）时，按这个顺序查：

1. **看“上次运行结果”与历史记录**：结果代码是第一线索（例如 0x1 常表示脚本或程序返回了错误，0x80070569 等代码指向登录或权限问题；具体代码含义以微软官方文档为准）。
2. **核对运行身份与密码**：账户是否被禁用、密码是否改过、账户是否有权登录为批处理作业（域策略可能限制这一点）。
3. **核对“起始于”与路径**：脚本里用的相对路径、网络路径，在任务的运行身份下是否可达。
4. **核对触发器与条件**：是不是条件没满足（例如笔记本拔电、网络未连）导致任务根本没启动，而不是启动后失败。
5. **手动运行一次**：在任务计划程序里右键选择“运行”，看能否复现失败；能复现就把脚本拿到交互式 PowerShell 里跑，看完整报错。

命令行管理任务用 `schtasks.exe`（示例未实测）：

```cmd
schtasks /query /tn "备份任务" /v /fo list
schtasks /run /tn "备份任务"
```

第一条查询指定任务的详细配置，第二条手动触发一次运行。任务名含中文或空格时要用引号包裹。PowerShell 的等价命令（`Get-ScheduledTask` 等）见[PowerShell 自动化](03-powershell-automation.md)。

## 5. 事件查看器：日志分类与事件 ID 定位方法

事件查看器（Event Viewer，`eventvwr.msc`）是 Windows 的日志中枢：系统、应用、安全事件都按统一的“事件”格式记录——每条事件有时间、来源、事件 ID、级别、描述。排障时先学会“去哪类日志里找”，再学会“按什么过滤”。

### 5.1 日志分类：先找对日志

事件查看器左侧分两大类：

**Windows 日志（Windows Logs）**——系统级核心日志，共五类：

| 日志 | 记录内容 | 典型用途 |
|---|---|---|
| 应用程序（Application） | 应用程序记录的事件（崩溃、报错、业务日志） | 应用崩溃、软件报错时先看这里 |
| 安全（Security） | 登录成功/失败、权限使用、对象访问等审核事件 | 登录异常、账户锁定、权限问题时看这里；需开启相应审核策略才有记录 |
| 系统（System） | 系统组件与驱动、服务控制管理器的事件 | 服务起不来、驱动加载失败、系统启动问题时看这里 |
| 安装程序（Setup） | 系统安装与更新过程的事件 | 系统更新、功能安装失败时看这里 |
| 转发的事件（Forwarded Events） | 从其他计算机集中收集来的事件 | 集中日志收集场景，单机一般为空 |

**应用程序和服务日志（Applications and Services Logs）**——各组件自己的专用日志，例如 Microsoft 子目录下各 Windows 组件的日志、硬件事件日志、任务计划程序自己的 operational 日志（Microsoft-Windows-TaskScheduler/Operational）。想查“某次任务计划为什么没跑”，要来这里看任务计划程序的 operational 日志，而不是在 Windows 日志里翻。

### 5.2 事件级别：先看红色与黄色

每条事件有一个级别，决定先看谁：

| 级别 | 含义 | 处理态度 |
|---|---|---|
| 错误（Error） | 功能失败或数据丢失 | 优先处理 |
| 警告（Warning） | 潜在问题，功能暂未失败 | 结合上下文判断是否需要处理 |
| 信息（Information） | 正常操作记录 | 排障时用来确认“某事确实发生了” |
| 审核成功 / 审核失败 | 安全审核的两种结果 | 安全类问题时看 |

注意：**日志里有错误不等于机器有问题**。正常运行的 Windows 机器日志里也会有零星错误与警告（例如某次网络重试、某个服务启动超时后自行恢复）。判断标准是“错误是否与你正在查的故障在时间上对应、来源上相关”，而不是“日志里有没有红色”。

### 5.3 事件 ID 定位方法

事件 ID 是同一来源下某类事件的编号，是定位与搜索的关键词。定位步骤：

1. **按时间缩小范围**：先用右侧“筛选当前日志”按时间段过滤（例如故障发生前后一小时），不要在全量日志里翻。
2. **按级别过滤**：先只看“错误”与“警告”，确认没有相关项再放宽到信息。
3. **按事件 ID 与来源过滤**：在筛选器里填事件 ID（例如服务控制管理器的 7000、7034）或来源名，只看这类事件在时间段内的全部记录。
4. **读“常规”选项卡的描述**：描述里通常直接写明失败原因与相关对象（服务名、文件名、错误代码），比只看 ID 更有用；“详细信息”选项卡是结构化数据，适合导出后分析。
5. **找成对出现的事件**：很多故障在日志里是成对的——例如“服务启动失败”前后常有“依赖服务启动失败”；只看一条可能误判根因。
6. **用“查找”做全文检索**：在当前日志里按关键词（服务名、文件名、错误代码）查找，适合不知道事件 ID 时的兜底做法。

命令行查日志用 `wevtutil.exe`（示例未实测）：

```cmd
wevtutil qe System /c:20 /rd:true /f:text
```

上面命令按时间倒序输出系统日志最近 20 条事件的文本。导出整份日志做离线分析：

```cmd
wevtutil epl System C:\Backup\system-log.evtx
```

导出的 `.evtx` 文件可在另一台机器的事件查看器里打开查看。PowerShell 的等价命令是 `Get-WinEvent`，详见[PowerShell 自动化](03-powershell-automation.md)。

### 5.4 日志满了与日志保留

每类日志有大小上限与写满后的策略（覆盖旧事件、按需存档、不覆盖）。系统日志与安全日志写满后如果设成“不覆盖”，新事件会写不进来——安全日志写满还可能导致需要写审核事件的操作失败。定期检查日志大小与保留策略，重要机器的安全日志应及时归档导出，不要等写满了再处理。

## 6. 结合任务计划做日志联动

事件查看器的“附加任务”与任务计划程序的“事件触发器”是同一机制的两面：**日志里出现符合条件的事件 → 自动执行一个任务**。典型用途：磁盘空间不足告警、关键服务崩溃后自动重启、特定安全事件出现时发通知或做快照。

### 6.1 创建联动：两种入口

- **从事件查看器创建**：在一条事件上右键选择“将任务附加到此事件”，向导会按该事件的日志、来源、事件 ID 自动填好触发器，再让用户指定操作（启动程序）。适合“已经有一条现成的事件、想对它做响应”的场景。
- **从任务计划程序创建**：新建任务时触发器选“发生事件时”，手动指定日志、来源、事件 ID。适合“先设计好响应规则、再等事件发生”的场景。

### 6.2 事件触发器的过滤：只响应想响应的事件

事件触发器可以只按日志 + 来源 + 事件 ID 过滤，也可以进一步用 **XPath 查询**做精细过滤（例如只响应事件数据里某个字段等于特定值的事件）。XPath 过滤的完整语法以微软官方文档为准（待核实）；日常使用中，先按日志 + 来源 + 事件 ID 过滤，确实需要更细的条件时再研究 XPath。

一个常见误区：**触发器配得太宽**。例如只按事件 ID 过滤、不限来源，可能导致不相关的同类事件也触发任务；任务反复触发又会反过来刷出更多日志。配好触发器后，先用“手动制造一次该事件”或等一次真实发生，确认任务只在预期情况下触发。

### 6.3 联动任务的注意事项

- **操作要轻、要幂等**：联动任务通常是“发告警、写标记、重启服务”这类轻操作；不要让联动任务本身去做重型、不可重复的操作——事件可能短时间内连续出现多次，任务也会连续触发多次。
- **联动任务也要配运行身份**：它在后台无人值守运行，适用第 4 节的全部规则（“不管用户是否登录都要运行”、凭据更新、最高权限按需勾选）。
- **联动任务的失败要能被发现**：联动任务本身的运行记录在任务计划程序的历史记录与 operational 日志里；如果联动任务静默失败（例如脚本路径错），事件还在发生、响应却一直没执行，比没有联动更危险——因为人会误以为“已经自动处理了”。
- **不要用联动替代根因修复**：服务崩溃后自动重启是缓冲，不是修复；重启次数多了，要回头查服务为什么反复崩溃（见[服务与进程管理实务](04-services-processes.md)第 5 节）。

## 7. 常见误解

- **“任务建好了就一定会跑”**：不一定。触发器、条件、运行身份、密码、电源状态，任何一环不满足任务都不会跑；建完要看一次“上次运行结果”确认。
- **“任务失败就是脚本写错了”**：不一定。权限、运行身份、密码过期、工作目录、条件未满足，都会让任务失败；先按第 4.4 节的顺序定位。
- **“日志里有红色错误就是机器坏了”**：不一定。先看错误的时间与来源是否与当前故障对应；孤立的、已自行恢复的历史错误不需要处理。
- **“事件 ID 是全系统唯一的”**：不是。事件 ID 只在同一来源内有意义；查资料时要“来源 + 事件 ID”一起查，只报 ID 查到的可能是另一个来源的同名事件。
- **“清空日志能解决问题”**：不能。清空日志只是删掉了证据，故障本身还在；清空前应先导出备份。

## 8. 小结

任务计划 = 触发器（什么时候）+ 操作（跑什么）+ 条件（什么前提）+ 设置（怎么管），无人值守任务的关键在运行身份与凭据维护。事件查看器 = 先找对日志分类，再按时间、级别、事件 ID 过滤，读描述、找成对事件。两者联动起来，就是“日志里出现某事件 → 自动执行响应任务”；但联动只是缓冲与响应，根因仍要靠日志定位后动手修复。
