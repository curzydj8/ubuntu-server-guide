# HLS/DASH 自适应码流

## 1. 本章目标

读完本篇能理解：HLS 与 MPEG-DASH 如何把一段连续的音视频切成小文件、写进清单文件，再让播放器按实时带宽在多档清晰度之间切换；以及延迟、稳定性与成本之间的账是怎么算的。

## 2. 背景与问题

本组上一篇（流媒体与直播基础）只讲了 HLS/DASH 在链路里的定位：它们是“拉流”一侧的 HTTP 方案。但定位讲完，真正的机制问题还在：播放器凭什么知道有哪些清晰度可选？一段视频切成多少块、每块多长？带宽一掉，播放器怎么决定降档，又在什么时候换？

这两种协议要解决的核心问题是同一个：**在不可靠、带宽会变的互联网上，用普通 HTTP 与 CDN 基础设施，分发“不断流、尽量清晰”的视频**。答案不是把视频当成一个大文件传，而是把它切成很多带编号的小段，再配一张清单告诉播放器“有哪些段、有哪些清晰度、按什么顺序拿”。

## 3. 总体架构

一条 HLS/DASH 分发链路的组成部分：

```
编码 ladder（同一内容多档码率，如 1080p/720p/480p）
        ↓ 打包器（packager）：切分片 + 写清单
清单文件（HLS：.m3u8 / DASH：.mpd）+ 媒体分片（.ts / .m4s）
        ↓ 普通 HTTP 服务器 / CDN 边缘缓存
播放器：读清单 → 估带宽 → 按段请求 → 解码渲染
        ↑________ 每个新段都是一次重新决策 ________|
```

关键点：**控制权完全在播放器（客户端）手里**。服务器只负责把所有档位都摆出来、把分片放好；选哪一档、何时切换，由播放器按自己测到的带宽与缓冲水位决定。这一点两种协议相同，DASH 的标准文本也明确写着“控制权在客户端”。

## 4. 工作机制

### 4.1 HLS：清单是纯文本，分片是文件

HLS 由 Apple 推出（2009 年，随 iPhone 3GS 时代发布），2017 年 8 月整理为 RFC 8216（信息类 RFC，描述协议第 7 版，非 IETF 共识标准）。

HLS 有两级清单：

- **主清单（master playlist）**：一张“菜单”，列出所有可用的码流（variant stream），每行用 `#EXT-X-STREAM-INF` 标明该档的带宽（BANDWIDTH，单位 bps）、分辨率（RESOLUTION）与编解码（CODECS），下一行就是该档媒体清单的地址。
- **媒体清单（media playlist）**：一张“节目单”，列出该档的一串分片。每片一行 `#EXTINF:时长,` 加分片地址；`#EXT-X-TARGETDURATION` 声明本清单中最长分片的时长（整数秒，向上取整）；`#EXT-X-MEDIA-SEQUENCE` 是第一个分片的序号。

直播时媒体清单是“滑动窗口”：新分片不断追加、旧分片不断从清单里移除，播放器反复轮询清单（通常每半个目标时长或一个目标时长一次）发现新段。点播时清单末尾有 `#EXT-X-ENDLIST`，表示分片已齐，播放器不必再轮询。

分片封装有两种：早期是 MPEG-TS（`.ts`），后来支持 fMP4（`.m4s`，与 DASH 共用同一套分片格式，见 4.5 节）。一个硬约束继承自上一篇：**切片只能落在关键帧上**，所以编码器的关键帧间隔（GOP）必须与目标段长对齐，否则实际段长就是 GOP 的长度。

### 4.2 DASH：清单是 XML，结构分四层

MPEG-DASH 由 MPEG 制定，国际标准 ISO/IEC 23009-1 首版发布于 2012 年 4 月 1 日。它的清单叫媒体呈现描述（MPD，`.mpd` 文件），是 XML，层级比 HLS 更规整：

```
MPD（整个呈现：时长、直播还是点播）
 └─ Period（时间段：一段节目，如正片与广告可分属不同 Period）
     └─ AdaptationSet（同一类内容的一组可选档：如“视频”组、“音频”组）
         └─ Representation（某一档：如 720p / 2 Mbps 的具体码流）
             └─ Segment（分片：按 SegmentTemplate 的模板地址生成）
```

每个 Representation 带 `bandwidth`、`width`、`height`、`codecs` 等属性，作用与 HLS 的 `#EXT-X-STREAM-INF` 一样。分片地址通常不逐个列出，而是用 `SegmentTemplate`（如 `chunk-stream$RepresentationID$-$Number%05d$.m4s`）加 `SegmentTimeline`（每段的起止时间表）让播放器自己算出第 N 个分片的 URL。DASH 的分片一般是 fMP4，每个 Representation 还有一个很小的初始化段（init segment），里面是解码器配置（编码参数、时间基准），播放器切档前必须先拿到新档的初始化段。

直播模式下 MPD 也有“滑动窗口”的等价机制：`type="dynamic"` 的 MPD 会随时间更新，播放器定期重新拉取；`availabilityStartTime` 与 `timeShiftBufferDepth` 告诉播放器“现在能看的最早位置”与“可回看多久”。

### 4.3 自适应码率切换：每次只换下一段

无论 HLS 还是 DASH，自适应切换（ABR）的循环都一样：

```
下载一段 → 测本次下载的实际吞吐 → 结合缓冲水位（还剩几秒没播）
    → 下一段选哪一档 → 请求下一段 → 循环
```

三条铁律：

1. **切换单位是“段”，不是帧**。正在播的这一段播完才能换档，所以段长直接决定切换灵敏度：6 秒一段，带宽骤降后最迟 6 秒才降档；2 秒一段，2 秒就能反应过来。
2. **切换只能在关键帧处发生**。各档分片的边界必须对齐到同一时间点的关键帧（即各档 GOP 对齐），否则切档时会花屏或卡住。转码 ladder 必须用同一 GOP 结构出所有档，这是打包环节最容易踩的坑。
3. **播放器是保守的**。带宽估计只看“刚下载完那一段的平均速度”，还受缓冲水位制约：缓冲快空了就先降档保不断流；缓冲很满才敢升档。升档慢、降档快，是绝大多数播放器的默认性格——因为一次卡顿比几秒低清更伤体验。

码率阶梯（ladder）本身也是设计：档与档之间通常按约 1.5–2 倍的码率递进（如 0.8 / 1.5 / 3 / 6 Mbps），档太密则切换频繁、转码成本高，档太疏则一降档画质断崖。阶梯的具体档位没有标准答案，按目标观众的带宽分布定。

### 4.4 延迟与缓存的权衡：段长是总开关

普通 HLS/DASH 的延迟账可以拆成三笔：

| 一笔账 | 大小 | 能不能省 |
|---|---|---|
| 打包等待：攒满一段才能发布 | 一个段长起步（段长 6 秒就至少 6 秒） | 缩短段长，或用部分段（见下） |
| 播放器缓冲：开播前攒几段才敢播 | 通常 1–3 个段（RFC 8216 建议不要从离直播边缘不足 3 个目标时长处起播） | 减小缓冲，但抗抖动变差 |
| CDN 与传输 | 几十到几百毫秒 | 边缘命中、预热可优化，但省不掉 |

低延迟版本就是在这三笔账上做文章：

- **LL-HLS（低延迟 HLS）**：Apple 在 WWDC 2019 提出。把一个段再切成若干“部分段”（part，约 0.2–1 秒），播放器不等整段攒满就开始拿部分段；同时用 HTTP/2 服务器推送或阻塞式清单重载（blocking playlist reload）让播放器更快知道新部分段到了。目标是把延迟从 10 秒量级压到 2–3 秒。
- **LL-DASH（低延迟 DASH）**：思路相同，用 CMAF 的分块传输（chunked transfer）：一个 fMP4 段在编码的同时就按块（chunk）边生成边发，播放器按块取，不等整段。两者都要求编码器、打包器、CDN、播放器整条链配合，缺一环就退回普通延迟。

代价是同一枚硬币的反面：段越短、部分段越碎，HTTP 请求数成倍上升，CDN 缓存命中率下降、回源增多，弱网下一次抖动就可能断流。**延迟不是免费的，是拿稳定性与成本换的**。赛事转播宁可 10 秒延迟也要稳，互动直播才值得付这笔账。

### 4.5 两种协议的趋同：CMAF 与加密

早期 HLS 用 TS、DASH 用 fMP4，两套分片互不通用，源站要存两份。CMAF（通用媒体应用格式）让两者共用同一套 fMP4 分片：同一份分片，配 HLS 清单就是 HLS 流，配 DASH 清单就是 DASH 流，存储省一半。CMAF 的标准编号与发布细节以官方发布为准（待核实），见文末未完成项。

加密也各有一套：HLS 常用 AES-128（清单里 `#EXT-X-KEY` 给出密钥地址，播放器下载密钥解密），DASH 常用 CENC（通用加密，分片本身加密、密钥管理交给 DRM 系统）。两者都只解决“传输与存储时不被偷看”，不解决“拿到密钥的人能不能录屏”——那是 DRM 与水印的范畴，不在本篇展开。

## 5. 关键设计取舍

- **延迟换稳定**：段长与缓冲是同一根绳子的两头。6 秒段 + 3 段缓冲极稳但延迟 15 秒以上；2 秒段 + 1 段缓冲延迟数秒，但一次抖动就卡。
- **切换灵敏度换请求成本**：段越短，ABR 反应越快，但请求数、CDN 日志量、回源压力同步上升；LL 方案还要 CDN 支持分块传输与阻塞式重载。
- **档位数量换转码与存储成本**：每多一档，转码算力与存储都多一份；档位不是越多越好，按观众带宽分布裁剪。
- **通用性换控制力**：HTTP 方案复用全网 CDN 与防火墙友好（80/443 端口），代价是服务器无法主动推数据，只能等播放器来拉——所有“实时性”改进都是在“拉”模式里打补丁。

## 6. 分类与变体

### 6.1 HLS 与 DASH 对比

| 维度 | HLS | MPEG-DASH |
|---|---|---|
| 归属与标准 | Apple 主导；RFC 8216（2017，信息类） | MPEG；ISO/IEC 23009-1（2012 首版，国际标准） |
| 清单格式 | 纯文本 `.m3u8`，两级清单 | XML `.mpd`，Period / AdaptationSet / Representation / Segment 四层 |
| 分片封装 | TS 或 fMP4 | fMP4 为主（也可 TS） |
| 编解码选择 | 早期偏 H.264/AAC，fMP4 后开放 | 从设计上编解码无关，H.264/H.265/VP9/AV1 均可 |
| 播放器支持 | Apple 全系原生；浏览器多需 JS 播放器（如 hls.js） | 浏览器多需 JS 播放器（如 dash.js、Shaka Player） |
| 低延迟版本 | LL-HLS（部分段 + 阻塞式清单重载） | LL-DASH（CMAF 分块传输） |
| 适用 | 移动端、Apple 生态、大众点播与直播 | 开放生态、Web、需要多编码与 DRM 灵活组合的场景 |

### 6.2 按场景选

- **点播（VOD）**：两者都行，段长可放宽到 6–10 秒（请求少、缓存命中高）；ABR 阶梯可以做多档。
- **普通直播（赛事、发布会）**：HLS/DASH 普通模式，段长 2–6 秒，延迟 10 秒量级可接受，稳定优先。
- **低延迟直播（带货、答题、弱互动）**：LL-HLS 或 LL-DASH，段长 1–2 秒 + 部分段/分块，延迟 2–5 秒，需全链路支持。
- **强互动（连麦、拍卖）**：不选这两者，选 WebRTC（见下一篇）。

## 7. 应用与限制

- **典型应用**：点播平台的多清晰度播放、赛事与发布会直播、OTT 机顶盒、移动端视频 App；几乎所有大规模视频分发背后都是这两者之一。
- **限制**：都不是“实时”协议——普通模式延迟以秒计；都依赖播放器的 ABR 算法，算法各家不同，同一网络下不同播放器表现可能差很多；直播的清单轮询与分片请求在超大规模并发下对 CDN 回源与源站是真实压力，需预热与分层缓存。
- **与上一篇的关系**：上一篇讲“链路与协议定位”，本篇讲“清单与分片机制”；上一篇的延迟账是全链路的，本篇只拆解其中“打包 + 缓存”这两笔。

## 8. 常见误解

- **“HLS 就是慢，DASH 就是快”**：错。两者延迟量级相同，都由段长与缓冲决定；快慢看配置（段长、LL 模式、全链路配合），不看协议名。
- **“段长设 1 秒就能低延迟”**：不完全对。段长只是其一，关键帧对齐、播放器缓冲、CDN 是否支持分块传输缺一不可；只改段长，播放器可能仍按 3 段缓冲起播。
- **“ABR 能解决一切卡顿”**：不能。ABR 只能在“已有档位”里选，带宽跌破最低档照样卡；而且切换要等段边界，带宽骤降时已有延迟。
- **“有了 CMAF 就不用两套协议了”**：错。CMAF 统一的是分片，清单（.m3u8 与 .mpd）仍然各有一套，播放器逻辑也不通用。

## 9. 可核验示例：同一段测试信号，打包成 HLS 与 DASH

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。只在本地把测试信号打包成清单与分片文件，**没有起流媒体服务器、没有推流、没有真实观众**，分发与播放环节未验证。测试信号为 ffmpeg 内置 testsrc2 测试图与 440 Hz 正弦波（合成信号，非真实直播画面）。

```bash
# HLS：同一内容出 720p 与 480p 两档，段长 2 秒，关键帧间隔 60 帧（30fps 下即 2 秒）
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=6 \
  -f lavfi -i sine=frequency=440:duration=6 \
  -filter_complex "[0:v]split=2[v720][v480];[v480]scale=854:480[v480s]" \
  -map "[v720]" -map "[v480s]" -map 1:a -map 1:a \
  -c:v libx264 -preset veryfast -crf 23 -g 60 -c:a aac -b:a 128k \
  -var_stream_map "v:0,a:0 v:1,a:1" -master_pl_name master.m3u8 \
  -f hls -hls_time 2 -hls_list_size 0 -hls_segment_filename "v%v/seg%d.ts" "v%v/index.m3u8"
# DASH：同一段信号，段长 2 秒，生成 MPD 清单
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=6 \
  -f lavfi -i sine=frequency=440:duration=6 \
  -c:v libx264 -preset veryfast -crf 23 -g 60 -c:a aac -b:a 128k \
  -f dash -seg_duration 2 -use_template 1 -use_timeline 1 manifest.mpd
```

本文写作时实际运行结果：

```
master.m3u8（主清单）：
  #EXT-X-STREAM-INF:BANDWIDTH=2994464,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
  v0/index.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=917439,RESOLUTION=854x480,CODECS="avc1.64001f,mp4a.40.2"
  v1/index.m3u8
v0/index.m3u8：TARGETDURATION 为 2，3 个 2 秒分片（seg0.ts 729,816 字节、seg1.ts 748,616 字节、seg2.ts 725,116 字节）
manifest.mpd：视频 Representation（bandwidth=2710757，1280x720）与音频 Representation（bandwidth=128000）各一，
  SegmentTemplate 为 chunk-stream$RepresentationID$-$Number%05d$.m4s，含初始化段 init-stream0.m4s / init-stream1.m4s，
  共生成 3 个视频分片与 4 个音频分片（含尾段）
```

教训：主清单里的 BANDWIDTH 是播放器选档的依据，是“峰值带宽”而非平均码率；两档的 BANDWIDTH（约 3.0 Mbps 与 0.92 Mbps）差出 3 倍多，ABR 才有切换的意义。档位之间码率拉不开，切换就形同虚设。
