# 跨平台播放器架构

## 1. 本章目标

读完本篇能理解：一个播放器内部由哪几层组成、音画同步靠什么时钟、以及面对 FFmpeg、GStreamer、ExoPlayer、AVPlayer 这些方案时，按什么维度选型。

## 2. 背景与问题

同一个播放需求，落在不同平台上会变成不同的工程：Android、iOS、Windows、macOS、Web 各有自己的系统播放器与解码能力，编码格式又不止一种。直接“每个平台各写一套播放器”，结果是多份重复代码、多份 bug；直接“只用一套系统播放器”，结果是换个平台就得重写。跨平台播放器架构要回答的是：**哪些层可以共用、哪些层必须按平台分开、以及在必须分开的地方留什么接口**。

本篇讲架构与选型，不重复编码原理（见本组 01 篇）、流媒体协议（见本组 02 篇）与 Web 端播放细节（见本组 12 篇）。

## 3. 总体架构

一个播放器的通用分层（各方案叫法不同，职责大体一致）：

```
数据源 / 网络层        取数据：本地文件、HTTP(S)、HLS/DASH 分段、直播流
        ↓  字节流
解封装（Demuxer）      拆容器：从 MP4/MKV/WebM/TS 等容器中分离音轨、视频轨、字幕与时间戳
        ↓  编码帧（Packet）
解码（Decoder）        解码：把压缩帧还原为 PCM 音频采样与 YUV/RGB 视频帧
        ↓  原始帧（Frame）
渲染（Renderer）       输出：音频送声卡、视频画到屏幕（见 4.3 节）
        ↑  同步时钟（见 4.4 节）决定“这一帧何时出”
播放控制               播放 / 暂停 / 拖进度 / 倍速 / 选轨 / 清晰度切换
```

分层的好处是替换成本低：换一种容器格式只换解封装，换一种编码只换解码器，换一个平台只换渲染，同步与控制逻辑可以共用。分层的代价是层间要传时间戳与缓冲状态，接口定不好，音画同步与拖进度就会先出问题。

## 4. 工作机制

### 4.1 解封装：从“盒子”里拆出音视频

解封装的输入是容器文件或流（如 MP4、MKV、WebM、MPEG-TS），输出是按时间戳排好的音频包与视频包。它的工作是读容器头（有哪些轨、各轨的编码格式、时长、索引），再按顺序拆包；它**不解码**，只负责“拆出来、排好序、贴上时间戳”。

拖进度（seek）主要靠解封装：播放器按目标时间查索引，找到最近的关键帧（I 帧，见 01 篇），从那里开始拆包、解码、丢弃关键帧之前的非关键帧，直到追到目标时间点。索引缺失或关键帧间隔过大时，seek 会变慢或不准——这是“拖进度卡”最常见的底层原因之一，不一定是解码慢。

### 4.2 解码：软解与硬解的分工

解码把压缩帧还原为可播放的原始帧。实现上有两条路线：

- **软解（软件解码）**：用 CPU 跑解码算法，优点是格式覆盖广、行为一致、不依赖设备；缺点是耗电、发热，高分辨率与高帧率时 CPU 可能扛不住，移动端尤其明显。
- **硬解（硬件解码）**：把解码交给芯片里的专用单元（GPU / 视频解码单元），优点是省电、低发热、高分辨率也流畅；缺点是支持的编码格式由芯片与系统决定，老设备可能没有新编码（如 AV1）的硬解，行为也随厂商实现而有差异。

实际产品通常是“硬解优先、软解兜底”：先试硬件解码，失败或不支持再回落到软件解码。选型时要先看目标用户设备的硬解覆盖，而不是只看解码器支持列表上的名字。

### 4.3 渲染：声音与画面各走各的出口

解码出的帧要送到两个不同的出口：

- **音频渲染**：PCM 采样送声卡（或系统音频接口）。音频渲染相对统一，关键是不要断流：音频缓冲一旦欠载就会出现爆音与卡顿。
- **视频渲染**：YUV / RGB 帧画到屏幕。常见出口随平台而变：Android 上是 Surface / SurfaceTexture、OpenGL ES / Vulkan，iOS 上是 Core Video / Metal，Windows 上是 Direct3D，跨平台方案常用 OpenGL / Vulkan 做统一渲染层。视频渲染还要处理色彩空间转换、缩放与旋转，细节见本组 03 篇的色彩空间与几何运算。

渲染层是平台差异最集中的地方，也是跨平台方案“共用逻辑、分离渲染”的分界线：解封装与解码可以跨平台共用，渲染一般要按平台写适配。

### 4.4 同步时钟：音画对齐靠什么

音频与视频是两条独立的轨，解码速度也不同，靠什么保证“嘴型与声音对上”？靠**时间戳与一个主时钟**。

- 每一帧都带时间戳（PTS，显示时间戳），表示它应该在什么时刻被呈现。
- 播放器维护一个播放时钟，常用做法是**以音频时钟为主时钟**：音频是连续输出的，时钟最稳；视频帧按自己的 PTS 与音频时钟比较，早了就等、晚了就丢或跳帧，把画面追到与声音一致。
- 时钟漂移是常态：音频采样率标称 48 kHz 的设备实际可能是 47,999 Hz，长期播放会累积出毫秒级偏差；同步逻辑要持续做小幅修正，而不是只在开头对齐一次。

同步出问题时的现象有迹可循：声音比画面快或慢且差值固定，多半是时间戳或起始偏移算错；差值越播越大，多半是时钟漂移没修正；画面一卡一卡但声音连续，多半是视频解码或渲染跟不上，在丢帧追赶。

### 4.5 缓冲与播放控制

播放器内部一般有两级缓冲：解封装后的包缓冲（应对网络抖动）与解码后的帧缓冲（应对解码波动）。缓冲策略与 02 篇的播放器缓冲是同一回事，只是这里的视角在播放器内部：缓冲越深越抗抖动、起播与 seek 越慢；缓冲越浅起播越快、越容易卡。直播与点播的取舍不同，见 02 篇第 5 节。

播放控制（播放、暂停、拖进度、倍速、选轨、清晰度切换）本质上是改时钟与改数据源：暂停是停时钟、保缓冲；拖进度是清空缓冲、按新位置重新解封装与解码；倍速是按倍率走时钟并相应调整同步策略；清晰度切换是在分段边界换数据源（HLS / DASH 的 ABR，见 02 篇）。

## 5. 关键设计取舍

- **共用换适配成本**：解封装与解码共用一套代码省维护量，但渲染与系统接口仍要按平台适配；想“一份代码处处运行”而不留平台适配层，往往会在渲染与硬解处付出更大代价。
- **硬解换覆盖**：硬解省电流畅但格式受限，软解通用但耗电；“硬解优先、软解兜底”是多数产品的折中，不是二选一。
- **延迟换稳定**：缓冲与前瞻能省码率、抗抖动，但抬高延迟；直播与互动场景要砍缓冲与 B 帧（见 01 篇），点播则可以放宽。
- **功能换体积与合规**：功能越多（格式、协议、DRM、滤镜），体积与合规负担越大；FFmpeg 的许可证问题（见 6.1 节）就是功能与合规之间最典型的一笔账。

## 6. 分类与变体：常见方案对比

### 6.1 方案一览

| 方案 | 归属与定位 | 覆盖范围 | 要点 |
|---|---|---|---|
| FFmpeg + 原生渲染 | 开源多媒体框架（libavformat 解封装、libavcodec 解码等）；播放器常以它为核心，自写或接平台渲染 | 全平台（Android、iOS、桌面、嵌入式） | 格式与协议覆盖最广；渲染、同步、控制要自己搭或接第三方播放器壳；许可证需注意：FFmpeg 按配置分 LGPL 与 GPL 部分，商用前须按实际配置核对，以官方发布为准 |
| GStreamer | 开源多媒体框架，管道（pipeline）+ 插件模型 | 全平台（Linux、Windows、macOS、Android、iOS） | 搭管道像拼积木，插件可插拔；适合需要自定义处理链（如转码、滤镜、分析）的场景；学习曲线与体积是代价 |
| ExoPlayer（现为 AndroidX Media3 的一部分） | Google 的 Android 应用级播放器（Java / Kotlin） | Android | 与 Android 系统集成好，支持 DASH / HLS 自适应流与常见 DRM；只覆盖 Android，跨平台要另配方案 |
| AVPlayer | Apple 的系统播放器（AVFoundation） | iOS、macOS、tvOS | 与苹果系统集成最好，支持 HLS 与 FairPlay；只覆盖苹果平台，格式与功能受系统限制 |
| 系统播放器（MediaPlayer / Media Foundation 等） | 各平台自带 | 各自平台 | 接入最快，但功能与格式最受限，跨平台行为最不一致 |
| VLC / mpv（libVLC / libmpv） | 基于 FFmpeg 等的开源播放器 / 播放库 | 全平台 | 开箱即用的完整播放器，适合快速落地；定制深度与体积需权衡；以各项目官方发布为准 |

注：上表“归属”均为公开事实；各方案的最新版本、维护状态与许可证细节以官方发布为准（待核实），见文末未完成项。

### 6.2 关键差异展开

**差异一：谁负责解封装与解码。** FFmpeg 与 GStreamer 自己带了解封装与解码，跨平台行为一致，代价是自己搭渲染与同步；ExoPlayer 与 AVPlayer 依赖系统解码能力，接入快、省电，但格式支持随系统而变，同一份代码在新旧设备上行为可能不同。

**差异二：谁负责自适应流与 DRM。** ExoPlayer 对 DASH / HLS 与 Widevine 的支持是内置卖点之一；AVPlayer 对 HLS 与 FairPlay 同理；FFmpeg 路线则要自己接自适应逻辑（或接 hls.js / dash.js 的思路，见 12 篇）与 EME / DRM 流程，灵活但工作量大。

**差异三：跨平台的真实含义。** “跨平台”有两种意思：一是同一套核心代码编到多个平台（FFmpeg、GStreamer、VLC / mpv 的路线），二是每个平台用各自的系统播放器、只共用上层业务逻辑（ExoPlayer + AVPlayer + Web MSE 的路线）。前者省核心维护量、费渲染适配；后者省渲染适配、费多份播放逻辑。没有哪一种在所有场景下都更省。

## 7. 选型要点

按场景给建议；没有把握的场景不给建议，写“待核实”：

- **如果目标是全平台、格式要全、要自己控同步与滤镜**：优先考虑 FFmpeg + 原生渲染，或 GStreamer；先核对许可证配置与包体积，再动手。
- **如果目标只是 Android 应用内播视频**：优先考虑 ExoPlayer（AndroidX Media3）；系统集成与自适应流是现成的，跨平台不是当前需求时不必为它付费。
- **如果目标只是苹果平台**：优先考虑 AVPlayer；FairPlay 与 HLS 的集成是系统级的，自己搭 FFmpeg 反而多余。
- **如果要快速验证一个播放想法**：优先考虑 VLC / mpv 这类完整播放器或其库，先跑通再决定是否自研。
- **如果场景是 Web 端**：不走本篇的原生路线，走 12 篇的 `<video>` + MSE / EME + hls.js / dash.js 路线。
- **选型前必核对的三件事**：目标用户设备的硬解覆盖（哪些编码真能硬解）、DRM 覆盖（目标设备支不支持所需的 CDM，见 12 篇 4.3 节）、许可证与合规（FFmpeg / GStreamer 的配置与授权，以官方发布为准）。

## 8. 应用与限制

- **典型应用**：跨平台视频 App、桌面播放器、机顶盒与嵌入式播放、直播观看端、需要自定义滤镜与分析的播放场景。
- **限制**：本篇只讲架构与选型，不涉及具体方案的接入代码与版本；各方案的 API 与行为随版本而变，动手前以官方文档为准；音画同步、硬解回落、DRM 等细节在真实设备上仍需实测，本文未做真机验证。

## 9. 可核验示例：分层自查清单（无代码）

> 本节不是可运行示例，而是一份接手或评审播放器方案时的自查清单；以下条目均未在真机上实测，仅作设计核对用。

- 解封装：支持的容器有哪些？seek 靠索引还是靠逐包扫描？关键帧间隔多大？
- 解码：硬解覆盖哪些编码？硬解失败时是否回落软解？回落时用户是否可感知？
- 渲染：视频走哪个出口（Surface / Metal / Direct3D / OpenGL）？色彩空间转换在哪一层做？
- 同步：主时钟是音频还是系统时钟？漂移如何修正？丢帧与重复帧的策略是什么？
- 控制：暂停、拖进度、倍速时缓冲如何处理？清晰度切换在哪个边界发生？
- 合规：FFmpeg / GStreamer 的配置对应哪种许可证？DRM 方案覆盖哪些设备？
