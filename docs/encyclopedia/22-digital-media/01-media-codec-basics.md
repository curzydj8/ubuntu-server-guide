# 音视频编码基础

## 1. 本章目标

读完本篇能理解：原始音视频为什么必须编码、编码器在“扔掉什么、保留什么”，以及面对 H.264、H.265、VP9、AV1、AAC、Opus 这些名字时按什么取舍。

## 2. 背景与问题

不编码的原始音视频大得无法传输和存储。算一笔账：

- 未压缩音频（CD 规格）：采样率 44,100 Hz × 量化 16 位 × 2 声道 = 1,411,200 bps，约 1.41 Mbps，一分钟约 10.6 MB。
- 未压缩视频（1080p30、每像素 3 字节）：1920 × 1080 × 3 × 30 ≈ 1.87 Gbps，一分钟约 14 GB。

没有编码，就没有流媒体、没有视频通话、手机里也存不下几部电影。编码要解决的核心矛盾是：**在人眼和人耳察觉不到（或可接受）的前提下，把数据量压到原来的几百分之一**。

## 3. 总体架构

编码器的工作可以画成一条流水线：

```
原始信号 → 采样/分帧 → 变换与预测 → 量化（有损的关键一步） → 熵编码 → 码流
                ↑                                              ↓
            颜色转换（视频）                              封装进容器（MP4/MKV/WebM）
```

解码器做反向操作。注意两个容易混的概念：

- **编码格式（codec）**：H.264、AAC 这种压缩算法，决定“怎么压”。
- **封装格式（container）**：MP4、MKV、WebM 这种“盒子”，决定“音视频、字幕、元数据怎么装在一起”。
- 说“MP4 编码”是错的：MP4 是盒子，盒子里装的视频可能是 H.264，也可能是 H.265 或 AV1。

## 4. 工作机制

### 4.1 音频：采样与量化

**采样**：每秒对声波取值多少次，就是采样率。奈奎斯特–香农采样定理说：要无失真地还原一个最高频率为 f 的信号，采样率必须大于 2f。人耳上限约 20 kHz，所以 CD 用 44.1 kHz、视频常用 48 kHz，都留有余量。采样率不够会怎样？高频信号会“折叠”成低频杂音，这叫混叠，采样之后无法修复，只能事前用低通滤波挡住超限频率。

**量化**：每个采样值用多少位二进制表示，就是量化位数。16 位能表示 65,536 级，24 位约 1,677 万级。量化会引入误差（量化噪声）；对正弦信号，信噪比约等于 6.02N + 1.76 dB（N 为位数），16 位约 98 dB，24 位约 146 dB。位数越多，底噪越低，但码率也越大。

**PCM 与压缩**：采样 + 量化得到的原始数据叫 PCM，完全不压缩。音频编码器在此基础上做两件事：一是利用人耳掩蔽效应（响亮声音附近的微弱声音听不见，可以少给码率甚至扔掉），二是利用信号自身的重复规律。无损编码（FLAC）只做后者，可完整还原；有损编码（AAC、MP3、Opus）两者都做，换更高的压缩比。

### 4.2 视频：颜色、帧间预测与变换

视频编码的三大省码率手段：

**第一，颜色转换与色度抽样**。人眼对亮度细节敏感、对色彩细节迟钝。视频先把 RGB 转成亮度 Y 与两个色度分量 Cb、Cr（统称 YCbCr），然后对色度降分辨率：最常见的 4:2:0 表示每 4 个像素共用一对色度值，色度数据量直接砍到一半，观感损失很小。这是所有主流视频编码的起点。

**第二，帧间预测**。视频由一组图像（GOP，一组图片）组成：

- I 帧（关键帧）：完整图像，不依赖其他帧，可独立解码，也是 seek（拖进度条）和切片的落点。
- P 帧：只记录相对前面帧的变化（运动矢量 + 残差）。
- B 帧：可参考前后两帧，压缩率最高，但编解码延迟较大。

运动估计就是“这块画面相对上一帧平移了多少”，编码器把“平移量 + 画面差值”写进码流，而不是重传整块画面。画面变化越小，省得越多；镜头一切换，省的效果就没了，码率会瞬间冲高。

**第三，变换、量化与熵编码**。残差图像先做 DCT（离散余弦变换）一类变换，把能量集中到少数系数上；然后量化：高频系数（细节）被粗暴地舍入甚至置零——这是视频有损压缩最主要的信息丢失点，量化步长越大，画面越糊、块效应越明显；最后熵编码（CABAC、CAVLC 等）给高频符号分配短码，进一步压体积。

### 4.3 码率控制：CRF、CBR、VBR

- **CRF（恒定质量因子）**：指定一个质量档（如 x264 的 CRF 23），编码器按画面复杂度自动分配码率。适合本地压制、点播转码，是最常用的“画质优先”模式。
- **CBR（恒定码率）**：码率被钉死，适合带宽固定的直播推流，代价是复杂画面糊、简单画面浪费。
- **VBR（可变码率）**：在平均码率约束下按需分配，介于两者之间。

## 5. 关键设计取舍

- **质量换体积**：量化步长是总开关。步长小、体积大、画质好；步长大、体积小、块效应和涂抹感出现。没有“又小又无损”的有损编码。
- **压缩率换算力**：更新的编码（AV1、H.265）压缩率更高，但编码耗时和解码算力也更高；老设备硬解跟不上时，再省码率也没用。
- **延迟换压缩率**：B 帧、前瞻分析能省码率，但要等未来帧到了才能编码，直播场景宁可少用 B 帧、缩短 GOP。
- **兼容性换先进性**：H.264 几乎所有设备都硬解；H.265、AV1 覆盖面逐年扩大，但仍有老设备不支持，选型时必须看目标观众的设备分布。

## 6. 分类与变体

### 6.1 视频编码定位

| 编码 | 推出方与时间 | 定位与取舍 |
|---|---|---|
| H.264 / AVC | ITU-T 与 MPEG，2003 年 | 兼容性之王，几乎全设备硬解；压缩率是后辈的基准线 |
| H.265 / HEVC | ITU-T 与 MPEG，2013 年 | 同等主观质量下码率约比 H.264 省一半（因内容与编码器而异）；专利授权复杂，浏览器支持不齐 |
| VP9 | Google，2013 年 | 开放免专利费路线，YouTube 曾主力；压缩率与 H.265 相当，硬件覆盖弱于 H.264 |
| AV1 | AOMedia，2018 年 | 开放免专利费，压缩率优于 H.265；编码最吃算力，硬件解码正在普及，适合点播大厂 |
| AV2 等 | 在研 | 尚未大规模商用，选型时不列入 |

### 6.2 音频编码定位

| 编码 | 定位与取舍 |
|---|---|
| AAC | 视频的默认配对音频（MP4 标配），通用性最好 |
| Opus | 互动场景最优：低延迟、可变码率、语音与音乐都强，WebRTC 的标配 |
| MP3 | 历史最广的兼容性，压缩效率已被 AAC、Opus 超过，新项目不优先选 |
| FLAC | 无损，体积约为 PCM 的一半，适合归档，不适合流媒体 |

## 7. 应用与限制

- **点播转码**：CRF 模式 + H.264/AV1 多码率 ladder（见下一篇流媒体），是当前最稳妥的组合。
- **直播推流**：CBR + H.264 + 短 GOP，优先保证不断流而不是极致画质。
- **实时通话**：Opus + VP8/VP9/AV1 实时档，延迟优先，接受画质波动。
- **归档**：FLAC（音频）与无损或近无损视频档，绝不用有损编码反复转码——每次有损转码都会叠加损失，所谓“代际损失”。
- **限制**：编码不能创造原信号没有的信息；低码率下的块效应、振铃、拖影是量化与预测的固有代价；HDR、10-bit、高帧率会显著抬高算力与码率，本文示例未覆盖。

## 8. 常见误解

- **“MP4 是编码格式”**：错，MP4 是封装；H.264、H.265、AV1 才是编码。
- **“码率越高画质一定越好”**：错，码率要和编码器、分辨率、内容复杂度一起看；用老编码高码率可能不如新编码中码率。
- **“无损压缩就是没压缩”**：错，FLAC、无损视频编码同样压缩体积，只是解码后与原始逐位一致。
- **“转码能提升画质”**：不能，转码只会保持或降低画质，绝不会凭空变清晰。

## 9. 可核验示例：同一段测试视频，CRF 23 与 CRF 28 的体积差

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。测试信号为 ffmpeg 内置的 testsrc2 测试图与 440 Hz 正弦波（合成信号，非真实拍摄与录音），仅用于验证编码器行为，画质结论不直接外推到真实画面。

```bash
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=5 \
  -f lavfi -i sine=frequency=440:duration=5 \
  -c:v libx264 -preset veryfast -crf 23 -c:a aac -b:a 128k -shortest demo-crf23.mp4
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=5 \
  -f lavfi -i sine=frequency=440:duration=5 \
  -c:v libx264 -preset veryfast -crf 28 -c:a aac -b:a 128k -shortest demo-crf28.mp4
ffprobe -v error -show_entries stream=codec_name,width,height,bit_rate \
  -show_entries format=duration,size,bit_rate -of default=noprint_wrappers=1 demo-crf23.mp4
```

本文写作时实际运行结果：

```
CRF 23：文件 1,760,665 字节，视频流 h264 1280x720 30fps，码率 2,680,300 bps；
        音频流 aac，码率 125,487 bps；总码率 2,817,064 bps，时长 5.000000 秒
CRF 28：文件 930,474 字节（约比 CRF 23 小 47%）
```

结论：CRF 每加 5 档，体积大约减半（对测试图而言；真实画面因内容而异），代价是量化更粗、细节损失更多。压制时先定 CRF 再看体积，不要先定体积再反推画质。
