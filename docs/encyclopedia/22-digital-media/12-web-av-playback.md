# Web 音视频播放开发

## 1. 本章目标

读完本篇能理解：在浏览器里播一段音视频，`<video>` / `<audio>` 标签、MSE、EME 各负责哪一段，以及 hls.js / dash.js 这类库为什么存在；遇到播不出来、播不出声、跨域报错时，先查哪一环。

## 2. 背景与问题

Web 播放的起点很简单：一个标签、一个地址，就能出声出画面。但真实产品很快会遇到三类超出标签能力的问题：

- **源不是单个文件**：直播和点播要按网络状况切清晰度、一段一段地取数据，标签本身不会做自适应切换。
- **内容要受保护**：付费、版权内容需要加密与授权，标签本身不管密钥与许可证。
- **浏览器各有限制**：自动播放、跨域、格式支持在不同浏览器里不一样，同一段代码换个浏览器就可能静默失败。

本篇只讲浏览器侧的播放机制与开发问题。编码原理见本组 01 篇，流媒体协议与分发见本组 02 篇，跨平台播放器的通用架构见本组 13 篇。

## 3. 总体架构

浏览器播放一条链路的角色分工：

```
媒体文件 / 流分段（服务器、CDN）
        ↓  HTTP(S) 取数据
播放器逻辑（JS 库，如 hls.js / dash.js；或浏览器原生）
        ↓  喂数据 / 解密
浏览器媒体管线（MSE / EME → 解码 → 渲染）
        ↓
<video> / <audio> 元素 → 画面与声音
```

关键分界：`<video>` / `<audio>` 是“出画面、出声音”的元素；MSE 是“让 JavaScript 往元素里喂数据”的接口；EME 是“让 JavaScript 接入受保护内容解密”的接口；hls.js / dash.js 是“用 MSE 把 HLS / DASH 流喂给元素”的 JavaScript 库。它们各管一段，不要互相替代。

## 4. 工作机制

### 4.1 `<video>` 与 `<audio>`：标签能做与不能做的事

最简单的播放只需要一个标签和一个地址：

```html
<!-- 示例未实测：仅示意标签的基本用法 -->
<video src="demo.mp4" controls preload="metadata" playsinline></video>
<audio src="demo.mp3" controls></audio>
```

常用属性的含义：

- `controls`：显示浏览器自带的播放控件；不加则画面无控件，需自己写界面。
- `preload`：`none` / `metadata` / `auto`，提示浏览器预加载多少；只是提示，浏览器可根据策略与网络自行决定，最终行为以浏览器实现为准。
- `autoplay`：请求自动播放，但是否真的播出受自动播放策略约束（见 4.4 节），不是写了就一定播。
- `muted`：静音播放；与自动播放策略直接相关，静音的自动播放通常被允许。
- `playsinline`：提示移动端浏览器在页面内联播放，而不是强制全屏；主要影响 iOS Safari 的行为。
- `loop`、`poster`（视频封面图）、`crossorigin`（跨域取数据时的凭证模式，见 4.5 节）。

标签本身能做的事是有限的：它能播一个浏览器原生支持的媒体文件，能响应播放、暂停、拖进度（`currentTime`）、调音量与倍速。但它**不会**做这些事：解析 HLS / DASH 索引并按带宽切换清晰度、处理加密内容的许可证流程、自己决定“带宽掉了就降档”。这些要靠 MSE / EME 或播放器库来补。

播放状态靠事件观察，常见事件有 `loadedmetadata`（元数据就绪，可读时长与尺寸）、`canplay`（已有足够数据可开始播）、`playing` / `pause` / `ended`、`error`（失败时先查 `video.error` 的错误码，再查网络与格式）、`timeupdate`（进度变化）。排障时先看事件走到哪一步，再定位是网络、格式还是策略问题。

### 4.2 MSE：JavaScript 往播放器里喂数据

MSE（Media Source Extensions）是 W3C 的浏览器接口，它的核心思想是：**把“取数据”和“解码播放”分开**。没有 MSE 时，`<video>` 的 `src` 直接指向一个文件，浏览器自己取、自己解；有了 MSE，JavaScript 可以自己取数据（分段下载、按带宽选清晰度），再一段一段喂给浏览器解码。

工作流程大致是：

```js
// 示例未实测：仅示意 MSE 的基本接线，不含错误处理与缓冲管理
const mediaSource = new MediaSource();
video.src = URL.createObjectURL(mediaSource);
mediaSource.addEventListener('sourceopen', () => {
  const sourceBuffer = mediaSource.addSourceBuffer('video/mp4; codecs="avc1.42E01E, mp4a.40.2"');
  // 取回一段媒体数据后喂给 SourceBuffer
  sourceBuffer.appendBuffer(segmentData);
});
```

需要理解的三个点：

- `MediaSource` 对象挂到 `video.src` 上后，浏览器不再自己拉文件，等 JavaScript 喂数据。
- `SourceBuffer` 对应一路音轨或视频轨，`appendBuffer` 喂进去的是已经封装好的媒体分段（例如 fMP4 片段），不是原始编码帧；解封装与自适应逻辑仍由 JavaScript 播放器库负责。
- 浏览器只接受它能解的编码组合，`addSourceBuffer` 的 MIME 类型字符串（如上例的 H.264 + AAC）若不被支持会直接抛错；写代码前应先用 `MediaSource.isTypeSupported()` 探查，而不是假定所有组合都可用。

MSE 不负责网络协议本身：取索引、选清晰度、重试、缓冲策略，都是调用方的活。MSE 只解决“喂数据”这一个接口问题。

### 4.3 EME：受保护内容的解密入口

EME（Encrypted Media Extensions）同样是 W3C 的浏览器接口，解决的是另一件事：**加密内容如何在浏览器里合法解密播放**。它本身不做加解密算法，不存密钥，不决定谁有权限看；它只提供一套标准接线，让网页 JavaScript、浏览器与内容解密模块（CDM，Content Decryption Module）协作：

```
加密媒体 → 浏览器发现需要密钥 → JS 向许可证服务器请求许可证
        → CDM 用许可证解密 → 解码渲染（解密后的内容一般不经 JS 之手）
```

常见的 CDM 与归属（公开事实）：Widevine（Google）、FairPlay（Apple）、PlayReady（Microsoft）。一部设备能播哪种受保护内容，取决于浏览器与操作系统内置了哪种 CDM，网页代码换不了这一点；同一套 DRM 方案在不同浏览器、不同设备上的覆盖面不同，选型时要按目标用户设备逐一核对，以各厂商官方文档为准。

EME 的关键边界：它只管“解密播放”这一段，不管账号、订阅、鉴权与计费——那些是业务系统在发许可证之前要做的事。另外，EME 与 MSE 常常一起出现（自适应流 + 加密），但两者是独立接口：可以只有 MSE（明文自适应流），也可以只有 EME（单个加密文件），也可以两者叠加。

### 4.4 hls.js 与 dash.js 的定位

HLS 与 DASH 的协议细节见本组 02 篇；这里只讲它们在浏览器里的落地问题：浏览器原生支持并不统一。公开可核实的一般情况是：Safari 对 HLS 有原生支持（可直接把 `.m3u8` 地址交给 `<video>`），而多数桌面与 Android 浏览器不原生支持 HLS，DASH 则普遍没有浏览器原生支持。于是需要 JavaScript 库把协议“翻译”成 MSE 能喂的数据：

| 库 | 定位 |
|---|---|
| hls.js | 开源 JavaScript 库，把 HLS 流（索引 + 分段）解析后，经 MSE 喂给 `<video>`；用于浏览器不原生支持 HLS 的场景；在原生支持 HLS 的浏览器（如 Safari）里通常直接用原生播放，不必经它 |
| dash.js | MPEG-DASH 的参考播放器（JavaScript 实现），把 DASH 流解析后，经 MSE 喂给 `<video>`；DASH 本身没有浏览器原生播放入口，所以 Web 端播 DASH 一般都要靠这类库 |
| Shaka Player 等 | 同类思路的其他开源播放器，有的还集成 EME / DRM 流程；选型时按协议、DRM、维护状态逐项核对 |

理解定位就能避免两个误区：一是“用了 hls.js 就不用管浏览器格式支持”——错，它底层仍依赖 MSE 与浏览器的解码能力，编码组合不支持一样播不出；二是“所有浏览器都要接 hls.js”——错，Safari 原生播 HLS 时多接一层反而多余，常见做法是先检测原生支持，不支持再 fallback 到库。

### 4.5 常见问题一：自动播放策略

主流浏览器为防止网页一打开就出声，普遍实行自动播放限制，一般规律是：

- **静音自动播放通常被允许**：`autoplay muted` 的视频多数浏览器会放行。
- **有声自动播放通常被阻止**：没有用户与页面的交互（点击、按键等）时，带声音的自动播放会被拦截，表现为画面停在第一帧或 `play()` 返回被拒绝的 Promise。
- **交互之后放行**：用户点过页面后，再调用 `play()` 一般可出声；有的浏览器还会按用户与该站点的历史互动（媒体参与度）放宽限制，具体规则随浏览器版本而变，以各浏览器官方文档为准。

开发上的标准处理是：先尝试 `video.play()`，捕获被拒绝的 Promise 后降级为静音播放或显示一个“点击播放”按钮，而不是假定 `autoplay` 属性一定生效。`play()` 返回 Promise、失败会 reject，这一点写代码时必须处理，否则静默失败很难排障。

```js
// 示例未实测：仅示意自动播放被拒时的降级思路
video.play().catch(() => {
  video.muted = true;      // 降级为静音播放，或改为显示播放按钮
  return video.play();
});
```

### 4.6 常见问题二：跨域（CORS）

媒体文件与网页不在同源时，浏览器按 CORS 规则取数据；出问题时通常表现为：能直接打开文件地址，但放到 `<video>` 里就报错，或 MSE 取分段失败。排障要点：

- 简单播放（`src` 直指文件）时跨域限制较松；一旦要用到 MSE 取分段、Canvas 抓取视频帧、或 `crossorigin="anonymous"` / `"use-credentials"`，服务器必须返回对应的 `Access-Control-Allow-Origin` 等响应头，否则浏览器会拦截。
- `crossorigin` 属性要与服务器响应头匹配：写了 `crossorigin` 却拿不到合法的 CORS 头，播放会直接失败；反过来，不写 `crossorigin` 时某些高级用法（如把视频画到 Canvas 再导出）会被“污染”而拒绝。
- 结论：跨域问题先查服务器响应头与浏览器控制台的 CORS 报错，不要先怀疑播放器代码；分段、索引、许可证、字幕等多个地址可能分属不同域名，要逐个核对。

### 4.7 常见问题三：格式兼容

浏览器能播什么格式，取决于浏览器与操作系统内置的解码器，不是 HTML 标准规定的。大致的公开情况（细节以各浏览器官方支持表与 MDN 文档为准，见文末未完成项）：

| 组合 | 兼容性概况 |
|---|---|
| MP4（H.264 视频 + AAC 音频） | 覆盖面最广，是 Web 点播的默认安全组合 |
| WebM（VP8 / VP9 视频 + Vorbis / Opus 音频） | Chrome、Firefox 等支持较好，Safari 的支持随版本而变，需核对 |
| MP4（H.265 / HEVC 视频） | 部分浏览器与系统支持，覆盖面窄于 H.264，不宜作唯一格式 |
| AV1 | 新一代开放编码，硬件与浏览器支持正在普及，是否作主力格式要看目标用户设备分布 |

选型原则与本组 01 篇一致：**兼容性优先于先进性**。面向全网用户的点播，先保证 H.264 + AAC 人人能播，再按需提供 VP9 / AV1 等更省码率的版本；只提供一种新格式，等于主动放弃一部分观众。提供多格式时靠 `<source>` 元素按顺序列出，浏览器会取第一个能播的：

```html
<!-- 示例未实测：仅示意多格式 fallback 的写法 -->
<video controls>
  <source src="demo.mp4" type="video/mp4">
  <source src="demo.webm" type="video/webm">
  您的浏览器不支持视频播放。
</video>
```

## 5. 关键设计取舍

- **原生标签换可控性**：直接用 `<video src>` 最简单、最省代码，但换不来自适应切换、加密与精细缓冲控制；要这些能力就得接 MSE / 播放器库，代价是代码量与排障面都变大。
- **清晰度换流畅**：自适应码率（ABR，见 02 篇）先保不断流再保高清；缓冲策略同理，缓冲越深越抗抖动、起播越慢，互动场景要反过来取。
- **静音换自动播放**：想一打开就动起来，只能接受先静音；想一打开就有声，必须等用户交互。产品设计要在这两者之间选，不能两头都要。
- **新格式换覆盖面**：VP9 / AV1 省码率，但老设备与部分浏览器播不了；H.264 费码率，但几乎人人能播。面向全网时先保覆盖，再谈节省。

## 6. 分类与变体

按播放器实现方式分三类：

- **原生标签直播**：`<video src="文件">`，适合单个文件、无自适应、无加密的简单场景。
- **MSE 播放器库**：hls.js / dash.js / Shaka Player 等，适合 HLS / DASH 自适应流、需精细控制缓冲与切换的场景。
- **原生 + 库混合**：检测到 Safari 原生支持 HLS 就走原生，否则走 hls.js；这是生产环境最常见的做法，兼顾兼容与维护成本。

按内容是否加密分两类：明文流（只需 MSE 或原生标签）与受保护流（MSE + EME + 许可证服务器，见 4.3 节）。

## 7. 应用与限制

- **典型应用**：点播站、直播观看页、在线课堂、短视频信息流（静音自动播放 + 点击出声是标准交互）。
- **限制**：Web 播放依赖浏览器解码能力，编码组合不支持就播不出；自动播放、跨域、DRM 覆盖面都受浏览器与操作系统制约，不是网页代码能单方面决定的；低延迟直播（亚秒级）一般不走 HLS / DASH 的 MSE 路线，见 02 篇的 WebRTC 拉流。
- **排障顺序**：先确认文件地址本身能否打开 → 再看浏览器控制台有无 CORS / 解码报错 → 再看 `video.error` 与播放事件走到哪一步 → 再查自动播放策略与 MSE / EME 接线。跳过前面直接换播放器库，是最常见的误诊。

## 8. 常见误解

- **“写了 autoplay 就一定自动播”**：错，有声自动播放会被浏览器策略拦截；静音或用户交互后才能放行。
- **“hls.js 让所有浏览器都支持 HLS”**：错，它依赖 MSE 与浏览器解码能力，编码不支持、MSE 不支持的环境一样播不出。
- **“跨域报错是播放器库的 bug”**：多数情况下是服务器没返回正确的 CORS 响应头，先查响应头再查代码。
- **“一种新格式能替代所有格式”**：错，格式兼容是按浏览器与设备分布算的，面向全网时多格式 fallback 仍是稳妥做法。
- **“EME 就是 DRM 本身”**：错，EME 只是浏览器侧的解密接线，密钥管理、授权与计费在业务系统与许可证服务器那边。
