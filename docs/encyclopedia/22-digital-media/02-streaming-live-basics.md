# 流媒体与直播基础

## 1. 本章目标

读完本篇能理解：直播从主播到观众要经过哪几站、每一站给延迟加了多少、以及卡顿通常卡在哪一站。

## 2. 背景与问题

视频文件可以慢慢下载再看，直播不行：观众要“正在发生”的画面，而且成千上万人同时看。流媒体解决的是两个问题：一是**边下边播**（不等整个文件到齐），二是**大规模分发**（源站不能直接扛所有观众）。代价是延迟：从主播开口到观众听到，中间每一站都要时间。

## 3. 总体架构

一场直播的完整链路：

```
采集 → 编码 → 推流 → 转码/打包 → CDN 分发 → 播放器缓冲 → 解码渲染
主播端        主播上行      源站/边缘              观众端
```

- **推流（publish）**：主播把编码后的流送到源站，只走一条上行。
- **转码/打包**：源站按需转出多清晰度（见第 6 节），并把连续码流切成小段或按帧转发。
- **CDN 分发**：观众不直连源站，而是从就近的边缘节点拿数据；边缘没有就回源取，取到后缓存给下一个观众。
- **拉流（play）**：播放器从边缘节点取数据，攒够缓冲再播；缓冲是抗抖动的第一道防线，也是延迟的主要来源之一。

## 4. 工作机制

### 4.1 推流：主播到源站只有一条路

推流协议的任务是把编码帧可靠、及时地送到源站，常见选择：

| 协议 | 定位 |
|---|---|
| RTMP | 老牌推流协议（TCP），工具支持最广；现多用于推流，播放侧已逐步被 HTTP 方案取代 |
| SRT | 基于 UDP 的可靠传输，抗丢包、支持加密，主打跨公网的高质量 contribution（场馆、远程演播室回传） |
| RTSP | 摄像头、监控领域常见，交互式控制（播放/暂停/定位）是其本行 |
| WebRTC 推流 | 浏览器、互动场景直接推流，延迟最低，但大规模分发要另搭架构 |

推流只看两个指标：上行带宽够不够（码率 + 20% 以上余量是经验下限）、抖动丢包扛不扛得住。主播端卡顿，十有八九先查上行。

### 4.2 拉流：观众怎么拿到流

| 协议 | 定位与延迟量级 |
|---|---|
| HLS | Apple 主导的 HTTP 方案：索引文件（.m3u8）+ 一段段 .ts 或 fMP4 文件；兼容性最好，普通 HLS 延迟通常在 10 秒量级，低延迟 HLS（LL-HLS）可压到数秒 |
| DASH | MPEG 的 HTTP 方案，与 HLS 思路相同（索引 + 分段），编解码与封装选择更开放 |
| HTTP-FLV / WebSocket-FLV | 把 FLV 流 over HTTP/WebSocket，延迟数秒，国内直播平台曾广泛使用 |
| WebRTC 拉流 | UDP 直连，亚秒级延迟，适合连麦、互动、拍卖等“等不起”的场景；分发成本高于 HTTP 方案 |
| RTMP 拉流 | 历史遗留，浏览器已不再原生支持，新项目不选 |

为什么 HLS 延迟大？因为它按“段”工作：播放器要先拿到索引、再下载至少一段才能开播；段长 6 秒，延迟天然就是“段长 × 缓冲段数 + 传输时间”。缩短段长、减小缓冲能降延迟，但段越短，请求越频繁、抗抖动越差——这是 HLS 延迟与稳定性的根本取舍。

### 4.3 延迟账：每一站加多少

| 环节 | 典型贡献 | 说明 |
|---|---|---|
| 采集与编码 | 几十到几百毫秒 | 编码器前瞻、B 帧越多越慢 |
| 推流传输 | 网络往返 + 抖动 | 跨洋、弱网显著放大 |
| 转码 | 数百毫秒到数秒 | 每转一路清晰度加一份；转码路数越多越慢 |
| 打包与切片 | 一个段长起步 | HLS/DASH 的固有成本 |
| CDN 传输 | 几十到几百毫秒 | 边缘命中快，回源慢 |
| 播放器缓冲 | 1–3 个段 | 抗抖动的代价 |
| 解码渲染 | 几十毫秒 | 通常最小的一站 |

结论：**延迟不是某一个环节的锅，是全链路叠加**。只优化播放器缓冲，省不下转码和切片的账；要亚秒级，就得全链路换 WebRTC 这类帧级方案。

### 4.4 自适应码率（ABR）：卡顿的缓冲垫

源站同时提供多档清晰度（如 1080p、720p、480p），播放器按实时带宽自动切换：带宽掉下去先降清晰度保流畅，而不是直接卡死。ABR 的切换单位通常是“段”，所以段长也决定了切换灵敏度。ABR 保的是“不断流”，不是“永远高清”——带宽不够时先糊后卡，是设计意图，不是故障。

## 5. 关键设计取舍

- **延迟换稳定**：缓冲越大越不怕抖动，但延迟越高；互动场景砍缓冲、接受偶发卡顿，赛事转播则相反。
- **成本换覆盖**：CDN 边缘越密、回源越少，观众体验越好，账单也越高；小众直播常常用单源站 + 有限边缘硬扛。
- **清晰度换流畅**：ABR 档位越多，切换越平滑，但转码与存储成本线性上升；档位不是越多越好。
- **通用性换延迟**：HLS/DASH 处处能播但延迟高；WebRTC 延迟低但分发架构复杂、成本高。选型先看场景对延迟的硬性要求，再看成本。

## 6. 分类与变体

按互动要求分三类，协议跟着场景走：

- **单向大并发（赛事、发布会、带货）**：HLS/DASH 为主，延迟 10 秒量级可接受，CDN 是主力。
- **弱互动（聊天、打赏、答题）**：HTTP-FLV 或 LL-HLS，数秒延迟，聊天与画面有可感知的时差，需在产品层提示。
- **强互动（连麦、拍卖、在线课堂点名）**：WebRTC，亚秒级；主播与观众在同一个实时会话里，延迟差超过 1 秒互动就对不上。

## 7. 应用与限制

- **典型应用**：赛事与发布会直播、带货直播、在线课堂、监控拉流、游戏直播。
- **卡顿排查顺序（按链路从前往后）**：主播上行带宽 → 编码器负载（CPU 满载会丢帧）→ 转码队列积压 → CDN 边缘命中与回源 → 观众下行带宽 → 播放器缓冲策略。跳过前面直接怪播放器，是最常见的误诊。
- **音画不同步**：音频与视频时钟漂移、转码重打包时时间戳处理不当都会导致；排查先看源流时间戳，再看播放器。
- **限制**：本文只讲链路与协议定位，不涉及具体平台的推流地址、鉴权与计费；那部分随平台而变，应以平台文档为准。

## 8. 常见误解

- **“换个播放器就能解决卡顿”**：播放器只负责最后一站；源站、CDN、主播上行的问题，播放器换谁都一样。
- **“延迟越低越好”**：对赛事转播，极低延迟意味着缓冲极小，一次抖动就卡；延迟目标应由场景定，不是越低越好。
- **“HLS 就是慢”**：普通 HLS 确实慢，但 LL-HLS、短段长、CDN 优化能把延迟压到数秒；“慢”是默认配置的结果，不是协议原罪。
- **“推流码率越高越好”**：推流码率超过主播上行能力，第一件事就是丢帧卡顿；推流码率要按上行实测定，不是按画质愿望定。

## 9. 可核验示例：本地打包 HLS，关键帧间隔决定切片长度

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。以下只在本地把测试信号打包成 HLS 文件，**没有起流媒体服务器、没有推流、没有真实观众**，分发与播放环节未验证。测试信号为 ffmpeg 内置 testsrc2 测试图（合成信号，非真实直播画面）。

```bash
# 不设关键帧间隔：6 秒只切出 1 个片段
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=6 \
  -c:v libx264 -preset veryfast -crf 23 \
  -f hls -hls_time 2 -hls_list_size 0 demo.m3u8
# 设关键帧间隔为 60 帧（30fps 下即 2 秒）：切出 3 个 2 秒片段
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=6 \
  -c:v libx264 -preset veryfast -crf 23 -g 60 \
  -f hls -hls_time 2 -hls_list_size 0 demo-g60.m3u8
```

本文写作时实际运行结果：

```
不设 -g：demo.m3u8 的 TARGETDURATION 为 6，只有一个 6 秒片段 demo0.ts
设 -g 60：demo-g60.m3u8 的 TARGETDURATION 为 2，有三个 2 秒片段
          demo-g600.ts（697,292 字节）、demo-g601.ts（713,836 字节）、demo-g602.ts（689,396 字节）
```

教训：**HLS 切片只能落在关键帧上**。`-hls_time 2` 只是“希望 2 秒一段”，关键帧间隔（GOP）没对齐，段长就还是 GOP 的长度。直播推流设置 GOP 与目标段长一致，是 HLS 低延迟的第一步；这一步错了，后面调播放器缓冲都没用。
