# FFmpeg 常用工作流

## 1. 本章目标

读完本篇能用 FFmpeg 完成最常见的几类媒体处理：转码、时间与画面裁剪、拼接、抽帧、截图、水印、格式转换，并理解每条命令里每个参数在干什么、什么时候该用流复制（`-c copy`）、什么时候必须重编码。

## 2. 背景与问题

音视频文件很少能直接用：手机拍的太大要压小、直播录像要截掉片头片尾、几段素材要拼成一条、要从视频里抽一张封面或一段 GIF、要在角落打上水印。这些活在图形软件里要点很多下鼠标，批量做更麻烦。FFmpeg 是一套命令行音视频处理工具（FFmpeg 项目提供，自由软件），一条命令就能完成其中任何一项，还能写进脚本批量跑。它的难不在“装不上”，而在参数太多：同一个目标有三四种写法，选错写法要么慢十倍，要么画质白白损失一轮。

## 3. 总体架构

一条 FFmpeg 命令的基本形状是：

```
ffmpeg [输入选项] -i 输入文件 [输出选项] 输出文件
```

- **输入（`-i`）**：可以是文件，也可以是内置测试源（`-f lavfi -i testsrc2=...`，见第 9 节）。多个 `-i` 就是多个输入（主视频 + 水印图、视频 + 外挂音频都属此类）。
- **解码 → 处理 → 编码**：默认流程是把输入解码成原始帧，经过滤镜（`-vf` / `-filter_complex`）处理，再按输出选项重新编码。加 `-c copy` 则跳过解码与编码，直接复制码流，又快又无损，但能做的事很少（见第 4.1 节）。
- **流与映射**：一个文件里可能有多条流（视频、音频、字幕）。默认 FFmpeg 每种类型只选一条输出流；想精确控制用 `-map`（如 `-map 0:v:0 -map 0:a:0`，即第 0 个输入的第 0 条视频流与第 0 条音频流）。
- **ffprobe 是它的孪生工具**：只负责“看”，不负责“改”，用来查文件的编码、分辨率、时长与体积。本文第 9 节的所有结果都用它核验。

```
输入文件 → 解复用 → 解码 → 滤镜处理 → 编码 → 复用 → 输出文件
                ↘ -c copy 时直接复制码流，跳过解码、滤镜、编码 ↙
```

## 4. 工作机制

### 4.1 转码：换编码还是只换盒子

转码有两个层次，别混为一谈：

- **只换封装（盒子）**：视频编码不变，只把 MP4 换成 MKV 之类。命令是 `-c copy`，即视频流与音频流都原样复制，不重新编码、不损失画质、速度接近文件复制。
- **重编码**：换编码器或改质量参数，如 H.264 换 VP9、CRF 23 改 CRF 28。命令要显式指定编码器，如 `-c:v libx264 -crf 28 -c:a aac -b:a 96k`。CRF 与码率控制的含义见本组编码篇（CRF 越大，体积越小、画质越低）。

```bash
# 只换盒子：MP4 → MKV，流复制（实测）
ffmpeg -y -i src.mp4 -c copy src-copy.mkv
# 重编码：CRF 28 + 音频 96k（实测）
ffmpeg -y -i src.mp4 -c:v libx264 -preset veryfast -crf 28 -c:a aac -b:a 96k transcode-crf28.mp4
```

`-preset`（如 `veryfast`、`medium`、`slow`）是 x264 的“速度换压缩率”档位：越慢，同等画质下体积越小，但耗时越长。`veryfast` 是日常折中档；`ultrafast` 更快但体积明显变大，只适合对延迟敏感的临时场景。

### 4.2 裁剪：时间裁剪与画面裁剪是两回事

**时间裁剪**（截取某一段）用 `-ss`（起始点）与 `-t`（持续时长）：

```bash
# 流复制裁剪：第 2 秒起、取 3 秒（实测）
ffmpeg -y -ss 2 -i src.mp4 -t 3 -c copy trim-copy.mp4
# 重编码裁剪：同样范围（实测）
ffmpeg -y -ss 2 -i src.mp4 -t 3 -c:v libx264 -preset veryfast -crf 23 -c:a aac trim-reencode.mp4
```

`-ss` 写在 `-i` 之前与之后，行为不同：

- 写在 `-i` 之前：FFmpeg 跳到指定位置附近再开始解码，速度快，但落点只能落在关键帧附近，配合 `-c copy` 时切点不精确。
- 写在 `-i` 之后：从头解码到指定位置再丢弃前面的帧，切点精确，但要多花解码时间。

本文实测印证了这一点：10 秒源文件（1280×720、30fps），流复制裁剪实际时长 3.067 秒（不是精确的 3 秒），因为流复制只能在关键帧处下刀；重编码裁剪实际时长 3.000000 秒、906,049 字节，切点精确。结论：**要精确切点就重编码；只要大致范围、又要快，才用流复制**。

**画面裁剪与缩放**用视频滤镜 `-vf`：

```bash
# 从 (320,180) 处裁 640×360，再缩放到 640×360（实测）
ffmpeg -y -i src.mp4 -vf "crop=640:360:320:180,scale=640:360" -c:a copy crop-scale.mp4
```

`crop=宽:高:左上角 x:左上角 y`；`scale=宽:高`，高写 `-1` 表示按比例自动算（如 `scale=640:-1`）。多个滤镜用逗号串联，按顺序执行。注意：用了 `-vf` 就必须重编码视频（`-c:a copy` 只对音频流复制有效），画面裁剪没有“流复制”写法。

### 4.3 拼接：同规格用 concat 复用器

把几段视频拼成一段，最稳的是 concat 复用器：先把每段切好，再写一个清单文件：

```bash
# 先切两段（各 3 秒，流复制）
ffmpeg -y -ss 0 -i src.mp4 -t 3 -c copy part1.mp4
ffmpeg -y -ss 3 -i src.mp4 -t 3 -c copy part2.mp4
# 清单文件 list.txt（两行）：
# file 'part1.mp4'
# file 'part2.mp4'
ffmpeg -y -f concat -safe 0 -i list.txt -c copy joined.mp4
```

实测：两段 3 秒拼成 6.156315 秒（流复制切点误差的累积，见第 4.2 节）。前提条件很严：**所有片段的编码、分辨率、帧率、时间基必须一致**，否则拼接会失败或音画错乱。规格不一致的素材要先统一转码成同一规格再拼；或者用 concat 滤镜重编码拼接（示例未实测，见未完成项）。

### 4.4 截图与抽帧：同一机制，两种用量

截图是“取某一帧”，抽帧是“按间隔批量取帧”，都用帧选择：

```bash
# 截图：第 5 秒那一帧存为 JPG（实测）
ffmpeg -y -ss 5 -i src.mp4 -frames:v 1 thumb.jpg
# 抽帧：每秒抽 1 帧，存为 PNG 序列（实测）
ffmpeg -y -i src.mp4 -vf fps=1 frame-%02d.png
```

- `-frames:v 1`：只输出 1 帧视频就停。
- `-vf fps=1`：把视频降到每秒 1 帧再输出；`fps=1/60` 就是每分钟抽 1 帧。
- 输出文件名里的 `%02d` 是序号占位符（01、02……），不写它，多帧会互相覆盖只剩最后一帧。
- 截图常用于封面与缩略图；抽帧常用于抽查画质、做逐帧分析或生成训练数据前的预览。实测中 10 秒源文件抽出 10 张 PNG，每张约 160 KB（测试图含大量锐利边缘与色块，真实照片的体积会不同）。

### 4.5 水印：图片叠加与文字叠加

水印分两种做法：

```bash
# 图片水印：把 logo.png 叠在左上角 (10,10)（实测）
ffmpeg -y -i src.mp4 -i logo.png -filter_complex "overlay=10:10" -c:a copy watermark-img.mp4
# 文字水印：用 drawtext 直接写字（实测）
ffmpeg -y -i src.mp4 -vf "drawtext=fontfile=/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf:text='CROZZ DEMO':fontsize=36:fontcolor=white:x=10:y=10" -c:a copy watermark-text.mp4
```

- `overlay=x:y` 是“把第二路输入盖在第一路上”，坐标从左上角算；想放右下角可用 `overlay=W-w-10:H-h-10`（W、H 是主视频宽高，w、h 是水印宽高）。
- `drawtext` 必须指定 `fontfile`（字体文件路径，随系统而异；本机实测用 DejaVuSans.ttf），否则会报错；中文水印要选带中文字形的字体文件。
- 两个输入时要用 `-filter_complex`（多路滤镜图），单路用 `-vf` 就够了。水印会触发视频重编码，耗时与正常转码相当。

### 4.6 格式转换与音频提取：按用途选容器与编码

```bash
# MP4 → WebM（VP9 视频 + Opus 音频，3 秒片段，实测）
ffmpeg -y -ss 0 -i src.mp4 -t 3 -c:v libvpx-vp9 -b:v 0 -crf 30 -c:a libopus webm-test.webm
# MP4 → GIF（2 秒、10fps、宽 320，实测）
ffmpeg -y -ss 0 -i src.mp4 -t 2 -vf "fps=10,scale=320:-1:flags=lanczos" gif-test.gif
# 只提音频：视频流丢弃，转 MP3（实测）
ffmpeg -y -i src.mp4 -vn -c:a libmp3lame -q:a 4 audio.mp3
```

- WebM 配 VP9/Opus 是网页免专利费路线的常见组合；但 VP9 编码明显慢于 x264，本次实测中 3 秒片段的 VP9 编码耗时远高于同等 x264（数十秒量级），批量转 VP9 要预留时间或改用硬件编码（未实测）。
- GIF 没有音频、只有 256 色，转 GIF 前先降帧率（`fps=10`）与分辨率，否则体积会大到没法用；实测 2 秒、320 宽的 GIF 为 89,817 字节。
- `-vn` 表示不要视频流；反过来 `-an` 表示不要音频流。`-q:a 4` 是 MP3 的可变码率质量档（0 最好、9 最差，4 是常用折中）。

## 5. 关键设计取舍

- **流复制换重编码**：复制快、无损，但只能做换盒子与粗切；一旦涉及滤镜、改分辨率、改编码，就必须重编码，付出时间与一次画质损失。
- **精确换速度**：`-ss` 在 `-i` 前快但不精确，在 `-i` 后精确但慢；切点精度要求决定写法。
- **质量换体积**：CRF、preset、音频码率三者共同决定输出体积；先定画质目标再看体积，不要反过来。
- **通用换先进**：H.264 + AAC + MP4 处处能播；VP9 + Opus + WebM 体积更小但编码慢、老设备支持差。选型先看观众设备（见本组编码篇）。
- **一次到位换反复转码**：每多一次有损转码就多叠加一轮损失。工作流里应保留一份高质量中间档，只在最后导出时转一次目标格式（与图像篇“只在最后存一次 JPEG”的纪律相同）。

## 6. 分类与变体

| 工作流 | 核心参数 | 是否重编码 | 典型用途 |
|---|---|---|---|
| 换封装 | `-c copy` | 否 | MP4 ↔ MKV，不动画质 |
| 重编码转码 | `-c:v / -crf / -preset` | 是 | 压小、换编码、统一规格 |
| 时间裁剪 | `-ss / -t` | 可选 | 截片段、去片头片尾 |
| 画面裁剪/缩放 | `-vf crop / scale` | 是 | 去黑边、改尺寸、竖屏裁切 |
| 拼接 | `-f concat` + 清单 | 否（同规格时） | 多段合成一条 |
| 截图 | `-ss + -frames:v 1` | 是（解码一帧） | 封面、缩略图 |
| 抽帧 | `-vf fps=N` | 是 | 逐帧检查、批量取样 |
| 水印 | `overlay / drawtext` | 是 | 版权标识、台标 |
| 格式转换 | 换 `-c:v / -c:a` 与容器 | 是 | WebM、GIF、MP3 提取 |

## 7. 应用与限制

- **典型应用**：短视频批量压制与加水印、录播剪辑前的粗切、直播录像转点播、封面图批量生成、播客音频提取、网页动图制作。
- **限制**：FFmpeg 是处理工具，不是剪辑软件——它没有时间线、没有预览、多段精细剪辑与转场要靠非编软件（见下一篇）；它也不做内容理解（识别、分类、自动剪辑属 17 域）。
- **批量处理**：同一命令要对一堆文件跑，用 shell 循环；写脚本前先对一个文件跑通，再批量——批量跑错的代价是整批文件返工。
- **覆盖风险**：FFmpeg 默认不覆盖已存在的输出文件，会直接报错退出；脚本里常用 `-y`（自动覆盖）或 `-n`（绝不覆盖），按场景二选一，不要混用。

## 8. 常见误解

- **“转码能提升画质”**：不能。转码只会保持或降低画质，详见本组编码篇。
- **“`-c copy` 裁剪为什么不准”**：因为流复制只能在关键帧处下刀，切点会被推到最近的关键帧；要精确切点必须重编码（见第 4.2 节实测）。
- **“参数越多越好”**：不是。多数命令只需要输入、输出与一两个关键参数；堆参数常把简单任务变复杂，出问题也更难定位。
- **“GIF 是视频格式”**：不是。GIF 是无声、256 色的图像序列格式，只适合几秒的短循环；长片段用视频格式，不要用 GIF。
- **“水印加了就去不掉”**：水印是烧进画面的像素，原则上不可逆；去水印会损失画面。原片与水印版要分开保存。

## 9. 可核验示例：同一段测试视频，全部工作流一次跑通

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。测试信号为 ffmpeg 内置的 testsrc2 测试图（1280×720、30fps、10 秒）与 440 Hz 正弦波（合成信号，非真实拍摄与录音），仅用于验证命令行为，体积与画质结论不直接外推到真实画面。以下命令全部为本文写作时实际运行通过。

```bash
# 生成源文件（10 秒）
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=10 \
  -f lavfi -i sine=frequency=440:duration=10 \
  -c:v libx264 -preset veryfast -crf 23 -c:a aac -b:a 128k -shortest src.mp4
```

本文写作时实际运行结果（ffprobe 核验）：

```
源文件 src.mp4：          3,512,906 字节，时长 10.000000 秒，h264 1280x720 + aac
只换盒子 src-copy.mkv：   3,507,092 字节（流复制，体积基本不变）
重编码 CRF 28：           1,499,271 字节（约比源文件小 57%）
流复制裁剪（2 秒起 3 秒）：时长 3.067 秒、1,784,455 字节（切点落在关键帧，不精确）
重编码裁剪（同范围）：    时长 3.000000 秒、906,049 字节（切点精确）
画面裁剪+缩放 640×360：   1,189,589 字节，ffprobe 确认 640x360
拼接两段 3 秒：            时长 6.156315 秒、3,187,256 字节
截图 thumb.jpg：           45,577 字节，1280x720
抽帧 fps=1：               10 张 PNG，每张约 160 KB
提取音频 audio.mp3：       41,179 字节
图片水印 watermark-img.mp4：3,325,459 字节，时长 10.000000 秒
文字水印 watermark-text.mp4：3,347,694 字节，时长 10.000000 秒
MP4 → WebM（VP9+Opus，3 秒）：1,243,532 字节，时长 3.008 秒
MP4 → GIF（2 秒、320 宽）：   89,817 字节，320x180
```

教训：流复制与重编码的取舍，集中体现在裁剪精度这一处——同一范围两种写法，时长差 0.067 秒；批量脚本里用错写法，整批片段的切点都会漂移。
