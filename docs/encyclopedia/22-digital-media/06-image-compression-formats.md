# 图像压缩与格式选型

## 1. 本章目标

读完本篇能理解：JPEG、PNG、WebP、AVIF、GIF 各自“压掉的是什么、保留的是什么”，以及面对照片、图标、截图、透明图、动图这些场景时，按什么依据选格式——而不是凭习惯或“越新越好”。

## 2. 背景与问题

同一张图存成不同格式，体积可以差几倍，画质、透明、动画支持也各不相同。选错格式的代价很具体：照片存 PNG 体积翻倍、图标存 JPEG 边缘发糊发脏、需要透明的图存 JPEG 直接没了透明通道、动图只会用 GIF 导致体积失控。

选型的难处在于，格式名背后是两组互相独立的取舍：一是**压缩方式**（有损还是无损，丢的是什么信息），二是**功能支持**（透明通道、动画、位深、HDR）。本篇先把这两组取舍拆开讲，再按场景给建议。本篇不讲修图操作——调色、裁剪、抠图见[图像处理基础](03-image-processing-basics.md)；DCT 与量化的通用原理见[音视频编码基础](01-media-codec-basics.md)。

## 3. 总体架构

一张光栅图像从像素到文件，要过三道关，每道关的取舍都不同：

```
像素阵列 → ① 变换与预测（把数据变得更“好压”） → ② 量化/丢弃（有损格式才有） → ③ 熵编码（无损收尾）
                                                                  ↓
                                              ④ 封装（文件头、透明通道、动画帧、元数据）
```

- **有损格式**（JPEG、WebP 有损模式、AVIF 有损模式）：第 ② 步主动扔掉人眼不敏感的信息，换体积；扔掉的回不来，重复保存会叠加损失。
- **无损格式**（PNG、WebP 无损模式、AVIF 无损模式、GIF）：没有第 ② 步，解码后与原像素逐位一致；体积下限由内容本身的规律性决定。
- **封装**决定格式“能装什么”：透明通道、动画帧、位深、色彩信息都写在文件结构里，与压缩算法无关——所以“支持透明”和“压得小”是两个维度的事，不能互相推导。

## 4. 工作机制

### 4.1 有损压缩丢的是什么

有损压缩不是“均匀地变模糊”，而是有选择地丢三类东西：

- **高频细节**：画面里变化剧烈的小尺度信息（发丝、文字边缘、噪声）。人眼对高频不敏感，量化时先拿它开刀；压得越狠，细节越先糊成块（块效应）或涂抹感。
- **色度细节**：人眼对亮度敏感、对色彩迟钝。JPEG 等格式先把 RGB 转成亮度 + 色度（YCbCr），再对色度降分辨率（色度抽样，常见 4:2:0），色度数据量直接减半，观感损失很小。红字边缘发紫、渗色，多半是这一步的代价。
- **心理视觉冗余**：亮部与暗部、平坦区域的微小差别，人眼本来就分辨不出，编码器直接不存。

共同边界：有损压缩的损失**不可逆**。同一张图反复“打开—编辑—存为 JPEG”，每次都会重新量化一次，损失叠加（代际损失）。工作流里应保留无损中间档，只在最后导出时转一次有损格式——这一点[图像处理基础](03-image-processing-basics.md)第 7 节已有结论，本篇不再重复论证。

### 4.2 JPEG：为照片而生的老标准

- **标准与年代**：JPEG（Joint Photographic Experts Group）标准为 ITU-T T.81 / ISO/IEC 10918-1，1992 年发布；文件常以 JFIF 容器封装。
- **压缩路线**：RGB 转 YCbCr → 色度抽样 → 按 8×8 分块做 DCT（离散余弦变换）→ 量化 → 熵编码。分块 DCT 是理解 JPEG 的关键：高压缩时块边界处的不连续会被放大，就是“块效应”；文字、线条这类锐利边缘跨块时最容易出伪影。
- **质量档**：质量参数（如 ffmpeg 的 `-q:v`）本质是量化步长的档位，档位越低量化越粗、体积越小、损失越大。没有“JPEG 固定比 PNG 小”的说法——体积取决于内容与档位（见第 9 节实测）。
- **不支持**：透明通道、动画、多图层。需要透明或动画时 JPEG 从一开始就不在候选里。

### 4.3 PNG：无损与透明的基准

- **标准与年代**：PNG 于 20 世纪 90 年代中期制定，1997 年成为 RFC 2083；设计目标之一就是替代 GIF 做无损静态图。
- **压缩路线**：逐行预测滤波（用相邻像素预测当前像素，只存预测残差）+ DEFLATE 无损压缩。没有量化，解码后逐位还原。
- **透明**：支持 8 位 alpha 通道（每像素 256 级透明度），边缘可以半透明过渡——这是它相对 GIF 最大的功能优势，图标、Logo、UI 切图的首选理由。
- **不支持**：动画（标准 PNG 本身没有动画帧；APNG 是扩展，支持度因平台而异，选型时不要默认它可用）。照片类内容用 PNG 通常比 JPEG 大得多，因为照片噪声多、规律少，无损压缩压不下去。

### 4.4 GIF：256 色与动画的遗产

- **标准与年代**：GIF 由 CompuServe 于 1987 年发布，采用 LZW 无损压缩。
- **色彩上限**：每帧最多 256 色（调色板索引色）。照片、渐变用 GIF 会出现明显的色带与抖动（dithering），不是“压坏了”，是格式本身装不下那么多色。
- **透明**：只有 1 位透明（某个调色板色指定为透明），边缘非全透即全不透，锯齿明显；需要柔和边缘时不要选 GIF。
- **动画**：多帧 + 每帧延迟时间，是 GIF 至今仍在用的唯一理由。短循环、小尺寸、色彩简单的动图可用；色彩丰富或较长的动画，用 GIF 体积会失控，应优先考虑视频或 WebP/AVIF 动画（见 4.6 节）。

### 4.5 WebP：有损与无损的双模

- **标准与年代**：WebP 由 Google 于 2010 年发布。
- **压缩路线**：有损模式源自 VP8 视频编码的帧内预测（比 JPEG 的分块 DCT 更善于利用图像内的空间相关性）；无损模式（VP8L）用预测 + 熵编码。同一格式内有损、无损两种模式可以并存，选型时要先问清“用的是哪种模式”，只说“存成 WebP”是不完整的描述。
- **功能**：支持 8 位 alpha 透明与动画（多帧），等于一只格式同时覆盖了 JPEG（照片）、PNG（透明图）、GIF（动图）三类需求的主要场景。
- **代价与边界**：压缩率通常优于 JPEG（同等主观质量下体积更小，幅度因内容而异），但编码速度与老设备、老工具的兼容性曾是短板；如今主流浏览器均已支持，兼容性已不是主要障碍，个别专业工具链仍需确认。

### 4.6 AVIF：最新一代，压缩率最高、门槛也最高

- **标准与年代**：AVIF（AV1 Image File Format）规范 1.0.0 由开放媒体联盟（AOMedia）于 2019 年 2 月 19 日发布，基于 AV1 编码与 HEIF 容器。
- **压缩路线**：用 AV1 的帧内编码压单张图像，预测与变换工具比 WebP、JPEG 新一代，压缩效率目前是本篇五种格式里最高的；同时支持有损与无损模式、8/10/12 位每通道、HDR 与广色域（与下一篇色彩管理衔接）。
- **功能**：支持透明通道与动画（图像序列），功能上与 WebP 对齐且位深、HDR 走得更远。
- **代价与边界**：编码速度明显慢于 JPEG/WebP（AV1 编码器算力需求高），编解码支持仍在普及中——老系统、部分工具与旧浏览器可能打不开。选型原则：能接受“新格式 + 降级兜底”时才用，不要把它当成唯一分发格式。

### 4.7 横向对照

| 维度 | JPEG | PNG | GIF | WebP | AVIF |
|---|---|---|---|---|---|
| 压缩性质 | 有损 | 无损 | 无损（256 色内） | 有损 / 无损双模 | 有损 / 无损双模 |
| 核心压缩手段 | 分块 DCT + 量化 | 预测滤波 + DEFLATE | LZW + 调色板 | VP8 帧内预测 / VP8L | AV1 帧内编码 |
| 透明通道 | 不支持 | 8 位 alpha | 1 位（全透/不透） | 8 位 alpha | 支持 alpha |
| 动画 | 不支持 | 不支持（APNG 为扩展） | 支持（多帧） | 支持 | 支持（图像序列） |
| 位深 | 8 位每通道 | 8 位（另有 16 位） | 8 位索引 | 8 位 | 8/10/12 位 |
| 典型年代 | 1992 | 1996–1997 | 1987 | 2010 | 2019 |
| 最大短板 | 无透明/动画、块效应 | 照片体积大、无动画 | 色彩上限 256、体积易失控 | 老工具兼容待确认 | 编码慢、支持仍在普及 |

## 5. 关键设计取舍

- **体积换可逆性**：有损格式体积小，但每存一次丢一次；归档与中间档永远选无损，只在最终分发时转有损。
- **通用性换压缩率**：JPEG、PNG、GIF 几乎处处能打开；WebP、AVIF 压得更小，但要确认目标观众的浏览器、工具、系统版本吃不吃新格式。网页分发可用 `<picture>` 元素做“新格式优先、老格式兜底”，而不是二选一。
- **功能换体积**：透明、动画、HDR 都是要花体积或兼容性买的；不需要的功能不要为它换格式——照片不需要透明，就不必为透明付 PNG 的体积账。
- **编码时间换体积**：AVIF 的体积优势是用编码算力与时间换来的；批量转码或实时生成场景要先测编码耗时，不能只看体积。

## 6. 分类与变体

- **按压缩性质**：有损（JPEG、WebP 有损、AVIF 有损）与无损（PNG、GIF、WebP 无损、AVIF 无损）。同一格式名可能横跨两类，选型时必须落实到模式。
- **按内容类型**：连续色调（照片、渲染图）与离散图形（图标、文字、截图、线条图）。前者适合有损变换编码，后者适合无损预测编码——内容类型是比格式新旧更可靠的选型依据。
- **其他相关格式（只做定位，不展开）**：HEIC/HEIF（与 AVIF 同容器、装 HEVC 编码，苹果生态常见）；JPEG XL（新一代通用格式，仍在演进，浏览器支持有变，本文写作时不列入推荐）；TIFF、RAW（专业归档与拍摄流程，不属于网页分发选型范围）。
- **矢量图的提醒**：SVG 是矢量格式（存图形指令而非像素），Logo 与简单图标在可缩放、无损耗上优于一切光栅格式；但它不在本篇五种光栅格式的比较范围内，图标选型时应先问“能不能用矢量”。

## 7. 应用与限制：按场景选型

| 场景 | 优先选 | 理由与注意事项 |
|---|---|---|
| 网页照片、摄影作品 | JPEG（兼容优先）或 WebP/AVIF 有损（体积优先，需兜底） | 照片噪声多，无损格式压不动；质量档先定画质再看体积 |
| 图标、Logo、UI 切图（需透明） | PNG；简单图形可考虑 SVG | 8 位 alpha 边缘平滑；JPEG 没有透明通道，绝不选 |
| 截图（文字、界面、线条多） | PNG 或 WebP 无损 | 锐利边缘最怕有损量化；JPEG 存截图边缘会脏、体积未必小 |
| 简单动图（短循环、色彩少） | GIF（兼容优先）或 WebP 动画 | GIF 色彩上限 256，超了就换 WebP 动画或直接用视频 |
| 长动画、色彩丰富的动图 | 视频格式（见编码篇）或 WebP/AVIF 动画 | GIF 体积失控时不要硬撑，动画本质是视频问题 |
| 归档、中间档、反复编辑 | PNG（或 TIFF/RAW，按专业流程） | 只存无损档；有损格式只做最终导出 |
| 追求最小体积且可控分发 | AVIF 有损 + WebP/JPEG 兜底 | 编码慢、需测目标端支持；不要单押 AVIF |

- **限制总汇**：没有一种格式在所有维度上都最优；“最新格式”不等于“适合当前场景的格式”。选型时先定内容类型（照片还是图形）、再定功能需求（透明？动画？）、最后定兼容性底线，顺序不要反。
- **体积预判的纪律**：体积取决于内容，不取决于格式名。第 9 节的实测表明，同一张合成图上高质量 JPEG 反而比 PNG 大——选型结论必须来自对自己内容的实测，而不是格式口碑。

## 8. 常见误解

- **“JPEG 一定比 PNG 小”**：错。体积取决于内容与质量档；锐利边缘多的合成图、截图，高质量 JPEG 可能比 PNG 更大（见第 9 节实测）。
- **“PNG 是无损的，所以画质永远最好”**：PNG 解码后与原像素一致，但它存不下照片的全部信息优势——对照片而言，PNG 只是“体积大”，画质并不比高质量 JPEG 更好；无损指的是“不丢像素”，不是“看起来最好”。
- **“转成 WebP/AVIF 就自动变小”**：不一定。内容、质量参数、编码器实现都会影响结果；无损模式的 WebP 对照片类内容未必比 JPEG 有损小，跨性质比较没有意义。
- **“GIF 动图小巧”**：只对色彩少、尺寸小的循环成立；色彩丰富或较长的 GIF 体积常常超过同等视频数倍。
- **“把 JPEG 再存成 PNG 能恢复画质”**：不能。有损丢失的信息已经没了，转无损格式只会把“已经损失的像素”原样存下来，体积变大、画质不回升。

## 9. 可核验示例：同一张测试图，四种写法的体积对比

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。测试图为 ffmpeg 内置 testsrc2 生成的单帧 1280×720 图像（合成测试图，含大量锐利边缘与色块，非真实照片），结论不直接外推到照片。以下命令本文写作时实际运行过。

```bash
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=1:duration=1 -frames:v 1 fmt.png
ffmpeg -y -i fmt.png -q:v 5 fmt-q5.jpg
ffmpeg -y -i fmt.png -q:v 10 fmt-q10.jpg
ffmpeg -y -i fmt.png -c:v libwebp -q:v 80 fmt-q80.webp
```

本文写作时实际运行结果：

```
fmt.png：      94,789 字节（PNG，无损）
fmt-q5.jpg：   71,476 字节（JPEG，质量档 q5）
fmt-q10.jpg：  49,885 字节（JPEG，质量档 q10，约比 PNG 小 47%）
fmt-q80.webp： 28,212 字节（WebP 有损 q80，约比 PNG 小 70%、比同图 JPEG q10 小 43%）
```

教训与边界：第一，同一张图上，WebP 有损确实明显小于 JPEG 与 PNG，但这是**合成测试图**上的结果，照片的相对差距会不同，选型前应对自己的内容实测；第二，本机 ffmpeg 未提供 AVIF 编码器，AVIF 的同图体积对比**未实测**（见未完成项），本文不给出 AVIF 的体积数字；第三，JPEG 的质量档是体积开关，q5 到 q10 体积差约三成，选档前先看内容类型。
