# 直播推流与低延迟

## 1. 本章目标

读完本篇能理解：RTMP、SRT、WebRTC 各自站在直播链路的哪一段、解决什么问题；“低延迟”到底在和什么做交易；以及一场直播按延迟要求不同，架构会长成哪几种样子。

## 2. 背景与问题

本组前两篇已经讲清：编码决定画质与体积（01 篇），HLS/DASH 决定分发怎么切段、怎么自适应（08 篇）。但中间还有一段没讲透：**主播的画面是怎么“进来”的**。主播在弱网的出租屋、场馆在跨洋的演播室、观众在几千公里外——画面进来的路走不稳，后面分发做得再好也没用。

推流（contribution，第一公里）与分发（distribution，最后一公里）是两段不同的路，用的协议也不同。把两者混成一种协议选型，是直播架构最常见的错误起点。

## 3. 总体架构

按“第一公里 / 中间 / 最后一公里”画一张直播全图：

```
采集 → 编码 → → 媒体服务器（收流、转码、打包）
主播端 RTMP / SRT / WHIP 源站
↓

HLS / DASH（CDN，大并发）或 WebRTC（SFU，低延迟）
↓
播放器 → 解码渲染（观众端）
```

同一场直播常常是“混合”的：主播用 SRT 把高质量信号从场馆回传到云端，云端转码后一路出 HLS/DASH 走 CDN 给十万观众，另一路出 WebRTC 给需要连麦互动的几十人。**没有一种协议能同时拿下“高质量进站、大规模分发、亚秒延迟”这三项**，架构就是按场景把协议拼起来。

## 4. 工作机制

### 4.1 RTMP：推流的事实标准，播放侧已经退场

RTMP（Real-Time Messaging Protocol，实时消息协议）由 Macromedia 在 2000 年前后为 Flash 平台开发，约 2002 年随 Flash Communication Server 发布；2005 年 Adobe 收购 Macromedia 后接手，2012 年 12 月 21 日发布公开的《RTMP Specification》1.0 版。Flash Player 于 2020 年 12 月 31 日终止支持，浏览器里的 RTMP 播放随之死亡——但**推流侧的 RTMP 活得很好**，至今仍是 OBS 等推流工具与各大直播平台之间最通用的 ingest 语言。

机制上 RTMP 走 TCP（默认端口 1935），把音视频与数据切成小块（chunk，默认 128 字节，可协商放大），按消息类型（音频、视频、AMF 数据）复用在一条连接上。TCP 保证按序、可靠，丢包就重传——在推流上行稳定的环境里这是优点（画面完整），在抖动丢包严重的弱网上就成了延迟来源（队头阻塞：一个包没到，后面的都得等）。

定位一句话：**RTMP 是“第一公里”的通用语，不再是“最后一公里”的播放协议**。它的短板也很明确：只支持老编码组合（经典 RTMP + FLV 容器长期只支持 H.264/AAC；支持 H.265/AV1 等新编码的是后来由 Veovera 组织维护的增强版 RTMP，具体版本以官方发布为准，见文末未完成项），且无内置加密（加密靠 RTMPS，即 RTMP over TLS，走 443 端口）。

### 4.2 SRT：为跨公网回传而生的可靠 UDP

SRT（Secure Reliable Transport，安全可靠传输）由 Haivision 开发，2013 年在 IBC 展会首次公开演示，2017 年 4 月开源（MPL-2.0），同年成立 SRT Alliance 推广。它源自 UDT 协议，走 UDP，但补上了 UDP 缺的东西：

- **丢包重传（ARQ）**：接收端发现序号缺口就向发送端要重传，配合一个可配置的“延迟窗口”（latency，典型值 120–1000 毫秒）：发送端把已发数据在窗口内留着备查，接收端在窗口内等齐了再交出去。窗口越大，抗丢包越强，延迟也越高——这是 SRT 最核心的旋钮。
- **加密**：AES 加密（128/192/256 位），密钥由通信双方协商。
- **三种连接模式**：caller（主动拨出）、listener（监听等对方来）、rendezvous（双方同时向对方发起，适合两端都在 NAT 后的打洞场景）。

定位一句话：**SRT 是“第一公里”的高质量回传协议**，典型场景是场馆、远程演播室、外场记者把信号经公网传回制作中心，替代过去昂贵的卫星与专线。它点对点，不负责大规模分发：一个 SRT 流到源站后，仍要转成 HLS/DASH 或 WebRTC 才能分给观众。

### 4.3 WebRTC：浏览器原生的实时会话

WebRTC（Web Real-Time Communication）不是单一协议，而是一整套实时通信标准：W3C 负责浏览器的 JavaScript API（如 RTCPeerConnection），IETF 负责线上的传输协议。2021 年 1 月 26 日，WebRTC 1.0 正式成为 W3C 推荐标准，同月 IETF 发布了核心 RFC 集群（RFC 8825–8835）。它 2011 年由 Google 开源，标准落地比实际部署晚了近十年。

机制上 WebRTC 走 UDP + RTP/SRTP 传媒体，DTLS-SRTP 强制加密；用 ICE + STUN/TURN 解决 NAT 穿透：能直连就直连（P2P），直连不了就经 TURN 服务器中继（代价是带宽与延迟都上去了）。它没有“段”的概念，媒体按帧流动，配合抖动缓冲（jitter buffer）与拥塞控制（如 GCC），延迟可以压到亚秒级（通常 0.2–0.5 秒量级）。

但 WebRTC 的代价在**分发侧**：P2P 只适合一对一或几个人；上千人同时看，需要媒体服务器做转发。两种角色：

- **SFU（选择性转发单元）**：只转发、不混流、不转码，把每个人的流按需转发给其他人。延迟低、算力省，是连麦、在线课堂的主流。
- **MCU（多点控制单元）**：把多路流混成一路再分发。观众端简单（一路流），但服务器要解码、混流、再编码，延迟与算力都高，如今较少用。

2025 年 3 月，WHIP（WebRTC-HTTP Ingestion Protocol）成为 RFC 9725，给了 WebRTC 一个标准化的推流入口：编码器用普通 HTTP POST 就能把流推给 WebRTC 服务器，不再各家各写一套信令。对应的播放侧协议 WHEP 截至本文核实日期尚未成为 RFC，以官方发布为准（待核实），见文末未完成项。

### 4.4 低延迟的权衡：延迟预算表

把“从主播开口到观众听到”的延迟拆开，每一站都能省、也都能贵：

| 环节 | 压延迟的做法 | 付出的代价 |
|---|---|---|
| 采集与编码 | 关 B 帧、缩短 GOP、用硬件编码、低延迟编码档 | 画质下降（同码率下）、编码器选择受限 |
| 推流传输 | SRT 小延迟窗口、WebRTC 直连 | 抗丢包变差、弱网易卡；TURN 中继又加延迟 |
| 转码 | 少转档位、甚至不转码直接透传 | 观众没有低清档位可选，弱网观众直接卡死 |
| 打包与切片 | 短段、LL-HLS/LL-DASH 部分段（见 08 篇） | 请求数与 CDN 成本上升、抗抖动下降 |
| 分发 | WebRTC SFU 直发、边缘节点就近 | SFU 扇出成本随人数线性上升，远高于 CDN 分发 |
| 播放器缓冲 | 缓冲压到 1 段以下甚至帧级 | 一次抖动就卡顿、重缓冲 |

结论与 02 篇一致，但这里更进一步：**延迟目标必须由场景定，再反推全链路**。要亚秒级，就得接受“编码画质让步 + 不转码或少转码 + WebRTC 分发 + 高成本”这一整套；只改其中一环，省下的延迟会被其他环吃回去。

成本曲线值得单独说一句：HLS/DASH 走 CDN 时，多一个观众的边际成本很低（边缘缓存命中后几乎是带宽钱）；WebRTC 走 SFU 时，每个观众都要一条独立的转发会话，带宽与服务器成本随人数线性涨。**人数上万还要求亚秒延迟，在现有架构下基本等于“烧钱换延迟”**，这也是大赛事宁可接受 10 秒延迟的经济原因。

## 5. 关键设计取舍

- **可靠换及时**：TCP（RTMP）与 SRT 的重传保证画面完整，但重传要等；WebRTC 的 RTP 丢了就丢了（靠前向纠错 FEC 与丢包隐藏 PLC 补），宁可丢一帧也不等。互动场景选“及时”，录制与回传场景选“可靠”。
- **画质换延迟**：B 帧、前瞻分析、双遍编码都能省码率提画质，但都要等未来帧；低延迟编码把这些全关掉，同码率画质必然下降。
- **规模换延迟**：CDN 分发便宜但延迟以秒计；WebRTC 分发亚秒级但成本随人数线性涨。先定观众规模，再定延迟目标，顺序不能反。
- **简单换可控**：RTMP 推流最简单（一个地址、一串流密钥，OBS 开箱即用）；SRT 要调延迟窗口、配模式；WebRTC 要搭信令、STUN/TURN、SFU。越低的延迟，运维面越宽。

## 6. 分类与变体

按延迟目标分三档，协议与架构跟着走：

| 档位 | 延迟量级 | 推流 | 分发 | 典型场景 |
|---|---|---|---|---|
| 大众直播 | 10 秒量级 | RTMP 或 SRT | HLS/DASH + CDN | 赛事、发布会、带货、演唱会 |
| 低延迟直播 | 2–5 秒 | RTMP 或 SRT | LL-HLS / LL-DASH / HTTP-FLV | 带货互动、答题、聊天打赏 |
| 实时互动 | 亚秒级（<1 秒） | WebRTC（WHIP）或 SRT | WebRTC SFU | 连麦、拍卖、在线课堂点名、远程手术示教 |

变体补充：

- **RTMP + HLS/DASH**：最常见的组合，推流 RTMP 进站，转码打包后 HLS/DASH 出站。
- **SRT + HLS/DASH**：高质量回传组合，场馆与演播室首选；源站收到 SRT 后再走常规分发。
- **全 WebRTC**：推流与分发都走 WebRTC，延迟最低，成本最高，适合小规模强互动。
- **SRT 进站 + WebRTC 分发**：场馆高质量回传、观众侧低延迟互动的折中，云端媒体服务器做协议转换。

## 7. 应用与限制

- **典型直播架构（大众直播）**：主播 OBS 经 RTMP 推流 → 源站收流 → 转码出多档 → 打包 HLS/DASH → CDN 边缘分发 → 观众播放器 ABR 选档。简单、便宜、能扛大并发。
- **典型直播架构（强互动）**：连麦者经 WebRTC 进 SFU → SFU 转发给其他连麦者与观众 → 观众侧 WebRTC 播放；同时可另出一路 HLS/DASH 给只看不互动的大量观众（“一路互动 + 一路围观”是常见做法）。
- **限制**：本文只讲协议定位与架构取舍，不涉及具体平台的推流地址、流密钥、鉴权与计费——那部分随平台而变，应以平台文档为准；真实推流服务器搭建、弱网下的 SRT 延迟窗口调参与 ABR 切换实测均未做（见文末未完成项）。
- **与前篇的关系**：02 篇讲全链路与延迟账，08 篇讲分发侧的清单与分片机制，本篇讲推流侧的协议选型与低延迟架构；三篇合起来才是一场直播的完整技术图。

## 8. 常见误解

- **“RTMP 已经死了”**：错。死的是 Flash 里的 RTMP *播放*；RTMP *推流*仍是各平台与 OBS 之间的通用语言，2020 年 Flash 终止支持后也没有被废弃。
- **“SRT 延迟一定比 RTMP 低”**：不一定。SRT 的延迟由 latency 窗口决定，窗口设 1 秒就比 RTMP 还慢；SRT 赢的是弱网下的稳定性与画质，不是无条件的低延迟。
- **“上了 WebRTC 就全场亚秒”**：错。WebRTC 只保证它自己那一段亚秒；编码、转码、混流（MCU）任何一环拖后腿，全链路照样慢；而且 TURN 中继与跨国链路都会加延迟。
- **“延迟越低越好”**：对围观型直播，极低延迟意味着缓冲极小、成本极高；延迟目标应由场景与观众规模共同决定。

## 9. 可核验示例：本机 ffmpeg 支持哪些推流协议

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。以下只核查了本机 ffmpeg 的协议支持情况，**没有起推流服务器、没有真实推流、没有真实观众**；RTMP/SRT 的实际推流命令均未在本机跑通过。

```bash
ffmpeg -hide_banner -protocols 2>&1 | grep -iE 'rtmp|srt|rtp'
```

本文写作时实际运行结果：

```
输入协议与输出协议列表中均包含：rtmp、rtmps、rtmpt、rtmps、rtp、srtp、srt
ffmpeg 构建配置中包含 --enable-libsrt（即 SRT 支持已编译进本机 ffmpeg）
```

结论：本机 ffmpeg 同时支持 RTMP 与 SRT 推流，工具侧没有协议短板；推流能不能通，取决于有没有可达的推流服务器与正确的推流地址、流密钥——这些是平台侧的配置，不在本文验证范围内。

> 推流命令示例（示例未实测——无推流服务器可接，本地 SRT 回环尝试未成功建立连接，未验证）：
>
> ```bash
> # RTMP 推流（示例未实测）：把编码后的流推给平台给定的地址
> ffmpeg -re -i input.mp4 -c:v libx264 -preset veryfast -g 60 -c:a aac \
> -f flv "rtmp://推流地址/live/流密钥"
> # SRT 推流（示例未实测）：caller 模式，延迟窗口 200 毫秒
> ffmpeg -re -i input.mp4 -c:v libx264 -preset veryfast -g 60 -c:a aac \
> -f mpegts "srt://推流地址:9000?mode=caller&latency=200"
> ```
