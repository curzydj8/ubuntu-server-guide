# 视频编码标准演进（H.264/AV1）

## 1. 本章目标

读完本篇能理解：H.264、H.265、VP9、AV1 四代视频编码标准各自为解决什么问题而出现、每一代比上一代多做了什么、以及选型时按什么取舍——而不是只记住“越新越好”。

## 2. 背景与问题

视频编码标准换代的直接动力是两个数字的赛跑：**画面越来越大，带宽涨得没那么快**。从 480p 到 1080p、4K 乃至 8K，像素数每代翻几倍；同一条宽带能传的码率却涨得慢得多。每一代新标准回答的都是同一个问题：**在主观画质不变的前提下，能不能用更少的码率装下同样的画面**。

还有一个并行的动力：**专利成本**。H.264、H.265 走 MPEG/ITU-T 的专利池路线，使用者要按规则缴纳许可费；VP9、AV1 则走开放免版税路线，试图让“压得更小”不再附带一张授权账单。理解演进史，必须同时看技术线和许可线，两条线经常互相推动。

两个前提概念（细节见本组编码篇）：

- **标准与编码器是两回事**。标准只规定码流的语法和解码器必须怎么解，不规定编码器具体怎么压。同一标准下，x264、x265、libaom、SVT-AV1 这些编码器实现的画质与速度可以差很多。选型时“选标准”与“选编码器实现”是两步。
- **压缩率、算力、兼容性是不可能三角**。新标准省下的码率，是用更多的编码搜索算力和更晚的硬件普及换来的。

## 3. 总体架构

四代标准与两条路线的演进全景：

```
技术路线 A（MPEG / ITU-T，专利池路线）：
  H.264/AVC（2003） ──→ H.265/HEVC（2013） ──→ H.266/VVC（2020，普及中）
技术路线 B（开放免版税路线）：
  VP8（2010，Google） ──→ VP9（2013，Google） ──→ AV1（2018，AOMedia）
                                              └─→ AV2（推进中，规范状态以 AOMedia 官方发布为准，待核实）
```

时间线上的关键事实：

- **2003 年，H.264/AVC**：ITU-T 与 MPEG 联合制定，正式编号 ITU-T H.264 | ISO/IEC 14496-10（MPEG-4 Part 10），成为此后近二十年的基准线。
- **2013 年，两条路线同年分叉**：H.265/HEVC（ITU-T H.265 | ISO/IEC 23008-2）发布，目标是同等主观质量下码率比 H.264 省约一半（因内容与编码器而异）；同年 Google 发布 VP9，作为 VP8 的后继，压缩率与 H.265 相当，但走免专利费路线。
- **2018 年，AV1**：开放媒体联盟（AOMedia，2015 年成立，创始成员包括 Amazon、Cisco、Google、Intel、Microsoft、Mozilla、Netflix 等）发布 AV1 码流规范（2018 年 3 月 28 日），并以免版税专利许可为卖点，目标是在互联网视频分发上取代 H.265。
- **2020 年，H.266/VVC**：ITU-T 与 MPEG 发布新一代标准，压缩率目标再进一步，专利格局与硬件普及仍在进行中（具体许可安排以官方发布为准，待核实）。

## 4. 工作机制

### 4.1 H.264/AVC（2003）：定下现代编码的基本盘

H.264 的基本工具链（帧间预测、变换、量化、熵编码）见本组编码篇；它作为标准的贡献在于把这套机制做成了一个**所有设备都能硬解**的通用底座：

- **16×16 宏块**是基本处理单元，帧内预测有 9 种方向模式（4×4 亮度块）。
- **多参考帧与 1/4 像素运动补偿**：运动估计可以参考多帧、精细到四分之一像素，静止与平滑运动的画面因此压得很小。
- **CABAC/CAVLC 两种熵编码**：CABAC 压得更小、算力更高，是画质优先时的默认选择。
- **档次（Profile）与级别（Level）**：Baseline、Main、High 等档次把工具集分层，手机、广播、蓝光各取所需——这是 H.264 能铺满全设备的制度原因。

H.264 的历史地位不在“最先进”，而在“够用且处处能播”。直到今天，它仍是兼容性的基准线。

### 4.2 H.265/HEVC（2013）：把块做大、把预测做细

H.265 不是 H.264 的小修补，而是为 4K 与更高分辨率重做的工具集：

- **编码树单元（CTU）最大 64×64**：相比 H.264 固定的 16×16 宏块，大块能自适应地切分——平坦区域用大块省码率，细节区域切小块保画质。高分辨率画面里大片平坦区域多，大块的收益尤其明显。
- **帧内预测增至 35 种模式**：方向分得更细，纹理复杂的静止画面预测残差更小。
- **更多的变换尺寸与更强的环路滤波**：变换块尺寸更灵活，去块滤波之外增加了样点自适应补偿（SAO），高压缩下的块效应与振铃被压得更低。
- **并行工具（Tiles、Wavefront）**：为多核编码而生，4K 编码不至于单核跑死。

代价同样明确：编码搜索空间随块尺寸与模式数膨胀，编码算力显著高于 H.264；解码也更重，老设备硬解跟不上。H.265 省下的码率，有一半是算力账单。

### 4.3 VP9（2013）：同代性能，换一条许可路线

VP9 是 Google 在收购 On2 之后、沿 VP8 路线发展的编码标准，与 H.265 同年、同代：

- **压缩率与 H.265 相当**（因内容与编码器而异），64×64 超级块、更细的帧内预测与变换选择，思路与 H.265 同源。
- **免专利费**：Google 承诺 VP9 不收取专利许可费，这是它与 H.265 最本质的区别，也是 YouTube 曾以 VP9 作为主力编码的原因。
- **短板在硬件覆盖**：VP9 的硬件解码普及晚于 H.264、弱于 H.265 的部分生态位，移动端与老设备的软解成本较高，限制了它在直播与实时场景的铺开。

VP9 的意义不在技术本身，而在于它证明了**不靠专利池也能做出同代压缩率**，为 AV1 铺平了组织与技术两条路。

### 4.4 AV1（2018）：把三家的工具拼成一代

AV1 由 AOMedia 联盟制定，技术来源是三条线的汇合：Google 的 VP9/VP10、Mozilla 与 Xiph.Org 的 Daala、Cisco 的 Thor。汇合的结果是工具箱最大的一代：

- **超级块最大 128×128**：比 H.265 的 64×64 再大一倍，4K/8K 画面的平坦区域收益继续放大；同时支持更细的多级块划分，细节处也不含糊。
- **更多预测与变换工具**：更丰富的帧内方向、多种变换核组合、更强的环路滤波（包括 CDEF 约束方向增强滤波等），以及对胶片颗粒（film grain）的专门处理——合成颗粒参数随码流传输，解码端再合成，省下为随机噪声花的码率。
- **免版税专利许可**：AOMedia 成员承诺对实施 AV1 所必需的专利给予免版税许可，这是 AV1 的立身之本；但第三方专利池（如 Sisvel）对 AV1 的权利主张仍存在争议，具体进展以官方发布为准（待核实）。
- **最大的代价是编码算力**：AV1 参考编码器 libaom 早期以“慢”著称；生产环境多用 Intel 与 Netflix 主导的 SVT-AV1 等优化实现，即便如此，同样画质下 AV1 的编码耗时仍明显高于 H.264。

### 4.5 代际共性：每一代都在“更细的搜索”上加码

四代标准的技术演进有一条共同主线：

| 维度 | H.264 | H.265 / VP9 | AV1 |
|---|---|---|---|
| 最大块尺寸 | 16×16 宏块 | 64×64 | 128×128 超级块 |
| 块划分 | 固定宏块细分 | 四叉树递归切分 | 更多级递归切分 |
| 帧内预测模式 | 9 种 | 35 种（H.265） | 更多方向与模式 |
| 变换 | 4×4 / 8×8 | 更多尺寸组合 | 更多变换核组合 |
| 环路滤波 | 去块滤波 | 去块 + SAO | 去块 + CDEF 等 |

规律是：**块越大越自适应、模式越多、滤波越强，压缩率越高；但编码器要试的组合呈指数级增长**。所以每一代标准的落地都依赖两件事：更强的编码器实现（更好的搜索剪枝），以及硬件解码的跟进。只看标准发布时间判断“该换了”，会漏掉这两件事。

## 5. 关键设计取舍

- **压缩率换算力**：AV1 与 H.265 比 H.264 省码率，但编码耗时与解码算力同步上涨。点播可以离线慢慢压，直播与实时通话压不起——场景先定，标准后选。
- **先进换兼容**：H.264 几乎全设备硬解；H.265 与 AV1 的硬件解码正在普及，但老设备、部分浏览器与机顶盒仍有缺口。选型前先看目标观众的设备分布，而不是看标准的新旧。
- **标准换实现**：同一标准、不同编码器，画质与速度差距很大。x264 的“慢档”可能压过仓促的 x265；AV1 用 SVT-AV1 与用参考编码器的成本完全不同。不要只报标准名就下结论。
- **专利换自由**：H.264/H.265 的专利池意味着可预期的合规成本与法律确定性；VP9/AV1 的免版税意味着更低的直接成本，但第三方权利主张的争议需要持续关注（见第 6 节）。

## 6. 分类与变体

### 6.1 演进对照（定位、年份、组织）

| 标准 | 发布 | 制定方 | 定位 |
|---|---|---|---|
| H.264 / AVC | 2003 年 | ITU-T 与 MPEG | 兼容性基准，处处能播 |
| H.265 / HEVC | 2013 年 | ITU-T 与 MPEG | 同等主观质量下码率约比 H.264 省一半（因内容与编码器而异），4K 主力之一 |
| VP9 | 2013 年 | Google | 与 H.265 同代、压缩率相当，开放免专利费，YouTube 曾主力 |
| AV1 | 2018 年 | AOMedia | 免版税、压缩率优于 H.265，点播大厂与浏览器主推，编码最吃算力 |
| H.266 / VVC | 2020 年 | ITU-T 与 MPEG | 下一代，压缩率再进一步，普及与许可进行中 |
| AV2 | 推进中 | AOMedia | AV1 后继，规范状态以 AOMedia 官方发布为准（待核实） |

### 6.2 专利与免版税格局（只写公开事实）

| 标准 | 许可模式（公开事实） | 注意点 |
|---|---|---|
| H.264 | 专利池许可（MPEG LA 专利池为主） | 许可条款成熟，商业使用按池规则缴纳；具体费率以官方发布为准（待核实） |
| H.265 | 多个专利池并存（如 HEVC Advance、MPEG LA 的 HEVC 许可等），另有独立权利人 | 池子多、条款不统一是 H.265 推广的最大阻力之一；具体费率与适用范围以官方发布为准（待核实） |
| VP9 | Google 免专利费承诺 | 不收取 VP9 专利许可费 |
| AV1 | AOMedia 免版税专利许可 | 成员专利免版税；但第三方专利池（如 Sisvel）的主张仍存在争议，进展以官方发布为准（待核实） |

提醒：许可费的具体数字、免费额度与豁免条件随时间与司法管辖区变化，**本文不给出费率数字**；商业决策前务必以各专利池与联盟的官方发布为准。

## 7. 应用与限制

按场景的选型建议（先看场景，再看标准）：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 点播转码（通用覆盖） | H.264 打底，多码率 ladder | 兼容性第一，任何设备都能播 |
| 点播转码（省带宽） | H.264 + AV1（或 H.265）双轨 | 高清档用新标准省带宽，低清档用 H.264 保覆盖 |
| 直播推流 | H.264 + CBR + 短 GOP | 编码快、延迟低、不断流优先（见流媒体篇） |
| 实时通话 | VP8/VP9/AV1 实时档 | 延迟优先，接受画质波动 |
| 浏览器播放 | H.264 必备，AV1 逐步加码 | 主流浏览器对 AV1 已逐步支持；H.265 的浏览器支持不齐，以各浏览器官方支持说明为准（待核实） |
| 移动端 | 看芯片硬解清单 | 没有硬解的新标准不如有硬解的老标准 |

限制：

- **编码器实现决定实际效果**：同一标准、不同编码器与参数，画质与速度差距可达数倍；脱离编码器谈标准排名没有意义。
- **硬件解码是硬门槛**：软解 4K AV1/H.265 会让手机发热、掉电、掉帧；目标设备没有硬解时，新标准省下的带宽会被体验账单吃回去。
- **“省一半码率”是条件句**：H.265 相对 H.264、AV1 相对 H.265 的官方压缩率数字，都是在特定测试集与编码器下的结果；真实内容、不同码率段、不同编码器实现下，收益会打折甚至反转。

## 8. 常见误解

- **“新标准一定更好”**：错。好坏取决于场景：直播要的是快与稳，H.264 仍是正确选择；老设备为主的观众群，AV1 再省码率也播不动。
- **“H.265 一定比 H.264 省一半码率”**：错。“约省一半”是同等主观质量、特定条件下的说法，因内容与编码器而异；动画、游戏录屏、噪点多的实拍，收益各不相同。
- **“AV1 完全免费、没有任何专利问题”**：不准确。AOMedia 成员的免版税许可是事实，但第三方专利池的主张与争议同样存在，商业使用前应以官方发布为准（待核实）。
- **“VP9 是 AV1 的旧版，可以直接等同”**：错。AV1 吸收了 VP9 的技术，但工具集与码流互不兼容；已有 VP9 资产不会自动变成 AV1。
- **“只看标准名就能比画质”**：错。编码器实现、参数、码率、内容四者共同决定画质；脱离这些比较标准名，是最常见的选型误诊。

## 9. 可核验示例：同档 CRF 数字不能跨编码器比较

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。测试信号为 ffmpeg 内置 testsrc2 测试图（合成信号，非真实拍摄画面），仅用于验证“跨编码器比较方法”本身，体积结论不外推为压缩率排名。

```bash
# 同一段 3 秒 640x360 测试图，四种编码各压一次
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -c:v libx264 -preset veryfast -crf 28 -an v-h264.mp4
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -c:v libx265 -preset veryfast -crf 28 -an v-h265.mp4
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -c:v libvpx-vp9 -b:v 0 -crf 32 -an v-vp9.webm
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -c:v libaom-av1 -cpu-used 8 -crf 32 -an v-av1.mp4
```

本文写作时实际运行结果：

```
H.264（CRF 28）：162,180 字节
H.265（CRF 28）：197,900 字节
VP9（CRF 32）：  299,750 字节
AV1（CRF 32）：  189,170 字节
```

教训：**CRF 28 的 H.265 体积反而比 CRF 28 的 H.264 大，VP9 体积最大——这不能读作“H.265 不如 H.264”**。四种编码器的 CRF 标尺本来就不一样（x264/x265 的 28 与 libvpx/libaom 的 32 不是同一把尺子），preset 与默认策略也不同；同档数字下的体积排序不是压缩率排名。严肃的横向对比要固定一种办法：要么固定目标码率比画质，要么用 VMAF/PSNR 等客观指标对齐质量后再比码率——直接拿 CRF 数字跨编码器比，是选型时最容易踩的坑。
