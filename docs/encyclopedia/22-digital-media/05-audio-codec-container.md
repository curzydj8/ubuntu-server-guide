# 音频编码与封装格式

## 1. 本章目标

读完本篇能理解：AAC、Opus、MP3、FLAC 这些音频编码各自适合什么、MP4/MKV/WebM 这些封装格式到底装了什么、以及“编码 × 封装”的组合该怎么选——拿到一个文件时，能说出它里面装的是什么、为什么这样装。

## 2. 背景与问题

音频和视频一样，不编码就没法传：CD 规格的未压缩音频约 1.41 Mbps（44.1 kHz × 16 位 × 2 声道），一分钟约 10.6 MB（算账见本组编码篇）。但只讲编码还不够——压好的音频码流本身只是一串没有头尾的字节，必须有人回答：这段音频的采样率是多少？视频轨和音频轨怎么对齐？从中间拖进度条该从哪里开始读？字幕、封面、章节信息放哪里？

回答这些问题的就是**封装格式**。编码与封装是两层分工：

- **编码（codec）**：决定“声音怎么压”，如 AAC、Opus、MP3、FLAC。
- **封装（container）**：决定“压好的音轨、视频轨、字幕、元数据怎么装在一个文件里”，如 MP4、MKV、WebM。

一个文件是否能播、好不好拖进度条、能不能挂多条音轨，更多是封装的事；音质好不好、体积多大，更多是编码的事。两者混为一谈，是选型时最常见的混乱来源。

## 3. 总体架构

从原始声音到一个可播放文件的流水线：

```
PCM 原始音频 → 音频编码器 → 音频码流
视频编码器 → 视频码流            ↘
字幕 / 元数据 / 封面               → 复用器（muxer）→ 容器文件（.mp4 / .mkv / .webm）
播放时反向：解复用（demuxer）按轨道拆出码流 → 各自解码 → 按时间戳同步播放
```

容器文件里通常有四类东西：

- **轨道（track）**：一条视频轨、一条或多条音轨、字幕轨等；每条轨道独立标注自己的编码格式。
- **时间戳**：每帧数据贴上“该在第几毫秒出现”的标签，音画同步与变速播放都靠它。
- **索引/寻址表**：记录关键帧与数据块在文件里的位置，没有它，拖进度条只能从头顺序扫描。
- **元数据**：标题、艺术家、封面、章节、语言标记等描述信息。

一个关键推论：**封装不改码流**。把同一条 H.264 + AAC 从 MP4 换装进 MKV（只做转封装 remux，不转码），音画质量逐位不变，变的只是盒子与兼容性。

## 4. 工作机制

### 4.1 音频编码怎么做：三条技术路线

采样与量化、PCM、人耳掩蔽效应的基础见本组编码篇。音频编码器在此基础上的做法分三条路线：

**第一，通用有损编码（AAC、MP3、Vorbis）**：以变换编码（MDCT 一类）为主，把音频切成短帧、变换到频域，再按心理声学模型分配码率——人耳听不见的频段少给甚至不给，听得见的重点保。AAC 是 MP3 的后继：同样的码率，AAC 的听感通常好于 MP3，尤其在中低码率；MP3 靠历史兼容性续命，新项目不优先选。

**第二，语音与音乐双核编码（Opus）**：Opus 把两套引擎拼进一个编码器——SILK 负责语音（基于线性预测，擅长人声的周期性），CELT 负责音乐（基于变换编码，擅长宽频信号），编码器逐帧判断内容类型并切换。加上 2.5–60 ms 可调的极短帧长，Opus 同时做到了低延迟与全频段覆盖，这正是它成为 WebRTC 强制音频编码的原因。

**第三，无损编码（FLAC、ALAC）**：不做心理声学丢弃，只做两件事——线性预测（猜出下一个采样值的大致位置）与残差熵编码（只存“猜错的部分”）。解码后与原始 PCM 逐位一致，代价是体积只压到 PCM 的一半左右，约为同等时长有损编码的数倍。无损编码压的是冗余，不是感知。

### 4.2 封装怎么做：盒子、交错与索引

**MP4（MPEG-4 Part 14，ISO/IEC 14496-14）**：基于 ISO 基础媒体文件格式，采用“盒子（box）嵌套”结构：文件类型盒（ftyp）、影片信息盒（moov，含轨道与索引表）、媒体数据盒（mdat，装实际音视频数据）。moov 是 MP4 的“目录”——播放器先读 moov 才知道文件里有什么、该怎么播；moov 放在文件尾时，网络播放要等整个文件下完才能开播（所谓 faststart 就是把 moov 移到文件头）。MP4 的长处是兼容性：几乎所有设备与浏览器都能播；短处是扩展受限，装多音轨、多字幕不如 MKV 自由。

**MKV（Matroska）**：开放的 EBML 可扩展结构，2002 年启动的开源项目。设计目标就是“什么都能装”：不限轨道数、不限编码组合、多字幕、多章节、附件（字体、封面）都能塞进一个文件。长处是功能最全、归档与收藏的首选；短处是部分设备、机顶盒与苹果生态支持不完整，播之前要确认播放端。

**WebM**：Matroska 的受限子集，由 Google 于 2010 年推出，专为网页视频而生：视频只允许 VP8/VP9/AV1，音频只允许 Vorbis/Opus。限制换来的是简单与一致——浏览器实现 WebM 解复用的成本低，网页播放最顺；代价是 H.264/AAC 这类组合进不了 WebM。

**Ogg 与裸格式**：Ogg（Xiph.Org）是页式流式容器，适合边下边播，装 Vorbis 或 Opus（Opus 在 Ogg 中的映射由 RFC 7845 规定，推荐扩展名 .opus）；MP3 文件本身没有容器，是裸帧直接拼接——没有全局头、没有索引，靠帧同步头定位，拖进度条只能靠码率估算，这也是 MP3 文件“跳转不准”的结构原因。WAV 则是 RIFF 容器装 PCM，通常不压缩，适合编辑中间档而非分发。

**交错存放（interleaving）**：复用器把音视频数据按时间切成小块、交错着写进文件，播放器读一小段就能同时拿到音画；不交错的文件，播放器要来回跳读，网络播放会频繁卡顿。转封装时交错策略不同，也会影响流式播放体验。

## 5. 关键设计取舍

- **有损换体积，无损换保真**：有损编码（AAC/Opus/MP3）用“扔掉听不见的”换数倍压缩；无损编码（FLAC/ALAC）一个比特不扔，体积只压一半。归档选无损，分发选有损；有损反复转码会叠加损失（代际损失），工作流里只在最后导出时转一次有损。
- **通用换功能**：MP4 处处能播但装得少；MKV 什么都能装但不是处处能播；WebM 网页最顺但编码选择受限。没有全能的盒子，只有场景合适的盒子。
- **延迟换效率**：Opus 的短帧与可变码率是为实时互动生的；AAC 的高压缩效率是为点播与发行生的。播客、音乐、通话对“延迟”的要求完全不同，编码选型先问延迟预算。
- **兼容换先进**：Opus、AV1 组合在浏览器里很顺，在老车机、老功放、老机顶盒上可能直接无法识别。受众设备越老，选型越要保守。

## 6. 分类与变体

### 6.1 音频编码定位

| 编码 | 发布与标准 | 类型 | 定位与取舍 |
|---|---|---|---|
| MP3（MPEG-1 Audio Layer III） | 1993 年，ISO/IEC 11172-3 | 有损 | 历史兼容性之王，几乎所有设备能播；压缩效率已被 AAC、Opus 超过；相关专利已于 2017 年到期，Fraunhofer 于 2017 年 4 月终止了 MP3 许可计划 |
| AAC（Advanced Audio Coding） | 1997 年，ISO/IEC 13818-7（MPEG-2），后纳入 MPEG-4 | 有损 | MP3 的后继，同等码率听感更好；视频的默认配对音频（MP4 标配）、苹果生态默认；分 LC、HE-AAC、HE-AAC v2 等档，低码率档用频带复制等技术再省码率 |
| Opus | 2012 年 9 月，IETF RFC 6716 | 有损 | 语音 + 音乐双核、低延迟（帧长可至 2.5 ms）、码率 6–510 kbps、内部 48 kHz；WebRTC 强制音频编码，互动场景最优；免版税 |
| Vorbis | 2000 年，Xiph.Org | 有损 | 开放免版税的老牌通用编码；Xiph 自 2013 年起对新项目推荐 Opus 而非 Vorbis |
| FLAC（Free Lossless Audio Codec） | 2001 年，Xiph.Org | 无损 | 体积约为 PCM 的一半，解码逐位一致；归档与无损发行的事实标准；不适合流媒体 |
| ALAC（Apple Lossless） | Apple | 无损 | 苹果生态的无损编码，功能对标 FLAC；跨生态兼容性弱于 FLAC |
| WAV / PCM | 1991 年，Microsoft 与 IBM（RIFF/WAVE） | 未压缩 | 不是编码，是原始采样数据本身；编辑中间档，不用于分发 |

### 6.2 封装格式定位

| 封装 | 结构 | 允许的编码 | 定位与取舍 |
|---|---|---|---|
| MP4（.mp4 / .m4a） | ISO 基础媒体文件格式，box 嵌套 | 视频：H.264/H.265/AV1 等；音频：AAC/ALAC 等 | 兼容性之王，手机、浏览器、电视处处能播；.m4a 是只装音频的 MP4；Opus 装进 MP4 在部分播放器上支持参差，以播放器实测为准（待核实） |
| MKV（.mkv） | Matroska，EBML 可扩展 | 几乎任意组合 | 功能最全：多音轨、多字幕、章节、附件；归档与收藏首选；部分设备与苹果生态支持不完整 |
| WebM（.webm） | Matroska 受限子集 | 视频：VP8/VP9/AV1；音频：Vorbis/Opus | 网页播放最顺，浏览器原生支持好；编码选择受限，装不进 H.264/AAC |
| MOV（.mov） | Apple QuickTime | 与 MP4 同源，编解码选择相近 | 苹果生态的编辑与分发格式；MP4 与之同源，多数内容可互通 |
| AVI（.avi） | Microsoft，1992 年，RIFF | 老式组合为主 | 历史遗留格式，索引与元数据能力弱，新项目不选 |
| Ogg（.ogg / .opus） | Xiph.Org，页式流式结构 | Vorbis、Opus、FLAC 等 | 流式友好，开放生态；通用播放器支持弱于 MP4 |
| FLAC 原生（.flac） | FLAC 自有封装 | 仅 FLAC | 无损音乐分发常用；本质是“FLAC 码流 + 最小封装” |

### 6.3 常见组合矩阵（“编码 × 封装”怎么配）

| 组合 | 常见度 | 说明 |
|---|---|---|
| MP4：H.264/H.265 + AAC | 最常见 | 点播、手机拍摄、社交平台的默认组合 |
| MP4：AV1 + AAC/Opus | 日渐常见 | AV1 点播的高清档；Opus 配 MP4 的播放器支持参差，以实测为准（待核实） |
| WebM：VP9/AV1 + Opus | 网页标准组合 | YouTube、浏览器播放的主力 |
| MKV：H.264/H.265/AV1 + AAC/FLAC/Opus/DTS 等 | 收藏与归档常见 | 蓝光原盘、影视收藏、多音轨多字幕场景 |
| MP3 裸帧 / M4A（AAC） | 音乐分发常见 | 纯音频文件，不需要视频轨 |
| MKV：H.264 + FLAC | 归档常见 | 视频有损、音频无损的混合归档思路 |

### 6.4 按场景选型

| 场景 | 推荐组合 | 理由 |
|---|---|---|
| 音乐发行（流媒体） | AAC（.m4a）或 Opus | AAC 兼容最广；Opus 同等听感码率更低，适合自有 App 与网页 |
| 播客 / 语音 | Opus 或 AAC | Opus 低码率下语音清晰度最好；AAC 兼容最稳 |
| 视频配音 / 点播 | MP4：H.264/H.265 + AAC | 处处能播，平台上传零转换 |
| 网页视频 | WebM：VP9/AV1 + Opus | 浏览器原生支持，无插件 |
| 影视收藏 / 归档 | MKV：原编码 + FLAC/无损音轨 | 功能最全，画质音质零二次损失 |
| 实时通话 / 连麦 | Opus（WebRTC） | 低延迟是硬指标，其他编码不在候选内 |
| 音频编辑中间档 | WAV/PCM 或 FLAC | 编辑过程零损失，最后导出再转有损 |

## 7. 应用与限制

- **转封装不转码**：只换盒子不换编码时（如 MP4 → MKV），用 ffmpeg 的 `-c copy` 直接复制码流，速度极快且质量逐位不变；只有播放器不支持该盒子时才需要转封装。
- **转码只会降质**：AAC → Opus、MP3 → AAC 这类有损到有损的转换，每转一次叠加一次损失；拿到源文件后先确认原始编码，尽量只转一次。
- **字幕与多音轨是封装问题**：要挂多条字幕、多条语言音轨、章节跳转，优先选 MKV；MP4 也能装但工具与播放器支持参差，事前要验。
- **网络播放看 moov**：MP4 的 moov 在文件尾时，边下边播要等很久；压制 MP4 用于网络分发时，应把 moov 移到文件头（faststart），否则首播延迟会异常大。
- **限制**：本文不展开环绕声编码（AC-3/DTS）与沉浸式音频（杜比全景声等）的声道布局细节；DASH/HLS 的分段封装（fMP4）属于流媒体分发层，与本文的“文件封装”衔接处未展开，见流媒体篇与未完成项。

## 8. 常见误解

- **“MP4 是编码格式”**：错，MP4 是封装；AAC、H.264 才是编码。说“MP4 音质”没有意义，要说“MP4 里 AAC 音轨的音质”。
- **“m4a 是一种编码”**：错，.m4a 是只装音频的 MP4 文件，里面通常是 AAC 或 ALAC；编码与扩展名是两回事。
- **“FLAC 比 WAV 音质好”**：错。FLAC 解码后与 WAV 逐位一致，听感相同；FLAC 的优势是体积小一半、元数据全，不是音质更高。
- **“MP3 音质差”**：不准确。128 kbps 与 320 kbps 的 MP3 是两种体验；编码器实现（LAME 与其他）也有差距。MP3 的问题是“同等码率下效率落后”，不是“不能听”。
- **“封装决定音质”**：错。封装只决定兼容性、功能与寻址，不改码流；同一条 AAC 从 MP4 换到 MKV，音质逐位不变。
- **“Opus 只能用于通话”**：错。Opus 的 CELT 音乐核同样擅长音乐，低码率音乐流媒体也可用；它“通话最优”不等于“只配通话”。

## 9. 可核验示例：同一段信号，三种容器装的轨道一览

> 环境：代理 VM（Ubuntu 24.04），ffmpeg 8.1.2。测试信号为 ffmpeg 内置 testsrc2 测试图与 440 Hz 正弦波（合成信号，非真实拍摄与录音），仅用于验证“容器与轨道”的对应关系；音频体积结论不外推到真实音乐。

```bash
# 同一段音视频，分别装进 MP4、WebM、MKV
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -f lavfi -i sine=frequency=440:duration=3 \
  -c:v libx264 -preset veryfast -crf 28 -c:a aac -b:a 128k -shortest c-mp4.mp4
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -f lavfi -i sine=frequency=440:duration=3 \
  -c:v libvpx-vp9 -b:v 0 -crf 32 -c:a libopus -b:a 128k -shortest c-webm.webm
ffmpeg -y -f lavfi -i testsrc2=size=640x360:rate=30:duration=3 -f lavfi -i sine=frequency=440:duration=3 \
  -c:v libx264 -preset veryfast -crf 28 -c:a flac -shortest c-mkv.mkv
ffprobe -v error -show_entries stream=codec_type,codec_name -of csv=p=0 c-mp4.mp4 c-webm.webm c-mkv.mkv
```

本文写作时实际运行结果：

```
c-mp4.mp4： video h264 / audio aac
c-webm.webm：video vp9  / audio opus
c-mkv.mkv： video h264 / audio flac
```

另附同一段 3 秒 440 Hz 正弦波的四种音频编码体积（已实测，仅作“纯音极易压缩”的演示）：AAC 47,966 字节、Opus 55,407 字节、MP3 48,945 字节、FLAC 44,323 字节。教训：**单一纯音测不出编码器差距**——正弦波对任何编码器都 trivially 可压，体积排序与听感排名无关；严肃的音频编码对比要用真实音乐与语音、固定码率、盲听或 PEAQ 等客观指标，拿纯音体积比编码器是无效比较。
