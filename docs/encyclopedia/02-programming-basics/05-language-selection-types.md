# 编程语言选型与类型系统入门（实践视角）

## 1. 一句话定义

类型系统是一套“值能是什么类型、能对它做什么操作”的规则；选型时看清一套语言的类型规则，就等于看清了它会在什么时候、以什么方式拦住你的错误。

## 2. 为什么需要它

同一段“把用户输入加 1”的代码，在不同语言里可能静默通过、编译时报错、运行时报错，或者算出一个你没想要的结果。差别不在语法，而在类型系统：它决定错误暴露的时机（写代码时、编译时还是运行时）、以及语言会不会替你“猜”类型转换。

选型时如果只看“这门语言火不火”，上线后就会为类型问题反复买单：动态语言的错常在运行时才现身，静态语言的错常在前期就逼你写更多类型信息。先理解类型系统的四个维度，再谈选哪门语言，才不容易被单一优点带偏。

## 3. 核心含义

类型系统的实践维度有三组，彼此独立，不要混为一谈。

### 3.1 静态与动态：类型在什么时候确定与检查

- **静态类型：**类型在执行前（通常是编译时）就确定并检查，类型不匹配在运行前被拒绝。Java、C++、Rust、Go 属此类。
- **动态类型：**类型在运行时才确定与检查，同一变量在不同时刻可以绑定不同类型的值。Python、Ruby、JavaScript 属此类。

注意：静态/动态说的是“类型何时确定”，不是“编译还是解释”——两者是不同维度，不要把“动态”等同于“解释执行”。

### 3.2 强类型与弱类型：类型错配时语言管得多严

- **强类型：**对类型错配管得严，不默默做隐式转换；类型不对的操作直接报错，要求程序员显式转换。Python 是典型例子：`1 + "1"` 不会被“好心”转成 `"11"`，而是直接抛错。
- **弱类型：**允许较宽松的隐式转换，语言会按自己的规则把一边转成另一边再运算，写起来省事，但结果可能出乎意料。JavaScript 是典型例子：`1 + "1"` 得到字符串 `"11"`，而 `"5" - 1` 却得到数字 `4`——同一门语言在不同运算符下用了不同的转换规则。

**必须提醒的一点：强/弱没有统一精确的定义。**不同资料对同一门语言的归类也可能不一致（例如 C 在有的资料里算弱类型、有的资料里只在部分意义上算强类型），所以四象限只能当作选型时的粗略地图，具体到一门语言，一定要按它的实际行为判断，不能只记标签。本篇的强/弱用法统一为上面这段操作含义：是否默默隐式转换、错配时是否直接报错。

### 3.3 类型推断与渐进类型：少写标注，但不放弃检查

- **类型推断（type inference）：**编译器自动推导出表达式的类型，程序员不必处处手写标注。分两种常见形态：局部推断（只在小范围内推，如 Go 的 `:=`、Java 10 起的 `var`）和更完整的推断（Hindley–Milner 体系，Haskell、OCaml、ML 一脉，编译器能推导出最一般的类型）。推断出的类型仍然是静态检查的——“不用写”不等于“没有类型”。
- **渐进类型（gradual typing）：**在动态语言里逐步引入静态检查。Python 的类型标注（PEP 484，Python 3.5 起）就是渐进类型：标注是给人和静态检查工具（mypy、pyright）看的，解释器在运行时并不强制执行它；TypeScript 则是给 JavaScript 加上静态类型与推断的渐进路线。渐进的好处是老代码不用重写，可以先给关键模块加标注；代价是“标注了”不等于“运行时安全了”，边界处仍需测试兜底。
- **鸭子类型（duck typing）：**动态语言里常见的做法——不看对象声明的类，只看它实际有没有所需的方法和属性（“走起来像鸭子、叫起来像鸭子，就当它是鸭子”）。它是动态类型在实践中的自然形态，但缺失方法时错误只在运行时现身。

三组维度的关系可以用一张表收拢：

|  | 强类型（错配直接报错） | 弱类型（允许隐式转换） |
| --- | --- | --- |
| 静态（执行前检查） | Java、Rust、Go | C、C++（部分场景，归类有分歧，见上） |
| 动态（运行时检查） | Python、Ruby | JavaScript、PHP |

表中 C、C++ 的位置只作示意：正因为强/弱无统一定义，它们的归类在不同资料中有分歧，选型时以目标语言的官方文档与实测行为为准。

## 4. 分类

按“错误何时暴露 × 语言管得多严 × 标注要写多少”三个维度，实践选型可分四类：

- **静态强类型 + 显式标注为主：**如 Java、C#。前期写得多、重构与 IDE 支持最好，适合多人长期维护的大型系统；代价是样板代码多、原型速度慢。
- **静态强类型 + 推断为主：**如 Rust、Go、Kotlin。静态检查的收益保留，日常代码不必处处写类型；代价是推断失败时的报错信息有时难读，需要适应编译器的“脾气”。
- **动态强类型 + 可选标注：**如 Python。原型最快，错配时报错明确（不默默转换）；代价是类型错误只在跑到那行时才暴露，大型项目需靠标注 + 检查工具 + 测试共同兜底。
- **动态弱类型：**如 JavaScript（不加 TypeScript 时）。写起来最自由；代价是隐式转换的结果最难预测，稍大项目通常要靠 TypeScript、测试与代码规范来收口。

选型没有“最好的一类”，只有“当前阶段最划算的一类”：原型期看重速度选动态，长期维护看重重构安全选静态，团队规模越大，静态检查与标注的收益通常越大。

## 5. 典型应用

- **写原型、做数据探索时用动态语言：**变量类型可变、不用先声明一整套类型，想法能最快落地验证；但进入生产前要补测试，覆盖“类型在运行时才暴露”的那类错误。
- **给 Python 关键模块加标注并跑检查工具：**标注本身不改变运行行为，但 mypy、pyright 能在运行前拦住一类错配；把检查接进持续集成，标注才不会慢慢过期失效。
- **用 TypeScript 收口 JavaScript 项目：**在不换运行时的前提下拿到静态检查与推断，渐进迁移：先给新模块、核心模块加类型，再逐步覆盖老代码。
- **在静态语言里用推断减少样板：**Go 的 `:=`、Java 的 `var`、Rust 的类型推断让局部变量不必重复写类型；但公开接口（函数签名、模块边界）的类型仍建议显式写清——那是给人阅读和重构的契约。

## 6. 限制与常见误解

- **“静态 = 强、动态 = 弱”**：错。这是两组独立维度，Python 就是动态强类型的反例；把两组维度压成一根轴，是选型时最常见的误判。
- **“加了类型标注就安全了”**：错，至少对 Python 是这样。标注在运行时不被解释器强制执行，见下面实测：标注 `int` 的函数照样接受字符串并跑出结果；真正拦错的是运行检查工具或运行时的显式校验。
- **“类型推断 = 动态类型”**：错。推断是静态检查省掉手写标注的手段，类型仍然在执行前确定；Go 的 `:=` 推断出 `int` 后，再塞字符串一样会在编译时被拒绝。
- **“静态类型就没有运行时类型错误”**：错。静态检查只能排除它“声称”排除的那类错误：空值、越界、逻辑错误、外部输入格式不对，仍可能在运行时出现；类型正确不等于程序正确。
- **“弱类型语言的结果不可预测，所以不能用”**：过了。弱类型的转换规则是确定的、可查的，只是需要学习成本；问题不在于“能不能用”，而在于团队是否愿意为这套规则付测试与规范成本。

### 实测示例

以下示例全部实际运行过，输出逐字记录；没运行的代码本篇一律不标“实测”。

**示例 1：动态 + 强类型（Python）。**同一变量可先后绑定不同类型，但 `int + str` 不隐式转换：

```python
x = 10
x = "ten"
print("dynamic rebind:", x, type(x).__name__)

try:
    print(1 + "1")
except TypeError as e:
    print("strong TypeError:", e)
```

> 实测通过（Python 3.12.3）：输出 `dynamic rebind: ten str`，`strong TypeError: unsupported operand type(s) for +: 'int' and 'str'`。

**示例 2：渐进类型——标注不被运行时强制执行（Python）。**函数标注了 `int`，传字符串仍正常运行：

```python
def add(a: int, b: int) -> int:
    return a + b

print("annotation ignored at runtime:", add("a", "b"))
```

> 实测通过（Python 3.12.3）：输出 `annotation ignored at runtime: ab`。要拦住这类调用，需另跑 mypy、pyright 等静态检查工具（工具本身的配置与版本以官方发布为准，见未完成项）。

**示例 3：动态 + 弱类型（JavaScript）。**同一组值在不同运算符下走了不同的隐式转换：

```javascript
console.log("weak 1 + '1' =", 1 + "1");
console.log("weak '5' - 1 =", "5" - 1);
console.log("weak typeof 1 + '1' =", typeof (1 + "1"));
```

> 实测通过（Node.js v24.22.1）：输出 `weak 1 + '1' = 11`，`weak '5' - 1 = 4`，`weak typeof 1 + '1' = string`。

**示例 4：静态 + 推断（Go）。**`:=` 让编译器推断类型，但类型错配在编译时就被拒绝：

```go
package main

import "fmt"

func main() {
    name := "hello" // 编译器推断为 string，无需手写类型
    count := 3      // 编译器推断为 int
    fmt.Printf("%s %d\n", name, count)
}
```

> 实测通过（Go 1.27.3）：输出 `hello 3`。把 `count` 的声明改成 `var n int = "hello"` 再编译，编译器实测拒绝，报错为 `cannot use "hello" (untyped string constant) as int value in variable declaration`——错误在运行前就暴露，这正是静态类型的收益。

## 7. 小结

选型看三组维度：静态/动态决定错误何时暴露，强/弱决定错配时语言管得多严，推断与渐进类型决定“少写标注”和“保留检查”能不能兼得。
没有最好的类型系统，只有当前阶段最划算的取舍；理论深度见前沿篇的类型系统文章。
