# 解释器、虚拟机与 JIT 入门

## 1. 本章目标

读完本篇，能说清“解释执行”不是一种执行方式而是一族执行方式：树遍历解释、字节码虚拟机、即时编译各解决什么问题，以及为什么现代语言运行时大多是几者的混合。

## 2. 背景与问题

上一篇讲的提前编译（AOT）有一个前提：编译时就知道目标机器。但很多场景不满足这个前提：脚本要“写完立刻跑”，同一份程序要跑在不同机器上，程序行为要到运行时才知道（如动态类型、插件、热更新）。这时需要把一部分翻译推迟到运行时——推迟多少、用什么形式推迟，就分出了本篇的三种执行方式。

另一个动机是启动速度：AOT 编译整个程序要花时间，解释执行可以“解析一点、跑一点”，对短命的脚本、小工具来说，省下的编译时间比损失的执行速度更重要。

## 3. 总体架构

```
源程序
    │
    ├─ 树遍历解释器：解析成 AST → 直接遍历 AST 执行
    │       （无中间代码，启动最快，执行最慢）
    │
    ├─ 字节码虚拟机：解析成 AST → 编成字节码 → 虚拟机逐条执行字节码
    │       （一次编译、多次执行；字节码与机器无关）
    │
    └─ 即时编译（JIT）：字节码 / 中间表示 → 解释执行并画像
            → 热点代码在运行时编成机器码 → 下次直接跑机器码
            （启动快、峰值快，代价是预热与内存）
```

三者不是互斥的选项，而是可以叠加的层：一个运行时可以先解释字节码，再对热点做 JIT；JIT 内部也可以分多层（基线层求快、优化层求强）。现代运行时几乎都是这种分层混合。

## 4. 工作机制

### 4.1 树遍历解释器：最直接，也最慢

树遍历解释器（tree-walking interpreter）不生成任何中间代码：解析出 AST 后，解释器直接按树的结构递归求值——遇到加法节点就先求左右子树再相加，遇到循环节点就反复求值循环体。

下面是一个只支持整数常量、`+`、`*` 的极简树遍历解释器，足以看清机制：

```python
# 极简树遍历解释器：只支持 + * 与整数常量
def ev(node):
    if isinstance(node, int):
        return node
    op, left, right = node
    if op == '+': return ev(left) + ev(right)
    if op == '*': return ev(left) * ev(right)
    raise ValueError(op)
tree = ('+', ('*', 3, 2), 10)
print("tree:", tree, "=>", ev(tree))
```

实测通过（Python 3.12.3，本地运行）：

```
tree: ('+', ('*', 3, 2), 10) => 16
```

它的优点是实现极简单、启动极快，适合教学和小语言原型；缺点同样直接：每次执行都要重新走一遍树、重新做类型分发，没有任何“上次算过”的积累，循环体跑一万次，树就遍历一万次。真实语言很少只用这一层，更多是把它当作原型或备用路径。

### 4.2 字节码虚拟机：一次编译，处处解释

字节码虚拟机在中间加了一层：先把源码（经词法、语法、语义分析，见上一篇）编成字节码（bytecode）——一种紧凑的、面向虚拟机的指令序列；运行时由虚拟机逐条取指、译码、执行。虚拟机是“用软件模拟的 CPU”：它有自己的程序计数器、求值栈或寄存器组，但指令最终还是由宿主机器一条条执行。

CPython 就是这条路线。下面的 `dis` 输出是 CPython 字节码的真实样子：

```python
import dis
def add(a, b):
    return a * 2 + b
dis.dis(add)
print("add(3, 10) =", add(3, 10))
```

实测通过（Python 3.12.3，本地运行）：

```
  2           0 RESUME                   0

  3           2 LOAD_FAST                0 (a)
              4 LOAD_CONST               1 (2)
              6 BINARY_OP                5 (*)
             10 LOAD_FAST                1 (b)
             12 BINARY_OP                0 (+)
             16 RETURN_VALUE
add(3, 10) = 16
```

读这段字节码不需要懂每个操作码的全部语义，抓住结构就够了：`LOAD_FAST` 把局部变量压栈，`LOAD_CONST` 把常量压栈，`BINARY_OP` 从栈顶取两个操作数运算后再压回结果，`RETURN_VALUE` 返回栈顶。这就是“栈式虚拟机”的执行模型——指令本身很简单，复杂性在虚拟机如何高效地分发这些指令。

字节码带来的关键好处是**可移植性**：字节码不依赖任何真实机器，同一份字节码可以在任何装了对应虚拟机的机器上跑。Java 的路线与此同构：`javac` 把 Java 源码编成类文件字节码，JVM 执行它。下面是实测：

```java
public class Hello {
    public static void main(String[] args) {
        int total = 3 * 2 + 10;
        System.out.println("total=" + total);
    }
}
```

实测通过（Temurin JDK 21.0.13，本地运行）：`javac Hello.java` 编译通过，`java Hello` 输出 `total=16`；`javap -c Hello` 的 `main` 方法字节码开头是 `bipush 16`——`3 * 2 + 10` 在编译时已被折叠为常量 `16`（与上一篇的常量折叠是同一机制，只是发生地在字节码编译器里）。

字节码虚拟机的代价是“分发税”：每条字节码都要经过取指、译码、分发，比直接跑机器码多一层间接开销。纯解释执行因此通常慢于 AOT 编译，这是下一层 JIT 要解决的问题。

### 4.3 JIT：运行时编译，用画像换速度

即时编译（Just-In-Time compilation，JIT）的基本想法是：先解释执行，同时记录程序的真实行为（哪些函数是热点、哪些变量实际是什么类型、哪些分支实际走了哪边），这份记录叫画像（profiling）；然后把热点代码按画像出的假设编成高度优化的机器码；下次再执行这段代码，就直接跑机器码，不再经过解释器。

JIT 能做静态编译器做不到的优化，核心原因是**它有运行时信息**：静态编译器不知道一个动态类型变量实际总是整数，JIT 知道；静态编译器不敢假设某个虚方法调用总是指向同一个实现，JIT 可以先按这个假设优化，并在假设失效时退回解释执行（去优化，deoptimization）。去优化是 JIT 正确性的安全网：优化可以大胆猜，猜错必须能无损退回。

分层编译（tiered compilation）是 JIT 的工程形态：不是“解释或 JIT”二选一，而是按热度逐级升级。典型分层是：

```
解释器（启动快，边跑边画像）
    ↓ 代码变热
基线 JIT（编译快、优化浅，去掉解释分发开销）
    ↓ 代码更热
优化 JIT（编译慢、优化深：内联、类型特化、循环优化）
    ↓ 假设失效
去优化 → 回到解释器 / 基线层（保证正确，再重新画像）
```

### 4.4 三个真实运行时：CPython、JVM、V8

**CPython**：标准实现是字节码解释器，3.11 起引入自适应解释器（按画像把通用字节码特化为针对常见类型的版本）。实验性 JIT 自 3.13 起随 PEP 744 引入，采用复制粘贴（copy-and-patch）模板技术；截至核实日期，它仍属实验性质、默认关闭——3.13 需要构建时开启，3.14 的官方 Windows/macOS 安装包已内置但默认仍关闭，需用 `PYTHON_JIT=1` 开启；后续是否转正以官方发布为准（待核实）。本地实测环境是 Python 3.12.3，尚无该 JIT，因此本篇没有“开启 CPython JIT 前后对比”的实测，JIT 分层描述为架构说明而非实测结论。

**JVM（以 HotSpot 为代表）**：解释器起步，热点方法先经快速编译层（C1，编译快、优化浅），最热的代码再经深度优化层（C2，编译慢、优化深），这就是“分层编译”这个词的典型出处。Java 字节码的可移植性与 JIT 的峰值性能结合，是 JVM 路线长盛的原因；代价是预热：程序刚启动时还在解释执行，峰值性能要跑一段时间才达到，短命进程可能还没热起来就结束了。

**.NET CLR 与 V8**：.NET 的公共语言运行时（CLR）同样对中间语言（CIL）做 JIT 编译，并提供提前编译选项作为补充；JavaScript 引擎 V8 的管线是 Ignition 字节码解释器起步，Sparkplug 做基线编译，Maglev 做中层优化，TurboFan 做深度优化，假设失效时去优化回解释层——分层思想与 HotSpot 同构，只是层数与各层名字不同，具体分层阈值与版本细节以官方发布为准（待核实）。Node.js 运行 JavaScript 时走的就是 V8 这条管线，本地实测：

```js
function add(a, b) { return a * 2 + b; }
console.log("add(3,10) =", add(3, 10));
```

实测通过（Node.js 24.22.1，本地运行）：输出 `add(3,10) = 16`。这段实测只证明“Node 能跑这段代码”，不证明它走了哪一层 JIT——分层切换是引擎内部的启发式决策，不由这段输出体现，写文章时不应把“跑通”等同于“观测到 JIT”。

**PyPy**：Python 的另一实现，用追踪 JIT（tracing JIT）记录热点循环的实际执行轨迹并编成机器码；对类型稳定的数值循环加速明显，对类型频繁变化的代码则反复去优化、收益有限。具体加速倍数高度依赖测试程序与版本，以官方发布为准（待核实），本篇不转载倍数断言。

## 5. 关键设计取舍

- **启动换峰值**：解释器启动最快、峰值最慢；AOT 峰值最快、启动要先编译；JIT 两头兼顾，代价是预热期与运行时内存（画像数据 + 编好的机器码都要占内存）。
- **可移植换性能**：字节码换来“一次编译、处处运行”，代价是多一层虚拟机；JIT 在可移植的基础上把热点恢复成机器码，代价是运行时复杂度与去优化机制。
- **假设换速度**：JIT 的优化建立在“过去的行为代表未来”的假设上；假设越具体，优化越强，去优化的风险也越高。类型稳定的代码是 JIT 的甜点，类型飘忽的代码是它的苦点。
- **确定性换自适应**：AOT 的性能在发布前就确定；JIT 的性能取决于真实负载，同一程序在不同输入下可能走完全不同的优化路径，性能测试因此必须用真实负载画像，不能只看空载启动。

## 6. 分类与变体

按“翻译发生在什么时候”分：

| 类别 | 翻译时机 | 启动 | 峰值 | 代表 |
|---|---|---|---|---|
| 树遍历解释 | 无翻译，边解析边执行 | 最快 | 最慢 | 教学解释器、早期脚本实现 |
| 字节码解释 | 运行前编成字节码，运行时解释 | 快 | 中等 | CPython（默认）、Ruby 早期实现 |
| 分层 JIT | 运行时按热度逐级编译 | 快 | 接近 AOT | HotSpot JVM、V8、.NET CLR |
| 提前编译 | 运行前全部编成机器码 | 需编译 | 最快且确定 | GCC、Clang、rustc（见上一篇） |

按 JIT 的优化策略分：方法 JIT（以函数/方法为单位编译，HotSpot、CLR 的主流形态）、追踪 JIT（以热点循环轨迹为单位编译，PyPy、LuaJIT 的形态）、模板 JIT（用预编译的代码模板拼接，CPython 实验性 JIT 的形态）。三种策略的共性是“先画像、再编译、猜错退回”，差别在编译单位与优化深度。

## 7. 应用与限制

典型应用：Web 浏览器与 Node.js 靠 V8 的分层 JIT 跑 JavaScript；服务端 Java/.NET 靠 JVM/CLR 的分层 JIT 兼顾启动与长期峰值；数据分析、运维脚本靠 CPython 的字节码解释换取“写完即跑”；嵌入式与启动敏感场景（如命令行小工具）则常选 AOT，避免预热与运行时开销。

限制：

- JIT 不适合“跑一次就退出”的短命进程：预热还没完成进程就结束了，JIT 的编译成本纯支出。
- JIT 占额外内存：画像、编译缓存、去优化用的备用路径都要内存，内存受限设备上要评估。
- JIT 的性能不可只凭感觉：同一段代码在解释层、基线层、优化层的速度可以差一个量级，压测必须跑到热稳态再取数，冷启动数字与热稳态数字是两回事。
- 安全面：运行时生成并执行机器码，意味着“可写即可执行”的内存区域管理必须谨慎，这是 JIT 运行时必须处理、AOT 不存在的风险面，具体机制超出本篇范围。

## 8. 常见误解

- **“解释型语言就是慢”**：错。慢的是“纯解释层”，不是语言本身；同一门语言换一个带 JIT 的实现，同一段代码的速度可以完全不同。评价执行速度要指明实现与层级，不能只报语言名。
- **“Python 没有编译”**：错。CPython 先把源码编成字节码（`dis` 输出就是证据），“解释型”指的是字节码的执行方式，不是“跳过编译”。
- **“JIT 一定比 AOT 快”**：错。JIT 的优势是运行时信息，劣势是编译时间预算有限、不能做耗时过长的全局优化；对编译时间无限、负载固定的场景，AOT 的深度优化仍可能更强。
- **“跑通 Node 代码就等于观测到 JIT”**：错。本篇 Node 实测只证明代码能跑；JIT 分层切换是引擎内部启发式，不体现在程序输出里，观测它需要引擎提供的画像/日志工具，不在本篇实测范围内。
