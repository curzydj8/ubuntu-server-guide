# 版本控制进阶：Git 工作流

## 1. 本章目标

读完本篇，能说清 Git 的分支模型、合并与变基的取舍、冲突的正确处理方式，以及提交规范的价值：协作不出乱，历史可追溯。

## 2. 背景与问题

多人改同一份代码，没有版本控制会怎样：文件传来传去，谁改了哪行不知道，改坏了回不去，上线前不知道谁的版本才是对的。版本控制解决三个问题：**每一次修改可记录、可回溯、可合并**。Git 是目前最主流的分布式版本控制工具：每个人的本地都是完整仓库，离线也能提交、查历史、开分支。

## 3. 总体架构

Git 的核心是四部分，关系如下：

```
工作区（你编辑的文件）
    │ git add
    ▼
暂存区（下一次提交包含什么）
    │ git commit
    ▼
本地仓库（提交组成的有向无环图 DAG）
    │ git push / git pull
    ▼
远程仓库（协作的汇合点）
```

关键理解点：

- **提交是快照，不是差异**：每个提交记录整个文件树的状态（内部以内容寻址的对象存储，对象 ID 就是内容的哈希——哈希思想见本批第一篇）。
- **分支是指针，不是副本**：新建分支只是新建一个指向某个提交的指针，几乎零成本；这就是 Git 鼓励多开分支的底气。
- **HEAD 是当前位置**：它指向你当前所在的分支，切换分支就是移动 HEAD。

## 4. 工作机制

### 4.1 提交与分支

一次好的提交只做一件事，提交信息说清“为什么”，而不是“做了什么”（代码本身已经说了做了什么）。分支的常规操作：

```bash
git checkout -b feature   # 新建并切换到 feature 分支
# …改代码…
git commit -am "feat: 增加功能"
git checkout main
git merge --no-ff feature -m "merge: 合并 feature"
```

实测（Git 2.43.0，本地演示仓库，身份为演示用）：

```
*   abee2b1 merge: 合并 feature
|\
| * cfa1299 feat: 增加功能
|/
* 5b5fbc4 feat: 初始版本
```

`--no-ff` 保留了一个合并提交，历史里能一眼看出“这次合并对应哪次功能开发”。不用 `--no-ff` 时，如果主线没动过，Git 会直接快进（fast-forward），分支痕迹消失——小修小补可以快进，功能开发建议保留合并提交。

### 4.2 合并（merge）：保留真实历史

合并是把两个分支的修改汇合，产生一个有两个父提交的合并提交。优点：历史真实，什么时候从哪分叉、什么时候汇合，一目了然；冲突处理发生在合并提交里，可追溯。缺点：分支一多，历史图呈网状，长期不合并的主线会很难读。

适用：多人协作的主线、功能分支合入、发布分支合入。也就是绝大多数团队的默认选择。

### 4.3 变基（rebase）：换来线性历史

变基是把当前分支的提交“拔起来”，接到目标分支的最新提交之后重放一遍，历史变成一条直线。

```bash
git checkout hotfix
git rebase main
```

实测（Git 2.43.0，本地演示仓库）：

```
Successfully rebased and updated refs/heads/hotfix.
* 0483a22 fix: 修复 fix.txt
* 051bde1 feat: 主线新增 new.txt
* aa3b0e2 feat: 初始版本
```

优点：历史线性、干净，`git log` 从上到下就是时间线。代价与红线：**变基改写提交 ID**。因此，**已经推送到远程、别人可能已经基于它工作的分支，绝不能变基**——否则别人的历史与你的历史对不上，只能强制推送收场，而强制推送可能覆盖别人的提交。变基只用于整理自己本地、尚未公开的提交。

合并与变基的取舍一句话：要真实选合并，要整洁选变基；公开历史只合并、不变基。

### 4.4 冲突：不是事故，是正常信号

当两个分支改了同一文件的同一处，Git 无法自动判断该听谁的，就会停下来让你决定。实测（Git 2.43.0，本地演示仓库）：

```
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
```

文件里会出现冲突标记：

```
<<<<<<< HEAD
main-line
=======
side-line
>>>>>>> side
```

处理流程固定四步：

1. 打开文件，看清两边各改了什么、为什么这样改（先理解，再动手）。
2. 编辑成正确的结果：可能是取一边，可能是两边都要，可能是两边都不对、要写第三种。
3. 删除所有冲突标记，`git add` 标记为已解决。
4. 提交合并结果，提交信息写清“为什么这样解决”，而不是只写“解决冲突”。

实测解决后的历史：

```
*   8c97c5a merge: 解决冲突，保留已确认版本
|\
| * a2bb941 side: 改第一行
* | 1514fa5 main: 改第一行
```

冲突本身不可怕：可怕的是不看内容就选一边，或者把标记留在文件里提交上去。合并前跑一次构建与测试，是防止“解决了冲突、引入了错误”的最低成本办法。

### 4.5 提交规范：让历史可读、可自动化

推荐 Conventional Commits 风格：`类型(范围): 描述`，例如 `feat(auth): 增加短信登录`、`fix(api): 修复空指针`、`docs(readme): 补充安装步骤`。类型常用：feat（新功能）、fix（修复）、docs（文档）、refactor（重构，不改行为）、test（测试）、chore（杂务）。

价值有三：看日志就知道每次提交的性质；工具可以按类型自动生成变更日志；出了问题按类型筛选，比翻“改了点东西”之类的提交快得多。规范贵在坚持：团队定一个，写进贡献文档，所有人遵守。

## 5. 关键设计取舍

- **真实换整洁**：合并保留分叉与汇合的真实过程，历史诚实但显乱；变基牺牲真实过程换取线性整洁，但改写历史。公开协作选真实，个人整理选整洁。
- **粒度换可读性**：提交太粗（一次提交改十处），回滚与定位都难；提交太碎（改一行提交一次），历史噪音大。标准是“一次提交只做一件事，且这件事可独立描述”。
- **自动化换自由度**：提交规范、分支保护、合并前检查，都是对自由的约束，换来的是协作规模扩大后不出乱。小团队可以松，大团队必须紧。

## 6. 分类与变体：三种分支模型

| 模型 | 做法 | 适用场景 | 注意事项 |
|---|---|---|---|
| Git Flow | main、develop、feature、release、hotfix 多分支 | 固定版本发布、有发布窗口的团队 | 分支多、管理成本高，小团队容易过度设计 |
| GitHub Flow | main + 短期 feature 分支，合并即部署 | 持续部署、快速迭代的团队 | 依赖自动化测试与发布流水线，主线必须随时可发布 |
| Trunk-based | 所有人直接向主线提交小步增量，或极短期分支 | 追求交付速度、有完善测试与特性开关的团队 | 对测试覆盖与代码评审要求最高，不适合无自动化保障的团队 |

没有哪种模型“最先进”：选模型先看发布节奏与自动化水平，再看团队规模。模型定下来就写进团队文档，不要每人一套。

## 7. 应用与限制

适用：多人协作的任何代码项目、文档项目、配置管理；个人项目同样受益（历史就是后悔药）。不适用或需谨慎：

- 大二进制文件（视频、模型权重、大型数据集）不适合直接进 Git 历史：每次修改都存一份快照，仓库会迅速膨胀；这类文件应走对象存储或专用大文件方案。
- 已推送的公开分支不要变基、不要强制推送；实在要改历史，先和所有协作者确认。
- Git 不解决“需求不清”：分支模型再好，也救不了没有评审、没有测试的协作。

## 8. 常见误解

- **“rebase 比 merge 高级”**：错。两者是取舍，不是等级；公开历史用 merge 是纪律，不是落后。
- **“冲突说明有人做错了”**：错。冲突说明两个人都改了同一处，是协作的正常信号；按流程解决即可。
- **“提交信息随便写写就行”**：错。三个月后定位问题时，提交信息就是第一线索；“改了点东西”等于没有线索。
