# 分支策略与代码评审流程

## 1. 一句话定义

分支策略是团队约定“代码从哪分叉、在隔离中活多久、以什么条件合回主线”的规则，代码评审则是合入主线之前由他人检查变更的流程；前者管节奏，后者管质量，两者合起来才构成可协作的主线。

## 2. 为什么需要它

没有分支策略，十个人就有十种合入习惯：有人直接推主线，有人开三个月不合的长分支，发布前夜才发现各分支互相冲突、谁的版本都不能单独上线。没有评审，主线就只能靠作者自己的检查兜底，而作者最容易漏的恰恰是自己写错的地方。策略与评审不是为了“管人”，而是把“什么时候能合入、谁说了算”从口头默契变成可执行的约定。

本篇不重复合并与变基的机制、冲突处理步骤、提交信息规范——那些在 [Git 工作流](02-git-workflows.md) 已讲全；本篇讲的是机制之上的选择：选哪种策略、评审按什么流程走、清单查什么。对象模型层面的“分支是指针”背景见 [Git 对象模型与内部原理](10-git-internals.md)。

## 3. 核心含义

### 3.1 分支策略的三要素

任何策略都可以用三个问题描述清楚，选型时先对齐这三个答案，再谈名字：

1. **主线有几条、各自代表什么**：只有一条可发布主线，还是另有一条集成线、一条发布线？
2. **分支活多久**：几小时、几天，还是几周？分支活得越久，合入成本越高，这是所有策略比较里最硬的指标。
3. **合入的门槛是什么**：评审通过即可，还是必须加自动化测试、发布检查、特定人员批准？

### 3.2 三种主流策略

#### GitFlow：为固定版本发布设计的重型模型

Vincent Driessen 在 2010 年提出的模型，核心是按用途分工的分支族：`main` 只放已发布的正式版本（每次合入都打标签），`develop` 是下一版本的集成线，`feature/*` 从 `develop` 分出、合回 `develop`，`release/*` 从 `develop` 分出做发布前稳定（只修 bug、不加功能），最后合回 `main` 并打标签、同时合回 `develop`；线上紧急修复走 `hotfix/*`，从 `main` 分出、两边都合回。

它适合的场景很具体：有固定发布窗口、多版本同时在外服役、需要把“开发中”和“已发布”严格分开的软件（桌面软件、应用商店上架、需要合规审计的版本）。代价同样具体：长期分支多、合入路径长、管理成本高；`develop` 一旦成为瓶颈，持续交付就被拖慢。Driessen 本人后来也补充过：持续交付的团队不应照搬 GitFlow——这个模型是为多版本在外并存设计的，不是为一天部署多次设计的。

#### GitHub Flow：一条主线 + 短期分支的轻型模型

规则只有两条硬性约定：`main` 随时可部署；所有工作都从 `main` 开短期分支，提拉取请求（Pull Request，PR），评审与自动化检查通过后合回 `main`，合入即部署。没有 `develop`，没有发布分支，发布就是主线的当前状态。

它适合大多数 Web 服务与小团队：持续部署、线上只有一个生产版本、想用最少的分支 bookkeeping 换来评审与部署纪律。前提必须说清楚：`main`“随时可部署”不是口号，它要求每次 PR 都跑完整测试、主线变红即停线处理；没有这条纪律，GitHub Flow 会退化成“直接合入主线再祈祷”。

#### 主干开发（Trunk-Based Development）：把“短”推到极致

主干开发只有一条主干（trunk，即 `main`）：开发者直接向主干提交，或用存活几小时到一天的极短期分支，每天至少一次合入主干；未完成的功能不靠分支隔离，而是靠特性开关（feature flag）在主干里藏起来——代码合入了，但开关关闭时用户看不到，开关打开才逐步放量。

它换来的是最高的集成频率与最低的合入成本，代价是对工程能力的要求也最高：快速可靠的持续集成、足够强的测试覆盖、特性开关的管理与清理、主干变红立即修复的文化，缺一不可。没有这些支撑，主干开发会悄悄退化回长分支开发，只是换了个名字。

### 3.3 选型比较：先看发布节奏，再看团队规模

| 维度 | GitFlow | GitHub Flow | 主干开发 |
|---|---|---|---|
| 长期分支 | `main` + `develop` + `release` | 仅 `main` | 仅主干 |
| 分支寿命 | 数天到数周 | 数小时到数天 | 数小时到一天 |
| 发布节奏 | 按计划版本发布 | 合入即部署 | 持续部署，多次 / 天 |
| 隔离未完成功能的手段 | 分支 | 分支 | 特性开关 |
| 对自动化测试的要求 | 中等 | 较高 | 最高（强制） |
| 适合场景 | 版本化软件、多版本并存、审计严格 | 多数 Web 服务、小到中型团队 | 成熟团队、高频交付、有完善 CI 与开关管理 |

选型口诀：**先看发布节奏，再看自动化水平，最后看团队规模**。一天部署多次的服务选 GitFlow 是自找瓶颈；没有自动化测试兜底的团队上主干开发是裸奔；多数团队的合理起点是 GitHub Flow，等测试与发布能力成熟后再向主干开发演进，而不是一开始就抄最激进的模型。策略定下来要写进团队文档并执行一致，策略本身比“选了哪个名字”更重要；策略变更（例如从 GitHub Flow 迁向主干开发）要当成一次正式变更来做：先补齐 CI 与开关能力，再缩短分支寿命上限，而不是只改文档里的名字。

### 3.4 评审流程：从开 PR 到合入的固定走法

一次评审的标准走法分六步，顺序有讲究——先看意图与设计，再看细节，避免在行为或授权问题还没看清时就陷入格式争论：

1. **作者自查**：提交前自己逐段读一遍 diff，删调试代码、确认测试覆盖了改动的行为与重要失败路径；PR 描述按模板写清（见 3.5 节）。
2. **开 PR 并过自动化关卡**：构建、测试、静态检查先跑；自动化红着的 PR 不应进入人工评审——人工时间不该花在机器能发现的问题上。
3. **评审者读意图**：先读 PR 描述与关联 issue，用一句话说出这次变更要达成的行为，再看 diff；意图不清的 PR 先问清意图，不猜着评审。
4. **按清单评审**：从设计、正确性、测试、安全、可读性依次检查（清单见 3.6 节），意见分级标注：必须改（Blocking）、建议改（Suggestion）、吹毛求疵（Nit）。
5. **作者回应与修改**：逐条回应意见，改动后重新请求评审；不要把“已解决”点掉却不改，也不要把评审意见当成个人评价来回怼。
6. **批准与合入**：批准的标准是“这次变更明确改善了代码整体健康”，而不是“完美无缺”——等完美才批准，等于用评审堵住交付。合入后主线变红，作者与评审者共同负责第一时间处理。

评审的另外两个硬约束是规模与速度。业界常用经验值是：一次评审控制在 200–400 行改动内、集中评审不超过 60–90 分钟，超出就应拆分；首次回应尽量在 1 个工作日内——评审排队越久，作者的上下文丢得越多，返工成本越高。这两个数字是经验参考，不是放之四海的硬性标准，各团队应按自己的代码与评审数据校准（见文末未完成项）。

### 3.5 PR 描述模板：让评审者不用猜

一个能独立说明问题的 PR 描述至少包含：改了什么、为什么改、怎么测的、风险与回滚办法。模板如下（模板文本本身是写作规范，不属于运行示例）：

```markdown
## 改了什么
（行为变化一句话；不复述 diff）

## 为什么改
（关联 issue / 需求背景；不做这个会怎样）

## 测试
（新增或修改的测试；手动验证步骤；未覆盖的部分如实写）

## 风险与回滚
（影响面；失败时怎么发现、怎么回滚；特性开关名，如有）
```

作者按模板写，评审者按模板读，评审的第一轮就不必来回追问“这个改动到底想干什么”。

### 3.6 评审检查清单

不是每一项都适用于每个 PR，但每一项都应在评审时过一遍脑子，只勾选与本次变更相关的项：

- **正确性**：每个分支都产生预期结果吗？空值、空集合、边界值、重复与非法输入处理了吗？错误路径是被恰当处理了，还是被静默吞掉了？
- **设计**：这次改动放在这一层合理吗？有没有把本应属于别处职责的代码塞进来？接口变化是否向后兼容，不兼容时迁移方案写清了吗？
- **测试**：测试证明的是改动后的行为，还是只证明了“代码能跑”？重要失败路径有测试吗？测试是否确定、可读、不依赖执行顺序？
- **安全**：外部输入（请求参数、文件上传、环境变量）都校验了吗？敏感信息（口令、密钥、个人信息）有没有进日志、进提交、进错误信息？权限检查在服务端做了吗（前端校验不算）？
- **性能与并发**：循环里有没有隐藏的重复查询或重复计算？并发访问下共享状态会出错吗？新增的依赖与资源消耗合理吗？
- **可读性与可维护性**：命名说清意图了吗？复杂逻辑有注释说明“为什么”，而不只是复述“做了什么”？重复代码是该抽出来，还是抽出来反而更难懂？
- **文档与运维**：用户可见行为变了，文档同步了吗？监控、日志、告警需要跟进吗？数据库或配置变更的部署顺序写清了吗？

清单的反模式是“清单式吹毛求疵”：风格、格式问题应交给格式化工具与 Lint 自动处理，评审意见里不应再逐条纠格式；评审者也不要对清单外的无关项凭空提意见。

### 3.7 评审礼仪与治理

- **对事不对人**：评论指向代码与行为，给出可操作的建议（“这里空指针时崩溃，建议先判空并返回某某”），而不是评价作者。
- **作者有回应义务，评审者有及时义务**：作者逐条回应，评审者不在 1 个工作日内回应就应说明原因或转交他人；评审不是单向权力。
- **主线保护是治理的底线**：对 `main` 设分支保护——至少要求 PR 评审通过、自动化检查通过后才能合入，禁止直接推送；多人协作的关键路径还可要求指定负责人（CODEOWNERS 式）评审。不同平台的保护规则叫法与选项各异，具体配置以所用平台的官方发布为准（待核实），见文末未完成项。
- **知识传递是评审的第二产出**：评审不只是找 bug，也是让第二个人理解这块代码；新人评审老人的代码、跨模块互相评审，都是有意安排的知识扩散，不是浪费时间。

### 3.8 演示：分支命名如何对应策略

下面的演示是在 VM 上真实建库跑出来的（Git 2.43.0，演示身份 `Demo User <demo@example.com>`），只展示策略对应的分支形态，不展开合并机制（机制见 02 篇）：

```bash
git init -b main
printf 'v1\n' > app.txt
git add app.txt
git commit -m "feat: initial version"
git branch develop
git checkout -b feature/login
printf 'v1\nlogin\n' > app.txt
git commit -am "feat: add login page"
git branch
git diff --stat main...HEAD
```

实测通过，输出：

```
  develop
* feature/login
  main
 app.txt | 1 +
 1 file changed, 1 insertion(+)
```

读法：`develop` 是 GitFlow 的集成线，`feature/login` 是从主线分出的短期分支，`*` 是当前分支；`diff --stat` 是评审者打开 PR 时先看的“改动规模”——1 个文件、1 行新增，属于一眼能看完的规模。GitHub Flow 下这个演示里不会有 `develop`，主干开发下 `feature/login` 的寿命应以小时计而不是以周计——同一组命令，策略不同，分支的含义与寿命上限就不同。

## 4. 分类

按“合入主线前的隔离方式”分，策略只有两类：**分支隔离**（GitFlow、GitHub Flow：未完成的工作待在分支里）与**开关隔离**（主干开发：未完成的工作进了主干、但被特性开关藏起来）。按“评审的触发方式”分，评审也只有两类：**合入前评审**（PR / MR 批准后才能合入，默认推荐）与**合入后评审**（先合入、后抽查，只适用于极小改动或有充分信任与快速回滚能力的场景，且须团队明文约定）。

## 5. 典型应用

- **Web 服务小团队**：GitHub Flow + PR 评审 + 自动化检查，合入即部署，分支 bookkeeping 最少。
- **版本化产品团队**：GitFlow + 发布分支稳定期，`release` 分支只修 bug，发布时在 `main` 打附注标签（标签对象见 10 篇）。
- **高频交付的成熟团队**：主干开发 + 特性开关 + 小步合入，评审粒度压到每次几十到几百行，靠 CI 与开关而不是长分支保质量。
- **开源项目**：外部贡献者 Fork 后提 PR，维护者按清单评审、按治理规则合入，PR 描述模板与检查清单就是项目的协作界面。

## 6. 限制与常见误解

- **“策略越重越专业”**：错。GitFlow 的重是为版本化发布付的成本，持续交付团队照搬它只会多付管理成本、少得交付速度；专业体现在选型与发布节奏匹配，不体现在分支多。
- **“评审就是找 bug”**：不全对。找 bug、知识传递、统一风格与设计共识，都是评审的产出；只盯着 bug 的评审会漏掉设计问题，也留不住新人的成长。
- **“PR 越大越高效，省得来回提”**：错。大 PR 评审质量下降、返工成本上升是已被反复验证的经验；拆成可独立测试的小 PR 才是真的省时间。
- **“评审通过 = 没有问题”**：错。评审通过只说明“按清单看过、明确改善了代码健康”；上线后的验证、监控与回滚预案仍然不能省。
- **“特性开关可以一直留着”**：错。开关是临时隔离手段，功能全量后应清理开关与死代码，否则开关组合爆炸会让测试与排障成本反噬。

## 7. 小结

分支策略定节奏：GitFlow 保版本、GitHub Flow 保简洁、主干开发保频率，选型先看发布节奏与自动化水平。评审保质量：小 PR、快回应、按清单从设计看到细节、批准标准是“明确改善”而非“完美”。策略写进文档、评审落到清单，主线才既快又稳。
