# 数据结构与算法基础

## 1. 本章目标

读完本篇，能说清常用数据结构的区别、复杂度分析的方法，以及排序与查找的选型依据：不是背代码，而是按场景做取舍。

## 2. 背景与问题

程序要处理的数据越来越多：几个元素时怎么写都行，几百万个元素时，写法不同，结果可能差几千倍。问题不在语言快慢，而在**数据怎么组织、操作怎么进行**。数据结构回答“怎么组织”，算法回答“怎么操作”，复杂度分析回答“代价随规模怎么增长”。

## 3. 总体架构

```
待解决的问题
    │
    ├─ 数据结构：数据在内存里怎么放（连续？链式？散列？）
    ├─ 算法：对这些数据做什么操作（查找？排序？插入删除？）
    └─ 复杂度：代价随数据规模 n 怎么增长（时间？空间？）
```

三者缺一不可：只谈结构不谈操作，等于只买了货架不进货；只谈操作不谈复杂度，等于不知道仓库多大时会爆仓。

## 4. 工作机制

### 4.1 数组与链表：连续与链式的根本差别

数组是一块连续内存，元素按下标定位，随机访问快；但中间插入、删除要搬移后面的元素，代价随规模增长。链表是节点加指针，插入、删除只要改几个指针；但访问第 k 个元素必须从头一步步走，没有下标直达。

还有一个常被忽略的差别：**缓存友好性**。数组连续，CPU 一次取一块，遍历时缓存命中率高；链表节点分散，遍历时缓存命中率低。同样是“走一遍”，数组往往更快。这就是为什么“理论复杂度相同，实测速度不同”——复杂度只数操作次数，不数缓存缺失。

### 4.2 栈与队列：受限的访问顺序

栈是后进先出（LIFO）：只允许在一端进出。典型用途：函数调用、表达式求值、撤销操作。队列是先进先出（FIFO）：一端进、一端出。典型用途：任务排队、消息缓冲、层序遍历。

两者都可以用数组或链表实现：选哪个实现，取决于是否需要动态扩容、是否在意缓存。接口（LIFO/FIFO）与实现（数组/链表）是两回事，不要混为一谈。

```python
from collections import deque

stack = []
for x in (1, 2, 3):
    stack.append(x)
print("stack pop order:", stack.pop(), stack.pop(), stack.pop())

queue = deque()
for x in (1, 2, 3):
    queue.append(x)
print("queue pop order:", queue.popleft(), queue.popleft(), queue.popleft())
```

实测输出（Python 3.12.3，本地运行）：

```
stack pop order: 3 2 1
queue pop order: 1 2 3
```

### 4.3 哈希表：用空间换时间的典型

哈希表把键通过哈希函数映射到桶，下标定位，平均查找接近常数时间。代价有三：

- **哈希冲突**：不同键算出同一个桶，必须用链表、开放寻址等办法解决；冲突一多，性能就退化。
- **负载因子**：元素数除以桶数，超过阈值就要扩容重哈希，扩容那一刻很贵（均摊后可接受）。
- **最坏情况**：如果哈希函数被针对性攻击（所有键挤进少数桶），查找退化到线性。工程上这就是为什么不能只看“平均 O(1)”。

```python
table = {"alice": 1, "bob": 2, "carol": 3}
print("hash lookup bob:", table["bob"])
```

实测输出：`hash lookup bob: 2`。字典是 Python 内置的哈希表实现，日常开发优先用它，而不是自己造轮子。

### 4.4 复杂度分析：大 O 只描述增长趋势

大 O 记号描述的是**规模增大时，代价的增长趋势**，不是绝对速度。O(1)、O(log n)、O(n)、O(n log n)、O(n²) 是不同量级，n 越大差距越悬殊。

下面这段实测最能说明问题：在 100 万个有序数里找一个目标，线性查找逐个比对，二分查找每次排除一半：

```python
data = list(range(1, 1_000_001))
target = 999_999
linear_steps = 0
for v in data:
    linear_steps += 1
    if v == target:
        break
lo, hi, binary_steps = 0, len(data) - 1, 0
while lo <= hi:
    binary_steps += 1
    mid = (lo + hi) // 2
    if data[mid] == target:
        break
    elif data[mid] < target:
        lo = mid + 1
    else:
        hi = mid - 1
print(f"linear steps: {linear_steps}, binary steps: {binary_steps}")
```

实测输出（Python 3.12.3，本地运行）：

```
linear steps: 999999, binary steps: 19
```

99 万 9 千多次比对对 19 次，这就是 O(n) 与 O(log n) 的差距。但要注意三个限定：

- 大 O 忽略常数项：n 很小时，O(n) 的简单实现可能比 O(log n) 的复杂实现更快。
- 要区分最好、平均、最坏：快速排序平均 O(n log n)，最坏 O(n²)；只报平均是耍流氓。
- 复杂度不算内存：哈希表快，是以额外内存为代价的；内存受限时，慢一点但省内存的方案可能更合适。

### 4.5 排序与查找的思想：没有万能算法

排序算法的选型看五个维度：数据规模、是否基本有序、是否要求稳定（相等元素的相对顺序不变）、内存是否受限、数据是否在内存里。

- 小规模或基本有序：插入排序简单直接，虽然最坏 O(n²)，但常数小、写起来不易错。
- 通用大规模：归并排序稳定但要额外内存；快速排序平均快但最坏退化；堆排序原地但不稳定。
- 日常开发：优先用语言内置排序。Python 的 `sorted()` 经过长期打磨，能自适应利用已有顺序，一般比自己写的排序更快更稳。

```python
def insertion_sort(a):
    a = a[:]
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a

sample = [5, 2, 9, 1, 7]
print("insertion:", insertion_sort(sample), "builtin:", sorted(sample))
```

实测输出：`insertion: [1, 2, 5, 7, 9] builtin: [1, 2, 5, 7, 9]`。结果一致，代价不同：手写插入排序是 O(n²)，内置排序是 O(n log n) 量级。

查找的选型同样看前提：无序数据只能线性找；有序数据才能二分；频繁按名查找用哈希表；需要范围查询（找某区间内的全部元素）时，有序结构比哈希表合适——哈希表不保序。

## 5. 关键设计取舍

- **时间换空间**：哈希表用额外内存换查找速度；内存紧张时，这个交换就不划算。
- **简单换性能**：插入排序、线性查找实现简单、不易错；复杂算法更快，但写错的概率和维护成本也更高。小规模场景下，简单往往是正确选择。
- **通用换专用**：内置排序、内置字典是通用优化的结果；只有当实测证明通用方案不够时，才值得写专用实现——而且要先实测，不要凭感觉。
- **理论换实际**：复杂度分析不考虑缓存、分支预测、内存分配。链表理论上插入是 O(1)，实际遍历缓存缺失可能让它慢于数组。选型时，理论是起点，实测是终点。

## 6. 分类与变体

数据结构按组织方式分：

| 类别 | 代表 | 访问特点 | 适用场景 |
|---|---|---|---|
| 线性连续 | 数组、字符串 | 下标直达，插入删除贵 | 随机访问多、规模固定 |
| 线性链式 | 链表 | 插入删除便宜，访问要遍历 | 频繁两端或中间增删 |
| 受限线性 | 栈、队列 | 只允许一端或两端操作 | 调用、排队、遍历 |
| 散列 | 哈希表、字典 | 平均常数查找，不保序 | 按名查找、去重、计数 |
| 树形 | 二叉树、堆、平衡树 | 分层组织，支持范围操作 | 排序、有序查找、优先队列 |
| 图形 | 邻接表、邻接矩阵 | 节点与边的关系 | 路网、依赖、社交关系 |

算法按思想分：分治（归并、快排）、减治（二分查找）、动态规划（重叠子问题加记忆）、贪心（每步局部最优）、回溯（试错加剪枝）。思想比具体代码重要：认出问题属于哪种思想，才知道往哪个方向找解法。

## 7. 应用与限制

典型应用：数据库索引用树形结构加速范围查询；缓存系统用哈希表做键值定位；任务调度用队列和堆；编译器用栈处理嵌套结构；前端框架内部同样用这些结构组织组件与状态（框架技术本身见 03 域文章，本篇不展开）。

限制：

- 复杂度是渐近分析，n 小时参考价值有限；选型前先估规模。
- 哈希表最坏会退化，关键系统要评估冲突与攻击面。
- 排序的稳定性、内存占用、是否原地操作，都是选型时必须同时看的维度，只看时间复杂度会选错。
- 算法不能解决“问题本身无解”：例如对无序数据做二分查找，前提就不成立。

## 8. 常见误解

- **“O(1) 永远最快”**：错。大 O 不含常数，哈希计算、内存分配都可能让 O(1) 在小规模下慢于 O(n)。
- **“链表一定比数组快”**：错。链表插入快，但遍历慢、缓存差；随机访问多的场景数组完胜。
- **“学算法就是背代码”**：错。背下来的代码换个条件就失效；理解“为什么这样组织、代价从哪来”，才能在新问题上做对取舍。
