# 调试与测试方法

## 1. 本章目标

读完本篇，能建立两套基本功：定位问题时的调试思路（复现、缩小、验证），以及预防问题时的测试分工（单元、集成、端到端各管什么，测试替身什么时候用）。

## 2. 背景与问题

程序一定有缺陷：需求理解有偏差、边界条件没考虑到、并发时序没料到。问题分两类活动：**调试是事后定位**——已经出错了，找出是哪一行、为什么错；**测试是事前预防**——在出错之前，用可重复的检查把问题拦下来。只会调试不会测试，等于只会救火不会防火；只会写测试不会调试，等于火着了不知道从哪灭。

## 3. 总体架构

调试循环：

```
复现问题 → 缩小范围 → 提出假设 → 验证假设 → 修复 → 回归验证
```

测试金字塔（从下到上，数量递减、速度递减、成本递增）：

```
        端到端测试（少）：真实环境走完整流程
      集成测试（中）：模块之间协作是否正确
    单元测试（多）：单个函数、单个模块是否正确
```

金字塔的含义：底层便宜、快速、定位准，应该占大多数；顶层真实、缓慢、定位难，应该只覆盖关键流程。倒过来的“冰淇淋筒”（端到端最多）是反模式：跑得慢、坏了不知道谁的问题、维护成本高。

## 4. 工作机制

### 4.1 调试思路：先复现，再缩小

调试的第一步永远是**稳定复现**：同样的输入、同样的步骤，能不能每次都重现问题。复现不了的问题，修了也无法验证。复现之后按顺序做：

1. **缩小范围**：注释一半代码、二分输入规模、换最小输入，看问题还在不在。范围每缩小一半，嫌疑对象就少一半。
2. **提出假设**：根据现象猜一个具体原因，例如“这个变量在这里应该是空，但实际不是”。
3. **验证假设**：打印、断点、单步，看变量的真实值；假设被证伪就换下一个，不要对着错误假设硬修。
4. **修复与回归**：修完后，先跑复现步骤确认问题消失，再跑相关测试确认没有引入新问题。

最常见的调试误区是跳过复现和缩小，直接凭感觉改代码：改完“好像好了”，下次换个输入又复发。

### 4.2 断点与日志：两种观察手段

**日志**是在程序里留痕：记录关键步骤的输入、输出、异常。日志分级要讲规矩：INFO 记正常流程的关键节点，WARNING 记“还能跑但不对劲”，ERROR 记“这一步失败了”。级别乱用，等于没有级别；生产环境日志量过大，还会拖慢程序、占满磁盘。

```python
import logging
logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logging.info("进入函数，参数 x=5")
logging.warning("x 超出建议范围，仍继续")
logging.error("写文件失败：权限不足（示例）")
```

实测输出（Python 3.12.3，本地运行）：

```
INFO 进入函数，参数 x=5
WARNING x 超出建议范围，仍继续
ERROR 写文件失败：权限不足（示例）
```

**断点**是让程序在指定位置停下来，检查当时的变量与调用栈。断点适合“不知道哪一步开始错”的场景：设在可疑区域之前，单步往前走，看哪一步的变量第一次偏离预期。日志适合“问题发生在别处、事后复盘”的场景：程序跑在服务器上，没法随时停下来看。两者互补，不是谁取代谁。

顺带说一句：`print` 调试不是原罪，简单场景下最快；但它的问题是临时性——调完要删干净，删漏了就会污染日志；而且生产环境出问题时，临时加的打印早就不在了。正式代码里用日志，临时排查时用打印或断点，分工要清楚。

### 4.3 单元测试：测最小单位，跑得最快

单元测试针对一个函数或一个模块，输入固定、断言明确、运行毫秒级。它的价值不只是“发现 bug”：写测试的过程会逼你把函数职责想清楚——一个函数如果很难写测试，往往是职责不清的信号。

Python 标准库 `unittest` 示例（本地实测，Python 3.12.3）：

```python
import unittest
from calc import add, divide

class TestCalc(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)

    def test_divide(self):
        self.assertEqual(divide(10, 2), 5)

    def test_divide_by_zero(self):
        with self.assertRaises(ValueError):
            divide(1, 0)
```

其中 `calc.py` 的 `divide` 在除数为 0 时主动抛出 `ValueError`，而不是返回一个含糊的结果。实测输出：

```
test_add (test_calc.TestCalc.test_add) ... ok
test_divide (test_calc.TestCalc.test_divide) ... ok
test_divide_by_zero (test_calc.TestCalc.test_divide_by_zero) ... ok

----------------------------------------------------------------------
Ran 3 tests in 0.000s

OK
```

单元测试的三个规矩：互相独立（一个测试失败不影响另一个）、可重复（不依赖当前时间、随机数、网络）、断言具体（断言“等于 5”，不要断言“大概对”）。

### 4.4 集成测试与端到端测试的分工

- **集成测试**：测模块之间的协作，例如函数调数据库、服务调接口。重点是“接口契约对不对”：参数格式、返回结构、异常传递。
- **端到端测试**：在接近真实的环境里走完整流程，例如“用户登录、下单、支付”。重点是“关键流程通不通”，只覆盖主干流程，不覆盖全部细节。

分工不清的典型症状：用端到端测试去覆盖所有分支——跑得慢、坏了定位难；或者只写单元测试、从不验证模块协作——每个零件都对，组装起来不对。

### 4.5 测试替身：隔离依赖的四种角色

测试替身是测试时用来代替真实依赖的 stand-in，常见四种：

| 替身 | 作用 | 例子 |
|---|---|---|
| Stub（桩） | 返回固定答案，不关心调用过程 | 查天气永远返回“晴天” |
| Mock（模拟） | 校验“有没有按预期调用” | 断言“支付接口恰好被调用一次” |
| Fake（伪造） | 有简化版的真实行为 | 内存版数据库，能增删查但不落盘 |
| Spy（间谍） | 记录调用过程，供事后断言 | 记下“函数被调用了几次、参数是什么” |

用替身的原则：能不用就不用——真实依赖跑得通，优先用真实；只有当依赖缓慢、昂贵、不稳定、不可控时，才用替身隔离。替身用得越多，测试离真实行为越远：测试全过、上线仍错，往往就是替身与真实行为不一致。

## 5. 关键设计取舍

- **粒度换成本**：单元测试便宜但离真实远，端到端真实但贵且脆弱；金字塔比例就是这笔账的答案。
- **隔离换真实**：替身让测试快而稳，但掩盖了与真实依赖的不一致；关键路径上，至少要有一部分测试用真实依赖。
- **覆盖换维护**：测试覆盖率越高，改代码时测试失败的概率也越高；覆盖率是参考指标，不是目标——100% 覆盖但断言空洞的测试，等于没有测试。
- **日志详细换性能**：日志越细，定位越快，但磁盘与性能代价越大；生产环境日志级别与采样，要按服务等级定，不是一股脑全开。

## 6. 分类与变体

测试按目的还可以分：回归测试（改完确认旧功能没坏）、冒烟测试（主干流程快速过一遍）、性能测试（负载下的响应与资源）、安全测试（见 10 域，边界与防御）。本篇重点是日常开发最常用的单元、集成、端到端三层，其他类型按需引入，不必一开始全上。

调试手段按场景分：日志复盘（事后、远程）、断点单步（本地、未知位置）、二分缩小（范围大时）、最小复现（提问题、报 bug 时）。报 bug 时附上最小复现步骤，是对接手的人最大的善意。

## 7. 应用与限制

应用：日常开发的提交前自查（先跑相关单元测试，再合并，见本批第二篇）、线上问题的定位流程、接手他人代码时的理解手段（先跑测试，再读代码，测试就是活的规格说明）。

限制，必须说清：

- 测试通过不能证明没有 bug：测试只能证明“测过的场景是对的”，没测的场景仍然未知。
- 不稳定的测试（flaky test，时过时不过）比没有测试更糟：它会让人对测试结果麻木，最后没人看测试报告。
- 遗留代码没有测试时，不要一上来就大重构：先为要改的部分补测试，再小步重构，每步都跑测试验证。
- 调试不能代替设计：同一个地方反复出问题，说明设计或接口有问题，该重构而不是再打一个补丁。

## 8. 常见误解

- **“测试全过 = 没 bug”**：错。测试只覆盖写了的场景；边界、并发、异常路径没写测试，就等于没验证。
- **“调试靠经验和运气”**：错。复现、缩小、假设、验证是固定流程；经验只是让假设更准，不是替代流程。
- **“mock 越多，测试越专业”**：错。替身是隔离手段，不是专业标志；过度替身会让测试与真实行为脱节。
