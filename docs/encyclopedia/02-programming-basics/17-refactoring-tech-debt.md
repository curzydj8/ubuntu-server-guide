# 重构方法与技术债管理

## 1. 一句话定义

重构是在不改变可观察行为的前提下改善代码内部结构的持续活动；技术债是为“先交付、后完善”所付出的未来改动成本，管理它的核心是记账、定价、按期偿还。

## 2. 为什么需要它

需求会变，理解会加深：第一版代码写的是当时对问题的理解，三个月后团队对业务的理解变了，代码却还停留在旧理解上。如果只加功能、不调整结构，每次改动都要绕过旧结构留下的弯路，改动成本越涨越高，最后出现“改一行、坏三处”的局面。重构就是定期把代码改回与当前理解一致的样子，让下一次改动仍然便宜。

技术债的另一面是现实：上线时间、演示节点、紧急修复，常常要求先交付一个“够用但不完美”的实现。借债本身不是错误——就像贷款本身不是错误一样。错误的是只借不还、不记账、不定价：没人知道欠了多少、利息有多高、什么时候会压垮团队。

## 3. 核心含义

### 3.1 重构的定义与边界

Martin Fowler 在《Refactoring》中的定义是：重构是“对软件内部结构做出的改动，目的是让它更容易理解、更便宜修改，同时不改变其可观察行为”。这个定义划出三条边界：

- **重构不加功能**：加功能是另一顶帽子，同一提交里不要既加功能又重构，否则出问题时无法判断是新功能错了还是重构错了。
- **重构不修 bug**：修 bug 会改变可观察行为（从错变对），同样要与重构分开提交。
- **重构可以小到一次改名**：重构不是“大重写”的同义词，恰恰相反，它主张由一系列小而安全的手法累积出结构改善。

“可观察行为不变”有一个实际的检验标准：重构前后，同一输入得到同一输出——这正是测试存在的意义（见 3.3）。

### 3.2 重构手法目录

手法按改动对象分组，每个手法都是一次“小步、行为不变”的变换。手法名称采用 Fowler《Refactoring》第 2 版（2018）的常用叫法，具体步骤以该书为准：

**命名与表达类（最常用、风险最低）**

| 手法 | 做法 | 什么时候用 |
|---|---|---|
| 改名（Rename） | 给变量、函数、类、文件换一个更准确的名字，全部引用点同步改 | 名字与实际作用不符、概念换了词、新人反复误解某个名字时 |
| 抽取变量（Extract Variable） | 把复杂表达式拆成一个名字自解释的中间变量 | 表达式太长、同一表达式出现多次、条件判断读不懂时 |
| 内联变量 / 内联函数（Inline） | 与抽取相反：把只用一次、名字没有增加信息的变量或函数合并回调用处 | 过度拆分导致跳转阅读成本高于收益时 |

**结构拆分类（降低单个单元的复杂度）**

| 手法 | 做法 | 什么时候用 |
|---|---|---|
| 抽取函数（Extract Function） | 从长函数里切出一段有独立意图的代码，变成新函数 | 函数超过一屏、一段代码有独立注释、同一逻辑在多处重复时 |
| 拆分条件（Decompose Conditional） | 把复杂条件、分支体分别抽成函数 | `if` 条件读三遍才懂、分支里混着计算与副作用时 |
| 拆分循环（Split Loop） | 一个循环里做两件以上的事时，拆成多个各做一件事的循环 | 循环体里既过滤又聚合、既计算又写日志时 |
| 引入卫语句（Replace Nested Conditional with Guard Clauses） | 把前置的异常、边界条件提前返回，消灭深层嵌套 | `if` 套 `if` 超过三层、正常流程被异常分支淹没时 |

**移动与归属类（让代码待在合理的位置）**

| 手法 | 做法 | 什么时候用 |
|---|---|---|
| 移动函数 / 移动字段（Move Function / Move Field） | 把函数或字段搬到更常使用它的模块或类里 | 某个函数用的全是另一个模块的数据、字段与函数分离存放时 |
| 抽取类（Extract Class） | 一个类承担两个以上职责时，拆出新类 | 类越长越大、两组字段各自只被一部分方法使用时 |
| 引入参数对象（Introduce Parameter Object） | 把总是一起传递的几个参数打包成一个对象 | 函数参数超过四个、同一组参数在多个函数签名里重复出现时 |

**接口与依赖类（改动面较大，需更谨慎）**

| 手法 | 做法 | 什么时候用 |
|---|---|---|
| 封装记录 / 封装集合（Encapsulate Record / Collection） | 把裸数据结构包在访问函数后面，收敛修改点 | 同一数据结构在十处被直接读写、改一个字段要改十处时 |
| 以查询取代临时变量、函数组合 | 用可复用的查询函数代替散落的临时计算 | 同一推导逻辑在多处重复、临时变量掩盖了数据来源时 |

手法选择的通用原则：**先从风险最低的开始**——改名、抽取变量、抽取函数这三样，几乎不需要理解全局；移动与拆分类需要理解模块边界；接口类手法会波及调用方，留到测试覆盖足够时再做。一次重构只用一种手法、只解决一个问题，做完验证通过再进行下一步。

### 3.3 安全重构的前提：测试是安全网，小步是操作方法

安全重构有两个前提，缺一不可：

**第一，有可运行的测试作安全网。** 重构的正确性不靠“我觉得没改坏”，靠“重构前后测试全部通过”。测试的具体写法与分工（单元、集成、端到端的职责，测试替身的用法）不在本篇展开，见同目录 [调试与测试方法](03-debugging-testing.md) 与 [单元测试与 Mock](12-unit-testing-mocks.md)。这里只定一条操作规矩：要重构的区域没有测试覆盖时，先补测试、再重构；补测试时先锁定当前行为（哪怕当前行为并不完美），重构时以“测试全过”为放行标准。

**第二，小步、每步验证。** 一次只做一个手法、只改一处，做完立即运行相关测试；测试红了，立刻回退这一步，而不是在红测试的基础上继续改。小步的另一个好处是评审友好：十次小提交，每次 diff 都清晰可审；一次大提交，评审人只能凭信任放行。

除此之外还有两条纪律：**功能与重构分开提交**（提交拆分的做法见 [Git 工作流](02-git-workflows.md)），以及**版本控制兜底**——任何一步走偏，都能用版本控制回到上一个绿测试状态，而不是凭记忆手工还原。

### 3.4 技术债：识别信号

技术债不是“代码写得不好看”的同义词。Ward Cunningham 在 1992 年 OOPSLA 关于 WyCash 投资组合管理系统的经验报告中提出这个比喻：第一次交付的代码像借债，少量债务能加快交付，只要及时用重写偿还；危险在于债务不还——每一分钟花在“不太对的代码”上，都是在付利息。Cunningham 后来澄清过：他从不主张故意写烂代码再补，债务的原意是代码与团队当前理解之间的差距。

识别技术债的实际信号（出现一条就值得记账，两条以上就该排期）：

- **改动成本信号**：一个小需求要改五处、改一处要回归十处、估算工时总是超预期。
- **理解成本信号**：新人接手同一模块要问三个人、注释与代码对不上、没人敢动某段代码。
- **质量成本信号**：同一模块反复出同类 bug、测试越写越难写（需要大量替身才能跑起来）、发布前总要“手工回归一遍”。
- **速度成本信号**：构建、测试、部署越来越慢，慢到影响日常开发节奏。

### 3.5 技术债的分类

Martin Fowler 在 2009 年给出的四象限分类，至今仍是讨论债务时最省事的框架（有意 / 无意 × 谨慎 / 鲁莽）：

|  | 谨慎（知道自己在做什么） | 鲁莽（不知道或不在乎） |
|---|---|---|
| **有意** | 故意借债：为赶上线时间点，先交付简化实现，并记下偿还计划 | 故意不讲究：明知有更好做法，为省事直接写死、复制粘贴 |
| **无意** | 学习后发现的债：当时以为是对的，后来理解加深才发现结构不对——这是最正常的债 | 无知造成的债：不知道有更好的做法，写出了难以维护的结构 |

按来源还可以再分一层，便于排期时分工：代码债（重复、长函数、坏命名）、设计债（模块边界错、职责不清）、测试债（缺测试、测试脆弱）、文档债（文档过期、关键决策没记录）、依赖债（长期不升级的库与工具链）。分类的目的不是贴标签，而是决定“谁来还、用什么方式还”。

## 4. 分类：偿还策略

### 4.1 按偿还方式分

- **顺手还（Boy Scout 式）**：每次改动经过一块代码时，顺手清理这块代码的小问题——改个名、抽个函数、删段死代码。不单独排期、不单独评审，靠日常积累消化小额债务。适合：单点小问题。
- **专项还**：为一块债务单独立项、排期、评审，例如“把支付模块的重复逻辑抽成统一服务”。适合：影响多个需求的模块级债务。
- **重写**：当结构已经无法通过小步重构挽回时，局部重写是选项，但它是最后手段：重写期间旧系统仍要维护，两套实现并存本身就是新债。重写前必须先有新旧行为一致的测试对照，否则等于无网高空作业。
- **不还（有意持有）**：债务所在的模块即将下线、极少改动、偿还成本高于利息时，理性选择是不还——但要书面记下来（为什么不还、什么条件下重新评估），而不是假装它不存在。

### 4.2 按排期策略分

- **固定比例法**：每个迭代留固定比例（例如 20%）给还债与重构，不单独争论每一笔。适合债务总量稳定、团队节奏固定的情况。
- **利息优先法**：先还“利息最高”的债——也就是最频繁改动、最拖慢需求的模块。判断标准是改动频率乘以每次多付的成本，而不是“代码最难看”。
- **需求捎带法**：下个需求要动哪个模块，就先还哪个模块的债（重构先行、功能随后，两步分开提交）。适合债务与需求高度重合的情况。
- **债务上限法**：给债务登记表设上限（例如未偿还项不超过 20 条、单项账龄不超过两个季度），超限就停新需求、先还债。适合债务已经失控、需要硬约束的团队。

### 4.3 记账：没有登记表的债，等于没有债

偿还策略要落到一张所有人可见的登记表，每项至少记：位置（模块 / 文件）、症状（哪个识别信号）、利息（每次改动多付多少成本，或哪个需求被拖慢）、偿还方案（顺手还还是专项还）、负责人与期限。登记表本身要定期复审：已下线的模块对应的债要销账，利息评估要随改动频率更新。没有登记表，技术债的讨论永远停留在“感觉代码很烂”的层面，排期时永远争不过新需求。

## 5. 典型应用

- **为新功能准备场地**：需求要动一个结构混乱的模块时，先小步重构出清晰的落点，再加功能；两步分开提交，测试全程护航。
- **接手遗留代码**：先补测试锁定行为，再按手法目录从改名、抽取函数开始小步清理；不要一上来就重写。
- **迭代中的债务排期**：每个迭代复审登记表，用利息优先法选出一两项专项偿还，顺手还的部分计入日常工作量。
- **评审中的债务发现**：评审时发现“为赶工期先这样写”的实现，当场要求补一条登记表记录（位置、原因、偿还期限），而不是只留一句口头约定。

## 6. 限制与常见误解

- **重构不是重写**：重写是推倒重来、行为对照困难；重构是一系列行为不变的小变换、可随时停下。把“重构”说成“重写”，等于把低风险活动包装成高风险活动，团队就不敢做了。
- **重构不产生用户可见价值，但产生开发速度**：向非技术角色解释重构时，谈“下个需求能快多少、少出多少回归 bug”，不要谈“代码变漂亮了”。技术债登记表里的“利息”一栏，就是为这种对话准备的。
- **没有测试的重构是赌博**：测试覆盖不足时，大手法（移动、拆类、改接口）必须先缓一缓；先补测试，再动手。测试的写法与分工见 [调试与测试方法](03-debugging-testing.md) 与 [单元测试与 Mock](12-unit-testing-mocks.md)，本篇不重复展开。
- **技术债不等于所有烂代码**：按 Cunningham 的原意，债务是“代码与当前理解的差距”；而纯粹写坏的代码、从不清理的复制粘贴，是鲁莽造成的债，管理方式不同（靠规范与评审拦截，见 [代码规范与风格指南](16-code-style-lint.md)），不要都记进同一张表。
- **借债必须有偿还计划**：评审里通过“先这样、以后再改”的实现时，必须同时留下登记表记录与期限；没有期限的“以后”，就是永不偿还。
- **重构不能代替设计评审**：同一地方反复重构、反复变脏，说明模块边界或需求本身有问题，该回到设计层面讨论，而不是再重构一次。

## 7. 小结

重构是“行为不变、结构变好”的一系列小手法，安全靠测试作网、小步作法、提交分离作纪律；技术债是交付换来的未来成本，借可以，但要记账、定价、按期还；还债的优先级看利息不看观感，最常改动、最拖慢需求的债先还。

## 附：示例与实测说明

下面示例演示最常用的手法“抽取函数”：重构前一个函数里混着求和、打折、计税三件事，重构后拆成三个各做一件事的函数，并用断言校验重构前后行为一致。运行环境：Python 3.12.3，VM 本地运行，实测通过：

```python
# 重构前：求和、打折、计税混在一个函数里
def total_before(prices, vip):
    total = 0
    for p in prices:
        total += p
    if vip:
        total *= 0.9
    total *= 1.1
    return round(total, 2)

# 重构后：抽取三个各做一件事的函数
def _subtotal(prices):
    return sum(prices)

def _apply_discount(amount, vip):
    return amount * 0.9 if vip else amount

def _apply_tax(amount):
    return amount * 1.1

def total_after(prices, vip):
    return round(_apply_tax(_apply_discount(_subtotal(prices), vip)), 2)

cases = [([100, 50, 25], True), ([100, 50, 25], False), ([], True), ([9.99], False)]
for prices, vip in cases:
    b, a = total_before(prices, vip), total_after(prices, vip)
    status = "一致" if b == a else "不一致"
    print(f"prices={prices} vip={vip}：重构前={b} 重构后={a} {status}")
    assert b == a
print("全部用例通过：抽取函数未改变可观察行为")
```

实测输出（Python 3.12.3，本地运行）：

```
prices=[100, 50, 25] vip=True：重构前=173.25 重构后=173.25 一致
prices=[100, 50, 25] vip=False：重构前=192.5 重构后=192.5 一致
prices=[] vip=True：重构前=0.0 重构后=0.0 一致
prices=[9.99] vip=False：重构前=10.99 重构后=10.99 一致
全部用例通过：抽取函数未改变可观察行为
```

注意：这只是“抽取函数”一个手法的最小演示，真实重构的安全网是项目自身的测试套件，不是这段演示脚本；测试套件的写法与分工见 [调试与测试方法](03-debugging-testing.md) 与 [单元测试与 Mock](12-unit-testing-mocks.md)。

| 位置 | 症状 | 利息 | 偿还方案 | 期限 |
|---|---|---|---|---|
| 支付模块计价函数 | 长函数、重复计税逻辑 | 每次改价目要改三处 | 专项还：抽取计价服务 | 下个迭代 |
