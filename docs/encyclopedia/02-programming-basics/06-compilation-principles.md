# 编译原理入门：词法、语法、语义、代码生成

## 1. 本章目标

读完本篇，能说清编译器把源码变成可执行程序要经过哪几步、每一步的输入输出是什么、以及“这段代码语法对但语义错”到底错在哪一层。

## 2. 背景与问题

人写的是给人看的高级语言，机器执行的却是机器指令。两者之间差的不只是一层翻译：高级语言有变量、类型、作用域、函数调用，机器只有寄存器、内存地址和跳转。编译器要做的，就是在不改变程序含义的前提下，把前者一步步降格为后者。

如果只有一层翻译，问题会立刻失控：每种语言乘以每种目标机器，就要写一套完整编译器。解决办法是分层：前端只懂语言，后端只懂机器，中间用一种与两者都无关的中间表示（IR）隔开。加一种语言，只要写一个新前端；加一种机器，只要写一个新后端。这就是现代编译器分前端、中端、后端的基本动机。

## 3. 总体架构

```
源程序（字符流）
    │
    ├─ 前端：词法分析 → 语法分析 → 语义分析 → 中间表示生成
    │       （只关心“这种语言是什么意思”，不关心目标机器）
    │
    ├─ 中端：在中间表示上做优化（与语言、机器都尽量无关）
    │
    └─ 后端：指令选择 → 寄存器分配 → 目标代码生成
            （只关心“这台机器怎么执行”，不关心源语言）
            │
            ▼
        目标程序（汇编 / 机器码 / 字节码，见第 7 节）
```

贯穿各阶段的还有两张辅助表：符号表（记录每个名字是什么、什么类型、在哪个作用域）和错误处理（每阶段发现问题都要报出位置和原因，而不是悄悄猜一个意思继续编）。

经典教材把编译过程划分为词法、语法、语义、中间代码生成、优化、代码生成六个阶段；前端、中端、后端的三分法是这六个阶段在工程上的归并：前端覆盖前四个阶段中的语言相关部分，中端做优化，后端做目标代码生成。两种说法不冲突，本篇按六阶段讲机制，按三段讲分工。

## 4. 工作机制

### 4.1 词法分析：把字符流切成记号

词法分析（lexing / scanning）读入字符流，按语言的构词规则把它切成一个个记号（token）：关键字、标识符、数字字面量、运算符、分隔符。切分依据是正则语言一类的简单规则，不涉及“这句话合不合语法”。

以 `total = price * 2 + 10` 为例，词法分析只关心切分结果：

```python
import tokenize, io
src = "total = price * 2 + 10\n"
for tok in tokenize.generate_tokens(io.StringIO(src).readline):
    print(tok.type, tokenize.tok_name[tok.type], repr(tok.string))
```

实测通过（Python 3.12.3，本地运行）：

```
1 NAME 'total'
55 OP '='
1 NAME 'price'
55 OP '*'
2 NUMBER '2'
55 OP '+'
2 NUMBER '10'
4 NEWLINE '\n'
0 ENDMARKER ''
```

注意：词法分析不知道 `price` 有没有定义，也不知道 `*` 和 `+` 谁先算——那是后面阶段的事。它能发现的错误只有构词错误，例如非法的字符、不完整的字符串字面量。经典工具是 Lex 及其后继 Flex（词法分析器生成器：按正则规则自动生成扫描器），具体版本以官方发布为准（待核实）。

### 4.2 语法分析：把记号流排成树

语法分析（parsing）按语言的文法（通常是上下文无关文法）检查记号流的结构，并建成一棵树：分析树（parse tree）记录推导全过程，抽象语法树（AST）则去掉括号、分号这类只起分隔作用的细节，只保留对含义有用的结构。

同一行代码的 AST 是这样的：

```python
import ast
print(ast.dump(ast.parse('total = price * 2 + 10'), indent=2))
```

实测通过（Python 3.12.3，本地运行，节选关键结构）：

```
Module(
  body=[
    Assign(
      targets=[
        Name(id='total', ctx=Store())],
      value=BinOp(
        left=BinOp(
          left=Name(id='price', ctx=Load()),
          op=Mult(),
          right=Constant(value=2)),
        op=Add(),
        right=Constant(value=10)))])
```

这棵树已经暗含了运算优先级：`price * 2` 是内层节点，`+ 10` 是外层节点，所以先乘后加。语法分析能发现的错误是结构错误，例如缺括号、缺分号、表达式写了一半。经典工具是 Yacc 及其后继 GNU Bison（语法分析器生成器：按文法自动生成解析器），具体版本以官方发布为准（待核实）。

一个常见的混淆要分清：**语法正确不等于语义正确**。`total = price * 2 + 10` 只要结构对就能通过语法分析，哪怕 `price` 从未定义、类型根本对不上。

### 4.3 语义分析：给树加上含义并查错

语义分析在语法树和符号表的基础上，检查程序是否符合语言定义的含义，主要做三件事：

- **作用域解析**：每个名字指向哪一次声明？内层遮蔽外层时，引用的是哪一个？
- **类型检查**：运算的操作数类型是否允许？函数调用的参数个数、类型是否匹配？赋值两边类型是否兼容？
- **其他语义约束**：例如变量使用前是否已声明、控制流是否符合语言规则（如 `break` 只能出现在循环内）。

下面这段 C 代码在语法上完全成句，却通不过语义分析：

```c
int main(void) { return missing_var; }
```

实测通过（GCC 13.3.0，本地运行，编译报错节选）：

```
undecl.c: In function 'main':
undecl.c:1:25: error: 'missing_var' undeclared (first use in this function)
```

语义分析的另一面是“补信息”：它会在树上标注类型、解析后的引用目标，后续阶段不再靠名字猜含义，而是直接用这些标注工作。语义分析之后，编译器才生成中间表示。

补充说明：有些语言把类型检查推迟到运行时（动态类型语言），那是“语义检查的时机不同”，不是“没有语义”。编译时能查的，动态语言往往要到运行时才暴露，调试成本因此更高。

### 4.4 中间表示生成：换一种与语言、机器都无关的写法

中间表示（IR）是介于源语言和目标机器之间的表示。它的价值在于解耦：前端把各种语言都降到同一种 IR，后端只要会处理这一种 IR；优化遍也写在 IR 上，与源语言和目标机器都无关。

常见的 IR 形态有：三地址码（每条指令最多一个运算符，如 `t1 = price * 2`）、静态单赋值形式（SSA，每个变量只被赋值一次，便于做数据流分析）。GCC 有自己的中间表示 GIMPLE 与 RTL，LLVM 则以 LLVM IR 为核心——这些是“同一种思想的不同实现”，具体指令集与版本以官方发布为准（待核实）。

### 4.5 优化：在保持语义的前提下改写程序

优化遍在 IR 上做等价改写，目标通常是更快、更小，或两者兼顾。常见优化包括：

- **常量折叠与常量传播**：编译时就能算出的表达式直接算出结果，不留到运行时。
- **死代码消除**：删掉结果永远用不上的计算。
- **循环优化**：把循环内不变的计算移出循环、展开小循环等。
- **内联**：把小函数的函数体直接展开到调用处，省掉调用开销（代价是代码变大）。

常量折叠是可以直接看到的。下面的 C 程序中 `3 * 2 + 10` 在编译时就被算成了 `16`：

```c
#include <stdio.h>
int main(void) { int total = 3 * 2 + 10; printf("total=%d\n", total); return 0; }
```

实测通过（GCC 13.3.0，本地运行）：`gcc -O0 -S` 生成的汇编中已出现 `movl $16, -4(%rbp)`，运行输出 `total=16`。连 `-O0`（不优化）都会做这种折叠，说明它更多是“编译时求值”而非激进优化。

优化必须服从一条红线：**不能改变程序的可观测行为**。编译器可以重排、删减、改写计算，但程序的输出、终止与否不能因此改变。优化越激进，证明“没改错”的负担越重——这正是编译器正确性要处理的问题，本篇不展开证明，只做链接，见相关主题。

### 4.6 代码生成：落到目标机器上

后端把优化后的 IR 翻译成目标代码，主要做三件事：

- **指令选择**：IR 的一个操作对应目标机器的哪条或哪几条指令？例如乘法在有的机器上是一条指令，在有的机器上要展开成移位加法。
- **寄存器分配**：程序里的变量远多于物理寄存器，哪些变量进寄存器、什么时候溢出到内存（spill），直接影响速度。
- **指令调度与汇编输出**：按目标机器的流水线特点调整指令顺序，最后输出汇编或机器码，再由汇编器、链接器拼成可执行文件。

后端是唯一必须懂目标机器的部分：换一台目标机器，前端和大部分优化可以不动，后端要重写。这也是“一次前端、多后端”成立的原因。

## 5. 关键设计取舍

- **分层换复用**：前端、中端、后端分层，换来语言与机器的组合复用；代价是 IR 必须足够通用，某些语言特性或机器特性在 IR 里表达起来会别扭。
- **优化换编译时间与可调试性**：优化越深，编译越慢，生成的代码与源码的对应关系越难追踪，调试时“单步执行跳来跳去”就是这个代价。开发期常用低优化级别、发布期用高优化级别，正是这个取舍的日常形态。
- **静态检查换灵活性**：静态类型语言在编译期查出更多语义错误，但要求程序员提前写清类型；动态类型语言写起来灵活，错误发现得更晚。没有绝对优劣，只有场景取舍。
- **报错位置换报错精度**：编译器报“第 1 行第 25 列未声明”是容易的；报“你真正想写的是哪个变量”需要猜测，猜错比不猜更有害。好的编译器在“准确定位”和“不瞎猜”之间取平衡。

## 6. 分类与变体

按翻译时机与产物分：

| 类别 | 含义 | 代表 |
|---|---|---|
| 提前编译（AOT） | 运行前一次性编成目标机器码 | GCC、Clang 编 C/C++，Rust 编译器（后端多用 LLVM） |
| 字节码编译 + 解释执行 | 先编成中间字节码，运行时由虚拟机执行 | CPython 编 Python 字节码（见下一篇） |
| 即时编译（JIT） | 运行时按需编成机器码 | JVM、.NET CLR、JavaScript 引擎（见下一篇） |
| 源码解释 | 不预编译，边解析边执行 | 早期脚本解释器、教学用树遍历解释器 |

按实现方式分：手写词法器/解析器（控制力强，适合语言本身较简单或已有成熟解析框架的场景）；生成器路线（Flex/Bison 按规则自动生成，适合文法稳定、规模较大的语言）。两种路线产出的编译器在阶段划分上是一样的，差别只在“前端代码是人写的还是工具生成的”。

代表性编译器与基础设施（版本与功能细节以官方发布为准，待核实）：GCC 是 GNU 的编译器套件，支持 C、C++、Fortran 等多种语言；LLVM 是一套模块化的编译器基础设施，Clang 是它上面最常见的 C/C++ 前端，Rust 编译器也以 LLVM 为后端；两者都是“前端 + IR 优化 + 后端”这一架构的工业级实现。

## 7. 应用与限制

典型应用：日常开发中每一次 `gcc`、`javac`、`rustc` 调用都是编译；跨平台工具链靠“多前端 + 多后端”覆盖语言与机器的组合；静态分析、代码格式化、IDE 的跳转与补全，大多复用了编译器前端的词法、语法、语义结果——它们不生成目标代码，但共享同一套“理解程序”的能力。

限制：

- 编译器只能保证“翻译忠实”，不能保证“程序逻辑正确”：算法写错了，编译器会忠实地把它编成高效的错误程序。
- 语义分析查的是“语言规则”，不是“业务规则”：把价格算错、把条件写反，编译器查不出来，那是测试与评审的事（见本域 03 篇）。
- 未定义行为是编译器的灰色地带：源语言标准说“这种情况结果未定义”，编译器有权按对自己最方便的方式处理，程序员不能依赖某次实测的表现。
- 编译时优化有天花板：运行时才知道的信息（如真实输入分布、实际类型），静态编译器看不到，这正是下一篇 JIT 要补的一块。

## 8. 常见误解

- **“编译通过 = 程序正确”**：错。编译通过只说明词法、语法、语义检查都过了，逻辑错误、业务错误、性能问题一概不在保证范围内。
- **“解释型语言没有编译”**：错。CPython 也会先把源码编成字节码再执行（见下一篇）；“解释型”说的是执行方式，不是“不经过编译”。
- **“优化一定让程序变快”**：错。内联、循环展开都会让代码变大，指令缓存装不下时反而变慢；优化是取舍，不是单调的“越多越好”。
