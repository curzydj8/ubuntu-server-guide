# 代码规范与风格指南

## 1. 一句话定义

代码规范是团队对“代码应该写成什么样”的一致约定，风格指南是把这套约定写成文的文档，lint 与 format 工具是让约定自动落地的执行手段。

## 2. 为什么需要它

代码被读的次数远多于被写的次数：接手的人、评审的人、半年后的自己，都要先读懂再改动。没有统一规范，同一份代码里会出现三种命名、两种缩进、五种换行方式，读代码的精力全花在适应风格上，而不是理解逻辑上。更实际的一点是：没有自动化工具背书的规范，会在评审里退化成无休止的风格争论——“这里该不该换行”这种问题，本该由机器回答，而不是由人争论。

规范解决的是三个问题：**可读性**（一眼看出结构与意图）、**一致性**（换人、换文件，风格不变）、**低摩擦协作**（评审只讨论逻辑对不对，不讨论格式好不好）。

## 3. 核心含义

### 3.1 规范管什么：命名、格式、结构三层

**命名：让名字说出意图。** 好名字回答三个问题：这是什么、起什么作用、边界在哪。`calc(a, b)` 不如 `calc_total(price, count)`，因为后者不需要读者再去读函数体猜参数含义。命名还有三条通用规矩：

- 同一个概念全仓用同一个词：不要一会儿 `user`、一会儿 `account`、一会儿 `customer` 指同一样东西。
- 名字里不藏类型缩写与无意义后缀：`data2`、`temp_str_final` 这种名字，等于把理解成本推给读者。
- 遵循语言社区的惯例，而不是自创一套：Python 里函数与变量用小写加下划线、类名用首字母大写的驼峰；JavaScript 里变量与函数多用小驼峰、常量用全大写加下划线。入乡随俗，读者才不用重新学习。

**格式：让排版不干扰阅读。** 格式管的是缩进、空行、行长度、括号与逗号的位置、引号风格这类“长什么样”的问题。格式本身不改变程序含义，但它决定了读者扫视代码时能不能快速定位：函数之间空行分隔、同一层级对齐、超长表达式折行，都是为了让结构一眼可见。

**结构：让写法不埋坑。** 有些规范超出排版，例如“一个函数只做一件事”“避免深层嵌套”“提前返回代替多层 else”。这类规范与代码质量直接相关，通常由 lint 规则或团队约定承载，而不是格式化工具。

### 3.2 行长度：没有唯一正确的数字，只有约定的数字

行长度是最容易引起争论的格式项，因为每个数字背后都有理由：

- **PEP 8 建议代码行不超过 79 字符、注释与文档字符串不超过 72 字符**，并允许团队协商一致后放宽到 99 字符。79 这个数字来自早期终端宽度，保守但通用。
- **Black 的默认行长度是 88 字符**（约为 80 的 110%，据其文档称该取值能产出更短的文件）。这是目前许多 Python 项目的实际默认值。
- 前端与 JVM 项目常见 80、100 或 120 字符的约定，具体数字由团队所选的风格指南决定。

关键结论：**行长度的数值本身不重要，重要的是全仓只有一个数值，并且由工具强制执行**。选 79 还是 88、100 还是 120，都可以；今天 79、明天 120、不同文件不同标准，不可以。行长度的上限还要和评审工具、分屏阅读的场景一起考虑：经常并排看两个文件、经常在小屏评审的团队，宜选更短的上限。

### 3.3 lint 与 format 的分工：一个管“对不对”，一个管“长什么样”

这是新手最容易混淆的一对工具，分工其实很干净：

| 工具 | 管什么 | 能不能自动改代码 | 出问题时谁处理 |
|---|---|---|---|
| format（格式化工具） | 只管排版：缩进、换行、空格、引号 | 能，而且应该全自动改 | 机器：保存时或提交前自动跑，不用人判断 |
| lint（静态检查工具） | 管规则与潜在问题：未使用变量、可疑写法、风格违规、部分 bug 模式 | 有的能自动修，有的只能报出来 | 人：看报告判断是真问题还是误报 |

分工不清的典型症状：用 lint 去争论缩进（该 format 管），或者指望 format 发现未使用变量（该 lint 管）。正确姿势是：**format 零容忍、零讨论**——保存即格式化，提交前自动检查，格式问题永远不进评审；**lint 分级处理**——错误级必须修，警告级逐条看，误报用规则配置或行内豁免说明原因，而不是悄悄关掉整条规则。

常见工具按语言分工（功能定位，具体版本与默认配置以官方发布为准）：

- Python：Black、Ruff format 负责格式化；Ruff、Flake8、Pylint 负责检查，其中 Ruff 把检查与格式化合在一个工具里。
- JavaScript / TypeScript：Prettier 负责格式化；ESLint 负责检查。
- C / C++：clang-format 负责格式化；clang-tidy 等负责检查。
- Go：gofmt 是官方自带的格式化工具，Go 社区普遍直接用它，争议最少。
- Rust：rustfmt 是官方自带的格式化工具；Clippy 负责检查。

### 3.4 EditorConfig：跨编辑器的最底层约定

EditorConfig 解决的是比 lint、format 更底层的问题：**不同编辑器打开同一个文件时，缩进、换行符、文件编码、行尾空格这些基础设定要一致**。它由一个放在项目根目录的 `.editorconfig` 文件（INI 格式）加各编辑器的插件组成：插件读到文件后，按其中的规则设置编辑器行为。它的关键字段都已按官方说明核对：

- `root = true`：写在文件顶部，声明这是最顶层的 EditorConfig 文件，向上查找就此停止。
- `indent_style = space | tab`：缩进用空格还是制表符。
- `indent_size`：每级缩进的列数；设为 `tab` 时取 `tab_width` 的值。
- `end_of_line`：换行符用 `lf` 还是 `crlf`，跨平台协作时尤其重要。
- `charset`、`trim_trailing_whitespace`、`insert_final_newline`：编码、行尾空格、文件末尾换行。

EditorConfig 的定位要摆正：它只管编辑器层面的基础格式，**不能替代 lint 与 format**。一个项目正确的做法是三层叠加：EditorConfig 定基础（缩进、换行）→ format 定排版（换行位置、引号）→ lint 定规则（命名、可疑写法）。三层之间有重叠时，以更具体的工具为准，不要在三处写互相矛盾的规则。

配置示例（已按 EditorConfig 官方说明核对字段含义；未在编辑器中实测加载效果）：

```ini
# 顶层 EditorConfig 文件
root = true

[*]
indent_style = space
indent_size = 4
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true

[*.{js,ts}]
indent_size = 2
```

上面例子里，`[*.{js,ts}]` 一节只对 JavaScript 与 TypeScript 文件把缩进改成 2，其余规则沿用 `[*]` 的通用设定——这就是 EditorConfig 按文件类型分段的用法。

## 4. 分类

### 4.1 按约束来源分

- **语言官方指南**：由语言官方或核心团队发布，社区默认遵守。代表是 Python 的 PEP 8、Go 的 gofmt 惯例。这类指南的权威性最强，新项目优先采用。
- **公司与组织指南**：由大公司公开发布，供自家开源项目与外部团队参考。代表是 Google 风格指南系列，覆盖 C++、Java、JavaScript、Python 等语言（Google 的公开说明指出，这些指南是其内部指南的副本，主要服务于 Google 发起的开源项目）。采用时注意：其中有些规则是 Google 内部环境的产物（例如其 C++ 指南对异常的限制），不一定适合所有项目，照搬前要判断。
- **社区流行指南**：由社区项目维护、被大量项目采用，例如 JavaScript 的 Airbnb 风格指南。这类指南的细节以官方发布为准，本文不逐条转述。
- **团队自定指南**：在官方或社区指南之上，只写“我们团队的例外与补充”，而不是重写一整套。例如“本项目行长度用 100，不用 Black 默认的 88”“本项目禁用某条 lint 规则，原因是……”。

### 4.2 按语言家族分

- **Python 家族**：PEP 8 是基准；Black 或 Ruff format 是事实上的格式化标准（默认行长度 88）。新项目建议直接用 Ruff（一站式检查加格式化）或 Black 加 Ruff 的组合，不要从零手写规则。
- **C / C++ 家族**：clang-format 是格式化主力，风格文件（`.clang-format`）入仓；Google C++ 风格指南、LLVM 风格是常见的预设起点，选其一后全仓统一。
- **JVM 家族（Java / Kotlin）**：Google Java Format 是 Java 的常见格式化工具；Kotlin 有官方的 Kotlin 编码规范，具体条目以官方发布为准（待核实）。
- **前端家族（JavaScript / TypeScript）**：Prettier 管格式、ESLint 管规则是主流分工；Airbnb、Google、Standard 是常见的规则预设，选其一并锁定版本，不要混用两套预设。
- **Go / Rust 家族**：官方自带格式化工具（gofmt、rustfmt）就是标准，争议空间最小；团队要做的只是“规定必须跑”，而不是“规定怎么排”。

### 4.3 按执行位置分

- **编辑器层**：保存时自动格式化（EditorConfig + format 工具），问题在写下时就消失。
- **提交前层**：提交钩子或提交检查跑 format 与 lint，格式问题拦在本地，不进仓库。
- **持续集成层**：CI 里跑 `format --check` 与 lint，任何人、任何分支都绕不过去。这是团队规范的最终防线：本地可以忘，CI 不能忘。

## 5. 典型应用

- **新项目落地**：建仓第一天就把三件套放进去——`.editorconfig`、format 配置、lint 配置与 CI 检查。规范越晚引入，已有代码的改造成本越高。
- **接手遗留代码**：先做一次纯格式统一提交（只改格式、不改逻辑），再开始改逻辑。格式与逻辑混在一个提交里，评审人无法分辨哪行是格式、哪行是逻辑变更。
- **代码评审提效**：评审约定“格式问题一律不人工提，由工具处理”，评审人的注意力只放在逻辑、边界、命名意图上。
- **跨编辑器协作**：团队里有人用 VS Code、有人用 JetBrains、有人用 Vim，EditorConfig 保证基础格式不因编辑器而异。

## 6. 限制与常见误解

- **规范好不等于代码好**：格式全对、lint 全过的代码，逻辑仍然可以是错的。规范是可读性的下限，不是正确性的证明。
- **不要搞全仓一次性大格式化加逻辑重构的混合提交**：纯格式提交会改动大量行，混进逻辑变更后，`git blame` 与评审都会失效。格式提交与逻辑提交必须分开（版本控制的提交拆分做法见 [Git 工作流](02-git-workflows.md)）。
- **lint 全过不等于没有问题**：lint 只能发现规则覆盖的模式；业务逻辑错误、需求理解偏差，lint 看不出来。不要把 lint 报告当成测试报告。
- **风格争论要用自动化终结**：两个人对同一格式各执己见时，正确动作是“选一个工具默认值、写进配置、以后不再讨论”，而不是每次评审重争一次。工具默认值可能不是你最喜欢的，但“全仓一致”比“我的偏好”重要。
- **规范要随项目演进，但改动要走流程**：行长度、规则开关这类变更，会影响全仓历史代码的格式；改之前先评估影响范围，改之后用一次纯格式提交落地，不要悄悄改配置。

## 7. 小结

代码规范是团队对命名、格式与写法的共同约定；行长度没有唯一正确答案，但全仓必须只有一个答案；format 管排版、lint 管规则、EditorConfig 管编辑器基础格式，三层叠加、各司其职；规范的终点是自动化执行——能由机器强制的，就不要留给人工争论。

## 附：示例与实测说明

下面示例用 Python 演示“命名”与“行长度”两个最直观的规范点。运行环境：Python 3.12.3，VM 本地运行，实测通过：

```python
def calc(a, b):
    return a * b + a * 0.1  # 含义不明的 a、b：单看名字不知道算什么

def calc_total(price, count):
    """单价 * 数量，再加 10% 税费；名字自解释。"""
    return price * count * 1.1

samples = {
    "过长行": "result = calculate_the_total_amount_of_the_order_including_all_taxes_and_fees(order)",
    "改写后": "total = calc_total(price, count)",
}
for name, line in samples.items():
    print(f"{name}：{len(line)} 字符，{'超过 79 字符' if len(line) > 79 else '在 79 字符内'}")

print("calc_total(100, 3) =", calc_total(100, 3))
```

实测输出（Python 3.12.3，本地运行）：

```
过长行：84 字符，超过 79 字符
改写后：32 字符，在 79 字符内
calc_total(100, 3) = 330.0
```

84 字符的长行超过了 PEP 8 的 79 字符建议，改写后 32 字符且名字自解释。注意：本示例只演示命名与行长度的度量，VM 上未安装 Black、Ruff、ESLint、Prettier，因此格式化工具的实际运行效果标为示例未实测，不声称已跑过。
