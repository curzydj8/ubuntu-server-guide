# Git 对象模型与内部原理

## 1. 一句话定义

Git 的核心是一个内容寻址的对象数据库：文件内容、目录结构、提交历史和带注释的标签都被存为不可变对象，用内容哈希作 ID，再由引用（分支、标签、HEAD）指向这些对象。

## 2. 为什么需要它

只看 `git log` 和 `git status`，Git 像个黑盒：一旦遇到“提交丢了能不能找回”“仓库为什么越来越大”“为什么改写历史这么危险”这类问题，黑盒视角就答不上来。理解对象模型后，这些问题都有确定的答案：提交是快照的指针链，分支只是可移动的指针，所谓“丢失”往往只是引用丢了、对象还在；而仓库膨胀与瘦身，对应的就是松散对象、打包与回收这条线。

本篇只讲内部原理。分支怎么开、合并与变基怎么选、冲突怎么处理、提交信息怎么写，见本目录的 [Git 工作流](02-git-workflows.md)；分支策略怎么选、评审怎么做，见下一篇 [分支策略与代码评审流程](11-branching-code-review.md)。

## 3. 核心含义

### 3.1 四种对象

Git 只有四种对象，每种对象由类型、大小和内容三部分组成，对象 ID 是对“类型 + 大小 + 内容”算出的哈希：

| 对象 | 存什么 | 关键点 |
|---|---|---|
| blob | 一个文件的内容 | 只有内容，没有文件名、权限、目录信息；内容相同的文件共享同一个 blob |
| tree | 一个目录的清单 | 每条记录含模式、类型、对象 ID、文件名，指向 blob（文件）或下一级 tree（子目录） |
| commit | 一次快照及其来历 | 指向一棵根 tree、父提交（合并提交有两个或更多父提交）、作者与提交者及时间、提交信息 |
| tag | 带注释的标签对象 | 含指向目标对象（通常是提交）、类型、标签名、标签者、日期、信息；注意与轻量标签区分，见 3.3 节 |

四种对象一层层搭起来就是一次提交的完整含义：commit 指向根 tree，tree 指向子 tree 与 blob，blob 是文件内容；commit 再通过父提交指针连成有向无环图（DAG），这就是历史本身。分支、标签、HEAD 都不存内容，只存指针。

### 3.2 内容寻址与松散对象存储

“内容寻址”的意思是：地址就是内容算出来的，不查表、不分配序号。同一份内容在任何仓库里算出同一个 ID，改一个字节就是另一个对象；读对象时 Git 会校验 ID 是否仍与内容对应，内容损坏能被发现，而不是静默读错。

新产生的对象先以“松散对象”形式落盘，放在 `.git/objects/` 下，按 ID 分目录：前 2 位十六进制字符作子目录名，剩下 38 位作文件名（SHA-1 为 40 位十六进制时）。单个对象文件经 zlib 压缩。仓库的另外两个关键部分是：`.git/refs/`（引用，见 3.3 节）和 `.git/index`（暂存区信息）；`.git/HEAD` 则指向当前分支。

下面的演示是在 VM 上真实建库跑出来的（Git 2.43.0，演示身份 `Demo User <demo@example.com>`，固定提交时间；哈希是该演示仓库的值，换一个仓库、换一次提交时间就会不同）：

```bash
git init -b main
printf 'hello\n' > hello.txt
git add hello.txt
git commit -m "feat: initial version"
git log --oneline
git cat-file -p HEAD
git ls-tree HEAD
git hash-object hello.txt
```

实测通过，输出：

```
bbe018e feat: initial version
tree aaa96ced2d9a1c8e72c56b253a0e2fe78393feb7
author Demo User <demo@example.com> 1793757600 +0800
committer Demo User <demo@example.com> 1793757600 +0800

feat: initial version
100644 blob ce013625030ba8dba906f756967f9e9ca394464a hello.txt
ce013625030ba8dba906f756967f9e9ca394464a
```

读法：`cat-file -p HEAD` 展示提交对象的内容——它指向根 tree `aaa96ce…`，并记录作者与提交者；`ls-tree HEAD` 展示根 tree 的一条记录：模式 `100644`（普通非可执行文件）、类型 blob、ID `ce01362…`、文件名 `hello.txt`；`hash-object` 直接算出 `hello.txt` 内容的 blob ID，与 tree 里的 ID 一致，验证了“文件名在 tree 里、内容在 blob 里”这一分工。此时 `.git/objects/` 下的松散对象正好是 3 个：

```
.git/objects/aa/a96ced2d9a1c8e72c56b253a0e2fe78393feb7
.git/objects/bb/e018efb14006b27e7cdf09a4a446f5d657ea97
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
```

### 3.3 引用：分支、标签与 HEAD

引用（ref）就是“给某个对象 ID 起的人名”，存在 `.git/refs/` 下：

- 分支：`refs/heads/<分支名>`，指向一个提交；提交时该指针前移。新建分支只是新建一个指针文件，几乎零成本——这正是 02 篇说“分支是指针，不是副本”的内部原因。
- 轻量标签：`refs/tags/<标签名>` 直接指向一个提交，没有自己的对象，适合本地临时标记。
- 附注标签：先产生一个 tag 对象，再由 `refs/tags/<标签名>` 指向它，适合正式发布（可签名、可写发布说明）。
- HEAD：通常是一个符号引用，指向当前分支（`ref: refs/heads/main` 之类）；“分离 HEAD”状态下它直接指向某个提交 ID。

演示（同一演示仓库，Git 2.43.0，实测通过）：

```bash
git tag v0.1
git tag -a v0.2 -m "release 0.2"
git cat-file -t v0.1
git cat-file -t v0.2
git cat-file -p v0.2
```

输出：

```
commit
tag
object bbe018efb14006b27e7cdf09a4a446f5d657ea97
type commit
tag v0.2
tagger Demo User <demo@example.com> 1793757600 +0800
```

`cat-file -t` 是查对象类型的管道命令：轻量标签 `v0.1` 直接就是 `commit` 类型（它本身不是对象），附注标签 `v0.2` 是 `tag` 类型，其内容指向被标记的提交 `bbe018e…`。发布时用附注标签、临时标记用轻量标签，分工就来自这一区别。

### 3.4 reflog：引用的“后悔药”

reflog 记录每个引用（最常用的是 HEAD）每次移动的旧值与新值。分支删了、提交被 `reset` 盖过去了，只要 reflog 还在、对象还没被回收，就可以按 `HEAD@{n}` 找回。reflog 不是历史本身：它记录的是“你的指针动过哪”，且只存在本地，不随推送同步给别人。

演示（同一演示仓库，Git 2.43.0，实测通过）：先在 `main` 上多提交一次，再 `reset --hard` 回到上一个提交，然后看 reflog：

```
bbe018e HEAD@{0}: reset: moving to HEAD~1
a66f1b5 HEAD@{1}: commit: feat: second version
bbe018e HEAD@{2}: commit (initial): feat: initial version
```

`HEAD@{1}` 的 `a66f1b5` 就是被 reset 盖过去的那个提交：只要知道这个 ID，就能重新建分支指向它把它捞回来。反过来也说明了边界：reflog 有过期时间，过期且不可达的对象才会被回收；reflog 本身被清空或过期后，这条找回路径就没了。

### 3.5 packfile：把松散对象打包、做增量

松散对象每对象一个文件，对象一多，文件数和磁盘占用都难看。packfile 把许多对象收进一对文件：`.pack`（对象数据）与 `.idx`（索引，支持按 ID 快速定位）。打包时 Git 还会对相似对象做增量（delta）压缩：一个对象存完整内容，另一个只存相对它的差异，读的时候再还原——历史越长、文件改动越小，增量压缩的收益越大。这也是“提交是快照”与“仓库不大”并不矛盾的原因：逻辑上每次提交都是完整快照，物理上相似内容只存差异。

### 3.6 gc：整理仓库的管家

`git gc` 是一组日常整理任务的合集：压缩文件修订、把松散对象打包进 packfile、打包引用（packed-refs）、清理 reflog、删除不可达对象、更新 commit-graph 等辅助索引。官方文档的定位是：日常使用一般不需要手动跑 gc，一次性优化或批量导入后的整理才需要手动跑；更激进的 `--aggressive` 会丢弃已有增量并重算，耗时明显更长，不要当成日常命令。

演示（同一演示仓库，Git 2.43.0，实测通过）：gc 前后用 `git count-objects -v` 对比：

```
# gc 前
count: 7
in-pack: 0
size-pack: 0
# git gc 后
count: 0
in-pack: 7
```

7 个对象（两个提交、两棵 tree、两个 blob、一个 tag 对象）全部进了包文件，松散对象清零。值得注意的是：被 reset 盖过去的提交 `a66f1b5` 也在包内——因为它仍被 reflog 引用，gc 不会把它当不可达对象删掉。gc 的默认 reflog 过期策略是：可达引用记录 90 天，不可达引用记录 30 天（以所用 Git 版本的官方文档为准）。所以“删分支后立刻 gc”并不会立刻丢数据，真正丢数据的是“reflog 过期 + 对象不可达 + gc 清理”三者凑齐。

## 4. 分类

按对象在仓库里的角色分两类就够了，不必另造分类：

- **内容对象（blob、tree、commit、tag）**：不可变，ID 由内容决定，构成快照与历史本身。
- **引用（分支、轻量标签、HEAD、远程跟踪分支等）**：可移动的人名，指向内容对象；移动引用不改写任何对象，只改指针文件。

按存储形态则是另一条线：松散对象（每对象一文件，写时快）与 packfile（打包 + 增量，读与传输省空间），gc 负责在两者之间搬运与清理。

## 5. 典型应用

- **找回“丢了”的提交**：先查 `git reflog`，找到旧 ID 后建分支指向它；这是处理误 reset、误删分支的第一步。
- **诊断仓库膨胀**：`git count-objects -v` 看松散对象与包大小，`git verify-pack -v` 看包内对象与增量情况，再决定是否 gc、是否把大二进制文件迁出历史（大文件问题本身见 02 篇第 7 节）。
- **理解“改写历史为什么危险”**：提交对象不可变，所谓改写其实是产生一批新对象、移动指针；已公开的旧对象别人手里还有，两套历史对不上就是混乱的来源。
- **读懂发布标记**：附注标签自带标签者与说明，适合发布；轻量标签只是个指针，适合临时标记——发布流程里混用两者会让“这个版本到底是谁、何时定的”说不清楚。

## 6. 限制与常见误解

- **“Git 存的是差异”**：错。逻辑上每次提交都是完整快照；差异只出现在 packfile 的物理压缩层。把两层混为一谈，就会误以为“改一行只存一行”是全部真相。
- **“删分支 = 删提交”**：错。删分支只删指针，对象还在；只要 reflog 未过期、gc 未清理，提交都可找回。反过来，真正想彻底删除敏感内容进历史，光删分支远远不够（需要改写历史并让所有副本过期清理，具体操作以官方发布为准，见文末未完成项）。
- **“gc 能随时放心跑”**：不完全对。gc 本身是常规整理，但它会清理过期且不可达的对象；在确认“被 reset 盖过去的提交确实不要了”之前跑带清理的 gc，等于亲手关掉后悔药的窗口。
- **“对象 ID 就是 SHA-1，永远不变”**：需加限定。本篇示例使用默认的 SHA-1 仓库（40 位十六进制）。Git 另有 SHA-256 对象格式，其作为生产默认的可用状态以官方发布为准（待核实），见文末未完成项。

## 7. 小结

Git = 内容寻址的对象数据库 + 可移动的引用。blob 存内容，tree 存目录，commit 存快照与父链，tag 给发布加注释；松散对象写时快、packfile 省空间、reflog 是本地后悔药、gc 是整理管家。记住“对象不可变、引用可移动”，历史相关的多数怪现象就都有了解释。
