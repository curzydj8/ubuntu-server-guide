# 编程范式比较：命令式、声明式、函数式、面向对象

## 1. 一句话定义

编程范式是组织和思考程序的一套高层风格：它决定程序由什么构成、状态放在哪里、变化怎样发生——同一门语言通常可以支持多种范式。

## 2. 为什么需要它

同一个需求可以用很多种写法实现，但写法背后的“思考方式”决定了代码好不好改、好不好测、出了问题好不好定位。范式就是给这种思考方式起的名字：先认出自己在用哪种范式，才能说清它的收益和代价，而不是凭感觉争论“哪种写法更好”。

没有范式意识的常见后果是：状态散落在各处、谁改了数据说不清；一个函数既算结果又改全局变量，测试时必须先搭好一整套环境；换一种写法时不知道自己到底在换什么。

## 3. 核心含义

理解范式先抓两个最关键的区分。

**第一组区分：命令式与声明式。**命令式（imperative）是“告诉计算机怎么做”：用一条条语句显式控制执行顺序、一步步改变程序状态。声明式（declarative）是“描述想要什么结果”：只声明结果应满足的性质，不规定详细的求解步骤，具体怎么执行由语言或执行引擎决定。

**第二组区分：范式不是语言的标签，而是写法的标签。**一种语言可以支持多种范式，同一个程序里也可以混用多种范式。给语言贴单一范式标签（例如“Python 是面向对象语言”）会误导选型：更准确的说法是“这段代码主要用了哪种范式”。

**状态与副作用是贯穿四种范式的标尺。**命令式程序的核心是状态变化；函数式追求用无副作用的函数组合出结果；面向对象把状态收进对象内部、用方法控制访问；声明式把“怎么变”藏进执行引擎。读一段代码时，先问“状态在哪、谁能改它”，范式就看清了一大半。

## 4. 分类

### 4.1 命令式：一步步改状态

命令式程序由显式规定执行顺序的语句组成，并允许副作用：某处代码改了状态，另一处代码随后读到新值。过程式（procedural）是命令式下最常见的组织方式：把语句分组为过程（函数），用变量、循环和函数调用推进计算。

```python
# 命令式：状态 total 一步步被改变
total = 0
for n in [1, 2, 3, 4]:
    total += n
print("imperative total:", total)
```

> 实测通过（Python 3.12.3）：输出 `imperative total: 10`。

**适合：**步骤本身就是需求的场景，如按固定流程处理数据、操作硬件或文件。**代价：**状态变化散开后，推理“此刻这个值为什么是这样”需要追踪整条执行路径。

### 4.2 面向对象：把数据和操作它的方法绑在一起

面向对象（object-oriented）把程序组织为对象：每个对象持有自己的状态（字段），并通过方法（method）对外提供行为，状态通常只由归属对象的方法修改。注意它的位置：大多数面向对象语言同时也是命令式语言——面向对象主要解决“代码怎么组织”，命令式解决“计算怎么推进”，两者不在同一层面上互斥。

```python
# 面向对象：余额是对象内部的状态，只能通过方法改变
class Account:
    def __init__(self, balance):
        self.balance = balance
    def deposit(self, amount):
        self.balance += amount

acc = Account(100)
acc.deposit(50)
print("oop balance:", acc.balance)
```

> 实测通过（Python 3.12.3）：输出 `oop balance: 150`。

**适合：**业务实体边界清晰的场景，如账户、订单、用户——把“这个实体能做什么”收拢到一处。**代价：**对象之间互相持有引用、状态层层传递时，系统行为会变得难以一眼看清；滥用继承会让改动牵一发而动全身。

### 4.3 函数式：用函数组合出结果，避开可变状态

函数式（functional）是声明式的一个子集：把期望结果声明为一系列函数求值的结果，强调像数学函数那样工作的函数——相同输入总得到相同输出，不修改外部状态（纯函数），多用函数组合与递归，少用可变变量和循环改状态。

```python
# 函数式：纯函数 double + filter/map 组合，原列表不被修改
def double(x):
    return x * 2

nums = [1, 2, 3, 4]
result = list(map(double, filter(lambda x: x % 2 == 0, nums)))
print("functional result:", result)
print("functional original unchanged:", nums)
```

> 实测通过（Python 3.12.3）：输出 `functional result: [4, 8]`，`functional original unchanged: [1, 2, 3, 4]`。

**适合：**数据变换管道、并发友好的计算——无副作用的函数天然容易单独测试和并行。**代价：**输入输出、随机数、时间这类“与世界打交道”的部分绕不开副作用，纯函数式语言也要用专门机制（如把副作用包进特定结构）来处理；全盘照搬函数式写法还可能让熟悉命令式的团队读不懂。

### 4.4 声明式（查询式）：只说要什么，让引擎决定怎么找

声明式不止函数式一种。查询式是另一类常见形态：SQL 只描述“要满足什么条件的数据”，不写遍历、比较、回表的步骤，数据库引擎自己选执行方式。

```python
# 声明式：SQL 只说“分数 >= 90 的学生姓名”，不说怎么遍历
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE students (name TEXT, score INTEGER)")
db.executemany("INSERT INTO students VALUES (?, ?)",
               [("小李", 95), ("小王", 80), ("小张", 92)])
rows = db.execute(
    "SELECT name FROM students WHERE score >= 90 ORDER BY name"
).fetchall()
print("declarative sql rows:", rows)
```

> 实测通过（Python 3.12.3，SQLite 3.45.1）：输出 `declarative sql rows: [('小张',), ('小李',)]`。

**适合：**“条件明确、执行可交给引擎优化”的场景，如数据库查询、界面布局描述、构建规则。**代价：**“不用管怎么执行”不等于“不用管性能”：同一条声明在不同数据规模下可能走完全不同的执行路径，慢查询仍需看执行计划、做实测——这部分以官方发布为准（待核实），见文末未完成项。

## 5. 典型应用

- **数据处理管道用函数式变换：**一批记录经过筛选、映射、聚合得到报表，中间结果不变，某一步算错只影响该步，定位快。
- **业务实体用面向对象建模：**账户、订单这类“有状态、有行为规则”的实体收进对象，存款、扣款等规则只在对象方法里改状态。
- **批量数据查询用声明式：**“找出分数 90 分以上的学生”写成一条 SQL，换数据库、换数据量时查询意图不用重写。
- **流程与底层步骤用命令式过程：**按固定顺序读写文件、调用接口、处理异常时，显式步骤最直观，也最容易单步调试。

## 6. 限制与常见误解

- **“一种语言只属于一种范式”**：错。Python、JavaScript、C++ 等主流语言都是多范式，同一项目里过程式、面向对象、函数式写法常常共存；范式描述的是写法，不是语言的出身证明。
- **“用了 class 就是面向对象”**：错。只把函数塞进类里、状态到处可改，等于穿了对象外衣的过程式代码；封装（状态由对象方法控制）和清晰的实体边界才是关键。
- **“函数式一定更快、一定更好测”**：错。纯函数确实好单独测试，但函数式写法本身不保证性能；是否快、是否省内存，仍要按实际数据规模实测。
- **“声明式就不用管执行”**：错。声明式只是把执行细节交给引擎，不是不存在执行细节；数据量、索引、引擎版本都会改变实际行为，关键路径仍需实测。
- **范式不能解决需求本身的问题**：需求模糊、边界不清时，换范式只是换一种方式写出同样混乱的代码；先把“状态归谁管、变化从哪来”想清楚，再选范式。

## 7. 小结

范式是组织程序的思考方式：命令式讲“怎么做”，声明式讲“要什么”，函数式是声明式下用纯函数组合的子集，面向对象是命令式下把状态收进对象的组织方式。
选范式不是站队，而是按场景取舍：状态归谁管、变化从哪来、出了问题好不好定位，才是判断标准。
