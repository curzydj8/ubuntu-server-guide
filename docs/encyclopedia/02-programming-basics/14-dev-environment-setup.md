# 开发环境搭建与容器化开发

## 1. 一句话定义

开发环境是写代码、构建、运行与调试所依赖的一整套工具、运行时与配置的组合；容器化开发环境是把这套环境装进容器里运行、从而让不同机器得到同一套环境的开发方式。

## 2. 为什么需要它

没有成文的开发环境，新人入职第一周可能都在装工具、调版本：同样的代码在 A 的机器上能跑，在 B 的机器上报错，报错原因不是代码，而是 Node、Python、编译器或系统库的版本不一样。更糟的是这种差异出现得很晚——本地通过的代码到了同事机器或 CI 上才失败，排查时先要排除“是不是环境问题”。

一份可复现的开发环境解决三个问题：**新人能按步骤装出同样的环境；同一项目在不同机器上行为一致；环境配置本身可以像代码一样被记录、评审和回滚**。容器化是把这一步推到底的做法：环境不再是一份“安装说明”，而是一个可以直接启动的镜像。

## 3. 核心含义

开发环境可以按层理解，从底向上每一层都可能成为“在我机器上能跑”的来源：

```text
操作系统与系统包（编译器、系统库）
    │ 语言运行时（Node、Python、JDK、Go……）
    │ 版本管理器（同一语言装多个版本、按项目切换）
    │ 编辑器与语言服务（补全、跳转、格式化、检查）
    │ 项目依赖（第三方库，见本域第 15 篇）
    │ 本地服务与配置（数据库、缓存、环境变量、密钥）
```

### 3.1 版本管理器：语言版本也要按项目钉住

一台机器上常常要同时维护多个项目，而不同项目可能要求不同的语言版本。版本管理器的作用就是：**同一语言装多个版本，并按项目自动或手动切换**，而不是全局只装一个版本、每次换项目就重装。

常见工具与按项目钉选的机制（各工具的安装命令以官方发布为准，见文末未完成项）：

- **nvm（Node.js）**：在项目根目录放一个 `.nvmrc` 文件写明版本，进入目录后执行 `nvm use` 即可切换到该文件指定的版本。
- **pyenv（Python）**：`pyenv local <版本>` 会在项目里写一个 `.python-version` 文件，之后进入该目录就使用对应解释器。注意 pyenv 只管解释器版本，不管包：包的隔离要另外用 Python 自带的虚拟环境（`python -m venv`，见第 15 篇实测）。
- **rustup（Rust）、SDKMAN!（JVM 生态）**：同一思路在各自生态的版本管理器；另外还有 mise、asdf 这类跨语言的版本管理器。

关键点不在于记住某个工具，而在于理解分工：**版本管理器管“语言本身是哪个版本”，包管理器管“项目依赖了哪些库、哪个版本”**，两者不要混为一谈。把 `.nvmrc`、`.python-version` 这类钉选文件提交进版本控制，团队成员 checkout 后就能对齐语言版本。

### 3.2 编辑器：编辑器是开发环境的“驾驶舱”

编辑器不只是写字的地方。现代编辑器通过语言服务器（LSP）提供跳转定义、补全、重构，通过格式化器与检查器（linter）统一代码风格与提前发现问题。选编辑器时真正要对齐的是三件事：

- **语言支持是否来自语言服务器**：同一语言在不同编辑器里体验接近，靠的是 LSP，而不是编辑器自带的高亮。
- **格式化与检查规则是否随项目走**：规则文件（如格式化配置）应放在仓库里，而不是只存在某个人的编辑器设置里，否则同一份代码在不同人手里会被格式化成不同样子。
- **插件与设置是否可复现**：团队可以约定一份推荐插件与设置清单；容器化开发（见 3.3 节）则把这一步也做进了容器配置里。

编辑器本身没有“唯一正确”的选择；但“每个人的编辑器行为都不一样”是一个真实成本，约定与配置进仓库就是在还这笔账。

### 3.3 devcontainer：把环境写进一个 JSON 文件

Dev Container（开发容器）的做法是：在项目里放一个 `.devcontainer/devcontainer.json`，声明开发容器用什么镜像、装哪些编辑器插件、转发哪些端口、启动后执行什么命令。支持该规范的编辑器（如 VS Code 的 Dev Containers 扩展）读到这个文件后，会构建或拉取镜像、创建容器，并把编辑、终端、语言服务都接到容器内部执行——代码仍在本地仓库，运行环境在容器里。

一个最小示例（**示例未实测**：本 VM 未安装 Docker，且本 VM 上容器无法实际运行，见第 6 节）：

```json
{
  "name": "Node.js Dev Environment",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint"]
    }
  },
  "forwardPorts": [3000]
}
```

其中 `image` 指定基础镜像，也可以改用 `dockerfile` 字段指向自定义 Dockerfile，或用 Docker Compose 描述“应用容器 + 数据库容器”这样的多容器开发环境；`forwardPorts` 把容器里的开发服务器端口映射到本机浏览器访问；`customizations` 里声明的插件会在容器内安装，而不是只装在本机。

这样做的好处是**环境配置与代码同仓库、同评审**：换一台机器，只要拉代码、按 devcontainer 打开，就能得到同一套工具链与插件；坏处是第一次构建镜像要花时间，且容器里跑开发服务器、文件监听与调试，性能与体验与本机直跑不完全一样，需要实测取舍。

### 3.4 容器化开发环境的边界：开发环境不是生产部署

容器化开发环境与生产部署共用“容器”这项技术，但目标不同，配置也不应混用：

- **开发镜像可以装调试工具、挂载源码目录、开热重载**；生产镜像应尽量小、只含运行所需文件、不含源码与调试工具。
- **开发环境的数据库、缓存等配套服务只是本地替身**：数据可以随时重建，丢了不心疼；生产数据绝不能这样对待。
- **密钥绝不写进镜像或 devcontainer 配置**：本地开发用环境变量或本机密钥管理注入，提交进仓库的配置里只能有占位符。

容器编排（多机调度、副本、服务发现、滚动升级）是另一层问题，本篇不展开，见相关主题里的 09 域文章。

## 4. 分类

按“环境跑在哪里”分，开发环境有四种常见形态：

- **本机直装**：工具直接装在自己的操作系统上。最简单、最快，但最容易随时间漂移（系统升级、全局包升级都会悄悄改变环境）。
- **版本管理器 + 虚拟环境**：语言版本与项目依赖分别钉住、彼此隔离。这是大多数项目性价比最高的形态，也是本机直装的升级版。
- **容器化开发环境（devcontainer）**：整个工具链在容器里，配置进仓库。一致性最强，但依赖容器运行时，构建与文件同步有额外成本。
- **云端开发环境**：开发环境跑在远端机器或云服务上，本地只留编辑器前端。换设备成本最低，但依赖网络，且计费与数据归属要单独评估（具体服务与价格以官方发布为准，见文末未完成项）。

没有一种形态在所有场景都最优：个人小项目本机直装足够；团队协作、入职频繁或“在我机器上能跑”反复出现时，值得升级到容器化或云端形态。

## 5. 典型应用

- **新人入职**：按仓库里的环境声明（版本钉选文件或 devcontainer）一步搭建，与老成员得到同一套工具链，而不是照着一份半年没更新的安装文档逐项排查。
- **多项目并行**：不同项目钉不同语言版本，切换目录即切换运行时，避免“为 A 项目升级 Node，结果 B 项目跑不起来”。
- **复现他人报告的问题**：用对方的环境声明重建同一环境，先确认问题与环境无关，再谈代码本身；排除了环境变量，调试范围立刻缩小。
- **教学与开源协作**：贡献者不用先花半天配环境就能跑起项目、跑通测试，参与门槛直接降低。

## 6. 限制与常见误解

限制，必须说清：

- **容器化不等于“绝对可复现”**：镜像标签（如 `latest` 或只写大版本）指向的内容可能随时间变化；要真可复现，需要钉住镜像摘要或确切版本，并把构建步骤本身也纳入版本控制。
- **本 VM 上容器无法实际运行**：本篇的 devcontainer 与 Dockerfile 示例均未在本 VM 上实测（Docker 未安装，且本 VM 的容器运行时受限，无法承诺容器执行）。读者应在自己有 Docker 的机器上实测后再采用。
- **容器不能解决所有环境问题**：宿主机的文件系统性能、端口占用、GPU 或 USB 等硬件直通，容器化后仍可能成为新的差异来源。

常见误解：

- **“用了容器，环境问题就消失了”**：错。容器只是把环境差异从“装了什么”转移到了“镜像怎么构建、哪个版本”；不钉版本、不进版本控制的容器配置，漂移只会换个地方出现。
- **“版本管理器能管所有依赖”**：错。以 pyenv 为例，它只管 Python 解释器版本；项目依赖的包版本要靠虚拟环境与依赖声明（见第 15 篇），两者缺一不可。
- **“devcontainer 就是生产部署”**：错。开发容器图的是调试方便与快速迭代；生产部署要考虑镜像大小、权限、密钥与编排，那是 09 域的范畴，本篇只做引用、不展开。

## 7. 小结

开发环境是工具、运行时与配置的组合，可复现是它的核心价值；版本管理器钉住语言版本，编辑器配置与依赖声明进仓库，容器化则把整套环境变成可启动、可评审的配置。边界是：开发环境解决“写代码时一致”，生产部署与容器编排是另一层问题。
