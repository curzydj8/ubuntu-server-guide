# 网络取证入门

> 本篇只讲网络取证的流程、方法与证据保全。示例一律用自造的测试数据，
> 不含真实案件数据、真实个人信息、真实 IP 地址或真实案件细节。采集流量
> 必须以合法授权为前提：只在自有网络、自有系统或明确授权的范围内采集，
> 未授权拦截他人通信不在本文讨论内。取证全流程与证据链见
> [取证基础与证据链](01-forensics-basics-evidence-chain.md)，本篇不复制。

## 1. 一句话定义

网络取证是在授权范围内，对网络流量记录与相关日志做采集、保全、检查、
分析并形成结论的过程，其目标是回答“网络上发生了什么、按什么顺序、
涉及哪些端点”，且每一步都可被第三方复核。

## 2. 为什么需要它

磁盘与内存取证回答的是“一台设备上发生了什么”，网络取证回答的是
“设备之间发生了什么”。很多痕迹只存在于网络一侧：一次异常连接的
时间与方向、一段时间内的数据流向、某个端点在事件窗口内联系过谁。
设备被重装或日志被清理后，网络侧的记录有时是唯一还能拼出时间线的
材料；反过来，网络记录本身也最容易消失——抓包文件会被滚动覆盖，
流记录会被聚合或丢弃，内存里的连接状态随进程退出而消失。

网络取证与入侵检测是配合关系，不是同一件事。检测负责实时发现异常
并告警（见[检测与应急响应](../10-security/03-detection-incident-response.md)），
取证负责在事件发生后，把网络侧的事实固定下来、拼成可验证的时间线。
只看告警不留证据，事后无法复核；只留原始流量不做分析，结论也出不来。

## 3. 核心含义

### 3.1 先定授权与范围，再动手采集

网络取证的第一步不是开抓包工具，而是确认三件事，并把确认结果写进
调查记录：

1. **授权**：采集行为是否有合法授权，授权来自谁、覆盖哪些网络段与
   时间段。超出授权范围的流量不采集、不查看、不留存。
2. **范围**：调查问题是什么，需要回答的是“某端点在某时间段内的对外
   连接”，还是“某服务在某时间段内的全部会话”。范围决定采集点与
   保留时长，范围不清就会采多（侵犯隐私、淹没分析）或采少（漏掉
   关键会话）。
3. **最小必要**：只采集调查问题需要的数据。流量里常含与调查无关的
   个人通信内容，采集、查看与留存都要限于必要范围，超出需要的
   部分不扩散。隐私边界的通用原则见
   [取证基础与证据链](01-forensics-basics-evidence-chain.md)第 3.7 节。

没有授权的流量拦截，即使技术上可行，也不属于本文讨论的取证行为。
授权测试的通用流程见
[授权测试工作流](../10-security/02-authorized-testing-workflow.md)。

### 3.2 流量采集原则：采全、采准、不干扰

常见的流量来源有三类，各有取舍，采集前要按调查问题选，而不是
默认“全量抓包就是最好”：

- **端口镜像（SPAN）**：把交换机上一个或多个端口的流量复制一份
  送到采集口。优点是不改变原始路径、不给被测链路增加设备；
  缺点是镜像口带宽不足时会丢包，丢掉的包不会出现在记录里，
  分析时要把“可能丢包”写进局限性。
- **抓包（报文捕获）**：在端点或采集点把经过的报文逐个记录下来，
  通常保存为抓包文件。优点是细节最全，可以逐报文复核；缺点是
  体量大、保留期短，长期全量抓包在多数网络里都不现实。
- **流记录（flow record）**：只记录会话的元数据——起止时间、
  双方端点、端口、协议、字节数等，不记录报文内容。优点是体量小、
  可长期保留、适合先定位“哪段时间、哪些端点值得深挖”；缺点是
  没有报文内容，无法回答“这次会话里传了什么”。

一条实用的采集顺序是：先用流记录与设备日志定位时间窗口与可疑端点，
再针对该窗口做定向抓包或调取已有的抓包文件；反过来，先无差别全量
抓包再慢慢翻，既存不下，也容易在无关内容里浪费时间。采集时还要
记录采集点位置、采集起止时间、采集工具与版本、是否出现丢包或
中断——这些记录本身就是证据链的一部分，见
[取证基础与证据链](01-forensics-basics-evidence-chain.md)第 3.6 节。

### 3.3 协议分析思路：从会话到报文，分层收敛

分析流量时按“由粗到细”收敛，不要一上来就逐报文翻：

1. **会话层先看全貌**：按时间、端点、端口、协议汇总会话，找出
   与调查问题相关的时间窗口与端点对。自造测试示例：某测试主机
   在自造时间窗口内与三台自造测试端点建立了会话，其中只有一台
   的会话出现在事件窗口内——分析先锁定这一台，再往下钻。
2. **协议层再看行为**：按协议分层理解会话在做什么——是域名解析、
   是建连握手、是文件传输，还是某个应用协议的交互。只看端口号
   猜协议是常见错误：端口可以被改，协议特征要以报文内容与
   交互模式为准。
3. **报文层最后核对细节**：对关键会话逐报文核对顺序、重传、
   异常字段与时间戳，确认结论不是由丢包、乱序或时钟偏差造成的
   假象。
4. **加密流量的边界**：加密会话的报文内容通常无法直接读取，分析
   只能做到元数据层面——起止时间、端点、端口、字节量、会话时长。
   不要把“加密流量的元数据模式”写成“内容结论”，两者之间要留
   一道明确的界线；解密他人加密通信不在本文讨论内。

工具类别上，报文分析类工具与流记录分析类工具各司其职：前者用于
逐报文复核，后者用于大时间跨度的会话定位。具体工具的当前版本号
以官方发布为准（待核实），见文末未完成项；本篇不写未实测的
抓包命令。

### 3.4 时间线重建：把多源记录对到同一根时间轴上

网络证据很少单独成立：一次会话要与端点日志、系统日志、磁盘时间线
对上，才能变成事实。重建时间线的关键做法是：

- **先对齐时钟**：不同设备的时钟可能有偏差。先确认各数据源的
  时区与时钟来源，必要时用同一参考事件（如一台设备的已知操作
  时间）校准偏差，再把记录排进同一时间轴；不校准就直接拼，
  顺序可能是错的。
- **以事件为单位合并**：把“某端点在某时刻发起连接”“某服务在
  某时刻记录一次登录”“某文件在某时刻被修改”按时间排成一条线，
  再看哪些事件在时间上相邻、在逻辑上相关。
- **区分事实与推断**：时间线上每一条都应标清来源（哪份抓包文件、
  哪条流记录、哪条日志）；由多条事实推出的判断要单独标为推断，
  并写清推断依据。磁盘与日志侧的时间线做法见
  [磁盘与文件系统取证入门](02-disk-filesystem-forensics.md)与
  [内存取证与日志分析入门](03-memory-log-forensics.md)。
- **留出缺口说明**：丢包、日志滚动、采集中断造成的缺口要如实写
  出来——“某时间段无记录”本身就是一条信息，假装时间线完整
  比承认缺口更有害。

### 3.5 证据保全与哈希留存

网络证据的保全与磁盘证据遵循同一套要求：原始文件只读存放，
分析用副本，哈希值作封条，移交有记录。采集完成后立即对抓包文件
与流记录导出文件计算哈希并记录；此后每次复制、每次移交、每次
分析前再算一次，哈希不变才说明文件在此期间没有被改动。

下面是本机实测的最小演示：验证“复制 + 哈希比对”机制本身。
环境为代理 VM，数据为自造文本（不是真实抓包文件——本 VM 未安装
抓包工具，故不写抓包命令、不声称实测过抓包）：

```bash
printf 'TEST-CAPTURE-LINE-01\nTEST-CAPTURE-LINE-02\n' > capture-test.txt
sha256sum capture-test.txt
cp capture-test.txt capture-copy.pcap.txt
sha256sum capture-copy.pcap.txt
cmp capture-test.txt capture-copy.pcap.txt && echo COPY-IDENTICAL
```

实测输出（2026-11-04，VM 上实际跑通）：

```text
725a7840bd6e25800b5b3aedd5992d1e61adb0df9e269f3695592c38cfd521d5  capture-test.txt
725a7840bd6e25800b5b3aedd5992d1e61adb0df9e269f3695592c38cfd521d5  capture-copy.pcap.txt
COPY-IDENTICAL
```

这个演示的边界与 01 篇相同：它验证的是复制与哈希机制，不是真实
网络取证。真实抓包文件的保全还要多做两件事——记录采集点与起止
时间、记录是否丢包；哈希能证明“文件没变”，不能证明“采全了”。

## 4. 分类

按证据形态，网络取证常分为以下几类：

- **报文捕获分析**：对抓包文件做逐报文检查，适合关键会话的细节
  复核，代价是体量大、保留期短。
- **流记录分析**：对会话元数据做汇总与定位，适合大时间跨度的
  异常发现与范围界定，代价是无报文内容。
- **日志关联分析**：把网络设备日志、系统日志、应用日志与流量记录
  对齐到同一时间轴，适合拼出跨设备的完整事件链，见
  [内存取证与日志分析入门](03-memory-log-forensics.md)后半部分。
- **实时采集与事后调取**：事件进行中布点采集，与事件发生后调取
  已有记录，是两种不同的采集姿态；事后调取受限于记录的保留期，
  保留期过了就取不到，这是网络取证最常见的不可逆损失。

## 5. 典型应用

以下场景均限定在**自有网络、自有系统或明确授权的范围**内：

- **内部事件范围界定**：自有网络出现异常后，用流记录定位受影响
  的端点与时间窗口，再定向分析关键会话。
- **演练与教学**：在隔离靶场里用自造流量走完整流程，验证采集点、
  保留策略与时间线方法是否真的可用。
- **合规留存**：按组织制度对关键网络事件的抓包文件与流记录做
  归档，使事后审计有据可查。
- **处置配合**：为应急响应提供“哪些端点在事件窗口内对外建连”
  的事实基础，处置动作本身见
  [检测与应急响应](../10-security/03-detection-incident-response.md)。

## 6. 限制与常见误解

- **抓包不等于“看到一切”**：镜像口丢包、加密内容、采集点之外的
  路径，都会让抓包文件不完整。结论要写清采集覆盖范围与已知缺口。
- **流记录不等于“内容证据”**：流记录只能证明“某时某端点之间有
  过会话”，不能证明会话里传了什么。把流记录写成内容结论是越界。
- **端口号不等于协议**：端口可以被改，协议判定要以报文交互为准。
- **时钟不对，时间线全错**：多源拼时间线之前必须先对齐时钟与时区。
- **哈希一致不等于采全**：哈希只证明已采文件没变，不证明没有漏采
  的采集点或时间段。
- **本篇不是法律意见**：流量拦截的合法性、留存期限、跨境数据的
  处理，各司法辖区规定不同，具体案件以当地法律与专业法律意见为准。

## 7. 小结

网络取证是让网络侧事实站得住的方法：先定授权与范围，再选采集
方式，用流记录定位、用报文复核细节，把多源记录对齐到同一时间轴，
最后用哈希与证据链把文件固定下来。采全、采准、不干扰，三者缺一
不可。
