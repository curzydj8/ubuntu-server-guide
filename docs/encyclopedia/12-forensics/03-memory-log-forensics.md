# 内存取证与日志分析入门

> 本篇只讲内存取证与日志关联分析的流程与原理。分析对象永远是镜像或副本，
> 不是正在运行的生产系统；示例一律用自造的测试数据，不含真实案件数据、
> 真实个人信息或真实案件细节。磁盘侧的流程见
> [磁盘与文件系统取证入门](02-disk-filesystem-forensics.md)，应急处置的配合
> 关系见[取证基础与证据链](01-forensics-basics-evidence-chain.md)，本篇不复制。

## 1. 本章目标

读完本篇能理解：为什么有些证据只在内存里、内存镜像怎么采、内存里能读出
哪些痕迹（进程、网络、注入痕迹）、日志怎么与内存和磁盘证据拼成一条线，
以及内存证据为什么“过期不候”。

## 2. 背景与问题

磁盘取证回答“过去发生了什么”，内存取证回答“采集那一刻系统正在做什么”。
两者互补，缺一不可：只在磁盘上找，会漏掉从未落盘的东西——正在运行的
进程、已建立的网络连接、解密后存在内存里的密钥、只在内存里展开的代码；
只看内存，会漏掉历史——内存只反映采集瞬间，关机就消失，之前发生过、
现在已退出的进程在内存里可能只剩残片。

内存取证的根本困难是“观察即改变”：在运行中的系统上执行任何采集命令，
都会占用内存、创建进程、改写一部分内存内容。完全不扰动的内存采集不存在，
目标是把扰动降到最小、把扰动记录下来：先采集、后分析，采集工具越小、
依赖越少越好，采集产物立即哈希并写到外部证据存储，不要写回被采主机的
系统盘（写回系统盘还可能覆盖磁盘上未分配空间里的证据）。

## 3. 总体架构

内存与日志证据的分析链路是：

```text
运行中的系统（采集瞬间）
  ├─ 内存镜像（RAM 全量快照：进程、模块、网络、句柄）
  │    └─ Volatility 解析 → 进程树、隐藏进程、网络连接、注入痕迹
  ├─ 系统日志（journald / syslog：服务、认证、内核事件）
  ├─ 应用与安全日志（Web、数据库、认证服务）
  └─ 磁盘时间线（文件 MACB、变更日志）
        └─ 关联分析：同一时间窗口内多源事件互相印证 → 结论
```

内存镜像是“快照”，日志是“流水账”，磁盘时间线是“档案”：快照定格一刻，
流水账讲清前后，档案补齐历史。三者时间必须对齐（NTP 同步是前提，见
[检测与应急响应](../10-security/03-detection-incident-response.md)第 1.4 节，
本篇不复制），否则拼出来的顺序就是错的。

## 4. 工作机制

### 4.1 内存镜像：先采、快采、写到外部

内存采集的顺序铁律是“内存第一”：按易失性顺序，内存证据在磁盘证据之前。
关机、重启、休眠都会让内存证据消失或大变样，因此“先重启再取证”在
内存取证里等于主动销毁证据。

Linux 内存采集的常用工具（工具名与定位经联网核查，命令形式来自公开文档，
示例未实测：本 VM 未安装这些工具，见文末未完成项）：

- **AVML**：微软出品的 Linux 用户态内存采集工具，静态单文件，无需事先
  了解目标发行版与内核、无需现场编译；输出 LiME 格式（压缩时除外），
  支持把镜像写到外部位置。内核 lockdown 功能启用时 AVML 可能无法采集，
  这是已知的硬限制。
- **LiME**：经典的内核模块式采集工具，需加载与运行内核匹配的模块，可把
  内存转储到本地文件或经网络发送；模块与内核不匹配就无法加载，因此采集
  前要记录准确的内核版本（`uname -r` 的输出要随证据一起保存）。
- **兜底路径**：现代内核对 /dev/mem 与 /dev/kmem 的完整访问有限制，
  /proc/kcore 可作为无模块时的备选，但体积大、可能不完整，属于“有总比
  没有好”的降级方案，不应作为首选。

采集时要同步记录的元数据：采集时间（UTC）、主机标识、内核版本、采集工具
与版本、输出路径、镜像哈希。镜像一落地立即算哈希并分开存放——内存镜像
体积大，截断或损坏的镜像比没有镜像更误导人，因为它看起来像一份完整证据。

### 4.2 内存解析：从一堆字节到进程与网络

内存镜像本身只是一段连续的字节，分析靠解析工具按操作系统内核结构把它
翻译回“进程、模块、连接”。开源事实标准是 Volatility 框架：Volatility 2
用“配置文件（profile）”描述目标系统，Volatility 3 改用符号表
（ISF，Intermediate Symbol Format），且 Linux 分析要求符号表与采集时的
运行内核精确匹配——内核版本记错，解析就可能全盘错位。这就是 4.1 节要求
记录 `uname -r` 的原因。

Volatility 3 的常用分析方向（Windows 插件名为例，Linux 有对应的
linux.* 插件；命令形式来自公开文档，示例未实测）：

```bash
# 示例未实测：列出可见进程（沿内核进程链表 walk）
vol -f memory.lime windows.pslist
# 示例未实测：扫描内存中的进程对象，可发现被摘链隐藏的进程
vol -f memory.lime windows.psscan
# 示例未实测：列出网络连接与监听端口
vol -f memory.lime windows.netscan
# 示例未实测：检测可疑内存区域（如注入痕迹的线索之一）
vol -f memory.lime windows.malfind
```

四个方向的研判逻辑：

- **进程树**：`pslist` 给出“系统自己承认在运行”的进程与父子关系。
  父子关系异常（例如一个本应由服务管理器拉起的进程，父进程却是一个
  普通应用）是值得深挖的线索，但不是定论——正常系统里也有例外。
- **隐藏进程**：`psscan` 不依赖进程链表，而是直接扫描内存找进程对象；
  把两者结果一 diff，只在扫描结果里出现、不在链表里的进程，就是“被
  摘链隐藏”的候选。单凭 diff 不能定性，还要结合命令行参数、加载模块、
  网络行为一起看。
- **网络痕迹**：`netscan` 给出采集瞬间的连接表（本地 / 远端地址与端口、
  状态、属主进程）。内存里的连接表能补上磁盘日志没有的东西：短暂存在
  又已关闭的连接、从未写日志的连接。判断时要结合业务解释——备份、更新、
  监控都会外联，见[检测与应急响应](../10-security/03-detection-incident-response.md)
  第 5 节，本篇不复制。
- **注入痕迹**：`malfind` 找的是“可疑的内存区域特征”（如可执行且无对应
  磁盘文件 backing 的私有内存），它是线索生成器，不是判决器；任何一项
  命中都要人工复核其所在进程、内存权限与内容特征。

一条贯穿始终的纪律：**绝不在分析环境里执行从镜像中提取出的代码或样本**。
内存分析是只读解析，提取物只用于静态查看与哈希比对；执行它等于在自己的
分析机上重演事件。

### 4.3 日志关联分析：把“流水账”拼成“事件链”

日志关联分析的目标，是把多个来源里指向同一件事的条目连起来。单个来源的
单条记录通常只是线索：一次登录失败可能是误输口令；但“同一账号短时间
大量失败 + 随后一次成功 + 成功后紧接着批量读取敏感目录 + 外联记录”
连起来，就是一条需要研判的事件链。

关联分析的四个实操要点：

1. **时间对齐**：所有来源统一到 UTC 再比较；先核对各主机的 NTP 状态，
   时区没统一的时间线不能直接拼。日志时间戳精度不一（秒级与毫秒级混排）
   时，要在报告中写明精度差异。
2. **标识对齐**：用“账号 + 来源地址 + 进程 / 会话标识”把条目串起来，
   而不是只凭时间相近就拼。时间相近的无关事件在繁忙系统上比比皆是。
3. **先过滤、后精读**：日志量极大时，先按时间窗口、账号、主机、事件级别
   过滤出候选集，再逐条精读；反向操作（先精读再过滤）会淹没在噪声里。
4. **留白即信息**：日志出现断档、某类事件突然消失、审计日志被清空的记录
   本身，就是一条值得记录的异常——但要先排除“日志轮转、采集中断”等
   正常原因，再下结论。

下面是本机实测的最小演示：用自造的两行日志验证“按时间排序”这一机制
本身。数据为自造文本，主机名与账号均为测试值：

```bash
printf '2026-11-04T10:00:00Z testvm sshd: Accepted publickey for testuser\n2026-11-04T09:58:00Z testvm sshd: Failed password for testuser\n' > test.log
sort test.log
```

实测输出（2026-11-04，VM 上实际跑通）：

```text
2026-11-04T09:58:00Z testvm sshd: Failed password for testuser
2026-11-04T10:00:00Z testvm sshd: Accepted publickey for testuser
```

读法：排序后才能看出“先失败、后成功”的顺序；原始日志若本身已按时间
顺序写入，排序只是验证手段。真实关联分析不是 `sort` 一条命令，而是
多源、多字段的过滤与对照（见 4.4 节），这里演示的只是“时间顺序是分析
的前提”这一个点。

另一个本机实测的辅助手段，是用 `strings` 从自造的二进制测试文件中
找回已知标记字符串——它演示的是“在无结构字节里按已知特征搜索”这一
内存与磁盘分析共用的基本操作：

```bash
printf 'MEMORY-MARKER-TEST-2026\n' > mem-test.bin
strings mem-test.bin | grep -F 'MEMORY-MARKER-TEST-2026'
```

实测输出（2026-11-04，VM 上实际跑通）：`MEMORY-MARKER-TEST-2026`。
边界同样要讲清：真实内存镜像里字符串搜索只能找到以明文形式残留的内容，
加密、编码或已覆盖的内容搜不到；搜到一个字符串也不等于证明了某行为，
它只是把分析引向对应的进程与内存区域。

### 4.4 超级时间线：内存、日志、磁盘的三源合一

磁盘篇介绍的 Plaso 超级时间线同样适用于内存与日志证据的合流：文件系统
MACB、系统日志、应用日志、浏览器与注册表类记录被归一化到同一条时间轴
上，再按时间窗口过滤。内存证据的特殊性在于它只有一个时间点（采集瞬间），
在超级时间线里它表现为“某时刻的系统状态快照”而不是一段连续事件——
分析时要把快照时刻前后一段时间的日志事件单独拉出来对照：快照里看到的
进程与连接，在快照前后有没有对应的启动记录、登录记录、文件创建记录？
有，说明它有来处；没有，说明它可能来自内存加载、或日志缺失，两者都要
在报告里写清，不能默认其中一种。

## 5. 关键设计取舍

- **采集扰动换取证据存在**：任何 live 采集都会扰动内存；不用“零扰动”
  的神话自我安慰，改用“最小工具、外部存储、完整记录扰动”来换取证据
  依然可辩护。
- **快照换取历史**：内存快照只定格一刻，换来的是磁盘上没有的当下状态；
  代价是快照之外的历史必须靠日志与磁盘补，单看快照下结论必然片面。
- **自动化解析换取人工复核成本**：Volatility、Plaso 这类工具把海量字节
  翻译成结构化条目，代价是工具可能误解析（符号表不匹配、内核结构变化）；
  关键结论必须抽查原始结构或换工具交叉验证。
- **集中日志换取单点依赖**：日志集中存放利于关联，但集中点本身成为
  关键资产——它的完整性、访问控制与留存期要单独保障（见
  [检测与应急响应](../10-security/03-detection-incident-response.md)第 1.4 节）。

## 6. 分类与变体

- **按采集时系统状态**：live 采集（系统运行中，含内存与网络状态）、
  dead 采集（关机后磁盘镜像，无内存内容）。两者不是二选一：条件允许时
  先 live 采内存与网络状态，再 dead 采磁盘。
- **按内存来源**：物理内存镜像（AVML / LiME 产物）、虚拟机快照与挂起文件
  （自带内存内容，需按虚拟化平台格式处理，以官方发布为准，见未完成项）、
  崩溃转储（crash dump，内核态为主，用户态信息有限）。
- **按日志来源**：系统日志（journald / syslog）、认证日志、应用日志、
  网络设备与云审计日志。不同来源的字段与精度不同，关联前先做字段对照，
  不要假设字段名一致。

## 7. 应用与限制

适用场景（均限定在自有设备或明确授权范围）：内部事件调查中“正在运行
什么、连着哪里”的快照分析、内存型痕迹的线索发现、日志关联复盘、
靶场教学。限制包括：

- **易失**：关机、重启后内存证据基本消失；采集不及时等于没有。
- **符号依赖**：Volatility 3 的 Linux 解析依赖与运行内核精确匹配的符号表，
  符号缺失时解析能力大幅下降，事前记录内核版本是硬性要求。
- **加密与混淆**：内存中的加密内容、编码数据无法直接靠字符串搜索还原；
  密钥类材料即使出现在内存里，也只能在授权范围内按最小必要处理，不得
  扩散（见[秘密信息管理](../../02-security/09-secrets-management.md)）。
- **反取证**：时间戳篡改、日志清空、内存痕迹擦除都会削弱结论；遇到
  “证据缺口”时，缺口本身要写入报告，而不是用推测填补。
- **隐私**：内存与日志可能含大量无关个人数据，按最小必要查看，查看范围
  记入调查记录。

## 8. 常见误解

- **“内存里什么都有”**：错。内存只有采集瞬间的内容，已退出的进程、
  已关闭的连接大多只剩残片或全无。
- **“工具列出的进程就是全部进程”**：错。`pslist` 只列链表上的进程，
  隐藏进程要靠 `psscan` 对照才能发现；两者 diff 才是完整图景的起点。
- **“日志没记就是没发生”**：错。日志可能缺失、可能被清空、可能根本
  没采集该来源；“无记录”与“无事件”是两回事，报告里要区分。
- **“时间对上就是因果”**：错。时间相近只是关联的必要条件，不是充分
  条件；因果需要账号、进程、会话等标识链佐证。
