# 磁盘与文件系统取证入门

> 本篇只讲磁盘取证的流程与原理。分析对象永远是镜像或副本，不是原始介质；
> 示例一律用自造的测试数据与自有测试镜像，不含真实案件数据。应急处置的
> 配合关系见[取证基础与证据链](01-forensics-basics-evidence-chain.md)，本篇不复制。

## 1. 本章目标

读完本篇能理解：磁盘证据是怎么从一块介质变成一份时间线与一组结论的——
镜像怎么采、文件系统怎么读、已删除文件为什么有时能找回来、时间线怎么拼，
以及每一步的边界在哪。

## 2. 背景与问题

磁盘是事件发生后最主要的持久证据来源：文件、配置、日志、缓存、浏览器记录、
删除残留，大多最终都落在磁盘上。但直接在原始磁盘上“打开看看”是最坏的
做法：挂载会改访问时间，系统启动会写日志，杀毒扫描会隔离文件，每一次
“看看”都在改写证据。磁盘取证要解决的核心矛盾是：**既要看清磁盘上的全部
内容，又不能改变磁盘上的一比特**。解法是分层隔离：先做一份逐位镜像并用
哈希封存，之后所有分析都在镜像或镜像的副本上做，原始介质封存不动。

另一个问题是“看不见的部分”：操作系统只显示当前文件系统认为存在的文件，
但磁盘上还有已删除文件的残留、未分配空间、松弛空间（slack space）里的旧
数据。这些部分不在目录里，却可能正是调查需要的部分。磁盘取证的很大一部分
工作，就是读操作系统不显示的那部分。

## 3. 总体架构

磁盘取证的分层结构自下而上是：

```text
物理介质（磁盘 / U 盘 / 镜像文件）
  └─ 分区表（GPT / MBR：盘上有几个分区、每个分区起止位置）
      └─ 文件系统（NTFS / FAT / exFAT / ext2/3/4 等：文件怎么组织）
          ├─ 元数据区（目录项、索引节点、主文件表：文件名、时间戳、数据位置）
          ├─ 数据区（文件内容按簇 / 块存放）
          └─ 未分配空间与松弛空间（已删除残留、旧数据碎片）
              └─ 时间线（把所有时间戳事件按时间排成一条线）
```

每一层只依赖下层提供的信息：不知道分区表，就找不到文件系统；不解析文件
系统，就只能对着原始字节猜；不理解元数据与数据区的分离，就解释不了
“文件删了为什么还能恢复”。工具（如 The Sleuth Kit）本质上就是把这几层
解析自动化的程序，分析者仍需理解每一层在做什么，才能判断工具输出可不可信。

## 4. 工作机制

### 4.1 镜像获取：逐位复制 + 写保护 + 哈希

镜像获取的目标是得到一份与原始介质逐位一致的副本。规范做法有三条：

1. **写保护**：通过硬件写保护器连接原始介质，或在只读方式下操作，防止
   采集过程本身写入原始介质。没有写保护的“直接读”，在严格意义上已经
   破坏了“原始不被改变”的要求。
2. **逐位复制**：复制整块介质的每一个扇区，包括未分配空间与松弛空间，
   而不是只复制“看得见的文件”。只拷文件等于主动丢弃删除残留，取证价值
   大打折扣。常见的镜像格式有原始（raw / dd）格式、Expert Witness（E01）
   格式与高级取证格式（AFF）；The Sleuth Kit 支持从 raw、Expert Witness
   与 AFF 格式的镜像中解析文件系统。
3. **立即哈希并分开存放**：镜像完成后立即计算哈希，哈希值与镜像分开存放、
   分开记录（见[取证基础与证据链](01-forensics-basics-evidence-chain.md)
   第 3.5 节）。分析前再算一次，哈希一致才开始分析。

下面这条命令**不是**设备取证命令，而是本机实测的“建一个测试文件系统
镜像并查看其基本参数”的演示，用自造的空镜像验证工具链本身可用。
真实设备取证务必经写保护器与取证工具操作，切勿把设备名套进 dd 之类的
命令里试错——源与目标写反会毁掉证据：

```bash
dd if=/dev/zero of=disk-test.img bs=1M count=16 status=none
mkfs.ext4 -q -F disk-test.img
dumpe2fs -h disk-test.img | grep -E 'Filesystem volume name|Block size|Inode size'
sha256sum disk-test.img
```

实测输出（2026-11-04，VM 上实际跑通，16 MB 自造空镜像）：

```text
Filesystem volume name:   <none>
Block size:               4096
Inode size:               256
487d1cdaa34aa9d90a9be4387465b69cf1da5245f32e38e2cc8335ce7cc38e31  disk-test.img
```

读法：这是一个块大小 4096 字节、索引节点大小 256 字节的 ext4 测试镜像；
哈希值是这份空镜像当时的封存值，镜像内容一变哈希就变。真实取证镜像的
哈希要在采集现场立即记录，而不是事后补算。

### 4.2 分区识别：先找分区，再谈文件

拿到镜像先看分区布局，再对每个分区做文件系统分析。The Sleuth Kit 的
`mmls` 命令用于列出镜像的分区布局（示例未实测：本 VM 未安装该工具，
命令形式来自工具公开文档，见文末未完成项）：

```bash
# 示例未实测：列出镜像的分区布局，只读操作，不改写镜像
mmls disk-test.img
```

分区表本身也可能被破坏或伪造：分区表说“这里没有分区”，不等于这里没有
数据——文件系统特征扫描（按文件系统签名在全盘搜索）是分区表失效时的
补救手段，但结果需要人工复核，不能直接当结论。

### 4.3 文件系统结构：元数据与数据是分开的

理解删除恢复，先要理解文件系统把“文件”拆成的两部分：

- **元数据**：文件名、大小、时间戳、权限、数据存放在哪些簇/块。NTFS 把
  这些放在主文件表（MFT）里，每个文件至少对应一条 MFT 记录；ext 系列
  把这些放在索引节点（inode）里；FAT 系列放在目录项与文件分配表里。
- **数据区**：文件内容本身，按簇（NTFS / FAT）或块（ext）存放。文件系统
  用一张“哪些簇已分配”的位图（如 NTFS 的 $Bitmap）来管理空闲空间。

常见文件系统的取证关注点各有侧重：

- **NTFS**：MFT 记录、$Bitmap、$LogFile（事务日志）、$UsnJrnl（变更日志）、
  备用数据流（ADS）。MFT 里的时间戳与日志里的变更记录是时间线的重要来源。
- **FAT / exFAT**：目录项与分配表结构简单，删除后元数据残留较少，恢复
  更依赖文件雕刻（见 4.4 节）。
- **ext2 / ext3 / ext4**：inode、块位图与目录结构；ext3 / ext4 的日志
  （journal）记录了近期的元数据变更，可用于还原被改动或删除的元数据，
  但日志是循环覆盖的，能回溯的窗口有限。
- **其他**：The Sleuth Kit 公开支持的解析范围包括 NTFS、FAT、exFAT、
  UFS 1/2、ext2/3/4、HFS、ISO 9660、YAFFS2；超出该范围的文件系统需用
  其他工具或以官方发布为准（待核实）。

### 4.4 删除文件恢复原理：删掉的通常是指针，不是数据

在传统机械硬盘上，删除一个文件时操作系统通常只做两件事：把元数据标记为
“未使用”（如 NTFS 把 MFT 记录标记为空闲、清除 $Bitmap 中对应簇的占用
标记），而不立即擦除数据区的内容。于是恢复分两个层次：

1. **元数据恢复**：元数据还没被重用时，根据残留的 MFT 记录或 inode 找到
   原数据簇的位置，把内容读出来。这一层恢复通常能保留原文件名与时间戳，
   是最理想的情况。
2. **文件雕刻（file carving）**：元数据已被重用或损坏时，不依赖文件系统，
   直接扫描未分配空间，按已知文件格式的文件头、文件尾等特征把数据块拼
   回文件。雕刻能找回内容，但通常丢文件名、目录结构与时间戳；碎片化的
   文件（数据块不连续）雕刻难度大增，部分覆盖的文件只能部分恢复。

两个硬边界必须讲清：**覆盖即丢失**——数据簇被新数据重用后，旧内容就
不存在了，任何工具都变不出来；**固态盘的 TRIM / unmap**——操作系统通知
设备某块已不再需要后，设备可能在后台真正擦除这些块，使“删了还在”的
规则失效。因此“删除文件一定能恢复”是误解，正确说法是“删除后、覆盖前、
未 TRIM 的数据有恢复可能，且越早镜像希望越大”。

The Sleuth Kit 的 `fls` 命令用于列出镜像中文件系统的文件（包括已删除项，
示例未实测，原因同 4.2 节）：

```bash
# 示例未实测：-r 递归，-p 显示完整路径；只读分析镜像，不写原始介质
fls -r -p disk-test.img
```

### 4.5 时间线分析：把所有时间戳排成一条线

时间线分析是把来自不同来源的时间戳事件按时间排序，还原“先后发生了什么”。
文件系统提供的 MACB 时间戳是最基础的一层：

- **M（Modified）**：内容最后修改时间；
- **A（Accessed）**：最后访问时间（部分系统为性能考虑可能不实时更新，
  以官方发布为准，见未完成项）；
- **C（Changed）**：元数据最后变更时间（如权限、属主变更）；
- **B（Birth）**：文件创建时间（部分文件系统提供）。

单看 MACB 容易误判：复制文件会刷新某些时间戳，改系统时间会让整条时间线
错位，时间戳本身也可能被人为篡改（timestomping）。可靠的做法是多源对照：
把文件系统时间戳、日志条目、注册表或应用记录、$UsnJrnl / 日志文件里的
变更记录放在同一条时间线上互相印证——某个时间点上“文件被创建 + 日志里
有对应记录 + 变更日志里有对应条目”三者一致，结论才硬；只有一个来源的
孤证，只能算线索。

把多来源事件自动汇成“超级时间线”的工具是 Plaso（log2timeline），它解析
文件系统、事件日志、浏览器记录等多种来源并归一化输出，再用 psort 做
过滤与排序（命令形式来自公开文档，示例未实测，见未完成项）。超级时间线
动辄数百万条事件，分析时要先按时间窗口与关键词过滤，再精读——直接通读
全文既不现实也无必要。

## 5. 关键设计取舍

- **只读分析换取可信度**：所有分析都在镜像副本上做，代价是多占一份存储、
  多花一次复制时间；换来的是原始证据永远可复核。这是取证不可妥协的一点。
- **逻辑采集与物理采集的取舍**：逻辑采集（只拷看得见的文件）快、省空间，
  但丢删除残留；物理采集（逐位镜像）全、但慢且占空间。取证场景默认选
  物理采集，逻辑采集只在“只要当前文件、且已说明会丢残留”的前提下用。
- **雕刻的查全与查准取舍**：放宽特征匹配能找回更多碎片，但误报（把无关
  字节拼成“文件”）也多；收紧匹配则干净但漏得多。雕刻结果必须逐项人工
  验证，不能批量直接当证据。
- **时间线先广后精**：先汇全量事件再过滤，比一开始就只采“可疑时间段”
  更可靠——后者容易把前兆事件排除在视野之外。

## 6. 分类与变体

- **按镜像格式**：原始（raw）格式最通用，任何解析工具都能读；E01 / AFF
  等封装格式可带压缩、校验与元数据，适合归档与移交，但依赖工具支持。
- **按分析方式**：文件系统解析（有元数据，快、信息全）、文件雕刻
  （无元数据、慢、信息少）、日志与变更记录解析（补时间线与行为链）。
- **按介质类型**：机械硬盘（删除残留保留较久）、固态盘（TRIM 影响大）、
  U 盘与存储卡（多为 FAT / exFAT，元数据残留少）、虚拟机磁盘（快照本身
  就是一份时间证据，见未完成项）。

## 7. 应用与限制

适用场景（均限定在自有设备或明确授权范围）：内部事件调查中的磁盘证据
分析、误删数据的恢复前保全、靶场教学中的磁盘取证演练。限制包括：

- **加密**：全盘加密且密钥不可用时，镜像只是密文，内容分析无从谈起；
  密钥管理背景见[秘密信息管理](../../02-security/09-secrets-management.md)。
- **覆盖与 TRIM**：已被覆盖或已 TRIM 的数据无法恢复，见 4.4 节。
- **时间不可靠**：系统时间被改、时区未统一、时钟漂移都会污染时间线；
  分析前先确认各来源的时区与时钟基准，并在报告中写明。
- **大容量与碎片化**：大容量盘的全量雕刻与超级时间线生成耗时很长，
  要先做范围界定（时间窗口、文件类型、目录范围），再开全量任务。
- **本篇不覆盖**：移动设备取证、云端取证、固件与芯片级取证，以官方
  发布为准（待核实）。

## 8. 常见误解

- **“删除 = 消失”**：错。删除通常只改元数据标记，数据区内容在覆盖前
  仍在（固态盘 TRIM 除外）。
- **“恢复出来的文件就是原件”**：不一定。雕刻恢复的文件可能缺文件名、
  缺时间戳、甚至内容不完整，必须在报告里写清恢复方式与完整度。
- **“时间戳就是事实”**：不一定。时间戳可被系统行为改变，也可被人为
  篡改；时间线结论要多源印证。
- **“工具说有就是有”**：错。工具会把残留字节、旧版本文件、系统缓存都
  列出来，哪些与调查问题相关，需要人判断。
