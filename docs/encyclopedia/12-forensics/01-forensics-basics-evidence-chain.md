# 取证基础与证据链

> 本篇只讲流程、方法与证据链管理。示例一律用自造的测试数据，不含真实案件数据、
> 真实个人信息或真实案件细节。应急处置的动作顺序（发现、定级、隔离、根除、恢复、
> 复盘）见本站 10 域文章，本篇不复制，只做链接。

## 1. 一句话定义

数字取证是在授权范围内，用可复现的方法获取、保全、检查、分析数字证据并形成
报告的过程，其核心要求是：原始数据不被改变，每一步都可被第三方复核。

## 2. 为什么需要它

事件发生后，第一个问题往往不是“怎么修”，而是“到底发生了什么、影响面有多大、
结论凭什么成立”。没有取证，处置就只能凭印象：日志可能被覆盖，重启可能清掉
内存，匆忙重装可能毁掉唯一能说明问题的痕迹。取证的价值不在“工具多高级”，
而在“结论站得住”——同样的镜像、同样的步骤，另一个人能得出同样的结果；每一步
操作都有记录，能说清谁在何时对哪份证据做了什么。

取证与应急响应是配合关系，不是同一件事。应急响应负责止损与恢复（见
[检测与应急响应](../10-security/03-detection-incident-response.md)），取证负责
在止损之前和止损之中把证据留下来、把事实拼出来。顺序错了就会互相伤害：
先重装后取证，证据没了；只取证不隔离，损失可能扩大。两者要在同一个时间线里
协调：先保全易失证据，再隔离，再做深入分析。

## 3. 核心含义

### 3.1 四个阶段：采集、检查、分析、报告

美国国家标准与技术研究院（NIST）SP 800-86《将取证技术融入事件响应的指南》
把取证过程分为四个阶段：采集（collection）、检查（examination）、分析
（analysis）、报告（reporting）。理解这四个阶段的递进关系，比记住工具名
更重要：

1. **采集**：识别、标注、记录并获取可能相关的所有数据源，同时保全其完整性。
   这一阶段的产出是“证据材料”，不是结论。
2. **检查**：用取证工具对采集到的数据做处理，提取出与调查问题相关的内容。
   这一阶段的产出是“信息”，例如某文件的元数据、某段时间内的日志条目。
3. **分析**：对信息做研判，回答最初提出的问题——发生了什么、按什么顺序、
   影响了哪些资产、根因是什么。这一阶段的产出是“结论”，结论必须能追溯到
   具体的信息条目，不能凭感觉。
4. **报告**：写清做了什么、用了什么方法与工具、发现了什么、还有什么没做、
   建议下一步做什么。报告是取证工作的最终产品，写不清楚的取证等于没做。

四个阶段不是严格的单向流水：分析中发现缺证据，要回到采集补采；报告中发现
某一步说不清，要回到记录里补齐。但“采集在先、结论在后”的方向不能反过来：
先有结论再找证据支撑，是调查的大忌。

### 3.2 另一套划分：识别、采集、获取、保全

ISO/IEC 27037《数字证据的识别、采集、获取与保全指南》（2012 年发布）覆盖
的是取证生命周期的前半段，即证据刚被发现到被妥善保存为止：

- **识别**：哪些设备、哪些数据源可能含有证据；
- **采集**：把设备或数据控制起来，防止在获取之前被改动或丢失；
- **获取**：用取证方法复制数据，得到可供分析的副本；
- **保全**：用证据链与受控存储维持副本的完整性与真实性。

这套划分与 NIST 的四个阶段不冲突，只是切分点不同：ISO/IEC 27037 讲的是
“证据怎么安全地拿到手”，NIST SP 800-86 讲的是“拿到手之后怎么变成结论”。
分析与解读本身属于 ISO/IEC 27042 的范围，不在 27037 之内。初学者不必纠结
用哪套名词，关键是同一件事不要漏环节：识别不全会漏证据，保全不严会让
已采的证据失去价值。

### 3.3 四条取证原则（ACPO）

英国警方首长协会（ACPO）《数字证据良好实践指南》提出的四条原则，至今仍被
广泛引用为数字证据处理的基本准则：

1. **不改变原始数据**：任何可能被法庭采信的数据，都不应当因取证操作而改变。
   实际做法是：分析用的永远是镜像或副本，不是原始介质。
2. **只有胜任者才能接触原始数据**：在确需接触原始数据的情况下，操作者必须
   具备相应能力，并能说明自己每个动作的意义与影响。
3. **留出可复现的审计轨迹**：所有施加于证据的处理过程都要记录下来，使独立
   第三方能够检查这些过程并得到相同结果。
4. **负责人负总责**：调查负责人对上述原则的遵守负总体责任。

这四条原则的共同指向是“可辩护性”：当有人质疑“这份证据有没有被动过手脚”
时，回答不是“我保证没有”，而是哈希值、操作记录、证据链记录这些可验证的
东西。ACPO 指南的版本年份在不同二手来源中有 2011 年与 2012 年两种说法，
本文不做定论，见文末未完成项。

### 3.4 易失性顺序：先取最容易消失的

RFC 3227《证据采集与归档指南》（2002 年 2 月，BCP 55）提出的核心规则是：
**从易失到不易失**。一个典型系统的易失性顺序大致是：

寄存器与缓存 → 内存 → 网络状态（连接、路由）→ 运行中的进程 →
已挂载的磁盘内容 → 磁盘上的持久数据 → 归档与备份介质。

这条规则决定采集顺序：关机前先取内存与网络状态，因为断电就没了；磁盘镜像
可以晚一步，因为关机后磁盘内容基本还在（但要注意加密盘断电后可能无法再
解密，以及固态盘的回收机制）。反过来做——先慢慢做磁盘镜像，内存证据早已
随一次重启消失——是新手最常见的损失。易失性顺序不是教条：具体顺序要结合
现场情况（是否加密、是否还在运行、是否联网）判断，但“易失者先行”的方向
不变。

### 3.5 完整性：哈希是证据的“封条”

哈希值是证明“副本与原始一致”的技术手段。采集完成后立即对原始与副本分别
计算哈希（常用 SHA-256），两者一致，说明复制过程没有引入改变；此后每次
移交、每次分析前再算一次，哈希不变，说明证据在此期间没有被改动。

下面是本机实测的最小演示：用自造的测试文件验证“复制前后哈希一致”这一
机制本身。环境为代理 VM，数据为自造文本，不含任何真实证据：

```bash
printf 'TEST-EVIDENCE-LINE-01\nTEST-EVIDENCE-LINE-02\n' > evidence-test.txt
sha256sum evidence-test.txt
dd if=evidence-test.txt of=evidence-copy.img bs=512 status=none
sha256sum evidence-copy.img
cmp evidence-test.txt evidence-copy.img && echo COPY-IDENTICAL
```

实测输出（2026-11-04，VM 上实际跑通）：

```text
95a55570a03789949cabed23865da81c9bda36b3a18cbbeffa50d8f9808359e2  evidence-test.txt
95a55570a03789949cabed23865da81c9bda36b3a18cbbeffa50d8f9808359e2  evidence-copy.img
COPY-IDENTICAL
```

注意这个演示的边界：它验证的是“复制 + 哈希比对”机制，不是真实设备取证。
真实设备取证要经过写保护器、用取证工具做逐位镜像，命令与流程见
[磁盘与文件系统取证入门](02-disk-filesystem-forensics.md)。哈希能证明“没变”，
但不能证明“采全了”——漏采的数据源不会出现在哈希里，采全要靠识别阶段的
清单，而不是哈希。

### 3.6 证据链：一份“证据的旅行记录”

证据链（chain of custody）记录证据从被发现到最终处置的全部流转。RFC 3227
要求能够清楚描述证据如何被发现、如何被处理、期间发生过什么。一份可用的
证据链记录至少包括：

- **证据标识**：唯一编号、证据类型（磁盘镜像、内存镜像、日志导出等）；
- **来源**：来自哪台设备、哪个系统、哪个数据源，由谁、在何时、何地发现；
- **采集方法与工具**：用的什么工具、什么版本、什么参数，是否经过写保护；
- **完整性值**：采集时与每次移交时的哈希值；
- **保管与移交**：谁保管、在哪保管、每次移交的交接双方与时间；
- **访问记录**：谁在何时出于什么目的访问过证据、做了什么操作；
- **处置**：证据最终是归档、返还还是按规定销毁。

证据链断了，证据的价值就打折：无法说明“这份镜像确实来自那台设备、中间
没人动过”，结论就站不住。实践中一个简单的原则是：**每次证据换手、换盘、
换分析环境，都先记一笔再动手**。记录可以简单，但不能事后补——事后补的
记录本身就不可信。

### 3.7 最小必要与隐私边界

取证经常不可避免地接触到与调查无关的个人数据。处理原则是最小必要：只采集
调查问题需要的数据源，只查看与问题相关的范围，超出需要的数据不查看、
不留存、不扩散。日志集中存放与访问控制的做法见
[检测与应急响应](../10-security/03-detection-incident-response.md)第 1.4 节，
本篇不复制。

## 4. 分类

按证据来源，数字取证常分为以下几类；本批文章覆盖前三类，移动设备与云端
取证不在本批范围：

- **磁盘取证**：对磁盘镜像做文件系统解析、删除恢复与时间线分析，见
  [磁盘与文件系统取证入门](02-disk-filesystem-forensics.md)。
- **内存取证**：对内存镜像做进程、网络与注入痕迹分析，见
  [内存取证与日志分析入门](03-memory-log-forensics.md)。
- **日志与网络取证**：对系统日志、应用日志、网络流量记录做关联分析，见
  [内存取证与日志分析入门](03-memory-log-forensics.md)后半部分。
- **移动设备取证**：手机、平板等设备的取证，涉及专用接口与加密机制，
  本批不展开，以官方发布为准（待核实）。
- **云端取证**：云服务商侧的日志与快照获取，涉及服务商配合与管辖权问题，
  本批不展开，以官方发布为准（待核实）。

## 5. 典型应用

以下场景均限定在**自有设备、自有系统或明确授权的范围**内：

- **内部事件调查**：自有服务器出现异常后，用取证流程确认影响面与根因，
  为修复与复盘提供可验证的事实基础。
- **数据恢复前的保全**：误删或故障导致数据丢失时，先做镜像再恢复，避免
  恢复操作本身覆盖掉还能找回的数据。
- **演练与教学**：在隔离靶场里用自造数据走完整流程，验证团队的采集清单、
  工具与证据链记录是否真的可用。
- **合规留存**：按组织制度对关键事件的证据做归档，使事后审计有据可查。

## 6. 限制与常见误解

- **取证不等于“恢复一切”**：被覆盖的数据、已 TRIM 的固态盘区块、加密后
  丢失密钥的数据，取证也找不回来。取证能做的是“把还存在的讲清楚”，不是
  “把不存在的变出来”。
- **工具输出不等于结论**：工具会列出成千上万条记录，哪些与调查问题相关、
  哪些是正常系统行为，需要人研判。把工具报告直接当结论，是最常见的错误。
- **哈希一致不等于证据完整**：哈希只证明副本与原始一致，不证明识别阶段
  没有漏掉数据源。
- **“先修好再说”是最贵的顺序**：重启、重装、清日志这些处置动作本身会
  改变甚至消灭证据。处置前至少先保全易失证据与关键日志（按组织流程）。
- **本篇不是法律意见**：证据的可采性、扣押与移交程序、跨境数据的处理，
  各司法辖区规定不同，具体案件以当地法律与专业法律意见为准。

## 7. 小结

取证是一套让结论站得住的方法：按易失性顺序采集，对副本而非原始做分析，
用哈希封存完整性，用证据链记录每一次流转，最后写出第三方可复核的报告。
工具会换代，这四条要求不会变。
