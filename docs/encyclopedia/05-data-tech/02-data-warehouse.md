# 数据仓库基础

## 1. 一句话定义

数据仓库是把多个业务系统的数据抽取、清洗、整合后，按分析友好的方式组织起来的历史数据集合，服务于报表、分析与决策，而不是直接支撑日常业务操作。

## 2. 为什么需要它

业务数据库是为“把一件事做对”设计的：下一单、改一个地址、扣一笔款，每次操作只动少量数据，但要求快、并发高、绝不能错。分析问题却是反过来的：“过去一年每个品类每月卖了多少？哪个渠道的复购最高？销售额下滑是从哪个地区开始的？”这类问题要扫大量历史数据、做聚合与对比，还要把订单系统、门店系统、客服系统的数据拼到一起回答。

直接在业务库上跑分析，会同时踩三个坑：第一，重查询拖慢业务操作，报表一跑、下单就卡；第二，各系统对同一概念的口径不一致——订单系统的“销售额”含不含退款、门店系统的“销售额”按不按开票口径，数字对不上，会议先吵口径再谈业务；第三，业务库通常只关心当前状态，昨天的价格、去年的组织架构、已改名的商品，历史快照留不住，趋势无从谈起。数据仓库就是为这三个问题建的独立场所：数据从业务系统复制出来、按统一口径整理好、按时间保留历史，分析在这里跑，不干扰业务。

本篇只讲概念与建模方法。数仓产品的部署、调优与运维不在这里；业务侧数据库的安装与运维见本站 11 章，网站的数据库选型与表设计见网站建设指南数据库教程（链接见文末相关主题）。

## 3. 核心含义

### 3.1 Inmon 的四个特征

Bill Inmon 给出的经典定义是：数据仓库是面向主题的（subject-oriented）、集成的（integrated）、随时间变化的（time-variant）、非易失的（non-volatile）数据集合，用以支持管理决策。四个词各对应一个与业务库的区别：

- **面向主题**：按业务主题组织（销售、客户、商品、库存），而不是按某个应用的界面或功能模块组织。订单系统、门店系统、客服系统里的客户信息，在数仓里汇成同一个“客户”主题。
- **集成的**：来自不同系统的数据要先统一：同一客户在不同系统里的编码要映射到同一标识，货币、单位、状态码、命名要对齐。未经整合的数据只是堆在一起，不是仓库。
- **随时间变化的**：每条数据都带时间属性，仓库保留较长历史（例如数年），同一指标在不同时点的值都能查到，这是做趋势与对比的前提。
- **非易失的**：数据一旦进入仓库，一般只追加、不被业务操作随意改写。修正历史错误要走受控的修正流程并留痕，而不是像业务库那样直接 UPDATE 覆盖——否则上个月出的报表这个月就复现不出来了。

需要提醒一点：这四个特征是经典定义，不是不可违反的铁律。现代实践中，实时数仓、修正重跑、可变维度的处理都会在细节上松动“非易失”等表述，关键是理解每条特征要解决的问题，而不是背诵定义。

### 3.2 数仓与业务数据库的区别

| 维度 | 业务数据库（OLTP） | 数据仓库（OLAP） |
|---|---|---|
| 目的 | 跑业务：下单、支付、改状态 | 做分析：报表、趋势、对比、挖掘 |
| 查询形态 | 大量小事务：增删改查少量数据 | 少量大查询：扫描聚合大量历史数据 |
| 数据状态 | 当前值为主，历史快照有限 | 历史数据为主，按时间保留 |
| 模式取向 | 高度规范化，减少冗余，保证写入一致 | 维度建模，适度反规范化，换取查询效率 |
| 并发与延迟 | 高并发、低延迟、单次操作毫秒级 | 低并发、查询可达秒到分钟级 |
| 一致性要求 | 事务强一致，绝不能丢单、错账 | 口径一致、可复现，比单次毫秒延迟更重要 |

OLTP 是联机事务处理（Online Transaction Processing），OLAP 是联机分析处理（Online Analytical Processing）。两者不是谁替代谁：业务系统产生数据，数仓消费数据；没有业务系统，数仓无源之水；没有数仓，分析只能挤在业务库上互相伤害。

### 3.3 数仓、数据集市、数据湖：三个词不要混用

- **数据仓库**：企业级、面向多主题的分析数据集合，强调整合与统一口径。
- **数据集市**：面向某个部门或主题的子集（例如只做销售分析的集市）。它可以是从数仓派生出来的，也可以是先建集市再整合成数仓——这正是下一节 Inmon 与 Kimball 的路线之争。
- **数据湖**：以原始形态保存各类数据的存储层，结构化、半结构化、非结构化数据都可以先落湖，不必事先建模。湖的优势是“先存下来，以后再定怎么用”，代价是如果没有目录、质量与治理，湖很容易退化成“数据沼泽”：数据都在，但没人知道每份数据是什么意思、能不能信。

三者经常共存：原始数据落湖，清洗整合后进仓，面向部门的视图形成集市。近年来厂商提出的“湖仓一体”（lakehouse）试图把湖的低成本原始存储与仓的结构化管理结合起来，但各厂商对这个词的口径并不统一，选型时应看具体产品在事务、模式管理、查询性能上的实际能力，而不是看它自称什么，以官方发布为准（待核实）。

## 4. 两条建模路线：Inmon 与 Kimball

数据仓库领域最经典的一组分歧，来自 Bill Inmon 与 Ralph Kimball：

- **Inmon 路线（自上而下）**：先建企业级、规范化的中心仓库（通常接近第三范式），保存最细粒度数据，再从中派生各部门的数据集市。优点是全局一致性强、口径统一；代价是前期投入大、见效慢，对建模与治理能力要求高。
- **Kimball 路线（自下而上）**：先按业务过程建维度数据集市（星型模型，见第 5 节），再用“一致性维度”（例如所有集市共用同一套客户、商品、日期维度）把集市整合成企业视图。优点是见效快、贴近业务；代价是如果没有人维护一致性维度，各集市的口径会逐渐漂移，最后拼不起来。

实践中多数团队走的是混合路线：中心层保证整合与口径，展示层用 Kimball 的维度模型服务查询。选路线时真正要问的不是“信谁”，而是：团队有没有能力维护全局模型？业务等不等得起自上而下的长周期？如果答案是“没有、等不起”，从一两个核心业务过程的维度集市起步、同时立好一致性维度的规矩，是更现实的起点。

## 5. 分层建模：数据从原始到可用的几站

分层没有全球统一标准，不同团队的层数与命名各不相同。下面是常见的一种分层做法，层名仅作示例，关键是每一层解决什么问题：

```
业务系统
    │
    ▼
贴源层（ODS / Staging）：原样或近原样落地，保留来源与抽取时间
    │  只做必要的清洗，不做业务口径加工
    ▼
明细层（DWD）：按主题整合、清洗、标准化，保存最细粒度事实
    │  口径在这里统一，历史在这里留痕
    ▼
汇总层（DWS）：按常用分析口径预聚合（日、月、品类、地区）
    │  用空间换查询速度
    ▼
应用层（ADS / 集市）：面向具体报表与产品的宽表、指标表
```

分层的价值在于隔离变化：源系统字段改了，先在贴源层与明细层消化，不至于让所有报表同时崩；某个报表的口径要改，只动应用层，不动明细层。反过来，分层也有成本：层数越多，链路越长，问题定位越难；小团队为三张报表建五层，是过度设计。层数应随数据规模与报表数量增长，而不是一开始就照搬大厂模板。

### 5.1 事实表与维度表：星型模型

Kimball 维度建模把分析数据分成两类：

- **事实表**：记录可度量的业务事件，例如一笔订单、一行订单明细。事实表里是数值型度量（金额、数量）加上一组外键，指向各个维度。事实表通常很大、增长最快。
- **维度表**：记录事件发生的背景，例如日期、商品、客户、门店、渠道。维度表里是描述性属性（商品名、品类、客户等级、门店城市），供筛选、分组与标注。

星型模型就是一张事实表居中、多张维度表围绕它、用外键直接相连的样子；如果维度表又进一步规范化拆成多级（例如商品 → 品类 → 大类各成一表），就成了雪花模型。星型连接少、查询直观，是多数场景的默认选择；雪花节省一点存储、但多一次连接，通常只在维度极大或层级维护有特殊要求时才考虑。

```sql
-- 示例未实测：星型模型的最小骨架（事实表 + 两张维度表）
-- 事实：订单明细；维度：日期、商品。真实落地时表名与口径以团队约定为准。
CREATE TABLE dim_date (
    date_key TEXT PRIMARY KEY,
    month TEXT NOT NULL
);
CREATE TABLE dim_product (
    product_key INTEGER PRIMARY KEY,
    category TEXT NOT NULL
);
CREATE TABLE fact_sales (
    date_key TEXT NOT NULL,
    product_key INTEGER NOT NULL,
    amount REAL NOT NULL
);
```

上面建表语句的形态在本地用 SQLite 实测过（Python 3.12.3，内存库）：建三张表并写入少量示例数据后，按品类汇总得到图书 150.0、文具 30.0，与手工加总一致。实测只验证了语句形态与连接聚合逻辑，不代表任何数仓产品的方言与性能表现。

### 5.2 维度会变：缓慢变化维

维度不是一成不变的：客户会升级等级、商品会换品类、门店会换城市。处理维度变化的常见做法（Kimball 称之为缓慢变化维，Slowly Changing Dimension）有：

- **类型 1：直接覆盖**：旧值改成新值，不留历史。适合“错了就改”的修正，例如纠正拼写错误；代价是历史报表会跟着变，复现不了。
- **类型 2：新增一行留历史**：旧行保留有效期，新行接上，事实表按发生时间关联到当时有效的维度行。适合“等级、品类、归属”这类需要按历史口径分析的变化；代价是维度表变长、关联逻辑变复杂。
- **类型 3：加一列存旧值**：只保留“当前值”与“上一值”两列。适合只关心最近一次变化的场景；变化两次以上就装不下了。

选哪种类型，取决于业务问题：“要不要按当时的口径复现历史报表？”要，就用类型 2；不要，就用类型 1。不要默认全用类型 2——它最贵，只应在确实需要历史口径的维度上用。

## 6. ETL 与 ELT：加工放在哪里

把数据从业务系统搬进仓库并整理好的过程，传统上叫 ETL（Extract，抽取；Transform，转换；Load，装载），现代云数仓里更常见的是 ELT（Extract，抽取；Load，装载；Transform，转换）。两者的区别只有一个：转换发生在装载之前还是之后。

| 维度 | ETL | ELT |
|---|---|---|
| 顺序 | 抽取 → 转换 → 装载 | 抽取 → 装载 → 转换 |
| 转换发生地 | 独立的转换引擎或中间服务器 | 数仓内部，通常用 SQL |
| 落仓的是什么 | 加工好的结果 | 原始数据 + 加工后的模型 |
| 返工成本 | 转换逻辑改了，往往要重抽源数据 | 原始数据已在仓内，重跑转换即可 |
| 适用倾向 | 目标仓算力有限、需在入仓前脱敏或强校验 | 仓内算力充足、希望保留原始数据以备新分析 |

选哪个，取决于算力位置与合规要求，而不是新旧：如果敏感字段绝不允许以原始形态进入分析环境，入仓前转换（ETL 的思路）仍是必要的；如果团队希望分析师能随时对原始数据做新口径的探索，ELT 保留原始数据的优势就很实在。不少团队实际是混合的：敏感处理在入仓前做，业务建模在仓内用 SQL 做。

无论 ETL 还是 ELT，三个质量环节都不能省：抽取要记录来源与批次（出问题能定位到哪一批）；转换要可重跑、可对比（同一批数据重跑结果应一致，差异要能解释）；装载后要做行数、金额、主键唯一性等校验，并把校验结果留档。没有校验的数仓，报表数字只能靠“感觉没问题”支撑。

## 7. 常见误区

- **“上了数仓，报表就准了”**：错。数仓解决的是整合与口径的场所问题，口径本身（例如“销售额含不含退款”）仍需业务方拍板并写成文档；没人拍板，数仓只是把不一致的数字集中到了一处。
- **“数仓就是把业务库复制一份”**：错。原样复制不做整合、建模与历史留痕，得到的是备份，不是仓库；分析查询一样会面临口径不一、无历史快照的问题。
- **“实时就是越快越好”**：错。实时数仓有价值的场景是风控、监控、实时运营；月度经营分析用天级甚至周级更新完全够用。为不需要实时的报表付出实时链路的复杂度与成本，是常见的过度建设。
- **“分层越多越专业”**：错。层是隔离变化的手段，不是专业程度的徽章；层数应与数据规模、报表数量、团队维护能力匹配。
- **“维度建模就是画星型图”**：错。星型图只是结果；真正的建模工作在前面：业务过程是什么、粒度定到多细、维度变化怎么处理、指标口径谁说了算。图画得再漂亮，口径没定下来也跑不出可信的报表。
- **“数仓建好就一劳永逸”**：错。业务会变、源系统会变、口径会变；没有人负责模型演进、口径文档与质量校验的数仓，会在一年内退化成没人敢信的旧表堆。
