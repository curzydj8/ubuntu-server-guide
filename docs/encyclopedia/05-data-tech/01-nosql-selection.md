# NoSQL 选型入门

## 1. 对比背景

关系型数据库用表、行、列和外键表达数据，并用连接（JOIN）即时拼装关系。这个模型通用、严谨，但当数据出现以下特征时，表模型会开始吃力：字段经常变化、嵌套结构很深、访问几乎总是按键直取、写入规模极大、或者数据本身就是一张关系网。NoSQL（Not Only SQL）不是某一种数据库，而是对“不以关系表为唯一模型”的各类数据库的统称。选型的第一步不是挑产品，而是先认清自己的数据长什么样、查询怎么问、一致性丢不起到什么程度。

本篇只讲选型与模型层面的概念和方法。某个产品的安装、认证、调优与运维步骤不在这里：本站已有对应章节，例如 [MongoDB 安装、认证与调优](../../11-databases/08-mongodb.md)与 [Redis 持久化、主从与 Sentinel](../../11-databases/07-redis.md)，以及网站建设指南的[数据库选型与表设计教程](../../website-guide/database/01-design.md)，重叠处以那些文章为准，本篇不再重复。

## 2. 先定一个前提：没有万能模型

选型讨论里最常见的错误，是把“新”当成“好”，把“灵活”当成“没有代价”。每一类 NoSQL 都是在某个维度上做了交换：

- 放弃预定义严格模式，换来字段演进的自由，代价是数据质量的责任从数据库移到了应用代码和写入校验上。
- 放弃跨分区的复杂连接与多行事务，换来水平扩展与高可用，代价是某些查询必须在写入时就预先想好、甚至冗余存储。
- 把关系存成一等公民，换来多跳遍历的效率，代价是在聚合、批量扫描这类场景上未必占优。

所以选型问题的正确问法不是“哪类最强”，而是“我的读写模式是什么，这个模型是不是为这种模式生的”。

## 3. 四类模型

### 3.1 文档型：把一次读到的数据放在一个文档里

文档型数据库以自包含的文档为基本单位，文档通常是类似 JSON 的结构，内部可以嵌套对象和数组。以 MongoDB 为代表：数据以 BSON（二进制 JSON）文档存放在集合（collection）中，同一集合内的文档不必有完全相同的字段，模式灵活而非完全没有模式——官方文档与后续实践都强调，灵活模式不等于放弃模式管理，必要时可以用校验规则约束写入。

```json
{
  "user_id": "u001",
  "name": "陈默",
  "addresses": [{ "city": "杭州", "zip": "310000" }],
  "tags": ["vip"]
}
```

上面这段 JSON 在本地实测（Python 3.12.3）中可正常序列化与解析，取 `addresses[0].city` 得到“杭州”。它只用于说明文档的嵌套形态，不代表任何产品的写入语句。

文档型适合的，是“一次读出一组相关数据”的场景：商品详情（商品加规格加图片）、用户画像、内容管理、日志事件。它的边界也很清晰：文档不宜无界增长——MongoDB 单文档有 16MB 的上限（见文末来源），把不断追加的数组无限塞进一个文档是典型的反模式；真正多对多、会被多方共享的数据，更适合用引用而不是无限制内嵌。

### 3.2 键值型：按键直取，最快也最简单

键值型数据库的模型只有一个：键对应一个值，键一般是字符串，值可以是字符串、哈希、列表、集合、有序集合等结构。以 Redis 为代表：它是一个内存键值数据库，值是一组内置数据结构而非不透明的二进制块，因此可以在服务端直接对列表、集合做操作，而不必把整个值取回客户端再写回。

键值型适合的，是访问模式已经简单到“知道键、取回值”的场景：缓存、会话、排行榜、计数器、限流、轻量消息队列。它的边界同样清晰：它不擅长“按值里的某个字段查询”“跨键连接”“复杂条件聚合”。如果业务天天要问“找出所有年龄大于 30 且在杭州的用户”，键值模型会逼着你在应用层扫全量键或另建索引——那说明模型选错了，而不是产品不够快。

### 3.3 列族型：为海量写入和按键分区查询而生

列族型（宽列存储）可以理解为“带分区键的表”：数据按分区键分布到不同节点，分区内再按聚簇列排序。以 Apache Cassandra 为代表：官方文档将其描述为分区式宽列存储模型，具有最终一致语义；其组织层次是键空间（keyspace）→ 表 → 分区 → 行 → 列，表用类 SQL 的 CQL 操作，但明确不实现需要跨分区协调的操作，因为这类操作难以同时保证高可用与全局语义。

列族型适合的，是写入量极大、读取几乎总是“给定分区键、按顺序取一段”的场景：时序数据、设备事件、消息记录、用户行为流水。选型的关键在分区键设计：分区键决定数据落到哪个节点，也决定查询能不能只命中少数分区。分区键选得太粗（例如所有数据共用一个分区键），热点分区会拖垮集群；选得太细，查询又要跨大量分区拼结果。建模时必须先写出查询，再倒推分区键——顺序反了，后期很难补救。

### 3.4 图型：关系本身就是数据

图型数据库把实体存为节点、把联系存为有向有类型的边（关系），节点和边上都可以挂键值属性。以 Neo4j 为代表：其属性图模型由节点、关系、属性、标签构成，关系有且仅有一个类型、有起点终点和方向，查询语言 Cypher 用类似 ASCII 图形的写法描述要匹配的模式。

图型适合的，是“问题本身就是关系”的场景：社交网络中的共同好友与推荐路径、反欺诈中的账户关联网络、权限与依赖关系、知识图谱。它的优势不在存量大，而在跳数深：一跳、两跳、三跳的遍历在图模型里是沿边行走，而在关系模型里是多次连接，跳数一深，代价差距就拉开。它的边界是：纯聚合统计、大批量扫描、简单键值读取都不是它的主场；如果业务里根本没有“沿着关系走”的查询，就不要为图模型付出建模与运维成本。

## 4. 对比表

| 维度 | 文档型 | 键值型 | 列族型 | 图型 |
|---|---|---|---|---|
| 基本单位 | 文档（嵌套结构） | 键 → 结构化值 | 分区内的行与列 | 节点与有向有类型的边 |
| 模式 | 灵活，可校验约束 | 键固定，值结构由命令决定 | 建表时定列，分区键是建模核心 | 标签与关系类型即模式的一部分 |
| 最擅长的查询 | 一次读出一组相关数据 | 按键直取、简单结构操作 | 按分区键取一段有序数据 | 多跳关系遍历、路径与模式匹配 |
| 最不擅长的查询 | 无界增长的内嵌、多对多连接 | 按值字段的条件查询、跨键聚合 | 跨分区连接、临时任意条件查询 | 大批量聚合扫描、简单键值读取 |
| 扩展思路 | 分片水平扩展 | 分片或集群（以产品实现为准） | 按分区键天然分布多节点 | 关系遍历优先，扩展需按产品架构评估 |
| 代表产品 | MongoDB | Redis | Apache Cassandra | Neo4j |

表中“代表产品”只用于定位模型，不代表对产品的推荐；同一类内不同产品的具体行为（例如一致性默认值、事务范围）以各自官方文档为准。

## 5. 关键差异展开

### 5.1 先看数据形状，再看产品

选型最可靠的起点，是把业务里最核心的三到五个查询写下来，越具体越好：“按用户 ID 取出用户全部资料”“按设备 ID 取最近一小时的读数”“找出与某账户三跳内有关联的账户”。然后看哪种模型能让这些查询自然表达：

- 查询总是“取一整组” → 文档型优先考察。
- 查询总是“按键取一个值” → 键值型优先考察。
- 查询总是“按某个键取一段有序流水” → 列族型优先考察。
- 查询总是“沿着关系走几跳” → 图型优先考察。

如果核心查询横跨两类模型（例如既要按键缓存、又要关系推荐），答案往往不是“选一个全能的”，而是“主存储一种、辅助场景另一种”，并接受数据要在两个系统之间同步的成本。这个成本必须在选型时算进去，而不是上线后才发现。

### 5.2 一致性：CAP 说的是分区时的取舍，不是永久标签

分布式数据系统绕不开 CAP 定理：Eric Brewer 在 2000 年提出猜想，Seth Gilbert 与 Nancy Lynch 于 2002 年给出形式化证明。其含义是，在网络分区发生时，一个分布式数据存储无法同时保证一致性（每次读都拿到最新写入）、可用性（每次请求都得到非错误响应）与分区容忍性（分区下仍继续运行）三者。实践中分区容忍对多节点系统几乎是必选项，因此真实取舍发生在分区时刻的一致性与可用性之间；没有分区时，系统还面临延迟与一致性的权衡（PACELC 扩展讨论的正是这一点）。

对选型的实际意义有三点：

- 不要把 CP / AP 当成产品的永久徽章。许多产品提供可调一致性：例如 Cassandra 允许按操作选择一致性级别，同一系统在不同读写上可以做出不同取舍。具体级别与默认值以官方文档为准，选型时应按“这次读写丢不起什么”逐项确认，而不是抄一张分类表。
- 注意 CAP 的“一致性”与 ACID 的“一致性”不是同一个词。前者指多副本读到的数据是否一致，后者指事务是否保持数据满足业务规则。把两者混为一谈，是选型讨论里最常见的概念错误。
- 最终一致不是“最终一定对”的保证书。它只表示：如果写入停止，副本最终会收敛到一致状态；收敛需要多久、冲突按什么规则解决（例如 Cassandra 按时间戳的最后写入胜出），都必须在选型时问清楚，并评估业务能不能接受这段窗口。

### 5.3 事务与连接：放弃之前，先确认业务离得开它们

关系型数据库的两大能力——多行事务与任意连接——在 NoSQL 里往往是受限的。MongoDB 自 4.0（2018 年）起支持多文档事务，但这不意味着可以把关系型建模原样搬过去：事务有其适用范围与代价，日常仍应以文档内嵌、单文档原子操作为主要建模手段。Cassandra 则明确不提供跨分区事务。Neo4j 是例外：它提供 ACID 事务，但这服务于图遍历场景，不改变它不擅长批量聚合的事实。

判断方法是反向的：列出业务里“必须原子完成”的操作（例如扣款与记账必须同生同死）和“必须临时组合”的查询（例如跨五张表的即席分析）。如果这类需求是核心且高频，优先认真评估关系型方案，而不是先选 NoSQL 再想办法绕过它的限制。关于关系型本身的表设计与事务，本站网站建设指南的数据库教程已有系统讲解，见第 1 节的链接。

### 5.4 模式灵活不等于模式缺失

“无模式”是 NoSQL 早期宣传里最容易误导的词。真实情况是：模式没有消失，只是从“数据库建表时强制”转移到了“写入代码、校验规则、文档约定”里。字段含义变了、类型变了、旧文档没补字段，读到旧数据的代码一样会出错。成熟的做法是：给文档定一份团队内部的模式约定（字段名、类型、必填项、版本号），在写入层或数据库校验规则里落地，并把“字段演进怎么兼容旧数据”写进变更流程。否则灵活模式省下的建表时间，会在排障与数据清洗上成倍还回去。

## 6. 选型决策清单

按顺序回答这七个问题，答案会收敛到一到两类模型；如果答不出来，先补业务调研，不要先装数据库：

1. **核心查询是什么？** 写出最频繁、最关键的三到五个查询，包括查询条件与返回形状。
2. **数据长什么样？** 是嵌套文档、扁平键值、有序流水，还是关系网？字段变化快不快？
3. **规模与增长？** 数据量、写入速率、读取速率各是什么量级？单机能不能扛住未来一年？
4. **一致性底线？** 哪些读写绝对不能读到旧值？哪些可以接受最终一致？冲突怎么解决？
5. **事务底线？** 有没有必须原子完成的多对象操作？有，范围多大、频率多高？
6. **查询演进？** 未来会不会出现今天没写进清单的即席查询？模型对未知查询的容忍度如何？
7. **团队与运维成本？** 团队是否具备该类数据库的建模、监控、备份、恢复能力？本站 11 章的运维文章与产品官方文档是评估这项的依据，不要只看开发阶段的顺手程度。

一个可复用的决策记录格式是：查询清单 → 候选模型 → 每个模型在七个问题上的答案 → 被否决的模型与否决理由 → 试点验证项（例如用真实量级数据压测核心查询）。这份记录比最终选了哪个产品更重要，因为半年后复盘时，理由比结论更有用。

## 7. 常见误解

- **“NoSQL 就是不要 SQL”**：错。NoSQL 是“不只用关系表模型”，许多 NoSQL 产品自带类 SQL 查询语言（例如 Cassandra 的 CQL），判断标准是模型与取舍，不是名字里有没有 SQL。
- **“文档型可以无限内嵌”**：错。内嵌适合“一起读、有上限”的数据；无界增长、多方共享的数据应引用或拆分，否则文档膨胀、更新代价与上限都会找上门。
- **“选了分布式数据库就自动高可用”**：错。高可用来自副本、分区容忍、故障切换与运维演练的组合，产品只是提供了机制；部署成单节点、从不演练恢复的分布式数据库，并不比单机可靠。
- **“关系型过时了”**：错。需要强事务、复杂连接、严格约束的业务，关系型仍是合理甚至更优的选择；NoSQL 是对模型谱系的扩展，不是替代。
