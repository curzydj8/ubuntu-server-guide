# 流处理入门

## 1. 对比背景

很多数据问题天然是“一直来、没完没了”的：用户点击、传感器读数、交易流水、日志事件。处理这类数据有两条路线：等一批攒够了再算（批处理），或者来一条算一条、结果持续更新（流处理）。两条路线都能算出结果，区别在结果什么时候出来、以及“正确”按什么时间算。

本篇只讲处理模型层面的概念与方法：批与流的区别、时间语义、水位线、窗口、框架定位。消息队列本身的部署、流作业的集群运维、检查点与状态后端的调优细节不在这里；数仓一侧的建模见本系列第 2 篇，操作侧存储选型见第 1 篇。

## 2. 批与流的区别：不是快慢，是数据有没有边界

区分批与流的关键概念是**数据集有没有边界**：

- **有界数据（批）**：数据集是完整的、已知大小的，例如昨天全天的订单表。处理可以从头读到尾，算完输出一个最终结果；算错了重跑整批即可。
- **无界数据（流）**：数据持续到达、没有“最后一行”，例如正在产生的点击流。处理程序不能等“全部到齐”再开始，因为全部永远到不齐；它必须持续输出阶段性结果，并随新数据到达不断修正。

由此派生出几个实际差异：

| 维度 | 批处理 | 流处理 |
|---|---|---|
| 数据形态 | 有界，已知起止 | 无界，持续到达 |
| 结果形态 | 一次性最终结果 | 持续更新的阶段性结果 |
| 延迟 | 取决于批次间隔与作业时长 | 取决于事件到达与处理链路，通常更低 |
| 出错重跑 | 重跑整批，语义简单 | 需处理状态恢复与重复输出，语义更复杂 |
| 适用场景 | 日报、月度结算、离线模型训练 | 实时监控、风控拦截、实时大屏、实时推荐特征 |

一个常见的误解是“流就是快的批”。快的批仍是批：它把无界数据切成一小批一小批处理，每批内部仍是“等齐了再算”。这种微批（micro-batch）路线在延迟要求不极端、且团队已有批处理生态时很划算；但它不是逐条处理，延迟下限由批次间隔决定。选型时应先问“业务到底要多快”，再决定是微批够用，还是必须逐条。

### 2.1 一个可直接跑通的窗口直觉

下面的纯 Python 示例（本地实测，Python 3.12.3）模拟了最基础的滚动窗口聚合：把事件按 10 分钟一段分组求和。它不依赖任何流框架，只用于建立“窗口 = 按时间把无界流切成可算的一段”的直觉：

```python
events = [(0, 3), (4, 5), (9, 2), (11, 7), (14, 1)]  # (事件发生分钟, 数值)
windows = {}
for t, v in events:
    w = (t // 10) * 10
    windows[w] = windows.get(w, 0) + v
print(dict(sorted(windows.items())))
```

实测输出：

```
{0: 10, 10: 8}
```

即 0–9 分钟窗口合计 10，10–19 分钟窗口合计 8。真实流处理在此基础上还要解决：事件迟到怎么办、窗口什么时候触发输出、状态存在哪里、失败后怎么不重不漏——这些正是下面几节的内容。

## 3. 时间语义：事件时间、处理时间、摄入时间

流处理里“时间”至少有三个意思，混用它们是结果出错的第一来源。以 Apache Flink 的划分为例：

- **事件时间（event time）**：事件在源头实际发生的时间，由事件自带的时间戳表示。例如用户 10:03 点击，事件时间就是 10:03，无论它几点才到达处理系统。
- **处理时间（processing time）**：某个算子实际处理这条事件时，处理机器的 wall-clock 时间。事件时间 10:03 的点击，可能在 10:07 才被处理，处理时间就是 10:07。
- **摄入时间（ingestion time）**：系统摄入这条事件时打上的时间戳，介于两者之间：比事件时间晚（因为传输有延迟），比处理时间确定的环节更早。

为什么必须区分？因为网络延迟、设备离线、重试都会让事件**乱序到达**：10:03 的事件可能比 10:05 的事件晚到。如果按处理时间分组，10:03 的事件会被算进 10:07 那个窗口，结果取决于到达顺序，重跑一次可能不一样；如果按事件时间分组，10:03 的事件永远属于 10:00–10:10 的窗口，结果可复现、可重放。代价是：按事件时间算，必须回答“等到什么时候才算这个窗口齐了”——这就是水位线要解决的问题。

一般原则：对正确性有要求的统计（计费、结算口径的实时指标、合规报表）优先用事件时间；对延迟极度敏感、且结果可接受近似的场景（例如粗略的实时大屏趋势），处理时间更简单直接。不要默认用处理时间，因为它最简单——简单换来的是结果不可复现。

## 4. 水位线与迟到数据

### 4.1 水位线：对“事件时间进展到哪了”的断言

水位线（watermark）是流处理中跟踪事件时间进展的机制：一条时间戳为 t 的水位线断言，该流中时间戳不大于 t 的事件“大概率”已经到齐了。窗口算子收到水位线推进到窗口结束时间时，就可以触发该窗口的计算并输出结果。

水位线的关键在“大概率”三个字：它是一个基于观测的推断，不是上帝视角的保证。常见的生成策略是“有界乱序”：水位线 = 目前见到的最大事件时间戳 − 允许的乱序容忍（例如 20 秒）。容忍设得小，窗口触发快，但迟到事件多；容忍设得大，迟到事件少，但结果出来得晚。水位线不是调大就好的参数，它是延迟与完整性之间的显式交易。

### 4.2 迟到数据：丢弃、修正，还是旁路

水位线过去之后才到的事件，就是迟到数据。处理迟到数据通常有三种选择，各有代价：

- **丢弃**：最简单，窗口结果不再修正。适合迟到数据极少、且业务可接受少量缺失的场景；但丢弃必须是显式决策，并有监控统计丢了多少，否则“数据少了”会在月底对账时才暴露。
- **允许迟到并修正**：窗口在水位线过后仍保留一段时间，迟到事件到达时重新触发并输出修正结果。代价是状态保留更久、下游必须能处理同一窗口的多次输出（例如覆盖写而不是追加写）。
- **旁路输出**：把迟到事件单独送到一个侧输出流，供离线补算或人工核查。适合“实时结果先出、迟到数据事后对账”的场景。

选哪种，取决于下游能不能接受修正：如果下游是追加式日志，修正结果会变成重复记录；如果下游是按窗口键覆盖的表，修正就是自然的更新。流作业的设计必须和下游的写入语义一起定，不能只在流这一侧拍板。

## 5. 窗口：把无界切成可算的一段

窗口是把无界流按某种规则划分成有限集合的操作。三种最常见的按时间划分的窗口是：

- **滚动窗口（tumbling）**：固定长度、互不重叠，每个事件恰好属于一个窗口。例如“每小时的销售额”：10:00–11:00、11:00–12:00 依次切分。
- **滑动窗口（sliding）**：固定长度、按步长滑动，相邻窗口重叠，一个事件可属于多个窗口。例如“每 10 秒输出过去 1 分钟的页面浏览量”：窗口长 1 分钟、步长 10 秒。
- **会话窗口（session）**：长度不固定，按活动间隙划分：事件之间 gap 超过阈值（例如 30 分钟无活动）就断开成两个会话。适合用户行为会话、设备活跃段这类“不知道会持续多久”的分析。

选窗口的依据是业务问题的原句：“每小时”对应滚动，“过去 N 分钟、每 M 秒更新”对应滑动，“一次会话内”对应会话。把滑动窗口的步长设得太小，会产生大量重叠窗口与重复计算；把会话 gap 设得太大，会把两个独立行为合并成一个会话；设得太小，又会把一次行为切碎。这些参数没有通用最优值，应按业务含义定，并用真实数据样本验证。

窗口之外还有两个常被忽略的概念：**触发器**（窗口什么时候输出：水位线到达、数据量达到、时间到达）和**状态**（窗口聚合的中间结果存在哪里、失败后怎么恢复）。触发器决定结果的时效与修正次数，状态决定作业的可靠性与成本；两者都属于“选型时必须问清楚”的项，而不是上线后才发现的细节。

## 6. 框架定位对比

流处理生态里几个常被并列比较的名字，其实不在同一个位置上。先分清“传输层”与“处理层”，对比才有意义：

| 维度 | Apache Kafka（含 Kafka Streams） | Apache Flink | Apache Spark Structured Streaming |
|---|---|---|---|
| 定位 | 分布式事件流平台（传输与存储）+ 内嵌库 | 原生流处理引擎，流优先、批是有界流 | 批处理引擎的流式 API，统一批流 |
| 执行模型 | Kafka 本身只存与传；Kafka Streams 在应用内逐条处理 | 逐条连续处理，有向无环算子图 | 默认微批，把流切成小批用批引擎算 |
| 时间与窗口 | Kafka Streams 提供基础的事件时间与窗口支持 | 事件时间、水位线、窗口是一等公民 | 支持事件时间、水位线与窗口 |
| 状态与容错 | Kafka Streams 内置状态存储，限于 Kafka 生态 | 托管状态、检查点与恢复是核心能力 | 有状态算子与检查点，复用 Spark 生态 |
| 最适合 | 已在 Kafka 生态内、逻辑较简单的 Kafka 到 Kafka 处理 | 低延迟、有状态、事件时间语义要求高的复杂流作业 | 已有 Spark 生态、批流同一套代码、延迟要求不极端的分析 |
| 边界 | Kafka Streams 只读写 Kafka 主题、不自带独立集群；复杂窗口与大规模状态不是其主场 | 运维门槛较高：状态、检查点、升级都需要规范操作 | 微批模型决定了延迟下限；把它当成逐条引擎用会失望 |

对比时要避免两个错误：第一，把 Kafka 与 Flink 直接比“谁更快”——Kafka 是高速公路，Flink 是路上的工厂，比的不是同一样东西；第二，把“统一 API”理解成“同一性能”——Spark Structured Streaming 让批与流共用一套 DataFrame 写法，但这不改变它默认微批的执行模型，延迟与语义仍需按微批来评估。

此外，Apache Beam 值得单独提一句：它是一个统一编程模型而非执行引擎，同一套 Beam 程序可以由 Flink、Spark、Dataflow 等不同的运行器（runner）执行。它的价值在可移植性，代价是语义与调优最终仍取决于所选运行器的能力矩阵。是否值得引入 Beam，取决于团队是否真的需要在多个运行器之间迁移；如果长期只用一个引擎，直接用该引擎的原生 API 往往更简单。

## 7. 选型建议

按场景给建议；没有把握的场景不硬给结论：

- **如果团队已在 Kafka 生态内，且处理逻辑是简单的过滤、转换、聚合后写回 Kafka**：优先考察 Kafka Streams——它以内嵌库形态跑在应用里，不需要额外部署一套集群。
- **如果要求低延迟、有状态、事件时间正确性，且窗口与迟到处理复杂（例如风控、实时计费口径）**：优先考察 Flink——它的时间语义、水位线与状态管理是为这类场景设计的。
- **如果团队已有 Spark 批处理资产，希望批与流共用代码与生态，且延迟容忍在秒级**：优先考察 Spark Structured Streaming——统一 API 与生态复用是它的真实优势。
- **如果业务只是每天或每小时跑一次报表**：不要上流处理。批处理更简单、更容易重跑与对账；为不需要实时的需求建流链路，是本系列第 2 篇提到的过度建设在流侧的翻版。
- **如果延迟、正确性、状态规模三者同时要求极高**：以官方发布为准（待核实），需按真实数据量与真实乱序程度做原型压测后再定，不要凭框架宣传页的延迟数字选型。

## 8. 常见误解

- **“流处理就是实时，批处理就是慢”**：错。区分标准是有界还是无界；微批的流仍有批次延迟，批处理在小数据量下也可以很快。
- **“用了事件时间就不会错”**：错。事件时间只保证分组可复现；水位线策略、迟到处理、下游写入语义任何一个没对齐，结果照样会错。
- **“水位线越大越安全”**：错。水位线越大，迟到越少，但结果延迟越大；它是延迟与完整性的交易，不是安全等级。
- **“流作业跑起来就不用管了”**：错。状态增长、检查点失败、迟到率上升、上下游 schema 变化，都是流作业长期运行中必须监控的项；没人看监控的流作业，出问题时往往已经丢了一段时间的数据。
