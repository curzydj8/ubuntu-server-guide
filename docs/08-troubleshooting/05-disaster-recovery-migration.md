# 灾难恢复与系统迁移

## 一、概述与使用场景

备份解决的问题是「数据还在不在」，灾难恢复解决的问题是「业务能不能在可接受的时间内重新跑起来」。两者不是一回事：有备份文件，不等于能在新机器上把系统、配置、服务与数据完整还原；真正出事时才发现备份缺了配置文件、少了密钥、不知道挂载顺序，是恢复失败最常见的原因。本章把恢复与迁移放在一起讲，因为两者的核心动作相同：采集源机信息、在目标环境重建系统底座、迁移数据与配置、修复引导与网络、按清单逐项验证。区别只在于迁移是计划内从容执行，灾难恢复是在压力与时间限制下执行同一套流程。

本章覆盖六类场景。第一类是整机迁移：老服务器退役、更换云厂商、从物理机迁到虚拟机，系统与数据整体搬家。第二类是系统盘损坏但数据盘完好，只重装系统盘、重新挂载数据盘。第三类是进不去系统但数据完好，典型是 SSH 密钥丢失或认证配置写错，需要从控制台或救援环境改回。第四类是发行版升级中断，软件包处于半配置状态，系统能进但包管理损坏。第五类是引导、initramfs 与文件系统故障，本章只讲分工与要点，完整流程链接到本部分 8.1。第六类是 Docker 数据卷恢复与 Compose 项目整体迁移。

全章贯穿一条硬规矩：**任何恢复动作完成后，都必须用命令验证并判读结果，不以「命令没报错」作为恢复成功的判据。** 因此每个恢复小节的结尾都固定给出验证命令与期望结果，未通过验证就不进入下一步，更不宣布恢复完成。

!!! warning "恢复与迁移的通用红线"

    第一，源机数据在验证完成前一律只读对待：迁移未确认成功前不格式化源盘、不删除源机、不释放源云主机。第二，凡涉及写引导、检查文件系统、带删除参数同步数据的命令，先核对设备名与目标路径再执行，核对方法在对应小节中逐条给出。第三，恢复过程中每完成一步就记录执行命令、输出与时间，记录本身就是事后复盘与二次恢复的依据。

## 二、环境准备与前置条件

开始恢复或迁移前，先确认以下条件，缺项先补，不要带着缺口开工：

- 源机信息仍可获取：源机还能开机时按 3.1 节先采集；源机已损坏时，确认数据盘、备份盘或云盘快照至少有一份可挂载的副本。
- 目标环境就绪：目标机的磁盘容量不小于源机已用容量，架构相同（x86_64 与 ARM 不可直接互迁系统盘），云服务器已开通控制台 VNC 或救援模式入口，并确认能登录云厂商控制台账号。
- 安装介质与救援工具：与源系统相同大版本的 Ubuntu Server 安装镜像（22.04 的系统用 22.04 介质，24.04 的系统用 24.04 介质），物理机准备 Live USB，云服务器确认镜像可挂载。
- 备份介质独立于源机与目标机：外接硬盘、对象存储或第三台机器均可，禁止把唯一备份放在正在迁移的同一块盘上。
- 停机窗口与回退方案：写明允许停机的时间段、业务切换顺序、迁移失败时如何切回源机继续服务。源机在目标机验证通过前保持可启动状态，就是最可靠的回退方案。
- 常用工具确认：源机与目标机均应具备 `rsync`，缺失时安装：

```bash
rsync --version
sudo apt update
sudo apt install -y rsync
```

### 2.1 先定指标：RTO 与 RPO

恢复目标不是「越快越好、丢得越少越好」这种空话，而是两个可量化的指标。先为每个系统定下这两个数，后面的备份频率、保留策略与演练强度才有依据。

| 指标 | 含义 | 怎么定 | 与备份策略的关系 |
| --- | --- | --- | --- |
| RTO（恢复时间目标） | 从故障确认到业务恢复可用，允许的最长停机时间 | 按业务能承受的停机损失倒推：对外网站常见为 1 至 4 小时，内部工具可放宽到 1 个工作日 | RTO 越短，越不能依赖事后重装，必须预置快照、热备或可一键拉起的镜像；RTO 以小时计时，重装加数据恢复加验证的流程才来得及 |
| RPO（恢复点目标） | 故障时最多允许丢失多长时间的数据，以时间计 | 按数据产生速度与价值倒推：订单与账务数据常见为 5 分钟至 1 小时，静态内容可放宽到 24 小时 | 备份间隔必须小于 RPO：RPO 为 1 小时就至少每小时增量备份一次；RPO 为 24 小时，每天一次全量即可；数据库类数据要配合日志归档把 RPO 压到分钟级 |

定指标的实操方法：先写业务方能签字接受的停机时长与数据丢失上限，再反推技术方案与成本，不要先拍脑袋定备份频率再去凑指标。指标定完后写入运维文档，并按 3.7 节的演练清单实测一次真实恢复耗时与数据时点，实测值达不到指标就调整方案或调整指标，两者必须对齐，不能只写在纸上。

验证本节是否落实的方法很简单：随机抽一个系统，能立刻说出它的 RTO、RPO、最近一次备份时间与最近一次演练恢复耗时，四个数都答得出来才算落实。

## 三、手把手操作步骤

### 3.1 整机迁移完整流程

整机迁移按五个阶段顺序执行：源机信息采集、目标机最小安装、数据与配置迁移、引导与网络恢复、迁移后验证。阶段不可跳，第一阶段采集的信息是后面所有阶段的对照表。

#### 阶段一：源机信息采集

在源机还能正常运行时，把下列信息完整采集并保存到独立介质（不要只存在源机上）：

```bash
mkdir -p /tmp/source-info
lsblk -f | tee /tmp/source-info/lsblk.txt
cat /etc/fstab | tee /tmp/source-info/fstab.txt
mount | tee /tmp/source-info/mount.txt
df -hT | tee /tmp/source-info/df.txt
dpkg --get-selections | tee /tmp/source-info/packages.txt
systemctl list-unit-files --state=enabled --no-pager | tee /tmp/source-info/enabled-services.txt
ip -br addr | tee /tmp/source-info/ip-addr.txt
ip route | tee /tmp/source-info/ip-route.txt
cat /etc/netplan/*.yaml | tee /tmp/source-info/netplan.txt
crontab -l | tee /tmp/source-info/crontab-user.txt
sudo crontab -l | tee /tmp/source-info/crontab-root.txt
cat /etc/os-release | tee /tmp/source-info/os-release.txt
```

逐项说明：`lsblk -f` 与 `fstab` 两份对照着看，确认每个文件系统的 UUID、挂载点与挂载选项，迁移后重建挂载全靠这两份记录。`dpkg --get-selections` 导出全部已装软件包清单，目标机用它批量装回同一组软件。服务清单只记已启用的单元，避免把装了但没用的服务也迁过去。网络信息要同时记地址、路由与 Netplan 原文件，目标机网卡名不同，配置不能照抄，只能按记录改写。采集完把整个目录复制到备份介质并校验文件数量：

```bash
cp -a /tmp/source-info /mnt/backup/source-info
ls -l /mnt/backup/source-info
```

验证：`ls` 输出中应有 11 个文件且每个文件大小大于零，任意一个为空说明对应采集命令在源机上执行失败，先补采再进入下一阶段。

#### 阶段二：目标机最小安装

用与源机相同大版本的安装镜像在目标机做最小安装：分区方案保持与源机相同的结构思路（系统盘与数据盘是否分离、是否使用 LVM），但容量可按新盘调整。安装时只装系统本身与 SSH 服务，不装业务软件，业务软件在阶段三按清单统一恢复。安装完成后先做两件事：更新系统、装回软件包清单中的软件：

```bash
sudo apt update
sudo apt upgrade -y
sudo dpkg --set-selections < /mnt/backup/source-info/packages.txt
sudo apt-get dselect-upgrade -y
```

`dpkg --set-selections` 把源机软件包的安装状态导入目标机，`apt-get dselect-upgrade` 按导入的状态实际安装。执行中若提示个别软件包在目标版本仓库中不存在，单独记录包名，不要中断整批安装，这类包多为源机手动安装的第三方包，最后单独处理。

验证：随机抽查三个关键服务的软件包状态与版本，与源机记录对照：

```bash
dpkg -l | grep -E "nginx|mysql|docker"
systemctl list-unit-files --state=enabled --no-pager
```

#### 阶段三：数据与配置迁移

迁移分两类对象分别处理：业务数据整目录同步，系统配置挑选后同步。业务数据用 `rsync` 从源机直传目标机，示例把源机的 `/data` 同步到目标机的 `/data`：

```bash
sudo rsync -avxHA --numeric-ids --info=progress2 /data/ 192.0.2.20:/data/
```

参数逐项讲解，这是全章最需要理解的一条命令：

- `-a` 归档模式，等价于递归复制并保留权限、属主、属组、时间戳、符号链接等基本属性，是数据迁移的基础参数，不可省略。
- `-v` 显示传输文件列表，迁移记录直接取自该输出。
- `-x` 不跨越文件系统边界，防止把挂载在 `/data` 下面的其他分区或绑定挂载重复拷入，也防止漏判分区结构。
- `-H` 保留硬链接关系，避免同一文件的多个硬链接在目标机变成多份独立副本，既占空间又破坏语义。
- `-A` 保留访问控制列表（ACL），使用过 `setfacl` 细粒度授权的目录缺了这个参数会丢权限。
- `--numeric-ids` 按数字用户与组编号同步，不按用户名映射。源机与目标机同名用户的编号可能不同，迁移阶段先保证编号原样落地，再在阶段五统一核对属主。
- `--info=progress2` 显示整体进度与预计剩余时间，长距离大文件传输时用于判断是否正常推进。

源路径末尾的斜杠有明确语义：`/data/` 表示同步该目录的内容到目标目录内，写成 `/data` 则会在目标路径下再套一层 `data` 目录。执行前先用干跑模式核对文件清单与方向，确认无误再去掉该参数正式执行：

```bash
sudo rsync -avxHA --numeric-ids --dry-run /data/ 192.0.2.20:/data/
```

!!! warning "rsync --delete 的使用条件"

    `--delete` 会删除目标端存在而源端不存在的文件，让目标与源严格一致。它只允许在确认目标端没有独有数据、且干跑输出逐行核对无误后使用。首次迁移一律不加该参数；增量补同步时加，也必须先干跑并保存输出。一旦方向写反再带上删除参数，会把正确一端的数据清掉，这是迁移事故中最严重的一类，执行前必须把命令中的源与目标大声读出来核对一遍。

`/etc` 配置不能整目录覆盖目标机，因为其中包含与硬件、网络、主机身份绑定的文件。取舍原则如下表：

| 配置 | 处理 | 原因 |
| --- | --- | --- |
| `/etc/nginx`、`/etc/mysql` 等业务服务配置目录 | 同步后逐项核对路径与端口再启用 | 属于业务资产，必须迁移，但可能引用源机特有路径 |
| `/etc/fstab` | 只作对照，不直接覆盖 | UUID 与目标机新盘完全不同，覆盖必然导致启动挂载失败，按 3.2 节方法重建 |
| `/etc/netplan` | 按目标机网卡名改写后使用 | 网卡名随硬件变化，阶段四处理 |
| `/etc/hostname`、`/etc/hosts` | 按目标机规划确认后修改 | 决定主机身份，同网两台同名会互相干扰 |
| `/etc/ssh/ssh_host_*` 主机密钥 | 默认不迁移，目标机用新生成的 | 迁移主机密钥等于让目标机冒充源机身份；只有源机彻底退役且需无缝承接时才迁，并记录在案 |
| 用户家目录、`/etc/passwd` 相关账号 | 优先在目标机按清单重建账号，再同步家目录数据 | 直接覆盖账号文件容易与目标机系统账号编号冲突 |

同步配置示例，先干跑再执行，目标端原配置先备份：

```bash
sudo cp -a /etc/nginx /etc/nginx.bak-before-migrate
sudo rsync -av --dry-run 192.0.2.10:/etc/nginx/ /etc/nginx/
sudo rsync -av 192.0.2.10:/etc/nginx/ /etc/nginx/
sudo nginx -t
```

验证：每个迁入的服务先做配置语法检查（如 `nginx -t`），再启动并查状态，两个命令都通过才算该服务配置迁移完成：

```bash
sudo systemctl restart nginx
sudo systemctl status nginx --no-pager
ss -tlnp | grep -E ":80|:443"
```

#### 阶段四：引导与网络恢复

全新最小安装的目标机引导是安装程序生成的，一般无需处理。以下两种情况才需要修引导：一是直接克隆系统盘到新盘启动，二是迁移后更换了磁盘或启动模式。处理方法与完整命令见 [系统无法启动故障修复](01-boot-repair.md) 的重装 GRUB 一节，本节只给迁移场景的判读点：克隆盘启动失败先查 EFI 启动项是否仍指向旧盘，再查 fstab 的 UUID 是否与新盘一致，两处都对齐后再考虑其他原因。

网络恢复是每次迁移必做的一步，因为目标机网卡名几乎必然与源机不同。先确认新网卡名，再改 Netplan：

```bash
ip -br link
ls /etc/netplan/
sudo cp /etc/netplan/50-cloud-init.yaml /etc/netplan/50-cloud-init.yaml.bak
```

把配置文件中的网卡名改为 `ip -br link` 显示的新名称，地址、网关与 DNS 按阶段一采集的规划值填写（换云厂商时这些值按新厂商分配修改）。先校验语法再应用：

```bash
sudo netplan generate
sudo netplan apply
ip -br addr
ip route
```

!!! warning "远程改网络的断联风险"

    通过 SSH 远程修改 Netplan 并应用，地址或网卡名写错会立即断开连接。操作前先打开云厂商控制台 VNC 作为第二通道，并在控制台中确认可登录，再回 SSH 会话执行应用命令；断联后从控制台按备份文件回滚。

验证：地址与默认路由与规划一致，且能实际访问网关与外部地址：

```bash
ping -c 4 192.0.2.1
ping -c 4 198.51.100.20
resolvectl query example.com
```

三条全通才进入阶段五；只有前两条通、域名解析失败时，先按本部分 8.2 的 DNS 层方法核对 Netplan 中的 nameservers 配置，不要急着改其他网络参数。

#### 阶段五：迁移后验证清单

逐项执行并记录结果，全部通过才允许切换业务流量、才允许源机退役：

- [ ] 系统版本与内核与规划一致：`cat /etc/os-release` 与 `uname -r`
- [ ] 全部预期文件系统已挂载且容量正常：`df -hT` 与源机采集记录对照
- [ ] 已启用服务清单与源机一致：`systemctl list-unit-files --state=enabled` 两边 diff 对照
- [ ] 无失败单元：`systemctl --failed` 输出为零个
- [ ] 关键端口监听齐全：`ss -tlnp` 与源机端口清单对照
- [ ] 数据量核对通过：对关键目录执行 `du -sh` 并与源机数值对照，数据库执行计数查询与源机对照
- [ ] 文件校验抽查通过：对关键数据目录在两端执行校验和抽查，命令如下
- [ ] 定时任务已恢复：`crontab -l` 与 `ls /etc/cron.d` 与采集记录对照
- [ ] 业务冒烟通过：从外部实际访问网站、接口与登录流程，而不是只在服务器本机测

文件校验抽查命令，在源机与目标机分别对同一目录执行，输出应一致：

```bash
cd /data && find . -type f | sort | head -n 1000 | xargs md5sum | md5sum
```

判读：两端最终的校验值相同，说明抽查范围内的文件内容一致；不同则缩小范围逐目录重复该命令定位差异目录，再做增量补同步。数据库不能只看文件大小，必须用计数与抽样查询验证，文件一致不代表数据库处于一致状态。

### 3.2 系统盘与数据盘分离时的恢复

系统盘与数据盘分离是服务器的推荐结构，它最大的好处在恢复时体现：系统盘损坏或系统被装坏，只需重装系统盘，数据盘原样重新挂载即可，数据零迁移。流程如下。

第一步，确认数据盘身份。重装前或用 Live 介质启动后，先记录数据盘的设备名、UUID 与内容特征，这是后面一切操作的对象锚点：

```bash
lsblk -f
sudo blkid
```

第二步，只对系统盘执行最小安装。安装分区界面务必选手动分区，只格式化系统盘分区，数据盘不做任何格式化或挂载点设置。看不清盘与数据的对应关系时停下来，用 `lsblk -f` 的容量、文件系统与标签反复核对，禁止凭设备名顺序猜。

第三步，系统装好后先手动挂载数据盘验证内容，再写 fstab 固化：

```bash
sudo mkdir -p /data
sudo mount /dev/sdb1 /data
ls -l /data
df -h /data
sudo umount /data
```

挂载后能看到预期目录与文件、容量数值与故障前记录相符，才进入写 fstab 这一步。内容不对立即卸载，该盘不是目标数据盘，回到第一步重新辨认。

第四步，重建 fstab 条目。UUID 一律从当前 `blkid` 输出复制，并给数据盘加上 `nofail`，让数据盘异常时系统仍能启动：

```bash
sudo cp /etc/fstab /etc/fstab.bak-$(date +%Y%m%d-%H%M%S)
sudo blkid /dev/sdb1
```

在 `/etc/fstab` 中加入一行，UUID 替换为上条命令的实际输出：

```text
UUID=数据盘的实际UUID /data ext4 defaults,nofail 0 2
```

文件系统类型按 `blkid` 显示的实际类型填写，使用 XFS 的盘写 `xfs`，不要照抄示例的 `ext4`。保存后先验证再重启：

```bash
sudo findmnt --verify --verbose
sudo systemctl daemon-reload
sudo mount -a
df -h /data
ls -l /data
```

验证：`findmnt --verify` 无错误、`mount -a` 退出码为零、`df -h` 中出现 `/data` 且文件可读。随后重启一次，再重复执行 `df -h /data` 与 `systemctl --failed`，两次都正常才算固化成功。

UUID 变化排错：重装、克隆或换盘后最常见的故障是 fstab 里仍写着旧 UUID，启动时卡在等待设备或进入 Emergency 模式。判读与修法：

```bash
sudo blkid
cat /etc/fstab
sudo journalctl -xb --no-pager | grep -i -E "timed out waiting for device|dependency failed"
```

日志中出现等待设备超时且设备号正是 fstab 中的某个 UUID，而 `blkid` 中查不到该 UUID，即可确诊为 UUID 失效。修正方法是在 Emergency 模式或 Live 加 chroot 环境中（进入方法见 [系统无法启动故障修复](01-boot-repair.md)），把该行 UUID 改为 `blkid` 中的现值；临时无法确认对应关系时，先在该行行首加井号注释并确认其他条目带 `nofail` 的必要性，待系统起来后再逐项补回，不要直接删行以免丢失原挂载信息对照。

验证：修正后执行 `sudo findmnt --verify` 与 `sudo mount -a` 均无报错，重启后 `systemctl --failed` 为零个失败单元，数据盘目录内容与故障前一致。

### 3.3 SSH 密钥丢失恢复

密钥文件丢失、私钥口令遗忘、或把 `authorized_keys` 写坏，都会导致 SSH 无法登录，但系统与数据本身完好。恢复思路只有一条：绕过 SSH，从带外通道进入系统，把正确的公钥重新写回。按手边条件选一种入口。

入口一：云厂商控制台或 VNC。登录云厂商控制台，用 VNC 或网页终端以本地账号加密码方式登录故障机。能进系统后直接修正密钥文件：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
cat >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

执行 `cat >>` 后把新公钥整行粘贴进去，再按 Ctrl 加 D 结束输入。若家目录或密钥文件属主不对，sshd 会静默拒绝密钥登录，一并修正：

```bash
sudo chown -R $(whoami):$(whoami) ~/.ssh
sudo sshd -T | grep -i -E "pubkeyauthentication|authorizedkeysfile"
```

入口二：云厂商救援模式或挂载系统盘到救援机。控制台密码也不可用时，用救援模式启动（救援系统是独立的小系统，原系统盘会被挂载或可手动挂载），把原根分区挂载后直接改文件：

```bash
lsblk -f
sudo mount /dev/vda2 /mnt
ls /mnt/home
sudo nano /mnt/home/zhang/.ssh/authorized_keys
sudo umount /mnt
```

根分区设备名以救援环境中 `lsblk -f` 的实际输出为准，能看到 `home`、`etc` 等目录的分区才是根分区。用户名目录按目标账号的实际家目录替换，不要照抄示例用户名。改完卸载并从正常系统重启。

入口三：本地物理机单用户模式。物理机在 GRUB 菜单按 e 编辑启动项，在以 linux 开头的行末尾加上 `init=/bin/bash`，按 Ctrl 加 X 启动后进入无密码的根 shell，先让根文件系统可写，再按入口一的命令修正目标账号的 `authorized_keys`：

```bash
mount -o remount,rw /
passwd -S root
sync
exec /sbin/init
```

或修改完成后直接重启。单用户模式绕过了全部认证，仅限本机物理可控场景，公共环境使用后要在恢复记录中注明。

恢复后验证，三项缺一不可：

```bash
ssh -i ~/.ssh/新私钥文件 -o IdentitiesOnly=yes zhang@192.0.2.10 "hostname; whoami"
sudo journalctl -u ssh --since "-10 minutes" --no-pager | grep -i accepted
ls -l ~/.ssh/authorized_keys
```

判读：新会话能登录且返回正确的主机名与用户名；服务端日志出现 Accepted publickey 记录；密钥文件权限为 600、目录为 700、属主为登录账号本人。三项全过才算恢复。

!!! warning "恢复后必须作废旧密钥"

    密钥丢失往往意味着旧私钥可能已落入他人之手。恢复登录后立即从 `authorized_keys` 中删除旧公钥对应的整行，只保留确认在自己手中的公钥；旧私钥曾用于多台服务器时，逐台更换。最后用旧私钥实测一次登录，确认被拒绝才算作废完成，该测试结果写入恢复记录。

### 3.4 发行版升级失败恢复

`do-release-upgrade` 中断（断电、断网、会话关闭、空间不足）后，典型状态是软件包半配置、依赖不完整、包管理命令报错。处置顺序固定：先保现场，再修包管理，最后才决定是否回退。

第一步，保留现场并确认空间，空间不足是升级中断最常见的原因，也是后续修复命令能否运行的前提：

```bash
df -h / /boot /var
ls /var/log/dist-upgrade/
sudo cp -a /var/log/dist-upgrade /var/tmp/dist-upgrade-backup
cat /etc/os-release
```

第二步，按顺序修复软件包状态，每条执行完看退出结果再执行下一条，不要连写成一行：

```bash
sudo dpkg --configure -a
sudo apt install -f
sudo apt update
sudo apt upgrade -y
sudo dpkg --configure -a
```

判读：`dpkg --configure -a` 把所有已解包未配置的软件包完成配置；`apt install -f` 修复破损依赖关系，它提出移除大量核心包的方案时不要直接接受，先停下来记录方案，这通常说明源配置处于跨版本中间状态，需要先把 `/etc/apt/sources.list` 与 `/etc/apt/sources.list.d` 中的版本代号统一到目标版本或回退到原版本，再重复本步骤。两条命令都能干净完成、`apt update` 无报错，说明包管理已回到一致状态。

第三步，决定继续升级还是回退。包管理修复成功且系统版本处于中间状态时，重新执行升级命令续完升级通常是最短路径：

```bash
sudo do-release-upgrade
```

若续升再次失败或核心服务已损坏，按决策点判断：有升级前快照或 Timeshift 还原点，直接回滚快照，不要在损坏的系统上反复修补；无快照但数据完好且业务停机窗口允许，走「重装新版本加按 3.1 节迁移数据与配置」的路线，比无限修补更可控。做决定前先确认数据与配置已按 3.1 阶段一的方法采集到独立介质。

关于快照思路：云服务器在升级前用云厂商控制台创建整机快照，回滚就是控制台一键恢复，升级前五分钟的操作换来最可靠的退路。物理机可用 Timeshift 在升级前创建系统还原点，它只快照系统文件不含用户数据，正好适合升级回滚这个场景；但 Timeshift 需要在升级前就安装并创建好还原点，事后无法补。没有事先快照时，Clonezilla 整盘镜像是物理机的等价退路，同样必须事前制作。

验证：升级或回滚完成后逐项确认，全部通过才恢复业务：

```bash
cat /etc/os-release
sudo apt update && sudo apt upgrade -y
sudo dpkg --audit
systemctl --failed
sudo reboot
```

判读：版本号为目标版本或回滚后的原版本且与决策一致；`apt upgrade` 显示无待升级且无破损；`dpkg --audit` 无输出，表示没有半配置软件包；重启后 `systemctl --failed` 为零个，关键服务逐个实际访问验证，不只查进程存在。

### 3.5 引导、initramfs 与文件系统故障：分工与要点

这类故障的完整修复流程已在 [系统无法启动故障修复](01-boot-repair.md) 中成章，本节只讲分工与迁移恢复场景中的要点，不重复整章内容。

分工判读：开机停在固件或 GRUB 阶段、进入 grub rescue 或 initramfs 提示符、Emergency 模式，先去 8.1 按其卡点判断表定位；本章 3.1 与 3.2 中涉及引导与 fstab 的部分，只处理迁移与重装场景下由 UUID 与网卡名变化引起的配置对齐，底层引导重装、initramfs 重建一律以 8.1 的命令为准，两处冲突时以 8.1 为准并回报修订。

文件系统检查只记一条安全前提：

!!! danger "fsck 只能对未挂载或只读挂载的文件系统执行"

    对已读写挂载的文件系统直接运行 `fsck` 修复，极可能把正在使用的文件系统写坏，造成比原故障更严重的数据损坏。正确顺序是：先用 `lsblk` 与 `mount` 确认目标文件系统的挂载状态，能卸载的先 `sudo umount` 卸载再检查；根文件系统无法在线卸载，必须用 Live 介质或救援模式启动后，对未挂载的根分区执行检查。只想先评估损坏程度时用只读检查模式，它不写盘：

    ```bash
    mount | grep /dev/sda2
    sudo fsck -n /dev/sda2
    ```

    `-n` 表示对所有提问回答否、只报告不修复。确认问题范围并完成备份后，再在未挂载状态下执行正式检查，是否加自动修复参数按 8.1 与现场策略决定，不要无条件对生产数据盘使用自动确认一切的修复方式。

验证：检查完成后先只读挂载看目录结构，再正常挂载并抽查关键文件可读，最后重启确认系统能完整启动且 `systemctl --failed` 为零个，三步都过才算文件系统恢复完成。

### 3.6 Docker 数据卷恢复与 Compose 项目迁移

Docker 环境的资产分三类，恢复方法各不相同：镜像可重新拉取或构建，不必备份；命名卷与绑定挂载目录是真实数据，必须备份；Compose 项目目录（包含编排文件、环境变量文件与相对路径挂载的数据）应整目录迁移。

先盘点现有卷与容器的数据落点：

```bash
docker volume ls
docker ps -a
docker inspect 容器名 | grep -A 5 Mounts
ls /var/lib/docker/volumes/
```

命名卷的实际数据位于 `/var/lib/docker/volumes/卷名/_data`。直接打包该目录只允许在对应容器已停止时进行，容器运行中直接拷卷目录可能得到写一半的数据。通用且安全的方法是用临时容器挂载卷做备份：

```bash
docker stop 应用容器名
docker run --rm -v 卷名:/data:ro -v $(pwd):/backup alpine tar czf /backup/volume-backup.tar.gz -C /data .
ls -lh volume-backup.tar.gz
```

`-v 卷名:/data:ro` 以只读方式把卷挂进临时容器，`--rm` 让临时容器退出即删，tar 把卷内容打包到当前目录。恢复到新机器时先建空卷，再用同样的方法解包：

```bash
docker volume create 卷名
docker run --rm -v 卷名:/data -v $(pwd):/backup alpine sh -c "cd /data && tar xzf /backup/volume-backup.tar.gz"
docker volume inspect 卷名
```

解包命令在容器内执行，卷名与备份文件名按实际值替换，禁止把备份文件路径写错到其他卷上。恢复后不要急于删源端备份，待应用验证通过再按保留策略处理。

Compose 项目整目录迁移：把项目目录连同其中的编排文件、`.env` 文件与绑定挂载的数据子目录一起同步，命名卷仍按上面的卷方法单独备份恢复，两条线不要混：

```bash
sudo rsync -avxHA --numeric-ids --dry-run /srv/app/ 192.0.2.20:/srv/app/
sudo rsync -avxHA --numeric-ids /srv/app/ 192.0.2.20:/srv/app/
cd /srv/app && docker compose config
```

`.env` 文件常含密码与密钥，迁移时确认传输走加密通道（rsync 默认经 SSH 即满足），迁移后检查其权限为仅属主可读，并在验证通过后评估是否需要轮换其中的密钥。

验证：卷与项目都恢复后拉起服务并做数据级检查，而不是只看容器状态为运行：

```bash
cd /srv/app && docker compose up -d
docker compose ps
docker compose logs --tail=50
curl -o /dev/null -s -w "%{http_code}\n" http://127.0.0.1:8080/
docker exec 应用容器名 ls -l /data
```

判读：容器状态为 Up 且日志无持续报错，接口返回预期状态码，容器内数据目录能看到恢复的文件且数量、时间与源端记录相符。数据库类容器还要执行计数查询与源端对照，文件在不等于数据对。

### 3.7 恢复演练清单

恢复能力只能靠演练证明，从未演练过的备份在故障时按「不存在」对待。按 RTO 分级安排演练频率：RTO 在 4 小时以内的系统每季度演练一次，其余系统每半年一次。演练必须在隔离环境进行（独立的测试虚拟机或临时云主机），禁止拿生产环境直接做恢复试验。

演练步骤清单，逐项勾选并记录每步耗时，全部耗时之和就是实测 RTO：

- [ ] 准备隔离环境：确认测试机与生产网络隔离，快照与备份介质可访问
- [ ] 从零恢复系统底座：按本章流程在测试机完成最小安装与软件包恢复
- [ ] 恢复数据与配置：完成数据同步、卷恢复与配置对齐，记录数据备份的时点，该时点与演练时刻的差值即实测可达 RPO
- [ ] 修复引导与网络：完成 fstab 对齐与 Netplan 改写，测试机能正常重启并联网
- [ ] 数据校验：执行目录校验抽查与数据库计数对照，结果与生产记录一致
- [ ] 应用冒烟：走完登录、核心查询、写入一笔测试数据、上传一个文件四类动作
- [ ] 记录实测值：把总耗时、数据时点、失败环节与改进项写入演练报告
- [ ] 销毁隔离环境中的敏感数据：演练用的生产数据副本在报告归档后删除，并记录删除时间

演练中任何一步失败都是有效成果：它在没有业务压力时暴露了流程缺口。失败项必须转化为对备份策略或本章流程的修订，并安排复演验证修订有效，只记录不修订的演练等于没有演练。

验证本节落实的标准：能拿出最近一次演练报告，其中实测 RTO 与 RPO 数值达到 2.1 节为该系统定下的指标，且失败项都有对应的修订记录。

## 四、效果验证与测试

无论本次做的是迁移、单盘恢复还是密钥恢复，最后统一按本节收口，核心仍是 3.1 阶段五的清单，此处给出一组可直接执行的总验证命令：

```bash
systemctl --failed
systemctl is-system-running
df -hT
lsblk -f
ss -tlnp
journalctl -b -0 -p err --no-pager
```

期望输出示例：

```text
$ systemctl --failed
  UNIT LOAD ACTIVE SUB DESCRIPTION
0 loaded units listed.
$ systemctl is-system-running
running
```

判读标准：无失败单元、系统状态为 running、本次启动日志错误级别无与恢复部位相关的新条目、全部预期挂载与端口齐备。再连续重启两次并重复关键项检查，因为 fstab 与引导类问题常在第二次重启才暴露。最后由业务侧从外部完成一次真实访问与一笔真实写入，恢复宣告以业务验证通过的时刻为准，该时刻与故障确认时刻的差值记入本次的实际 RTO。

## 五、常见错误与排坑指南

**错误一：迁移还没验证完就释放源机或格式化源盘。** 现象是目标机上线后发现某类数据没迁或配置缺失，源机已经销毁，无从补迁。原因是把「文件传完」当成「迁移完成」。正确做法是源机至少保留到目标机通过阶段五全部清单并稳定运行一个业务周期之后，退役动作单独走审批与记录，与迁移操作分开执行。

**错误二：fstab 照抄源机或凭设备名填写，重启后进入 Emergency 模式。** 现象是恢复时手动挂载一切正常，一重启就启动失败。原因是 UUID 已随新盘变化，设备名在多盘环境下也不稳定。正确做法在 3.2 节：UUID 只从当前系统的 `blkid` 输出复制，数据盘加 `nofail`，改后必须先用 `findmnt --verify` 与 `mount -a` 验证再重启。

**错误三：对读写挂载中的文件系统直接执行 fsck 修复，或对运行中的 Docker 卷目录直接打包。** 两者是同一类错误：在数据仍被写入时做离线语义的操作，得到损坏或不一致的副本还不自知。正确做法是先停写再操作：文件系统先卸载或进救援环境，卷先停容器或用只读挂载的临时容器备份，判读标准见 3.5 与 3.6 节。

**错误四：升级中断后反复运行修复命令，却先统一不了软件源版本。** 现象是 `apt install -f` 每次提出移除大量软件包，越修依赖越乱。原因是系统处于跨版本中间状态，软件源代号新旧混杂。正确做法是先停手，统一软件源到一个明确版本代号后再修包管理；有升级前快照时直接回滚，不要在中间状态上持续叠加操作，具体判读见 3.4 节。

**错误五：密钥恢复后只顾登录成功，忘了作废旧密钥与修正权限。** 现象是自己能登了，但旧私钥若已外泄，他人同样能登；或权限过宽导致 sshd 在某些配置下拒绝密钥。正确做法按 3.3 节收尾三件套：删旧公钥行并实测旧私钥被拒、目录与文件权限分别收紧为 700 与 600、属主核对为登录账号本人。

## 六、生产环境最佳实践与安全建议

第一，备份策略与 RTO、RPO 绑定并写成文档：每个系统登记备份方式、频率、保留代数、介质位置与负责人，指标变更时同步改备份策略，不允许只改其中一边。第二，备份必须与源机隔离：至少一份副本放在独立故障域（不同物理机、不同云账号或离线介质），勒索与误删场景下同机备份等于没有备份。第三，恢复通道预先验证：云控制台登录、VNC、救援模式、Live 介质每半年实测一次可用性，这些通道平时不用，出事时才发现账号过期或权限不足是最痛的二次故障。第四，升级与大变更前强制快照：发行版升级、分区调整、引导变更之前创建快照或整盘镜像，并在变更单中写明回滚步骤与触发条件，没写回滚的变更单不执行。第五，配置纳入版本管理：Netplan、fstab 模板、服务配置与 Compose 项目目录进入 Git 仓库（敏感值用占位符，真实值另行保管），迁移与恢复时以仓库版本为配置基准，减少靠从旧机拷贝的漂移。第六，演练常态化并公开实测值：按 3.7 节清单定期演练，实测 RTO 与 RPO 达不到指标就如实上报并调整方案或指标，恢复能力以演练报告为准，不以备份任务显示成功为准。
