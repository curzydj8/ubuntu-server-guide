## 4. 使用前提

动手前请先确认下面五项，缺一项就先补齐，不要直接在生产库上练：

1. 你有一个能登录的数据库账号，并且知道它有没有备份所需的权限（见第 8 节的检查清单）。

5. 你已经读过 DB-01，知道什么是事务、什么是索引、什么是主键，不知道的话先回去读 DB-01。

## 6. 技术原理

### 6.1 备份的三种分法

- 全量与增量：全量是一次把整个库导出来；增量是只导上次备份之后变的部分。MySQL 逻辑备份的增量一般不靠 mysqldump 本身，而是靠 Binlog：全量备份加之后的 Binlog，就是“恢复到指定时间点”的材料。
- 逻辑备份与物理备份：逻辑备份是导出 SQL 语句（mysqldump、pg_dump 属于这一类），优点是跨版本、跨机器好恢复，缺点是大库导出和导入都慢；物理备份是直接拷数据文件（xtrabackup、文件系统快照属于这一类），优点是快，缺点是对版本和路径要求严。本篇第 10 节用逻辑备份，因为它最通用、最容易演练。
- 冷备与热备：冷备是停库再拷，热备是不停库直接备。mysqldump 加 `--single-transaction` 是对 InnoDB 的热备做法，见第 12 节。

### 6.2 恢复到指定时间点

恢复到指定时间点（PITR）需要两样东西，缺一样就做不到：

1. 一份全量备份，时间点记为 T0；
2. 从 T0 之后连续的 Binlog，没有断档。

恢复时先把全量备份导入，再按顺序重放 Binlog 到目标时间点。Binlog 一旦断档、过期被清理、或者根本没开，PITR 就做不到了，这就是第 8 节要求先核对 Binlog 是否开启的原因。

### 6.3 迁移的本质

表结构迁移的本质，是“把数据库从一个已知的结构版本，变到下一个已知的结构版本”，并且每一步都可追踪、可回滚。迁移文件要编号（如 `0001`、`0002`），按顺序执行，执行记录要落库或落文件，不能靠人脑记“这个库改到哪一步了”。MySQL 有一个必须知道的特性：DDL 语句（如 `ALTER TABLE`）会隐式提交，不能放在事务里回滚，所以迁移前的备份不是可选项，是必选项，见第 18 节。

### 6.4 慢查询的判定

一条查询是不是慢查询，不靠感觉，靠两个证据：

1. 慢日志：执行时间超过阈值（`long_query_time`）的查询会被记下来，阈值由你定，见第 11 节；
2. EXPLAIN：看执行计划，重点看有没有走索引、扫描了多少行、有没有临时表和文件排序，见第 9.4 节。

没有这两个证据就加索引，是最常见的误诊：索引加错了地方，慢查询还是慢，还多了一份写负担。

### 6.5 主从复制的原理

主从复制的原理是一句话：从库不断向主库要 Binlog，拿到之后在自己身上重放一遍。主库负责写，从库负责读，读的压力就被分出去了。但复制是异步的，主库写完立刻返回，不等从库重放完，所以从库的数据在某一刻一定落后主库一点，这段落后叫复制延迟。半同步复制可以缩小这个窗口，但代价是主库写要等至少一个从库确认，写会变慢。延迟、读写分离、主从切换的坑，都从“异步”这两个字长出来，见第 7 节和第 16 节。

### 6.6 高可用保证什么

高可用保证的是“主库挂了之后，服务能在约定的时间内恢复”，不保证“永远不宕机”。两个指标要先定下来，再谈方案：

- RTO（恢复时间目标）：从主库挂掉，到服务恢复，最长允许多久；
- RPO（恢复点目标）：最多允许丢多少数据，是零丢失，还是允许丢几秒。

RPO 为零的方案代价最高，RPO 为几秒的方案代价低很多。先定指标，再选方案，不要先买方案再反推指标。

## 7. 架构说明

### 7.1 备份架构

备份架构只有一条铁律：备份不能和数据放在同一个故障域里。同一块盘、同一台机器、同一个机房的备份，只能防“误删”，防不了“盘坏了”“机器没了”。按预算从低到高，备份存放可以是：本机另一块盘、同一内网的另一台机器、对象存储或异地机器。本篇的脚本把备份写到本机备份目录，异地复制是下一步，见第 9.5 节的收尾清单。

### 7.2 主从与读写分离架构

```
用户请求
  -> Nginx / 应用
    -> 写请求 -> 主库
    -> 读请求 -> 从库（一个或多个）
主库 --Binlog--> 从库（重放）
```

- 写只走主库，读走从库，应用层或代理层按读写分流；
- 从库可以挂多个，读压力大了就加从库，但从库越多，延迟不一致的窗口也越明显；
- 报表、导出、备份这类重读操作，优先走从库，不要压在主库上。

### 7.3 故障转移架构

主库挂了之后，故障转移要做三件事，缺一件服务就起不来：

1. 选出新的主库（原来延迟最小、数据最新的从库）；
2. 让所有从库改向新的主库；
3. 让应用的写流量改到新的主库（改配置、改代理、改 VIP，三种办法见第 9.5 节）。

故障转移最容易出的问题是“脑裂”：旧主库其实没死，只是网络断了一下，它又回来继续接受写，两个主库各写各的，数据就合不回来了。所以自动故障转移必须配“ fencing ”思路：确认旧主库真的不能写了，再让新主库接管；没有把握时，宁可手动切换，也不要自动切换，见第 17 节。

## 8. 操作前检查

动手前逐项打勾，有一项不通过就先修好，不要带着问题往下做：

| 检查项 | 检查办法 | 不通过的后果 |
| --- | --- | --- |
| 数据库能登录 | 用备份账号登录一次，能连上、能看库 | 备份脚本一跑就失败 |
| Binlog 已开启 | 查配置文件里 `log_bin` 是否开启，见第 11 节 | 做不了恢复到指定时间点 |
| 慢日志已开启 | 查 `slow_query_log` 是否为 ON | 慢查询无据可查 |
| 磁盘空间够 | 看备份目录所在盘的剩余空间，至少能放两份全量 | 备份写到一半失败，得到一份坏备份 |
| 备份目录权限对 | 备份目录只允许数据库运维账号读写，见第 17 节 | 备份文件被无关账号读到，等于数据泄露 |
| 有测试库 | 测试库能登录、能建表、能删表 | 恢复演练无处可做 |
| 从库延迟可看 | 从库上能查到复制状态和延迟秒数 | 延迟失控了都不知道 |
| 时钟已同步 | 服务器时间与标准时间差在秒级以内 | 备份文件名与 Binlog 时间点对不上 |

## 9. 逐步操作

### 9.1 搭备份任务

1. 按第 11 节建凭据文件 `/etc/mysql-backup/client.cnf`，权限改成 600，属主改成跑备份的账号；
2. 把第 10 节的备份脚本存为 `/usr/local/bin/mysql-backup.sh`，权限改成 700；
3. 按第 11 节加 cron，每天凌晨 2 点 30 分跑一次；
4. 手动跑一次脚本，看日志文件里有没有 `backup ok` 那一行，再看备份目录里有没有当天的备份文件和校验和文件；
5. 用 `sha256sum -c` 验一次校验和，确认备份文件没写坏。

### 9.2 做恢复演练

1. 在测试库上建一个空库，库名与生产库不同，避免误操作；
2. 把备份文件解压后导入测试库；
3. 对照生产库的表清单，逐表核对表在不在、行数对不对得上；
4. 跑一条业务查询（例如查最新一篇文章的标题），确认能查出数据；
5. 把演练结果记下来：备份文件是哪一份、导入花了多久、有没有报错、行数对不对；
6. 演练通过了，这份备份才算“能用”；演练没做过的备份，在第 18 节的红线里等于没有备份。

### 9.3 做表结构迁移

1. 先按第 9.1 节做一份全量备份，确认备份文件和校验和都在；
2. 写迁移文件，文件名带编号，如 `0001_add_summary_to_articles.sql`，内容见第 10 节；
3. 先在测试库上执行迁移文件，再跑一遍应用的冒烟测试；
4. 测试库通过了，再在生产库上执行，执行时避开业务高峰；
5. 执行完核对表结构（新字段在不在、类型对不对），再跑一次冒烟测试；
6. 写好回滚语句，和迁移文件放在同一个目录，见第 18 节。

### 9.4 定位一条慢查询

1. 打开慢日志，确认阈值（本篇示例为 1 秒），等慢查询被记下来，或者直接查已有的慢日志；
2. 从慢日志里抄出那条 SQL 的原文，不要凭记忆重写；
3. 在测试库上对这条 SQL 跑 `EXPLAIN`，看四个点：`type` 是不是 `ALL`（全表扫描）、`key` 是不是空（没用上索引）、`rows` 扫了多少行、`Extra` 里有没有 `Using filesort` 或 `Using temporary`；
4. 四个点里至少有一个对得上，才能说“这条查询慢的证据找到了”；
5. 再决定修法：加索引、改写法、分页、拆查询，四种修法各有代价，见第 15 节；
6. 修完再跑一次 `EXPLAIN` 和慢日志，确认扫描行数下来了、慢日志里不再出现它，才算修好。

### 9.5 搭主从与故障转移

1. 主库开启 Binlog，配好 `server-id`，建复制专用账号，只给复制权限；
2. 从库用主库的全量备份先恢复到同一时间点，再指向主库开始复制；
3. 查从库复制状态，确认复制在跑、延迟在秒级、没有最后一次错误；
4. 应用层按读写分流：写走主库，读走从库，报表和备份走从库；
5. 故障转移先练手动切换：停主库写、等从库追平、提升从库为新主库、改应用写地址、确认写能落到新主库；
6. 手动切换练熟了，再考虑自动切换工具；自动切换没有把握时，宁可手动，见第 7.3 节。

### 9.6 PostgreSQL 读者的对照

PostgreSQL 的思路与本篇相同，命令换一套：备份用 `pg_dump`，恢复用 `psql` 或 `pg_restore`，时间点恢复靠 WAL 归档，主从叫流复制，慢查询看 `pg_stat_statements` 或慢日志。不要把 mysqldump 的参数往 `pg_dump` 上套，也不要把 MySQL 的 Binlog 概念往 PostgreSQL 上套，两边的名字和机制都不一样。


## 10. 完整代码

### 10.1 备份脚本

存放路径：`/usr/local/bin/mysql-backup.sh`，权限 700，属主为跑备份的账号。适用数据库：MySQL 8.0、8.4 与 MariaDB 10.x。口令不写进脚本，通过第 11 节的凭据文件引用。

```bash
#!/usr/bin/env bash
set -euo pipefail
BACKUP_ROOT="/var/backups/mysql"
RETENTION_DAYS=14
DB_NAME="appdb"
CRED_FILE="/etc/mysql-backup/client.cnf"
DATE="$(date +%F_%H%M%S)"
BACKUP_DIR="${BACKUP_ROOT}/${DATE}"
LOG_FILE="/var/log/mysql-backup.log"
mkdir -p "${BACKUP_DIR}"
mysqldump --defaults-extra-file="${CRED_FILE}" --single-transaction --routines --events --triggers --databases "${DB_NAME}" | gzip > "${BACKUP_DIR}/${DB_NAME}.sql.gz"
sha256sum "${BACKUP_DIR}/${DB_NAME}.sql.gz" > "${BACKUP_DIR}/${DB_NAME}.sql.gz.sha256"
find "${BACKUP_ROOT}" -mindepth 1 -maxdepth 1 -type d -mtime +"${RETENTION_DAYS}" -exec rm -rf {} +
echo "[${DATE}] backup ok: ${BACKUP_DIR}/${DB_NAME}.sql.gz" >> "${LOG_FILE}"
```

脚本的每一步说明：

- `set -euo pipefail`：任何一步失败就停下来，不让失败的备份冒充成功；
- `--single-transaction`：对 InnoDB 表做一致性热备，不锁全库；
- `--routines --events --triggers`：把存储过程、事件、触发器也导出来，缺了这三个，恢复出来的库是不全的；
- `--databases`：导出时带上建库语句，恢复时不用先手动建库；
- `gzip` 压缩：备份文件小很多，传输和存放都省空间；
- `sha256sum`：给备份文件留校验和，恢复前先验，写坏的备份早发现；
- `find -mtime +14`：只删 14 天以前的备份目录，当天的和近 14 天的都留着；
- 日志只写一行 `backup ok` 加备份路径，失败时脚本直接退出，cron 会把错误输出发到系统邮件或日志里，不要让失败静默。

### 10.2 恢复演练步骤

存放路径：演练步骤本身不需要存文件，照着做一遍，把结果记在运维记录里。演练用的库名是 `appdb_restore_test`，绝不用生产库名。

```bash
mkdir -p /tmp/restore-test
gunzip -c /var/backups/mysql/2026-11-03_023000/appdb.sql.gz > /tmp/restore-test/appdb.sql
mysql --defaults-extra-file=/etc/mysql-backup/client.cnf -e "CREATE DATABASE IF NOT EXISTS appdb_restore_test CHARACTER SET utf8mb4;"
mysql --defaults-extra-file=/etc/mysql-backup/client.cnf appdb_restore_test < /tmp/restore-test/appdb.sql
mysql --defaults-extra-file=/etc/mysql-backup/client.cnf -e "SHOW TABLES FROM appdb_restore_test;"
mysql --defaults-extra-file=/etc/mysql-backup/client.cnf -e "SELECT COUNT(*) FROM appdb_restore_test.articles;"
mysql --defaults-extra-file=/etc/mysql-backup/client.cnf -e "SELECT id, title FROM appdb_restore_test.articles ORDER BY id DESC LIMIT 1;"
```

注意三点：备份文件路径里的日期 `2026-11-03_023000` 是示例，实际用演练当天那一份备份的真实路径；恢复前先用 `sha256sum -c` 验一次校验和；演练完把 `/tmp/restore-test` 里的解压文件删掉，解压后的 SQL 明文同样是生产数据，不能长期留在临时目录。

### 10.3 表结构迁移 SQL

存放路径：`db/migrations/0001_add_summary_to_articles.sql`，与应用代码放在同一个仓库里，编号递增，不改已执行过的迁移文件。适用数据库：MySQL 8.0、8.4 与 MariaDB 10.x。

```sql
ALTER TABLE articles ADD COLUMN summary VARCHAR(500) NULL AFTER title;
```

这条迁移只有一句话，但它背后有三条规矩，缺一条都不要执行：

1. 执行前先按第 9.1 节做一份全量备份，备份文件和校验和都要在；
2. 先在测试库上执行，再在生产库上执行，顺序不能反；
3. 回滚语句和迁移文件放在同一个目录，见第 18 节。

MySQL 的 DDL 会隐式提交，不能放在事务里回滚，所以“执行前备份”不是建议，是这条迁移能执行的前提。

## 12. 每个关键配置项的解释

### 12.1 备份脚本关键项

| 配置项 | 解释 |
| --- | --- |
| `BACKUP_ROOT` | 备份根目录，本篇示例为 `/var/backups/mysql`，实际换成自己的备份盘路径 |
| `RETENTION_DAYS` | 保留天数，本篇示例为 14 天，到期自动删，删之前确认异地还有一份 |
| `DB_NAME` | 要备份的库名，一个库一份脚本，多库就多份脚本或循环处理，不要把多个库混进一个文件还不留清单 |
| `CRED_FILE` | 凭据文件路径，口令只在这里，脚本里只引用路径 |
| `--single-transaction` | 对 InnoDB 表做一致性热备，不锁全库；MyISAM 表不适用，混用引擎时要先确认 |
| `--routines --events --triggers` | 导出存储过程、事件、触发器，缺了恢复出来的库是不全的 |
| `--databases` | 导出时带上建库语句，恢复时不用先手动建库 |
| `sha256sum` | 给备份文件留校验和，恢复前先验，写坏的备份早发现 |

### 12.2 定时任务关键项

| 字段 | 解释 |
| --- | --- |
| `30 2 * * *` | 分、时、日、月、周，每天凌晨 2 点 30 分，避开业务高峰 |
| `root` | 以 root 身份跑脚本，脚本本身权限 700，普通账号读不到凭据路径的引用关系 |
| `/usr/local/bin/mysql-backup.sh` | 备份脚本的完整路径，cron 里必须写完整路径，不能只写脚本名 |

### 12.3 数据库配置关键项

| 配置项 | 解释 |
| --- | --- |
| `server-id` | 主从复制里区分机器的编号，主库和从库不能相同，从库之间也不能相同 |
| `log_bin` | 开启 Binlog，不开就做不了恢复到指定时间点，也做不了主从复制 |
| `binlog_format=ROW` | 按行记录变更，恢复和复制都更准确，是目前最常用的格式 |
| `binlog_expire_logs_seconds=604800` | Binlog 保留 7 天，604800 秒等于 7 天；保留期要比全量备份的间隔长，否则恢复到指定时间点会断档 |
| `slow_query_log=1` | 开启慢日志，不开慢查询无据可查 |
| `slow_query_log_file` | 慢日志文件路径，定期归档，不要让它无限长大 |
| `long_query_time=1` | 超过 1 秒的查询记入慢日志，阈值按业务定，定得太低会记太多，定得太高会漏掉真慢的查询 |

## 15. 常见错误

| 错误 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 备份脚本里直接写口令 | 口令会进脚本文件、进版本库、进日志，谁读到脚本谁就拿到了数据库口令 | 口令只放 600 权限的凭据文件，脚本里只引用路径，见第 11.1 节 |
| 备份不带存储过程、事件、触发器 | 恢复出来的库缺东西，应用一跑就报错，还以为是恢复失败 | mysqldump 加上 `--routines --events --triggers`，见第 12.1 节 |
| 备份和数据放同一块盘 | 盘坏了，数据和备份一起没，备份等于没有 | 备份至少放另一块盘，最好再有一份异地，见第 7.1 节 |
| 从来不做恢复演练 | 备份文件写坏了、缺东西了、版本不对了，全都不知道，真要恢复时才发现 | 每月至少演练一次，演练结果记下来，见第 9.2 节 |
| 迁移前不备份 | MySQL 的 DDL 会隐式提交，执行错了回不去，只能靠备份恢复 | 迁移前先做全量备份，确认校验和，见第 9.3 节 |
| 改了已执行过的迁移文件 | 已经执行过的库和没执行过的库，结构就对不上了，排障排到天亮 | 迁移文件一旦执行过就不再改，有问题写新的迁移文件 |
| 凭感觉加索引治慢查询 | 索引加错地方，慢查询还是慢，还多了一份写负担 | 先拿慢日志和 EXPLAIN 的证据，再决定修法，见第 9.4 节 |
| 把从库当主库用 | 从库延迟的那几秒，读到的是旧数据，严重时读到的是还没同步过来的空 | 读到旧数据会出问题的查询走主库，见第 7.2 节 |
| 故障转移全自动还不设 fencing | 旧主库其实没死，只是网络断了一下，回来又写，两个主库各写各的 | 没有把握时宁可手动切换，见第 7.3 节 |
| 把高可用说成永不宕机 | 高可用保证的是约定时间内恢复，不是永远不宕机，承诺过头等于给自己挖坑 | 先定 RTO 和 RPO，再谈方案，见第 6.6 节 |

## 16. 故障排查

| 现象 | 先查什么 | 常见原因与处理 |
| --- | --- | --- |
| 备份脚本跑失败 | 看脚本的错误输出和日志文件，看凭据文件权限是不是 600、路径对不对 | 凭据文件权限太松会被 MySQL 拒绝读取；备份目录不存在或写不进；磁盘满了 |
| 备份文件很小，明显不对 | 看备份文件的大小和校验和，看脚本日志里有没有报错 | 导出时库名写错，导了个空库；导出中途失败，管道没报错就继续往下走了 |
| 恢复时报表已存在 | 看恢复目标库是不是空库 | 恢复必须进空库或测试库，往已有数据的库里恢复会冲突，先确认目标库 |
| 恢复后行数对不上 | 对照备份时的行数和恢复后的行数，看是不是 Binlog 重放断了 | 全量备份之后的数据要靠 Binlog 补，Binlog 断档就补不上，先查 Binlog 保留期 |
| 迁移执行报错字段已存在 | 看迁移是不是重复执行了，看迁移执行记录 | 迁移文件不能重复执行，执行记录要落库或落文件，重复执行先核对表结构再决定跳过还是回滚 |
| 慢日志里没有慢查询 | 看慢日志开没开、阈值是不是定得太高、日志文件路径对不对 | 阈值定得太高会漏掉真慢的查询；日志文件写满了也会停 |
| 从库延迟越来越大 | 看从库复制状态、主库写量、从库机器负载 | 主库写量突然变大、从库机器变慢、大事务堵住重放，都会让延迟涨上去；先找到变慢的那一环 |
| 从库复制停了 | 看复制状态里的最后一次错误 | 主键冲突、表结构不一致、权限不足都会停复制，先修错误原因，再决定跳过还是重做从库 |
| 故障转移后应用还在写旧主库 | 看应用的写地址配置、代理配置、DNS 缓存 | 写地址没改过来，或者改了但缓存还没过期，先确认写流量到底落到了哪台机器 |

## 17. 安全注意事项

1. 凭据文件权限必须是 600，属主必须是跑备份的账号，权限太松会被 MySQL 拒绝读取，也会被无关账号读到口令。
2. 备份脚本权限是 700，备份目录只允许运维账号读写，备份文件本身就是生产数据的完整拷贝，泄露备份等于泄露数据库。
3. 备份专用账号只给备份所需的最小权限，不要给它删库、改结构的权限，备份账号被盗时损失才可控。
4. 恢复演练用的测试库，用完要清掉里面的生产数据，解压后的 SQL 明文文件也要删掉，不能长期留在临时目录。
5. 备份文件传到异地时要走加密通道，落盘后按需加密存放，传输和存放两个环节都要想，不要只想一个。
6. 故障转移的自动切换，必须先想好 fencing：确认旧主库真的不能写了，再让新主库接管；没有把握时手动切换，见第 7.3 节。
7. 慢日志和 Binlog 里都可能出现业务数据，日志文件的权限和保留期要和备份文件一样对待，不要随手公开。

## 18. 回滚和恢复

### 18.1 红线

没演练过的备份等于没有备份。这句话不是口号，是本章的验收标准：恢复演练没通过的备份，在故障真正发生时不能指望它。每月至少演练一次，大版本升级、换机器、改备份脚本之后，都要再演练一次。

### 18.2 迁移的回滚

迁移文件 `0001_add_summary_to_articles.sql` 的回滚语句，和迁移文件放在同一个目录，文件名带上 `rollback` 字样：

```sql
ALTER TABLE articles DROP COLUMN summary;
```

回滚的规矩和迁移一样：先在测试库上执行，确认应用在没有这个字段时还能跑，再在生产库上执行；回滚前同样先做一份全量备份。删字段会丢掉这个字段里已有的数据，执行前确认这个字段里的数据是不是真的可以丢，不能丢就先导出再删。

### 18.3 恢复的回滚

恢复演练本身不需要回滚，因为它只在测试库上做。但生产恢复有两种情况要分清：

- 误删了数据：用全量备份加 Binlog 恢复到误删之前的时间点，恢复到新库，核对无误后再切流量，不要直接往生产库里倒；
- 迁移执行错了：先停写，再用迁移前的全量备份恢复到新库，核对无误后再切流量，旧库保留到确认无误之后再清理。

### 18.4 主从切换的回滚

手动切换练错了，或者新主库接管后发现问题，回滚办法是：停写、确认各库的数据状态、选数据最新的那台重新提升、改回应用写地址、逐项核对。切换前记下各库的复制位置和延迟，切换后核对一遍，这是回滚时唯一的依据，切换前没记，事后就说不清了。
