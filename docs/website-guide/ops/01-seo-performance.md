## 6. 技术原理

### 6.1 搜索引擎的三步：抓取、索引、排名

1. **抓取（Crawl）**：搜索引擎派爬虫顺着链接一个个访问页面。爬虫能走到哪里，取决于内链结构与 `robots.txt` 有没有挡路，也取决于服务器响应速度——响应太慢，爬虫一次抓得就少。
2. **索引（Index）**：爬虫把页面内容存进索引库，并判断这个页面值不值得收录。重复内容、空页面、被 `noindex` 标记的页面，可能抓到了也不收录。
3. **排名（Rank）**：用户搜索时，搜索引擎从索引里挑出相关的页面排出来。排名取决于内容相关性、页面质量、加载体验等几百个因素，站长能控制的是内容与体验，控制不了的是算法本身与竞争对手。

一句话结论：SEO 不是“做一次就排第一”的操作，而是让爬虫顺畅地发现、理解、收录你的页面，剩下的交给内容与时间。

### 6.2 一次页面加载的时间花在哪里

| 阶段 | 含义 | 慢的常见原因 |
|---|---|---|
| DNS 解析 | 把域名变成 IP | DNS 服务商慢、TTL 过大导致换记录生效慢 |
| 建立连接 | TCP + TLS 握手 | 服务器离访客太远、TLS 配置不当 |
| 服务器响应（TTFB） | 从发出请求到收到第一个字节 | 后端慢、数据库慢、没开缓存 |
| 下载资源 | HTML、CSS、JS、图片、字体 | 文件太大、没压缩、没用 CDN |
| 渲染 | 浏览器解析、布局、绘制 | CSS/JS 阻塞渲染、图片没定尺寸导致布局跳动 |

优化顺序就是按这个表从大到小找：先看哪一段最长，再动那一段。不要一上来就折腾最小的那一段。

### 6.3 关键渲染路径：浏览器先画什么

浏览器拿到 HTML 后，先解析出 DOM，再解析 CSS 得到 CSSOM，两者合起来算出布局、画出页面。CSS 会阻塞渲染（没拿到 CSS，浏览器不知道怎么画），JS 如果放在 `head` 里没加 `defer` 也会阻塞解析。所以性能优化的第一原则是：**首屏需要的 CSS/JS 尽快给，不需要的往后放**。图片、字体、第三方脚本，默认都不该挡住首屏。

### 6.4 缓存的三层

| 层 | 在哪里 | 失效靠什么 |
|---|---|---|
| 浏览器缓存 | 访客自己的浏览器 | `Cache-Control` 与 `Expires`，以及文件名带哈希 |
| CDN 缓存 | 离访客最近的边缘节点 | CDN 的缓存规则与主动刷新 |
| 服务器端缓存 | 源站（页面缓存、对象缓存） | 应用自己的失效逻辑 |

三层的关系是：浏览器缓存命中了，就不发请求；没命中才到 CDN；CDN 没命中才回源站。缓存时间越长，重复访问越快，但更新越慢——所以 HTML 一般缓存时间短（甚至不缓存），带哈希文件名的 CSS/JS/图片可以缓存很久（文件名变了就是新文件，不怕旧缓存）。

### 6.5 图片为什么总是最大的那一块

一张没处理过的照片经常是几 MB，而整个 HTML 可能只有几十 KB。图片体积由四个因素决定：格式、尺寸、压缩率、数量。优化图片就是在这四个因素上做取舍：格式选对（照片用有损压缩格式、图标用矢量或无损格式）、尺寸按显示尺寸给（不要用 4000px 的图显示 400px 的框）、压缩率适中（肉眼看不出差别即可）、数量上懒加载（首屏之外的图片等滚到再加载）。

## 7. 架构说明

### 7.1 访客、CDN、源站、搜索引擎四者的关系

| 角色 | 做什么 | 与本篇的关系 |
|---|---|---|
| 访客浏览器 | 打开页面、存浏览器缓存 | 缓存策略的最终受益者 |
| CDN 边缘节点 | 就近返回静态资源、回源取新内容 | CDN 缓存规则与刷新 |
| 源站（Nginx + 应用） | 生成 HTML、返回静态文件、发缓存头 | Nginx 缓存与压缩配置的落点 |
| 搜索引擎爬虫 | 顺着内链抓取、读 sitemap、遵守 robots | 站内 SEO 基础设施的服务对象 |
| 统计工具 | 收页面访问数据、汇总成报表 | 只看核心指标，不追踪个人身份 |

### 7.2 站内 SEO 结构：三样东西缺一不可

1. **内链结构**：首页能点到分类页，分类页能点到文章页，文章页能回到分类与首页；孤岛页面（全站没有任何链接指向它）爬虫很难发现。
2. **`sitemap.xml`**：告诉搜索引擎“本站有哪些页面、最后更新时间是什么时候”，是内链的补充，不是替代——sitemap 里列了但内链没有的页面，权重仍然低。
3. **`robots.txt`**：告诉爬虫“哪些目录不要抓”，只用来挡后台、管理页、搜索结果页这类不需要收录的路径，绝不能用来挡正常内容页（挡了就等于告诉搜索引擎不要收录）。

### 7.3 性能优化的分层

| 层 | 优化手段 | 对应章节 |
|---|---|---|
| 传输层 | 开 gzip / Brotli 压缩、用 CDN、开 HTTP/2 或 HTTP/3 | 第 9.3 节、第 11 节 |
| 缓存层 | 静态资源长缓存、HTML 短缓存、文件名带哈希 | 第 9.4 节、第 11 节 |
| 资源层 | 图片格式与尺寸、懒加载、字体按需加载 | 第 9.5 节、第 10.3 节 |
| 渲染层 | CSS 不阻塞、JS 加 `defer`、图片定宽高防布局跳动 | 第 9.2 节 |

### 7.4 缓存失效的两种办法

- **文件名带哈希**：构建时把 CSS/JS/图片文件名加上内容哈希（如 `main.a1b2c3.css`），内容一变文件名就变，浏览器与 CDN 自然认为是新文件，不用等旧缓存过期。这是最干净的办法，优先用。
- **主动刷新**：改了内容后，在 CDN 后台点“刷新”或调刷新接口，让边缘节点删掉旧缓存。适用于没法改文件名的场景（如 HTML、接口响应）。

### 7.5 统计工具选型：只看核心指标

| 选型维度 | 说明 |
|---|---|
| 部署方式 | 第三方托管（贴一段脚本）或自托管（自己装，如 Umami、Plausible 的自托管版） |
| 隐私合规 | 是否收集个人身份、是否用 Cookie 追踪、是否符合你所在地区的隐私要求 |
| 核心指标 | 访问量（PV/UV）、来源渠道、热门页面、跳出率、平均停留——够用就好，不要贪多 |
| 性能影响 | 统计脚本本身也要轻，不要为了统计拖慢页面 |

选型结论不点名推荐某一家为“最好”，按上面四个维度自己打分；第 17 节讲隐私合规的底线。

## 9. 逐步操作

### 9.1 第一步：理清内链结构

1. 从首页出发，画一张“首页 → 分类页 → 文章页”的链接图，检查有没有孤岛页面；
2. 每个分类页列出该分类的全部文章链接，不要只列最新几篇、其余的靠搜索才能找到；
3. 每篇文章底部加“上一篇 / 下一篇”与“相关文章”链接，让爬虫顺着文章也能走到别的文章；
4. 面包屑导航（首页 > 分类 > 文章）每个内容页都要有，既方便访客，也方便爬虫理解层级。

### 9.2 第二步：补页面渲染层面的性能

1. 把阻塞渲染的 JS 从 `head` 移到 `body` 末尾，或加 `defer` 属性；
2. 首屏关键 CSS 内联或优先加载，非首屏 CSS 延迟加载；
3. 给所有图片写死 `width` 与 `height` 属性，防止图片加载后把页面撑开、布局跳动；
4. 第三方脚本（统计、分享、评论）一律延迟加载，不要让它们挡住首屏。

### 9.3 第三步：开压缩与 CDN

1. 在 Nginx 里开 gzip（第 11 节有完整配置），压缩文本类资源（HTML、CSS、JS、JSON、SVG）；
2. 如果 CDN 已接好，确认静态资源走了 CDN 域名或 CDN 回源正常，HTML 是否走 CDN 按需决定（动态页面一般不走 CDN 缓存）；
3. 用开发者工具确认响应头里有压缩标识（`Content-Encoding: gzip`），没有就是没生效，回去查配置。

### 9.4 第四步：配缓存策略

1. 带哈希文件名的 CSS/JS/图片：缓存 1 年，`immutable`（告诉浏览器这文件永远不变）；
2. 不带哈希的 CSS/JS：缓存 7 天，给更新留出窗口；
3. HTML：缓存 1 天以内，或不缓存，保证内容更新后访客很快能看到；
4. 接口响应（`/api/`）：默认不缓存，需要缓存的接口单独写规则，不要一刀切。

### 9.5 第五步：做图片优化

1. 先量：把页面上所有图片列出来，记下每张的格式、尺寸、大小；
2. 再选格式：照片类用 JPEG / WebP，图标与简单图形用 SVG / PNG，动图先看能不能用视频或 CSS 动画代替；
3. 再改尺寸：按页面实际显示宽度出图，移动端与桌面端显示尺寸不同的，用响应式图片（`srcset`）给两套；
4. 再压缩：用压缩工具压一遍，肉眼看不出差别即可，不要追求极致压缩把图压糊；
5. 最后懒加载：首屏之外的图片加 `loading="lazy"`，等滚到再加载。

### 9.6 第六步：上 sitemap、robots 与统计

1. 生成 `sitemap.xml` 放到网站根目录，格式见第 11 节；
2. 写 `robots.txt` 放到网站根目录，格式见第 11 节，只挡不需要收录的路径；
3. 到搜索引擎后台提交 sitemap，查收录与抓取错误；
4. 贴统计脚本（或装自托管统计），只看第 7.5 节的核心指标；
5. 一周后回来看一次：收录数有没有涨、加载时间有没有降、热门页面是哪些，再决定下一轮改什么。

| 带哈希的 CSS/JS/图片 | 1 年 | `Cache-Control: public, immutable` | 文件名变了就是新文件 |
| 不带哈希的 CSS/JS | 7 天 | `Cache-Control: public` | 等过期，或 CDN 主动刷新 |
| HTML | 1 天以内或不缓存 | `Cache-Control: public` 或 `no-cache` | 改完很快生效 |
| 接口响应 | 默认不缓存 | `Cache-Control: no-store` 或按接口定 | 接口自己控制 |
| 字体文件 | 1 年 | `Cache-Control: public, immutable` | 文件名带哈希 |

## 11. 完整配置文件

### 11.1 Nginx 缓存与压缩配置

存放路径：`/etc/nginx/conf.d/cache-gzip.conf`（Ubuntu/Debian 系，`include` 进主配置或站点配置均可；改之前先备份原配置，见第 18 节）。

```nginx
# 缓存与压缩配置：OPS-01 第 11 节
# 作用：给文本资源开 gzip，给静态资源定缓存时间，给 HTML 短缓存
gzip on;
gzip_vary on;
gzip_proxied any;
gzip_comp_level 6;
gzip_min_length 1024;
gzip_types
    text/plain
    text/css
    application/json
    application/javascript
    text/javascript
    text/xml
    application/xml
    image/svg+xml;

# 带哈希文件名的静态资源：缓存 1 年，immutable
# 注意：这条只适用于文件名带哈希的资源目录，见第 12 节的解释
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

# 不带哈希的 CSS/JS：缓存 7 天
location /stylesheets/ {
    expires 7d;
    add_header Cache-Control "public";
}

location /javascripts/ {
    expires 7d;
    add_header Cache-Control "public";
}

# HTML：短缓存，保证内容更新后访客很快能看到
location / {
    expires 1d;
    add_header Cache-Control "public";
}
```

### 11.2 `robots.txt`

存放路径：网站根目录，即 `https://你的域名/robots.txt` 能打开的位置（例如 Nginx 站点根目录下的 `robots.txt` 文件）。

```text
# robots.txt：OPS-01 第 11 节
# 含义：允许所有爬虫抓取全站，只挡不需要收录的路径
User-agent: *
Allow: /
Disallow: /admin/
Disallow: /search/
Sitemap: https://example.com/sitemap.xml
```

注意：`Sitemap:` 后面的地址要换成你自己的真实域名，不要照抄 `example.com`；`Disallow` 只挡后台、管理、站内搜索结果这类不需要收录的路径，绝不要把正常内容页挡掉。

### 11.3 `sitemap.xml`

存放路径：网站根目录，即 `https://你的域名/sitemap.xml` 能打开的位置。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://example.com/</loc>
    <lastmod>2026-11-03</lastmod>
    <changefreq>daily</changefreq>
    <priority>1.0</priority>
  </url>
  <url>
    <loc>https://example.com/articles/first-post/</loc>
    <lastmod>2026-11-02</lastmod>
    <changefreq>weekly</changefreq>
    <priority>0.8</priority>
  </url>
</urlset>
```

注意：`loc` 里的域名要换成你自己的真实域名；`lastmod` 是该页面最后更新的日期，改了内容就要更新；`changefreq` 与 `priority` 只是给搜索引擎的提示，不是命令，搜索引擎不一定照单全收。

## 12. 每个关键配置项的解释

### 12.1 Nginx 缓存与压缩配置项

| 配置项 | 含义 | 写错的后果 |
|---|---|---|
| `gzip on` | 开启 gzip 压缩 | 不开则文本资源原样传输，体积大 |
| `gzip_vary on` | 响应头里加 `Vary: Accept-Encoding`，告诉缓存“压缩版与未压缩版是两个版本” | 不开则 CDN 可能把压缩版发给不支持压缩的客户端 |
| `gzip_proxied any` | 对经过代理的请求也压缩 | 不开则 CDN 回源的响应可能不压缩 |
| `gzip_comp_level 6` | 压缩级别 1–9，6 是体积与 CPU 的平衡点 | 级别太高省不了多少体积、反而耗 CPU |
| `gzip_min_length 1024` | 小于 1024 字节的文件不压缩（压了也省不了多少，还多一次 CPU） | 设太小则小文件也被压缩，得不偿失 |
| `gzip_types` | 列出要压缩的 MIME 类型 | 漏了 `application/javascript` 则 JS 不压缩；图片、视频不要列进来（已经是压缩格式，再压没用） |
| `expires 1y / 7d / 1d` | 告诉浏览器这份资源缓存多久 | HTML 设 1 年则内容更新后访客长期看旧版 |
| `Cache-Control: public, immutable` | 公共缓存可用，且文件永远不变 | 用在不带哈希的文件上，则更新后访客拿不到新版 |

### 12.2 `robots.txt` 配置项

| 配置项 | 含义 | 写错的后果 |
|---|---|---|
| `User-agent: *` | 规则适用于所有爬虫 | 写成某个爬虫名则别的爬虫不受约束 |
| `Allow: /` | 允许抓取全站 | 与 `Disallow` 冲突时，按“最长匹配”算，不要两边都写 `/` |
| `Disallow: /admin/` | 不抓后台目录 | 把内容目录写进来则内容页不被收录 |
| `Sitemap:` | 告诉爬虫 sitemap 在哪里 | 地址写错则爬虫找不到 sitemap |

### 12.3 `sitemap.xml` 标签

| 标签 | 含义 | 写错的后果 |
|---|---|---|
| `loc` | 页面完整地址，必须是绝对地址 | 写相对地址则搜索引擎认不出来 |
| `lastmod` | 最后更新日期，格式 `YYYY-MM-DD` | 日期写成未来时间或长期不更新，提示就失真了 |
| `changefreq` | 更新频率提示（`daily` / `weekly` / `monthly`） | 只是提示，不是保证，写 `always` 也不会让爬虫天天来 |
| `priority` | 相对重要性，0.0–1.0 | 只是站内相对值，不是全网排名，写 1.0 不会让你排第一 |

## 14. 成功验证

按下面清单逐项验证，全部通过才算本篇做完：

1. Nginx 配置检查通过：`nginx -t` 输出成功，再 `systemctl reload nginx`（或 `nginx -s reload`）重载；
2. 压缩生效：浏览器开发者工具 Network 里，CSS/JS 的响应头有 `Content-Encoding: gzip`，且大小比原来小；
3. 缓存生效：第二次打开同一页面，静态资源的响应是 `from disk cache` 或 `from memory cache`，而不是重新下载；
4. 缓存失效可用：改一个带哈希文件名的资源，文件名变了，浏览器拿到的是新文件；改 HTML 内容，1 天内访客能看到新版；
5. 图片检查：页面上图片按显示尺寸出图，首屏外图片滚到才加载，开发者工具里图片总大小比优化前明显下降（下降多少以你自己的实测为准，不要照抄第 13 节的示例数字）；
6. sitemap 与 robots 可访问：浏览器打开 `https://你的域名/sitemap.xml` 与 `https://你的域名/robots.txt` 都返回 200，且内容与第 11 节一致（域名换成你自己的）；
7. 搜索引擎后台：提交 sitemap 后，后台显示“已发现”或“已提交”，抓取错误列表里没有新增的大面积错误；
8. 统计生效：打开自己站点，统计后台当天能看到这次访问（先排除自己的访问再看趋势，见第 17 节）；
9. 移动端检查：手机模式下首屏内容一屏能看完、没有横向滚动条、图片没有把布局撑开。

## 15. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| HTML 缓存设成 1 年 | 内容更新后访客长期看旧版 | HTML 短缓存，见第 9.4 节 |
| 不带哈希的文件用 `immutable` | 更新后访客拿不到新版 | 只有带哈希的文件名才用 `immutable` |
| 图片没写宽高 | 图片加载后布局跳动，访客体验差、性能指标也差 | 所有图片写死 `width` 与 `height` |
| 用 `robots.txt` 挡正常内容页 | 内容页不被收录，等于白写 | `Disallow` 只挡后台、管理、站内搜索结果页 |
| sitemap 里列了不存在的页面 | 搜索引擎后台报抓取错误，浪费抓取配额 | sitemap 只列真实存在的页面，删了的页面要从 sitemap 里去掉 |
| 统计脚本放 `head` 且不延迟 | 统计脚本拖慢首屏 | 统计脚本延迟加载 |
| 只看总访问量，不看来源与热门页面 | 不知道访客从哪来、看了什么，优化没方向 | 每周看一次来源与热门页面，再决定改什么 |
| 把 `noindex` 写在全站模板里 | 全站不被收录 | `noindex` 只用在确实不需要收录的页面（如后台、感谢页） |

### 15.1 黑帽手法：不要做

下面这些手法 WEB-03 第 5 节已经划过界，本篇再明确写清为什么不要做——因为会被搜索引擎降权或除名，短期看起来有效、长期一定亏：

| 手法 | 是什么 | 为什么不要做 |
|---|---|---|
| 关键词堆砌 | 在页面里反复塞同一个关键词，读起来不像人话 | 搜索引擎能识别，轻则降权、重则除名 |
| 隐藏文字 | 把文字颜色设成与背景一样，或藏在看不见的元素里 | 属于欺骗爬虫，查到就处罚 |
| Cloaking（障眼法） | 给爬虫看一套内容、给访客看另一套 | 直接违反搜索引擎规则，处罚最重的一类 |
| 买外链 | 花钱买大量低质量外链，想抬权重 | 外链质量会被识别，买来的外链可能连坐降权 |
| Doorway 页（门页） | 做一堆只为排名、没有实际内容的页面，再跳转到目标页 | 被识别为 doorway 页后整站受牵连 |

效果承诺的红线：不要承诺任何排名效果、流量数字、收录时间。凡是效果类表述，一律写“取决于内容与搜索引擎，无法保证”——本篇全文没有一处承诺排名、流量、收录时间，读者也不要在自己的运营计划里写这种承诺。

## 16. 故障排查

| 现象 | 可能原因 | 排查步骤 |
|---|---|---|
| 改了 CSS/JS，访客还是旧版 | 浏览器或 CDN 缓存没失效 | 先确认文件名有没有带哈希；没带哈希的，等过期或去 CDN 后台主动刷新；再让访客硬刷新（`Ctrl + F5`）验证 |
| 开了 gzip 但响应头没有 `Content-Encoding` | `gzip_types` 漏了该类型，或文件小于 `gzip_min_length` | 对照第 12.1 节逐项核对，先看类型、再看大小 |
| sitemap 提交后后台报“无法获取” | sitemap 地址不对、返回不是 200、格式错误 | 浏览器直接打开 sitemap 地址，看状态码与内容；用 XML 校验工具过一遍格式 |
| 收录数长期不涨 | 内链有孤岛、robots 挡了路、内容重复 | 先查 robots 有没有误挡，再查孤岛页面，最后看内容是不是大量重复 |
| 图片压完变糊 | 压缩率太高，或尺寸改得太小 | 压缩率往回放一档，尺寸按显示尺寸出图，不要压到显示尺寸以下 |
| 统计后台看不到访问 | 脚本没贴对位置、被广告拦截插件挡了、统计服务本身故障 | 先看页面源码里有没有统计脚本，再换个没装拦截插件的浏览器打开验证 |
| 移动端加载比桌面端慢很多 | 移动端与桌面端用了同一套大图 | 按第 9.5 节做响应式图片，移动端给小尺寸图 |

## 17. 安全注意事项

1. **统计与隐私**：统计工具不要收集访客的姓名、手机号、精确位置等个人身份信息；如果用了 Cookie 追踪，要按你所在地区的隐私要求做告知与同意；自己的访问要先排除，否则趋势全是自己的数据。
2. **`robots.txt` 不是权限控制**：`robots.txt` 只能告诉守规矩的爬虫“请不要抓”，挡不住恶意爬虫，更挡不住人。真正不想公开的页面（后台、管理、内网）要用登录鉴权挡，不要只靠 `robots.txt`。
3. **统计后台不要公开**：统计报表里有访问来源、热门页面、访客地域，不要把统计后台的链接或截图公开贴出来。
4. **第三方脚本要节制**：每多一个第三方脚本，就多一个拖慢页面与泄露数据的口子。统计、分享、评论脚本，能少用就少用，用之前先看它的数据收集说明。
5. **缓存不要缓存私密内容**：登录后的页面、含个人信息的接口响应，绝不要进公共缓存（CDN 与浏览器共享缓存），否则 A 访客可能看到 B 访客的内容。

## 18. 回滚和恢复

动手之前先备份，改坏了按下面步骤往回退：

1. **备份 Nginx 配置**：改之前先复制一份，例如 `cp /etc/nginx/conf.d/cache-gzip.conf /etc/nginx/conf.d/cache-gzip.conf.bak`，改坏了把备份文件拷回来，再 `nginx -t` 通过后重载；
2. **缓存策略回滚**：把 `expires` 与 `Cache-Control` 改回原来的值（或删掉新增的 location 块），重载后访客下一次访问就按新策略来；已经发出去的长缓存要等过期，或去 CDN 后台主动刷新；
3. **图片回滚**：原图不要删，优化后的图另外存一份，效果不好就把原图换回来；懒加载出问题就先去掉 `loading="lazy"`，恢复立即加载；
4. **sitemap / robots 回滚**：改错了直接把旧文件拷回根目录，搜索引擎下一次抓取就会读到旧版；robots 误挡内容页时，改回后要在后台请求重新抓取；
5. **统计回滚**：统计脚本出问题就先从页面里去掉，页面本身不受影响，统计数据断几天不影响站点运行。
