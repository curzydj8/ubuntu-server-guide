## 6. 技术原理

Go 写 Web 服务的模型只有四步，所有框架都在这四步上做加法：

1. **监听**：程序监听一个端口（例如 8080），等浏览器或 `curl` 把请求送过来；
2. **路由**：按请求的方法（GET、POST、PUT、DELETE）与路径（例如 `/tasks/3`），找到对应的处理器函数；
3. **中间件**：请求在到达处理器之前、响应在返回之前，会依次穿过一串中间件：记日志、恢复 panic、鉴权、跨域处理都放在这里；
4. **处理器**：处理器读请求（路径参数、查询参数、JSON 体），做业务逻辑，写响应（JSON、HTML、状态码）。

标准库 `net/http` 已经把这四步都给了：`http.Server` 负责监听，`http.ServeMux` 负责路由，中间件就是“接收一个处理器、返回一个处理器”的普通函数。框架补的东西主要是三样：更好写的路由（路径参数、分组、简写）、更顺手的上下文（一个对象上同时有请求、响应、绑定、渲染方法）、成套的中间件与错误处理。框架没有改变 Go 的并发模型：每个请求仍由一个 goroutine 处理，共享数据必须自己加锁，本文实战的内存存储就是用 `sync.RWMutex` 保护的。

一个容易误解的点：框架快不快，主要取决于你的处理器做了什么（查几次库、算多少东西），而不是框架本身的名字。不要在还没写业务逻辑时就先为“哪个框架更快”纠结，选型对照在第 9 节最后给出。

## 7. 架构说明

一个 Go Web 服务通常分四层，从外到内是：

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 接入层（Nginx / 负载均衡） | 对外收请求、TLS、静态文件、反向代理 | 业务逻辑 |
| 路由与中间件层（框架或 ServeMux） | 按方法与路径分发、日志、恢复、鉴权 | 业务规则 |
| 处理器与服务层 | 参数校验、调用服务、组装响应 | 直接拼 SQL（应交给数据层） |
| 数据层 | 读写数据库、缓存、外部接口 | HTTP 细节（不应知道请求长什么样） |

本文实战的部署拓扑（单服务器，学习阶段够用）：

```text
浏览器 / curl
    |
    v
Nginx（80 端口，对外）
    |
    v
Go 服务（127.0.0.1:8080，systemd 托管）
    |
    +-- 内存任务存储（实战阶段）
    +-- PostgreSQL（接数据库阶段，见第 9.5 节）
```

请求在服务内部的流向（以 `POST /api/tasks` 为例）：

```text
请求 -> 路由匹配 -> 日志中间件 -> 鉴权中间件 -> 处理器
  -> 绑定并校验 JSON -> 服务层写入存储 -> 统一 JSON 响应
```

### 9.1 Gin：介绍与第一个项目

**介绍。** Gin 是 Go 生态用得最广的 Web 框架之一，基于 httprouter 的路由，特点是上手快、文档与例子多、中间件生态全。它的上下文 `*gin.Context` 把请求、响应、参数绑定、JSON 渲染都集中在一个对象上，写接口时很少需要自己碰 `http.ResponseWriter`。

**同类对比（先给结论，详细对照见 9.6 节）。** Gin 与 Echo 同属“基于标准库 net/http、加一层顺手封装”的路线，两者互相迁移的成本不高；Fiber 走 fasthttp 路线，性能取向更激进，但与标准库的互通性要差一截；标准库则是什么都不加，自由度最高、样板代码最多。

**安装与第一个项目。** 在家目录下建项目目录并初始化模块（以下命令都在 `~/go-projects/ginhello` 目录、以普通用户执行）：

```bash
mkdir -p ~/go-projects/ginhello
cd ~/go-projects/ginhello
go mod init example.com/ginhello
go get github.com/gin-gonic/gin@v1.12.0
```

目录结构（最小项目只有一个文件，文件多了再拆包）：

```text
ginhello/
  go.mod
  go.sum
  main.go
```

`main.go`（完整文件，复制后可直接用）：

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

type user struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func main() {
	r := gin.Default()
	r.GET("/ping", func(c *gin.Context) {
		c.JSON(http.StatusOK, gin.H{"message": "pong"})
	})
	r.GET("/users/:id", func(c *gin.Context) {
		c.JSON(http.StatusOK, user{ID: 1, Name: "示例用户"})
	})
	r.POST("/users", func(c *gin.Context) {
		var in user
		if err := c.ShouldBindJSON(&in); err != nil {
			c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
			return
		}
		in.ID = 2
		c.JSON(http.StatusCreated, in)
	})
	r.Run(":8080")
}
```

**核心语法与 API（Gin）。** `gin.Default()` 自带日志与恢复中间件，`gin.New()` 则是什么都不带，需要的中间件自己用 `r.Use()` 加。路由写法：`r.GET`、`r.POST`、`r.PUT`、`r.DELETE`；路径参数用冒号，例如 `/users/:id`，处理器里用 `c.Param("id")` 取；查询参数用 `c.Query("page")`；JSON 绑定用 `c.ShouldBindJSON(&in)`，绑定失败会返回错误，处理器要自己决定返回 400。响应写法：`c.JSON(状态码, 对象)`；`gin.H` 就是 `map[string]any` 的别名，适合拼简单的响应。路由分组用 `r.Group("/api")`，分组上加的中间件只对组内路由生效。

**页面编写（Gin）。** Gin 也能渲染 HTML 页面，适合“接口 + 少量页面”的项目。先放一个模板文件 `templates/hello.html`，再在 main 函数里加载它（下面是片段，接在 `r := gin.Default()` 之后，不是完整文件）：

```go
	r.LoadHTMLGlob("templates/*")
	r.GET("/hello", func(c *gin.Context) {
		c.HTML(http.StatusOK, "hello.html", gin.H{"name": "示例用户"})
	})
```

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
<meta charset="utf-8">
<title>问候</title>
</head>
<body>
<h1>你好，{{ .name }}</h1>
</body>
</html>
```

模板里的 `{{ .name }}` 会被换成传进来的 `name`。纯 API 项目不需要模板，直接返回 JSON 即可，不要为了“完整”硬加页面。

**中间件（Gin）。** 中间件就是 `func(c *gin.Context)`，里面调 `c.Next()` 表示放行到下一个中间件或处理器，不调 `c.Next()` 并直接写响应就是拦截（鉴权失败时常用）。全局中间件用 `r.Use()`，分组中间件用 `group.Use()`，单个路由也可以在处理器前面再挂中间件。`gin.Recovery()` 会在处理器 panic 时恢复并返回 500，生产服务不要去掉它。

**数据与状态、错误处理（Gin）。** Gin 本身不带数据库层，数据读写按第 7 节的分层放到服务层与数据层，处理器里不要直接拼 SQL。错误处理用统一格式：成功返回业务对象，失败返回 `{"error": "原因"}` 并配上合适的状态码（参数错 400、找不到 404、没权限 401 或 403、服务器错 500），不要把 Go 的原始错误堆栈直接吐给客户端。

**性能与安全、构建发布、Ubuntu 部署要点（Gin）。** 性能上先保证处理器不做无谓的重复查询与大对象拷贝，再谈框架；安全上注意四点：不要在响应里回显原始错误、不要把密钥写进代码（放环境变量）、JSON 绑定要设字段校验（例如必填用 `binding:"required"`）、对外服务前面放 Nginx 做 TLS 与限流。构建用 `go build -o taskapi .`，部署见第 11 节的 systemd 与 Nginx 配置。

### 9.2 Echo：介绍与第一个项目

**介绍。** Echo 是另一个基于标准库 net/http 的轻量框架，特点是自带的功能比较全：绑定、校验、中间件、集中错误处理都是一套的，写起来比较规整。v5 是当前主线，写代码前先确认 `go.mod` 里是 `echo/v5`。

**安装与第一个项目。** 在 `~/go-projects/echohello` 目录、以普通用户执行：

```bash
mkdir -p ~/go-projects/echohello
cd ~/go-projects/echohello
go mod init example.com/echohello
go get github.com/labstack/echo/v5@v5.4.1
```

如果 `v5.4.1` 这个补丁号在安装时已经不是最新，把它换成官网 Releases 当场公布的 v5 补丁号，命令结构不变。目录结构与 Gin 的最小项目相同：`go.mod`、`go.sum`、`main.go`。

`main.go`（完整文件，v5 写法，注意处理器签名是 `*echo.Context`）：

```go
package main

import (
	"log"
	"net/http"

	"github.com/labstack/echo/v5"
	"github.com/labstack/echo/v5/middleware"
)

type user struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func main() {
	e := echo.New()
	e.Use(middleware.Logger())
	e.Use(middleware.Recover())
	e.GET("/ping", func(c *echo.Context) error {
		return c.JSON(http.StatusOK, map[string]string{"message": "pong"})
	})
	e.GET("/users/:id", func(c *echo.Context) error {
		return c.JSON(http.StatusOK, user{ID: 1, Name: "示例用户"})
	})
	e.POST("/users", func(c *echo.Context) error {
		var in user
		if err := c.Bind(&in); err != nil {
			return c.JSON(http.StatusBadRequest, map[string]string{"error": err.Error()})
		}
		in.ID = 2
		return c.JSON(http.StatusCreated, in)
	})
	srv := &http.Server{Addr: ":8080", Handler: e}
	log.Fatal(srv.ListenAndServe())
}
```

**核心语法与 API（Echo）。** 处理器返回 `error`，返回非空错误时由 Echo 的集中错误处理器统一转成响应，这是 Echo 与 Gin 最大的写法差异：Gin 是在处理器里自己写错误响应，Echo 是把错误“交上去”。路由写法与 Gin 类似：`e.GET`、`e.POST`，路径参数同样用冒号，取参用 `c.Param("id")`；绑定用 `c.Bind(&in)`，它会按 Content-Type 自动选 JSON 或表单绑定；校验需要另外接校验器（Echo 不内置校验规则，常用 `go-playground/validator`，在 `e.Validator` 上挂接）。

**中间件、数据与状态、错误处理（Echo）。** 中间件在 `middleware` 包里：`middleware.Logger()`、`middleware.Recover()`、`middleware.CORS()`、`middleware.RateLimiter()` 都是现成的，用 `e.Use()` 挂全局。数据层与错误格式的原则与 Gin 一节相同：处理器不直接拼 SQL，错误响应统一格式，不要回显原始错误堆栈。集中错误处理可以自定义 `e.HTTPErrorHandler`，把 404、405、500 的响应体统一成项目自己的格式。

**性能与安全、构建发布、Ubuntu 部署要点（Echo）。** 与 Gin 相同：构建用 `go build`，部署用 systemd + Nginx；安全上多注意一点：Echo 的静态文件中间件与代理中间件在 2026 年 10 月曝过几处鉴权与路径绕过问题（见第 19 节延伸阅读），所以 Echo 项目要格外注意保持补丁号最新，不要长期停在旧补丁上。

### 9.3 Fiber：介绍与第一个项目

**介绍。** Fiber 是仿 Express 风格的框架，底层用 fasthttp 而不是标准库 net/http，特点是接口风格对写过 Node.js 的读者很亲切，内置中间件多。代价是与标准库的互通性较差：标准库的处理器与中间件不能直接插到 Fiber 里，需要经过适配中间件转换；需要用到标准库生态（例如某些只提供 `http.Handler` 的库）时要先确认有没有 Fiber 的适配写法。

**安装与第一个项目。** 在 `~/go-projects/fiberhello` 目录、以普通用户执行，要求 Go 1.26 以上：

```bash
mkdir -p ~/go-projects/fiberhello
cd ~/go-projects/fiberhello
go mod init example.com/fiberhello
go get github.com/gofiber/fiber/v3@v3.6.1
```

如果 `v3.6.1` 在安装时已经不是最新，换成官网 Releases 当场公布的 v3 补丁号。目录结构同样是 `go.mod`、`go.sum`、`main.go`。

`main.go`（完整文件，v3 写法）：

```go
package main

import (
	"github.com/gofiber/fiber/v3"
	"github.com/gofiber/fiber/v3/middleware/logger"
)

type user struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func main() {
	app := fiber.New()
	app.Use(logger.New())
	app.Get("/ping", func(c fiber.Ctx) error {
		return c.JSON(fiber.Map{"message": "pong"})
	})
	app.Get("/users/:id", func(c fiber.Ctx) error {
		return c.JSON(user{ID: 1, Name: "示例用户"})
	})
	app.Post("/users", func(c fiber.Ctx) error {
		var in user
		if err := c.BodyParser(&in); err != nil {
			return c.Status(fiber.StatusBadRequest).JSON(fiber.Map{"error": err.Error()})
		}
		in.ID = 2
		return c.Status(fiber.StatusCreated).JSON(in)
	})
	if err := app.Listen(":8080"); err != nil {
		panic(err)
	}
}
```

**核心语法与 API（Fiber）。** 处理器签名是 `func(c fiber.Ctx) error`，`fiber.Ctx` 是接口；路由方法名是首字母大写：`app.Get`、`app.Post`、`app.Put`、`app.Delete`；路径参数用冒号，取参用 `c.Params("id")`；查询参数用 `c.Query("page")`；请求体解析用 `c.BodyParser(&in)`（v3 也提供了 `c.Bind().JSON(&in)` 的新写法，老项目升级时按迁移指南换）。响应写法：`c.JSON(对象)` 默认 200，需要其他状态码时先调 `c.Status(状态码)` 再调 `c.JSON`。

**中间件、数据与状态、错误处理（Fiber）。** 中间件在 `fiber/v3/middleware` 下面：`logger`、`recover`、`cors`、`limiter`、`csrf` 都有现成的。数据层与错误格式的原则与前面两节相同。要注意 Fiber 的上下文对象来自对象池：处理器返回后不要再持有 `fiber.Ctx` 去别的 goroutine 里用，需要跨 goroutine 传数据时先把值拷出来。

**性能与安全、构建发布、Ubuntu 部署要点（Fiber）。** 构建与部署与前面相同。安全上注意：Fiber 的 v2 与 v3 是两条线，旧项目升级要用官方迁移工具 `fiber migrate --to v3`，不要手工把 `v2` 字样批量替换成 `v3`；另外 2026 年公开的 Fiber 安全公告里有闪存 Cookie 与超多路由参数导致的拒绝服务问题（见第 19 节），保持补丁号最新是必须的。

### 9.4 标准库：介绍与第一个项目

**介绍。** 标准库 `net/http` 不需要装任何第三方依赖，Go 1.22 起的 `ServeMux` 已经支持“方法 + 路径”模式与路径通配，写中小型服务完全够用。它的代价是样板代码多：绑定、校验、统一错误格式、日志格式都要自己写几行。

**安装与第一个项目。** 不需要 `go get`，只要建目录并初始化模块（在 `~/go-projects/stdhello` 目录、以普通用户执行）：

```bash
mkdir -p ~/go-projects/stdhello
cd ~/go-projects/stdhello
go mod init example.com/stdhello
```

`main.go`（完整文件，Go 1.22 以上写法）：

```go
package main

import (
	"encoding/json"
	"log"
	"net/http"
)

type user struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func ping(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]string{"message": "pong"})
}

func getUser(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]string{"id": id, "name": "示例用户"})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /ping", ping)
	mux.HandleFunc("GET /users/{id}", getUser)
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

**核心语法与 API（标准库）。** 路由注册用 `mux.HandleFunc("方法 路径", 处理器)`，例如 `"GET /users/{id}"`；路径里的 `{id}` 用 `r.PathValue("id")` 取；查询参数用 `r.URL.Query().Get("page")`；读 JSON 体用 `json.NewDecoder(r.Body).Decode(&in)`，写 JSON 用 `json.NewEncoder(w).Encode(对象)`，写之前先设 `Content-Type: application/json`。中间件就是普通函数：接收一个 `http.Handler`，返回一个包了一层逻辑的 `http.Handler`，例如先记日志再调 `next.ServeHTTP(w, r)`。页面编写用 `html/template` 包，它默认对插值做转义，比直接拼字符串安全。

**数据与状态、错误处理（标准库）。** 与框架方向完全相同的原则：处理器不直接拼 SQL，错误响应统一成 `{"error": "原因"}`。标准库没有集中错误处理器，统一格式要靠自己写一个小的响应辅助函数，所有处理器都走它，不要每个处理器各写一套。

**性能与安全、构建发布、Ubuntu 部署要点（标准库）。** 构建与部署与框架方向相同。标准库的优势是依赖为零、升级风险最小；劣势是路由、绑定、校验都要自己写，项目一大就容易各处写法不一致，需要团队自己定一套规范并坚持。

### 9.5 数据与状态：从内存存储接真实数据库

实战阶段用内存存储即可，结构就是一个带读写锁的 map（完整代码见第 10 节）。要接真实数据库时，改动只发生在数据层：

1. 选驱动：PostgreSQL 用 `pgx`，MySQL 用 `go-sql-driver/mysql`，SQLite 用 `modernc.org/sqlite`（纯 Go，不需要 C 编译器）；
2. 连接串不要写进代码：放环境变量或配置文件，口令用占位符表示，真实口令只存在服务器的 env 文件里（见第 11 节）；
3. 服务层不感知数据库换没换：存储接口保持“按 ID 查、列出、新增、更新、删除”这五个方法，内存实现与数据库实现互换时处理器不用改；
4. 上线前必须做的三件事：连接池上限（别用默认无限）、查询超时（`context.WithTimeout`）、慢查询日志。

### 9.6 选型对照：什么时候直接用标准库就够了

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| 只有两三个接口的内部工具、健康检查、Webhook 接收 | 标准库 | 依赖为零，写完即走，升级没有负担 |
| 常规业务接口（增删改查 + 鉴权 + 分页），团队第一次用 Go | Gin | 例子最多，遇到问题最容易搜到解法 |
| 想要一套规整的绑定、校验、集中错误处理 | Echo v5 | 错误“交上去”的写法让处理器更干净；但要先定好主线 v5 |
| 写过 Express、追求内置中间件齐全、接口量大 | Fiber v3 | 风格亲切；但要接受与标准库互通性差、上下文不能跨 goroutine 持有 |
| 极端追求吞吐、且团队能接受 fasthttp 生态 | Fiber v3 | fasthttp 路线在纯转发与简单接口上占优；业务一复杂，优势会被数据库与业务逻辑吃掉 |

一句话结论：先按“接口数量、团队经验、要不要标准库生态”三条选，选完就不要来回换。框架之间的迁移成本主要不在路由写法，而在中间件、错误处理、上下文用法这些细节上，换一次就要把测试全跑一遍。

## 10. 完整代码：Gin 任务清单接口

本节以 Gin 方向做一个完整的小应用：任务清单接口，含增删改查、日志与请求 ID 中间件、API 密钥鉴权中间件、统一错误格式、优雅停机。文件全部放在项目根目录 `~/go-projects/taskapi`，先初始化模块并安装 Gin（以下命令都在该目录、以普通用户执行）：

```bash

cd ~/go-projects/taskapi
go mod init example.com/taskapi
go get github.com/gin-gonic/gin@v1.12.0
```

目录结构：

```text
taskapi/
  go.mod
  go.sum
  main.go
  config.yaml
```

`main.go`（完整文件，复制后可直接用；数据库接法见 9.5 节，本节先用内存存储）：

```go
package main

import (
	"context"
	"errors"
	"log"
	"net/http"
	"os"
	"os/signal"
	"strconv"
	"sync"
	"syscall"
	"time"

	"github.com/gin-gonic/gin"
)

type task struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
	Done  bool   `json:"done"`
}

type taskInput struct {
	Title string `json:"title" binding:"required"`
	Done  bool   `json:"done"`
}

var errNotFound = errors.New("task not found")

type store struct {
	mu    sync.RWMutex
	items map[int]task
	next  int
}

func newStore() *store {
	return &store{items: make(map[int]task), next: 1}
}

func (s *store) list() []task {
	s.mu.RLock()
	defer s.mu.RUnlock()
	out := make([]task, 0, len(s.items))
	for _, t := range s.items {
		out = append(out, t)
	}
	return out
}

func (s *store) create(in taskInput) task {
	s.mu.Lock()
	defer s.mu.Unlock()
	t := task{ID: s.next, Title: in.Title, Done: in.Done}
	s.items[t.ID] = t
	s.next++
	return t
}

func (s *store) get(id int) (task, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	t, ok := s.items[id]
	if !ok {
		return task{}, errNotFound
	}
	return t, nil
}

func (s *store) update(id int, in taskInput) (task, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if _, ok := s.items[id]; !ok {
		return task{}, errNotFound
	}
	t := task{ID: id, Title: in.Title, Done: in.Done}
	s.items[id] = t
	return t, nil
}

func (s *store) delete(id int) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if _, ok := s.items[id]; !ok {
		return errNotFound
	}
	delete(s.items, id)
	return nil
}

func requestID(c *gin.Context) {
	id := strconv.FormatInt(time.Now().UnixNano(), 10)
	c.Set("request_id", id)
	c.Header("X-Request-ID", id)
	c.Next()
}

func apiKeyAuth(c *gin.Context) {
	expected := os.Getenv("API_KEY")
	if expected == "" {
		c.Next()
		return
	}
	if c.GetHeader("X-API-Key") != expected {
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "unauthorized"})
		return
	}
	c.Next()
}

func parseID(c *gin.Context) (int, bool) {
	id, err := strconv.Atoi(c.Param("id"))
	if err != nil {
		c.JSON(http.StatusBadRequest, gin.H{"error": "invalid id"})
		return 0, false
	}
	return id, true
}

func main() {
	s := newStore()
	r := gin.New()
	r.Use(gin.Recovery(), requestID)
	r.GET("/healthz", func(c *gin.Context) {
		c.JSON(http.StatusOK, gin.H{"status": "ok"})
	})
	api := r.Group("/api")
	api.Use(apiKeyAuth)
	api.GET("/tasks", func(c *gin.Context) {
		c.JSON(http.StatusOK, s.list())
	})
	api.POST("/tasks", func(c *gin.Context) {
		var in taskInput
		if err := c.ShouldBindJSON(&in); err != nil {
			c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
			return
		}
		c.JSON(http.StatusCreated, s.create(in))
	})
	api.GET("/tasks/:id", func(c *gin.Context) {
		id, ok := parseID(c)
		if !ok {
			return
		}
		t, err := s.get(id)
		if err != nil {
			c.JSON(http.StatusNotFound, gin.H{"error": "task not found"})
			return
		}
		c.JSON(http.StatusOK, t)
	})
	api.PUT("/tasks/:id", func(c *gin.Context) {
		id, ok := parseID(c)
		if !ok {
			return
		}
		var in taskInput
		if err := c.ShouldBindJSON(&in); err != nil {
			c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
			return
		}
		t, err := s.update(id, in)
		if err != nil {
			c.JSON(http.StatusNotFound, gin.H{"error": "task not found"})
			return
		}
		c.JSON(http.StatusOK, t)
	})
	api.DELETE("/tasks/:id", func(c *gin.Context) {
		id, ok := parseID(c)
		if !ok {
			return
		}
		if err := s.delete(id); err != nil {
			c.JSON(http.StatusNotFound, gin.H{"error": "task not found"})
			return
		}
		c.Status(http.StatusNoContent)
	})
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	srv := &http.Server{
		Addr:              ":" + port,
		Handler:           r,
		ReadHeaderTimeout: 5 * time.Second,
	}
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()
	go func() {
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Fatalf("listen: %v", err)
		}
	}()
	<-ctx.Done()
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Fatalf("shutdown: %v", err)
	}
	log.Println("server stopped")
}
```

关于上面代码的四点说明：

1. `API_KEY` 为空时鉴权中间件直接放行，这是开发阶段的省事写法，上线前必须在 env 文件里把它设成随机长串（见第 11 节），否则接口等于没锁；
2. 内存存储重启就丢数据，这是学习阶段的取舍，不是生产方案；接数据库按 9.5 节只改数据层；
3. `list` 返回的任务顺序是不固定的（map 遍历顺序随机），需要稳定顺序时在返回前按 ID 排一次序；
4. `parseID` 里已经写过错误响应，调用处用 `if !ok { return }` 直接返回，不要再写一次响应，否则 Gin 会报重复写响应。

## 12. 每个关键配置项的解释

| 配置项 | 位置 | 含义与注意事项 |
| --- | --- | --- |
| `go 1.27` | go.mod | 模块声明的语言版本；低于它的工具链会拒绝构建，高于它的工具链按声明版本约束语言特性 |
| `require gin v1.12.0` | go.mod | 锁定的 Gin 版本；升级前先看 Releases 的破坏性变更说明，不要直接改数字就构建 |
| `PORT` | 环境变量 / env 文件 | 服务监听端口；Nginx 的 `proxy_pass` 必须指向同一个端口 |
| `API_KEY` | env 文件 | 鉴权中间件比对的密钥；为空时中间件放行，只许开发阶段为空 |
| `ReadHeaderTimeout: 5s` | main.go 的 Server | 读请求头超时，防慢速连接占着连接池；不要设成 0（0 表示不限时） |
| `Restart=on-failure` | systemd | 进程异常退出后自动重启；正常停机（优雅停机）不会触发重启 |
| `NoNewPrivileges=true` | systemd | 禁止服务进程提权，提权类攻击打进来也升不上去 |
| `proxy_set_header X-Forwarded-Proto` | Nginx | 把原始协议（http/https）透传给 Go 服务，服务拼回调地址时才不会把 https 写成 http |
| `CGO_ENABLED=0` | Dockerfile | 纯静态编译，二进制拷到 slim 镜像里能直接跑，不依赖宿主的 C 库 |

## 15. 常见错误

| 现象 | 原因 | 做法 |
| --- | --- | --- |
| `go.mod requires go >= 1.26` 之类版本报错 | 本机 Go 工具链低于框架最低版本 | 升级 Go 工具链，不要反手把 `go.mod` 里的版本号改低 |
| Echo 处理器签名报错（接口与指针混用） | `go.mod` 里是 v4 还是 v5 没定清，代码按另一主线写的 | 先查 `go.mod`，v5 用 `*echo.Context`，v4 用 `echo.Context`，统一主线后再改代码 |
| Fiber 里标准库中间件插不进去 | Fiber 底层是 fasthttp，不直接接受 `http.Handler` | 走 Fiber 的适配中间件转换，或换用 Fiber 自带的同类中间件 |
| `bind` 失败但错误信息看不懂 | JSON 字段名与结构体 tag 对不上，或必填字段没传 | 先对着结构体 tag 逐个核字段名，再看 `binding:"required"` 有没有漏传 |
| 端口被占用，启动直接退出 | 8080 已有服务在用 | 查占用进程并停掉它，或改 `PORT` 再启动，并同步改 Nginx 的 `proxy_pass` |
| 响应里出现重复写响应警告 | 错误分支里写了一次响应，调用处又写了一次 | 像第 10 节的 `parseID` 那样：写过响应的分支返回一个“已处理”标志，调用处直接 return |
| 上线后接口没鉴权 | `API_KEY` 为空，中间件放行了 | 检查 env 文件是否被 systemd 读到（`EnvironmentFile` 路径与权限），并确认值不是空 |

错误写法只放在表格与行内代码里说明，例如把 `r.Run(":8080")` 写在注册路由之前会导致路由没注册上、把密钥直接写进 `main.go` 会导致密钥进版本库——这两类错误不要写成可复制的代码块。

## 16. 故障排查

按“先分层、再定位”的顺序查，不要一上来就改代码：

1. **服务起没起来**：看终端日志与 `systemctl status taskapi`，先确认进程在、端口在监听（`ss -ltnp` 看 8080）；
2. **Nginx 还是 Go 的问题**：服务器本机 `curl 127.0.0.1:8080/healthz` 通、走域名不通，就是 Nginx 或 DNS 的问题；本机都不通，就是 Go 服务的问题；
3. **接口 404**：先核路由注册的方法与路径（GET 写成 POST 最常见），再核路径参数格式（Gin 与 Echo 用 `:id`，标准库用 `{id}`，Fiber 用 `:id`，混用会匹配不上）；
4. **接口 400**：先看请求体是不是合法 JSON、字段名与 tag 是否对得上，再看必填字段有没有漏；
5. **接口 401**：先核 `X-API-Key` 请求头有没有带、env 文件里的值与请求头的值是否一致、systemd 有没有重载 env（改 env 文件后要 `systemctl restart taskapi`）；
6. **服务越跑越慢**：先看处理器有没有没关的响应体、有没有在循环里查库、有没有共享 map 没加锁（没加锁先是偶发错乱，压力一大就 panic）；
7. **优雅停机没生效**：确认信号处理接的是 SIGINT 与 SIGTERM、停机超时是不是 5 秒、是不是用了 `srv.Shutdown` 而不是直接 `os.Exit`。

## 17. 安全注意事项

1. **密钥与口令只放 env 文件与密钥管理工具**，绝不写进代码、配置文件示例、聊天记录与版本库；本文所有示例口令都是占位符；
2. **错误响应不要回显原始错误**：数据库报错、堆栈信息只写日志，客户端只看到统一格式的简短原因；
3. **JSON 绑定要设校验**：必填字段用 `binding:"required"`，数字范围、字符串长度按业务加规则，不要无条件信任请求体；
4. **鉴权中间件要挂在正确的分组上**：健康检查可以公开，业务接口必须在鉴权分组里；挂错分组等于没鉴权，上线前用不带密钥的 curl 逐个接口测一遍；
5. **依赖要定期升级**：2026 年公开的 Echo 与 Fiber 安全公告都集中在旧补丁号上，`go list -m all` 定期看一遍，`govulncheck ./...` 定期跑一遍；
6. **前面放 Nginx**：TLS、限流、请求体大小限制放 Nginx 层做，不要每个 Go 服务各写一套；
7. **不要用 root 跑服务**：systemd 的 `User=taskapi` 与 `NoNewPrivileges=true` 是底线，服务被打穿时损失才可控。

## 18. 回滚和恢复

- **代码回滚**：部署前先留好上一个能跑的二进制（例如 `/usr/local/bin/taskapi.prev`），新版本出问题时停掉服务、把旧二进制拷回去、重启即可；不要在服务器上现场改代码救火；
- **配置回滚**：改 Nginx 与 systemd 之前先备份原文件（例如 `cp taskapi /etc/nginx/sites-available/taskapi.bak`），`nginx -t` 不通过时直接恢复备份再重载；
- **依赖回滚**：升级框架版本前先提交 `go.mod` 与 `go.sum`，出问题用版本库里的旧文件恢复，不要手工把版本号改回去再猜依赖；
- **数据回滚**：内存存储没有回滚可言，接数据库后备份与恢复按数据库篇的做法走；上线前先在测试环境把“备份—删库—恢复”完整演练一遍；
- **Echo 与 Fiber 主线回滚**：v4 升 v5、v2 升 v3 是破坏性升级，回滚不是改一行版本号，而是整个分支切回去；升级前务必先在分支上跑通全部测试。
