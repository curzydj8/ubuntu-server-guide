# crozz.me 网站建设与部署实战指南 · 总计划（MASTER_PLAN）

> 定位：crozz.me 从“一本 Ubuntu 服务器手册”升级为“服务器运维 + 网站建设”的综合技术手册。
> 最终形态：Ubuntu 服务器与网站建设实战手册——从 Linux 基础到服务器运维，从网站开发到生产环境部署，从零开始，直到正式运营。
> 执行原则：分阶段、分模块、逐项验收。禁止一次性生成整个项目；每次只做一个小任务，验收通过才进下一个；没有真实执行的测试不得标记为通过。

## 1. 目标读者

- 零基础读者：按教程从买域名、准备服务器、写页面、部署、上线、备份、监控，一步一步独立完成一个网站。
- 有经验的开发者 / 服务器管理员：能直接查到完整配置、框架级教程、架构选型和故障排查，不用再看概念性介绍。

## 3. 统一文档标准（每篇教程必须满足，缺一不可）

1. 本章目标；2. 适用人群；3. 适用系统和版本；4. 使用前提；5. 所需资源；
6. 技术原理；7. 架构说明；8. 操作前检查；9. 逐步操作；10. 完整命令；
11. 完整配置文件（注明存放路径）；12. 每个关键配置项的解释；13. 执行结果示例；
14. 成功验证；15. 常见错误；16. 故障排查；17. 安全注意事项；
18. 回滚和恢复；19. 延伸阅读；20. 相关章节链接。

硬性禁令：

- 不允许只有概念，没有操作；不允许用省略号代替关键配置；不允许只给片段不说明放置位置。
- 不允许使用未经验证的命令；不允许把测试环境配置直接当作生产环境配置。
- 命令必须说明在哪个目录、以什么用户身份执行；改配置前必须给备份方法；破坏性操作必须明确警告。
- 不同 Ubuntu 版本的差异必须说明；涉及中国大陆备案时必须说明适用范围，不能把备案要求错误地推广到所有地区。
- 外部软件版本、下载地址和官方文档必须尽可能核实，标注适用版本，不能用过时教程冒充当前最佳实践。

## 5. 三个必须补的专项（否则知识体系仍有缺口）

1. **建站方案选型决策树**：只展示产品 → 静态网站；博客 → WordPress / Typecho；企业管理后台 → Django / Laravel；高并发 API → Go / Java / Node.js 按业务选；多个网站 → Nginx + Docker 或统一主机管理架构。让读者按需求选方案，而不是先学一堆技术再回头选。
2. **完整配置文件库**：Nginx、Docker Compose、PHP-FPM、systemd、数据库、HTTPS、自动备份、自动部署的完整模板，每个模板给适用场景、参数解释和安全检查，不只解释配置。
3. **一台服务器托管多个网站的旗舰实战**：同一台 Ubuntu 服务器同时托管 WordPress 企业站、Django 站、Node.js 站、PHP 站、Go API、PostgreSQL / MySQL、Redis、Docker 服务，统一用域名、Nginx、HTTPS、日志、监控、备份和防火墙管理。这是整个建站指南的旗舰项目，放在最后阶段做。

## 7. 实施方式与保护规则

- 每次任务开始前检查 Git 状态，只改本任务文件，不得覆盖其他任务的未提交修改，不得删除原有文章，不得擅自修改现有网站导航和首页。
- 新增内容放在独立一级导航“网站建设与部署实战指南”下，目录建议为 `docs/website-guide/`，导航接入只在全站整合阶段（阶段 12）经站长批准后做，之前各阶段的文章只做本地构建验证，不上线。
- 每完成一个阶段：检查新增文件、Markdown 格式、内部链接、图片和资源、导航、执行 MkDocs 构建、执行适用的自动化测试、修复问题、形成阶段验收报告。
- 交互工具优先浏览器端实现，避免不必要的服务器请求和 API 费用；生成的配置和脚本提供复制、下载和使用说明。

最终提交（阶段 12 才给）：完整新增文档、完整目录树、新增工具及其测试、修改文件清单、自动化测试报告、章节覆盖率报告、尚未解决的问题、Git 提交记录、正式发布地址。
