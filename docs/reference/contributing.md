# 内容贡献规范

本页面向想给本站纠错、补章节或改进内容的读者与贡献者。规则不复杂，但有三条是硬性的：**命令必须核对过来源、验证状态不许夸大、危险操作必须标注**。其余格式问题都可以在审查时商量，这三条不达标会被直接打回。

仓库地址：[curzydj8/ubuntu-server-guide](https://github.com/curzydj8/ubuntu-server-guide)。参与方式与每页右上角的「编辑此页」按钮呼应：小修小补直接点「编辑此页」在线改完提 PR；大段新增先开 Issue 对齐范围，再按下面流程提交。

## 本站结构

- 正文按主题分 15 个部分（01 基础入门到 15 命令速查），外加[版本兼容页](../compatibility.md)、[更新日志](../changelog.md)、[互动工具](../tools/index.md)与本参考索引部分。
- 每部分一个目录，目录内 `index.md` 是导览，正文章节按 `序号-英文短名.md` 命名；导航顺序由仓库的 `mkdocs.yml` 显式维护，新增章节时由维护者在集成时统一登记，贡献者不必自己改导航。
- 每个文件开头必须带 frontmatter `description`（一句话说明本页内容，进搜索结果与页面元信息），正文用简体中文，命令与配置保持原文。

## 六段式文章模板

正文章节统一六段式：概述与场景 → 前置条件 → 手把手步骤 → 效果验证 → 排坑指南 → 生产最佳实践。新增章节直接复制下面的骨架填写，不要自创结构：

````markdown
---
description: "一句话说明本章解决什么问题、面向什么版本。"
---

# 章节标题

## 一、概述与使用场景

本章解决什么问题、什么场景下用、不用会怎样。先讲清价值，再给命令。

## 二、环境准备与前置条件

系统版本、权限、需要先装的软件、需要提前确认的信息清单。

## 三、手把手操作步骤

改任何配置文件之前，先给备份命令：

```bash
sudo cp /etc/目标文件 /etc/目标文件.bak-$(date +%F)
```

每一步给完整命令，关键参数逐行或逐项讲解，不省略、不写「同理可得」。

## 四、效果验证与测试

给出可执行的验证命令与预期输出，让读者能自己确认做对了没有。

## 五、常见错误与排坑指南

新手最容易踩的坑：现象、原因、修复方法，危险操作在此处或步骤内用警示块标出。

### 回滚与恢复（强制小节）

本章操作失败、做错或需要撤销时怎么办：改动前备份的对象在哪、按什么顺序退回、退回后用什么命令验证已恢复原状。标题必须含「回滚」或「恢复」二字（可独立成节，或作为第五、六节下的子节），不许只在正文里提一句带过。

## 六、生产环境最佳实践与安全建议

上生产前的安全与运维建议：最小权限、审计、监控、回滚路径。
````

速查类条目（第 15 部分）不套六段式，按速查固定结构写：用途、语法、参数表、示例、常见错误、风险提示，见[速查手册导览](../15-command-reference/index.md)的条目结构说明。

## 命令测试要求

- **来源核对**：新增或修改的命令、参数与配置写法，必须在 Ubuntu 22.04 / 24.04 上核对来源——以 Ubuntu 官方文档与各项目官方文档为准，并在 PR 描述里写明依据（文档名或链接）。只在博客、论坛帖子里见过、官方文档查不到的写法，不要提交。
- **状态如实**：本站验证状态只有三级——**已实测**（在真实机器上实际运行并确认效果）、**文档核对**（与官方文档逐项核对一致、但未在实机完整运行）、**待核验**（尚未核对或尚未实测）。禁止把未实测的内容标成已验证：自己只做过文档核对，就按文档核对申报；拿不准的按更低一级申报。
- **与兼容页的关系**：[版本兼容与验证状态](../compatibility.md)是全站唯一的验证状态基准页。正文与 PR 描述中的状态表述必须与兼容页口径一致；新增章节或状态升级时，必须在同一个 PR 里同步更新兼容页的逐章状态表，否则不予合并。Ubuntu 26.04 目前全站为「待核验」，没有在 26.04 实机上跑过的内容不许提前宣称兼容。
- **他人实测的引用**：读者反馈的实测结果经复核后可以推动状态升级，但必须注明来源与环境，不许冒充本站实测。

## 代码与配置格式

- 代码块必须标注语言（`bash`、`yaml`、`ini`、`nginx`、`sql` 等），不写无语言的裸代码块；命令默认给出可直接执行的完整形式，需要 root 的命令显式带 `sudo`。
- 配置文件示例逐行注释关键行：这一行改的是什么、为什么改成这个值、不改会怎样；占位符（域名、IP、口令）用明显的示例值，并在注释里提醒替换。
- **改前备份命令必备**：凡是步骤里出现编辑配置文件的动作，前面必须先出现该文件的备份命令（见模板第三节），这是本站的固定动作，不许省略成一句「请先备份」。
- **回滚/恢复小节必备**：每个正文章节必须有一个标题含「回滚」或「恢复」的小节（见模板第五节的强制小节），写清备份对象、回退步骤与退回后的验证命令；审查时按标题检索核查，缺失不予合并。纯概念导览页与速查条目除外，但凡含可执行变更步骤的章节一律适用。
- 示例 IP 只使用文档保留段 192.0.2.0/24 与 198.51.100.0/24，凭据只用占位符；不许出现真实公网 IP、真实口令、私钥或任何密钥材料。脚本类内容必须提示「先下载审阅再执行」。

## 风险标注规范

使用 MkDocs Material 的警示块，按后果选级别：

- `!!! danger`：误操作会造成**不可逆破坏**的场合——数据删除、磁盘与分区改写、权限体系损坏、防火墙锁死整机、数据库端口暴露公网等。标题直接写清动作与后果，如 `!!! danger "rm -rf 与根目录误删"`。
- `!!! warning`：有明确风险但可控或可恢复的场合——远程改网络可能断联、操作需要维护窗口、版本差异会导致行为不同、内容已弃用（见下一节）。
- `!!! note` / `!!! tip`：补充说明与经验建议，不用于风险场合，不要拿它们代替上面两级。

以下危险命令在正文出现时**必须**配 danger 警示块并给出安全替代写法（清单与[命令索引](command-index.md)的高风险等级对应）：`rm -rf`、递归 `chmod -R` 与 `chown -R`、`dd` 与 `mkfs` 等写盘命令、`fdisk` 等分区写操作、`ufw reset` 与清空防火墙规则集、`docker compose down -v` 与批量删除容器镜像、`crontab -r`、在 SSH 会话中改网卡地址或路由。警示块里要写清：错在哪、后果是什么、正确顺序或替代命令是什么。

## 过期内容标记规范

内容过期（软件改名、参数废弃、版本停止维护）时不要直接删除，先按下面样式在原位置加弃用提示块，并给出替代方案链接，让从搜索引擎落到旧内容的读者有路可走：

```markdown
!!! warning "已弃用"
    本节介绍的 旧方案名称 已于 年份 停止维护（或自 某版本 起不再适用），
    新环境请改用 [替代方案章节](相对链接)，本节仅供维护存量系统时参考。
```

处理原则：

- 替代方案必须真实存在并给出站内链接；暂时没有替代方案的，在提示块里写明「暂无替代方案」与原因，不要留一个死链接。
- LTS 版本到达 EOL 时，相关内容按[更新日志](../changelog.md)的维护约定标「已停止维护」，同样先标记、后归档，不直接删。
- **发现过期内容的反馈路径**：到仓库开 Issue，标题注明「内容过期」与章节名，正文写清你看到的现状（如新版命令输出、官方变更公告链接）与你的系统版本；维护者复核后按本节规范标记或更新，并在兼容页与更新日志留痕。

## 审查流程

1. **提交**：Fork 仓库、建分支、按模板与格式规范完成修改后提 PR；PR 描述写明改动范围、命令依据来源、本次内容的验证状态申报（已实测须注明实测的系统版本与环境）。
2. **复核命令与链接**：维护者逐条复核——命令与参数对照官方文档、示例能独立看懂、站内相对链接与锚点真实存在、危险操作有警示块、改配置处有备份命令；任一项不过，PR 退回修改，不代改后强行合并。
3. **同步基准页**：涉及新增章节、章节删除或验证状态变化的 PR，必须同时更新[版本兼容页](../compatibility.md)（矩阵与逐章状态表）与[更新日志](../changelog.md)（新增一条记录，必要时加版本行）；两处缺一不予合并。导航（`mkdocs.yml`）由维护者在合并集成时统一调整。

## 通过 GitHub 参与

- **纠错与小改**：打开对应页面，点右上角「编辑此页」直接改，提交即生成 PR——最适合错别字、命令笔误、链接失效这类小问题。
- **报告问题**：到仓库 [Issues](https://github.com/curzydj8/ubuntu-server-guide/issues) 新建 Issue。请写清：出问题的章节链接、你的系统版本（`lsb_release -a` 输出）、你执行的命令、实际结果或报错原文、你预期的结果。信息越完整，复核越快；只写「命令不能用」的 Issue 会被要求补充信息。
- **新增章节**：先开 Issue 说明选题、拟覆盖范围与你能提供的验证环境，对齐后再动手写，避免与进行中的工作撞车或写完才发现选题不合本站范围。
- 提交即表示同意本站以相同开源方式发布你的贡献；不要在 Issue、PR 或示例里贴任何真实口令、密钥与个人信息，贴日志前先打码。
