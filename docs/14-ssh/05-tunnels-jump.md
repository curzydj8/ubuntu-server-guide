# SSH 隧道与跳板机

## 一、概述与使用场景

SSH 隧道（端口转发）是在一条已建立的 SSH 加密连接里，再承载其他 TCP 流量。不需要额外开 VPN、不需要在防火墙上新开端口，只要能 SSH 登录一台服务器，就能借它的网络位置访问它能到达的服务，或把自己这边的服务临时送到它那边。

```mermaid
flowchart LR
    A["你的电脑<br/>127.0.0.1:8080"] -->|"明文，仅本机回环"| B["ssh 客户端"]
    B -->|"SSH 加密通道<br/>公网 / 内网链路"| C["服务器 sshd<br/>192.0.2.10:22"]
    C -->|"以服务器身份发起连接"| D["目标服务<br/>127.0.0.1:80 或内网主机"]
```

三种转发对应三种场景：

- **本地转发 `-L`**：在你的电脑上开监听端口，流量经服务器转发到目标。最常用：访问只绑服务器本机或内网的管理面板、把数据库连接安全地拉到本地，全程不把目标端口暴露到公网。
- **远程转发 `-R`**：在服务器上开监听端口，流量反向回到你这边的服务。适合临时让同事经服务器访问你内网的测试机，或给没有公网地址的设备留一个受控入口。
- **动态转发 `-D`**：在本地开 SOCKS5 代理，目标由每个请求动态决定。适合临时让浏览器或命令行工具借服务器出口上网、访问只能从服务器网段到达的一批站点。

跳板机（ProxyJump）解决另一类问题：目标服务器不直接对外，只允许从一台中间机器访问。你先连跳板机，再由它转接到目标，对你只是一条 `ssh` 命令。隧道与跳板机常组合使用：先经跳板机连上内网服务器，再在同一条连接里做本地转发。

!!! warning "先想清楚边界再开隧道"
    隧道本质上等于绕过原有的网络边界：防火墙没放行的端口、只绑内网的服务，开了隧道就等于给它们开了一条旁路。这不是漏洞利用，而是 SSH 的正规功能，但用之前必须确认你被授权这样做，详见第六节。

隧道与 VPN 的取舍见 [VPN 与隧道](../04-network/03-vpn-tunnel.md)：隧道适合单个服务、临时使用、零服务端改造；需要整网段互通或长期常驻时 VPN 更合适。要把内网服务长期提供给公网用户，应使用正规方案，见 [NAT 穿透与内网服务发布](../10-game-servers/04-nat-traversal.md)，不要拿远程转发长期顶替。

## 二、环境准备与前置条件

本章适用于 Ubuntu 22.04 LTS 与 24.04 LTS（客户端与服务端命令通用），不宣称在 26.04 上验证。开始前确认：

- 你已能正常 SSH 登录目标服务器，连接与 `~/.ssh/config` 基础写法见 [连接与配置文件](02-connect-config.md)。本章示例服务器为 `192.0.2.10`（文档示例段，请替换为真实地址），登录用户为 `ubuntu`。
- 服务端 `AllowTcpForwarding` 未被设为 `no`（Ubuntu 默认允许；被禁用时所有转发都会被拒绝）。
- 目标服务确实在运行。隧道只搬运流量，目标没起来，隧道建得再对也打不开。
- 本地监听端口未被占用，且大于 1024（普通用户即可绑定）。

!!! note "示例地址说明"
    `192.0.2.x`、`198.51.100.x` 为文档示例段；`10.0.0.x` 为内网示意，表示服务器所在局域网。

## 三、手把手操作步骤

### 3.1 本地转发 -L：把远端服务拉到本地端口

语法逐段拆解：

```bash
ssh -L 8080:127.0.0.1:80 ubuntu@192.0.2.10
```

- `-L`：声明一条本地转发规则，格式固定为 `-L [本地监听端口]:[目标地址]:[目标端口]`。
- `8080`：在**你的电脑**上监听的端口。命令执行后，你访问 `127.0.0.1:8080`，就等于在访问目标服务。
- `127.0.0.1:80`：目标地址与目标端口。**最关键的一点：这个地址以服务器的视角解析**，不是以你的电脑的视角。写 `127.0.0.1` 指的是服务器自己的回环地址；写 `10.0.0.25` 指的是与服务器同内网的另一台主机 `10.0.0.25`（内网示意）。这是新手写错最多的地方，也是第五节排坑的重点。
- `ubuntu@192.0.2.10`：你实际 SSH 登录的服务器。隧道寄生在这条登录连接上，连接断开，隧道随即失效。

执行后终端会正常登录进服务器（这条连接同时兼作隧道）。保持这个终端不要关，再开一个本地终端验证：

```bash
curl http://127.0.0.1:8080/
```

```text
<!doctype html><html><head><title>管理面板</title>...</html>
```

能返回目标页面即说明转发已通。浏览器打开 `http://127.0.0.1:8080` 即可使用面板，而该面板在服务器上可能只绑了 `127.0.0.1:80`，公网访问不到，也无需改它的绑定地址。

场景一：访问只绑内网的管理面板。许多面板（监控、数据库管理、内部后台）只监听 `127.0.0.1` 或内网地址，正确做法不是改成监听 `0.0.0.0` 再去防火墙放行，而是用本地转发临时拉到本地，用完关闭。

场景二：数据库安全转发。把本地 `13306` 转发到服务器本机的 MySQL：

```bash
ssh -N -L 13306:127.0.0.1:3306 ubuntu@192.0.2.10
mysql -h 127.0.0.1 -P 13306 -u appuser -p
```

数据库客户端连的是本地 `13306`，流量经加密隧道到达服务器的 `127.0.0.1:3306`。这样 MySQL 只需监听本机、防火墙无需放行 3306，账号与远程访问的配置原则见 [MySQL 用户与远程访问](../11-databases/02-mysql-users-remote.md)：能用隧道时，就不要为了图方便把 3306 直接暴露到公网。

### 3.2 远程转发 -R：把本地服务送到服务器侧

语法与 `-L` 方向相反：

```bash
ssh -R 18080:127.0.0.1:8000 ubuntu@192.0.2.10
```

拆解：`18080` 是在**服务器上**开的监听端口；`127.0.0.1:8000` 是以**客户端视角**解析的目标，即你本机正在跑的 `8000` 端口服务。成功后在服务器上 `curl http://127.0.0.1:18080/` 即可访问你本机服务。目标也可写成你内网的另一台主机，如 `-R 18080:10.0.0.30:8000`（内网示意）。

!!! danger "GatewayPorts 默认 no，不要随手改成 yes"
    远程转发默认受服务端 `GatewayPorts no` 约束：转发端口只绑在服务器的 `127.0.0.1` 上，只有服务器本机能访问，外人连不上——这是有意的安全默认值。若在服务端把 `GatewayPorts` 改为 `yes`，转发端口将绑到 `0.0.0.0`，等于把一个内网服务未经防火墙策略审核直接发布到公网，任何人都能尝试连接。确有对外需求时，应走正规发布方案（见第一节互链的内网穿透章节），并经过网络管理员批准、配合防火墙与访问控制，不要图省事改这个开关。

### 3.3 动态转发 -D：一个本地 SOCKS5 代理

```bash
ssh -N -D 1080 ubuntu@192.0.2.10
```

`-D 1080` 在本地 `127.0.0.1:1080` 开一个 SOCKS5 代理。与 `-L` 不同，它不预先写死目标：每个请求要去哪里，由使用代理的程序在请求时告诉 SSH，再由服务器代为连接。因此一个 `-D` 就能访问服务器能到达的任意地址，适合目标多、地址不固定的场景。

使用要点：

- **命令行验证**：用 `curl` 确认代理可用并核对出口 IP。

```bash
curl --socks5 127.0.0.1:1080 https://ifconfig.me
curl https://ifconfig.me
```

```text
198.51.100.10
192.0.2.55
```

第一条经代理，应返回服务器一侧的出口地址（`198.51.100.10` 为示意）；第二条不走代理，返回本地出口。两者不同，证明流量确实绕经了服务器。`ifconfig.me` 只是举例，也可用任何可信的 IP 查询方式核对。

- **浏览器**：在浏览器或系统代理设置中选 SOCKS5 代理，地址 `127.0.0.1`、端口 `1080`，并开启「通过代理解析 DNS」（Firefox 为使用 SOCKS v5 时代理 DNS 查询），否则内网域名会在本机解析失败，本地 DNS 还会泄露访问目标。
- **系统代理**：设为同一地址后，未单独设置代理的程序也会走隧道；用完务必改回直连，否则关掉 SSH 后这些程序会集体断网。

### 3.4 常用参数：让隧道连接更可靠

```bash
ssh -N -f -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 13306:127.0.0.1:3306 ubuntu@192.0.2.10
```

- `-N`：不执行远程命令、不给终端，只建连接和转发。纯做隧道时应加上。
- `-f`：认证完成后转入后台，终端立即释放。配合 `-N` 是常驻隧道的标准组合；关闭时用 `pkill -f "ssh -N"` 或按进程号结束，不要留着不管。
- `-o ExitOnForwardFailure=yes`：转发端口绑定失败时直接报错退出。强烈建议加上：没有它时，端口被占用也可能「登录成功」，你会对着旧进程的端口白调试半天。
- `ServerAliveInterval=30` 与 `ServerAliveCountMax=3`：每 30 秒发一次保活探测，连续 3 次无响应判定连接已死并退出。宽带、公司 NAT、笔记本休眠都会让空闲连接被中间设备回收，保活能显著减少「隧道莫名其妙断了」。

!!! tip "常用隧道写进配置文件"
    长期反复用的转发可以写进 `~/.ssh/config` 对应主机的 `LocalForward` / `RemoteForward` / `DynamicForward` 字段，之后一条 `ssh 别名` 即带起隧道。具体字段写法见 [连接与配置文件](02-connect-config.md)。

### 3.5 跳板机：-J / ProxyJump 一条命令进内网

设拓扑为：你的电脑 → 跳板机 `ubuntu@192.0.2.20` → 目标机 `opsadmin@10.0.0.40`（内网示意，目标机只允许跳板机访问）。单级跳板：

```bash
ssh -J ubuntu@192.0.2.20 opsadmin@10.0.0.40
```

地址解析视角要分清：`192.0.2.20` 由你的电脑解析和连接；`10.0.0.40` 由**跳板机**解析和连接——你的电脑根本不需要能到达 `10.0.0.40`，这正是跳板机的意义。认证仍是端到端的：你对目标机的密钥认证经跳板机透传，跳板机只搬运加密流量，看不到目标机的会话内容。

多级跳板用逗号串联，按从近到远的顺序写：

```bash
ssh -J ubuntu@192.0.2.20,opsadmin@198.51.100.20 opsadmin@10.0.0.40
```

落到 `~/.ssh/config` 后日常使用最省事，整段示例逐行讲解：

```sshconfig
Host jump
    HostName 192.0.2.20
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

Host db-internal
    HostName 10.0.0.40
    User opsadmin
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump jump
```

- `Host jump`：给跳板机起别名 `jump`，下面三行是它的真实地址、用户与私钥。
- `Host db-internal`：目标机别名。`HostName 10.0.0.40` 是内网地址，由跳板机负责到达，你的电脑解析不了它也没关系。
- `ProxyJump jump`：核心一行，声明连 `db-internal` 时先经别名 `jump` 中转，等价于命令行 `-J ubuntu@192.0.2.20`，用户与密钥自动取 `jump` 段配置。

配置完成后只需 `ssh db-internal`；再叠上本地转发即 `ssh -L 13306:127.0.0.1:3306 db-internal`，一条命令完成「经跳板机进内网 + 拉回数据库端口」。

`ProxyCommand` 是更底层的老式写法：让 SSH 执行一条外部命令充当传输通道（如经 `nc` 或专用代理工具连接）。普通跳板场景一律优先用 `ProxyJump`，配置更短；只有中间环节不是标准 SSH 服务器时才需退回 `ProxyCommand`，本章不展开。

## 四、效果验证与测试

隧道是否真的通，按三层依次验，不要只看 `ssh` 没报错：

第一层，看本地监听是否建立：

```bash
ss -lntp | grep 8080
```

```text
LISTEN 0 4096 127.0.0.1:8080 0.0.0.0:* users:(("ssh",pid=12345,fd=5))
```

判读：出现 `127.0.0.1:8080` 且进程为 `ssh`，说明转发端口已在本机监听。查不到，说明转发没建起来，先看建隧道那个终端的报错。

第二层，实际发请求验证目标可达：

```bash
curl -v http://127.0.0.1:8080/
```

能拿到目标服务的正常响应（哪怕是登录页或 403，都算通，因为说明流量已到达目标服务）；`Connection refused` 表示隧道在、但服务器侧连目标失败；一直超时则多为目标地址以服务器视角写错（见第五节）。

第三层，看服务器侧日志确认连接来源：

```bash
sudo journalctl -u ssh --since "-10 min" --no-pager
```

能看到你账号的 `Accepted` 记录，即证明会话落在预期服务器上。跳板场景还应在目标机核对：日志里连接来源应是跳板机的内网地址，而非你的公网地址——这是跳板链路正确的标志。

## 五、常见错误与排坑指南

### 5.1 本地端口被占用：Address already in use

- **现象**：执行转发命令时报 `bind [127.0.0.1]:8080: Address already in use`，并提示 `channel_setup_fwd_listener ... cannot listen to port`。
- **原因**：本地 `8080` 已被其他程序（或你上一次没关干净的 `ssh` 隧道）占用。
- **修复**：先查占用者再决定。`ss -lntp | grep 8080` 看进程名与 PID：是旧隧道就结束它后重开；是别的业务程序就换个本地端口，例如把 `-L 8080:` 改成 `-L 18080:`，目标部分不动。同时养成加 `-o ExitOnForwardFailure=yes` 的习惯，让这类失败立即显形。
- **验证**：重开后 `ss -lntp` 显示新端口由当前 `ssh` 进程监听，`curl` 能拿到目标响应。

### 5.2 绑定地址不对：bind: Cannot assign requested address

- **现象**：给 `-L` 额外指定了监听地址（如 `-L 192.0.2.99:8080:...` 写了本机并不拥有的地址）时直接报错退出。
- **原因**：进程只能绑定本机真实存在的地址。概念上要与远程转发的 `GatewayPorts` 分清：`-L` 默认只绑 `127.0.0.1` 是客户端行为，想让局域网其他机器也能连你这个转发端口，需显式写 `-L 0.0.0.0:8080:...` 或在配置里设 `GatewayPorts clientspecified`（客户端侧语义），且这等于把目标服务开放给整个局域网，非必要不要做；写了一个本机根本没有的 IP，则必然是上面的报错。
- **修复**：删掉多余的绑定地址，回到 `-L 8080:...` 只绑回环；确需局域网共享时写 `0.0.0.0` 并同步评估风险。
- **验证**：`ss -lntp | grep 8080` 的监听地址与预期一致（`127.0.0.1` 或 `0.0.0.0`）。

### 5.3 转发建立了，但页面打不开

- **现象**：`ssh` 登录正常、本地端口也在监听，但访问转发端口超时、空白或被拒绝。
- **原因**：最常见是目标地址视角写错——把目标在**你本地**的内网地址填进 `-L`，服务器在自己的网络里找不到它。其次是目标只监听 IPv6 的 `::1` 而你写了 `127.0.0.1`（或反过来），或目标自身的访问控制拒绝了来自服务器本机的连接。
- **修复**：另开会话登录服务器，直接 `curl http://127.0.0.1:80/` 并用 `ss -lntp` 核对目标监听的地址与端口；服务器本机都不通，先修目标服务或把转发目标改为实测可达的地址；只监听 IPv6 时把目标改为 `::1`。
- **验证**：服务器本机 `curl` 目标成功后，本地 `curl http://127.0.0.1:8080/` 应立即得到相同响应。

### 5.4 连接一断，隧道全部失效

- **现象**：网络切换、合上笔记本、空闲一段时间后，转发端口还在，但请求全部超时或连接被重置。
- **原因**：隧道寄生在 SSH 连接上，连接被 NAT 空闲回收、网络切换或服务端重启打断后，转发随之死亡；本地监听残留时还会误导你以为它还活着。
- **修复**：建隧道时加保活参数 `-o ServerAliveInterval=30 -o ServerAliveCountMax=3`，让死连接能被及时发现并退出；发现失效后结束残留 `ssh` 进程再重建。需要无人值守长期维持的隧道，可了解 `autossh` 这类自动重连工具的思路（本章只作提及，按需另行评估部署），临时使用则手工重开即可。
- **验证**：重建后重复第四节三层验证；主动断网再恢复，确认保活能让死连接退出、新隧道能干净重建。

## 六、生产环境最佳实践与安全建议

- **授权先行**：隧道等于绕过网络边界，只在被明确授权的网络与服务器上使用。在公司、学校等受管网络中，私自用隧道（尤其是 `-D` 代理与 `-R` 对外）可能违反网络安全政策；不确定时先问网络管理员。
- **最小开放**：本地转发默认只绑 `127.0.0.1`，不要为让同事「也能连」随手改成 `0.0.0.0`；远程转发坚守 `GatewayPorts no` 默认。对外发布走正规反向代理或内网穿透方案，并配访问控制与日志。
- **密钥与账号**：隧道连接同样使用密钥认证、独立账号，不共用账号、不把带隧道的命令写进会泄露的仓库；离职、交接或设备丢失时，及时从服务器 `authorized_keys` 移除对应公钥，入口随即失效。
- **用完即关（回滚/收尾）**：隧道是临时通道，不是长期架构。收尾清单：① 结束隧道会话，后台隧道用 `pkill -f "ssh -N"` 或按 PID 结束；② 浏览器或系统代理曾指向 `-D` 端口的，改回直连或原设置；③ 曾为转发临时改过服务端配置（如 `GatewayPorts`、`AllowTcpForwarding`）的，把配置还原，`sudo sshd -t` 校验后 `sudo systemctl reload ssh`，并用新会话验证普通登录不受影响；④ 本地与服务器两侧各执行一遍 `ss -lntp`，确认无遗留的转发监听。
- **留痕可查**：生产环境的跳板与转发使用应能在 `journalctl -u ssh` 与 `/var/log/auth.log` 里对上记录；跳板机账号独立设置、只给需要的人，并按服务端加固标准维护——它是所有内网入口的前门。
