    CPU 与内存异常飙高定位¶

    一、概述与使用场景¶

    CPU 与内存异常是服务器性能故障中最常见的两类，表现包括：系统负载持续高于核数、命令执行明显变卡、接口响应时间翻倍、进程被系统强制结束、内存交换分区被大量使用导致整机迟缓。处置这类问题的核心难点不是会不会用工具，而是能否把现象拆成可验证的结论：到底是用户态计算占满、内核态开销过高、等待输入输出拖高负载，还是内存不足引发的交换与回收在消耗 CPU。

    本章的定位顺序固定为四步：先用全局指标判断瓶颈类型，再定位到进程，再按服务与控制组归类确认影响范围，最后用性能采样与系统调用跟踪拿到代码层面的证据。每一步都有明确的判据与停止条件，证据不足时不下根因结论，只记录现象与已排除项。

    内存问题还要额外区分三种情形：真实内存泄漏，进程占用随时间单调增长且不回落；正常缓存占用，free 显示空闲很少但可用内存充足，这不是故障；突发大内存申请触发 OOM，内核按规则选中并结束占用最大的进程，系统日志会留下完整记录，事后分析以这份日志为准。

    负载高不等于 CPU 忙

    系统负载统计的是正在运行与等待运行、以及处于不可中断睡眠状态的任务数量。大量任务在等待磁盘时负载同样很高，但 CPU 利用率可能很低。判断瓶颈类型必须同时看负载、CPU 利用率构成与内存交换情况，单看任何一个数字都会得出错误结论。

    二、环境准备与前置条件¶

    排查前确认以下条件：

    • 具有 sudo 权限，性能采样、查看其他用户进程的系统调用与读取内核日志都需要管理员权限。
    • 安装本章工具，Ubuntu 22.04 与 24.04 的安装命令如下，其中性能工具包的名称随内核版本变化，应使用与当前内核匹配的包：
    sudo apt update
sudo apt install -y sysstat procps strace lsof htop linux-tools-common linux-tools-generic
uname -r
perf --version
    • 确认基线数据：正常时段的负载、CPU 利用率、内存可用量与关键进程占用，来自监控系统或历史记录。没有基线时只能判断当前是否异常，无法判断异常幅度。
    • 明确采样窗口：性能问题常与业务高峰同步，采样应覆盖问题时段，低峰期采样得出的正常结论不能推翻高峰期的故障。
    • 生产采样要控制开销：perf record 与 strace 都会给目标带来额外负担，使用规则在对应小节中写明，先在测试进程上验证命令写法，再对生产进程执行。

    三、手把手操作步骤¶

    3.1 全局指标判读：先分清瓶颈类型¶

    uptime
top -b -n 1 | head -n 30
vmstat 1 5
free -h
sar -u 1 3

    判读逐项说明。uptime 末尾三个负载数字分别对应最近一分钟、五分钟、十五分钟，三者接近且持续高于 CPU 核数说明压力稳定存在，只有第一个数字高说明是刚发生的突发。top 顶部 CPU 行逐项含义：us 为用户态占用，高说明应用计算繁忙；sy 为内核态占用，高说明系统调用、网络或驱动开销大；id 为空闲，接近零说明 CPU 确实饱和；wa 为等待输入输出占用，高说明瓶颈在存储而不是计算；st 为虚拟化环境被宿主机抢占的时间，云主机上该值高应联系云厂商而不是查本机应用。vmstat 重点看 r 列等待运行的任务数长期大于核数即 CPU 排队，si 与 so 两列持续非零说明正在频繁换入换出内存，内存不足正在直接拖慢整机。free -h 以 available 列为准判断内存是否真的紧张，不要用空闲列下结论，文件缓存占用的内存在压力下会自动释放并计入可用量。

    期望的正常输出示例：

    $ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       6.2Gi       1.1Gi       320Mi       8.4Gi       8.6Gi
Swap:          2.0Gi          0B       2.0Gi

    该例中空闲只有 1.1 吉字节，但可用为 8.6 吉字节且交换分区未使用，属于健康状态。

    3.2 定位进程：谁在消耗 CPU 与内存¶

    全局确认是 CPU 或内存瓶颈后，按占用排序定位进程：

    ps aux --sort=-%cpu | head -n 15
ps aux --sort=-%mem | head -n 15
top -o %CPU
top -o %MEM
pidstat -u 1 3
pidstat -r 1 3

    判读逐项说明：单次 ps 只是一个瞬间快照，pidstat 按秒连续采样给出的平均值更可信，用它确认目标进程是持续高占用还是瞬时尖峰。记录目标进程的进程号、启动命令、所属用户与已运行时间，后续所有跟踪都以进程号为准。若高占用进程是短命进程反复拉起，ps 很难抓到，应在 top 中观察进程号不断变化的同名进程，并去查它的父进程与定时任务来源。

    3.3 按服务定位：使用 systemd-cgtop 与 systemctl¶

    现代 Ubuntu 的服务都运行在 systemd 控制组中，按服务归类能直接回答哪个业务受影响：

    systemd-cgtop
sudo systemctl status nginx
systemctl show nginx -p MemoryCurrent -p CPUUsageNSec -p MemoryMax
ps -eo pid,ppid,cmd,%cpu,%mem --sort=-%cpu | head -n 15

    systemd-cgtop 按控制组实时列出各服务的 CPU、内存、任务数与读写量，刷新方式与 top 相同，适合在故障现场快速锁定异常服务。再用 systemctl show 读取该服务的当前内存与累计 CPU 时间，和监控基线对比确认异常幅度。若服务设置了资源上限，还应检查它是否已经顶到上限被限制，这类信息会出现在服务状态与日志中。定位到服务后，先按应急原则处置：无状态服务可重启或扩容，有状态服务先限流或摘流，根因采样要在处置前尽量完成，至少保留一份 perf 采样或进程快照。

    3.4 perf 采样：把 CPU 时间花在哪个函数上¶

    进程级定位只能说明谁忙，perf 回答忙在何处，是区分应用计算、系统调用与锁等待的关键证据：

    sudo perf top
sudo perf record -F 99 -p 12345 -g -- sleep 30
sudo perf report
sudo perf stat -p 12345 -- sleep 10

    判读逐项说明：perf top 实时显示占用最高的函数，符号为应用函数名说明计算集中在业务代码，符号大量为内核函数则结合 top 的内核态占比判断是否为系统调用或网络收发开销。perf record 以 99 赫兹对指定进程采样三十秒并记录调用栈，-g 保留完整调用关系，采样结束后用 perf report 按占比从高到低查看，把前三名函数与占比写入故障记录。perf stat 给出指令周期、缓存未命中等计数器概览，缓存未命中率异常高时，问题可能是数据访问模式而不是单纯的算力不足。

    perf 在生产环境的使用边界

    perf record 会产生采样数据文件并占用额外 CPU，采样频率与时长按本节示例控制，不要对全系统做长时间高频采样。采样文件可能包含进程符号与路径信息，按故障证据管理，问题关闭后及时归档或销毁。对延迟敏感的核心进程，优先在同版本的测试环境复现采样，生产只做短时低频验证。

    3.5 strace 跟踪：看进程在反复做什么系统调用¶

    当进程 CPU 高但业务量未涨，或进程像是卡住不动时，用 strace 看它实际在执行的系统调用：

    sudo strace -p 12345 -c -f
sudo strace -p 12345 -tt -T -f -o /tmp/strace-output.txt
sudo strace -p 12345 -e trace=file -f
tail -n 100 /tmp/strace-output.txt

    判读逐项说明：先以统计模式运行，输出按系统调用汇总次数、耗时与错误数，重点看三类异常：某个调用次数在短时间内达到几十万次，说明存在忙循环或无退避的重试；错误数集中在同一调用且错误码相同，例如反复连接失败或文件不存在，说明进程在无效重试中空转；单次调用耗时异常长，说明它在等存储、网络或锁。用带时间戳的模式抓取明细时，要限定时间在三十秒以内，输出文件增长很快，长时间跟踪既拖慢目标进程也会写满磁盘。跟踪结束后及时停止，跟踪本身造成的开销不能算进故障数据。

    strace 的性能影响

    strace 会让目标进程的每次系统调用都暂停并经过跟踪者，系统调用密集的进程可能被拖慢数倍。生产使用顺序是先统计模式短时观察，再决定是否抓明细，并避开业务最高峰执行。跟踪数据库等核心进程前先告知业务负责人，出现明显变慢立即停止跟踪，改用采样类工具。

    3.6 lsof 辅助定位：进程在操作哪些文件与连接¶

    sudo lsof -p 12345 | head -n 50
sudo lsof -p 12345 | wc -l
sudo lsof -i -p 12345
ls -l /proc/12345/fd | head -n 50
cat /proc/12345/status | grep -E "VmRSS|VmSwap|Threads"
cat /proc/12345/io

    判读逐项说明：lsof 列出进程打开的文件、网络连接与管道，结合句柄总数能判断高占用是否与连接暴涨或文件未关闭有关。/proc/进程号/status 中的实际驻留内存与交换占用是判断单个进程真实内存压力的直接来源，线程数异常增长往往伴随内存同步增长，两条线一起看有助于区分线程泄漏与堆内存泄漏。

    3.7 内存持续增长与泄漏的确认方法¶

    怀疑内存泄漏时不能只看一次占用，要做时间序列确认：

    ps -o pid,etime,%mem,rss,vsz,cmd -p 12345
watch -n 60 "ps -o pid,rss,vsz,cmd -p 12345"
sudo smem -P example-app
journalctl -k -b -0 --no-pager | grep -i -E "oom|out of memory|killed process"

    判读逐项说明：每隔数分钟记录一次同一进程的驻留内存，业务量平稳而内存只涨不跌、重启后回到低位再重复增长，三个条件同时满足才可判定疑似泄漏。smem 按进程汇总实际占用，适合多进程同名服务的场景。确认泄漏后的应急处置是设定重启窗口或给服务设置内存上限并配合自动重启，根因修复在应用层，需要开发侧结合堆分析定位未释放对象，运维侧提供增长曲线与重启记录作为证据。

    3.8 OOM 日志分析：进程被谁结束、为什么被选¶

    进程突然消失且无应用错误日志时，先查内核是否触发了内存不足处理：

    sudo dmesg -T | grep -i -A 20 "out of memory"
sudo journalctl -k --since "2026-10-21 00:00:00" --until "2026-10-21 23:59:59" --no-pager | grep -i -E "oom|killed process"
grep -i -E "oom|killed process" /var/log/kern.log
sudo systemctl status nginx

    期望日志示例：

    kernel: Out of memory: Killed process 12345 (example-app) total-vm:8203640kB, anon-rss:6102448kB, file-rss:0kB, shmem-rss:0kB
kernel: oom_reaper: reaped process 12345 (example-app), now anon-rss:0kB, file-rss:0kB, shmem-rss:0kB

    判读逐项说明：日志会列出触发时刻各进程的内存占用表与被选中进程的得分，被选中的通常是当时占用最大的进程，但它不一定是根源，可能是其他进程泄漏挤占后由它承担了最后的申请。分析时要同时看同一时段所有进程的增长情况与整机可用内存曲线。防护手段包括给关键服务在单元文件中设置 OOMPolicy 与内存上限、为次要服务设置较高的被结束优先级倾向值、扩容或增加交换空间作为缓冲，这些配置都要在测试环境验证后再上生产。

    四、效果验证与测试¶

    处置后用与定位相同的命令复测，保证前后口径一致：

    uptime
vmstat 1 5
free -h
ps aux --sort=-%cpu | head -n 10
systemd-cgtop -n 1
sudo journalctl -k -b -0 --no-pager | grep -i -E "oom|killed process"
curl -o /dev/null -s -w "%{http_code} %{time_total}\n" http://example.com/

    期望输出示例：

    $ uptime
 14:20:01 up 30 days,  3:12,  2 users,  load average: 0.85, 0.92, 0.88
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       7.0Gi     900Mi       320Mi       7.6Gi       7.8Gi
Swap:          2.0Gi       128Mi       1.9Gi

    判读标准：负载回到与核数相称的基线范围，vmstat 的换入换出归零或偶发，目标进程占用稳定不再单调增长，本次启动以来无新的进程被结束记录，业务接口状态码与耗时恢复正常。验证需跨越一个业务高峰，高峰下复测结果与定位时的数据一并写入故障记录，注明采样时间与业务量级，避免低峰结论掩盖问题。

    五、常见错误与排坑指南¶

    错误一：看到 free 显示空闲内存很少就判定内存不足并重启服务。 现象是空闲列只有几百兆字节，便反复重启应用。原因是把文件缓存占用误判为泄漏，缓存内存在压力下会自动释放。正确做法是只以可用列与交换使用情况判断，内存紧张的硬证据是可用量持续低位且换入换出频繁，两项不成立就不要动服务。

    错误二：负载高就断定 CPU 不够并申请扩容。 现象是负载达到两位数，扩容后负载依旧。原因是负载中包含大量等待存储的任务，瓶颈在磁盘而不是计算，加 CPU 毫无作用。正确做法是先看 top 中等待输入输出的占比与 vmstat 的队列构成，确认用户态与内核态计算确实饱和后，再谈扩容或代码优化。

    错误三：对生产进程长时间运行 strace 并把跟踪开销当成故障加剧。 现象是跟踪一开接口超时暴增，误以为故障恶化而扩大处置动作。原因是跟踪使每次系统调用都被暂停，密集调用的进程会被显著拖慢。正确做法是先统计模式短时采样，明细跟踪限定秒级时长并避开高峰，发现目标明显变慢立即停止并改用 perf 采样。

    六、生产环境最佳实践与安全建议¶

    第一，基线与告警成对建设：采集负载、CPU 分项利用率、可用内存、交换速率与核心进程占用，告警阈值按基线设置并区分持续时长，瞬时尖峰不误报、持续异常不漏报。第二，资源隔离先行：用 systemd 给关键服务设置 CPU 与内存的上限和权重，把单个服务的异常限制在自身范围内，具体参数在服务的覆盖配置中管理并纳入版本记录。第三，留存性能证据：重大性能故障保留 perf 采样文件、进程快照与同一时段的监控截图，归档周期在故障管理制度中写明。第四，泄漏类问题建台账：每个疑似泄漏服务记录增长速率、重启周期与版本对应关系，版本发布后重点观察曲线是否改变，用数据推动开发侧修复。第五，交换空间要有预案：交换分区大小与使用倾向参数按机器角色设置，数据库类机器与应用类机器分别管理，参数变更写入系统配置文件并记录原因。第六，定期做性能巡检：每月按本章顺序对核心机器跑一遍全局指标与服务归类检查，把缓慢增长的异常在变成故障之前处理掉。
