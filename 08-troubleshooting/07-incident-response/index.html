    事故响应与取证¶

    一、概述与使用场景¶

    事故响应处理的是「已经出事之后怎么办」：服务中断、性能雪崩、数据异常，尤其是疑似入侵这类安全事件。它与日常排障的区别在于三点：有明确的响应时限与升级机制，所有动作要留时间线与证据，处置过程本身不能破坏后续追责与复盘所需的现场。本章给出一套可直接套用的流程与模板：分级、宣告、止血、取证、根因、恢复、复盘，并把每个环节的最小动作定死，避免现场忙乱时各凭经验发挥。

    与本部分第 05 章 灾难恢复与系统迁移 分工明确：那边讲系统与数据怎么恢复，本章讲事故全程的响应组织与取证保全。恢复动作本身按第 05 章执行，本章负责在恢复之前把级别定对、把现场保住、把时间线记全，恢复之后把验证与复盘做完。

    适用场景包括：核心服务不可用或大面积报错；数据库数据异常、误删或疑似被篡改；发现异常登录、可疑账号、陌生进程或计划任务等入侵迹象；云厂商或监控平台通报主机在外发垃圾流量、挖矿或被植入后门。无论最终查明是误报、故障还是真入侵，前期动作都按本章流程走，降级比升级容易。

    二、环境准备与前置条件¶

    事故随时可能发生，以下条件要在平时落实，出事时再补就来不及：

    • 值班与升级路径明确：谁是第一响应人、谁有权宣布事故与批准止血动作、什么级别通知到哪一层管理者，写成一页纸放在值班群与离线介质上。
    • 通道可用：云厂商控制台、串口与带外管理的登录方式定期实测，方法与分级路线见本部分第 06 章；证据存放位置预先准备一块不与业务共用的磁盘或存储空间。
    • 时钟可信：全网机器时间已按第 04 部分 时间同步与系统日志 对齐，时间线与跨机器日志对齐才有意义，时钟不一致时先在记录中注明各机偏差。
    • 模板就位：时间线表格与复盘骨架提前存入团队文档库，事故中直接复制使用。

    先保全再处置：改配置、停服务、隔离主机之前

    本章的止血动作（改 sshd 配置、停用账号、改防火墙、断网隔离、重启服务）大多会改变或销毁现场。执行任何一项之前，先按 3.4 节完成最小保全：创建云快照或记录主机状态、导出关键日志到证据目录、拍下控制台与监控画面。无法先保全的情况（例如攻击正在持续扩散）要在时间线中写明原因与跳过项，事后在复盘中单独评价。改任何配置文件之前，另把原文件复制一份带时间戳的备份，这是全站的通用要求，本章同样适用。

    三、手把手操作步骤¶

    3.1 事故分级¶

    分级决定响应速度、通报范围与谁来做决定，先定级再动手，级别可随信息增多随时升降。下面的时限是示例值，组织应按自身业务调整后写进预案，不要直接把示例当承诺。

    级别 影响面示例 首次响应时限示例 处置要求示例
    SEV1 核心业务全面不可用、确认数据泄露或被篡改、大面积用户受影响 15 分钟内 立即宣告事故，管理层与业务方同步通报，连续处置直到恢复，事后必须复盘
    SEV2 核心功能部分受损、单点服务不可用但有降级方案、疑似入侵待确认 30 分钟内 值班负责人牵头处置，定时通报进展，事后必须复盘
    SEV3 非核心功能异常、单机故障不影响业务、已排除入侵的普通故障 1 个工作日内 按普通工单处理，记录时间线，复盘视情况决定

    判读原则：影响面拿不准时先按高一级定，确认可控后再降级；只要出现入侵迹象，无论业务影响大小，至少定为 SEV2，因为取证与凭据轮换的动作等级已经超出普通故障处理。

    3.2 响应总流程：止血优先，但先做最小保全¶

    总流程六步，顺序不可跳：确认与宣告、止血、取证保全、根因分析、恢复、复盘。确认与宣告是把事故从「有人在群里喊了一声」变成「有负责人、有级别、有时间线在记」的正式状态，宣告内容包括级别、影响范围、响应负责人与通报节奏。止血是让损失停止扩大的动作：回滚刚发布的变更、摘除异常节点、停用被盗账号、隔离受感染主机。取证保全在止血之后、根因之前集中做一轮，内容见 3.4 节。根因分析只基于保全下来的证据下结论，不基于猜测宣布原因。恢复按第 05 章流程执行并过 3.7 节清单。复盘在恢复后约定的时间内完成，模板见 3.8 节。

    这里有一对必须讲清的取舍：止血优先，但止血动作会破坏现场。 重启服务会清掉内存中的异常进程状态，改配置会覆盖被篡改的原文件，断网隔离会中断正在进行的连接与外传流量里的取证线索。正确顺序不是「先取证完再止血」，业务损失不等人；也不是「先止血、证据以后再说」，很多证据只有一次机会。落地做法是止血前花几分钟做最小保全，只做三件事：第一，能创建云快照的主机先打快照，不能打的记录当前时间与主机状态；第二，把 3.4 节清单中的关键日志先导出到证据目录；第三，把要改动的配置文件先复制备份。做完这三件再执行止血，并在时间线中注明哪些保全已做、哪些因紧急跳过。

    3.3 时间线记录规范¶

    时间线是事故的黑匣子：复盘、定责、保险与法务沟通都以它为准。记录规范只有四条：一是统一时钟，所有时间一律用北京时间（CST，UTC+8）记录，并注明来源机器的时钟是否已同步，未同步的机器日志时间要换算后再引用，时间同步的配置方法见第 04 部分 时间同步与系统日志；二是当时就记，不要事后凭记忆补，补记的条目要标注为补记并写明补记时间；三是每条包含时间、动作、执行人、结果四个要素，动作写具体命令或操作，结果写观察到的现象而不是推测；四是时间线由专人维护，其他人提供信息不直接改表，避免多版本互相覆盖。

    事故开始时直接复制下面这张表开记，示例行按实际删除：

    时间（北京时间） 动作 执行人 结果 证据或备注
    2026-10-21 14:03 收到监控告警：web-srv-01 的 443 端口探测失败 值班工程师 确认外部访问返回 502，宣布 SEV2 告警截图存证据目录
    2026-10-21 14:07 在云控制台创建 web-srv-01 系统盘快照 值班工程师 快照创建成功 快照编号记入事故单
    2026-10-21 14:12 导出 journal 与 auth.log 到证据目录并计算哈希 值班工程师 导出完成，哈希已留档 见证据清单

    3.4 证据保全：日志、只读镜像与哈希¶

    证据保全的目标是：事故结束后，任何结论都能回到原始材料上验证。保全分三层：先导日志，再按需做磁盘镜像，最后统一算哈希并登记保管。

    关键日志清单与导出方法如下，先建证据目录，再逐项导出，目录名用事故开始时间，放在不与业务共用的磁盘或挂载点上：

    sudo mkdir -p /mnt/evidence/incident-20261021-1403
sudo journalctl -b -0 --no-pager | sudo tee /mnt/evidence/incident-20261021-1403/journal.txt > /dev/null
sudo cp /var/log/auth.log /mnt/evidence/incident-20261021-1403/auth.log
sudo dmesg -T | sudo tee /mnt/evidence/incident-20261021-1403/dmesg.txt > /dev/null
ps auxf | sudo tee /mnt/evidence/incident-20261021-1403/ps.txt > /dev/null
ss -tulnp | sudo tee /mnt/evidence/incident-20261021-1403/ss.txt > /dev/null
ls -lh /mnt/evidence/incident-20261021-1403

    清单逐项说明：auth.log 记录登录、sudo 与密钥使用，是入侵类事故的第一证据；journal 覆盖 systemd 与多数服务的结构化日志，用 journalctl 按时间范围导出，不要直接拷二进制 journal 文件；dmesg 反映内核与硬件层异常；进程与端口快照记录导出时刻的运行状态。应用日志按业务补充：Web 访问日志、数据库日志与云厂商的操作审计日志都要导，云侧日志从控制台导出，不要只依赖主机上的副本，主机被入侵时其上的日志可能已被清理。导出后立即转只读保存，分析时用副本，原件不再写入。

    怀疑磁盘内容被篡改或需要完整取证时，再做磁盘只读镜像。镜像必须在源盘停止写入的状态下做：云主机用快照导出，物理机从 Live 介质或救援环境启动后对未挂载的源盘操作，不要在源系统运行中镜像其系统盘。

    dd 做镜像的四条红线

    第一，目标绝不能写错：dd 的输出文件必须落在证据盘上，源盘与目标盘写反会把证据盘的内容覆盖到源盘上，事故变二次事故，执行前用 lsblk 逐字核对设备名与容量。第二，绝不对原盘写入：镜像过程对源盘只有读操作，任何修复、挂载读写、文件系统检查都不能在原盘上做，需要分析时用镜像或镜像的副本。第三，能只读就只读：源盘先设为只读或以只读方式挂载查看，云快照要在控制台确认创建完成后再导出。第四，dd 没有进度回滚一说，中途参数写错只能停下重来，命令下发前把完整命令读一遍再执行。

    镜像与哈希留档命令如下，设备名与路径按现场实际值替换，示例中的 /dev/sdb 是待取证盘，/mnt/evidence 是证据盘挂载点：

    lsblk
sudo dd if=/dev/sdb of=/mnt/evidence/incident-20261021-1403/disk-sdb.img bs=4M status=progress conv=noerror,sync
sudo sha256sum /mnt/evidence/incident-20261021-1403/disk-sdb.img | sudo tee /mnt/evidence/incident-20261021-1403/disk-sdb.img.sha256
sudo sha256sum /mnt/evidence/incident-20261021-1403/journal.txt /mnt/evidence/incident-20261021-1403/auth.log
ls -lh /mnt/evidence/incident-20261021-1403

    conv=noerror,sync 让读到坏块时不中断并以填充方式对齐，适合已有损伤的盘；镜像完成后第一时间算 sha256 并留档，之后每次移交或复制镜像后都重算比对，哈希不一致说明副本已不可信。证据保管链只记一条原则：每份证据在任何时刻都能说清「谁、何时、从哪台机器、以什么方式取得，现在存在哪里，哈希是多少」，说不清交接过程的证据不作为结论依据。 把这条信息随证据清单一起保存，清单本身也纳入时间线附件。

    3.5 入侵处置：隔离取舍与后门排查¶

    确认或高度怀疑入侵时，第一个决策是隔离方式，这里同样有取舍。拔网线或在云安全组断网能立即切断攻击者的控制与外传通道，止损最快，代价是内存中的进程、连接与解密密钥等易失证据随断电或进程结束而消失，且若机器随后关机，内存取证就再无机会。更稳妥的顺序是：在控制台先按 3.4 节做最小保全与内存侧快照（进程、连接、登录会话），再断网隔离，最后才考虑关机或重装。例外只有一种：数据正在持续外传或破坏正在扩大时，先断网止损，证据损失在时间线中如实记录。隔离优先用云安全组或防火墙规则实现而不是拔线，这样机器保持开机、磁盘与内存现场还在，且隔离动作本身有云侧审计记录。

    隔离后按清单排查后门，切入点固定为四类，不要漫无目的地翻文件：

    getent passwd
sudo ls -la /root/.ssh
ls -la /home
crontab -l
sudo crontab -l
ls -lt /etc/cron.d
systemctl list-timers --all
ls -lt /etc/systemd/system
sudo sshd -T | grep -iE "permitrootlogin|passwordauthentication|authorizedkeysfile"
last -a | head -n 30

    逐项判读：账号类，看 getent passwd 里有没有陌生账号、有没有本应禁用的账号被启用、陌生账号的家目录与登录 shell 是否正常，并核对各账号 .ssh/authorized_keys 里有没有不认识的公钥；计划任务类，看用户与 root 的 crontab、/etc/cron.d 与 systemd 定时器里有没有近期新增或名称伪装的条目；配置类，把 /etc/ssh/sshd_config 与变更记录或备份逐项核对，重点看允许 root 登录、密码认证、密钥文件路径等开关有没有被改动，sshd 的安全基线见第 02 部分 SSH 安全加固；登录记录类，用 last 与 auth.log 对照陌生来源的成功登录时间，与时间线互相印证。查到的每一项都先记录再处置：记录文件路径、修改时间与内容摘要，然后才删除或停用，不要先删后记，否则根因分析会失去对象。宁可多隔离一轮，也不要急着恢复没查清的主机。

    3.6 全量凭据轮换¶

    入侵确认后，凡是可能在该主机上出现过的凭据，一律按已泄露处理，全部轮换，不逐个评估「这个应该没事」。轮换清单如下，逐项执行并在时间线中登记完成时间：

    • 系统账号口令：本机所有可登录账号的口令重置，确认入侵入口的账号先停用后重置。
    • SSH 密钥：删除各账号 authorized_keys 中的旧公钥，只放入重新生成的密钥对的公钥；私钥曾存放在该主机上的，按已泄露处理并在所有使用它的机器上同步更换。
    • 数据库密码：应用连接串、备份脚本与监控探针里用到的数据库账号全部改密并同步更新引用处。
    • API Key 与访问令牌：云厂商、对象存储、第三方服务在本机配置过的 Key 全部吊销重发。
    • 证书与私钥：本机存放过私钥的 TLS 证书按已泄露处理，重新签发并替换，私钥文件不再复用。

    轮换的操作规范见第 02 部分本期同批新增的 秘密信息管理，证书的签发、部署与到期管理见 证书生命周期管理，本章只定轮换范围与顺序：先吊销旧凭据再发放新凭据的顺序只适用于能短暂中断的场景，业务不能断时先发新凭据、切换引用、验证通过后再吊销旧的，顺序写进时间线。

    3.7 恢复验证清单¶

    恢复动作按第 05 章执行，恢复完成的宣布权在本节清单：四类逐项确认，全部通过并留记录后，才对外宣布恢复。只重启成功、进程在跑，不算恢复。

    • [ ] 服务类：关键服务状态正常，systemctl --failed 为零，本机与外部访问各测一次核心接口与登录流程
    • [ ] 数据类：关键表与目录做计数与抽查，与备份或业务方确认的基准值对得上，恢复点时间已明确写入时间线
    • [ ] 监控类：监控采集恢复上报，告警链路实测可达，隔离期间积压的告警已逐条确认处置
    • [ ] 日志类：各服务日志恢复正常写入，日志转发与归档链路通畅，事故时段日志已按 3.4 节归档完毕

    入侵类事故在此之上再加两项：后门排查清单已逐项关闭，凭据轮换清单已全部完成并登记。任何一项未过，事故保持未关闭状态，宁可延长隔离与降级运行，也不要带着未确认项恢复全量服务。

    四、效果验证与测试¶

    本章流程的有效性用一次完整演练或一次真实事故的收尾数据验证，核对命令与判读如下，证据目录路径按实际事故替换：

    ls -lh /mnt/evidence/incident-20261021-1403
sudo sha256sum -c /mnt/evidence/incident-20261021-1403/disk-sdb.img.sha256
systemctl --failed
timedatectl

    期望输出与判读：证据目录中日志、快照与镜像文件齐全且大小大于零；sha256sum -c 对镜像校验返回 OK，说明证据副本未被改动；systemctl --failed 为零个失败单元；timedatectl 显示时钟已同步，时间线的时间基准可信。再人工核对三项：时间线从告警到关闭无断档、恢复验证清单四类全部勾选、复盘改进项每项都有负责人与期限。三组都过，本章流程才算在该事故上闭环。

    五、常见错误与排坑指南¶

    场景一：发现异常后先重启服务「恢复业务」，重启完再想起来取证。 根因是把止血与保全当成二选一。内存中的异常进程、连接与未落盘日志在重启后永久消失，根因只能靠猜。修复：按 3.2 节的最小保全先做快照与日志导出，三件事几分钟可以做完，再执行重启等止血动作；已经重启的，在时间线中如实注明证据缺口，结论中不写无法证明的根因。

    场景二：几个人在不同机器上各查各的，时间线对不起来。 根因是时钟未统一且记录分散在聊天记录与个人笔记里。修复：宣告事故时指定专人维护唯一一份时间线并统一用北京时间，引用未同步机器的日志时先注明偏差再换算，平时按第 04 部分把全网时间同步落实到位。

    场景三：做磁盘镜像时把源盘与目标盘写反。 根因是深夜疲劳下只看设备名不核对容量与挂载点。修复：执行 dd 前用 lsblk 把源盘与证据盘的设备名、容量、序列信息逐项念出来与工单核对，源盘全程只读，镜像完成后先验哈希再做任何分析，全程遵循 3.4 节的四条红线。

    场景四：入侵处置只删了看得见的异常文件，没有轮换凭据就恢复上线。 根因是把后门等同于文件，忽略了攻击者可能已经拿走密钥与口令。修复：按 3.5 节四类切入点查全，按 3.6 节清单全量轮换并登记，两份清单都关闭后才允许恢复，恢复验证按 3.7 节再加这两项确认。

    场景五：复盘写成情况说明，改进项没有负责人与期限。 根因是复盘目标定成了「交代清楚」而不是「关掉缺口」。修复：直接套用 3.8 节骨架，改进项表格四列填满才算成文，并在下一次演练中回验关闭情况，未关闭的改进项在事故系统中持续挂账。

    六、生产环境最佳实践与安全建议¶

    第一，预案先于事故：分级标准、升级路径、最小保全动作与模板在平时定版并演练，SEV1 与 SEV2 至少每半年做一次桌面推演或实机演练，演练记录按真实事故同等标准留存。第二，证据意识先于处置速度：值班考核中把「先保全再动手」作为硬要求，监控与日志的保留周期要覆盖最常见的事后发现窗口，云侧审计日志单独开启并防止被主机侧权限删除。第三，凭据管理日常化：秘密集中存放、定期轮换与最小授权按第 02 部分 秘密信息管理 落实，日常做得好，事故时的全量轮换才有清单可依、有记录可查。第四，隔离能力预先打通：云安全组隔离、快照与救援模式的权限提前授予值班角色并实测，不要在事故中临时走审批。第五，复盘改进项纳入正式跟踪：每项改进有负责人、期限与验证方式，未关闭项定期回顾，同一根因出现第二次时，先复盘上一次的改进项为什么没有拦住它。
