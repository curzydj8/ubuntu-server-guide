    网络不通、高延时与丢包排查流程¶

    一、概述与使用场景¶

    网络故障的表现非常宽泛：整机连不上、某个服务端口不通、域名解析失败、访问时快时慢、延时从几毫秒涨到几百毫秒、持续丢包导致远程桌面卡顿与接口超时。初学者最容易犯的错误是跳过基础层直接怀疑应用或防火墙，结果在上层反复改配置，真正的故障点例如网关写错、网线松动、路径 MTU 不一致却一直未被检查。

    本章采用分层排查法，顺序固定为：物理与链路层、IP 地址层、路由层、DNS 层、端口与传输层、应用层。每一层都有明确的通过判据，上一层未确认通过就不进入下一层。这样做的好处是结论可复现：任何人按同一顺序复查，都能得到相同的定位结果，交接班时也不会丢失上下文。

    本章示例统一使用文档专用地址段：服务器地址为 192.0.2.10，网关为 192.0.2.1，外部测试目标为 198.51.100.20，域名使用 example.com 与 example.org。实际排查时把这些地址替换为本机真实地址即可，命令结构不变。

    延时与丢包类问题与完全不通类问题的处置差异在于：完全不通先找断点，延时与丢包先量化。用连续 ping 与 mtr 先测出丢包率、延时分布与抖动，再判断是本机、局域网、运营商路径还是对端的问题，避免凭单次超时下结论。

    二、环境准备与前置条件¶

    开始排查前确认以下条件：

    • 具有 sudo 权限的账号，能查看网卡、路由、防火墙与抓包。抓包需要 root 权限，普通账号执行 tcpdump 会提示无权限打开网卡。
    • 本机已安装常用工具。Ubuntu 22.04 与 24.04 默认带有 ip、ping、ss、curl、dig 的基础环境，部分工具需要单独安装：
    sudo apt update
sudo apt install -y iputils-ping mtr-tiny tcpdump dnsutils curl iproute2 ethtool
    • 准备对照信息：本机应有的 IP 地址、子网掩码、网关、DNS 服务器，来自网络规划或云厂商控制台；没有对照值时，很多错误配置根本看不出来。
    • 准备两个外部参照目标：一个稳定的 IP 地址目标用来排除 DNS 因素，一个域名目标用来验证完整链路。参照目标应事先确认本身可用。
    • 记录故障时间范围与影响范围：只有本机不通还是同网段多台不通，只有出方向不通还是入方向也不通，这些信息决定排查起点。

    先分清故障方向

    从故障机向外测是出方向，从正常机器向故障机测是入方向。两个方向的结论经常不同：出方向正常而入方向不通，问题多在防火墙、安全组或对端回程路由。排查记录中必须注明每次测试的方向与源地址、目标地址，混在一起的记录事后无法使用。

    三、手把手操作步骤¶

    3.1 物理与链路层：网卡是否存在、链路是否协商成功¶

    ip -br link
ip -br addr
sudo ethtool enp3s0
sudo journalctl -k -b -0 --no-pager | grep -i -E "link|eth|enp"

    判读逐项说明：ip -br link 中目标网卡状态应为 UP，若为 DOWN 先执行 sudo ip link set enp3s0 up 再复查；ethtool 输出中 Link detected: yes 表示物理链路已连接，Speed 与 Duplex 显示实际协商速率，千兆网口只协商到百兆通常是网线或对端端口问题。内核日志中频繁出现 link up 与 link down 交替记录，说明链路在反复抖动，优先更换网线、交换机端口再继续上层排查。虚拟机环境则检查宿主机虚拟交换机与网卡绑定状态，云服务器检查网卡是否被误解绑。

    3.2 IP 层：地址、掩码与邻居是否正确¶

    ip addr show enp3s0
ip route show table main
ip neigh show
ping -c 4 192.0.2.1

    判读逐项说明：ip addr 中地址应为规划值 192.0.2.10/24，掩码写错最典型的现象是同网段可通、跨网段不通，或反过来。ip neigh 显示网关的 MAC 地址与状态，状态为 REACHABLE 或 STALE 属于正常，长期停在 INCOMPLETE 或 FAILED 说明二层无法到达网关，回到 3.1 节查链路或同网段设备。ping 网关四次应全部收到回复且延时在局域网内通常小于数毫秒，网关都不通时不要继续测外网。

    3.3 路由层：默认路由与回程路径¶

    ip route get 198.51.100.20
ip route show default
tracepath -n 198.51.100.20

    ip route get 直接给出访问目标时系统选用的出口网卡、源地址与下一跳，这是判断多网卡、多路由场景下选路是否符合预期的最准方法，期望输出示例：

    198.51.100.20 via 192.0.2.1 dev enp3s0 src 192.0.2.10 uid 1000
    cache

    若输出的源地址或出口与规划不符，问题在路由表：检查是否存在多条默认路由、度量值是否正确、是否存在被脚本写入的错误静态路由。修改路由前先记录原表，临时验证用 ip route replace 并写明恢复方法，确认有效后再写入 Netplan 配置文件 /etc/netplan/50-cloud-init.yaml 或本机实际使用的 Netplan 文件并执行 sudo netplan apply 使其持久化。

    修改路由与网络配置的风险

    在远程会话中修改默认路由、IP 地址或执行 netplan apply，可能立即断开当前连接。生产操作应先通过云控制台或带外管理口保持第二通道，修改前记录原配置内容，修改后在同一窗口内完成连通性验证。没有带外通道时，先用定时回滚命令预留退路，再执行变更。

    3.4 DNS 层：解析是否正确、是否被污染或超时¶

    先绕过 DNS 直测 IP，再测解析，两步对比即可判定问题是否在 DNS：

    ping -c 4 198.51.100.20
dig example.com
dig @192.0.2.53 example.com
resolvectl status
resolvectl query example.com
cat /etc/resolv.conf

    判读逐项说明：dig 输出的 status 应为 NOERROR，ANSWER SECTION 中应有地址记录，Query time 过大说明 DNS 服务器响应慢。直接向指定 DNS 服务器查询的结果与默认解析结果不一致，说明本机默认 DNS 配置有问题，按 resolvectl status 中每块网卡的 DNS 列表逐一核对。Ubuntu 服务器版使用 systemd-resolved 时，/etc/resolv.conf 通常指向本地 Stub 解析器，不要直接改这个文件，应在 Netplan 或 /etc/systemd/resolved.conf 中修改上游 DNS 后重启 systemd-resolved 服务。

    3.5 端口与传输层：服务是否监听、连接卡在哪一步¶

    ss -tulnp
ss -tn state established
ss -s
curl -v --connect-timeout 5 http://198.51.100.20:8080/
curl -v --connect-timeout 5 http://example.com:8080/
telnet 198.51.100.20 8080

    判读逐项说明：ss -tulnp 需要 sudo 才能显示进程名，目标端口应处于 LISTEN 状态且监听地址符合预期，监听在 127.0.0.1 的服务只能本机访问，对外不通是必然结果而不是防火墙问题。curl -v 的输出按阶段判读：卡在域名解析阶段是 DNS 问题，卡在尝试连接且超时多为路由、防火墙或对端未监听，连接已建立但长时间无响应则是应用处理慢。用 IP 与用域名各测一次，两次结果不同即可把范围缩小到解析环节。

    3.6 用 ping 与 mtr 量化延时与丢包¶

    ping -c 100 -i 0.2 198.51.100.20
mtr --report --report-wide --no-dns 198.51.100.20
mtr --report --report-wide example.com

    判读逐项说明：ping 汇总行给出丢包率与最小、平均、最大延时，平均延时正常但最大值远高于平均值说明存在抖动，常见于链路拥塞或无线链路干扰。mtr 报告逐跳列出丢包率与延时，判读规则只有两条：某一跳开始丢包且后续每一跳都丢，故障点在该跳或其后链路；只有中间某一跳丢包而最后一跳不丢，是中间设备限制了探测报文速率，不是真实故障。最终结论以最后一跳的数据为准。

    3.7 用 tcpdump 抓包确认报文去向¶

    当上层工具结论矛盾时，抓包给出最终证据。先在故障机抓与目标之间的往来报文：

    sudo tcpdump -i enp3s0 -nn host 198.51.100.20 and port 8080 -c 50
sudo tcpdump -i any -nn icmp -c 50
sudo tcpdump -i enp3s0 -nn -w /tmp/network-capture.pcap host 198.51.100.20

    判读逐项说明：只有出方向报文没有回包，说明请求已发出但被中间设备丢弃或对端未回复，去对端或防火墙上继续抓；出入报文都有但应用仍报错，问题在应用层内容而不是连通性；出现大量重传报文，对应延时与丢包问题，多为链路质量或 MTU 问题。抓包文件保存后可用 Wireshark 在本地打开分析，抓包时限定主机与端口条件，避免把无关流量与敏感内容写入文件。

    3.8 MTU 不一致的典型坑与验证方法¶

    MTU 问题最典型的现象是：小包全通、大包卡死。表现为 ping 正常、网页能打开但加载不全、文件传输到固定位置停滞、某些接口小请求正常而大响应超时。验证命令如下：

    ping -c 4 -M do -s 1472 192.0.2.1
ping -c 4 -M do -s 1400 192.0.2.1
ip link show enp3s0

    -M do 表示禁止分片，-s 1472 加上报文头共 1500 字节。若 1472 失败而 1400 成功，说明路径实际 MTU 小于 1500，隧道、PPPoE 与部分 VPN 场景常见此问题。处置方法是从大到小二分测出最大可用值，把网卡 MTU 或对应路由的 MTU 设置为测得值加 28 字节头开销对应的载荷上限，并在 Netplan 中持久化。修改前记录原 MTU，修改命令为：

    sudo ip link set dev enp3s0 mtu 1400
ip link show enp3s0

    临时修改立即生效用于验证，验证通过后写入 Netplan 配置的 mtu 字段，再执行 sudo netplan apply 并复测大包连通性。

    四、效果验证与测试¶

    修复后按层回测并记录数值，不能只凭感觉判断恢复：

    ping -c 20 192.0.2.1
ping -c 100 -i 0.2 198.51.100.20
mtr --report --report-wide --no-dns 198.51.100.20
dig example.com
curl -o /dev/null -s -w "%{http_code} %{time_total}\n" http://example.com/
ss -tulnp

    期望输出示例：

    100 packets transmitted, 100 received, 0% packet loss, time 19852ms
rtt min/avg/max/mdev = 18.204/19.631/24.908/1.112 ms
200 0.183

    判读标准：网关与外部目标丢包率均为零，平均延时回到故障前基线范围，curl 返回预期状态码且总耗时正常，目标端口保持监听。延时类故障还需在业务高峰时段复测一次，因为拥塞类问题在低峰期可能完全消失。高峰复测结果一并写入故障记录。

    五、常见错误与排坑指南¶

    错误一：只 ping 域名就判定网络不通。 现象是 ping 域名提示名称解析失败，便直接去改路由与防火墙。原因多为把 DNS 故障误判成链路故障。正确做法是永远先 ping IP 地址再 ping 域名，两步结果一对比就能分清是解析问题还是连通问题，顺序不可颠倒。

    错误二：看到 mtr 中间跳丢包就断定运营商链路故障。 现象是报告中段某跳丢包率很高，便向运营商报障。原因是中间路由器常对探测报文限速，中间跳丢包而最后一跳正常并不代表转发丢包。正确做法是只以最后一跳的丢包与延时为判据，必要时用双向 mtr 与持续 ping 交叉验证后再报障。

    错误三：在远程会话中直接改 IP 或默认路由且不留退路。 现象是命令执行后会话中断，机器彻底失联，只能去机房或找云厂商救援。原因是网络变更对当前连接立即生效。正确做法是变更前准备带外通道、备份原配置、用临时命令先验证再持久化，关键生产机变更安排在有现场支持的时段执行。

    六、生产环境最佳实践与安全建议¶

    第一，建立基线：记录每台服务器正常状态下的网关延时、外部延时、丢包率与常用端口清单，故障时有对照才能量化影响。第二，部署持续监测：用监控系统对网关、外部目标与关键端口做分钟级探测并告警，丢包率与延时设置分级阈值，避免用户先于运维发现故障。第三，配置变更走流程：IP、路由、DNS、MTU 的变更全部写入 Netplan 等配置文件并纳入版本管理，禁止只用临时命令改完就结束，重启后配置丢失是反复出现的同类故障源头。第四，抓包注意合规：抓包文件可能包含业务数据与敏感内容，只抓定位所需的最小流量，文件加密保存、限定访问人员，问题关闭后及时销毁。第五，准备应急预案：写明运营商报障电话与所需信息、云厂商工单入口、备用线路切换步骤，每半年做一次切换演练并更新文档。第六，保留排查记录模板：源地址、目标地址、方向、每层测试命令与结果、最终故障点、修复动作六项固定填写，积累成册后同类故障的定位时间会明显缩短。
