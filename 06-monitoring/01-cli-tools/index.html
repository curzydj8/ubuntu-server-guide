    命令行即时监控工具¶

    一、概述与使用场景¶

    命令行监控工具解决的是一个问题：服务器变慢或无响应时，在不安装任何重型系统的前提下，用最短时间判断瓶颈出在 CPU、内存、磁盘还是网络。它们不需要数据库，不需要 Web 界面，SSH 登录后敲一条命令就能看，是所有运维工作的第一现场。

    典型使用场景有四类。第一类是故障定位：用户反馈网站打开慢，先用 htop 看负载与进程占用，再用 iotop 看是不是某个进程在狂写磁盘。第二类是日常巡检：每天登录后扫一眼 btop 的全景图，确认资源水位正常。第三类是容量判断：扩容前先用历史采样确认到底缺的是内存还是磁盘吞吐。第四类是变更验收：上线新服务后观察一段时间，确认新进程的资源占用符合预期。

    不配这些工具的风险很直接：只能靠猜。没有进程级视角时，一个失控的日志狂写进程可以把磁盘 IO 打满，进而拖慢整机所有服务，而表面症状却像网络故障或数据库故障，排查方向全错。另一个常见瓶颈是内存：Linux 会把空闲内存用作缓存，free 命令的输出常被误读为内存不足，htop 对内存构成的拆分展示可以避免这类误判。把本章工具练熟，后续 Prometheus 体系负责长期趋势，命令行工具负责当下这一分钟，两者分工明确。

    工具分工

    即时定位用本章工具，趋势与告警用第 2 章的 Prometheus。不要用命令行工具代替长期监控，也不要在故障现场等 Grafana 曲线刷新来做判断。

    二、环境准备与前置条件¶

    • 操作系统：Ubuntu Server 22.04 LTS 或 24.04 LTS。
    • 权限：普通用户 ubuntu 即可运行大部分工具；iotop、iftop 需要 root 权限或 CAP_NET_ADMIN 与 CAP_SYS_PTRACE 能力，本章统一用 sudo 执行。
    • 网络：需要能访问 Ubuntu 软件源以下载安装包。
    • 终端：建议终端宽度不小于 120 列，btop 与 glances 的全景界面在窄终端下会折叠部分面板。
    • 依赖：无额外依赖，六个工具均可通过 apt 直接安装，其中 glances 基于 Python，安装体积相对较大。

    先更新软件源索引并确认系统版本：

    lsb_release -a
sudo apt update

    期望看到 Description 一行为 Ubuntu 22.04 或 Ubuntu 24.04 字样。若系统版本不在此范围，本章命令大体仍可使用，但个别工具的默认界面与快捷键可能不同。

    三、手把手操作步骤¶

    3.1 一次性安装全部工具¶

    sudo apt install -y htop btop glances iotop iftop nload

    各工具定位如下表：

    工具 主要维度 启动命令 是否需要 sudo
    htop CPU 与内存与进程 htop 否
    btop CPU 与内存与磁盘与网络全景 btop 否
    glances 全维度加历史与导出 glances 否
    iotop 进程级磁盘读写 sudo iotop 是
    iftop 网卡级实时流量与对端 sudo iftop 是
    nload 网卡吞吐曲线 nload 否

    3.2 htop：进程视角的基本功¶

    直接运行：

    htop

    界面分三区。顶部是 CPU 核心条：每个核心一条，绿色为普通用户进程，红色为内核进程，蓝色为低优先级进程。内存条分三段颜色：绿色为已用内存，蓝色为缓冲区，黄色为页缓存。Swap 条单独一行，非零且持续增长说明物理内存确实吃紧。

    进程列表关键列含义：

    列名 含义 判读方法
    PID 进程号 后续 kill 与 renice 时使用
    USER 运行用户 确认进程归属，避免误杀系统进程
    CPU% CPU 占用百分比 多核机器上单进程可超过 100
    MEM% 物理内存占用百分比 结合 RES 列看真实占用
    RES 常驻物理内存 判断内存大户以此列为准
    TIME+ 累计 CPU 时间 异常偏大说明长期高消耗
    Command 完整命令 按 M 按内存排序后逐个核对

    常用操作：按 P 按 CPU 排序，按 M 按内存排序，按 T 按累计时间排序，按 F5 切换树状视图看父子关系，按 F9 结束选中进程，按 F7 与 F8 调整 nice 值。顶部 Load average 三个数值分别对应过去 1 分钟、5 分钟、15 分钟的平均可运行队列长度，经验上持续高于 CPU 核心数即表示 CPU 排队。

    实战场景：网站变慢时先按 M 排序，若某个进程 RES 远超预期且 Swap 已启用，基本可判定为内存瓶颈；再切回按 P 排序确认 CPU 侧是否同时打满。

    3.3 btop：单屏全景巡检¶

    btop

    btop 用一块屏幕同时展示 CPU、内存、磁盘、网络与进程，适合巡检与大屏值守。CPU 区显示每核心占用与温度（传感器可用时）；内存区区分已用、缓存、可用三部分，并列出各挂载点磁盘使用率；网络区显示上下行实时速率与累计流量；进程区支持搜索与过滤。

    常用按键：按 Esc 打开菜单切换主题与刷新间隔，按 f 输入关键字过滤进程，按 e 切换进程树。默认刷新较快，CPU 开销稍高于 htop，老旧机器上可把刷新间隔调到 2000 毫秒以上。

    实战场景：新服务上线后开着 btop 观察十分钟，网络、磁盘、内存三条曲线平稳且无 Swap 增长，即可初步判定上线成功。

    3.4 glances：跨平台与可导出¶

    glances

    glances 按颜色给出健康判断：绿色正常，蓝色注意，紫色警告，红色严重。顶部依次是 CPU、内存、Swap、负载；左侧是网络、磁盘、文件系统；右侧与下方是进程列表。它会直接标出瓶颈项，例如 CPU 一行出现 CARE 或 WARNING 标记时，右侧会提示主要消耗来源。

    常用按键：按 a 自动按瓶颈排序进程，按 c 按 CPU 排序，按 m 按内存排序，按 i 按 IO 排序，按 q 退出。需要留档时可以导出为 CSV：

    glances --export csv --export-csv-file /tmp/glances.csv --time 5

    该命令每 5 秒采样一次并写入文件，按 Ctrl 加 C 停止。采样文件适合在容量评估时做离线分析。

    3.5 iotop：抓磁盘狂写进程¶

    sudo iotop -o -P

    参数说明：-o 只显示正在发生 IO 的进程，避免满屏零值干扰；-P 按进程聚合而不是按线程展示。关键列为 DISK READ、DISK WRITE 与 IO 百分比。IO 百分比表示该进程让磁盘等待的时间占比，单进程接近 100 且整机变慢时，它就是元凶。

    只看总量不够时去掉 -o 查看全部进程，再按左右方向键切换排序列。常见元凶包括失控的日志写入、正在跑全表扫描的数据库、以及定时备份任务与业务高峰重叠。

    3.6 iftop 与 nload：网络维度¶

    iftop 看谁在通信：

    sudo iftop -i ens3 -n -P

    网卡名 ens3 需按本机实际修改，可用 ip link 查看。-n 表示不解析主机名，直接看 IP，速度更快；-P 表示显示端口。界面每行是一个连接对，右侧三列分别是最近 2 秒、10 秒、40 秒的平均速率，顶部横条是总带宽标尺。示例对端地址形如 198.51.100.25，发现流量集中到某个陌生对端时，结合端口即可判断是备份传输、更新下载还是异常外连。

    nload 看吞吐曲线：

    nload ens3

    nload 以字符曲线展示入站与出站速率，并给出当前值、平均值、最小值、最大值与累计流量。判断带宽是否打满时看 Curr 与 Max 的关系：Curr 长期贴近线路上限且业务变慢，才需要考虑升级带宽；只是偶发尖峰则属于正常突发。

    3.7 组合排障流程示例¶

    以目标主机 192.0.2.10 上的 Web 服务变慢为例，固定顺序如下：

    uptime
htop
sudo iotop -o -P
free -h
df -h
sudo iftop -i ens3 -n -P

    判读顺序：先看 uptime 的负载是否超过核心数；再在 htop 中确认是单个进程打满还是整体吃紧；然后用 iotop 排除磁盘因素；free -h 中重点看 available 列而不是 free 列，available 才是可回收后真正可用的内存；df -h 确认磁盘空间未满，空间满同样会表现为全站变慢；最后用 iftop 确认流量形态。六步走完，瓶颈维度基本可以锁定。

    结束进程前先确认归属

    在 htop 或 btop 中结束进程前，必须核对 USER 与 Command 两列，并先用 systemctl status 确认它对应的服务与重启方法。对数据库与队列类进程直接 kill 可能造成数据损坏，应优先用 systemctl stop 走正常停止流程。

    htop --version

    期望输出示例（版本号以撰写时 Ubuntu 软件源提供的版本为准，此处只示意格式）：

    htop 3.x

iftop 帮助信息正常打印
nload 帮助信息正常打印

    功能验证：

    stress-ng --cpu 2 --timeout 30s

    若未安装 stress-ng，先执行 sudo apt install -y stress-ng。在压力运行期间另开一个终端运行 htop，应看到两个 stress-ng 进程各占满一个核心、Load average 明显上升；30 秒后压力自动结束，数值回落。能完整观察到上升与回落，说明监控链路有效。

    网络验证：在 nload 界面打开的状态下，从另一台机器向 192.0.2.10 传输一个大文件，应看到入站曲线与 Curr 数值同步上升。

    五、常见错误与排坑指南¶

    5.1 iotop 报错权限不足¶

    报错原文片段：

    Netlink error: Operation not permitted

    原因：iotop 需要读取其他进程的 IO 计数，普通用户权限不足。修复方法：使用 sudo 运行，或给当前用户长期授权时仍建议按需提权，不做永久放权。

    sudo iotop -o -P

    5.2 iftop 提示找不到网卡¶

    报错原文片段：

    interface ens3 not found

    原因：网卡名写错，不同云厂商与安装方式下网卡名可能是 eth0、enp1s0 等。修复方法：先列出真实网卡名再替换。

    ip -br link
sudo iftop -i eth0 -n -P

    5.3 btop 或 glances 界面花屏错位¶

    报错现象：边框线条显示为字母或方块，面板重叠。原因：终端的 TERM 类型或字体不支持 Unicode 线条字符，常见于老旧 SSH 客户端。修复方法：切换 TERM 并换用等宽字体后重开终端。

    export TERM=xterm-256color
btop

    若仍错位，在 btop 菜单中关闭 Truecolor 并选用基础主题即可恢复可读性。

    六、生产环境最佳实践与安全建议¶

    第一，工具常驻安装。六个工具合计体积很小，建议在所有服务器的初始化清单中默认装好，故障时再装往往受制于磁盘已满或网络已断。

    第二，提权最小化。iotop 与 iftop 只在排障时用 sudo 短时运行，不要把普通账号加入可无密码执行任意命令的组，也不要给二进制设置 setuid。

    第三，采样留档规范化。需要留证时用 glances 导出 CSV 或用脚本定时保存 top 批处理输出，文件名带日期时间，保留周期与第 3 章的日志保留周期保持一致，避免采样文件本身把磁盘写满。

    top -b -n 1 > /tmp/top-snapshot.txt
vmstat 1 5
iostat -x 1 3

    其中 iostat 来自 sysstat 包，未安装时执行 sudo apt install -y sysstat。vmstat 重点看 r 列排队数与 si、so 两列的换入换出，非零的持续换出说明内存不足已经影响性能。

    第四，阈值要有基线。负载多高算异常取决于本机核心数与平日水位，先记录一周的平日峰值再定阈值，不要照搬他人的经验数字。

    第五，监控账号隔离。巡检使用只读的普通账号即可完成大部分工作，涉及结束进程、调整优先级的操作单独走 sudo 审计，sudo 日志会进入 journal，后续可追溯。

    把排障顺序写成清单

    把 3.7 节的六步顺序保存为值班清单贴在团队文档中。新人按清单执行，既不会漏查磁盘空间这类低级因素，也能在交接时说清已经排除了哪些维度。
