    秘密信息管理¶

    一、概述与使用场景¶

    秘密指一旦被无关的人拿到，就能直接换成访问权的东西：账号口令、API Key、访问令牌、证书私钥、数据库密码都算。它们与普通配置的区别不在格式，而在后果：普通配置泄露顶多暴露系统长什么样，秘密泄露等于把钥匙交出去，对方用合法通道就能进来。本章不讲花哨工具，只讲三件基本功：秘密有哪些、各自放在哪里才算合格、出事与轮换时按什么顺序处置。

    先做分类，不同类的秘密保护重点与轮换方式并不一样：

    类别 例子 特点与保护重点
    账号口令 系统登录口令、应用管理员口令、邮箱口令 人要记、要输，重点是强度、唯一性与不在多处复用
    API Key 云服务与 AI 服务的调用密钥、支付接口密钥 机器调用用，重点是权限最小化、按用途拆分、能单独吊销
    访问令牌 个人访问令牌、OAuth 令牌、部署令牌 通常带有效期与授权范围，重点是缩短有效期、到期自动失效
    证书私钥 TLS 私钥、SSH 主机与用户私钥 与证书成对，治理细则见 本部分第 08 章，泄露必须吊销换新
    数据库密码 应用连接数据库的账号密码、备份加密口令 被应用高频读取，重点是落位方式与轮换时不断连接

    事故面由存放方式决定：同一个 API Key，放在 600 专用文件里，事故面是「拿到本机 root 的人」；写死在仓库里，事故面变成「所有能看仓库的人加每一次克隆与备份」；贴在工单里，再加上工单系统的全部可见范围。管理目标就是持续收小事故面，并保证每个秘密能单独轮换、单独吊销。规模不大时分级文件方案就够用，量涨上去再上第 3.4 节的工具。

    AI 工具纪律先说在前面：在 第 13 部分《AI 命令行工具》 场景里，API Key 只通过安全落位交给工具，不要写进提示词、粘进对话或留在命令历史与日志里，它们的留存范围远比你以为的大。

    二、环境准备与前置条件¶

    本章适用于 Ubuntu 22.04 LTS 与 Ubuntu 24.04 LTS，命令按 systemd 官方文档核对，属于「文档核对」级别；Ubuntu 26.04 上的 systemd 凭据行为标记为「待核验」。操作需要带 sudo 的管理账号。本章不要求先装任何专用工具，第 3.1 至 3.3 节只用系统自带的权限与 systemd 能力，第 3.4 节的工具只做概念选型，选定后再按其官方文档单独部署。

    改配置前先备份，秘密文件同样适用，且要求比普通配置更高：备份要保持原权限与属主、存到带日期的受控目录、备份目录本身收紧权限：

    sudo mkdir -p /root/secrets-backup-$(date +%F)
sudo cp -a /etc/myapp /root/secrets-backup-$(date +%F)/myapp
sudo chmod 700 /root/secrets-backup-$(date +%F)
ls -l /root/secrets-backup-$(date +%F)/myapp/

    说明：路径按本机实际服务目录调整。cp -a 保留权限与属主；备份里含明文秘密，敏感程度与源文件相同，不得放进普通网盘同步目录或代码仓库。回滚时从这份备份恢复对应文件，恢复后立刻用第 4 节的 stat 复查权限。处置泄露时先不要急着删旧备份：它可能是判断泄露范围的证据，是否保留按第 3.6 节的应急顺序决定。

    开始前先盘点本机秘密散落在哪些文件里，做到心中有数：

    sudo grep -R -l -i -E "password|api_key|secret|token" /etc/myapp /etc/systemd/system 2>/dev/null
systemctl list-units --type=service --state=running --no-pager

    第一条只列文件名不打印内容，避免把秘密再复制进终端滚动记录与日志。清单里每个文件在第 3 节都要有一个明确落位结论，没有结论的视为待整改项。

    三、手把手操作步骤¶

    3.1 反模式清单：先停掉正在扩散的做法¶

    以下三种做法最常见，也最容易把一次小失误放大成事故，每种都给出替代方向：

    秘密写死在代码与配置文件并提交仓库

    把密码与 Key 直接写进代码、示例配置或脚本并提交到 Git，等于把秘密复制到每一次克隆、每一份备份与仓库的完整历史里，事后删掉当前文件也删不掉历史。已提交过的秘密一律按已泄露处理：先吊销换新，再清理历史，不要反过来。替代做法是代码只写变量名与读取逻辑，真实值由第 3.2 与 3.3 节的落位方式在运行期注入，仓库里只放不含真实值的示例文件。

    秘密打进容器镜像层

    在镜像构建时把密钥文件复制进镜像，镜像推送后任何能拉取的人都能逐层取出，且镜像分发范围通常比服务器大得多。已进镜像层的秘密同样按已泄露处理。替代做法是运行期注入：用编排工具的秘密挂载或 systemd 凭据把文件在容器与服务启动时送进去，构建上下文里不出现真实秘密。

    秘密贴在工单、聊天与文档里

    把口令与 Key 贴进工单、聊天记录与共享文档，看似方便交接，实际是把秘密复制进留存周期最长、可见范围最难控的系统，且之后无法确认谁看过、无法干净回收。临时传递必须走团队批准的一次性或限时分享方式，事后按已扩大可见范围评估是否轮换；长期交接靠落位文件与权限，不靠复制粘贴。

    另有两个隐性反模式：多机多服务共用同一个秘密，出事无法单独吊销与定位；把秘密写进命令行参数，它会出现在进程列表与审计日志里。工具需要秘密时用配置文件、标准输入或凭据文件传。

    3.2 落位方案分级一：配置文件权限 600 与属主隔离¶

    基础级方案适合单机与小规模：秘密集中放在专用配置文件里，权限 600，属主只给需要它的服务账号。这是合格线，不是凑合：做对了，它能挡住同机其他普通账号与无关进程。

    sudo mkdir -p /etc/myapp
sudo nano /etc/myapp/secrets.conf
sudo chown root:myapp /etc/myapp/secrets.conf
sudo chmod 600 /etc/myapp/secrets.conf
stat -c "%a %U %G %n" /etc/myapp/secrets.conf

    文件内容只放键值对，不写注释里的真实旧密码，不把新旧两套值同时留着：

    # /etc/myapp/secrets.conf 仅为格式示例，值均为占位符
DB_PASSWORD=change-me-from-vault-or-manual
API_KEY=example-key-placeholder

    逐段说明：目录 /etc/myapp 与业务普通配置分开，便于单独备份与审计；属组给服务账号是为了让以该账号运行的进程能读，若服务以 root 运行则属主 root、权限 600 即可，不要为了让某个账号能读就把权限放宽到 640 以外或 644。应用侧改为从此文件读取秘密后，立刻从原代码与原配置里删掉明文，并按已扩散范围评估旧值是否需要轮换：曾经进过仓库或镜像的旧值，必须换新，不能只搬家。

    边界要认清：600 文件挡得住普通账号，挡不住 root，也挡不住能读磁盘镜像与备份的人。所以这一级必须配合第 2 节的备份纪律与主机本身的登录控制（见本部分前几章），不要把它宣传成万无一失。

    3.3 落位方案分级二与三：EnvironmentFile 的边界与 LoadCredential 进阶写法¶

    中级方案是用 systemd 的 EnvironmentFile= 把秘密文件交给服务进程。写法是在 unit 里指向第 3.2 节的 600 文件：

    # /etc/systemd/system/myapp.service 片段
[Service]
User=myapp
EnvironmentFile=/etc/myapp/secrets.conf
ExecStart=/opt/myapp/server

    改完执行重载与重启，并验证服务确实读到了变量，这部分命令在第 4 节。必须写清的边界是：环境变量不是保险箱。秘密进入环境后，对同一用户的其他进程与该进程的全部子进程可见；更关键的是，进程的环境可通过 /proc/<pid>/environ 被读到，能读该路径的主体（进程属主本人与 root）可以完整看到里面的秘密值。也就是说，EnvironmentFile= 解决的是「秘密不写死在代码与 unit 里」的落位问题，并没有缩小同用户范围内的可见面。同一账号下还跑着不可信脚本或多人共用该账号时，不要用这一级，直接上 LoadCredential= 或专用工具。另外，不要把秘密直接写在 unit 的 Environment= 行里：unit 文件通常权限宽松且常被贴进排障记录，等于换个地方明文存放。

    进阶方案是 systemd 的 LoadCredential=：systemd 在服务启动时把凭据文件读入，放到只属于该服务的凭据目录里，该目录位于 tmpfs 内存文件系统上，通过环境变量 $CREDENTIALS_DIRECTORY 告诉服务路径。源文件不需要对服务账号可读，服务账号只能看到被递送的那一份；服务停止后凭据目录随之消失，不在磁盘上留副本。unit 片段如下：

    # /etc/systemd/system/myapp.service 片段
[Unit]
Description=MyApp service
After=network-online.target

[Service]
User=myapp
LoadCredential=db-password:/etc/credstore/myapp-db-password
ExecStart=/opt/myapp/server --db-password-file ${CREDENTIALS_DIRECTORY}/db-password
Restart=on-failure

[Install]
WantedBy=multi-user.target

    逐行讲解：

    行 含义
    User=myapp 服务以专用账号运行，凭据目录只对该账号与 root 可见
    LoadCredential=db-password:/etc/credstore/myapp-db-password 冒号前是凭据在本服务内的名字，服务里以此名取文件；冒号后是宿主机上的源文件路径，由 root 管理，源文件本身保持 600
    ExecStart=... ${CREDENTIALS_DIRECTORY}/db-password systemd 把凭据目录路径展开在此变量里，应用按文件路径读秘密，不经环境变量传值本身
    Restart=on-failure 与凭据无关的常规项，列出是为了让片段可直接参考

    应用需要改造为「从文件读秘密」而不是「从环境变量读值」，这是这一级的迁移成本，换来的好处是秘密不进进程环境、不被子进程自动继承、磁盘上只有 root 管理的一份源文件。源文件的准备与权限：

    sudo mkdir -p /etc/credstore
sudo nano /etc/credstore/myapp-db-password
sudo chmod 600 /etc/credstore/myapp-db-password
sudo chown root:root /etc/credstore/myapp-db-password
sudo systemctl daemon-reload
sudo systemctl restart myapp.service

    文件里只放密码值本身一行，不写键名与注释。需要更高保护时 systemd 还提供加密凭据形式，是否启用以官方文档与本机版本为准，本章不展开参数，先把明文源文件加 tmpfs 递送这条主线走通。

    三级方案怎么选，一句话归纳：单服务、能改代码读文件，直接用 LoadCredential=；应用只认环境变量且运行账号可信，用 EnvironmentFile= 并接受其可见边界；暂时改不动应用的，先用 3.2 节的 600 文件兜底并排期改造。三级都不解决跨机器分发与集中审计，那是下一节工具的事。

    3.4 专用工具选型：概念级对比¶

    当秘密数量、机器数量或合规要求涨到文件方案管不过来时，再引入专用工具。三类代表如下，只做概念对比，部署按各自官方文档单独进行，本章不给未经核实的深度安装步骤：

    工具路线 解决什么 适用规模 主要代价
    HashiCorp Vault 集中存储、按身份授权、动态生成短命凭据、完整审计 多服务多机器、需要动态凭据与审计的团队 要独立部署与运维一个高可用服务，解封与备份流程本身就是关键资产
    云厂商 KMS 与 Secrets Manager 托管存储与加解密，与云上身份体系打通 已深度使用某家云、应用主要在云上时 与云厂商绑定，跨云与本地环境要另做衔接，按调用与条数计费
    SOPS 加 age 或 GPG，加密文件进 Git 秘密以密文进仓库，解密密钥在仓库外分发 小团队、配置即代码、秘密量不大时 解决的是存储与分发，运行期仍要把明文安全递给服务；密钥分发与人员离职回收要自建流程

    选型原则：云上重优先云托管，本地与混合环境且有专职运维再评估 Vault，小团队先用 SOPS 消掉「明文进仓库」。任何路线都要能回答：人员离职时如何一次性收回他能解开的全部秘密。

    Vault 开发模式禁用于生产

    Vault 的开发模式以内存存储、自动解封并直接给出高权限令牌的方式启动，官方明确说明它只供本地学习与调试：数据不落盘、通信保护与解封流程都被简化。把它当生产部署省事做法，等于把保险库建在沙地上。生产使用必须走带持久存储、传输加密与正式解封流程的部署，具体步骤以 Vault 官方生产加固文档为准，不要照搬开发模式的命令。

    3.5 凭据轮换流程：通用五步¶

    轮换是计划内的换新，目标是全程不断服务、随时可退回。通用五步对口令、Key、令牌与数据库密码都适用：

    步骤 动作 要点
    1 生成新凭据 在签发方创建新值，旧值保持有效 新旧双凭据并存是过渡前提，不支持并存的系统要单独排维护窗口
    2 更新落位 把新值写进 3.2 至 3.4 节的落位位置 只改落位文件或工具里的值，不改代码；写完用 stat 复查权限未被编辑器重置
    3 切换服务 重启或重载服务，逐台切换，不要全网同时换 每切一台先验证该台业务正常再继续，异常立刻切回旧值
    4 观察 在双凭据并存下观察一个完整业务周期 看错误率、登录与调用失败日志，确认没有遗漏的调用方还在用旧值
    5 吊销旧凭据 在签发方禁用或删除旧值，并更新台账 吊销后复查一次调用是否仍正常；旧值进过仓库的，确认新值从未进仓库

    轮换节奏按风险定：高权限与对外 Key 定期轮换，人员离职与岗位变动时相关秘密立即轮换，疑似泄露不走本流程、直接走下一节应急。每次轮换在台账上记日期、执行人、新凭据标识与旧值吊销确认，不要记明文值本身。

    回滚说明：观察期内回滚是把落位改回旧值并重载，前提是旧值还没吊销，所以顺序不能颠倒。回滚前先查清失败是值本身错误还是调用方没跟上。

    3.6 泄露应急：先止血，再定范围¶

    发现秘密已经泄露或高度疑似泄露时，动作顺序不能乱，复盘与追责都排在止血之后：

    1. 先吊销或冻结泄露的凭据，让已流出的值立刻失效；无法单独吊销的，先在入口侧封禁或改掉它。
    2. 再换新凭据并按 3.5 节的切换方法部署到落位，恢复业务到新值上运行。
    3. 查访问日志定影响面：看泄露窗口内该凭据被谁、在哪些来源、调用了什么，据此判断是否还有其他秘密与数据受牵连。
    4. 扩大处置：同一存放位置的其他秘密若也在泄露范围内，一并轮换，不要只换被实锤的那一个。
    5. 复盘与留痕：记录发现方式、时间线、影响结论与防复发动作，更新台账与巡检项。

    系统层面的入侵排查、证据保全与恢复流程与 第 08 部分《事故响应与取证》 衔接：本节只管凭据这条线，若泄露原因是机器已被入侵，先按那一章保全证据与隔离主机，再在本机之外完成凭据吊销与换新，不要在已失陷的机器上生成并存放新秘密。

    泄露后不要先删日志与现场

    慌乱中重装系统、删日志、清仓库历史，会把判断影响面唯一的证据一起毁掉，还可能让仍有效的旧凭据继续被用。正确顺序永远是先在签发方让旧值失效，这一步不需要动本机现场；证据保全按事故响应章执行，清理动作排在定完影响面之后。

    四、效果验证与测试¶

    验证只看三件事：权限对不对、服务拿秘密的方式对不对、加固后有没有明显短板。第一，查落位文件权限与属主：

    stat -c "%a %U %G %n" /etc/myapp/secrets.conf
stat -c "%a %U %G %n" /etc/credstore/myapp-db-password
sudo grep -R -i -E "password|api_key" /opt/myapp --include="*.py" --include="*.js" --include="*.yaml" 2>/dev/null

    期望：两个秘密文件都是 600 且属主符合 3.2 与 3.3 节的设计；第三条在应用代码目录里期望无明文秘密命中，命中变量名与读取逻辑是正常的，命中真实值则回 3.1 节按已扩散处理。路径按本机实际应用目录调整。

    第二，确认服务状态与凭据递送生效：

    sudo systemctl daemon-reload
sudo systemctl restart myapp.service
systemctl status myapp.service --no-pager
sudo systemctl show myapp.service -p EnvironmentFiles -p Credentials 2>/dev/null || sudo systemctl show myapp.service | head -n 40

    期望：服务为正常运行状态且业务冒烟通过。systemctl show 的可用属性随 systemd 版本而异，命令的意图是核对 unit 实际加载的落位配置与凭据设置，以本机输出为准，不要把某一版本的字段名当作跨版本结论。用 LoadCredential= 的服务，再在应用侧确认它读到的文件路径位于凭据目录且内容可用，不要用打印秘密值的方式验证，日志里出现明文即是一次新的扩散。

    第三，用 systemd-analyze security 做一次整体思路核查：

    systemd-analyze security myapp.service

    期望用法：它按一组加固项逐项评估 unit 并给出汇总，重点看与秘密相关的项，例如服务是否以专用用户运行、文件系统保护是否开启、私有临时目录是否启用。输出是改进清单而不是合格证书：逐项评估与业务的兼容性，能开的补进 unit 并重启验证，不能开的记录原因。本章不预设具体得分与单项结果，不同版本与 unit 写法的输出差异很大。

    五、常见错误与排坑指南¶

    场景一：改完权限 600 后服务起不来，报读不到配置文件。根因是文件属主与服务运行账号不一致：权限收紧本身没错，错在没有同步把属主或属组给到服务账号。修复按落位方式二选一，不要改回 644：

    stat -c "%a %U %G %n" /etc/myapp/secrets.conf
systemctl show myapp.service -p User -p Group
sudo chown root:myapp /etc/myapp/secrets.conf
sudo chmod 600 /etc/myapp/secrets.conf
sudo systemctl restart myapp.service

    先对照服务实际的 User 与 Group 再改属主；用 LoadCredential= 的服务则检查源文件是否可被 root 读取以及凭据名是否写错，这一级不需要源文件对服务账号可读。

    场景二：以为用了 EnvironmentFile= 就万无一失，审计时被指出同账号可读。根因是忽略了环境变量的可见边界：同用户的进程与子进程能继承，/proc/<pid>/environ 对属主与 root 可读。处置不是给环境变量再套一层文件权限，而是升级落位：

    sudo cat /proc/1/environ | tr "\0" "\n" | cut -d= -f1

    这条只列变量名不打印值，用来直观确认环境里确实带着秘密键。确认风险后按 3.3 节迁移到 LoadCredential=，并把「该账号下只跑可信进程」写进该机的运维约束；迁移完成前不要新增往环境里放秘密的服务。

    场景三：轮换后部分调用方报错，误以为新凭据有问题又换了一套。根因多半是调用方不止一处：某台旧机器、某个定时任务或某个同事本地脚本还在用旧值，而旧值已被提前吊销。排查先看签发方或服务端的认证失败日志，按来源定位还在用旧值的调用方：

    sudo journalctl -u myapp.service --since "1 hour ago" --no-pager | grep -i -E "auth|denied|invalid" | tail -n 50

    修复是把遗漏的调用方更新到新值，而不是再生成第三套值让局面更乱。今后轮换严格按 3.5 节顺序执行：观察期结束、确认无旧值调用记录后，才吊销旧值。

    六、生产环境最佳实践与安全建议¶

    第一，一秘密一用途：每个服务、每台机器用独立凭据，禁止全网共用一个高权限 Key，这样轮换与吊销才能单独进行、日志才能定位来源。第二，最小权限签发：API Key 与令牌只给完成工作所需的最小范围与最短有效期，高权限凭据不用于日常调用。第三，台账与巡检：秘密清单只记标识、用途、落位、责任人与轮换日期，不记明文；每月抽查落位文件权限与 unit 写法，发现 644 与明文进代码的新增项当周整改。第四，自动化衔接：落位文件纳入配置管理时必须以密文或引用形式管理，明文只存在于目标机的落位位置与批准的备份里。第五，AI 与自动化工具同守此章：给 AI 工具与脚本的 Key 按用途单独签发、单独落位，不进提示词、不进日志、不进命令参数，细则与 第 13 部分 对照执行。第六，Ubuntu 26.04 的 systemd 凭据行为为「待核验」，升级后先在测试服务上重走第 4 节验证，确认 LoadCredential= 递送与权限表现无变化，再推广到生产服务。
